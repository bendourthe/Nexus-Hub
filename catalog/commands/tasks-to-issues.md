# Tasks to Issues

Convert the strict task checklist in a feature directory's `tasks.md` (or the in-plan task list inside `plan.md`) into linked GitHub issues via the user's local `gh` CLI. The command parses every `- [ ] T### [P?] [US?] ...` line, builds an issue payload (title, body, labels), and either dry-runs the `gh issue create` invocations or executes them sequentially. The command always asks for confirmation before creating issues without `--dry-run`.

This command drives the `[[tasks-to-issues]]` skill end-to-end. The skill body documents the parsing rules; this command file documents the user-facing flow.

## How to Run This Command

- `/tasks-to-issues` -- resolve the active feature directory from `.specify/feature.json` (set by `/generate-plan --specs-layout`); fall back to the most recent plan under `docs/<version>/plans/` if no `.specify/feature.json` exists. Parse `tasks.md` if present, else the task list inside `plan.md`.
- `/tasks-to-issues <feature-dir>` -- explicit feature directory (e.g., `specs/003-user-auth/` or `docs/v2.1.0/plans/`).
- `/tasks-to-issues --dry-run` -- print the `gh issue create` invocations one per task; do not call `gh` at all.
- `/tasks-to-issues --dry-run <feature-dir>` -- combined.

The command is opt-in -- it never runs automatically as part of `/generate-plan` or any post-phase sequence.

## Step 1: Pre-flight checks

1. **`gh` CLI installed and authenticated**. Run `gh auth status`. If the command is missing or exits non-zero, abort with the remediation message: `Install the GitHub CLI from https://cli.github.com and run "gh auth login" before re-trying.`
2. **Working directory is inside a GitHub-tracked repo**. Run `gh repo view --json nameWithOwner -q .nameWithOwner`. If `gh` reports no repo (the directory is not a git repo, or the remote is not on GitHub), abort with: `Working directory does not resolve to a GitHub repo. Configure the remote with "gh repo set-default" or run from a GitHub-tracked clone.`
3. **Resolve the feature directory** in this priority order:
    1. Positional argument, if supplied.
    2. `.specify/feature.json` -> `feature_directory` field, if the file exists at the repo root.
    3. Most recent plan under `docs/<version>/plans/` (sort by mtime).
    4. Abort if no candidate is found.
4. **Locate the task source** inside the feature directory:
    1. `<feature-dir>/tasks.md`, if present.
    2. Else `<feature-dir>/plan.md` (parse task lines from inline phase blocks).
    3. Else the single Markdown file at the resolved plan path (default layout).
5. **Parse every task line** against the strict regex `^- \[ \] T[0-9]{3,}( \[P\])?( \[US[0-9]+\])? .+$` (the format enforced by Phase 6 of `docs/v2.1.0/plans/adoption-spec-kit.md`). If any line in the source file starts with `- [ ]` and a `T###` token but does NOT match the regex, abort and list the offending lines so the user can re-run `/generate-plan` with the strict-format validator.
6. **Detect already-filed issues** in the source file: any task with `[gh#<num>]` after the description marks the task as already converted. Skip those during the conversion pass and report the count in the summary.

---

## Step 2: Build the issue payload

For each parsed task, build a payload with three fields:

1. **Title**: `[T###] <description>` where `<description>` is the task's description with the file path appended in parentheses. Cap at 200 characters; truncate the description (NOT the task ID) with an ellipsis if needed.
2. **Body**: a fixed Markdown block containing the task ID, the file path, the parallel marker (when `[P]` present), the user-story link (when `[US#]` present), a reference back to the source file path, and a trailing "Generated by /tasks-to-issues" line. When the task carries a `[US#]` label and the feature directory contains a `spec.md` with a matching user story heading, link to the heading anchor (e.g., `[US1](../spec.md#user-story-1-authentication-priority-p1)`).
3. **Labels**: a comma-separated list. Always include `nexus-hub` and `spec-driven-task`. Add `parallel` when the `[P]` marker is present. Add `user-story-N` (where N matches the `[US#]` integer) when `[US#]` is present. The command does NOT create labels that are missing in the repo -- `gh issue create` will warn; the user must pre-create labels via `gh label create <name>` if they want them on the issue.

Render an in-memory preview table (T### | Title | Labels) and show it to the user before any `gh` invocation. The table is the same shape that `--dry-run` would emit.

## Step 3: Dry-run or execute

### Dry-run mode (`--dry-run`)

Print the resolved `gh issue create` invocations one per task, each on its own line, in the exact form the command would otherwise run:

```
gh issue create --title "[T001] Create project structure (docs/v2.1.0/plans/)" --body "..." --label "nexus-hub,spec-driven-task"
gh issue create --title "[T002] [P] Implement auth middleware (src/middleware/auth.py)" --body "..." --label "nexus-hub,spec-driven-task,parallel"
```

Do not call `gh` in dry-run mode. The output is for inspection only.

### Execution mode (default, no `--dry-run`)

1. Confirm with the user: `About to create N GitHub issues in <repo>. Continue? [y/N]`. Abort on any answer that is not `y` or `Y`.
2. Invoke `gh issue create` sequentially (not in parallel) -- one task per call. Sequential execution avoids GitHub's secondary rate limit on issue creation.
3. Capture the URL emitted by `gh issue create` on stdout and the issue number from the URL's trailing path segment.
4. After each successful creation, **rewrite the source task line** to append `[gh#<num>]` immediately after the task description. This idempotency marker makes re-runs of the command safe: tasks already filed are skipped (per Step 1.6). Save the file atomically after each rewrite.
5. If any `gh issue create` invocation fails (non-zero exit, rate limit, network error), stop the loop, leave the not-yet-filed tasks unmarked, and surface the failure to the user with the remediation message: `Issue creation for T### failed -- inspect <error>. Already-created issues remain. Re-run /tasks-to-issues to file the rest.`
6. After the loop completes (or aborts), emit a final summary table: `T### | Created issue URL | Labels`. Include a separate line counting skipped (already-filed), failed, and newly created.

## Step 4: Helper script

The parsing + `gh` invocation logic is implemented by the bundled helper script at `catalog/skills/workflow/tasks-to-issues/scripts/tasks-to-issues.sh` (POSIX) and the parallel `.ps1` (Windows). The command orchestrates the flow above and delegates the mechanical parts to the script. Both helpers ship under the per-skill `scripts/` subdirectory and are auto-copied to `~/.nexus-hub/skills/workflow/tasks-to-issues/scripts/` by the installer's recursive `safe_folder_copy` primitive (no installer edit needed for per-skill bundled subdirs per `AGENTS.md`).

The script accepts the same flags as the command (`--dry-run`, `--feature-dir`, `--repo-root`) and prints the same final summary on stdout. The command file is the authoritative user-facing surface; the script is the executable detail.
