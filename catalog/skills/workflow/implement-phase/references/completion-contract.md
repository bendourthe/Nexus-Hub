# Completion Contract

The single definition of "done" for a full `/implement` run: the predicates a plan must satisfy, the evidence each reads, what happens when evidence cannot be read, the four verdicts, and the run record that binds a run to the approvals the user gave at its start. `scripts/check_plan_completion.py` implements this file. The installer copies it to `~/.nexus-hub/scripts/check_plan_completion.py`, so in any project every `check_plan_completion.py <subcommand>` named here, in the runbook, or in the commands runs as `python ~/.nexus-hub/scripts/check_plan_completion.py <subcommand>`; a missing installed copy is `BLOCKED: platform-unavailable`, never a reason to skip the run record; the completion gate, the runner, and `/update release` consume the checker's verdict and never re-derive it. Read this before changing the checker, a gate adapter, the runner, or any approval point in the implement or release flow.

This file is the only owner of the predicate list. Commands and skills refer to "the completion contract" and to predicate ids; they do not restate a predicate's rule.

## Verdicts

The checker prints exactly one verdict line first, then one line per predicate id, and exits with the verdict's code.

| Verdict line | Exit | Meaning |
|---|---|---|
| `PLAN COMPLETE <plan> <head> <nonce>` | 0 | Every predicate is met. `<head>` is `git rev-parse HEAD`; `<nonce>` is the run record's nonce, or `-` when no record exists. When deferred gaps were accepted, the line ends with ` (N deferred)`. |
| `INCOMPLETE: <id> <id> ...` | 1 | At least one predicate is unmet or cannot be verified. Ids only, space-separated, in contract order. |
| `BLOCKED: <category>` | 3 | The run record holds an open blocker, or the record failed an integrity check. `<category>` is one value from the closed list below. |
| `PAUSED` | 4 | The user paused the run with `/implement pause`. |
| `MINOR COMPLETE <minor> <head> <nonce>` | 0 | `check-minor vX.Y` only: every member and every minor-level line is met (see "Minor verdict"). |
| (error message) | 2 | Malformed input: a plan path outside `docs/**/plans/`, a plan with no `T###` lines, an unreadable plan. Never reported as complete. |

Every line after the verdict has the form `<id> met|unmet|cannot-verify|deferred|n/a`. The checker never prints free text taken from the plan, the gaps file, `git`, or `gh` output, so a gate or runner can pass the output to a model without relaying injected text.

Precedence when several states hold: a record that fails integrity (`record-tampered`) first, then `PAUSED`, then any other open blocker, then the predicates.

## Predicates

Ids are fixed strings. "Cannot verify" always counts as unmet: offline, unauthenticated, or slow evidence produces `INCOMPLETE`, never a pass.

| Id | Met when | Evidence source | Cannot verify when |
|---|---|---|---|
| `task.T###` (one per task line) | The line is checked (`- [x] T###`) and, when a run record exists, at least one commit since the record's `start_head` touches the path named at the end of the line | The plan file; `git log <start_head>..HEAD -- <path>` | The named path is absent from the line (reported `unmet`) |
| `gaps.version` | Every open item in `<version_dir>/known-gaps.md` under this plan's `## v<version>` subsection is resolved, or carries a gap type (`NI`, `DF`, `BG`, `MT`, `WN`, `QG`) the user named for deferral in the upfront round; an item added during the run whose Source phase names one of this plan's own tasks is never deferrable; for a minor member, an item whose migration verifies (see "Minor gaps and archive") is closed, and an open item whose id is in the record's frozen `gap-migration` list is `deferred` until the minor close, where `gaps.minor` decides it (a security or high-severity item only when the approval also names it individually; otherwise it stays unmet) | The gaps file; the record's `deferrable_gap_types` and `start_head` | The gaps file is unreadable |
| `evidence.file` | `<version_dir>/development/<version>-last-phase-evidence.md` exists with every required section heading (see "Required evidence sections"). The legacy `last-phase-evidence.md` counts only when it names this plan's filename | The evidence file | Never (a missing file is `unmet`) |
| `tests.evidence` | The evidence file's `## Full-suite testing and stabilization` section quotes a passing command and names at least one test path this run changed | The evidence file; `git diff --name-only <start_head>..HEAD` | No run record, so the changed set cannot be computed (`cannot-verify`) |
| `approval.remote` | The live `git remote get-url --push --all origin` returns exactly one URL matching the push URL frozen in the signed approvals, a plain `git push` of the source branch goes to `origin`, no git transport override can redirect that push, and the URL names the approved GitHub `owner/repo` on a host verified with the ssh git itself runs (see "Push route") | The run record; `git remote get-url --push --all origin`; `git config`; the environment; `<git's ssh> -G <host>` for an SSH remote | No run record; any transport override; git's ssh cannot be determined for an SSH remote. A missing, unrecognized, changed, or additional push URL, a push remote other than `origin`, or an unverified host is `unmet` |
| `integration.merged` | The plan branch's pull request into the integration branch is merged | `gh pr view <branch> --repo <owner/repo> --json state,mergeCommit` | `gh` missing, unauthenticated, offline, or over budget |
| `integration.checks` | Every required check on that pull request concluded success. Required-ness comes from `docs/policy/required-checks.json` when present, else `gh pr checks --required`, else it cannot be verified | The manifest; `gh pr checks` | As above, or no source of required-ness |
| `release.tag` | Tag `v<version>` exists locally and on the remote | `git tag -l`; `git ls-remote --tags <remote>` | Remote unreachable |
| `release.changelog` | `CHANGELOG.md` has a `## [<version>]` heading | The file | Never |
| `release.version-sync` | The project's declared version-sync command passes (Nexus-Hub: `python scripts/check_version_sync.py`); `n/a` when the project declares none | The command's exit code | The command times out |
| `release.github` | A GitHub Release for the tag is published (not a draft) | `gh release view v<version> --repo <owner/repo> --json isDraft` | As for `integration.merged` |
| `release.main` | The release branch (`main`) contains the tag | `git merge-base --is-ancestor v<version> <remote>/main` | Remote ref absent |
| `cleanup.branches` | Every branch listed in the record's `cleanup.branches` is gone locally and on the remote | `git branch --list`; `git ls-remote --heads` | Remote unreachable |
| `cleanup.worktree` | Every worktree listed in the record's `cleanup.worktrees` is absent from `git worktree list` | `git worktree list --porcelain` | Never |
| `cleanup.merged` (only when a schema-1 record carries `cleanup-merged`; for a minor run, the minor verdict) | The sealed final-pass receipt beside the record (see "Cleanup receipt") names the record's nonce and its target branch as `integration_branch`, used an idle window of at least 24 hours, was taken when the integration branch's tip already contained the last merge (the plan's integration pull request; for a minor, the closing pull request), and every item it removed is still gone. Items that became eligible after the receipt never reopen the verdict; they are reported by the next pass | The receipt; `gh pr view <branch> --json state,mergeCommit`; `git merge-base --is-ancestor`; `git for-each-ref`, `git ls-remote --heads`, `git worktree list` | `gh` unavailable, no merge commit reported, or the tip's history is not local. A missing, unsealed, or other-run receipt is `unmet` |

Post-integration predicates (`release.*`, `cleanup.*`) are derived from repository and hosting state, never from checkboxes, because the tasks that produce them are ticked by the same agent the checker is judging.

Every hosting call is pinned with `--repo <owner/repo>` from the record's frozen approvals, runs with `GH_PROMPT_DISABLED=1` and `GIT_TERMINAL_PROMPT=0`, resolves `git` and `gh` to absolute paths outside the working tree, and shares one 20-second wall-clock budget for the whole check. `owner/repo` is resolved by the installed `repo_host.py`: the record's frozen repository when one exists, otherwise the `origin` URL (`https://`, `ssh://`, or `git@host:owner/repo`), accepted only when its host is the one `gh --repo` queries (`GH_HOST` when set, otherwise `github.com`). An SSH host alias is replaced by the `hostname` that `ssh -G <alias>` reports and is refused when routed through a proxy, and without a record the answer is cross-checked with `gh repo view`; an unverified host or a disagreement yields no repository, so every hosting predicate is `cannot-verify`, never a lookup of a same-named github.com repository. The rules that decide whether a push really reaches that host are in "Push route" below. `record create` refuses a push URL that does not name that approved repository; a later push-URL change makes `approval.remote` unmet and permits an `approval-not-covered` blocker even when `push-merge` was approved. Local predicates run first so an offline check still reports them.

### Push route

This subsection is the single owner of the push-route rule (v4.13.5 WN-2 and WN-3); `repo_host.verify_push_route` implements it, and `approval.remote` is `met` only when every step passes:

1. **Effective push remote.** The remote a plain `git push` of the record's source branch uses is resolved in git's own order: `branch.<b>.pushRemote`, `remote.pushDefault`, `branch.<b>.remote`, then `origin`. Any remote other than `origin`, whose push URL the record froze, is `unmet`.
2. **Transport overrides.** Any setting that can send the push somewhere other than the verified host makes the predicate `cannot-verify`, never `met`: `GIT_SSH`, `GIT_SSH_COMMAND`, or `core.sshCommand` for an SSH remote; for an HTTPS remote, anything that weakens or replaces TLS verification (`http.sslVerify` false, also per URL; `GIT_SSL_NO_VERIFY`; `GIT_SSL_CAINFO`, `GIT_SSL_CAPATH`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, or `CURL_CA_BUNDLE`; `http.sslCAInfo` or `http.sslCAPath` set in a global, local, worktree, or command scope) and `http.curloptResolve`, also per URL; for any remote, `remote.origin.vcs` (git then pushes through a `git-remote-<vcs>` helper), a `<transport>::<address>` URL for the same reason, `GIT_EXEC_PATH` (it replaces the transport programs), and `GIT_CONFIG_PARAMETERS` or `GIT_CONFIG_COUNT`, which inject config the checker's own git calls strip but a push would honor. The checker also strips `GIT_EXEC_PATH` from its own git calls. An empty value disables a setting and does not count.
3. **Proxies and rewrites (deliberate).** A proxy alone is not an override: `http.proxy`, `http.<url>.proxy`, `remote.origin.proxy`, and `http_proxy`, `https_proxy`, or `all_proxy` are ignored, because with TLS verification intact a CONNECT proxy cannot present github.com's certificate, so it can refuse or delay the push but cannot deliver it to another host (and `http_proxy` does not apply to an HTTPS URL at all). What would let it do so, a disabled check or a substituted trust anchor, is listed above. `http.sslBackend` is not an override: it chooses the TLS implementation, which still verifies, and Git for Windows sets it by default. A CA bundle set in system scope is not counted either, because writing system config needs administrator rights and Git for Windows' installer sets `http.sslCAInfo` there. An `insteadOf` or `pushInsteadOf` rule is an override only when the configured URL and the effective push URL (which `get-url --push` reports with the rewrite applied, and which is what the checker verifies) name different verified repositories; a rewrite such as `url."git@github.com:".insteadOf https://github.com/` is therefore `met`.
4. **git's own ssh.** For an SSH remote the host is resolved with the ssh git itself runs, found by asking git's shell for `command -v ssh`, because git spawns ssh with that PATH; on Windows an extensionless answer maps to its `.exe` or `.cmd` sibling. When that cannot be determined, or the answer lives inside the working tree, the predicate is `cannot-verify`. Every probe passes exactly what git passes: `<git's ssh> -G [-p <port>] [<user>@]<host>`, so a `Match user` or port-specific block is read as it would apply to the push. A literal accepted host (`github.com`, or `GH_HOST`) is `cannot-verify` when that probe reports another `hostname`, a `ProxyCommand`, or a `ProxyJump`, which is how a `Host github.com` block in ssh config would reroute it. An alias is resolved as described above, with the same ssh.

The checker explains a failure on stderr as `notice: approval.remote <status>: <reason id>`, with a fixed id (`push-remote-not-verified-remote`, `transport-override-<kind>`, `ssh-undetermined`, and similar), never a URL or a config value.

A hosting answer that the pull request or release does not exist (`gh`'s whole stderr line is `no pull requests found for branch "<branch>"` or `release not found`) is `unmet`, not `cannot-verify`: GitHub was reached and the run's next step is to create it. Only an unreachable, unauthenticated, or over-budget call is `cannot-verify`. The agent probes hosting the same way, always with `--repo <owner/repo>` from the record; an un-pinned `gh` call that fails is not evidence that the platform is unavailable, and never justifies merging, tagging, or releasing through `git` alone.

### Required evidence sections

The evidence file must carry these `##` headings, matching the implement-phase runbook's last-phase list: `Architecture refactor`, `Known-gaps reconciliation`, `Living docs architecture`, `Git-tree hygiene`, `CI/CD coverage`, `Tier 3 deep pass`, `Goal-vs-codebase review`, `Human/manual testing suggestions`, `Full-suite testing and stabilization`, `Publication and integration`.

### Definition-of-Done mapping

| Plan DoD item (v4.13.2) | Predicates |
|---|---|
| Every task, phase, and known gap | `task.T###`, `gaps.version` |
| Green CI with the tests the work needs | `tests.evidence`, `integration.checks` |
| The merged integration | `approval.remote`, `integration.merged` |
| The full release | `release.tag`, `release.changelog`, `release.version-sync`, `release.github`, `release.main` |
| Removal of merged branches and worktrees | `cleanup.branches`, `cleanup.worktree`, and `cleanup.merged` under a `cleanup-merged` approval |
| Last-phase duties recorded | `evidence.file` |

### Cleanup receipt

This subsection owns the `cleanup.merged` evidence. `cleanup_merged.py` (installed beside the checker) is the only code that removes a branch or worktree a run did not list; the seven checks it applies and why are in `docs/decisions/proposed/policy/2026-09-28-verified-merged-and-idle-cleanup.md`, and nothing here restates them. Per-plan runs keep `cleanup.branches` and `cleanup.worktree` for their own items and use the executor only when their record carries `cleanup-merged`, which the approval page offers for a one-plan run as well (its page then shows the cleanup rule `merged-and-idle` instead of `run-owned`).

`cleanup_merged.py --apply --receipt --plan <plan> --session <id>` (or `--minor vX.Y`) runs the final pass after the last merge and writes `<record key>.cleanup-receipt.json` beside the run record, owner-only. It refuses with `BLOCKED: approval-not-covered` and `reason: no-cleanup-merged-approval` when the record does not carry `cleanup-merged`, and prints the record's forced verdict when it is paused, blocked, or tampered. The receipt holds `kind` (`cleanup-merged-receipt`), `receipt_schema` (`1`), `scope`, `record_nonce`, `created`, `integration_branch`, `integration_tip` (the live remote tip when the pass ran, fetched so its history is local), `idle_hours` (the window the pass used; the executor refuses anything below 24), `removed` (each item as `{kind, name, remote, path}`), `kept` (each item label with its check), and `seal`, an HMAC-SHA256 under the runs secret over the canonical JSON of every other field, in its own domain so no other sealed file verifies as a receipt. The receipt carries no `schema` or `repo_root`, so record lookups by content never mistake it for a run record. No receipt is written when any item was kept for `gh-unavailable`, `remote-unreadable`, or `records-unreadable`: the pass could not see, so it prints `BLOCKED: cannot-verify` and exits 3 instead, and `cleanup.merged` stays `unmet`.

## Run record

### Location and binding

One file per run at `~/.nexus-hub/runs/<key>.json`, where `<key>` is the sha256 of the repository root, the resolved `owner/repo`, and the scope (`plan:<repository-relative plan path>` or `minor:vX.Y`), joined by newlines. The `owner/repo` is the one the verified push URL names, else the one the fetch URL names, lowercased, else empty; it is resolved without a `gh` call so the key does not depend on the network. A record written before v4.13.6 used the sha256 of the root, the raw fetch URL, and the plan path; that key is still read, and a new record for the plan moves the old file to `runs/retired/`. Because the key names mutable remote configuration, a record that is not at its key is also found by content (the same `repo_root` and the same `plan` or `minor`), so a changed remote reports `approval.remote unmet` instead of hiding the record. The directory is created owner-only (0700; owner-only ACL on Windows) and the file 0600. The record lives outside every working tree so no commit, branch switch, or `git clean` can create, alter, or delete it. The location decision and its alternatives: `docs/decisions/implemented/tooling/2026-09-25-completion-run-record-outside-the-working-tree.md`.

Schema-1 (one plan) fields: `schema` (`1`), `plan` (repository-relative path), `plan_sha256` (at approval time), `repo_root`, `remote_url`, `repo` (`owner/repo`), `session_id`, `worktree`, `start_head`, `nonce` (the approval round's 128-bit nonce, 32 hex characters; see Approval origin), `created`, `approvals`, `approvals_hmac`, `deferrable_gap_types`, `cleanup` (`branches`, `worktrees`), `blockers`, `pause`.

### Approvals as exact actions

Each approval is a tuple of exact values plus the verbatim user text that granted it: the plan path; the fetch remote URL, push remote URL, and `owner/repo`; source and target branch; release version and tag name; the branches and worktrees to remove; and each approval class with its bound. The per-plan classes are: `push-merge`, `release` (version, tag, publication, release pull requests, and back-merge for that one version), `repush` (after a locally reproduced fix, bound 3), `release-notes`, `refactor-moves` (inside plan-touched folders only), `spend` (a USD cap per vendor), and one `ask-first:<surface>` per "Ask first" surface the plan names. The minor-level classes, recorded only in a schema-2 record, are `cleanup-merged` (also offered to a one-plan run), `gap-migration` (bound: the frozen list of migratable gap ids, such as `v0.5#WN-3`, plus `named`, the security or high-severity ids among them; see "Minor gaps and archive"), `archive-minor`, and `minor-close-pr` (push, pull request, merge, and back-merge for the closing pull request). A minor run requires `cleanup-merged`, `archive-minor`, and `minor-close-pr`: Definition of Done for a minor is the final cleanup pass after the last merge, the merged closing pull request, and the archive, so `record render` and `record create --minor` refuse a spec without all three, and `check-minor` reads a missing one as `unmet`, never `n/a`. A per-plan approvals file that names `gap-migration`, `archive-minor`, or `minor-close-pr` is malformed. CI workflow, permission, and secret changes are never approvable in advance; they are always a `ci-security-change` blocker.

An older signed record without `push_remote_url` yields `approval.remote unmet`; creating a fresh record from a current user approval is required before publication. A changed destination cannot be authorized by editing the old record.

`approvals_hmac` is an HMAC-SHA256 over the canonical JSON of `approvals`, `plan_sha256`, `session_id`, `repo`, `deferrable_gap_types`, `start_head`, `nonce`, and `created`, plus `schema`, `scope`, `minor`, `members`, `excluded`, and `completed` for any record that is not schema 1 (the schema-1 payload is unchanged, so existing records still verify), keyed by the owner-only secret `~/.nexus-hub/runs/.secret`, which `record render` or `record create` creates when it is absent. `pause` and `blockers` are not yet signed (v4.13.2 known gap WN-8). No prompt text, command, or skill references the secret's content.

### Schema 2: the minor record

`/implement vX.Y` writes one schema-2 record for the whole minor, and while it is valid it is the only authority for every member. `record render --minor vX.Y` and `record create --minor vX.Y` (with `--session` and `--approvals`) follow the Approval origin rule below, and `record create` prints `RECORDED minor vX.Y nonce=<nonce>`. The approvals file lists the per-plan classes once, applied to every member (a `release` class is bound to each member's own version), then the minor-level classes (`spend` and `unattended-with-bypass` are among them: one cap and one decision for the whole run, shown once on the page, never copied into each member, which would multiply the cap), and optional per-member overrides (`"members": {"vX.Y.Z": {"source_branch", "target_branch", "tag", "cleanup"}}`). `defer-gaps` is refused: in a minor run a gap is fixed or migrated.

Fields: `schema` (`2`), `scope` (`"minor"`), `minor` (`vX.Y`), `repo_root`, `remote_url`, `repo`, `session_id`, `worktree`, `start_head`, `nonce`, `created`, `members`, `excluded` (the plans the page showed as not members, with their reasons), `approvals` (the minor level: `remote_url`, `push_remote_url`, `repo`, `target_branch`, the minor-level `classes` with the pasted line as their text, `spend_caps`, and `page_sha256`), `approvals_hmac`, `blockers`, `pause`, and `completed`. Each member is `{version, plan_path, plan_sha256, source_branch, target_branch, release_version, tag, approvals: {classes, cleanup}}`, holding the same exact per-plan classes a schema-1 record holds, plus `start_head` and `started` once the member gate (see "Minor verdict") has passed.

- **Identity by version.** A member is identified by its `version`, never its path. The loader finds each member's plan by version across the canonical, legacy, and archive layouts, so an archived member still resolves, and the archive commit re-freezes `plan_path` under the recorded `archive-minor` approval.
- **Projection.** `project(record, version)` in the checker returns the per-plan view of one member: the record's frozen remote and repository, the member's branches, tag, cleanup, and classes plus the minor-level classes, and no deferrable gap types. `evaluate`, the gates, and the runner therefore keep one code path. A schema-1 record is its own view.
- **Integrity.** A schema-2 record is `record-tampered` when it fails any schema-1 integrity check below, when `scope` is not `"minor"` or `minor` differs from the requested token, when `members` is empty, or when a member's plan no longer hashes to its frozen `plan_sha256`. Removing `scope`, `minor`, or a member, or relabelling the record as schema 1, fails the HMAC. A schema-2 record found under a plan key is also tampered.
- **Validity.** The record stays valid across sessions until `MINOR COMPLETE` (it then carries `completed`), a pause, or 14 days after `created`, whichever comes first; an older or completed record is ignored with a notice. In a session other than the one it is bound to, it is ignored until the user pastes the resume line: `record render --minor vX.Y --session <new> --action resume` prints it, and after the paste `record resume --minor vX.Y --session <new>` rebinds the record to the session where the paste was captured, clears any pause, and re-signs it. A resume is never a new approval, because the frozen approvals do not change.
- **One authority.** `record render` and `record create --minor` refuse with `BLOCKED: approval-not-covered (per-plan record exists for vX.Y.Z)` and name `check_plan_completion.py record retire <plan>` when any member still has a per-plan record, at either of its keys or found by content. In the other direction, `record render` and `record create` for one plan refuse with `BLOCKED: approval-not-covered (minor record vX.Y covers vX.Y.Z)` while a valid, uncompleted minor record lists that version (paused or blocked still counts). A live minor record is never replaced: a second `record render` or `record create --minor` refuses with `BLOCKED: approval-not-covered (minor record vX.Y is live; resume or complete it)`. The two authorities are never merged.
- **Retire.** `record retire <plan> [--session <id>]` moves every per-plan record for the plan (keys and content matches) to `runs/retired/`, never deleting it, and refuses while a runner holds it. A record older than 72 hours, or one bound to the caller's own `--session`, moves at once. Another session's live record moves only after the user pastes the line `record render <plan> --session <id> --action retire` prints, under the Approval origin rule, because retiring it removes that run's authority, pause, and blockers.
- **One run.** `record path --minor vX.Y` prints the record's path. The runner's lock beside it (`<key>.runner.lock`) refuses a concurrent second runner, and `record render` or `record create --minor` refuses with `BLOCKED: owned-by-another-run (vX.Y)` while that lock is live. A frozen member that becomes owned by another run (see Minor membership) makes the loader report `BLOCKED: owned-by-another-run (vX.Y.Z)`.

### Approval origin

This section is the single owner of the exact-binding rule; other documents link here and do not restate it. An approval is recorded only when the user's submitted prompt equals, as a whole, the exact paste line the checker generated for that page, once. This holds for every user-origin record write: `record create`, `record answer`, `record pause`, and `record resume`. `record block` records the agent's own stop and needs no user origin.

1. **Render.** `record render <plan> --session <id|auto>` (with `--approvals <file>` for `create`, or `--action answer --blocker <n>`, `--action pause`, `--action resume`) builds the canonical JSON of exactly what the page shows: for `create`, the scope, each member with its `plan_sha256`, the verified `owner/repo`, the current `HEAD`, the source and target branches, the releases and tags, the cleanup rule and today's estimate, the migratable gap ids, the spend caps, and the approval classes with their bounds; for a mid-run action, the scope, the record's `nonce`, and (for an answer) the blocker's index and category. It draws a fresh 128-bit round nonce and derives `code` = the first 8 base32 characters of `HMAC-SHA256(runs secret, canonical {page, nonce})`. Only the checker generates codes; the agent never does. It writes an owner-only pending round at `~/.nexus-hub/runs/pending/<key>.json` (same `<key>` as the record, same permission helper) holding the page, code, nonce, the render time, a 30-minute expiry, the bound session, and the exact paste line(s) with their digests, sealed by an HMAC under the runs secret over every one of those fields, and prints the line(s). A round whose seal does not verify (for example one whose digests, expiry, or session were edited) is refused as `pending-unreadable`. The line is built only from validated fields (a version token, a blocker index, the code) and carries no path or script name. A newer render for the same record replaces the older round, whose code is then refused as `code-superseded`.
2. **Paste.** The user pastes the line as their whole prompt. On platforms with a documented prompt-submit hook (Claude Code `UserPromptSubmit` and the equivalents in `docs/policy/completion-levers.json`), the `approval-capture` hook stores, per session, the sha256 of the whole submitted prompt (normalized: trimmed, internal whitespace collapsed) in hook-owned state at `~/.nexus-hub/runs/prompts/<sha256(session id)>.jsonl`, one JSON line `{"session": ..., "prompt": <digest>, "at": <capture time>}` per prompt. No prompt plaintext and no per-line digest is stored, so a line inside a longer prompt, a quoted code, or a pasted body never matches. The hook skips capture in any session whose environment has `NEXUS_RUNNER_LAUNCH=1`, which `nexus-hub run-plan` sets for every session it launches.
3. **Record.** The write recomputes the page from live state and requires, in order: not a runner-launched environment; an open round of the same action whose seal verifies; not expired; the same code (any change to the page, such as a plan edit outside task checkboxes or a moved `HEAD`, fails here); the bound session, when the round names one, and for `record answer`, `record pause`, and `record resume` also the session the run record is bound to (`session-mismatch` otherwise); exactly one captured whole prompt in that session equal to each paste line; and at least one other prompt captured in that session before the round was rendered (`session-too-new` otherwise), since the user's own session already holds the `/implement` request while a headless session launched only to submit the line does not. It then deletes the pending round, leaves a used marker, and, for `create`, adopts the round nonce as the record's `nonce` and stores the pasted line as each class's verbatim text. With `--session auto`, the session is the newest one whose captured whole prompts include the line. The round lives for 30 minutes from render; the end of a session is not detected, so within that window a later session can record a line the user pasted in an earlier one, and the record is then bound to the session where the paste was captured.
4. **No capture.** Where no prompt-submit hook exists, or the named session has no capture file, the write refuses with `approval-not-captured`. There is no terminal fallback: a process that owns the console or a pseudo-terminal can type into `/dev/tty` or `CONIN$`, so a terminal read would not show that the user typed the line. On such a platform the run records no approval and asks at each approval point, as a one-phase run does.

A refusal prints `BLOCKED: approval-not-covered` on the first line, so existing consumers parse it unchanged, and `reason: <id>` on the second, where `<id>` is one of: `runner-launched`, `not-rendered` (no open round for this action), `pending-unreadable`, `code-used` (the round was already consumed), `code-superseded`, `code-expired`, `session-mismatch`, `session-too-new`, `page-changed`, `approval-not-captured`, or `push-remote-outside-approval`. A refused write does not consume the round, except that a claimed `--text` different from the pasted line spends it.

### Integrity

The checker rejects a record, reporting `BLOCKED: record-tampered`, when any of these hold: the record path is inside a git working tree or tracked by git; `plan_sha256` differs from the plan file's current hash for any change outside task checkboxes and the header Status value (a schema-1 record written before v4.13.6 froze a hash that normalized checkboxes only, and that hash is still accepted for schema 1; a schema-2 record accepts only the current hash); `approvals_hmac` does not verify; the record's `schema` is unknown. Task checkbox ticks and the header Status value are excluded from the plan hash so the run can progress. Only the FIRST `**Status**:` line above the first `## ` heading is normalized, and only when its whole value is one of `queued`, `in-progress`, `complete`, `superseded`, `shipped`, or `blocked` (optionally in backticks); any other text on that line, and every other Status line, is hashed, so an instruction appended there is an edit.

**Threat model (honest boundary).** These controls stop an agent from widening its authority through ordinary actions: editing the record or a pending round, rewriting the plan, or treating a reply that is not the generated line (a lone "ok", a quoted code, a pasted body, a replayed or superseded line, a runner-launched prompt, a fresh headless session opened only to submit the line) as an approval. They do not stop an agent that deliberately forges a user origin. A prompt submitted by a headless CLI the agent launched, a payload the agent pipes into `completion_gate.py capture`, or a line appended to the capture file is indistinguishable from the user's paste, and none of them is a user origin; this residual is open as v4.13.2 WN-9 in `docs/releases/v4/v4.13/known-gaps.md`. They are not a sandbox. A process with the user's file access can read the secret and recompute the HMAC, and the prompt digests sit in the same home directory. The design therefore relies on three things together: the approval-origin rule (an approval must match text the user submitted), the fixed-id output that keeps injected text out of the loop, and the named-blocker rule that makes widening an approval a visible stop rather than a silent success.

### Blockers

A blocker is an entry in the record's `blockers` list with exactly one category from this closed list, the evidence (the command run and its output, truncated to 2000 characters), and `open: true`:

`approval-not-covered`, `unreproducible-red-check`, `user-edit-guard`, `destructive-outside-approval`, `ci-security-change`, `no-progress`, `record-tampered`, `platform-unavailable`.

A blocker whose question the frozen approvals already answer is rejected at write time. In a minor run, `record block --minor vX.Y [--member vX.Y.Z]` writes the blocker to the minor record; with `--member` the entry carries that `version` and the verdict reads `BLOCKED: <category> (vX.Y.Z)`. `no-progress` is written by the gate or the runner when the progress score has not increased over three consecutive refusals or cycles.

### Pause and resume

`/implement pause` writes a user-origin `pause` entry (subject to the approval-origin rule, so the user pastes the rendered pause line) and is always honored; the checker then reports `PAUSED`. `/implement <plan>` resumes: the upfront round shows any open blocker and the pause, records the user's pasted answer or resume line as an approval, and clears them.

### Usage-limit handoff

This contract is the single owner of how the turn-end gate treats a usage-limit handoff (v4.13.7). The `usage-guard` hook and the `session-handoff` skill only produce the evidence.

On a turn end the gate allows the stop, counts no refusal, writes no blocker, and leaves the record unchanged (never complete, never paused) only when both hold:

1. The repository's `.nexus-hub/handoff.md`, found by walking up to the git root, has a first line `# Handoff | TIMESTAMP | PLATFORM | usage-limit WINDOW PERCENT` whose timestamp is later than the gate's last refusal for this session (or, before any refusal, the record's `created`).
2. The usage probe (`_usage_probe.py`, through `usage-guard`'s platform detection) reports `ok`, or `stale` under 30 minutes, with a tracked window at or over `NEXUS_HANDOFF_THRESHOLD` (default 99).

The gate then prints one line on stderr saying the run stopped for a usage-limit handoff and resumes when the user pastes the handoff prompt. The run resumes through `/implement <plan>` as usual. When the probe is unavailable or below the threshold, the platform is unrecognized, or either module is missing, the gate behaves exactly as before, so writing a handoff file alone never releases a run. The gate loads `usage-guard.py` and `_usage_probe.py` only from the calling hook's own directory (`NEXUS_GATE_HOOK_DIR`, set by the adapter) and never from inside the repository, so a workspace-scoped install, whose hooks live in the repository, never takes this exception. A process with the user's file access could still write a probe cache under `~/.nexus-hub/state/usage-probe/`; that residual is the same home-directory boundary as the threat model above.

### Hook-owned state

The refusal counter and the last progress score live beside the record at `~/.nexus-hub/runs/<key>.gate.json`, never inside it, so writing them never invalidates the HMAC.

### Stale records

A record whose session is gone and whose `created` is older than 72 hours is stale: the checker reports it once on stderr and treats it as absent for any other session.

## Minor membership

This section owns which plans a minor run covers. `check_plan_completion.py members vX.Y`, implemented in the sibling `completion_minor.py`, prints one repository-relative plan path per member in semantic-version order by parsed integers (`v0.5.2` before `v0.5.10`), and one `<version> <reason>` line per excluded plan on stderr. It reads every plan under `docs/releases/vM/vM.m/plans/`, the legacy `docs/vM/vM.m/`, `docs/versions/vM/vM.m/`, and `docs/vM.m/` layouts, and the archive layouts `docs/archives/vM/vM.m/`, `docs/archive/vM/vM.m/`, and `docs/archive/versions/vM/vM.m/`, and keeps only plans whose own `**Version**` line is in the minor. Tokens are canonical: a minor token or a plan version with a leading zero (`v0.05`, `v0.05.2`) is refused, so one minor has exactly one record key.

A plan is a member when all three hold:

1. Its `**Status**` is not `complete`, `superseded`, or `shipped` (excluded as `status-<value>`).
2. It is not shipped: its tag exists locally and on `origin` AND its GitHub Release is published, whatever its Status says (excluded as `shipped`). When either cannot be read, the plan is excluded as `cannot-verify-shipped`, and `record render` or `record create --minor` stops with `BLOCKED: platform-unavailable (vX.Y.Z)` rather than rebuild a release.
3. It is not owned by another live run: no per-plan record created within 72 hours, at either key or found by content (an unreadable one counts as owned); no live runner lock beside either of its record keys; no other live minor record (within 14 days, not completed) that lists the version; and no `feat/<version>-*` branch, local, remote-tracking, or live on `origin`, whose tip is not merged into the integration branch (`origin/develop`, else `develop`) and which this minor's verified record does not list as a member's own source branch (excluded as `owned-by-another-run`). When `git ls-remote origin` fails, a plan none of these owns is excluded as `cannot-verify-owned`, and the round stops with `BLOCKED: platform-unavailable (vX.Y.Z)`, as for `cannot-verify-shipped`.

Hosting calls are pinned to the frozen record repository, else `repo_host.resolve_repo`, else the verified push URL's repository. Exit codes: `0` with at least one member; `1` with none, printing `No queued plans in vX.Y`; `3` with `MALFORMED: duplicate version vX.Y.Z` or `MALFORMED: plan unreadable <path>`; `2` for a token that is not `vMAJOR.MINOR`. An owned plan does not block the run: it is not a member, `members` reports it on stderr, and the approval page lists it under `excluded` with its reason, so the user sees what the approval leaves out. Only a plan that is already a frozen member and later becomes owned stops the run, with `BLOCKED: owned-by-another-run (vX.Y.Z)`.

## Minor gaps and archive

This section owns the two minor-level predicates a minor run's verdict reads besides its members, `gaps.minor` and `archive.minor`, and the rules for what a gap migration must satisfy. They are implemented in `completion_minor.py` (`gaps_minor_status`, `archive_minor_status`); `minor_close.py status --minor vX.Y` prints both lines, and the minor verdict (see "Minor verdict") aggregates them. The writes that satisfy them are performed only by `minor_close.py migrate` and `minor_close.py archive`, whose procedures belong to the known-gaps-tracker (Migrate mode) and docs-layout-refactor ("Archive a closed minor") skills.

**Open item.** In a known-gaps ledger, an item is a level-3 to level-6 heading whose text starts with an id of two to four capital letters, a hyphen, and letters or digits (`### WN-7 ...`, `#### WN-3: ...`, `##### WN-D - ...`, `#### DF-v24 ...`), outside fenced code (CommonMark fences: an opener of three or more backticks or tildes indented at most three spaces, a backtick opener's info string holding no backtick, closed only by the same character at least as long with nothing after it). It is resolved when its heading carries the RESOLVED marker, or the CLOSED marker archive reconciliation writes, either as its status prefix (`NI-1 - CLOSED: ...`) or at its end, optionally followed by a date or a short parenthetical (`... - RESOLVED 2026-09-22`); or when it sits under a `### Resolved...` subsection. It is migrated when its heading ends with ` - MIGRATED to vX.Y.Z`, and open otherwise, wherever it sits: an item outside an `### Open Items` block still counts, so an unusual layout reads as open work, never as none. A ledger has a **parse problem**, which makes `gaps.minor` `cannot-verify` (never met), when a fence is still open at the end of the file, when a heading, list row, or table row outside every item and outside a `### Resolved...` subsection starts like an item id but is not an item, or when its header (before the first `## ` heading) states `**Open items**: N` for an N other than the number of open items parsed.

**Scope.** Every ledger at a layout path for a version at or below the run's minor: `docs/releases/vM/vM.m/`, the legacy `docs/vM/vM.m/`, `docs/versions/vM/vM.m/`, and `docs/vM.m/`, and the archives `docs/archives/vM/vM.m/`, `docs/archive/vM/vM.m/`, and `docs/archive/versions/vM/vM.m/`. Ledgers for later versions are out of scope, so a migrated copy there never reopens the verdict and a later version's own gaps are never acted on. A ledger of an earlier minor that another live run is working on is excluded and reported as `gaps.minor excluded <path> (<reason>)`, never edited: one changed by a live branch not merged into the integration branch (`changed-on-live-branch`), or one whose minor has a not-done plan a live run owns (`owned-by-another-run`: a live per-plan record or runner lock, another live minor record listing the version, or a live `feat/<version>-*` branch; plans are read one by one, so a historical minor with two plans of one version still resolves, while an unreadable plan leaves ownership undecided). A branch is live only when it is checked out in another worktree, named as a source branch by a live run record other than this run's, or the head of an open pull request; a stale branch excludes nothing. The run's own minor is never excluded, and the run's own branches (its members' source branches, the current branch, and `chore/close-vX.Y`) are never another run's. An excluded ledger that still holds an item not resolved makes `gaps.minor` `cannot-verify`, never met.

| Id | Met when | Evidence source | Cannot verify when |
|---|---|---|---|
| `gaps.minor` | Every item in every in-scope ledger is resolved or its migration verifies, and no in-scope ledger has a parse problem. There is no deferrable state in a minor run | The ledgers; the minor record's frozen `gap-migration` list and `start_head`; `git for-each-ref`, `git ls-remote --heads origin`, `git diff --name-only <integration>...<tip>`, `git worktree list`, live run records, `gh pr list --state open`, `git show <start_head>:<ledger>` | A ledger is unreadable or has a parse problem, the integration branch or `origin` cannot be read, an unmerged tip's history is not local, which branches are live or who owns a plan cannot be decided, or an excluded ledger still holds an open item |
| `archive.minor` | Every active tree of the minor (`docs/releases/vM/vM.m/` and the legacy layouts) is absent on the integration branch and `docs/archives/vM/vM.m/` is present there; `unmet` when the record carries no `archive-minor` approval, since a minor completes only once archived | `git ls-tree <origin/develop, else develop> -- <tree>` | The integration ref or `ls-tree` cannot be read |

**A migration verifies** only forward: its target is a later minor's `.0` version, so a marker naming the item's own minor or an earlier one (a self-marker, or a cycle between two minors) is `unmet`. The target minor's ledger must hold an entry with `**Migrated from**: <source minor>#<id>` (a patch form such as `v0.5.2#WN-3` names the same item as `v0.5#WN-3`, because ids are unique per minor file), and then:

- a target at or below the run's minor needs nothing more, because the copy is itself in scope and is judged on its own: open, resolved, or migrated forward again. This is how a gap an earlier minor run migrated into this one is carried, and forward-only targets make a loop impossible;
- a target beyond the run's minor must be the next minor's `.0` version, the id must be in the record's frozen `gap-migration` list, a security or high-severity item must also be in that class's `named` list, the entry's reason must be `vendor-feature`, `user-credential`, or `user-deferred`, and the item must already exist in the source ledger at the minor record's `start_head` (a projected member reads `minor_start_head`), because an item created during the run never migrates.

Anything else, including a hand-written marker pair for an unlisted id, is `unmet`. An item is security or high-severity when its heading or enclosing `###` subsection names security, it has a `**Security**` field, or its `**Severity**` is high or critical. The approvals file names such items in `{"class": "gap-migration", "bound": [...], "named": [...]}`, where `named` must be a subset of `bound`, and the page shows `named` with the class, so the approval code covers it.

`gaps.version` applies the same check to a minor member: in a member's projection, an Open Items heading ending with ` - MIGRATED to vX.Y.Z` is closed only when its migration verifies against the minor record. In a per-plan run there is no migration, so the marker alone stays `unmet`.

## Minor verdict

This section is the single owner of the minor verdict. `check_plan_completion.py check-minor vX.Y [--json] [--session ID] [--repo PATH]`, implemented in `completion_minor.py`, prints exactly one verdict line first and exits with its code, then, for an evaluated minor, one `member.<version> met|unmet|cannot-verify` summary per member, that member's `<version>:member.gate` line and every per-plan predicate as `<version>:<id> <status>`, and the five minor-level lines. Exit codes match the per-plan check: `0` `MINOR COMPLETE`, `1` `INCOMPLETE`, `3` `BLOCKED`, `4` `PAUSED`, `2` malformed input.

| Verdict line | When |
|---|---|
| `BLOCKED: record-tampered` | The minor record fails an integrity check (see "Schema 2: the minor record"), including a member that no longer resolves by version. No predicate lines follow. |
| `PAUSED` | The record carries a pause. No predicate lines follow. |
| `BLOCKED: <category> (vX.Y.Z)` | An open blocker recorded against that member (`<category>` alone for a minor-level blocker), a frozen member now owned by another run, `member-gate` (below), or `new-member-not-approved`: a plan in the minor whose version is neither a frozen member nor in the record's signed `excluded` list and is not shipped (tag local and remote AND a published Release), whatever its Status line says. A new plan is never absorbed or archived; the run ends and the next `/implement vX.Y` opens a new approval round. No predicate lines follow. |
| `INCOMPLETE: <id> ...` | Any member line or minor-level line is `unmet` or `cannot-verify`. Member ids carry their version (`v0.5.2:release.tag`); a member the budget could not reach reads `member.vX.Y.Z`. |
| `MINOR COMPLETE <minor> <head> <nonce>` | Every member is `PLAN COMPLETE` under its projection (a `deferred` pending-migration gap counts), every started member's gate is met, and every minor-level line is `met` or `n/a`. The checker then writes `completed` into the record and re-signs it, which ends its authority; a later `check-minor` still verifies it and prints the same line, and `record block` still accepts a blocker on it. A hand-written `completed` fails the HMAC (`record-tampered`). |

Precedence: `record-tampered`, then `PAUSED`, then the blocked states in the order listed, then the predicates. A member's own verdict is its projection through `project()` evaluated by the per-plan `evaluate`, so the per-plan rules apply unchanged.

**Member gate.** A member starts only through `record member-start --minor vX.Y --member vX.Y.Z --session ID --head SHA` (`--head` is required), which refuses with `BLOCKED: member-gate (vX.Y.Z)` and a fixed `reason:` line unless the previous member is `PLAN COMPLETE` (`previous-member-incomplete`), the local `origin/<target>` equals the live remote tip (`fetch-stale`), that tip contains the previous member's release tag, which means `main` was back-merged (`back-merge-missing`), and `--head`, when given, is that tip (`head-not-integration-tip`). It then records `start_head` (and `started`) in the member entry and re-signs the record; `members` is signed, so the gate's write is a signed update and a hand edit is `record-tampered`. A second call with the same tip is a no-op; a different one is refused (`already-started`). `check-minor` enforces the gate on every check: every member after the first without a recorded `start_head` reads `member.gate unmet`, so skipping the gate can never reach `MINOR COMPLETE`; a recorded `start_head` that does not contain the previous member's release tag (or whose previous tag exists neither locally nor on origin), or that is not an ancestor of the member's merged pull request's merge commit, is `BLOCKED: member-gate (vX.Y.Z)`; a tag on origin that was not fetched is `cannot-verify`.

| Id | Met when | Evidence source | Cannot verify when |
|---|---|---|---|
| `<version>:member.gate` | The member's recorded `start_head` contains the previous member's release tag and, once its pull request merged, is an ancestor of the merge commit; `unmet` for a member after the first with no recorded start; `n/a` for the first member without one | `git rev-parse refs/tags/<tag>`, `git ls-remote --tags origin`, `git merge-base --is-ancestor` | The tag is on origin but not local, or git cannot answer |
| `members.approved` | No unshipped plan was added to the minor after approval (else the verdict is `BLOCKED: new-member-not-approved`); a late plan is excused only by its release, never by its Status line | The minor's plan files; the record's `members` and `excluded`; the shipped rule of "Minor membership" | A plan is unreadable, or whether a candidate shipped cannot be read |
| `gaps.minor` | See "Minor gaps and archive", read from the ledgers committed on the integration branch (`git show <origin/target>:<ledger>`), never the working tree: an uncommitted or unmerged migration closes nothing | `git ls-tree` and `git show` on the integration ref, then as there | The integration ref cannot be read, then as there |
| `minor.close-pr` | The closing pull request from `chore/close-vX.Y` is merged, and its merge commit is on the target branch and descends from the record's `start_head` and the last member's release tag (merged after the approval and the last release); no frozen id is still open on the integration branch; the diff from that tag to the merge touches every ledger holding a migrated frozen id and, when `archive-minor` is recorded, the archive tree; its required checks passed (as `integration.checks`); and the live target branch contains the live `main` tip (the back-merge). The branch name alone never satisfies it. Never `n/a`: the close always carries the archive, and when nothing migrates it carries only the archive. `unmet` when the record lacks `minor-close-pr` | `gh pr view --json state,mergeCommit` and `gh pr checks` for the closing branch; `git merge-base --is-ancestor`; `git diff --name-only <tag> <merge>`; `git ls-remote origin refs/heads/main refs/heads/<target>` | As for `integration.merged`, or the tips' history is not local |
| `cleanup.merged` | The Cleanup receipt rule, with the minor's last merge being the closing pull request; `unmet` without a `cleanup-merged` approval, since the final cleanup pass is part of a minor's completion | As in "Cleanup receipt" | As there |
| `archive.minor` | See "Minor gaps and archive" | As there | As there |

**Budget.** One `check-minor` has a 120-second total cap; each member gets its own share of at most 20 seconds (the per-plan budget) inside what remains, and a member reached with less than one second left is not evaluated and reads `member.vX.Y.Z` (`cannot-verify`). Any hosting or git call past its budget is `cannot-verify`, never met. `NEXUS_CHECK_MINOR_BUDGET_SECONDS` can only lower the cap. The turn-end gate runs one `check-minor --json`, whose JSON line carries `met` and `head`, so the verdict and the score come from the same evaluation; it keeps part of its budget (up to 5 seconds) back for writing a blocker, and a refusal counts toward `no-progress` only when a score was read, never when the evaluation or score timed out. A tampered, paused, or blocked verdict spends no member budget.

**Closing pull request.** The procedure (cut `chore/close-vX.Y` from the post-release `origin/develop`, migrate, archive, one push, one pull request, merge under `minor-close-pr`, back-merge, final cleanup pass, evidence file) belongs to the implement-phase runbook's "Minor driver" section and `/update release`; this section only judges its result.

## Progress score

`check_plan_completion.py score <plan>` prints `<met-count> <head> <latest-ci-run-id-or-dash>`. The gate and runner compare scores lexicographically on the met count first; a larger count or a new `HEAD` is progress. `score-minor vX.Y` prints the same three fields for a minor: the met count summed over every member's lines, each started member's `member.gate`, and the minor-level lines, and the latest run on the first unfinished member's branch (the closing branch once every member is complete). `no-progress` applies to that score.
