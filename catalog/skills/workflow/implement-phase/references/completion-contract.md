# Completion Contract

Summary: the single authority for completion predicates, run authorization and genuinely captured approval decisions.
Read this when: changing a checker, gate, runner, approval display or implement/release consent point.
Covers: trusted host mode, signed scope, automatic continuation, manual decisions, blockers, evidence and terminal verdicts.

The single definition of "done" for a full `/implement` run: the predicates a plan must satisfy, the evidence each reads, what happens when evidence cannot be read, the four verdicts, and the run record that binds a run to the approvals the user gave at its start. `scripts/check_plan_completion.py` implements this file. The installer copies it to `~/.nexus-hub/scripts/check_plan_completion.py`, so in any project every `check_plan_completion.py <subcommand>` named here, in the runbook, or in the commands runs as `python ~/.nexus-hub/scripts/check_plan_completion.py <subcommand>`; a missing installed copy is `BLOCKED: platform-unavailable`, never a reason to skip the run record; the completion gate, the runner, and `/update release` consume the checker's verdict and never re-derive it. Read this before changing the checker, a gate adapter, the runner, or any approval point in the implement or release flow.

This file is the only owner of the predicate list. Commands and skills refer to "the completion contract" and to predicate ids; they do not restate a predicate's rule.

## Verdicts

The `check` and `check-minor` completion checks print exactly one verdict line first, then one line per predicate id, and exit with the verdict's code. After an operational `record` subcommand refuses a change, preserve state, diagnose the cause under the authorization policy below, and run the completion check again. The completion check's first-line verdict controls continuation; an operation refusal supplies neither new authority nor successful verification.

| Verdict line | Exit | Meaning |
|---|---|---|
| `PLAN COMPLETE <plan> <head> <nonce>` | 0 | Every predicate is met. `<head>` is `git rev-parse HEAD`; `<nonce>` is the run record's nonce, or `-` when no record exists. When deferred gaps were accepted, the line ends with ` (N deferred)`. |
| `INCOMPLETE: <id> <id> ...` | 1 | At least one predicate is unmet or cannot be verified. Ids only, space-separated, in contract order. |
| `BLOCKED: <category>` | 3 | The run record holds an open blocker, or the record failed an integrity check. `<category>` is one value from the closed list below. |
| `PAUSED` | 4 | The user paused the run with `/implement pause`. |
| `MINOR COMPLETE <minor> <head> <nonce>` | 0 | `check-minor vX.Y` only: every member and every minor-level line is met (see "Minor verdict"). |
| (error message) | 2 | Malformed input: a plan path outside `docs/**/plans/`, a plan with no `T###` lines, an unreadable plan. Never reported as complete. |

Every line after the verdict has the form `<id> met|unmet|cannot-verify|deferred|n/a`. The checker never prints free text taken from the plan, the gaps file, `git`, or `gh` output, so a gate or runner can pass the output to a model without relaying injected text.

Precedence when several states hold: a record that fails integrity (`record-tampered`) first, then `PAUSED`, then any other open blocker, then the predicates.

## Predicates

Ids are fixed strings. "Cannot verify" always counts as unmet: offline, unauthenticated, or slow evidence produces `INCOMPLETE`, never a pass.

A path containing the token `YYYY-MM-DD` once names a dated record by its template: it is met when exactly one file with a real date in that place changed since `start_head` | The plan file; `git log --full-history <start_head>..HEAD -- <path>` | The named path is absent from the line (reported `unmet`); zero or several dated matches (reported `unmet`) |

Post-integration predicates (`release.*`, `cleanup.*`) are derived from repository and hosting state, never from checkboxes, because the tasks that produce them are ticked by the same agent the checker is judging.

Every hosting call is pinned with `--repo <owner/repo>` from the record's frozen approvals, runs with `GH_PROMPT_DISABLED=1` and `GIT_TERMINAL_PROMPT=0`, resolves `git` and `gh` to absolute paths outside the working tree, and shares one 20-second wall-clock budget for the whole check. `owner/repo` is resolved by the installed `repo_host.py`: the record's frozen repository when one exists, otherwise the `origin` URL (`https://`, `ssh://`, or `git@host:owner/repo`), accepted only when its host is the one `gh --repo` queries (`GH_HOST` when set, otherwise `github.com`). An SSH host alias is replaced by the `hostname` that `ssh -G <alias>` reports and is refused when routed through a proxy, and without a record the answer is cross-checked with `gh repo view`; an unverified host or a disagreement yields no repository, so every hosting predicate is `cannot-verify`, never a lookup of a same-named github.com repository. The rules that decide whether a push really reaches that host are in "Push route" below. `record create` refuses a push URL that does not name that approved repository; a later push-URL change makes `approval.remote` unmet and permits an `approval-not-covered` blocker even when `push-merge` was approved. Local predicates run first so an offline check still reports them.

Conditional-decline verification completes the approved-route preflight before dispatching five independent fresh remote proof queries with at most three workers. Every invocation repeats all lookups under the original shared deadline. Queued work refuses expiry, and all running workers join before success or refusal returns. Local protected-file, evidence, ancestry and tag checks remain required; no live result is cached.

### Push route

This subsection is the single owner of the push-route rule (v4.13.5 WN-2 and WN-3); `repo_host.verify_push_route` implements it, and `approval.remote` is `met` only when every step passes:

1. **Effective push remote.** The remote a plain `git push` of the record's source branch uses is resolved in git's own order: `branch.<b>.pushRemote`, `remote.pushDefault`, `branch.<b>.remote`, then `origin`. Any remote other than `origin`, whose push URL the record froze, is `unmet`.
2. **Transport overrides.** Any setting that can send the push somewhere other than the verified host makes the predicate `cannot-verify`, never `met`: `GIT_SSH`, `GIT_SSH_COMMAND`, or `core.sshCommand` for an SSH remote; for an HTTPS remote, anything that weakens or replaces TLS verification (`http.sslVerify` false, also per URL; `GIT_SSL_NO_VERIFY`; `GIT_SSL_CAINFO`, `GIT_SSL_CAPATH`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, or `CURL_CA_BUNDLE`; `http.sslCAInfo` or `http.sslCAPath` set in a global, local, worktree, or command scope) and `http.curloptResolve`, also per URL; for any remote, `remote.origin.vcs` (git then pushes through a `git-remote-<vcs>` helper), a `<transport>::<address>` URL for the same reason, `GIT_EXEC_PATH` (it replaces the transport programs), and `GIT_CONFIG_PARAMETERS` or `GIT_CONFIG_COUNT`, which inject config the checker's own git calls strip but a push would honor. The checker also strips `GIT_EXEC_PATH` from its own git calls. An empty value disables a setting and does not count.
3. **Proxies and rewrites (deliberate).** A proxy alone is not an override: `http.proxy`, `http.<url>.proxy`, `remote.origin.proxy`, and `http_proxy`, `https_proxy`, or `all_proxy` are ignored, because with TLS verification intact a CONNECT proxy cannot present github.com's certificate, so it can refuse or delay the push but cannot deliver it to another host (and `http_proxy` does not apply to an HTTPS URL at all). What would let it do so, a disabled check or a substituted trust anchor, is listed above. `http.sslBackend` is not an override: it chooses the TLS implementation, which still verifies, and Git for Windows sets it by default. A CA bundle set in system scope is not counted either, because writing system config needs administrator rights and Git for Windows' installer sets `http.sslCAInfo` there. An `insteadOf` or `pushInsteadOf` rule is an override only when the configured URL and the effective push URL (which `get-url --push` reports with the rewrite applied, and which is what the checker verifies) name different verified repositories; a rewrite such as `url."git@github.com:".insteadOf https://github.com/` is therefore `met`.
4. **git's own ssh.** For an SSH remote the host is resolved with the ssh git itself runs, found by asking git's shell for `command -v ssh`, because git spawns ssh with that PATH; on Windows an extensionless answer maps to its `.exe` or `.cmd` sibling. When that cannot be determined, or the answer lives inside the working tree, the predicate is `cannot-verify`. Every probe passes exactly what git passes: `<git's ssh> -G [-p <port>] [<user>@]<host>`, so a `Match user` or port-specific block is read as it would apply to the push. A literal accepted host (`github.com`, or `GH_HOST`) is `cannot-verify` when that probe reports another `hostname`, a `ProxyCommand`, or a `ProxyJump`, which is how a `Host github.com` block in ssh config would reroute it. An alias is resolved as described above, with the same ssh.

The checker explains a failure on stderr as `notice: approval.remote <status>: <reason id>`, with a fixed id (`push-remote-not-verified-remote`, `transport-override-<kind>`, `ssh-undetermined`, and similar), never a URL or a config value.

A hosting answer that the pull request or release does not exist (`gh`'s whole stderr line is `no pull requests found for branch "<branch>"` or `release not found`) is `unmet`, not `cannot-verify`: GitHub was reached and the run's next step is to create it. Only an unreachable, unauthenticated, or over-budget call is `cannot-verify`. The agent probes hosting the same way, always with `--repo <owner/repo>` from the record; an un-pinned `gh` call that fails is not evidence that the platform is unavailable, and never justifies merging, tagging, or releasing through `git` alone.

### Conditional full decline

A frozen minor-member plan may explicitly require "On a full decline, stop after the merge: no tag". That wording alone is not a skip flag. To qualify the observed decline, create a member-scoped `approval-not-covered` blocker with `approval_class` `conditional-outcome` and one exact request: `outcome` (`declined`), frozen `plan_sha256`, a plain `condition`, unique checked admission-conditional `tasks`, immutable `evidence` entries (`path`, SHA-256), and exact approved pull-request `head` and `merge` commits. Alternatively, qualify an existing member-scoped `platform-unavailable` blocker that has no approval class by supplying that JSON object with `--conditional-outcome FILE` to both `record render --action answer` and `record answer`. No other technical blocker is eligible. Render and answer through the existing genuine native capture flow. Both operations revalidate the entire binding; a supplied non-object is refused before capture. Ordinary blocker answers remain unsigned diagnostics; this narrow answer stores its full binding, immutable origin and capture provenance inside signed member approvals. Standalone plan records do not support this disposition. Hand-editing a blocker or writing "Approve" into evidence grants nothing.

Only frozen tasks whose prompt starts "Run only if at least one slot passed every gate.", "Run only for slots that passed every gate.", or "Run only on admission." qualify. Their named paths and backticked file references are mandatory protected inputs. Unqualified filenames resolve against the immutable original, head and merge trees as well as the current index. The declined head and merge must leave these inputs unchanged from the original start. The current tree must match that merge, or the latest qualifying later member of the same signed frozen run: its recorded start, exact source and target, green merged PR and ancestry through the live integration tip must verify. An uncommitted restoration cannot mask that later merge. Evidence must match its digest in the approved merge and its current Git content; choose captures that need no native archive link repair. The exact approved source branch, target branch, head and merge, original-start ancestry, current integration ancestry, remote route and required green checks must all verify. A local or remote release tag, a GitHub release, or inability to prove their absence rejects the no-release disposition.

An exact listed evidence path beneath this release's canonical `development/` tree is proof rather than an unchanged application input. Such a path is exempted from the protected set only while every immutable-evidence check above passes. Application files outside that tree remain protected even when supplied as evidence. This accommodates an admission task citing its newly recorded trial result.

While that signed disposition verifies, only its named checked tasks satisfy their task-path requirement without an admission edit, and `release.tag`, `release.changelog`, `release.github` and `release.main` read `n/a`. A captured decline cannot authorize a release. `release.version-sync`, every other task, tests, remote, integration, gaps, archive, closing-PR and cleanup requirements remain unchanged. New gaps gain no migration authority. Without the signed disposition, ordinary release predicates remain mandatory.

The completion anchor is the verified release tag for an ordinary member and the exact verified integration merge for an approved decline. Member ordering, controller handoff, archive readiness and closing-PR ancestry use that anchor; `shipped()` remains release-specific and does not excuse unapproved late plans. Only the canonical active plan or its authenticated archived path is eligible. The native archive transaction moves only the disposition's current plan path/hash and task-block hashes through its canonical path repair. It preserves the immutable captured origin and historical evidence bindings; arbitrary plan edits still fail signature or frozen-plan checks.

### Required evidence sections

The evidence file must carry these `##` headings, matching the implement-phase runbook's last-phase list: `Architecture refactor`, `Known-gaps reconciliation`, `Living docs architecture`, `Git-tree hygiene`, `CI/CD coverage`, `Tier 3 deep pass`, `Goal-vs-codebase review`, `Human/manual testing suggestions`, `Full-suite testing and stabilization`, `Publication and integration`.

### Cleanup receipt

An active minor controller or active worker that the cleanup executor keeps remains available through member releases until supported handoff or final minor cleanup. Record its `KEEP` reason; never override the executor or change signed roots by copying state. Pending cleanup does not block the next ordered publication admission, but every final cleanup predicate still applies to `MINOR COMPLETE`. After verified merge, canonical controller evidence preserves approved worker teardown without replacing active worker evidence before merge.

This subsection owns the `cleanup.merged` evidence. `cleanup_merged.py` (installed beside the checker) is the only code that removes a branch or worktree a run did not list; the seven checks it applies and why are in `docs/decisions/proposed/policy/2026-09-28-verified-merged-and-idle-cleanup.md`, and nothing here restates them. Per-plan runs keep `cleanup.branches` and `cleanup.worktree` for their own items and use the executor only when their record carries `cleanup-merged`, which the approval page offers for a one-plan run as well (its page then shows the cleanup rule `merged-and-idle` instead of `run-owned`).

`cleanup_merged.py --apply --receipt --plan <plan> --session <id>` (or `--minor vX.Y`) runs the final pass after the last merge and writes `<record key>.cleanup-receipt.json` beside the run record, owner-only. It refuses with `BLOCKED: approval-not-covered` and `reason: no-cleanup-merged-approval` when the record does not carry `cleanup-merged`, and prints the record's forced verdict when it is paused, blocked, or tampered. The receipt holds `kind` (`cleanup-merged-receipt`), `receipt_schema` (`1`), `scope`, `record_nonce`, `created`, `integration_branch`, `integration_tip` (the live remote tip when the pass ran, fetched so its history is local), `idle_hours` (the window the pass used; the executor refuses anything below 24), `removed` (each item as `{kind, name, remote, path}`), `kept` (each item label with its check), and `seal`, an HMAC-SHA256 under the runs secret over the canonical JSON of every other field, in its own domain so no other sealed file verifies as a receipt. The receipt carries no `schema` or `repo_root`, so record lookups by content never mistake it for a run record. No receipt is written when any item was kept for `gh-unavailable`, `remote-unreadable`, or `records-unreadable`: the pass could not see, so it prints `BLOCKED: cannot-verify` and exits 3 instead, and `cleanup.merged` stays `unmet`.

## Run record

### Location and binding

One file per run at `~/.nexus-hub/runs/<key>.json`, where `<key>` is the sha256 of the repository root, the resolved `owner/repo`, and the scope (`plan:<repository-relative plan path>` or `minor:vX.Y`), joined by newlines. The `owner/repo` is the one the verified push URL names, else the one the fetch URL names, lowercased, else empty; it is resolved without a `gh` call so the key does not depend on the network. A record written before v4.13.6 used the sha256 of the root, the raw fetch URL, and the plan path; that key is still read, and a new record for the plan moves the old file to `runs/retired/`. Because the key names mutable remote configuration, a record that is not at its key is also found by content (the same `repo_root` and the same `plan` or `minor`), so a changed remote reports `approval.remote unmet` instead of hiding the record. The directory is created owner-only (0700; owner-only ACL on Windows) and the file 0600. The record lives outside every working tree so no commit, branch switch, or `git clean` can create, alter, or delete it. The location decision and its alternatives: `docs/decisions/implemented/tooling/2026-09-25-completion-run-record-outside-the-working-tree.md`.

Schema-1 (one plan) fields: `schema` (`1`), `plan` (repository-relative path), `plan_sha256` (at approval time), `repo_root`, `remote_url`, `repo` (`owner/repo`), `session_id`, `worktree`, `start_head`, `nonce` (the approval round's 128-bit nonce, 32 hex characters; see Approval origin), `created`, `approvals`, `approvals_hmac`, `deferrable_gap_types`, `cleanup` (`branches`, `worktrees`), `blockers`, `pause`.

### Approvals as exact actions

Each approval is a tuple of exact values plus the verbatim user text that granted it: the plan path; the fetch remote URL, push remote URL, and `owner/repo`; source and target branch; release version and tag name; the branches and worktrees to remove; and each approval class with its bound. The per-plan classes are: `push-merge`, `release` (version, tag, publication, release pull requests, and back-merge for that one version), `repush` (after a locally reproduced fix, legacy consent bound 3; see scoped autonomous correction policy below), `release-notes`, `refactor-moves` (inside plan-touched folders only), `spend` (a USD cap per vendor), and one `ask-first:<surface>` per "Ask first" surface the plan names. The minor-level classes, recorded only in a schema-2 record, are `cleanup-merged` (also offered to a one-plan run), `gap-migration` (bound: the frozen list of migratable gap ids, such as `v0.5#WN-3`, plus `named`, the security or high-severity ids among them; see "Minor gaps and archive"), `archive-minor`, `minor-close-pr` (push, pull request, merge, and back-merge for the closing pull request), and the optional `archive-member` (archive each member when it is released; see "Member archive"). A minor run requires `cleanup-merged`, `archive-minor`, and `minor-close-pr`: Definition of Done for a minor is the final cleanup pass after the last merge, the merged closing pull request, and the archive, so `record render` and `record create --minor` refuse a spec without all three, and `check-minor` reads a missing one as `unmet`, never `n/a`. A per-plan approvals file that names `gap-migration`, `archive-minor`, or `minor-close-pr` is malformed. CI workflow, permission and secret changes follow "Authorization policy" below. An ordinary publication class does not grant those actions; only explicit scoped policy or a genuine manual decision can cover them.

An older signed record without `push_remote_url` yields `approval.remote unmet`; creating a fresh record from a current user approval is required before publication. A changed destination cannot be authorized by editing the old record.

`approvals_hmac` is an HMAC-SHA256 over the canonical JSON of `approvals`, `plan_sha256`, `session_id`, `repo`, `deferrable_gap_types`, `start_head`, `nonce`, and `created`, plus `schema`, `scope`, `minor`, `members`, `excluded`, and `completed` for any record that is not schema 1 (the schema-1 payload is unchanged, so existing records still verify), keyed by the owner-only secret `~/.nexus-hub/runs/.secret`, which `record render` or `record create` creates when it is absent. `pause` and `blockers` are not yet signed (v4.13.2 known gap WN-8). No prompt text, command, or skill references the secret's content. A minor record includes optional implementation_controller in this payload once native implementation admission creates it; the binding contains the canonical controller repo_root and git_common_dir. Legacy records without it sign exactly as before. Upgrade both native helpers and their gate/runner readers before the first reservation; older readers do not support the extended signed state.

### Historical scope supplement

### M5 manifest coordinator permission

The dedicated `permit-manifest` round permits only `bendourthe/Nexus-Hub` minor `v4.14`, member `v4.14.5`, to register literal `MANIFEST.sha256` as a later publication coordinator claim. Rendering and consumption require an admitted implementation, unchanged frozen plan and original implementation claims, an original-scope-clean worker, and no prior publication start or permission. ### Schema 2: the minor record

`/implement vX.Y` writes one schema-2 record for the whole minor, and while it is valid it is the only authority for every member. `record render --minor vX.Y` and `record create --minor vX.Y` (with `--session` and `--approvals`) follow the Approval origin rule below, and `record create` prints `RECORDED minor vX.Y nonce=<nonce>`. The approvals file lists the per-plan classes once, applied to every member (a `release` class is bound to each member's own version), then the minor-level classes (`spend` and `unattended-with-bypass` are among them: one cap and one decision for the whole run, shown once on the page, never copied into each member, which would multiply the cap), and optional per-member overrides (`"members": {"vX.Y.Z": {"source_branch", "target_branch", "tag", "cleanup"}}`). `defer-gaps` is refused: in a minor run a gap is fixed or migrated.

- **Identity by version.** A member is identified by its `version`, never its path. - **Integrity.** A schema-2 record is `record-tampered` when it fails any schema-1 integrity check below, when `scope` is not `"minor"` or `minor` differs from the requested token, when `members` is empty, or when a member's plan no longer hashes to its frozen `plan_sha256`. The short-reply and compatibility paths are owned by "Approval origin".

The two authorities are never merged.
- **Retire.** `record retire <plan> [--session <id>]` moves every per-plan record for the plan (keys and content matches) to `runs/retired/`, never deleting it, and refuses while a runner holds it. A completed record, or one bound to the caller's own `--session`, moves at once. Another session's live record moves only after the user pastes the line `record render <plan> --session <id> --action retire` prints, under the Approval origin rule, because retiring it removes that run's authority, pause, and blockers.

A code embedded in a longer prompt never grants authority. Runner-launched sessions with `NEXUS_RUNNER_LAUNCH=1` cannot capture their own approval.
3. **Record.** Native record writes verify the sealed challenge, current page and condition, matching action and session, genuine capture time and single unused response. The session must already contain a user prompt before rendering, preventing a fresh headless session created only to submit an answer. Creation retains the original nonce, exact authority and genuine-capture provenance in signed state. Answering closes only the bound blocker and never changes frozen approval classes, limits or scope. A short affirmative is valid because it is genuinely captured and challenge-bound, not because an agent supplied matching text.
4. **Unavailable capture.** With no verified prompt-submit or native receipt path, the write refuses with `approval-not-captured`. A terminal read, synthetic capture payload, agent-authored capture file or headless prompt is never user-origin proof. State the limitation plainly and leave the decision pending; do not repeatedly ask for code pastes that the platform cannot capture.

A refused write reports `BLOCKED: approval-not-covered` and its native `reason:` id. The existing code-bearing messages remain a compatibility path with the same whole-message, session and one-use checks, including the platform's `goal_capture` restriction. A valid pending round has no time expiry; changed conditions and consumed responses still invalidate it.

### Integrity

The checker rejects a record, reporting `BLOCKED: record-tampered`, when any of these hold: the record path is inside a git working tree or tracked by git; `plan_sha256` differs from the plan file's current hash for any change outside task checkboxes and the header Status value (a schema-1 record written before v4.13.6 froze a hash that normalized checkboxes only, and that hash is still accepted for schema 1; a schema-2 record accepts only the current hash); `approvals_hmac` does not verify; the record's `schema` is unknown. Task checkbox ticks and the header Status value are excluded from the plan hash so the run can progress. Only the FIRST `**Status**:` line above the first `## ` heading is normalized, and only when its whole value is one of `queued`, `in-progress`, `complete`, `superseded`, `shipped`, or `blocked` (optionally in backticks); any other text on that line, and every other Status line, is hashed, so an instruction appended there is an edit.

**Threat model (honest boundary).** These controls bind genuine user decisions, trusted host mode evidence and existing authority to a specific scope and condition. They reject ambiguous, stale, replayed, cross-session and agent-generated answers. A process with the user's home-directory access can still forge captures or read secrets; such fabrication violates this contract and is never a legitimate receipt. The controls are not a sandbox. Keep captured user authority distinct from automatic provenance, retain fixed-id checker outputs, and surface unresolved technical conditions honestly.

### Blockers

A blocker is an entry in the record's `blockers` list with exactly one category from this closed list, the evidence (the command run and its output, truncated to 2000 characters), and `open: true`:

`approval-not-covered`, `unreproducible-red-check`, `user-edit-guard`, `destructive-outside-approval`, `ci-security-change`, `no-progress`, `record-tampered`, `platform-unavailable`.

A blocker whose question the frozen approvals already answer is rejected at write time; consult "Authorization policy" before creating one. Repeated `record block` observations of the same open category, member, approval class and action scope reuse the existing blocker. Changed evidence updates the condition and supersedes any pending answer to its previous fingerprint. In a minor run, `record block --minor vX.Y [--member vX.Y.Z]` writes to the parent; the member remains part of its binding. `no-progress` still applies after three consecutive refusals or cycles without increased progress.

To answer a blocker, render its current question with `record render --minor vX.Y --session <id> --action answer --blocker <n> [--member vX.Y.Z] --question` (or `<plan>` for one plan), then follow "Manual decisions" and "Approval origin". `record answer` closes only that entry after genuine matching capture, retaining the frozen authority and its HMAC. An invalid index, closed entry, member mismatch or stale condition changes no record. Automatically repaired conditions use native resolution with fresh evidence and automatic provenance, never a fabricated manual answer.

An older hook can create a `no-progress` entry without a verification command. In an approved full-access run, `record resolve` may resume that sole legacy stop from the latest genuine whole-message `Continue`, captured after the blocker. It verifies the current host mode and signed correction policy, refuses a competing manual question or another open blocker, consumes that user event once, and records continuation under existing authority rather than technical repair. It grants no new approval and changes no verification predicate, retry limit, spend limit or edit-conflict decision. A command-bearing no-progress condition keeps the fresh-probe procedure.

### Pause and resume

`/implement pause` is always honored through native user-origin capture and makes the checker report `PAUSED`. Resume follows the same manual decision and capture rules, preserving original scope and limits. Repeated rendering reuses the unchanged decision. A resume alone never clears technical blockers or proves a repair succeeded.

A per-plan resume may adopt the existing signed record into the session that genuinely captured the rendered decision, matching minor-level resume. Native code verifies the original record before rendering and consuming, updates only its session binding and pause state, and re-signs it. Original approvals, cleanup scope, nonce, creation time, starting head, blockers and bounds remain intact. Pause and blocker answers still require the owning session; missing capture, a different bound session, replay or tampering grants no takeover.

### Usage-limit handoff

**Default status (2026-10-28).** No turn-end gate is registered by default: a full run ends on the checker's verdict, and `nexus-hub run-plan` resumes a session that ended before it. The gate, its usage-handoff rule below, and its hook-owned state apply only where a user opted in to it (`docs/policy/completion-levers.md` names the opt-in), and `completion_gate.py capture` still records genuine approval pastes for the approval flow.

This contract is the single owner of how the turn-end gate treats a usage-limit handoff (v4.13.7). The `usage-guard` hook and the `session-handoff` skill only produce the evidence.

On a turn end the gate allows the stop, counts no refusal, writes no blocker, and leaves the record unchanged (never complete, never paused) only when both hold:

1. A validated home-owned usage decision for the canonical project and detected platform records pending delivery, the user's submitted `wait` or `handoff` choice, or an exhausted `credits` choice in the same active usage episode. The shared decision retains its original question facts and binds submitted answers to the genuine host request and response references. Repeated hooks and goal continuations reuse it; a repository timestamp cannot grant credits or replace its answer. When no shared decision exists, conservative legacy compatibility may read the repository's `.nexus-hub/usage-decision.json` for `pending`, `wait`, or `handoff` only, with `recorded_at` later than this session's last gate refusal (or the run's `created` time before any refusal). The handoff itself is printed in chat; a `.nexus-hub/handoff.md` file is never read.
2. The usage probe (`_usage_probe.py`, through `usage-guard`'s platform detection) reports `ok`, or `stale` under 30 minutes, with a tracked window at or over `NEXUS_HANDOFF_THRESHOLD` (default 99).

The gate then prints one line on stderr saying the run stopped for a usage-limit handoff and resumes when the user pastes the handoff prompt. The run resumes through `/implement <plan>` as usual. When the probe is unavailable or below the threshold, the platform is unrecognized, or either module is missing, the gate behaves exactly as before, so a recorded answer alone never releases a run. The gate loads `usage-guard.py` and `_usage_probe.py` only from the calling hook's own directory (`NEXUS_GATE_HOOK_DIR`, set by the adapter) and never from inside the repository, so a workspace-scoped install, whose hooks live in the repository, never takes this exception. A process with the user's file access could still write a probe cache under `~/.nexus-hub/state/usage-probe/`; that residual is the same home-directory boundary as the threat model above.

### Hook-owned state

The refusal counter and the last progress score live beside the record at `~/.nexus-hub/runs/<key>.gate.json`, never inside it, so writing them never invalidates the HMAC.

### Run record lifetime

A run record never expires: its approvals hold however long the run takes, so a run can be approved now and checked much later. A one-plan record is live until the check that reports `PLAN COMPLETE` stamps it `completed` (the time and `HEAD`) and re-signs it; a minor record is live until `check-minor` stamps it the same way at `MINOR COMPLETE`. The stamp is signed once present, so adding or removing it by hand reads as `record-tampered`, while a record without it signs exactly as before. A completed record still verifies, so the same check keeps reporting its verdict, but it no longer counts as live: another run may take its plan, cleanup no longer protects its branches, and `record retire` moves it at once. A record bound to another session is ignored for that session, whatever its age. A run that is abandoned without completing stays live until the user retires it (`record retire`).

## Minor membership

This section owns which plans a minor run covers. `check_plan_completion.py members vX.Y`, implemented in the sibling `completion_minor.py`, prints one repository-relative plan path per member in semantic-version order by parsed integers (`v0.5.2` before `v0.5.10`), and one `<version> <reason>` line per excluded plan on stderr. It reads every plan under `docs/releases/vM/vM.m/plans/`, the legacy `docs/vM/vM.m/`, `docs/versions/vM/vM.m/`, and `docs/vM.m/` layouts, and the archive layouts `docs/archives/vM/vM.m/`, `docs/archive/vM/vM.m/`, and `docs/archive/versions/vM/vM.m/`, and keeps only plans whose own `**Version**` line is in the minor. Tokens are canonical: a minor token or a plan version with a leading zero (`v0.05`, `v0.05.2`) is refused, so one minor has exactly one record key.

A plan is a member when all three hold:

1. Its `**Status**` is not `complete`, `superseded`, or `shipped` (excluded as `status-<value>`).
2. It is not shipped: its tag exists locally and on `origin` AND its GitHub Release is published, whatever its Status says (excluded as `shipped`). When either cannot be read, the plan is excluded as `cannot-verify-shipped`, and `record render` or `record create --minor` stops with `BLOCKED: platform-unavailable (vX.Y.Z)` rather than rebuild a release.
3. It is not owned by another live run: no live per-plan record (not stamped `completed`; see "Run record lifetime"), at either key or found by content (an unreadable one counts as owned); no live runner lock beside either of its record keys; no other live minor record (not completed) that lists the version; and no `feat/<version>-*` branch, local, remote-tracking, or live on `origin`, whose tip is not merged into the integration branch (`origin/develop`, else `develop`) and which this minor's verified record does not list as a member's own source branch (excluded as `owned-by-another-run`). When `git ls-remote origin` fails, a plan none of these owns is excluded as `cannot-verify-owned`, and the round stops with `BLOCKED: platform-unavailable (vX.Y.Z)`, as for `cannot-verify-shipped`.

Hosting calls are pinned to the frozen record repository, else `repo_host.resolve_repo`, else the verified push URL's repository. Exit codes: `0` with at least one member; `1` with none, printing `No queued plans in vX.Y`; `3` with `MALFORMED: duplicate version vX.Y.Z` or `MALFORMED: plan unreadable <path>`; `2` for a token that is not `vMAJOR.MINOR`. An owned plan does not block the run: it is not a member, `members` reports it on stderr, and the approval page lists it under `excluded` with its reason, so the user sees what the approval leaves out. Only a plan that is already a frozen member and later becomes owned stops the run, with `BLOCKED: owned-by-another-run (vX.Y.Z)`.

## Minor gaps and archive

This section owns the two minor-level predicates a minor run's verdict reads besides its members, `gaps.minor` and `archive.minor`, and the rules for what a gap migration must satisfy. They are implemented in `completion_minor.py` (`gaps_minor_status`, `archive_minor_status`); `minor_close.py status --minor vX.Y` prints both lines, and the minor verdict (see "Minor verdict") aggregates them. The writes that satisfy them are performed only by `minor_close.py migrate` and `minor_close.py archive`, whose procedures belong to the known-gaps-tracker (Migrate mode) and docs-layout-refactor ("Archive a closed minor") skills.

`check-minor vX.Y --detail` and `minor_close.py status --minor vX.Y --detail` may show read-only gap diagnostics beneath a blocked verdict, only after the record verifies. They preserve that verdict and its exit code, never mark the run complete, and do not expose predicates from an unverified record. The former diagnoses integration-branch ledgers; the latter diagnoses the current checkout.

**Open item.** In a known-gaps ledger, an item is a level-3 to level-6 heading whose text starts with an id of two to four capital letters, a hyphen, and letters or digits (`### WN-7 ...`, `#### WN-3: ...`, `##### WN-D - ...`, `#### DF-v24 ...`), outside fenced code (CommonMark fences: an opener of three or more backticks or tildes indented at most three spaces, a backtick opener's info string holding no backtick, closed only by the same character at least as long with nothing after it). It is resolved when its heading carries the RESOLVED marker, or the CLOSED marker archive reconciliation writes, either as its status prefix (`NI-1 - CLOSED: ...`) or at its end, optionally followed by a date or a short parenthetical (`... - RESOLVED 2026-09-22`); or when it sits under a `### Resolved...` subsection. It is migrated when its heading ends with ` - MIGRATED to vX.Y.Z`, and open otherwise, wherever it sits: an item outside an `### Open Items` block still counts, so an unusual layout reads as open work, never as none. A ledger has a **parse problem**, which makes `gaps.minor` `cannot-verify` (never met), when a fence is still open at the end of the file, when a heading, list row, or table row outside every item and outside a `### Resolved...` subsection starts like an item id but is not an item, or when its header (before the first `## ` heading) states `**Open items**: N` for an N other than the number of open items parsed.

**Scope.** Every ledger at a layout path for a version at or below the run's minor: `docs/releases/vM/vM.m/`, the legacy `docs/vM/vM.m/`, `docs/versions/vM/vM.m/`, and `docs/vM.m/`, and the archives `docs/archives/vM/vM.m/`, `docs/archive/vM/vM.m/`, and `docs/archive/versions/vM/vM.m/`. Ledgers for later versions are out of scope, so a migrated copy there never reopens the verdict and a later version's own gaps are never acted on. A ledger of an earlier minor that another live run is working on is excluded and reported as `gaps.minor excluded <path> (<reason>)`, never edited: one changed by a live branch not merged into the integration branch (`changed-on-live-branch`), or one whose minor has a not-done plan a live run owns (`owned-by-another-run`: a live per-plan record or runner lock, another live minor record listing the version, or a live `feat/<version>-*` branch; plans are read one by one, so a historical minor with two plans of one version still resolves, while an unreadable plan leaves ownership undecided). A branch is live only when it is checked out in another worktree, named as a source branch by a live run record other than this run's, or the head of an open pull request; a stale branch excludes nothing. The run's own minor is never excluded, and the run's own branches (its members' source branches, the current branch, and `chore/close-vX.Y`) are never another run's. An excluded ledger that still holds an item not resolved makes `gaps.minor` `cannot-verify`, never met.

| Id | Met when | Evidence source | Cannot verify when |
|---|---|---|---|
| `gaps.minor` | Every item in every in-scope ledger is resolved or its migration verifies, and no in-scope ledger has a parse problem. There is no deferrable state in a minor run | The ledgers; the minor record's frozen `gap-migration` list and `start_head`; `git for-each-ref`, `git ls-remote --heads origin`, `git diff --name-only <integration>...<tip>`, `git worktree list`, live run records, `gh pr list --state open`, `git show <start_head>:<ledger>` | A ledger is unreadable or has a parse problem, the integration branch or `origin` cannot be read, an unmerged tip's history is not local, which branches are live or who owns a plan cannot be decided, or an excluded ledger still holds an open item |
| `archive.minor` | Every active tree of the minor (`docs/releases/vM/vM.m/` and the legacy layouts) is absent on the integration branch and `docs/archives/vM/vM.m/` is present there; `unmet` when the record carries no `archive-minor` approval, since a minor completes only once archived | `git ls-tree <origin/develop, else develop> -- <tree>` | The integration ref or `ls-tree` cannot be read |

**A migration verifies** only forward: its target is a later minor's `.0` version, so a marker naming the item's own minor or an earlier one (a self-marker, or a cycle between two minors) is `unmet`. The target minor's ledger must hold an entry with `**Migrated from**: <source minor>#<id>` (a patch form such as `v0.5.2#WN-3` names the same item as `v0.5#WN-3`, because ids are unique per minor file), and then:

- a target at or below the run's minor needs nothing more, because the copy is itself in scope and is judged on its own: open, resolved, or migrated forward again. This is how a gap an earlier minor run migrated into this one is carried, and forward-only targets make a loop impossible;
- a target beyond the run's minor must be the next minor's `.0` version, the id must be in the record's frozen `gap-migration` list, a security or high-severity item must also be in that class's `named` list, the entry's reason must be `vendor-feature`, `user-credential`, or `user-deferred`, and the item must already exist in the source ledger at the minor record's `start_head` (a projected member reads `minor_start_head`), because an ordinary item created during the run never migrates. The separate recording-only disposition below applies only to exact future opportunities explicitly required by the frozen plan.

Anything else, including a hand-written marker pair for an unlisted id, is `unmet`. An item is security or high-severity when its heading or enclosing `###` subsection names security, it has a `**Security**` field, or its `**Severity**` is high or critical. The approvals file names such items in `{"class": "gap-migration", "bound": [...], "named": [...]}`, where `named` must be a subset of `bound`, and the page shows `named` with the class, so the approval code covers it.

`gaps.version` applies the same check to a minor member: in a member's projection, an Open Items heading ending with ` - MIGRATED to vX.Y.Z` is closed only when its migration verifies against the minor record. In a one-plan run the marker closes the item only as "Single-plan carry and archive" below allows; otherwise it stays `unmet`.


### Historical reconciliation scope

Strict historical headings of the form `1.P1.A -- Title (DF, P1)` retain their raw identifier, priority and complete body. The existing named-ID grammar represents them as an injective category-prefixed alias such as `DF-1-P1-A`. Unknown forms, duplicate raw identities and alias collisions fail closed. Explicit resolved notes and legacy headings inside explicit closed audit sections keep their recorded resolution; ordinary words such as "closed" in a feature title never close work.

Additional historical carries require a genuine native answer to a `legacy-ledger-reconciliation-v1` request. The request names every additional identity individually, its immutable starting commit, source-ledger hashes, raw IDs, heading/body hashes, sole next-minor destination and exact reviewed tooling packet. Validation precedes answer consumption. A nonce-bound signed supplement grants only those identities and leaves the original frozen classes and bounds unchanged. Overlapping supplements are refused. Both ordinary migration and verification enforce the supplement's destination and preserved source bodies.

For a pre-existing technical blocker without a recorded probe, the same reviewed request may name its exact index, fingerprint, corrective IDs and literal native `probe-condition` command. Native `record bind-probe` requires that signed scope, an actual incomplete-condition observation, the sole open named technical blocker and verified ownership. It retains the original blocker and observed output in signed history, registers the exact command and a new signed freshness anchor, and leaves the condition open. `migrate --repair-scope <scope-id>` permits only the named corrective carries to the signed destination while that blocker remains open. Planning and writes hold the native minor lease with full-record byte checks; rollback restores only this transaction's unchanged writes and preserves concurrent edits.

Native resolution requires the signed binding's exact scope, fingerprint, command and timestamp plus a fresh successful matching receipt completed after binding. Changing unsigned blocker metadata, answering the bound blocker by consent, reusing a pre-binding receipt or changing a real predicate cannot close the condition. Archive, closing integration and cleanup retain their ordinary gates.

An optional `owner_retirements` list is a separate explicit part of that same displayed decision. It names each older minor authority by original path, full byte hash, nonce and member versions. Native validation requires authenticated ownership in the same repository, an older minor, unchanged bytes and no live runner. `record retire-owner` acts only after that exact grant is natively captured. It moves the original bytes to a deterministic scope-bound path under the canonical private `runs/retired/` directory and saves a signed retirement receipt. It never marks the older run or its unchecked tasks complete and never changes its project files. Other active ownership exclusions remain enforced.

Retirement holds the current and older record locks in descending minor order. An interrupted move is recovered only from its exact deterministic authenticated destination. Commit classification and rollback reacquire both locks in the same order. A durable signed receipt prevents restoration of the old owner; an uncertain commit preserves the archive and refuses. Pre-commit rollback creates the old slot exclusively, so it cannot overwrite a recreated record. A restored old slot, changed record, occupied destination, redirect outside the private retired directory, live runner or unlisted authority is refused.

Historical migration verification first retains its ordinary strict copy check. Only an ambiguous minor-qualified origin may retry the same unchanged verifier with the source section's exact patch-qualified ID. That normalized source identity must be unique within its ledger and belong to the same minor. Every destination candidate remains visible, and duplicate exact-qualified origins or altered bodies still fail.

During one `evaluate` call, the freshly verified conditional outcome flows directly to its dependent local gap proof through an internal token bound to that exact context object, original positive budget, nonce, plan hash and receipt digest. The token is never accepted as CLI/record input and is never stored on a context, record or global cache. Each new evaluation performs fresh remote verification; direct helper calls retain their fresh verification. Runtime deadlines and the three-worker ceiling are unchanged.

### Planned follow-on recording tasks

A frozen schema-2 plan can explicitly require a task to file future work as a known gap while excluding that future work from its implementation. This recording-only disposition is separate from deferring a new defect and from the frozen inherited-id migration class. It changes no recorded approval, class, budget, retry or publication limit.

Only a DF entry derived by `planned_followon_entry` from a verified minor member's exact frozen plan is eligible. The plan must have one unique `File ... as a known gap <ledger>` task, a complete one-to-one numbered phase/substep/task sequence, one matching prompt naming that plan, and explicit Reason and Suggested next step fields. The ledger must belong to the plan's minor. Unsupported or ambiguous forms fail closed.

The source heading and complete body must equal the derived canonical entry: an OPEN planned-follow-on disposition, the exact version/phase/task, plan filename, frozen plan hash, exact task hash, and the frozen prompt's reason and next step. Extra, altered, duplicated or sensitive content is not that opportunity. A new implementation or test defect cannot borrow a task id or quote to qualify. The ordinary no-new-defect rules remain in force.

A frozen plan written before that template can still carry a recording task that the template cannot derive, recognized only from its frozen wording by `recorded_followon_task`: its line names the plan's minor ledger and says it records, files, or makes a known gap; its line reconciles known gaps including a parked item; or its own sub-task prompt says "record a known gap" or "add one entry per/for each". Its entries cannot be derived, because the plan states no reason, so `recorded_followon` binds every other field exactly instead: an OPEN planned-follow-on disposition, the version with the task's real phase and id, the plan filename, the frozen plan hash and the exact task hash, then one-line Reason and Suggested next step fields and nothing after them. The title must name a scope of at least eight characters that the frozen plan states verbatim, and no other entry in the minor's ledgers may carry the same task and title. The same DF-only, non-sensitive, member-bound and archive-reconstruction rules apply, and every other new gap stays non-deferrable.

Both the member's pending-carry check and the minor migration check use the same classifier. The existing next-minor .0 migration helper performs the copy; existing visibility, title, full-body, provenance, forward-target, ownership, parser and id checks remain required. The target must remain OPEN, preserve the canonical body, and carry only the helper's user-deferred provenance and one-line migration evidence. One shared strict copy validator enforces those invariants in both write preflight, for new and reused targets before any write, and read-only verification. Other migration reasons are refused during preflight. Resolving or changing the actual study without its proving evidence is forbidden. The original inherited-id migration bound and individually named subset remain unchanged.

Legacy recording-only tasks have a separate publication-backed proof. This fallback applies only to a non-sensitive DF id explicitly frozen in the migration bound and proved absent in a reliably parsed ledger at the approved start. One frozen member plan must uniquely declare a `Create the <minor> ledger with the <scope> deferral <ledger>` task and the exact deferral title. Its source task, phase, ledger and version must match. A provisional id may differ only with the exact recorded mapping and proof that the inherited id already existed. The current entry must be unique and preserve the complete OPEN publication-time body from the verified release or signed-decline anchor; publication ancestry, plan hash and tag-object parity remain required. Malformed baseline, publication or current ledgers cannot prove this disposition. The per-member view reuses its authenticated signed disposition rather than projecting it twice. Native migration copies preserve the full body with only the existing relative-link repair and exact user-deferred provenance. Native archive recovery retains the same signed-start, unique-original and exact-repair rules described below. No historical obligation is considered closed by this exception.

After a native archive re-freezes repaired plan paths, canonical opportunity bodies keep their original hashes and scope. Historical reconstruction is permitted only in the canonical archive layout with no active source tree, archive authority present, the verified member's current path and whole plan hash matching, and its exact immutable publication-start commit recorded. The historical plan is read only at that signed start commit over the existing source layouts and same plan filename. It must have the unique same version, and applying only the existing archive link and path repair must reproduce the current whole frozen plan hash. Only then may its exact original task and canonical body match the preserved source and target entries. Arbitrary history, changed tasks or scope, ambiguous history, active layouts and missing publication anchors fail closed. The member projection carries its exact signed version, plan path and member start explicitly; a user-supplied dictionary is never verified authority.

## Member archive

This section owns archiving one member of a minor-scope run as soon as that member is released, instead of only at the minor close. It is optional: it applies only when the minor record carries the `archive-member` approval, which is minor-level, unbound, and valid only beside `archive-minor`, and which also covers the push, pull request, and merge of each `chore/archive-*` branch. A record without it archives exactly as before, verifies exactly as before, and reports no `archive.member` line. The write is `minor_close.py archive-member --minor vX.Y --member vX.Y.Z --session ID [--dry-run | --apply]`; its procedure belongs to the implement-phase runbook ("Minor driver") and `/update` ("Release scope: member archive").

**Adding the class to a running record.** A record created without `archive-member` gains it only by a genuine decision of its own: `record render --minor vX.Y --session ID --action add-class --class archive-member` prints a page that states the changed archive timing (each plan's own documents move when it is released, shared files still move at the close) and its paste line, under the "Approval origin" rule; after the user pastes that line in the record's own session, `record add-class --minor vX.Y --session ID --class archive-member [--text LINE]` consumes the captured prompt once and appends only that class, with the pasted text and an `added` provenance (`at`, the page's `page_sha256`, and the capture context), then re-signs. It refuses a completed, paused, blocked, or tampered record, a record without `archive-minor`, any other class, a paste from another session, and a round that was never pasted. Re-running it once the class is present prints `ALREADY ADDED` and changes nothing.

**What a member owns.** For member `V` of active tree `T` (`docs/releases/vM/vM.m/` or a legacy layout): its frozen plan under `T/plans/`; every entry directly under `T/development/`, `T/development/history/`, `T/research/`, or `T/analysis/` whose name starts with exactly `V-` (a file or a whole directory, so `v4.14.1-` never matches `v4.14.10-`). Everything else stays active until the minor close: `known-gaps.md`, `docs-cleanup-report*`, `vX.Y-minor-close-evidence.md`, all of `comparisons/` and `handbooks/`, every unprefixed file, and every other version's files. Each owned path moves to the same place the final archive would put it (`docs/archives/vM/vM.m/` plus its path under `T`), so the minor close later merges file by file into that destination and composes with it.

**Refusals** (each `REFUSED: <id> (<detail>)`, exit 3, nothing changed): `approval-not-covered` (no `archive-member` or `archive-minor`, or no live record in this session); `not-a-member`; `use-minor-close` (the last member in version order, which the minor close archives); `member-not-released` or `cannot-verify` with the failing id among `integration.merged`, `release.tag`, `release.github`, `release.main`, `back-merge`, and `tag-on-integration` (the member's tag on `origin/<target>`); `member-incomplete` (the plan has an unchecked task, or a member line other than `cleanup.*` and `archive.*` is not met, the member-start filter: the archive rewrites task-line paths and creates them, so it must never stand in for unfinished work); `not-on-archive-branch` (the checkout must be `chore/archive-<member>[-<member>...]`, naming only members and this one); `branch-not-on-integration-tip` and `branch-not-archive-only` (the branch must contain the live `origin/<target>` tip and carry nothing beyond it but verified member-archive commits, so the push, pull request, and merge the approval covers carry only archive content); `unmerged-branch-touches-tree` (an unmerged branch, pushed or checked out in a worktree, changes a moved or repaired path); `dirty-worktree` (rollback needs a clean checkout); `member-worktree-dirty` (the member's registered worktree has a change under a moved path); `archive-collision`; `attributes-differ` (`git check-attr -a` differs between a file's old and new path, which would change its bytes); `member-plan-cross-reference` (a repair would rewrite another member's frozen plan, which would read as tampering); `plan-bound-by-another-run`; and `link-checker-unavailable`.

**The move.** Links are repaired everywhere in Markdown and plain mentions on the usual allowlist, once per moved prefix and for exactly that prefix, so a mention of a shared path (the known-gaps file) is left as it is. The docs-layout-refactor link checker must report zero newly broken links; any failure restores the tree and the record. Like the final archive, the command commits once (`docs(archives): archive released member vX.Y.Z of vX.Y`); before that commit it signs into the member, under the record's lease, `archived = {plan_path, plan_sha256, from, original_sha256, moved, at}`: the archived plan path and its hash after repair, the original path and frozen hash, every `[old, new, blob]` entry the commit writes (renames and repaired files, each with the blob id staged at its new path), and the time. A failed commit restores the tree and removes that identity again. A re-run once nothing owned is left prints `ALREADY ARCHIVED MEMBER vX.Y.Z <path>`.

**Identity.** A member's frozen `plan_path` and `plan_sha256` never change at a member archive. Every reader that checks a member's plan (the loader, the controller handoff, the worker projection, the planned follow-on reconstruction) accepts it when the plan hashes to the frozen `plan_sha256`, or when it sits at the signed `archived.plan_path` and hashes to `archived.plan_sha256`. A hand edit of `archived` fails the HMAC, and a signed identity whose path or hash does not match the file is `record-tampered`. When a member carries `archived`, its original plan text for the planned follow-on rules is `git show <member start, else the record start>:<archived.from>`, which must hash to `archived.original_sha256`; no active-tree rule and no tree replay apply. The minor close's re-freeze records `archived.from` and `archived.original_sha256` before it overwrites `plan_path` and `plan_sha256`, unless a member archive already did, and signs its own archive commit as `archived.close_commit`.

**Verified archive commits.** A member-archive commit is identified by content, never by name or message: it has one parent and changes exactly the paths one member's signed `moved` entries name, each moved or repaired file at its signed blob id and each old path deleted (`git diff-tree --raw`). A commit that touches the same files with other content, or a signed identity whose commit never landed (a crash between signing and committing), therefore identifies nothing. A verified archive merge is a merge whose second-parent side holds only verified archive commits and that adds nothing of its own: its change against its first parent is nothing but blobs those commits wrote, or its tree equals the clean automatic merge of its parents (`git merge-tree --write-tree`), which covers an archive merged after a concurrent edit to a repaired shared file. When its other parents bring only verified archive commits but the merge cannot be shown to add nothing (its tree differs from the clean automatic merge, merge-tree reports conflicts or is unavailable, or it is an octopus merge), the merge is uncertain, and a task line on the paths its archive commits signed is `cannot-verify`, never met; a real edit on an unrelated path still counts. `git merge-tree --write-tree` writes the merged objects to the repository's object store and may run configured merge drivers.

**Landing check.** A signed archive counts only through a verified archive commit that the evaluated ref reaches (from the minor record's `start_head`). The command verifies its own commit right after making it, including that its parent is the commit it started from. When a hook or another process changed what was staged or committed first, it undoes the commit under a fresh rollback budget (soft reset, every moved, repaired, and changed path restored exactly, the identity removed, the tree proven clean) and refuses with `archive-commit-unverified`. When git cannot answer (a failed call, the budget spent), it keeps the commit and the identity and refuses with `cannot-verify`: that is the crash-after-commit state the landing check already reads correctly, and undoing a commit that may be right is worse. An archive whose plan sits in the evaluated tree with no verified commit reachable (amended, rebased over an edit to a repaired file, squash-merged, or rewritten by a hook after landing) makes `<version>:archive.member` and every task line on its signed paths `cannot-verify`, never met. A `chore/archive-*` branch must therefore land through a merge commit or a fast-forward, never a squash or a rebase that rewrites its archive commits.

**Task lines once an archive happened.** As soon as any member of the record carries `archived`, every member's `task.T###` (plain, folder, glob, and dated paths alike) drops every commit that is any member's verified archive commit or archive merge, and the signed `close_commit`. Git pathspec matching is kept, and a task path re-pointed at the archive is also searched at its original location (the active layout beside `archived.from`), so neither archive ever satisfies a task: not the archived member's, and not another member's whose tracker, shared folder, or moved path an archive commit rewrote or deleted. The `close_commit` is recognized by its signed commit id, so a squash-merged closing pull request would not carry it; Nexus-Hub merges with merge commits, which keep it.

**Claim audits.** A worker's historical claim audit, in a single-parent span, walks the span's first-parent chain and leaves out a path solely when every commit touching it there is another member's verified archive commit or archive merge; a coordinator-named, sensitive, or moved path that any other commit also changed is audited as usual. A two-parent merge already excludes those commits through its integration parent.

**Shared state of an archived member.** For a member whose record carries its signed `archived` identity (a plan in an archive folder without one reads as before), `gaps.version` of a plan in its minor's archive tree reads the minor's ledger across every layout (the active one stays until the close), and two ledgers for one minor are `cannot-verify`; reading only the archive folder, which holds no ledger yet, would read every open gap as met. `evidence.file` searches `development/` of the archive tree first and then of the active tree, since a shared unprefixed evidence file stays active. At the minor close, plans already in the minor's own archive tree are on the mention allowlist, so their references to the tree being archived are repaired too.

| Id | Met when | Evidence source | Cannot verify when |
|---|---|---|---|
| `<version>:archive.member` | `n/a` without `archive-member` (the line is then not reported). Met when `archive.minor` is met, or when on the integration branch the signed `archived.plan_path` hashes to `archived.plan_sha256` and no active tree of the minor lists a path the member owns. Required for `MINOR COMPLETE`, which the final archive satisfies; never a member-start gate | `git show` and `git ls-tree -r` on `origin/<target>` (else the local branch) | The integration ref cannot be read |

## Single-plan carry and archive

This section owns what a one-plan run (a schema-1 record) must do with the gaps it leaves open, and when it must archive its minor. It is the checker's form of the run goal's last two steps. The predicates are implemented in `completion_minor.py` (`gaps_carried_status`, `last_plan_status`, `archive_minor_status`, `empty_dirs_status`) and evaluated by `check_plan_completion.py` for a schema-1 record or no record; a minor member's projection never reads them, because the minor close owns its gaps and its archive. The writes are `minor_close.py carry --plan <plan>` and `minor_close.py archive --minor vX.Y --plan <plan> --apply`.

**Last plan.** A plan is the last of its minor when every other plan of the minor, across every layout, is superseded or shipped (its tag is local and on `origin`, and its GitHub Release is published). It is decided at check time, so a plan added to the minor later makes the running plan no longer last.

**Carrying.** `carry --plan` needs a verified run record carrying `carry-gaps`. It picks every open item in the plan's `## v<version>` section, or with `--id` the named ones. A security or high-severity item (as defined in "Minor gaps and archive") is carried only when its id is in that class's `named` list. An item is identified by its section's version and its id, because ids repeat across a ledger's version sections (`#### WN-3 (v4.13.7): ...` and `#### WN-3 (v4.13.8): ...`). When the plan is not the last, each item moves into the `## vX.Y.(Z+1)` section of the same ledger, created when absent, under the next free id of its kind in the file, with a `(vX.Y.Z)` tag at the start of its title changed to the target's, and gains `- **Carried from**: v<version>#<old id> on <date>`; both sections' Summary Open counts are re-derived. When the plan is the last, every open item anywhere in the minor's ledger instead migrates to the next minor's `.0` section, in the same form a minor close writes (a `- MIGRATED to vX.(Y+1).0` source marker and a copy with `**Migrated from**: v<version>#<id> on <date> (reason: user-deferred)`, naming the full source version so a repeated id never matches).

| Id | Met when | Evidence source | Cannot verify when |
|---|---|---|---|
| `gaps.carried` | Not the last plan: no item in the plan's `## v<version>` section is open or migrated. Last plan: no item anywhere in the minor's ledger is open, and every migrated item's copy names it in the next minor's `.0` section. In both cases, every item that was open in the plan's section at the record's `start_head` is still in the ledger: in that section, or in a later version's section with a `**Carried from**: v<version>#<id>` line, or migrated as above. A deleted item is `unmet` | The ledgers; `git show <start_head>:<ledger>` | A ledger is unreadable, ambiguous, or has a parse problem, the start ledger cannot be read, or whether this is the last plan cannot be decided |
| `archive.minor` (one-plan run) | `n/a` unless this is the last plan; then as in "Minor gaps and archive", with the run record's `archive-minor` approval | As there | As there, or whether this is the last plan cannot be decided |
| `archive.empty-dirs` | `n/a` unless this is the last plan; then no directory under `docs/releases/` is empty | The working tree | A directory cannot be listed, or whether this is the last plan cannot be decided |

`gaps.version` counts a `- MIGRATED to vX.(Y+1).0` item of a one-plan run as closed only when the run record carries `carry-gaps` and the copy names it. An item carried to a later section is no longer in the plan's section, so `gaps.version` no longer reads it.

**Archiving.** `archive --minor vX.Y --plan <plan> --apply` takes its authority from the plan's verified run record carrying `archive-minor`, and refuses unless the plan is the last of its minor. Every other closure condition of `archive` applies unchanged (a closed register, every plan released, no live worktree or unmerged branch on the tree, a clean tree on `chore/close-vX.Y`, zero newly broken links), except that a one-plan run's migrations verify as in `gaps.carried`. After the archive commit it removes every directory left empty under `docs/releases/`, then re-points the run record at the plan's archived path: the record's `plan` and `plan_sha256` are re-frozen, it is re-signed, and it moves to the key of the new path, so `check <archived plan path>` finds it. The closing pull request is the record's `minor-close-pr` approval; `archive.minor` is met only once it has merged.

## Minor verdict

This section is the single owner of the minor verdict. `check_plan_completion.py check-minor vX.Y [--json] [--session ID] [--repo PATH]`, implemented in `completion_minor.py`, prints exactly one verdict line first and exits with its code, then, for an evaluated minor, one `member.<version> met|unmet|cannot-verify` summary per member, that member's `<version>:member.gate` line and every per-plan predicate as `<version>:<id> <status>`, and the five minor-level lines. Exit codes match the per-plan check: `0` `MINOR COMPLETE`, `1` `INCOMPLETE`, `3` `BLOCKED`, `4` `PAUSED`, `2` malformed input.

| Verdict line | When |
|---|---|
| `BLOCKED: record-tampered` | The minor record fails an integrity check (see "Schema 2: the minor record"), including a member that no longer resolves by version. No predicate lines follow. |
| `PAUSED` | The record carries a pause. No predicate lines follow. |
| `BLOCKED: <category> (vX.Y.Z)` | An open blocker recorded against that member (`<category>` alone for a minor-level blocker), a frozen member now owned by another run, `member-gate` (below), or `new-member-not-approved`: a plan in the minor whose version is neither a frozen member nor in the record's signed `excluded` list and is not shipped (tag local and remote AND a published Release), whatever its Status line says. A new plan is never absorbed or archived; the run ends and the next `/implement vX.Y` opens a new approval round. No predicate lines follow. |
| `INCOMPLETE: <id> ...` | Any member line or minor-level line is `unmet` or `cannot-verify`. Member ids carry their version (`v0.5.2:release.tag`); a member the budget could not reach reads `member.vX.Y.Z`. |
| `MINOR COMPLETE <minor> <head> <nonce>` | Every member is `PLAN COMPLETE` under its projection (a `deferred` pending-migration gap counts), every started member's gate is met, and every minor-level line is `met` or `n/a`. The checker then writes `completed` into the record and re-signs it, which ends its authority; a later `check-minor` still verifies it and prints the same line, and `record block` still accepts a blocker on it. A hand-written `completed` fails the HMAC (`record-tampered`). |

Precedence: `record-tampered`, then `PAUSED`, then the blocked states in the order listed, then the predicates. A member's own verdict is its projection through `project()` evaluated by the per-plan `evaluate`, so the per-plan rules apply unchanged.

**Implementation admission.** `record member-implement-start --minor vX.Y --member vX.Y.Z --session ID --repo CONTROLLER --worktree WORKER --head SHA --claims FILE` admits implementation independently of release order. The claims JSON contains exactly `depends_on`, `read_paths` and `write_paths` arrays. Native validation binds the active parent approval, frozen member and plan hash, approved source branch, canonical linked worktree/common Git directory and proposed base; it refuses self, unknown or cyclic dependencies and requires each actual prerequisite's verified merged commit to be an ancestor of the worker base. Unknown compatibility, legacy unmerged members without verified claims, write/write or write/read overlap refuse concurrent admission. Claims use normalized literal repository-relative paths, directory prefixes ending in `/`, and case-insensitive comparison; absolute paths, traversal, malformed aliases and symlink escapes are rejected. Every changed worker path must be owned. Read claims name semantic implementation inputs. Generic broad validators may inspect a pinned isolated worker snapshot without turning every scanned file into an implementation dependency; defer broad validation to the coordinator's refreshed complete candidate and never use that snapshot result as current integration proof. A model-routing preflight reads the pinned verified orchestration baseline, never unpublished sibling changes. Actual semantic read/write dependencies remain blocking. Shared known-gaps ledgers, CHANGELOG, version/release metadata and trackers remain coordinator-only.

Implementation registration is a signed native update of `members`, preserving the original approval, nonce, frozen hashes, aggregate limits and global `start_head`. A resume is idempotent only for the same registered branch/root/base/claims. Failed, interrupted and implementation-ready workers retain reservations until their verified merged commit is an ancestor of the integration base. Agent termination is not claim retirement. No standalone child approval or automatic abandonment is implied.

**Parent-bound member projection.** `check-member --minor vX.Y --member vX.Y.Z --session ID --repo CONTROLLER [--json]` reads the parent minor approval rather than a standalone per-plan record. While implementation is active, it validates the registered worker identity, branch and frozen plan prose, then reads that worker's local task/evidence state. A missing or mismatched worker is cannot-verify, never authority to substitute another root. After independently verified merge and integration ancestry, it reads canonical merged artifacts through the controller so legitimate approved worker removal does not invalidate proof. Only the controller writes the record; worker checkboxes alone confer no publication authority.

**Member gate (publication admission).** `record member-start --minor vX.Y --member vX.Y.Z --session ID --repo CONTROLLER --head SHA [--coordinator-claims FILE]` records the publication base once. It refuses unless every evaluated predecessor predicate other than `cleanup.*` and `archive.*` passes (a valid `deferred` pending-migration gap counts), local `origin/<target>` equals the live remote tip, that tip contains the previous release tag/back-merge, and the supplied head is that tip. An unmet or cannot-verify non-cleanup predicate refuses publication. The refusal reason is `previous-member-incomplete (vX.Y.Z)`, except when the predecessor's own 20-second share (or the whole budget) ran out and no predicate is `unmet` and the member gate is neither `unmet` nor `violated`: the reason is then `previous-member-unverified (vX.Y.Z)` with a stderr notice, because slow hosting or `git ls-remote` answers prove nothing about the predecessor. Both refuse publication with the same `BLOCKED: member-gate` line and exit 3; repeating `record member-start` against unchanged state is the retry for the second. A verified `unmet` is never relabeled. Cleanup remains mandatory for final completion. Optional coordinator claims contain only `{"write_paths": ["<exact-relative-file>"]}`: native admission signs exact literal file paths traced to the frozen plan or standard release duties, rejects other active semantic read/write conflicts, and never grants CI/workflow, permission or secret authority. Only after that gate may the coordinator apply those deltas; the changed-path audit then permits the union of worker and signed coordinator paths. Original implementation tasks remain unchecked until applied and tested; complete them before comprehensive final validation. Refresh the worker's unpublished commits onto this integration base and finish affected comprehensive local validation before its first push; hosted required checks and the current member's green merged integration still precede release.

The native write records `start_head` and `started` and re-signs the member; a hand edit is `record-tampered`. A second call with the same publication base is a no-op; a different one is refused. `check-minor` still enforces `<version>:member.gate`: every member after the first without a publication start is unmet, and its recorded base must contain the predecessor release tag and be an ancestor of its actual merged result. A tag present remotely but not fetched is cannot-verify. Separate early implementation registration never weakens these release-order predicates.

|---|---|---|---|
| `<version>:member.gate` | The member's recorded `start_head` contains the previous member's release tag and, once its pull request merged, is an ancestor of the merge commit; `unmet` for a member after the first with no recorded start; `n/a` for the first member without one | `git rev-parse refs/tags/<tag>`, `git ls-remote --tags origin`, `git merge-base --is-ancestor` | The tag is on origin but not local, or git cannot answer |

An unavailable controller discovery or record-provenance observation reports `INCOMPLETE` with `controller.ownership cannot-verify` or `record.provenance cannot-verify`. An unavailable initial repository observation similarly reports `repository cannot-verify`. These observations establish neither ownership nor tampering; verified signature failures, tracked records and controller mismatches retain their existing refusal gates.

**Budget.** One `check-minor` has a 360-second total cap, including record/controller discovery, publication gates and final minor predicates; each member gets its own share of at most 20 seconds (the per-plan budget) inside what remains, and a member reached with less than one second left is not evaluated and reads `member.vX.Y.Z` (`cannot-verify`). Any hosting or git call past its budget is `cannot-verify`, never met. `NEXUS_CHECK_MINOR_BUDGET_SECONDS` can only lower the cap. The turn-end gate runs one `check-minor --json`, whose JSON line carries `met` and `head` (`met: null` when any observation is unavailable or a member exhausted its share, and `head: null` when the repository observation is unavailable), so the verdict and the score come from the same evaluation; it keeps part of its budget (up to 5 seconds) back for writing a blocker, and a refusal counts toward `no-progress` only when a score was read, never when the evaluation or score timed out. A tampered, paused, or blocked verdict spends no member budget. A member whose own share runs out mid-evaluation (as opposed to one never reached) keeps the lines it read, every lookup after the share reads `cannot-verify`, and a notice says the check can be repeated unchanged; `check-member`, `check-minor` and `record member-start` read the same share, and a share spent this way is never read as met.

**Closing pull request.** The procedure (cut `chore/close-vX.Y` from the post-release `origin/develop`, migrate, archive, one push, one pull request, merge under `minor-close-pr`, back-merge, final cleanup pass, evidence file) belongs to the implement-phase runbook's "Minor driver" section and `/update release`; this section only judges its result.

## Progress score

`check_plan_completion.py score <plan>` prints `<met-count> <head> <latest-ci-run-id-or-dash>`. The gate and runner compare scores lexicographically on the met count first; a larger count or a new `HEAD` is progress. `score-minor vX.Y` prints the same three fields for a minor: the met count summed over every member's lines, each started member's `member.gate`, and the minor-level lines, and the latest run on the first unfinished member's branch (the closing branch once every member is complete). `no-progress` applies only to a successfully observed score. An unavailable minor observation makes `score-minor` exit 1 without a numeric score; gate and runner counters remain unchanged. The runner gives minor checks the effective total cap plus 5 seconds of process overhead, respects a caller-lowered cap, and treats an outer timeout as an unavailable observation. Ledger reads reuse successful blob text only at immutable full commit SHAs within one evaluation, and branch scanning observes each exact branch-name/tip-SHA pair once; moving refs, negative reads, and authority decisions are never cached.
