# Handbook refresh procedure

`technical-documentation` owns discovery, source freshness, migration, and refresh. `document-to-interactive-html` owns the output contract in `references/dual-view-handbooks.md`. `documentation-consistency` audits the resulting links, coverage, and generated state. `/update` owns release sequencing and approvals; this procedure never bypasses them.

## Discover and refresh

1. Resolve the actual requested working tree or release candidate, including authorized uncommitted changes. Record revision and input hashes. Do not silently document `main` while preparing a different candidate. Inspect `docs/handbooks/` recursively, existing authoring instructions, generators/manifests, Markdown, topic folders, HTML, and project brand assets. Preserve the existing layout, URLs, anchors, and build entry points.
2. Refresh handbook explanations against current code behavior, interfaces, algorithms, examples, and figures, not just dates or version counts. Inventory every maintained handbook HTML, including standalone topic files outside `html/`. Exclude vendored/archived material with explicit reasons. If no handbook exists but the project has enduring technical topics needing explanation, create a focused handbook under `docs/handbooks/`; record a reasoned no-op only when no eligible material exists.
3. Use retained authoring inputs and approved design settings to update the detailed reading page and title/top-menu Presentation Mode together. Apply the shared dual-view contract, including independent depth/theme, reset-to-first entry, contextual design quality, source fidelity, and browser verification. Presentation is the handbook default; honor an explicit project/user opt-out and record it. Do not rerun presentify's design interview on every documentation refresh.
4. Migrate existing HTML in place when presentation mode or reproducible inputs are missing. Preserve the original before migration, recover the semantic content and source map, and verify every retained topic and anchor. Do not overwrite hand-authored content with a guessed extraction or claim a missing generator passed. Keep an unresolved migration as an explicit incomplete refresh.
5. Reuse the project's manifest and source layout. If none exists, retain authoring inputs in `docs/handbooks/_sources/<slug>/` with an index `docs/handbooks/handbooks.json` recording output path, source inputs/hashes, build/check commands, revision, coverage, and presentation settings. Supply a deterministic local build and read-only freshness check using the project's existing tooling or a minimal script; do not assume a generic Nexus builder implements this contract. A second unchanged build must reproduce the artifact bytes. The checker verifies inputs and output hashes without making edits or invoking an agent.
6. Run that freshness check plus source coverage and rendered dual-view QA on the final files. A clean content hash is not visual proof. Report updated, unchanged-but-verified, opted-out, and incomplete handbooks separately. A full refresh is incomplete when any eligible output remains stale or lacks its required presentation mode.

## Release timing

For a plan's final phase, refresh and verify the candidate's living handbooks before its local completion/publication gate, recording evidence with the final-phase files. When `/update release` begins after its integration prerequisites, run documentation refresh as the first content step before version changes. Recheck the actual integrated candidate; reuse evidence only when all relevant inputs and output hashes match. After version changes, rebuild and recheck any handbook that embeds changed version metadata. Release closure snapshots use the existing archive procedure; living handbooks remain under `docs/handbooks/`.

If a required source, generator, or browser is unavailable, state what remains unverified and stop the handbook completion claim. Do not convert that failure into an empty-directory no-op, a fresh date, or a structural-only pass. Tag, push, release, and back-merge retain their existing approval gates.
