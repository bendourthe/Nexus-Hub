# Handbook refresh procedure

`technical-documentation` owns discovery, source freshness, migration, and refresh. `document-to-interactive-html` owns the output contract in `references/dual-view-handbooks.md`. `documentation-consistency` audits the resulting links, coverage, and generated state. `/update` owns release sequencing and approvals; this procedure never bypasses them.

## Discover and refresh

1. Resolve the actual requested working tree or release candidate, including authorized uncommitted changes. Record revision and input hashes. Do not silently document `main` while preparing a different candidate. Inspect `docs/handbooks/` recursively, existing authoring instructions, generators/manifests, Markdown, topic folders, HTML, and project brand assets. Preserve the existing layout, URLs, anchors, and build entry points.
2. Refresh handbook explanations against current code behavior, interfaces, algorithms, examples, and figures, not just dates or version counts. Inventory every maintained handbook HTML, including standalone topic files outside `html/`. Exclude vendored/archived material with explicit reasons. If no handbook exists but the project has enduring technical topics needing explanation, create a focused handbook under `docs/handbooks/`; record genuinely excluded non-document surfaces with reasons; a missing tree or missing build input is not a no-op.
3. Use retained authoring inputs and approved design settings to update the detailed reading page and title/top-menu Presentation Mode together. Apply the shared dual-view contract, including independent depth/theme, reset-to-first entry, contextual design quality, source fidelity, and browser verification. Presentation is the handbook default; honor an explicit project/user opt-out and record it. Do not rerun presentify's design interview on every documentation refresh.
4. Migrate existing HTML in place when presentation mode or reproducible inputs are missing. Preserve the original before migration, recover the semantic content and source map, and verify every retained topic and anchor. Do not overwrite hand-authored content with a guessed extraction or claim a missing generator passed. Keep an unresolved migration as an explicit incomplete refresh.
5. Reuse the project's manifest and source layout. If none exists, retain authoring inputs in `docs/handbooks/_sources/<slug>/` with an index `docs/handbooks/handbooks.json` recording output path, source inputs/hashes, build/check commands, revision, coverage, and presentation settings. Supply a deterministic local build and read-only freshness check using the project's existing tooling or a minimal script; do not assume a generic Nexus builder implements this contract. A second unchanged build must reproduce the artifact bytes. The checker verifies inputs and output hashes without making edits or invoking an agent.
6. Run that freshness check plus source coverage and rendered dual-view QA on the final files. A clean content hash is not visual proof. Report updated, unchanged-but-verified, opted-out, and incomplete handbooks separately. A full refresh is incomplete when any eligible output remains stale or lacks its required presentation mode.

## Release timing

For a plan's final phase, refresh and verify the candidate's living handbooks before its local completion/publication gate, recording evidence with the final-phase files. When `/update release` begins after its integration prerequisites, run documentation refresh as the first content step before version changes. Recheck the actual integrated candidate; reuse evidence only when all relevant inputs and output hashes match. After version changes, rebuild and recheck any handbook that embeds changed version metadata. Release closure snapshots use the existing archive procedure; living handbooks remain under `docs/handbooks/`.

If a required source, generator, or browser is unavailable, state what remains unverified and stop the handbook completion claim. Do not convert that failure into an empty-directory no-op, a fresh date, or a structural-only pass. Tag, push, release, and back-merge retain their existing approval gates.

## Small fallback map and evidence

Reuse an existing native source map; adapt it to this schema for checking rather than replacing its generator. Otherwise maintain `docs/handbooks/handbooks.json` with `schema_version: 1`, a nonempty `handbooks` array, and optional `excluded` mapping from exact HTML paths to reasons. Discovery includes topic directories and legacy `markdown/` + `html/` pairs; archive and build-cache directories are excluded. Authored HTML fragments discovered under the living tree need an explicit source-only exclusion. No automatic folder migration occurs.

Each handbook entry contains a stable `id`, repository-relative `output`, `inputs` (all source, configuration, assets, renderer and runtime dependencies), nonempty `code_inputs` naming the inputs whose claims were reviewed, `builder` with `identity` and tracked `inputs`, an `evidence` JSON path, and explicit boolean `presentation`. A false value also requires `opt_out_reason` identifying the approved instruction. Source aliases never reassign surviving slide IDs or saved themes. Preserve existing depth, slide ceiling, agenda, anchors, authentic brand variants and independent reading alternation; only new IDs receive assignments unless policy changes explicitly.

The bundled `scripts/check_handbooks.py --root <project-root> --inventory` emits snapshots without qualifying them. Run the repository-owned build and read-only check command, review claims against the listed code dependencies, and inspect the final artifact in a browser. Retain these real review artifacts; do not certify a keyword check or a hash as semantic or visual review. The receipt JSON has `snapshot` copied from the inventory and `checks.content`, `checks.build`, `checks.rendered`. Each check requires `status: pass`, the actual repository-relative `evidence` file and its `evidence_sha256`. Rendered evidence also names `browser` and the final `output_sha256`. An unavailable check remains unavailable and blocks the complete refresh. A receipt is a review attestation, not independent proof that a human or agent performed that review.

Run `python <this-skill>/scripts/check_handbooks.py --root <project-root>` after the reviews. It reads files only, verifies source/map/builder/output/review hashes, reports the actual git revision and uncommitted state, and never invokes a generator or an agent. `--scope <id>` is allowed for explicit limited documentation work and reports that limitation; release and final-plan checks always use full scope. In Nexus-Hub, `python scripts/check_release_preconditions.py --pre-version` delegates the full check before version mutation; `--handbooks` names the same check at final-plan publication. Integration and approval gates still belong to the release workflow.

If code changes, first update its explanation in retained sources and both views, then regenerate and review new evidence. If the integrated candidate changes, run the check against that candidate; relevant input changes invalidate receipts, while an unrelated merge does not force unchanged handbook bytes to churn. A version metadata dependency invalidates only documents that track it. Evidence must not claim a clean committed revision for dirty input. Archive snapshots include the map, rebuild inputs and outputs, named for the described version, while the living tree stays in place. Native builder failures, missing legacy sources and concurrent edits preserve the original; recover sources with topic/anchor/visual parity before any replacement. The checker never repairs, overwrites, stamps a pass or hides such failures.
