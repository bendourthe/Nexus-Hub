How it works

Three things make this more than a prompt library

Skills that load themselves, hooks the model cannot talk past, and governance that holds output to written rules.

SKILLS

Procedures that auto-load

336 senior-level procedures. The agent triggers the right one from the task; three-tier loading keeps only a summary in context until one is needed.

HOOKS

Guardrails it cannot bypass

Where skills advise, hooks enforce. 31 scripts fire on tool events and block the action outright, whether or not the model remembered to be careful.

GOVERNANCE

Aligned to the project's rules

Write MUST and SHOULD norms with /constitution; every /plan checks against them and /spec clarifies a vague request before code is written.

Guardrails & Safety

Adds an extra layer of security

Every agentic platform already asks permission before a risky action. That prompt is advisory to the model, and a model can be talked past it.

Nexus Hub registers 31 hooks on the platform's own tool events, 16 of them before an action runs, and they block the action whatever the prompt said: secret scanning on every write, confirmation on destructive git operations, a large-file guard, and a memory-store guard.

It is local-first. The reverse-engineer-first MCP policy keeps search, embeddings, scraping, and generation off third-party services, and this guide itself makes zero network calls.

The concepts behind every AI-assisted project

This page explains the terms and the mechanics at a high level: what a model reads, how a prompt and its context shape one request, what an agentic platform adds, and where a harness fits. Read it once and the rest of the guide makes sense.

Tokens Definition

The units a model actually reads

A model never sees words. It sees tokens: the small pieces text is cut into first. A token can be a whole word, part of one, a punctuation mark, or a space attached to the word after it.

This is the real cl100k_base split. Other models cut the same sentence differently, so there is no fixed words-to-tokens ratio. The count matters because it is what fills the working budget, and it is one factor in speed and in metered cost.

Images are split too. Every square above holds real pixels from the picture beside it. Nine is the number in this picture, chosen to be countable; it is not a literal token count.

Prompt Engineering

Stating the job so the result is checkable

The prompt is where the job is stated. The same request can be asked in a way nobody could grade, or in a way anyone could check. That difference is the whole skill.

A useful prompt states the Query, points at the Context, defines the Goal the answer has to reach, and asks for a usable Format. Miss one and the model has to guess, and it will guess confidently.

Vague Prompt

“Look at this contract.”

  • No request: nothing says what looking at it should produce
  • No context: which contract, and which parts of it
  • No goal: nothing the answer can be checked against
  • No format: any shape is arguably correct, so none is wrong
Engineered Prompt

Summarise this contract and list every deadline. Use the signed PDF I attached, sections 4 to 9 only. Every dated obligation appears once, with its clause number. Return a table: date, obligation, clause, who owes it.

Request

Context

Goal

Format

Every part is now checkable: the request can be graded, the context is named, the goal is explicit, and the format is stated. The answer can be checked against the contract, line by line.

Context Engineering

Choosing the material the job needs

The prompt states the job. Context is the material the job runs on, and it is separate from the words of the request. It can be an image, a file or document, a project folder or workspace, or a codebase.

Context is optional, and it is not free. Everything attached shares one finite working budget measured in tokens, alongside the instructions, the conversation so far, and any tool results. Material can also be stale, duplicated, or simply too large to be worth its space.

So the skill is selection, not volume. Attaching the whole drive is not more helpful than attaching the two sections the question is about.

Context Engineering Best Practices

Attach everything in the project
files the job never touches

The material the job names gets a sliver, and there is almost no room left to answer.

  • More tokens: the budget fills with material nobody asked about
  • Slower: every attached file has to be read before anything is answered
  • Costs more: metered work is charged on what was read, not on what was needed
  • Likelier to miss: the one line that mattered is a needle in a haystack
Attach what the job names
the screenshot, guidelines, and SVG assetsroom to answer

Same budget, spent on the material the job runs on.

  • Fewer tokens: only the material the job runs on is read
  • Faster: less to read before the first useful sentence
  • Costs less: the same answer for a fraction of the metered work
  • Likelier to land: the material that decides the answer is not buried

Models

Learned intelligence, one request at a time

Learn from examples, improve through feedback

Pre-training builds a neural network's broad abilities from text, images and code. Its learned connection strengths are called weights.

Post-training can use reinforcement learning: score responses, then adjust the weights to favor better results. Training improves behavior; it does not guarantee correctness.

Agentic Platforms

Where a chatbot answers, an agentic platform can act

A chatbot answers a wide range of questions, and that is where it stops. It cannot carry out the job or change what already exists: the work surface stays untouched.

An agentic platform wraps the same model in a loop that can do things. It plans the job, delegates independent work to specialized agents, routes every action through one permission and tool boundary, checks the observations, and reports. No platform changes the machine unbidden; every capability below is conditional.

The difference is where the work happens, and what each lane leaves behind.

Having a tool is not the same as being allowed to use it. Every capability above stays conditional on this setting.

The parts that make the loop work
Planner
Breaks the goal into steps and picks the next useful one.
Specialists
Take genuinely independent subtasks and return results.
Tools
Narrow operations: read a file, edit content, run a test.
Boundary
Decides what is allowed, refused, or needs approval.
Observations
Report what actually happened, so the next step can correct.
Verifier
Checks the result against the request before reporting done.

Remove any one of these and the loop still runs. It just stops being safe, or stops being able to tell whether it finished.

Neither lane promises success. The chatbot lane hands back an answer to act on; the agentic lane, with permission, acts and shows its checks. A saved change is not a finished job either: the loop has to observe the result and say what it verified.

Harnesses

The built-in loop, and the one Nexus Hub adds

Every agentic platform already ships a harness: the built-in runtime loop wrapped around its model. It assembles the context, offers the tools, enforces the permissions, executes the actions, and feeds the observations back in. That loop belongs to the platform, and each one builds its own.

Nexus Hub is a portable workflow layer above that built-in capability. It does not replace the model, and it does not replace the platform runtime; it standardizes how the work is asked for, gated, and recorded, whichever platform is in use.

What the outer loop adds, and the artifact behind each claim
  • One catalog with host adapters: one source installs into every supported platform
  • Matched procedures load on demand, so the workflow is prompt-independent instead of retyped
  • Hooks fire on supported events — only where the host exposes the registered event
  • Written gates carry a definition of done the work must meet before it advances

    /testDrive coverage to a threshold across test tiers until it and a 100% pass rate are met.
    
          
    
            
    
              
    allUnit, then integration, then e2e, then CI — each to threshold.
    
              
    unitDrive unit-test coverage to threshold.
    
              
    integrationDrive integration-test coverage to threshold.
    
              
    e2eDrive end-to-end coverage to threshold.
    
              
    ciVerify the pipeline runs the suite and gates coverage.
    
              
    tddRed-green-refactor cycle for one feature or bug.
    
            
    
            
    Flags: --threshold overrides the 80% line-coverage target; --pass-rate overrides the 100% pass gate.
    
            
    
            
    
              
    type it like this
    
              
    
                
    > /test unit
