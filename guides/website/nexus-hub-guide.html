Installation

One command, then restart your assistant

Paste the line for your system. The installer copies the catalog into ~/.nexus-hub/, wires every assistant it detects, and preserves files you customized. There is no download to unzip first.

Windows · paste into PowerShell
> irm https://raw.githubusercontent.com/bendourthe/Nexus-Hub/main/install.ps1 | iex
macOS / Linux · paste into Terminal
$ curl -fsSL https://raw.githubusercontent.com/bendourthe/Nexus-Hub/main/install.sh | bash
  1. 1

    Check that it installed. Run either command in your assistant:

    /skills list /commands

    You should see the command cheatsheet.

  2. 2

    Restart your assistant.

    Hooks and rules load at startup, so they only take effect after a restart.

Troubleshooting
No curl

Use the wget fallback.

wget -qO- https://raw.githubusercontent.com/bendourthe/Nexus-Hub/main/install.sh | bash
One project

Add --workspace <path> to install into one project instead of globally.

Selected assistants

Add --platforms <comma-list> to limit which integrations are installed.

No prompts

Add --yes for an unattended refresh of managed files.

Upgrade

Refresh the installed catalog in place.

nexus-hub upgrade

Advanced flags and install locations are on Cheatsheets.

What it adds

Keep your platform. Add the workflow.

Use the assistant you prefer; Nexus-Hub adds reusable procedures, guardrails, and quality gates around it. The differences below map to the installer, catalog files, and GO / NO-GO gates, not to a claim that one model is smarter.

Without Nexus-Hub → With Nexus-Hub

  1. Portability

    Built-in commands stay on the assistant you set them up in.

    One catalog installs into every assistant it detects.

  2. Reusable procedures

    You re-explain the job every session.

    Skills load on demand; a command starts the same workflow each time.

  3. Enforcement

    Safety depends on the model remembering to be careful.

    Hooks fire on every action, whatever the prompt said.

  4. What survives

    The useful output lives in a chat transcript.

    Every step leaves a file that the next step reads.

  5. Team consistency

    Everyone invents their own prompt.

    One shared loop, with a written definition of done.

Foundations

What actually happens when an AI works on your project

Build the mental model behind useful AI work: how a model is trained, what a platform adds, how tokens and prompts shape one request, and how a harness makes the result repeatable.

Tokens Definition

The units a model actually reads

A model never sees your words. It sees tokens: the small pieces your text is cut into first. A token can be a whole word, part of one, a punctuation mark, or a space attached to the word after it.

This is the real cl100k_base split. Other models cut the same sentence differently, so there is no fixed words-to-tokens ratio. The count matters because it is what fills the working budget, and it is one factor in speed and in metered cost.

Images are split too. Every square above holds real pixels from the picture beside it. The nine-square grid illustrates the idea; it is not a literal token count.

Prompt Engineering

Stating the job so the result is checkable

The prompt is where you state the job. The same request can be asked in a way nobody could grade, or in a way anyone could check. That difference is the whole skill.

A useful prompt names the Goal, points at the Material, defines what Done means, and asks for a Format you can use. Miss one and the model has to guess, and it will guess confidently.

Vague

“Look at this contract.”

No goal, no finish line, no shape. Any answer is arguably correct, so none can be wrong.

Precise

Goal
Summarise this contract and list every deadline.
Material
The signed PDF I attached, sections 4 to 9 only.
Done
Every dated obligation appears once, with its clause number.
Format
A table: date, obligation, clause, who owes it.

Now the answer can be checked against the contract, line by line.

Context Engineering

Choosing the material the job needs

The prompt states the job. Context is the material the job runs on, and it is separate from the words of your request. It can be an image, a file or document, a project folder or workspace, or a codebase.

Context is optional, and it is not free. Everything you attach shares one finite working budget measured in tokens, alongside the instructions, the conversation so far, and any tool results. Material can also be stale, duplicated, or simply too large to be worth its space.

So the skill is selection, not volume. Attaching the whole drive is not more helpful than attaching the two sections the question is about.

Models

Trained patterns, used one request at a time

A model is a trained system that turns the information in a request into an output. Training happens long before your request. A platform later integrates the trained model, gathers your request and useful context such as files, workspace, documents, scripts, and lets the model process or reason over that material before returning a result.

The result can be an answer, a draft, an image, or a request to use a tool. It is not a guaranteed transcript of the model's internal reasoning.

Agentic Platform

A loop that gives the model tools

An agent platform wraps the model in a working loop. It assembles context, offers tools and permissions, carries out approved actions, returns each result to the model, and stops when the job reaches a finish condition or needs you.

The model proposes the next step; the platform owns the work surface and execution boundary. Together they can inspect material, act on it, check what happened, and report back.

Chatbot vs. Agentic Platform

Same request, different handoff

In a browser chat, the usual handoff is an answer: you carry the useful parts into the place where the work lives. In an agentic platform with access to that work surface, the handoff can be the changed material, a check of what happened, and a report.

This is not a hard capability wall. Chatbots can also gain tools, and agentic platforms can be limited to conversation. The practical question is where the work happens and what the exchange leaves behind.

Harnesses

Portable workflow discipline above the built-in loop

An agentic platform already supplies the inner harness: the runtime loop that gives a model context and tools, runs permitted actions, and feeds observations back. Nexus-Hub does not replace that runtime.

It adds a portable workflow layer: one source catalog adapted into each supported assistant's native files; procedures that load when invoked or matched; hooks triggered by supported host events rather than prompt wording; written verification gates; and durable artifacts that chain forward, such as a plan into /implement and phase history or known gaps into later work.

The platform makes the agentic turn possible. Nexus-Hub makes selected workflows portable, repeatable, and auditable.

Nexus-Hub Harness

One governed loop that leaves a durable trail

Follow one job — fix the thing that keeps failing — through both setups. Same model, same permitted material, same platform loop. A host-native run can inspect, change, verify, save the result, and report it.

With Nexus-Hub, that same loop also loads the matched procedure, follows a written gate, and leaves durable plan, test, history, and known-gap artifacts for the next workflow. The added value is not extra model intelligence; it is portable process and a checkable trail.
