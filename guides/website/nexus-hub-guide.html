Nexus-Hub is the experience layer for AI coding assistants

A reusable, multi-platform harness: a catalog of skills, slash commands, hooks, agents, and rules that an installer copies onto your machine and wires into the assistants you already use. The model still supplies knowledge and reasoning. Nexus-Hub supplies reusable procedures, governed workflows, deterministic guardrails, durable artifacts, and quality gates.

The same loop works on Claude Code, Codex, Cursor, Gemini / Antigravity, and GitHub Copilot. OpenCode receives the same command bodies through its instruction file, without a slash menu.

Install

One command, then restart your assistant

Paste the line for your system. The installer copies the catalog into ~/.nexus-hub/, wires every assistant it detects, and preserves files you customized. There is no download to unzip first.

Windows · paste into PowerShell
> irm https://raw.githubusercontent.com/bendourthe/Nexus-Hub/main/install.ps1 | iex
macOS / Linux · paste into Terminal
$ curl -fsSL https://raw.githubusercontent.com/bendourthe/Nexus-Hub/main/install.sh | bash
  1. 1

    Check that it installed. Run either command in your assistant:

    /skills list /commands

    You should see the command cheatsheet.

  2. 2

    Restart your assistant.

    Hooks and rules load at startup, so they only take effect after a restart.

Need another option?

No curl? Use wget -qO- https://raw.githubusercontent.com/bendourthe/Nexus-Hub/main/install.sh | bash. Scope one project with --workspace, limit assistants with --platforms, or skip the conflict prompt with --yes. Refresh later with nexus-hub upgrade. Advanced flags and what lands in ~/.nexus-hub/ versus per-tool config are on Cheatsheets.

Commands, skills, hooks, agents, and rules

Commands are slash entry points. Skills are procedures the agent loads when the task matches. Hooks are scripts that fire on tool events. Agents are specialist reviewer personas. Rules are per-language style and security standards. Details stay in Cheatsheets.

The loop

One governed loop, from first look to shipped

Every project runs the same sequence. Each command reads what the previous one wrote, so nothing lives only in chat scrollback.

/describemap it → /reviewjudge it → /plandecompose it → /implementbuild it → /testharden it → /updateship it

Foundations

What actually happens when an AI works on your project

Five minutes, four ideas: the model, the platform that gives it hands, the context it actually sees, and the harness that turns it into a governed teammate. No marketing — just the mental model the rest of this guide builds on.

The model: text in, text out

A language model does one thing: given everything in the current request, it predicts useful next text. It is very good at that. It also has no hands — it cannot open your files, run anything, or remember what you did yesterday. On its own, it can only talk about your work.

The platform: the loop that gives it hands

An agent platform — Claude Code, Codex, Cursor, Antigravity, Copilot — wraps the model in a loop. The platform shows the model your project; the model replies with something to do; the platform does it and hands back what happened. Round and round until the job is done. That loop is what people mean by an agent.

Context: what the model actually sees

The model sees exactly one thing: the context window — the text the platform packs into this turn. The rules, the job, the relevant excerpts, the results so far. Pack it with the right material and the answer lands; pack it with noise and the model confidently changes the wrong thing. Choosing what the model sees is context engineering, and it is half the game.

The harness: procedure, not vibes

Nexus-Hub wraps that loop in four guardrails. Skills load a written procedure the moment the job matches one. Commands start the same workflow every time. Hooks fire on every action, whatever the prompt said. Gates hold the work to a written definition of done.

The model still does the thinking. The harness decides how the work is allowed to happen.

One job, two runs

Follow one real job — fix the thing that keeps failing — through both setups. Same model, same project. The unharnessed run answers in chat and evaporates when the tab closes. The harnessed run loads the right procedure, works the loop, gets stopped once by a guardrail, passes the gate, and leaves a finished result plus a written trail. The difference is not intelligence; it is what survives the session.
