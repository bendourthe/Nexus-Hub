Internal walkthrough

Take an untested codebase to a coverage target you can defend.

Four Nexus-Hub commands, run in a fixed order, with the measurement step deliberately separated from the step that writes the tests. This page shows what each command reads, what it writes, and which gate has to go green before you move on.

SHAPE

Why the order matters more than the commands

Anyone can run a coverage tool. The reason this sequence holds up under review is that the command which measures coverage is contractually forbidden from changing code, so your final number is produced by a different tool than the one that wrote the tests.

/review is read-only by contract. Its own definition states that every scope "analyzes and reports; remediation goes into a plan, not into the working tree". It cannot quietly add a test to make its own report look better.

/test and /implement are the mutating commands. They generate test files, run suites, fix failures, and commit. They are the only two that touch your working tree in this workflow.

Measure with the tool that cannot write. Write with the tool that cannot grade.

That separation is what makes step 4 (the iteration) meaningful. When you re-run /review coverage after a phase, you are getting an independent read, not a restatement of what the generator believed it accomplished.

Read-only lenses /review at every scope: structure, quality, coverage, security, pentest, changes, deps, sbom, skill-scan.
Mutating commands /test writes and runs tests. /implement writes code, lints, tests, then runs the post-phase docs and commit sequence.
Planning only /plan writes a plan document under docs/. It does not touch source.

WALKTHROUGH

Five stages, in order

Scroll the right column. The pipeline on the left tracks where you are, and you can click any node to jump to it.

Stage 1 / establish the baseline

Find out where you actually are

Before any target is chosen, get an honest read of current coverage, the pass and fail counts, and specifically which paths are uncovered. The coverage scope delegates to the codebase-review lens and does gap identification, not just a percentage.

Stage 1
# read-only: reports coverage and names the uncovered paths
/review coverage

# wider read before a big push: adds structure, quality,
# security, and the pending-diff lens, then one verdict
/review full
ReadsSource tree, existing suite, coverage output
WritesNothing. Read-only by contract.
You getCoverage now, pass/fail counts, named gaps

/review full also emits a project-health block (git, version, branch model, baseline docs, per-version docs tree). On a codebase nobody has governed yet, expect MISSING rows and a pointer to /setup project.

Stage 2 / commit to a number

Turn the gap into a phased plan

Every planning scope runs a goals-first step before decomposition: fix the target, the persona, and an observable definition of done. This is the step people skip, and skipping it is why "add more tests" campaigns drift. "80% line coverage on the payments module, 100% pass rate, enforced in CI" is a definition of done. "Better coverage" is not.

Stage 2
# goal + definition-of-done only, no full plan yet
/plan goals reach 80% line coverage on the payments module

# the phased plan itself
/plan feature

# optional: living progress tracker, and GitHub issues
/plan todos
/plan issues
ReadsCodebase, strategy anchor, prior known-gaps
Writesdocs/v<M>/v<M>.<m>/plans/vX.Y.Z-<slug>.md
You getPhases, per-phase tasks, per-phase model tier

Two things the plan contract guarantees. Each phase's testing sub-task also creates or updates CI/CD for that phase's changes, so coverage enforcement lands incrementally rather than as an afterthought. And every plan ends with a mandatory final phase: architecture refactor, known-gaps reconciliation, and CI/CD.

Stage 3 / build one phase at a time

Implement, with the gate at the end

One command per phase. It resolves the plan and phase, reviews the phase against the codebase, works subtask by subtask, lints, runs the suite with coverage, augments missing tests, then enters a troubleshooting loop until a GO / NO-GO gate passes. Only then does it run the post-phase sequence.

Stage 3
# first incomplete phase of the discovered plan
/implement next

# or name the plan slug and the phase explicitly
/implement payments-coverage phase-2
ReadsThe plan phase, the codebase, the suite
WritesSource, tests, CI config, docs, devlog, commit
You getA green phase plus a known-gaps entry

The post-phase sequence is the part that keeps the loop honest: gitignore check, test review, CI/CD check, known-gaps update, docs cleanup audit, devlog, documentation, session history, commit message, then a commit-and-push prompt. Nothing is tagged or pushed automatically.

Stage 4 / the workhorse

Drive the number with two gates

This is the command that actually generates tests, and it runs a loop per tier: analyze uncovered paths, generate tests for them, run the suite, check both gates, repeat or advance. Both gates, not one: coverage at or above threshold and a 100% pass rate on generated tests.

Stage 4
# unit tier only, explicit threshold
/test unit --threshold 80

# every tier in order: unit, integration, e2e, then ci
/test all --threshold 85 --pass-rate 100

# red-green-refactor on one specific bug or feature
/test tdd
ReadsCoverage report, uncovered paths in scope
WritesTest files, fixtures, CI wiring
You getPer-tier summary: coverage before/after, tests added

Threshold precedence is worth knowing: when your project config (pyproject.toml, a vitest config, a CI gate) already declares a stricter threshold than the one you passed, the stricter value wins and the command says so. You cannot accidentally lower your own bar from the command line.

Stage 5 / close the loop

Verify independently, then re-plan the remainder

Re-run the read-only lens. If the target is met, review the diff and ship. If it is not met, the shortfall is already written down: each phase appended its gaps to known-gaps.md, and the categories include MT (missing tests / coverage gaps) and QG (quality-gate gaps).

Stage 5
# independent re-measure with the read-only lens
/review coverage

# multi-agent persona review of the test code you just added
/review changes

# short of target? a new plan ingests the open gaps
/plan feature
ReadsSuite, coverage, known-gaps.md, the diff
WritesNothing on review; a new plan on plan
You getAn independent number and a carry-forward list

This is the mechanism that makes the second iteration cheap. /plan reads the immediately prior version's known-gaps.md plus any older still-in-progress files, and offers to ingest the open items into the new plan. You do not re-derive what was left over.

GATES

What "done" is allowed to mean

Three verdicts exist, and only one of them is a clean pass. The value of naming the middle one is that it stops a conditional pass from being quietly recorded as a full one.

GO

Both tier gates green

Coverage at or above the threshold, and a 100% pass rate on generated tests. The tier advances, or the phase completes.

GO WITH CONDITIONS

Shippable, with the shortfall written down

The remainder is recorded in known-gaps.md under MT or QG, with a source phase, a plan reference, a reason, and a suggested next step.

NO-GO

The troubleshooting loop owns it

Failing tests get fixed before re-checking. Correct the test when the test is wrong. Correct the code only when it is genuinely buggy and in scope.

The last distinction is the one to hold onto during a coverage push. A generated test that fails is not automatically a bug you found. Most of the time it is a test that encoded a wrong assumption about the code, and rewriting the source to satisfy it turns a coverage exercise into an unplanned refactor. The rule is explicit: fix the test when the test is wrong, and only touch the code when it is genuinely buggy and in scope for the phase you are in.

Gap categories NI not implemented, DF deferred, BG bugs, WN warnings, MT missing tests, QG quality-gate gaps.
Where it lives docs/v<M>/v<M>.<m>/known-gaps.md, one file per minor version, appended per patch.

    TRAPS

    Five ways this goes wrong

    Each of these is a real failure mode with a specific mechanism, not a general caution.

    Treating the coverage percentage as the goal

    Coverage measures which lines executed, not whether anything was asserted. A suite can execute 85% of your lines and verify almost nothing, and it will pass the threshold gate cleanly.

    This is why the second gate exists, and why /review coverage does gap identification rather than just reporting a number. When the percentage matters commercially, add mutation testing to prove the tests actually detect changed behavior.

    Skipping the goals-first step because the goal "is obvious"

    "Add unit tests to the codebase" is not a definition of done, so the plan that follows it has no stopping condition and no way to fail. Every phase looks like progress and no phase is ever the last one.

    The goals step costs one exchange and produces the thing you will be judged against: a target, a scope, and an observable condition. /plan goals runs only that step and stops.

    Rewriting source code to satisfy a generated test

    A generated test that fails is usually a wrong assumption about the code, not a discovered bug. Changing the implementation to make it pass converts a coverage task into an unplanned behavior change, and it does so inside a commit whose message says "tests".

    The stated rule: correct the test when the test is wrong, and correct the code only when it is genuinely buggy and in scope for the current phase. Anything else becomes a known-gaps entry for a later phase.

    Fanning out across the whole codebase on the first run

    Both /test and /review can fan work out in parallel across a large surface. That path carries roughly a five to fifteen times token multiplier, so pointing it at an entire unfamiliar repository as the first action is expensive and hard to steer.

    Calibrate on one module first, confirm the generated tests look the way you want, then scale. The scope-first caution is part of the command definition, not an optional nicety.

    Letting the shortfall live in your head instead of known-gaps.md

    If phase 3 ends at 71% against an 80% target and that fact only exists in the session transcript, the next plan starts from nothing and someone re-derives the same list a week later.

    The post-phase sequence appends it for you, and the next /plan ingests open items automatically. The failure mode is bypassing the post-phase sequence, usually by stopping right after the tests go green.

    • 1. /review coverage
    • 2. /plan goals then /plan feature
