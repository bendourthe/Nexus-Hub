## Overview

A reader opens an ordinary handbook, reads its detailed page, and can select "Present this handbook" from the title page to show a presentation at the chosen concise, balanced, or deep-dive depth. Both views use the same facts, figures, and data. The presentation has useful navigation, Replay, progress, accessible keyboard behavior, readable mobile layouts, and a reliable return to the page. Standalone presentify asks whether to include presentation mode, recommending Yes, then asks its theme and depth together only when enabled. Handbook maintenance includes presentation mode by default and retains the saved project theme and depth policies.

A documentation update inventories the project's handbook set, checks its claims against the selected code revision, updates affected sources, builds affected HTML, and verifies every required output. Release preparation runs the same work before the version bump, using the exact release candidate after the existing integration preconditions pass. Existing handbooks receive the presentation capability in place; source Markdown, APIs, spreadsheets, paths, branding, and authored detail remain intact.

"Single shot" means one user request includes extraction, authoring, deterministic assembly, automated inspection, and bounded internal repair before delivery. It does not mean a promise of perfect unverified output from one model call. Production-ready means content, semantic visuals, structure, and behavior all passed on the final bytes; a browserless or exhausted run is a clearly labeled draft or blocked release, never a visual pass.

### Contract decisions

1. **One reading page, optional presentation mode**: every new output starts as an ordinary scrolling website. Ask whether to include presentation mode, recommending Yes. When enabled, there is one hero entry control; no detached presentation-only page section. When disabled, deliver the complete scrolling page without a deck, hidden deck payload, or presentation CTA. Initial page navigation, search, anchor links, and detail remain useful in either case. The deck follows the selected depth with claim-based headings, an optional outline for longer stories, chapter dividers where useful, content-specific composition with readable evidence, complete qualifiers, and continuations only within the recorded slide budget; a bullet quota never determines coverage. Short subjects must not acquire filler slides to meet a template. Handbook documentation/release maintenance retains presentation mode enabled by default.

2. **Separate page canvas from presentation inclusion**: remove "Slide deck (16:9, arrow keys)" from the output-format menu. Keep full-width scrolling, standard scrolling column, and portrait scrolling canvas plus a free-text layout response. Add `--presentation yes|no`, `--presentation-theme light|dark|mixed`, and `--presentation-depth concise|balanced|deep-dive` for explicit and automated callers. Legacy `--nav slides` becomes a compatibility alias for including presentation mode, with a one-line migration note; it no longer makes the deliverable start as a deck. Legacy `--nav scroll` only binds the reading-page start and does not imply No to presentation. Explicit `--presentation no` wins over a legacy slides alias or supplied theme/depth, with a brief note that the inapplicable option is ignored. A theme or depth flag alone implies presentation enabled. Explicit values suppress only their corresponding questions. `--layout` governs the scrolling canvas; the deck uses its own responsive composition. `--mode deck|report|compile` continues to describe source organization, not the output format. Existing slide deep links remain supported when the deck is enabled without assuming a fullscreen permission gesture.

3. **Fullscreen and input lifecycle**: user-gesture entry prefers native fullscreen. Denial/unsupported APIs leave a named, usable viewport presentation with visible Exit. Native fullscreen exit and Escape restore the page and origin focus; nested lightboxes get first Escape before deck exit. Navigation keys defer to editable fields, chart controls, code/table scroll regions, and composing text. Repeated open/close/replay, rapid navigation, resize, and hash changes must not strand state.

4. **Shared truth with separate interaction state**: each figure has a stable source key; page and deck use the same canonical data/definition. Zooming or hiding series in one view must not silently change the other view's starting state. Different teaching illustrations can express the same fact, but are identified as separate visual explanations and linked to source claims; they do not duplicate raw numeric models or masquerade as the same figure.

5. **Source retention and deterministic assembly**: retain authored page content, storyboard, figure definitions, theme tokens, and asset sources under the project. Default new managed sources may live at `docs/handbooks/_sources/<slug>/`; keep existing layouts and native generator inputs when present. A small explicit source/output map lives at `docs/handbooks/handbooks.json` unless an existing equivalent already owns that mapping. Builds are deterministic from frozen inputs; AI performs content updates upstream, never inside `--check`.

6. **Current truth**: a standalone docs run resolves the requested branch/revision or current working tree and records uncommitted source hashes where applicable. A release run first proves the existing integration prerequisites, then refreshes against the exact releasable candidate tree. Do not hardcode "current main" when the candidate is still on integration, and do not label it released before publication. Unchanged mapped source content can retain output bytes across unrelated commits; the release verification record carries the checked candidate separately.

7. **Inventory versus rewrite**: full docs/release runs inspect every live handbook HTML, including the atlas and component companions. Regenerate changed/stale outputs only after initial migration. Missing sources on an existing HTML file are a migration need, not an excuse to omit it. Preserve the original while capturing a maintainable source/model and verify topic/figure parity before replacement. A missing handbook tree is bootstrapped with a useful project overview and relevant architecture/usage material from actual code; do not generate an arbitrary quota of documents.

8. **Quality floors win over geometry**: the source 1600x900 canvas is a desktop composition baseline, not permission to scale text into unreadability. Retain the current 16px body / 13px secondary / 12px interactive rendered floors. Chart/diagram labels have explicit measured roles; no 11-design-pixel global exception. Rearrange within the logical-slide budget and provide a useful mobile reading/reflow view. On supported presentation viewports, reserve actual control space and require a scrollbar-free stage in every authored state. Do not hide overflow or silently add slides. Identify unsupported presentation sizes honestly and offer the reading view. Measure native CSS pixels after transforms.

9. **Brand continuity and intake**: full project documentation maintenance reuses committed project tokens and presentation-theme/depth policies and runs without repeated aesthetic interviews. Explicit current user instructions win. Standalone presentify keeps design direction, scrolling canvas, interactivity, and imagery choices; add the presentation-inclusion question to that initial batch and ask the unresolved theme and depth choices together only after Yes. The removed "presentation style" is the slide-deck output-format choice shown in the screenshot, not the separate design-direction question. Stock/AI assets remain opt-in under existing boundaries; automatic handbook updates use local/procedural assets and do not acquire new outbound dependencies.

10. **Production-readiness status**: required content, structural, semantic-visual, and behavioral gates must all pass on final bytes. Missing browser capability, missing source inputs, a runtime defect, or an exhausted repair budget records a non-pass with exact reason. A standalone run can return a clearly labeled draft; a release requiring those handbooks stays blocked. A known-gap entry is evidence of the block, not a waiver that makes failed output pass.

11. **Presentation-theme policy**: when presentation is enabled, offer "Light theme only", "Dark theme only", and "Random light/dark mix to catch attention". Light-only and dark-only govern every slide, including cover, outline, chapter dividers, content, controls, diagrams, charts, code, and progress indicators; the source example's dark-divider/light-content pattern must not override either choice. Mixed mode assigns complete light/dark palettes per slide during authoring, uses both palettes when there are at least two slides, and avoids long runs of the same palette. Save the seed and the resolved theme per stable slide ID in the retained storyboard/design record. Repeated builds, Replay, back/forward navigation, and reopening never reroll themes. Theme changes occur only between slides, never as flashing or animation within a slide. The reading-page theme remains independent. Respect brand colors and measured contrast on every assigned palette. A one-slide deck records its single chosen palette rather than pretending to alternate.

### Presentation depth and coverage

Presentation depth is independent of `--verbosity`, which controls how much source material becomes the main page. The presentation derives from the resulting main page: a deep dive covers that entire page, even when the page itself was distilled from a larger source. Theme and depth are asked together in one conditional follow-up after Yes; an explicit value suppresses only its own question.

| Depth | Content contract | Coverage proof |
|---|---|---|
| Concise and compact | Present the main message, key findings, essential visuals, decisions, and material caveats in a short narrative. Summarize or omit supporting detail explicitly. | Map included, summarized, and omitted page content with reasons; retain qualifications necessary to keep the main message accurate. |
| Balanced | Cover every major topic with its key explanation, representative figures/examples, and important caveats. Summarize lower-level detail. | Every major page section maps to slides; detail omissions/summaries are recorded without losing a major conclusion or limitation. |
| Deep dive | Present all substantive main-page content, including explanations, subsections, figures, tables, code, examples, caveats, and appendix content, within the applicable logical-slide budget. Rephrase for speaking without removing meaning. | Every substantive page content unit maps to an authored slide/state. No omitted content or link-back-only substitute; page navigation chrome and decorative elements are not content units. |

Add `--presentation-depth concise|balanced|deep-dive`. A depth flag alone implies presentation enabled; explicit `--presentation no` still wins and ignores supplied depth with a brief note. Record depth and the page-to-slide coverage map in retained authoring inputs. Save the chosen depth per handbook; subsequent docs/release updates preserve it. Non-interactive new handbooks use balanced unless a project policy specifies another depth. Do not infer depth from the page's verbosity, theme, file size, or source format.

Depth controls coverage within the applicable slide budget and never waives readability. For an existing slide deck or slide PDF, default to no more logical slides than the source, including cover, dividers, and appendices. Preserve the count or consolidate redundant material with a complete source mapping; do not expand merely because deep dive was selected. The local 68-page board case has a maximum of 68 presentation slides. For a handbook or non-slide report, retain an audience/time/content budget instead of inventing a page-count ceiling. Explicit current user constraints win, and saved budget policies survive docs/release refresh.

Author an effective composition for each message, comparison, or evidence set; no universal four-bullet or one-figure quota determines coverage. Use progressive builds within one coherent composition when useful, with Replay and an inspectable complete state. Unrelated full-screen panels must not be disguised as one slide to evade the ceiling. Continuations are permitted only within the recorded total budget. A deep dive must not shrink text, omit detail, substitute original screenshots, or rely on an unvisited detail drawer to satisfy its contract. If full coverage, readable fit, and the count remain incompatible after composition work, report the conflict and the bounded decision needed; never silently downgrade depth or expand count. Every slide and authored state remains in the QA inventory.

No skips both theme and depth questions and the entire deck authoring/QA path; page QA still runs. Changing Yes to No clears pending theme/depth questions and deck work. Non-interactive callers use Yes plus saved project theme/depth policies, otherwise mixed and balanced. Documentation/release automation keeps presentation enabled and preserves these policies without interviewing once per handbook; newly introduced handbooks use mixed and balanced when no policies exist. An unanswered question in an interactive run is not consent to a choice. This conditional follow-up is intentional and does not restart unrelated design questions.

### Positive design and viewport qualification

Pattern review must challenge overcorrected plainness as well as generic ornament. Gradients, shadows, curves, rounded surfaces, accent rules, strong typography, and purposeful animations remain available when the supplied references and content justify them. Do not transfer application-shell prescriptions such as a single theme or blanket hero/card bans into every document format. The design owner records the requested visual direction, authentic brand assets, type hierarchy, palette roles, depth/surface treatment, composition families, and motion intent. A minimal aesthetic is valid when chosen for the task; it is not a safe universal fallback after criticism.

Before expanding a full artifact, author representative cover, narrative, complex figure, dense table, and chapter-transition treatments in both enabled views. Compare them against the user's accepted references and evaluate hierarchy, clarity, use of space, visual character, and explanatory motion. This is an internal authoring gate, not an extra mandatory user approval or a restart of answered intake. Missing quality requires redesign, not a high technical score or added effect quotas. For this source family, retain the reference's stronger headings, coordinated color, layered visual fields, purposeful curves/surfaces, and staged figure explanations. Other projects retain their own approved language. Documentation and release regeneration must preserve the saved brief and demonstrate that it still works with changed content.

Motion is authored per composition: nonblocking reading reveals and compact chapter transitions; presentation entrance, staged explanation, chart/edge drawing, emphasis, and Replay where they aid understanding. Respect the chosen intensity and reduced-motion instant content. Do not use random theme flashing, constant ornamental loops, or force motion into static document formats. Verify initial, intermediate, final, Replay, and interrupted states separately from the static composition.

Viewport QA must go beyond named device samples. Record actual CSS/visual viewport dimensions, available stage dimensions after chrome, and device-pixel ratio; record browser zoom/display scaling when actually exercised, without inferring them from screenshots. Exercise every relevant layout breakpoint immediately below, at, and above its boundary, plus resize transitions and representative wide/short desktop windows. Include supported zoom conditions through a real browser mechanism; changing only device-pixel ratio is not proof of browser zoom. The observed 850/851-height failure and ordinary 1280x720, 1536x784, and 1920x900 cases become neutral regressions. An explicit exploratory table region does not waive the required presentation's stage-fit or coverage contract. Occupancy measurements diagnose layout; they are not aesthetic pass thresholds.

Final verdicts for source fidelity, engineering behavior, and reference-calibrated design are independent and all required. Record rejected output as rejected even if selected checks pass. Neutral tests must include a technically valid but underdesigned artifact and a legitimate rich brand treatment so neither minimalism nor decoration becomes the automatic answer.

It must not push, open a pull request, or start remote CI. Record new commands, dependencies, environments, test paths, and artifacts as CI impact; edit pipelines only in Phase 7. Use repository-native commands discovered in the active checkout; where Make is unavailable, run its exact underlying commands.

Paths proposed below are deliberate implementation targets, not claims that files already exist. Existing files can be extended instead of adding proposed helpers if that is sufficient and the same acceptance contract holds. `construction-debt: no second extractor, no second chart framework, no new MCP or skill by default, no generic migration platform, no mandatory browser installation during planning`.

Phase evidence goes to `docs/releases/v4/v4.9/development/interactive-handbooks/`; session histories go to `docs/releases/v4/v4.9/development/history/`. Evidence records source/build/output hashes, actual commands, inspected counts, results, and limitations. Use neutral fixtures in tests; keep private source material out of distributed bundles.
