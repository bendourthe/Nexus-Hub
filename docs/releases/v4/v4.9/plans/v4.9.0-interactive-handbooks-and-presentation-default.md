## Overview

A reader opens an ordinary handbook, reads its detailed page, and can select "Presentation Mode" from the title page or global top menu to show a presentation at the chosen concise, balanced, or deep-dive depth. Global entry always starts at slide 1; chapter links have explicit targets. Both views use the same facts, figures, and data. The presentation has useful navigation, Replay, progress, accessible keyboard behavior, readable mobile layouts, and a reliable return to the page. Standalone presentify asks whether to include presentation mode, recommending Yes, then asks its theme and depth together only when enabled. Handbook maintenance includes presentation mode by default and retains the saved project theme and depth policies.

A documentation update inventories the project's handbook set, checks its claims against the selected code revision, updates affected sources, builds affected HTML, and verifies every required output. Release preparation runs the same work before the version bump, using the exact release candidate after the existing integration preconditions pass. Existing handbooks receive the presentation capability in place; source Markdown, APIs, spreadsheets, paths, branding, and authored detail remain intact.

"Single shot" means one user request includes extraction, authoring, deterministic assembly, automated inspection, and bounded internal repair before delivery. It does not mean a promise of perfect unverified output from one model call. Production-ready means content, semantic visuals, structure, and behavior all passed on the final bytes; a browserless or exhausted run is a clearly labeled draft or blocked release, never a visual pass.

### Contract decisions

1. **One reading page, optional presentation mode**: every new output starts as an ordinary scrolling website. Ask whether to include presentation mode, recommending Yes. When enabled, there is one hero entry control and a global top-menu entry when a top menu is present, both labeled Presentation Mode under R25; no detached presentation-only page section. When disabled, deliver the complete scrolling page without a deck, hidden deck payload, or presentation CTA. Initial page navigation, search, anchor links, and detail remain useful in either case. The deck follows the selected depth with claim-based headings, an optional outline for longer stories, chapter dividers where useful, content-specific composition with readable evidence, complete qualifiers, and coherent builds within the recorded slide budget; a bullet quota never determines coverage. Short subjects must not acquire filler slides to meet a template. Handbook documentation/release maintenance retains presentation mode enabled by default; an explicit applicable user opt-out is recorded, preserved, and checked as page-only rather than treated as a missing deck.

2. **Separate page canvas from presentation inclusion**: remove "Slide deck (16:9, arrow keys)" from the output-format menu. Keep full-width scrolling, standard scrolling column, and portrait scrolling canvas plus a free-text layout response. Add `--presentation yes|no`, `--presentation-theme light|dark|mixed`, and `--presentation-depth concise|balanced|deep-dive` for explicit and automated callers. Legacy `--nav slides` becomes a compatibility alias for including presentation mode, with a one-line migration note; it no longer makes the deliverable start as a deck. Legacy `--nav scroll` only binds the reading-page start and does not imply No to presentation. Explicit `--presentation no` wins over a legacy slides alias or supplied theme/depth, with a brief note that the inapplicable option is ignored. A theme or depth flag alone implies presentation enabled. Explicit values suppress only their corresponding questions. `--layout` governs the scrolling canvas; the deck uses its own responsive composition. `--mode deck|report|compile` continues to describe source organization, not the output format. Existing slide deep links remain supported when the deck is enabled without assuming a fullscreen permission gesture.

3. **Fullscreen and input lifecycle**: a click on Presentation Mode or a chapter presentation entry opens the deck and requests native fullscreen within that user activation by default; retain an explicit user opt-out. Passive page load and hash/deep-link restoration open fitted mode without requesting fullscreen. Keep a clearly labeled fullscreen toggle and visible Exit. Request fullscreen on a supported ancestor that contains the deck and all required controls, with correct modal/top-layer ownership; never fullscreen only a painted stage while leaving its controls inert outside it. Denial/unsupported APIs leave the fitted presentation usable. Escape or browser-native fullscreen exit closes the presentation and restores the reading page, scroll and origin focus, even if a detail overlay was open; clean up nested overlays too. When already in fitted mode, a nested detail modal consumes its first Escape before the deck's next Escape. An explicit in-deck fullscreen toggle may exit native fullscreen while keeping the fitted presentation usable; distinguish that action from Escape/browser-native exit. Navigation keys defer to editable fields, chart controls, code/table scroll regions, and composing text. Repeated open/close/replay, rapid navigation, resize, and hash changes must not strand state. Prove this with actual browser clicks and fullscreenchange events, not only simulated key handlers.

4. **Shared truth with separate interaction state**: each figure has a stable source key; page and deck use the same canonical data/definition. Zooming or hiding series in one view must not silently change the other view's starting state. Different teaching illustrations can express the same fact, but are identified as separate visual explanations and linked to source claims; they do not duplicate raw numeric models or masquerade as the same figure.

5. **Source retention and deterministic assembly**: retain authored page content, storyboard, figure definitions, theme tokens, and asset sources under the project. Default new managed sources may live at `docs/handbooks/_sources/<slug>/`; keep existing layouts and native generator inputs when present. A small explicit source/output map lives at `docs/handbooks/handbooks.json` unless an existing equivalent already owns that mapping. Builds are deterministic from frozen inputs; AI performs content updates upstream, never inside `--check`.

6. **Current truth**: a standalone docs run resolves the requested branch/revision or current working tree and records uncommitted source hashes where applicable. The final implementation phase refreshes and verifies handbooks before feature publication. A release run first proves the existing integration prerequisites, then rechecks/refreshes against the exact releasable candidate tree before version mutation. After a version bump or release-metadata change, rebuild/reverify only affected content and metadata, including embedded document identity, before final release qualification. Matching dependency/output hashes permit evidence reuse; a changed embedded version does not. Do not hardcode "current main" when the candidate is still on integration, and do not label it released before publication. Unchanged mapped source content can retain output bytes across unrelated commits; the release verification record carries the checked candidate separately.

7. **Inventory versus rewrite**: full docs/release runs inspect every live handbook HTML, including the atlas and component companions. Record exclusions for archives/caches and applicable explicit user scope or presentation opt-outs; missing sources are not exclusions. Regenerate changed/stale outputs only after initial migration. Missing sources on an existing HTML file are a migration need, not an excuse to omit it. Preserve the original while capturing a maintainable source/model and verify topic/figure parity before replacement. A missing handbook tree is bootstrapped with a useful project overview and relevant architecture/usage material from actual code; do not generate an arbitrary quota of documents.

8. **Quality floors win over geometry**: the source 1600x900 canvas is a desktop composition baseline, not permission to scale text into unreadability. Retain the current 16px body / 13px secondary / 12px interactive rendered floors. Chart/diagram labels have explicit measured roles; no 11-design-pixel global exception. Rearrange within the logical-slide budget and provide a useful mobile reading/reflow view. Declare supported desktop/projector and compact presentation ranges. Within desktop/projector ranges, reserve actual control space and require a scrollbar-free stage in every authored state. A deliberately authored compact presentation may reflow and scroll below its declared breakpoint while retaining logical slide identity, coverage, and readable controls; it is not permission for desktop overflow. Do not hide overflow or silently add slides. Identify unsupported presentation sizes honestly and offer the reading view. Measure native CSS pixels after transforms.

9. **Brand continuity and intake**: full project documentation maintenance reuses committed project tokens and presentation-theme/depth policies and runs without repeated aesthetic interviews. R30 owns preference precedence: current explicit instructions/flags, current-session resolved answers, approved project settings, then documented defaults only for non-interactive callers. Record the origin of each choice. Resolve an actual contradiction once; do not restart settled intake. Unrelated remembered preferences do not authorize new imagery or network use. Standalone presentify keeps design direction, scrolling canvas, interactivity, and imagery choices; add the presentation-inclusion question to that initial batch and ask the unresolved theme and depth choices together only after Yes. The removed "presentation style" is the slide-deck output-format choice shown in the screenshot, not the separate design-direction question. Stock/AI assets remain opt-in under existing boundaries; automatic handbook updates use local/procedural assets and do not acquire new outbound dependencies.

10. **Production-readiness status**: required content, structural, semantic-visual, and behavioral gates must all pass on final bytes. Missing browser capability, missing source inputs, a runtime defect, or an exhausted repair budget records a non-pass with exact reason. A standalone run can return a clearly labeled draft; a release requiring those handbooks stays blocked. A known-gap entry is evidence of the block, not a waiver that makes failed output pass.

11. **Presentation-theme policy**: when presentation is enabled, offer "Light theme only", "Dark theme only", and "Random light/dark mix to catch attention". Light-only and dark-only govern every slide, including cover, outline, chapter dividers, content, controls, diagrams, charts, code, and progress indicators; the source example's dark-divider/light-content pattern must not override either choice. Mixed mode assigns complete light/dark palettes per slide during authoring, uses both palettes when there are at least two slides, and avoids long runs of the same palette. Save the seed and the resolved theme per stable slide ID in the retained storyboard/design record. Repeated builds, Replay, back/forward navigation, and reopening never reroll themes. Theme changes occur only between slides, never as flashing or animation within a slide. The reading-page theme remains independent under R27. When source edits add slides, preserve surviving stable IDs and their assignments; choose themes for new IDs coherently without rerolling the existing deck. Re-theme existing IDs only for an explicit theme-policy change. Respect brand colors and measured contrast on every assigned palette. A one-slide deck records its single chosen palette rather than pretending to alternate.

### Presentation depth and coverage

Presentation depth is independent of `--verbosity`, which controls how much source material becomes the main page. The presentation derives from the resulting main page: a deep dive covers that entire page, even when the page itself was distilled from a larger source. Theme and depth are asked together in one conditional follow-up after Yes; an explicit value suppresses only its own question.

| Depth | Content contract | Coverage proof |
|---|---|---|
| Concise and compact | Present the main message, key findings, essential visuals, decisions, and material caveats in a short narrative. Summarize or omit supporting detail explicitly. | Map included, summarized, and omitted page content with reasons; retain qualifications necessary to keep the main message accurate. |
| Balanced | Cover every major topic with its key explanation, representative figures/examples, and important caveats. Summarize lower-level detail. | Every major page section maps to slides; detail omissions/summaries are recorded without losing a major conclusion or limitation. |
| Deep dive | Present all substantive main-page content, including explanations, subsections, figures, tables, code, examples, caveats, and appendix content, within the applicable logical-slide budget. Rephrase for speaking without removing meaning. | Every substantive page content unit maps to an authored slide/state. No omitted content or link-back-only substitute; page navigation chrome and decorative elements are not content units. |

Add `--presentation-depth concise|balanced|deep-dive`. A depth flag alone implies presentation enabled; explicit `--presentation no` still wins and ignores supplied depth with a brief note. Record depth and the page-to-slide coverage map in retained authoring inputs. Save the chosen depth per handbook; subsequent docs/release updates preserve it. Non-interactive new handbooks use balanced unless a project policy specifies another depth. Do not infer depth from the page's verbosity, theme, file size, or source format. An explicit request to preserve and present the entire source binds comprehensive reading coverage and deep-dive presentation together; this is an answered content requirement, not an inference. An explicitly different current choice on either axis must be resolved and recorded, not silently overridden.

Depth controls coverage within the applicable slide budget and never waives readability. For an existing slide deck or slide PDF, default to no more logical slides than the source, including cover, dividers, and appendices. Preserve the count or consolidate redundant material with a complete source mapping; do not expand merely because deep dive was selected. The local 68-page board case has a maximum of 68 presentation slides. For a handbook or non-slide report, retain an audience/time/content budget instead of inventing a page-count ceiling. Explicit current user constraints win, and saved budget policies survive docs/release refresh.

Author an effective composition for each message, comparison, or evidence set; no universal four-bullet or one-figure quota determines coverage. Use progressive builds within one coherent composition when useful, with Replay and an inspectable complete state. Unrelated full-screen panels must not be disguised as one slide to evade the ceiling. Do not generate continuation slides to repair CSS overflow or rigid table chunking. For source decks, preserve source pages or consolidate them with a complete mapping; source counts include all logical covers/dividers/appendices. Non-deck continuations require deliberate authoring within the recorded content/time budget. A deep dive must not shrink text, omit detail, substitute original screenshots, or rely on an unvisited detail drawer to satisfy its contract. If full coverage, readable fit, and the count remain incompatible after composition work, report the conflict and the bounded decision needed; never silently downgrade depth or expand count. Every slide and authored state remains in the QA inventory.

No skips theme/depth questions and deck authoring. Page QA and the absence check for deck payload/controls still run; other deck checks are N/A. Changing Yes to No clears pending theme/depth questions and deck work. Non-interactive callers use Yes plus saved project theme/depth policies, otherwise mixed and balanced. Documentation/release automation enables presentation by default, honors an applicable recorded opt-out, and preserves resolved policies without interviewing once per handbook; newly introduced handbooks use mixed and balanced when no policies exist. An unanswered question in an interactive run is not consent to a choice. This conditional follow-up is intentional and does not restart unrelated design questions.
