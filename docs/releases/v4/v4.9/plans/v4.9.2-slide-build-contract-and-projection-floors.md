# v4.9.2 -- Slide build contract, projection type floors, and figure re-layout

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Close the three gaps in `document-to-interactive-html` that let a handbook ship a presentation mode with randomly-ordered builds, document-sized type on a projected stage, and figures scaled rather than re-laid-out.

**Architecture:** Three reference-contract additions, one schema field, and four automated checks in the existing scorer. No new script, no new skill, no new dependency. The fragment stepper, the figure model, and the QA loop all already exist; this makes them answer questions they currently do not ask.

**Tech Stack:** Markdown contracts, Python 3.12 (`visual_qa_score.py`), pytest.

**Spec:** this document (combined design and plan; the design decisions were settled in session and are recorded in section 1).

**Status**: COMPLETE except Task 6 Step 1. Tasks 1-4 (the reference contracts) were already implemented before this pass and were verified by reading the files, not the boxes. Of Task 5's four checks, three already existed under the repository's naming convention (`check_slide_type_variety`, `check_slide_figure_scaled`, `check_slide_fragments`); the fourth, the 2%-of-stage-height floor, is implemented in `measure_handbook.py` rather than `visual_qa_score.py` because a rendered share of stage height is a render probe, which that script's own docstring already stated. Task 6 Step 1 is NOT done: it names decks under an external project path absent from this repository, and no frozen inventory for a repository handbook exists. Evidence: `docs/releases/v4/v4.9/development/v4.9.2-stage-floor-evidence.md`. Completed 2026-09-21.

### 1.2 The gaps

**Gap 1 -- fragment order is unspecified.** Section 4 of `slide-navigation.md` defines how a fragment *steps* and what state it resolves to. It never says how `n` is *chosen*. An implementation is therefore free to assign fragments by element type, and one did: grouping every stroked path, then every dashed path, then every marker, then every text node. On a flow diagram that renders as every box, then every label, then every arrow, which is not how a flow diagram is read. Observed on a shipped handbook deck; the reviewer's description was "animations appear in total random order... no logic, no consideration of the content".

**Gap 2 -- no projection-distance type floor.** The floors in `responsive-typography.md` are page floors, set for a reading page at desk distance. A slide stage has none, so a figure carrying page typography passes into presentation mode unchallenged. Observed: axis labels authored at 12.44px inside a viewBox subsequently scaled to fit a stage.

**Gap 3 -- no aspect-change re-layout rule.** `figure-reconstruction.md` covers recovering a figure's data and redrawing it. Nothing states that a figure composed for one aspect ratio must be re-laid-out, rather than scaled, when placed at a materially different one. A figure built for a narrow reading column, scaled into a 16:9 stage, letterboxes: the drawing occupies a band and the stage carries large dead margins. Observed: vertical ink fill of 40-76% with 190-290px dead bands.

**Gap 4 -- the figure model cannot express a build.** Searching the shipped figure engine for `fragment|data-step|anim` returns two incidental hits. The model is `{panels: [{rect, title, ylabel, xticks, yticks, xscale, yscale, lines[], markers[], spans[], bands[], legend[], notes[]}]}` with series `{u[], v[], color, width, dash, opacity, band}`. There is nowhere to say when a drawable arrives, so even an author who knows the right order has no way to record it, and the renderer has nothing to stamp.

**Gap 5 -- a page can ship a presentation without declaring one (found during implementation).** The slide-mode check family is gated on `data-nav="slides"` or a `nav` field in the design record. `check_slide_record_agreement` guards the case where the record claims slides and the markup lost the attribute. Nothing guards the reverse. Running the extended scorer against the five shipped handbook decks showed all five scoring `nav: scroll` and skipping every slide check, including the three added by this plan: the decks are hand-built with their own class names and declare no record, so the family never looked at them. A check that skips a page which HAS the feature is worse than no check, because it reports success. This is why none of gaps 1 to 3 was ever caught automatically.

### 1.3 Why these five, and not more

Gap 1 is the cause of the reported animation defect, gap 2 of the readability defect, gap 3 of the layout defect, gap 4 is what makes 1 expressible rather than merely required, and gap 5 is why none of them was caught. Each is stated without reference to any particular document. Everything else the reviewer reported (verbose titles, weak slide copy, redundant takeaway lines) is already covered by `hallmark-design` and `anti-slop-editing` and needs no new rule.

## 2. Task 1: Fragment order derives from content

**Files:**
- Modify: `catalog/skills/specialized-domains/document-to-interactive-html/references/slide-navigation.md`
- Modify: `catalog/skills/specialized-domains/document-to-interactive-html/references/visual-qa-rubric.md`

- [ ] **Step 1: Add section 4.1 to `slide-navigation.md`**, immediately after the existing "One fragment per discrete state" bullet block and before "Idempotence (BINARY)":

```markdown
### 4.1 Choosing n (BINARY)

Section 4 defines how a fragment steps. This defines how its number is chosen, because an
unspecified order is not a neutral default: an implementation with no rule falls back to the
order it can see, which is element type or DOM position, and that is what produces "every box,
then every label, then every arrow" on a diagram.

- **Order derives from the content's own logic** -- the order a knowledgeable presenter would
  reveal it while talking. Write the order down as a manifest of `(n, what this step shows)`
  before assigning a single attribute; if the manifest cannot be written in plain sentences, the
  slide has no argument and the fragments are decoration.
- **Never derive order from element type, tag name, stroke style, or DOM order alone.** Grouping
  by what an element IS rather than what it MEANS is a defect, not a fallback.
- **Dependency**: nothing reveals before the thing it acts on. A marker cannot precede the series
  it sits on; an annotation cannot precede its subject; a connector cannot precede its source.
- **Flow and process diagrams**: a node and the connector arriving at it share one fragment. The
  reader follows one path rather than watching a disconnected set of boxes appear.
- **Comparison figures**: the baseline reveals before the variant it is compared against.
- **Data figures**: frame and axes, then the data, then derived overlays (thresholds, fits,
  regions), then the single element the slide concludes on.
- **Budget**: at most 8 fragments per slide. More than eight discrete states is two slides.
- **Duplicate n reveals together** (section 4) and is the correct way to say "these arrive as one
  idea", not a way to evade the budget.
```

- [ ] **Step 2: Add the rubric row.** In `visual-qa-rubric.md`, add to the presentation criteria:

```markdown
- **Fragment order follows content, not element type.** Each slide's fragment manifest reads as a
  sequence of ideas; no step reveals a marker, label, or connector before its subject.
```

- [ ] **Step 3: Verify the contract is self-consistent.** Confirm no existing rule in `slide-navigation.md` or `interactive-features.md` contradicts the new section.

## 3. Task 2: Projection-distance type floors

**Files:**
- Modify: `.../references/responsive-typography.md`
- Modify: `.../references/visual-qa-rubric.md`

- [ ] **Step 1: Add the slide-mode section** to `responsive-typography.md`, after the existing page floors:

```markdown
## Slide-mode floors (BINARY)

The floors above are reading-page floors, set for a document at desk distance. A presentation
stage is read across a room, and a figure that satisfies the page floors can still be illegible
on it. Slide mode has its own floor, expressed as a share of the stage so it holds at any canvas
size:

- **No rendered text on a slide stage is smaller than 2% of the stage's height.** On a 900-unit
  design canvas that is 18 units; on a 1080px stage, 21.6px. Measure the RENDERED size, after any
  transform the stage applies, not the authored value.
- **At most four distinct rendered text sizes per slide.** A slide carrying six or seven sizes is
  a page that was moved rather than a slide that was composed.
- **The floor applies to every text node**, including axis ticks, legends, table cells, source
  lines, and annotations inside an SVG. A figure's internal type is not exempt because it is
  inside a figure.
- A figure whose authored type satisfies the page floors and whose rendered type fails the stage
  floor has been scaled rather than re-laid-out; see `figure-reconstruction.md`.
```

- [ ] **Step 2: Add the rubric row** to `visual-qa-rubric.md`:

```markdown
- **Stage typography.** Every rendered text size on a slide clears 2% of stage height, and no
  slide carries more than four distinct sizes.
```

## 4. Task 3: Aspect-change re-layout

**Files:**
- Modify: `.../references/figure-reconstruction.md`
- Modify: `.../references/visual-qa-rubric.md`

- [ ] **Step 1: Add the rule** to `figure-reconstruction.md`:

```markdown
## Re-use at a different aspect ratio (BINARY)

A figure is composed for the box it was drawn for. Placing it in a box of a materially different
aspect ratio is a new composition, not a resize.

- **When the target aspect differs from the source by more than 25%, re-lay-out the figure; do
  not scale it.** Re-layout means recomputing the panel rectangle, the tick density, the legend
  placement, and the type sizes for the new box. Scaling means multiplying everything by one
  factor, which carries the source's proportions and the source's typography into a box that
  suits neither.
- The common case is a reading-column figure (tall, narrow) placed on a 16:9 stage (wide, short).
  Scaled, the drawing occupies a horizontal band with dead margins above and below, and its type
  lands below the stage floor. Both are symptoms of the same omission.
- **A scaled figure is detectable and is a defect**: rendered text smaller than authored text
  means a uniform transform was applied. Re-layout changes the authored values instead.
- Re-layout is a property of the FIGURE, not of the container. Fitting the container, letterboxing
  inside `preserveAspectRatio`, or scaling a wrapper are all the same omission wearing different
  clothes.
```

- [ ] **Step 2: Add the rubric row:**

```markdown
- **Figures are composed for their box.** No figure is a uniformly scaled copy of a figure drawn
  for a different aspect ratio; ink fills its box rather than sitting in a band.
```

- [ ] **Step 3: Commit.**

## 5. Task 4: `fragment` in the figure model

**Files:**
- Modify: `.../references/content-model.md`
- Modify: `.../references/figure-reconstruction.md`

- [ ] **Step 1: Extend the drawable schema.** In `content-model.md`, document the field on every drawable a figure model can carry:

```markdown
### Build fragments in a figure model

Any drawable in a figure model -- a line, marker set, span, band, legend entry, or note -- MAY
carry `fragment: <n>`, an integer giving its reveal order within the slide that hosts the figure.
The renderer stamps it onto the emitted element as `data-fragment="<n>"`, which is the attribute
the deck's fragment stepper already consumes (`slide-navigation.md` section 4).

    {"lines": [{"u": [...], "v": [...], "color": "...", "fragment": 2}],
     "markers": [{"u": [...], "v": [...], "fragment": 4}],
     "notes":   [{"text": "...", "fragment": 5}]}

Rules:

- The numbers are chosen per `slide-navigation.md` section 4.1; they encode the content's order.
- Omitting `fragment` on every drawable in a figure means the figure has no build and reveals
  whole. That is a legitimate choice for a simple figure and MUST NOT be filled in automatically
  by the renderer -- an inferred order is the defect 4.1 exists to prevent.
- Omitting it on SOME drawables while others carry it is an authoring error: the unassigned
  drawables have no defined position in the build. A checker flags this.
- The field is inert on the reading page, where figures reveal whole. One model, two views.
```
