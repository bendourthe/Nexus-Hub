## Why the missing check went where it did

`check_slide_type_variety`'s docstring already recorded the reason its sibling did not exist: "the
rendered floor itself is a render probe (references/responsive-typography.md section 4.1)". A 2%
share of stage height cannot be decided from markup, because the value that matters is the size
after the stage's transform. Implementing it in `visual_qa_score.py`, as the plan's table implies,
would have contradicted a reasoned decision already in the code.

It is therefore implemented in `measure_handbook.py`, which already measures rendered `fontSize`
multiplied by the accumulated transform scale and already measures the presentation view with each
`[data-dv-slide]` as its root. No browser-side change was needed: the floor's basis is the viewport
height the probe is already iterating, which is also what the contract's arithmetic uses.

## The gate

`SLIDE_STAGE_FLOOR_FRACTION = 0.02`, applied inside the existing per-font loop and only when
`view == "presentation"`. It is a SECOND floor beside the page floors, not a replacement: both can
fire on one text node, and they answer different questions (too small at a desk, versus too small
across a room).

## Evidence

Measured directly, at two viewports, with the slide's body type forced to 18px:

```
1366x768:  floor 15.36   body 18.00  ok
1920x1080: floor 21.60   body 18.00  FAILS stage
```

That is the isolating case the tests are built on: 18px clears the page body floor of 16, so the
pre-existing gate is silent, while the stage floor correctly rejects it on a tall stage.

**The basis is the VIEWPORT height, and the first implementation got this wrong.** It used the
slide element's `clientHeight`, which is the CONTENT height whenever the stage reflows. Compact mode
at 390x844 measured a 4070px element, making the floor 81.4px, which no type can meet - and it broke
`test_long_content_reflows_in_compact_mode_but_fails_desktop_stage`, a pre-existing test that
asserts compact mode legitimately reflows taller than its viewport. The contract's own arithmetic
settles the question: "on a 1080px stage, 21.6px" is 2% of the viewport, not of the content box. A
desktop stage that scrolls is a separate error the probe already reports.

Three tests in `tests/skills/test_presentify_measure_handbook.py`:

- `test_stage_floor_fires_where_the_page_floor_passes` -- asserts the stage error AND the absence of
  an "undersized body" error, which is what proves the two gates are independent rather than one
  gate counted twice.
- `test_stage_floor_is_relative_to_the_stage_not_absolute` -- the same 18px passes at 1366x768,
  where the floor is 15.36px, pinning the fraction so a later edit cannot "simplify" it into a px
  constant.
- `test_stage_floor_passes_compliant_stage_type` -- negative control at 24px.

Mutation-checked: with the gate replaced by `if False`, the first test fails and the two controls
correctly stay green. Restored, all three pass.

```

50 passed in 126.44s        # the whole file, after the viewport-basis correction
```

## Two things that were tried and did not work, recorded so they are not retried

**Injecting markup into `[data-dv-slide]` is not measurable.** The presentation view builds its
slides at runtime, so an `<svg><text>` inserted into the slide never appears in the probe's output
-- it reported only the heading and the body. The first draft of these tests did exactly that and
passed vacuously in the negative control. A slide-scoped stylesheet rule reaches the measured tree;
injected elements do not.

**The first `</h2>` in the page belongs to the reading section, not the slide.** The existing
page-floor tests replace it correctly, because page floors apply to both views. A stage-floor test
that replaces it is measuring the wrong subtree.

## Task 6 was NOT performed, and why

Step 1 asks for the extended scorer to be run "against an existing handbook deck that predates
these rules", naming decks under an external project path (`rd-data-dev/...`) that is not present
in this repository. No frozen `--inventory` for a repository handbook exists either, so a real-deck
run would require constructing one, and a constructed inventory is not the pre-existing deck the
step asks for.

`check_handbooks.py` passes, but that is NOT validation of this gate: it verifies source, build and
output hashes, and never invokes the render probe. Claiming it as evidence would be false.

Recorded as a known gap rather than substituted with a weaker check.
