## Overview

This plan operationalizes the seven recommended candidates from its seeding comparison, in the reverse-engineer-first order that comparison fixed. Six are `skill-native` and the seventh is `re-full`. No candidate introduces an outbound call, a credential, a new runtime dependency, or a third-party data processor. The two candidates the comparison classified `drop-outright` (adopting Tencent BrowserSkill, and adopting cloud-by-default factory infrastructure) are out of scope.

The deliverables are mostly instruction text, but the plan is not only instruction text: it also changes one repo-internal script, adds test coverage, and files two decision records. That distinction matters for effort estimation and is stated here rather than left to be discovered mid-release.

**This document was substantially rewritten on 2026-09-17 after a five-lens plan review returned roughly seventy findings, fifteen at P1.** Ten of those were verified against the repository and were correct, including four that would have shipped defects: a Phase 4 instruction that would have reinstated count-based queue-membership inference against a settled decision record; a Phase 5 instruction that would have violated the `AGENTS.md:282` attribution rule and embedded a live agent-directed install URL into a distributed skill; a Phase 1 lookup table whose Anthropic rows are all superseded generations; and a per-phase test gate (`--profile fast`) that runs no pytest at all, so five phases would each have committed "stable" work whose tests had never executed. The `## Review corrections` section records every change so a later reader can see what was wrong rather than only what is now written.

The highest-risk phases are **1 and 5**, not 2. An earlier draft named Phase 2 highest-risk on coordination grounds, but Phase 2 is the only phase with a genuinely behavioral test. Phase 1 derives guidance from a single unrefereed study about a superseded model generation, and Phase 5 writes about a real third party in a distributed artifact. Both were previously scheduled as routine.

**Recommended model tier**: frontier

### Sub-tasks

#### 1.1 -- Add harness as a named cost concern, with no ratio table

**Objective**: Teach the mechanism and the verification requirement without freezing a superseded snapshot into the catalog.

**Failure modes**: Asked about a model with no measurement, the step returns "unmeasured; verify before assuming" and never extrapolates from a neighbouring model or generation. With web access unavailable, no ratio is invented and the absence is stated. When a harness consideration conflicts with the host the user is on, the host wins and the delta is reported, never silently applied.

**Build class**: load-bearing.

**Prompt**:

> Edit `catalog/skills/ai-development/model-routing/SKILL.md` to add harness as a named cost concern, placed after Step 3 so it reads as a separable decision rather than a sixth complexity signal.
>
> **Ship the mechanism, not the numbers.** The durable finding is threefold: harness choice moved cost far more than it moved success rate; the effect is strongly model-conditional; and a ratio does not transfer across model generations. State all three. Do NOT reproduce the measured ratio table. The seeding comparison's coverage caveat explains why: only three of the sixteen cells in the plan's model map carry any measurement, every frontier cell is unmeasured, and the single measured Anthropic model produced a null result. A table that is empty exactly where users operate is worse than no table, because it reads as authoritative and returns nothing.
>
> **State the evidence honestly where you cite it.** One study, 30 tasks per cell, Holm-corrected across 14 comparisons, measuring a model generation that has since been superseded. Say that a non-significant rate result means "no difference detected at this power", never "no difference". Do not write a rule that defaults users toward the cheaper harness on the strength of an undetected difference.
>
> **Add the two rules the same source motivated** (comparison S4.3 and S4.4), which an earlier draft of this plan orphaned:
>
> - A benchmark-reading rule: uncorrected per-pair comparisons overstate differences, so a cited result without a stated correction and sample size is not evidence for a routing default. This matters generally, because a great deal of catalog content cites external evaluation.
> - A cost-with-quality rule: when recommending a configuration, cost and success must be reported together, never separately. A cost figure alone invites the exact error this phase exists to avoid.
>
> **State the advisory boundary and bound the noise.** `/route` is host-native and cannot switch harness, so the output is a recommendation for the user's next session. Emit it only when it would change a decision: once per plan rather than per phase, and only when the concern is material. A recommendation the agent cannot act on, repeated every routing decision, trains users to ignore the whole routing block.
>
> Add Common Rationalizations rows for extrapolating a ratio to an unmeasured model or generation, and for reading a null result as equivalence. Respect the 800-line cap.
>
> Do NOT touch `templates/ai-instructions/base-*.md`. The policy file states routing is command and skill behavior, not a base-template lockstep concern.

#### 2.2 -- Implement the durable-knowledge decision

**Objective**: Make learned knowledge durable and readable, in whatever form 2.1b chose.

**Failure modes**: With a malformed or absent knowledge file, the skill reports it unreadable and continues with what it can read, never treating an empty read as "nothing has been learned". With an unrecognized `schema` value, the entry is reported and skipped, never coerced or rewritten. When a prune and a mint target the same entry in one session, the mint wins and the prune is re-offered.

**Build class**: load-bearing.

**Prompt**:

> Implement the 2.1b decision, editing whichever skill it assigned. Do not assume the target from this plan's task lines; they are outcome-neutral by design.
>
> **State the invariant precisely.** "Never rolled back" is wrong as written, because the required prune rule includes Delete, Replace and Consolidate verdicts that remove entries. The contract the design needs is: *a knowledge entry is never removed as a side effect of an artifact rollback or rejection; it is removed only by an explicit user-confirmed prune verdict.* Scope it to the trigger, not the file, or the 2.4 negative control cannot distinguish a prohibited side-effect deletion from a permitted prune.
>
> Ship the prune rule in the same sub-task, modelled on `[[solution-refresh]]` and carrying its confirmation guard (verdicts that remove content always require explicit confirmation). The source research names unbounded growth as an unsolved limitation, so inheriting the design without the mitigation inherits a known defect.
>
> **Add a `schema` discriminator to every new on-disk record**, with the forward rule that an unrecognized value is reported and skipped. `.nexus/` already exists in users' repositories and its current stores have no version field, which is why a reader cannot distinguish "old shape" from "malformed". This is the last cheap moment to fix that.
>
> **Add a redaction rule before any write.** These records derive from `.nexus/observations.jsonl`, which captures `prompt_sample` (user prompt text), and the existing design bounds that exposure with 1 MiB truncation and manual pruning. A durable store removes that bound for exactly the layer carrying diffs and evidence. Cross-link `[[egress-redaction]]`, require redaction before write, state that deletion for secrets is the one exception to the never-removed-as-a-side-effect rule, and instruct consumers to gitignore the new paths.
>
> Keep an optional provenance field linking an entry to what it motivated. Keep it optional and confined to this layer; do NOT add a required provenance file to catalog skills or to `validate_skills.py`.
>
> Everything stays local. No background observer, no upload, no cross-project sharing.

#### 2.3 -- Add the proposal and rejection ledger

**Objective**: Record proposals with outcomes, require reading before proposing, and keep the block appealable.

**Failure modes**: With the ledger absent or unparseable, a proposal proceeds but is flagged unverified against history rather than treated as novel. With the ledger large, the pre-proposal read is a bounded index read whose completeness does not depend on log size. With two proposals in one session, entries append in order and neither overwrites the other.

**Build class**: load-bearing.

**Prompt**:

> Add an append-only ledger recording per proposal: what was proposed, the diff or a summary, the validation outcome, and an Accepted or Rejected verdict. Add the read step that makes it load-bearing: before proposing, read the ledger and do not re-propose an approach recorded as rejected. `grep -rniE "already (tried|proposed|rejected)|prior proposal|re-propose" catalog/skills/workflow/` currently returns nothing, which is the gap.
>
> **Do not make the block permanent or unappealable.** Rejections come from an automated gate that fails for transient reasons - a flaky test, a missing dependency, an unrelated regression. A single such failure must not permanently ban a correct approach. Require three things: a rejection-reason taxonomy distinguishing *validated-worse* from *environment-failure*, an explicit supersede entry a human can file, and a staleness rule making a rejection older than N versions advisory rather than blocking. Only *validated-worse* blocks.
>
> **Make the read bounded without losing history.** A byte-truncated read of an append-only log silently drops one end, and the guarantee would degrade exactly as the ledger accumulates value. Keep a compact rejected-approaches index beside the full log, keyed by the existing stable-id convention and mirroring how `_index.md` already sits beside the instinct YAMLs, so the mandatory read is an index lookup. If a read is ever truncated, report it as partial rather than as "no prior rejection found".
>
