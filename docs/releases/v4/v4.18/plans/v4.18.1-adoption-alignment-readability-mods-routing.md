**Goal**: A planning interview opens with the agent's reading of the user's goals, problem, and assumed constraints, so a misreading is corrected at no extra turn. A user who asks for ASD-STE100-style output, at a full or softened level, gets one consistent STE-inspired register. Every `/implement` phase leaves one local, never-committed routing-outcome line, and a standard-library report counts those lines per tier, so a later calibration plan starts from recorded evidence instead of none. Each rule has exactly one owning skill.

## Problem

| User | Harm today | Item |
|---|---|---|
| A developer starting `/plan` or `/grill` | The agent starts questioning from its own reading of the request. A misread goal surfaces only when a phase is wrong, after the plan is written | DoD 1 |
| A reader who asks for ASD-STE100 or "plain controlled English" (the request the seeding comparison's Source 2 describes) | No skill names the register, so each answer improvises a different, unchecked approximation | DoD 2 |
| A maintainer deciding whether the routing rubric over-spends | 231 of 347 scored v4 plan phases (67%) are `frontier` and none are `fast`, and nothing records how any phase actually went. Under-tiering stays invisible and a future calibration has no data to start from | DoD 3, 4 |

The ledger makes under-tiering visible (upshifts and failed attempts per tier). It cannot by itself prove over-tiering, because a frontier phase that passed does not show a cheaper tier would have passed; that counterfactual belongs to the calibration plan parked as P3.

## Definition of Done

**Must have:**

1. `catalog/skills/developer-experience/design-interview/SKILL.md` owns a readback that opens round one: a block with three labeled parts (Goals, Problem, Assumed constraints), at most two sentences each, in the agent's own words, followed in the same message by the round's questions. If the user corrects the readback, the agent recomputes the frontier before using any answer. The readback is skipped when a readback of the same goal was already confirmed earlier in the session by any skill (including `idea-refine` Step 1, the `/plan` goals-first step, and the `/implement` approval page). In an unattended run it is recorded as a stated assumption and the run continues. In seeded mode it reads back the caller's stated goal. The `## Rule ownership` table gains the row. `implementation-plan/SKILL.md` Phase A, `catalog/commands/plan.md` (goals-first step), and `idea-refine/SKILL.md` Step 1 each carry one handoff sentence naming `[[design-interview]]`, restating none of its wording. `tests/skills/test_interview_readback.py` proves the placement, the labels, the skip and unattended clauses, and each handoff.
2. `catalog/skills/developer-experience/writing-editing/references/controlled-language.md`, linked from `SKILL.md`, owns a requestable STE-inspired register with a full level and a softened level, defined as an explicit keep/drop table over named rules, in original wording. It states that it is not certified ASD-STE100 conformance, that the specification and dictionary are obtained from ASD, and it contains no approved or not-approved word table. `writing-editing/SKILL.md` carries a rule-ownership table for the writing cluster, and `technical-writer/SKILL.md` carries one handoff sentence on register precedence. The `writing-editing` description carries the trigger nouns ASD-STE100, Simplified Technical English, and controlled language, plus a SKIP clause; `writing-editing/evals/trigger-cases.json` passes `python scripts/run_trigger_evals.py --gate`; `data/skills.json` agrees with the frontmatter; `tests/skills/test_controlled_language_register.py` proves both levels, the keep/drop table, the disclaimer, and the absence of a word table.
3. `model-map.py record` appends one validated JSON line per completed `/implement` phase attempt to `~/.nexus-hub/routing/<repo-key>/<version>-<slug>.jsonl` (override `NEXUS_HUB_ROUTING_DIR`), outside every working tree, never committed. The format contract lives in `model-routing/references/routing-ledger.md`, its only owner: schema, keys, enumerations, attempt numbering, the first-pass definition, and the privacy boundary (no prompt text, file content, path, or account identifier; model ids only from the model map, else `other`; ledger lines are unsigned telemetry and never completion or approval evidence). On by default; `NEXUS_ROUTING_LEDGER` set to `0`, `false`, `off`, or `no` (any case) disables it; the first write per repository prints a one-time notice naming the file and the disable switch. `implement-phase/references/implement-phase-runbook.md` calls it at both phase-commit points (non-final phases and the final phase), and a failed call never blocks a commit. A decision record under `docs/decisions/proposed/tooling/` records the choice with `## Alternatives considered`.
4. `model-map.py report` prints counts only: per-tier counts of plan-phase recommendations under `--root`, and per-recommended-tier ledger totals for the current repository (phases, attempts, outcome counts, upshift total, first-pass count, executed-tier mismatches, and skipped lines), with `--all` for every repository and `--json`. It states no threshold and no calibration rule. The plan-field pattern it reads is pinned by a test against the `implementation-plan` template so a template change fails a test instead of silently zeroing the counts.

## Overview

The v4.18.1 comparison found three gaps. Nexus-Hub asks good interview questions but never first shows what it thinks the user wants. It has no controlled-language register although the seeding comparison's Source 2 shows the request. And it routes every plan phase through a careful rubric whose results nobody records: two thirds of phases land on `frontier`, and nothing shows how they went.

Phase 1 records predecessor states and freezes the baseline numbers. Phase 2 lands the readback with a structural test. Phase 3 lands the register with a structural test, trigger evals, and registry agreement. Phase 4 adds a `record` subcommand to the existing standard-library `model-map.py`, backed by a sibling module in the same `scripts/` folder, and wires it into the implement runbook. Phase 5 adds the counts-only `report`. Phase 6 is the mandatory fail-closed final phase. No skill, command, or hook is added, and the new module sits inside a skill bundle that both installers copy recursively, so no installer or registry count changes.

Success is observable: an interview transcript opens with the readback block above round one's questions, the gated trigger evals route an STE request to `writing-editing`, and after any `/implement` phase `model-map.py report` counts that phase's attempt under its tier.

3. Routing scope is record plus a counts-only report (interview Q2). The calibration rule, its 30-phase threshold, and the downshift-needs-a-decision-record requirement move to parked branch P3 as that plan's starting specification, because a rule for data that will not exist for many releases has no call site (AGENTS.md scope-fit review).
4. The readback shares round one's message (interview Q3), so a correct reading costs no turn. The skip rule and the unattended behavior are owned by `design-interview` alone.
5. The v4.15.2 source-refresh note landed with this plan's documentation change (interview Q4), as `### Source refresh, 2026-10-02` in `docs/releases/v4/v4.15/comparisons/v4.15.2-comparison-claude-code-mods.md`, and is not part of this plan's Definition of Done.
6. Ledger key and attempts: a line is identified by `version`, `slug`, `phase`, and `attempt`, never by a path, so plan renumbering and archive moves do not split a phase's history. `attempt` is computed by `record` as one more than the existing lines for the same `version`, `slug`, and `phase`. First-pass for a phase means its first attempt has outcome `complete`, `gate_iterations` of 1, `upshifts` of 0, and `counts_source` of `observed`.
7. Outcome enumeration is owned by `routing-ledger.md`: `complete`, `partial`, `failed`. If v4.17.3 has landed a loop-outcome vocabulary, the reference carries an explicit mapping table and the decision record says why; any later change to the enumeration bumps `schema`, and `report` reads every known schema.
8. The ledger records both `recommended_tier` and `executed_tier` (after any confirmation change or upshift), so outcomes are never attributed to a tier that did not run.
9. Plan prose that quotes the field literals must not be counted: the report and the Phase 1 baseline use one line-anchored pattern, `^\*\*Recommended model tier\*\*:\s*(frontier|strong|standard|fast)\b` (and the matching effort pattern), case-insensitive.
10. The register's vocabulary rule is original wording ("prefer the most common single-sense word; define each technical term once and use only that term"), not a dictionary. The softened level is named "softened"; "80% of the way to STE" is a trigger synonym only.
