**Goal**: Every candidate change carried by Nexus-Hub's verified improvement loop records, before its edit is applied, which cases it should fix, which it puts at risk, and which observable tool call must appear if it actually fired; the loop scores that prediction after replay, refuses a candidate that re-proposes a recorded rejection, and refuses to judge a change against target fixtures that every run passes or every run fails. An `absent` signature makes the candidate "not supported" even when its tests pass; `unobservable` permits approval only with a human note naming the missing capture. Step 5's non-degrade condition covers the development-pool regression cases and `at_risk` cases; the held-out split stays untouched, and the reference names `ai-output-evaluation` (`references/evaluator-validation.md`) as its owner instead of restating it. A new Step 4a reads that history before proposing: a candidate targeting the same instinct and the same `regression_id` as a rejected entry stops unless its manifest adds `differs_from_rejected` with one sentence naming what changed. Step 7 gains a fail-closed row for a malformed `candidate_history`.
3. `catalog/skills/workflow/skill-eval-loop/references/fixture-signal.md`, linked from `SKILL.md`, applies to **target fixtures only** (`targets_fix`, `targets_stabilize`); regression and `at_risk` fixtures keep counting as non-degrade evidence at a pass rate of 1. A target's baseline pass rate is measured over K runs (default 5) and cached until the fixture or the skill changes. A rate of 0 or 1 is signal-free: reshape toward 0.4 to 0.6 by changing the start state, blocking a shortcut action, or trimming the observation, recorded before the candidate is measured, or exclude the target with its reason. ## Overview

The comparison reduced five sources to one structural gap: Nexus-Hub's improvement loop checks outcomes but never records a prediction, so it cannot tell a change that worked from one that passed by accident, and it cannot recognize a fix it already rejected. A second gap sits in evaluation: a target fixture that never varies is counted as evidence.

Phase 1 records predecessor states, file hashes, the count of real loop records, and which trace features the current replay emits. Phase 2 lands the manifest, the candidate history, Step 4a, the failure annotations, and the behavioral gate. Phase 3 lands the fixture-signal reference. Phases 4 to 7 carry the four nice-to-have items, each cuttable from the tail. Phase 8 is the mandatory final phase.

Success is observable in behavior, not only in text: in the Phase 2 gate, a fresh session following the loop marks a seeded unattributed pass "not supported" and stops a seeded re-proposal at Step 4a, in 3 of 3 runs each, against a Phase 1 baseline taken before the change.

## Resolved decisions

Recorded from the 2026-10-05 plan review (five lenses: coherence, feasibility, product, scope-guardian, design; security and adversarial skipped because no auth, user data, or hostile-reachable surface is involved; 42 findings, 13 P1, no P0, verdict REVISE) and the design interview (one round, three decisions):

1. Scope: everything ships, with every review fix applied (interview). Cut order runs from the tail so an implementer cutting under time pressure removes the last phase first.
2. Candidate history lives in the instinct YAML the candidate edits (interview). It is the only learned-layer store that already persists (`.nexus/instincts/<slug>.yaml`), so no ledger is added. A surface is one instinct file.
3. Enforcement is an ordering rule plus a paid 3-run behavioral gate (interview): the manifest is recorded with `rollback_ref` before the edit, and Phase 2 cannot close without the gate.
4. The held-out split is never read by a candidate disposition; `evaluator-validation.md` forbids it for any tuning decision. Non-degrade uses the development pool and `at_risk` cases (feasibility, scope, design).
5. Attribution signatures are limited to tool calls observable in the replay transcript, because hook events and self-reported citations are not captured or not independent (design, product).
6. The fixture-signal rule applies to target fixtures only and defers assertion-level non-discrimination to the existing F1 and H5 owners (design, product).
7. The concentration rule counts all dispositioned candidates, because approved ones have a hit rate near 1 by construction and the rule could never fire on them alone (design). Its thresholds are provisional (product, scope).
8. The surface enum and routing table live in `error-analysis.md` next to the annotations that use them; `failure-mode-ownership.md` gains one ownership row only (design).
9. Rejections match on the same instinct and the same `regression_id`, not on diff text, so a reworded re-proposal is still caught (design).
10. The controlled-language checker extends v4.17.10's shape detector, per that plan's no-sibling rule, and waits for v4.17.6, v4.17.10, and v4.18.1 (feasibility).
11. The state-machine skill's checker scope stays a `decision:` sub-task; its gate and verification are conditional on the choice (coherence, scope).
