**Goal**: A question a user skips during `design-interview` is never treated as agreement: a skipped high-impact question is asked once more, a second skip parks its branch, and a skipped low-impact question is listed as a default the user did not confirm. In the same release, round-trip payloads from HTML artifacts are treated as data, and a loop's check command must be deterministic and treat a retry-only pass as a failure. The one behavioral measure: in three fresh sessions, an agent following the changed skill re-asks a skipped high-impact question and does not re-ask a skipped low-impact one, and does so more reliably than the unchanged skill did at baseline.

**Also delivered unless cut** (structural checks only, no behavioral measure in this version): reproducible old-versus-new comparison (DoD 6), "must never happen" properties (DoD 7), compile-time authorization proofs for TypeScript (DoD 8), a reviewable plan page with its linter (DoD 9, 10), and seeded tests in Nexus-Hub's own suite (DoD 11). Cutting any of these along the stated cut order is an expected outcome, not a Goal miss.

## Problem

| Who is harmed | Harm today | Item |
|---|---|---|
| A developer answering a `/plan` or `/grill` round | `design-interview` attaches a recommended answer to every question but has no rule for a question the user skips, so a default the user never read can become a decision (Phase 1 measures how often this happens) | DoD 1, 3 |
| A user approving an `/implement` run | The paste section says approval "approves everything listed under Details" without saying that this includes the plan's defaults | DoD 2 |
| A user of an HTML artifact with a copy-as-JSON round trip | `html-output-conventions` defines the round trip with no rule that the returned payload is data, so pasted-back free text can steer the agent | DoD 4 |
| An operator whose loop trusts a flaky check | `loop-engineering` requires a timeout on `check_command` but not determinism, so a check that passes on the third try is read as success and the defect ships | DoD 5 |
| A user whose system an agent rewrote | `behavior-preservation-checker` Step 4 compares old and new on generated inputs but records no seed, normalization, or first divergence, so a reported mismatch cannot be reproduced and is dismissed as noise | DoD 6 |
| A user relying on an agent's self-checks | `property-based-test-generator` frames positive laws; no verification skill links to "must never happen" checks, so forbidden outcomes go unchecked | DoD 7 |
| Users of a TypeScript service | Authorization skills find missing checks after the fact; none shows how to make a missing check fail to compile, so the next refactor can drop a check unnoticed | DoD 8 |
| A reviewer of a long plan | Decisions sit in a long Markdown list, far from what they change, so a reviewer approves without reading them | DoD 9, 10 |
| A Nexus-Hub maintainer | The plan-queue ordering bug class (lexical versus integer sort) has no property test, and hook parity runs on fixed payloads only | DoD 11 |

## Definition of Done

**Must have:**

1. `catalog/skills/developer-experience/design-interview/SKILL.md` owns one canonical label set for answers: "answered", "not answered; default held", "accepted by blanket reply", and "held twice; parked". Step 1: a held default does not count as decided, so questions that depend on it wait. Step 2 and Step 4: a skipped question is "not answered; default held". It is asked once more in the next round when its default changes a phase, a file, a dependency, or the security posture (high impact). A second skip parks the branch with the reason "held twice; parked", so the frontier can empty. A skipped low-impact question is not re-asked. A blanket reply ("go with your suggestions") answers low-impact questions only; high-impact ones still get their one re-ask. Step 6, the first Verification item, and one Common Rationalizations row ("the user skipped it, so they agree") name the held state. In an unattended run, held defaults go to the session handoff owned by `session-handoff` (the `## Decisions taken by default` section once `v4.18.2` lands).
