## Goals First and Definition of Done

The target user is a developer who wants Nexus-Hub agents to work longer without supervision and to communicate results visually on whichever host they use (Claude Code, Codex, Cursor, Antigravity, OpenCode, Copilot, and the other registered integrations). The problems are: a scheduled agent that treats a failed read as a quiet day or posts twice; a comparison whose "the source lacks X" claims cannot be checked; and charts that show numbers without the query behind them. No `STRATEGY.md` or `docs/solutions/` exists at authoring; `README.md`, `AGENTS.md`, the existing owners and the seeding comparison are the available grounding.

1. **Unattended reliability (B1, B2)**: Every frozen unattended scenario produces its expected state through the run-ledger helper, including a failing source (reported by name, bookmark kept), a replay (no duplicate), an unclear write (`maybe posted`, nothing else changes), a crash between act and confirm, a stale lock, a far-future item, a lagging destination search, a spoofed matching title, and injected source text. Fresh-session agents on at least two hosts follow the protocol through the helper on three scenarios each.
2. **Autonomy outcome (B3)**: Five consecutive unattended runs through a local OS scheduler on each of two host classes complete with zero duplicate actions, zero silent skips, and every human intervention counted and attributed in the run records. The autonomy claim is scoped to the hosts actually exercised.
3. **Evidence-backed comparisons (C1, C2, C3)**: A comparison produced by the updated skill has a machine-readable ledger entry behind every finding row, no unbounded absence claim, a closed question checklist and an unknowns register. The checker verifies quotes against per-source roots, flags the drifted fixture, and reports on the v4.18.5 comparison and on the v4.18.4 comparison as a before/after: claims reclassified, adoption tasks changed, and report-length delta.
4. **Cross-platform reach (B3, V1)**: A dated scheduler-lever table covers every registered integration in one of three states (VERIFIED with source and date, "none documented", or "unverified as of date" tracked as a known gap). The template bullets ship to all thirteen substantive templates and every parity validator passes, unless v4.16.0's instruction-necessity verdict vetoes them, in which case the veto is recorded.
5. **Provenance visuals (V2, motion)**: `/visualize` gains a `query` mode that renders a multi-panel provenance page against a local SQLite fixture, with each panel's query, data-as-of timestamp and row count beside its numbers, refreshed by one re-run command; and an `animate` mode that renders a chart animation from its own data as editable CSS/SVG with a reduced-motion static alternative. Both work on a rendering host and degrade to a file path plus a table summary on a terminal-only host.
6. **Optional capability (C4, MP4)**: Cuttable. If kept, `/compare` accepts a built web bundle with source maps under the stated safety limits, and an animate-mode scene exports to an MP4 that `ffprobe` validates. If cut, each becomes a known gap with a named target version.
7. **Delivery**: The final phase's evidence, handbook and installer gates, independent Goal review and local suite pass. Implementation ends only on the completion checker's terminal result and the approved green integration flow, not on these authored checkboxes.

## Overview

The plan adopts the comparison's recommendations through existing owners in reverse-engineer-first order: skill-native protocol and evidence work first (B1, B2, C1, C2), with their bundled helpers (the run ledger and the citation checker, C3) built in the same phases because the contracts are only testable through them; then cross-platform verification and template distribution (B3, V1); then the `/visualize` query and animate modes (V2, motion); then the cuttable items (C4 limited to built web bundles, MP4 export gated on v4.18.0). The two blocking decisions (the run-ledger runtime and the dashboard ceiling) are recorded in Phase 1 so visual-scope risk surfaces before effort is spent.

Every item extends an existing owner: `loop-engineering`, `cross-project-comparison`, `platform-contract-verification`, `inline-visualization` and its `/visualize` command, and `html-output-conventions`. The only possible new skill is the v4.18.0 video owner in Phase 8, if its un-park decision designates one (+1 skill in that case). Both bundled helpers live inside skill trees, which both installers copy recursively, so no installer edit is needed. Query mode's verified client is Python's standard-library `sqlite3`; MP4 export uses ffmpeg and a headless browser only when already installed.

**Cut ceiling**: Phases 7 and 8 are cuttable without failing the Goal (DoD item 6). Excluded throughout: warehouse connector MCPs, hosted refresh, a live dashboard server, filters, vendor hand-offs, generated footage, REA's software or installer, Electron/APK/firmware/binary compare routes (deferred known gaps), Claude Managed Agents file formats as a distributed format, and blanket permission-bypass or auto-approve flags in scheduled runs. Construction-debt: reuse the loop schema, the comparison skill, `/visualize`, the representation ladder and the chart template; add only the fields, rules and helpers the defined outcomes need.

**Durable state tier**: bookmarks, the seen-id window, the item ledger and the latest write-attempt record form one per-loop-definition state document. It persists across runs, unlike the existing per-execution Instance State, which is deleted when an execution ends. It is gitignored, owner-only, replaced atomically as a single file, pruned by a stated retention rule, and never committed or shared without `egress-redaction`.

**Write-attempt states versus exit reasons**: `posting`, `posted` (with destination ids, a list), and `maybe posted` describe one write attempt. `budget_reached`, `no-data`, `failed`, and v4.17.3's outcomes describe how the run ended. A run that dies between act and confirm leaves `posting`, which the next run resolves exactly like `maybe posted`.

**Unclear-write resolution**: every write carries a unique run token (run id plus a hash of its item ids) in its body. `maybe posted` resolves only by an exact token match on a post written by the run's own account, or by direct lookup of a returned destination id. "Not found" inside the stated destination-lag window stays unclear. After a stated number of unresolved runs, the job stops and escalates to a human rather than retrying.
