Fourteen insights extracted; nine become adoption items, all local and skill-native or rebuilt locally, with no new third-party destination, credential, or runtime dependency.

Corrected the same day: the first inventory was read from a working tree 50 commits behind `origin/develop`; facts were re-checked on `origin/develop` and three were corrected (insight 11, the `html-output-conventions` template count, and the v4.13.9 queue row).

## Section 1: Executive Summary

Nexus-Hub already has the ingredients each source describes, but it lacks four specific mechanisms.

1. **Silence is read as agreement.** `design-interview` attaches a recommended answer to every question, and the `/implement` approval page approves everything under one paste line. Neither records whether the user actually looked at a default. S1's response sheet labels every decision either "kept as proposed" (opened, default kept) or "not opened; default kept", and tells the agent not to treat the second as agreement. This is the highest-value, lowest-effort item (A1).
2. **Plans have no reviewable rendering.** Nexus-Hub plans are Markdown phase lists, and they must stay Markdown because `implement-phase` and `check_plan_completion.py` parse their `T###` lines. Nothing renders them as a page that a reviewer can read in a minute and answer in place. S1's claim tree is the pattern to rebuild: behaviour claims at level 1, one exhibit per claim, decisions on the claim they change, a lint pass, and one pasted response. The rebuild is A2 and A3, with an original template and a Python linter. The S1 runtime is not vendored.
3. **The verification skills cover S2's tests unevenly.** End-to-end and property-based testing are covered, and `behavior-preservation-checker` Step 4 already compares old and new code on generated inputs. What it lacks is a recorded seed, a named normalization, shrinking to the first divergence, and reporting the seed and input (A7). No skill requires a loop's check command to be deterministic, or says that a check which passed only on retry has not passed (A8).
4. **Authorization-as-proof is untaught.** The catalog detects access-control flaws (`api-object-level-authorization-flaws`, `advanced-attack-patterns`) and designs RBAC/ABAC (`authentication-patterns`). It never shows how to make a missing check fail to compile. S3's pattern (named values, trusted proof modules, sensitive functions that demand proofs, and lint against forged assertions) becomes a TypeScript reference that teaches the pattern only, per the user's decision (A12). Its "file of code that must not compile" regression technique becomes A13.

Already covered, with no action: S1's STE prose rule (owned by queued `v4.18.1`, checked by `v4.18.2`) and S2's end-to-end ground truth (`e2e-testing-automation`, `functional-verification`, the `## Run and Verify` rule, and queued `v4.17.6`).

## Section 8: Risks, Conflicts, and NOT Recommended (Step 7)

Risks and conflicts:

- **Markdown remains canonical (A2).** `implement-phase` and `check_plan_completion.py` parse plan Markdown. The HTML page is a render that is answered and then folded back into the Markdown. If the two diverge, the Markdown wins, and the linter should fail a page whose claim count does not match the plan's DoD.
- **Two files over their line targets.** `property-based-test-generator` (682 lines) and `implementation-plan` (526 lines) are both above the 500-line target, so A9 ships as a reference file and A2 adds no body text to `implementation-plan`.
- **Approval-page budget (A1).** `approval-page.md` caps the summary and paste section at 140 words. A1's sentence must fit inside that cap, and the renderer's tests must prove it.
- **Security guidance accuracy (A12).** A wrong example in authorization guidance is worse than none. The reference must include the TypeScript limits (forged proofs, stale proofs, older compilers) and the stopping rule, and its examples must type-check under `tsc --noEmit` in the phase's verification.

NOT recommended:

| Item | Reason |
|---|---|
| Vendor or install the S1 plugin and runtime as a distributed artifact | It is a Claude-only plugin surface, while Nexus-Hub must reach every supported platform (AGENTS.md "Installer-Aware Changes"). Copying a 1,299-line runtime adds maintenance the catalog does not need; A2 and A3 rebuild the pattern originally. Users remain free to install the plugin themselves |
| Ship S1's STE substitution table | Conflicts with `v4.18.1` DoD 2, which forbids an approved/not-approved word table (ASD dictionary terms) |
| Name or recommend the upstream S3 npm package in a distributed artifact | The user chose a pattern-only adoption on 2026-10-06; the Reverse-Engineering Attribution Rule keeps upstream names out of distributed content |
| Add `hypothesis` as a development dependency for A10 | A seeded standard-library generator is the first sufficient rung (`minimal-construction`). Revisit only if shrinking of a real failure is needed |
| Apply S3's proofs to Nexus-Hub's own Python | Not applicable: Nexus-Hub scripts and local stdio MCP servers have no multi-user authorization decision to guard |
