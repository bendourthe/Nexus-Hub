Covers a goal-and-problem readback prompt, controlled-language and visual output formats, the public Claude Code Mods getting-started post, and a measured harness-side model router. Read it before planning v4.18.1. Key topics: readback round, ASD-STE100 register, mods source refresh, routing outcome ledger, tier calibration, MCP Registry Policy drops.

## Section 1: Executive Summary

Nexus-Hub already covers most of what these sources recommend. It routes work in the harness rather than through a gateway, routes subagents, refuses to downshift a failing task, prefers diagrams and HTML over long prose through a deliberate representation ladder, and has already analyzed Claude Code Mods (v4.15.2) and parked code-rendered video (v4.18.0 branch P1).

Three gaps are real and cheap to close:

1. **No readback before planning.** Nexus-Hub restates an idea only inside `idea-refine` Step 1, which runs for vague ideas. `/plan` and `/grill` start interviewing without first playing back the user's goals and problem for correction. S1's prompt does that playback, and it is the cheapest point to catch a misreading.
2. **No controlled-language register.** Nothing in the catalog names ASD-STE100 or offers a stricter, requestable writing register. Users who ask for it get an improvised approximation.
3. **Routing is never measured.** This is the strongest finding. Across 347 scored v4 plan phases, 231 (67%) are `frontier`, 98 `strong`, 18 `standard`, and none `fast`. The `/implement` run record stores no routing outcome, so nothing can tell whether those frontier phases needed it. In S4's test, by contrast, only 10% of threads needed the top tier, while a cheap-only control arm was stopped within a day. S4's core lesson is to "put measures of success in place before you route", and Nexus-Hub has the rubric but not the measurement.

The recommendation is to measure first and calibrate second. Loosening the rubric now would trade the no-degradation guarantee for savings no evidence supports.

S3 adds no new adoption item. It is a newer and more public source for the surface v4.15.2 already plans, so it becomes a dated source-refresh note on that plan.

## Section 6: Sequenced Adoption Plan (Step 6)

2. **A1, readback round.** Add a "Round 0: readback" step to `catalog/skills/developer-experience/design-interview/SKILL.md`: before the first question round, restate in the agent's own words (a) the user's goals, (b) the problem being solved, and (c) assumed constraints, each in one or two sentences, then ask for corrections. 3. **A2, controlled-language register.** Add `catalog/skills/developer-experience/writing-editing/references/controlled-language.md` and link it from the body. Two levels. *Full*: one topic per sentence, procedural sentences at most 20 words and descriptive at most 25, one instruction per sentence, imperative mood for steps, active voice, one meaning per word, noun clusters of at most three words. *Softened* ("80%"): keep the sentence-length and one-meaning rules and relax the vocabulary restriction. Add trigger nouns ("ASD-STE100", "Simplified Technical English", "controlled language") to the `writing-editing` description, and update `data/skills.json` and `data/SKILL_INDEX.md` text to match. State that the register applies only on request and overrides `technical-writer`'s 25-word average only then.
4. **A3, routing outcome ledger.** Extend the `/implement` run record defined in `implement-phase/references/completion-contract.md` with per-phase fields: recommended tier and effort, resolved model, upshift count, GO/NO-GO iteration count, and final verdict. After v4.17.11 lands, add its `verification_effort`. Reuse v4.17.3's outcome vocabulary (`no-data`, `partial`, `complete`, `failed`) rather than inventing values. Store no prompt text. Add tests in the existing `tests/` layout.
5. **A4, calibration procedure.** Add `catalog/skills/ai-development/model-routing/references/calibration.md` with one command (an extension of `model-map.py`, standard library only) that reports tier distribution from plan files and ledger outcomes per tier. Review rule: no rubric change is proposed until at least 30 ledger phases exist. A tier earns a downshift proposal only when its phases passed GO/NO-GO on the first iteration with no upshift, and any proposal is recorded as a decision record before the rubric changes. The no-downshift-mid-failure rule stays untouched.
6. **Final phase.** Architecture refactor, known-gaps reconciliation, registry checks (`python scripts/check_registry_entries.py --check --strict`), the `full` CI profile, and the single integration PR.

## Section 8: Risks, Conflicts, and NOT Recommended (Step 7)

### Risks and conflicts for recommended items

- **A1** adds one exchange before planning. Mitigation: the skip clause for a readback already answered in the session, and a two-sentence cap per part.
- **A2** conflicts mildly with `technical-writer`'s 25-word average. Resolved by scoping: the register applies only when requested.
- **A3** edits an existing contract file (higher risk than adding a file) that the plan-completion checker reads. Its tests must prove that existing run records without the new fields still parse.
- **A4** could be read as permission to downshift. The review rule and the untouched no-downshift rule prevent that; a calibration is a proposal recorded as a decision, never an automatic change.
- **Transfer limit**: S4 measured chat threads; Nexus-Hub routes plan phases, which are larger by construction. A 67% frontier share is not proof of overspend, only proof that it is unmeasured.

### Explicitly NOT recommended

| Candidate | Reason |
|---|---|
| Hosted narration (ElevenLabs) for explainer videos (S2.4) | Generation-as-service is on the MCP Registry Policy hard-no list, and the narration script leaves the machine. Local speech belongs to v4.18.0 branch P1 |
| LangSmith Insights and Custom Apps for trace analysis (S4.9) | Hosted trace analytics send prompts and code to a third party with no existing commercial relationship; fails MCP Registry Policy tier 4 condition 1. A3 and A4 are the local equivalent |
| Jev classifier and LangChain routing middleware (S4.9) | A hosted classifier is generation-as-service, and Nexus-Hub is not a LangChain application. The rubric already classifies in the harness |
| Loosening the routing rubric now (S4.8) | No local evidence yet. It would weaken the no-degradation guarantee on the strength of another team's chat traffic |
| Third-party benchmark index as tier authority (X1) | `model-routing` holds placement as operator judgment (lines 89, 182). An aggregator can inform a deliberate move recorded in a plan's map section, but adopting it as an authority would recreate the reshuffle defect the `diff` guard exists for |
