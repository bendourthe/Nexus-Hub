# Comparison: Code-Rendered Animation and Illustration Quality

Authored: 2026-09-28
Authoring cycle: v4.13.x (last tag `v4.13.3`)
Adoption target: v4.18.0 (confirmed 2026-09-28; items 7 to 9 parked for a follow-on plan, see `plans/v4.18.0-adoption-code-rendered-animation-and-illustration-quality.md` parked branch P1)
Sources: seven (one supplied prompt, three Git repositories, three articles)
Skill: `cross-project-comparison`

This comparison asks one question: can the prompts and pipelines behind the recent wave of code-rendered Opus 5.5 videos raise the quality of the illustrations Nexus-Hub produces in `/presentify`, PowerPoint decks, and report figures? The short answer is yes, but only through the process disciplines. The paid generation stack in the supplied prompt (hosted image generation, hosted video generation, hosted sound design) is categorically out of scope under the MCP Registry Policy, and the sources themselves show it is not what made the videos work: the best-documented example drew every pixel in JavaScript with no generation model at all.

The adoption target is `v4.18.0`. The plan queue is occupied through `v4.17.8`, and `v4.17.9` already holds an unplanned comparison. A new rendered-video capability is a minor-version feature, not a patch, so the next free minor is the natural slot. `cross-project-comparison` Step 6.5 says "Always CONFIRM the resolved target with the user before writing the report"; the report was written first because it is a reversible file, and the target moves with the user's choice.

## Step 7: Risks and conflicts

- **Conflict with the job-fidelity rule.** `scroll-scrub.md` section 2 forbids inventing a narrative in presentify. Items 1 to 3 improve how the source's own content is shown; they must not license new story content in a handbook. Only item 7, a separate skill, authors original narrative, and only when the user asks for a video.
- **Conflict with readability of data figures.** B2's text-light rule comes from a cartoon. Charts, maps, and diagrams need labels, so item 2 carries the explicit exception.
- **New dependency.** Items 7 and 8 introduce `ffmpeg` as a hard requirement for that route only. It is detected lazily and never checked by the base installers.
- **Maintenance cost.** Item 7 is a new skill with a renderer script and needs tests (render a two-second fixture scene, assert frame count and duration with `ffprobe`), plus a `.ps1`-safe path story because the script runs through Python, not bash.
- **Existing files changed.** Items 1 to 6 edit existing references, which is a higher risk than adding files. Each edit is additive and scoped to one section.
- **Quality claims.** None of these items guarantees a result "better than anyone's ever seen". The strongest documented example took two full generations and a model-written style guide. The plan should measure improvement with paired before and after renders, the method `v4.17.6` already uses.

## Answer to the originating question

The prompts and examples can raise illustration quality in `/presentify`, PowerPoint, and report figures, but the part that transfers is the production discipline behind the videos, not their tools. Five habits carry the effect:

1. Decide the medium and the anti-reference before drawing anything (item 1).
2. Write down what each visual must make the viewer understand, and keep it to one idea (item 2).
3. Define recurring elements once and reuse them, so a set of figures looks like one piece (item 1).
4. Review sequences as contact sheets instead of one screenshot at a time (item 6).
5. Keep every frame a pure function of time, so a figure can later become a video without a rewrite (item 7).

Items 1 and 2 are small reference edits and deliver most of the value for static output. Items 6 to 8 add a genuinely new, fully local capability: an MP4 rendered from code.
