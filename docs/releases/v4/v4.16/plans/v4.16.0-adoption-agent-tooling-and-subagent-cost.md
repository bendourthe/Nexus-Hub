## Definition of Done

All six hold:

1. `CLAUDE_CODE_SUBAGENT_MODEL` is named in the lever contract with fetched, dated first-party evidence, and a key-level assertion enforces that it cannot be declared in the defaults source without that row.
2. Every Nexus-Hub agent whose output quality depends on reasoning tier carries explicit `model:` frontmatter, committed BEFORE any subagent default is seeded.
3. The seeded value reaches a user who is UPGRADING, not only a user installing fresh, proven by a regression test over a pre-existing settings file.
4. The UI skill cluster's owning skill names a runnable deterministic check in its Verification section that did not exist before.
5. `multi-agent-code-review` Stage 1 states a deterministic grouping rule in place of its current "~800 changed lines" heuristic, with coverage provably unchanged.
6. `python scripts/ci/run.py --profile full` is green and the integration pull request's required checks are green.

- **No `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`.** It is recorded in the `doc_statement` for accuracy and deliberately not seeded. Forcing would also capture the built-in Explore and Plan subagents, which is a larger behavioral change than this plan is scoped for.
- **No new runtime dependency, outbound call, API key, or third-party data processor.** The two comparison sources that would have added any of these were classified `drop-outright`.
- **No theme-catalog artifact**, per the Scope Excluded gate in `hallmark-design`.
- **No accessibility rule restated.** Contrast severity and reduced-motion stay owned by `[[accessibility-engineering]]`.
- **No Nexus-Hub-authored lint rule set.** Phase 4 ships guidance plus one adaptable reference configuration. Authoring and maintaining original rules has no active call site in this repository and fails the `AGENTS.md` Boundaries gate; it is recorded as a rejected alternative in the Phase 4 decision record, not deferred silently.
- **No change to the existing `model: opus` pin** in `configs/platform-defaults.json`.

## Overview

This plan operationalizes the adoption items from the seeding comparison, restructured after a six-lens plan review that returned three findings serious enough to change what the plan does.

**The correction that reshaped this plan.** The seeding comparison, and this plan's first draft, both asserted that seeding a subagent default without the force flag "preserves the `model:` frontmatter on Nexus-Hub's shipped agent definitions". That is false. `grep -l "^model:" catalog/agents/*.md` matches 0 of 23 files; no shipped agent declares a model. Seeding therefore routes every Nexus-Hub agent, including the review personas and the plan-review lenses, to the seeded tier, and it does so while `configs/platform-defaults.json` still carries a `model: opus` rationale stating that a fresh install should "reason at full strength". Phase 2 exists to make the original claim true before Phase 3 makes the change. The comparison's A1 note is annotated with this correction.

**Two gate-passing no-ops the first draft would have shipped.** `scripts/sync_platform_defaults.py` propagates only the keys listed in each `derived_artifacts[].keys` array, which is hardcoded to four keys for `claude`. Declaring the lever under `settings.env` alone changes neither derived artifact, and `--check` still exits 0, satisfying the draft's own Stability Gate while delivering nothing. Separately, `install_core_settings` in both installers early-returns when a settings file already has `model` plus an effort lever, which is true of every prior Nexus-Hub install, so the seeded value would reach fresh installs only. The draft's proposed verification (a fresh install into a throwaway directory) exercises exactly the path that works. Phase 3 closes both.

**Ordering.** The comparison's Step 5.4 table ordered the items A2, A4, A1, A3. This plan sequences the subagent work as one contiguous block (evidence, then pinning, then delivery) and the skill work after it. The reverse-engineer-first rule exists to stop a vendor tool being adopted before a local rebuild is attempted, and it does real work when a `vendor-intrinsic` candidate is present; no item here is `vendor-intrinsic`, so the bucket ordering has no work to do, while splitting a three-phase safety sequence around unrelated skill edits would make the riskiest change harder to review and revert. To restore the comparison's literal order instead, move the review-fanout phase ahead of the seeding phases; no phase content changes.

**Build class convention.** Sub-tasks are labelled `load-bearing` (the artifact that proves the design works) or `scaffolding` (provisional, with its replacement named). The label appears only where a reader could not otherwise tell, and is omitted from prose-only and tooling-only sub-tasks.

## Phase 2: Pin the Shipped Agents

**Goal**: Every Nexus-Hub agent whose output quality depends on reasoning tier declares explicit `model:` frontmatter, so the Phase 3 seed governs only agents that are genuinely tier-indifferent.

**Prerequisites**: None (independent of Phase 1; must complete before Phase 3).

**Stability Gate**: Each of the 23 agents in `catalog/agents/` either declares `model:` frontmatter or appears in a written deliberately-unpinned list with a one-line reason, and a test asserts that partition covers all 23 with no file in neither set.

**Verification Expectation**: Run the new partition test and observe it pass; then deliberately add a new agent file with no `model:` and no list entry, run it again, and observe it FAIL. The point of this phase is that a future agent cannot be added unpinned by accident.

**Recommended model tier**: strong

**Recommended effort level**: medium

**Rationale**: Mechanically simple frontmatter edits, but the judgment about which agents are tier-sensitive determines whether Phase 3 causes a silent quality regression.

### Sub-tasks

#### 2.1 -- Classify and pin the agents

**Objective**: Decide per agent whether its quality depends on reasoning tier, and pin the ones that do.

If a pinned value conflicts with a platform that does not read `model:` frontmatter, the key is ignored rather than breaking the definition; verify this against the read contract before mass-editing. ## Phase 3: Declare, Propagate, and Deliver the Default

**Goal**: The lever is declared in the source of truth, propagated to every derived artifact, and actually delivered to an upgrading user's settings file by both installers.

**Prerequisites**: Phase 1 (the key-level assertion added in 1.4 makes this a machine block, not only a policy one) and Phase 2 (pinning must precede seeding, or the seed downgrades every agent).

**Stability Gate**: `python scripts/sync_platform_defaults.py --check` exits 0 after `--apply`, BOTH derived artifacts visibly carry the new key, a regression test proves an upgrade over a pre-existing `settings.json` receives it, and `python scripts/ci/run.py --profile full` is green.

**Verification Expectation**: Run the upgrade regression test: seed a temporary `settings.json` containing `model` and `effortLevel` (the shape every prior Nexus-Hub install produced), run the installer's core-settings path against it, and observe that `env.CLAUDE_CODE_SUBAGENT_MODEL` is present afterward while the pre-existing values are unchanged. A fresh-install check does NOT satisfy this gate; the fresh path already works and is not where the defect lives.

**Recommended model tier**: frontier

**Recommended effort level**: max

**Rationale**: Edits the single source of truth for a value seeded into every installing user's settings, plus both installers, a generator, a fallback constant, and a project-scoped stub. Highest blast radius in the plan.

### Sub-tasks

**Objective**: Add the lever to `configs/platform-defaults.json` AND to both `derived_artifacts[].keys` arrays, without which the declaration propagates nothing.

**Failure modes**: If `--check` fails after `--apply`, the fallback constant in `scripts/lib/integrations/claude.py` has drifted and must be reconciled rather than the check suppressed. If the seeded alias is unreachable by an account, behavior follows the Phase 1.1 finding; if 1.1 recorded a gap instead of a statement, this sub-task stops and escalates rather than assuming graceful degradation. If a user already set the key, seed-if-absent leaves their value untouched and no overwrite path is added.

**Build class**: load-bearing.

**Prompt**:

> Edit `configs/platform-defaults.json` only (never a derived artifact). In the `claude` entry:
>
> 1. Add `"CLAUDE_CODE_SUBAGENT_MODEL": "sonnet"` inside `settings.env`.
> 2. **Append `env.CLAUDE_CODE_SUBAGENT_MODEL` to the `keys` array of BOTH `derived_artifacts` entries** (`catalog/hooks/settings.json` and `scripts/lib/integrations/claude.py`). `sync_platform_defaults.py` iterates `artifact["keys"]`, not the settings tree, so without this the declaration is a no-op that still passes `--check`. #### 3.3 -- Deliver the value to upgrading users
