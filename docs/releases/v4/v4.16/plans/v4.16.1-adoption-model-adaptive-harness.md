## Overview

This plan is the decision half of the comparison against OpenAI's "Rethinking skills and prompts for GPT-6 Astra". It builds no runtime capability. It answers whether one should exist.

That shape is the result of a seven-lens plan review of this document's own first draft, which returned one P0 and eight P1 findings against a version that went straight to building. Three of those findings changed the plan structurally. The scope and product lenses independently found the instruction-surface work unrelated to the runtime work and higher in user value, so it has moved to the companion plan `v4.16.0` and ships regardless of what this one decides. The product lens found the original pilot measured cost with no instrument for benefit, and that it ran after the code was already written, where an honest negative result competes against sunk cost. And the security and adversarial lenses found that the profile layer this plan would consume is not merely unconsumed but arguably unfit to consume, which is evidence about the decision rather than a task to work around.

**The P0, stated plainly, because it is the plan's most important input.** The `model-prompting-research` profile layer is populated by an agent reading third-party vendor web pages and extracting claims. Those claims are schema-valid, confidence-scored, adversarially refuted, and primary-source cited. None of that is a trust control: the content still originates outside this project and would terminate in the agent's context window on every turn. Nine of the seventy-two committed claims carry imperative harness-altering language, including one on `claude-opus-5` reading "so REMOVE explicit verification instructions and legacy harness verification scaffolding". Injecting that verbatim would instruct the agent to drop the scaffolding `[[verification-before-completion]]` exists to enforce. A quality gate was mistaken for a provenance gate, and Phase 1 exists partly to establish how much that finding actually bears on the verdict.

**What this plan does not do.** It adds no resolver, no schema field, no hook, no injected context, no dependency, no credential, and no outbound call. Its only new executable artifact is a throwaway prototype that is deleted inside the same phase that creates it. If the verdict is to build, the build is a separate future minor release authored against this plan's evidence; this plan does not pre-specify it, because pre-specifying it is what produced the build-by-default pressure the review found.

**Relationship to v4.13.0.** The adjacent `v4.13.0-adoption-evidence-driven-agent-improvement.md` plan covers neighbouring ground (its Phase 5 is context fact freshness, its Phase 6 a bounded skill-trigger and context-loading pilot). This plan deliberately does not amend it. Task ids here begin at `T101`, and `v4.16.0` begins at `T201`, so all three plans can be fanned out to issues together without collision.

**Knowledge-base grounding.** No `docs/solutions/` store and no root `STRATEGY.md` exist. The product lens noted this is the second queued plan to record that absence and recommended running `[[product-strategy]]`; that recommendation is carried into Phase 3's known-gaps reconciliation rather than actioned here.

#### 1.2 -- Build, run, and delete the measurement prototype

**Objective**: Produce real cost and benefit numbers before any decision, using a prototype that never enters the catalog.

**Failure modes**: With a missing, unreadable, or non-regular `transcript_path` (a FIFO, device node, directory, or symlink resolving outside the session directory), the prototype returns a fixed enum reason and reads nothing; a FIFO that blocks forever would otherwise hang the exercise. With a dependency unreachable or slow: there is no dependency, but the transcript itself is the slow case, so the read is bounded by BYTES (seek at most 256 KiB from EOF) rather than by line count, because one legitimately multi-megabyte JSONL record satisfies a line bound while exhausting memory; any single candidate line over a stated cap is discarded unparsed. With conflicting operations: the harness appends to the transcript while the prototype reads it, so a truncated final line is the NORMAL case rather than corruption; unparseable lines are skipped and scanning continues backward to the last well-formed assistant record.

**Build class**: scaffolding. It lives in the session scratchpad, never under `catalog/` or `scripts/`, and sub-task 1.4 deletes it in this same phase. Nothing in a later phase depends on it existing.

**Prompt**:
> Write a throwaway prototype **in the session scratchpad directory only**. It must not be created under `catalog/`, `scripts/`, or anywhere in the committed tree, and 1.4 deletes it before this phase ends.
>
> It reads a hook payload on stdin and prints either a resolved model id or `unresolved: <reason>`. Implement the failure modes above. Two hard privacy constraints apply even to a throwaway, because it reads full conversation history:
> - Extract ONLY `message.model`. Every failure reason is drawn from a fixed closed enum of constant strings; no reason string may interpolate any value read from the transcript. A `json.JSONDecodeError` message embeds the offending document fragment, so never propagate exception text.
> - Wrap all transcript I/O and parsing in a single catch-all boundary. Write no log, cache, or debug file anywhere.
>
> Then measure, on a fixed prompt set of at least five realistic prompts, and record everything in `docs/releases/v4/v4.16/development/injection-prototype.md`:
> - **Cost**: baseline tokens, injected tokens, delta per turn, and whether prompt caching was preserved. Measure the WORST realistic case (`claude-fable-5-1`, which carries 18 claims), not a sparse one.
> - **Latency**: p50 and p95 wall-clock for resolution, measured against a real long-session transcript rather than a fixture. A component that would run on every prompt submission can fail by stalling, and token delta does not detect that.
> - **Benefit**: a paired with/without run on the same prompt set, graded by assertion or rubric. This repo already ships `[[skill-eval-loop]]` for paired runs and `[[ai-output-evaluation]]` for the rubric; use them. **If a benefit instrument is genuinely out of reach at this scope, say so explicitly and label the exercise UNEVALUATED**, so nobody later reads the token table as validation.
>
> Before measuring, read `v4.11.1-adoption-cache-and-diagram-quality` and record what it constrains about caching. Note in the record that its intent is not yet landed behavior.
>
> One premise to test rather than inherit: the seeding comparison asserts that per-prompt injected text "sits in front of the cached prefix and can defeat prompt caching". `UserPromptSubmit` stdout is appended alongside the user's message, at the END of the conversation, in which case per-prompt injection costs tokens without invalidating the cache and the stated rationale is wrong. Determine which is true from the measurement and record the answer.

#### 1.3 -- Audit the profile layer for runtime fitness

**Objective**: Establish whether the content a consumer would inject is fit to enter an agent's context, which the seven-lens review identified as the decision's most important input.

**Prompt**:
> Write `docs/releases/v4/v4.16/development/profile-layer-trust-audit.md`. Audit every committed claim in `catalog/skills/ai-development/model-prompting-research/assets/profiles-index.json` (72 claims across 12 models as of 2026-09-14) and record:
>
> 1. **Reachability.** The resolver reads `message.model` from a Claude Code transcript, so it can only ever produce an Anthropic id. Exactly three of the twelve profiled models are Anthropic (`claude-opus-5`, `claude-fable-5-1`, `claude-sonnet-5`); `claude-haiku-4-5` is rostered but unprofiled. State plainly that a Claude Code consumer would reach a quarter of the layer, which is the number the "closes the consumer gap" framing must be judged against.
> 2. **Trust classification.** Classify each claim as runtime-safe reference material, or as carrying an imperative directive that would alter harness behavior. Quote the worst examples verbatim. As of 2026-09-14 nine claims match imperative remove/disable/ignore language, including `claude-opus-5`'s "so REMOVE explicit verification instructions and legacy harness verification scaffolding", which directly contradicts `[[verification-before-completion]]`.
> 3. **Actionability.** Many claims are addressed to a prompt author rather than to a running agent, and several are API-transport claims a Claude Code session cannot act on at all (`gpt-6-astra`'s "Remove temperature, top_p, and top_logprobs from requests"). Count them. `references/schema.md` defines no field distinguishing the two, so record that a correct runtime filter cannot be written against today's schema.
> 4. **Selection basis.** The claims array is unordered and carries no priority field, so any payload bound would truncate at an arbitrary index. Record that a bound without a ranking basis makes a measurement irreproducible.
> 5. **Data defect.** Eleven of twelve entries carry `"platform": "claude-code"`, including `composer-2.5`, `cursor-grok-4.5`, `cursor-grok-4.6`, and four `gemini-*` ids that Claude Code does not serve. This is pre-existing and not caused by this plan; record it for Phase 3's known-gaps reconciliation.
>
> Frame the whole audit through `[[prompt-injection-defense]]`: the trust chain runs vendor web page -> agent extraction -> bundled JSON -> installer -> per-turn agent context, and a poisoned or merely careless vendor page is a supply-chain input to that chain. Do NOT design or build a fence here. The audit is evidence for the Phase 2 verdict; building sanitization machinery is exactly the scope the review warned against.
