## Step 2-3 -- Insight Extraction and Classification

### S1 -- WikiSkill (arXiv 2608.27454v1)

The paper separates an agent workspace into three layers and runs a four-stage evolution loop. Its measured claims, for reference: WikiSkill lifts average accuracy over the strongest competing skill-evolution method by 3.3 to 12.0 points across five models, and the ablation isolating the persistent wiki moves the Skill Proposer from 48.7 percent to 63.7 percent average.

### S4 -- HarnessTax study

Read from the study's own chart JSON. Design: 7 models paired across 3 harnesses (Pi as baseline, Claude Code, Codex), 30 tasks per cell, Holm-corrected significance.

**SWE-bench Lite, success rate.** 1 of 14 pairs shows a difference surviving Holm correction: Claude Opus 4.8 on Codex, +6.7pp over Pi (p_holm 0.042). The other 13 cover zero.

**SWE-bench Lite, cost.** 8 of 14 cost ratios survive Holm. Selected:

| Model | Harness vs Pi | Cost ratio (mean) | Median | Rate delta | Rate clear after Holm |
|---|---|---|---|---|---|
| GPT-5.6 Luna | Claude Code | **5.09x** | 5.22x | +0.022 | No |
| GPT-5.6 Sol | Claude Code | **3.50x** | 3.50x | +0.033 | No |
| Claude Opus 4.8 | Claude Code | **2.06x** | 2.98x | +0.044 | No |
| Claude Fable 5 | Claude Code | **2.00x** | 2.24x | +0.011 | No |
| Kimi K3 | Codex | **1.86x** | 2.20x | +0.022 | No |
| Claude Opus 4.8 | Codex | 1.47x | 2.09x | +0.067 | **Yes** |
| Claude Sonnet 4.6 | Claude Code | 0.99x | 1.13x | +0.022 | No |

Terminal-Bench 2 is descriptive only, with no confirmatory test on any pair.

**Coverage caveat (added 2026-09-17, after plan review).** These ratios are not usable as a lookup table today, and an earlier draft of this section overstated their applicability. Mapped against this comparison's own 16-cell model map, only three cells carry any measurement and one of those is a null result:

| Tier | Anthropic | OpenAI | Google | Cursor |
|---|---|---|---|---|
| frontier | Opus 5 - unmeasured | GPT-6 Astra - unmeasured | unmeasured | unmeasured |
| strong | Fable 5.1 - unmeasured | GPT-5.6 Sol - 3.50x | unmeasured | unmeasured |
| standard | Sonnet 5 - unmeasured | GPT-5.6 Terra - unmeasured | unmeasured | unmeasured |
| fast | Haiku 4.5 - measured, null | GPT-5.6 Luna - 5.09x | unmeasured | unmeasured |

Every frontier cell is empty, the whole Google and Cursor columns are empty, and the single measured Anthropic model (Haiku 4.5) produced no effect surviving Holm correction on either axis. Kimi K3 carries a real 1.86x but is not in the map. Two further limits bound what may be claimed: at 30 tasks per cell under Holm correction across 14 comparisons, the design detects only large success-rate gaps, so a non-significant rate result means "no difference detected at this power", never "no difference"; and a cost ratio is partly a function of vendor pricing at measurement time, which moves independently of behavior. The **mechanism** is well supported and is what candidate A adopts. The **numbers** are a dated snapshot about a superseded generation and are deliberately not shipped into the catalog.

### NOT recommended

**H -- Adopting Tencent/BrowserSkill as a dependency. Classification: `drop-outright`.**

Grounds, against the MCP Registry Policy decision tree. It is not tier 1 (not internal, not Anthropic-official). It is not tier 2 (a browser automation runtime is not achievable by instructing an LLM). It is not tier 4: Tencent is not the intrinsic destination of the data, and Nexus-Hub has no commercial relationship with Tencent, so the your-own-account condition fails outright. That leaves tier 3 or tier 5. Tier 3 is not viable at acceptable cost, because a local equivalent means writing and maintaining a browser extension plus a native daemon.

Three further concerns independent of the policy tree. The documented install path has an agent fetch and follow a remote instruction file, which is the seam `[[agentic-endpoint-hardening]]` exists to close, so adopting it would have Nexus-Hub recommending the pattern it teaches others to guard against. The tool writes into the same per-harness skill directories `scripts/installer.{sh,ps1}` own, with no defined precedence. And it grants an agent reach into live authenticated sessions, which is a materially different blast radius from anything currently in the catalog.

The underlying capability is real and unmet. Verification behind a login is a genuine gap in `[[browser-testing-with-devtools]]`, and `catalog/rules/html/visual-self-verification.md` already requires an agent to render and inspect its own output rather than ask the user for a screenshot, which it cannot do for an authenticated page. **Record this as a known gap via `[[known-gaps-tracker]]` with the `re-partial` classification.** Do not schedule it for v4.16.3; it needs its own design pass, and the honest local starting point is a separate browser profile driven by an already-present automation library, not a new daemon.

**I -- Cloud-by-default factory infrastructure. Classification: `drop-outright`.**

The source is vendor marketing for Warp Factories, ending in a $10k early-access offer, and its central recommendation ("Development in the cloud by default") inverts Nexus-Hub's local-first posture. The valuable parts of S6 are either already implemented (S6.1, S6.2, S6.4-S6.7) or extracted as G. Nothing remains that justifies the trust transfer.

### Considered but not recommended for other reasons

- **S1.8** (denying the inference agent wiki access) is an experimental control in the paper's own design, not a portable rule.
- **S3.7** (git-mailbox coordinator agents) presupposes an always-on cloud fleet. `[[agent-orchestration-primitives]]` covers in-session orchestration, which is the shape Nexus-Hub actually runs.
- **S1.5** (`PURPOSE.md` provenance per skill) is genuinely attractive and was nearly promoted to its own candidate, but it would add a required file to all 337 skills and to `validate_skills.py`. Folded into B as an optional provenance field on the knowledge layer instead, where it costs nothing catalog-wide.
