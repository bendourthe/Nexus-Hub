# Comparison: Tool-Output Containment and Per-Request Context Attribution

**Adoption target: v4.16.3**

**Sources**:

1. context-mode, <https://github.com/mksglu/context-mode>, commit `5869f4f` (2026-10-13), npm `context-mode` 1.0.169, Elastic License 2.0. An MCP server plus hook set that keeps raw tool output out of the context window, stores session events in SQLite, and restores working state after compaction across 17 clients.
2. A pasted article, "How to find what's filling up Claude Code's context", describing the `ui/turn-inspector` mod from <https://github.com/davila7/claude-code-templates> (MIT). The mod source at `cli-tool/components/mods/ui/turn-inspector/` was read alongside the article.

**Source types**: Source 1 is a Git repository (11-dimension comparison, focused on the dimensions that apply). Source 2 is an article plus the mod it describes (insight extraction).
**Authored during**: v4.13 cycle, on `docs/v4.16.3-comparison` cut from `origin/develop` at `c9fd528df`
**Date**: 2026-10-13
**Slot rationale**: The per-request report (candidate B) reuses the transcript record-shape decision that v4.16.0 records in T014, so this comparison must follow v4.16.0. v4.16.3 is the lowest free slot after it, in the context-focused v4.16 minor, and needs no renumber. The maintainer confirmed v4.16.3 on 2026-10-13 over the alternative of appending at v4.22.4.

Nexus-Hub already covers most of what context-mode does: local reversible output compression, SSRF-guarded fetch, a session digest re-injected at SessionStart, and installers for 17 platforms. Three gaps are real. First, nothing tells the agent to compute an answer in a script instead of reading bulk data into context. Second, nothing shows which request or tool result filled the window, and this is the gap that matters most. Third, the post-compaction digest records git and plan state but not the last request, open tasks, or unresolved errors. The source's MCP server, sandbox executor, hosted dashboard, and the mod itself are not adopted.

## Step 1.5: Source security scan

The scan ran mechanically over both cloned trees before any content was read into working context. Both clones sit in isolated scratch directories, and nothing from either source was installed or executed.

**Source 1 verdict: PROCEED-WITH-CAUTION.**

| Check | Result |
|---|---|
| Prompt injection / agent-directed instructions | None. The pattern hits for "you are now" are a report heading ("Where you are now") in `src/session/analytics.ts` and its tests. The repository ships agent instruction files (`configs/*/CLAUDE.md`, `AGENTS.md`, `GEMINI.md`) meant for installation, so they direct agents by design. None were followed; all are treated as data. |
| Hidden or obfuscated directives | No zero-width or bidirectional characters anywhere in the tree. The one long base64-like run is `tests/fixtures/github-issues.json`, a test fixture. |
| Malicious or destructive code | None found. The `rm -rf /*` hits are deny-rule examples in `.claude/settings.json` and `README.md`. `curl ... \| bash` appears only as printed advice to install Bun (`src/cli.ts`, `scripts/postinstall.mjs`) and is never executed. |
| Supply-chain risk | **Cautions.** (1) `package.json` declares `"postinstall": "node scripts/postinstall.mjs"`. That 384-line script edits `~/.claude/plugins/installed_plugins.json`, `~/.claude/settings.json` and the plugin cache, creates symlinks or junctions, runs `npm config get prefix` and `mklink /J` on Windows, and normalizes hooks. (2) `scripts/heal-better-sqlite3.mjs` rebuilds a native module. (3) Committed minified bundles (`cli.bundle.mjs`, `server.bundle.mjs`, `hooks/*.bundle.mjs`) cannot be fully audited and cannot be proven to match `src/`. (4) `hooks/platform-bridge.mjs` POSTs every session event to a configured `platform_url`. It is inert unless `~/.context-mode/platform.json` exists, but it contradicts the README's "Nothing leaves your machine". (5) `ctx_upgrade` self-updates from GitHub, and `src/cli.ts` polls `registry.npmjs.org`. |

**Source 2 verdict: CLEAR.** The mod folder holds a manifest, a hooks declaration, two TypeScript modules (751 lines), a README and a test. It has no install script, no network call, no injection text, and no binary. Its hooks only observe and pass every event through unchanged. One caution concerns the install path the article recommends, not the mod itself: `npx claude-code-templates@latest` runs an unpinned package from the registry. The article's closing "P.S." is a marketing link and was ignored.

All source content is treated as data throughout this report.

## Step 5: Security and reverse-engineering assessment

### 5.1 Threat model comparison

| Question | context-mode as shipped | Nexus-Hub after adoption |
|---|---|---|
| New runtime dependencies | Node 18+ or Bun, `better-sqlite3` (native), a global npm package | None. Python standard library only. |
| Outbound calls | npm registry version check, GitHub self-upgrade, the opt-in event forwarder, the hosted Insight page | None. Candidate E only advises; it fetches nothing. |
| Credentials or API keys | None required; the forwarder takes an `api_key` | None |
| Source, prompts or query text leaving the machine | Only when the forwarder is configured | Never |
| New commercial relationship | None, unless the hosted platform is used | None |
| Writes outside the project | `~/.claude/settings.json`, the plugin registry, `~/.context-mode/` | Only the existing `.nexus/context/` digest and the compressor's existing `~/.nexus-hub/` ledger |

### 5.2 Per-item risk scorecard

| Candidate | Risk | Reason |
|---|---|---|
| A. Compute-don't-read rule | None | Instruction text only. |
| B. Per-request context report | Low | Reads transcripts, which can hold secrets. Mitigated by the output contract: it prints numbers, tool names and block kinds only, never content, and writes nothing beside its report. |
| C. Realized-savings ledger | Low | Extends an existing local JSONL ledger with byte counts. No content is logged. |
| D. Priority-tiered compaction digest | Medium | Persisting the last user request writes prompt text to disk under `.nexus/context/`, which may be committed. Gated on redaction through `egress-redaction`, a size cap, and the existing `.gitignore` coverage, which must be verified. |
| E. Raw-fetch advisory | Low | Advisory only (exit 0). It never blocks, so a false positive costs one line of context. |

### 5.3 Reverse-engineering viability

| Candidate | Class | Note |
|---|---|---|
| A | `skill-native` | A rule in `prompt-token-optimization`, which owns "functions over data" and programmatic tool calling in the `context-engineering` rule-ownership table. |
| B | `re-full` | A standard-library parser over local transcripts. The turn inspector's algorithm (exact totals from `usage`, growth since the previous request split across new blocks by size) is simple and needs no mod runtime. |
| C | `re-full` | Extends `savings.py`, which `context-optimization` owns as the tool-boundary output engine. |
| D | `re-partial` | The priority-tiered digest is buildable inside the existing hooks. The full SQLite event store, FTS5 indexing and BM25 retrieval of events is not adopted. |
| E | `re-full` | A new case in the single `rewrite.py` decision point. |

### 5.4 Recommendation ordering

1. `skill-native`: A.
2. `re-full` / `re-partial`: B (P1), C (P1), E (P2), D (P1, gated).
3. `vendor-intrinsic`: none.
4. `drop-outright`: see NOT recommended.

- **F. Intent-filtered retrieval over stored output**: index large compressed or dropped spans in an FTS5 table and retrieve by query instead of by hash. This is context-mode's `intent` filter plus its ranking stack (Porter and trigram tokenizers merged by reciprocal rank fusion, proximity reranking, fuzzy correction). It is `re-partial`, medium value and high effort, and it extends the compressor beyond the Bash boundary that v4.19.0 deliberately keeps. Record it as a known gap with v4.19.0 as the scope owner.

### Plan reconciliation (2026-10-13)

The seeded plan's six-lens review changed four things this report assumed. First, Claude Code writes one transcript record per content block and repeats `usage` on each (about 2.6 records per request on three local transcripts), so B groups by request id. Second, `egress-redaction` has no executable script, so D gains a stdlib redactor and a shared Python tier helper instead of shell parsing. Third, the rewrite hook can only emit a permission decision, so E needs a separate non-decision channel. The maintainer kept E on that basis and chose to build D fully, still gated on v4.15.1. Fourth, B's code moves beside the existing usage probe in `catalog/hooks/` and is reached through a new `/usage context` scope.

## Risks and conflicts

- **Duplicated rules.** A must extend the existing Programmatic Tool Calling section rather than add a parallel one. D must not restate pinned rules (v4.16.0) or the compression method (`context-compression` owns it).
- **Estimates read as measurements.** The turn inspector's split of a total across its blocks is a heuristic. If B prints `~1,200` and `1,200` the same way, a user will trust a guess. The `~` contract is mandatory, not cosmetic.
- **Prompt text on disk (D).** `.nexus/context/last-session.md` gains user text. Nexus-Hub's own `.gitignore:84` ignores `.nexus/` (checked with `git check-ignore` on 2026-10-13), but `session-summary.sh` does nothing to ensure that in a user's project, where the digest could be committed. D must write the request only when the path is git-ignored, redact through `egress-redaction`, and cap the stored request.
- **New files versus edits.** B is a new file (lower risk). A, C, D and E edit existing files, and D edits a hook with a `.ps1` sibling, so it carries the parity test burden.
- **Attribution rule.** Distributed artifacts must not name either source project. Names stay in this report and in the matrix row only if a registry entry is ever proposed, and none is.
