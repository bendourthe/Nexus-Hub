# Comparison: Agent Tooling and Subagent Cost Control

**Adoption target**: v4.16.0

**Authored**: 2026-09-15 (during the v4.12.0 closure cycle)

**Sources**: five, mixed type (one article excerpt, one landing page, three Git repositories)

**Source security verdict**: PROCEED-WITH-CAUTION (Step 1.5, recorded below)

This comparison evaluates five external sources against Nexus-Hub. One yields a first-party-verified configuration lever that Nexus-Hub's own source of truth is missing, one yields a deterministic verifier for a skill cluster that today is graded entirely on model judgment, one yields a pattern worth copying without its tool, one is declined on evidence, and one could not be read.

## Source security scan (Step 1.5)

Verdict: **PROCEED-WITH-CAUTION**. No prompt injection, embedded agent-directed instructions, obfuscated payloads, credential harvesting, or destructive code was found in any fetched source. All instruction-like text in the sources was treated as data. Two findings justify the caution tier rather than CLEAR:

- `totec448-spec/chat-on-steroids` requires the user to enable ChatGPT Developer mode and then drives an authenticated ChatGPT web session from a third-party Electron application. This is a trust-boundary and account-terms concern, not malicious code.
- `alibaba/open-code-review` installs a global npm package (`npm install -g @alibaba-group/open-code-review`) whose setup flow prompts interactively for a provider API key. Standard for its category, but it is a new credential surface and a new outbound destination.

No source was BLOCKED, so ingestion proceeded.

## S1: Subagent model environment variable

The article claims Claude Code subagents inherit the session model and that setting `CLAUDE_CODE_SUBAGENT_MODEL=opus` reduces usage. The variable is real and documented. The article's procedure is incorrect in two ways, both verified first-hand against official vendor documentation on 2026-09-15.

**Correction 1: the article omits the flag that makes it work.** `code.claude.com/docs/en/sub-agents` states: "Setting `CLAUDE_CODE_SUBAGENT_MODEL` by itself doesn't change the model the built-in Explore and Plan subagents run on." Explore and Plan are the highest-volume built-in subagents, so the article's three steps leave the dominant consumers untouched. Covering them requires `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` set to `1`.

**Correction 2: the article's recommended value is the wrong direction.** The article routes to `opus` to reduce usage. `code.claude.com/docs/en/model-config` gives its cost-reduction example as `haiku`. Opus is a frontier tier; routing a frontier session's subagents to another frontier tier is not a reliable saving. This matches what [[model-routing]] already states in its own overview: model choice is the reliable cost lever, and the lever only pays when the tier actually drops.

**Documented resolution order** (quoted from the vendor page, highest precedence first):

1. The per-invocation `model` parameter.
2. The subagent definition's `model` frontmatter, where `inherit` selects the main conversation's model.
3. The `CLAUDE_CODE_SUBAGENT_MODEL` environment variable.
4. The main conversation's model.

Setting the variable to `inherit` is documented as equivalent to leaving it unset.

**The gap in Nexus-Hub.** `docs/policy/platform-defaults-levers.md:33` classifies `claude` as VERIFIED and lists its levers as `effortLevel`, `model`, `env.CLAUDE_CODE_EFFORT_LEVEL`, `attribution.commit`, and `attribution.pr`. `configs/platform-defaults.json` seeds exactly those. Neither file mentions `CLAUDE_CODE_SUBAGENT_MODEL`. A repo-wide search returns no occurrence of the string in any config, script, skill, or policy file.

This is a documented, first-party, dated lever on a platform already classified VERIFIED, on a config surface Nexus-Hub already writes. It satisfies the `do_not_invent` rule in `configs/platform-defaults.json` without exception. Its absence is a genuine gap in the single source of truth, not a deliberate omission: the file's `omitted` mechanism exists to record deliberate exclusions with a reason, and this lever has no such entry.

## S3: alibaba/open-code-review

Go and TypeScript, Apache-2.0, distributed as a global npm package. It reviews Git diffs by combining a deterministic layer (file selection, bundling of related files, rule matching, comment positioning) with an agent layer (scenario-tuned prompts, context retrieval through a purpose-built toolset). It requires an LLM provider and an API key, or a Delegation Mode in which the user's own agent performs the review. It claims significantly higher precision and F1 at roughly one ninth the token consumption of a general-purpose agent, benchmarked on 200 real pull requests across 50 repositories.

**The tool is declined; the pattern is adopted.** Adopting the tool would add a new global npm dependency and a new provider credential to do what [[multi-agent-code-review]] already does, which is squarely the generation-as-service shape the MCP Registry Policy names in its hard-no list. Delegation Mode avoids the key but then the tool contributes only its deterministic layer, which is the part that is reverse-engineerable.

The pattern is genuinely relevant. `multi-agent-code-review/SKILL.md:114` already acknowledges that a persona fanout plus per-finding verification "carries a 5-15x token multiplier" and prescribes scope-first calibration as the mitigation. Scope-first is an instruction to the agent. A deterministic pre-pass that selects and bundles related changed files before any persona runs would cut the same multiplier mechanically rather than by asking the agent to be disciplined, and it would produce a deterministic verifier-class input rather than a model-judged one. This is `skill-native` plus an optional bundled script, entirely local, no new dependency.

## S4: totec448-spec/chat-on-steroids

TypeScript, Electron, Vite, plus a Chrome extension. MIT. A desktop application that lets ChatGPT read and edit files, run tests, hold terminals open, and use the desktop, with multi-worker task distribution, a Markdown skills framework invoked by `/` commands, and Goal / Loop / Compact-and-Resume task management.

**The direct question asked was whether this reduces Codex usage. It does not.** The project's own documentation states that "ChatGPT Work and Codex share usage limits". It routes work through the user's ChatGPT conversation rather than invoking Codex directly, which moves consumption between two pools that bill against one limit. The README makes no optimization or token-reduction claim at all. Activation additionally requires enabling ChatGPT Developer mode and granting a third-party Electron application control of an authenticated session, which expands the trust boundary for no measured saving.

Classified `drop-outright` and moved to the NOT-recommended list. The actual Codex-side cost lever already exists in Nexus-Hub: `model_reasoning_effort` in `~/.codex/config.toml`, declared in `configs/platform-defaults.json` and owned by [[model-routing]].

One secondary observation is recorded without an adoption recommendation: the project's skills framework is Markdown files invoked by `/` commands, which is structurally the same contract Nexus-Hub distributes. It is evidence that the SKILL.md-style convention is spreading beyond the vendors Nexus-Hub tracks, and it may become a read-contract question later. It is not a v4.16.0 item.

## S5: shadcn-ui/lint

TypeScript, MIT, published as `@shadcn/lint`. An agent-first linter for Tailwind design systems, shipped as both an ESLint (v9.30+) and an Oxlint (v1.80+) plugin. Six built-in rules detect restyling, raw colors, arbitrary values, inline styles, unknown classes, and non-static class strings. Contracts are customizable per component, messages support placeholders such as `{{sizes}}` and `{{file}}` so the diagnostic itself tells the agent how to fix the violation, and it is design-system agnostic rather than tied to shadcn/ui. No API keys. No outbound network calls.

**This fills a hole Nexus-Hub has already named in its own contract.** `multi-agent-code-review/SKILL.md:106` requires every finding to name its verifier class from the four-class taxonomy (deterministic, evidence-based, model-based, human) and states the reason directly: "a review whose findings are entirely model-based has been graded on one axis". Nexus-Hub's UI skill cluster is currently that single axis. The `## Verification` block in `hallmark-design/SKILL.md` asks that "every gate in the catalog passes" with no machine check named anywhere, and a search across `catalog/skills/developer-experience/` finds no skill that references ESLint, Oxlint, or a lint rule as a design-system verifier.

shadcn/lint converts a subset of those gates from model judgment into a deterministic verifier. The relevant Nexus-Hub surfaces are [[hallmark-design]], [[color-systems]], [[layout-and-spacing]], and [[interface-review]]. The adoption is the pattern of a machine-checkable design-system contract, expressed as Nexus-Hub skill guidance plus optionally a bundled configuration reference, not a vendored copy of the package.

### Notes on A1

> **CORRECTION, 2026-09-15.** The original version of this section asserted that Nexus-Hub's shipped agent definitions declare their own `model:` frontmatter, and that omitting `_FORCE` therefore preserves those pins. **That is false.** `grep -l "^model:" catalog/agents/*.md` matches 0 of 23 files; no shipped agent declares a model. The error was found by the plan-review lenses during `/plan from-comparison` and verified directly. Its consequence: seeding any subagent default routes EVERY Nexus-Hub agent, including the review personas and plan-review lenses, to the seeded tier. The adopting plan (`../plans/v4.16.0-adoption-agent-tooling-and-subagent-cost.md`) therefore adds a phase that pins the tier-sensitive agents BEFORE the seed lands, which is what makes the reasoning below true rather than aspirational. The bullets are corrected in place.

The confirmed posture is declare and seed `sonnet` without `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`, preceded by an explicit agent-pinning phase. The reasoning is recorded here so the implementing plan inherits it rather than re-deriving it:

- Seeding `haiku` with `_FORCE` is the larger saving and is the vendor's own documented cost example, but `_FORCE` is documented as overriding per-invocation models and definition `model` fields. Once the tier-sensitive agents carry explicit pins (the adopting plan's Phase 2), `_FORCE` would override those pins, trading review quality for cost without measurement.
- Seeding `sonnet` without `_FORCE` applies only to subagents that have no model assigned another way. Before Phase 2 that population is ALL 23 shipped agents; after Phase 2 it is only the agents deliberately left tier-indifferent, which is the population where a default is appropriate. The ordering is what makes this bullet true.
- The `env_precedence_warning` in `configs/platform-defaults.json` applies: this lever is environment-variable only, with no scalar counterpart in `settings.json`, so it is declared under the existing `env` block alongside `CLAUDE_CODE_EFFORT_LEVEL`.
- The vendor statement that `_FORCE` is required to reach the built-in Explore and Plan subagents must be recorded in the `doc_statement` field, because a future reader will otherwise assume the seeded value covers them. It does not.

## Risks and conflicts (Step 7)

- **A1 changes distributed behavior for every installing user.** It is the only item here that does. It is reversible, it is seed-if-absent so it never overwrites a user's own value, and it must be documented against the capability usage gate in `catalog/commands/update.md` governance step 6: activation mechanism, validation command, disable path, the authority it does not grant, and a canonical documentation link.
- **A1 edits a derived-artifact source.** `configs/platform-defaults.json` is the only hand-edited file; `catalog/hooks/settings.json` and `scripts/lib/integrations/claude.py` are derived and must be regenerated with `sync_platform_defaults.py --apply`, never hand-edited. `--check` runs in `make validate` and CI and will fail on drift.
- **A1 must not be seeded before A2 lands.** `configs/platform-defaults.json` forbids a platform lever without a VERIFIED row in `docs/policy/platform-defaults-levers.md`, and `tests/validators/test_platform_defaults_levers.py` enforces it mechanically. Sequencing A2 first is a hard ordering constraint, not a preference.
- **A3 must not create a theme-catalog artifact.** `hallmark-design/SKILL.md` carries an explicit Scope Excluded gate against that, and its verification block requires the Hallmark and Together AI attribution be preserved. A3 adds a verifier, it does not restructure the skill.
- **A3 must respect rule ownership.** Contrast severity and reduced-motion belong to [[accessibility-engineering]], per the existing handoff in `hallmark-design`. A design-system lint contract must not restate those rules, only reference the owner.
- **A4 risks duplicating an existing contract.** `multi-agent-code-review` already owns depth modes, finding caps, and the verifier taxonomy. A4 adds a deterministic pre-pass, and must not restate scope-first discipline that the skill already owns.
