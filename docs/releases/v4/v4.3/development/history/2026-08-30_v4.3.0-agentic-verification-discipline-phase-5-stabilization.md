### 2.3 Regression triage

A throwaway detached worktree at `HEAD` ran the same three affected test files and passed 29 of 29, establishing that all six failures were regressions introduced by the uncommitted platform work rather than inherited flakiness. The worktree was then removed.

Three distinct root causes were isolated:

**RC1 - the Copilot opt-in gate no longer guarded anything.** Agent and native-hook installation had been inserted into `wire_project_surfaces` ABOVE the `_copilot_skills_enabled` check, so 82 files were written into `.github/agents/` and `.github/hooks/` with the opt-in absent. `.github/` is commit-visible, which is precisely why that surface is documented as off by default; the defect would have placed 82 uninvited files into every consuming repository.

**RC2 - a silent write failure in the ownership helper.** `_link_like_managed_ancestor` compared only `os.path.abspath` spellings, which normalizes neither Windows 8.3 short names nor POSIX symlinked parents. Every write under such a root returned `kept` with nothing on disk and no error raised. Demonstrated directly on this host, where `TEMP` is the short-name form.

**RC3 - an intentional change applied to one adapter and not the other.** A vendor-verified move of `AGENTS.md` to the workspace root was applied completely to OpenCode (config, code, and read contract) but only to Antigravity 2.0's code, leaving its config declaring `.agents` while the code wrote to the root. The same contract update also invalidated a test that hardcoded `.opencode/AGENTS.md` instead of reading the config its sibling test reads.

### 2.4 Fixes, test-first

RC2 was fixed with a failing-first regression test that constructs an alternate spelling of the target root (Windows short name, or a POSIX symlinked parent, skipping where neither is available); it failed with `expected a real write, got 'kept'` before the fix. The repair adds `_relative_within`, which falls back to a canonical comparison only for containment. The ancestor walk deliberately continues to use the ORIGINAL spelling, because `realpath` resolves exactly the symlinked entries the guard exists to detect.

RC1 was fixed by moving the agents and hooks install below the opt-in early return. One assertion in the bundle-selector test was scoped to the skills tree rather than every created file, which preserves what it checks (the correct bundle was seeded) without weakening it.

A third defect surfaced while fixing RC2: the guard refused EVERY destination outside `target_root`, silently disabling global-scope writes to `~/.copilot`, `~/.claude`, and the VS Code user directory. On the maintainer's decision the guard now treats an out-of-root destination as having no managed ancestor to police, and leaf-level protection is retained. Two regression tests cover it: the out-of-root write lands, and a hard-linked destination is still never written through.

RC3 was fixed by declaring `instruction_workspace_dir` on the Antigravity 2.0 config so the config remains the single source of truth for placement, and by deriving the OpenCode teardown path from that config.

### 2.6 Publication, a red integration result, and stabilization

The branch was pushed once as commit `89bf4e40` and PR #146 was retitled and rewritten to cover both deliverables. Four required or contributing checks came back RED (`ci-required`, `tests`, `tests-windows`, and `install-smoke` on all three operating systems), which reopened the phase.

Every cause was reproduced locally before a fix was written. Three of the four were unreachable from a single Windows developer host, which is the argument FOR the pull request being the plan's first remote validation rather than evidence against the local gate:

- A Windows-only `stat` constant read at class-definition time made one test an unconditional Linux error instead of a check of the reparse-tag fallback.
- The Copilot permission bridge required `st_nlink == 1` exactly. Windows populates that field only when the stat call opens a handle, so a runner on the fast path reports `0` and every authoritative rewrite was denied. Reproduced locally with a failing-first test that simulates `st_nlink = 0`, then fixed to `> 1`, the predicate that actually detects a hard link and the one the ownership helper already used.
- `ci.yml` asserted a stale Codex verify label, and fixing it exposed a second stale Gemini assertion the fail-fast loop had never reached.

The verified read contract was consulted BEFORE the Gemini assertion was changed, to confirm the product was correct and the assertion stale rather than editing a test to match broken output. CI's exact install-smoke loop was then replayed locally against a throwaway `HOME` with all five expectations matching, and the full local gate re-run green at 42 passed with profile exit 0.

### 2.7 A wrong diagnosis, and the interpreter defect it was hiding

The Push 1 stabilization fixed three of four causes. `tests-windows` failed again, and the reason is worth recording: the first diagnosis was wrong. It attributed the failure to the bridge's `st_nlink == 1` predicate, and the fix built on that hypothesis changed nothing.

What settled it was comparing the observed output against the branches that can produce it, rather than reasoning further about the test. A non-zero child returns `deny` with the default reason; an authority rejection returns `modifiedArgs` with no `permissionDecision`. CI's output matched the first exactly, so permission authority was never involved. The `st_nlink` change and its regression test were reverted, because a security predicate should not be loosened on a disproven hypothesis.

The empty stderr was the clincher. A missing interpreter raises `OSError` and surfaces a `hook-compat:` reason; the default reason means `bash` was found, ran, exited non-zero, and printed nothing to stderr, which is the Windows WSL launcher stub's exact signature (its notice goes to stdout). `tests/conftest.py` documents that hazard for the suite; the production bridge had no equivalent.

This is a user-facing defect rather than a test artifact: on a Windows host whose PATH `bash` is the stub, every guarded tool call would have been denied with no actionable diagnostic. `_resolve_bash_command` now resolves a bare `bash` to a verified absolute Git Bash on Windows, leaves a caller-chosen absolute interpreter alone, leaves POSIX untouched, falls back to the original command when no Git Bash exists, and rewrites at the execution site only so the permission-authority binding is unchanged.

### 2.8 Closing the gate's blind spot

The third integration round confirmed the interpreter resolver: `tests-windows` passed. `tests` failed on a defect in the round-3 TEST rather than the product, because patching `os.name` on Linux makes `pathlib.Path()` construct a `WindowsPath` and raise. A `_windows_host()` indirection replaced it.

That prompted the wider question the maintainer chose to settle before release: three of four causes across two red rounds were invisible to a green local suite because they depended on the host, and nothing in the gate could observe that class at all. The exposure is broader than the bridge, since the assistant host launches every Nexus-Hub bash hook as `bash <script>` and a WSL-stub `bash` leaves all of them silently inert.

The closure has three parts: an end-to-end regression test that places a stub `bash` first on PATH (verified to fail with the resolver disabled), a shared probe reported by `runner.py verify` as an actionable NEEDS-ACTION line, and a new `interpreters` gate group in the fast, full, and platform profiles. The group sits inside existing profiles rather than being a new workflow job, so it adds no required status context.
