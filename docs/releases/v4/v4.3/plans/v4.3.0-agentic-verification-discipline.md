# Plan -- Agentic Verification Discipline

**Project**: Nexus-Hub
**Version**: v4.3.0
**Slug**: agentic-verification-discipline
**Plan Type**: Feature / Enhancement (harness capability)
**Created**: 2026-08-29
**Goal**: Nexus-Hub stops verifying only artifacts and starts verifying behaviour. A tiered verification ladder ships in the catalog: cheap deterministic checks at every phase gate including a functional smoke of what that phase actually built, a recorded plan-delta note so the plan is questioned as it is executed rather than trusted to the end, and a fail-closed deep pass before release that dynamically exercises every feature the plan produced, checks rendered output for visual defects with a real detector, runs an adversarial pass, and audits whether the plan itself was complete -- all scaled to blast radius so a docs typo stays cheap while a user-facing surface cannot ship unexercised. Every consuming project inherits it on install.

## Overview

The maintainer's third guide review named a pattern rather than a defect list: obvious visual and UX problems keep reaching them. Investigation found the cause is structural, not a lapse in diligence.

**The harness verifies artifacts, never behaviour.** `implement-phase`'s GO/NO-GO gate evaluates four things -- tests pass, coverage at or above 80 percent, zero lint errors, build succeeds -- and every one of them can be true of a feature that has never been run once. A page whose text spills outside its container satisfies all four. Nothing in the gate asks whether the thing built actually works when exercised.

**The plan is treated as ground truth.** From the moment `/plan` writes it until the Goal-vs-codebase review in the final phase, nothing asks whether the plan was right. That final review checks that the Goal *landed*, not whether the Goal was *sufficient*. A plan that omitted a necessary step produces a phase-complete, gate-green, genuinely incomplete result, and nothing catches it.

**There are no instruments for whole classes of defect.** `catalog/rules/` covers bash, go, python, and typescript but has no html or css entry. No hook inspects an `.html` write. `validate_unicode_safety.py` still excludes `.html`. Visual defects are invisible to the harness by construction, so every catch to date has depended on a human noticing a screenshot.

This release fixes all three, on an economy the maintainer specified: **cheap and continuous at every gate, expensive and deep once at the end.** Deep verification at every phase boundary is both costly and wasteful, because later phases rewrite earlier work. So the ladder puts fast deterministic checks everywhere and reserves the expensive judgment-based work -- dynamic exercise of every feature, UI and UX assessment, adversarial review, plan-completeness audit -- for a single thorough pass before release. Depth scales with blast radius: a user-facing surface triggers the full pass, a docs typo records a no-op.

Scope is deliberately harness-only. The guide rebuild that exposed this moves to **v4.4.0**, where it becomes this discipline's first real test case. That ordering matters: building the guide with the process that produced the current defects would repeat them.

Nothing here is new machinery for its own sake. It composes existing skills -- `[[verification-before-completion]]`, `[[adversarial-verifier]]`, `[[e2e-testing-automation]]`, `[[browser-testing-with-devtools]]`, `[[implementation-convergence]]`, `[[quality-gate-definitions]]` -- which already exist and are simply not wired into the gate. The new surface is one skill that owns the procedure, one detector, one rule, one hook, and the wiring that makes them fire.

## Phase 1: Design the Verification Ladder

**Goal**: Decide the discipline before building it, because a verification regime that is expensive, noisy, or vague gets disabled, and a disabled gate is worse than an honest absence of one.
**Prerequisites**: None.
**Stability Gate**: A written contract exists covering every tier, every trigger, and the cost of each check, reviewed against this project's own failure history; it names what is deliberately NOT checked and why.
**Recommended model tier**: frontier
**Recommended effort level**: max
**Rationale**: Pure design with high leverage and no undo -- every later phase and every consuming project inherits these decisions, and a wrong economy here makes the whole discipline unusable.

### Sub-tasks

#### 1.1 -- decision: the tier contract

**Objective**: Fix what runs when, and prove the economics work, before any code exists.

**Prompt**:
> Write `docs/releases/v4/v4.3/development/verification-ladder.md`, the contract this release implements. Define four tiers. **Tier 0**, per subtask, effectively free: the compile-or-import check that already exists. **Tier 1**, per phase gate, cheap and deterministic, seconds not minutes: today's four checks (tests, coverage, lint, build) PLUS artifact-appropriate static checks PLUS a functional smoke that actually runs what this phase built. **Tier 2**, per phase, a paragraph: the plan-delta note, recording whether implementing this phase revealed the plan to be wrong, incomplete, or based on a false assumption -- recorded always, acted on only when blocking. **Tier 3**, once before release, deep and expensive: dynamic exercise of every feature the plan produced, UI and UX verification where applicable, an adversarial pass, and a plan-completeness audit.
>
> For each tier state: what runs, what it costs in time and tokens, what a failure means, and who may waive it. Justify the economy explicitly -- the maintainer's instruction is fewer iterations per phase and more at the end, because later phases rewrite earlier work and re-verifying at every boundary pays repeatedly for results that get thrown away. Show that arithmetic rather than asserting it.
>
> Ground every tier in this project's own history, which is the evidence that the current gate is blind: a text chip too narrow for its label, a subtitle past its viewBox, two captions colliding, a takeaway rule stopping at 45 percent width, a command echoed twice, a monitor silently dead because `jq` was absent, and a contrast token that regressed the moment a new component used it. For each, say which tier would have caught it and how. Any historical defect no tier catches means the ladder is still incomplete.
>
> Finally, name what is deliberately NOT verified and why. A discipline that claims to check everything is not believed, and specificity about the boundary is what makes the rest credible.

## Phase 2: Build the Instruments

**Goal**: Build the missing detectors, starting with the defect class that has no instrument at all: rendered visual defects.
**Prerequisites**: Phase 1.
**Stability Gate**: The detector reports zero findings on a correct fixture and the right finding on each broken fixture; the responsive-layout rule exists; the hook blocks a fixed-width text cap and its PowerShell sibling agrees on every exit code; `make lint` and `make test` pass.
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: Heuristic design where a noisy detector is worse than none, plus mandatory cross-platform hook parity that has bitten this repository before.

### Sub-tasks

#### 2.1 -- The visual-defect detector

**Objective**: Make "the layout is fine" a testable claim rather than an opinion.

**Failure modes**: With Playwright absent it exits non-zero with an install hint, never a silent success -- a checker that is quiet when it did not run is the exact failure that let a `jq`-less monitor sit silent through a red CI run in v4.2.2. A page that fails to load is a finding, not an empty pass. Elements hidden by design (`display: none`, `hidden`, zero-opacity scroll-reveal states) are excluded from geometry checks so a not-yet-revealed section is not reported as clipped. Two findings on one element report once at the highest severity. A selector that cannot be evaluated is reported as "could not evaluate", never dropped.

**Build class**: load-bearing.

**Prompt**:
> Implement the detector defined by the Phase 1 taxonomy as `catalog/skills/testing/functional-verification/scripts/detect_visual_defects.py`. It renders a local HTML file with Playwright across a viewport matrix and emits findings as JSON plus a readable summary, exiting non-zero on any gate-severity finding. Measure from `getBoundingClientRect()` and computed styles: an element escaping its parent's padding box beyond a tolerance; SVG content past its `viewBox`; overlapping boxes between text-bearing nodes that are not ancestor-descendant; `scrollWidth` over `clientWidth` where no `overflow-x` scroller is declared; a `max-width` in `px` or `ch` on a text-bearing element; a rendered box under a minimum size that still holds text; and a computed `font-size` below the legibility floor.
>
> Take a tolerance flag so sub-pixel rounding is not a finding, and an allowlist file so a deliberate exception is recorded in the repository rather than by weakening the rule. Print every finding with its selector, viewport, measured numbers, and the rule that fired -- a finding the reader cannot locate does not get fixed. This lives in a skill's bundled `scripts/`, which both installers copy recursively; confirm against the "Per-skill Bundled Resources" section of AGENTS.md that no installer edit is required rather than assuming it.

- [x] T005 Renderer-backed visual-defect detector catalog/skills/testing/functional-verification/scripts/detect_visual_defects.py

#### 2.2 -- Proving fixtures

**Objective**: Prove the detector detects, and prove it does not cry wolf.

**Failure modes**: Each fixture is broken in exactly one way, so a passing test names the class it proved. The clean fixture uses the same components as the broken ones, or it proves only that an empty page has no defects. Fixtures are committed HTML, never generated at runtime, so a detector change cannot move its own goalposts.

**Build class**: load-bearing -- this is what makes the detector trustworthy enough to gate on.

**Prompt**:
> Create `tests/verification/fixtures/visual/` with one small HTML file per gate-severity defect class, each broken in exactly that way, plus `clean.html` using the same components correctly. Write `tests/verification/test_visual_defect_detector.py`: clean yields zero gate findings, and each broken fixture yields exactly its expected class. Include the false-positive cases that would otherwise get the tool switched off: a legitimate `overflow-x: auto` scroller is NOT a horizontal-overflow finding; a scroll-gated element at zero opacity is NOT a clipping finding; and `@media (max-width: 720px)` is NOT a fixed-width finding -- that last one produced five false offenders in v4.2.3 and is the single likeliest way this detector becomes untrusted. Skip cleanly when Playwright is unavailable, and assert the no-Playwright path exits non-zero with a hint rather than reporting success.

#### 2.3 -- Responsive-layout rule and enforcement hook

**Objective**: Stop fixed-width text at the moment it is written, not at review.

**Failure modes**: The hook exits 0 cleanly on a non-HTML path, absent content, or unparseable payload -- a guardrail that blocks unrelated work gets disabled. It matches a `max-width` declaration on a text-bearing selector, never a `@media (max-width: ...)` breakpoint. It reads only the payload and never opens the network. Its block message names the declaration, the file, and the rule. The documented `NEXUS_DISABLED_HOOKS` mechanism provides a per-session escape.

**Build class**: load-bearing.

**Prompt**:
> Create `catalog/rules/html/responsive-layout.md`, a new language directory beside bash, go, python, and typescript. It states the maintainer's rule of 2026-08-29: generated HTML must never cap text at a fixed `px` or `ch` width; the container governs and text stays responsive to the window. Cover what IS allowed (one container max-width, `overflow-x: auto` on genuinely wide content, `text-wrap: balance` on headings, a bounded media element) and what is not. State that it binds every HTML artifact the harness produces -- documentation, `/presentify`, `document-to-interactive-html`, reports -- not just this repository's guide. Match the existing rules files' terse tone.
>
> Then write `catalog/hooks/html-responsive-guard.sh` as a PreToolUse hook on Write and Edit that blocks such a declaration, and the MANDATORY `catalog/hooks/html-responsive-guard.ps1` sibling with matching behaviour -- `test_hook_sibling_parity.py` fails when a sibling is missing, does not parse, or disagrees on an exit code, and CI parses every catalog `.ps1` unconditionally. Prefer native PowerShell (`ConvertFrom-Json`, not `jq`; `[Console]::IsInputRedirected` for the tty check). Register the bash invocation in `catalog/hooks/settings.json`. Write `catalog/hooks/tests/test_html_responsive_guard.py` with a `run` fixture parametrized over BOTH implementations so every behavioural assertion doubles as a parity assertion, covering the block case, the media-query false positive, and each clean-exit path.

**Objective**: Author the skill that owns how to dynamically exercise a built artifact.

**Failure modes**: A skill that is too abstract ("test your feature thoroughly") is unfollowable and gets skipped; one that is too specific to one stack does not fit the projects that install it. The body must give per-artifact-type procedures with concrete observable outcomes. It must NOT restate rules owned elsewhere per the Phase 1 ownership table -- it references those owners by name.

**Build class**: load-bearing -- this is the release's procedural core.

**Prompt**:
> Author `catalog/skills/testing/functional-verification/SKILL.md`. It owns one concern: HOW to actually exercise a built artifact, as opposed to whether you are allowed to claim done, which `[[verification-before-completion]]` owns.
>
> Follow the AGENTS.md SKILL.md contract exactly: required frontmatter (`name`, `description`, `summary_l0` at most 15 words, `overview_l1` at most 150 words); a PUSHY description listing trigger phrases verbatim ("did you actually test it", "verify this works", "check the feature runs", "does the UI actually render", "exercise the feature") AND a SKIP clause fencing off look-alikes (writing unit tests, which `[[unit-tests]]` owns; auditing accessibility, which `[[accessibility-engineering]]` owns; judging visual design, which `[[hallmark-design]]` owns). Body sections in the required order.
>
> The Instructions section is the substance: per-artifact-type procedures, each with a concrete observable outcome. Cover at least a CLI (run it with real arguments; assert exit code AND output, since a zero exit with wrong output is the classic false pass), a library or API (call it across a real boundary, not only unit-tested in isolation), a web UI (render it, interact with it, run the visual detector), a hook or script (fire it with real payloads including malformed ones), a document or artifact generator (generate one and open it), and a configuration change (apply it and observe the effect). For each, say what evidence counts and what does not.
>
> Write Common Rationalizations from this project's actual history, not generic principles: "the tests pass" is how four blind gates certified a broken layout; "the screenshots looked fine" is how a chip too narrow for its label shipped; "I checked it earlier" is how a contrast token regressed the moment a new component used it; "it is a small change" is how a trailing newline blocked a pull request. Verification must be binary and observable -- an artifact, an exit code, a measured number -- never "it looks right".
>
> Register in all three registries: `data/SKILL_INDEX.md`, `data/skills.json`, `data/marketplace.json` (increment the category `skill_count` and `statistics.total_skills`). Run `make validate` after.

## Phase 4: Wire the Discipline Into the Harness

**Goal**: Make the ladder fire automatically. A discipline that depends on being remembered is the failure mode this release exists to remove.
**Prerequisites**: Phase 3.
**Stability Gate**: `implement-phase` carries Tier 1 and Tier 2 at its gate and Tier 3 in its final-phase duties; `implementation-plan` emits verification expectations into new plans; `verification-before-completion` names behavioural evidence; every HTML-producing skill cites the responsive-layout rule; template parity holds; `make validate`, `make lint`, `make test` pass.
**Recommended model tier**: frontier
**Recommended effort level**: max
**Rationale**: Edits across the most load-bearing workflow skills in the catalog, where a mistake changes how every future plan and phase behaves for every user.

### Sub-tasks

#### 4.1 -- Gate and final-phase wiring

**Objective**: Put Tier 1 and Tier 2 in the phase gate and Tier 3 in the final-phase duties.

**Failure modes**: Tier 1's functional smoke must be proportionate -- a full suite at every gate is the expense the maintainer explicitly rejected. **Build class**: load-bearing.

**Prompt**:

(2) Add Tier 2 to the Phase 8 post-phase sequence as a new numbered step: the plan-delta note, recording whether this phase revealed the plan to be wrong, incomplete, or built on a false assumption -- recorded always, escalated only when blocking. Say where it is written.
