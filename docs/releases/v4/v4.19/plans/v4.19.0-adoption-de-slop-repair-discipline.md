**Goal**: An agent repairing flagged code in a Nexus-Hub-equipped project states the behavioral post-condition before it edits, must justify a new abstraction by what it deletes in the same change, and has a named procedure for enabling a rule set against a codebase that produces thousands of findings.

## Overview

This plan operationalizes the three recommended candidates from its seeding comparison, in the reverse-engineer-first order that comparison fixed. All three are `skill-native`: they introduce no outbound call, no credential, no new runtime dependency, and no third-party data processor.

**The deliverable is instruction text, and the automated gates prove presence, placement, and single-ownership only.** Whether an agent that loads these skills actually writes a post-condition before repairing is not statically decidable. This plan therefore carries a paired eval baseline (Phase 1) and a post-change re-run (Phase 5) using `[[skill-eval-loop]]`, so the Goal has a before/after number attached to it rather than only a presence assertion. That is the honest limit of what this plan can prove, and it is stated here rather than in the last sub-task.

**This document was substantially rewritten on 2026-09-18 after a five-lens plan review returned 41 findings, 1 at P0 and 9 at P1.** Four of those changed the plan's structure, and two would have shipped defects: a task-line set that pre-committed every ownership outcome Phase 1 claimed to decide, and a headline gate that duplicated a rule `verification-before-completion` already owns. The `## Review corrections` section records every change.

The highest-risk phase is **Phase 2**, not Phase 4. Phase 4 is the largest by volume but is now fully deferrable under the cut-line. Phase 2 edits `verification-before-completion`, an always-on discipline gate that fires before every completion claim in every session, so a careless edit there has the widest blast radius in the catalog.

## Cut-line

If the release slot tightens, this is the drop order, decided in advance rather than under pressure:

- **Must ship**: Phase 2 (behavioral post-condition) and Phase 3 (deletion test). These are the comparison's two P0 items, both single-skill prose edits, and each is independently useful if the other slips.
- **Deferrable**: Phase 4 (rule-set adoption). It is the comparison's only P1, it is the largest by volume, and it is the only phase that creates a new skill with the three-registry obligation. If it is dropped, its item is recorded as an open known gap in T019 rather than partially implemented.
- **Never dropped**: Phase 5. It is the repository's standard terminal phase and owns publication.

## Definition of Done

1. The behavioral post-condition rule exists in `verification-before-completion`, and `lint-repair-loop` applies it at its repair step with a pointer rather than a restatement.
2. The deletion test exists in `code-simplification`, with pointers in `minimal-construction` and `over-engineering-review`.
3. Each rule is stated in exactly ONE skill; the aggregate ownership test proves it.
4. The paired eval shows a measured before/after delta for whether a repair response names a behavioral post-condition, recorded in `last-phase-evidence.md`. A null or negative delta is a valid, recorded outcome, not a failure to hide.
5. Either Phase 4 shipped the rule-set adoption skill with all three registries updated, or its item is recorded as an open known gap under the cut-line.
6. `python scripts/ci/run.py --profile full` is green.

## Phase 2: Behavioral Post-Condition

**Goal**: An agent repairing flagged code states what the program must know or do afterward, so a silenced warning cannot stand in for an established guarantee.
**Prerequisites**: Phase 1.
**Stability Gate**: `verification-before-completion` carries the rule; `lint-repair-loop` carries the application at its repair step plus a pointer and no restatement; the aggregate ownership test passes.
**Verification Expectation**: Run `python scripts/ci/run.py --profile full --only tests` and observe the new assertions pass. Then read `lint-repair-loop` top to bottom and confirm the application appears BEFORE its step 4 repair instruction and that it points at the owner rather than restating the rule; a restatement passes a naive presence test and is exactly the duplication this plan exists to avoid.
