The source argues that reasoning effort mostly buys verification and independent judgment, not raw intelligence, and that its value depends on how many hidden edge cases a task has and whether a human is in the loop. Nexus-Hub's `model-routing` couples effort rigidly to capability tier through one five-signal table, so it cannot express "a mid-tier task that deserves heavy verification" or "a well-specified phase whose implementation needs little judgment". The actionable result is a failure-class-aware escalation rule, a split between implementation effort and verification effort, and a concrete list of the verification behaviors that high effort produces, which Nexus-Hub can request explicitly.

## Step 2: Extracted insights

| # | Insight | Section |
|---|---|---|
| E1 | Effort approximates how much compute the user wants spent. Higher effort shows up as more independent verification, more edge-case testing, and more judgment calls made on the user's behalf. | 1, 7 |
| E2 | Higher effort pays off on tasks with many hidden edge cases: sanitizers and parsers, security review, hardware, performance work, code review, and bug fixes in brownfield code. | 9, 10, 11 |
| E3 | More effort reduces failures caused by missed edge cases but does not fix failures caused by the wrong approach. | 9 (failure-mode diagram) |
| E4 | A productive loop: interview the user for missing details, implement at low or medium effort, review for gist, iterate at low effort, then verify and test at high effort. | Intro, 7 |
| E5 | Specification completeness changes the value of effort. Given a detailed spec, outputs at different effort levels converge; on an underspecified task, higher effort produces more features and more assumptions. | 4, 5, 6 |
| E6 | Whether a human is in the loop changes the right level. In the loop, low effort gives fast iteration and lets the user steer; unattended, high effort does better because it resolves ambiguity itself (gsea-proteomics example). | 7, 10 |
| E7 | High effort is observable as specific behaviors: reproduce the crash before editing, write a randomized test against a reference implementation that never takes the risky path, confirm the new tests fail on half-finished fixes, test against a brute-force solver, time larger inputs, try two data-preparation methods and investigate when results differ, adversarially review the first draft, read the dependency's source, run a standard test suite, write a fuzzer. | 9, 10 |
| E8 | Latency and cost scale steeply: 1 minute vs 28 minutes on a design sketch, about 2 vs 33 minutes on a sanitizer. | 5, 9 |
| E9 | A rule of thumb: low for brainstorming, sketching, and easy changes; medium for regular feature work; high for verification-heavy and edge-case work such as a brownfield bug fix; max for fully autonomous end-to-end work and critical security review. | 11 |
| E10 | Effort curves differ by model; each model has its own score-vs-tokens curve. | 2, 8 |
| E11 | On the newest models, Claude Code changes effort without breaking the prompt cache, and `/effort` works mid-conversation. | Intro, 11 |

## Step 7: Risks, conflicts, and items not recommended

**Conflicts to resolve during implementation:**

- **No-degradation guarantee vs. E5 and E6.** `model-routing`, `/plan`, and `/route` all promise that uncertainty never resolves downward. The source says lower effort can be the better choice for well-specified or in-the-loop work. This adoption keeps the guarantee intact for everything except A5b, and A5b ships only with measured evidence and a decision record.
- **Decision-table rows.** `effort-level-strategy.md` recommends `xhigh` for interactive coding; E9 recommends medium for regular feature work. Both can hold (a familiar-codebase interactive session vs spec'd implementation followed by high-effort verification), so A2 adds rows rather than replacing the existing one, and the shipped default stays `high` per `v4.17.6`.
- **`max` in autonomous work.** E9 recommends max for fully autonomous end-to-end work; `effort-level-strategy.md` forbids `max` in loop-operator and temporal runs. The difference is one long autonomous task vs many compounding iterations. A2 states that distinction explicitly instead of picking one rule.

**Not recommended:**

| Item | Reason |
|---|---|
| Copying the article's Terminal-Bench numbers or per-task timings into skill text | Model-specific and dated within months; the `model-routing` rule "a recognized name is not a known name" already argues against baking such figures into guidance. |
| Replacing the five-signal rubric with the article's four-row rule of thumb | The rubric is deterministic, tested, and cross-provider; the rule of thumb is one vendor's heuristic. A2 and A5a absorb its content as inputs instead. |
| Treating "effort changes do not break the cache" as a general property | Contradicted for the API by `step-8-optimize-cost-and-latency.md` (verified 2026-09-10). A6 records it as model-specific instead. |
| Lowering any effort recommendation before measurement | The source's sample size cannot carry that weight; see A5b. |
