# Comparison: Testing Discipline, a Component Library CLI, and Opus 5.5 Prompting

Authored: 2026-09-23
Authoring cycle: v4.13.x (last tag `v4.13.0`)
Adoption target: v4.17.6
Target status: confirmed by the user on 2026-09-23 (next free slot after the highest queued plan, `v4.17.5`)
Sources: four (one inline snippet, one Git repository, two web articles)
Additional scope: one user-requested item outside the comparison (S1, keyword-style headings)
Skill: `cross-project-comparison`

This comparison reads four user-selected sources against Nexus-Hub and asks of each what it knows about steering a coding agent that Nexus-Hub does not already state, or states in the wrong place. The sources share no author. They converge on one theme: the default an agent sees without a trigger decides its behavior. For testing, Nexus-Hub's only always-loaded testing guidance pushes coverage quotas. For Opus 5.5, the shipped effort default predates the model. For the component library, the interesting parts are the always-on hooks, not the catalog volume.

The snippet is over-broad as written. Characterization tests before a refactor and regression tests for a reproduced bug are legitimately written after the code. Nexus-Hub's own hook suite (`catalog/hooks/tests/`) is the useful counterexample: pytest-hosted, but it drives the real `.sh` and `.ps1` as subprocesses and asserts exit-code parity, which is boundary testing in the snippet's sense.

## Additional scope S1: keyword-style headings (user request, outside the comparison)

Added on 2026-09-23 at the user's request so the from-comparison plan carries it. It comes from no source above and is scored on the same matrix.

**Requirement.** Whenever any agent on any Nexus-Hub-supported platform generates text, Word documents, reports, PowerPoint decks, presentify HTML, handbooks, or similar artifacts, titles and headings use Keyword Style (topic and category labels) and never Full Sentence Style (action or assertion titles).

| Keyword Style (required) | Full Sentence Style (not allowed) |
|---|---|
| Revenue by Region | Revenue grew 12% in EMEA while APAC stalled |
| Testing Discipline | We should stop writing unit tests after the code |
| Database Connections | Configure database connections |
| Risks and Conflicts | Three risks could block the rollout |

**Working definition.** A keyword-style title names a topic, category, or object: a noun phrase with no finite verb, no clause, no stated conclusion, and no terminal punctuation. The claim a sentence title would carry moves into the first line of the body.

**Scope (stated assumptions, to confirm at plan time).**

1. Applies to document titles, headings at every level, slide titles, section dividers, chart, table, and figure titles, and tab or navigation labels. Body text, bullets, and captions placed under a figure stay unaffected.
2. Applies to headings in chat replies as well as files, because the request says "creating text".
3. Excludes identifiers governed by their own convention: commit subjects (imperative per `code-commit-workflow`), PR titles, issue titles, and skill `description` fields.
4. Forward-only. Existing Nexus-Hub documents are not retrofitted in this item.
5. When presentify or another converter ingests a user's document whose headings are sentences, the converter rewrites them to Keyword Style by default and preserves the source headings only when the user opts in. (Resolved 2026-09-23; this reverses the original assumption, which would have exempted presentify HTML and handbooks from the requirement.)

**Current state and conflicts.**

- Always-loaded surface: no template states a heading style. `## Writing Discipline` (lockstep invariant in the five `base-*.md`, asserted on all thirteen) is the natural owner, since it already binds every reply and generated file.
- Direct conflicts to rewrite: `catalog/skills/business-product/technical-writer/SKILL.md:96` recommends "Configure database connections" over "Configuration", an action title. `catalog/skills/specialized-domains/pptx-generation/references/step-4-slide-design-patterns.md:15` defines a "Key Takeaway" slide built on a headline. `catalog/skills/business-product/internal-comms/SKILL.md:195` uses a `<one-line headline>` incident title.
- Generation surfaces that need a one-line reference to the owner: `pptx-generation`, `docx-generation`, `pdf-document-generation`, `xlsx-generation` (sheet and chart titles), `document-to-interactive-html` and `catalog/commands/presentify.md`, `deep-research-compilation`, `technical-writer`, `technical-documentation`, `user-documentation`, `internal-comms`, `writing-editing`, `doc-coauthoring`, and `catalog/style-guides/markdown.md`.
- Orthogonal, not in conflict: sentence case versus title case (`technical-writer:98`, `:440`) governs capitalization, not form. "Revenue by region" is keyword style in sentence case.

**Rule ownership.** `## Writing Discipline` decides when the rule applies. The `anti-slop-editing` skill's Detect mode owns measuring and repairing violations. Generation skills reference the owner in one line and never restate the rule.

**Enforcement.** Guidance alone is advisory. A deterministic check makes it observable: flag a heading that ends in terminal punctuation, exceeds about 8 words, or opens with a pronoun or a common finite-verb pattern. Host it where rendered and generated artifacts are already inspected (the `document-to-interactive-html` visual QA scripts and the anti-slop Detect mode) as an advisory finding, not a hard gate, because verb detection without an NLP dependency produces false positives.

## Step 5.4: Adoption plan, ordered by RE class

P-tier orders items within each bucket.

### Bucket 1: `skill-native` (zero code)

1. **P0: T2, O1.** Soften the coverage quotas in the three rules files, and author the Opus 5.5 profile. Both are small, and both correct a default that is wrong today.
2. **P1: T1, T3, T4, T5, T6.** One testing-cluster phase. T1 is the load-bearing item and carries a decision record (a new invariant block). Recommended block text, adapted to house voice:

    ```markdown
    ## Testing Discipline

    - Write a test before the code it covers, or not at all. Do not generate tests afterward to raise coverage; a test that restates the implementation cannot fail when the behavior is wrong. Characterization tests before a refactor and regression tests for a reproduced bug are the exceptions.
    - Prefer tests that drive the real boundary a user or consumer reaches (CLI, endpoint, screen, public API), and end with a repeatable artifact another person can re-run or inspect. For a library or pure function, the public API is that boundary.
    - Before implementing a unit that needs isolated tests, list the ways it can fail, turn that list into failing tests, then write the code.
    ```

    Rules-file replacement line for T2: "Coverage reports show what never ran; treat a low number as a prompt to ask which behavior is unprotected, never as a quota to fill."

    Rule ownership for the testing cluster, declared once so no skill restates another's rule: the `## Testing Discipline` block decides when a test is written and at what boundary; `functional-verification` owns what counts as boundary evidence; `edge-case-generator` owns failure enumeration; `false-confidence-test-audit` owns detecting tests that cannot fail.

3. **P1: S1.** Pair it with T1 in one template phase, so the thirteen templates are edited once. S1 extends an existing invariant block rather than adding a new one, which keeps it cheaper against the `v4.16.0` standing-rule cap.
4. **P1: O2, O4, O5, O6, O7, B6, B1.** O2 is a decision, not an edit: measure a representative workload at `medium` and `high` on Opus 5.5 before changing the shipped default, and record the verdict whichever way it goes.
