Authored: 2026-09-25

Sources: two (one inline article, one Git repository)
Skill: `cross-project-comparison`

This comparison reads two unrelated sources against Nexus-Hub. Source A argues that a coding agent performs better when asked for a named pattern ("build a tracer bullet") than when given a paragraph describing it, and that the named pattern itself (one thin, working path from input to output before widening) prevents the subtle breakage that stalls agent-built apps. Source B is a Go agent runtime that consumes SKILL.md-standard skills. Nexus-Hub already holds the theory behind Source A under the name "leading words", but only inside skill-authoring guidance, and it never tells a planning agent to build a tracer bullet first. Source B offers little catalog content but three transferable engineering patterns and one install-surface question.

Evidence quality: Source A reports one practitioner's experience and cites no measurement. Nexus-Hub's own `v4.13.0` pilot closed `MEASURED_NO_CHANGE` on a different prompt-level intervention (`docs/releases/v4/v4.13/plans/v4.13.0-adoption-evidence-driven-agent-improvement.md:10`), which is a reminder that plausible prompt advice often does nothing. The recommendations below therefore keep the change in Tier-2 skill bodies, where a wrong call costs little, and attach a paired eval to the one item (A1) that changes plan shape.

Terminology hazard: the article treats "golden path" as a synonym for tracer bullet. In Nexus-Hub, "golden path" already means an internal-developer-platform paved road (`catalog/skills/infrastructure/platform-engineer/SKILL.md`, 12 occurrences). Adopting it as a synonym would make one leading word point at two concepts, which defeats the purpose of a leading word. Use "tracer bullet", with "walking skeleton" (Cockburn) as the one recognized alias.

A second distinction from the source book matters for the rule text: *The Pragmatic Programmer* separates tracer code, which is kept and grown, from a prototype, which is thrown away. Nexus-Hub already has the throwaway form ("spike"). The rule must say the tracer path is production-quality and stays, or an agent will read it as permission to stub.

Additional runtime patterns observed:

- **Context-change record.** The context builder returns the model input together with a record of everything omitted, truncated, or compacted (`harness/contextbuilder/contextbuilder.go:12-14`, README "Components"). Nexus-Hub's compression engine is non-lossy for tool output (`<<ccr:HASH>>` markers, `catalog/skills/developer-experience/context-optimization/SKILL.md:65-71`), but the `context-compression` methodology for conversation summaries does not require the summary to list what it dropped; it only warns that agents drop decisions "silently" (`catalog/skills/orchestration/context-compression/SKILL.md:342`).
- **Pure translation, durable operations.** A tool translator validates a call and emits serializable operations; it "must not perform I/O or suspend the loop" (README glossary). Execution happens separately and is persisted, which is what makes the log-replay fuzz targets possible. The pattern has two established names Nexus-Hub already uses elsewhere: functional core / imperative shell, and event sourcing (`event-driven-architecture`).
- **Preamble.** Tells the model to issue independent tool calls in one turn and to treat the prompt as a goal until met (`harness/contextbuilder/prompts/preamble.md`). Nexus-Hub's `## Autonomous Operation` block already covers goal persistence; parallel tool calls are instructed by the major harnesses' own system prompts.

## Step 5.4: Adoption plan, ordered by RE class

P-tier orders items within each bucket.

### Bucket 1: `skill-native` (zero code)

1. **P0: A1.** The one item that changes what agents build. Recommended rule text, adapted to house voice:

    ```markdown
    **Tracer bullet first.** When the work crosses more than one layer (UI, API, storage, external service), Phase 1 builds a tracer bullet: the thinnest path that takes real input through every layer to real output, built to production quality and kept. Later phases widen that path; none of them add a layer the tracer did not already reach. A tracer bullet is not a spike: a spike is thrown away, the tracer is the first slice of the product. Do not stub a layer to make the path pass. Skip this rule for single-layer work.
    ```

    Rule ownership, declared once: `implementation-plan` decides that Phase 1 is a tracer bullet and what it must reach; `functional-verification` owns how its end-to-end run is exercised and evidenced; `incremental-implementation` only names the tracer as its first task and restates nothing.

2. **P1: A1-eval, A2, A3, U2, U5.** A1-eval rides with A1. A2 and A3 are one edit pass across `prompt-engineering` and `agent-writing-theory.md`. U5 touches the repo's workflows, so its CI half belongs to the adopting plan's final phase.
3. **P2: A4, U4.** A4 depends on A2 (it is the reference A2 links to). Before writing A4, grep each term against its named owning skill; drop any term whose owner does not already use it.

## Step 7: Risks and conflicts

- **A1 changes the shape of every multi-layer plan** `/plan` generates. Mitigations: the single-layer skip clause, and A1-eval, which may show no behavior change. A no-change result is a valid outcome and should be recorded, not hidden.
- **A1 can be misread as "stub everything, then fill in".** The rule text forbids stubbing the path and distinguishes tracer from spike for that reason.
- **A2 and A4 risk a leading-word list that looks authoritative but changes nothing.** A4 admits only terms an existing skill already uses, and A2 keeps the "one differing constraint" clause so a canonical term never replaces a project-specific requirement.
- **"Golden path" collision.** Recorded above; the adopting plan should grep new text for it.
- **U5 can break a job that pushes, tags, or publishes** (the release workflow). Audit each workflow for write operations before flipping `persist-credentials`, and keep credentials where a job needs them.
