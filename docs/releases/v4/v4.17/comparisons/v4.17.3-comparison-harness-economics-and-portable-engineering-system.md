## Step 5: Security and reverse-engineering assessment

### Threat model comparison

| Dimension | Nexus-Hub today | Candidates A-C as recommended | Rejected approaches D-E |
|---|---|---|---|
| Runtime dependencies | Repository scripts and installed platform tools | No new third-party dependency required; B may invoke user-installed harness binaries only in explicit evaluation runs | ECC adds a Node package and broad executable surface; Grokbot's pattern adds an always-on shared cloud host |
| Outbound calls | Vary by user-selected AI platform; catalog policy is local-first | A and C add none. B defaults to isolated local orchestration and permits provider calls only when explicitly configured, budgeted, and recorded | Shared cloud execution and imported tooling expand destinations and update channels |
| Credentials | Platform credentials remain separated by the user's setup | A and C add none. B consumes only credentials already configured for the selected harness and never copies them into receipts | Shared credentials increase lateral reach across agents and tasks |
| Source code and prompts | Remain local unless the chosen provider receives them | B uses synthetic or explicitly approved repository workloads and records redacted receipts | Cloud-hosted shared workspaces move a broader data surface to another trust domain |
| Failure containment | Skills, approvals, budgets, and isolation controls | B requires per-trial worktrees or disposable copies, hard cost/time/turn limits, network-off evaluation where possible, and cleanup evidence | A shared machine makes state bleed and credential reuse expected behavior |

### MCP Registry Policy decision

No candidate needs a new MCP registry entry.

- A is LLM-native instruction and belongs in an existing skill.

The MCP Registry Policy orders skill-native work before locally rebuilt capability. Priority applies within each bucket.

3. **C, re-full/platform-native, P1**: use B's baseline to measure instruction payload and behavior before and after AGENTS.md convergence.

## Step 6: Adoption shape and acceptance criteria

### A: Complete the unattended-loop contract

Target `catalog/skills/workflow/loop-engineering/SKILL.md` and its existing tests. Do not create a new skill, routine engine, scheduler, or board.

Acceptance criteria:

- A routine declares a narrow trigger and records a test run before unattended use.
- No-data and stale-input are explicit outcomes, not silent success or fabricated zeroes.
- Partial completion reports completed units, failed units, retryability, and the next safe action.
- Existing approval, evidence-freshness, idempotency, budget, and termination rules remain owned by `[[loop-engineering]]` and are not duplicated elsewhere.

### B: Add behavioral harness evaluation beside structural audit

Keep `scripts/harness_audit.py` as the deterministic structural audit. Add the minimum separate local runner only after `[[eval-pipeline-audit]]` defines the evaluation contract.

Acceptance criteria:

- Input manifest pins workload revision, model identifier, harness version, instruction-bundle hash, tool-schema hash or byte count, pricing source and date, trial count, maximum turns, maximum time, and maximum spend.
- Each pairing records task success, latency, input/output tokens where available, total cost, cost per successful task, initial context size, tool-schema size, retries, and a normalized failure fingerprint.
- Repeated trials and confidence intervals are supported; a one-run result cannot be presented as a ranking.
- Workloads are representative Nexus-Hub tasks or synthetic fixtures with independent pass/fail evaluators. Public benchmark scores are context, not a substitute.
- Trials run in disposable worktrees or equivalent isolated copies, with network off unless the selected provider requires it and the user explicitly opts in.
- The runner fails closed when isolation, pricing, or a hard budget is absent. Secrets and raw prompts are excluded or redacted from receipts.
- Structural audit scores and behavioral measurements remain separate fields so file presence cannot be mistaken for task success.
- The report format names unavailable measurements rather than coercing them to zero.

### C: Converge Claude project instructions without breaking exceptions

Target `docs/policy/platform-read-contracts.md`, `scripts/lib/integrations/claude.py`, both installers, related platform registries, tests, and `scripts/harness_audit.py`. Rebaseline after v4.16.0 and v4.16.2 if either lands first.

Acceptance criteria:

- Supported Claude Code sessions may use the shared root `AGENTS.md` when no `CLAUDE.md` is required and the user has not disabled the fallback.
- Bedrock, Vertex, Foundry, global instruction surfaces, and any other unsupported path retain their required Claude-specific file.
- Existing user-authored files survive installation and upgrade; the installer does not silently overwrite or delete either instruction file.
- Audit logic scores the effective supported instruction path instead of requiring both files unconditionally.
- Tests cover fallback enabled, fallback disabled, unsupported provider, pre-existing `CLAUDE.md`, pre-existing `AGENTS.md`, and both present with defined precedence.
- Candidate B measures the initial payload before and after convergence. A smaller file count alone is not proof that the effective context shrank or behavior remained intact.
- No mods-system work enters scope without a verified official contract.

## Step 7: Risks, conflicts, and items not recommended

### Conflicts to resolve during planning

| Concern | Conflict | Resolution |
|---|---|---|
| Behavioral evaluator scope | A general benchmark platform would exceed the evidence and duplicate existing evaluation skills. | Limit B to a manifest, runner, receipt, and a small representative workload set. Route evaluation design through `[[eval-pipeline-audit]]`. |
| Cost measurement | Harnesses expose token and price data differently, and subscriptions may not map to API prices. | Record the pricing basis and missing fields. Never convert unknown subscription cost to zero. Report both per-run and per-success cost only when supported. |
| Isolation versus provider access | Provider-backed trials require network access, while reproducibility benefits from network-off execution. | Keep repository and filesystem isolation mandatory. Make provider egress explicit and allow network-off local or replay fixtures as a separate mode. |
| AGENTS.md precedence | Claude's fallback applies only when `CLAUDE.md` is absent, and users can disable it. | Model the effective read path as a capability decision. Do not blindly install both full instruction bodies or delete a user file. |
| Shared-template parity | v4.16.0 may change the base instruction set before C begins. | Rebaseline after the predecessor and edit the existing canonical owner rather than copying new shared text into an adapter. |
| Comparison dispatcher | The invoked `/compare` dispatcher names a `compare-project` delegate that is not present in this checkout. | This report used the available canonical `cross-project-comparison` skill and records the missing delegate honestly. Repairing the dispatcher is outside this comparison's adoption scope. |

### Not recommended

**Adopt ECC wholesale. Classification: `drop-outright`.** Its structured workflow is strong evidence that planning, testing, review, verification, memory, security, reusable skills, and thin adapters form a coherent system. Nexus-Hub already implements those concepts under dedicated owners. Importing ECC would add overlapping instructions, hooks, commands, agents, installers, dependencies, and update channels. Its structural harness audit does not provide the live cross-harness experiment B requires, and its evaluation CLI explicitly withholds gate execution until isolation exists.

**Adopt Grokbot's shared cloud computer and credentials. Classification: `drop-outright`.** Persistent workspace state can reduce handoff friction, but the proposed shared-machine trust model makes every bot and task part of the same credential and filesystem blast radius. Nexus-Hub should keep the durable-state idea through local artifacts while preserving per-task isolation and least privilege.

**Copy Arena's 5x ratio or declare one harness the winner. Classification: `drop-outright`.** The result is a reason to measure, not a durable routing table. It covers particular model and harness versions, two public benchmarks, fixed API prices, and a limited task sample. Models, prices, context loading, and tool implementations change.

**Create a hosted benchmark or analytics connector. Classification: `drop-outright`.** B is locally reproducible. A hosted evaluation, scraping, generation, or embeddings service would add source and prompt egress without being the intrinsic data destination, failing the MCP Registry Policy.

**Implement Claude Code mods. Classification: `defer`.** The reviewed official v2.1.277 release evidence confirms AGENTS.md fallback and its provider exceptions but does not confirm the quoted mods interface. Wait for a primary contract.

### Considered but rejected as duplicate scope

- A new planning, TDD, review, memory, or security skill from ECC: existing Nexus-Hub skills own each concern.
- A new manager-bot abstraction from Grokbot: current orchestration and review owners already separate manager, implementer, and verifier roles.
- A new external work board: `docs/todos.md`, plans, evidence, and known-gap ledgers already provide durable state.
- A new browser-automation helper: `[[helper-script-authoring]]`, browser-testing guidance, and existing automation surfaces already cover the useful principle.
- A replacement for `scripts/harness_audit.py`: structural health remains useful and should coexist with B rather than be renamed into a behavioral claim.

## Conclusion

Nexus-Hub already contains most of the structured engineering system described by Grokbot and ECC. The comparison does not justify importing either system. The novel, high-value gap is measurement: Nexus-Hub can audit whether harness components exist but cannot yet prove how a model-harness pairing performs on representative work or what its success-adjusted cost is.

The recommended v4.17.3 plan should therefore remain narrow: refine unattended-loop outcome semantics, add an isolated behavioral evaluator, then use its baseline to converge supported Claude Code project instructions on AGENTS.md without breaking hosted-provider or user-configuration exceptions. No new MCP, vendor service, catalog duplicate, shared credential model, or frozen benchmark ranking is warranted.
