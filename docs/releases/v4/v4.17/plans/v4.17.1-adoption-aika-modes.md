**Goal**: Close the four adoption items the AiKA Modes comparison recommends, in its Section 6 order, so the agent gains a response confidence signal grounded in observed tool results and hosted on a surface that actually loads, a default-deny tool posture bound to the file-level policy and honest about being advisory, an explicit statement of what each added quality stage costs, and either a declarable quality-stage contract that demonstrably simplifies two skills or a recorded decision not to build one, with zero new outbound calls, dependencies, or credentials.

## Overview

The seeding comparison found that Nexus-Hub and Spotify's AiKA Modes converge on the same shape - a named specialization with its own instructions, tools, and quality controls - and that Nexus-Hub is ahead on instruction authoring, context economy, and invocation policy. It diverges on one axis: AiKA lets a mode DECLARE its response-quality stages, while Nexus-Hub performs five of those six disciplines somewhere in the catalog but bakes each into the individual skill that needed it.

One capability is genuinely absent rather than merely unreachable: a response confidence signal. `multi-agent-code-review` anchors confidence per FINDING with cross-reviewer promotion and a late gate; nothing rates a whole agent response by how well observed tool results support it. That is Phase 1 and the highest-value item, because it is hallucination control on the surface the user reads.

Phase 1 carries a question the first draft of this plan got wrong and that must be settled before anything is written. The rating is meant to apply when the agent states a conclusion, which happens most in explaining, reading, and proposing. `verification-before-completion` explicitly excludes exactly those cases in its own when-NOT-to-use, and `agent-communication` is likewise a trigger-gated skill body. A rule hosted where its subject is excluded will not load when needed. T002 therefore decides the host surface and the rating vocabulary together, with the instruction-template route costed as a real option.

The plan is small: four items, all `skill-native`, no new skill and therefore no registry edit. Its structural risk is Phase 4, where a stage contract is one bad paragraph away from being a framework nobody asked for. That phase opens with a decision whose valid outcome includes dropping the item entirely.

## Goals First / Definition of Done

**Target problem**: A Nexus-Hub mode declares what posture to adopt and which tools to prefer, but declares nothing about the quality of what it returns. Meanwhile the agent states a conclusion with identical assurance whether it observed a tool result or recalled it from training.

**Persona**: a user reading an agent's answer who cannot currently tell which parts were verified against something and which were asserted.

**Definition of done**, observable:

1. A confidence rating and the EVIDENCE RULE that assigns it are stated in exactly one owning surface, chosen in T002, with a defined place in the output contract. The scale itself is whatever T002 chooses; this item does not pre-commit it.
2. The rating vocabulary is reconciled with the existing anchor scale in `catalog/skills/code-review/code-quality/references/confidence-anchored-scoring.md` rather than competing with it, and if the reconciliation requires editing that file, it was edited.
3. The rating is surfaced only where it changes what the reader does, and a suppression path exists and is documented.
4. `context-modes` states a default-deny tool posture bound to `agent-access-policy`, says plainly that the mode allowlist is advisory model behavior rather than platform enforcement, and carries the server-wide grant warning.
5. `context-modes` and `agent-presets` each state that every model-judgment stage is an extra round trip and that bounded retries multiply it, while deterministic local stages are not.
6. Either the stage contract exists and demonstrably removed duplication from `context-modes` and `agent-presets`, or it was dropped with the reason recorded. Both are acceptable; shipping an unused contract is not.
7. `python scripts/ci/run.py --profile full` is green.
8. Net catalog delta is `+0 skills` and `data/SKILL_INDEX.md`, `data/skills.json`, `data/marketplace.json`, and `data/bundles.json` are all unchanged.

**Not done** if a confidence label ships without a rule that determines it. A label the agent may assign at will is decorative, and a decorative rating is worse than none, because it reads as verified. **Not done** if the rating is hosted on a surface that excludes the responses it is meant to rate.

#### 1.3 - The evidence rule

- [ ] T003 Write the rule that determines the rating, on the T002 surface `docs/releases/v4/v4.17/development/v4.17.1-phase-1-notes.md`

**Objective**: Make the rating a consequence of stated evidence rather than a judgment the agent may make freely.

**Failure modes**: Malformed or absent input: the response makes no factual claim (a greeting, a clarifying question), so no rating applies rather than one being forced. Unreachable or slow dependency: the session has no tool results because the work was purely generative, so the rule yields a rating grounded in that absence rather than defaulting to high. Conflicting operations: an observed result contradicts model knowledge; the observed result wins and the disagreement is surfaced, not silently resolved.

**Build class**: load-bearing. This rule is the phase's entire value; the label is a consequence of it.

**Prompt**:
> Implement the T002 decisions. Write the rule on the surface T002 chose and update this task line's path to match; if the template route was chosen, edit all thirteen `templates/ai-instructions/` files in lockstep and run `python scripts/check_base_template_parity.py` before committing. If T002 chose to unify vocabularies, also edit `catalog/skills/code-review/code-quality/references/confidence-anchored-scoring.md` as part of this task.
> The rule must determine the rating from named evidence, not impression. Define the evidence classes explicitly: a claim backed by a tool result OBSERVED this session; a claim backed indirectly or partially; a claim asserted from model knowledge with no observation this session; a claim contradicted by an observation. State how a mixed response is rated: **the weakest load-bearing claim governs, not the average**, because an average lets one unverified critical claim hide behind several verified trivial ones. State the three failure-mode behaviors above. Forbid assigning a rating without naming which evidence class the load-bearing claims fell into. Keep it under 50 lines; if the body would cross the 500-line reference threshold, put the evidence-class detail in a `references/` file and link it.
