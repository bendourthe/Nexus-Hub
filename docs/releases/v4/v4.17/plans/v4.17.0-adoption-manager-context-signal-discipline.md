**Goal**: Every report-producing skill in the catalog is bound by one stated contract governing what it may report, each reported claim names its source, one event is reported once, the four named capture surfaces clear one stated save bar, and a developer invoking an affected skill observes a bounded, sourced, deduplicated report where they previously received an unbounded one.

## Overview

Nexus-Hub already owns the discipline this adoption generalizes. `AGENTS.md` carries a "Review-output restraint" convention requiring a mode-based finding cap and a "Considered but Rejected" list, with the stated reason that a thorough review finding little must not look like a shallow one. That rule is scoped to review skills. Every other report-producing skill in the catalog is free to return everything it found, and several capture skills each state their own admission threshold in their own words. The seeding comparison's finding is that the qualifier, not the rule, is the defect.

This plan states a report-output contract with four clauses (a finding cap bound to depth mode, a considered-but-rejected list, a mandatory source citation per claim, and a one-event-one-entry deduplication rule), then applies it to the report-producing skills named in the comparison. It separately states one save bar as a floor the four named capture surfaces clear, without flattening the additional criteria those surfaces deliberately apply on top. It closes with a new `signal-briefing` skill in the `workflow` category that answers "what changed, why it matters, what needs attention, what next" over local files the user points it at, applying the contract rather than restating it.

Two review findings reshaped the plan and are worth stating up front, because they are not obvious from the comparison. First, the contract cannot live in `AGENTS.md`: neither installer copies that file, so a distributed skill told to "reference the AGENTS.md owner" would, on a user's machine, resolve that name against the user's own project `AGENTS.md`. An unrelated project-controlled file would silently become the authority defining what a Nexus-Hub skill may report. The canonical contract therefore lives in `catalog/style-guides/report-output-contract.md`, which both installers already copy to `~/.nexus-hub/style-guides/`, and `AGENTS.md` links to it. Second, a single output cap misfits the roster: capping a judgment-based reviewer prevents padding, but capping an enumerator such as `documentation-consistency` silently hides real broken links. The cap clause is therefore split by output kind, with a non-negotiable floor that no cap ever suppresses a top-severity finding.

A prose convention with no gate is how the original rule stayed review-only, so the durable half of this adoption is a validator that derives its roster rather than hand-maintaining it. Nothing here adds a dependency, a credential, an outbound destination, or an installer edit: skill trees and style guides are both copied recursively, and the three registry files are the only other distribution surface touched.

#### 1.2 -- Author the contract in a distributed artifact

**Objective**: Write the canonical contract in `catalog/style-guides/report-output-contract.md`, which both installers copy to `~/.nexus-hub/style-guides/`, and reduce the `AGENTS.md` subsection to a pointer.

**Build class**: load-bearing. This file is the single statement of the contract; everything else references it.

**Prompt**:

> Create `catalog/style-guides/report-output-contract.md` as the canonical contract. Do NOT state the contract in `AGENTS.md`.
>
> The reason is a verified distribution boundary. Neither installer copies the repo-root `AGENTS.md`; `scripts/installer.sh` writes `~/.codex/AGENTS.md` from `templates/ai-instructions/base-codex.md`, which is a different file. `catalog/style-guides/` IS copied to `~/.nexus-hub/style-guides/`, the pattern `markdown.md` and `doc-headers.md` already use. A distributed skill told to reference "the AGENTS.md owner" would, on a user's machine, resolve that bare name against the USER'S OWN project `AGENTS.md`, letting an unrelated and potentially untrusted project file define what a Nexus-Hub skill may report and cite. That is a trust-boundary inversion, not a broken link.
>
> The contract carries four clauses, each with the concrete failure it prevents:
>
> 1. **Finding cap, bound to output kind and depth mode.** This clause is SPLIT, because one cap misfits the roster.
>     - *Judgment-derived output* (ranked findings, severities, scored assessments): each depth mode binds a coverage scope AND an output cap. Never pad to the cap; a short or clean result is valid. Without a cap, cosmetic padding buries the finding that mattered.
>     - *Deterministic enumeration* (an exhaustive list of verifiable defects such as broken links or duplicate entries): UNCAPPED. Report completely, with a total count and a stated ordering. A capped enumerator silently leaves real defects unreported, which is a user regression rather than restraint.
>     - **Non-negotiable floor, applying to both**: a cap governs ordering and volume, never suppression at the top severity band. A report whose findings exceed its cap states the number withheld and their severities. Without this, generalizing a review rule into a higher-priority document flattens the existing carve-out in `security-review` whereby a P0 at confidence anchor 50 or above is always surfaced.
> 2. **Considered but Rejected.** List real inspected candidates that were not reported, each with a reason. Never invent filler; a thin scope says so. Without this, a thorough report that found little looks like a shallow one.
> 3. **Source citation per claim.** Every reported claim names the artifact it came from (a file path plus a locator, a commit, a session id). A claim with no named source is not reportable. A citation is a path and a locator, NEVER the secret-bearing content itself: do not quote raw log lines or credential-shaped values as evidence.
> 4. **One event, one entry.** When the same event appears in more than one source, report it once and name the duplicate sources on that single entry. Prevents an agent reading `docs/todos.md`, a version `known-gaps.md`, and an open plan's unchecked tasks reporting one deferred item three times.
>
> State the ownership split in the file, per the rule-ownership convention: this style guide owns the general contract; `multi-agent-code-review` retains the review-specific cap table and references this file rather than restating it. Name the roster mechanism chosen in T001 so a reader can tell whether a given skill is bound.
>
> Then edit `AGENTS.md`: replace the body of `#### Review-output restraint` with a short pointer naming the style guide as the owner, following the pattern the "Markdown Style for Generated Documentation" section already uses. Rename the heading to match the widened scope. Do not restate any clause. Before committing, run `python scripts/validate_doc_budgets.py` and confirm `AGENTS.md` remains under its 9100-word ceiling; the pointer approach should REDUCE its word count, and the ceiling ratchets down rather than up.
>
> Constraints: ASCII only, no hard-wrapped paragraphs, blank line before and after every list and heading, per `catalog/style-guides/markdown.md`.
>
> Acceptance criteria: the style guide states four clauses including the split cap and the no-suppression floor; `AGENTS.md` points rather than duplicates and is under budget; no clause is stated in two places.

#### 1.3 -- Build the contract validator
