**Goal**: A Nexus-Hub user can install or remove a single skill or command by name with manifest-tracked ownership, the installer's settings-merge behavior is written down and never widens a user's permissions, and an agent editing outside its active plan's scope sees an opt-in advisory warning, each proved on the host operating system and at parity across the bash and PowerShell installers, adding no new third-party destination, credential, or dependency.

## Definition of Done

**Must have:**

1. `docs/reference/settings-merge-contract.md` matches the code, and a test proves an existing `settings.json` with user `deny` and `ask` entries keeps an identical `permissions` object after install, init, and add.
2. `nexus-hub add skill <name>` and `nexus-hub remove skill <name>` (and `command`) work from the user-facing CLI and from both installers, with names validated against `^[a-z0-9]+(-[a-z0-9]+)*$`, and removal touching only manifest-owned, hash-matched paths.
3. `spec-scope-notice` ships as a `.sh`/`.ps1` pair, opt-in, with parametrized parity tests and a recorded false-positive rate on a real plan's edit set.

**Nice to have (cut in this order):** B7 statusline presets, B4 doctor environment checks, B1 AI command guard recipe.

## Non-Goals

- B8 installed-inventory analyzer: known gap.
- `add` or `remove` for hooks and agents in v1: they need per-platform hook translation and the settings-merge contract as a dependency; known gap after Phase 2 lands.
- Any default registration of a model-judged hook.

## Fixed security requirements

Carried from the seeding plan's design interview and the plan-review security and adversarial lenses. They are requirements, not options:

1. The AI command guard never returns an allow or `permissionDecision: "allow"`. Its only outcomes are deny or no opinion, so the permission system still decides.
2. A settings merge never adds to, widens, or removes a user's `permissions.allow`, `ask`, or `deny`, and never writes `defaultMode`. The only permission write is the existing Read/Glob/Grep stub into a settings file that does not exist yet.
3. Item names are validated before any filesystem use, resolved only through catalog membership, and removal deletes only paths the manifest records as Nexus-owned with a matching content hash, never following symlinks.

## Overview

The seeding comparison found four locally rebuildable ideas in a Claude Code component library: spec-scope gate hooks, an AI-evaluated Bash guard, single-item install, and explicit settings-merge rules. The plan-review of the combined draft found each under-designed: the CLI has no route for a new subcommand, the manifest records flat path lists with no item identity, the hook had no call site in this repository's plan format, and two items could weaken a user's permissions. This plan resolves those designs first (Phase 1), then builds in dependency order: the merge contract before single-item install, and the hook after the scope-source decision.

All work runs locally. The installers stay at parity; any change to `installer.sh` or `installer.ps1` needs the user's approval (AGENTS.md "Ask first").

## Phase 1: Design decisions

**Goal**: Settle the four designs every later phase depends on, each as a decision record, before any code changes.
**Prerequisites**: None.
**Stability Gate**: Four decision records under `docs/decisions/` each carry `## Alternatives considered` and a chosen option; `docs/releases/v4/v4.17/development/v4.17.7-design.md` links them.
**Verification Expectation**: Open each decision record and observe a chosen option, its rejected alternatives, and the evidence (file and line, or vendor URL) it rests on.
**Recommended model tier**: frontier
**Recommended effort level**: max
**Rationale**: Schema and routing decisions under the manifest that doctor, repair, teardown, and uninstall trust, where a wrong choice is expensive to migrate.

### Sub-tasks

#### 1.1 -- decision: Manifest item ownership

**Objective**: Decide how the manifest records which item, and which source, owns a path.

**Prompt**:
> Read `scripts/lib/integrations/manifest.py` (flat `tracked`, `shared`, `org_tracked`, `org_shared` path lists) and the `org_tracked` precedent in `scripts/lib/integrations/org_knowledge.py`. Propose an additive field, for example `item_owners: {"skill:<name>": {"sources": ["bundle:<id>", "explicit"], "paths": [...], "sha256": {...}}}`, with reference counting so removing an explicit add leaves bundle ownership intact, and state how a full reinstall treats an item the user removed. Alternatives: no schema change (reject: nothing records item identity), a separate per-item manifest file, the additive field. Present to the user with a recommendation; record the answer as `docs/decisions/<lifecycle>/tooling/2026-MM-DD-manifest-item-ownership.md`. Unblocks Phase 3.

---

#### 1.2 -- decision: CLI routing for add and remove

**Objective**: Decide where the new subcommands enter.

**Prompt**:
> Trace the user-facing path: `scripts/nexus-hub` and `nexus-hub.cmd` hand off to `scripts/nexus_hub_cli.py` (attribution, version, upgrade, verify, setup-media, map, org), while `doctor` and `init` enter only through `installer.sh` and `installer.ps1 -Subcommand` into `scripts/lib/integrations/runner.py`. Also read `scripts/lib/installer/selection.py`, whose docstring says the shell installers re-implement the selection contract natively under `tests/fixtures/install-selection/cases.json`. Propose the routing: `nexus_hub_cli.py` dispatches `add` and `remove` to `runner.py`, both installers accept the same subcommand with a parity case, and the selection contract document (`docs/releases/v3/v3.16/development/install-selection-contract.md`) gains a single-item selector. Record as a decision with alternatives (CLI-only; installers-only; both). Unblocks Phase 3.

---

#### 1.3 -- decision: Spec-scope source

**Objective**: Decide which file defines "in scope" for the hook.

**Prompt**:
> The draft hook read `spec.md` or `tasks.md` by modification time, but this repository keeps its task lines in `docs/**/plans/*.md`, each strict `T###` line names one primary path while the task edits several files, and a file the agent itself edits cannot be a trustworthy scope source. Propose: an explicit pointer (`.nexus/active-plan`, written by `/implement` at phase start and read by the hook), scope = the directory prefixes of every `T###` path in the active phase plus any explicit `Files in scope:` list, silence when no pointer exists, and a warning that notes when the scope file itself was edited this session. Alternatives: mtime discovery (reject: gameable and contradictory), nearest ancestor spec, drop the hook. Present with a recommendation and record the decision. Unblocks Phase 4.

## Phase 4: Spec-scope notice hook

**Goal**: An agent editing outside its active plan phase's scope sees one advisory line, opt-in, identical across the bash and PowerShell implementations.
**Prerequisites**: Phase 1 (1.3). User approval to change `catalog/hooks/settings.json`.
**Stability Gate**: `python -m pytest catalog/hooks/tests/test_spec_scope_notice.py catalog/hooks/tests/test_hook_sibling_parity.py -q` passes; the false-positive rate on a real plan's edit set is recorded.
**Verification Expectation**: With a fixture run record for the active plan (per `v4.13.2`), pipe an out-of-scope Edit payload into both implementations and observe the same single stderr line and exit 0; pipe an in-scope payload and observe silence; replay the edit set of one completed v4.17 phase and record how many edits warned.
**Recommended model tier**: strong
**Recommended effort level**: high
**Rationale**: Two hook implementations with exit-code parity across bash and PowerShell 5.1, reading repository files an attacker can influence.

### Sub-tasks

#### 4.1 -- Hook implementation (B2)

**Objective**: Warn, never block, per the 1.3 scope rule.

**Failure modes**: Malformed or absent input (no stdin, invalid JSON, no `tool_input.file_path`, no pointer file): exit 0 silently. Unreachable or slow dependency (no `jq` on bash; a huge plan file; a symlinked plan): bash follows the existing `workflow-phase-notice.sh` no-op on missing `jq`, an accepted safe-direction divergence the parity test skips for stderr only; plan files over 1 MB, symlinks, and paths resolving outside the repository are ignored; a wall-clock budget of 500 ms ends in a silent exit 0. Conflicting operations: when the scope file itself was edited this session, the warning says so.

**Build class**: load-bearing.

**Prompt**:
> Write `catalog/hooks/spec-scope-notice.sh` and `.ps1` modeled on `workflow-phase-notice.{sh,ps1}`, implementing the 1.3 decision. Normalize `tool_input.file_path` (separators, `./` and `../`, case on Windows and macOS) before comparing. Output one fixed-template stderr line containing only the edited path and the pointer's plan path, with control characters, ANSI escapes, and newlines stripped and a length cap; never echo plan content. Honor `NEXUS_DISABLED_HOOKS=spec-scope-notice` and `NEXUS_HOOK_PROFILE=minimal`. Make `/implement` write `.nexus/active-plan` at phase start (edit `catalog/skills/workflow/implement-phase/SKILL.md`). Write `catalog/hooks/tests/test_spec_scope_notice.py` with a `run` fixture parametrized over both implementations, including a filename with newline and ANSI sequences. Register it opt-in (documented, not in the default chain) unless the measured false-positive rate is below 10 percent, and then only with user approval. Acceptance: tests pass; false-positive rate recorded.
