**Goal**: An agent working in a Nexus-Hub-equipped project cannot terminate a process it does not own, and its code review spends deterministic checks first, reports an unrefuted middle verdict honestly, and can assess only the delta between two commits without inheriting a stale or unreachable-path verdict.

## Definition of Done

One testable outcome per must-have. The plan is done when all eight are observable; nice-to-haves may be cut without reopening the Goal.

**Must have:**

1. A dev-server and process-safety rule exists whose matching mechanism is executable on Windows, macOS, and Linux.
2. A process-ownership guard hook is registered on every tool surface that can carry a kill command, blocks the PID-laundering idioms as well as the name-based ones, and does not block an agent editing the rule file that documents those idioms.
3. The review runs a deterministic pass before the persona fanout and seeds the fanout with its findings.
4. A third validation state exists that does not collide with an existing term, with a verdict rule stated per review mode.
5. A `review-state` script persists a prior run's record and evaluates the invalidation predicate deterministically.
6. Incremental reuse exists, gated by an invalidation rule that includes a reachability condition, and a fixture proves the rule fires on a changed-caller-unchanged-callee regression.
7. A loop reports consumed budget back into its own prompt, and states the supersede-over-fold rule.
8. A prevented-incident metric produces a number from this repository's history on its git-only path, with no network access required.

**Nice to have:** the judgment-primitive vocabulary (must-have 4 and 5 are its first consumers; if both slip, the vocabulary is deferred with them).

**Explicitly out of scope**, each with a reason:

- The six instruction-surface items (dictation tolerance, reconcile-against-corrections, anticipate-the-next-step, delegation split, operator identity and tooling placeholders, selection-over-generation). They are standing rules, and `v4.16.0` exists to cap and reduce standing rules in a surface loaded on every session. They move to the sibling plan, hard-blocked on `v4.16.0` landing, so its before-and-after figure is not measuring a surface this plan inflated.
- The four `drop-outright` comparison items (B1 TypeSafe System One, B7 runtime vendor-doc authority, C9 Toto forecasting, C10 Polylane). Rejected on MCP Registry Policy grounds in the comparison, recorded in known gaps by the final phase so a later reader can tell a policy rejection from an oversight.
- Repository-wide refactor and the Tier 3 deep pass in the final phase are a fixed house convention, not Goal-traceable work. They are excluded from the task-count when judging this plan's size.

## Overview

This plan operationalizes the locally-buildable half of a three-source comparison. Both vendor services in that comparison were rejected outright, because in each case the decision input is the payload. What survives is entirely local.

The comparison's fourteen items split along a seam the plan now respects. Six are always-on instruction rules whose home is a decision two queued plans own, and they are excluded here. Eight are local logic: a process-safety rule, a judgment vocabulary, three changes to the review pipeline, two loop mechanics, and one measurement. Those eight need no predecessor and ship together.

The riskiest work is deliberately sequenced last among the substantive phases. Incremental review reuse is the only item whose failure mode is a false negative inside a safety gate: a stale reuse drops a finding while every test stays green. The plan therefore builds a real `review-state` script rather than prose, decides the invalidation rule and the storage design before either is implemented, and requires a fixture proving the rule fires on the regression shape that a naive citation-keyed rule cannot catch.

#### 1.3 -- decision: the incremental-reuse invalidation rule

**Objective**: Decide what forces a full re-review, before any reuse path exists.

**Prompt**:
> This is the only item in the plan whose failure mode is a false negative inside a safety gate, so its rule is agreed before implementation. The rule is evaluated as an OR over its conditions: any single trigger forces a full re-review. Include at minimum these, and state why each is in or out: (a) the later commit touches a file any retained finding cited; (b) the later commit touches a file the deterministic pre-pass read; (c) the review skill, its schema, the persona roster, or the review severity gate threshold differs from the persisted record; (d) a deterministic check was recorded not-run or cut in the prior run, so its silence is not a pass; (e) the runs are not ancestor-related; (f) **a reachability condition**: a changed file's callers or callees, within the import or dependency closure at the depth the review already computes, were assessed in the prior run. Condition (f) is mandatory and is the reason this decision exists. Every other candidate condition keys on something a prior finding PRODUCED, so a clean verdict on file B cites nothing and nothing can invalidate it, yet the classic regression is commit 2 changing caller A so unchanged sink B becomes reachable with attacker-controlled input. Default to full re-review whenever the answer is unclear: the cost of an unnecessary full review is time, and the cost of a wrong reuse is a missed defect in a gate the user trusts. Record under `## Incremental reuse invalidation` with the rejected alternatives. Acceptance: conditions pre-selected in the file (not left for the implementer to weigh), and (f) present.

## Phase 2: Process and port safety

**Goal**: An agent pins its dev-server port, reuses a matching healthy server, and cannot terminate a process it does not own, on Windows, macOS, and Linux alike.
**Prerequisites**: Phase 1 (`## Guard scope`).
**Stability Gate**: The rule file states four constraints each with a per-OS mechanism; the guard is registered under every matcher T004 named; a parity fixture proves identical exit codes across both implementations including on a host without `jq`; and a fixture proves that writing the rule file itself is NOT blocked.
**Verification Expectation**: Start two servers on different ports from different working directories, run the documented reuse procedure, and observe that it attaches to the matching one and refuses to terminate the other. Then attempt `kill -9 $(lsof -ti:PORT)` against the non-matching server and observe the guard block it. The second observation is the one that matters: the name-based block is the easy case.
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: Cross-platform process semantics, a two-implementation parity obligation, and a guard whose false positives would get it switched off; the blast radius is another session's unrecoverable work.

### Sub-tasks

#### 2.1 -- Author the rule with portable matching evidence

**Objective**: State the four constraints with a mechanism that actually executes on every supported OS.

**Failure modes**: When the port registry is absent or malformed, the rule pins an explicit port and records it, never scans for a free port silently. When a discovered server is unreachable or slow to answer its health check, it is treated as not-matching and left alone rather than terminated. When two servers both claim the same project directory, or when no portable ownership evidence is available at all, constraint four applies: stop and report both rather than choosing.

**Build class**: load-bearing.

**Prompt**:
> Create `catalog/rules/process/dev-server-safety.md` with four constraints. One: consult the project's port registry file if present, and pin an explicit port with the framework's strict-port flag (`--strictPort` for Vite; name the documented equivalent for each other framework the catalog references) so a collision fails loudly instead of relocating silently. Two: before starting a server, look for a healthy running server belonging to this project and reuse it. **Do NOT specify "matching process working directory" as the mechanism**: reading another process's CWD is `/proc/<pid>/cwd` on Linux and `lsof -p <pid>` on macOS, and is effectively unavailable on Windows, where `Win32_Process` exposes `CommandLine` and `ExecutablePath` but not `CurrentDirectory`. Windows is a primary supported platform, so a rule whose central mechanism cannot run there is unfollowable. Specify portable evidence instead, naming the per-OS mechanism for each: a port-registry entry this session wrote (pid, port, project path), the server's own health endpoint reporting its project root, or `Get-CimInstance Win32_Process` CommandLine containing the project path. Three: never terminate a process selected by name pattern, and never terminate a PID obtained by resolving a name or a port; terminate only a PID this session started or positively established as this project's. Four: when the match is ambiguous or no portable evidence exists, stop and report. Follow `catalog/style-guides/markdown.md`. Acceptance: four constraints, a named per-OS mechanism for constraint two, and no reliance on reading another process's working directory.

## Phase 3: Deterministic pre-pass and the unrefuted verdict

**Goal**: The review runs its cheapest and strongest checks first, and names the state between confirmed and refuted with a word that is not already taken.
**Prerequisites**: Phase 1 (`## Queue reconciliation`).
**Stability Gate**: A review over a fixture diff emits at least one deterministic-class finding before any persona output, findings can carry the new state with a chained derivation, and the verdict rule is stated per review mode.
**Verification Expectation**: Run the review over a fixture diff containing a lint error and observe the deterministic finding present in the pre-pass output before any persona runs, and absent from the personas' own output rather than duplicated. Then read the verdict rule and confirm it states what governs in interactive mode, where Stage 6 does not run.
**Recommended model tier**: strong
**Recommended effort level**: high
**Rationale**: Control-flow and schema changes to a safety gate, bounded in size but with a mode-dependent correctness trap.

### Sub-tasks

#### 3.1 -- Deterministic pre-pass seeds the persona fanout

**Objective**: Run the deterministic verifier class first and hand its findings forward.

**Failure modes**: When a deterministic check's tool is absent or errors, the pre-pass records the check as not-run and the fanout proceeds unseeded, rather than the review aborting. When a check exceeds the stage budget it is cut and recorded as cut, never silently dropped; both states are invalidation triggers for Phase 4 reuse, because a skipped check inherited as a pass is a silent regression. When the pre-pass and a persona report the same defect, the deterministic finding wins and the persona duplicate merges into it.

**Build class**: load-bearing.

**Prompt**:
> Extend `catalog/skills/code-review/multi-agent-code-review/SKILL.md` Stage 1 so a deterministic pass runs before the persona fanout and seeds it. The pass runs the checks already classed `deterministic` per `ai-output-evaluation/references/verifier-taxonomy.md` (failing tests, linter output, schema checks, type errors), and passes its findings into the fanout as established context so personas neither re-derive nor re-report them. State a named starter list of high-risk patterns drawn from what this repository actually ships, not from the source article's database examples. #### 5.2 -- Supersede rather than fold

**Objective**: State that a new input cancels the in-flight assessment.

**Failure modes**: When cancellation cannot be effected, the loop lets the in-flight call finish and discards the result rather than blocking. When the superseding input arrives after completion there is nothing to cancel and a fresh run starts. When inputs arrive faster than a run completes, the loop takes the latest and states that intermediate inputs were skipped rather than queueing them silently.

**Build class**: load-bearing.

**Prompt**:
> Extend `catalog/skills/workflow/loop-engineering/SKILL.md` with the supersede rule: when a new input arrives that invalidates the assessment in flight, cancel and restart from the new input rather than folding it in. Note the counterintuitive part explicitly, because a reader will assume the opposite: folding appears cheaper since partial work is kept, but is usually slower, because the run carries context established against a state that no longer holds and spends its remaining budget reconciling it. State the non-cancellable fallback. Acceptance: the rule, its reasoning, and its fallback are all present.
