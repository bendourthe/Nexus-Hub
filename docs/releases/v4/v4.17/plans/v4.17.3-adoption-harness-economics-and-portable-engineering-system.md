## Overview

Nexus-Hub already supplies planning, testing, review, memory, security, reusable skills, structural harness auditing, and cross-platform instruction installers. The approved comparison found three narrower gaps: unattended routines do not explicitly report no-data and partial-completion outcomes; maintainers cannot measure a `model x harness x workload` pairing with one local, versioned receipt; and supported Claude Code project sessions still receive a generated `CLAUDE.md` even though Claude Code v2.1.277 can fall back to the repository's `AGENTS.md` (v2.1.281 on Amazon Bedrock, Google Vertex AI, Microsoft Foundry, LLM gateways, and telemetry-off sessions).

This plan closes those gaps without importing ECC, adding a hosted benchmark service, copying a public ranking, or creating a second routine framework. Structural conformance remains owned by `scripts/harness_audit.py`; the new evaluator owns observed local behavior. Project instruction content gains one platform-neutral shared owner, while platform integrations become consumers. Supported Claude Code sessions consume that shared `AGENTS.md`; below-floor, fallback-disabled, or precedence-blocked sessions retain `CLAUDE.md`.

## Review corrections

The mandatory coherence, scope, feasibility, design, product, security, and adversarial review ran against the first draft. The revised plan applies every P1 and P2 finding:

- Added terminal-outcome precedence so malformed input cannot masquerade as no data.

- Added execution modes, environment identity, paired ordering, a three-repeat minimum, named 95% interval methods, predeclared acceptance gates, Pareto reporting, and a restrained recommendation rule.

- Reduced the evaluator to a fresh serial repository-local MVP; resumability, parallel scheduling, quarantine, installer distribution, and a dashboard are deferred.

- Separated workspace hygiene from enforceable live isolation and delegated the live containment contract to `[[agent-execution-isolation]]`.

- Separated time, turn, and spend enforcement; hard cost claims now require provider- or adapter-enforced rejection before spend is incurred, while cancellation-only telemetry is bounded-overshoot observational evidence.

- Moved workload evaluators to a hashed read-only trusted root and required allowlisted, bounded, redacted, escaped output before any persistence.

- Added credential-free Claude Code and Codex profiles so the first real harness comparison does not require a custom bridge.

- Replaced the nonexistent single `AGENTS.md` owner with a proposed platform-neutral shared resource, per-platform semantic inventories, reachable platform-specific owners, persisted consumers, a capability-decision record, four Claude migration states, last-consumer teardown protection, and deterministic release gates.

- Added missing stabilization and specialized lifecycle task lines and reconciled one initial publication with scoped corrective re-pushes after failed required checks.

**Interview decision - approved 2026-09-21**: Use the platform-neutral `base-agents.md` owner proposed here. Every integration currently capable of writing root `AGENTS.md` becomes a consumer of the shared resource, with platform-specific guidance preserved through a verified native sidecar or platform-owned global surface. ## Goal

Give Nexus-Hub maintainers an honest, local way to decide whether a model-harness pairing earns its cost for a representative workload, while reducing duplicate project instructions for supported Claude Code sessions and making unattended-loop outcomes explicit when inputs are absent, stale, or only partly processed.

## Personas and user stories

- **US1 - Routine operator**: As a maintainer running an unattended routine, I can distinguish no data, stale input, partial completion, and full completion without reading raw logs.

- **US2 - Harness evaluator**: As a maintainer selecting a coding-agent harness, I can run repeated bounded trials over the same workload, with enforceable isolation for live runs, and compare success, cost, latency, context payload, and failure fingerprints from versioned local receipts.

- **US3 - Multi-tool repository maintainer**: As a maintainer using Claude Code with other coding tools, I can keep one project instruction file where Claude supports `AGENTS.md`, while preserving `CLAUDE.md` for below-floor versions, disabled fallback, precedence-blocked projects, and global Claude instructions.

## Non-goals

- Do not import ECC, its catalog, its runtime, or its installer.

- Do not adopt a shared cloud computer, shared credentials, a hosted benchmark service, or any search-, scraping-, embedding-, or generation-as-service MCP.

- Do not encode Arena's reported ratios or a permanent harness ranking.

- Do not author a Claude Code mod. Mods are verified built-in Claude Code plugins with a hooks module, but the vendor's `mods/README.md` marks them early access and warns that "the API these mods are written against may change between releases without notice" (D2).

- Do not replace `scripts/harness_audit.py`; structural audit and behavioral evaluation remain separate.

- Do not make a minimal harness the automatic winner. Lower overhead is one measured input, not the decision rule.

## Definition of Done

1. `[[loop-engineering]]` defines narrow-trigger test runs and observable `no-data`, `stale-input`, `partial`, `complete`, and `failed` outcomes, treats a source, connector, or input-format change as invalidating the last test run (`stale-input` until re-tested), and has regression tests that reject ambiguous success.

2. A local evaluator accepts an explicit workload and harness-adapter manifest, validates it before execution, and produces deterministic machine-readable receipts for synthetic fixtures without making provider calls.

3. Trusted synthetic trials run in workspace-separated temporary roots. Live trials run only through an enforceable isolation backend from `[[agent-execution-isolation]]` that constrains filesystem access, process trees, network destinations, and credential injection. Command execution avoids shell interpolation; typed redaction occurs before persistence; unavailable measurements remain explicitly unavailable.

4. Aggregation reports task success, latency, cost, cost per successful task, initial instruction bytes and estimated tokens taken from `scripts/measure_rendered_context.py --json` (no second estimator), organic skill selection, tool-schema bytes, repeated-trial uncertainty, and normalized failure fingerprints. Each workload predeclares acceptance gates and a decision policy; reports refuse a recommendation for incomparable, insufficient, or non-qualifying samples.

5. `scripts/harness_audit.py` remains a structural auditor and reports the effective project instruction path by capability rather than treating both `AGENTS.md` and `CLAUDE.md` as simultaneously required.

6. A platform-neutral shared-instruction resource owns the project `AGENTS.md` managed block and persists its active consumers. Supported Claude Code project sessions (v2.1.277+, or v2.1.281+ on Bedrock, Vertex AI, Foundry, LLM gateways, and telemetry-off sessions) whose effective `instructionFiles` value permits fallback consume it without becoming a writer. Global Claude instructions and below-floor, fallback-disabled (`claude-md`, `managed-only`, legacy equivalents, or a disabled built-in), or precedence-blocked project sessions retain `CLAUDE.md`. No-load modes (`--bare`, `--safe-mode`, `CLAUDE_CODE_DISABLE_CLAUDE_MDS`) are out of scope, and the documented residual differences are published as dated exceptions.

7. Bash and PowerShell installers, integration registry behavior, read-path verification, merge preservation, smoke postconditions, and legacy-parity tests agree on the effective Claude instruction path and preserve user-authored content. A per-platform semantic inventory proves that universal content moved to shared `AGENTS.md` and platform-specific instructions retained on a native sidecar or platform-owned global surface remain reachable for every migrated consumer.

8. A before-and-after evaluation records the instruction payload change and behavioral result for at least one approved local pairing, and a `NEXUS_HUB_SKILL_INDEX=full` against `pointer` receipt records payload and organic skill selection (including guard skills). v4.13 DF-1 is either decided from live evidence or stays open under this plan with the missing evidence named; synthetic receipts alone cannot flip the default. Fresh supported installs must have one active managed project body; deterministic synthetic outcomes must be identical; shared instruction bytes must not grow. A failed gate blocks convergence. If a live provider run is unavailable, the result is `needs-live-validation`; synthetic success is not reported as live evidence.

9. Every phase has focused tests, a CI-impact record, a session-history entry, and exactly one planned local phase commit. No phase before the terminal publication task pushes or starts remote CI. A failed required remote check reopens Phase 5 and permits only a separately recorded corrective commit and re-push.

10. The terminal phase completes architecture review, known-gap reconciliation, living-doc checks, git hygiene, CI/CD reconciliation, the Tier 3 deep pass, an independent Goal-vs-codebase review, human testing suggestions, a full local profile at one revision, and approval-gated publication.

## Phase 1: Ownership baseline and explicit loop outcomes

**Goal**: Reconcile the live queue and landed instruction work, then make unattended-loop outcomes explicit inside the existing loop owner.

**Prerequisites**: Approved comparison; clean understanding of the current dirty worktree; no destructive cleanup.

**Stability Gate**: Focused loop bundle tests prove each terminal outcome and reject a success claim for stale, absent, or partly processed input. Queue and ownership decisions are recorded in the phase evidence.

**Verification Expectation**: Run the loop bundle validator against positive and negative fixtures, including zero records, stale records, one failed item among successes, an expired budget, and a repeated idempotent retry.

**Recommended model tier**: strong

**Recommended effort level**: high

**Rationale**: The change is narrow and localized, but outcome semantics are trust-bearing and must remain compatible with existing loop budgets and termination rules.

### Sub-tasks

#### 1.1 -- Reconcile the queue and freeze ownership

**Prompt**:

> Re-run the queue enumerator, inspect landed diffs for v4.16.0, v4.16.2, v4.16.3, and v4.17.0, and record exact effects in `phase-1-evidence.md`. Confirm the three v4.13 handoffs this plan owns (DF-1 skill-index default flip, DF-4 measurer reuse, DF-5 shared merge primitive) are still open and unchanged in `docs/releases/v4/v4.13/known-gaps.md`. Preserve the ownership table above unless a landed artifact proves a conflict; in that case amend the plan before code changes.

**Failure modes**:

- Malformed or absent queue metadata yields `unknown`, never an inferred status.
- An unreachable plan file is recorded with its path and blocks only the affected dependency decision.
- Conflicting landed owners stop the affected task until one owner is selected; they are not merged silently.

#### 1.2 -- Add explicit loop outcomes

**Prompt**:

> Extend `[[loop-engineering]]` and its schema reference with a closed outcome vocabulary: `no-data`, `stale-input`, `partial`, `complete`, and `failed`. Add a precedence table: malformed, unreadable, schema-invalid, or unverifiable input is `failed`; a valid query returning zero records is `no-data`; any stale required source is `stale-input` unless fresh records were processed, in which case unfinished work is `partial`; any progress followed by budget exhaustion is `partial`; only all-valid and all-processed work is `complete`. Add a re-test rule: a change in a routine's source, connector, or input format invalidates its last test run, and the routine reports `stale-input` until a new bounded test run passes; a pending re-test outranks `partial`, so records processed after an untested source change still yield `stale-input`, and `partial` applies only once the re-test has passed; record the changed input identity and the invalidated test-run timestamp. Add no new outcome value. Require a narrow trigger, one bounded test run before scheduling, processed/failed/skipped counts, a last-success timestamp where applicable, and a next action for every non-complete outcome.

**Failure modes**:

- Missing or malformed input becomes `failed`; only a valid empty result becomes `no-data`.
- A stale source becomes `stale-input` even when cached output exists.
- Conflicting retries preserve the idempotency key and report partial progress rather than double-counting work.

#### 1.3 -- Prove the outcome vocabulary

**Prompt**:

> Extend `tests/validators/test_loop_engineering_bundle.py` with independent positive and negative controls. Assert exact required fields and demonstrate that deleting or weakening each outcome rule fails at least one test. Cover mixed fresh/stale records, zero processed after retries, corruption versus valid-empty input, partial progress followed by budget exhaustion, and a source-format change after a passing test run that must yield `stale-input` until re-tested.

**Failure modes**:

- A malformed fixture must fail with an actionable field path.
- A slow or unavailable external source is represented by a fixture and consumes no network access.
- Tests must reject simultaneous terminal outcomes and mismatched processed/failed totals.

#### 1.4 -- Testing and Stabilization

**Prompt**:

> Run the focused loop tests, the relevant skill validators, Markdown checks, and strict Unicode validation for every touched path. Fix failures, record CI impact, generate the phase session history, and create exactly one local commit. Do not push.

**Failure modes**:

- A missing test dependency is recorded and blocks the phase rather than being treated as a skip.
- A slow validator is bounded and its timeout is a failure.
- Conflicting unrelated worktree changes stay unstaged and out of the phase commit.

## Phase 2: Behavioral evaluation contract and fixtures

**Goal**: Define a versioned, fail-closed contract for comparable harness trials before implementing any live orchestration.

**Prerequisites**: Phase 1; v4.16.3 harness-cost guidance landed or the phase stops with a recorded dependency; reuse v4.17.0 evidence vocabulary if it landed.

**Stability Gate**: Schema and fixture tests distinguish valid, incomparable, no-data, partial, budget-exhausted, and malformed results without invoking a provider or harness binary.

**Verification Expectation**: Parse frozen positive and adversarial manifests and receipts; recompute every aggregate with an independent oracle; prove that pricing, payload, or sample gaps remain unavailable rather than becoming zero.

**Recommended model tier**: frontier

**Recommended effort level**: max

**Rationale**: Cross-harness comparability, uncertainty, pricing, and failure normalization have high semantic uncertainty and can create convincing but false evidence if the contract is weak.

### Sub-tasks

#### 2.1 -- Define manifest, trial, and receipt schemas

**Prompt**:

> Add `guides/reference/HARNESS_PAIRING_EVALUATION.md` with the durable system contract and add versioned JSON fixtures under `tests/fixtures/harness_pairings/`. Bind each run to workload hash, repository revision, harness and model identity, adapter version, effective instruction hash, instruction variant (including the `NEXUS_HUB_SKILL_INDEX` mode), tool-schema hash, pricing snapshot, trial seed, isolation mode, operating system and architecture, harness configuration, model parameters, cache policy, concurrency level, retry policy, trial order, budgets, and timestamps.

**Failure modes**:

- Missing required identity or budget fields reject the manifest before execution.
- Unavailable version or pricing data is explicit and makes affected comparisons `incomparable`.
- Conflicting trial IDs, workload hashes, or schema versions are rejected rather than merged.

#### 2.2 -- Define outcomes and objective metrics

**Prompt**:

> Define task success from a workload-owned deterministic evaluator, not harness self-report. Define latency, observed provider cost, cost per successful task, initial instruction bytes, tool-schema bytes, trial counts, uncertainty intervals, and normalized failure fingerprints. Take initial instruction bytes and estimated tokens from `scripts/measure_rendered_context.py --json`, importing its estimator rather than defining a second one (v4.13 DF-4). Define organic skill selection as the set of skills a trial actually loads without being named in the prompt, and record guard skills (for example `security-review`) separately. Declare `NEXUS_HUB_SKILL_INDEX=full` against `pointer` as the required first variant pair. Keep every raw trial beside aggregates. Separate `synthetic`, `metered-live`, and `observational-live` modes: synthetic cost is not applicable; metered live requires provider- or adapter-enforced spend control; observational live may report cost but cannot satisfy a hard-cost claim or recommendation gate.

**Failure modes**:

- No successful task makes cost per success unavailable, not zero or infinity presented as a score.
- Missing provider usage data preserves success and latency while marking cost unavailable and blocks a cost-based recommendation.
- Conflicting evaluator and harness claims resolve in favor of the workload-owned evaluator with both values retained.

#### 2.3 -- Define comparison eligibility and ranking restraint

**Prompt**:

> Require the same workload revision, evaluator revision, environment identity, model parameters, cache policy, retry policy, paired seeds, trial-order policy, budget class, and pricing basis for a direct comparison. Default to three repeats per pairing, a 95% Wilson interval for binary success, and a fixed-seed percentile bootstrap interval for continuous metrics. Alternate or randomize pairing order with the recorded seed. Each workload must predeclare minimum success, maximum latency and cost where applicable, and a tie-break policy. Report qualifying pairings and their Pareto frontier; name one recommendation only when the predeclared tie-break applies and the relevant 95% intervals do not overlap.

**Failure modes**:

- Fewer than three repeats cannot yield a recommendation.
- A timed-out pairing remains in the report as partial evidence.
- Conflicting price dates or budget classes split comparison groups rather than being normalized silently.

#### 2.4 -- Define the adapter and isolation boundary

**Prompt**:

> Define adapters as argv arrays plus a narrow JSON input/output protocol. Forbid `shell=True`, inline secrets, inherited environment by default, and receipt capture of credential values. Treat all adapter bytes as hostile: bound output before parsing, accept allowlisted typed fields only, redact in memory before any persistence, escape control sequences and Markdown/HTML, and keep raw stdout/stderr ephemeral unless an explicitly protected diagnostic channel is selected. Require disposable workspace roots, a sentinel before cleanup, an environment allowlist, and explicit network/provider permission.

**Failure modes**:

- String commands, traversal paths, missing sentinel, or unknown environment names fail before process start.
- An unavailable or slow harness exits with a bounded typed failure and retained logs.
- Colliding runs cannot share a mutable workspace or receipt path.

#### 2.5 -- Add independent contract tests and negative controls

**Prompt**:

> Add `tests/integrations/test_harness_pairing_contract.py` with an independent aggregate oracle and mutations for absent values, inconsistent totals, forged success, secret-shaped fields, invalid UTF-8, NULs, ANSI escapes, forged Markdown headings, oversized fields, path escape, budget overrun, mixed comparison groups, environment or trial-order drift, and an instruction-byte figure that disagrees with `measure_rendered_context.py` output for the same file.

**Failure modes**:

- A malformed fixture names its schema path and never reaches execution.
- Tests use frozen local data and remain valid without network or provider credentials.
- Mutually inconsistent outcomes cannot pass because both producer and test use the same helper.

#### 2.6 -- Route audit findings without merging owners

**Prompt**:

> Update `[[eval-pipeline-audit]]` to recognize missing cross-harness behavioral evidence and route it to the local evaluator. State that `scripts/harness_audit.py` remains structural and the evaluator remains behavioral. Link the reference contract without embedding runner mechanics in the audit skill.

**Failure modes**:

- An absent evaluator is reported as not covered, not reconstructed by the audit skill.
- An unreachable reference produces an explicit broken-link failure.
- Conflicting structural and behavioral results are shown side by side, not collapsed.

#### 2.7 -- Testing and Stabilization

**Prompt**:

> Run contract tests, skill bundle validation, documentation links, schema mutations, Markdown checks, and strict Unicode validation. Fix failures, record CI impact, generate the phase session history, and create exactly one local commit. Do not push or call a provider.

**Failure modes**:

- An unavailable optional parser cannot weaken the stdlib validation path.
- A slow mutation suite is bounded and fails visibly.
- Unrelated dirty files stay outside the commit.

## Phase 3: Isolated local pairing runner

**Goal**: Implement a serial local runner that executes trusted synthetic adapters with workspace hygiene, executes live adapters only behind proven isolation and budget capabilities, and emits comparable receipts redacted before persistence.

**Prerequisites**: Phase 2 contract frozen and green; at least one deterministic synthetic workload, two fake adapters, and credential-free conformance profiles for the Claude Code and Codex CLIs.

**Stability Gate**: A complete serial synthetic matrix run and an interrupted run produce schema-valid receipts; independent recomputation matches; cleanup touches only sentinel-owned temporary roots; canary secrets and hostile control bytes appear in no persisted artifact; live mode is rejected unless containment and budget capabilities are proven.

**Verification Expectation**: Exercise the command end to end with fake adapters that succeed, fail, hang, emit malformed or hostile output, omit pricing, and attempt host escape.
