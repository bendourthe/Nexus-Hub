## Why this plan is separate

The six items here are always-on instruction rules. They live in a surface loaded on every session across roughly twenty platform integrations, and `v4.15.0-instruction-necessity-review` exists specifically to cap and reduce accumulation in that surface, which currently runs to 541 lines. Shipping six new rules before its before-and-after baseline is recorded would make that measurement report a surface this work had just inflated.

So the dependency here is a **hard block, not a preference**. There is no provisional-cap path: if `v4.15.0` has not landed, this plan does not start. The eight local-logic items from the same comparison were split into the sibling plan precisely so the highest-value safety work is not held behind this gate.

#### 2.2a -- Behavioral post-condition rule, the pre-edit counterpart (moved from v4.18.2 T006)

**Objective**: Extend `verification-before-completion` with the pre-repair half of its existing behavioral-evidence rule, in the same release as the post-edit half in 2.2, so the two land together.

**Failure modes**: When the flagged code's correct behavior is not knowable from the call site, the rule must instruct reading the caller and the tests before writing a post-condition, not skipping it. When the linter's own message already states a behavioral requirement, the rule must not be satisfied by copying that message verbatim, since that is the tool state restated. When two findings in one file imply conflicting post-conditions, the rule must require both to be written and the conflict surfaced rather than one silently chosen.

**Prompt**:
> Extend `catalog/skills/workflow/verification-before-completion/SKILL.md` with the **behavioral post-condition** rule. Use that exact term throughout. Do NOT use "acceptance condition": `catalog/agents/loop-operator.md` already defines that term six times as "what done looks like in the verification output (e.g. 0 failures, exit 0)", which is precisely the tool-state formulation this rule rejects, and shipping both would leave the catalog stating two contradictory definitions of one term.
> The rule: before repairing a flagged finding, write what the program must KNOW or DO afterward, in behavioral terms, and treat that as what the repair must achieve.
