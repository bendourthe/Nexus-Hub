**Goal**: Nexus-Hub recommends reasoning effort by what it buys (verification and independent judgment), not only by capability tier. When a phase keeps failing, the escalation raises effort for missed edge cases and changes tier, re-plans, or asks for a wrong approach. A plan phase can carry a verification effort higher than its implementation effort. `model-map.py score` raises that verification effort for edge-case-dense work, one level further when the run is unattended, never above `high`, never for unattended work alone, and never lowers any recommendation. The GO/NO-GO step requests the named verification behaviors that high effort produces when a phase's verification effort is above its effort, and treats them as advisory otherwise. No new third-party destination, credential, runtime dependency, or model download is added.

## Overview

The seeding comparison read a practitioner article arguing that higher effort mostly buys verification and independent judgment: it fixes failures caused by missed edge cases, does not fix a wrong approach, and matters most when nobody is in the loop to steer. Nexus-Hub computes effort from the same aggregate score as tier, runs verification at the implementation effort, and escalates a failing phase without asking why it fails.

Phase 1 records baselines, drafts three definitions every later phase uses, and files two known gaps. Phase 2 writes those definitions once into their owner, `model-routing`, and changes guidance text: failure-class-aware escalation, a refreshed effort decision table, and a correction to an over-general cache claim. Phase 3 writes the verification-behaviors reference. Phase 4 changes the routing contract: a raise-only verification effort computed by `model-map.py`, an optional per-phase plan field checked by a new `plan_status.py --check` mode, the pre-flight that applies both, and a decision record. Phase 5 is the mandatory final phase.

The work is Markdown plus changes to two standard-library Python scripts and their tests. Nothing is sent anywhere.

**Objective**: Make three judgments observable enough for a planner and an implementer to reach the same answer.

**Prompt**:

(1) Edge-case density: `high` when the phase parses or sanitizes untrusted input, crosses a security or permission boundary, touches concurrency, storage, or crash recovery, implements a numeric or search algorithm with a correctness or performance target, or fixes a bug in existing code from a failure report; `medium` when it handles several input shapes or states with known boundaries; `low` for mechanical, documentation, or configuration work.
