# Comparison: Evidence-Driven Agent Improvement

This report compares nine supplied documents with Nexus-Hub's current catalog and release plans. It is for the maintainer deciding what to adopt next: evaluation feedback, agent observability, instruction loading, context freshness, visual explanations, and established-codebase practice.

Adoption target: v4.11.0

**Date:** 2026-09-08. **Baseline:** local branch `feat/v4.9.0-visa-vulnerability-agentic-harness`, HEAD `202eff9e` at initial inspection. **Scope:** comparison and adoption recommendations only. **Status:** finalized; target and planning/publication authorized by the maintainer on 2026-09-08. Source facts and implementation state are dated observations, not permanent claims.

## Decision

Extend existing owners; do not add a self-training platform, new memory service, telemetry backend, or general-purpose visual skill. Nexus-Hub already has most of the underlying practices. Six bounded improvements remain worthwhile, led by judge sensitivity checks and safer, interoperable observability examples.

The distinction is between a catalog that teaches a method, an executable helper that enforces it, and a measured result on a real workload. This review establishes catalog and local-code coverage. It does not claim that Nexus-Hub has run a calibrated production improvement loop or reproduced any vendor's benchmark.

### Proposed trace example contract for A6

Use standard `gen_ai.*` names only for concepts defined by the pinned convention. Keep Nexus-specific iteration, budget, verifier, evidence-reference, and health fields separately namespaced; do not present them as OpenTelemetry attributes. Remote agent creation/invocation uses CLIENT semantics; local invocation/workflow/planning uses INTERNAL where the source defines it. Emit planning spans only when planning boundaries are reliably observable. Tool execution is referenced by the agent document, but exact tool-span fields must be verified against the sibling inference/tool specification during implementation.

A trace records what the integration could observe, not what it imagines the model thought. Unavailable reasoning is omitted or marked unavailable in a local coverage record. Human-readable summaries, if voluntarily supplied, are not authenticated internal reasoning. Missing spans, a passing answer, or an absence of alerts are not proof that no unsafe action occurred. Keep authorization and isolation controls outside the trace system. Reuse v4.9 audit-health ownership where relevant after that work is actually implemented.

## Considered but not recommended

- A wholesale specialized-model stack: S1/S2 describe product training and serving economics, not a catalog capability that Nexus-Hub can reproduce with prompts. No vendor percentage is an expected Nexus-Hub saving.
- A four-model critic/judge panel by default: the extra model calls need evidence of benefit; existing independent-verifier rules do not require a particular ensemble size.
- Learned gist-token compression as a skill-authoring optimization: requires model-level training and cannot be equated with shorter Markdown.
- Redis or hosted evaluation/telemetry adoption: introduces an unnecessary destination and duplicates local capabilities. The future Redis session is a source-revisit item only.
- Copying the entire visual skill or expanding handbook implementation: useful selection behavior belongs to current owners; the separately queued handbook plan remains unchanged.
- Removing tests or safety constraints because Astra is more capable: existing restraint already removes redundant effort; trust-boundary and observable verification requirements remain necessary.
- Generic "respect prior art" additions: already explicit in the construction and planning owners. No new legacy-codebase skill is warranted.
- Treating TechTimes' architectural claims as established facts, or demanding internal reasoning traces to compensate: neither is justified by the verified primary evidence or available integration boundaries.
