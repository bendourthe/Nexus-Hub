# v4.10.0 Claude Usage Monitor scoped weekly bar

Development record for the second weekly bar in the Claude Usage Monitor. This record covers the API finding that drove the design, the changed surfaces, the verification actually run, and the boundary this work stops at. Originally authored as a standalone v4.9.1 release that was never pushed or tagged; the work was folded into the v4.10.0 line on 2026-09-12, because v4.10.0 merged to `develop` first and a 4.9.1 stamped onto a tree containing it would have been wrong. Only the slot moved: no design or verification claim below is changed by the fold.

## Trigger

The Claude usage page now shows two weekly bars, "All models" and "Fable", where the extension showed one. The request was to surface the second bar in the extension's dashboard and status-bar hover, and to leave the status-bar text alone.

## API finding

The account usage endpoint was probed once with the local Claude Code OAuth token, the same single first-party request the extension already makes, to establish the real field names rather than guess them. Two things were observed.

The response now carries a self-describing `limits` array. Each entry has a `kind` (`session`, `weekly_all`, or `weekly_scoped`), a `percent`, a `resets_at`, and, for a scoped entry, a `scope.model.display_name`. On the probed account the three entries read 72 percent session, 43 percent `weekly_all`, and 0 percent `weekly_scoped` with display name `Fable`, matching the account page exactly.

The same scoped number is also carried by a flat sibling key, `nimbus_quill`, sitting among `tangelo`, `cinder_cove`, `copper_kite`, `harbor_lantern`, `amber_ladder`, `juniper_tide`, and `seven_day_omelette`. These are rotating internal codenames. Binding a shipped bar to one would break silently the moment it is renamed, and it would be the same class of mistake as the fabricated `.kimi/agent.yaml` companion dropped in v3.15.0. The `limits` array is read instead, and the flat per-window fields are kept only as the fallback path for a response that does not carry the array.

| Surface | Change |

| `src/types.ts` | Adds `ScopedUsageMetric` (a `UsageMetric` plus the API-reported `label`) and the optional `UsageData.weeklyScoped` field. |
| `src/providers/claude.ts` | Adds the `limits` entry shape, makes every response field optional, and moves mapping into the exported pure `mapClaudeUsageResponse`, matching the shape the Codex monitor already uses. |

| `src/dashboardPanel.ts` | Same relabel, and the scoped section is rendered only when the data carries one. |
| `test/claude-usage-mapping.test.ts` | New. Six cases covering the scoped read, the fallback path, an account with no scoped limit, an unnamed scoped entry, an empty payload, and extra-credit minor-unit conversion. |

## Decisions

**The label comes from the API, never from a hardcoded model name.** The account page names this bar after the model, so the name travels with the number. A scoped entry that arrives without a usable display name is skipped rather than shown under an invented label, because a bar with a number and no stated meaning is worse than no bar.

**The scoped bar is display-only.** Urgency thresholds, status-bar highlighting, and threshold notifications continue to evaluate the session and all-models weekly metrics only. This follows the stated requirement that the second bar stay out of the taskbar. The consequence is recorded in the release notes and in known gaps: a scoped limit approaching capacity is visible on hover and in the dashboard but will not interrupt the user.

**Escaping was added for the SVG label.** The tooltip percent-encodes a whole inline SVG into a data URI, so an unescaped `<` in a server-provided label would still reach the SVG parser as markup. Every tooltip label now goes through `escapeXml`; the dashboard already had `escapeHtml`.

The live-payload check is the one that matters most here, because the hand-written fixture and the mapper were written by the same pass and could have agreed with each other while both being wrong about the real response.

## Not done

Rendering was not exercised in a running extension host. The type check and the unit tests prove the normalized model is correct; they do not prove the tooltip and dashboard draw the second bar. That requires loading the built extension in VS Code and hovering the status-bar item.

Nothing was pushed, tagged, or published. The version bump, changelog entry, README section, and this record are local only.
