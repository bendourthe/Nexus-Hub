**Goal**: Make a comparison, a plan, an implementation phase, and a release each account for the OTHER plans queued around them, so a plan authored against one codebase state is re-validated before it is executed against a later one, and so queue order is a reasoned decision rather than an accident of allocation order.

## Overview

A comparison is a snapshot. A plan derived from it is executed later, against a codebase that has moved, alongside other plans that will move it further. Nothing in the current command set re-validates that assumption at any point between authoring and execution. This plan closes that gap at the four moments where the assumption is actually made, and adds a ranked ordering recommendation with an assisted renumber behind explicit confirmation.

The capability is built once and consumed four times. One skill owns what makes a plan stale and how the queue is ranked; one repository script deterministically enumerates the queue; `/compare`, `/plan`, `/implement`, and `/update release` each delegate to that owner rather than carrying their own copy of the rule.

The problem is not hypothetical in this repository. At authoring time four plans are open with 112 unstarted tasks between them, and the earliest slot in the queue (`v4.9.1`, interactive handbooks) is a documentation plan, which is precisely the class the maintainer wants sequenced last. Three manual renumbers were performed on 2026-09-10 alone: the cache-and-diagram and attribution slots were swapped, the evidence plan was moved out of the way to v4.13.0, and this plan was then swapped ahead of cache-and-diagram into v4.10.0. Those three operations are the motivating instance and the design input for Phase 5, and the third of them was performed while cache-and-diagram was already mid-implementation, which is the hardest case the procedure must handle.

## Goals First / Definition of Done

**Persona and problem**: A Nexus-Hub maintainer holds several plans at once. Each was written against the codebase as it stood at authoring time. By the time one is implemented, earlier plans have changed the files it targets, invalidated its assumptions, or already delivered part of its scope. The maintainer currently has no way to learn this except by re-reading every queued plan by hand, so in practice it is not done, and a stale plan is executed as written.

| ID | Observable completion condition |
|---|---|
| D1 | The enumeration script reports every plan under the release tree with its version, slug, open and completed task counts, and the file paths its task lines name. It sorts on parsed integers so `v4.10` follows `v4.9`, scans the whole tree rather than the current minor, and reports a malformed or unreadable plan as an explicit finding rather than omitting it from the queue. |
| D2 | Given one plan or comparison plus the enumerated queue, the assessment produces a per-queued-plan verdict of no impact, content impact, or ordering impact, each with the specific evidence that produced it. An unreadable input yields an explicit unknown, never a silent no-impact. |
| D3 | `/compare` and `/plan` each account for queued plans: the comparison records which queued plans may change its findings before adoption, and a generated plan records the queued predecessors whose completion would alter its own content. |
| D4 | `/implement` re-assesses at plan entry and at every phase entry, comparing the plan against the current codebase, and surfaces a required plan edit as a blocking finding rather than proceeding silently. An assessment that finds nothing writes that result explicitly. |
| D5 | `/update release` evaluates the newly released state against every still-open queued plan and reports which of them the release has changed, with the affected task lines named. |
| D6 | The ordering recommendation ranks the queue by parallel-implementation compatibility and by impact on Nexus-Hub as a harness, places documentation, interactive-guide, and refactor classes last, and marks a last-placed plan as requiring a content refresh against everything sequenced before it. The assisted renumber is propose-then-apply behind explicit confirmation, moves the release tree, renames the plan and comparison files, repairs every inbound reference, and proves the repair with a residual-reference check that fails on a single survivor. |
| D7 | The final evidence connects D1-D6 to actual artifacts, preserves existing command behavior for a repository with an empty queue, proves distribution on supported operating systems, and records all scoped validation and independent review results. |

**Definitions.** *Content impact* means a queued plan, if completed first, would change what this plan should say or do. *Ordering impact* means two plans touch an overlapping file surface and therefore cannot be implemented in parallel. *Parallel-compatible* means two plans have disjoint touched-file surfaces and no stated dependency; it is a claim about file conflict, not about reviewer capacity. *Impact on Nexus-Hub as a harness* is a maintainer judgement the skill structures and records; it is not computed.
