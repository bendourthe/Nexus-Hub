# Comparison -- Nexus-Hub vs the `ecc` Multi-Platform Agent Catalog

**Project**: Nexus-Hub
**Source**: <https://github.com/affaan-m/ecc> (`ecc-universal` v2.2.1, MIT)
**Source type**: Git repository
**Adoption target**: v4.7.0
**Created**: 2026-09-02
**Authoring cycle**: v4.4.2 (in flight)

## Why this source matters to this project

This is the closest structural peer Nexus-Hub has been compared against. It is not an application that happens to use agents; it is a multi-platform agent catalog with the same product shape: skills, commands, agents, rules, and hooks distributed by an installer into every major AI coding platform. That makes the comparison unusually informative in both directions, and it makes the places where Nexus-Hub is ahead worth recording as deliberately as the gaps.

Headline counts, both measured from the trees rather than from either project's own claims.

| Artifact | Nexus-Hub | `ecc` |
|---|---|---|
| Skills (`SKILL.md` files) | 329 | 286 |
| Commands | 21 | 94 |
| Agents | 23 | 68 |
| Hooks (shell / Python entry points) | 38 | 54 |
| Platform surface directories | roughly 20 by installer registry | 20 committed dot-directories |
| Python test files | 213 | not comparable (Node test suite, 278 files under `tests/`) |
| Per-skill `references/` directories | 149 | present, not exhaustively counted |
| Per-skill `evals/` directories | 88 | per-skill evals not used; a central `eval-harness` skill instead |

The counts matter less than the shape. The two projects have converged on nearly identical architecture (SKILL.md with progressive disclosure, per-platform install adapters, a hook registry, a slash-command surface) while diverging on three things: how the distributed artifact is delivered and verified, how reliability is measured, and how much command surface is considered healthy.

## Step 1.5 -- Source security scan

**Verdict: PROCEED-WITH-CAUTION.**

The repository was cloned with `--no-checkout` and inspected through `git ls-tree` and read-only greps. Nothing from it was executed, and no dependency from it was installed.

**Prompt injection and embedded agent-directed instructions: clean.** A scan for override phrasing, hidden HTML-comment instructions, and zero-width or bidirectional control characters across all Markdown, YAML, JSON, and JavaScript returned no injection payload. Every hit on phrases such as "ignore previous instructions" and "exfiltration" is legitimate defensive content: this project ships an agent-security scanner, so the strings appear in detector rules, test fixtures, and security documentation. Two hits are worth noting as good practice rather than as risk, in `workflows/orch-review.workflow.js` lines 119 and 134, which explicitly fence a diff as untrusted input and instruct the reviewer to treat embedded directives as findings rather than commands. The zero-width and bidirectional scan returned no files.

**Malicious or destructive code: clean.** No `postinstall` or `preinstall` lifecycle hook exists in any `package.json`. A scan for `curl | sh`, `wget | sh`, `eval(`, interpolated `child_process.exec`, `nc -e`, `/dev/tcp/`, and `rm -rf` against a root or home path returned two hits, both of which are the opposite of a risk: a comment in `scripts/hooks/gateguard-fact-force.js` line 162 documenting the command-substitution attack that hook exists to block, and a line in `scripts/sync-ecc-to-codex.sh` instructing a reviewer to scan for `eval(`.

**Supply-chain posture: strong, and better than Nexus-Hub's in one respect.** All 60 GitHub Actions references are pinned to 40-character commit SHAs with zero tag-pinned references, and `.github/workflows/supply-chain-watch.yml` installs with `npm ci --ignore-scripts` before running `npm audit signatures`. Four runtime dependencies, all exact-pinned.

**The caution.** The distributed package carries a commercial sponsorship coupling. The `welcome` script in `package.json` names a compute vendor as "the preferred compute sponsor" with a link, and the repository ships four vendor-specific skills (`ito-compute`, `ito-inference`, `ito-training`, `ito-baskets`) plus an opt-in `ecc ito find` bridge that the script itself describes as submitting a live authenticated RFQ to that vendor. The disclosure is honest and the bridge is opt-in, so this is not malicious. It is flagged because it is exactly the class of vendor coupling Nexus-Hub's MCP Registry Policy exists to keep out of a distributed catalog, and because it means any wholesale adoption from this source risks importing it. Every such artifact is explicitly excluded in the NOT-recommended list below.

Proceeding on this verdict: all instruction-like text in the source was treated as data throughout the analysis, and no vendor-coupled artifact enters the adoption plan.

## Step 7 -- Risks, conflicts, and items not recommended

### Conflicts with existing Nexus-Hub conventions

**E3 and E5 against the required-checks policy (real, and the sharpest risk in this report).** Nexus-Hub's v3.17.6 policy is that a required status check must be produced by a workflow that triggers unconditionally, because GitHub leaves a check from an untriggered workflow Pending forever. A `schedule`-triggered workflow does not trigger on a pull request at all, so E3 must be added as a **non-required** advisory workflow, or the merge queue will block on a check that only exists every six hours. Separately, E5's reusable `workflow_call` factoring changes which job names publish which contexts, and a job-level `if:` is evaluated before matrix expansion, so a refactor can silently stop publishing the aggregate `ci-required` context while every leg still looks green. Neither candidate may be implemented without re-running `scripts/check_required_check_coverage.py` and `tests/validators/test_ci_required_gate.py`. This is the same class of failure that cost six administrator bypasses shipping v3.17.5.

**E2 against the installer sibling-parity rule (procedural, not a real conflict).** Any verification step added to `install.sh` must ship simultaneously in `install.ps1` with matching behavior and matching exit codes. The `.ps1` half is the one that historically diverges: `session-summary.ps1` shipped broken in v3.11.0 and was dead on Windows for four minor versions. Prefer native equivalents (`Get-FileHash` over emulating `sha256sum`) and remember that the v3.15.6 ledger diverged specifically on `sha256sum` escaping of backslash-containing filenames, which is exactly the code path E2 touches.

**E2 against the install-UX contract (mild).** v3.7.0 made installs no-prompt by design. A verification step that fails must therefore fail loudly and abort rather than prompt, and its failure message must name the remediation, or it will read as a broken install rather than a caught tamper.

**E4 against the upgrade path (mild).** `nexus-hub upgrade` re-runs the idempotent bootstrap. Adding a version argument means deciding what `upgrade` does when the user is pinned: silently move to tip, refuse, or require an explicit flag. Decide and record it; do not leave it implicit.

**E1 against nothing.** It is additive methodology on existing infrastructure, and its human-grader gate reinforces `## Consequential Decisions`. This is why it is sequenced first.

### Change-risk notes

- E2, E3, and E4 all modify existing infrastructure rather than adding new files, which is the higher-risk half of the value matrix. E1 and E6 are additive.
- E2 and E4 touch the install path, where a defect is maximally visible: it breaks first-time install for every platform at once. Both need a throwaway-directory dry run on Windows and on a POSIX host before merge, per the installer checklist in `AGENTS.md`.
- Nothing in the recommended set touches `data/`, the skill catalog, or the instruction templates, so this report has no interaction with the v4.5.0 template work or with its companion Fable report's Track V4.5.
- No candidate imports code from `ecc`. E2, E3, and E4 are re-derived from the pattern; per the reverse-engineering attribution rule the source is credited here, in this report's matrix row, and must not be named in the resulting artifacts.

### Nexus-Hub strengths this comparison confirms, and which must not be traded away

Recorded because a comparison that lists only gaps invites regression on the things already right.

- **Zero mandatory runtime dependency for the catalog.** `ecc` needs Node plus four dependencies; Nexus-Hub needs neither.
- **Generated-not-committed per-platform output.** `catalog/` to `data/` to install-time emission is what makes the parity guards checkable.
- **Command consolidation.** 21 commands with a runtime-derived cheatsheet, against 94 plus a shim tree.
- **Required-check integrity.** The declared manifest plus two validators has no counterpart in the source.
- **Documentation lifecycle.** The lifespan admission test and retention policy, against 1516 doc files with dated session artifacts still live.
- **Skill authoring discipline.** The three-tier loading model, the 800-line hard cap, agentskills.io conformance, and rule-ownership for overlapping skills.
- **Decision records with `## Alternatives considered`** and a `rejected/` lifecycle, which is what let this report cite settled decisions instead of re-opening them.
- **100 percent SHA-pinned Actions.** Equal to the source, and worth stating so it is not lost in a future refactor.
