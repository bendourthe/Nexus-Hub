# Comparison -- Nexus-Hub vs the GPT-6 Astra Prompting Guide, with a Fable 5.1 Re-check

**Project**: Nexus-Hub
**Sources**: <https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6-astra#prompting-best-practices> (first-party vendor documentation, GPT-6 Astra model guide) and <https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1> (first-party vendor documentation, re-checked against the 2026-09-02 comparison)
**Source type**: Web articles
**Adoption target**: v4.7.0 (amendments to the committed, not-yet-started model-behavior plan; see resolution below)
**Created**: 2026-09-04
**Authoring cycle**: v4.4.5 (in flight, branch `feat/v4.4.3-guide-illustration-rebuild`)

## Why these sources matter to this project

Nexus-Hub distributes always-loaded behavioral guidance into every major agent platform, and two of those platforms are Codex and Claude Code. The vendor pages that describe how the current frontier model of each behaves are therefore primary inputs to what the catalog should say. The Anthropic page was compared in full two days ago (`docs/releases/v4/v4.5/comparisons/v4.5.0-comparison-fable-5-1-prompting.md`, 17 insights, routed into the v4.5.0 and v4.7.0 plans). The OpenAI page has never been compared, and the catalog's per-model prompting-profile layer holds no OpenAI model at all: `model-prompting-research/assets/profiles-index.json` lists a Claude-only roster verified 2026-07-27, with every Claude entry still marked unprofiled or unverified.

So this comparison does two different jobs. For the Fable page it asks one question: has anything changed since 2026-09-02? For the Astra page it extracts every recommendation, classifies each against the catalog, and finds that the model-specific items have no home because the profile layer is empty on the OpenAI side, while the model-agnostic items are mostly cross-vendor corroboration of rules the v4.7.0 plan already carries from the Anthropic page.

### Step 7 -- Risks, conflicts, and items not recommended

**Conflicts with existing conventions.**

- **G2 vs the Skill Discovery rule.** Every substantive template says "Do not mention the skill lookup to the user." O5 says name and link the skill when it causes a pause. These target different moments (routine routing versus a skill instruction that blocks or changes what the user asked for), but the templates do not say so, and a reader of both rules today would see a contradiction. G2 must add the distinction in words, not just the new rule.
- **G1 vs the profile index schema.** `profiles-index.json` records one `meta.platform` and one roster. An OpenAI model verified against the Codex roster does not fit without a schema decision, which is why G1 is preceded by a `decision:` ticket and why the schema minor is bumped rather than the file hand-edited.
- **O9 vs bounded fan-out.** OpenAI's guide says parallelize whenever possible; the catalog's orchestration and loop skills say fan out only for a measured problem and budget the tax. This is a deliberate difference, not an omission. Recording it as a one-sentence note in the primitives skill is optional; adopting the vendor rule is not recommended.
- **G5 vs two same-day plans.** The v4.4.6 plan maps `gpt-6-astra` at frontier; the v4.8.0 plan leaves it unmapped. Whichever way Phase 1 decides, one of those plan maps should be corrected at implementation time, and the decision should be quoted rather than re-derived.

**Change-risk notes.** G2 touches the seven templates the parity guard does not cover; read each one. G1 is the only item that runs a research pass and is bounded by the runbook's per-model budget and kill switch.

**NOT recommended for adoption.**

| Item | Grounds |
|---|---|
| O9, parallelize whenever delegation is possible | Deliberate override by `agent-orchestration-primitives` Step 6 and the loop skill's orchestration-tax doctrine; adopting it would reintroduce the failure mode those rules exist to prevent. |
| Putting any O13 to O19 content into a template, command, or shared skill body | The `model-prompting-research` hard rail: model-specific claims never enter a shared body, because a shared body is distributed verbatim to every platform. |
| Re-comparing the Fable 5.1 page's 17 items | No delta since 2026-09-02; the prior report and its routing stand. |

**Nexus-Hub strengths these sources confirm.** The catalog's communication contract already states O6, O7, and O10 more precisely than either vendor page; the idempotent-gate and tiered-verification rules already cover O12; and the profile layer's hard rail is exactly the mechanism that keeps O13 to O19 from leaking into shared guidance, which neither vendor page addresses because each speaks for one model.
