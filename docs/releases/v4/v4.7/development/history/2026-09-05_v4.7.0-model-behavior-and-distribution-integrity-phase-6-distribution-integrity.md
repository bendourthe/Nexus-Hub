## Outcome

A release now publishes its own artifact set (a deterministic tarball, a GNU-format `SHA256SUMS`, and a GitHub-native build-provenance attestation) attached to the GitHub Release, and both bootstrap installers download that tarball for a tagged ref and verify it fail-closed: a mismatch, a missing checksum file, and an unresolvable ref each abort with a distinct message and a non-zero exit, and nothing installs unverified. Both installers accept a `--ref` / `-Ref` pin and record it; `nexus-hub upgrade` refuses to move a pinned install unless told where, and `--ref` doubles as rollback. A scheduled, advisory supply-chain watch audits the six extension packages and their optional extras weekly and is proven absent from the required-check set.

## What the plan assumed and what the tree held

The plan described the install path as "no checksum, no signature, no provenance". The tree already carried a checksum layer in both bootstraps (an env-var pin, a checksums file, a CWE-22 guard, and tests for match, mismatch, and traversal) and a `NEXUS_HUB_REF` override. Two gaps were real and larger than described: a tagged ref built a `refs/heads` URL, so a pinned install could not download at all, and a tag with no published checksum installed unverified after a warning. Phase 6 therefore extended the existing layer rather than replacing it, and the pre-existing seams (`NEXUS_HUB_EXPECTED_SHA256`, `NEXUS_HUB_CHECKSUMS`, `NEXUS_HUB_SKIP_CHECKSUM`) still work.

## Plan delta

**Disposition: Incomplete (non-blocking, resolved inside the phase).**

Evidence: the plan's premise ("no checksum, no signature, no provenance") understated what existed and missed the defect that mattered most (a tagged ref could not download). Its prescription still applied, so the phase extended the existing layer. Two of the plan's asks are recorded honestly rather than claimed: the dry-run install "on both a POSIX host and Windows" ran the Windows leg through the parametrized suite and the POSIX leg only by hand under Git Bash on this Windows host (the suite's bash leg skips here by design; CI's ubuntu runner is the POSIX proof at publication), and the `workflow_dispatch` exercise of the scheduled watch and the attestation job can only be observed remotely after the branch merges and a tag is cut, so it is recorded as `MT-1` for Phase 7's publication and the next `/update release`.

Consequence for remaining phases: Phase 7's CI/CD reconciliation must compare the two changed workflow files against the canonical contract (this phase is the one permitted to change them) and confirm the required set is unchanged; `/update release` for v4.7.0 will be the first run of `publish-artifact`, and the round-trip step should verify the published `SHA256SUMS` against the downloaded tarball in addition to the manifest check.
