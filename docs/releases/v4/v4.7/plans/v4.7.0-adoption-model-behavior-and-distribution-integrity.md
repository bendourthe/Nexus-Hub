**Goal**: Nexus-Hub's routing data names the models that actually exist, the vendor-documented behavioral rules that govern autonomous long-horizon work are distributed to every substantive instruction template with a mechanical guard proving they stay distributed, the skills that summarize sources and emit large deliverables carry the specific guidance their failure modes call for, agent reliability is expressed as a measured metric rather than a pass or fail, and a user installing Nexis-Hub can verify that what they downloaded is what the project published.

## Overview

This plan operationalizes two comparison reports that share an adoption target and one underlying theme. Both concern the integrity of what Nexus-Hub distributes: the first that the behavioral guidance it ships matches what the current frontier model actually does, the second that the artifact carrying that guidance can be verified and pinned. They are sequenced in one release because both are catalog, template, installer, and CI work with no shared runtime, so each track verifies independently and the two integrate once. This mirrors the v4.5.0 precedent, where one release absorbed two unrelated comparison reports on the same grounds.

**Track A (phases 1 to 5), distributed model-behavior guidance.** The finding that drove this is not that a rule was written badly, it is that the rules were never written at all. A grep for all sixteen techniques Anthropic documents for its current frontier model across `templates/ai-instructions/` returns zero files. Nexus-Hub's entire product is always-loaded behavioral guidance for roughly twenty platforms, so the vendor's own measured list of behavioral differences is not adjacent material, it is the same artifact class written by the party holding the measurements. Phase 1 comes first because it is a correctness fix rather than an addition: the routing map currently names `claude-fable-5`, which the vendor's model overview now lists under legacy, so every phase recommendation in every plan resolves to a superseded model. Phases 2 through 5 then distribute the behavioral rules in descending blast-radius order, templates first while the reconciliation decisions are fresh, then the skills whose specific failure modes the guidance addresses.

**Track B (phase 6), distribution integrity.** Nexus-Hub installs by downloading a branch tarball into `~/.nexus-hub/src` with no checksum, no signature, and no provenance attestation, and it always installs tip-of-branch with no pinned-version or rollback path. The compared project closes both gaps, and does so through mechanisms Nexus-Hub can reach without adopting a package registry: GitHub-native artifact attestation using permissions the repository already holds, and a scheduled advisory watch using tooling already present in CI. Phase 6 is sequenced last within the implementation phases because it is the only track that touches the installer and the pipeline, which is where a defect is most visible and where the required-checks trap described below lives.

**What this plan does not do.** It creates no new skill, adds no MCP registry entry, introduces no runtime dependency, adds no credential, and makes no new outbound call. Every finding has an owner among existing templates, skills, installers, or workflows. Six candidates were classified `drop-outright` in the two reports and are not implemented here: the vendor-coupled compute skills and sponsored bridge, third-party AI review services, command-surface expansion, hook dispatcher consolidation, documentation localization, and the vision container. Two further items are deliberately excluded from scope: per-skill presentation metadata (report item E6, scored P3 with no known host that renders it) and reusable `workflow_call` CI factoring (E5, a refactor of working CI whose only benefit is maintainer ergonomics and which carries the required-context risk described in phase 6). Both are recorded as known gaps in the final phase rather than silently dropped.

**Two writing items are deliberately absent.** The Fable report's items A5 (mannered prose) and A6 (formatting in chat) target v4.5.0, not this release, because the open v4.5.0 plan is already authoring an always-on writing-discipline block across the same twelve templates. Folding them here would mean a second cross-template edit of one block in two releases. They are being added to v4.5.0 phases 1 and 3 in the same pass that produced this plan.

**Prior known-gaps ingest.** `docs/releases/v4/v4.4/known-gaps.md` carries two open items. `DF-1` (three platform entries using text treatments pending distributable vendor marks) is guide-specific and out of scope here; it stays owned by the v4.4 ledger and is carried forward unchanged. `WN-1` is directly relevant and is folded into this plan: it records that a phase ran one tier below its recommendation because Claude Code cannot switch models programmatically, and its suggested next step is to re-surface the tier recommendation at every subsequent phase pre-flight. Every phase in this plan therefore states its tier and effort in both the glance table and its own fields, and phase 1's correction of the map is what makes those recommendations resolve to a real model in the first place.

### Sub-tasks

#### 2.1 -- decision: where is the boundary between autonomous operation and Consequential Decisions?

**Objective**: Resolve the one real conflict in the Fable report before any template is edited, so the two rules ship as one boundary rather than as two instructions the agent reconciles at runtime.

`## Consequential Decisions` requires a plain-language walkthrough before asking the user to approve anything that changes security posture, deletes or overwrites data, changes distributed or user-facing behavior, or expands scope. The vendor's autonomous-operation block instructs the agent not to ask permission for work the original request already covered, stopping only for destructive actions or genuine scope changes. These are reconcilable, because both draw the line at destructive and scope-changing actions, but shipping both texts unreconciled leaves the agent to infer the boundary.

**Options**: (a) state the boundary once inside the new block and have `## Consequential Decisions` reference it; (b) keep both sections and add one explicit precedence sentence naming which governs when they disagree; (c) fold `## Consequential Decisions` into the new block entirely.

**What would settle it**: The maintainer's choice, informed by whether `## Consequential Decisions` is load-bearing as a separately citable section. It is referenced by name from the org-knowledge layer, which argues against (c).

**Unblocks**: 2.2, 2.3, and 2.4.

**Prompt**:
