## The CI-profile discrepancy, and why it was not accepted as a failure

The canonical profile run reported `6 failed, 3833 passed`, all six in `tests/installer/test_core_settings_seeding.py` PowerShell variants. That number is not in the evidence block as a failure, and the reason is recorded rather than quietly dropped.

Those tests seed a settings file and compare it byte-for-byte. The profile run's `repo-tests` group spanned 16:33 to 17:30, and the interrupted installer executions described below were concurrently writing the same platform settings files between 17:04 and 17:15. That is a direct and sufficient explanation, so it was tested rather than assumed: re-running the identical tree with nothing else mutating configuration returned `458 passed, 36 skipped`. The failures were self-inflicted contention, not a code defect.

## The blocking defect: an ineffective installer sandbox

Task 7.5 requires a real installer execution on the current host. Running the real installer against live configuration was judged too invasive to do unasked, so it was run with `HOME` redirected to a scratch directory.

**That isolation did not work**, and the failure mode is the lesson. `$HOME/.nexus-hub` honored the override and landed in the sandbox, which made the run look isolated. But the per-platform integration paths are resolved in Python through `expanduser`, which on Windows reads `USERPROFILE` and ignores `HOME` entirely. Every platform write therefore went to the real user profile. Redirecting one environment variable is not a sandbox when two different resolution mechanisms are in play.

The runs were then interrupted by tool timeouts, so the result is a partial install. Uneven skill counts across `~/.claude` (352), `~/.codex` (370), `~/.gemini` (373), `~/.cursor` (351), and `~/.qwen` (350) are the evidence; a complete install produces consistent counts. Two orphaned installer processes were still running when this was found and were terminated.

`~/.nexus-hub` was never written by these runs: it still reports VERSION 4.4.0 and `nexus-hub verify` returns PASS with 1835/1835 files matching the manifest. The repository working tree is unmodified, and no push, pull request, or remote CI run occurred.

The repair is one idempotent command reinstalling from that pristine hash-verified source tree. Attempting it automatically was refused by the host permission layer, which is why this phase stops at a recorded NO-GO instead of working around the refusal.
