## Why it was overlapping

Both figures drew their labels as SVG `<text>` inside a `0 0 540 300` viewBox. At a narrow column
the port names, the ring captions, and the caption strip were all positioned independently in that
coordinate space, so they collided with each other and with the rings. This is the same root cause
as the guardrails figure in Phase 2, and it has the same answer: nested elements cannot overlap
their own labels, because each ring sizes to its content and each label is an inline box.

## What one scene contains

The review's instruction was explicit: no need for two harness sections, define what a harness is
first, then illustrate what Nexus Hub adds. The merged scene does that in four movements.

1. **The structure.** Two nested rings with the model innermost. The platform ring carries its five
   ports (context, tools, permissions, execution, observations); the Nexus Hub ring carries its four
   (skills, hooks, gates, artifacts). Nesting is asserted geometrically, not by eye.
2. **The journey**, which is the movement the review asked for: prompt and material in from the
   operator, Nexus Hub loading matched procedures and gates, the platform harness assembling context
   and enforcing permissions, the model reasoning inside that loop, hooks checking each action while
   the verification pass repeats until the gate is met, and reviewed verified work coming out with
   the artifacts that record it. Six numbered stops, lit in order.
3. **The five claims**, unchanged, each still carrying the repository artifact behind it.
4. **The trail**, still reading platform-loop-alone before platform-loop-plus-Nexus-Hub.

Every honesty phrase the earlier scenes carried survived verbatim, including "does not replace the
model" and "only where the host exposes the registered event". Those were checked by assertion
rather than by memory.

## A regression this plan shipped, found here

Phase 4 removed the `fx-budget`, `fx-bar`, `fx-legend`, and `fx-key` rules. It counted four usages
of `fx-budget`, and read that as "the two boxes I am replacing". Two of the four were in the harness
trail. For four commits that comparison rendered with no border, no background, and no columns, and
nothing caught it because no test tied markup to style.

The lesson is exact: **a usage count cannot tell you where a class is used.** The fix is not just
the rebuild. This phase adds `test_every_class_used_in_foundations_has_a_style_rule`, which ties
every class in the Foundations markup to a declaration in the stylesheet, and it immediately found
one more gap: a Phase 7 wrapper with no rule, which now has one. A smaller instance of the same
oversight went with it, a narrow-width media query still naming a deleted rule.

## A vacuous test, made real

`test_harness_svg_text_stays_inside_its_viewbox` selected `.fx-hstack svg text`. With the SVG gone
it would have passed by matching nothing, which is worse than failing. It is now
`test_harness_text_stays_inside_its_own_box` and measures the glyph run of every leaf in the figure
against the element that owns it, at six widths. That is a stronger property than the one it
replaced, and it cannot pass vacuously while the figure exists.

## The intrinsic-width trap, for the third time in this plan

At 320px both rings sat 88px outside the scene and the document scrolled sideways. The cause was
`width: max-content` on the model box: an element sized to its content contributes its MAX-content
as the minimum of the `auto` grid track above it, so the whole figure grew to the longest sentence
inside it. This is the same defect as Phase 1's label inflation and Phase 5's `.fx-mat--row`
specificity miss, and it now has a standing rule in the README: bound the track with
`minmax(0, 1fr)` whenever a descendant is intrinsically sized.

## One subtitle too long for its own rule

The merged scene opened with a 66-character label, which cannot hold one line at 720px above the
15px floor, so it wrapped and `test_no_heading_wraps_from_720_upward` failed. The label was
shortened to 44 characters. Loosening a rule written three phases earlier to accommodate new copy
would have been the wrong repair.

## Three counts that legitimately changed

## A silent no-op in my own tooling

The per-phase ledger rows for phases 5 through 8 never reached the contract. The edit scripts used a
plain string replace with no assertion, so when an anchor did not match (a thousands comma written
differently), the call did nothing and reported nothing. Four rows were missing before an audit of
the file found it. Every substitution in this plan's scripts that carries an assertion behaved
correctly; the ones written without one are where the loss happened. The ledger has been rebuilt
from the measured file size at each phase close, and the rule is simple: **a replace without an
assertion is a wish, not an edit.**

## One splice bug worth recording

The first attempt at the merge computed both scene offsets, then replaced the stylesheet block, then
spliced with the offsets it had already computed. The stylesheet sits earlier in the file, so every
later index had shifted and half of the old scene survived the splice. An assertion that no retired
class remained caught it. Offsets into a string are invalidated by any earlier edit; the spans are
now recomputed immediately before the splice.
