## Overview

Keep the recognizable Home identity and light/dark palette, while replacing repeated benefit copy with one concrete demonstration. Rebuild Foundations as seven small, illustrated lessons that share an everyday example. Refine Training around a truthful action-to-evidence flow and retain the existing arcade as the hands-on coding example. Essential content is visible at rest; restrained motion explains state changes and can be replayed.

The plan has seven phases. Phase 2 carries the most implementation risk because the current visibility, heading-fitting, connector, and animation lifecycles interact. Phase 1 measures those paths before changes, and every later phase captures and inspects the actual revised interface. The deliverable remains one offline HTML file, with the existing external Training JSON maintained as its authoring source.

## Teaching and illustration storyboard

Use "Turn meeting notes into a status brief" as the shared non-technical example. Its artifacts are notes, a project summary, a brief, and a checklist. The existing arcade becomes the later coding example of the same method, not the prerequisite for understanding it. Illustrations use the guide's teal accent, neutral surfaces, restrained amber for missing evidence, consistent strokes, and visible text labels rather than unexplained symbols.

| Surface / question | Visible copy direction and example | Illustration and appropriate motion |
|---|---|---|
| Home: What does Nexus Hub add? | Proposed benefit: "Reusable workflows for the AI platform already in use". Supporting sentence: "Give an assistant clear procedures, project rules, and checks that leave evidence". Retain one install action and one Foundations action. | Preserve compact Nexus lockup and marks; place a small request -> procedure -> checked artifact scene beside the benefit on desktop and beneath it on mobile. Accent one transition once; do not float every element. |
| Model: What generates the response? | "A model is a trained system that uses learned patterns to generate an output from the current input". Separate training from use, and mention that fluent output can be wrong. Brain-with-learned-knowledge is an analogy, not a literal mechanism. | Small training inset ends at a fixed model. Main diagram: notes/request -> model -> brief. An adjacent next-text-token strip reveals three candidate continuations with explicitly illustrative probabilities, then extends the sentence. Do not generalize this text-generation diagram to every media model. |
| Tokens: What does the model process? | "Tokens are the pieces used to represent the input and output". One real, fixed tokenizer example with its tokenizer named in a caption; words and tokens differ. | A sentence segmented into readable chips, a selected chip linked to its span, and a labeled input/output budget bar. Static image-patch inset marked conceptual; no universal image token count. Reveal one added output chip without moving the paragraph. |
| Prompt engineering: What should happen? | Before: "Write a summary". After: "From these notes, write a status brief with decisions, owners, and due dates. Mark missing dates as unknown". | Compact before/after pair with three or four annotations tied directly to the improved prompt. Highlight objective, evidence boundary, and output format once; never erase the readable prompt during replay. |
| Context engineering: What information is needed now? | The same request gets relevant notes and the project summary, rather than unrelated old messages. Show that useful information includes instructions, selected evidence, conversation/tool results, and state. | A small document tray feeding a working-context window. Relevant documents fill labeled segments while unrelated material stays outside. One reserve for output; exact capacity remains illustrative. Tie one statement in the brief to its source. |
| Harness engineering: What surrounds the model? | "The harness organizes tools, context, state, and permissions around model calls". The platform provides a runtime; Nexus adds reusable procedures, rules, and evidence conventions on supported host surfaces. | Three compact nested layers with one distinct responsibility each: model, platform, Nexus. Alongside, the same task produces brief.md plus checks.md. One permission gate visibly blocks a prohibited write. No new proprietary runtime is implied. |
| Loop engineering: How does work improve and stop? | "Draft, check, fix, then stop when the evidence meets the goal". A brief initially misses an owner; the checker finds it; revision resolves it or marks it unknown. | Four-node loop, one concrete failed check, corrected artifact, then terminal success. Always show alternate stop branches: budget reached and needs human input. Max two illustrative attempts, explicit Replay; no endless spinning arrows. |
| Graph engineering: Who does which part, and how do results join? | "A graph makes work steps and their connections explicit". Extract decisions and extract dates independently, then combine and check the brief. Nodes may be tools, code, humans, or agents. | Four or five labeled nodes with a real fork and join; parallel branches share no mutable output, and the join waits for both. Include a small failed-branch state and a human approval endpoint. Note that one loop can be a graph and multiple agents are optional. |
| Training: What changed, and what proves it? | Start with "Observe a defect, guide a fix, inspect the proof". Map eight existing commands to Understand / Change / Verify without hiding them. Keep the simulation label visible. | Reuse game, assistant, and artifact panes; stage 1 highlights the defect, stage 2 the changed artifact, stage 3 the check. Expose one deterministic "Show the defect" action if existing controls cannot demonstrate it reliably. No live agent calls or real publication. |

No guaranteed platform-wide hook coverage without current local contract evidence.

### Pass/fail rules

1. No unintended horizontal document overflow, clipping, collisions, inaccessible controls, cropped diagram labels, or arrows crossing label text. Short navigation labels and command names remain intact; prose wraps naturally.
2. Use one visible title hierarchy across pages. Desktop lesson titles should normally fit one line through concise wording and adequate columns. Mobile may use two lines at the body/heading floor; never shrink headings to force a line or insert `<br>` for one screenshot width. Avoid isolated one-word heading tails by revising copy or available width.
3. Body copy stays approximately 45-75 characters per line on desktop. Do not solve long full-width paragraphs with tiny type. Diagram labels remain selectable text, normally >=14px; shortened labels replace squeezed paragraphs.
4. A meaningful diagram occupies its assigned area. No empty fixed-height panel reserved for an animation or unanswered terminal. Flag intra-lesson empty bands >96px on desktop or >64px on mobile unless they serve a documented reading boundary; inspect visually before deciding. Preserve deliberate breathing room and touch targets.
5. No dense paragraph disguised as a diagram, repeated definition in title/subtitle/caption/body, or multiple competing animations in the same viewport. One visual focal point and one main takeaway per lesson.
6. Reduced motion shows a complete static result with manual steps where needed. Animations that convey change have visible controls and no essential information available only while moving. No flashing, autoplay audio, or scroll hijacking.
7. Every captured image has an associated verdict: typography, wrapping, spacing, illustration semantics, contrast, and motion state. A defect stays open until a fresh capture proves its correction. Do not pad with cosmetic findings; include real "considered but rejected" candidates only.

### Performance acceptance protocol

Phase 1 records machine, browser/version, viewport, theme, motion preference, source hash, and three repeated runs of cold Home -> Foundations navigation, full Foundations scroll, resize, 20 route switches, and Training start/pause/exit. Capture long tasks, frame intervals during a defined ten-second scroll, layout/style/script time, and attributable timers/animation work. Use one warm-up, then compare medians; keep navigation, screenshots, and measurement windows separate so screenshot encoding does not contaminate timings. Add a 4x CPU-throttled diagnostic, clearly distinct from the normal reference run.

Proposed budgets on the fixed reference environment: route or control feedback within 200ms; p95 frame interval <=33ms during the defined scroll; no guide-attributed long task >100ms during normal interaction; no repeated layout observer cycle while idle. Phase 1 must report which budgets already pass and which fail. If lag is not reproduced, record that honestly and retain traces for diagnosis rather than claiming it is fixed. After changes, compare the identical workloads and require no >10% median regression in previously passing scenarios. On reduced motion or a hidden document, instructional animation timers/frames stop; offscreen scenes stop independently. The decorative constellation may remain subtly active on Home but should be static on reading-heavy Foundations and paused during active Training. Do not add a generic telemetry system to collect these numbers.
