# Harness Safety and Maintenance Workflows

Comparison of an agent SDK and a maintenance-automation case study against Nexus-Hub. For maintainers deciding which runtime-safety and job-control practices to add to existing skills; covers source screening, current coverage, residual gaps, security, queue placement, and acceptance evidence.

Date: 2026-11-13
Adoption target: v4.15.12
Target status: Confirmed for planning publication by the maintainer on 2026-11-13; no existing version moved or execution authorized.
Local baseline: `origin/develop` at `0ce5dc00cedb612ba33ee610f73974f9063e509a`.
Scope: Comparison and prioritized adoption proposal only. No runtime, distributed skill, connector, approval record, or pipeline changed.
Evidence: [Source and baseline receipt](v4.15.12-comparison-harness-safety-and-maintenance.evidence.json).

## Recommendation

Adapt five small capabilities into existing owners. Prioritize safe recovery after uncertain side effects, then checks at each lifecycle boundary. Extend the existing scheduled-triage recipe with job identity, ownership, and terminal outcomes. Treat remembered decisions as scoped advice and measure actual review effort using local records. Do not replace the harness, introduce a new orchestrator, or equate installed guidance with enforced isolation.

The clearest defect is existing advice in [lifecycle-hooks.md](../../../../../catalog/skills/ai-development/ai-agent-development/references/lifecycle-hooks.md): it groups timeouts and server errors under bounded retry without distinguishing reads from writes that may already have happened. A lost response is insufficient evidence that a mutation failed.

## Adoption Plan

Order follows the comparison policy: skill-native work first, then a local implementation only if evidence shows it is needed. Priority ranks within those buckets.

| Order | Candidate | Value / effort / priority | Owner and bounded change | Acceptance evidence |
|---|---|---|---|---|
| A1 | Safe retry and recovery contract | High / low / P0; skill-native | Target the transient-retry paragraph in `ai-agent-development/references/lifecycle-hooks.md`; cross-link loop state rather than creating a runner | Frozen cases: read retry succeeds; timed-out write remains unknown until status reconciliation; restart after committed write causes zero duplicate mutations; denial/cancellation survives resume; provider failover does not replay a write. |
| A2 | Lifecycle check matrix | High / medium / P1; skill-native | Extend the same reference or one linked focused reference; delegate redaction to egress-redaction and execution confinement to agent-execution-isolation | Before-tool rejection yields zero effects. Post-tool rejection records an already executed action and withholds the unsafe result without rerun. Output rejection does not silently rerun the turn. Missing enforcement capability is reported unsupported. |
| A3 | Bounded maintenance-job contract | Medium / medium / P2; skill-native | One optional reference linked from loop-engineering; reuse scope, caps, gates, traces, and task-readiness owners | Record owner, work class, source event ID, stable problem signature, repository/base, verification command, active job identity, review limit, and terminal disposition. Two triggers for one active problem cause one investigation; changed evidence can explicitly reopen it; unrelated similar problems remain distinct. |
| A4 | Scoped decision-reuse example | Medium / low / P1; skill-native | Reuse agent-memory and memory-substrate-contract; add a focused example linked by the maintenance recipe | Remembered advice carries source, owner, scope, date, and supersession/invalidation conditions. Changed owner, permission, schema, or repository context causes re-evaluation. A remembered approval never passes a new authorization gate. No live memory writes are part of this comparison. |
| A5 | Maintenance outcome measurements | Medium / medium / P2; re-full, conditional | Adapt product-pulse to supplied local outcome records after A3. Begin with manual records; add a parser only if existing reporting cannot answer the agreed questions | Fixture counts separate clean merge, merge after automated fix, merge after human edits, closed-without-PR, closed-unmerged, duplicate, nonreproducible, and already-fixed jobs. Report denominators, excluded jobs, unresolved jobs, elapsed/review time, and missing values. |

Indicative total: two to four focused engineering days for guidance, frozen behavior cases, and one local pilot, subject to predecessor refresh and host availability. This is an estimate, not a committed phase schedule. No five-VM fanout is required. Start with one known maintenance case, one replay/duplicate case, and one legitimate no-change outcome under existing cost and time limits.

The proving cases must drive a consuming agent or controlled fake-tool adapter and inspect observed effects. Tests that merely search for new words in a skill cannot prove recovery, deduplication, or decision safety. Fixture work and the pilot belong to a later implementation plan.

| Surface | External deployment implications | Proposed adoption |
|---|---|---|
| Dependencies/processes | S1 can add a native process, runtime packages, execution environments, and optional shared storage; S2 uses a managed orchestration platform | No added runtime dependency, scheduler, cloud worker, or MCP. Existing owners only. |
| Network/data | Model-provider requests and optional telemetry destinations; work tickets, chats, repository data, and production signals in S2 | Local fixtures and supplied exports only. Any later provider pilot requires declared destinations and the existing egress policy. |
| Credentials | Application-managed model credentials and optional sandbox/service credentials; connector credentials for managed workflows | None introduced. Keep real credentials outside model-readable files; do not equate in-memory storage with isolation from tools sharing the process. |
| Approval | Several S1 approval modes, including automatic review and review bypass; S2 retains engineer merge | Existing native authorization remains authoritative. Advice, imported history, summaries, model verdicts, and cached decisions cannot mint permission. |
| Isolation | Configured tool isolation differs from trusted callback execution | Name each actual boundary and unsupported path. Worktrees organize files; they do not enforce OS isolation. |
| Persistent artifacts | Traces, state, dedup signatures, and decision notes may contain sensitive data | Apply redaction before persistence; retain minimal identifiers. Never store raw secrets or untrusted instructions as reusable decisions. |

| Candidate | Risk | Main failure mode and mitigation |
|---|---|---|
| A1 | Low as guidance; high if a host ignores it | Duplicate mutations after lost acknowledgement. Require state inspection or established idempotency before retry. |
| A2 | Low as guidance | Treating a result block as undo. Record the effect separately and never retry merely to recover blocked output. |
| A3 | Medium | Duplicate jobs, false deduplication, or shared-file conflicts. Use scoped identities, explicit reopen reasons, one owner, and the existing isolation procedure. |
| A4 | Medium | Stale preference becomes authority. Preserve provenance, narrow scope, supersession, and fresh authorization. |
| A5 | Low | Metrics reward PR volume or hide reviewer effort. Preserve no-change outcomes, denominators, missing values, and effort measures. |

## Risks and Conflicts

- A1 changes a shared reference and therefore needs a regression for safe read retry as well as unsafe write replay. Removing all retries would be a behavior regression.
- A2 must reference the owning redaction and isolation skills rather than duplicate their policies. A boundary matrix describes enforcement requirements; it does not supply enforcement.
- A3 must preserve all current loop-schema fields and optionality. Do not make maintenance-specific fields mandatory for unrelated loops.
- A4 must stay inside the selected memory substrate's permissions. This task writes no memory and changes no existing approval.
- A5 starts from local records and can stop at a documented manual table. A new database, dashboard, exporter, daemon, or hosted analytics service is beyond the construction limit.
- No speed, cost, merge-rate, or clinical/security effectiveness improvement is claimed for Nexus-Hub from the sources' reported results.

## Considered but Rejected

Compaction engines, placeholder-credential brokers, generic multi-agent dispatch, and mandatory PR evidence were inspected as possible gaps. Existing owners and queued plans already address them; wholesale additions would duplicate scope. A managed factory, five-VM default, Rust SDK import, and new Slack/Linear wrappers were rejected because no residual requirement justifies their operational or data-access costs. Automatic merging and cached authorization were rejected because they conflict with existing authority boundaries.
