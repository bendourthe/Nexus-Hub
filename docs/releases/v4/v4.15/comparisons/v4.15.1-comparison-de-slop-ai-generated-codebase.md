# Comparison: De-Slopping an AI-Generated Codebase

**Source**: <https://www.builder.io/blog/de-slop-ai-generated-codebase> (Alice Moore, Builder.io, 2026-09-16)
**Source type**: Web article (insight extraction)
**Authored during**: v4.18 cycle
**Adoption target**: v4.15.1
**Date**: 2026-09-18

This comparison reads an article on removing AI-generated "slop" from a codebase against the Nexus-Hub catalog. The headline result is a high pre-existing coverage rate: seven of eleven recommendations are already implemented, one of them (the TypeScript defect catalog) almost line-for-line. Four gaps are genuine, all of them instruction-level, and all four are classified `skill-native` with no new dependency, outbound call, or credential.

### Missing (4)

| # | Insight (article section) | Gap |
|---|---|---|
| 8 | The deletion test: before accepting a new abstraction, name what existing code it lets you remove, and make before/after concrete ("Refactor when the same design keeps producing the mess") | `grep -ri "deletion test" catalog/` returns zero hits. `minimal-construction` rung 7 governs whether to write new code at all (pre-write); `over-engineering-review` emits a delete-list after the fact. Neither requires a PROPOSED abstraction to pay for itself in deletions. |
| 9 | Introducing a rule set on a dirty codebase: run without autofix, scope to one package, keep the output as a baseline, decide the disposition of existing findings before blocking work, keep batches explainable, drop rules that keep objecting to correct code ("How to introduce the rules without wrecking your codebase") | No skill owns this. `lint-repair-loop` explicitly routes it away in its When NOT to Use table: "Choose or design the lint / type-check config -> Configure the tool directly; this skill runs an existing config". The article's motivating figure is 41,280 warnings from one rule-set run. |
| 10 | Write the acceptance condition first, in terms of what the program must know or do afterward, so "the warning is gone" cannot become the acceptance test ("Tell the agent what the repair must accomplish") | `grep -ri "acceptance condition" catalog/skills/` returns zero hits. `verification-before-completion` owns freshness of evidence AFTER the work; nothing establishes the behavioral post-condition BEFORE the repair starts. |
| 11 | A gate that checks only changed files is a trap: pre-existing findings ride forever, and an unrelated touch drags unrelated repairs into the commit ("How to introduce the rules without wrecking your codebase") | Not stated anywhere. `pre-commit-checklist` sets up gates without warning about this scoping failure. |

## Risks and conflicts

| Item | Conflict or risk | Mitigation |
|---|---|---|
| 1. Acceptance condition | `verification-before-completion` owns completion claims and proving commands. A pre-repair gate could be read as restating its rule. | The two are distinct: one sets the post-condition BEFORE the work, the other requires fresh evidence AFTER it. State the handoff by name; do not restate the evidence rule. Per the AGENTS.md rule-ownership convention, exactly one skill owns each half. |
| 2. Deletion test | Three-way overlap between `minimal-construction`, `over-engineering-review`, and `code-simplification`. Adding the gate in the wrong place produces the same finding reported twice. | Apply the AGENTS.md tie-break: one skill decides WHEN a constraint applies, another owns MEASURING it. The deletion test is a pre-write decision rule, so `minimal-construction` owns it and the other two point at it. |
| 3. Rule-set adoption | Highest collision risk. Touches `lint-repair-loop`, `pre-commit-checklist`, and the v4.16.2 lint-contract owner. | Resolve ownership first, in writing, before any edit. If it becomes a new skill, it needs all three registry updates (`data/SKILL_INDEX.md`, `data/skills.json`, `data/marketplace.json`) per the AGENTS.md skill-registration rule. |
| All | `lint-repair-loop` is 70 lines and `minimal-construction` 142, both far under the 500-line target, so the size norm is not at risk. `AGENTS.md` sits at 8790 of a 9100-word ceiling that ratchets down. | Keep all added text inside the SKILL.md files. Do not add to `AGENTS.md`. |

## NOT recommended

| Item | Reason |
|---|---|
| Adopt the external Oxlint anti-slop rule package named in the article | Classified `re-full` and ALREADY reverse-engineered. `typed-boundary-hygiene` independently implements the same defect catalog (chained assertions, `as unknown as`, broad dictionary internals, widen-then-assert, module mocks). Adopting the package would add a third-party dependency to every consuming project's toolchain for capability the catalog already ships. The MCP Registry Policy reverse-engineer-first tier applies, and the Reverse-Engineering Attribution Rule keeps the upstream name out of distributed artifacts. |
| Ship a fixed numeric warning threshold (for example the article's 41,280) | A figure from one repository at one revision. A threshold that is not measured against the consuming project is a round number wearing a lab coat. The item-9 procedure teaches establishing a baseline, not importing someone else's. |
| Add a "slop score" or similar aggregate metric | Not in the article, and it would compress exactly the distinction the article insists on: which findings are local repairs, which are architectural questions, and which are correct code to leave alone. |
