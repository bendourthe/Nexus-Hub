# Comparison - CI Speed and Codebase Untangling

**Project:** Nexus-Hub
**Date:** 2026-11-06
**Baseline:** `origin/develop` at commit `73efff30b` (PR #618 merged)
Adoption target: v4.15.7
**Placement status:** User-confirmed on 2026-11-06. v4.15.5 is claimed by open PR #616 and v4.22.11 by open PR #604, so v4.15.7 is the first free slot after the v4.15.6 worktrees plan. The maintainer chose the early slot because every later plan pays the CI wait in its final phase.
**Scope:** Two-source comparison. The maintainer asked what Nexus-Hub can adopt to make CI/CD faster without losing coverage. Source 1 ideas are recorded here and handed to the queued v4.18.2 de-slop repair plan, also by maintainer decision. Catalog, workflows, and runtime behavior are unchanged by this report.

A code pull request on Nexus-Hub waits a median of about 50 minutes for CI (14 recent full runs). Machine wait is under 40 seconds per job and setup is about a minute, so the article's largest fix, faster third-party runners, would buy almost nothing here. Nearly all the time is test work, and the critical path is one Linux job that runs about 10,700 tests serially on one 4-core runner. Splitting that job across parallel runners, the pattern the repository already uses for its Windows and browser suites, should bring a pull request to about 34 minutes with no test removed. Sharding the two slowest Windows jobs next could reach roughly 25 minutes. Both figures are hypotheses until the latency audit (C2) measures them.

## Measured Baseline

Evidence was pulled with the maintainer's own `gh` from the 14 most recent successful full `ci.yml` runs (run IDs 41798494952 to 42270325948, 2026-11-04 to 2026-11-06). Docs-only pull requests finish in about 2 minutes, because the `changes` job already skips the test jobs for ignorable documentation (`.github/workflows/ci.yml:91`).

**Wall clock per run:** median 50 minutes, range 37 to 59 minutes.

**Per job (mean over 14 runs; queue = created to started, setup and work from step timings):**

| Job | Mean total | Queue | Main work step | Runner |
|---|---|---|---|---|
| `tests` | 47.8 min | 37 s | "Test profile groups" 2,826 s | `ubuntu-latest` |
| `tests-windows` | 33.8 min | 26 s | "Windows platform profile group" 1,994 s | `windows-latest` |
| `tests-windows-validators-2` | 29.6 min | 15 s | 1,747 s | `windows-latest` |
| `tests-windows-validators` | 22.6 min | 7 s | 1,321 s | `windows-latest` |
| `guide-render` (3 shards) | 19.5 min | 23 s | 1,092 s | `ubuntu-latest` |
| `tests-windows-installer-core` | 6.5 min | 28 s | 358 s | `windows-latest` |
| `tests-windows-installer` | 6.4 min | 18 s | 353 s | `windows-latest` |
| every other job | 3.1 min or less | 40 s or less | - | mixed |

The largest non-test step in any slow job is Chromium installation at 54 s per `guide-render` shard. Checkout is 11 to 13 s.

**Inside the `tests` job** (run 42270325948 report artifact `ci-test-reports`, `summary.json`): the 24 commands of the `tests` group run one after another (`scripts/ci/profiles.py:311`, `_pytest` at `:114` adds no parallel workers).

| Command | Tests | Duration |
|---|---|---|
| `hook-tests` (`catalog/hooks/tests`) | 3,243 passed | 1,421 s |
| `repo-tests-governance` | 4,271 passed | 872 s |
| `repo-tests-installer` | 873 passed | 522 s |
| `repo-tests-skills` | 2,288 passed | 92 s |
| 16 remaining commands plus `extension-tests` | - | under 300 s combined |

**Caches:** `gh cache list` shows the same `setup-python` pip keys and the 270 MB `ms-playwright-chromium-Linux-1.63.0` entry saved again for each pull request. `ci.yml` has no `push` trigger and `post-merge.yml` sets up Python without a cache, so no cache is ever written in the `develop` scope that every pull request could restore. This is the bug S2 section 6 describes. Its cost here is small (about 1 minute per guide shard, about 20 s per pip install), because setup is not where the time goes.

**Parallel workers today:** `tests-windows-installer`, `tests-windows-validators`, and `tests-windows-validators-2` set `PYTEST_ADDOPTS: "-p xdist -n 2 --dist loadfile"` (`ci.yml:421`, `:474`, `:519`). `tests/workflows/test_guide_render_serial_shards.py:89` forbids `pytest-xdist` anywhere else. The reason is recorded in `docs/releases/v4/v4.15/known-gaps.md:1003`: concurrent software-WebGL browser workers on one runner starve each other.

## Not Recommended and Considered but Rejected

| Inspected candidate | Decision and reason |
|---|---|
| Third-party runner fleets (K1) | Rejected. Measured queue is 40 s or less per job, so the gain is near zero. A vendor fleet would receive the full source and run fork pull-request code, a new third-party processor that is not intrinsic to this repository (MCP Registry Policy, bucket 5 by analogy; `cicd-architect` runner rules at `SKILL.md:155`). Reopen only if C2 shows median queue above 2 minutes. |
| Paid larger GitHub runners (K4, "buy cores") | Deferred. The repository is public, so standard runners cost nothing; larger runners are billed per minute. Parallel shards on free runners reach a similar wall clock. Reopen if C1, C3, and C4 leave the median above 25 minutes. |
| Faster linter or typechecker (K2, K3) | Not applicable; both run inside a 1.2 min job off the critical path. |
| Affected-only test selection with a nightly full run (K11) | Rejected for now. It trades pull-request coverage for a nightly run, which conflicts with the maintainer's "without losing" constraint and with `cicd-architect`'s rule that scheduled runs are only for outside-world drift (`SKILL.md:126`). `change_scope.py` already exists if this is reopened after C1 to C4. |
| Parallel workers on the Linux corpus | Deferred. Validators and installer already pass under `-n 2 --dist loadfile` on Windows, but enabling it on Linux needs a recorded change to the guard at `tests/workflows/test_guide_render_serial_shards.py:89`, and after C1 those groups are off the critical path. Hook tests have no parallel-worker evidence on either platform. |
| Raising Windows workers above 2 | Deferred. Measure with C2 first; S2 section 6 reports oversubscription causing a flaky test. |
| Deleting tests for speed | Rejected. S2's own audit of 20,000 cases found almost nothing to cut, and the time here is in process launches. |
| Disabling test isolation globally (K5 literal) | Rejected. Leaks state between files; per-file worker reuse is the safe analog and is already used. |
| Adopting S1 as a new standalone skill | Rejected. Its ideas extend existing cleanup skills; a parallel skill would restate rules those skills own. Handed to v4.18.2. |
