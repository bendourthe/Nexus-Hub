## Section 1: Executive Summary

Mods are Claude Code plugins whose behavior is TypeScript running inside Claude Code's engine. The architecture is a Koa-style middleware algebra over a single engine interface named `$`. The hook environment has no ambient filesystem or network access, but `$` exposes mediated filesystem, HTTP, and process capabilities. Validation can list capability calls; it does not prove the runtime paths, destinations, or effects of those calls.

**This comparison is not primarily an adoption opportunity. It is a contract-drift finding and a security finding.**

The contract drift is that `hooks.json` has gained a fifth hook type. Beside the four documented types (command, prompt, agent, http), it may now name a `modules` array pointing at a `.js`, `.ts`, `.jsx`, or `.tsx` file in the plugin's `hooks/` directory (Section 1). Nexus-Hub's living platform read-contract does not know this surface exists. Its freshness gate checks Nexus-Hub's own verified version, not per-entry vendor changes, so this comparison calls for a dated findings record and a separate positive presence test. At the original comparison snapshot, grepping `catalog/`, `docs/`, `guides/`, `scripts/`, and `configs/` for `function hook`, `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS`, and `mods` returned zero hits.

The security finding is the reason the `sec-default` built-in mod exists. Its stated purpose is to keep "an organization's classic hooks, prompt content, managed settings and tool policy out of reach of installed plugins", and it is seated outermost on machines with managed settings or for Team/Enterprise organizations unless managed plugin ordering says otherwise. Nexus-Hub currently has 36 shell hooks, 36 PowerShell siblings, and 7 Python hooks. The target profile for this finding is an individual installation without managed settings; the presence of installed third-party mods and their ordering must be checked before claiming an exposure on a particular machine.

**What Nexus-Hub should NOT do is build mods now.** The September 2026 source gated the surface behind `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1`, and the current [official Mods README](https://github.com/anthropics/claude-code/blob/main/mods/README.md) still declares hooks modules early access and changeable without notice. It is not stable public documentation with a version guarantee. Nexus-Hub's do-not-invent rule requires a fetched official vendor document with a `source_url` and a `verified` date before a platform lever enters `configs/platform-defaults.json`, and the v3.15.0 `.kimi/agent.yaml` incident is the standing precedent for lowering that bar. Mods also cut directly against the catalog's architecture: TypeScript runtime code distributed to roughly twenty platforms, of which exactly one can execute it, would fracture the five-template lockstep parity model into a two-tier catalog where Claude users get enforcement and everyone else gets advice.

**Recommended adoption: four items, all documentation or repo-internal checks, zero new outbound calls, zero new dependencies, zero new credentials, zero new third-party processors.** Three further items are deferred for a future review triggered by stable public documentation; removal of the opt-in gate separately triggers a new exposure review. Runtime mods and telemetry adoption are declined in this cycle.

## Section 5: Security and Reverse-Engineering Assessment (Step 5)

### 5.1 Threat model comparison

| Axis | Nexus-Hub today | If mods were adopted as a build target |
|---|---|---|
| New runtime dependencies | None added by this comparison | TypeScript toolchain, `tsconfig.json`, `claude plugin validate` in the release gate |
| Outbound-call destinations | None added | `$.http.fetch` can reach the host network unless administrator policy denies it; destinations depend on runtime arguments |
| Credentials / API keys | None added | No new key required by the Mod API itself; a mod can access capabilities granted to its session |
| Source code or prompts leaving the machine | None caused by this documentation comparison | Possible through mediated file reads and `$.http.fetch`; disabling `$.telemetry` alone does not prevent egress |
| New commercial relationship | None | None; Anthropic is already the platform vendor |
| Platform coupling | Catalog is platform-agnostic across roughly twenty platforms | Claude Code only; one of roughly twenty targets could execute the artifact |
| API stability | Markdown contracts, versioned by Nexus-Hub | Vendor-declared unstable, "may change between releases without notice" |

The deferred build risks are **platform coupling, declared instability, and mediated data egress**. The recommended documentation and test work adds no mod or outbound call.

## Section 8: Risks, Conflicts, and NOT Recommended (Step 7)

### Risks and conflicts for recommended items

- **A** touches `platform-contract-verification`, which participates in release checks. Its freshness gate compares `meta.verified_for_version` with Nexus-Hub's plugin version; it does not churn on Claude Code releases or observe findings-record entries. Mitigation: record `modules` as dated early-access findings, add a positive presence test, and do not promote it to a VERIFIED lever in `configs/platform-defaults.json` without stable public documentation.
- **B** is documentation about a third-party risk. It must describe the exposure without implying that Nexus-Hub can mitigate it, because on the target install profile (individual machine, no managed settings) Nexus-Hub cannot.
- **C** risks duplicating the v4.13.0 observability work. Mitigation is a single installed owner, selected against the v4.13.0 outcome, with pointers from non-owners.
- **D** adds vocabulary to a surface bound by five-template lockstep parity if it lands in a shared instruction block. Mitigation: place it in `AGENTS.md` and the settings reference, both repo-internal, not in `templates/ai-instructions/base-*.md`.

### Explicitly NOT recommended

| Item | Grounds |
|---|---|
| Ship TypeScript mods in the catalog now | The vendor declares the surface "may change between releases without notice" and gates it behind `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1`. The Nexus-Hub do-not-invent rule requires a fetched official vendor document before a platform behavior enters the distribution; the GitHub issue, the design PDF, and the official Mods README, which still labels hooks modules early access and changeable without notice, do not meet that bar for a stable contract. The v3.15.0 `.kimi/agent.yaml` fabrication is the standing precedent |
| Migrate existing classic hooks to function hooks | Would strand the other skill-bearing platforms. Classic hooks remain registered beside function hooks, but an earlier mod can return without `next(e)` and suppress an unmanaged classic hook for an event; migration would not solve that trust boundary |
| Adopt `$.telemetry` | `drop-outright`. Nexus-Hub is local-first and adds no analytics surface. The built-in mod "sends nothing when Claude Code analytics are off", but adopting it would make Nexus-Hub behavior depend on a vendor analytics setting the user controls elsewhere |
| Build item F or G in this cycle | Deferred. Stable public documentation triggers re-evaluation of E, F, and G even if the opt-in flag remains; removal of the flag separately triggers a fresh exposure review. Neither signal alone approves a runtime build; any future build needs a new plan and verified vendor contract |

### Answering the invoking request directly

The pasted use case was: "in the desktop app, hide sensitive values by default and reveal them on hover." That is a `ui.render` hook (Section 3.2) matching on a component with the `desktop` surface, rewriting props before continuing the chain. It is not achievable by any existing Nexus-Hub setting, skill, or classic hook, and the early-access Mods surface requires function hooks to be enabled. It is a legitimate future mod, and it is precisely the class of capability item F would cover. It is out of scope for v4.15.2 on the same instability grounds as F.
