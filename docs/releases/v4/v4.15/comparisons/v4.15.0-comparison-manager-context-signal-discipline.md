# Comparison: Manager-Context Agent and Signal Discipline

**Adoption target**: v4.15.0

**Authored**: 2026-09-17 (during the v4.16.2 authoring cycle, on branch `docs/v4.16.2-agent-tooling-and-subagent-cost`)

**Sources**: one article in three parts - a pasted summary plus the two Substack posts it links

**Source security verdict**: CLEAR (Step 1.5, recorded below)

**Scope decision**: signal discipline only. The people / 1:1 / manager-tracking half of the source is deliberately excluded as out of domain for a developer-tooling catalog. Confirmed with the user before authoring.

This comparison evaluates an engineering manager's agent-context system against Nexus-Hub. The system is not novel in its parts (scope files, a briefing prompt, a scheduled run). Its value is a single discipline Nexus-Hub already possesses but has scoped too narrowly: an explicit, enforceable contract for what an agent report is allowed to say. Nexus-Hub binds that contract to review skills only. The source applies it to every agent report, and that generalization is the adoption.

## Source security scan (Step 1.5)

Verdict: **CLEAR**. All three source texts were scanned before ingestion for prompt injection, embedded agent-directed instructions, obfuscated payloads, credential harvesting, destructive code, and supply-chain risk. None was found.

The sources do contain a large quantity of instruction-like text, because Part 2's subject matter is literally an agent prompt (`daily.md`). Every such passage was read as data describing a third party's prompt, never as an instruction to this agent, per [[prompt-injection-defense]]. No source directs the reading agent to take any action, access any resource, or alter any behavior. No code, dependency, or install step is distributed by any source.

### Evidence for each status

**I1 - Missing.** Nexus-Hub has several capture surfaces and no admission bar shared between them. [`catalog/skills/workflow/agent-memory/SKILL.md`](../../../../../catalog/skills/workflow/agent-memory/SKILL.md) says to record "only what should survive the session"; [`catalog/skills/workflow/continuous-learning/SKILL.md`](../../../../../catalog/skills/workflow/continuous-learning/SKILL.md) mints instincts on a confidence score; [`catalog/skills/workflow/solution-knowledge-base/SKILL.md`](../../../../../catalog/skills/workflow/solution-knowledge-base/SKILL.md) captures solved problems. Each states its own threshold in its own words. None states a testable one, and no two agree.

**I3 - Partially implemented.** [`catalog/skills/workflow/product-strategy/SKILL.md`](../../../../../catalog/skills/workflow/product-strategy/SKILL.md) declares the problem, approach, persona, metrics, and active tracks; [`catalog/skills/workflow/project-constitution/SKILL.md`](../../../../../catalog/skills/workflow/project-constitution/SKILL.md) declares MUST / SHOULD rules; per-version `known-gaps.md` files carry open concerns. The gap is that none of these is written to be read as a *search scope*. They tell an agent what the project is for. They do not tell it what to go look at.

**I5 - Partially implemented.** `docs/todos.md` (via [`dev-progress-tracker`](../../../../../catalog/skills/workflow/dev-progress-tracker/SKILL.md)) and the per-version `known-gaps.md` files (via [`known-gaps-tracker`](../../../../../catalog/skills/workflow/known-gaps-tracker/SKILL.md)) both carry tasks. Provenance back to the originating event is conventional, not required.

**I7 - Missing.** This is the structural idea in the source and it inverts the usual order. Nexus-Hub's retrieval skills filter after gathering: [`session-query`](../../../../../catalog/skills/workflow/session-query/SKILL.md) scans local session logs then narrows by topic, branch, or window; [`direct-corpus-interaction`](../../../../../catalog/skills/developer-experience/direct-corpus-interaction/SKILL.md) refines a hypothesis against a corpus. Loading a declared scope first is a different and cheaper contract, and nothing in the catalog specifies it.

**I8 - Partially implemented.** [`catalog/skills/business-product/product-pulse/SKILL.md`](../../../../../catalog/skills/business-product/product-pulse/SKILL.md) is the closest structural match in the catalog: a time-windowed, single-page report over four dimensions, computing deltas against the previous window and ending in a prioritized followups list. Its dimensions are product outcomes (usage, performance, errors, followups), not attention demands. It answers "how is the product doing", never "what needs you today". The session digest at `.nexus/context/last-session.md`, written by [`catalog/hooks/session-summary.sh`](../../../../../catalog/hooks/session-summary.sh) and read back by [`catalog/hooks/session-start.sh`](../../../../../catalog/hooks/session-start.sh), is the other partial: it is automatic and unattended, which is the hard part, but its content is branch, status, last five commits, and touched files. That is what moved, ranked by nothing.

**I10, I11, I15 - Partially implemented, and this is the central finding.** Nexus-Hub already owns this discipline. `AGENTS.md`, under "Review-output restraint", requires every review skill to carry a mode-based finding cap and a "Considered but Rejected" list, with the stated reason that "a thorough review that found little looks the same as a shallow one". [`catalog/skills/code-review/multi-agent-code-review/SKILL.md`](../../../../../catalog/skills/code-review/multi-agent-code-review/SKILL.md) is the canonical contract and is explicitly named as such. Severity tiers are likewise real but local: the review cluster uses its own, [`vulnerability-prioritization-with-ssvc`](../../../../../catalog/skills/security/vulnerability-prioritization-with-ssvc/SKILL.md) uses SSVC, [`technical-debt-analyzer`](../../../../../catalog/skills/developer-experience/technical-debt-analyzer/SKILL.md) uses SQALE. The convention exists, it works, and it stops at the review category boundary. Every other report-producing skill in the catalog - `product-pulse`, `session-query`, `analyze-codebase`, `plan-queue-assessment`, `skill-stocktake`, `commit-sweep`, `documentation-consistency` - is free to return everything it found.

**I12 - Missing.** No catalog skill states a cross-source deduplication rule. This matters most where it is least visible: an agent reading `docs/todos.md`, a version `known-gaps.md`, and an open plan's unchecked tasks will find the same deferred item three times and report it three times.

**I13 - Partially implemented.** `agent-memory` requires it outright ("every write must name a source"), and `context-pack-builder` requires every distilled fact to cite its source session and timestamp. Report-producing skills do not inherit the requirement.

**I14 - Implemented.** [`verification-before-completion`](../../../../../catalog/skills/workflow/verification-before-completion/SKILL.md) and [`functional-verification`](../../../../../catalog/skills/testing/functional-verification/SKILL.md) already require fresh evidence before any completion claim, which is a stronger rule than the source's.

**I17 - Not applicable by policy, not by absence.** [`catalog/skills/workflow/loop-engineering/SKILL.md`](../../../../../catalog/skills/workflow/loop-engineering/SKILL.md) states that "the loop driver remains the host platform's `/loop` or `/goal` command; Nexus-Hub references those commands and never reimplements them". The host already ships `/schedule` and `/loop`. A Nexus-Hub scheduler would duplicate a host surface the catalog has an explicit rule against duplicating.

P-tiers operate within each reverse-engineering bucket, not across buckets.

| Order | ID | Item | P | Effort | Target location |
|---|---|---|---|---|---|
| 1 | A1 | Promote "Review-output restraint" to a general reporting contract: every report-producing skill declares a finding cap bound to its depth mode, and lists what it inspected and did not report | P0 | Medium | `AGENTS.md` (rename and widen the existing section); the report-producing skills named in the evidence for I10 |
| 2 | A6 | Require every reported claim to name its source artifact | P0 | Low | Same section as A1 |
| 3 | A5 | Require one event reported once, with the duplicate sources named on the single entry | P1 | Low | Same section as A1 |
| 4 | A2 | State one save bar, in the source's testable three-part form, and have the capture skills cite it instead of restating their own | P1 | Medium | A shared statement in `AGENTS.md`, referenced from `agent-memory`, `continuous-learning`, `solution-knowledge-base`, `known-gaps-tracker` |
| 5 | A3 | Add scope-first retrieval as a named step in the briefing skill: read the declared scope before searching, never after | P1 | Low | Folded into A4's skill body |

A1 is first because it is the enabling item: A5, A6, and the output half of A4 are all clauses of the contract it establishes. Doing them separately would write the same rule in four places, which is precisely what the `AGENTS.md` rule-ownership convention forbids.

### Bucket 2: reverse-engineered local build

| Order | ID | Item | P | Effort | Target location |
|---|---|---|---|---|---|
| 6 | A4 | New skill `signal-briefing` (category `workflow`): produce a "what changed, why it matters, what needs attention, what next" briefing over local sources the user points it at, applying the A1 contract | P1 | Medium | `catalog/skills/workflow/signal-briefing/SKILL.md`, plus the three registry files per the AGENTS.md skill-registration rule |

A4 depends on A1 through A3 and is sequenced after them deliberately: written first, it would embed its own private copy of the reporting contract and become the fourth place the rule lives.

The skill body must carry three constraints by name, because each is a boundary a later contributor would plausibly cross without realizing it is a boundary:

- Sources are local files or already-connected host surfaces the user explicitly points the skill at. The skill never adds a connector, a credential, or an outbound destination. This mirrors the contract `product-pulse` already states.
- Scheduling is the host's. The skill documents that `/schedule` or `/loop` drives it and does not implement a scheduler, per `loop-engineering`.
- The briefing is zero-outbound. Anything leaving the machine is governed by [`egress-redaction`](../../../../../catalog/skills/security/egress-redaction/SKILL.md).

## Risks and conflicts (Step 7)

**A1 edits existing files, which is the higher-risk change class.** Widening the `AGENTS.md` section touches a document every agent working in this repository reads, and the affected skills are ones already in use. The mitigation is that the rule is not new - it is the existing review-cluster rule with its category qualifier removed, so the review skills themselves need no behavioral change.

**A1 must not collide with the rule-ownership convention.** `AGENTS.md` already names `multi-agent-code-review` as the canonical contract for review-output restraint. Widening the rule requires deciding who owns the general form. The recommended resolution is that `AGENTS.md` owns the general contract and `multi-agent-code-review` keeps ownership of the review-specific cap table, referencing the general rule rather than restating it.

**A2 risks flattening thresholds that are deliberately different.** `continuous-learning` scores confidence; `known-gaps-tracker` logs deferrals whether or not they are actionable. The save bar should be stated as a floor every surface clears, not as a replacement for each surface's own additional criteria.

**A4 risks becoming a connector feature.** The source's version reads Slack, Drive, GitHub, and email. That is the part a contributor will reach for first, and it is the part the MCP Registry Policy hard-no list and tier ordering exist to prevent. Naming the boundary in the skill body is the control.

**A3 has a quiet dependency.** Scope-first retrieval assumes a declared scope exists. A repository with no `STRATEGY.md` and no current `known-gaps.md` gives the briefing nothing to bound itself with. The skill must degrade to an explicit "no declared scope found" statement rather than silently falling back to scanning everything, which would reproduce the exact failure the source is about.

## NOT recommended

**A7 - connector-driven scanning of Slack, Google Drive, and email.** Dropped on policy grounds. The MCP Registry Policy decision tree reaches tier 4 (trusted vendor wrapper) only when the vendor is the intrinsic data destination, reverse-engineering is not viable, and the feature is extremely worth it. Here the destination is incidental (the manager's employer happens to use those tools), and the capability is reachable without any of them by pointing the skill at local exports. Tier 3 applies and the local build is A4. Nexus-Hub is a catalog installed onto other people's machines; shipping a registry entry that causes a stranger's agent to authenticate against their corporate Slack is a materially different act from one engineer wiring up their own.

**A8 - a Nexus-Hub scheduler.** Dropped on existing policy. `loop-engineering` states the driver stays with the host. The host ships `/schedule` and `/loop` today. Building a second one would create a surface the catalog would then have to keep working across every supported platform, to duplicate something already present on the platform that matters.

**A9 - Logseq output format, the Projects / People / Tasks / Misc node taxonomy, and person-scoped pages.** Dropped as out of domain, per the scope decision confirmed at the top of this report. The node taxonomy encodes a personal note-taking preference, the output format is one tool's linking syntax, and person-scoped tracking is manager tooling rather than developer tooling. The transferable part of all three - that reported items link back to a named entity - survives as A6.

## Summary

The source's genuine contribution is not its file layout and not its tooling. It is the observation that an agent report is only useful if the agent is contractually forbidden from padding it. Nexus-Hub reached the same conclusion independently and wrote it down in `AGENTS.md` under "Review-output restraint" - then scoped it to code review and left every other reporting skill in the catalog free to return everything it found. Generalizing that rule is the whole of the recommendation. The briefing skill is its first consumer, not its justification.
