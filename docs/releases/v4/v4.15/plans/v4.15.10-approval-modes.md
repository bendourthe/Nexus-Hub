# Plan -- Approval Modes

**Project**: Nexus-Hub
**Version**: v4.15.10
**Filename**: v4.15.10-approval-modes.md
**Slug**: approval-modes
**Plan Type**: Feature
**Created**: 2026-11-11
**Status**: queued
**Goal**: The checker asks for decisions with a short reply instead of a pasted code line, and a user picks one approval mode (`manual`, `auto`, or `full-auto`) in the Nexus Hub settings panel that decides both how often an `/implement` run asks and which permission posture the host tools use: `manual` asks for every decision, `auto` asks once at the start of a run and afterwards only for a fixed checker-verified list, and `full-auto` never asks and stops with a plain message where a fixed limit or an unplanned high-risk action is reached; a missing or invalid mode file is treated as `manual`, an agent-issued mode change is blocked by a guard on hosts that support hooks, and the documentation states plainly what the seal and the guard do not prevent.

## Overview

`/implement` runs ask for approval too often and in the hardest possible form. The checker defines twelve approval actions (`scripts/approval_page.py`), and its default render prints an exact line with a one-time code that the user must paste as a whole message. A friendlier path exists: `record render --question` accepts `Approve`, `Yes`, or `Continue`, and a run can continue automatically when the host session is in full access and a reviewed policy was adopted. Nothing lets the user choose between these, and the default output, one runbook step, and the pause instruction in `catalog/commands/implement.md` still produce paste lines. On 2026-11-11 the maintainer was asked for two pasted lines in twenty minutes (a resume, then an amendment that added five plans), and a plain "Continue" was refused. That incident is this plan's baseline.

Phase 1 removes the paste line as the normal interaction; it needs no stored setting and delivers most of the relief on its own. Phases 2 to 4 add one setting, `approvals`, with three values, shown in the settings panel. The mode table lives in one machine-readable file from which the checker's copy is generated. In every mode the fixed limits of a run stay fixed: no mode raises a spend cap, the re-push bound, or the deletion rule, and no mode changes the repository, remote, branch, tag, or version. Spend caps are displayed and not measured, because the checker has no record of money spent; the documentation and the panel say so instead of promising a stop. The same setting derives the existing `posture` control for host tools, so the user has one switch.

The security question is who set the mode. An agent runs as the user's own operating-system account: it can read the run secret that seals the mode file, and the settings engine's human-presence check has a recorded bypass (known gap DF-19). The plan therefore does three things and claims no more than they deliver. A hook guard blocks agent-issued mode changes and writes to the mode file and the secret on hosts that support hooks, and it does not step aside in full-access sessions. Where no such guard exists, `full-auto` is refused and the run behaves as `auto`. The seal detects hand edits and corruption; a missing or invalid file means `manual`; the mode is copied into the signed run record when a run starts, so a later weaker value waits for the next run. What remains possible is stated in the user documentation: a determined process running as the user, on a host without the guard or outside the guard's reach, can forge run state.

| D8 | Per-project override | Global only now | The override is recorded as a known gap with its design note: key by the repository's shared git directory so worktrees share one value. |
| D9 | Start of a run in `auto` | Ask once at start | `manual` and `auto` show the frozen limits and ask for one short reply. `full-auto` starts without asking, with baseline limits only; anything a plan declares above the baseline is refused with a stop. |
| D10 | High-risk actions in `full-auto` | Proceed if planned, else stop | A CI, permission, or secret change proceeds only when the approved plan named it with exact paths. Otherwise the run stops. A deletion outside the cleanup rule stops in every mode. |
| D11 | Spend caps | State it honestly | Caps are shown and not measured. Real spend measurement is a known gap. |
| D12 | Host value for `auto` | Native auto where proven | Claude Code gets its native `auto` permission mode if a fresh-session proof passes, `accept-edits` otherwise. The panel lists per tool what each mode changes and what cannot be set. |

Author's calls, made while applying the review findings. Each is open to correction at the confirmation step.

| ID | Call | Reason |
|---|---|---|
| A1 | The effective result is the strictest of the action row, the blocker-category row, the mode copied into the run record, and the current mode (`stop` over `ask` over `proceed`) | Removes the undefined case where an action says proceed and a category says stop, and closes mid-run weakening. |
| A2 | One authority function reads the mode table; full-access evidence becomes an input to it, not a separate gate | Avoids a third parallel authority mechanism, and makes `manual` hold even when a host is in full access. |
| A3 | `approvals` gets a `derives` field that runs a normal `posture` set inside the same lock and presence check | The catalog cannot map one control's values through another control's `value_map`; each write keeps one owning control. |
| A4 | The checker's copy of the table is generated from the JSON, with a `--check` step in the fast profile | The installed checker cannot read `docs/policy/`; a hand-copied security table drifts. |
| A5 | In `auto`, `permit-outputs` and `supplement-scope` proceed only when every path is already inside the approved write paths; otherwise they ask | Both accept agent-supplied paths and could widen publication. |
| A6 | An agent may pause a run; resuming a pause the user recorded asks in `manual` and `auto` and stops in `full-auto`; `retire` asks in `manual` and `auto` and stops in `full-auto` | Pausing is the safe direction. An agent must not undo a human pause or retire a narrower record. Rebinding a live, unpaused run to a new session proceeds in `auto` and `full-auto`. |
| A7 | An unflagged render never prints a paste line; with `--session auto` it prints the question without enabling short replies and tells the caller to pass the session id | Short replies need one explicit bound session; that rule was deliberate and stays. |
| A8 | Every stop message names the limit or action, says why it exists, and gives the one command that continues | A bare `STOPPED` leaves an unattended run with no next step. |
| A9 | On a fresh install the panel and `show` read "Auto (host tools not yet set)" with an apply action that needs a person | The installer has no presence proof, so it does not write host posture. |

## Phase 2: Mode Table, Guard, and Sealed Store

**Goal**: The mode table exists as reviewed data, a person can set the mode through the settings engine, a guard blocks agent-issued changes, and any script can read the effective mode with its reason.
**Prerequisites**: Phase 1; v4.15.8 merged to `develop`.
**Stability Gate**: `nexus-hub settings set approvals auto` succeeds only with human presence and writes a sealed `~/.nexus-hub/approvals.json`; `python ~/.nexus-hub/scripts/approval_mode.py show` prints the effective mode and reason; a deleted, hand-edited, replayed, or forged-but-unguarded file is covered by a named test that either fails closed to `manual` or is recorded against DF-19 as residual; the guard blocks an agent-issued set on both implementations.
**Verification Expectation**: In a throwaway `NEXUS_HUB_HOME`: set `auto` with a simulated panel token and observe the sealed file; delete the file and observe `manual (absent)`; edit one byte and observe `manual (seal-invalid)`; feed the guard a tool payload that runs `nexus-hub settings set approvals full-auto` with `permission_mode` `bypassPermissions` and observe exit 2 from both the `.sh` and the `.ps1`. Exercise through [[functional-verification]].
**Recommended model tier**: frontier
**Recommended effort level**: max
**Rationale**: A new trust boundary with a known bypass to close, hook parity on two shells, an exception to the full-access rule, and two installers.

### Sub-tasks

#### 2.1 -- decision: Mode Table
