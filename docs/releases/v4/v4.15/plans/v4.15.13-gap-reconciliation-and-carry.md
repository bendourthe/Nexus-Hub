## Overview

The v4.15 minor run cannot let v4.15.1 start publishing while the open items in `docs/releases/v4/v4.15/known-gaps.md` (section `## v4.15.0`) are neither resolved nor approved for deferral. The only native way to approve deferral is an `amend-minor` page that carries a `gap_migration` list, and that page must also add at least one new member plan. The maintainer decided on 2026-11-13 and 2026-11-14 that the added member should be a real plan that owns the carry work, not a placeholder.

This plan is that member. It was added to the v4.15 run by an amendment that also carries the gap-migration grants. Those grants, not this plan's implementation, are what let v4.15.1 start. Implementation of this plan itself happens at the minor close, after the other members have released, because only then is the set of items that remain open final.

Scope is the ledger as it stands on `develop` after PR #659 (`9e85ea87d`): 85 open `####` items under `## v4.15.0` / `### Open Items` (38 DF, 4 BG, 30 WN, 8 MT, 5 QG; BG-5, BG-6, BG-7, WN-31 and DF-39 are already resolved) plus the 34 open `### AR-1` to `### AR-34` items in the same file, 119 in all. By the checker's `sensitive()` rule only WN-29 is security or high-severity, so only WN-29 must be named individually in the grant.

No runtime code changes are expected. The write set is the two ledgers, one reconciliation document, this plan file, and `docs/todos.md` for the coordinator. If a re-check shows that closing an item needs a code or catalog change, that item is carried instead and the finding is recorded; this plan does not grow a fix.

## Goals First and Definition of Done

**Persona**: The maintainer closing the v4.15 minor, who needs a ledger that states for each deferred item what was re-checked, what was found, and why any remaining item waits.

**Problem**: 119 items carry forward-contract text written at different dates. Some are probably already satisfied by later work, and the rest wait on a vendor feature, a user credential, or a user decision. Without a per-item re-check the carry would copy stale claims into v4.16.0.

1. A1: All 119 items have a recorded re-check against current `develop`, using the item's own acceptance text and proving command. An item whose proving command cannot run because it is manual is recorded as not performable, never as passed.
2. A2: Every item that is already satisfied is marked resolved in place with its proving evidence, and the ledger's `Open items` header and Summary table agree with the remaining open count.
3. A3: Every remaining item has exactly one migration reason from `vendor-feature`, `user-credential`, or `user-deferred`, recorded in `docs/releases/v4/v4.15/development/v4.15.13-gap-reconciliation.md`. An item no allowed reason truthfully fits is not carried; it is reported to the maintainer as a blocker.
4. A4: WN-29 has an explicit disposition (resolved, or carried by name with its reason). The `sensitive()` scan over all 119 items is quoted, and any item it flags beyond WN-29 is named individually in the grant.
5. A5: At the minor close, each remaining item is migrated to the v4.16.0 ledger through `minor_close.py migrate`, with a `**Migrated from**: v4.15#<id>` entry, and the completion checker's `gaps.minor` reading for v4.15 shows no unapproved open item.
6. A6: The reconciliation table, the two ledgers, and the migrated entries agree item for item. No item is dropped, duplicated, or silently reworded.

## Scope and Construction Limit

In scope: `docs/releases/v4/v4.15/known-gaps.md`, `docs/releases/v4/v4.16/known-gaps.md` (created by the first migration if absent), `docs/releases/v4/v4.15/development/v4.15.13-gap-reconciliation.md`, this plan, its last-phase evidence file, and the `docs/todos.md` entry.

Out of scope: fixing any item that needs code, catalog, installer, hook, or CI changes; rewording item bodies; changing the checker or the migration helper; resolving an item without evidence; and any item whose owner is another still-open v4.15 member (it stays with that member).

construction-debt: Reuse `scripts/minor_close.py migrate`, the read-only ledger parser in `scripts/completion_minor.py`, and the `known-gaps-tracker` resolve and migrate procedures. Add no script, no parser, and no new ledger format. The reconciliation table is a Markdown table maintained by hand.

Failure handling: a re-check that cannot reach its evidence (offline, missing host, missing account) yields "not performable", which carries the item with its existing reason; it never yields "resolved". A migration the helper refuses is a finding to read, not to bypass; do not hand-edit a ledger to get around a refusal.
