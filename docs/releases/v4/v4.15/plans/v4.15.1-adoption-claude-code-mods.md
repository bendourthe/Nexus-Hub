## Overview

The seeding comparison read Anthropic's function-hooks architecture against Nexus-Hub and reached an unusual conclusion for an adoption plan: **build no mod.** Mods are Claude-Code-only TypeScript running inside the engine, gated behind `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1`, and declared "EARLY ACCESS: this surface may change between releases without notice". Distributing runtime code to user machines against that surface would fracture the five-template lockstep parity model into a two-tier catalog where Claude users get enforcement and the other nine skill-bearing platforms get advice. The two highest-value items are therefore not capabilities to build; they are a missing contract record and a live exposure to document.

The contract record is that `hooks.json` gained a fifth hook type. Beside command, prompt, agent, and http, it may now name a `modules` array pointing at a `.js`, `.ts`, `.jsx`, or `.tsx` hooks-module. Nexus-Hub's platform read-contract has no knowledge of the surface. The exposure is the reason Anthropic ships a `sec-default` mod at all: it fences an organization's classic hooks, prompt content, managed settings, and tool policy from installed plugins, and it seats outermost only on machines that have managed settings. Nexus-Hub installs 32 shell hooks, 32 PowerShell siblings, and 7 Python hooks onto individual developer machines, which by definition have none.

Everything here is documentation plus one repo-internal test. No new skill, so no registry edit. No new dependency, no new credential, no new outbound call, and nothing added to `templates/ai-instructions/`.

**What a seven-lens plan review corrected in this plan before it was approved.** The first draft claimed that recording an early-access surface would churn the release freshness gate, and built a three-option decision around avoiding that. Three lenses independently read `scripts/check_platform_contract_freshness.py` and established that it compares only `meta.verified_for_version` against `.claude-plugin/plugin.json`; it reads no per-entry data and makes no network call, so the gate keys on Nexus-Hub's own release cadence and cannot churn on a vendor release. The same script therefore could not have verified this plan's own deliverable either: it exits 0 with the entry absent. Both defects are corrected below, and the representation question is settled rather than deferred, because the repository already has an idiom for exactly this case (four dated blocks labelled "findings record only; NOT consumed by any guard").

#### 1.2 -- Write the exposure advisory with its four accuracy bounds

**Objective**: State the exposure precisely enough that a reader can act, and no more strongly than the evidence supports.

**Build class**: load-bearing.

**Failure modes**: This sub-task produces security-classed prose consumed by a reader with no context. Malformed or absent input: if 1.1 could not verify the managed-settings answer, the advisory states the question as unresolved rather than choosing a side. Unreachable or slow dependency: the advisory makes no runtime call, so it cannot fail at read time; its risk is staleness, which the Phase 3 re-check step addresses. Conflicting operations: if this advisory and the Phase 3 findings record disagree about the surface's status, the dated findings record is authoritative and the advisory links to it rather than restating the date.

**Prompt**:
> Read the comparison Sections 1 and 3 (insights I2, I6, I9, I17) and `guides/ORG_KNOWLEDGE_LAYER.md`. Write the advisory into `guides/ORG_KNOWLEDGE_LAYER.md`, cross-referencing its existing "grants no enforcement authority" statement rather than contradicting it.
> Open with a two-column boundary statement before any risk language: Nexus-Hub hooks are separate operating-system processes the engine invokes, whose interface is stdin/stdout plus an exit code; a mod is in-engine TypeScript sharing the `$` interface with every other plugin. That asymmetry is the finding.
> The advisory MUST carry all four bounds:
> (a) PRECONDITION - the surface is gated behind `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1`, observed on Claude Code v267/v268. Leaving it unset closes the exposure entirely, and that is the one free mitigation this persona controls. Classify the exposure as prospective-under-early-access, not live.
> (b) BOUND - `$` is the only door; the hook environment has no ambient filesystem or network, so a mod does not edit hook files on disk. Its reach is the dispatch chain: observe events, rewrite payloads, or decline to call the continuation.
> (c) BOUND - command, prompt, agent, and http hooks keep running beside function hooks. This is interception risk, not automatic bypass.
> (d) ACTION - `claude plugin validate` enumerates a plugin's hooked events before any hook runs, and the `$`-only constraint is what makes those side effects statically determinable. Name it as the pre-install check. Do NOT write "install only trusted plugins" as the guidance; it names an outcome, not a method.
> Restate the ordering claim precisely: the prepend and append zones are admin-only and unreachable on an unmanaged machine, while among ordinary plugins order is dependency order and the earlier-registered hook wraps the later. Relative authority between two installed plugins is set by their dependency declarations, not by the user. Do not write "nothing seats above".
> Carry the 1.1 managed-settings answer. Do NOT imply Nexus-Hub mitigates this; it does not.
> Acceptance: all four bounds present; the string "install only trusted plugins" absent; no claim of Nexus-Hub-side mitigation.
