**Goal**: A dedicated read-only `/status` command reports implementation progress in the maintainer-approved full format without starting work or changing anything, `/update status` keeps working as a forwarding alias, and every message that ends while an `/implement` run is in progress carries the maintainer-approved compact status footer, with both formats defined once in a reference that costs no tokens outside an active run.

## Overview

Today the only progress report is `/update status`, and the maintainer finds that wrong because `/update` is a write command: its other scopes bump versions, commit, tag and publish. A read-only request should not live under a write command. The progress contract itself is sound (`catalog/skills/workflow/implement-phase/references/progress-reporting.md` already forbids starting work, changing files or run state, spawning workers and running tests), so the change is placement and presentation, not new behavior.

The plan makes three changes. First, the two approved formats (a compact footer and a full report) are written once in a new reference, `status-formats.md`, next to the progress contract, and the contract gains a footer rule: while an `/implement` run is in progress, every message that ends carries the compact footer, and the full report appears only on request or through `/status`. Second, a new `catalog/commands/status.md` dispatches to that contract with no logic of its own, and `/update status` becomes a one-line forward to it. Third, the headline command counts and cross-references that name the old entry point are reconciled.

Nothing is added to the always-loaded instruction templates (`templates/ai-instructions/`). The footer rule lives in `progress-reporting.md`, which an `/implement` run loads at start or resume, so it costs no tokens in any other session. Task counts reuse `scripts/plan_status.py --plan`, which the contract already names; no new script is written. No CI or workflow file changes, so no phase touches `.github/workflows/`.

## Format Specification

This section is the specification. The maintainer approved both formats verbatim on 2026-11-12 after several iterations, and the approval note lives outside the repository, so the plan reproduces it fully; an implementer works from this section and the worked examples below, never from memory.

### Compact footer

1. Emit it at the end of every message that ends while a run is in progress, after a `---` rule. It is the default.
2. First line: bold `**Status: v<X.Y>**`, then a 10-segment bar and whole percent, then task counts, then remaining time, separated by `&nbsp;&nbsp;&nbsp;&nbsp;·&nbsp;&nbsp;&nbsp;&nbsp;` because Markdown collapses plain spaces.
3. `🙋 N decisions waiting:` and a bullet per decision, each titled so it stands alone (`#1 Approval-mode gap`). Omit the block when none are waiting.
4. `🔄 N running:` and a bullet per running item, linked to its page, with bar, percent and a short parenthetical (`(CodeQL fix)`). A final bullet may state a shared state such as `both stopped, waiting on decision #3`. Omit the block when nothing is running.
5. End with one italic pointer line: `*Full report: /status*`.

### Full report

1. Three sections, in order, each separated from the next by a `---` rule: Status Update, Waiting on you, Running now.
2. A `&nbsp;` paragraph precedes EVERY `---` rule (after the plan table and after the last decision's table), so both rules sit at the same distance from the table above.
3. Heading `## Status Update: v<X.Y> Implementation Progress`. No summary line under it; the Total row carries it.
4. One plan table with columns in this order: Version | Goals | Progress | Tasks | Elapsed | Remaining. No Status column.
5. Version is bold (`**v4.15.4**`). Goals are two short descriptive goals per plan, separated by an escaped pipe, `Goal 1 \| Goal 2`, in one cell, never extra rows (multi-row cells and `<br>` render badly).
6. Progress is a 10-segment bar of `▰` (done) and `▱` (not done) plus a whole percent, not in backticks. Filled segments are `floor(percent / 10)`. Tasks is `done/total`. The Total row is last with bold totals; its percent is summed checked over summed total, never an average of percents.
7. Dependencies go in Remaining, for example `~1.5 d (after v4.15.2)`.
8. No Timing section. State an estimate's basis only when it changes. Table border thickness is set by the chat renderer and cannot be styled from Markdown.
9. `## 🙋 Waiting on you` has, per decision in numeric order, a `### 1️⃣ Decision #1: <title>` heading (number emoji 1️⃣ 2️⃣ 3️⃣ and so on), then 1 to 3 bullets that explain it so it stands alone (never a bare "Decision #1"), then an options table with columns Option | What it means | Effect, with `A (recommended)` first and `B` after. No extra spacer between a decision's table and the next decision heading.
10. `## 🔄 Running now` is a table with columns Item | Progress | Tasks | State | Elapsed | Remaining. Item is linked to its page (for example the pull request checks URL). Progress is the bar plus percent. Tasks is done/total checks. Elapsed is measured from the run's start. Remaining comes from observed durations of the same job.
11. All three section headings sit at the same level (`##`).

### Measured data rule

Elapsed and Remaining come only from measured data: each plan's own commits on its plan branch (first commit time to now, or to the last commit when the plan is complete) and the run's observed per-task and per-release durations. A value without a measured source prints as `unknown`, never an estimate invented to fill the cell. Blocked time is reported separately from active time. The existing remaining-time rules in `progress-reporting.md` (ranges, dependency chain, no division by agent count) stand and supply the Remaining values.
