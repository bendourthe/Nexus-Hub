# Plan - Push-time repository size guard

**Project**: Nexus-Hub
**Version**: v4.15.0
**Slug**: push-size-guard
**Filename**: v4.15.0-push-size-guard.md
**Plan Type**: Feature / enhancement on an existing project
**Created**: 2026-09-11
**Status**: Authored 2026-09-11; implementation not started, 0/23 tasks and 0/5 phases complete.
**Goal**: Stop a large file reaching a git remote in the first place, on every machine and for every actor rather than only for the agent, because on the hosts Nexus-Hub users actually use the mistake is either permanent or expensive to undo.

## Overview

Pushing a large file is the rare software mistake with no cheap correction. Deleting the file in a later commit does not reclaim anything: the blob stays in history. Rewriting history reclaims it but changes every commit hash, which in a regulated repository means rewriting the audit trail. And on Bitbucket Cloud even a rewrite is insufficient, because objects pushed to a pull request are preserved server-side to render that pull request's diff after it closes; they are unreachable from any ref, absent from every clone, and removable only by Atlassian support.

That last case is the motivating instance, observed on 2026-09-10 in a consumer repository powered by this harness. The remote reported 2.4 GB against a 4 GB hard limit above which pushes are rejected. A complete clone of the same repository - every branch, every tag, full history - was 19.79 MiB. Atlassian confirmed the difference as preserved pull-request objects and offered two options: delete the stored pull requests, taking one to two weeks and multiple internal approvals because it alters customer data, or raise the ceiling to 8 GB. Deletion was declined because that repository's 21 CFR Part 11 documentation cites pull requests as the change-control evidence under section 11.10(k). The ceiling was raised instead, which defers the problem rather than solving it.

The single moment where the cost is still zero is immediately before the push. That is what this plan adds.

Nexus-Hub already ships `large-file-guard.{sh,ps1}`, and it does not cover this. It is a Claude Code `PreToolUse` hook on the `Write` tool, thresholded at 500 lines and 50 KB, and it is non-blocking by construction - its own header says "Non-blocking (always exits 0)". Four properties are wrong for this failure: it fires on a tool call rather than a push, its scale is kilobytes rather than megabytes, it advises rather than refuses, and it only observes what the agent writes. The realistic way two gigabytes accumulate is a human pushing a data capture, an archive, or a notebook with embedded outputs, none of which an agent-side hook ever sees. That hook keeps its own purpose - discouraging bloated source files - and this plan does not touch it.

## Goals First / Definition of Done

**Persona and problem**: A developer on a Nexus-Hub-powered project commits a file that is large by accident - a captured dataset, a build artifact, an archive, a notebook with embedded image output. Nothing between their keyboard and the remote objects to it. They discover the consequence weeks later as a quota warning, at which point the cheap fix no longer exists and the remaining options are a history rewrite or a vendor support ticket measured in weeks.

| ID | Observable completion condition |
|---|---|
| D1 | A push that would introduce a new blob above the configured threshold is refused with a non-zero exit, and the output names every offending path with its actual size and states the threshold that rejected it. The push does not proceed. |
| D2 | The guard inspects only the objects the push would ADD to the remote, computed from the ref updates git supplies on stdin, not the working tree and not the whole history. A push of already-pushed history passes, a first push of a new branch is bounded to commits the remote does not have, and a branch deletion is a no-op. |
| D3 | A push with nothing oversized produces no output and exits 0. A file tracked by Git LFS passes, because what is pushed is a pointer; this is asserted by test rather than assumed. |
| D4 | The bash and PowerShell implementations return the same verdict for the same repository state, proven by a shared fixture set rather than by inspection of the two sources. |
| D5 | Both installers install the hook through the existing `~/.git-templates/hooks` mechanism that `commit-msg` already uses, `scripts/check_installer_parity.py` passes, and a repository cloned after installation has the hook without any per-repository step. |
| D6 | The documentation states three limits plainly rather than implying enforcement: the hook is per-clone so existing clones need an explicit install step; `git push --no-verify` bypasses it; and a server-side `pre-receive` hook would be authoritative but Bitbucket Cloud does not offer them. It also states that this does not replace `large-file-guard` and why the two are separate. |
| D7 | The final evidence connects D1-D6 to real artifacts, proves the hook on both supported operating systems, demonstrates the escape hatch, and records all scoped validation and independent review results. |

**Definitions.** A *new blob* is a blob reachable from a pushed ref and not reachable from the corresponding remote ref. The *threshold* is a per-blob byte size, not a cumulative push size, because the failure being prevented is one oversized object and a cumulative limit would reject a legitimate large refactor. *Blocking* means a non-zero exit from the `pre-push` hook, which git honours by aborting the push.

**construction-debt: ceiling**: Two hook files (one per shell), one install routine added to each existing installer, one test module, and documentation added to an existing skill. **Excluded, each with its reason**:

- **A CI workflow template.** Nexus-Hub cannot enforce CI in a consumer repository, and shipping a workflow per provider (GitHub Actions, GitLab CI, Jenkins, Bitbucket Pipelines) is four artifacts to maintain for a backstop the user can write in five lines. The skill documents the check; it does not ship it.
- **History-rewrite tooling.** `filter-repo` and BFG already exist and are well documented. Wrapping them would imply Nexus-Hub endorses a rewrite as routine, which for a regulated repository it is not.
- **Git LFS migration.** A separate decision with its own quota and workflow consequences, and not required to prevent the failure.
- **Cumulative push-size limits, commit-count limits, or file-count limits.** None of them describe the failure being prevented.
- **Any claim that this reduces repository size.** It prevents future growth. It reclaims nothing already pushed, and the plan must not imply otherwise.

## Phase 2: The pre-push hook, both shells

**Goal**: Implement the guard so that it refuses the failure and nothing else.
**Prerequisites**: Phase 1 stable and locally committed.
**Stability Gate**: Both implementations refuse an oversized push, pass a clean push silently, and agree on every fixture.
**Verification Expectation**: A fixture suite driving real repositories with real pushes to a local bare remote, run against both implementations.
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: The object-set derivation has several edge cases that are individually easy and collectively the whole correctness of the hook, and a false refusal teaches bypassing.

### Sub-tasks

#### 2.1 - The bash implementation

- [ ] T005 [US2] Add the bash pre-push hook `catalog/hooks/pre-push`

**Objective**: The reference implementation of the contract.
**Build class**: load-bearing; it is the only thing standing between a mistake and a permanent cost.
**Failure modes**: A false refusal is worse than no hook, because the developer learns `--no-verify` and keeps using it. An unparseable stdin line, an unavailable `git`, or a missing remote ref must fail OPEN with a warning rather than blocking a legitimate push on a hook defect.

**Prompt**:

> Add `catalog/hooks/pre-push` following the conventions T003 recorded from `commit-msg`. Read ref updates from stdin. For each, skip deletions (local sha all zeros). Derive the added objects: when the remote sha is all zeros the branch is new, so bound the range with `git rev-list <local-sha> --not --remotes` rather than walking the whole branch; otherwise use `<remote-sha>..<local-sha>`. Feed the range through `git rev-list --objects` and `git cat-file --batch-check` to get blob sizes, and collect every blob at or above the threshold with its path. Refuse with exit 1 if any, printing each offending path, its human-readable size, the threshold, and the bypass instruction. Exit 0 silently otherwise. Honour the two environment variables T002 named. Fail open with a warning on any internal error. Keep it POSIX-compatible bash, stdlib and git only, no jq dependency.

- [ ] T006 [US2] Add the PowerShell pre-push hook `catalog/hooks/pre-push.ps1`

**Objective**: The same contract for Windows-native installs.

**Prompt**:

> Add `catalog/hooks/pre-push.ps1` implementing the identical contract, matching the repository's existing PowerShell hook conventions. Same stdin parsing, same range derivation, same thresholds, same messages, same exit codes, same fail-open behaviour. Do not diverge the message text between the two; the fixture suite will compare them.

#### 2.3 - Fixture suite

- [ ] T007 [US2] Add the fixture suite `tests/validators/test_pre_push_size_guard.py`
