## Overview

The v4.15.7 comparison measured 14 recent full CI runs. Machine wait and setup are small; nearly all time is test work. The critical path is the Linux `tests` job (47.8 minutes mean), which runs about 10,700 tests serially on one runner: `hook-tests` 1,421 s, `repo-tests-governance` 872 s, `repo-tests-installer` 522 s. Next come `tests-windows` (33.8 minutes), `tests-windows-validators-2` (29.6), `tests-windows-validators` (22.6), and `guide-render` (19.5).

The plan applies the comparison's recommendations in reverse-engineer-first order. Everything is local to the repository or the distributed skill catalog: no vendor, credential, dependency, or outbound call is added beyond the user's own `gh`. Phase 1 ships a latency audit in `cicd-architect` and records the baseline with it. Phases 2 and 3 (the Linux test matrix with a partition proof, and the Windows job split) moved on 2026-11-13 to a standalone CI pull request on branch `ci/split-slow-test-jobs` that ships before this plan. Optional Phase 4 adds an opt-in local pre-push fast gate, develop-scoped cache seeding, and a blobless checkout for the `changes` job. The final phase reconciles the pipeline, publishes once, and uses that first remote run as the after-measurement.

Optional Phase 4, if it ships, changes `.github/workflows/` files (and the moved Phases 2 and 3 change them in the standalone pull request). That placement follows the mid-plan sequencing rule because CI/CD is the phase's explicit deliverable; it does not supply sensitive-path write authority. No phase pushes, opens a pull request, or starts remote CI before the final phase, including to collect measurements.

## Goals First

**Target problem**: Every plan's final phase and every re-push waits about 50 minutes for CI, and agents spend that time idle or retrying.

**Persona**: The maintainer and the agents implementing queued Nexus-Hub plans; secondarily, Nexus-Hub users whose own pipelines `cicd-architect` reviews.

**Definition of Done**:

- `ci_latency_audit.py`, given the comparison's 14 run IDs, reproduces the comparison's per-job mean totals within 0.1 minute, and its output is the recorded baseline. It also runs successfully against a second repository the maintainer owns.
- Release gate: the first green attempt of the integration pull request's CI run reaches a terminal `ci-required` result in 30 minutes or less, measured by the audit script and quoted in the last-phase evidence. If a re-push was needed, the measured attempt is named. This plan does not deliver the speed-up, the standalone CI pull request does; a result above 30 minutes is recorded as a known gap against that pull request, not fixed here.
- Follow-up outcome (maintainer decision, 2026-11-06): the median `ci-required` time over the next 10 full-scope code pull requests is checked with the audit script and recorded. The plan records this as a dated known gap with an owner, because it cannot be observed inside the plan.
- Moved to the standalone CI pull request on `ci/split-slow-test-jobs` (2026-11-13), not delivered by this plan: a partition proof shows that, for every sharded root, the shard node-ID sets are pairwise disjoint and their union equals the unsharded collection, on every host the shards run on.
- `docs/policy/required-checks.json` is unchanged; no new job declares a `permissions:` block broader than the workflow's `contents: read`; every new `uses:` line is pinned to a 40-hex commit SHA.
- If Phase 4 ships: with the hook installed, a push carrying a deliberate fast-profile failure is refused locally within the measured per-host budget recorded in Phase 1, and `CONTRIBUTING.md` documents the install, the budget, the agent shell-timeout implication, and the `git push --no-verify` bypass.
- No test is deleted, skipped, or weakened to buy speed.
- Phase 4 is optional. Phase 1 is the required scope (Phases 2 and 3 moved to the standalone CI pull request) and reaches the Goal without it. Phase 4 may be deferred to a known gap with a stated reason, recorded by T020 with an owner and a next step. The final phase does not depend on any Phase 4 output. Before declaring a deferral, confirm against the completion contract how the completion checker counts the unticked Phase 4 tasks, and amend the plan if it requires the deferred tasks to move into the known gap.

#### 1.2 - Latency Audit Script

- [ ] T002 Implement the read-only CI latency audit catalog/skills/infrastructure/cicd-architect/scripts/ci_latency_audit.py

**Objective**: One stdlib-only command that splits each job into queue, setup, and work; names the critical-path job; and reports time to the gate and to the first failed job.

**Failure modes**: Malformed or absent input: an invalid `--repo` (must match `^[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+$`), a non-file-name `--workflow`, or a non-numeric run ID is refused before any call; a jobs payload missing timestamps or steps is reported per job as `incomplete` and excluded from statistics, never counted as zero; a non-GitHub repository gets a clear "only GitHub Actions is supported" message. Unreachable or slow dependency: `gh` missing, unauthenticated, rate-limited, or past its timeout exits nonzero with at most the first five lines of `gh` stderr, token-shaped strings masked, and a one-line remedy; it never falls back to unauthenticated HTTP. Conflicting operations: re-run attempts are keyed by run ID and attempt number so a retried run is not double-counted; skipped and cancelled jobs are listed separately; fork-triggered runs are excluded by default (`event` and `head_repository` recorded per run).

**Build class**: load-bearing.

**Prompt**:
> Create `catalog/skills/infrastructure/cicd-architect/scripts/ci_latency_audit.py` (stdlib only, Python 3.10+, `from __future__ import annotations`, full type hints, under 400 lines). Inputs: `--repo`, `--workflow <file>` with `--runs N`, or `--run-ids <id,...>`; `--from-json <dir>` for offline fixtures; `--conclusion success|failure|any` (default `success`); `--gate <job>`; `--include-forks`; `--json`; `--gh <path>`. No other options. Resolve `gh` once with `shutil.which` (or `--gh`), refuse a resolution inside the current directory or repository root, and call it with an absolute argv[0], an explicit argv list, `-X GET` with `-f` parameters (never a hand-built query string), a timeout, `GH_DEBUG` and `DEBUG` removed from the child environment, and on Windows `creationflags=getattr(subprocess, "CREATE_NO_WINDOW", 0)`. Route every call through one injectable runner function so tests never start a stub process. Per job: queue (`created_at` to `started_at`), work (the longest step), setup (other steps), total. Per run: wall clock to the `--gate` job's completion, time to the first failed job, and the critical-path job, defined as the non-aggregate job that finished last, where a job is aggregate if it is the gate or started after every other job but one had completed. Output mean, median, and max per job. Render Markdown with job and step names escaped (`|`, backticks, angle and square brackets), CR/LF collapsed, control and ANSI characters stripped, and names truncated to 80 characters. Follow the failure modes above. The script cannot import repository helpers, because it ships inside the skill.
