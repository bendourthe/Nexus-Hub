**Goal**: Establish one configurable, consistently enforced worktree location across Nexus-Hub projects; inventory every discoverable local linked worktree on this machine; safely move retained worktrees, remove approved completed worktrees, resolve every exception, and provide other agents with an accurate discovery and handoff prompt.

## Overview

Keep main repositories in their existing locations. Place new linked worktrees under `~/.worktrees/<repository-identity>/<worktree-name>`, with `%USERPROFILE%/.worktrees` as this machine's proposed default. A configured local root on another volume is supported. Neither the shared root nor its children are independent repository clones: linked worktrees still depend on their main repository's Git storage. Repository identity must distinguish separate clones with the same basename or remote, and worktree names must distinguish branches whose sanitized names collide.

Deliver a small repository-owned Python helper through the existing `nexus-hub` CLI and both installers, update the single owning skill and its consumers, and verify actual enforcement on supported platforms. Instructions alone are insufficient. Native worktree tools receive the resolved destination when supported; a tool that cannot honor it needs an explicit, visible exception. No claim of universal enforcement applies to arbitrary manual shells or hosts that do not execute Nexus-Hub checks.

This plan includes the actual migration and cleanup campaign on the current Windows machine, not just a migration guide. Other repositories' source code, releases, main checkouts, unrelated backups, and business behavior remain outside scope. Planning, plan publication, later implementation approval, installed adoption, and individual destructive actions retain their separate authority. No worktree is moved or deleted merely by approving this planning document.

## Goals First

**Target problem**: Parallel agents create worktrees in inconsistent sibling, vendor, and temporary folders; completed worktrees accumulate and active work becomes difficult to locate.

**Persona**: The maintainer and agents concurrently working across Nexus-Hub, algorithms, console-dev, rd-data-dev, and other local repositories.

**Definition of Done**:

- Every supported Nexus-Hub creation flow uses the same resolver; out-of-policy creation is refused on enforced surfaces, and unsupported surfaces are explicitly documented and tested as uncovered.
- Every accessible fixed local volume is covered by a resumable Git-metadata discovery pass. Access failures, excluded storage, unmounted volumes, and ambiguous ownership are reported, never silently treated as absence.
- Every discovered linked worktree has a verified final disposition: retained at its canonical destination, removed with approved preservation and merged evidence, or retained under an explicitly approved location exception. A pending move, unknown owner, unanswered deletion choice, inaccessible discovery region, or unresolved path binding prevents a full-machine completion claim.
- Moves preserve HEAD, branch or detached state, tracked edits, staged edits, untracked files, ignored files, submodule state, Git pointers, applicable native authority, and usable project behavior. Removals preserve unique local content and satisfy that repository's integration policy.
- The old project parents contain no displaced linked worktrees except approved exceptions; empty old containers are removed only after a fresh empty-directory check. Main repositories and recovery backups remain intact.
- A copy-ready agent notice and final old-to-new lookup are delivered locally. Other agents can find their worktree, acknowledge a handoff, and resume without recreating an old path.
- Repository validation, required integration checks, release evidence, installed delivery, machine receipts, and the native completion verdict cover their own scopes. A green package alone does not prove the machine migration finished.

## Policy and Command Contract

The proposed CLI is `nexus-hub worktree` with `path`, `create`, `list`, `audit`, and `migrate` actions; these actions do not exist yet. Freeze this contract in T001 before implementing its consumers. `path --repo <existing-checkout> --name <worktree-name> --json` resolves without writing; `create --repo <existing-checkout> --branch <branch> --base <commit> --name <worktree-name>` creates through that resolver; `list --repo <existing-checkout> --json` reports Git-registered paths and canonical destinations; `audit --machine --json --output <coverage-report>` reports discovery and unresolved findings. `migrate --dry-run --inventory <coverage-report> --manifest <new-file>` writes the exact proposal; `migrate --apply --manifest <reviewed-file> --expect-sha256 <reviewed-digest>` executes only that unchanged versioned manifest, matching the local approval receipt's digest and per-item authorities. A changed, malformed, stale, unsigned-by-applicable-authority, or wrong-schema proposal refuses before mutation. Use explicit terminal JSON status plus nonzero exit for refusal or partial/cannot-verify results; partial discovery is never exit-zero complete. Existing cleanup authority stays with `cleanup_merged.py`; do not build another branch-deletion policy.

Resolve the default from the OS user home plus `.worktrees`, or a trusted user-configured root / NEXUS_WORKTREE_ROOT override. Never read executable policy from a repository-controlled file or silently fall back to a sibling, vendor, temporary, network, or synchronized folder. Validate overrides before any mutation. Use short readable names plus collision-safe identity suffixes, Windows reserved-name and case rules, and a stable local repository identity rooted in Git's canonical common directory. Do not use basename or remote URL alone. Persist only the minimum local identity mapping needed to survive a supported main-repository relocation; refuse conflicting mappings rather than guessing.

Keep this root separate from `~/.nexus-hub`, tool-specific directories, and source repositories. Detect path traversal, symlink/junction escapes, nested repositories, case collisions, same-name branches, detached worktrees, path-length limits, disconnected volumes, and destinations owned by another Git common directory. Use explicit argv and the shared Windows process owner. No shell string assembly, force switches, broad recursive deletion, service, database, or new external dependency is needed.

Native-tool integrations must state whether they can set a destination and enforce it. Supported pre-tool guards check recognized mutating worktree operations; unknown compound mutations cannot be certified by a regex and must use the helper or stop. Unsupported hosts receive explicit guidance and an audit finding, never a false enforced label. This is organizational enforcement within supported Nexus-Hub surfaces, not an OS security boundary.

## Machine Scope and Preservation

Discovery must enumerate accessible fixed local volumes and configured development/user/vendor roots, inspect Git markers without executing repository code, and merge those findings with each common repository's NUL-delimited worktree registry. Avoid reparse cycles, record every skipped directory and permission failure, and distinguish independent main clones, bare recovery repositories, linked worktrees, nested repositories, transient fixture repositories, and plain backup folders. Scan exclusions are performance hints for an initial pass, not proof that an entire machine was covered. Require an explicit disposition for every uncovered region before claiming completion. Discovery never elevates privileges or mutates another user's files.

Inspection uses one trusted Git executable and a dedicated non-executing command profile: sanitize inherited Git overrides, disable repository-configured fsmonitor, hooks, external diff/text conversion and applicable filters/helpers, suppress optional writes, pagers, interactive prompts and network access, and retain safe ownership checks. Do not bypass ownership with safe.directory wildcards. Restrict inspection to a bounded command allowlist; malformed executable configuration is a finding, not something to run. Separate authorized creation and project smoke execution from metadata inspection. Bind every smoke command and its trusted source to the reviewed manifest. Hostile Git-configuration fixtures must prove that discovery and preservation checks launch no configured program and change no repository state.

Store full machine manifests, preservation packages, mappings, and receipts locally under the configured Nexus-Hub state directory, outside every removal target. Publish only sanitized aggregate evidence. Immediately before an action, revalidate repository identity, HEAD, working/index state, untracked and ignored inventory, destination ownership, manifest identity, owner acknowledgement, and process/lock observations. Absence of a detected process is not owner consent. Unknown, stale, or changing observations stop that item without marking it complete.

Move active work only after its agent checkpoints and acknowledges the handoff. Do not reset, stash, unlock, prune, or stop another session automatically. Preserve dirty/index/ignored bytes in place and in a verified preservation package. Use `git worktree move` where supported; design a separately reviewed preservation/recovery procedure for submodules or cross-volume moves rather than attempting force or Explorer moves. Signed runs use their owner's supported relocation procedure; never hand-edit run records or their signatures.

Delete a linked worktree only after its repository's merged-history/release conditions, unique-content preservation, and actual per-item authorization are satisfied. Detached worktrees require explicit ancestry and retained-content proof; detached does not mean disposable. Preserve main checkouts, all unresolved work, independent clones, and backup/release-evidence folders. The existing per-item decisions for check-minor-budget-qualified, develop-install-2ef94ca, and develop-install-8bc588e remain pending unless separately answered. Retain every existing cleanup KEEP protection and original idle/expiry policy. Any proposed change to that policy is out of scope.
