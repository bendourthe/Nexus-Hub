## Overview

This plan is the decision half of the comparison against OpenAI's "Rethinking skills and prompts for GPT-6 Astra". It builds no runtime capability. It answers whether one should exist.

That shape is the result of a seven-lens plan review of this document's own first draft, which returned one P0 and eight P1 findings against a version that went straight to building. Three of those findings changed the plan structurally. The scope and product lenses independently found the instruction-surface work unrelated to the runtime work and higher in user value, so it has moved to the companion plan `v4.15.0` and ships regardless of what this one decides. The product lens found the original pilot measured cost with no instrument for benefit, and that it ran after the code was already written, where an honest negative result competes against sunk cost. And the security and adversarial lenses found that the profile layer this plan would consume is not merely unconsumed but arguably unfit to consume, which is evidence about the decision rather than a task to work around.

**The P0, stated plainly, because it is the plan's most important input.** The `model-prompting-research` profile layer is populated by an agent reading third-party vendor web pages and extracting claims. Those claims are schema-valid, confidence-scored, adversarially refuted, and primary-source cited. None of that is a trust control: the content still originates outside this project and would terminate in the agent's context window on every turn. Nine of the seventy-two committed claims carry imperative harness-altering language, including one on `claude-opus-5` reading "so REMOVE explicit verification instructions and legacy harness verification scaffolding". Injecting that verbatim would instruct the agent to drop the scaffolding `[[verification-before-completion]]` exists to enforce. A quality gate was mistaken for a provenance gate, and Phase 1 exists partly to establish how much that finding actually bears on the verdict.

**What this plan does not do.** It adds no resolver, no schema field, no hook, no injected context, no dependency, no credential, and no outbound call. Its only new executable artifact is a throwaway prototype that is deleted inside the same phase that creates it. If the verdict is to build, the build is a separate future minor release authored against this plan's evidence; this plan does not pre-specify it, because pre-specifying it is what produced the build-by-default pressure the review found.

**Amendment scope (2026-11-13).** The paragraphs above describe the decision half (Phases 1, 2 and 3). The status work folded in on 2026-11-13 (Phases 2b to 2d) is separate: it adds one command file, one format reference, a footer rule in an existing reference, and one test. It still adds no resolver, schema field, hook, or injected context, no dependency, credential or outbound call, and no text to the always-loaded instruction templates. Section `Status Command and Progress Footer` below carries its scope and format specification.

**Relationship to v4.13.0.** The adjacent `v4.13.0-adoption-evidence-driven-agent-improvement.md` plan covers neighbouring ground (its Phase 5 is context fact freshness, its Phase 6 a bounded skill-trigger and context-loading pilot). This plan deliberately does not amend it. Task ids here begin at `T101`, and `v4.15.0` begins at `T201`, so all three plans can be fanned out to issues together without collision.

**Knowledge-base grounding.** No `docs/solutions/` store and no root `STRATEGY.md` exist. The product lens noted this is the second queued plan to record that absence and recommended running `[[product-strategy]]`; that recommendation is carried into Phase 3's known-gaps reconciliation rather than actioned here.

## Format Specification

This section is the specification. The maintainer approved both formats verbatim on 2026-11-12 after several iterations, and the approval note lives outside the repository, so the plan reproduces it fully; an implementer works from this section and the worked examples below, never from memory.

### Compact footer

1. Emit it at the end of every message that ends while a run is in progress, after a `---` rule. It is the default.
2. First line: bold `**Status: v<X.Y>**`, then a 10-segment bar and whole percent, then task counts, then the last released version (`last released v<X.Y.Z>`, or `none released yet`), then the number of versions still to release (`N versions left`; a plan folded into another counts as none), then remaining time, separated by `&nbsp;&nbsp;&nbsp;&nbsp;·&nbsp;&nbsp;&nbsp;&nbsp;` because Markdown collapses plain spaces. Remaining time shows a figure only when the measured data rule below supplies one; otherwise it reads `time left: not measured yet`.
3. `🙋 N decisions waiting:` and a bullet per decision, each titled so it stands alone (`#1 Approval-mode gap`). Omit the block when none are waiting.
4. `🔄 N running:` and a bullet per running item, linked to its page, with bar, percent and a short parenthetical (`(CodeQL fix)`). A final bullet may state a shared state such as `both stopped, waiting on decision #3`. Omit the block when nothing is running.
5. End with one italic pointer line: `*Full report: /status*`.
6. A message that asks the user for a new decision shows the full report, never the compact footer. The footer lists decisions only as a reminder of ones already asked, and never carries a decision that is being asked for the first time.
7. Decision numbers restart at 1 for each new batch of open decisions; they do not continue from decisions already answered, except that a still-open decision carried over keeps its number when renumbering would confuse a reference to it.

### Full report

1. Three sections, in order, each separated from the next by a `---` rule: Status Update, Waiting on you, Running now.
2. A `&nbsp;` paragraph precedes EVERY `---` rule (after the plan table and after the last decision's table), so both rules sit at the same distance from the table above.
3. Heading `## Status Update: v<X.Y> Implementation Progress`. No summary line under it; the Total row carries it.
4. One plan table with columns in this order: Version | Goals | Progress | Tasks | Elapsed | Remaining. No Status column.
5. Version is bold (`**v4.15.4**`). Goals are two short descriptive goals per plan, separated by an escaped pipe, `Goal 1 \| Goal 2`, in one cell, never extra rows (multi-row cells and `<br>` render badly).
6. Progress is a 10-segment bar of `▰` (done) and `▱` (not done) plus a whole percent, not in backticks. Filled segments are `floor(percent / 10)`. Tasks is `done/total`. The Total row is last with bold totals; its percent is summed checked over summed total, never an average of percents.
7. Dependencies go in Remaining, for example `~1.5 d (after v4.15.2)`.
8. No Timing section. State an estimate's basis only when it changes. Table border thickness is set by the chat renderer and cannot be styled from Markdown.
9. `## 🙋 Waiting on you` has, per decision in numeric order, a `### 1️⃣ Decision #1: <title>` heading (number emoji 1️⃣ 2️⃣ 3️⃣ and so on), then 1 to 3 bullets that explain it so it stands alone (never a bare "Decision #1"), then an options table with columns Option | What it means | Effect, with `A (recommended)` first and `B` after. No extra spacer between a decision's table and the next decision heading.
10. `## 🔄 Running now` is a table with columns Item | Progress | Tasks | State | Elapsed | Remaining. Item is linked to its page (for example the pull request checks URL). Progress is the bar plus percent. Tasks is done/total checks. Elapsed is measured from the run's start. Remaining comes from observed durations of the same job.
11. All three section headings sit at the same level (`##`).
12. A message that asks the user for a new decision shows the full report, never the compact footer. The `## 🙋 Waiting on you` section of that report carries the decision details and the options tables.
13. Decision numbers restart at 1 for each new batch of open decisions; they do not continue from decisions already answered, except that a still-open decision carried over keeps its number when renumbering would confuse a reference to it.

### Measured data rule

Elapsed and Remaining come only from measured data: each plan's own commits on its plan branch (first commit time to now, or to the last commit when the plan is complete) and the run's observed per-task and per-release durations. A value without a measured source prints as `unknown`, never an estimate invented to fill the cell. Blocked time is reported separately from active time. The existing remaining-time rules in `progress-reporting.md` (ranges, dependency chain, no division by agent count) stand and supply the Remaining values.

#### 1.2 -- Build, run, and delete the measurement prototype
