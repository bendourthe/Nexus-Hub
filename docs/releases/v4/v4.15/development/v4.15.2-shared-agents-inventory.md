# v4.15.2 Shared AGENTS.md Inventory

Summary: a section-by-section inventory of every integration that can write the project-root `AGENTS.md` or the project Claude instruction file, which content is universal, where platform-specific content lives, and which consumers migrate. Read this before changing `templates/ai-instructions/base-agents.md` or adding a root-writing integration.

**Version**: v4.15.2
**Method**: heading and line diffs of the `templates/ai-instructions/base-*.md` files against `base-codex.md`, plus a read of each integration's workspace write path in `scripts/lib/integrations/`.

## Universal content

`base-codex.md`, `base-cursor.md`, and `base-opencode.md` carry the same 22 sections (Tech Stack through User Attribution). Their diffs against each other are:

| Difference | Where | Class |
|---|---|---|
| `- Skills: \`.codex/skills/\``, `.cursor/skills/`, or `skills/` | Context References | Platform-specific pointer |
| One extra bullet ("Before a new investigation ...") present in Codex and Claude and absent from Cursor and OpenCode | Working Conventions | Universal; the shared body keeps it |

`base-agents.md` is `base-codex.md` with the skills line replaced by a shorter neutral one ("Skills: your tool's skills folder (auto-activated)"), so the shared body is 7 bytes smaller than the `base-codex.md` body it replaces at the project root (the plan's no-growth gate). `base-claude.md` has the same universal sections plus five Claude-only sections.

## Blocked migrations and the shared marker

Antigravity 2.0, OpenClaw, and the Windsurf root file write their own templates into the same marker block as the consumers. A workspace that installs one of them together with a consumer therefore has one managed body whose text depends on install order, which was already true before this plan. They are not consumers, so the teardown protection added to `MarkdownIntegration.teardown` (a block is kept while another integration still tracks the same file) applies to them too, which fixes the removal half of the problem. The content half stays open as a known gap with a named next step: give each a verified sidecar or global owner for its platform-specific text, then migrate it.

## No-loss check

For each migrated consumer the removed text is exactly one skills-folder line. The skills themselves are reached by each platform's native discovery path recorded in `docs/policy/platform-read-contracts.md`, and the global instruction file for Codex and OpenCode still carries the platform template. For Claude on the supported path, the Claude-only sections move to the sidecar verbatim (`claude_only_sections` extracts them from the rendered `base-claude.md`), so nothing is dropped; a test compares them with the template.
