# v4.15.7 Shard Measurements

Summary: the shard sets chosen for the Linux and Windows test jobs, the per-leg minutes that choice produced, the options it beat, and the one Windows job still above the 22-minute leg target. Read it before rebalancing a shard or adding a CI job. The Linux and Windows splits were delivered by standalone PR #650 (merge `c3c483d3b`), taken out of plan v4.15.7 so plans v4.15.1 to v4.15.6 would not pay the slower rounds first. This document records the decision and evidence that T005 and T010 ask for, measured after that merge.

## Evidence

- Method: `ci_latency_audit.py` (Phase 1) over 10 successful full-scope `ci.yml` pull-request runs after PR #650 (run IDs 43502582917, 43497533230, 43752195566, 43749029475, 43653349436, 43620079279, 43616141040, 43569062996, 43562106083, 43559108690; re-run attempts excluded by the script). Gate `ci-required`.
- Per-command times: the `summary.json` of the Windows report artifacts of runs 43752195566, 43749029475 and 43653349436 (three runs; values below are the range).
- Host caveat: these are CI-runner times, measured, not local estimates. The local per-file durations that T005 and T010 describe were not collected: during this run other sessions were executing `scripts/ci/run.py --profile full` and `pytest tests/skills` on the same workstation, and the plan requires a quiet machine, so local timings would not describe a CI runner. Per-file Windows evidence stays unavailable from CI as well, because only the hook shards write a JUnit file with test cases; the validator commands write none.

## Linux decision (T005)

Options considered against the rule that every leg, with about 1.5 minutes of setup, is predicted at 22 minutes or less and the fan-out stays within the 40-concurrent-job limit of the GitHub Pro plan:

| Option | Legs | Verdict |
|---|---|---|
| A. Plan option: four legs (hooks-heavy, hooks-rest, governance, installer plus remaining) | 4 | Rejected: `tests-hooks` already ran as its own Linux job with two legs, so a fourth leg would duplicate it. |
| C. Plan option: five legs, a separate skills leg | 5 | Rejected: `repo-tests-skills` takes about 92 s; its own runner would spend more on setup than on work. |
| Delivered by PR #650: `tests` = validators, governance and core legs; `tests-hooks` = heavy and rest legs | 5 | Chosen. |

Measured result (mean of the 10 runs, total job minutes including queue and setup):

| Leg | Mean | Median | Max | Within 22 min |
|---|---|---|---|---|
| tests (validators) | 15.2 | 16.0 | 17.8 | yes |
| tests (core, with extension tests) | 12.0 | 11.7 | 14.6 | yes |
| tests (governance) | 3.6 | 3.7 | 4.1 | yes |
| tests-hooks (heavy) | 11.6 | 11.0 | 14.7 | yes |
| tests-hooks (rest) | 11.1 | 11.4 | 13.0 | yes |

The former single `tests` job averaged 47.8 minutes; its slowest successor now averages 15.2. The heavy hook files are named once in `HOOK_HEAVY_FILES` (`test_hook_sibling_parity.py`, `test_git_guardrails.py`, `test_user_edit_guard.py`, `test_settings_guardrail_switches.py`); every other hook test file falls into the catch-all shard. Fan-out: 31 jobs per full run (counted from the audit table), under the 40-job limit with room for a parallel agent pull request. The decision record is `docs/decisions/implemented/tooling/2026-11-13-ci-test-shards-with-partition-proof.md`.

The Windows decision (T010) is recorded in Phase 3.
