## Classification and actionability

Every source claim has one row below. **D = 326** claims contain imperative or authoring directives that would change prompts, adapter configuration, or behavior if treated as instructions. **R = 31** are descriptive reference material. R means safe to retain as quoted data for review, never authorized to override active instructions or to execute. D is deliberately conservative and is not a claim that every directive is malicious. Source citation, confidence, schema validity, and reviewer agreement do not turn either category into trusted instruction.

The audit used a conservative action-verb pass plus explicit review of all 57 initially unmarked candidates; 26 of those needed D classification. Each row retains a 12-character SHA-256 of its exact claim text so the source identity is checkable without a new schema. API/transport wording occurs in 116 claims; prompt-authoring wording occurs in 194. These are overlapping transparent text tags, not exact runtime-actionability counts. No schema field defines runtime actionability or rank, so a semantic runtime selection is not derivable from these tags. No filter or injection mechanism was built.

The complete source exposes claim, source_url, confidence, scope, optional note and evidence_scope fields. The latter describes what the evidence supports; it is not permission to act. Claims are arrays without an explicit priority field. Selecting a bounded prefix therefore privileges authoring order, not a documented runtime ranking.

## Trust boundary and concrete hazards

The path is vendor page to agent extraction to bundled index to installer to optional on-demand reader. The proposed automatic final hop into prompt-time context does not exist. The existing bundled apply_prompting_edits.py is an authoring proposal/apply consumer, and references/model-profiles.md links generated Tier-3 mirrors for explicit on-demand reading. The accurate gap is absence of automatic prompt-time consumption, not absence of all consumers.

The existing claude-opus-5 claim 5 contains the instruction to "REMOVE explicit verification instructions and legacy harness verification scaffolding". It conflicts with Nexus-Hub's verification requirement if adopted as live instruction. Other D rows steer search, delegation, progress updates, thinking controls, or request parameters. A running agent cannot necessarily change its host's request transport, and a prompt-author recommendation is not a user instruction. These entries were inspected as untrusted audit data; none was followed.

Runtime consumption would require a separately approved design with an independently specified trust boundary, actionability semantics, selection basis, and retraction path. This evidence-only plan adds none of those mechanisms and does not weaken verification.
