## Why this source matters to this project

Nexus-Hub's core product is always-loaded behavioral guidance distributed into roughly twenty AI platforms. This document is the vendor's own list of sixteen behavioral differences in its current frontier model, each with the vendor's recommended prompt wording. It is therefore not adjacent to Nexus-Hub's product, it is the same category of artifact, written by the party holding the measurements.

A grep for every one of the sixteen techniques across `templates/ai-instructions/` returns zero files. The catalog covers some of the same ground in trigger-gated skills, which is a materially different property: a skill fires when the user asks for it, an instruction template binds every turn.

## Adoption target resolution (Step 6.5)

Numeric enumeration of `docs/releases/v*/v*/plans/`, parsing each directory into integer major and minor rather than sorting lexically, shows authored plans through v4.6, so the next free slot is v4.7.0. Note that `git status` reports the v4.5 and v4.6 trees as untracked at the time of writing: their plans exist on disk but are uncommitted, and are treated as occupying their slots because both are authored and one is marked APPROVED SCOPE. The target is deliberately split rather than defaulted, for one reason.

The open plan `docs/releases/v4/v4.5/plans/v4.5.0-anti-cliche-and-agent-security.md` is already building an always-on writing-discipline block across all twelve substantive instruction templates plus a mechanical parity guard (its phases 1 and 2), and extending the cliche catalog (phase 3). It is planned and not yet implemented. Two items in this report are the same shape as that work and touch the same twelve files. Routing them anywhere later would mean a second cross-template edit of the same block in a subsequent release.

- **v4.5.0** receives item A5 (writing density). It is content for a block that release is already authoring.
- **v4.7.0** receives the other sixteen items, including A6.

**Amended 2026-09-02, after reading the v4.5.0 plan.** A6 (formatting in chat) was initially routed to v4.5.0 alongside A5 and has been moved to v4.7.0 phase 4 sub-task 4.2. Two constraints in the target plan forced it. Its sub-task 1.1 carries a hard 14-line budget on the Writing Discipline block, and its stated failure modes reserve response structure to `## Communication Contract`, which that plan deliberately leaves untouched. A6 is a rule about when lists, headers, and bold are appropriate, which is response structure, so folding it into the Writing Discipline block would have violated that plan's own ownership boundary and created exactly the two-skills-one-concern duplication the rule-ownership requirement in `AGENTS.md` prohibits. The v4.7.0 plan's sub-task 4.2 already edits `## Communication Contract` across all twelve templates, so A6 lands there at no extra cost. A5's placement is unchanged, with its one-line class name in the v4.5.0 phase 1 block and its full vendor definition in the phase 3 reference file.

This source also independently corroborates the v4.5.0 plan's central architectural finding: the vendor's own remedy for prose quality is a system-prompt-level instruction, not a user-invoked tool.

## Step 7 -- Risks, conflicts, and items not recommended

### Conflicts with existing Nexus-Hub conventions

**A8 against `## Consequential Decisions` (real, manageable).** Nexus-Hub requires a plain-language walkthrough before asking the user to approve anything consequential. A8 instructs the agent not to ask permission for work already requested. These are reconcilable because A8 already carves out destructive actions and genuine scope changes, which is the same boundary `## Consequential Decisions` draws. The adoption must state that boundary once, in one place, rather than shipping both rules and leaving the agent to resolve them at runtime. Shipping A8 verbatim without that reconciliation is the largest risk in this report.

**A10 against `/test` (real, needs a decision).** `/test` drives coverage to a threshold with a 100 percent pass rate. A10 says to commit tests only where the task asks or the repository already keeps them, at roughly one focused test per stated behavior. A threshold-driven command and a restraint rule will contradict each other on the same task. The v4.7.0 plan must decide which governs when they disagree, and record that decision. Do not ship A10 into the templates while `/test` is unreconciled.

**A2 and A14 against `## Output Minimization` (mild).** Output Minimization suppresses verbose logs and summarizes long output. A2 asks for more mid-turn narration and A14 warns against re-drafting long deliverables. These operate on different things, tool-command output versus the agent's own prose, but the adopted wording should say so explicitly, because a reader applying Output Minimization to A2 would cancel it.

### Change-risk notes

- A8, A13, A6, A5, and A2 modify existing always-loaded files across twelve templates, the highest-blast-radius change class in this repository. All of them must pass `scripts/check_base_template_parity.py` and, for the seven non-lockstep templates, a dedicated validator in the pattern of `tests/validators/test_construction_discipline_rule.py`.
- A17 and A1 must not be hand-edited into derived artifacts. `configs/platform-defaults.json` is the single source, and `scripts/sync_platform_defaults.py --check` fails on drift.
- A17 carries a do-not-invent constraint: a `claude-fable-5-1` tier value may be written only from a fetched first-party page recording a `source_url` and a `verified` date, and the Mythos 5.1 availability question must be re-verified rather than inherited from the existing `claude-mythos-5` note.
- Every item in this report is additive instruction text with no rollback cost beyond reverting the file, except A12, which changes a shipped skill's asset pipeline.

### NOT recommended for adoption

| ID | Item | Grounds |
|---|---|---|
| A16 | Vision container with PIL / OpenCV, or a crop-and-enlarge tool | Classified `drop-outright` in Step 5.3. Nexus-Hub is a catalog and installer; it ships no agent runtime and so has nowhere to mount a container or register a crop tool. Adopting it would mean either adding a runtime dependency to a zero-dependency distribution or writing guidance for a harness the project does not control. The MCP Registry Policy dependency ceiling applies: the benefit is a capability the project does not claim, and the cost is a permanent cross-platform dependency. Revisit only if Nexus-Hub ever ships its own execution surface. |
| A3, A4 (mechanism half only) | The beta API delivery mechanisms: turn-scoped system messages (`mid-conversation-system-clear-at-2026-08-21`), `thinking.display` (`thinking-display-updates-2026-08-18`), and `thinking.block_binding` (`thinking-binding-controls-2026-08-01`) | The prompt content of A3 and A4 is recommended for adoption as guidance. Document them inside `claude-agent-sdk`, where an Anthropic-specific API detail belongs, and keep the templates provider-neutral. |
