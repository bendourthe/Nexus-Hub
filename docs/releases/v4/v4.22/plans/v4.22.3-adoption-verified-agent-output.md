## Goals First and Definition of Done

The target user is a maintainer who delegates multi-phase work to an agent and reviews only the integration pull request. The problems are: a phase that turns red to green by deleting, skipping, deselecting or loosening tests reads exactly like a real fix; the pull request arrives with no test plan, so the reviewer re-derives what was verified and never sees what was waived; an ad-hoc `git push` or `gh pr create` has no check at all; and memory growth has no documented gate. No `STRATEGY.md` or `docs/solutions/` exists at authoring; `AGENTS.md`, the existing owners and the seeding comparison are the available grounding.

**Enforcement reach, stated plainly.** M-A and M-B are runbook rules plus installed scripts: they reach every platform that runs `/implement`, enforced as far as the agent follows the runbook. M-C is a `PreToolUse` hook: it reaches only hosts that honor Claude-style hooks, and on other hosts the opt-in variable has no effect. Every gate here makes a weakening or an unchecked publication visible and inconvenient; none can stop an agent that deliberately edits files under `.git` or its own settings. That boundary is documented with each surface.

1. **Test integrity (M-A)**: On every frozen change-set fixture, the installed checker reports the canonical rule id and location; a clean diff, a same-root rename and a waived finding pass. Implement-phase Phase 7 runs it on every phase diff against the phase base the runbook recorded at phase entry, including untracked files; an unwaived finding or an exit 2 is NO-GO. A deleted test file, a lowered coverage threshold or narrowed test collection additionally needs a recorded `ask-first:test-weakening` approval. Run over the last 20 real phase commits in this repository that touch tests, the checker raises at most 2 findings a reviewer judges legitimate-without-waiver-needed, and the count is recorded.
2. **Pull request proof (M-B)**: The integration pull request body composed at implement-phase step 9F.4 contains a short How to Test with reviewer-runnable steps that quote the command, exit code and commit each claimed observation came from; links that resolve to the phase evidence files in the branch; a Test integrity section listing every waived finding or "none"; and demo captures only under the media rules. This plan's own integration pull request shows all four sections, checked in T025.
3. **Publication tripwire (M-C, cuttable)**: With `NEXUS_PREPUBLISH_CHECK` set to the check command, a publication through the Bash or PowerShell tool or a GitHub MCP tool is blocked unless a check receipt shows that exact command exited 0 on the content tree being published; a missing, malformed, mismatched or hand-edited receipt blocks; a fault the agent cannot cause (no git, unparseable hook input) reports UNGATED and allows; unset is a no-op; both siblings agree on every frozen case; and `/implement` with the mode set publishes without a second suite run. If cut, a known gap with a named target version.
4. **Resource metrics (M-D, cuttable)**: `performance-regression-gate` documents peak resident memory and a growth ratio across repeated runs; leak and growth fixtures are flagged by the existing `perf_baseline.py` and a clean fixture passes. If cut, a known gap.
5. **Delivery**: The final phase's evidence, handbook and installer gates, independent Goal review and local suite pass, and the checker's whole-plan run is clean or fully waived. Implementation ends only on the completion checker's terminal result and the approved green integration flow, not on these authored checkboxes.

**Canonical rule ids** (used by fixtures, the checker, waivers and the pull request section): `deleted-test`, `deleted-test-file`, `test-moved-out-of-collection`, `added-skip`, `added-focus`, `removed-assertion`, `loosened-assertion`, `removed-parametrize-case`, `widened-tolerance`, `narrowed-collection-config`, `lowered-coverage-threshold`, `ignored-test-failure`, and the advisory `expectation-without-source` (reported, never NO-GO, because pairing a test with its source is heuristic). Rules are data-driven: one table row per pattern and framework, so adding a framework is a row plus a fixture.

**Waiver format**: a fenced block tagged `test-integrity` in the phase sidecar `<version_dir>/development/<version>-phase-N-test-integrity.md`, one line per finding: `<rule> <path> <anchor> - <reason>`, where the anchor is the test symbol or, when there is none, the first 12 hex digits of the SHA-256 of the hunk text. Lines and line numbers are informational and never part of the match.
