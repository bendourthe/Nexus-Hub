## Goals First and Definition of Done

The primary user is a maintainer delegating app work to an agent and reviewing the result. The problem is unqualified confidence from partial checks: extracted memory may omit evidence, a guide may describe behavior the app no longer has, a small diff may still affect a sensitive path, and marketing or export instructions can manufacture proof or override a real design. Four existing owner clusters receive bounded guidance and observable acceptance cases.

1. **Memory**: Independently checked worksheets compare full context when it fits, lexical retrieval, model-directed raw search and extracted memory with equal evidence. Writer/reader, source revision, construction, updates, reuse, cached/uncached tokens, retries, latency and correctness remain distinct inputs. Reviewed M01-M04 examples correctly reject finite break-even for nonpositive query savings and show omitted-fact recovery only from an authorized raw source. These examples demonstrate a coherent procedure, not a deployed memory system or measured model behavior.
2. **Verification maintenance**: The v4.19.0 verification owner, if actually landed, gains only missing lifecycle rules: doctor after a failed drive, owned-instance recovery, evidence surviving cleanup, explicit unreachable prerequisites and app-regression versus guide-drift triage. Following the procedure on a real isolated fixture app proves that it is executable and preserves proof. The run does not demonstrate that an agent will choose or follow the procedure unprompted. Guide-only maintenance cannot repair a product or weaken its journey to get a pass.
3. **Review routing**: Existing review/gate owners explain sensitive and uncertain changes; independently reviewed R01-R03 worked outputs preserve checks, required review and approval. PR guidance and the repository template expose testing, risk and rollback. An unavailable eligible owner remains unresolved review. No classifier accuracy, measured agent-routing rate, GitHub setting or CODEOWNERS enforcement is claimed.
4. **Design intake**: A landing-page brief and independently reviewed D01-D03 examples capture audience, offer, intended action, objections, source-backed proof and constraints. Missing facts remain unknown; ordinary app screens do not receive a marketing formula. Any export text is conditional on a real predecessor gap; supplied source/reference judgments remain within existing design and accessibility owners. No generated production page, measured agent adherence or new renderer is part of this scope.
5. **Proof**: Protocol-first only: frozen synthetic worksheets, actual test-owned fixture-app actions, and independently reviewed sample outputs. Record the exact procedure, inputs, expected/observed result and review provenance. Do not launch automated/provider-backed agent trials or benchmarks, build a complete-workspace model adapter, or require trial spending/containment infrastructure. No measured agent-adherence, comparative improvement, cost-saving, statistical equivalence or live-agent containment claim can follow from these artifacts. Ordinary implementation/review assistance is separate from a controlled experiment and cannot be reported as one.
6. **Delivery**: +0 skills, +0 commands, +0 agents, +0 hooks, +0 MCP entries, +0 bundles, +0 production helper scripts and +0 runtime dependencies. Existing installers deliver linked references. Phase 1 proves an isolated baseline installation; Phase 2 installs the revised memory guidance, opens/parses it with its references and checks its worked examples. This is delivery/readability proof, not installed-agent behavioral proof. Native validators determine any coordinator-owned metadata delta.
7. **Closure**: Every phase verifies locally and ends with one local commit. The final phase owns complete native local validation, installer/handbook evidence, independent Goal review, bounded deep pass and one authorized integration publication. Green merged integration precedes release; draft creation and checked task boxes cannot establish completion.
