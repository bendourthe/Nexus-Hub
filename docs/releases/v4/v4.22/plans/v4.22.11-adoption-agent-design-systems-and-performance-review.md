## Overview

This plan adopts five candidates from the v4.22.11 comparison through existing owners. The performance half removes "add a caching layer" as a default remedy and adds a cache audit (A1), adds a performance rule-ownership table, makes `code-optimizer` always write a case-matched hotspot table before editing with an approval stop on review requests (A2), and ships a data-oriented-design reference under a real cut-line (A3). The design-system half adds one authoring reference under `frontend-ui-engineering` covering six layers (D1), a "read the project's design system first" step in `ui-component-generation`, and a tier-direction configuration in the existing lint contract that defers the rule to D1's owner (D2).

A fresh-agent behavioral gate, recorded before the changes (baseline) and after them (acceptance), proves agent behavior changed rather than only skill text. Phase 1 refreshes the baseline and confirms the D1 home; Phase 2 is the cache audit; Phase 3 is design-system authoring, which runs ahead of triage in the comparison's priority order; Phase 4 is triage, A3, and behavioral acceptance; Phase 5 is the mandatory final phase. No new skill, command, MCP entry, hook, script, or runtime dependency is created unless the Phase 1 decision escalates and the maintainer approves.

## Goals First and Definition of Done

**Problem and persona**: (a) A developer who asks an agent to "make it faster": the shipped `performance-review` skill lists "Add caching layer" as the remedy for repeated work, and no performance owner audits whether an existing cache hides a slow path. That text defect is observed; whether agents therefore add caches over slow designs is the hypothesis the Phase 1 baseline run tests. (b) A developer who wants agents to build UI matching the product: token linting and component generation exist, but no runbook turns design decisions into a system agents read, no skill fires on that request, and component generation does not look for an existing system.

**Must have**:

1. No performance owner presents adding a cache or memoization as the default remedy for repeated work. `performance-review` owns the redesign-first cache policy and a cache audit (each existing cache with key, invalidation, fronted path, and a redesign flag); `code-optimizer`, the checklist, and `performance-reviewer` cite that rule by name. The cache-correctness rows (TTL, invalidation, key collisions, tenant identity, stampede) keep their content.
2. A `performance-review` rule-ownership table names one owner per concern: cache policy and audit, triage case table, applying remedies and the approval stop, concurrency patterns, and regression pass/fail.
3. `code-optimizer` always writes the triage table before editing: the top five measured hotspots, extended until they cover at least 80 percent of self time (capped at ten), each with measured time, exactly one matched case, a `file:line` target, and an expected speedup labeled as an estimate that names its runtime. It stops for approval only when the user asked for a review or report. `performance-review` itself never edits.
4. One reference under `frontend-ui-engineering` covers primitives, semantic tokens (cross-domain tier structure and the tier-direction rule, owned here), component inventory, reusable blocks, an instruction-file rules block, and project skills, including a path for teams that already have tokens or a component library. The `interface-review` ownership table names that owner; color, spacing, and type owners keep naming, theming, and values. `ui-component-generation` reads a project's design system before generating a component.
5. The design-system lint contract defers the tier-direction rule to its owner and adds a configuration and smoke test that make a primitive token in component source fail, with its coverage limits stated.
6. The fresh-agent behavioral acceptance (Phase 4) passes both tasks, and required local and integration checks, the handbook gate, and a separate Goal-vs-codebase verdict for each half pass on the final candidate.

**Measures**: performance acceptance task passes all four observations (table precedes any edit; one case per hotspot; no cache recommended as a default; sample unchanged in review mode) versus the recorded baseline; design acceptance task produces all six layers and emits components that use semantic tokens only; `run_trigger_evals.py --gate` reports zero new un-allowlisted collisions and zero routing failures; the `frontend-ui-engineering` description grows by at most 250 characters; +0 skills, commands, MCP entries, hooks, and runtime dependencies. No speedup or UI-quality improvement is claimed beyond these observations.
