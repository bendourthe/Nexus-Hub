## Goals First and Definition of Done

The primary user is a developer whose coding agent runs through Nexus-Hub on any supported platform, including Kimi Code CLI and Qwen Code, sometimes pointed at an open-weight model. Today the catalog lets an agent add decorative kicker labels and animate high-frequency menus without objection, has no prompting profile for the model families two installed platforms run, documents only one OpenAI-compatible endpoint, and leaves spend-incurring commands guarded by prose alone.

1. **Earned eyebrows**: `hallmark-design` carries an earned-eyebrow gate (stable slug `earned-eyebrow`; its number is the next free one T001 records, expected 31). A label above a heading passes only when it carries information the heading lacks (a category, a step in a real sequence, a status, a date); a decorative kicker, a label repeated on every section, or an ordinal numbering marketing sections fails. It is judged in context, never as a quota, and defers size and weight to `web-typography`. Existing gate numbers do not change.
2. **Frequency-aware motion**: gate 25, the inline motion defaults in `SKILL.md`, and `references/motion-recipes.md` tell the agent to estimate how often an interaction occurs. High-frequency surfaces (context menus, command palettes, menu-item hover, tab switches) get no entrance animation and no hover-color transition, and at most an exit of 150ms or less. Reduced-motion requirements stay with `accessibility-engineering`.
3. **Behavioral proof for 1 and 2**: 8 episodes, no retries: three audit fixtures (F1 to F3) and one build task (F4), each run once with the baseline skill tree and once with the candidate. DoD 3 passes when the candidate matches every frozen verdict AND differs from the baseline on at least one verdict. A baseline that already matches everything is recorded as "no observable change", which fails DoD 3 for that rule rather than passing it. A grep for the gate text is not proof.
4. **Open-model profiles**: `profiles-index.json` carries a `qwen` platform roster (source `picker`, read from the installed Qwen Code) and a `kimi` platform roster (source `manual`, from Moonshot AI documentation), each capped at the platform's documented default model plus at most two others. Every claim cites a host on the T003 allowlist. The documented default model of each platform has at least one sourced claim; any capped model without one is reported UNVERIFIED and recorded as a known gap, never filled from a hosting provider's guide.
5. **Endpoint guidance**: `multi-provider-ai` has one vendor-neutral section for any OpenAI-compatible endpoint: base URL, key variable and model id; self-hosted server first; a plain statement that a hosted endpoint receives prompts and code; the key loaded from the environment and never committed; a base URL never adopted from an untrusted repository's files; HTTPS for any non-loopback endpoint. Proof for this item is presence and review only, stated as such.
6. **Spend-command layer**: `ai-billing-safeguards` makes credential isolation and provider-side caps the primary control, and adds the platform's native permission deny rule as a secondary layer in user-level settings. The skill says plainly that a deny rule is a command-prefix filter that `bash -c` or a wrapper script can bypass. Evidence: a paired control on Claude Code (the stand-in command runs with only an allow rule, and is refused once the deny rule is added) plus one bypass probe, all recorded as observed.
7. **Closure**: Delta +0 skills, +0 commands, +0 hooks, +0 MCP entries, +0 bundles, +0 scripts. Focused checks end each phase with one local commit. The final phase runs the complete local gate, the Tier 3 pass, an independent Goal review and the single approved publication.
