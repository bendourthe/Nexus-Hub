**Goal**: Redesign the Nexus-Hub interactive guide into a concise, distinctive, portfolio-aligned learning experience that lets software engineers understand the model-versus-harness distinction, install Nexus-Hub immediately, and follow a realistic command-to-result workflow inside an interactive IDE simulation of the post-v4.1.2 product.
**Primary source**: `guides/website/nexus-hub-guide.html`
**Published copy**: sibling repository, outside this tree, at `<portfolio-root>/nexus-hub/index.html` (commonly `../online-portfolio/` next to Nexus-Hub). Absence of that clone does not block Nexus-Hub phases.

## Overview

The current guide is comprehensive but too dense for first contact, and it is also stale. Home still prints 252 skills / 14 commands and installer v3.10.0 against a 328-skill, v4.1.2 catalog. Foundations teaches six concepts across two ladders before the distinction a workshop audience needs most. Training is a 31-slide deck that often splits a command from its result.

This enhancement keeps the self-contained, offline, single-file contract and changes the teaching model. Home becomes a short orientation and installation surface. Foundations leads with model-as-brain versus harness-as-experience. Training becomes one IDE workbench whose panes update together for each scene. The visual system inherits the portfolio's tokens, `portfolio-theme` key, and constellation behavior, and it must clear the `hallmark-design` anti-slop gates.

Rank 17 exists so this guide describes the product after the v4.0.0 bundle and v4.1 catalog work. The Training scene list is a closed set of eight scenes, hard-capped at ten. `/presentify` is taught as the communicate closer and is not the authoring path for this redesign.

Each non-final phase ends with local verification and one local commit. No non-final phase pushes, opens a pull request, authors GitHub Actions, or starts remote CI. The final phase writes `docs/releases/v4/v4.2/development/last-phase-evidence.md`, publishes once with approval, and hands a green integration to `/update release`.

## Goals First

**Target problem**: Software engineers seeing Nexus-Hub for the first time cannot quickly explain what it adds to an AI coding assistant or visualize how its commands change a real project's files, artifacts, tests, and decisions.

**Primary persona**: A software engineer or engineering team attending a live workshop and evaluating whether Nexus-Hub belongs in their daily coding workflow.

**Secondary persona**: A self-guided portfolio visitor who needs a credible overview, installation command, and concrete demonstration without facilitator narration.

**Observable definition of done**:

- A first-time visitor can state in one sentence that the model supplies knowledge and reasoning while Nexus-Hub supplies reusable experience, workflows, and enforced guardrails.
- The visitor can install Nexus-Hub from Home using one macOS/Linux or Windows command without opening a separate Installation page.
- The visitor can step through the closed Training scene set and, for each scene, see the input, tool activity, durable artifact or code change, quality gate, and next human decision.
- Every catalog command is either a Training scene, a Reference row, or explicitly declined with a reason in the Phase 1 inventory.
- The guide supports light and dark modes, persists only `light` or `dark` under `portfolio-theme`, uses the constellation in dark mode only, and remains usable with reduced motion.
- The canonical Nexus-Hub guide has a documented copy path to the portfolio; shipping v4.2.0 does not require editing the sibling repository.

**Success measures**:

- Structural: Home, Foundations, Training, Workflows, and Reference are reachable by keyboard and their state is reflected in the URL; focused guide tests pass locally.
- Accessibility: Lighthouse Accessibility is at least 90 in both themes, with no high-severity keyboard, contrast, heading, or reduced-motion defect. This bar is last-phase human evidence, not a mid-plan gate.
- Workshop (last phase only): at least 4 of 5 participants can explain model versus harness and identify the next command after the workbench. A recorded bounded non-pass (fewer than five people, or below 80 percent) is an accepted close for the study, not a reason to reopen Phases 4-5.
- Fidelity: desktop, tablet, phone, projector, light-mode, and dark-mode visual QA records no open high-severity hallmark issue.
- Lighthouse Performance, SEO, and Best Practices are advisory. They are recorded in last-phase evidence and do not block merge.

## Scope

### Must-ship

- Simplify Home, absorb the two one-command install paths, and keep a scannable platform-reachability beat (which platforms expose `/commands`, and the first verify step).
- Remove Installation from primary navigation; keep advanced install detail in Reference.
- Rewrite Foundations around model versus harness, with a user-initiated raw-versus-harness comparison (range slider or toggle, not cinematic scroll-scrub).

### Presentify inherit / reject

`/presentify` is a document-to-site authoring command. This guide is a durable, portfolio-aligned first-contact product. They share a file contract and fight on visual identity. Phase 2 motion and Phase 5 Training must follow this table.

| Capability | Guide use | Reason |
|---|---|---|
| `nav=scroll` | Inherit for Home, Foundations, Workflows, Reference | Those pages are a scrolling field guide |
| `nav=slides` as the page model | Reject | Training is leaving a 31-slide deck. Viewport-fitted slides recreate it |
| `applyState(scene, beat)` idempotence, fragment beats, key-disengage inside interactive regions, `replaceState` for autoplay ticks | Inherit into the Training controller | Keyboard next/prev and deep links need snapshots, not a second deck runtime |
| Rich before/after or pinned graphic | Inherit for Foundations only, user-initiated | Phase 4 comparison is a range slider or toggle, not scroll-scrub |
| Cinematic / `scroll-scrub-engine.js` / video clips | Reject | A camera fly-through destroys stable IDE spatial orientation. Size-gated clips blow the single-file budget. Reduced motion deletes the effect |
| `design_seed` uniqueness / entropy | Reject | The guide must match the portfolio, not look new every generation |
| html-output-conventions, hallmark-design, visual-QA viewports | Inherit | Offline, no CDN, reduced-motion static equivalents. Workshop QA may substitute 1920 projector + 390 phone for the 2560 leg, and must keep a 25px computed-style floor for workbench text at 1920x1080 |
| `/presentify` as a taught command | Keep and update | Workflow communicate and the Training closer. Mention `--nav scroll\|slides` and `--interactivity restrained\|balanced\|rich\|cinematic` in Reference, not as this page's runtime |

### URL grammar

One composed encoding, specified here and implemented in two steps:

- Page: `#<page-id>` from an allowlist. Unknown page id maps to `home` and rewrites the URL.
- Training: `#training/<scene-id>` with beat as a non-history query (`?beat=<n>`) or an equivalent that uses `history.replaceState` for beat ticks. `history.pushState` only for user-initiated page or scene jumps.
- `#training` without a scene id is valid after Phase 2 and loads Training at scene 1 beat 0 once scenes exist.
- Unknown scene id, NaN, negative, or beat past the last beat clamps to scene 1 beat 0, rewrites the URL, and renders a complete snapshot. Scenes are full snapshots, not deltas, so a cold mid-tour URL is coherent.
- Page router owns page id. Training owns scene and beat only while the page is `training`. ArrowLeft / ArrowRight / Space never both change page and scene.
- Deck/scene keys disengage when focus is in the editor, terminal, file tree, or the Foundations slider (`event.target` containment). Escape returns focus to the page or workbench chrome.
- Phase 2 implements page routing and `#training`. Phase 4's handoff is `#training`, not a scene URL. Phase 5 adds scene id and beat.

### Trust boundary (public HTML)

- Fixture strings render with `textContent` / `createTextNode`. No `innerHTML` for scene data.
- Inline JSON lives in `<script type="application/json">` with `</script>` encoded. The Trivia Quiz `index.html` already contains `</script>`; that string is a required fixture test.
- `portfolio-theme` accepts only `light` or `dark` before apply or write. Wrap `localStorage` in try/catch; on failure fall back to `prefers-color-scheme` and still render. Theme sharing with the portfolio works only on the same https origin; `file://` must still boot.
- Install copy payload is a JS/HTML constant equal to the visible command and to `curl -fsSL https://raw.githubusercontent.com/bendourthe/Nexus-Hub/main/install.sh | bash` or `irm https://raw.githubusercontent.com/bendourthe/Nexus-Hub/main/install.ps1 | iex`. Tests assert `data-copy === textContent ===` those constants.
- If `location.origin` is not the documented GitHub or portfolio host (including `file://`), show a persistent warning that copy-paste installers from this copy are untrusted. Do not hide the host inside overflow.
