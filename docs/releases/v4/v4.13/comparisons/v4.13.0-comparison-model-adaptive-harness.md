**Headline question**: Can Nexus-Hub detect the model behind a submitted prompt and adapt the skills, rules, hooks, and commands it surfaces?

## Why this source matters to this project

Nexus-Hub distributes always-loaded behavioral guidance into roughly twenty agent platforms, two of which run the vendors whose frontier models this article is about. The article is the first source to argue that the catalog's own shape, not merely its content, should change as models improve: that elaborate scaffolding authored for weaker models actively degrades stronger ones. That is a claim about Nexus-Hub's architecture rather than about any single skill.

This is a genuinely new source. The existing `v4.7.0-comparison-gpt-6-astra-prompting.md` compared the GPT-6 Astra **API prompting guide** (`developers.openai.com/api/docs/guides/latest-model`), which covers reasoning-effort parameters, the Responses API, and tool-calling mechanics. This blog post covers skill authoring, `AGENTS.md` hygiene, decision boundaries, and persistence. No report in `docs/` cites this URL; verified by a repository-wide grep for the article slug, which returned no matches.

The operator's question goes further than the article does. The article says guidance should be tuned per model; it does not ask whether a harness can do that tuning automatically at prompt time. That feasibility study is the headline of this report and is answered from verified evidence in the dedicated section below.

## Headline study -- Model-adaptive routing feasibility

The operator's question: can Nexus-Hub detect which model is behind a submitted prompt on a supported platform, and reroute skills, rules, hooks, and commands so each prompt adapts to that model?

### Finding 1: Detection is solved on Claude Code, by three channels

Verified against the vendor hooks reference and against a live transcript on this machine.

| Channel | Availability | Evidence |
|---|---|---|
| `SessionStart` hook `model` field | Optional, fires once per session | Vendor docs: "Only `SessionStart` hooks can receive a `model` field, and Claude Code doesn't always include it." |
| `PreModelSwitch` / `PostModelSwitch` hooks | Fires only on change; carries `from_model` and `to_model` | Vendor docs recommend `PostModelSwitch` "to follow the model as it changes during a session". |
| `transcript_path` -> last assistant record -> `message.model` | Present in every hook payload | Empirically confirmed on this session's transcript: `"model":"claude-opus-5"`, located at `message.model` inside a record of `type: assistant`. |

Two dead ends, both documented rather than assumed. There is **no `model` field on the `UserPromptSubmit` payload**, and there is **no `$CLAUDE_MODEL` environment variable**; `$ANTHROPIC_MODEL` exists only if the user sets it and does not track `/model` switches. Separately, `effort.level` IS carried in the standard payload, so reasoning effort needs no resolution work at all.

The robust design layers all three: transcript read as the authority, `PostModelSwitch` as a cache-invalidation signal, and the optional `SessionStart` value as the cold-start seed for turn one, where no assistant record yet exists.

### Finding 2: The injection seam already exists

`catalog/hooks/skill-activation-suggest.py` is registered on `UserPromptSubmit` and already writes to stdout, which Claude Code appends to agent context. Its own docstring states the contract: "For `UserPromptSubmit`, stdout is added to the agent's context, so this nudges the agent to load the matched skill(s)." It reads a declarative `skill-rules.json` whose per-rule fields include `promptTriggers` with `keywords` and `intentPatterns`, and it already supports `rule_skipped_by_env` and `rule_skipped_by_session` gating. A model predicate is a natural third gate alongside those two.

### Finding 3: The per-model knowledge exists but is write-only

`model-prompting-research` maintains `assets/profiles-index.json` and `references/models/*.md`, including a `gpt-6-astra.md` with claims verified 2026-09-05 against fetched primary sources.

A repository-wide grep for any reference to `profiles-index`, `model-prompting-research`, or `references/models` **outside that skill's own directory returned no matches**. Nothing reads the profile layer at runtime. The research pipeline populates it; no consumer exists. This is the single missing wire, and it is the entire gap between what Nexus-Hub has today and a model-adaptive harness.

### Finding 4: Three constraints that bound the answer

**C1 -- Claude Code only, against a platform-agnostic principle.** Of roughly twenty platforms in `docs/policy/platform-read-contracts.json`, only Claude Code has a hook runtime; `AGENTS.md` describes the hook channel as reaching "platforms that honor Claude-style hooks". Codex, Cursor, Gemini, Antigravity, Copilot, OpenCode, Qwen, Kimi and the rest receive static files with no runtime interception point. A model-adaptive harness would therefore be a single-platform capability inside a catalog whose stated constraint is that instruction-template changes "must be platform-agnostic". That tension is architectural and belongs in a decision record, not in a phase note.

**C2 -- "Reroute skills, rules, hooks, commands" overstates the mechanism.** A hook cannot change which `SKILL.md` files exist on disk mid-session, and rules and commands are static files the platform discovers on its own schedule. Hooks can be disabled through `NEXUS_DISABLED_HOOKS` and `NEXUS_HOOK_PROFILE=minimal`, but those are per-session environment settings, not per-prompt decisions. What is actually achievable is **model-aware context injection plus model-aware skill-activation bias**. The honest scope is that, not catalog swapping.

**C3 -- The hard rail is satisfied, not violated.** `model-prompting-research` forbids model-specific guidance from entering any shared body, because shared bodies ship verbatim to every platform and one model-named line is wrong for every other reader. A runtime injector writes to no file; it adds text to one session's context, on the platform whose model it just resolved. It is therefore the architecturally correct consumer the profile layer has always lacked, and it strengthens the rail rather than eroding it.

### Verdict

**Feasible on Claude Code, with the expensive half already built.** Detection is a documented and empirically confirmed capability, the injection hook is already registered and already reads a declarative ruleset, and the per-model content already exists and is schema-valid. The missing work is a resolver plus a model predicate on the existing rule schema. It is not feasible on the other nineteen platforms by any mechanism currently available, and the scope must be stated as context injection rather than catalog rerouting.

Three review findings drove this. The **scope and product lenses independently** found the A-series instruction work unrelated to the M-series runtime work, independent of the C1 verdict, and higher in user value, so it split to v4.13.2 and ships either way. The **product lens** found the original pilot measured cost with no instrument for benefit, and ran after the code was written where an honest negative result competes against sunk cost, so measurement moved into Phase 1 on a throwaway prototype. **P0 correction to this report's own Finding 3.** This report framed the profile layer as a data-quality artifact whose only problem was having no consumer. That framing was incomplete in two ways, both verified on 2026-09-14:

1. **"Write-only" overstates it.** `scripts/apply_prompting_edits.py` reads the layer, and `references/models/*.md` are Tier-3 files an agent reads on demand. The accurate gap is narrower: no AUTOMATIC consumer at prompt time. Under the accurate phrasing, the decline alternative is a serious contender rather than a consolation prize.
2. **The layer may not be fit to consume at runtime.** Its claims originate on third-party vendor web pages and would terminate in the agent's context window every turn. Separately, only 3 of the 12 profiled models are reachable by a Claude Code transcript resolver, so a consumer would reach a quarter of the layer, not all of it.

This is evidence for the verdict, not a task to engineer around, and the maintainer confirmed that framing. Building a fence, an integrity digest, and a claim filter is precisely the scope creep the review flagged.

## Step 7 -- Risks, conflicts, and items not recommended

### Conflicts with existing conventions

**A1 conflicts head-on with a deliberate house rule.** The article wants descriptions "as concise as possible". `AGENTS.md` mandates the opposite under "combat undertriggering", trading "6 words for 60" because Claude measurably under-triggers on narrow descriptions. Both positions are evidence-based; they simply describe different models and different failure modes. This is the single clearest illustration of the article's own A10 thesis, and it is precisely why per-model profiles exist. **Recommendation: do not adopt A1 into any shared body.** If it is adopted at all, it belongs in the OpenAI profile layer as a model-specific claim, which is where the `model-prompting-research` hard rail would put it anyway.

**A8 touches user-global instructions, not just repository ones.** The two MANDATORY rules most exposed to A8 live in the user's global `CLAUDE.md`, outside this repository. A v4.13.0 phase can recommend the change and can fix the repository-side instances; it cannot unilaterally edit the operator's global file. Scope the task to what the repository owns and surface the rest as a recommendation.

**C1 is a decision, not a task.** Shipping a Claude-Code-only behavioral capability contradicts the platform-agnostic constraint on shared instruction surfaces. `AGENTS.md` requires a decision record for "a new policy, a new supported platform, a new validator or gate". This qualifies. The record must state the alternatives, including declining to build it.

### Risk register

| Risk | Item | Mitigation |
|---|---|---|
| Transcript read widens data exposure | M1 | Parse only the final assistant record; extract only `message.model`; never log, echo, or persist any other field. Make this an exit-checklist assertion with a test, not a code comment. |
| Cold start has no model | M1 | On turn one no assistant record exists. Fall back to the optional `SessionStart` value, then to no-op. Never guess a model, and never default to a named one. |
| Prompt-cache invalidation | M3 | Per-prompt injected text can defeat caching. Re-check against v4.11.1 before implementing; prefer injecting once per session or on model change rather than on every prompt. |
| Compaction interaction | M3 | Re-check against v4.10.1 adaptive compaction. |
| Per-prompt token cost | M3 | Injected guidance costs tokens every turn it appears. Bound the payload and measure it; the phase is already framed as a measured pilot, and a measured no-change result is explicitly a valid outcome there. |
| Stale profile injected as current | M3 | Profiles carry a `Last verified` date. Inject the date alongside the guidance so the agent can discount stale claims, consistent with the visibly-dated fallback pattern `model-routing` already uses. |
| Silent no-op | M1 to M3 | All three fail open by design, matching the existing hook contract. A capability that silently does nothing is indistinguishable from one that is working. Require one observable signal that resolution occurred. |

### Not recommended for adoption

| Item | Reason |
|---|---|
| **A1 as written** (`drop-outright` for shared bodies) | Directly contradicts the evidence-based undertriggering rule in `AGENTS.md`. Model-specific by nature; belongs in the profile layer if anywhere. |
| **Extending model-adaptive routing to non-Claude platforms** | No hook runtime exists on the other nineteen platforms. There is no mechanism to reverse-engineer, so this is not `re-partial`; it is unavailable. Record it as a known gap rather than a backlog item, so nobody re-derives the same negative result. |
| **A model field in any shared instruction template** | The `model-prompting-research` apply engine independently blocks any edit that introduces a model identifier into a shared body, whatever its declared scope. Any design that needs this is the wrong design. |
