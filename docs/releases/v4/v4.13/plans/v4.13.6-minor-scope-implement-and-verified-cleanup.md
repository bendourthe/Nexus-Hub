**Goal**: A user who types `/implement v0.5` reads one plain-language approval page, pastes one exact line, and the run then builds every queued plan in that minor in version order, releases each patch, fixes every fixable known gap in that minor and earlier versions and migrates the rest to the next minor, removes every branch and worktree that is verifiably merged and idle, and closes and archives the minor through one final pull request, stopping only on a named blocker or the user's pause, with the goal set through the platform's own goal command wherever one exists and the deterministic checker as the only authority on done.

## Definition of Done

1. `/implement vX.Y` resolves its member plans with the membership rule in 2.2 (not shipped, not owned by another live run), in semantic-version order, and runs each through the existing per-plan driver under one approval.
2. `check_plan_completion.py check-minor vX.Y` prints `MINOR COMPLETE vX.Y <head> <nonce>` only when every member is `PLAN COMPLETE`, the gap scope in 4.2 has no open item, the final cleanup pass has run after the last merge, the closing pull request is merged, and the minor is archived. Otherwise it prints `INCOMPLETE`, `BLOCKED`, or `PAUSED`, and a blocker in any member stops the run.
3. An approval is recorded only when the user's submitted prompt equals, as a whole, the exact paste line the checker generated for that page, including a single-use code the checker derived from the page's data. A lone "ok", a quoted code, a pasted issue body, or a prompt the runner launched never produces a record (closes v4.13.2 WN-9 for every record type).
4. Cleanup removes an item only when every check in 3.1 passes at the moment of removal, re-read immediately before. A failing item is listed with its failed check. Nothing is removed with `-D`, `--force`, or `worktree remove --force`, and no gitignored file outside the allowlist is ever deleted.
5. An unfixable gap in the gap scope moves to the next minor's `known-gaps.md` with path-independent provenance and a reason from a closed set, only if its id was listed on the approval page. The source minor then reads `**Open items**: 0` and is archived, and archived member plans still resolve for `check-minor`.
6. The approval page reads as plain language by test: the highest-risk effects come first, a banned-jargon list passes above the paste line, sections stay under a sentence-length ceiling, and the paste line carries no file paths or script names. One non-engineer read-back is recorded in the final phase.
7. The goal is restated in `/implement`, the mandatory final-phase template, and `/update release`, each naming the same checker verdict and linking the completion contract without redefining a predicate. Each says plainly that in an interactive session it can only ask the user to paste the line again, and that `nexus-hub run-plan` is the only fully automatic path.
8. The end-to-end harness proves a two-plan minor on stand-ins: an SSH-alias remote, another session's merged but recently active worktree kept, a squash-merged branch handled, a gitignored `.env` never deleted, one gap migrated and the run still completing, both releases, the closing pull request, the archive, and `check-minor` after the archive.
9. The public website guide's Cheatsheets `/implement` card lists every mode and scope form in `catalog/commands/implement.md`, enforced by a test, and the `/update` card names the closing pull request and the checked cleanup.

## Non-Goals

- No new CI workflow, permission, or secret handling. These stay never-approvable-in-advance blockers.
- No agent-typed slash commands. The native goal is set by the user's own paste or a documented headless entry point.
- No deletion of branches whose pull request was closed unmerged, of branches merged without a pull request, or of anything failing a 3.1 check. Those stay report-only.
- This plan does not archive v4.13 itself while v4.13.4 is in flight in another session.
- Gaps in versions later than the run's minor are never acted on; they belong to their own plans.

## Overview

v4.13.2 made `/implement <plan>` run one plan to a checker-decided finish. Users expect "implement v0.5" to mean the whole minor: every plan, the releases, the leftover gaps, the cleanup, and the archive. This plan adds a minor-scope driver above the per-plan driver. One run record covers every member plan, the member plans run one after another with a gate between them, and a final closing pull request carries the gap migrations and the archive onto develop.

Because one paste now authorizes several releases, deletions, and an archive, the plan first closes the approval weakness recorded as v4.13.2 WN-9. Today any single line the user typed can satisfy an approval. After Phase 1 only the exact line the checker generated for that page counts, once. The approval page itself is rewritten as a short plain-language page whose final line doubles as the platform's native `/goal` command. The official docs show `/goal` is user-typed only on Claude Code and Codex, so that paste is the honest way to set the native goal in an interactive session. `nexus-hub run-plan` sets it itself where a headless goal is documented. The deterministic checker remains the only authority on done, and the native goal is advisory: its model-judged evaluator can be satisfied by printed text, so the goal condition names the checker's tool result, not a string.

Cleanup widens to every merged and idle branch and worktree, not only the run's own. At the user's direction the approval covers anything that qualifies when cleanup runs, not a frozen list, so the safety lives in the per-item checks, the re-read before each removal, and one final pass after the last merge.

#### 1.2 -- Bind approvals to the exact generated line

**Objective**: Close WN-9: an approval requires the whole submitted prompt to equal the checker-generated line, containing a single-use code derived from the page data.

**Failure modes**: The page data changes between render and paste (a plan edited, a branch moved): the recomputed code differs and `record create` refuses with `page-changed`. A code pasted twice or after expiry (30 minutes, or the session ending): refused with `code-used` or `code-expired`. The pending code file is missing or unreadable: refused, never recorded without it. Two approval rounds open at once for the same scope: the newer render invalidates the older code.

**Build class**: load-bearing.

**Prompt**:
> In `scripts/check_plan_completion.py` (delegating new logic to a sibling `scripts/approval_binding.py`, registered in BOTH installers), add `record render <scope>`. It builds the canonical JSON of exactly what the approval page shows (scope, members with `plan_sha256`, `owner/repo`, branches, releases, the cleanup rule and today's estimate, the migratable gap ids, spend caps) plus a fresh 128-bit round nonce, computes `code = first 8 base32 characters of HMAC-SHA256(runs secret, canonical JSON)`, and writes a pending file beside the run records (owner-only, as the records are) holding the canonical JSON, the code, the nonce, an expiry, and the session id. Only the checker generates codes; the agent never does. `record create` recomputes the canonical JSON from live state, requires the same code, requires that exactly one captured prompt digest for the session equals the digest of the exact rendered paste line (whole prompt, after the existing normalization, not a line within a prompt), consumes the pending file, and adopts the round nonce as the record nonce.
