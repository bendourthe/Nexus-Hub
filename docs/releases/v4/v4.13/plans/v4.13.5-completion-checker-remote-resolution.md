## Overview

The checker parses `owner/repo` from `git remote get-url origin` with a regex that only accepts a host literally named `github.com`. Developers with several GitHub accounts commonly use an SSH host alias (`git@github-work:owner/repo.git`), which leaves the repository empty and turns every hosting predicate into `cannot-verify`. A full run can therefore never finish in such a repository. The fix resolves the real host first and parses the path second, and it refuses to guess.

The resolution order is: a run record's frozen `repo` when one exists; otherwise the remote URL, whose host is taken directly for `https://` and `ssh://` forms and from `ssh -G <alias>` (the `hostname` line) for the scp-like `git@<alias>:owner/repo` form; the path is accepted only when that host is `github.com` or `GH_HOST`. `gh repo view --json nameWithOwner` is used as a cross-check when no record exists, and a disagreement is `cannot-verify`, because `gh repo set-default` lives in `.git/config`, which an agent can write.

### Sub-tasks

#### 1.1 -- Build the shared resolver

**Objective**: Create `scripts/repo_host.py` with the resolution order from the Overview.

**Failure modes**: Malformed or absent remote: return no repository, and callers report `cannot-verify`. `ssh` absent or `ssh -G` slow: treat the alias host as unverified (no repository), inside the caller's shared time budget. `gh` unreachable: skip the cross-check and rely on the verified URL parse. The URL and `gh repo view` disagree: no repository, never a pick. A fork with several remotes: resolve `origin` only, and expose the resolved remote name so a caller can assert it pushes to the same repository.

**Build class**: load-bearing.

**Prompt**:
> Create `scripts/repo_host.py` exposing `resolve_repo(root, record_repo=None, budget=None) -> tuple[str | None, str]` (repository and a reason code) and `absolute_tool(name, repo_root)` (move the checker's `_which_on_path` / `_tool` logic here so git and gh resolve to absolute paths outside the working tree). Order: frozen `record_repo`; else parse the origin URL (`https://host/owner/repo(.git)`, `ssh://git@host[:port]/owner/repo(.git)`, `git@alias:owner/repo(.git)` with the host from `ssh -G alias`), accept only `github.com` or `GH_HOST`; then, when `gh` is available, cross-check with `gh repo view --json nameWithOwner -q .nameWithOwner` and return no repository on disagreement. Use only the standard library. Register the file in BOTH `scripts/installer.sh` and `scripts/installer.ps1` next to the `generate_report.py` copy block so the installed checker can import it as a sibling.

#### 1.2 -- Switch every caller to the resolver

**Objective**: Remove every copy of the host regex.

**Prompt**:
> In `scripts/check_plan_completion.py`, `REMOTE_RE` (line 87) was tightened on 2026-09-28 by the v4.13.2 WN-1 and WN-13 follow-ups (PRs #372 and #374) to accept only a literal `github.com` host, and it now has two consumers: the `default_repo` assignment in `Context.__init__` (line 254) and `_approved_remote_status` (line 472, predicate `approval.remote`), which binds push approval to the exact `push_remote_url` and `repo` recorded at approval. Replace both uses with `repo_host.resolve_repo` (importing it as a sibling module; the installed layout is flat under `~/.nexus-hub/scripts/`). For `approval.remote`, keep the WN-1 binding exactly: the current push URL must still equal the recorded `push_remote_url` byte for byte, and the repository resolved from that URL (now alias-aware and host-verified) must equal the recorded `repo`. Do not relax either comparison, and keep a regression test proving that a push URL pointing at a different repository is still `unmet`. Search `scripts/` and `catalog/hooks/` for `github\.com[:/]` and switch any other remote parser to the module. Keep `--repo owner/repo` pinning on every hosting call unchanged.
