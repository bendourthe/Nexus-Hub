## 2. Chronological Steps

### 2.1 Prove the missing section seam

Two self-contained browser tests failed before implementation because `window.NexusTraining.mountSection` did not exist. One test checks that the live deck already owns its root and renders one reply per run. The other mounts two temporary section roots with distinct terminal, tools, artifact, gate and file content, triggers the second root's button, and verifies the first root is unchanged. It also checks duplicate-mount rejection, inertness after disposal and remounting.

### 2.2 Move action state behind each root

`createTrainingSection(sectionRoot, record, options)` resolves every action widget, file explorer and optional game from its own root. It owns its selected path, animation token, click and file-key listeners, and disposal. `mountSection` guards a root with a `WeakMap` before creating another controller. The current deck now mounts one controller per scene, disposes it on navigation, and delegates its run and explorer actions to that controller. The old global terminal, explorer and action handlers were removed. The existing `window.NexusTraining` methods and deck navigation remain available; `mountSection` is the one new API seam needed by Phase 6.

An additional red assertion found that a standalone section could reveal a pending file by clicking its explorer item before Run. The controller now keeps that section's files hidden until its action completes. The live deck continues to use its cumulative-state callback for the same boundary; the corrected controller and explorer tests pass 6/6.

### 2.3 Keep the source and visible behavior stable

The eight scene records, presentation controls, previous/next navigation and cumulative project model did not change. A 61-test affected browser run passed across Training explorer, shooter, presentation geometry and the new section-controller module. The new controller tests pass 2/2 on their own. No CSS, deck markup, scene source or game simulation changed in this phase.
