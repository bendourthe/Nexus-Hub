## What this phase was for

OpenCode, OpenClaw, Pi, and Hermes have no shell hooks; their only turn-end lever is a typed plugin. This phase gave each a thin plugin over the same installed gate core, so a full run continues there too.

## Queue re-assessment (phase entry)

No drift from queued plans. The plan asked to re-verify each plugin API first, because the continuation use is "only partly documented". A research pass on 2026-09-25 against first-party docs and source confirmed the lever on all four and found three design constraints (below).

## Steps taken

1. **Decision record** (`docs/decisions/implemented/architecture/2026-09-25-install-completion-plugins-by-default.md`): default-on with the `NEXUS_HUB_COMPLETION_PLUGINS=0` opt-out, reversing DF-4 for this one purpose, with opt-in and runner-only as the rejected alternatives.
2. **Plugins** under `catalog/plugins/completion-gate/`:
    - **OpenCode** (`nexus-completion-gate.ts`): `session.idle` with `event.properties.sessionID`, continues with `client.session.prompt` (never `noReply`).
    - **Pi** (`nexus-completion-gate.ts`): `agent_before_settle`, session id from `ctx.sessionManager.getSessionId()`, returns one `custom_message` entry with `continue: true`.
    - **OpenClaw** (`package.json`, `openclaw.plugin.json`, `index.ts`): `definePluginEntry` with `before_agent_finalize`, session id from `ctx.sessionId`, returns `revise` with an `idempotencyKey`; the core runs on a 10-second budget inside OpenClaw's 15-second handler limit.
    - **Hermes** (`plugin.yaml`, `__init__.py`): `pre_verify` returning `{"action": "continue", "message": ...}`.
    All three TypeScript plugins carry one identical gate-call block (asserted by test), spawn the core with an argument array and `shell: false`, and import only Node built-ins (plus OpenClaw's own SDK entry).
3. **Installation** (`scripts/lib/integrations/_completion_plugins.py`): user-global only, behind each integration's detection gate, manifest-owned, skipped on opt-out. OpenCode gained an `install_global` override that installs only when `~/.config/opencode` existed beforehand.
4. **Core** gained the `plugin` output format (`{"decision": "continue", "reason": ...}`) and `NEXUS_GATE_BUDGET_SECONDS`.

## Constraints found by the research

- **Pi's `pi.exec` ignores stdin**, so it cannot deliver the payload; the plugin uses `node:child_process` directly.
- **OpenClaw and Hermes load a plugin only after an enablement step** (`openclaw plugins enable` plus `allowConversationAccess`; `hermes plugins enable`), and the config file locations are not verified verbatim. The installer places the files and reports NEEDS SETUP with the documented command rather than editing an unverified config path.
- **Hermes' `pre_verify` fires only on turns that edited code** (open vendor issue #109816); the runner is Hermes' primary layer.

## Troubleshooting

### The stub core hid a missing output format

The first plugin tests passed against a stub core, while the real core did not know the `plugin` format the plugins request and would have answered `block`, so no plugin would ever continue. The core gained the format, and a test now drives the Hermes plugin through the real core.

### The OpenClaw plugin created a state directory the user did not have

The full integration suite failed two OpenClaw cases: with an explicit config path or a workspace environment variable, the resolved state directory need not exist, and the plugin install created `~/.openclaw` to write into it. The plugin now installs only into an existing state directory.

## Plan delta

**Disposition: Incomplete** (non-blocking).

Consequences for remaining phases: Phase 8 evaluates OpenCode, whose plugin auto-loads, so the evaluation is unaffected. The enablement step is filed as a known gap for automation once the config paths are verified.
