## What this phase was for

Phase 3 could say which lines an old install left outside the managed markers. This phase lets an install act on that, deleting from a file the user owns, without ever deleting a line the user did not see and approve.

## Troubleshooting

### A token printed by one writer would be stale on the next run

Two integrations write `~/.gemini/GEMINI.md`, and org-knowledge merges after the Nexus block. Computing the token inside each merge (as the plan's prompt describes) would print a token that the next writer in the same install immediately invalidates. The report is therefore built once, after every write, from the final on-disk bytes (the dry-run case reads current bytes, which is what the plan asks for there).

### A refused token would have failed every other platform's install

The installers call the runner once per platform, so a token for Claude's file is unused by the Codex call. A first version exited 1 on an unused token, which would have printed "install reported a non-zero exit" for every other platform. The runner now records `consumed` and `refused` and exits 0. The installers aggregate, reporting a token as refused only when no call consumed it and keeping only the last candidate list per file.

### Escaped literals mangled by the shell

Heredoc edits turned `"\r\n"` and a BOM byte literal into raw characters in `instruction_merge.py`. They were repaired with a script written through the Write tool, and every later multi-line edit used that route.

### Windows `os.replace` Access Denied

One run failed with WinError 5 on an atomic replace that passed alone. That is the documented transient-handle class (v4.9 BG-1); the bounded retry fixed it at the source rather than by rerunning.

## Verification expectation

Driven through the installer's own engine rather than the full installer: the full PowerShell installer also installs VS Code extensions through the real `code` CLI and writes the real `%APPDATA%` settings, which a redirected HOME does not isolate. The script ran one quiet `runner.py install --summary-json` call per platform (Claude, Codex), then `runner.py legacy-report`, exactly as both installers do, on a throwaway home seeded with a copy of an observed-layout file in both targets.

- Run 1 (no token) reported each file's two spans with line ranges, estimated tokens (228 and 10305), diff paths, and exact `--remove-legacy-instructions=` commands. Text above the markers was unchanged, and verified backups were written.
- Run 2 (Claude's two tokens) left zero Claude candidates and one `**Total:` line, with the managed block intact. The identical text in Codex's file was untouched.
- Run 3 (the same tokens again) refused both by name and left the file byte-identical. The backups grew from two to four entries with none deleted.

Byte preservation outside the consented spans was confirmed separately (the result equals the original with only those line ranges removed).

## Plan delta

**Disposition: Delta, recorded.**

Evidence and consequences:

- The report is computed after all writers instead of inside each merge (see Troubleshooting). This is behavior the plan's acceptance requires ("valid for the immediately following unchanged install") that per-merge computation cannot deliver when writers share a file.
- The full removal diff is written to an owner-only file under `~/.nexus-hub/state/legacy-candidates/` and the report prints its path, rather than printing a 300-line diff into the install log.
- Runner refusals exit 0 and are aggregated by the installers.

Phase 5 is unaffected. The final phase moves the decision record from `proposed` to `implemented` if the release ships it unchanged.
