## Copilot usage monitor

Sub-task 1.1. The monitor may display a figure only when GitHub serves it, or when it is a served count multiplied by a constant GitHub publishes. Nothing below is reconstructed from data GitHub does not serve, which is the defect that withdrew the earlier GitHub monitor ([withdrawal record](../../../../decisions/implemented/architecture/2026-08-22-withdraw-the-github-usage-monitor.md)).

### (1) Personal figure

**Options**: (a) `GET https://api.github.com/copilot_internal/user` with the VS Code GitHub session, the endpoint the Copilot extension's own usage popup reads; (b) the documented `GET /users/{username}/settings/billing/ai_credit/usage`; (c) no personal figure.

**Evidence**

- `copilot_internal/user` is **undocumented**. A search of docs.github.com and github.blog on 2026-09-30 returned no page that names it, and it does not appear in the fine-grained token permissions reference ([permissions page](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens)). It is the same class of dependency as the Codex monitor's `wham/usage` endpoint: it can change shape without notice.
- The documented alternative exists: `GET /users/{username}/settings/billing/ai_credit/usage`, "Gets a report of AI credit usage for a user" ([billing usage](https://docs.github.com/en/rest/billing/usage)), under "User permissions for "Plan"" read in the permissions reference. It returns line items of credits used, not the plan quota, so on its own it gives a numerator and no denominator.
- Published personal plan allowances ([plans](https://docs.github.com/en/copilot/get-started/plans)): Copilot Pro "Base: 1,000" plus a 500 flex allotment (1,500 total); Copilot Pro+ "Base: 3,900" plus a 3,100 flex allotment (7,000 total); Copilot Free "An allowance of GitHub AI Credits" with no number stated. The page does not state the personal reset date.
- VS Code authentication API ([vscode-api authentication](https://code.visualstudio.com/api/references/vscode-api#authentication)): `authentication.getSession(providerId, scopeListOrRequest, options?)` resolves to "an authentication session or undefined if a silent flow was used and no session was found". `silent`: "Whether to request a session silently without user interaction. When `true`, no UI is shown for authentication." `createIfNone`: "Whether a new session should be created if none exists. When `true`, the user may be prompted to authenticate." `account`: "If not provided, the user will be shown a quickpick to choose which account they would like to use." `clearSessionPreference` clears the remembered account choice. The session carries `accessToken`, `account`, `id`, and `scopes`. The documentation does **not** list the scopes the built-in `github` provider accepts.
- Account pinning ([VS Code 1.94 release notes](https://code.visualstudio.com/updates/v1_94)): an extension's account is changed from the Accounts menu > account > Manage Trusted Extensions > gear icon, or from the extension's gear icon > Account Preferences; "Choosing any of these options takes you to a Quick Pick where you can change the account that an extension uses." This is a per-extension preference inside VS Code; it does not touch git's `user.name`/`user.email` or the `gh` CLI's stored login, which are separate stores.

**Captured readings (settled 2026-10-01)**

- Token: `copilot_internal/user` returned HTTP 200 for both accounts with a classic personal access token that has **no scopes**, sent as `Authorization: token <value>`. No scope is therefore needed beyond the token identifying the user.
- Fields, from `quota_snapshots`, which holds one object per quota (`chat`, `completions`, `premium_interactions`):
    - `entitlement`: the quota (personal Copilot Free: `chat` 200, `completions` 2000, `premium_interactions` 0).
    - `remaining` and `quota_remaining`: what is left (the same value, integer and float).
    - `percent_remaining`: the served percentage left; used percent is `100 - percent_remaining`.
    - `credits_used`: the used figure (0 on every quota in both captures).
    - `unlimited` and `has_quota`: whether a quota applies. Free `premium_interactions` has `has_quota: false`, `entitlement: 0`, `percent_remaining: 0.0`, which is "no allowance", not "exhausted".
    - `overage_permitted`, `overage_count`, and (member only) `overage_entitlement`.
    - Reset: top-level `quota_reset_date` (`"2026-11-01"`) and `quota_reset_date_utc` (`"2026-11-01T00:00:00.000Z"`); per-quota `quota_reset_at` was `0` on both accounts and is not a usable reset field.
    - Plan: `copilot_plan` (`individual`, `business`) and `access_type_sku` (`free_limited_copilot`, `copilot_for_business_seat_quota`).
- Personal plan (Copilot Free): every limited quota served `entitlement`, `remaining`, and `percent_remaining`, all unused, reset 2026-11-01. The billing page, read at 2026-10-01 23:44 UTC (capture 23:41:23 UTC), showed plan Copilot Free, $0 Copilot usage for October 1-31, 2026, and 0 additional AI credits; it shows no credits-used figure and no reset date, so the comparison is "$0 and 0 additional credits" against "0 used on every quota", which agree. The page's $13.27 metered usage is GitHub Actions, not Copilot.
- Business member seat: every quota has `unlimited: true`, `entitlement: 0`, `remaining: 0`, `credits_used: 0`, and `percent_remaining: 100.0`; `premium_interactions` has `overage_permitted: true`. The response carries **no per-person limit** and no figure that could serve as a denominator. `percent_remaining: 100.0` on an unlimited quota is a constant, not a reading, and the monitor never shows it.

**Mapping rule for 2.2**: a quota yields a percentage only when `unlimited` is false, `has_quota` is true, and `entitlement > 0`; percent used is `100 - percent_remaining`, cross-checked against `(entitlement - remaining) / entitlement`. The status-bar quota is `premium_interactions` when it qualifies, else `chat`, else `completions`, and the dashboard lists every qualifying quota. When no quota qualifies (every Business or Enterprise seat in this capture), the view is credits used, summed from `credits_used`, with no percentage. `resets_at` is `quota_reset_date_utc`, else `quota_reset_date` at 00:00:00 UTC.

**getSession scopes (settled 2026-10-01)**. Source: the built-in provider's `getSessions` in [`extensions/github-authentication/src/github.ts`](https://github.com/microsoft/vscode/blob/main/extensions/github-authentication/src/github.ts), fetched 2026-10-01, filters with `(!sortedScopes.length || arrayEquals([...session.scopes].sort(), sortedScopes))`: a non-empty list must match a stored session's scopes exactly, and an empty list matches a session of any scopes.

- Background refresh: `getSession("github", [], { silent: true })`. It finds the existing session of the pinned account (for example the one the Copilot extension created) without a prompt, and the capture proves any user token suffices for this endpoint.
- User-initiated "Sign in to GitHub" action only: `getSession("github", ["read:user"], { createIfNone: true })`, the narrowest named OAuth scope, because an interactive request mints a token with exactly the scopes asked for and creating a session with an empty list was not tested. The next silent `[]` lookup finds that session.
- Declined: `["user:email"]` or a broader list, which asks for more than the endpoint needs; and an exact `["read:user"]` silent lookup, which misses the Copilot extension's existing session and would leave most users at "Sign in" for no reason.

**Chosen**: (a) for the percentage, because it is the only source that serves the quota beside the used figure; the monitor treats it as fragile, ignores unknown fields, and falls back to "credits used, no percentage" when no quota qualifies. (b) is recorded as the documented fallback for the used figure if (a) disappears. Settled by the readings above.

**Unblocks**: 2.2.

### (1b) Which GitHub account the monitor reads

Recorded from the maintainer on 2026-10-01. The maintainer's Copilot seat is on a work GitHub account that owns the organization, while many projects live under a personal account. The monitor must show the work account's usage while the user works in a personal repository.

**Options**: (a) read usage from the GitHub account the user pins for this extension in VS Code (Accounts > Manage Extension Account Preferences), independent of the open repository; (b) infer the account from the repository remote or the git identity; (c) use the `gh` CLI's login.

**Evidence**: VS Code core's `doGetSession` in [`mainThreadAuthentication.ts`](https://github.com/microsoft/vscode/blob/main/src/vs/workbench/api/browser/mainThreadAuthentication.ts), fetched 2026-10-01, returns the session whose account matches the extension's stored account preference (`_getAccountPreference(extensionId, providerId, sessions)`) whenever the caller passes no `account` option; with no preference and several valid sessions, a silent request does not choose one. With (b) the bar would change meaning every time the user opened a repository from the other account, and a personal repository would show the Free plan instead of the seat in use. With (c) the monitor would read a credential store outside VS Code, which the plan forbids.

**Chosen**: (a).

- The provider never passes `account` to `getSession`, so the pinned preference decides the account; it never reads git config, a remote URL, the git identity, or the `gh` login.
- With several signed-in GitHub accounts and no preference, the monitor shows "Choose GitHub account" and runs an interactive `getSession` only when the user clicks it; VS Code stores that choice as the extension's preference.
- A "Switch GitHub account" command calls `getSession` with `clearSessionPreference: true` on the user's click only.
- The dashboard names the plan (`copilot_plan`) the figure comes from, never the login.

**Phase 2 acceptance test (required in 2.6)**: stub `vscode.authentication` with two GitHub sessions, a work account whose token returns `copilot-internal-user.business-member.json` and a personal account whose token returns `copilot-internal-user.personal.json`; set the extension's account preference to the work account; open a workspace whose git remote and `user.email` belong to the personal account. Assert that the provider requests the work account's session, sends only its token, and renders the member view (credits used, no percentage). Then switch the preference to the personal account and assert the Free-plan percentage view, with no workspace change. A static check asserts that the extension source contains no read of `.git/config`, `git config`, `hosts.yml`, or a `gh` invocation.

**Unblocks**: 2.2 and 2.6.

### (2) Organization pool used

**Options**: (a) sum `usageItems[].discountQuantity` from `GET /organizations/{org}/settings/billing/ai_credit/usage`; (b) sum `grossQuantity`; (c) no organization view.

**Evidence** ([billing usage](https://docs.github.com/en/rest/billing/usage), fetched 2026-09-30)

- Documented: "Gets a report of AI credit usage for an organization." "To use this endpoint, you must be an administrator of an organization within an enterprise or an organization account." "Only data from the past 24 months is accessible via this endpoint." Billing managers are not mentioned.
- Headers: `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2026-03-10`.
- Query parameters: `year` ("Default value is the current year"), `month` ("Default value is the current month"), `day` ("If specified, only return results for a single day"; no default), plus `user`, `model`, `product`. Omitting `day` returns the month.
- Response: `timePeriod {year, month, day}`, `organization`, `user`, `product`, `model`, and `usageItems[]` with `product`, `sku`, `model`, `unitType`, `pricePerUnit`, `grossQuantity`, `grossAmount`, `discountQuantity`, `discountAmount`, `netQuantity`, `netAmount`, all required. The page has no example body.
- **No field records why a discount was applied.** This is the same shape that sank the Actions monitor. What differs is the billing model: the Copilot billing page names exactly one cost reduction, the included pool ("A user's included AI credits are pooled at the billing entity level"; [usage-based billing](https://docs.github.com/en/copilot/concepts/billing-and-usage/organizations-and-enterprises/billing)), and usage beyond it is charged "at published per-credit rates". The Actions page, by contrast, stated two discount reasons in one sentence. The absence of a second reason in the docs is evidence, not proof.
- Token: the permissions reference lists this endpoint under "Organization permissions for "Administration"" read, for fine-grained PATs.
- Observed 2026-09-28 (plan Overview): 10,928.07 from the API; the billing page read 10,990 a few minutes later during active use.

**Paired reading (VERIFIED 2026-10-02)**

- API, captured 2026-10-01 23:57:30-23:57:32 UTC with the fine-grained organization token (HTTP 200): top-level keys `timePeriod` (`{year: 2026, month: 10}`, no `day` because none was requested), `organization`, and `usageItems`. One line item: `product` `Copilot`, `sku` `Copilot AI Credits`, `model` `Auto: GPT-6 Luna`, `unitType` `ai-credits`, `pricePerUnit` 0.01, `grossQuantity` = `discountQuantity` = 0.9069921, `grossAmount` = `discountAmount` = 0.009069918, `netQuantity` 0, `netAmount` 0. Sum of `discountQuantity` = 0.907 credits.
- Page, the organization's AI usage page (`github.com/organizations/{org}/settings/billing/ai_usage`, timeframe current month), read about 2026-10-02 00:05 UTC: "Included credits 1 / 13,300 AI credits", "Monthly limit resets in 30 days on November 1, 2026", "Additional usage $0.00", "Each AI credit costs $0.01"; the usage breakdown has one row, model "Auto: GPT-6 Luna", Included credits 0.91, Additional credits 0, Gross amount $0.01, Additional usage $0.00.
- The API and the page agree exactly: 0.907 rounds to the breakdown's 0.91, net 0 matches "Additional credits 0" and "$0.00" additional usage, and the organization Overview page read at 23:58 UTC also showed $0 additional usage "based on 0 additional AI credits beyond your included usage".
- **Rounding**: the page headline rounds included credits to a whole number ("1 / 13,300") while its breakdown shows two decimals (0.91). The monitor displays used credits with two decimals and computes the percentage from the unrounded sum; the dashboard says so in its tooltip, so a reader comparing against the headline knows why 0.91 appears where the page says 1.
- **Per-model field**: each API line item carries `model`, which matches the page's per-model breakdown row for row. The dashboard may list used credits per `model` as the page does.
- Distinct values present: one `product` (`Copilot`), one `sku` (`Copilot AI Credits`), one `unitType` (`ai-credits`). No line item with a discount from another SKU exists in this capture, so option (a) is not falsified. A future SKU that is not `Copilot AI Credits` is excluded from the sum and logged once, rather than counted.

**Chosen**: (a), summing `discountQuantity` over line items with `product` `Copilot` and `unitType` `ai-credits`. Verified against the page.

**Still to watch**: the paired reading was taken on day one of the cycle with less than one credit used. A mid-cycle pair taken under real use, to confirm the agreement holds at scale, is recorded as a Phase 2 verification step (the plan's Phase 2 Verification Expectation already compares the pool bar with the AI usage page); a divergence beyond normal use between the two readings is the falsifier in (5).

**Unblocks**: 2.3.

### (3) Organization pool total

**Options**: (a) `GET /orgs/{org}/copilot/billing` `.seat_breakdown.total` times the published per-seat rate for `.plan_type`; (b) a user-entered pool size; (c) no total.

**Evidence**

- Rate, quoted from [usage-based billing](https://docs.github.com/en/copilot/concepts/billing-and-usage/organizations-and-enterprises/billing): "Copilot Business | 1,900" and "Copilot Enterprise | 3,900" included AI credits per user per month; [plans](https://docs.github.com/en/copilot/get-started/plans) repeats "Total per user per month: 1,900" and "3,900". The 7 x 1,900 = 13,300 reading of 2026-09-28 agrees and is corroboration only.
- Reset: "the pool resets to the full monthly amount at 00:00:00 UTC on the first day of each calendar month." Unused credits do not carry over.
- Mid-cycle seat changes: "Adding licenses mid-cycle increases the pool immediately. Removing licenses mid-cycle doesn't shrink the pool: the decrease is reflected at the start of the next billing cycle." The page does **not** say whether an added seat contributes its full allowance or a prorated one.
- Seat endpoint ([Copilot user management](https://docs.github.com/en/rest/copilot/copilot-user-management)): "Only organization owners can view details about the organization's Copilot Business or Copilot Enterprise subscription." Classic tokens need "either the `manage_billing:copilot` or `read:org` scopes". Response `seat_breakdown` has `total`, `added_this_cycle`, `pending_cancellation`, `pending_invitation`, `active_this_cycle`, `inactive_this_cycle`, and `plan_type` is `business` or `enterprise`. `GET /orgs/{org}/copilot/billing/seats` gives each seat's `created_at`, `pending_cancellation_date`, and `plan_type`. The fine-grained permissions reference lists `GET /orgs/{org}/copilot/billing` under both "Administration" read and "GitHub Copilot Business" read, with the note "Some endpoints require more than one permission. Other endpoints work with any one permission from a set of permissions"; resolved decision 2 grants both, which satisfies either reading.

**Rules that follow from the evidence**

- Total = `seat_breakdown.total` x rate(`plan_type`). An enterprise-level pool, or a mix of plans, is out of scope: the organization view states that the figure covers this organization only.
- `approximate = true` when `added_this_cycle > 0` (proration unknown) or when `pending_cancellation > 0`. A seat removed outright this cycle still counts toward the pool but no longer appears in `total`, so the computed total can be low and the percentage high; the dashboard states this. The captured `seat_breakdown` has no "removed this cycle" field (keys: `pending_invitation`, `pending_cancellation`, `added_this_cycle`, `total`, `active_this_cycle`, `inactive_this_cycle`), so a seat removed outright this cycle is **not detectable** from this endpoint; the dashboard note covers it.
- `active_this_cycle` and `inactive_this_cycle` count seat usage, not pool size; the total uses `total` only. In the capture, 4 active plus 3 inactive equals the 7 total.

**Paired reading (VERIFIED 2026-10-02)**: the API, captured 2026-10-01 23:57 UTC, returned `plan_type` `business` and `seat_breakdown` `total` 7, `added_this_cycle` 0, `pending_cancellation` 0, `active_this_cycle` 4, `inactive_this_cycle` 3. The organization Overview page, read 23:58 UTC, showed 7 billable Copilot licenses, and the maintainer confirmed no seat was added or removed this month. The AI usage page, read about 2026-10-02 00:05 UTC, showed a pool of "13,300 AI credits" resetting "on November 1, 2026". Computed total 7 x 1,900 = 13,300 matches it exactly, with `approximate` false because `added_this_cycle` and `pending_cancellation` are both 0. (A separate GitHub Team subscription on the same page, 9 licenses, is not Copilot and is not counted.)

**Open verification item (not a failure)**: proration of a seat added mid-cycle. This cycle had no added seat, so the rule "`approximate` when `added_this_cycle > 0`" stands untested against the page. It is checked the first time a seat is added, by comparing the computed total with the AI usage page's pool figure; until then the label stays "approximate" in that case.

**Chosen**: (a), with the `approximate` rule above. Verified for a cycle with no seat change.

**Unblocks**: 2.3.

### (4) Members without billing access

**Evidence**

- User-level budgets exist: "The user-level budget (ULB) caps how many AI credits a single user can consume in a billing cycle" from the shared pool and from additional (metered) usage ([budgets concept](https://docs.github.com/en/copilot/concepts/billing-and-usage/organizations-and-enterprises/budgets)). The page does not say where a member can see their own budget.
- The budgets REST API ([budgets](https://docs.github.com/en/rest/billing/budgets)) supports `budget_scope: "user"` but every endpoint requires that "The authenticated user must be an organization admin or billing manager." No documented endpoint lets a member read their own budget.

- Captured 2026-10-01 23:55 UTC on a Copilot Business seat (the organization owner's own seat, no user-level budget checked): every `quota_snapshots` entry is `unlimited: true` with `entitlement: 0` and `overage_entitlement: 0`. **Chosen**: the member view shows credits used with no percentage, consistent with the capture. A user-level budget becomes the denominator only if a future capture of `copilot_internal/user` on a seat that has a budget shows it as a limited quota (`unlimited: false` with `entitlement > 0`); the mapping rule in (1) then picks it up with no code change. The maintainer's organization has no such budget, so this stays untested and is not a blocker. The monitor never divides by 1,900 to show a "fair share".

**Unblocks**: 2.4.

### (5) Reopen condition

The withdrawal record reopens a GitHub monitor only when GitHub serves both consumed and total for a scope.

- **Consumed**: served, by a documented endpoint (2).
- **Total**: a served seat count times a constant GitHub publishes on its billing page (3). No input is inferred from present-day state applied to historical data, which is the specific mechanism that failed for Actions.
- **Answer (VERIFIED 2026-10-02)**: the condition is met for the organization pool and for a personal plan whose quota `copilot_internal/user` serves; it is not met for a member without billing access, who gets no percentage.
- **Evidence**: organization pool, API at 2026-10-01 23:57 UTC against the AI usage page at about 2026-10-02 00:05 UTC: used 0.907 (API) against 0.91 in the page breakdown and "1" in its rounded headline; total 13,300 computed (7 seats x 1,900) against "13,300 AI credits" on the page; additional usage 0 against "$0.00"; reset 2026-11-01 against "November 1, 2026". Personal plan, API at 23:41 UTC against the billing page at 23:44 UTC: every quota unused against "$0" and 0 additional credits. Member seat, API at 23:55 UTC: unlimited quotas with no entitlement, so no percentage, as (4) requires.
- **Falsifiers**: the API sum and the billing page diverge by more than normal use between two readings taken minutes apart; a discounted line item that is not included-pool usage; GitHub changing the per-seat rate without the page changing; `copilot_internal/user` dropping its quota fields. On any of these the affected view shows credits used without a percentage.
- **Open verification items, not failures**: the paired reading was taken with under one credit used, so a mid-cycle pair under real use is repeated in the Phase 2 Verification Expectation; the proration rule in (3) awaits a cycle with an added seat.

**Unblocks**: 1.3 and every Phase 2 sub-task.

### (1) Copilot usage source

**Options**: (a) the Copilot Usage Monitor writes a percentages-only state file and the hook reads it; (b) the hook calls `api.github.com/copilot_internal/user` itself; (c) no automatic layer for Copilot.

**Evidence**

- A hook is a child process of the agent host. The VS Code secret store is reachable only through the extension host API (`context.secrets`), and the VS Code GitHub session only through `vscode.authentication.getSession` (both quoted in the Copilot usage monitor section, item (1)). A hook subprocess has neither, so (b) cannot obtain a token without the hook reading a credential store of its own, which the plan forbids (resolved decision 3).
- The schema is item (6) above: `schema_version`, `provider: "copilot"`, `fetched_at`, `approximate`, and `windows[]` of `{name: "monthly", percent, resets_at, source: "personal" | "organization"}`. It carries no login, organization name, account id, email, or token.

**Chosen**: (a). The probe's Copilot provider in 6.2 reads `~/.nexus-hub/state/usage-probe/copilot.json` and nothing else: no network call, no credential read.

- A missing file, an unparseable file, a `schema_version` other than 1, a `provider` other than `"copilot"`, or a `fetched_at` older than 30 minutes reads as `unavailable`.
- The window carried is `monthly`: the personal plan's quota percentage when `source` is `"personal"`, or the organization pool percentage when the owner connected a token and `source` is `"organization"`. When `approximate` is true the guard still acts on the percentage, because the error from proration makes the shown percentage high rather than low (item (3) above), which errs toward an early handoff.
- A Business or Enterprise member with neither figure gets `windows: []`, so the guard stays silent for them. That member still has the checkpoint rule and `/handoff`.
- Declined: (b), because it cannot reach the token; (c), because the monitor already holds the figure and a file read costs nothing.

**Unblocks**: 6.2 and 7.1.

### (2) Platform detection inside the hook

### (4) Copilot output schema and the compatibility wrapper

Sub-task 7.1. Fetched 2026-10-01 from the [VS Code hooks reference](https://raw.githubusercontent.com/microsoft/vscode-docs/main/docs/agents/reference/hooks-reference.md).

**Evidence**

- `PostToolUse` output: "`hookSpecificOutput.hookEventName` | `"PostToolUse"` | Identifies the event-specific output" and "`hookSpecificOutput.additionalContext` | string | Additional context for the model."
- `UserPromptSubmit`: "The hook supports the common output", which is `continue`, `stopReason`, and `systemMessage`. It has no context field.
- `Stop` output: `{"hookSpecificOutput": {"hookEventName": "Stop", "decision": "block", "reason": "..."}}`, where `decision: "block"` "Prevents the agent execution from stopping" and `reason` is "Required when `decision` is `"block"`". The page adds: "Check `stop_hook_active` to prevent the agent from continuing indefinitely."
- Every Copilot hook runs through `copilot-hook-compat.py` (`scripts/lib/integrations/_cascade_hook_compat.py`). Before this phase, its `translate_copilot_payload` passed the child only `hook_event_name`, `tool_name`, `tool_input`, `session_id`, `cwd`, and `transcript_path`, so the child never saw `timestamp` or `stop_hook_active`; and `translate_child_result` lifted `additionalContext` to the top level only, the Copilot CLI shape, which the VS Code reference does not read.

**Chosen**

- Copilot gets the mid-session directive on `PostToolUse` only, rendered as `hookSpecificOutput.additionalContext`. `UserPromptSubmit` stays registered (it is derived from `settings.json`) and the guard answers it with nothing.
- Copilot gets the turn-end continuation in the `Stop` shape quoted above. The wrapper already emits both the top-level and the `hookSpecificOutput` form for a blocked `Stop`.
- The wrapper now passes `timestamp` and `stop_hook_active` through to the child, and for `PostToolUse` emits `hookSpecificOutput` beside the top-level `additionalContext`.
- The Copilot signature in (2) holds, read after the wrapper: the script runs from the `nexus-hub-scripts` directory beside `copilot-hook-compat.py`, and `timestamp` is an ISO-8601 string, as the VS Code reference documents. A payload whose `timestamp` is missing or not an ISO-8601 string stays silent. Copilot CLI reads the same hooks directory; its payload has not been captured, so whether it passes this signature is unverified. The `PENDING maintainer reading` in (2) still applies.

**Unblocks**: 7.1 and 7.2.

### (5) Turn-end interplay with the completion gate

Phase 7 review, finding F3. Recorded 2026-10-01 from the orchestrator.

**Problem**: during a full `/implement` run, the v4.13.6 completion gate and `usage-guard` both answer `Stop`, in that order in `catalog/hooks/settings.json` and in Cursor's native `stop` list. At the threshold they give opposite instructions: the gate says continue with the next unmet item, the guard says hand off and start no new work. After the hand-off the gate keeps refusing until its no-progress rule writes a `no-progress` blocker, so a run that stopped correctly for a usage limit ends looking stuck.

**Options**

- (a) Status quo. The conflict is bounded (one guard continuation, then the gate's three no-progress refusals), but the run records a false `no-progress` blocker and spends turns at the cap.
- (b) The guard yields to the gate: emit no continuation while a full-run record is bound. The agent then keeps working into the cap, which is the failure the guard exists to prevent.
- (c) The gate yields when `.nexus-hub/handoff.md` carries a usage-limit header, with no usage check. Rejected: an agent could release any run by writing that file.
- (d) The gate yields only when the handoff header is newer than its last refusal AND the probe confirms a window at or over `NEXUS_HANDOFF_THRESHOLD`.

**Chosen**: (d). `scripts/completion_gate.py` allows the stop, counts no refusal, writes no blocker, and leaves the record unchanged; it prints one stderr line that the run stopped for a usage-limit handoff and resumes when the user pastes the prompt. It loads `usage-guard.py` and `_usage_probe.py` only from the calling hook's directory (`NEXUS_GATE_HOOK_DIR`, exported by `completion-gate.sh` and `.ps1`) and never from inside the repository. When the probe is unavailable or below the threshold, the gate behaves exactly as before. The rule is owned by the completion contract (`catalog/skills/workflow/implement-phase/references/completion-contract.md`, "Usage-limit handoff"). Residual: a process with the user's file access could write a probe cache under `~/.nexus-hub/state/usage-probe/`; that is the same home-directory boundary the contract's threat model already states.

**Cursor merge order**: the [Cursor hooks page](https://cursor.com/docs/hooks), fetched 2026-10-01, says "All matching hooks from every source run, and Cursor merges their responses", and "For other fields, such as `followup_message`, the last response wins", with sources merged in its priority order. It does not say how two entries in the same `hooks.json` array combine. `PENDING verification`: with both the gate and the guard returning `followup_message` from one native `stop` array, which message Cursor sends. Until then, the guard's directive also tells the agent to write the handoff first if another hook asks it to continue.

### (6) Guard state after review

Phase 7 review, findings F1, F2, and F4.

- A window counts as announced only when a message about it was emitted. The platform's prior-continuation flag (`stop_hook_active`, Cursor `loop_count`) is honored only when this guard's own continuation caused that turn, because the completion gate sets it on every chained turn and Cursor counts every hook's follow-ups.
- A window is forgotten, so the next crossing warns again, when a usable reading puts it below the clear line (the threshold minus up to 5 points, which keeps a reading that wavers around 99% quiet) or when its reset time moves by more than 30 minutes (a new period).
- At turn end every window over the threshold whose continuation was not sent gets one, highest first, one per turn end. The bound is one directive and one continuation per window period per session.
