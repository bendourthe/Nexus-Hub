## Copilot usage monitor

Sub-task 1.1. The monitor may display a figure only when GitHub serves it, or when it is a served count multiplied by a constant GitHub publishes. Nothing below is reconstructed from data GitHub does not serve, which is the defect that withdrew the earlier GitHub monitor ([withdrawal record](../../../../decisions/implemented/architecture/2026-08-22-withdraw-the-github-usage-monitor.md)).

### (1) Personal figure

**Options**: (a) `GET https://api.github.com/copilot_internal/user` with the VS Code GitHub session, the endpoint the Copilot extension's own usage popup reads; (b) the documented `GET /users/{username}/settings/billing/ai_credit/usage`; (c) no personal figure.

**Evidence**

- `copilot_internal/user` is **undocumented**. A search of docs.github.com and github.blog on 2026-09-30 returned no page that names it, and it does not appear in the fine-grained token permissions reference ([permissions page](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens)). It is the same class of dependency as the Codex monitor's `wham/usage` endpoint: it can change shape without notice.
- The documented alternative exists: `GET /users/{username}/settings/billing/ai_credit/usage`, "Gets a report of AI credit usage for a user" ([billing usage](https://docs.github.com/en/rest/billing/usage)), under "User permissions for "Plan"" read in the permissions reference. It returns line items of credits used, not the plan quota, so on its own it gives a numerator and no denominator.
- Published personal plan allowances ([plans](https://docs.github.com/en/copilot/get-started/plans)): Copilot Pro "Base: 1,000" plus a 500 flex allotment (1,500 total); Copilot Pro+ "Base: 3,900" plus a 3,100 flex allotment (7,000 total); Copilot Free "An allowance of GitHub AI Credits" with no number stated. The page does not state the personal reset date.
- VS Code authentication API ([vscode-api authentication](https://code.visualstudio.com/api/references/vscode-api#authentication)): `authentication.getSession(providerId, scopeListOrRequest, options?)` resolves to "an authentication session or undefined if a silent flow was used and no session was found". `silent`: "Whether to request a session silently without user interaction. When `true`, no UI is shown for authentication." `createIfNone`: "Whether a new session should be created if none exists. When `true`, the user may be prompted to authenticate." `account`: "If not provided, the user will be shown a quickpick to choose which account they would like to use." `clearSessionPreference` clears the remembered account choice. The session carries `accessToken`, `account`, `id`, and `scopes`. The documentation does **not** list the scopes the built-in `github` provider accepts.
- Account pinning ([VS Code 1.94 release notes](https://code.visualstudio.com/updates/v1_94)): an extension's account is changed from the Accounts menu > account > Manage Trusted Extensions > gear icon, or from the extension's gear icon > Account Preferences; "Choosing any of these options takes you to a Quick Pick where you can change the account that an extension uses." This is a per-extension preference inside VS Code; it does not touch git's `user.name`/`user.email` or the `gh` CLI's stored login, which are separate stores.

**Pending**

- `PENDING maintainer reading`: which response fields carry entitlement, used, remaining or percent remaining, and the reset date, on a personal plan and on a Business member seat. Captured by `capture-copilot.ps1` as `copilot-internal-user.personal.json` (and a second run on the member account).
- `PENDING maintainer reading`: which token types the endpoint accepts (HTTP status per attempt is recorded in `capture-notes.txt`), and therefore the minimum scope list to pass to `getSession`. Until settled, 2.2 requests the narrowest list the capture proves sufficient; an empty or `read:user` list is the first candidate.
- `PENDING maintainer reading`: the billing-page figure (github.com/settings/copilot or the billing page) at the same time as the capture, with both UTC timestamps.

**Chosen**: (a) for the percentage, because it is the only source that serves the quota beside the used figure; the monitor treats it as fragile, ignores unknown fields, and falls back to "credits used, no percentage" when no quota field is present. (b) is recorded as the documented fallback for the used figure if (a) disappears. Provisional until the readings above land.

**Unblocks**: 2.2.

### (2) Organization pool used

**Options**: (a) sum `usageItems[].discountQuantity` from `GET /organizations/{org}/settings/billing/ai_credit/usage`; (b) sum `grossQuantity`; (c) no organization view.

**Evidence** ([billing usage](https://docs.github.com/en/rest/billing/usage), fetched 2026-09-30)

- Documented: "Gets a report of AI credit usage for an organization." "To use this endpoint, you must be an administrator of an organization within an enterprise or an organization account." "Only data from the past 24 months is accessible via this endpoint." Billing managers are not mentioned.
- Headers: `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2026-03-10`.
- Query parameters: `year` ("Default value is the current year"), `month` ("Default value is the current month"), `day` ("If specified, only return results for a single day"; no default), plus `user`, `model`, `product`. Omitting `day` returns the month.
- Response: `timePeriod {year, month, day}`, `organization`, `user`, `product`, `model`, and `usageItems[]` with `product`, `sku`, `model`, `unitType`, `pricePerUnit`, `grossQuantity`, `grossAmount`, `discountQuantity`, `discountAmount`, `netQuantity`, `netAmount`, all required. The page has no example body.
- **No field records why a discount was applied.** This is the same shape that sank the Actions monitor. What differs is the billing model: the Copilot billing page names exactly one cost reduction, the included pool ("A user's included AI credits are pooled at the billing entity level"; [usage-based billing](https://docs.github.com/en/copilot/concepts/billing-and-usage/organizations-and-enterprises/billing)), and usage beyond it is charged "at published per-credit rates". The Actions page, by contrast, stated two discount reasons in one sentence. The absence of a second reason in the docs is evidence, not proof.
- Token: the permissions reference lists this endpoint under "Organization permissions for "Administration"" read, for fine-grained PATs.
- Observed 2026-09-28 (plan Overview): 10,928.07 from the API; the billing page read 10,990 a few minutes later during active use.

**Pending**

- `PENDING maintainer reading`: a fresh capture with the billing-page "included" reading taken immediately after, both timestamps recorded. Falsifier: sum of `discountQuantity` exceeds the pool total, or differs from the page by more than plausible use between the two readings.
- `PENDING maintainer reading`: the distinct `product`, `sku`, and `unitType` values present, so 2.3 sums only Copilot AI-credit items and not another product that happens to report on this route. If any item has `discountQuantity > 0` with a `sku` that is not an included-pool SKU, option (a) is falsified and the monitor shows credits used with no percentage.

**Chosen**: (a), filtered to Copilot AI-credit line items, provisional on the two readings.

**Unblocks**: 2.3.

### (3) Organization pool total

**Options**: (a) `GET /orgs/{org}/copilot/billing` `.seat_breakdown.total` times the published per-seat rate for `.plan_type`; (b) a user-entered pool size; (c) no total.

**Evidence**

- Rate, quoted from [usage-based billing](https://docs.github.com/en/copilot/concepts/billing-and-usage/organizations-and-enterprises/billing): "Copilot Business | 1,900" and "Copilot Enterprise | 3,900" included AI credits per user per month; [plans](https://docs.github.com/en/copilot/get-started/plans) repeats "Total per user per month: 1,900" and "3,900". The 7 x 1,900 = 13,300 reading of 2026-09-28 agrees and is corroboration only.
- Reset: "the pool resets to the full monthly amount at 00:00:00 UTC on the first day of each calendar month." Unused credits do not carry over.
- Mid-cycle seat changes: "Adding licenses mid-cycle increases the pool immediately. Removing licenses mid-cycle doesn't shrink the pool: the decrease is reflected at the start of the next billing cycle." The page does **not** say whether an added seat contributes its full allowance or a prorated one.
- Seat endpoint ([Copilot user management](https://docs.github.com/en/rest/copilot/copilot-user-management)): "Only organization owners can view details about the organization's Copilot Business or Copilot Enterprise subscription." Classic tokens need "either the `manage_billing:copilot` or `read:org` scopes". Response `seat_breakdown` has `total`, `added_this_cycle`, `pending_cancellation`, `pending_invitation`, `active_this_cycle`, `inactive_this_cycle`, and `plan_type` is `business` or `enterprise`. `GET /orgs/{org}/copilot/billing/seats` gives each seat's `created_at`, `pending_cancellation_date`, and `plan_type`. The fine-grained permissions reference lists `GET /orgs/{org}/copilot/billing` under both "Administration" read and "GitHub Copilot Business" read, with the note "Some endpoints require more than one permission. Other endpoints work with any one permission from a set of permissions"; resolved decision 2 grants both, which satisfies either reading.

**Rules that follow from the evidence**

- Total = `seat_breakdown.total` x rate(`plan_type`). An enterprise-level pool, or a mix of plans, is out of scope: the organization view states that the figure covers this organization only.
- `approximate = true` when `added_this_cycle > 0` (proration unknown) or when `pending_cancellation > 0`. A seat removed outright this cycle still counts toward the pool but no longer appears in `total`, so the computed total can be low and the percentage high; the dashboard states this. `PENDING maintainer reading`: whether the current `seat_breakdown` fields make a seat removed this cycle detectable at all.
- `PENDING maintainer reading`: proration of an added seat, by comparing the computed total with the billing page in a cycle where a seat was added.

**Chosen**: (a), with the `approximate` rule above.

**Unblocks**: 2.3.

### (4) Members without billing access

**Evidence**

- User-level budgets exist: "The user-level budget (ULB) caps how many AI credits a single user can consume in a billing cycle" from the shared pool and from additional (metered) usage ([budgets concept](https://docs.github.com/en/copilot/concepts/billing-and-usage/organizations-and-enterprises/budgets)). The page does not say where a member can see their own budget.
- The budgets REST API ([budgets](https://docs.github.com/en/rest/billing/budgets)) supports `budget_scope: "user"` but every endpoint requires that "The authenticated user must be an organization admin or billing manager." No documented endpoint lets a member read their own budget.

**Chosen**: the member view shows credits used with no percentage. A user-level budget becomes the denominator only if a capture of `copilot_internal/user` on a member seat that has a budget shows it there (`PENDING maintainer reading`, and only if such a budget exists in the maintainer's organization). The monitor never divides by 1,900 to show a "fair share".

**Unblocks**: 2.4.

### (5) Reopen condition

The withdrawal record reopens a GitHub monitor only when GitHub serves both consumed and total for a scope.

- **Consumed**: served, by a documented endpoint (2).
- **Total**: a served seat count times a constant GitHub publishes on its billing page (3). No input is inferred from present-day state applied to historical data, which is the specific mechanism that failed for Actions.
- **Provisional answer**: the condition is met for the organization pool and for a personal plan whose quota `copilot_internal/user` serves; it is not met for a member without billing access, who gets no percentage.
- **Falsifiers**: the API sum and the billing page diverge by more than normal use between two readings taken minutes apart; a discounted line item that is not included-pool usage; GitHub changing the per-seat rate without the page changing; `copilot_internal/user` dropping its quota field. On any of these the affected view shows credits used without a percentage.
- `PENDING maintainer reading`: the fresh paired readings in (2) and (3) turn this answer from provisional to settled.

**Unblocks**: 1.3 and every Phase 2 sub-task.

### (6) Handoff state file

Settled by the maintainer (resolved decision 3). Path: `~/.nexus-hub/state/usage-probe/copilot.json`. Schema:

```json
{
  "schema_version": 1,
  "provider": "copilot",
  "fetched_at": "2026-09-30T12:00:00Z",
  "approximate": false,
  "windows": [
    {
      "name": "monthly",
      "percent": 82.6,
      "resets_at": "2026-10-01T00:00:00Z",
      "source": "organization"
    }
  ]
}
```

- `source` is `"personal"` or `"organization"`. `percent` is a number from 0 to 100; when no percentage exists (a member without billing access), the monitor writes `windows: []` rather than a null percent, so the guard stays silent.
- The file carries no login, organization name, account id, email, or token. Phase 2's leak test asserts this.
- Organization `resets_at` is the first day of the next calendar month at 00:00:00 UTC, from (3). Personal `resets_at` comes from the captured response field (`PENDING maintainer reading`).
- 4.1 copies this schema into the probe cache contract (T009) and treats a missing file, or one older than 30 minutes, as `unavailable`.

**Unblocks**: 2.5 and 4.1.

## Handoff guard decisions

Sub-task 4.1. Written 2026-10-01. Documentation claims were fetched from first-party pages that day; the Claude Code payload was captured live that day.

**Execution order.** Phase 4 ran before Phases 1-3, which wait on the maintainer's live Copilot readings. Its only dependency on them is the Copilot state-file schema, which the maintainer settled as item (6) of the Copilot usage monitor section above. Item (1) below therefore copies that schema rather than a Phase 2 implementation; if Phase 2 changes the schema, item (1) and the probe contract in 6.2 change with it.

### (1) Copilot usage source

**Options**: (a) the Copilot Usage Monitor writes a percentages-only state file and the hook reads it; (b) the hook calls `api.github.com/copilot_internal/user` itself; (c) no automatic layer for Copilot.

**Evidence**

- A hook is a child process of the agent host. The VS Code secret store is reachable only through the extension host API (`context.secrets`), and the VS Code GitHub session only through `vscode.authentication.getSession` (both quoted in the Copilot usage monitor section, item (1)). A hook subprocess has neither, so (b) cannot obtain a token without the hook reading a credential store of its own, which the plan forbids (resolved decision 3).
- The schema is item (6) above: `schema_version`, `provider: "copilot"`, `fetched_at`, `approximate`, and `windows[]` of `{name: "monthly", percent, resets_at, source: "personal" | "organization"}`. It carries no login, organization name, account id, email, or token.

**Chosen**: (a). The probe's Copilot provider in 6.2 reads `~/.nexus-hub/state/usage-probe/copilot.json` and nothing else: no network call, no credential read.

- A missing file, an unparseable file, a `schema_version` other than 1, a `provider` other than `"copilot"`, or a `fetched_at` older than 30 minutes reads as `unavailable`.
- The window carried is `monthly`: the personal plan's quota percentage when `source` is `"personal"`, or the organization pool percentage when the owner connected a token and `source` is `"organization"`. When `approximate` is true the guard still acts on the percentage, because the error from proration makes the shown percentage high rather than low (item (3) above), which errs toward an early handoff.
- A Business or Enterprise member with neither figure gets `windows: []`, so the guard stays silent for them. That member still has the checkpoint rule and `/handoff`.
- Declined: (b), because it cannot reach the token; (c), because the monitor already holds the figure and a file read costs nothing.

**Unblocks**: 6.2 and 7.1.

### (2) Platform detection inside the hook

**Options**: (a) an explicit `--platform <key>` argument in each registration; (b) inference by elimination ("Claude Code sends none of the other markers"); (c) a positive signature per platform, silent when none matches.

**Evidence against (a)**: three parsers read the script name from the LAST command token, so a trailing argument would be taken as the script. `script_basename()` in `scripts/lib/integrations/_hooks_common.py` returns `os.path.basename(parts[-1])` and serves the Codex, Gemini CLI, Qwen, Kimi, and Copilot adapters; `catalog/hooks/cursor-hook-compat.py` rewrites commands by a regex on the script path and its launcher takes `hook_name = command[-1]`.

**Evidence against (b)**: Qwen Code, Gemini CLI, and Kimi receive the same `settings.json` hooks. Qwen's hooks page lists Claude-style event names (`PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `Stop`) and sets `CLAUDE_PROJECT_DIR` for command hooks ([Qwen hooks](https://qwenlm.github.io/qwen-code-docs/en/users/features/hooks/)), so a Qwen payload would be misread as Claude Code.

**Signatures, by first-party source**

| Platform | Positive signature | Source |
|---|---|---|
| Cursor | `cursor_version` in the payload; `CURSOR_VERSION` in the environment | [Cursor hooks](https://cursor.com/docs/hooks): base fields "conversation_id, generation_id, model, model_id, model_params, hook_event_name, cursor_version, workspace_roots, user_email, transcript_path"; environment "CURSOR_PROJECT_DIR, CURSOR_VERSION, CURSOR_USER_EMAIL, CURSOR_TRANSCRIPT_PATH, CURSOR_CODE_REMOTE, CLAUDE_PROJECT_DIR". Cursor sets `CLAUDE_PROJECT_DIR` too, so that variable identifies nothing. Already used by `completion_gate.py` and `cursor-hook-compat.py`. |
| Codex | `turn_id` and `model` both present, no `cursor_version` | [Codex hooks](https://learn.chatgpt.com/docs/hooks): common fields "session_id, transcript_path, cwd, hook_event_name, model, permission_mode, turn_id (turn-scoped hooks)". The guard's events (`UserPromptSubmit`, `PostToolUse`, `Stop`) are all turn-scoped, so `turn_id` is present on each. Cursor also sends `model`, which is why `cursor_version` is checked first. |
| Claude Code | `scratchpad_dir` in the payload, or (when the session has no scratchpad) `prompt_id` or `permission_mode` together with `CLAUDE_CODE_ENTRYPOINT` in the environment; in both cases no `timestamp`, `turn_id`, `cursor_version`, `session_title`, or `client_type` key | [Claude Code hooks](https://code.claude.com/docs/en/hooks) documents `scratchpad_dir` ("Path to the session's scratchpad directory. **Chosen**: (c). The guard tests Cursor, then Codex, then Kimi, Gemini CLI, and Qwen (each of which ends in silence), then Claude Code and Copilot by their positive signatures; anything else is silent.

**Unblocks**: 7.1 and 7.2.

### (2b) Cursor delivery path

**Evidence**: Cursor imports Claude `settings.json` hooks and runs them through `cursor-hook-compat.py`, and it also runs its native `hooks.json`. Registering `usage-guard` in both would inject the directive twice per event.

**Chosen**: native registration only. `usage-guard` emits nothing when it sees a `cursor_version` payload while running from a `.claude/hooks/` path. This keeps Cursor covered when Claude Code is not installed.

**Unblocks**: 7.2.

### (3) Tracked windows

| Platform | Window | Field, from the existing monitor or hook | Guard name |
|---|---|---|---|
| Claude Code | 5-hour | `five_hour.utilization` (`extensions/claude-usage-monitor/src/providers/claude.ts`; `catalog/hooks/usage-display.sh`) | `five_hour` |
| Claude Code | weekly | `seven_day.utilization`, plus every model-scoped `seven_day_*` object the response carries (today `seven_day_opus`, `seven_day_sonnet`, `seven_day_oauth_apps`, `seven_day_cowork` in `claude.ts`), each mapped to `weekly`; the guard acts on the highest | `weekly` |
| Codex | weekly only | the rate-limit window whose `limit_window_seconds` is the 7-day length, read from `rate_limit.primary_window` or `rate_limit.secondary_window` (`extensions/codex-usage-monitor/src/providers/codex.ts`). Classify by duration, not by position: `codex.ts` records that a weekly-only plan puts its weekly window in `primary_window` with a null `secondary_window`. The 5-hour window is not tracked, per resolved decision 5. Percent field `used_percent`; reset `reset_at` (epoch seconds). | `weekly` |
| Cursor | monthly | the plan's included-usage percentage for the billing cycle, taken as delivered and never recomputed (`extensions/cursor-usage-monitor/src/providers/liveTransport.ts` finding 2): `planUsage.totalPercentUsed` when present, otherwise the higher of `planUsage.autoPercentUsed` and `planUsage.apiPercentUsed`; reset `billingCycleEnd` (epoch milliseconds as a string) | `monthly` |
| GitHub Copilot | monthly | `windows[0].percent` from the state file in (1) | `monthly` |

Taking the highest of several weekly or pool percentages can fire the guard for a pool the user is not drawing on. That is the safe direction (an early handoff, once per session per window), and the alternative needs the guard to know which model the session is using, which no payload states reliably. `PENDING maintainer reading`: a fresh Cursor capture confirming `totalPercentUsed` is still served; until then 6.2 falls back to the two pool fields.

**Unblocks**: 6.2.
