# v4.13.11 Ledger Decisions

This record defines the Phase 2 ledger and migration choices against develop `ae60a3240a538a84bf8cfc2f92b6612594e0d226`. It is used while normalizing historical origins, preserving residual obligations, and preparing the migration approval baseline.

## Canonical markers

Selected on 2026-10-09: normalize actual item headings to the existing terminal ` - RESOLVED`, ` - CLOSED`, or ` - MIGRATED to vX.Y.0` syntax. Preserve historical text and add dated body evidence rather than teaching the parser that ACCEPTED, CHECKED, body prose, or arbitrary table rows prove closure. Unknown structures continue to refuse closure. This reuses the current grammar and makes disposition explicit for readers as well as the helper.

Alternatives considered: accepting all historical marker variants would reduce document edits but could silently retire work whose acceptance has a residual; broad table parsing would conflate source items with repeated reconciliation summaries. Neither is justified. Narrow structural compatibility will be added only if an audited valid structure cannot be represented with the existing grammar; no such addition is authorized by this decision alone.

Audit actual refused rows by source file and line. Convert genuine source gap rows to existing heading or resolved-subsection form, with all cells retained. Reconciliation, counts, and binding tables are metadata only when their obligations are independently represented and traceable. Keep those tables and format their identifiers as references; never hide an unaccounted obligation as metadata. Derive Open items from parsed state after normalization.

## Migration destination completeness

The existing helper reuses the first entry whose Migrated from line matches. A stub or two matching entries can therefore cause source mutation without preserving the source obligation. Repair the existing preflight: require exactly one matching destination, its exact target section, preserved title, and the full reconciled source body after move-aware link rewriting. Preserve every origin, owner, acceptance criterion, and proving command by checking the complete content rather than a selected field subset. Added destination evidence is allowed; omitted or altered required content is refused before either file is written.

Use the same completeness predicate in migration verification so a historical or subsequently truncated copy cannot pass status merely because provenance exists. Keep approval, forward-minor, next-minor, severity, and source-history gates. Negative fixtures cover provenance-only stubs, truncated bodies, duplicate matching entries, and wrong patch sections. A complete existing copy must remain idempotent. No new migration schema or sweep framework is introduced.
