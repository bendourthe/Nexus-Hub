# v4.13.9 hook size bound - measurement and classification

Summary: measured on-disk growth of every catalog hook that appends to or rewrites a file, classified into append-only, bounded-rotation, and intentional-overwrite, with the absolute caps and known breaches that `catalog/hooks/tests/test_hook_size_bound.py` enforces.
Read this when: changing a file-writing hook, adding a new one, or deciding whether a size-bound failure or xfail is a regression or a known gap.
Covers: method and isolation, the measured table (2026-10-03), per-class rules, known breaches, the auto-devlog.sh liveness defect, encoding inflation on Windows, and the hooks that were skipped with reasons.

## Method

Each hook ran in a temp root on a Windows 11 host (Git Bash for `.sh`, Windows PowerShell 5.1 for `.ps1`, the current Python for `.py`). Every hook got 20 ordinary synthetic events, then one multi-byte-payload event (500 code points, 1500 bytes of UTF-8), then one oversized-payload event (64 KiB in each payload-controlled string field the hook copies). The multi-byte event runs before the oversized one, so an overwrite file or a re-listed commit does not carry the 64 KiB field into the multi-byte reading.

Isolation: HOME, USERPROFILE, HOMEDRIVE/HOMEPATH, APPDATA, LOCALAPPDATA, TMP/TEMP/TMPDIR, every XDG_* and every NEXUS_* path variable point into the temp root. Each run starts from a temp git repository with no global or system git config. Provider credentials are removed from the child environment, proxies point at a closed local port, and in-process sockets refuse to connect. A guard snapshots the real `~/.nexus-hub`, `~/.claude`, and this repository's `git status` before and after each run. It fails on any change that carries the run's unique token. Every synthetic event carries that token in its session id, its temp repository name, or its payload.

The guard attributes changes by token instead of requiring strict equality. The user's own installed hooks and concurrent agent sessions write to the real `~/.claude` and `~/.nexus-hub` while the suite runs, so strict equality would fail on their writes. The second run saw one or two such unattributed changes per case; they were reported and ignored. Meta-tests prove the guard fails a fixture hook that writes to a sentinel "real home" or into the "real" repository, and passes one that stays in its temp home.

Bytes per event: for append-only and rotation targets, the median growth over the 20 ordinary events; for overwrite targets, the resulting file size. The oversized and multi-byte columns use the same convention for that single event. "After 20" is the file size after the 20 ordinary events.

## Classes and rules

- **append-only**: the file never shrinks, and each event adds at most an absolute per-event cap. Members: `session-summary` session log, `auto-devlog` DEVLOG. The DEVLOG is rewritten on each event, but it only ever gains an entry, so it is classified by its growth, not by its write mechanism.
- **bounded-rotation**: the file stays at or under its documented cap after more events than the cap. Members: `learning-capture` (halves by lines above `NEXUS_LEARNING_MAX_BYTES`, default 1 MiB) and `provenance-ledger` (keeps the last `NEXUS_PROVENANCE_MAX` lines, default 500). The per-event caps also apply.
- **intentional-overwrite**: the resulting file stays under an absolute bound, so an oversized field must be truncated. Members: the `session-summary` digest and the `skill-tracker` state file (the de-duplicated list of skill names used in one session).

The test also checks liveness: under default caps no rotation happens within 20 events, so every ordinary event must add bytes to an append-only or rotation file. Without this check, a hook that runs, exits 0, and writes nothing would pass every size assertion.

Absolute caps in the test, with reasoning recorded next to each: learning-capture 1024 B normal and 2048 B multi-byte or oversized; provenance-ledger 1024 B normal and multi-byte, 8192 B oversized; session log 512 B per row; session digest 8192 B; DEVLOG 4096 B per entry for ASCII subjects and 8192 B for the multi-byte case; skill-tracker state 32768 B (the whole 339-skill catalog fits).

## Known breaches (reported, not fixed by this plan)

The test lists each breach in `KNOWN_BREACHES`. It asserts that the breach still reproduces and then xfails, so fixing a hook makes the test fail until its entry is removed.

- **learning-capture (.sh and .ps1)**: `prompt_sample` is cut to 400 characters, but `hook_event_name` and `tool_name` are copied whole. Two 64 KiB fields produce a ~131.5 KB line. Rotation recovers on a later event, but one event can still exceed the byte cap.
- **provenance-ledger (.sh and .ps1)**: the path is recorded whole (65699 B line). Rotation bounds lines, not bytes, so the ledger's worst case is `NEXUS_PROVENANCE_MAX` times the longest path. Real paths are bounded by the OS (4096 on Linux, 32767 on Windows with long paths), but the payload itself is not validated.
- **session-summary (.ps1; .sh only when jq is on PATH)**: `session_duration` is copied whole into the log row (65604 B) and into the digest (65751 B). The multi-byte duration produced a 3568 B log row against a 512 B cap. The `.sh` leg copies the field only through `jq`, which this host lacks, so the `.sh` row stayed at 70 B. On a CI runner with `jq`, the test expects the same breach for `.sh`.
- **auto-devlog (.ps1)**: commit subjects are listed whole. A 64 KiB subject produced a 70099 B entry, and it is re-listed in later entries while it stays newer than the newest entry date.
- **skill-tracker (.py)**: the skill name is stored whole. A 64 KiB name made a 74784 B state file against the 32768 B bound.

## Defect found: auto-devlog.sh drops entries after the second one

This is a correctness defect, not a size breach. `auto-devlog.sh` computes `INSERT_LINE = FIRST_H2_LINE - 1` and has awk print the entry before that line. On a standard `# Title`, blank line, `## [date]` file, the first entry lands above the blank line, and the second lands above the title. Once a `## [` heading sits on line 1, `INSERT_LINE` is 0, awk's `NR == 0` never matches, and every later entry is silently dropped. The hook still prints "entry prepended". The measured per-event growth was 269, 476, then 0 for the remaining 18 events. The `.ps1` sibling splices the entry directly before the first heading and grew on every event, so this is also a parity divergence. The test records it as a known `liveness` breach for the `.sh` leg.

## Encoding inflation on Windows

The multi-byte payload is 1500 bytes of UTF-8. Several legs wrote far more than that on this host. The likely cause is the child decoding UTF-8 input with a legacy codepage, so each byte becomes one character and is re-encoded:

- `session-summary.ps1` wrote a 3568 B row and a 3715 B digest. Windows PowerShell 5.1 reads stdin through the console input encoding.
- `auto-devlog.ps1` wrote a 4574 B entry. PowerShell 5.1 decodes git's output through the OEM codepage.
- `skill-tracker.py` wrote 9244 B. Python reads stdin as cp1252 on this host, and `json.dumps` then escapes each mis-decoded character.
- `provenance-ledger.ps1` wrote a 451 B line, against 291 B for the `.sh` leg.

The test bounds these readings with explicit caps. The text corruption itself is not asserted and is recorded here for follow-up.

| `cursor-hook-compat.py` | Rewrites a settings file only in its installer-time `--rewrite-settings` mode. As a hook it proxies stdout and stderr and writes no file. |
| `skill-guard.py`, `skill-activation-suggest.py` | Read the skill-usage state through `_skill_rules.py` and never write it. The writer, `skill-tracker.py`, is measured above. |
| `lint-autofix`, `auto-format-on-write` | Reformat the user's own edited file in place with an external formatter. They own no file of their own, and the result size is the formatter's, so they are out of this bound's scope. |
| Every other `catalog/hooks` script | Reviewed by reading. They write only to stdout or stderr. |
