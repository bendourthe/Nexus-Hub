## T302 decision: the profile authoring path

**Chosen path: (A), the governed research path** (`/tune-prompting claude-sonnet-5-5 --profiles-only`, ending in `write_model_prompting_profile.py write`). Path (B), a hand-written claim-only payload, cannot create the entry: the skill's step 7 states that a claim-only payload may update an already-rostered model but cannot add a new model or claim roster freshness, and `claude-sonnet-5-5` is not in the recorded roster.

**Payload shape the writer requires** (from `references/research-runbook.md`): one JSON object with `platform` (`claude-code`), `roster_source`, `verified_at`, `roster` (the complete list of model ids, recorded verbatim), and `models`, a map from model id to a list of claims, each with `claim`, `source_url`, `confidence`, and `scope`. A payload with a complete live `roster` re-stamps the roster and its hash. A payload that omits `roster` and `roster_source` is claim-only.

**Can `/tune-prompting` reach a live roster non-interactively here?** No. On 2026-09-30, `enumerate-models.sh claude-code` returned the picker sentinel: `{"source":"picker","models":[],"note":"no scriptable model list; read models from the platform model picker"}`. The recorded roster in the index is source `config`, 16 ids, last verified 2026-09-08.

**Consequence for Phase 2.** The roster for `claude-code` can only be completed by reading every model id from the Claude Code model picker (provenance `picker`). That is a human-supplied input, so Phase 2 begins by asking for that list. If it is not supplied, this plan's rule applies unchanged: Phase 2 stops as a blocking outcome and Definition of Done item 1 is reported unmet; no partial entry is written.

**Expected side effect.** A refreshed roster may also list other unprofiled models, for example `claude-opus-5-5`. `check_model_prompting_freshness.py` and the `v4.17.6` rebase will surface them. They are recorded, not researched, in this plan.

## T314 decision: optimizer split design, key semantics, and loop behavior

Recorded 2026-09-30 after reading `scripts/optimize_skill_description.py`, `references/description-optimizer.md`, `references/schemas.md`, and the "Description optimizer (A7)" section of `skill-eval-loop`. Today the optimizer splits 60/40 and both selects `best_description` by the test score and reports that same score, so the reported number is a selection score, not a held-out one.

**Evidence on set sizes.** The catalog holds 88 `trigger-cases.json` sets of 2 to 12 entries (15 of 2, 53 of 6, the rest 7 to 12) and one optimizer-format `evals.json` of 3 entries. None reaches 24. A 12-entry minimum would leave a test split of about 3, whose score can only be 0, 1/3, 2/3, or 1.

1. **Minimum.** The three-way mode runs only when the set has 24 or more entries AND every split (train, validation, test) can hold at least 2 entries of each `should_trigger` class. Otherwise the two-way split is kept and the output carries `reported_optimistic: true`. With today's sets, every run stays two-way and is labelled.
2. **Key semantics.** In every mode the output gains `split_mode` (`two-way` or `three-way`), `selection_split` and `reported_split` (the entry ids each score came from), and `reported_optimistic`. In two-way mode every old key keeps its exact value and meaning; `selection_split` and `reported_split` both equal `split.test_ids`, and `reported_optimistic` is `true`. In three-way mode the baseline and each candidate gain `validation_trigger_rate`, `split.validation_ids` is added, `selection_metric` is `validation_trigger_rate`, and `test_trigger_rate` with `split.test_ids` means the untouched reported split. `reported_optimistic` is then `false`. The shift is recorded in `schemas.md`.
3. **Loop behavior.** In three-way mode, iterations score train and validation only. The test split is scored exactly once for the final `best_description` and once for the original description as a baseline, recorded in `final.json`. Early stop, the plateau rule, and the perfect-score stop read the validation score only. The two-way loop is unchanged.
4. **Split integrity.** In three-way mode, entries are grouped before assignment, so a group never spans two splits. The grouping key is an optional `group` field when present; otherwise the query text normalized for case, whitespace, and punctuation; for a multi-turn entry, its turns joined and normalized. Two-way mode keeps today's ungrouped shuffle so its old values stay identical.
5. **Options.** The split reuses the existing `--seed` (default 42) and `--train-fraction` (default 0.6). Three-way mode gives train its fraction of each class and divides the remainder evenly between validation and test. A new `--split` option takes `auto` (the default, three-way when eligible) or `two-way` (always the legacy split).

This unblocks T315 to T318.

## T319 decision: pilot design, go rule, and dispatch contract

Recorded 2026-09-30, before any paid run, after reading the `skill-eval-loop` safety contract, persistence discipline, and reproducible receipts, `references/cli-adapter.md`, `[[ai-billing-safeguards]]`, and the `claude-sonnet-5-5` profile from Phase 2.

1. **Arms.** Each arm appends at most one sentence as the final sentence of the user turn. Everything else in the prompt is byte-identical across arms.
    - `baseline`: no addition.
    - `first-principles`: "Reason from first principles: restate the problem in your own terms and identify what must be true before choosing an approach."
    - `control`: "Think the problem through before you answer." (the vendor's documented think-first line).
    - Prompt length differs by arm (0, 128, and 45 characters added, each counting the joining space). This is recorded as a known confound, not controlled.
2. **The cell.** Skill `bug-localization`, model `claude-sonnet-5-5`, effort `high` passed explicitly with `--effort high`, thinking mode at the model default and recorded per run where the output exposes it. 5 self-contained prompts, one trial each, 3 arms: 15 runs. Run order is the 15 (prompt, arm) pairs shuffled once with seed 42, and that order is recorded before the first dispatch.
3. **Grading.** Every prompt asks, identically in all arms, for a final line `ROOT CAUSE: <function name>`. A run passes only when both programmatic assertions hold: the line is present, and its value equals the reference root-cause function, compared case-insensitively after stripping backticks and `()`. Naming the function where the symptom appears fails. The grader reads only the final answer text. It never looks at the arm sentence, the phrasing, or the reasoning path. It uses no LLM, and it grades with the arm label removed from its input.
4. **Go rule (pre-registered).** Go only if the `first-principles` pass rate is at least 20 percentage points above `baseline` AND at least equal to `control`. Otherwise the verdict is "not shown at this power". It is never "rejected".
5. **Power statement.** With 5 prompts per arm, each arm's rate moves in steps of 20 points, and only gaps of about 40 points or more separate signal from noise. A go therefore authorizes designing a powered test. It is not evidence of an effect. A ceiling (every arm 5/5) is a likely outcome on prompts a strong model solves, and it reads as "not shown at this power".
6. **Spend.**
    - Cap USD 20 in total.
    - A cumulative ledger (`ledger.json`) is checked before every dispatch and fails closed. A dispatch is refused when the spent amount plus the per-run ceiling would exceed the cap.
    - The per-run ceiling is enforced by the CLI itself with `--max-budget-usd 1.00`.
    - Each run's measured `total_cost_usd` from the CLI's JSON output is added to the ledger.
    - The phase profile carries no verified price, so the pre-run estimate is a range, not a quote: roughly USD 0.05 to 0.30 per run, USD 1 to 5 in total. The smoke run replaces it with a measured figure.
    - The smoke run is one cell first (baseline, prompt 1).
    - Approval is bound to this exact matrix. Any change to the arms, prompts, model, effort, run count, or cap needs a new approval.
7. **Dispatch contract.**
    - **Command.** `claude -p <prompt> --bare --setting-sources "" --model claude-sonnet-5-5 --effort high --tools "" --no-session-persistence --output-format json --max-budget-usd 1.00 --append-system-prompt-file <catalog/skills/bug-fixing/bug-localization/SKILL.md>`. It runs with an empty scratch directory as its working directory.
    - **Deviation from the adapter, found on 2026-09-30.** The installed CLI (2.1.283) documents no `--skill <path>` option. The adapter's Claude command therefore cannot be used verbatim, so the skill body is supplied with `--append-system-prompt-file`, identically in every arm. The shared adapter is not modified. Its drift is filed as a known gap.
    - **Isolation.** `--bare` skips hooks, CLAUDE.md discovery, auto-memory, and keychain reads. `--tools ""` disables every built-in tool, so the model cannot read files or run commands.
    - **Credentials.** `--bare` authenticates strictly through `ANTHROPIC_API_KEY`, so runs are API-billed. The wrapper copies the user's pilot key (`NEXUS_PILOT_ANTHROPIC_API_KEY`) into `ANTHROPIC_API_KEY` in the child process environment only. The key never appears in arguments, logs, ledgers, or records.
    - **Storage.** Raw outputs are stored as inert `.json` files, never `.md`. Prompts and outputs are untrusted data and are never executed or imported.
    - **Before the commit,** a secret scan runs over the pilot directory.
    - **Effort confirmation.** If the run metadata cannot confirm that `high` effort took effect, the pilot stops after the smoke run and records the effort confound instead of claiming it was controlled.
8. **Scope of the vendor evidence.** The vendor's evidence for the think-first line covers structured-JSON reasoning tasks at low and medium effort. A result at `high` effort on bug localization does not generalize to that case, and the record says so.

The cap, the matrix, and the go rule need the user's explicit approval before the first paid run. This unblocks T320 to T325.
