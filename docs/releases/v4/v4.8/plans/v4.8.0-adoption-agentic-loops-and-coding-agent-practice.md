## Overview

This plan operationalizes one comparison report seeded from two documents: a skills map for operators of coding agents, and a field guide to agentic loops and graph engineering for knowledge work. The report classified 44 insights and found 28 already implemented, which is the expected result for a catalog that adopted loop engineering in v3.3.0, loopmaxxing defenses in v3.5.0, and agentic verification discipline in v4.3.0. The eleven partial or missing insights collapsed into ten adoption candidates, all local, all skill-native except one validator field, none adding a dependency, credential, outbound call, or MCP entry.

**Track A (phases 1 to 3), doctrine hardening in the orchestration and evaluation clusters.** The loop skill gains the intake test it lacks (a seven-dimension readiness scorecard and five when-not-to-loop anti-fits), a run-contract extension of its schema (scope, permissions, state contract, audit evidence, and a budgets map), and a failure-mode ownership table that names one owning skill per loop failure mode, which the repository's own rule-ownership requirement already calls for. The orchestration skill gains a Step 0 autonomy ladder and a graph-readiness checklist as the written form of its escalation gate. The evaluation skill gains a verifier taxonomy whose evidence-based class has no home today, and the research command gains a completion-evidence block that turns citation coverage, duplicate rate, and URL resolution into a finish line. The stocktake gains a flag that proposes, and never applies, retirement of skills a model refresh has made redundant.

**Track B (phase 4), the OWASP agentic mapping.** Roughly fifteen agent-security skills map to ATT&CK, ATLAS, D3FEND, F3, CSF, and AI RMF, and none map to the one public framework written specifically about agents. A seventh optional frontmatter field, `owasp_agentic`, is added to the validator and the coverage builder, documented in the framework-mapping skill, and applied to the skills whose bodies already teach the corresponding control. IDs are transcribed from the fetched OWASP document (`ASI01` to `ASI10`, confirmed on 2026-09-04), never invented, and the Agent Control Standard is recorded as a watch item because it has published no identifiers.

**The guide item is absorbed elsewhere.** The comparison's item A9 (two Foundations scenes teaching the loop and graph layers) is already planned as Phase 5 of `docs/releases/v4/v4.4/plans/v4.4.6-guide-learning-experience.md` (sub-task 5.2, bounded loop and branch/join lessons), a guide patch authored the same day as this plan. This plan therefore carries no guide phase. Its final-phase Goal review checks that those lessons, once shipped, point the reader at the Phase 1 scorecard and the Phase 2 checklist, and records a known gap if they do not.

**What this plan does not do.** It creates no new skill, adds no MCP registry entry, introduces no runtime dependency or credential, and makes no new outbound call at runtime. Two items were classified `drop-outright` in the report and are not implemented: adopting a durable graph runtime, and mapping to the OWASP Agent Control Standard before it publishes identifiers. Three items were not applicable at catalog granularity.

**Prior known-gaps ingest.** `docs/releases/v4/v4.4/known-gaps.md` is the most recent ledger and carries several open items. `HT-4` (no human comprehension cohort for the guide illustrations) is why the final phase's human-testing duty asks for one outside reader of the v4.4.6 loop and graph lessons rather than another operator round. `GA-1` (a dead-selector sweep for the guide stylesheet) is carried unchanged; this plan does not touch the guide. `CQ-1`, `HT-2`, `QG-1`, `RV-3`, `RV-4`, and `RV-5` are unrelated to this scope and carry forward unchanged. The v4.5.0, v4.6.0, and v4.7.0 plans are committed on the integration branch ahead of this one and do not touch these skills; the v4.4.6 guide plan owns the guide.

**Knowledge-base grounding.** No `docs/solutions/` store and no `STRATEGY.md` exist in this repository, so Phase B.5 grounding was best-effort: the plan is grounded instead in the three prior loop-engineering comparisons and the v4.3.0 verification plan named above.

#### 1.2 -- Run-contract extension of the loop schema

**Objective**: Let a loop definition declare what it may touch, what it may spend, what survives between runs, and what it leaves as audit evidence, without invalidating any existing definition.

**Failure modes**: A definition that omits every new field stays valid, because all five are optional and the schema's required set is unchanged. A `budgets` map naming a dimension the driver cannot measure (for example `cost` on a host with no token accounting) is recorded as `unmeasured` in the trace, not silently dropped and not treated as satisfied. When `permissions` and a `gates` entry conflict (a write path allowed by `permissions` but gated), the gate wins, because a gate is the narrower and later declaration.

**Build class**: load-bearing.

**Prompt**:
> In `catalog/skills/workflow/loop-engineering/references/loop-schema.md`, extend the Fields table with five optional fields, each with Purpose and Example, and update the sentence after the table so it names them among the additive optional fields. `scope`: included and excluded topics, paths, systems, and actions, so a loop cannot drift toward a path it was never given. `permissions`: read and write boundaries, network destinations, secrets, and which actions require approval; state that a `gates` entry wins over a permissive `permissions` entry when they conflict. `budgets`: a map with any of `cost`, `tool_calls`, `subagents`, `retries`, and `wall_time`, orthogonal to `iteration_cap` and `per_iteration_budget`; a dimension the driver cannot measure is recorded as `unmeasured` in the trace. `state_contract`: the compact canonical state persisted after each cycle and handed to the next run (objective, plan, completed work, open issues, evidence, decisions, budgets consumed, next actions), cross-linked to the resume-from-checkpoint pattern in `SKILL.md`. `audit_evidence`: the artifacts every run must leave (trace, tool-call log, test results, citations, diffs, final verification record) so that "every run ends with an exit reason and an audit record" is a field, not a hope. Also extend the `trace_log` field's JSONL object with an optional `score` (number or null, the check metric this iteration) so quality per token and per second can be aggregated; state the aggregation rule in one sentence under the field. Extend the Worked Example with `scope`, `budgets`, and `audit_evidence` for `ship-pr-until-green`. Confirm every loop in `references/loop-library.md` still validates by reading each against the required-field list; change none of them. Keep the schema's required set unchanged. ASCII only.
