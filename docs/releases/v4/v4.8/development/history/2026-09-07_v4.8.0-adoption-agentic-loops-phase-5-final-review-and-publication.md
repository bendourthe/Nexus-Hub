## What the duties found

The two duties that produced real findings are worth naming, because the other eight came back clean and a reader should be able to tell the difference.

**The Tier 3 deep pass found what four phases of green gates did not.** Attacking the one new parser this plan added showed the membership check was bypassable by INDENTING a line. `build_framework_coverage.py` matches a frontmatter key with `line.strip()` and keeps the last occurrence; the validator skipped indented keys and read only the first. So a nested `owasp_agentic: [ASI99]`, or a duplicate key with the bad value second, passed validation and rendered `ASI99` into `docs/framework-coverage.md`. That is precisely the failure the decision record names as the reason for validating membership at all, so the feature's justification was defeated by its own implementation. Fixed by validating the union of every occurrence, indented ones included, which is deliberately broader than YAML's semantics because the builder is broader too and the validator must be the wider of the two to fail closed.

**The Goal review found a clause half-delivered.** Goal clause 3 says "every REVIEW and research deliverable names the verifier class that grades it". The research half landed on both surfaces. The review half did not: the taxonomy exists and is cited from `ai-output-evaluation`, but no task line (T011 to T017) wired it into any review skill, so a review deliverable still does not name its verifier class. Recorded as `DF-1` rather than fixed, because choosing which review surfaces carry the rule is a design decision outside every phase's declared scope, and fixing it silently would expand the plan after its review.

Two further findings were recorded rather than fixed for a stated reason: `WN-G` and `WN-H` are one-line changes to a parser shared by all seven framework fields, and a change to shared parsing behavior should land with a test matrix covering all seven rather than riding along in a mapping phase.

## Plan delta

**Disposition: Incomplete (non-blocking for four items, one escalated to a gap).**

Evidence. The phase's duties were sufficient and ran as written; what the plan did not anticipate was what they would find.

1. The plan assumed the last-phase duties would be confirmatory. Three of them were not: the deep pass found P1 bypasses in code that had passed four phases of gates, the Goal review found clause 3 half-delivered, and the adversarial pass found two pre-existing defects in a shared parser. A plan that treats its final phase as a formality would have shipped all five.
2. The plan's own Phase 5 assumed a pull request into `develop` while the session began ON `develop`. This was caught at the Phase 0 pre-flight, raised as a blocking question, and resolved by the maintainer choosing to branch. Recorded here because a plan whose final phase is impossible from its own starting state is a planning defect, not an execution one.
3. `T033`'s wording ("Do not copy or improvise that procedure here: use its blast-radius decision, delegated owners, plan audits, and global iteration budget exactly as written") was load-bearing. Following the runbook rather than improvising is what produced the adversarial pass, and the adversarial pass is what found the bypasses.

Consequence for remaining phases: none, this is the last. Consequence for the RELEASE: `/update release` is held until the integration pull request is green and merged. Two items belong in the release notes per the capability-usage gate: the completion-evidence block is an advisory surface (activation is automatic, it never blocks, and the disable path is that there is nothing to disable because it only reports), and the `owasp_agentic` field is an opt-in per-skill declaration whose absence is never an error.
