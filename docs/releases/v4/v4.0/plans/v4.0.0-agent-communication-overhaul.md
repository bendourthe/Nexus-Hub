# Plan - Agent Communication Overhaul

**Project**: Nexus-Hub
**Target version**: v4.0.0
**Slug**: agent-communication-overhaul
**Rank**: 14 of 17 in [`docs/roadmap-prioritization.md`](../../../../roadmap-prioritization.md)
**Retargeted**: 2026-08-21, was v3.17.9. Body text below may still cite v3.17.9 (known-gaps section names, self-referencing plan paths, release-step version numbers); the Target version above governs. Reconcile those citations when implementing.
**Plan Type**: Feature
**Created**: 2026-08-18
**Goal**: Any agent with Nexus-Hub installed communicates in a consistent, concise, plain-language way across every supported platform: readable end-of-task reports, copy-paste commands with no unfilled placeholders, guided step-by-step instructions that repeat the remaining steps after an error, and docs deep-links instead of inline technical detail.

## Overview

Today Nexus-Hub governs how agents write documents (the `catalog/style-guides/markdown.md` guide, the `writing-editing` / `anti-slop-editing` / `technical-writer` skills) but almost nothing about how agents write chat responses. The only live-response rules are four short bullets under `Communication Style` in the instruction templates plus the `End-of-Task Summary` block, and the one per-response structure block that exists (`generic-instructions.md` `## Response Format`) is not distributed to any platform. The observed failure modes follow directly: wordy jargon-heavy reports, template placeholders pasted verbatim into terminals, corrected steps that never restate the remaining sequence, and detail inlined instead of linked.

This plan closes the gap with one canonical artifact and thin distribution. Phase 1 authors `catalog/style-guides/agent-communication.md`, the single source of truth for live-response communication (structure, plain language, placeholder discipline, the guided-steps protocol, the end-of-task report shape, the docs deep-link rule, and waiting-state interim updates), plus the required decision record. Phase 2 wraps the contract in a new `agent-communication` skill so skills-native platforms discover it and the detail loads only on demand. Phase 3 distributes a compact pointer contract into all 12 substantive instruction templates in lockstep, extends the parity guard so the new section cannot drift, and stays inside the ratchet-down word budgets by deep-linking rather than inlining. Phase 4 upgrades the workflow touchpoints that actually produce the reports the user sees (`implement-phase` completion report, `/plan` and `/update` closing outputs). The mandatory final phase reconciles gaps and CI.

Success looks like: after one installer run, an agent on Claude Code, Codex, Cursor, Antigravity, OpenCode, or Copilot ends a phase with a short plain-language report a non-engineer can follow, every command block is runnable as pasted or carries an explicit REPLACE marker with where to find the value, and a mid-sequence error response always re-issues the full remaining steps.

## Design inputs (research and repo grounding)

- Placeholder conventions: the GitHub CLI syntax doc and the Google developer style guide both warn that bracketed placeholders break copy-paste and that click-to-copy examples must avoid brackets, pipes, and braces. The contract therefore requires the agent to fill values it can derive itself, and to flag the rest explicitly with a lookup instruction.
- Instruction-writing canon (Technical Writing Essentials, CMS plain-language guidelines, NN/G cognitive-load principles): grade 7-8 reading level, prerequisites first, one action per step, chunked content, and restating the remaining sequence after a correction.
- CLAUDE.md community experience: vague directives ("be concise") are ignored; measurable rules ("3 sentences unless asked to elaborate", "repeat all remaining steps verbatim") are followed. The contract is written as testable rules, not adjectives.
- Repo constraints (verified 2026-08-18): `docs/policy/doc-budgets.json` headroom is thin (`base-claude.md` +133 words, the other lockstep four +94/95 each), so the in-template contract must be roughly 90 words plus a deep-link; `check_base_template_parity.py` invariant blocks currently cover `End-of-Task Summary` and `Consequential Decisions` but NOT `Communication Style`; the guardrails-only five templates are outside the parity gate and can silently drift; `base-claude.md` and `base-codex.md` carry a Read/Glob/Grep narration bullet the other templates lack.

## Phase 1: Communication contract and decision record

**Goal**: One canonical, installable style guide defines every live-response communication rule, backed by a decision record.
**Prerequisites**: None.
**Stability Gate**: `catalog/style-guides/agent-communication.md` exists, passes `make validate` and the markdown style self-check, and a decision record under `docs/decisions/` records the design and its alternatives.
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: This file is the single source of truth every later phase points at; ambiguity here propagates to every platform.

### Sub-tasks

#### 1.1 - Author `catalog/style-guides/agent-communication.md`

**Objective**: Write the canonical live-response contract.

**Build class**: load-bearing.

**Prompt**:
> In the Nexus-Hub repo, create `catalog/style-guides/agent-communication.md`, the canonical contract for how an installed agent writes chat responses (NOT generated documents; `catalog/style-guides/markdown.md` keeps that scope, and this guide must state the boundary in its opening paragraph and cross-link it). The installer already copies `catalog/style-guides/` to `~/.nexus-hub/style-guides/`, so no installer edit is needed. Write every rule as a testable behavior, never an adjective. Cover exactly these seven sections:
>
> 1. **Response structure**: lead with the outcome in the first sentence; use headings only when a response has 3+ distinct topics; bullets for enumerable facts with explanations in prose; bold the action the user must take; at most one icon/emoji per section and only as a scannable status marker (e.g. a warning marker on a destructive step); short paragraphs, one idea per sentence.
> 2. **Plain language**: default to language a non-engineer can follow (grade 7-8 target); define any unavoidable technical term in place, in parentheses; name things by what they do, not by internal codenames the user never saw; keep counts and file paths, drop internals that do not change what the reader does next.
> 3. **Placeholder discipline in commands**: every command block must be runnable exactly as pasted. If the agent can derive a value (a path, a container name, a branch, an IP it can read from the environment), it MUST fill it in itself before presenting the command. If a value is genuinely unknowable (a password, a remote hostname the agent cannot see), the command block is preceded by a REPLACE line naming each placeholder, the exact token to replace, and a one-line instruction or command for finding the value. Never put angle brackets, square brackets, or ALL-CAPS templates inside a copy-paste block without that REPLACE line. Include a before/after example.
> 4. **Guided steps protocol**: state prerequisites before step 1; number every step; one action per step, with the expected result on success ("expect: empty output"); when the user reports an error at step N, the response must contain the fix AND re-issue the FULL remaining sequence (the fixed step plus every step after it), renumbered, so the user never scrolls back; never write "then continue with the steps above". Include a worked error-recovery example.
> 5. **End-of-task report shape**: the closing report uses exactly these labeled parts, in order: **Completed** (what changed, plain language, 1-2 lines), **Verified** (the evidence: test/validate results, counts), **Open** (blocked, skipped, deferred, or risky items, stated explicitly; "nothing outstanding" when empty), **Next** (the concrete next action, or that there is none). One optional line of plain-language context for non-technical readers. This extends the existing `End-of-Task Summary` template block and must not contradict it.
> 6. **Docs deep-link rule**: when a topic needs more than ~5 lines of technical detail, put the detail in (or link to) a readable file under `docs/` and link it with a repo-relative markdown link (per `markdown.md` rule 13); the chat response keeps the plain-language summary. Never link out as a substitute for answering the question asked.
> 7. **Waiting-state and interim updates**: when a turn ends with work still running (tests executing, a background task pending, a long build), the FIRST line of the response is a status banner stating what is running, that no user action is needed, and that the agent will report when it finishes (e.g. "Tests running (integration suite, ~5 min) - no action needed; I will report the results when they finish."). The rest of the interim update is capped at ~8 lines: what was just finished, in plain language, and nothing that belongs in the completion report. Detailed findings, design notes, and full file lists are deferred to the completion report that follows the running work, so the user never has to isolate a one-line "still waiting" signal from a wall of technical text. Include a bad/good before-after example modeled on a long technical dump that buries an "integration tests now running" sentence at the bottom.
>
> Follow `catalog/style-guides/markdown.md` conventions (ASCII punctuation, blank lines around lists, no hard-wrap). Target 150-250 lines. End with a Verification checklist section (binary, observable items) so the guide can audit a response against itself.

### Sub-tasks

#### 2.1 - Author the skill

**Objective**: Create the `agent-communication` skill wrapping the Phase 1 contract.

**Failure modes**: If the style guide file is absent at read time (a consuming project without a full install), the skill body must carry enough of the contract to act on alone and treat the guide as an enrichment, not a hard dependency; if a platform ignores skill frontmatter, the skill still works as plain SKILL.md; there are no conflicting operations (read-only guidance).

**Build class**: load-bearing.

**Prompt**:
> Create `catalog/skills/developer-experience/agent-communication/SKILL.md` per the AGENTS.md skill conventions. Frontmatter: name `agent-communication`; a pushy description with verbatim trigger phrases ("summarize what you did", "explain this to me simply", "give me the steps", "walk me through it", "make this readable", "report the results", plus auto-trigger guidance: apply whenever composing an end-of-task report, a step-by-step instruction sequence, or a response for a non-technical reader) and a SKIP clause (authoring standalone documents - use writing-editing; de-slopping a finished draft - use anti-slop-editing; generated-file markdown mechanics - markdown.md governs those); `summary_l0` <= 15 words; `overview_l1` <= 150 words. Body <= 400 lines: When to Use, Instructions (condense the seven contract sections from `catalog/style-guides/agent-communication.md` and link the guide plus `references/response-contract.md` for the full text and worked examples), Common Rationalizations (must include: "the user is technical so jargon is fine", "the remaining steps are just above in the chat", "the placeholder is obvious", "a longer report is more complete" - each with a concrete failure mode), Verification (binary checks: every command block runnable-as-pasted or REPLACE-flagged; error responses re-issue all remaining steps; closing report has the four labeled parts; a turn ending with running work opens with the status banner and stays under ~8 lines), Related Skills (writing-editing, anti-slop-editing, internal-comms, technical-writer with one-line relationships). Create `references/response-contract.md` with the full worked examples (the before/after placeholder example and the error-recovery re-issued-steps example at minimum) and reference it from SKILL.md so the orphan audit passes. Create `evals/trigger-cases.json` with at least 3 positive cases (real phrasings) and 3 near-miss negatives drawn from the SKIP clause.

**Objective**: Register in the three data files without touching anything else in `data/`.

**Prompt**:

Also update the skill-count figures in `AGENTS.md` and `README.md` if they state a total (search for the current total and bump by one; do not blanket-replace counts). Run `make validate`.

#### 2.3 - Testing and Stabilization

**Objective**: Generate and run all tests for this phase. Iterate until stable.

**Prompt**:

**Goal**: Every platform's always-loaded instruction file carries the same compact communication contract, machine-locked against drift, inside the word budgets.
**Prerequisites**: Phases 1-2.
**Stability Gate**: All 12 substantive templates carry the new section; `check_base_template_parity.py` enforces it as an invariant block across the lockstep five; `python scripts/validate_doc_budgets.py` passes; `make validate`, `make lint`, `make test` pass.
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: Twelve-file lockstep edit plus a parity-guard extension plus ratchet-down budget ceilings is the highest-blast-radius work in the plan; a silent miss here is exactly the cross-platform inconsistency the plan exists to fix.

### Sub-tasks

#### 3.1 - Design the compact in-template contract

**Objective**: Draft the ~90-word section that fits every budget.

**Build class**: load-bearing.

**Prompt**:
> Draft a new `## Communication Contract` section (working title; keep or rename consistently) of at most 90 words for the instruction templates. It must compress the Phase 1 contract to its six testable behaviors: (1) lead with the outcome, plain language a non-engineer can follow, jargon defined in place; (2) command blocks runnable as pasted - fill derivable values yourself, flag the rest with a REPLACE line saying where to find each value; (3) numbered steps with prerequisites first and expected results; after any reported error, re-issue ALL remaining steps renumbered - never point back up the chat; (4) close every task with the labeled report: Completed / Verified / Open / Next; (5) put detail beyond ~5 lines into a linked docs/ file, keep the response summary plain; (6) when work is still running at the end of a turn, open with a one-line status banner (what runs, no action needed, results will follow) and keep the interim update under ~8 lines. End with: "Full contract: `~/.nexus-hub/style-guides/agent-communication.md`." Verify the draft against `docs/policy/doc-budgets.json` headroom for all five lockstep files (base-claude +133 words, others +94/95); if it does not fit, first trim the draft, then (only if still short) relocate an equivalent word count from a non-invariant section per the MT-1 disposition pattern (move detail to a `guides/reference/` file), never raise a ceiling.

#### 3.2 - Roll out to all 12 substantive templates

**Objective**: Insert the section, byte-identical, everywhere it belongs.

**Failure modes**: A template missed here silently ships a platform with the old behavior (the exact defect class AGENTS.md warns about for the non-lockstep seven); a wording variant across the lockstep five fails the parity gate loudly (desired); if the `End-of-Task Summary` block is edited it must stay byte-identical across the five or the existing invariant check fails.

**Prompt**:
> Insert the approved `## Communication Contract` section byte-identically into: the lockstep five (`templates/ai-instructions/base-{claude,codex,cursor,gemini,opencode}.md`), the guardrails five (`base-{aider,kimi,openclaw,qwen,windsurf}.md`), `base-google-shared.md`, and `generic-instructions.md`. Place it immediately after each file's existing communication bullets (`Communication Style` in base-claude, the comms bullets inside `Working Conventions` elsewhere). In `generic-instructions.md`, reconcile the existing `## Response Format` (L198-204) and `## Global Style & Communication Preferences` with the new section so there is one consistent story - the Response Format three-part shape is superseded by the Completed/Verified/Open/Next report for task-ending turns; keep it for mid-task turns if it still earns its words. Amend the existing `## End-of-Task Summary` invariant block in all files that carry it by appending one bullet: "Use the labeled parts Completed / Verified / Open / Next" (byte-identical across the lockstep five). Do NOT touch the four antigravity/gemini-cli surface-note stubs. Resolve the pre-existing asymmetry deliberately: the Read/Glob/Grep narration bullet exists only in base-claude and base-codex; leave it as is (it is a Claude/Codex-specific verbosity control, not part of this contract) and note that in the phase's session history.

#### 3.3 - Extend the parity gate

**Objective**: The new section cannot drift across the lockstep five.

**Failure modes**: If the section heading is missing from a lockstep file the check must fail naming the file; if a body diverges by one byte it must fail with a diff pointer; the check must not reject the intentionally-different non-lockstep seven (they are out of its roster by design - document that residual risk in known-gaps if not already tracked).

**Build class**: load-bearing.

**Prompt**:
> In `scripts/check_base_template_parity.py`, add the new section heading to `REQUIRED_HEADINGS` and to `INVARIANT_SECTIONS` so its body must be byte-identical across the five lockstep templates. Add or extend the corresponding pytest in `tests/validators/` (follow the existing parity-test pattern): assert the gate fails on a seeded one-word divergence in the new section and passes on the real tree. This is a repo-internal guard: no `.ps1` sibling, no installer copy step (confirm it is either already covered by or does not need `DEV_ONLY_SCRIPTS` in `catalog/hooks/tests/test_installer_smoke.py`).

#### 3.4 - Testing and Stabilization

**Objective**: Prove the rollout is complete, parity-locked, and budget-clean.

**Prompt**:

After all tests pass, run `/generate-session-history` to document Phase 3.
