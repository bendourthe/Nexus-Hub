## Overview

Nexus-Hub currently encourages every plan phase to create, update, and optimize CI/CD, and `/implement` offers both commit-only and commit-and-push at the end of every phase. Those defaults can publish incomplete work repeatedly, start redundant remote pipelines, and let each skill or project generate a different pipeline architecture. Nexus-Hub's own `.github/workflows/ci.yml` also duplicates repository commands inside YAML, runs comprehensive validation on both pull requests and shared-branch pushes, and postpones some Windows and macOS compatibility gates until after merge.

This plan establishes one canonical lifecycle. Each phase is implemented, tested, documented, and committed locally exactly at its completion boundary. Non-final phases are not pushed and do not trigger remote CI. The final phase audits the existing pipeline against Nexus-Hub's optimized contract, proposes and applies approved adjustments, runs the complete local gate, commits and pushes the completed plan branch, opens the integration pull request, and lets required checks test the synthetic merge result. Post-merge workflows run only on protected integration or release branches, and `/update release` runs only after the integration result is green.

The contract is distributed through the existing Nexus-Hub commands, skills, instruction templates, and installer rendering paths so it behaves the same in Claude Code, Codex, Cursor, Gemini, Antigravity, GitHub Copilot, OpenCode, Nexus AI, and the other supported integrations. Nexus-Hub's own repository becomes the reference implementation: portable CI profiles live in `scripts/ci/`, GitHub Actions remains a thin trigger and reporting layer, public repositories use standard GitHub-hosted runners, private repositories can select isolated self-hosted runners when hosted-minute cost warrants them, and all platforms produce concise summaries plus structured reports.

## Goals First

**Target problem**: Agentic projects using Nexus-Hub can trigger expensive or duplicated remote CI during incomplete phase work and can generate inconsistent, YAML-heavy pipelines because planning, implementation, commit, branch, and release guidance does not share one lifecycle contract.

**Primary persona**: A developer using Nexus-Hub from any supported agentic platform to plan and implement multi-phase work in a Git repository.

**Secondary persona**: A Nexus-Hub maintainer who needs the harness itself and downstream projects to use the same portable, secure, cost-aware CI/CD architecture.

**Observable definition of done**:

- Every new `/plan` output requires local verification and one end-of-phase commit for each phase, forbids non-final pushes by default, and ends with an audit that compares the repository's pipeline against the canonical Nexus-Hub CI/CD contract.
- `/implement` enforces commit-only completion for non-final phases, final-phase commit and push after all local gates, pull-request integration checks, and `/update release` only after the integration result is green.
- The canonical CI/CD skills define repository-native fast, full, platform, report, and release profiles; public/private runner selection; merge-aware event separation; security controls; structured reports; and cost controls without depending on one CI provider.
- Nexus-Hub's installed instruction and command surfaces render the same lifecycle policy across Claude, Codex, Cursor, Gemini, Antigravity, Copilot, OpenCode, and inherited integrations.
- Nexus-Hub's own workflows call repository-native CI profiles, perform complete supported-platform validation before merge, avoid a duplicate full post-merge run, publish readable and machine-readable results, and use immutable action references with least-privilege permissions.
- Direct pushes to protected integration and release branches are prohibited through the documented branch/ruleset contract, so branch-filtered `push` workflows represent merges or release operations rather than arbitrary developer pushes.

**Success measures**:

- A deterministic contract test proves `/plan`, `/implement`, `/update release`, the retained lifecycle skills, and the canonical instruction templates agree on commit-only non-final phases, final-only push, terminal pipeline reconciliation, and release handoff.
- Installer and platform-parity tests prove the policy reaches every supported platform's actual instruction, command, and skill discovery paths.
- A downstream fixture project can run the same repository-native CI profile locally and through a generated GitHub Actions workflow without duplicated test logic.
- Nexus-Hub pull-request validation covers Linux, Windows PowerShell 5.1, and macOS compatibility before merge, while post-merge workflows do not rerun the complete validation suite.
- Required checks always resolve to success or failure, including docs-only and path-scoped changes; no required check remains pending because its workflow was skipped by a top-level path filter.
- Report artifacts contain a concise Markdown summary, JUnit results, coverage data, SARIF where supported, platform metadata, and a short explicit retention period.

## Scope

### In scope

- Define one provider-neutral optimized CI/CD lifecycle and make `cicd-architect` its authoritative skill.
- Align `cd-pipeline-generator` and `cicd-integration` with the canonical lifecycle instead of maintaining independent trigger and orchestration defaults.
- Change `/plan`, `implementation-plan`, `/implement`, `implement-phase`, `code-commit-workflow`, `git-branching-workflow`, `/update release`, and related release guidance so phase commits remain local until the final phase.
- Add an end-of-plan pipeline comparison that detects the active CI provider, compares the existing pipeline with the canonical profile/event/reporting/security contract, proposes a scoped migration, and records declined differences as known gaps.
- Propagate the lifecycle through the canonical AI instruction templates and every integration that inherits from them, including Copilot's use of `base-codex.md` and Antigravity/Gemini CLI inheritance from `base-google-shared.md`.
- Add repository-native CI profiles and structured reporting to Nexus-Hub.
- Migrate all Nexus-Hub GitHub Actions workflows to thin orchestration, final-plan pull-request validation, protected-branch post-merge work, and release/tag work.
- Document branch protection, required checks, billing review, runner selection, and manual repository-setting verification without mutating external GitHub settings automatically.
- Add deterministic tests for command/skill contract alignment, platform rendering, CI profile behavior, workflow security, event separation, report generation, and required-check completion.

### Out of scope

- Provisioning or administering physical self-hosted runner machines for the user.
- Modifying GitHub billing plans, repository rulesets, branch protection, organization settings, secrets, or environments automatically.
- Migrating unrelated repositories during this Nexus-Hub release; the released harness supplies the default and migration mechanism for later use in those repositories.
- Introducing Jenkins, GitLab, Woodpecker, Buildkite, or another CI control plane into Nexus-Hub itself.
- Replacing GitHub Actions as Nexus-Hub's trigger, checks, reporting, and release interface.
- Running remote CI for ordinary non-final phase commits or feature-branch pushes.
- Publishing v3.19.0 while authoring or approving this plan; publishing belongs to the final implementation phase and `/update release`.

## Grounding and Constraints

- The source report is a legacy-style research document without an `Adoption target:` field. The user confirmed `v3.19.0` and the filename `v3.19.0-adoption-cost-effective-ci-cd.md` on 2026-07-30; add an `Adoption target:` field to future comparison/research artifacts that seed plans.
- No `STRATEGY.md`, version strategy file, `docs/solutions/` store, or v3.16 constitution exists. The goals and personas above are therefore grounded in the user's approved scope, the source report, and the inspected repository rather than a durable strategy anchor.
- Nexus-Hub uses a develop-plus-main model: feature work integrates through `develop`; `main` is the protected release branch. The implementation must not commit feature or version work directly to `main`.
- The current worktree contains unrelated in-progress security-skill changes and untracked planning artifacts. Every implementation phase must preserve them and stage only files that trace to this plan.
- The canonical remote lifecycle is: local phase work and local phase commits -> final-phase local full gate -> final feature-branch push -> pull-request checks against the integration merge result -> merge to the integration branch -> concise post-merge work -> `/update release` -> protected release-branch merge/tag/publish.
- A GitHub `push` event cannot prove that an update came from a merge. Merge-only semantics therefore require protected integration/release branches that reject direct pushes, plus workflows filtered to those branches.
- Pull-request validation remains authoritative and comprehensive, but it is first triggered only when the completed plan branch is pushed and the final integration pull request is opened. Corrective changes after a remote failure reopen the final phase and must pass local gates before the final commit is amended or superseded.
- Public repositories default to standard GitHub-hosted runners. Private repositories may select isolated self-hosted runners when GitHub-hosted minute cost is material, subject to untrusted-code and credential isolation controls. Persistent self-hosted runners must not execute untrusted public-fork code.
- Required checks must have a stable, always-resolving aggregate job. Top-level path filters or skip annotations must not leave a required check pending indefinitely.
- The canonical CI implementation is provider-neutral. GitHub Actions is the primary example and Nexus-Hub reference implementation, not a hard dependency for downstream projects.
- English Markdown, commit messages, generated summaries, and task prompts are ASCII-only and never hard-wrapped.

## Lifecycle Contract for This Plan

- Phases 1 through 7 end with local validation, documentation, session history, and one phase-scoped local commit. They do not push, open a pull request, or start remote CI.
- Every phase records its CI impact against the canonical contract. A phase may change CI source files when CI is its explicit deliverable, but no remote run occurs until Phase 8.
- Phase 8 performs the terminal pipeline comparison and complete local validation, then creates the final phase commit and pushes the plan branch.
- The final integration pull request starts the one comprehensive remote validation gate. Failed remote checks reopen Phase 8; fixes are locally verified before the final commit is amended or followed by a narrowly scoped stabilization commit.
- After the integration pull request is green and merged to `develop`, only post-merge smoke, publishing, provenance, or environment-specific work runs.
- `/update release` begins only after the `develop` result is green and the user approves release notes derived from the actual diff. It owns the release commit, develop-to-main promotion, tag, push, and GitHub Release confirmation gates.
