# Session History - v4.0.0 cost-effective-ci-cd, Phase 7

**Date**: 2026-08-25
**Plan**: [`docs/releases/v4/v4.0/plans/v4.0.0-cost-effective-ci-cd.md`](../../plans/v4.0.0-cost-effective-ci-cd.md)
**Phase**: 7 - Nexus-Hub Workflow Migration
**Branch**: `feat/v4.0.0-cost-effective-ci-cd`

## What this phase delivered

GitHub Actions is now a thin orchestration layer: one comprehensive gate on the integration pull request, minimal work after a merge, and a release path that runs no validation at all. This is the phase the whole plan was aimed at.

### T043 - The event topology

Three workflows now own three distinct events.

`ci.yml` **lost its `push` trigger.** Under a pull-request-only merge policy, a push to `develop` IS the merge commit of the pull request that just ran, so the tree is identical and the second run could not discover anything the first did not. It gained `merge_group:` so a merge queue validates the queued result with the same gate.

**The expensive legs moved to the pull request.** `tests-windows`, `bootstrap-windows`, the macOS leg of `bootstrap`, and the full three-OS `install-smoke` matrix were all gated to `push` before, which meant Windows PowerShell 5.1 and macOS compatibility were proven only AFTER merge. That did not save the minutes; it spent them where they could no longer prevent a bad merge.

`post-merge.yml` is new: the fast profile against the merged tree, plus a provenance report. Its purpose is narrow and worth stating, because "run something after the merge" invites scope creep: it catches a bad MERGE rather than bad code, which is the semantic-conflict class the pull-request gate cannot see when the base moved after the last synthetic merge was computed.

`release.yml` is new: the release profile on a `v*` tag or an explicit dispatch. Before this, a tag ran the entire ci.yml suite including its matrix, which was a third full validation of a tree the pull request and the merge had already covered, on the one event where a failure can no longer prevent anything.

### T043 - Profile delegation

The `validate` job's 31 inline `run:` steps became one call to `scripts/ci/run.py --profile full --only ...`. Same for `shellcheck`, `tests`, and `tests-windows`. `ci.yml` went from 1056 lines to 566, and the reduction is entirely duplicated command list.

A test now asserts the duplication cannot return: `test_ci_does_not_re_declare_the_validator_list` fails on any `run: python scripts/<name>.py` in the workflow.

### T046, T047 - The remaining workflows

| Workflow | Change |
|---|---|
| 5 extension workflows | `push` leg removed; pull-request only, path filters kept |
| `doc-colocation.yml` | `push` removed, `merge_group` added; triggers stay unfiltered because `colocation` is required |
| `presentify-extractor.yml` | `verify` re-gated from `!= 'schedule'` to pull-request only; `render` keeps its push leg because it genuinely depends on the merged state |
| `nexus-memory.yml` | the three-OS locking matrix was gated on a push it will never receive again, so it moved to the pull request |
| `codeql.yml` | analysis moved to the pull request (it previously ran on push to `main` only, so a PR into `develop` got no signal and the analysis landed two merges after the code); workflow-level `permissions` added; the weekly schedule stays |

The `nexus-memory.yml` case is the one worth flagging. Removing the push trigger without re-gating that job would have left it conditioned on `github.event_name == 'push'`, which can never be true, so a three-OS locking matrix would have silently stopped running. A skip reports Success. That is the fail-open shape this whole release is about, and it was one line away from being introduced by the fix for it.

### T048, T049 - Security, cost, and reporting

Action pinning was already complete (every `uses:` is a 40-character SHA with a version comment) and is now asserted per workflow. `codeql.yml` was the last workflow without a top-level `permissions` block; all eleven now declare one.

Concurrency is deliberately split. Pull-request validation cancels superseded runs; `release.yml` and `post-merge.yml` do NOT, because each tag is a distinct artifact and each merge a distinct state, so there is no later run that covers the earlier one.

Every lifecycle workflow appends `reports/summary.md` to `$GITHUB_STEP_SUMMARY` with `if: always()`, so a red run is readable by someone other than its author.

### T050 - Validator extension

`scripts/validate_workflow_security.py` gained four lifecycle rules alongside its supply-chain rules: duplicate pull-request-plus-push validation, an unfiltered push trigger, unbounded artifact retention, and a self-hosted runner reachable from a fork. They are written against workflow SHAPE rather than Nexus-Hub job names, so they stay meaningful in a fork.

### T051 - `tests/validators/test_ci_workflow_contract.py`

49 assertions: the three lifecycle workflows and their distinct events, no duplicate complete suite, profile delegation with no re-declared validator list, the always-resolving aggregate, report publication surviving failure, permissions and pinning, and the docs-only path.

### T052 - The settings runbook

`docs/v4/v4.0/development/github-ci-settings-runbook.md`: protected branches, required checks with the three rules each learned from a shipped defect, merge queue, fork restrictions, runners, billing review, artifact retention, and an eight-item verification checklist.

It opens by stating why the settings are load-bearing rather than hygiene: `post-merge.yml` means "a merge happened" ONLY IF the branch rejects direct pushes. Without that, the same workflow fires on any developer push and every post-merge assumption is false while the pipeline still reports green.

## Troubleshooting

### Two validator rules were too coarse and produced false positives

The first run of the extended validator reported two findings, and both were wrong.

`cursor-usage-monitor.yml` was flagged for a self-hosted runner. The phrase appeared in a PROSE COMMENT ("on other images, self-hosted or future"); the workflow runs entirely on GitHub-hosted runners. Fixed by matching the `runs-on:` VALUE rather than any occurrence in the file.

`presentify-extractor.yml` was flagged for duplicate validation. It legitimately carries both a pull-request `verify` job and a post-merge `render` job in one file, separated by per-job `github.event_name` conditions. Fixed by treating a per-job event condition as CONFORMING.

Worth recording as a principle rather than two fixes: for a hard gate, precision matters more than coverage. A validator that cries wolf gets disabled, and then it catches nothing at all. Both rules now state their exemption and why it exists.

### Eleven pre-existing workflow tests encoded the old topology

`test_workflow_policy_repo_wide.py`, `test_cursor_usage_monitor_workflow.py`, `test_presentify_extractor_workflow.py`, and `test_ci_runs_every_repo_test.py` all failed. None was stale; each correctly encoded the pre-v4.0.0 contract that this plan changes. Each was reviewed individually rather than bulk-updated:

- **Concurrency**: a `NO_CANCEL` set for `release.yml` and `post-merge.yml`, with the reasoning in the constant's docstring.
- **Push scoping**: a tag-only push trigger is the release event, not a branch push, and is narrower than any branch list rather than broader.
- **Path filtering**: a `LIFECYCLE_EVENT_WORKFLOWS` set for the two workflows scoped by EVENT rather than by path. Adding a path filter to them would make them skip the merge or the tag they exist to observe.
- **Cursor monitor**: the push assertions became an assertion that the push leg is GONE, which is stronger than deleting them.

### The test-collection property test had to follow the indirection

`test_ci_runs_every_repo_test.py` asserts that every test under `tests/` is reachable from a CI pytest target. With the workflow calling a profile, reading only the YAML reported the whole tree as uncovered.

The fix resolves targets THROUGH the profile definitions, reading `scripts/ci/profiles.py` live rather than copying it. That matters for a reason beyond the false alarm: the easy way to silence the failure would have been to re-add a literal `pytest tests` line to the workflow, which would have reintroduced exactly the duplicate-command-list defect the engine removes. The failure message now says so explicitly.

## CI impact record (contract 2.1)

CI/CD IS this phase's explicit deliverable, so pipeline files change here by design. This is the one place in the plan where that is true.

- `ci.yml` rewritten: 1056 to 566 lines. `post-merge.yml` and `release.yml` added. Seven other workflows edited for event separation.
- No new dependency, no new action, no new credential, no new outbound call.
- **External settings are unchanged and MUST be verified by hand.** Nothing here mutated branch protection or the required-check list, and `docs/policy/required-checks.json` is unchanged (`validate`, `shellcheck`, and `ci-required` are still produced by `ci.yml`, `colocation` by `doc-colocation.yml`, `verify` by `presentify-extractor.yml`). The runbook's section 8 checklist is what closes this out.
- No remote CI was started. No push occurred. The topology change takes effect on the plan's single publication in Phase 8, which is also its first real-world test.
