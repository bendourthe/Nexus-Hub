## Decisions

### Expected-red tests use strict xfail, not a red suite

The plan asked for failing-first contract tests and forbade weakening them. Both are satisfiable at once with `pytest.mark.xfail(strict=True)`: the assertion is written in full, it does not pass today, and it cannot be quietly satisfied later because a strict xfail that starts passing FAILS the run until its marker is removed. Recorded as MT-1 in the known gaps, and Phase 8 verifies that no marker survives.

### Two plan findings were already closed

The plan lists "floating `actions/setup-node@v4` references" and "top-level path filtering can leave a required check unresolved" as open problems. Neither is. Every `uses:` across all nine workflows is a full 40-character SHA with a version comment, and `ci.yml` has had unfiltered triggers with job-level scoping plus `scripts/check_required_check_coverage.py` since v3.17.6. Both are recorded in section 4 of the workflow audit as CLOSED, with what closed them, and a test now keeps the SHA pinning true. Listing a fixed problem as open would have sent Phase 7 to fix something that already works.

## Troubleshooting

One real correction, and the mechanism that caught it is worth recording.

Audit rows E3 and E4 initially said `cd-pipeline-generator` and `cicd-integration` carry "no cross-link to a canonical CI policy". The strict-xfail test asserting that link disagreed: it XPASSed, which under `strict=True` is a failure. Both skills do carry `[[cicd-architect]]` -- in their Related Skills footer.

The assertion was TIGHTENED rather than deleted. A footer pointer and a body-level conformance rule are different things, and the original assertion could not tell them apart, so it would have passed for the wrong reason once Phase 2 landed. It now requires the conformance statement to appear in the skill body. The audit rows are corrected and the correction is recorded in the audit itself as section G2.
