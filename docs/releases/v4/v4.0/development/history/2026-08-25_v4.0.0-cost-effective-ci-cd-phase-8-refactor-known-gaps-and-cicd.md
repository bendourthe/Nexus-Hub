### T054 - Architecture refactor

`docs/v4/v4.0/development/ci-cd-final-audit.md` sections 1 and 2: the ownership map (who owns what, once), the detector output, and one near-miss.

The near-miss is the finding worth carrying forward. Removing the `push` trigger from the extension workflows left `nexus-memory.yml`'s three-OS locking matrix conditioned on `github.event_name == 'push'`, which can never be true again. Left alone, that matrix would have silently stopped running, and a skipped job reports Success. That is the exact fail-open shape this release exists to remove, and it was one line away from being introduced BY the fix for it. The general lesson is not about that job: removing a trigger requires auditing every `if:` that referenced it.

## Troubleshooting

### The full validators run found eight failures, all one class

The first complete `tests/validators` run after Phase 7 reported 8 failures out of 1263. None was a defect in shipped behavior.

Seven asserted that a guard is wired into CI by grepping `ci.yml` for a literal `scripts/<name>.py`. The workflow now calls a profile, so the string is gone while the wiring is intact.

**The tempting fix was the dangerous one.** Re-adding literal `run: python scripts/x.py` lines would have made every grep pass and would have reintroduced the duplicated command list the engine exists to remove -- the same list that had already diverged in production, silently dropping a security validator from CI while the local list still ran it.

Fixed with `tests/validators/_ci_reachability.py`: one shared helper that answers "would a CI job run this script?" by resolving through the live profile definitions. Six tests now call `assert_wired_into_ci(...)`, and its failure message names the correct remedy AND warns against the wrong one, because the wrong one is what a hurried reader will reach for.

The eighth (`test_push_event_uses_before_sha`) asserted classifier behavior for a push event `ci.yml` can no longer receive. It now asserts the fail-closed fall-through, with a companion test that the premise still holds -- so if a push trigger ever comes back, the test that depends on its absence fails rather than passing silently.

### Two long profile runs did not complete

`--profile full` ran for roughly 50 minutes without finishing and was stopped; the `windows-hooks` group of `--profile platform` likewise. Both are slow rather than hung: `full` runs the hooks tree, the whole `tests/` tree, and six extension suites in sequence, and the per-command timeouts bound the worst case around 2.5 hours.

Recorded as DF-2 with what IS verified in their place, rather than as a pass. Every constituent group of `full` was run individually and passed; what is unproven is the single aggregated invocation and its cross-group exit status. If that proves impractical to run locally, it is a finding about the profile's shape and argues for splitting `full` by group.
