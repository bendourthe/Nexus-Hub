## What this phase delivered

Every plan `[[implementation-plan]]` writes from now on carries the lifecycle: local verification and one local commit per phase, no non-final push, a per-phase CI-impact record instead of per-phase pipeline authorship, and a mandatory terminal reconciliation plus publication in the final phase.

### T013 - `implementation-plan` rewritten around the lifecycle

Five changes to the generated-plan contract:

1. The per-phase Testing and Stabilization prompt no longer says to "create or update the CI/CD pipeline ... and optimize it". It now records CI IMPACT against `[[cicd-architect]]` (new commands, dependencies, environment variables, test paths, artifacts, and whether the pipeline already covers them), states the one legitimate exception (a phase whose explicit deliverable IS the pipeline), declares a no-op record valid, requires one local commit, and forbids push, pull request, and remote CI in as many words.
2. The phase exit checklist template gained three items: CI impact recorded with no remote run, one local commit created, and no branch push or remote CI run occurred.
3. The Phase Design Guidelines row "CI/CD per phase" became three rows: CI impact per phase, Local commit per phase, and Publication is terminal. Each states the failure mode rather than the rule alone.
4. The mandatory final phase gained sub-task N.9 (Publication and integration), and its N.5 changed from open-ended optimization to the six-step reconciliation. N.8 was corrected from "confirm CI/CD passes" to a complete LOCAL gate, since it must pass BEFORE the branch is published and therefore cannot depend on a remote run. That ordering error was latent in the previous template.
5. The Verification checklist gained three lifecycle items, and its final-phase item was updated to nine sub-tasks.

### T013b - The strict task-line format now lives in the producer

The `- [ ] T### [P?] [US?] <file-path>` grammar was documented only in `[[tasks-to-issues]]`, the CONSUMER. The generator that must emit it said nothing about it. A round-trip test written against this plan's own 62 task lines is what surfaced the asymmetry.

`implementation-plan` now carries a "Strict Task-Line Format (required)" section with the consumer's exact regex and the reason it is a hard requirement: a non-matching line makes `tasks-to-issues` ABORT rather than skip, so a loosened line is not degraded output, it is a stopped tool.

### T014 - `/plan` states the guarantee and stops

A new "Plan lifecycle (guarantee)" section: six bullets covering per-phase local commits, no non-final push, per-phase CI-impact recording, terminal reconciliation, single publication, and release gated on green integration. It names `[[implementation-plan]]` and `[[cicd-architect]]` as the owners and copies no procedure.

A test asserts the dispatcher contains none of the procedural tokens (DETECT, COMPARE, PROPOSE, the N.5 heading, the N.9 heading) and stays under 150 lines, because "thin" is a size property as well as a content property.

### T015 - `tests/skills/test_plan_lifecycle_contract.py`

23 assertions across five groups: strict task format (including a round-trip parse of this plan's real 62 task lines rather than a synthetic fixture), per-phase lifecycle, the mandatory final phase, dispatcher thinness, and plan-review detection.

### T016 - Plan review can detect a non-conforming plan

Ownership decision, recorded here as the plan's sub-task 3.4 requires: the checks went to `[[plan-review]]`, not `[[cross-artifact-analyzer]]`. The analyzer operates over a feature DIRECTORY and would need a new single-document scope to see a plan at all, while `plan-review` already takes a plan document as its input and already runs a feasibility lens. Adding a scope to the wrong tool to avoid touching the right one is how a second review path gets built.

`plan-review` gained a "Lifecycle checks (always-on, feasibility lens)" table: five detection signals, each with why it is a finding and a severity floor, from P2 (missing local phase commit) to P0 (release before green integration). It cites `[[cicd-architect]]` and deliberately restates no policy. A test asserts the absence of policy tokens owned elsewhere, so the boundary is enforced rather than merely intended.

## Troubleshooting

### A literal backspace character in a regex

`test_this_plans_own_task_lines_parse` reported zero matches against a plan that visibly has 62 task lines. The cause was in the patch script, not the test logic: a word-boundary escape was written inside a NON-raw Python string, so it became byte `0x08` rather than a regex word boundary, and `cat -A` showed the compiled pattern ending in `^H`. Removed the boundary (it was not needed) and re-ran.

Worth recording because the repository already gates this class: `validate_unicode_safety.py --strict` treats a stray control character as a finding. The test failure arrived first only because it runs faster.

### The body crossed the 500-line soft cap

The Phase 3 additions took `implementation-plan/SKILL.md` from 521 to 543 body lines, and the bundle audit's warning count moved 64 to 65. `AGENTS.md` is explicit about the remedy: beyond 500 lines, add a `references/` subdirectory rather than expanding the body.

So the roughly 75-line mandatory-final-phase TEMPLATE moved to `references/mandatory-final-phase.md`, leaving the RULE in the body with a pointer. That is the right split on its own terms, not just a line-count trick: the template is copied once at plan-generation time, while the rule is guidance the agent needs whenever the skill triggers. The body is now 499 lines, the warning is gone, and two tests assert that the reference is named from the body (so it is not an orphan) and that the template exists in exactly one place (so the two copies cannot drift).

Isolating which of the three edited files caused the warning took a per-file revert loop, because `validate_skills.py --bundles-only` prints only a count unless `--verbose` is passed. Noted for the next person.

### Warning-count context

For the record, since the number moves in both directions: 67 warnings at the branch point, 64 after Phase 2 (the `cicd-architect` rewrite removed three), 65 mid-Phase-3, 64 again after the reference extraction.
