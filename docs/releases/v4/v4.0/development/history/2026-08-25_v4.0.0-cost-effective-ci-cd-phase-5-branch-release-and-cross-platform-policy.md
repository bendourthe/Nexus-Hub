## What this phase delivered

The lifecycle now reaches every supported platform through the installed instruction layer, and the branch and release skills enforce its ordering. All 23 expected-red assertions from Phase 1 are green, with zero markers remaining.

### T024 - `git-branching-workflow`

Two new steps between "never commit to the protected branch" and "work, validate, integrate":

- **Step 4b, publication timing.** Creating a branch and PUBLISHING it are separate decisions. Create at the start of the plan, keep phase commits local, push once in the final phase after the complete local gate and with explicit approval, integrate only through a pull request against the INTEGRATION branch. Explicitly scoped to plan-driven work: a one-off fix on a short-lived branch is published whenever it is ready, because the rule exists to stop a multi-phase plan multiplying the cost, not because pushing is bad.
- **Step 4c, what a protected branch buys you.** A push event carries no evidence that an update came from a reviewed merge. "This workflow runs on merges" is true only in a repository whose branch protection REJECTS direct pushes. The settings are therefore load-bearing for correctness, not just discipline, and they cannot be set from a pipeline file.

Step 6 gained the green-integration precondition, plus two Common Rationalizations: pushing per phase as a backup, and assuming a branch filter implies a merge.

### T025 - `/update release`

A new FIRST step, "the integration gate", before any version mutation: the plan branch is merged, integration CI is green (a pending check is not a green check), the working tree is clean and matched to its remote, and release notes are approved from the ACTUAL diff over the real tag range rather than from the plan.

The CI/CD step in the release flow changed from "create/update/optimize" to a CONFORMANCE RE-CHECK. By release time the plan's final phase has already reconciled the pipeline; if the re-check finds unreconciled drift, that is a finding against the final phase and belongs there, not in a release-time rewrite of the pipeline.

The ordering line now reads: integration gate, then docs, gitignore, version, changelog, devlog, refactor, known-gaps, CI/CD conformance re-check, manifest, then the existing commit/tag/push/publish flow.

### T026 - `version-upgrade`

A new Step 0 carrying the same four-part integration gate, with an explicit no-op for ad-hoc bumps outside a plan. The reason is stated where it will be read: a version bump is the point after which every later step assumes the release is happening, so an unwind costs more than a wait.

### T027, T028 - Twelve instruction templates

The 104-word "Plan Lifecycle and CI/CD" block was added to all twelve substantive templates: the lockstep five, the guardrails five, `base-google-shared.md`, and `generic-instructions.md`. The four antigravity and gemini-cli surface-note stubs were deliberately left alone and a test asserts they stay clean.

Placement is after `## Branching` and before `## Consequential Decisions`, which is the reading order: which branch, then when it leaves the machine, then how to ask about it.

### T029, T030 - This repository's own governance

`AGENTS.md` gained a "Plan lifecycle (v4.0.0)" paragraph in the Branching and Release Workflow section, including the point that a `push`-filtered workflow means "a merge or a release happened" ONLY because `main` and `develop` reject direct pushes. `CLAUDE.md` gained a seventh quick-reference rule.

### T031, T032 - Rendering and rollout coverage

`tests/skills/test_cicd_lifecycle_contract.py` gained four aggregates modeled on the existing Communication Contract rollout test: roster completeness (a new template must be classified or it silently escapes), a count guard, stub exclusion, and body identity across all twelve. Body identity is stronger than the parity gate, which reaches only the lockstep five.

`tests/integrations/test_lifecycle_block_rendering.py` is new. It installs every registered integration into a throwaway target and asserts against what landed on disk, because template parity proves the block is in the SOURCE and says nothing about whether it survives rendering into the file an agent actually reads. Those are different claims, and this repository has shipped a defect in the gap between them before.

## Decisions

### Raising seven doc-budget ceilings

The block breaches seven of the eight ceilings in `docs/policy/doc-budgets.json`. Six of those were already flagged `<- tight` (under 5% headroom) before this change, which the policy itself calls "a stricter policy than intended".

The block was condensed from 110 words to 104 first, with everything expandable pushed to `[[cicd-architect]]`, which is on-demand and unbudgeted by design. The seven ceilings were then re-seeded to the manifest's own documented rule (current size plus roughly 10%) rather than raised by the minimum that would pass, because a minimum raise reproduces the frozen state that produced the six `tight` entries.

The offset was taken on the skill side, in the same release: `cicd-architect` 790 to 275 lines, `code-commit-workflow` 504 to 394, `version-upgrade` 510 to 447, `implementation-plan` 543 to 499. Roughly 1,100 lines of per-trigger content removed against roughly 1,600 words of per-session content added.

Full reasoning and the five rejected alternatives: [`docs/decisions/implemented/policy/2026-08-25-raise-instruction-doc-ceilings-for-the-lifecycle-block.md`](../../../../../decisions/implemented/policy/2026-08-25-raise-instruction-doc-ceilings-for-the-lifecycle-block.md).

### Inheritance is tested as inheritance

Three platforms (Antigravity 1.0, Antigravity 2.0, Gemini CLI) do not carry a body at all; their rendered instruction file is an `@base-google-shared.md` include. The rendering test resolves the include chain against the catalog templates, with cycle protection, and accepts inherited delivery.

Demanding a literal copy would have reported a working surface as broken and pushed someone toward duplicating the body into an alias, which is the exact drift the include exists to prevent. The test still fails if the include is missing, or if it points at a template that does not carry the block, so a rename of the included file is caught.

## Troubleshooting

### The rendering test surfaced the inheritance architecture

Three integrations failed the first run with zero occurrences of the heading. That was the test being wrong about the delivery mechanism, not the rollout being incomplete: the assertion assumed every platform gets a copy. Fixed as described above.

### Windows MAX_PATH, not a missing file

Three other cases failed with `[WinError 3] The system cannot find the path specified` while copying skill references. The message reads like a missing file and is a path-length ceiling: installing a platform copies the whole catalog, the deepest artifact is around 160 characters (`skills/tests-generation/<skill>/references/step-2-....md`), and pytest's own `tmp_path` is already about 100 characters, which lands at or past the Windows limit of 260.

Fixed with a `short_root` fixture that allocates one directory directly under the system temp with a three-character prefix and single-character subdirectories. Deliberately NOT by requiring long-path support on the host, which cannot be assumed for a contributor machine. The fixture docstring records the arithmetic so the next person does not re-diagnose it.

### A newline escape became a real newline

The same class as Phase 3's stray backspace, in the opposite direction: writing `"\\n## "` through a patch script produced a literal newline inside a Python string, which is a `SyntaxError` at collection. Replaced with a module-level `NEXT_SECTION` constant, which is clearer than an escape at every call site anyway.
