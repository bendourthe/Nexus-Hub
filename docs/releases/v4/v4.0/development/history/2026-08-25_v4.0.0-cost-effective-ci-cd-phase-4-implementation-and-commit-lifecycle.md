## What this phase delivered

Phase 3 made plans SAY the lifecycle. Phase 4 makes `/implement` ENFORCE it. `implement-phase` is the only skill in the catalog that mutates git history and external state, so this is the phase where the policy becomes behavior.

### T018, T019 - The runbook and the skill invariants

Four changes to `references/implement-phase-runbook.md`:

1. **Step 8.3** was "CI/CD readiness + optimization (per-phase)", which detected the CI system and then ran an optimization pass every phase. It is now "CI impact record (per-phase, no remote run)": it records what this phase added that CI would need to know about and whether the pipeline already covers it, declares a no-op record valid, and forbids changing a pipeline file unless CI/CD is THIS phase's explicit deliverable. Anything the record shows uncovered becomes an input to the terminal reconciliation.

2. **Step 8.10** was "Commit-and-push prompt", and every mode offered push: the one-phase ask had "2. Commit and push", the phase-by-phase menu had two push options out of five. It is now "Commit prompt", and a non-final phase is commit-only in EVERY mode. One-phase asks Commit / Amend / Stop; `phase-by-phase` offers commit-and-continue, commit-and-pause, other; `in-full` auto-commits, which is what it already did.

3. **Duty 5 of section 9.0** was "create or update the CI/CD pipeline ... and optimize it". It is now the six-step terminal reconciliation via `[[cicd-architect]]`, and it states explicitly that this is the one place in the whole plan where pipeline files change.

4. **Section 9B** was "Verify tests and CI/CD readiness". It is now "Complete LOCAL gate", with the reason stated: it runs before publication, so it cannot depend on a remote result, and anything provable only remotely is a hole in the local gate rather than a reason to publish early and find out.

**New section 9F** carries the plan's single remote event as nine numbered steps: final commit, explicit approval gate, one push, integration pull request against the integration branch, wait for terminal check states, reopen-on-red with a mandatory local reproduction, merge only on green plus user approval, verify the post-merge workflow stayed minimal, and quote the evidence. The 9C-9E handoff hold conditions gained three clauses: branch not published, a required check not green, merge not landed.

`SKILL.md` (the always-loaded invariants) was updated to match, plus three new Common Rationalizations and two tightened Verification items.

### T020 - The `/implement` dispatcher

A "Phase lifecycle (guarantee)" section with three guarantees and no procedure. The push options were removed from the argument-resolution lines. A test asserts the dispatcher contains none of the runbook's procedural tokens and stays within a 120-line budget.

### T021 - Plan-context mode in `code-commit-workflow`

A new section, explicitly scoped ("Outside that context, ignore it"), covering four things: the commit unit is the phase rather than the sub-task, non-final plan commits stay local, the final commit is the only one that publishes, and correction work after a red check is an amend OR one stabilization commit, never both and never a series.

The phase-as-unit argument is worth stating precisely, because it looks like a relaxation of atomicity and is not. A plan phase is the smallest independently revertible unit the plan defines: its sub-tasks are written to complete together and its exit checklist gates on all of them. Committing per sub-task produces intermediate states that never passed the phase gate, so reverting one leaves a tree the plan never validated. The exception is explicit: when the plan itself defines finer units, the plan wins.

The generic one-off commit workflow is unchanged and is asserted to survive.

### T022 - `tests/skills/test_implement_lifecycle_contract.py`

36 assertions across the four transitions the plan named (non-final, final, failed remote check, release handoff), plus dispatcher thinness and the commit skill.

Seven of them are NEGATIVE fixtures asserting that the pre-v4.0.0 wording is gone. That is deliberate: "commit and push every phase" and "update CI every phase" were the DEFAULTS before this release, so a regression would read as a restoration to anyone who remembers the old runbook. Asserting absence is what makes a removal stick.

## Decisions

### The no-push rule removes a default, not the user's authority

Both the runbook and `code-commit-workflow` state that a user who explicitly asks to push a non-final phase gets it, after a one-line statement of the cost. A test asserts that sentence is present.

This matters because the alternative reading (a hard prohibition) would be wrong on two counts. It would put the skill in the position of refusing an ordinary, reversible git operation the user is entitled to, and it would invite the user to work around the skill entirely, which loses the cost warning as well as the default. What was actually broken was the DEFAULT: a menu that offered push at every phase boundary made the expensive path the easy one.

### Pushing for backup is a real need with a wrong solution

Added as a rationalization rather than ignored: a remote branch is a backup, but a remote PIPELINE RUN is a bill. Someone pushing per phase for durability is solving a real problem in a way that costs six runs of knowingly incomplete work. The answer is a branch that does not trigger validation, or a local mirror, not a change to the lifecycle.

## Troubleshooting

### Four pre-existing tests locked in the removed behavior

`tests/skills/test_implement_driver_modes.py` asserted the exact push options this phase removes: `"2. Commit and push"`, `"(2) commit, push, and continue"`, `"(4) commit, push, and pause"`, and `"five-option menu"`.

These were not stale tests. They correctly encoded the v3.21.0 contract, and this plan deliberately changes that contract. They were updated rather than deleted, keeping their original job (proving the three modes exist and are named consistently across the command, the skill, and the runbook) and handing the removed options to the negative fixtures in the new lifecycle file. The module docstring records what changed and why, so the next reader does not have to reconstruct it from a diff.

### Two skill bodies crossed the 500-line soft cap

`code-commit-workflow` went to 504 body lines when the plan-context mode was added. Same remedy as Phase 3: the 116-line "Commit Message Examples" section moved to `references/commit-message-examples.md`, which is the right split on its own terms since examples are looked up when writing a specific message rather than needed on every trigger. The body is now 394 lines, which leaves real headroom rather than sitting one edit under the cap.

### Two parity tests broke on a Phase 3 move, not a Phase 4 change

`tests/skills/test_installer_parity_lifecycle.py` failed on `implementation-plan/SKILL.md` missing "more than one installer" and "execute the real installers on their target operating systems". Neither string was deleted: Phase 3 moved the mandatory-final-phase template, which carries the installer-parity language, into `references/mandatory-final-phase.md`.

The tests were reading only `SKILL.md`, so they reported a standing release gate as MISSING when it had merely moved one file. Fixed by reading the skill and its final-phase reference together, with a comment recording why the planning contract is now two files.

Worth recording as a class: extracting content to a Tier 3 reference relocates every assertion that pointed at it, and the assertion does not have to be in the same test file, the same phase, or written by the same person. The whole-suite run is what caught this; the targeted per-phase runs did not touch that file.

### An assertion pinned the wrong casing

`test_correction_work_is_an_amend_or_one_stabilization_commit` asserted `"Never both, and never a series."` against the runbook, where the sentence appears mid-clause in lowercase. Relaxed to a case-insensitive match and strengthened with a second assertion that the runbook cites `[[code-commit-workflow]]` as the owner of the amend-versus-stabilize choice, so the test now checks the ownership boundary as well as the rule.
