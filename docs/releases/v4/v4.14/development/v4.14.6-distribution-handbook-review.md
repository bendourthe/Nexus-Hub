# Distribution Handbook Review - v4.14.6

**Covers**: whether the distribution handbook's claims change when v4.14.6 edits `scripts/nexus_hub_cli.py`, and the evidence behind refreshing that input's digest in `docs/handbooks/_sources/distribution/evidence.json`. Phase 3 also edits `scripts/installer.sh` and `scripts/installer.ps1`, and this record covers that change. Phase 5 edits both installers again to build and install the VS Code extension, and its section below covers that change.

## Phase 2 change

Phase 2 adds one subcommand to the CLI core: `nexus-hub settings` with two read-only actions, `show` and `explain`. `git diff --numstat -- scripts/nexus_hub_cli.py` shows additions only (0 deletions): a `SettingsCliError` class, `_load_settings_control`, `_settings_parser`, `_settings_project`, `_settings_show`, `_settings_explain`, `cmd_settings`, one `sub.add_parser("settings", ...)` registration in `build_parser`, and one `if raw and raw[0] == "settings"` interception in `main`. No existing function, including the upgrade path, is changed.

The new command reads the tool configuration files and the environment and prints a report. It writes no file, changes no installer behavior, seeds no key, and sends nothing over a network. `scripts/lib/settings_control/` rides along with the installers' whole-tree copy of `scripts/lib`, so neither installer script changes in this phase.

## Phase 3 change

Phase 3 adds the write side to the same `nexus-hub settings` subcommand: `set`, `reset`, `remove-override`, `record-editor-write`, and `owned-keys`, plus `_load_settings_apply`, `_settings_write`, and the extra parser entries. The existing `show` and `explain` paths and the upgrade code are untouched.

Both installers change in one place each, inside the existing core-settings function (`install_core_settings` and `Install-CoreSettings`). Before seeding, the function runs `nexus-hub settings owned-keys --json --home <home>` from the tree being installed (`$repo_root/scripts/nexus_hub_cli.py`, not the previously installed copy, which may predate the command) and skips every key path the user's ownership record lists: it is neither seeded when absent, nor upgraded when it equals an old seed, nor retired as a legacy effort variable. When Python is missing or the record cannot be read, the function prints a warning and seeds nothing, so a recorded choice is never overwritten blind. A missing record means no recorded choices. The platform-defaults seeder (`scripts/lib/integrations/platform_defaults.py`, which is not a handbook input) applies the same rule to Codex and Copilot.

Nothing else in either installer changes: no new function, no new copy step (`scripts/lib` is copied as a whole tree), no network call, no write outside the files the function already wrote.
