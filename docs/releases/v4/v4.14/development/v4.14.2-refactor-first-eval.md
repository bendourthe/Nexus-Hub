## Pre-registered rule

Copied verbatim from the admission file, where it was dated 2026-10-20 before the first paid run:

8. Verdict rule, pre-registered here and copied unchanged into the admission file before any run (Q9). Fixtures: three small repositories, each with one expression duplicated across three files (a pricing-style formula, a display format string, a numeric threshold), a passing test suite, and a task asking for a feature that needs that logic. Runs: 4 per fixture per arm (24 runs), plus up to 12 treatment re-runs in one revision round. A run passes refactor-first when its transcript shows a green test run after the last refactor edit and before the first feature edit, and the final suite is green. A run passes enumerate-every-copy when a search of the final tree finds the expression in exactly one definition and every original caller uses it. A rule is CHANGED when the treatment passes at least 4 more of 12 runs than the control; otherwise NO_CHANGE.

9. On NO_CHANGE for a rule: revise that rule's wording once within the remaining cap and re-run the treatment arm only; if still not CHANGED, keep it as low-cost guidance and record a known gap. Rules are never reverted on a negative verdict.

## What the instrument could and could not see

- Validity: every counted run is valid under the definitions frozen in the admission file before the first paid run ("Valid run" and "Refactor-first anchor clause"): each record reads `measured`, and the anchor test is about the staged skills, which carried the clause in every treatment and revision run and lacked it in every control run. Those definitions do not require the agent to load a skill, so the verdicts above stand as NO_CHANGE rather than NOT_MEASURED; the next point is what they therefore do and do not show.
- Across all 36 counted runs, the agent invoked no skill: 0 `Skill` calls in each arm. The rule bodies therefore never reached the agent; only the skill descriptions in its listing did. This evaluation measures whether the rules change behavior when merely available, not whether they work once read.
- No run edited `web.py`, `batch.py`, or `report.py`. Every run wrote the new feature module and its test, and most reused one existing copy. The task text asks for the feature in `feature.py` and for the existing APIs to stay unchanged, which pulls toward that outcome in every arm.
- The frozen permissions allow only the suite command, and some runs had a quick check command denied before they edited; this applied equally to all arms.
- "Final suite green" partly measures how the command was typed: the grader counts only the exact `python -m pytest -q`, and the runs that piped the full suite to `tail` (6 in control, 10 in treatment, 5 in revision) are not counted. Neither rule's verdict depends on this column, because no run passed either rule in any arm.
- The two revised wordings echo the fixture task (a feature placed in a new file). They are kept as catalog text because the revision rule never reverts a rule, but they were written against this evaluation, which DF-18 and DF-19 should be read with.
- Plan sub-task 5.1 speaks of each run's "loaded" text; the admission file froze that, before the first run, as the skills staged into the run's home. Because no run loaded a skill body, this is recorded as a deviation from the plan's wording rather than as compliance with it.
