# v4.14.0 Permission Writer Proposal

The existing Windows strict-permission writer can skip the requested security overlay when settings contain JSON keys that differ only by case. This tested proposal changes only Merge-StrictPermissions in scripts/installer.ps1. It has not been applied. CI inclusion blocker 1 is already answered; this is a new permission-writer approval boundary.

## Problem

Core settings now preserve exact JSON names and add the documented uppercase subagent key. If a differently cased user key already exists, the unchanged strict writer cannot parse that pair into its case-insensitive object and skips the explicitly selected strict option. The same failure occurs with unrelated VAR/var environment keys. The actual native original-function negative controls reproduced this in Windows PowerShell 5.1 and PowerShell 7.6.7. A warning does not establish that the requested security settings were installed.

## Exact change

[The review patch](v4.14.0-phase-7-receipts/strict-permissions-proposal/strict-permissions.diff) contains 27 added and 16 removed lines, all within Merge-StrictPermissions. The proposal reuses Read-JsonDocument and exact-key dictionaries, checks object and string-array shapes before writing, preserves the existing allow list and user data, retains the additive deny/ask merge and original messages, and uses literal paths for file checks and the pre-write backup. It does not change the shipped overlay, its 22 deny entries or 12 ask entries, any permission default or flag, a workflow, secret, dependency, or another function.

## Cost and risk

Cost is one function with 11 net lines and an existing reader. No additional workflow run, job, runner, runtime dependency, policy entry or network request is introduced. The main compatibility change is that malformed custom permission data visibly refuses instead of being coerced or partially merged. The current backup naming and fail-soft behavior remain. The tested 100-level serialization ceiling is bounded, not an arbitrary-depth promise.

Applying this proposal makes an already selected strict option install its intended deny/ask rules on the demonstrated valid case-sensitive inputs. Doing nothing keeps the warning-and-skip behavior and leaves the requested overlay absent. Recommendation: approve the function-only patch, then rerun the affected and full gates. Legacy hook writers' case-sensitive parsing skips remain a separate in-scope finding to repair before the final installer claim.
