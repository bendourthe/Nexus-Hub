## Section 1: Executive Summary

AiKA Modes is Spotify's internal-developer-portal answer to the same question Nexus-Hub answers with `context-modes` and `agent-presets`: how do you stop one general assistant from behaving identically across support, review, and incident work? The concepts converge almost exactly. Nexus-Hub is ahead on the parts that concern authoring quality and context economy, and behind on exactly one axis.

**The one substantive gap is the processor pipeline.** AiKA lets a mode declare optional response-quality stages (classification, planning, answer formatting, verification with bounded retries, confidence scoring, context management) as composable configuration, each with its own model override. Nexus-Hub already performs five of those six disciplines somewhere in the catalog, and in places performs them better, but it performs them as bespoke logic baked into individual skills rather than as a contract a mode or preset can declare. [`multi-agent-code-review`](../../../../../catalog/skills/code-review/multi-agent-code-review/SKILL.md) has confidence anchoring, an independent validation pass, mode-aware demotion, and a cheaper model tier for advisory reviewers; [`lint-repair-loop`](../../../../../catalog/skills/code-cleanup/lint-repair-loop/SKILL.md) has a bounded repair loop capped at three judgment iterations. Neither discipline is reachable from [`context-modes`](../../../../../catalog/skills/workflow/context-modes/SKILL.md), which declares posture and prose-level forbidden actions but no output contract, no verification stage, and no confidence signal.

**One genuinely absent capability**: response-level confidence scoring. `multi-agent-code-review` scores individual findings by corroboration; nothing in the 337-skill catalog rates a whole agent response low / medium / high according to how well tool results actually support it. That is the single highest-value item here, because it is hallucination control on the output surface rather than on a findings list.

**Where Nexus-Hub is clearly ahead**: mode-instruction authoring (the AGENTS.md pushy-description rule plus mandatory SKIP clauses plus [`skill-description-authoring`](../../../../../catalog/skills/developer-experience/skill-description-authoring/SKILL.md) is a far more developed treatment than the source's three bullets), context management (`extensions/nexus-context-compressor` and the v4.10.1 adaptive compaction work versus a `tokenLimit.limit` field), and invocation policy (the `disable-model-invocation` / `user-invocable` frontmatter pair is more expressive than private/public visibility).

**Recommended adoption: four items, all `skill-native`, zero new outbound calls, zero new dependencies, zero new third-party processors, zero new credentials.** Four further insights are declined, three of them because they are multi-tenant SaaS concerns with no meaning in a local-first catalog.

## Section 6: Sequenced Adoption Plan (Step 6)

1. **A1 - response-level confidence scoring (P0).** Define the low / medium / high rating and, crucially, the evidence rule that assigns it: how much of the claim is backed by a tool result observed in this session versus asserted from model memory. Target a new skill or an extension of [`verification-before-completion`](../../../../../catalog/skills/workflow/verification-before-completion/SKILL.md), cross-linked from [`agent-communication`](../../../../../catalog/skills/developer-experience/agent-communication/SKILL.md) so the rating has a defined place in the output contract. Reuse the anchor vocabulary already established in `catalog/skills/code-review/code-quality/references/confidence-anchored-scoring.md` rather than inventing a second scale.
2. **A3 - mode-bound tool allowlist (P1).** Independent of A1, so it can run in parallel. Convert the `context-modes` "Forbidden actions" column from prose into an explicit default-deny statement bound to `agent-access-policy`, and carry over the source's warning that granting a server without naming tools grants everything on it.
3. **A2 - cost honesty (P1).** Depends on nothing. State in `agent-presets` and `context-modes` that each added quality stage is an extra model round trip and that bounded retries multiply it.
4. **A4 - declarable quality stages (P1).** Sequenced last because it consumes A1, A2, and A3: the stage contract should be able to name the confidence rating, carry the cost statement, and reference the tool allowlist. Retrofit `context-modes` and `agent-presets` to declare stages, and give the bounded round count a stated default, taking the existing `lint-repair-loop` cap of 3 as the precedent rather than importing the source's 2-and-5.

## Section 8: Risks, Conflicts, and NOT Recommended (Step 7)

### Conflicts and risks for adopted items

| Item | Conflict / risk | Mitigation |
|---|---|---|
| A1 | A second confidence vocabulary competing with the existing per-finding anchor scale would make two ratings mean different things under one word. | Reuse or explicitly subordinate the `confidence-anchored-scoring` vocabulary; state the relationship in the skill body. |
| A1 | A confidence label becomes decorative if the agent can assign it without a rule, and a decorative rating is worse than none because it reads as verified. | The evidence rule (tool-result support observed this session) is the deliverable; the label is a consequence of it. |
| A3 | Modifies an existing skill (`context-modes`) rather than adding a file, which is the higher-risk change shape. | Narrow edit confined to the tools column plus a cross-link. |
| A4 | Highest risk of all four: a stage contract is exactly the kind of "design possibility turned into unused production structure" the `Boundaries` section of `AGENTS.md` declines, and `minimal-construction` applies. | Do not build a stage framework. Adopt only stages with a real call site: `context-modes` and `agent-presets` are the two call sites, and if the retrofit does not simplify them, drop A4. |
| A4 | Adding stages to presets risks stacking cost by default. | A2 must land first; stages are opt-in, never default-on. |

### NOT recommended

| Declined | Grounds |
|---|---|
| I11 analytics half (request-type labels for usage reporting) | Requires collecting and retaining usage telemetry. Nexus-Hub is local-first and collects none. The routing half is already covered by `model-routing`; the analytics half is dropped on privacy grounds, consistent with the MCP Registry Policy hard-no on shipping user activity to a third party. |
| I14 popularity discovery (top 5 modes, 30 days) | Same telemetry premise, plus a shared workspace that does not exist. `skill-stocktake` audits quality deliberately rather than popularity, and a popularity ranking would actively degrade skill selection by favouring frequency over fit. |
| I15 private/public visibility | Multi-tenant premise. Git ownership plus the Organization Knowledge Layer's explicit-connection model already covers distribution, and a visibility flag would add a second, weaker authority surface. |
| I16 ownership transfer to a group | Same premise; git already owns this. |
| The source's literal config schema (`mcpTools`, `maxRounds`, `tokenLimit.limit`, `labels`) | Copying a hosted product's YAML shape into a Markdown-skill catalog imports form without function. A4 adopts the DISCIPLINE and expresses it in Nexus-Hub's own idiom, per the skill's compare-function-not-form rule and the AGENTS.md Reverse-Engineering Attribution Rule. |
