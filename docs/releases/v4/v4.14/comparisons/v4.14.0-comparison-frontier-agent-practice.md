# Comparison: Frontier Agent Practice (kiro.dev, pstack, Gemini token reduction)

**Adoption target: v4.14.0**

**Authored during**: the v4.10.0 cycle (`feat/v4.10.0-plan-queue-continuity`)
**Authored on**: 2026-09-10
**Source type**: three article-class sources (one web page, two local `.docx` guides)
**Comparison mode**: insight extraction and relevance analysis (no project source, so the 11-dimension matrix does not apply)

## Section 1: Executive Summary

Three sources were compared against Nexus-Hub. They are not equally novel, and saying so up front is the point of this report.

**Source 3 (the Gemini token-reduction guide) is a near-total re-run of work Nexus-Hub already shipped.** Its subject, the `headroom` compression layer, was compared in [`docs/releases/v3/v3.2/comparisons/v3.2.0-comparison-headroom.md`](../../../v3/v3.2/comparisons/v3.2.0-comparison-headroom.md) and adopted across seven phases in v3.2.0 as `extensions/nexus-context-compressor`. Every headline feature the article describes already has an owned internal equivalent: `SmartCrusher` maps to the JSON-array dedup strategy, `CodeCompressor` to the AST-aware code strategy, and compress-cache-retrieve to the reversible `<<ccr:HASH>>` marker plus the content-hashed SQLite store. On one axis Nexus-Hub is stricter than the source: `headroom` is lossy by design and returned `NOT PRESENT` for an ordinary record, while the internal engine is documented as non-lossy with deferred rather than destroyed information. Only three things in the article are net-new, and the most valuable of them is a test methodology rather than a feature.

**Source 2 (the pstack guide) is the substantive source.** Its `/teach`, `/how`, `/why` and `/recall` skills were already adopted in v3.2.0 via [`v3.2.0-comparison-teach.md`](../../../v3/v3.2/comparisons/v3.2.0-comparison-teach.md), and its conditionally-loaded "playbook" pattern is exactly Nexus-Hub's Tier-3 `references/` convention. But two of its ideas have no counterpart anywhere in the 337-skill catalog: the **Build the Lever** principle, which has the agent generate and maintain a project-specific control CLI that every later agent drives instead of writing throwaway scripts, and the **Feature Map**, a searchable `references/features/` catalog recording each feature, its user-POV route, its drive commands, and its gotchas. Nexus-Hub's [`functional-verification`](../../../../../catalog/skills/testing/functional-verification/SKILL.md) tells an agent how to exercise an artifact; nothing tells an agent to build and maintain the instrument that does the exercising. That is the single highest-value gap in this cycle.

**Source 1 (the kiro.dev frontier-engineering page) is thin on evidence and mostly confirmatory.** The live page publishes only ten principle titles with no bodies, sub-practices, tooling, or metrics, so every claim below rests on a title plus the summary text supplied in the request. Eight of the ten map onto capabilities Nexus-Hub already ships. One, "treat code as disposable", is genuinely absent as a stated doctrine and converges with pstack's "scrap when the design is wrong" gate, so the two are merged into a single adoption candidate.

The recommended adoption is deliberately small: **five items, all `skill-native` or `re-full`, zero new outbound calls, zero new dependencies, zero new third-party processors.** Four further items are explicitly declined, three of them because they contradict decisions this repository has already recorded.

## Section 8: Risks, Conflicts, and Items NOT Recommended

### Conflicts with existing conventions

- **A1 versus the v4.3.0 verification ladder.** [`docs/releases/v4/v4.3/plans/v4.3.0-agentic-verification-discipline.md`](../../v4.3/plans/v4.3.0-agentic-verification-discipline.md) is partially implemented and already owns tiered verification gating. A1 must declare a rule-ownership split per the `AGENTS.md` overlapping-skills rule: **v4.3.0 owns when verification runs and how severe a failure is; A1 owns building and maintaining the instrument.** Without that split, a review reports one root cause twice.
- **A6 owner ambiguity.** Restate-before-acting plausibly belongs to [[ambiguity-detector]] or [[idea-refine]]. Exactly one must own it.
- **A8 and existing gates.** A deterministic validator must not restate what [[plan-review]] and [[cross-artifact-analyzer]] already judge; scope it to structure and format only.
- **A1 body size.** The control-CLI plus Feature Map material will exceed the 500-line soft target if inlined. It must ship as a thin body plus `references/`, per the size norm in `AGENTS.md`.

### Items explicitly NOT recommended

- **N1: Cloud agents in place of git worktrees** (pstack P18). `drop-outright`. Vendor-intrinsic to Cursor infrastructure, requires a commercial relationship, and ships source code off the machine. It fails condition 1 of the trusted-vendor-wrapper tier of the **MCP Registry Policy** (the vendor is not the intrinsic data destination; it is incidental compute) and contradicts Nexus-Hub's local-first posture and the recorded position in [[using-git-worktrees]]. The underlying goal, parallelism, is already served locally.
- **N2: Compression proxy with a `base_url` override** (Gemini G7). `drop-outright`, and already declined once. The v3.2.0 comparison rejected it as N2 because a proxy holds the user's provider API keys and intercepts all traffic, a broad new trust surface under the **MCP Registry Policy** preference for zero new outbound and zero new processors. Re-encountering the same recommendation from a second source is not new evidence. Keep declined.
- **N3: Delete plans when finished** (pstack P17). Declined on recorded policy. [`docs/policy/docs-retention.md`](../../../../policy/docs-retention.md) states that `plans/` never ages out, and the v4.10.0 plan-queue work depends on committed plans remaining readable to enumerate the queue. Adopting P17 would break `scripts/enumerate_plan_queue.py`.
- **N4: Never review abstract plans adversarially** (pstack P19). Declined, with the tension recorded rather than resolved. The source's reasoning (agents hallucinate theoretical risks in abstract review) is a real failure mode, but Nexus-Hub ships [[plan-review]] with adversarial lenses as a deliberate gate, and the source's proposed replacement (prototype instead) is captured by A2 and by [[competitive-generation]]. Adopting the prototype-first habit is compatible; deleting adversarial plan review is not.

### Evidence limitations

- **Source 1 depth could not be obtained.** The kiro.dev page publishes ten titles and no bodies. Every S1 row rests on a title plus the summary supplied in the request. If the linked per-principle pages later become available, K3, K4, and K6 are the rows most likely to change.
- **Source 2 is a vendor-authored guide** describing a proprietary skill pack (`pstack`) whose implementation was not inspected. Behavior claims (2,462 PRs in a month, 100-1000x output) are reproduced as source claims and were not verified.
- **Source 3 benchmark numbers were not reproduced.** The 76% reduction and TTFT figures are the article's, on `gemini-3.8-flash` via Vertex, and are cited as motivation for A3, not as a target for Nexus-Hub's own engine.
