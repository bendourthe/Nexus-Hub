# Comparison: Codex Memory Model Overrides

Authored: 2026-10-15
Authoring cycle: v4.13.x (last tag `v4.13.13`)

Target status: confirmed by the user on 2026-10-15. Lowest free slot after in-flight `v4.14.0`, which edits the same two defaults files, and ahead of `v4.15.2` (edits the same levers contract) and `v4.16.1` / `v4.20.1` (edit `agent-memory`), so the memory-store rule below lands before those plans build on it. Sources: one (a practitioner article pasted inline, no URL)
Skill: `cross-project-comparison`

The source tells Codex users to pin larger models for background memory generation through two `[memories]` keys in `~/.codex/config.toml`. OpenAI's own documentation confirms both keys and both model ids, but the recipe as published does nothing: Memories is off by default and the snippet never turns it on. For Nexus-Hub the recipe itself is not adoptable, because seeding an account-dependent model id into users' configs is exactly what the do-not-invent rule forbids. What is adoptable is the evidence around it: record the memory levers as VERIFIED and deliberately not seeded, make "not seeded" enforceable by a test, close a gap in the memory-substrate contract that assumes every host memory surface is an editable index, and decide whether to seed the one memory lever that reduces prompt-injection persistence.

## Step 7: Risks, conflicts, and items not recommended

**Conflicts to resolve during implementation:**

- **Contract wording versus reality.** `memory-substrate-contract.md` line 3 says a harness surface "is never a competing store". A4 does not weaken the substrate's authority; it adds a class for a store Nexus-Hub does not own, so the substrate still wins in agent behavior while the host store is left untouched.
- **A3 versus `v4.14.0`'s key-level assertion.** Two key parsers in one test file would be the duplication the rule-ownership convention forbids. A3 reuses whatever `v4.14.0` lands.
- **A5 and Nexus-Hub's own MCP servers.** Seeding `disable_on_external_context = true` protects memory from tool-returned content, but it also excludes every thread that called any MCP tool or web search, including Nexus-Hub registry servers such as `nexus-skill-server` when a user has configured them. The decision record must weigh this, and "do not seed, document the lever" is a valid outcome.

**Not recommended:**

| Item | Reason |
|---|---|
| Seeding `memories.extract_model` or `memories.consolidation_model` with any model id | Do-not-invent rule: V1 documents no default and no self-selecting value. Availability is account-dependent (V3: `gpt-6.1-sol` absent on Free and Go, admin-gated on Enterprise and Edu), and ids rotate quickly (V3: `gpt-5.5` retired 2026-10-14, `gpt-5.4` on 2026-08-31). A pinned id would also move rate-limit cost onto users who never chose it. V1 and V2 do not say what Codex does when an override model is unavailable; that unknown is itself a reason not to seed. |
| Seeding `features.memories = true` | Turns on summarization and persistence of every eligible thread. That changes the user's privacy posture and is the user's decision, not an installer default. |
| Publishing M's recipe in a guide | As written it is a no-op (M7) and names ids that will be stale within months. A1 records the keys with links to V1 and V2, which stay current. |
| Mapping memory overrides into `model-routing` tiers | `model-routing` chooses the model for the working session, not for vendor background jobs; a mapping would encourage pinning ids, which the first row rejects. |
| Attributing background memory passes in `/usage` | Low value: the vendor already skips passes below the 25 percent threshold (M6), and `v4.16.3` owns `catalog/commands/usage.md`. Backlog only. |
