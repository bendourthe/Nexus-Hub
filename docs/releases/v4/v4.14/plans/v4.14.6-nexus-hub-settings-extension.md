# Plan -- Nexus-Hub Settings: Proven Central Defaults for Claude Code, Codex, and GitHub Copilot

**Project**: Nexus-Hub
**Version**: v4.14.6
**Slug**: nexus-hub-settings-extension
**Filename**: `v4.14.6-nexus-hub-settings-extension.md`
**Plan Type**: Feature
**Created**: 2026-10-15
**Status**: queued
**Seeded from**: maintainer decision Q10 (2026-10-14), recorded in the `## Follow-on` section of `docs/releases/v4/v4.14/plans/v4.14.4-adoption-gate-outcomes-and-opt-in-git-guard.md`, and the 2026-10-15 `/plan feature` request.

**Goal**: A user sets their default reasoning effort, default model, approval posture, commit attribution, and git-guardrails mode once, in one place (a `nexus-hub settings` command and a "Nexus-Hub Settings" panel in VS Code), and every new Claude Code, Codex, and GitHub Copilot session starts with those defaults. Every control the panel shows has been observed changing a fresh session before it shipped. Anything that would stop a default from taking effect (an environment variable, a project file, an organization policy, a mode the tool's own UI remembers, or a tool that has no such setting) is shown to the user instead of a toggle that silently does nothing.

## Problem

| User | Harm today | DoD |
|---|---|---|
| Anyone using two or more of Claude Code, Codex, and Copilot | Each default lives in a different file with a different key and value set (`~/.claude/settings.json`, `~/.codex/config.toml`, `~/.copilot/settings.json`, VS Code user settings). Changing "start at high effort" means editing four places, three of them by hand | DoD 2, DoD 4 |
| The maintainer, who wants High effort by default | `~/.claude/settings.json` holds `env.CLAUDE_CODE_EFFORT_LEVEL`, seeded before any seed record existed. It outranks `/effort` and every saved per-model level, so an in-session choice never persists (memory `settings-changes-must-be-proven-live`; known gaps WN-13 and DF-14) | DoD 2, DoD 5, DoD 8 |
| A user who switches on "Bypass permissions" | A remembered in-panel mode, a project `.claude/settings.json`, a repository `.github/copilot/settings.json`, Nexus-Hub's own Copilot CLI `disableBypassPermissionsMode: "disable"` seed, or an organization policy can override the default with no visible sign | DoD 3, DoD 5 |
| Anyone who tries a settings toggle in any tool | A toggle that writes a key the tool ignores looks identical to one that works. v3.17.2 already retired an "autonomy controller" that could not guarantee its effect (`CHANGELOG.md`, v3.17.2 "Removed") | DoD 1, DoD 7 |

## Definition of Done

**Must have:**

1. **Admission before code.** Every control and every per-tool write the plan ships appears in a bundled catalog, `scripts/lib/settings_control/catalog.json`, with:

    - the key and file;
    - allowed values;
    - the override layers that can beat it;
    - when it takes effect;
    - the tool-version range it was proven on;
    - a `weakens_safety` flag;
    - a source;
    - a **Proof Record**: the effect observed in a fresh session.

    Vendor writes cite a fetched primary vendor URL and date. The one internal control (git-guardrails) cites its owning decision record and is proven by a probe that its hook blocks or allows. A per-tool cell with no Proof Record is cataloged **Not-Settable** with its reason, never as a control. Keys shared with `configs/platform-defaults.json` point to that entry, and a validator fails when the two disagree on the key or its value set. `docs/policy/settings-control-contract.md` is the human companion and extends `docs/policy/platform-defaults-levers.md` rather than restating it.
2. **Five controls**, each with a per-tool value map. Effort takes one value applied to every tool, with an optional per-tool override. Model is chosen per tool, because each tool has its own model family. A cell with no faithful mapping is Not-Settable, never mapped to a looser or stricter mode.
    - **Default effort** (`low`, `medium`, `high`, `xhigh`). `max` is never written as a default.
        - Claude Code: `modelSettings.<model-id>.effortLevel` for each current Claude model id (a list bundled with the engine), plus top-level `effortLevel` for older models.
        - Codex: `model_reasoning_effort`.
        - Copilot CLI: `effortLevel`.
        - VS Code Copilot Chat: Not-Settable, because it is set per model in the model picker.
    - **Default model** (per tool).
        - Claude Code: `model`.
        - Codex: `model`.
        - Copilot CLI: `model`.
        - VS Code Copilot Chat: Not-Settable, because only the organization policy `ChatDefaultModel` exists.
    - **Approval posture** (`ask`, `accept-edits`, `full-auto`).
        - Claude Code: `permissions.defaultMode` and VS Code `claudeCode.initialPermissionMode`. `full-auto` also writes `skipDangerousModePermissionPrompt`, and any extension-side opt-in key Phase 1 proves the panel needs.
        - Codex: `ask` and `accept-edits` write `approval_policy = "on-request"` with `sandbox_mode = "workspace-write"`. `full-auto` writes `approval_policy = "never"` and keeps `workspace-write`. These writes happen only when the file does not use `default_permissions`. The retired value `untrusted` is never written.
        - VS Code Copilot Chat: `full-auto` writes `chat.tools.global.autoApprove: true`, and `ask` writes `false`. `accept-edits` is Not-Settable, because the switch is all-or-nothing.
        - Copilot CLI: `ask` and `accept-edits` leave the tool default. `full-auto` lifts the `permissions.disableBypassPermissionsMode` block. Allow-all itself is a launch flag and Not-Settable.
    - **Commit attribution off**.
        - Claude Code: `attribution.commit` and `attribution.pr` set to `""`.
        - Copilot CLI: `includeCoAuthoredBy: false`.
        - Codex: whatever Phase 1 verifies, otherwise Not-Settable.
        - VS Code Copilot Chat: Not-Settable.
    - **Git-guardrails mode**: `~/.nexus-hub/guardrails.json` `block_git_bypass_flags`, the switch v4.14.4 builds. The panel names the platforms whose hooks enforce it, and the `NEXUS_GUARD_GIT_BYPASS` override.
3. **The override view.** For every control and tool, `nexus-hub settings show` reports exactly one state. Notes the resolver cannot verify go in a separate `caveats` field (for example, the Claude Code panel remembers the last mode picked), never as a second state. The states are:

    - `in-effect`: the user's value applies.
    - `tool-default`: nothing is set, so the documented default applies.
    - `overridden-by <layer>`: names the file, environment variable, or policy, with a one-line fix built from catalog text only.
    - `not-settable`: shown with its reason.
    - `not-covered <model-id>`: a current Claude model with no effort entry.
    - `unverified-for-version <x>`: the installed tool is outside the proven range.
    - `tool-not-installed`.
    - `cannot-detect`: shown with its reason, for a layer no file or API exposes, such as an organization policy that VS Code `inspect()` does not report.

    A **Cannot remove** list per tool states what still prompts under `full-auto`: deny and ask rules, protected `.git` and `.claude` paths, critical-path `rm`, managed policy, and a running session's mode.
4. **One engine, two front ends.** `scripts/lib/settings_control/` reads and writes the tool config files. `nexus-hub settings` is its command-line front end, with these actions:

    - `show`, `explain`, `set`, and `reset`, each with `--json`, `--dry-run`, and `--project <dir>`;
    - `remove-override`;
    - `record-editor-write`.

    The VS Code extension `extensions/nexus-hub-settings/` is a thin panel over that JSON. It writes VS Code-host keys (`claudeCode.*`, `chat.*`) through the VS Code configuration API, because VS Code `settings.json` is JSON-with-comments and is stored per profile. It reports every editor write's previous value through `record-editor-write`, so `reset` returns the matching editor restores.

    File writes preserve comments and unrelated keys (`tomlkit` for TOML), follow symlinks to the real file, keep its permissions, are atomic, and address keys as segment arrays (a dotted model id is never split). Every write is recorded in `~/.nexus-hub/settings-control.json` (owner-only), keyed by tool, file, and key path, keeping the first previous value. `reset` restores a key only when its current value still equals what Nexus-Hub wrote. Otherwise it refuses, names the change, and drops the entry as user-owned.
5. **One ownership record, honored everywhere.** `~/.nexus-hub/settings-control.json` is the only record of user choices. Both installers and the platform-defaults seeder skip any key it lists, through one Python helper (`nexus-hub settings owned-keys --json`) rather than three parsers. A successful `reset` removes the entry, so normal seeding resumes.

    The **remove-override** action is offered for an override that Nexus-Hub probably seeded but has no seed record, for example the maintainer's legacy `env.CLAUDE_CODE_EFFORT_LEVEL` or the Copilot CLI bypass block. It removes the key only after the user confirms, and records the removal so `reset` restores it. A test proves both installers respect the record.
6. **Safety-weakening writes need a human.** Any write the catalog marks `weakens_safety` needs either the panel's confirmation dialog or an interactive terminal (a TTY on stdin and stdout). Those writes are `full-auto` posture, git-guardrails off, `remove-override` of a safety block, and `chat.tools.global.autoApprove`. They are refused when the tool's documented agent-session marker is present (for example `CLAUDECODE=1`). No flag bypasses this check. The confirmation repeats VS Code's own auto-approve warning, which the configuration API skips, and lists the Cannot remove items.
7. **Distribution and live proof.**
    - Both installers build and install the extension into VS Code. Cursor and Antigravity are a follow-on.
    - Installer parity, the smoke test, and a path-filtered CI workflow cover the extension.
    - The panel uses the Nexus-Hub logo (`assets/nexus-hub-favicon/android-chrome-512x512.png`).
    - The final phase re-runs the proof matrix for every shipped control on the maintainer's machine, from the final-phase branch build installed into a scratch home, and quotes the results.
8. **The maintainer's outcome.** On the maintainer's upgraded machine, removing the legacy effort override and choosing `high` and `full-auto` in the panel makes a fresh session in each tool start as follows:
    - Claude Code CLI: high effort, `bypassPermissions`.
    - Claude Code VS Code panel: `bypassPermissions`, unless a remembered mode is reported as a caveat.
    - Codex: high reasoning effort, approval `never`, sandbox `workspace-write`.
    - VS Code Copilot Chat: no tool-approval prompts.
    - Copilot CLI: high effort, with `--yolo` accepted.

    The panel states this per-tool table up front.

**Cut-line.** Phases 1 to 3 are the core that could be released on its own: a proven catalog, plus `nexus-hub settings show`, `set`, `reset`, and `remove-override` from the command line, plus installer agreement. Together they fix the effort and bypass harms. If the schedule slips, Phases 4 and 5 (the panel and its distribution) move to the next release, and `full-auto` in the panel is the first item deferred.

**Nice to have:** none. Advanced per-tool controls are deferred by maintainer decision (2026-10-15) and listed in `## Follow-on`.

## Non-Goals

- Changing a running session. Every control is a default for new sessions, and the panel says so.
- Overriding another extension's approval decisions at run time, through hooks or any VS Code API. That is what v3.17.2 retired. This plan only writes keys each vendor documents as user defaults.
- Persisting `max` effort, a Copilot CLI allow-all mode, or a VS Code Copilot Chat default model. None has a documented user-level setting, so each is shown Not-Settable with its reason.
- Writing project-level or managed files. Only user-level files are written; project and managed layers are read, never written.
- Hosting the panel in Cursor or Antigravity in v1 (maintainer decision Q1). Writes there would change that editor's settings, not VS Code's.
- Platforms other than Claude Code, Codex, and GitHub Copilot.
- Changing the installer's own seeded defaults. That is v4.14.0 Phase 6, whose effort lever this plan's design interview aligned (Q3).

## Overview

The settings extension was parked as a follow-on of v4.14.4 with two conditions: it may only set effort through levers each vendor documents, and it must show what it can never change. Research on 2026-10-15 against first-party documentation for all three vendors confirms both are needed. Of roughly 70 candidate keys, about 40 are documented, user-level, and observable. Three of the most-wanted controls have no user-level setting on at least one surface: the VS Code Copilot Chat default model, Copilot CLI allow-all, and `max` effort.

The plan is therefore **admission-first**. Phase 1 re-fetches the vendor pages and runs a **proof spike**. Each candidate write is applied in a scratch configuration home that holds a copy of the user's sign-in files. A fresh session of the real tool starts in an empty folder with its tools turned off, and the effect is recorded. Where the tool prints its effective settings non-interactively the observation is automatic. Otherwise it is a manual observation the maintainer makes in a normal session. Only writes that pass become controls.

Phases 2 and 3 build the engine (read side, then write side) behind `nexus-hub settings`. Phase 4 builds the panel, and Phase 5 distributes it. The final phase re-proves every control from the built candidate.

Every write is a plain edit to a documented user file, recorded with its previous value and reversible with `reset`. No background process, outbound call, or credential is added. The only dependency used is the existing optional `tomlkit`.

## Resolved decisions

**Discovery round (2026-10-15, every recommendation accepted):**

1. **Engine:** a Python engine behind `nexus-hub settings`, with the VS Code extension as a thin panel.
2. **Claude effort lever:** `modelSettings.<model-id>.effortLevel` for each current model. `/effort` keeps working in a session, and `max` cannot be a default.
3. **Scope:** the five core controls, the override view, and the Cannot remove list.
4. **Full autonomy:** offered behind a confirmation that names every remaining prompt.

**Plan review (2026-10-15).** Seven lenses ran: coherence, feasibility, product, scope, design, security, and adversarial. After dedup and cross-lens promotion, the confidence gate kept 0 P0 and 13 P1 findings. The design interview (round 1, every recommendation accepted) decided six of them:

1. **Q1, editor hosts:** VS Code only in v1. Editor writes are recorded through `record-editor-write` and restored by `reset`. Cursor and Antigravity go to the follow-on.
2. **Q2, legacy override:** a confirmed `remove-override` action, recorded so `reset` restores it. No heuristic auto-removal.
3. **Q3, v4.14.0 alignment:** v4.14.0 sub-task 6.1's recommendation is amended in this commit to seed `modelSettings` and stop seeding the environment variable.
4. **Q4, agent self-escalation:** the human-presence check in DoD 6. The `--confirm-full-auto` flag is dropped. A hook rule is a follow-on.
5. **Q5, proof-spike safety:** scratch homes with copied sign-in files (owner-only, deleted afterward). Real files are never touched. Manual observations are made by the maintainer.
6. **Q6, cut-line:** Phases 1 to 3 are the core that could be released alone.

**Applied directly from the review**, with no human choice needed:

- **Panel launch:** the panel runs an absolute Python interpreter with `~/.nexus-hub/scripts/nexus_hub_cli.py` from a fixed working directory, with no shell and no PATH lookup. The Windows `.cmd` launcher cannot be spawned without a shell, and a repository could plant a `nexus-hub` binary.
- **Workspace and webview:** untrusted workspaces get read-only behavior. Webview messages are validated against a catalog allowlist, the content security policy uses a nonce, and external links must use https on a vendor-host allowlist.
- **Secrets:** proof evidence quotes only the matched field and passes through redaction. Backups are owner-only and deleted after their hash check.
- **Single ownership record:** one Python helper for the installers. The record is keyed by segment-array key paths, keeps the first previous value, and `reset` refuses on drift.
- **Catalog:**
    - cross-checked against `configs/platform-defaults.json`;
    - an `internal` write kind for git-guardrails, with a hook-block probe;
    - proven version ranges;
    - a bundled Claude model-id list with a parity test against the model map;
    - the omitted-key list baked in at build time, because installed trees carry no `configs/`.
- **CI coverage:** `tests/settings_control/` is added to the repository-native profile in Phase 2, because no profile collected it on any operating system.
- **Override view:** a `tool-default` state, a separate `caveats` field, and a `cannot-detect` badge.
- **Proof matrix:** VS Code Claude Code panel rows prove bypass on that surface.
- **Panel ordering:** editor overrides are checked before the CLI writes anything, and a failed editor write rolls back the file writes.
- **Removed as unnecessary:** the record lock with its 10-second wait, the Windows lock retry, schema-version negotiation, and the guide's table generator.

## Phase 1: Admission: vendor re-check and proof spike

**Goal**: Before any engine code exists, every candidate write has a source and an observed effect in a fresh session, and every candidate without both is recorded as Not-Settable with its reason.

**Prerequisites**: v4.14.0 merged (same installer block, see Queued predecessors). v4.14.4 and v4.14.5 merged, or their absence recorded, so the dependent controls ship Not-Settable.

**Stability Gate**: `scripts/lib/settings_control/catalog.json` exists. `python -m pytest tests/validators/test_settings_control_catalog.py -q` passes, proving that:

- every entry has its key, file, values, override layers, take-effect timing, proven version range, `weakens_safety` flag, source, and either a Proof Record or a Not-Settable reason;
- shared keys agree with `configs/platform-defaults.json`;
- the bundled Claude id list matches the model map.

`docs/releases/v4/v4.14/development/v4.14.6-proof-matrix.md` holds one row per enumerated candidate, with the action, the observed field quoted, and the verdict. The user's real configuration files hash identically before and after the spike.

**Verification Expectation**: Pick three proof-matrix rows at random and repeat them: apply the write in a scratch home, start a fresh session of the real tool, and observe the recorded effect. Example effects are a Claude Code `stream-json` init line reporting `"permissionMode":"acceptEdits"`, Codex `/status` reporting `Approval: never`, or `git commit --no-verify` being blocked under the guardrails probe. Procedure via [[functional-verification]].

**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: This phase decides what ships. A wrong admission produces exactly the toggle that does nothing, which this plan exists to prevent. The spike also handles copies of the maintainer's sign-in files.
