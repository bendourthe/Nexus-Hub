**Seeded from**: `docs/releases/v4/v4.14/comparisons/v4.14.3-comparison-argon-enforcement-and-replayable-gates.md` (items B, C1, C2, and D; split from v4.14.3 by the maintainer on 2026-10-14)

**Goal**: A quality gate that cannot judge the work reports UNGATED. The agent then explains why in a short, plain message and asks the user whether to retry or to record a known gap; after two more failed attempts, or immediately on an unattended run, it records the gap with what would resolve it. Any logged gate verdict can be recomputed from what the record stores. A recurring review blocker that a machine can detect is promoted to a check whose message names the fix, proven red and then green. Teams that opt in get a `git-guardrails` mode that blocks the flags that skip git hooks or commit signing, switchable without a restart. `git-guardrails` also runs for the PowerShell tool, not only Bash. It is stated as defense-in-depth with documented limits, not a security boundary. No new third-party destination, credential, runtime dependency, or model download is added.

## Problem

| User | Harm today | Item |
|---|---|---|
| A developer relying on a quality gate | A gate with no criteria, or one with nothing measured, has only PASS or FAIL to report, so it can be read as a pass | DoD 1 |
| A developer whose agent cannot finish a gated task | The agent either loops or silently gives up; nothing tells the user why in plain words or asks what to do next | DoD 2 |
| A reviewer auditing a gate result later | A logged verdict cannot be recomputed, and a later edit to the gate silently changes what an old PASS meant | DoD 3 |
| A team whose agents repeat the same review blocker | `review-trapdoors` keeps the blocker as a checklist line and proposes a check only past about 15 entries, for the lowest-frequency ones | DoD 4 |
| A team that wants hooks and signing enforced | Nothing stops an agent from passing `--no-verify`, `-n`, or `--no-gpg-sign`; the rule exists only as an instruction | DoD 5 |
| A Windows user whose agent runs git through the PowerShell tool | `git-guardrails` is registered only for the Bash tool (`catalog/hooks/settings.json`), so every existing block (force push, hard reset, and the rest) is skipped | DoD 6 |

## Definition of Done

**Must have:**

1. `catalog/skills/orchestration/quality-gate-definitions/SKILL.md` adds an UNGATED outcome, with the precedence FAIL (blocking) > FAIL (fixable) > UNGATED > PARTIAL > PASS.
    - **Definition:** a gate with no required criteria; an automatic required criterion with no measured value or a zero denominator; a manual required criterion with no recorded judgment (approver and date); a pass^k criterion with fewer than k recorded trials; or a check that could not run.
    - **Optional criteria:** an unmeasured optional criterion yields PARTIAL, not UNGATED.
    - **Never a pass:** UNGATED never proceeds as PASS.
    - **Reasons:** the reason is recorded as a fixed category (`no-criteria`, `not-measured`, `zero-denominator`, `no-judgment`, `too-few-trials`, `tool-missing`, `timeout`), never as raw error text.
    - **Regression:** a required criterion that an earlier run of the same gate measured, and this run did not, is reported beside the outcome as a regression.
2. The same skill defines what happens after an UNGATED outcome, or a FAIL that has used up its retries.
    - **Interactive:** the agent shows the user a short structured message: what could not be judged, why, in plain words, and the two choices (retry, or record a known gap). After at most two further failed attempts, it records the known gap itself, with why it failed and what would resolve it.
    - **Unattended:** with no user to ask, the agent records the gap immediately, with the same explanation.
    - **Who accepts:** only the user accepts a known gap interactively, and the record names who accepted it. A gap recorded at the retry limit or on an unattended run names the reason instead.
    - **Missing-evidence wording:** handed off to `[[verification-before-completion]]` in one sentence.
    - **Retry loop:** `/implement`'s troubleshooting loop hands off to this rule in one sentence rather than defining its own.
3. The skill's Step 5 tracking template records each gate run so its verdict can be recomputed from the record alone:
    - The record stores the gate name; the definition's repository path and the commit SHA it ran against; and the sha256 of a defined canonical form of the definition block. That form runs from the `## Gate:` heading to the next heading of equal or higher level, with LF line endings, trailing whitespace stripped, and UTF-8 without BOM encoding.
    - Per required criterion, it stores the measured value (numbers and booleans only), the threshold, the comparison, and the producing command with a hash of its output, then the outcome.
    - The digest is for drift detection; the old definition is fetched from git by path and SHA.
    - A run whose definition changed in the same change set as the run is flagged.
    - Every rerun is logged, never overwritten.
    - Any other input is hashed per `[[egress-redaction]]`, never stored raw.
    - The template includes a worked example with its published digest.
4. `catalog/skills/code-review/review-trapdoors/SKILL.md` Step 5 promotes a recurring trapdoor to an automated check when the blocker is mechanically detectable, not when the list passes a size.
    - The check's failure message names the fix.
    - The trapdoor moves to a "promoted" list that names the check's path, but only after the check is shown failing on a seeded reproduction of the original blocker and passing once it is fixed.
    - Running and repairing the check is handed off to `[[lint-repair-loop]]`, and scripting it to `[[helper-script-authoring]]`.
5. `catalog/hooks/git-guardrails.sh` and `catalog/hooks/git-guardrails.ps1` gain an opt-in bypass-flag mode, specified by the Phase 4 decision record.
    - **Switch:** inert unless `~/.nexus-hub/guardrails.json` sets `"block_git_bypass_flags": true`. That file is read on every hook run, so the switch takes effect without a restart. The variable `NEXUS_GUARD_GIT_BYPASS=0` or `1` overrides it. Both are read only from the hook process's environment and files, never parsed from the command text.
    - **Blocked when on:**
        - `--no-verify` on commit, push, merge, rebase, and am, including git's unique abbreviations such as `--no-verif`;
        - `-n` as a `git commit` option, including combined short flags, with the cluster scan stopping at an option that takes an argument;
        - `--no-gpg-sign` on commit, merge, rebase, cherry-pick, and revert;
        - inline `-c commit.gpgsign=<false-like>` and persistent `git config [--global] commit.gpgsign|tag.gpgsign <false-like>`, matching config keys in any letter case;
        - all of the above when git global options come before the subcommand (`git -C repo commit -n`).
    - **Before matching:** quoted `-m`/`--message`/`-F` values and heredoc bodies that write a file are stripped. A heredoc body fed to an interpreter (`bash`, `sh`, `pwsh`, `python`) is scanned.
    - **Not blocked:** `git push -n` (dry run), `git log -n`, and `git commit --no-edit`.
    - **Limits** listed in the decision record and in the hook header: environment-variable skips (`HUSKY=0`, `SKIP=`, `LEFTHOOK=0`, `GIT_CONFIG_*`), git plumbing (`commit-tree`, `update-ref`), shell aliases and scripts, `bypassPermissions` mode, and an agent that edits `guardrails.json` itself.
6. `catalog/hooks/settings.json` registers `git-guardrails` for the PowerShell tool as well as Bash, and `catalog/hooks/tests/test_git_guardrails.py` proves the same exit code from both implementations for every blocked, allowed, and switch case, including a PowerShell-tool payload.

**Nice to have (cut in this order):**

1. Case-insensitive matching of the existing `core.hooksPath` and `core.fsmonitor` patterns, a pre-existing gap the review found. If cut, record it as a known gap with the evidence.

## Overview

The comparison's decision-toolkit source showed the value of a separate "ungated" result: a gate that measured nothing must never look like a pass. The anti-slop source argued that a recurring mistake belongs in a check rather than an instruction, and the agent-catalog source showed a hook that blocks hook-skipping flags. The plan review then found that the draft hook design claimed more than a regular-expression hook can deliver. The maintainer chose an opt-in guard with honest limits, a live switch, and registration for the PowerShell tool.

Phase 1 adds the UNGATED outcome and the explain-retry-or-record flow. Phase 2 makes gate records recomputable. Phase 3 refines trapdoor promotion. Phase 4 records the guard decision, then implements the opt-in mode in both hook languages and registers the hook for the PowerShell tool. Phase 5 is the mandatory fail-closed final phase.
