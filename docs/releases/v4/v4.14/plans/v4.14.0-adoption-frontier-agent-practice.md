**Goal**: Close eight of the eleven adoption candidates the frontier-agent-practice comparison scores, so the catalog gains a verification-instrument doctrine with a project-local control CLI and Feature Map, a compression adversarial-recall probe, a deterministic plan-structure validator, agent-facing CLI ergonomics, a disposability and scrap doctrine, a restate-before-acting threshold, a Diataxis one-mode-per-document rule, README-driven design, and one durable motivation-archaeology rule, with zero new outbound calls, dependencies, or credentials.

## Overview

The seeding comparison read three sources against Nexus-Hub and found that most of what they teach is already shipped. Eleven candidates survived scoring. This plan builds eight of them, cuts two, and reduces one to a single rule.

The most valuable item is the verification-instrument doctrine, and this plan builds it second rather than fifth. Nexus-Hub already tells an agent how to exercise an artifact through `functional-verification`, but nothing tells an agent to build and maintain the instrument that does the exercising. The source's answer is a project-local control CLI plus a persisted feature catalogue, both re-synced on a stated cadence. Nexus-Hub ships the meta-skill; the consuming project gets the generated artifact, derived from the project in front of it rather than from a command list fixed in advance. No shared runtime, no new dependency.

Everything here is catalog content and repo-internal tooling. Five items are prose added to existing skills, one is a new skill with bundled resources and registry registration, and two are local code: an eval fixture and probe for the existing compression engine, and a deterministic plan-structure validator.

Two risks are live and are handled by named gates rather than by care. The new skill can become a framework specification instead of a doctrine, so its cut-line is pre-committed in this plan rather than delegated to the implementer who wants to build it. And the plan-structure validator gates the pre-commit profile, so its corpus is bounded here rather than discovered during implementation: 3 of the repository's 106 plan files carry `## Queued predecessors` and 49 carry `## Current model map`, so a repo-wide section check would fail the build on day one.

## Goals First / Definition of Done

**Target problem**: The catalog teaches an agent to verify, plan, and write well, but it does not teach the agent to build its own instruments, to throw away output that missed, or to keep one document to one purpose.

**Persona**: the maintainer of a project that consumes Nexus-Hub, whose agent re-derives an ad-hoc verification script every session because nothing told it to build a durable one.

**Definition of done**, observable:

1. A new skill under `catalog/skills/testing/` teaches control-CLI and feature-catalogue generation, is registered everywhere `check_registry_entries.py --strict` requires, and declares rule ownership against `functional-verification`.
2. **Outcome, not artifact**: given a consuming project and a verification task phrased the way a user would phrase it, the agent loads that skill unprompted. Measured by the routing gate in Phase 2, with a stated pass bar.
3. `extensions/nexus-context-compressor/tests/test_adversarial_recall.py` fails when an ordinary mid-distribution record does not survive compression, and was observed failing before being accepted.
4. `scripts/check_plan_structure.py` exists, is registered in a group reached by both the fast and full profiles, rejects a malformed task line anywhere in the repository, and applies section checks only to plans at or after v4.14.
5. `tool-design`, `technical-writer`, `spec-driven-development`, `idea-refine`, and the surface chosen in T002 each carry their new content, with no rule stated twice.
6. One durable motivation-archaeology rule exists: an agent states the history depth it actually had and names the sources it could not consult.
7. `python scripts/ci/run.py --profile full` is green.
8. Net catalog delta is `+1 skill`, verified by diffing the skill NAME list against the T001 baseline, not by comparing counts.

**Not done** if any recommended item silently becomes a known gap without the cut being stated here or recorded through `known-gaps-tracker` with an owner and a next step. **Not done** if item 2 fails: a skill that never triggers is indistinguishable from a skill that was never written.

## Grounding and sequencing

`docs/solutions/` does not exist, so solved-problem grounding found nothing to reuse and is recorded as not applicable rather than skipped. `STRATEGY.md` does not exist either. These items are therefore **adoption-driven rather than demand-driven**: each is in this plan because a source taught it and the comparison scored it, not because a user reported the gap. That is stated plainly so the reader can weigh it. Authoring a strategy anchor through `product-strategy` before the next adoption cycle would let scope be checked against something.

**Sequencing departs deliberately from the comparison's Step 5.4 bucket ordering.** That ordering puts all `skill-native` items before all `re-full` items, which would place the plan's most valuable item third and its only P0 fifth. This plan front-loads value instead: the verification-instrument doctrine is Phase 2 and the adversarial-recall probe is Phase 3, so a plan cut short still ships what mattered. The departure and its reason are recorded here rather than left for a reviewer to discover. The one real dependency is preserved: A1 consumes the CLI ergonomics section, so A4 stays in Phase 1.

Each non-final phase ends with automated verification, a scoped session history under `docs/releases/v4/v4.14/development/history/v4.14.0-phase-N.md`, tracker updates, and exactly one local commit. The `v4.14.0-` prefix is required: the sibling plan v4.14.1 writes into the same directory. Do not push, open a pull request, or start remote CI before Phase 6. CI impact is recorded each phase; pipeline edits belong to Phase 6 alone.

**This plan writes `docs/releases/v4/v4.14/development/last-phase-evidence-v4.14.0.md`**, not the unsuffixed file. The sibling plan owns `-v4.14.1.md`. Both plans also write `docs/releases/v4/v4.14/known-gaps.md`; this plan records the A10/A11 carried gaps there and the sibling plan must preserve them.

`python scripts/ci/run.py --profile fast` and `--profile full` are the canonical gates, on every host. Inspect each with `--list` at execution time. Do not invoke `make` targets: `make` is absent on a stock Windows workstation, which is the declared development host, and the v4.8.0 record in `docs/archives/v4/v4.8/development/last-phase-evidence.md` documents a composite claim that was never true at one revision because a target's steps were run individually. Where this plan names a check, run it through the profile runner or directly by script path.

Note that the CATALOG and TESTS groups run in `full` only, not `fast`. A registration or trigger defect will therefore not surface under a `fast` gate; the tasks that can produce one run their specific check directly.

Every step must produce a written artifact with measured output. A step that asserts a check occurred without quoting its result is not acceptable evidence.

Any skill file this plan edits must still satisfy the 800-line hard cap enforced by `scripts/validate_skills.py --bundles-only`. Where an addition would push a body past 500 lines, add a `references/` file and link to it rather than growing the body.

**Bounded reopen rule**: several tasks below reopen an earlier task when an observable check fails. Each such loop is capped at **three** attempts, matching the existing judgment-iteration cap in `lint-repair-loop`. On exhaustion, record a known gap with an owner and a next step and continue; blocking a phase indefinitely on a stochastic behavioral check is not an outcome.

**Stability Gate**: `docs/releases/v4/v4.14/development/last-phase-evidence-v4.14.0.md` exists with one quoted section per duty below, including `## Tier 3 deep pass`. A missing Goal, a Goal-review miss without a recorded known-gap, or a missing evidence section blocks `/update release`.

**Recommended effort level**: max

#### 6.5 - Terminal CI/CD reconciliation

- [ ] T028 Reconcile the pipeline against the canonical contract `.github/workflows/ci.yml`

**Objective**: The repository's pipeline is compared field by field against the canonical contract, and every difference is either applied with approval or recorded as a known gap.

**Prompt**:
> Invoke [[cicd-architect]] in existing-pipeline comparison mode and run its six steps in order: DETECT the active CI provider (recording "none detected" rather than assuming one); COMPARE the existing pipeline against every field of the canonical contract - repository-native profiles, event separation, runner selection, the always-resolving aggregate required check, permissions, immutable action or plugin references, caching, concurrency, path scoping, artifact retention, structured reports, deployment boundaries, and failure recovery; PROPOSE each difference with its cost, its risk, and the smallest change that closes it; obtain explicit APPROVAL per change (silence is not approval); APPLY the approved changes and re-run the local gate; and RECORD every declined or environment-only difference as a known gap with an owner and a next step via [[known-gaps-tracker]]. The comparison concludes PASS only when every required field has observable evidence; a green pipeline run is not evidence, because a pipeline that checks nothing is green for the wrong reason. If this repository ships more than one installer, run or add a declarative cross-installer parity gate covering distributed artifacts, supported platforms, named capability counterparts, and external-tool fallbacks, then execute the real installers on their target operating systems with identical postconditions. Cross-link [[platform-contract-verification]] so discovery and delivery are checked in the same pass. If the repository ships zero or one installer, record a silent no-op and continue. Quote the per-field comparison result under `## CI/CD coverage`.
> Phase 3 added a gate step to a shared group. Confirm it is reached by the aggregate required check, that the required check is still produced by a workflow that triggers unconditionally per the `Required Status Checks` rule in `AGENTS.md`, and that the aggregate context is not a per-matrix-leg context.
