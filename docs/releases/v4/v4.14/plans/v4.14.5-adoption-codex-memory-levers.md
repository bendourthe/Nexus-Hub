## Definition of Done

**Must have:**

1. `docs/policy/memory-substrate-contract.md` defines a **host-generated store** beside the existing harness-native index:
    - **Class test:** the host fills it outside the agent's turn (background extraction or consolidation) and the vendor documents it as generated state not to be edited. A file the agent writes during its turn with ordinary file tools is an index. Claude Code's `MEMORY.md` is named as an index and Codex Memories (`~/.codex/memories/`) as a host-generated store, so the two examples sit on opposite sides of the line.
    - **Never read:** the agent never opens, globs, or reads a host-generated store's files; it reacts only to content the host itself injects into the session. The "Session-start read order" section says so.
    - **Untrusted:** injected content is untrusted, model-summarized data. It ranks below user instructions, project instruction files, and the substrate, and never on its own authorizes a destructive, outbound, credential, or approval-changing action; instruction-like content is surfaced to the user, per `prompt-injection-defense`.
    - **Conflict:** when it disagrees with the substrate, the agent acts on the substrate, tells the user once per session what disagreed, and points to the vendor's own reset or disable control; it never edits the host store.
    - **No laundering:** host-generated content is recorded into the substrate only after the user confirms, with a `source` naming the host store (for example `host:codex-memories`).
    - Line 3's "never a competing store" is scoped to harness-native indexes. `catalog/skills/workflow/agent-memory/SKILL.md` line 44 gains one pointer sentence.
2. `catalog/skills/security/prompt-injection-defense/SKILL.md` names a host memory store as a persistence channel for untrusted tool or web output and for credentials (vendor redaction is best-effort). It recommends Codex's `memories.disable_on_external_context` and states its limit: it excludes only threads that used MCP tools, web search, or tool search, not shell fetches, files from a cloned repository, or subagent output.
3. `docs/policy/platform-defaults-levers.md` records, in the `### codex - VERIFIED` detail section, a "Memories levers" paragraph: `features.memories`, `memories.extract_model`, `memories.consolidation_model`, `memories.disable_on_external_context`, and `memories.min_rate_limit_remaining_percent`, each with the vendor URL, the date checked, its documented default, and "not seeded" with the reason. The verification log gains one row with its scope limit.
4. `configs/platform-defaults.json` names all five keys under the Codex `omitted` map, each with a one-sentence reason, and its `meta` gains an `omitted` statement: a key named there is never declared under `settings`; seeding it later means removing it from `omitted` in the same edit, with a decision record.
5. `tests/validators/test_sync_platform_defaults.py` fails when a platform's declared `settings` include a key its own `omitted` map names.
    - **Function:** a pure function over the loaded platforms object, called by a file test and by in-memory red cases.
    - **Match rule:** a declared path matches an omitted key when it equals the key or starts with the key followed by `.`; table-node paths count, so an empty `{"memories": {}}` table matches an omitted `memories.*` key.
    - **Paths:** computed with the seeder's own `_leaf_paths`, imported, plus table nodes; the file is loaded the way the seeder loads it (`load_source`).
    - **Red cases:** one per omitted key in the real file, each asserting the guard reports exactly that `platform: key`.
    - **Boundary:** the guard covers declared `settings` only. Keys an integration writes in code (for example `scripts/lib/integrations/_codex_native.py` agent TOML), profile-scoped keys, and environment variables are outside it, and the decision record says so.
6. Two decision records in `docs/decisions/implemented/`: `tooling/2026-10-15-omitted-defaults-are-never-seeded.md` (the guard, its boundary, and the documented deletion limit) and `policy/2026-10-15-codex-memory-external-context-not-seeded.md` (record, do not seed), each with `## Consequences` and `## Alternatives considered`.

**Nice to have:** none. The `/usage` memory-pass note the first draft listed was rejected by the comparison and belongs to `v4.16.3`.

## Non-Goals

- Seeding any Codex memory key, including any model id, `features.memories`, or `memories.disable_on_external_context`.
- A `nexus-hub doctor` warning when Codex Memories is on without the external-context exclusion. Parked as a follow-on (see `## Follow-on`).
- Guidance for Codex users who want better memory. OpenAI's Memories page is the guide; the contract's Codex instance links it, and the levers paragraph records the facts without model ids.
- Reading, cleaning, or editing `~/.codex/memories/`.
- Changing any other platform's seeded values. DoD 5 adds a guard over existing data; it changes no setting.

## Overview

The comparison's source recommended pinning larger models for Codex background memory. OpenAI's documentation confirms the keys but shows the recipe is a no-op as written (Memories is off by default) and that the ids depend on the user's plan. Nexus-Hub adopts the evidence, not the recipe.

Phase 1 fixes the memory contract first, because it carries the security content and depends on nothing in flight: a host-generated store is defined by how it is written, never read, never trusted on its own authority, and never laundered into the substrate. Phase 2 records the Codex levers, makes the `omitted` convention enforceable on every platform, and files the two decision records; it waits for v4.14.0, which edits the same files.

The work adds no dependency, outbound call, credential, or installer copy step, and changes nothing a user's machine receives.
