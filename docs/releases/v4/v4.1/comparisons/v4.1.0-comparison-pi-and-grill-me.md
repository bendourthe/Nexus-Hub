# Comparison: Pi Agent Harness and the grill-me Skill Family

**Adoption target**: v4.1.0
**Date**: 2026-08-25
**Sources compared**:

1. `https://github.com/earendil-works/pi` (Pi Agent Harness, MIT, TypeScript, 97,210 stars, 12,015 forks, last push 2026-08-25)
2. `https://github.com/mattpocock/skills` (Skills for Real Engineers, MIT, 236,623 stars, last push 2026-08-24), specifically `skills/productivity/grill-me`, `skills/productivity/grilling`, and `skills/engineering/grill-with-docs`

**Baseline**: Nexus-Hub v3.21.0 released, v4.0.0 in flight on `feat/v4.0.0-cost-effective-ci-cd`.

## Executive Summary

Two requests, two very different outcomes.

Pi is an agent runtime, not a skill catalog. It is a peer of Claude Code rather than a peer of Nexus-Hub, so most of it is structurally unadoptable. The valuable discovery is narrower and better than a feature list: Pi implements the same `agentskills.io` specification Nexus-Hub already validates against, and it documents stable global and project skill directories plus a Markdown slash-command format. That makes Pi a low-cost new distribution target for a catalog that already emits conformant files, reaching a harness with 97k stars for roughly the cost of a copy-target and a prompt emitter.

The grill-me request is the opposite shape. The capability already exists in Nexus-Hub as `design-interview`, whose description already lists `"grill me"` as a trigger phrase, and `idea-refine` already carries an opt-in interactive grill mode. Shipping a new `grill-me` skill would create a fourth overlapping owner of one concern, which the repository's own rule-ownership convention forbids. What is genuinely missing is not a skill. It is an algorithm upgrade inside the existing engine, plus the wiring that makes it fire automatically after a plan's first draft.

The single highest-value item in this report is that wiring, because it closes a real gap: `implementation-plan` references `design-interview` only in its Related Skills list, so today no plan is ever interrogated unless the user thinks to ask.

## Part 1: Pi Agent Harness

### What Pi Is

Pi is a TypeScript monorepo providing an agent runtime: a unified multi-provider LLM API, an agent loop with tool calling and state management, a terminal UI library with differential rendering, vendor-neutral telemetry contracts, and an interactive coding-agent CLI. It ships packages for `agent`, `ai`, `client`, `coding-agent`, `evals`, `protocol`, `server`, `session-backends`, `telemetry`, and `tui`.

### Category Check (why most of Pi is not adoptable)

Nexus-Hub is a catalog distributed by an installer into other people's agent harnesses. Pi is one of those harnesses. Adopting Pi's agent loop, TUI renderer, or provider abstraction would mean Nexus-Hub becoming a runtime, which is a different product. Those components are recorded here as deliberately not adopted, not as gaps.

### Assessments for Pi Candidates

**A1: Pi as a supported distribution platform.**

*Security*: The change copies Markdown files into user-owned directories. It adds no dependency, no credential, no MCP server, and no outbound call. Pi's own documentation warns that skills can instruct a model to take actions, which is a property of every platform Nexus-Hub already targets and is unchanged by this work. Global installs must remain detection-gated so a user without Pi receives nothing, matching the Qwen and Kimi precedent.

*Reverse-engineering*: Decision-tree tier 1, local-only. Nothing is wrapped and no vendor service is involved. The contract is read from fetched official vendor documents (`packages/coding-agent/docs/skills.md` and `packages/coding-agent/docs/prompt-templates.md`), which satisfies the do-not-invent rule. Both paths and both formats must be recorded in `docs/policy/platform-read-contracts.json` with a `source_url` and a `verified` date before any installer edit lands.

**A3: Supply-chain install hardening.**

*Security*: This is purely a hardening change and is the highest-severity item in the report by consequence, since Nexus-Hub's installer executes on user machines.

*Reverse-engineering*: Tier 1. These are configuration and CI practices, not a service. Nothing to wrap.

**A4: Multi-session git discipline.**

*Security*: Guardrail strengthening only, acting in the safe direction by blocking more.

*Reverse-engineering*: Tier 1, local hook logic.

### Field note: a guardrail precision bug found while writing this report

Writing this report tripped the `git-guardrails` hook. The hook matched the name of a history-rewriting command appearing as **prose inside a documentation file**, in the table row describing Pi's forbidden-command list, and blocked the write. The pattern match does not distinguish a command being executed from a string being written into a file.

This is worth folding into A4, because the same imprecision cuts the other way: a guard that fires on quoted prose trains its user to work around it, and a worked-around guard protects nothing. The fix is to match the command position rather than any occurrence in the command text, so a heredoc payload or a quoted argument does not read as an invocation.

## Part 2: The grill-me Skill Family

### What Upstream Actually Ships

The finding that matters is that `grill-me` is a delegator, not an implementation. Its entire body is one line instructing the agent to call a `grilling` skill, under a two-field frontmatter with `disable-model-invocation: true`. `grill-with-docs` is the same pattern, delegating to `grilling` plus `domain-modeling`.

All the substance lives in `grilling`, and its algorithm is specific enough to be worth naming precisely:

- Model the work as a **design tree** in which every decision branches into the decisions hanging off it.
- Work in **rounds**. The **frontier** is every decision whose prerequisites are already settled, meaning every question answerable now without guessing at an answer not yet heard.
- Ask the **whole frontier in one round**, numbering each question and attaching a **recommended answer** to each, then wait.
- A question depending on another question still open in the current round belongs to a later round.
- **Finding facts is the agent's job, never the user's.** When a frontier question needs an environment fact, dispatch a sub-agent. Do not block: only questions downstream of that exploration wait, and the rest of the frontier is asked immediately.
- The session ends when the frontier is empty. Do not act until the user confirms shared understanding.

### Gap Analysis Against Nexus-Hub

Nexus-Hub's coverage of this territory is already substantial and somewhat fragmented.

| Concern | Current Nexus-Hub owner | Status |
|---|---|---|
| Interview engine, triggers on "grill me" | `design-interview` | Present. Strictly one question at a time, no hard cap |
| Opt-in interactive grill mode on an idea | `idea-refine` | Present, explicitly gated as non-default |
| Non-interactive adversarial critique of a finished plan | `plan-review`, with seven persona lenses | Present and strong |
| Async interrogation of an absent stakeholder | `decision-questionnaire` | Present |
| Structured gap detection on a written spec | `ambiguity-detector` | Present |
| Domain glossary as a durable interview output | `design-interview` via `CONTEXT.md` | Present, and richer than upstream |

Against that, the true deltas are narrow:

| Delta | Detail | Verdict |
|---|---|---|
| Frontier-round questioning | Nexus-Hub asks exactly one question per turn. Upstream asks the entire settled frontier per round. On a plan with twelve independent open decisions, the current engine costs twelve turns where one round would do, which is also why the repository's global batch-not-ping-pong rule exists | **ADOPT (A2)** |
| Recommended answer per question | Upstream attaches a recommendation to every question so the user reacts rather than composes. Nexus-Hub does not mandate this | **ADOPT (A2)** |
| Sub-agent fact-finding, non-blocking | Upstream forbids asking the user anything the agent could look up, dispatches a sub-agent, and blocks only the downstream branch. Nexus-Hub's engine does not state this | **ADOPT (A2)** |

| A new standalone `grill-me` skill | Would become a fourth owner of one concern | **DROP** |

### Assessment for the grill Candidates

*Security*: No security surface. These are instruction-text changes to an interview algorithm. No outbound call, dependency, credential, or executable is introduced. The sub-agent fact-finding rule uses the harness's existing agent facility.

*Reverse-engineering*: Decision-tree **tier 2, LLM-native skill**. The capability is achieved by instructing the model, so per the policy it ships as skill content and never as an MCP. Attribution stays in this report's rationale rather than in the distributed artifact, per the reverse-engineering attribution rule, and the upstream project is not named in the shipped skill body.

*Boundaries check*: The scope-fit gate asks for a shipped behavior or an active call site before new structure is added. A2 adds no new file and changes an existing engine's algorithm. A5 adds one call site inside an existing step. A new `grill-me` skill would fail this gate, which is why it is dropped.

### The Design Tension in the Request, Stated Plainly

The request asks that grill-me run automatically after a plan's first draft to make the plan more robust. There is a real conflict inside that sentence, and resolving it improves the result.

Grilling is **interactive**. It interrogates the user and waits, and it cannot proceed without answers. Automatically starting an interrogation is legitimate, but it is not the same thing as automatically improving the plan, and on its own it would stall a plan the moment the user stepped away.

Critiquing is **autonomous**. `plan-review` already reads a finished plan through seven independent lenses and returns severity-tagged findings without asking anything.

Neither alone does what the request wants. Composed, they do, and the composition is better than either source:

1. Draft the plan.
2. Run `plan-review` autonomously. It finds contradictions, infeasible sequences, missing cut-lines, and unstated assumptions with no user input.
3. **Seed the grill frontier from those findings.** Every unresolved decision the lenses surfaced becomes a round-one question, each carrying a recommended answer.
4. Ask the whole frontier in one round. Recompute and repeat until the frontier empties.
5. Fold the resolved decisions back into the plan before Step 5 asks for approval.

This yields a grill whose questions are evidence-backed rather than speculative, which is exactly the property upstream is reaching for when it insists the agent find facts itself. It is a Nexus-Hub-native synthesis of two capabilities the repository already owns, not a port.
