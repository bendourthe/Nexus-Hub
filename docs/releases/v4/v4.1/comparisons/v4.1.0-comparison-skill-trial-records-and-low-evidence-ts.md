## Source A: 8,135 trial records (insight extraction)

The PDF is a 4-page industry write-up, not the academic paper itself. It does not name the authors or a DOI. Claims below are cited to PDF pages and treated as the article's findings, not independently re-run.

### What the article claims

Skills help, but not for the reason most catalogs are written. Distilling noisy past runs into a standardized skill beats injecting those same logs as "workflow memory" by **6.06 percentage points**. Procedural anchoring (a runbook that keeps the agent on the execution path) accounts for **65.7%** of successful skill cases; explicit knowledge injection accounts for **4.5%**. Environment and tooling failures drop from **5.3%** (raw) to **0.2%** (distilled skill). Distilling a mixed batch of successful and failed trajectories without labeling which is which collapses later success from **74.6%** to **40.0%** on the Gemini agent ("no-hint" ablation). As a retrieved pool grows from 5 to 100 skills, actual-use precision falls from **29.6%** to **3.3%**, yet downstream task success stays roughly **36-39%** because related non-ground-truth skills still supply partial procedure. Exact ground-truth invocation is "neither sufficient nor necessary." The failure mode that does hurt is **semantic confusability** (skills that look identical to a retriever). The recommended architecture is two-level: domain bucket first, then a strict trigger (for example an exact error string). The closing line: skill use is a **lifecycle**, not a single memory-injection.

### Generic rules the source enforces (all `error` in the README)

- `no-chained-type-assertions` -- nested `as` that fabricates evidence (`input as object as User`)
- `no-conditional-empty-object-spread` -- `...(cond ? { k: v } : {})`
- `no-known-value-widening` -- explicit `Record<string, T>` (and similar) that discards known keys; prefers `satisfies`
- `no-module-mocking` -- Vitest/Jest `vi.mock` / `jest.mock` in favor of real seams
- `no-object-parameters` -- `value: object` on inputs
- `no-reflect-apply` / `no-reflect-get` -- untyped Reflect instead of typed calls / access
- `no-runtime-typeof` -- ad hoc `typeof` narrowing; optional `allowInTypeGuards`
- `no-shape-in-symbol-names` -- `shape` in type/interface/variable names
- `no-unknown-parameters` / `no-unknown-returns` / `no-unknown-type-aliases` -- `unknown` as a function or alias contract except an explicit `cause` convention
- `no-unsafe-dictionary-type` -- `Record<string, unknown | any | object | {}>` and equivalents
- `no-widen-then-assert` -- widen a known value then assert it back
- `require-safety-comment-for-type-assertion` -- every non-`as const` assertion needs an adjacent `SAFETY:` comment naming the checked invariant

Opt-in Effect rule `no-service-constructor-imports` is framework-specific and out of Nexus-Hub's default catalog.

### Current-only strengths to preserve

- Multi-platform installer, MCP Registry Policy, hook parity, and the three-tier loading model. None of the adoptions below may add an Oxlint runtime dependency to Nexus-Hub itself or route TypeScript users through `skills.sh`.
- `anti-slop-editing` stays the prose-slop skill. Do not rename or overload it.
- `typescript-expert`'s "validate at the boundary with Zod / `safeParse`" is already the healthy form of what the lint plugin wants (parse unknown at I/O, do not launder it through `as`). Keep that; tighten the contract-level `unknown` advice.

## Step 7: Risks, conflicts, and NOT recommended

Risks and conflicts on recommended items:

- **A1 vs language-specialists.** Ten `*-expert` skills are currently knowledge walkthroughs (`catalog/skills/language-specialists/`). The rule must not demand a rewrite of all ten in v4.1.0. Apply the runbook bar to **new and edited** expert skills, and have `skill-stocktake` 4b flag existing ones as a backlog rather than a gate. Otherwise this comparison becomes an unbounded rewrite.
- **A3 vs combat-undertriggering.** Pushy descriptions increase lexical overlap. The paper's confusability finding does **not** license a return to terse descriptions (already rejected in `docs/v3/v3.2/comparisons/v3.2.0-comparison-loop-engineering.md` item A12). The fix is stronger SKIP fences and category ownership, not quieter descriptions.
- **B1 vs `typescript-expert`.** Direct rule clash on `unknown`. Without the ownership table, a multi-skill review will report both "use unknown" and "do not use unknown" as findings. Tie-break: B1 decides when `unknown` is a violation (function contracts, aliases, dictionaries); `typescript-expert` keeps boundary parsing and Zod.
- **B1 vs `anti-slop-editing`.** Different domains (types vs prose) but the same vernacular. B1's description SKIP must name `anti-slop-editing` explicitly ("SKIP: prose/voice slop").
- **B3 maintenance.** Oxlint's JS plugin API (`@oxlint/plugins`, `eslintCompatPlugin`) will move. Vendoring means Nexus-Hub owns a TypeScript plugin it does not run in CI. That is why B3 is P2 and optional; B1 does not depend on it.
- **Source A provenance.** The PDF is a secondary summary without a paper title. Do not hard-code the percentage figures into AGENTS.md as if they were Nexus-Hub measurements. Cite them as external study claims in the skill/rationalization text, or drop the numbers and keep the operational rule.
