## Executive decision

Do not install Ponytail as a plugin, npm package, MCP server, or always-on hook into Nexus-Hub, and do not copy its brand, persona, or per-host adapter tree. Nexus-Hub already owns post-write simplification (`code-simplification`), dead-code removal (`dead-code-eliminator`), quality and smell review (`code-quality`, `code-smell-detector`), plan-scope control (`plan-review`, AGENTS.md scope-fit), completion evidence (`verification-before-completion`), and skill evaluation (`skill-eval-loop`).

The useful gap is timing and trigger, not a missing cleanup product. Ponytail's ladder runs **before** the agent writes code and is injected every session, so it catches over-building that Nexus-Hub's post-write skills never see. Nexus-Hub should reverse-engineer that pre-write discipline as generic catalog content: a compact always-on instruction-template section, a dedicated skill with a rule-ownership table, and a delete-list review skill. Measurement stays on `skill-eval-loop`. Safety floors stay with their current owners.

Recommended v4.1.2 adoption:

1. Add a compact construction-discipline section to the distributed instruction templates, parity-gated like `Consequential Decisions`.
2. Add a `minimal-construction` skill that owns the pre-write ladder, intensity levels, and skipped-work output, and that defers safety, tests, and communication to existing owners.
3. Add an `over-engineering-review` skill that produces a tagged delete-list for a diff or a repo, complementary to `code-quality` and `code-simplification`.
4. Add an in-code deferred-simplification marker convention and a harvest path, without replacing `known-gaps-tracker` or `technical-debt-analyzer`.
5. Prove the new skill with `skill-eval-loop` assertions for native/stdlib reuse and for refusing to drop validation, security, or accessibility.

## Gap analysis

### G1. Construction discipline fires after the damage, or not at all

`catalog/skills/code-cleanup/code-simplification/SKILL.md` tells the agent to collapse existing over-abstraction without changing behavior. `catalog/skills/developer-experience/dead-code-eliminator/SKILL.md` finds unused code after it exists. AGENTS.md "Boundaries" stops Nexus-Hub contributors from adding unused modules to this repo. None of those is a distributed, pre-write ladder that says: skip it, reuse it, use the stdlib, use the native control, use an already-installed dependency, then write one line.

Ponytail's `skills/ponytail/SKILL.md` makes that ladder a reflex on every coding task, with explicit rungs and worked lite/full/ultra examples (cache class vs `@lru_cache`). That is the capability Nexus-Hub under-triggers today: `code-simplification` descriptions talk about code that has already grown complex, so agents writing a new date picker never load it.

### G2. Always-on presence vs trigger-loaded skills

Ponytail solves under-triggering by injecting the ruleset on SessionStart and SubagentStart (`hooks/claude-codex-hooks.json`, `hooks/ponytail-subagent.js`). Nexus-Hub's `catalog/hooks/session-start.sh` injects catalog navigation, not how to write code. Skills load on description match.

For a 326-skill catalog, copying Ponytail's full-body injection would tax every session. The Nexus-Hub-shaped equivalent is the same pattern as `Consequential Decisions`: a short invariant section in `templates/ai-instructions/`, byte-locked by `scripts/check_base_template_parity.py`, plus a full skill that loads when the user asks for intensity, a review, or an audit.

### G3. Over-engineering review is buried inside general quality review

Ponytail-review is exclusively a delete-list: `L12-38: stdlib: 27-line validator class. "@" in email, 1 line.` Nexus-Hub `code-quality` is Phase 2 of a six-phase review and scores SOLID, complexity, and smells. `code-smell-detector` uses Fowler's catalog. Neither produces a net-lines cut list, and both will happily recommend more abstraction. A dedicated owner for "what to delete because it should never have been built" keeps that report from being padded with SOLID findings.

### G4. Marked shortcuts have no harvest path

Ponytail requires a `ponytail: <ceiling>, <upgrade path>` comment on deliberate corners and harvests them with `skills/ponytail-debt/SKILL.md`. Nexus-Hub `known-gaps-tracker` records version-level deferrals in docs. `technical-debt-analyzer` scores SQALE debt. An in-code ceiling comment that names the trigger to revisit is a different artifact. Adopt the convention under a generic marker, not the upstream name.

### G5. Measurement already exists; the scoreboard does not belong

Ponytail's README and `skills/ponytail-gain/SKILL.md` advertise 80-94% less code from a single-shot promptfoo run, later corrected to a mean 54% LOC cut on an agentic FastAPI+React repo (`benchmarks/`). `skill-eval-loop` already does with-skill vs without-skill on the user's CLI, with cost and duration in `benchmark.json`. Do not ship a static marketing scoreboard. Do add eval assertions that fail if the agent installs a picker library instead of a native control, or if it drops a trust-boundary check.

### MCP Registry Policy decision tree

1. **Local-only**: Not applicable as an MCP. The behavior is instructions.
2. **LLM-native skill**: Stop here. A ladder, a review format, and a comment convention are achievable by instructing the agent. Nexus-Hub already distributes skills and instruction templates.
3. **Reverse-engineer into a local MCP**: Do not. An MCP that only returns a prompt duplicates the skill.
4. **Trusted vendor wrapper**: Not applicable.
5. **Otherwise / drop**: Plugin marketplace adapters, npm publish, statusline, settings mutation, hosted benchmark APIs, and the product brand.

**Decision**: `skill-native` for G1-G4, with existing local parity/eval scripts. No MCP entry. Cite the MCP Registry Policy for any item that would have added Node, an MCP SDK, or a third-party eval API.

## Ordered adoption plan

Skill-native first, then local scripts if needed. P-tier is within the skill-native bucket. `reverse-engineer-first=true` for any `/plan from-comparison`.

1. **PT1 (P0).** Draft a short construction-discipline section (ladder + safety handoff + "this governs what you build, not how you talk"). Land it in the lockstep five and the other substantive instruction templates. Add the heading to `INVARIANT_SECTIONS` in `scripts/check_base_template_parity.py`. Do not put it in Output Minimization.
2. **PT2 (P0).** Author `catalog/skills/code-cleanup/minimal-construction/SKILL.md` with the ownership table above, intensity levels, skipped-work line, and SKIP fences for prose, security audits, and post-write refactors. Register it in `data/SKILL_INDEX.md`, `data/skills.json`, and `data/marketplace.json`. Cross-link from `code-simplification` (post-write owner) without duplicating the ladder.
3. **PT3 (P1).** Author `catalog/skills/code-review/over-engineering-review/SKILL.md` with the five tags and the lean-already exit. Cross-link from `multi-agent-code-review` as an optional lens, not a replacement for `code-quality`.
4. **PT4 (P1).** Document a generic marker (`construction-debt:` or equivalent) and a harvest section, either in `minimal-construction` references or a thin companion skill. Do not name the upstream product in distributed files (Reverse-Engineering Attribution Rule).
5. **PT5 (P1).** Add `evals/trigger-cases.json` plus `skill-eval-loop` assertions that reward native/stdlib solutions and fail dropped trust-boundary checks. Use the user's CLI; do not import promptfoo or hosted judges.
6. Validate: `make validate`, `make lint`, trigger evals, template parity, recursive installer (skill folder auto-copies; no installer edit unless a new `scripts/*.py` appears).
7. Mandatory closing: architecture/known-gaps note, CI/CD no-change declaration (unless a new validator is added), integration PR on the plan's final phase.
