## Goals First

**Target problem**: Two independent gaps in the same seeding report.

1. Nexus-Hub generated plans and presented them with nothing in between. `plan-review` (seven persona lenses) and `design-interview` (a full interview engine that already triggered on "grill me") both existed and were never invoked from the planning path. A plan was challenged only when the user thought to ask, which in practice meant almost never, and the first real challenge arrived during implementation.
2. Pi reads the `agentskills.io` specification Nexus-Hub already conforms to, and received nothing.

**Persona**: the maintainer running `/plan` on a multi-phase effort, and the Pi user who installs the catalog.

**Definition of done** (observable):

- Running `/plan` on any planning scope produces a plan that has been critiqued by `plan-review` and grilled through `design-interview` before the phase breakdown is presented for approval.
- `/grill` resolves to the interview engine, and `/plan grill <path>` re-runs the gate on an existing plan.
- A user with `~/.pi` present receives flattened skills and one prompt template per command; a user without it receives nothing.
- The whole change set is validated on the CURRENT `develop` tree, not on the base it was authored against.

**Explicit non-goal**: shipping a standalone `grill-me` skill. Rejected in `docs/decisions/rejected/process/2026-08-25-standalone-grill-me-skill.md`.

## Overview

Seven phases. Phases 1 to 4 are complete and evidenced against the current base. Phase 5 lands the work on `develop`. Phases 6 and 7 are open, and Phase 7 carries what risk remains.

The work divides cleanly along the seeding report's priorities: A2 and A5 (the grill engine and the gate) are one unit, A1 (Pi) is self-contained, and A3 plus A4 (supply chain and guardrails) are independent.

## Phase 1: Interview Engine, Frontier Rounds

**Status**: COMPLETE. **Recommended model tier**: strong. **Recommended effort level**: medium.
**Rationale**: a self-contained algorithm rewrite inside one skill body, with an existing structure to preserve.

### Sub-tasks

1.1 **Replace one-question-at-a-time with dependency-ordered frontier rounds** (`load-bearing`). The frontier is every decision whose prerequisites are settled. A question whose answer depends on another open question in the same round belongs to a later round.

1.2 **Require a labelled recommended answer per question** (`load-bearing`). Converts a blank prompt into a proposal the user can accept or counter.

1.3 **Add non-blocking sub-agent fact-finding** (`load-bearing`). Facts are the agent's job; only the branch downstream of a pending lookup waits.

1.4 **Preserve the single-question mode for callers that need it** (`load-bearing`). Frontier logic unchanged, round size capped.

1.5 **Adapt the round format to ASCII.** Upstream uses emoji markers; this repository's English Markdown is ASCII-only.

1.6 **Update registries and eval cases.** `data/SKILL_INDEX.md`, `data/skills.json`, and `evals/trigger-cases.json` (added positives for "grill this plan" and "stress-test my thinking", plus a `plan-review` negative).

### Phase 1 Exit Checklist

- [x] `design-interview` body carries the frontier rule, the round format, the recommendation requirement, and the sub-agent rule
- [x] Rule-ownership table names this skill sole owner of interview mechanics
- [x] Rationalizations cover BOTH failure directions (drip-feeding one question, and dumping dependent questions)
- [x] Description under the 1024-character agentskills.io limit **without** being added to the grandfathered list (verified: 1001 characters)
- [x] Registries and eval cases updated; `run_trigger_evals.py --gate` passes
- [x] CI impact: none (no new command, dependency, or test path)

## Phase 2: Critique-and-Grill Gate and the `/grill` Entry Point

**Status**: COMPLETE. **Recommended model tier**: frontier. **Recommended effort level**: high.
**Rationale**: changes the behavior of a core command on every platform, and composes two skills whose contracts must not blur.

### Sub-tasks

2.1 **Add `implementation-plan` Step 4.5** (`load-bearing`). Stage 1 invokes `plan-review` autonomously; stage 2 invokes `design-interview` with those findings as the seeded first round. Both automatic.

2.2 **Fold results back before Step 5** (`load-bearing`). A declined finding is recorded as a parked branch or known gap, never dropped.

2.3 **State the unattended-stall cost in the skill body** (`load-bearing`). The user chose fully-automatic over the offered alternative; the cost is documented rather than hidden.

2.4 **Add missing-delegate honesty** (`load-bearing`). An unavailable delegate is reported as uncovered, never reconstructed from memory.

2.5 **Add `catalog/commands/grill.md` and the `/plan grill` scope** (`load-bearing`). Thin dispatcher; no logic duplicated from the engine.

2.6 **Cross-link `plan-review`** so the pairing is discoverable from both ends, preserving its read-only contract.

2.7 **Failure modes.** Malformed or absent input: a draft with no open decisions yields an empty first round and the gate completes. Unreachable dependency: either delegate missing is reported as uncovered. Conflicting operations: `plan-review` stays read-only, so only the planning step writes.

## Phase 5: Land on `develop`

**Status**: OPEN. **Recommended model tier**: standard. **Recommended effort level**: low.
**Rationale**: a branch-ref move plus one commit. It was scoped as the plan's riskiest phase until the divergence claim above was checked and disproved.

### Sub-tasks

5.1 **Capture the change set as a patch before touching any branch** (`load-bearing`). Kept even though the move is now trivial: this repository has a recorded incident of OneDrive aborting a git operation mid-flight and corrupting a tag, and a working tree carrying 31 uncommitted files is exactly what that incident destroys.

5.2 **Fast-forward local `develop` to the current HEAD content** (`load-bearing`). `develop` is a strict ancestor of HEAD with zero commits of its own, so moving the ref is a fast-forward rather than a rewrite. Verify ancestry with `git merge-base --is-ancestor` BEFORE moving, and verify the HEAD hash before and after.

5.3 **Commit the adoption onto `develop`** (`load-bearing`). Stage explicit paths only, per the Step 5b discipline this plan itself added. Do not stage anything that does not trace to this plan.

5.4 **Do not push as part of this phase.** Publication belongs to Phase 7, which is the plan's first remote validation. Pushing here would bill a pipeline run to validate work the plan still calls incomplete.

5.5 **Failure modes.** Malformed or absent input: if the ancestry check fails, stop rather than forcing the ref. Unreachable dependency: none, this phase is entirely local. Conflicting operations: the working tree already matches `origin/develop`, so the ref move changes no file.

### Phase 5 Exit Checklist
