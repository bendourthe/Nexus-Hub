**Goal**: Give every Nexus-Hub-backed agent a pre-write construction ladder (skip, reuse, stdlib, native, installed dependency, one line, then minimum) without vendoring Ponytail, adding an MCP, injecting a full ruleset through hooks, or weakening security, verification, or communication owners.

## Goals First

**Target problem**: Agents over-build (new libraries, wrappers, and speculative layers) because Nexus-Hub's simplification skills fire after the extra code exists, or never load. There is no distributed, always-on pre-write ladder that stops at the first sufficient rung.

**Primary persona**: A developer using a Nexus-Hub-installed coding agent who wants the smallest correct change, not a framework.

**Secondary persona**: A Nexus-Hub maintainer who must keep construction discipline from restating or weakening security-review, verification-before-completion, or agent-communication.

**Observable definition of done**:

- All 12 substantive instruction templates carry a short `Construction Discipline` section; include-only shims do not duplicate it; lockstep parity and a 12-template identity test fail if it drifts or disappears.
- `minimal-construction` is a registered skill that owns the pre-write ladder and intensity levels, with a rule-ownership table that names existing owners for safety, tests, talk, dead code, and post-write simplification.
- `over-engineering-review` is a registered skill that emits a tagged delete-list (or `Lean already. Ship.`) and does not apply fixes or flag required proving commands as bloat.
- Deferred corners use a generic `construction-debt:` marker with a harvest path; `known-gaps-tracker` and `technical-debt-analyzer` remain the owners of version ledgers and SQALE scoring.
- Eval cases reward native/stdlib reuse and fail dropped trust-boundary checks. No MCP, Node runtime, plugin adapter tree, statusline, or `settings.json` mutation is added.

## Non-Goals

- Install, vendor, or wrap DietrichGebert/ponytail as a plugin, npm package, or hook set.
- Add an instruction-serving MCP or any new MCP registry row.
- Copy per-host plugin adapters, SessionStart full-ruleset injection, flag files, statusline badges, or `settings.json` edits.
- Adopt "code first, three lines" or "YAGNI applies to tests".
- Ship a static marketing scoreboard or the upstream product name in distributed skills, templates, or commands.
- Add a new env var or config file for construction intensity. Intensity is a skill argument; the compact template is always on.
- Rewrite `code-simplification`, `dead-code-eliminator`, `code-quality`, or `verification-before-completion` into this skill.

## Overview

This plan implements PT1 through PT5 from the seeding comparison, in reverse-engineer-first order: skill-native instructions and skills only. The source repository is evidence, not a dependency. Attribution stays in the comparison and this plan. Distributed artifacts use generic names (`minimal-construction`, `over-engineering-review`, `construction-debt:`).

Phase 1 lands the always-on compact rule on the same surface as `Consequential Decisions`. Phase 2 adds the full pre-write skill. Phase 3 adds the delete-list review skill. Phase 4 adds the deferred-corner harvest and eval proof. Phase 5 is the fail-closed architecture, known-gaps, CI/CD, and publication phase.

Each non-final phase ends with local verification and one local commit. No non-final phase pushes or starts remote CI. The final phase reconciles the pipeline, publishes once with approval, and hands a green integration to `/update release`.
