**Goal**: Catalog authors write skills as procedural runbooks with outcome-labeled distillation and confusable-trigger fences, and agents writing TypeScript follow a named typed-boundary-hygiene skill instead of laundering types through `unknown`, without adding Oxlint to Nexus-Hub itself.

## Goals First

**Target problem**: Skills in a large catalog fail in two ways the seeding sources measured. Knowledge-shaped bodies do not keep an agent on the execution path, and TypeScript guidance that treats `unknown` as the safe `any` substitute lets low-evidence contracts land in user code.

**Primary persona**: A Nexus-Hub maintainer authoring or auditing SKILL.md files.

**Secondary persona**: An engineer whose coding agent uses the installed catalog while writing TypeScript or JavaScript.

**Observable definition of done**:

- `skill-create`, `skill-stocktake`, and a short `AGENTS.md` pointer state that a skill body is a runbook (steps, gates, artifacts), not a tutorial, and that mixed success/failure traces must be labeled before distillation.
- A new `typed-boundary-hygiene` skill owns function-contract `unknown` / `object` / unsafe dictionaries, chained assertions, widen-then-assert, and `SAFETY:` comments; `typescript-expert` hands those contracts off and no longer verifies "replace `any` with `unknown`".
- `skill-stocktake` reports confusable trigger clusters per category; `skill-description-authoring` teaches two-level triggers (category, then a strict observable) without dropping pushy descriptions.
- `skill-eval-loop` can run an optional third arm (raw-log injection vs distilled SKILL.md) without a new runner dependency.
- Oxlint is not a Nexus-Hub runtime or CI dependency. A vendored-plugin install skill exists only if Phase 5's decision is yes.

## Overview

This plan operationalizes the dual comparison against the 8,135-trial skill-mechanics write-up and the [dmmulroy/anti-slop](https://github.com/dmmulroy/anti-slop) Oxlint plugin. All P0 and P1 items are skill-native: authoring-rule edits, one new catalog skill, and a rule-ownership handoff. The one `re-full` item (vendoring an Oxlint plugin into a *user* TypeScript repository) is gated on an explicit decision ticket and is not in the default path.

Delivery is catalog-shaped. The existing installers already copy `catalog/skills/` recursively, so a new skill needs registry rows, not installer copy lines. `AGENTS.md` stays a short pointer so the word-budget ceiling does not regress. Language-specialist textbooks are not mass-rewritten in this version; `skill-stocktake` flags existing expository expert skills as a backlog.

Sequencing follows the comparison Step 5.4 reverse-engineer-first order: skill-native P0 (Phases 1-2), remaining skill-native P1/P2 (Phases 3-4), optional `re-full` (Phase 5), mandatory terminal refactor/known-gaps/CI (Phase 6). Dropped items (skills.sh, Effect plugin, Oxlint-in-Nexus-Hub, catalog shrink, LLM router, renaming `anti-slop-editing`) stay out of scope.

**Objective**: A language-specialist skill that an agent can follow while writing TS/JS, named generically so it does not collide with `anti-slop-editing`.

**Failure modes**: If the description omits a SKIP fence for prose slop and for `typescript-expert` type-system design, both skills over-trigger. If the body restates Oxlint visitor code instead of agent-checkable rewrites, it becomes another textbook. If the skill is named `anti-slop`, `anti-slop-editing` and this skill become confusable. **Build class**: load-bearing (this is the shipped capability, not a stub).

**Prompt**:
> In the Nexus-Hub repo, create `catalog/skills/language-specialists/typed-boundary-hygiene/SKILL.md` following AGENTS.md "Adding a New Skill" exactly (quoted `summary_l0` / `overview_l1`, pushy description with verbatim trigger phrases and a SKIP clause, When to Use, Instructions as a runbook, Common Rationalizations with concrete failure modes, binary Verification, Related Skills). Name MUST be `typed-boundary-hygiene` (directory matches). Do **not** call it anti-slop. Do **not** name dmmulroy, Oxlint, or the source repo in the skill body (Reverse-Engineering Attribution Rule); attribution stays in the seeding comparison and, if Phase 5 ships, a matrix row.
>
> Description triggers MUST include: low-evidence TypeScript, chained type assertion, `as unknown as`, `Record<string, unknown>`, unknown parameter, unknown return, SAFETY comment for assertion, vi.mock, conditional empty object spread. SKIP MUST name: prose/voice slop (`anti-slop-editing`), ESLint dead-code cleanup (`javascript-cleanup`), type-system design / generics / Zod schemas (`typescript-expert`), Effect service constructors.
>
> Instructions are a runbook the agent runs on the files it is editing, one pattern per step, each with a smell, a rejected snippet, and the preferred rewrite. Cover these generic patterns (re-authored, not copied from upstream source): chained type assertions; conditional empty object spread; known-value widening (prefer `satisfies` / `as const`); module mocking (`vi.mock` / `jest.mock`) in favor of real seams; `object` parameters; `Reflect.apply` / `Reflect.get`; ad hoc `typeof` narrowing (allow inside type predicates if you document that option); unknown on parameters / returns / type aliases except an explicit error-`cause` convention; unsafe dictionaries (`Record<string, unknown | any | object>`); widen-then-assert; require a `SAFETY:` comment naming the checked invariant on every non-`as const` assertion. Omit `shape` in symbol names as a catalog-wide rule (comparison drop); if mentioned at all, one sentence of taste, not a Verification item.
>
> Include a **rule-ownership table**: this skill owns function-contract `unknown`/`object`/unsafe dictionaries, chained assertions, widen-then-assert, and assertion comments. `typescript-expert` owns type-system design, generics, discriminated unions, and **boundary parsing** (Zod / `safeParse` of data that entered as unknown at I/O). `javascript-cleanup` owns ESLint/dead-code/ES6+ modernization. `anti-slop-editing` owns prose. Non-owning skills must not restate the owned rule.
>
> Ship `evals/trigger-cases.json` with at least four positive cases (chained `as`, `Record<string, unknown>`, `vi.mock`, assertion without SAFETY) and four negative cases (de-slop prose, write a generic, fix ESLint unused, Zod schema). Keep the SKILL.md body <= 500 lines; push long pattern tables to `references/patterns.md` if needed and link them from the body (orphan-bundle audit).
>
> Register +1 skill by hand-editing `data/SKILL_INDEX.md`, `data/skills.json`, and `data/marketplace.json` (language-specialists `skill_count` and `total_skills` if present). Do not run a full catalog rebuild. Do not add installer copy lines (skill tree is recursive). Acceptance: `make validate` passes; `python scripts/run_trigger_evals.py` (or the repo's equivalent) does not mis-route the new evals onto `anti-slop-editing` or `typescript-expert`.

## Phase 3: Distillation Labels, Confusability, Two-Level Triggers

**Goal**: Distillation refuses unlabeled mixed traces; stocktake reports confusable clusters; description authoring teaches two-level triggers without replacing pushy descriptions.
**Prerequisites**: Phase 2 (confusability audit must include the new skill's SKIP fences).
**Stability Gate**: `continuous-learning` and `skill-create` require success/failure labels; `skill-stocktake` emits a per-category confusable-cluster section; `skill-description-authoring` (and `references/agent-writing-theory.md` if needed) teach Level 1 category / Level 2 strict observable, plus "exact invocation is neither sufficient nor necessary".
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: One high reasoning signal (designing a bounded confusability check that does not become a 324-skill pairwise explosion).

### Sub-tasks

#### 3.1 - Outcome-annotated distillation (A2)

**Objective**: Mixed success/failure evidence cannot silently become a skill.

**Failure modes**: If labels are optional, authors skip them and the 74.6% vs 40.0% failure mode returns. If unlabeled traces hard-error with no way to proceed, a maintainer who has only git history (success-biased) cannot draft. If the skill invents success labels, it bakes hallucinations in.

**Prompt**:
> In the Nexus-Hub repo, update `catalog/skills/workflow/continuous-learning/SKILL.md` and `catalog/skills/workflow/skill-create/SKILL.md` so distillation is outcome-annotated. Each observation or git-derived example used as evidence MUST carry an explicit success or failure label before it may enter a minted instinct or a SKILL.md draft. If the set is mixed and unlabeled, warn hard, list the unlabeled items, and refuse to draft until the user labels them or drops the failures. Git history is success-biased: say so, and require at least one cited failure mode (from a revert, a follow-up fix, or a user-supplied counterexample) in Common Rationalizations rather than pretending git log is a balanced dataset. Do not hard-code study percentages in the skill body; the rationalization may say unlabeled mixed traces have been measured to collapse later success. Do not add an outbound LLM-as-judge service (MCP Registry Policy hard-no). In-session agent judgment plus user labels is the control. Acceptance: both skills contain the refuse-until-labeled rule; `make validate` passes.

Output a "Confusable clusters" section in `.nexus/skill-stocktake/report.md`: skill A, skill B, overlapping phrases, whether SKIP fences actually separate them, and a proposed description/SKIP repair. Propose repairs only; never delete a skill. Calibrate on `language-specialists` first before fanning out (scope-first token caution; dynamic workflows optional via [[agent-orchestration-primitives]] if the harness has them). Keep this advisory, not a `validate_skills.py` hard error. Acceptance: a Full Stocktake dry-run on `catalog/skills/language-specialists/` names at least the `typed-boundary-hygiene` vs `typescript-expert` split and reports whether their SKIP fences separate; `make validate` still passes with only quality warnings.
