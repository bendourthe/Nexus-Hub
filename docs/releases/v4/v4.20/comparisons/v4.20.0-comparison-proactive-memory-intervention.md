# Comparison: Proactive Memory Agent for Long-Horizon Agents

**Source**: Wu, Zhang, Zhou, Wang, Peng, Li, Fan, Zhao (Meta AI), "Remember When It Matters: Proactive Memory Agent for Long-Horizon Agents", arXiv:2607.08716v1, 2026-07-09
**Source type**: Research paper supplied as a document (insight extraction)
**Authored during**: v4.19 cycle
**Adoption target**: v4.20.0
**Date**: 2026-09-18

The paper argues that memory for a working agent is an INTERVENTION problem, not a storage or retrieval problem: the question is not what to remember but whether remembered execution state should re-enter the agent's next decision. Nexus-Hub covers the symptoms this addresses and does not cover the mechanism. Six insights are missing outright, each confirmed by a zero-hit grep across the whole catalog.

One finding dominates the plan shape: the paper's architecture IS a context-injection runtime, and v4.13.1 is a queued plan whose entire purpose is deciding whether such a runtime should be built at all. The implementable half of this comparison is therefore gated on that verdict and is recorded as blocked rather than planned.

### Missing (6)

Each confirmed by `grep -ri` across `catalog/` returning zero hits on 2026-09-18.

| # | Insight (section) | Gap |
|---|---|---|
| 6 | **Behavioral state decay**: information may still sit in the transcript, or even inside the context window, and yet no longer exert reliable control over behavior (Sec 1) | Zero hits for "state decay" or "behavioral state". `context-degradation` frames the problem as context QUALITY decaying, with mitigations that are session-management moves (refresh, split, checkpoint and restart, compaction). That diagnosis prescribes restarting the session; the paper's prescribes reactivating one item. Treating an inert-but-present fact as an absent one sends the reader to the wrong fix. |
| 7 | **Memory as intervention**: the control question is whether retained state should enter the loop, which is strictly stronger than what a summarizer asks (Sec 2.5) | Zero hits for "when to intervene". No catalog skill frames reminder timing as a decision with its own policy. |
| 8 | **Null intervention as an explicit first-class action** (Sec 3.3) | Zero hits for "remain silent" or "no_intervention". Nothing in the catalog treats declining to speak as a chosen action with its own justification, rather than as the absence of one. |
| 9 | **Three-part memory bank with a PRIVATE status field** (Sec 3.2) | Zero hits for "memory bank". The private-status idea is the subtle half: the memory process keeps a working model of progress, open issues, and unresolved risks that is never shown to the action agent, so maintaining the model does not itself consume the agent's context. |
| 10 | **Trigger-function design** `g(t)`: fixed interval used to isolate the effect, with named alternatives (after tool errors, failed tests, repeated commands, large context shifts) (Sec 3.4) | No catalog skill discusses when a companion process should wake. `loop-engineering` owns loop exit conditions and stall detection, not observation cadence for an advisory process. |
| 11 | **Over-intervention is a measured harm, not merely waste** (Sec 4.3, 4.4, Table 4a) | Zero coverage. Three separate results: always-inject loses to selective on the domain-balanced macro average; injection-only without a bank actively HURTS one domain relative to baseline (62.0 vs 68.0 on airline); and an untrained 27B memory agent REDUCES reward (0.709 to 0.693) before SFT and GRPO recover it. The catalog has no rule anywhere that an advisory surface can be net-negative. |

## Step 5: Security and reverse-engineering assessment

### 5.1 Threat model comparison

| Dimension | The paper's architecture as published | Nexus-Hub after the recommended adoption |
|---|---|---|
| New runtime dependencies | A second LLM (Claude Opus 4.6 in the main results) running alongside the action agent | None. All three recommended candidates are instruction text. |
| Outbound call destinations | One frontier model call per memory step | None added. |
| Credentials or API keys | A model credential for the memory agent | None. |
| Source code, prompts, or query text leaving the machine | The recent trajectory window is sent to the memory model on every memory step | Nothing added. The blocked candidate D, if ever built, would be deterministic and local by construction. |
| New commercial relationship | Yes, if the memory model is a third-party endpoint | None. |
| Context-window exposure | A reminder terminates in the action agent's context at every intervention | None from the recommended candidates. This is precisely the exposure v4.13.1 is scoped to evaluate. |

### 5.3 Reverse-engineering viability

| Candidate | Classification | Note |
|---|---|---|

Deterministic reminder hook | `re-partial`, **gated** | The trigger and injection halves reverse-engineer cleanly: `catalog/hooks/workflow-phase-notice.sh` is an existing PostToolUse hook that inspects the tool payload and emits an advisory reminder, exit 0, never blocking. Deterministic triggers (a repeated command, a tool error, a failed test) are derivable from the same payload with no model call. The BANK-MAINTENANCE half does not reverse-engineer: deciding which of several remembered items is currently behaviorally relevant is a judgment the paper assigns to an LLM, and a deterministic rule would fire on keyword coincidence rather than relevance. ## NOT recommended

| Item | Reason |
|---|---|
| **Run an LLM memory agent alongside the session (candidate E)** | Dropped on two independent grounds. First, cost: the architecture calls a model at every memory step, and the paper's main results use a frontier model for that role across an entire long-horizon trajectory. v4.16.0 exists precisely because subagent cost is a live concern in this repository. Second, the obvious cost fix is unavailable: insight 11 measures that an undertrained memory agent REDUCES outcomes below having none, so the role cannot be routed to a cheap tier to make it affordable. A third-party memory endpoint would additionally hit the MCP Registry Policy hard-no on generation-as-service. |
| **Adopt Mem0 or the paper's reference implementation** | Both are named in the source and neither is adopted. Mem0 is a persistent memory layer the paper itself benchmarks and beats on macro-average; Nexus-Hub already has a local persistent store in `agent-memory`, so adding a vendor memory layer would duplicate an owned capability while adding a data processor. The reference implementation is a research artifact, not a distributable dependency. Per the Reverse-Engineering Attribution Rule, neither name appears in any distributed artifact; both stay in this report. |
| **Ship the paper's reported point estimates as expected gains** | The +8.3 pp and +6.8 pp figures are from one preprint, one harness, and a specific action/memory model pairing, on 85 and 278 tasks respectively. Quoting them in a skill would present a single unreplicated measurement as a property of the technique. The ablation ORDERING is the transferable finding; the magnitudes are not. |
| **Implement the four `memory_*` tool signatures as a Nexus-Hub interface** | Nexus-Hub does not own an agent run loop in which to register tools. They are retained inside candidate B as design description of what a well-constrained bank interface looks like, which is the part a reader building an agent can actually use. |
