# Plan - Org Knowledge Layer

**Project**: Nexus-Hub
**Version**: v3.17.4
**Slug**: org-knowledge-layer
**Plan Type**: Feature
**Created**: 2026-08-13
**Goal**: A user runs `nexus-hub org connect <path-or-url>` against their organization's standards bundle and, on every subsequent install/upgrade, all 16 platforms render an org-standards block (with explicit org-over-catalog precedence) plus org rule files, surviving catalog refreshes untouched.

## Overview

Nexus-Hub's catalog is deliberately generic and company-neutral. Organizations adopting it have no supported way to layer their own coding standards, safety rules, CI/CD frameworks, naming conventions, documentation style, branching strategy, or testing requirements over the generic guidance. This plan ships the org knowledge layer: the organization maintains a bundle of plain-Markdown standards (a local/shared directory or a git repo) plus a small `org.json` manifest; a new `nexus-hub org` CLI surface connects it; and a seeding module at the `IntegrationBase.install()` dispatcher seam projects it into every platform's instruction file as a second, independently replaceable marker block positioned after the Nexus-Hub block, with an explicit statement that org standards take precedence over the generic guidance above, plus org rule files wherever the platform has a rules surface.

The design follows the decisions recorded in [`docs/releases/v3/v3.17/development/org-knowledge-layer-research.md`](../development/org-knowledge-layer-research.md): Option A (connect + project), both directory and git-URL sources, layered-text precedence (no suppression mechanism in this version), and the guided authoring experience shipping in the same version as an `org-standards-authoring` skill plus an `/org` command. Precedence is expressed as text ordering plus an explicit statement because no platform exposes a cross-vendor rules-priority lever, and the do-not-invent rule forbids fabricating one; where a platform documents a stronger native mechanism (managed CLAUDE.md, Cursor Team Rules, Copilot org instructions), the authoring skill teaches it as the escalation path rather than this feature implementing it.

Success is observable: after `nexus-hub org connect`, `nexus-hub org status` reports the connection and the per-platform posture (default / advisory); each installed platform's instruction file carries a `<!-- NEXUS_HUB_ORG_START/END -->` block whose content matches the org bundle's core document; a subsequent full installer run or `nexus-hub upgrade` regenerates the Nexus-Hub block without disturbing the org block or org rule files; and `nexus-hub org disconnect` removes every org artifact cleanly via the manifest.

## Phase 1: Org Bundle Contract

**Goal**: Define and validate the shape of an organization's standards bundle so every later phase builds against a fixed contract.
**Prerequisites**: None.
**Stability Gate**: `make validate` and `make test` pass with the new validator module and its pytest suite; the example bundle validates clean; a deliberately broken bundle produces actionable errors.
**Recommended model tier**: strong
**Recommended effort level**: medium
**Rationale**: Schema and validator design with clear precedents (`configs/platform-defaults.json`, `configs/README.md`) and no cross-platform blast radius.

### Sub-tasks

#### 1.1 - Bundle layout and manifest schema

**Objective**: Fix the org bundle convention and the `org.json` manifest schema, documented in `configs/`.

**Failure modes**: A manifest with unknown keys is accepted with a warning (forward compatibility); a manifest missing required keys (`schema_version`, `org_name`, `core`) fails validation with the exact missing key named; a bundle whose `core` file exceeds the always-on budget validates with a WARNING (not an error) quoting the budget rationale. Malformed JSON reports the parse position. There is no dependency call and no concurrent operation in this component.

**Prompt**:
> In the Nexus-Hub repo, define the org knowledge bundle contract. Read `docs/v3/v3.17/development/org-knowledge-layer-research.md` first (sections 2 and 3) and model everything on the `configs/platform-defaults.json` + `configs/README.md` pattern (the repo-internal declarative-config precedent, see `configs/README.md:3` for the "nothing here is copied as-is" boundary).
>
> Deliverables: (1) `configs/org-bundle.schema.json` - a JSON Schema for `org.json` with required `schema_version` (int, 1), `org_name` (string), `core` (relative path to the always-on Markdown core, default `core.md`), and optional `rules_dir` (default `rules/`), `references_dir` (default `references/`), `precedence_statement` (string; when absent a default statement is used at render time). (2) `configs/examples/org-bundle-example/` - a minimal example bundle: `org.json`, a `core.md` under 60 lines demonstrating the <200-line always-on budget (cite Anthropic's guidance from the research doc), `rules/python/code-style.md` showing an org rule that mirrors the `catalog/rules/<lang>/<topic>.md` layout, and `references/ci-cd-standards.md` showing on-demand detail. (3) A new section in `configs/README.md` documenting the bundle contract, the always-on token budget rationale, and the boundary: the repo ships schema + example + validator; the org's actual content lives outside the repo.
>
> Constraints: everything under `configs/` is repo-internal and needs NO installer copy step. Do not touch `catalog/`, either installer, or `templates/ai-instructions/`. Follow `catalog/style-guides/markdown.md` for all Markdown. Add a CHANGELOG `## [Unreleased]` entry.
>
> Acceptance criteria: schema file parses as valid JSON Schema; example bundle files exist and cross-reference each other; `configs/README.md` section added; `make validate` passes; CHANGELOG updated.

## Phase 3: Cross-Platform Materialization

**Goal**: A connected org bundle is projected into every installed platform: an org marker block in each instruction file with explicit precedence, and org rule files where the platform has a rules surface - surviving catalog refreshes.
**Prerequisites**: Phases 1-2.
**Stability Gate**: With the example bundle connected, a full registry install materializes the org block on every `MarkdownIntegration` platform and org rules on every `rules_subdir` platform; an immediate second install reports `unchanged`; a refresh-mode install does not delete org artifacts; disconnect + repair removes them.
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: This is the dispatcher-seam change with 16-platform blast radius, ordering interactions with legacy installer copy blocks, and pruning semantics that a wrong assumption would silently break.

### Sub-tasks

#### 3.1 - `seed_org_knowledge()` at the dispatcher seam

**Objective**: Grow `org_knowledge.py` with the seeding half: called once per integration from `IntegrationBase.install()`, immediately after `seed_platform_defaults`.

**Failure modes**: No connection recorded means a silent no-op (one `_note()` line in verbose mode only); an unreadable or invalidated bundle logs one warning and skips seeding rather than failing the install (degrade-never-fail, per `platform_defaults.py:301-306`); a destination instruction file that does not exist yet is skipped for that platform (the marker write only ever targets files the platform integration just wrote or that already exist); manifest tracking is wrapped in try/except so it can never break an install; two installs racing on the same file are acceptable last-writer-wins because the block content is deterministic from the bundle.

**Build class**: load-bearing.

**Prompt**:
> Extend `scripts/lib/integrations/org_knowledge.py` with `seed_org_knowledge(integration_key, ctx)` and wire it into `IntegrationBase.install()` at `scripts/lib/integrations/base.py:154-194`, immediately after the `seed_platform_defaults` call (`:191-193`), gated identically (`ctx.scope` handling and `result.detected is not False`) and with the same dispatcher-not-install_global rationale comment (`base.py:177-182`). Read `docs/v3/v3.17/development/org-knowledge-layer-research.md` sections 2-3 first.
>
> Behavior per platform: (1) For platforms with an instruction file (every `MarkdownIntegration`), append/replace an org block in the DESTINATION instruction file via `merge_marker_section` (`scripts/lib/installer/instruction_merge.py:56-62`) with dedicated markers `<!-- NEXUS_HUB_ORG_START -->` / `<!-- NEXUS_HUB_ORG_END -->`, positioned AFTER the Nexus-Hub block. ## Phase 4: Guided Authoring Surface

**Goal**: An organization can be guided, end to end, through collecting, organizing, and budgeting its internal documents into a valid bundle - via a catalog skill and an `/org` command.
**Prerequisites**: Phases 1-3 (the skill teaches the shipped contract, not a speculative one).
**Stability Gate**: The skill passes `make validate` (including the placeholder lint and bundle audit); the command dispatches correctly; all three registry files updated; trigger evals pass.
**Recommended model tier**: strong
**Recommended effort level**: medium
**Rationale**: Skill and command authoring against well-documented catalog conventions; the risk is registration completeness, not design.

### Sub-tasks

## Release Scope Amendment: GitHub Usage Monitor Resilience

**Status**: Included in the uncommitted v3.17.4 release candidate and locally verified on 2026-08-17; pending final release-note approval and release commit.
