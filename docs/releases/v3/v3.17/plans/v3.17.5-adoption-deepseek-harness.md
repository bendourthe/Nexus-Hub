**Project**: Nexus-Hub

**Goal**: Nexus-Hub adopts the nine recommended items from the DeepSeek Harness comparison: a doc word-budget gate, a `deepseek-harness` SDK skill, three skill extensions, a decision-record lifecycle, a registry drift-check, and invocation-policy frontmatter, all local-only and validated by `make validate` + CI.

## Overview

The v3.17.5 comparison against DeepSeek Harness (dsh) found that the transferable value of that runtime framework is its meta-engineering, not its product code. This plan operationalizes the report's adoption table in its confirmed sequencing: reverse-engineered local guards first where they unblock later phases (the doc word-budget ratchet), then the catalog-native deliverable (a `deepseek-harness` skill, a peer of `claude-agent-sdk` and `google-antigravity-sdk`), then three additive skill extensions, then the two governance builds (decision-record lifecycle, registry drift-check), and finally the invocation-policy frontmatter that touches the installer surface.

Every item is MCP Registry Policy bucket 2 (skill-native) or bucket 3 (local reverse-engineered build): zero outbound calls, zero credentials, zero dependencies beyond the Python stdlib. Delivery is the normal catalog path: files land in `catalog/`, `scripts/`, and `docs/`, validated by `make validate`, `make lint`, `make test`, and distributed by the installers with no installer edits except where a new repo-level script requires the explicit-name copy step (none do; all new scripts here are repo-internal guards in `DEV_ONLY_SCRIPTS`).

Success looks like: `make validate` enforces doc budgets and decision-record format; the catalog ships 272 skills including `deepseek-harness` with green trigger evals; the three extended skills carry the new named patterns without trigger regressions; `docs/decisions/` exists with the consolidated content of `.claude/memory/decisions.md`; and the B5 gate-DAG runner is recorded as a deferred known gap rather than silently dropped.

## Phase 1: Doc Word Budgets (B1)

**Goal**: A stdlib-only word-budget validator gates every listed standing doc under a ceiling, with a ratchet-down policy.
**Prerequisites**: None.
**Stability Gate**: `make validate` fails when any budgeted doc exceeds its ceiling, when the manifest lists a missing file, or when a ceiling is not a positive integer; all currently budgeted docs pass; pytest suite for the validator is green.
**Recommended model tier**: standard
**Recommended effort level**: medium
**Rationale**: A small deterministic script port (dsh's equivalent is 58 lines) with clear acceptance criteria; complexity is low and the blast radius is contained to validation.

### Sub-tasks

#### 1.1 - Budget validator and manifest

**Objective**: Create `scripts/validate_doc_budgets.py` and `docs/policy/doc-budgets.json`, seeded with ceilings for the always-loaded instruction docs.

**Failure modes**: Malformed or absent manifest (bad JSON, non-integer ceiling, empty object) exits 1 with a per-entry `BAD` line naming the key, never a traceback. A budgeted file missing from disk is a `MISS` failure (the manifest must be updated in the same change), not a silent skip. Two entries naming the same path after normalization are a duplicate-key failure. All failures are collected and printed before the single exit, so one bad entry does not mask another.

**Build class**: load-bearing.

**Prompt**:
> In the Nexus-Hub repo, create `scripts/validate_doc_budgets.py` (Python 3, stdlib only, module docstring, type annotations per repo hook conventions). It reads `docs/policy/doc-budgets.json`, a JSON object mapping repo-relative paths to positive-integer word ceilings, counts whitespace-delimited words per file, and reports three failure classes, collecting all before exiting 1: `BAD` (non-positive-integer ceiling), `MISS` (budgeted file absent), `OVER` (word count exceeds ceiling, print count and ceiling). Support `--list` to print a usage table (path, words, ceiling, headroom) and exit 0. The `OVER` message must say "relocate or condense; raising a ceiling requires justification in the PR", never suggest raising as the default. Seed the manifest with ceilings at current-size-plus-10%-headroom (measure with `--list` first) for: `AGENTS.md`, `CLAUDE.md`, the five lockstep `templates/ai-instructions/base-*.md` files, and `catalog/style-guides/markdown.md`. Document the ratchet policy (ceilings only decrease over releases; keep >=5% headroom) in a comment block at the top of the manifest's companion note `docs/policy/doc-budgets.md`. Wire the script into `make validate` and add it to `DEV_ONLY_SCRIPTS` in `catalog/hooks/tests/test_installer_smoke.py` (repo-internal guard, no installer copy step, no `.ps1` sibling needed per the `check_version_sync.py` precedent). Acceptance: `python scripts/validate_doc_budgets.py` exits 0 on the seeded manifest; corrupting a ceiling, deleting a budgeted file, or exceeding a ceiling each produce the correct labeled failure.

## Phase 5: Registry Entry Drift-Check (B4)

**Recommended effort level**: medium

### Sub-tasks

#### 5.1 - Entry-scoped drift-check script

**Objective**: Create `scripts/check_registry_entries.py` that renders each skill's expected registry presence in memory and diffs against committed bytes.

**Failure modes**: A skill directory with malformed frontmatter (unparseable YAML, missing summary_l0) is reported as a source failure naming the skill, distinct from registry drift. A registry file that fails to parse aborts with a file-level error, not a per-skill cascade. A skill present in the catalog but absent from a registry (or vice versa) is an explicit membership failure; a field mismatch names skill, file, and field. Fields that are editorial rather than derivable (downloads, security scores, priority) are compared for presence and type only, never value, so the check cannot demand a regeneration it is forbidden to perform.

**Build class**: load-bearing.

**Prompt**:
> Create `scripts/check_registry_entries.py` (stdlib + the YAML frontmatter approach existing validators already use). For every `catalog/skills/<cat>/<name>/SKILL.md`: parse frontmatter; verify a `data/SKILL_INDEX.md` row exists with matching name, category, quoted summary_l0, and path; verify a `data/skills.json` entry exists with matching name, category, path, and summary fields (presence-and-type-only for editorial fields: downloads, security, priority, size); verify `data/marketplace.json` per-category `skill_count` sums and `statistics.total_skills` equal the catalog census. Default mode is `--check` (read-only, exit 1 with `stale: <skill> <file> <field>` lines); provide `--emit <skill>` printing the expected INDEX row and skills.json entry to stdout as a paste-ready aid, explicitly NOT writing files (the hand-edit convention from the skill-registration memory stands; this tool makes the hand edit checkable and paste-assisted, not automatic). Wire `--check` into `make validate` and `DEV_ONLY_SCRIPTS`. ## Phase 6: Invocation-Policy Frontmatter (B3)

**Goal**: Skills can declare `user-invocable` / `disable-model-invocation`, validated for type and cross-surface consistency, and mapped at install time only where a platform documents an equivalent lever.
**Prerequisites**: Phases 2 and 5 (schema additions ride on a checkable registry).
**Stability Gate**: `validate_skills.py` accepts the optional booleans and rejects type errors and the invalid combination; the platform-lever survey is recorded in the levers policy doc with source URLs or explicit "no lever documented" verdicts; installer seeding (if any) is gated on VERIFIED classifications; maintainer approval obtained before any installer edit.
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: Touches the installer surface (ask-first territory) and the do-not-invent rule; the fabricated-Kimi-lever incident is the direct precedent for what failure looks like here.

### Sub-tasks

#### 6.1 - Schema and validator extension

**Objective**: Add the two optional frontmatter booleans to the SKILL.md contract and validate them.

**Failure modes**: A non-boolean value (string "true", integer) is a type error naming skill and field. The invalid combination `disable-model-invocation: true` with `user-invocable: false` (a skill nobody can invoke) is a hard error. Absence of both fields is the valid default (model-invocable, user-invocable) and produces no output, so 270+ existing skills pass untouched.
