# Plan - Comparison Versioning Fix (Adoption-Target Placement + Co-location + Drift Check)

**Project**: Nexus-Hub
**Version**: v3.14.2
**Slug**: comparison-versioning-fix
**Plan Type**: Bug-fix campaign (harness convention flaw)
**Created**: 2026-07-16
**Goal**: A `/compare` report is versioned and placed by the release that will *adopt* it (not the authoring cycle), `/plan from-comparison` writes the resulting plan into that same version directory, and a `documentation-consistency` drift check flags any comparison whose seeded plan lives in a different version directory so the mismatch cannot silently recur.

## Overview

A real reorganization on 2026-07-16 exposed a systemic flaw: comparison reports were landing in the wrong version directory. The codex-lb comparison sat under `docs/v3/v3.13/` while its adoption plan was v3.14; the codesight comparison sat under `docs/v3/v3.13/` while its adoption plan was authored v3.14 and belonged in v3.15. Both files even documented their own discomfort ("this report lives with v3.13.0 docs", "the natural home is a future version, e.g. v3.15.0"), which is the signature of a convention flaw rather than an execution slip: the agent followed the rule faithfully and flagged the mismatch in prose. Those two files were corrected by hand; this plan fixes the rule so it stops happening.

The root cause is the version-resolution convention shared by `/compare` and `/plan from-comparison`, not the `docs-layout-refactor` skill (which is a reorganizer that deliberately preserves existing placement to avoid mid-version path churn and has no notion of "logical version by adoption target"). Two concrete defects: (1) `/compare` versions and places a comparison by the in-flight *authoring* cycle (resolved from git tags/CHANGELOG via the docs-layout-refactor Version-directory resolution), but a comparison is intrinsically forward-looking - it seeds a *future* adoption; and (2) `/plan from-comparison` resolves the plan's `version_dir` fresh and ignores the comparison's own stated target (the codesight comparison explicitly said "adoption target v3.15.0", yet the plan was generated v3.14.0). The two compound so a comparison and the plan it seeds diverge across version trees, and nothing moves the comparison forward when adoption slips (the common case, since the current release's plan is usually already locked).

The fix is three coordinated changes, each small and instruction-level: (A) give every comparison an explicit `Adoption target: vX.Y.Z` field and version/place the file by that target; (B) make `/plan from-comparison` read that field and write the plan into the same `version_dir` as the comparison (a co-location guarantee); and (C) add a drift check to `documentation-consistency` that flags any comparison whose seeded plan (or any plan whose `Seeded from` comparison) lives in a different `version_dir`, and run it once to reconcile the current active versions. Historical/archived comparisons under `docs/archive/**` and prior-major trees are grandfathered, mirroring the docs-layout-refactor grandfathering norm.

Delivery: this is a v3.14 patch, independent of and orderable with the v3.14.1 installer hotfix; branch `fix/comparison-versioning` off `develop`. All edits are to command `.md` files (`catalog/commands/compare.md`, `catalog/commands/plan.md`) and skill bodies (`cross-project-comparison`, `implementation-plan`, `documentation-consistency`) - which the installer auto-distributes via folder copy, so there is no installer copy-step edit and no `base-*.md` lockstep change. If any skill frontmatter changes (a `version:` bump, or the `description`/`summary_l0`/`overview_l1`), the three `data/` registry files (`SKILL_INDEX.md`, `skills.json`, `marketplace.json`) must be hand-synced (do NOT run the full catalog rebuild - it rewrites the entire tree). Validate with `python scripts/validate_skills.py` and `python scripts/check_version_sync.py` (run the underlying commands directly since `make` is unavailable in this environment), plus a self-run of the new drift check against the repo.

## Phase 1: Adoption-Target Placement (Fix A)

**Goal**: A comparison declares the release that will adopt it and is versioned/placed by that release, so a comparison authored during one cycle that adopts in a later release lands in the later release's directory.
**Prerequisites**: None.
**Stability Gate**: A dry-run of `/compare` against a sample source resolves an `Adoption target: vX.Y.Z` (defaulting to the next free version slot, confirmed with the user) and writes the report to `docs/v<MAJOR>/v<MAJOR>.<MINOR>/comparisons/v<MAJOR>.<MINOR>.<PATCH>-comparison-<name>.md` for that TARGET version, not the in-flight version; `python scripts/validate_skills.py` passes.
**Recommended model**: Strong reasoning tier (Opus-class), medium effort. Rationale: this changes a placement convention that both `/compare` and `/plan` rely on; wording must be exact and backward compatible with existing comparisons; re-confirm against the live model set at implementation time.

## Phase 2: From-Comparison Co-location (Fix B)

**Goal**: `/plan from-comparison` reads the comparison's `Adoption target:` field and writes the generated plan into the same `version_dir` as the comparison, guaranteeing a comparison and the plan it seeds always live together.
**Prerequisites**: Phase 1 (the `Adoption target:` field must exist for Fix B to read).
**Stability Gate**: A from-comparison dry-run seeded by a report carrying `Adoption target: vX.Y.Z` writes the plan to `docs/v<...>/vX.Y/plans/vX.Y.Z-adoption-<name>.md` (same version tree as the comparison); when the field is absent (a legacy comparison) it degrades to the current resolution with a one-line note. `python scripts/validate_skills.py` passes.
**Recommended model**: Strong reasoning tier (Opus-class), medium effort. Rationale: edits the plan generator's version-directory resolution and must degrade gracefully for legacy comparisons; re-confirm against the live model set at implementation time.

### Sub-tasks

#### 2.1 - Read the adoption target in from-comparison mode

**Objective**: The plan generator honors the comparison's stated target instead of re-resolving to the in-flight/next version.
