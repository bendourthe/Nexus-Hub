# Plan - Split the Usage Monitor into Two Separate Extensions (Claude-only + Codex-only)

**Project**: Nexus-Hub
**Version**: v3.14.4
**Slug**: usage-monitor-split
**Plan Type**: Refactor + feature (extension de-merge)
**Created**: 2026-07-18
**Goal**: Ship two independently-installable VS Code extensions - a Claude-only "Claude Usage Monitor" and a brand-new Codex-only "Codex Usage Monitor" - that coexist without collision, each with its own identity, branding, and status-bar icon, wired end-to-end into the installer, CI, and docs, released as v3.14.4.
**Persona**: A Nexus-Hub user who runs Claude Code and/or the Codex (ChatGPT) app inside VS Code and wants an at-a-glance, per-tool usage monitor in the status bar - each tool branded and independent, so installing one never implies or mislabels the other.
**Definition of Done** (all observable):

- `extensions/claude-usage-monitor/` contains zero Codex code, config, tests, or user-facing strings; `displayName` is "Claude Usage Monitor"; it compiles, all Vitest tests pass, and it packages + installs as `nexus-hub.claude-usage-monitor`.
- `extensions/codex-usage-monitor/` exists, is fully self-contained (no shared build dependency on the Claude folder), Codex-only; `displayName` is "Codex Usage Monitor"; the Marketplace/extension icon is `codex-2048x2048.png`; the status bar shows a Codex glyph derived from `codex-white.png` (theme-tinted, same mechanism as Claude); the hover/tooltip and dashboard progress-bar fill is `#5244BB`; it uses its own command namespace (`codex-usage.*`), config section (`codexUsage.*`), `globalState` keys, and warning-view container/context; it compiles, tests pass, and packages + installs as `nexus-hub.codex-usage-monitor`.
- Both extensions can be installed and run **simultaneously** with no collision of extension id, command id, `globalState` key, view-container id, or `when`-context key; both status-bar items appear at once.
- `scripts/installer.sh` and `scripts/installer.ps1` each build + package + install **both** extensions; `.github/dependabot.yml` has an entry for each; each extension has a path-filtered CI workflow.
- Root `README.md`, `CHANGELOG.md`, `docs/DEVLOG.md`, `llms.txt`, and both extension READMEs describe the two extensions; the repo version is bumped `3.14.3 -> 3.14.4` across every sync surface and `python scripts/check_version_sync.py` passes.

## Overview

In v3.14.0 (commit `1b98837`) the `claude-usage-monitor` extension was generalized into a "unified multi-provider extension": a single `UsageProvider` interface with a Claude implementation and a Codex implementation, selected at runtime by a `usageMonitor.provider` setting, a "Usage: Switch Provider" command, and a settings-panel dropdown. Its `displayName` became "Claude & Codex Usage Monitor". In practice this mislabels the Claude extension (it advertises Codex it is not monitoring unless the user flips a setting) and buries the Codex capability behind a provider switch instead of shipping it as its own branded tool.

This plan de-merges that work. The v3.14.0 refactor did the hard part - a clean, vendor-neutral seam (`UsageProvider`, the normalized `UsageData` model, and `describeProviderError`), plus a fully-implemented, test-covered Codex provider (credential resolution, the `chatgpt.com/backend-api/wham/usage` mapping, and reframed throttle/wait/rotate recommendations). So the work is mostly **separating** one codebase into two single-provider extensions, not building Codex monitoring from scratch.

Per the user's decisions:

- **Independent copies** - two fully self-contained extension folders (no shared build package); each packages to its own VSIX independently.
- **Surgical de-Codex** for Claude - remove all Codex code, the provider switch, the provider config, and the Codex tests; keep the current UI and Claude as the sole path (not a hard git revert to 0.6.2).
- **Traced Codex glyph font** - because a VS Code status-bar item can render only text plus theme icons (codicons or contributed icon-font glyphs), never an arbitrary PNG, `codex-white.png` is traced to an SVG and built into a `codex-icon` font (mirroring the existing `scripts/generate-icon-font.js`), so the status bar shows a theme-tinted Codex glyph. `codex-2048x2048.png` is the full-color Marketplace/extension icon.

The two source images the user referenced (`codex-2048x2048.png` = the purple `>_` cloud; `codex-white.png` = the white monochrome mark) are **not yet in the repo** - they are the two images attached to the request and are added as assets in Phase 2.

**Coexistence is the load-bearing constraint.** Both extensions will frequently be installed at once. Every VS Code identifier that is global-per-editor must differ between them: extension id, all command ids, `globalState` storage keys (`claudeUsageData` today at `usageStore.ts:13-15`), the webview ids (`claudeUsageDashboard`, `claudeUsageSettings`), the activity-bar view container (`claudeUsageWarning`), and the `when`-context key (`claudeUsage.warningActive`). The Codex build gets the `codexUsage.*` / `codex-usage.*` / `codexUsageWarning` / `codexUsage.warningActive` equivalents throughout.

Independent versioning: the extensions carry their own semver, decoupled from the repo's `3.14.x`. The Claude extension bumps `0.7.0 -> 0.8.0` (feature-level: capability removed + rename). The Codex extension starts at `0.1.0`.

Delivery: branch `feat/usage-monitor-split` off `develop` per the develop+main model. `extensions/` is **not** part of the installer's recursive `catalog/` copy - the installer builds and installs each extension by explicit name - so the new Codex extension requires explicit installer entries in both `installer.sh` and `installer.ps1` (Phase 3). No `base-*.md` lockstep change and no MCP registry change are involved. Finalize under `## [Unreleased]` in `CHANGELOG.md`; then hand off to `/update release` for the v3.14.4 bump, tag, and GitHub Release (the user runs the release).

## Complexity Tracking

- **Scope**: ~13 TypeScript source files per extension, two `package.json` manifests, an icon-font asset pipeline, both installers, dependabot, one new CI workflow, and the docs/version surfaces. Moderate but well-bounded.
- **Primary risk - id/key collision when both are installed** (mitigated in Phase 2 by distinct namespaces across extension id, commands, `globalState` keys, webview ids, view container, and `when`-context; verified in Phase 3).
- **Secondary risk - Codex glyph fidelity**: `codex-white.png` is a raster mark; tracing it to a clean single-color SVG glyph for the icon font is lossy. Mitigation: trace, visually verify at status-bar size, and fall back to a simple recognizable silhouette if the trace is noisy (the extension icon stays the full-color PNG regardless).
- **Tertiary risk - `wham/usage` endpoint instability** (pre-existing DF-1): undocumented endpoint; the provider already fails soft. Carried forward, not re-litigated here.
- **De-risking lever**: the vendor-neutral seam already exists, and the Codex provider + recommendations are already test-covered, so most edits are deletions and rebrand string swaps against a fully-enumerated branch list (see the recon anchors cited per sub-task).
