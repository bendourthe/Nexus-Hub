# Plan - Presentify Upfront Design Questions (Batch the Four High-Level Choices Before Content Analysis)

**Project**: Nexus-Hub
**Version**: v3.14.3
**Slug**: presentify-upfront-questions
**Plan Type**: Feature enhancement (UX / workflow-ordering fix)
**Created**: 2026-07-16
**Goal**: `/presentify` works end-to-end from a clean install: its delegate skill `document-to-interactive-html` actually loads (no "Unknown skill" - Phase 0 fixes the invalid YAML frontmatter that broke it), and then, running on any input, it presents all four high-level design questions (style / design direction, layout / output aspect, interactivity level, imagery tier) in a SINGLE batched round immediately after the command is submitted and BEFORE any content extraction or figure-reconstruction runs, without ever pre-answering a choice from a recalled memory or saved preference (only an explicit flag or the headless fallback skips a question); a run that names any of the four on the command line binds it and drops it from the batch; a non-interactive / headless run never blocks and keeps the existing content-aware fallbacks; the imagery question offers license-free stock (images plus, when a Pexels key and explicit consent are present, video), prioritizes real commercial-free stock over AI-generated visuals while still offering local AI, and reconciles the current "video out of scope" wording; and no "resolved right after the style / aspect" sequencing language remains in the skill or its references.

## Overview

A real run against a PDF surfaced two coupled UX defects. First, the design questions arrived far too late: the user expected to choose the high-level design direction up front but the style prompt only appeared after several functions had run and the extractor had begun analyzing the first page. Second, only the style question ever appeared: after 30 minutes the layout, interactivity, and imagery questions had still not been asked. Both are the same root cause, in [document-to-interactive-html/SKILL.md](../../../../../catalog/skills/specialized-domains/document-to-interactive-html/SKILL.md): the four design choices live in **Step 4**, which runs after Step 2 (extract to the content model) and Step 3 (the mandatory, expensive figure-classification + OCR-verification pass over every image), and the four choices are resolved as four SEPARATE sequential menus spread across a long-running pipeline. So the first menu appears only after extraction begins, and the remaining three never surface while the pipeline grinds.

None of the four choices depends on the document's content. The only content-aware logic is the non-interactive fallback (a deck defaults to full-width / balanced; a report defaults to standard / restrained), and that fires only when the menu cannot be answered. So the entire block of choices is safe to hoist to the very front and to collapse into one batched question round (the interactive question surface accepts up to four questions at once). The generative half of the current Step 4 (the seeded entropy roll and the concrete-token brainstorm for the chosen direction) legitimately benefits from having seen the content and is NOT a blocking user prompt, so it stays after extraction; only the four choices move.

The imagery question also gets a content upgrade, per the user's request: when the stock / media tier is selected, the pipeline PRIORITIZES real, license-free, commercial-use stock media relevant to the content and MINIMIZES AI-generated images, while still offering local AI generation as an explicit option. Stock VIDEO is offered in the question but gated: actual embedding runs only when a Pexels key and explicit consent are present, otherwise the run degrades to images-only with a one-line note. This reconciles today's inconsistency, where the command already advertises stock "images / video" and `fetch_stock_media.py` already has a Pexels video path, but the skill's "When NOT to use" and the extraction runbook both flatly declare video embedding out of scope. The reconciliation clarifies that SOURCE-embedded media stays ignored (the extractor does not carry video out of input documents) while license-free stock video in the OUTPUT is supported through the gated stock tier, base64-embedded so the offline guarantee holds.

First-time setup and automation (Phase 3): stock IMAGES need no setup - the default source (Openverse) is keyless and license-clean - but stock VIDEO is Pexels-only and needs a free `PEXELS_API_KEY`. To spare the user from understanding any of this, v3.14.3 adds a bring-your-own-key helper: a guided, opt-in, one-paste setup that persists the key once to `~/.nexus-hub/config/media.env` (read by `fetch_stock_media.py` as a fallback to the environment variable), surfaced on first use (the moment the user first picks stock video and no key is found) and runnable anytime via a new `nexus-hub setup-media` subcommand. It is deliberately NOT added to the default no-prompt install. The honest limit: we cannot auto-provision the key - a Pexels key is tied to the user's own free account, and creating that account or shipping a shared embedded key is both a terms-of-service violation and a secret-handling hazard - so the helper guides the user through the ~30-second signup and takes it from there. Security: the key is entered via a no-echo terminal prompt (never pasted into the agent chat, never passed as a command-line argument that would land in shell history), stored with restrictive permissions (0600) outside any repository, and never logged or echoed.

Scope note: Phase 0 (added 2026-07-17) is code-bearing and installer-aware - it quotes the invalid `description` frontmatter across 47 skills, adds a strict-YAML gate to `scripts/validate_skills.py`, and switches BOTH installers to flatten skills for Claude (the fix that makes `document-to-interactive-html` load at all). Phases 1-2 are INSTRUCTION-ONLY (the command file and the skill's Markdown - SKILL.md, two reference files, and the extraction runbook - with no code change; `fetch_stock_media.py` already enforces the Pexels-key + `--consent` gate and degrades to Tier 1 on any missing key / consent / result). The verification surface is therefore the catalog validator plus a grep-based self-consistency check and a behavioral dry-run for Phases 1-2, and a real pytest module plus a secret-handling review for Phase 3.

## Findings from Live-Install Diagnosis (added 2026-07-17)

A real v3.14.0 install surfaced TWO defects when running `/presentify` on a PDF. Diagnosing them against the installed tree (`~/.claude/skills`, `~/.codex/skills`, `~/.gemini/...`) and the catalog produced the findings below; this plan is amended (new Phase 0, new sub-task 1.6, and the frontmatter-assumption corrections noted inline) to cover them. The evidence is recorded here so `/implement` does not re-derive it.

### Finding A - `/presentify` fails at delegation with "Unknown skill: document-to-interactive-html" (NEW - was not in this plan)

The command loads, but its `Skill(document-to-interactive-html)` delegation fails with `Unknown skill: document-to-interactive-html`. The entire reorder this plan proposes is invisible until this is fixed, because the skill that does the work never loads. TWO independent root causes compound:

1. **Invalid YAML frontmatter (must-fix; in scope for this plan - Phase 0).** The `description:` field in [document-to-interactive-html/SKILL.md](../../../../../catalog/skills/specialized-domains/document-to-interactive-html/SKILL.md) is an UNQUOTED YAML scalar that contains the sequence `SKIP: ` (colon followed by a space). YAML forbids a `: ` sequence inside a plain scalar, so a strict parser aborts: PyYAML raises `ScannerError: mapping values are not allowed here` (confirmed, at column ~1372 of the description line). `summary_l0` and `overview_l1` survive only because they are already double-quoted; `description` is the one Tier-1 field left bare. A catalog-wide strict-parse scan found **47 of 267 skills** carrying the same defect (an unquoted `description` whose text includes a `: ` from a `SKIP:` or inline clause). The repo's own `scripts/validate_skills.py` does NOT strict-parse the frontmatter, so `make validate` is green while a strict consumer silently drops the skill. Fix: wrap the `description:` value in double quotes (the parsed string is identical; only the YAML syntax is corrected). This DOES change the frontmatter bytes, which contradicts this plan's repeated "frontmatter unchanged -> no `data/` registry edit" assumption (see the correction under Scope, and Phase 0.4).

2. **The installer does not flatten skills for Claude (installer bug; likely v3.14.1 hotfix scope, NOT this plan).** Claude Code discovers skills exactly one level deep (`~/.claude/skills/<name>/SKILL.md`). But BOTH installers install Claude skills category-NESTED: `scripts/installer.ps1` (line ~1262) and `scripts/installer.sh` (lines ~896-900) invoke the registry integration with `--instruction-only` and then `safe_folder_copy catalog/skills -> ~/.claude/skills`, producing the undiscoverable `~/.claude/skills/<category>/<name>/` layout. This contradicts `scripts/lib/integrations/claude.py`, which declares `flatten_skills_layout: True`. On the user's disk, `~/.claude/skills/specialized-domains/document-to-interactive-html/SKILL.md` exists (the undiscoverable category copy) while the discoverable flat `~/.claude/skills/document-to-interactive-html/` is ABSENT. The flat skill set Claude actually reads is STALE (for example `~/.claude/skills/brand-styling` is dated Jun 1, before this skill was added in v3.13.0 ~Jul 15); because the v3.14.0 Claude install never re-flattened, the newly-added skill never got a discoverable flat entry. The same skill installed correctly to Codex (`~/.codex/skills/document-to-interactive-html`) and Gemini/Antigravity (`~/.gemini/.../document-to-interactive-html`), which DO flatten via the registry adapter (`scripts/lib/integrations/_catalog_adapters.py::flatten_skills`) - confirming this is a Claude-path-specific gap, not a catalog problem.

Routing (decided 2026-07-17): BOTH root causes are fixed in Phase 0 of THIS plan. Root cause 1 is fixed for `document-to-interactive-html` and swept across all 47 affected skills (Phase 0.1-0.2), with a strict-YAML validator gate to prevent regression (0.3). Root cause 2 - the installer-flatten parity fix - is folded in here (Phase 0.5) rather than deferred to v3.14.1, at the user's direction, because it is the change that actually lands the skill in Claude's discoverable space on a normal install. This makes Phase 0 installer-aware; the plan's "instruction-only" framing for the early phases is updated accordingly (see Scope and Delivery).

### Finding B - `/presentify` picked a style from memory instead of asking (PARTIALLY covered by Phase 1)

On a run with no `--style`, the agent read a recalled `presentation-style-preference` memory (written by a prior session) and silently committed "Corporate & Professional" instead of asking; it also asked only the style question, and layout / interactivity / imagery never surfaced. This is two problems:

- **Asked too late, one at a time, and the last three never appeared** - this is exactly Phase 1's target (hoist + batch the four choices up front). COVERED as written.
- **Used a recalled memory / saved preference to pre-answer** - NOT covered. Nothing in the skill or the command forbids pre-filling a choice from a recalled memory, a saved preference, a prior run, or inferred context. Batching the four questions does not, by itself, stop an agent that auto-applies a recalled preference from skipping one. The user's requirement is explicit: presentify must NOT use memories and must always ask. New sub-task 1.6 adds the rule: the ONLY thing that skips a question is an explicit flag in THIS invocation; recalled memories / saved preferences / prior runs / inferred context are ignored for these four choices.

### Additional hygiene finding

Three skill bundles carry compiled build artifacts in the working tree (`scripts/__pycache__/*.pyc`): `document-to-interactive-html`, `docs-layout-refactor`, `demo-capture`. They are gitignored (confirmed via `git check-ignore`), so they are NOT shipped in the release and are not the install cause - but they should be removed from the working tree, and the validator / installer should skip `__pycache__` defensively. Folded into Phase 0.4.
