## Overview

Nexus-Hub already has strong evaluation foundations in `rag-implementation`, `ai-output-evaluation`, and `skill-eval-loop`, but it does not connect them into a concrete lifecycle for auditing an evaluation pipeline, measuring retrieval independently from generation, classifying trace failures, validating evaluators against held-out labels, constructing synthetic coverage, and running disciplined human review. This plan closes those gaps through one thin `eval-pipeline-audit` coordinating skill and Tier-3 references owned by existing skills. It does not import the external repositories' branding, prose, scripts, integrations, or product structure.

Nexus-Hub also already defines `minimal`, `core`, and `full` profiles, six capability modules, and role bundles in `data/bundles.json`, but those definitions are metadata rather than a complete universal-installer contract. This plan makes them operational across the legacy Bash and PowerShell installers and the Python integration registry. The no-selector default remains `full`. Selection resolves a dependency-closed skill set; commands and agents install only when their declared skill dependencies are satisfied; hooks, rules, templates, settings, and other policy infrastructure remain present. Every path produces the same deterministic selection manifest and fails closed on invalid or ambiguous selectors.

Success is observable: the evaluation skills route correctly and produce documented local artifacts; RAG guidance defines Recall@k, Precision@k, MRR, NDCG, and multi-hop recall; profile/module/bundle selection gives byte-equivalent results across Bash, PowerShell, and registry installs; upgrades preserve the chosen selection; `full` remains compatible with the current install; generated catalogs and platform read contracts remain consistent; and the full local validation surface passes without a new dependency, credential, outbound service, or direct download-to-shell instruction.

## Goals First

**Target problem**: AI engineers using Nexus-Hub lack an end-to-end evaluation method, while all Nexus-Hub users must install the full skill catalog even though profiles, modules, and role bundles already describe smaller coherent capability sets.

**Target persona**: Primary: AI engineers building and evaluating RAG or LLM systems. Secondary: developers and platform administrators who need a focused, reproducible Nexus-Hub installation across Claude, Codex, Cursor, Gemini, Antigravity, Copilot, OpenCode, and inherited integrations.

**Approach**: Add evaluation depth through the existing three-tier skill architecture, then operationalize the existing bundle metadata through one documented selection contract implemented natively by each installer path and verified by shared fixtures.

**Definition of done**:

- Evaluation-pipeline auditing, RAG retrieval measurement, trace error analysis, evaluator calibration, synthetic data design, and human review have concrete local-first workflows and binary verification.
- `eval-pipeline-audit` is registered, trigger-tested, included in the AI-engineering module and AI-engineer role bundle, and distributed to every supported platform.
- `--profile`, `--modules`, and `--bundles` or their PowerShell equivalents resolve deterministically, preserve `full` as the default, close dependencies, and reject invalid selectors before copying files.
- Commands and agents never install with unsatisfied required-skill dependencies; policy infrastructure remains present under every selection.
- Bash, PowerShell, and Python integration paths emit equivalent selection manifests and installation results for the shared fixture matrix.
- Upgrades and repairs preserve the recorded selection unless the user explicitly changes it.
- No adopted capability adds an outbound call, API key, runtime dependency, hosted evaluation service, vendor MCP, or automatic upstream synchronization.
- All local skill, catalog, installer, integration, platform-contract, security, and documentation gates pass before final publication.

| Dynamic workflows | Unavailable in the current harness; use single-agent implementation. If available later, calibrate on one selector fixture before any fan-out. |
