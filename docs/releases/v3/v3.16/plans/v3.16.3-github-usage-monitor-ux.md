# Plan - GitHub Usage Monitor rename, first-run connect, and Claude-parity panel UX

**Project**: Nexus-Hub
**Version**: v3.16.3
**Slug**: github-usage-monitor-ux
**Filename**: v3.16.3-github-usage-monitor-ux.md
**Plan Type**: Feature (extension rename with migration, first-run authentication, panel UX parity, allowance derivation)
**Created**: 2026-08-08
**Seeded from**: maintainer UX report against the shipped `nexus-hub.github-usage-monitor` 0.1.0 build
**Goal**: Bring the GitHub monitor to visual and behavioral parity with the Claude and Codex usage monitors - renamed to "GitHub Usage Monitor", connecting itself on install, and presenting a single panel with three buttons, an expanding settings section, and teal usage bars that show real percentages.

## Overview

The GitHub monitor shipped in v3.15.8 and was reworked in v3.15.12. It works, but it does not look or behave like its two siblings. This plan closes five maintainer-reported gaps: the product name, the button row, the split settings panel, the manual connection step, and the absence of usage bars.

Four of the five are contained UI work that ports an existing in-repo pattern. The Claude monitor already solved the inline-settings problem: `extensions/claude-usage-monitor/src/settingsPanel.ts` exports `settingsStylesCss()`, `settingsSectionHtml()`, and `settingsScriptJs()` as three composable pieces that `dashboardPanel.ts` embeds behind a `toggleSettings()` gear, while the GitHub monitor opens a second `createWebviewPanel("githubUsageSettings", ...)`. Phase 4 replaces the second panel with the composition pattern rather than inventing one.

The fifth gap - usage bars - is not UI work, and it is the plan's main finding. Grounding against the maintainer's own billing page established that **the bar is missing for two independent reasons, and fixing only one produces a UI that is confidently wrong.**

**Defect one: there is no denominator, and GitHub does not serve one.** The extension calls only the enhanced-billing usage endpoints. Three endpoint families were checked field by field. `/settings/billing/usage` returns `date`, `product`, `sku`, `quantity`, `unitType`, `pricePerUnit`, `grossAmount`, `discountAmount`, `netAmount`, `repositoryName`. `/settings/billing/usage/summary` returns `usageItems` of `product`, `sku`, `unitType`, `pricePerUnit`, `grossQuantity`, `grossAmount`, `discountQuantity`, `discountAmount`, `netQuantity`, `netAmount`. The Budgets API returns `budget_amount`, `effective_budget`, `consumed_amount`, `prevent_further_usage`, and alerting fields. **No entitlement, quota, or included-quantity field exists in any of them.** The legacy product-specific endpoints that did return `included_minutes` were [closed down in September 2025](https://github.blog/changelog/2025-09-26-product-specific-billing-apis-are-closing-down/). The "2,000 min included" and "0.5 GB included" figures on `github.com/settings/billing` are composed by the web UI from a source the REST API does not expose.

**Defect two: the numerator is also wrong, and this is the more dangerous one.** For the same account and the same month, the extension reports **1,003 Actions minutes** while GitHub's own Included-usage panel reports **119.7 min used / 2,000 min included**. The difference is public-repository Actions usage, which is free and never draws down the included quota - the billing page states it directly: applicable discounts cover Actions usage in public repositories *and* included usage for Actions minutes and storage. The extension is summing `grossQuantity`, which measures total consumption; the allowance is drawn down by a strict subset of that. Supplying the correct 2,000-minute denominator without correcting the numerator would render **50%** where the truth is **6%**, an eight-fold overstatement presented with full visual confidence. That is materially worse than today's honest blank, and it is the specific failure this plan exists to avoid.

The maintainer's proposed workaround - treat an unknown allowance as zero and fill the bar to 100% at reduced opacity - is rejected on evidence. It is wrong on the numbers, and it is forbidden twice over by contracts this repository already carries: [`github-usage-data-contract.md`](../../v3.15/development/github-usage-data-contract.md) line 71 states that an unknown allowance is not zero and the UI must not render `0%` or `100%`, and [`github-usage-visual-contract.md`](../../v3.15/development/github-usage-visual-contract.md) line 39 requires unknown allowances to use the bordered absolute-usage treatment. Those rules were written deliberately and are kept.

A third state surfaced from the same evidence and is new to the data model. The billing page shows an Included-usage panel for **Actions, Git LFS, and Packages**, and none at all for **Copilot and Codespaces**. So "this product has no included allowance" is a real, knowable state, distinct from "the allowance is unknown". Copilot Free carries no AI-credit entitlement, which means the Copilot card should say so plainly rather than implying a missing measurement. The maintainer's instinct that some allowances are genuinely zero was correct for Copilot specifically; it was the generalization to all metrics that failed.

The same evidence also undermines the static-plan-table approach that a first draft of this plan proposed. The account's Git LFS shows **10 GB included** for both bandwidth and storage, which does not match the commonly-published free-tier figure. Whatever the cause - a data pack, a plan change, an unpublished adjustment - it demonstrates the data contract's line 75 in the wild: static plan tables are guidance, not a verified account denominator, and the extension has no way to detect when the table disagrees with the account. Phase 2 therefore demotes the table from a prefill source to an optional labeled hint, and makes explicit manual entry the primary path.

A fourth defect is folded into Phase 2. The billing page reports storage entitlement in **GB** while the usage API reports consumption in **GigabyteHours** - confirmed on the maintainer's page, which shows "0 GB used / 0.5 GB included" for Actions storage against the API's 63.92 GigabyteHours. These are different dimensions, not different scales, and `validMatchingAllowance()` at `providers/allowances.ts:42` correctly rejects the mismatch - which means a user who reads "0.5 GB" off the billing page and types it in gets silent refusal with no explanation. Storage needs either a documented conversion or an explicit unsupported state; guessing a conversion is not acceptable.

Phase 2's shape follows from all four. It attempts to reconstruct the drawdown numerator from documented data, gates the entire percentage feature on that reconstruction reconciling against GitHub's own displayed figure, and ships bars only where a denominator is genuinely verified. Where reconstruction fails, the honest absolute treatment stays and gains an explanation. `AllowanceInputs.api` remains unpopulated, because nothing in the current API can fill it truthfully.

The rename is a reversion, not a new decision. The extension was named "GitHub Usage Monitor" through v3.15.11 and renamed to "GitHub Billing Usage" in v3.15.12 Phase 3, a decision recorded in the visual contract line 48. Phase 1 reverses it and amends that line rather than silently contradicting it. The maintainer chose the deep rename, so command ids and configuration keys move too, which makes a one-time settings migration mandatory - a rename without it silently resets every threshold, color, owner, and allowance the user has set.

Scope note: this plan touches `extensions/github-usage-monitor/` plus four files outside it (`.github/workflows/github-usage-monitor.yml`, `.github/dependabot.yml`, `catalog/hooks/tests/test_installer_smoke.py`, and the two v3.15 contract documents). It changes no skill, no command, no `base-*.md` template, and no `data/` registry file, so the catalog stays at 270 skills and `check_base_template_parity.py` is unaffected. No new outbound call, dependency, credential, or third-party data processor is introduced; the plan-entitlement table is a static local constant.

## Phase 1: Rename to GitHub Usage Monitor, with settings migration

**Goal**: Restore the "GitHub Usage Monitor" name across every surface, including command ids and configuration keys, without destroying any setting a user has already configured.

**Prerequisites**: None.

**Stability Gate**: `package.json` `displayName` is `GitHub Usage Monitor`; no `github-usage.` command id and no `githubUsage.` config key remains in `src/`; a fixture holding every old key migrates to new keys on first activation and does not re-run on second activation; the status bar, both webview titles, and all command titles read "GitHub Usage Monitor"; `npm run compile` and `npm test` pass; `.github/workflows/github-usage-monitor.yml` is green.

**Recommended model tier**: Strong. **Recommended effort**: Medium.
**Rationale**: Mechanically broad but conceptually simple. The one part that carries real risk is the migration, because getting it wrong silently wipes user configuration - which is why the gate above tests it against a full-key fixture rather than a sample.

### Sub-tasks

#### 1.1 - Identifier and string rename

**Objective**: Move every identifier and user-visible string to the new name in one pass.

**Prompt**:
> In `extensions/github-usage-monitor/`, rename the extension from "GitHub Billing Usage" to "GitHub Usage Monitor".
>
> In `package.json`: set `displayName` to `GitHub Usage Monitor`; rewrite `description` to describe a usage monitor rather than a billing reader while keeping it accurate about what it reads (Actions minutes and storage, plus Copilot billing, for one configured billing owner); bump `version` to `0.2.0`. Rename every command id from `github-usage.<verb>` to `githubUsageMonitor.<verb>`, and set each `title` and `category` to use "GitHub Usage Monitor". Rename the configuration section `title` and every property key from `githubUsage.*` to `githubUsageMonitor.*`, preserving each property's type, default, enum, and description unchanged. Rename the view container id `githubUsageWarning` to `githubUsageMonitorWarning`, its `title`, the view id, and the `when` context key `githubUsage.warningActive` to `githubUsageMonitor.warningActive`.
>
> In `src/`: update every `vscode.commands.registerCommand` and `executeCommand` call, the `getConfiguration("githubUsage")` lookups, the `setContext` call for the warning key, the webview panel ids (`githubUsageDashboard`, `githubUsageSettings`), the `StatusBarManager` `item.name`, and every heading, title, and label string. The `dashboardPanel.ts` webview posts bare verbs and re-prefixes them at the receiver, so update the prefix in one place rather than every button.
>
> Do NOT change the extension id `nexus-hub.github-usage-monitor`, the publisher, the icon contribution id `github-icon`, the icon assets, or `GITHUB_BAR_FILL`. The folder name is already correct.
>
> Outside the extension, update `.github/workflows/github-usage-monitor.yml`, `.github/dependabot.yml`, and `catalog/hooks/tests/test_installer_smoke.py` for any renamed path or string. Do NOT rewrite any file under `docs/archive/v3/v3.15/development/history/`; those are immutable records of what was true when written.

#### 1.2 - One-time settings migration

**Objective**: Carry every user-set value from the old configuration keys to the new ones, exactly once.

**Prompt**:
> Add `src/migration.ts` exporting `migrateSettings(context, config)` and call it from `activate()` before any other initialization.
>
> Behavior: guard the whole migration on a `globalState` flag (`githubUsageMonitor.settingsMigrated.v0_2_0`); if set, return immediately. Otherwise, for each old key `githubUsage.<name>`, inspect it with `config.inspect()` and copy the value to `githubUsageMonitor.<name>` ONLY when the user actually set it - that is, when `globalValue` or `workspaceValue` is defined. Never copy a `defaultValue`, because writing defaults explicitly would pin the user to today's defaults forever. Preserve the scope: a workspace-set value migrates to workspace scope, a global one to global. Set the flag after a successful pass.
>
> Do not delete the old keys in this release. A user who downgrades should still find their settings, and a deletion that races a failed write loses data outright. Record the deletion as a v3.17.0 follow-up instead.
>
> Migrate the SecretStorage token key the same way if its name changes, reading the old key and re-writing under the new one before clearing the old. If the token cannot be re-written, leave the old one in place and log one line - a lost token forces a full re-authentication, which is a worse outcome than a stale key name.
>
> Handle a partial failure honestly: if any single key fails to write, do not set the completion flag, log which key failed, and let the next activation retry. A half-migrated state that claims completion is the failure mode to avoid.

#### 1.3 - Contract amendment

**Objective**: Record the reversion in the contract that documented the original rename.

**Prompt**:
> Amend `docs/v3/v3.15/development/github-usage-visual-contract.md` line 48 and `docs/v3/v3.15/development/github-usage-data-contract.md` line 10. Both currently state that the extension is titled "GitHub Billing Usage", renamed from "GitHub Usage Monitor" in v3.15.12 Phase 3.
>
> Rewrite both as a dated correction rather than a silent overwrite: state that v3.16.3 reverted the name to "GitHub Usage Monitor" for consistency with the Claude, Codex, and Cursor usage monitors, that the extension id `nexus-hub.github-usage-monitor` was never changed in either direction, and that command ids and configuration keys moved to the `githubUsageMonitor.*` prefix in v3.16.3 with a one-time migration. Keeping the v3.15.12 decision visible alongside its reversal is the point - a reader of the older plan must be able to see what happened and why.

#### 1.4 - Tests

**Objective**: Prove the rename is complete and the migration is safe.

**Prompt**:
> Add tests covering: no `github-usage.` or `githubUsage.` string survives in `src/` or in the `contributes` block of `package.json` (a repository-grep assertion, so an incomplete rename fails loudly rather than degrading at runtime); every command id declared in `package.json` is registered in `extension.ts` and vice versa; migration copies a full fixture of user-set old keys to new keys at the correct scope; migration ignores keys left at their default; migration is idempotent across two activations; migration does not set its completion flag when a write fails, and retries on the next activation.

## Phase 2: Allowance and drawdown truth

**Goal**: Determine whether a correct percentage is derivable at all from documented GitHub data, ship bars only where it is, and explain the absence everywhere else.

**Prerequisites**: Phase 1 (new config keys exist).

**Stability Gate**: A probe document records, with fetched URLs and dates, whether an entitlement field exists and whether the drawdown numerator reconciles; a percentage renders for a metric only when both a verified denominator and a reconciled numerator exist; the reconciliation is validated against GitHub's own displayed figure for a real account and agrees within the stated tolerance, or the percentage feature stays off for that metric; `allowanceSource` is never `"api"` unless an API entitlement was found in 2.1; the three states (verified, no-allowance-exists, unknown) each render distinctly and none renders `0%` or `100%` for a null allowance; storage either applies a documented conversion or reports an explicit unsupported state; `npm test` passes.

**Recommended model tier**: Frontier. **Recommended effort**: Max.
**Rationale**: Raised from High after grounding found a second, independent defect. This phase decides whether the extension is allowed to show a number at all, and the failure mode is not a blank UI but a confident wrong one - an eight-fold overstatement was demonstrated on real data. Every remaining shortcut here (inferring a denominator, guessing a unit conversion, dividing by the wrong numerator) produces exactly that.

**Cut line**: sub-tasks 2.1, 2.2, and 2.5 are mandatory. If 2.3's reconciliation fails, ship 2.5's explained-absence states and stop; percentages are dropped from this release rather than approximated. That is an acceptable outcome for this phase and must not be treated as a phase failure.

### Sub-tasks

#### 2.1 - Re-verify both findings before building on either

**Objective**: Confirm at implementation time that no endpoint serves an entitlement, and establish exactly which quantity GitHub counts against an allowance.

**Prompt**:
> Before writing any code, re-verify the two findings this phase rests on. GitHub's billing API has changed twice in eighteen months, and one of these findings was itself corrected mid-planning after being checked against a real account.
>
> First, the entitlement question. Fetch the current `https://docs.github.com/en/rest/billing/usage`, the billing REST index, and the Budgets API reference. Confirm field by field that no documented response carries an included allowance, entitlement, quota, or remaining balance. As of 2026-08-08 the checked field sets were: `/usage` returning `date`, `product`, `sku`, `quantity`, `unitType`, `pricePerUnit`, `grossAmount`, `discountAmount`, `netAmount`, `repositoryName`; `/usage/summary` returning `usageItems` of `product`, `sku`, `unitType`, `pricePerUnit`, `grossQuantity`, `grossAmount`, `discountQuantity`, `discountAmount`, `netQuantity`, `netAmount`; and Budgets returning `budget_amount`, `effective_budget`, `consumed_amount`, `prevent_further_usage`, and alerting fields. Note `consumed_amount` is spend against a user-defined budget, NOT usage against an included allowance - do not conflate them.
>
> Second, the numerator question, which is the one that was missed. Establish from GitHub's Actions billing documentation exactly which usage draws down included minutes: confirm that public-repository Actions usage is free and excluded, and establish whether per-runner-OS multipliers (Linux, Windows, macOS) apply to the minutes counted against the allowance. The SKU strings on usage line items encode the runner type, so a multiplier, if it applies, is derivable.
>
> Record both results in `docs/v3/v3.16/development/github-entitlement-probe.md` with fetched URLs, dates, and exact fields observed, including the negative results - a future contributor must be able to see that the Budgets API was checked and rejected, rather than re-checking it.
>
> If an entitlement field DOES now exist, stop and escalate: `AllowanceInputs.api` was built for exactly that, and sub-task 2.2 becomes unnecessary while 2.3 becomes more important, not less. A real denominator does not fix a wrong numerator.

#### 2.2 - Allowance entry, with the plan table demoted to a hint

**Objective**: Let the user supply a denominator explicitly, without the extension asserting one it cannot verify.

**Prompt**:
> Make explicit manual entry the primary path for allowances. The existing `githubUsageMonitor.allowances.*` settings and the `applyAllowances(..., { manual })` path already support this; the gap is discoverability and labeling, not mechanism.
>
> In the settings section, present one allowance field per metric, each labeled with the exact unit the API reports for that metric so the user knows what to type, and each carrying a short line pointing at where the figure appears on `github.com/settings/billing`. Write accepted values to the existing settings so `allowanceSource` becomes `"manual"`.
>
> A static plan-entitlement table MAY ship as an optional labeled hint beside the field ("GitHub Free publishes 2,000 minutes"), but it MUST NOT prefill the input, MUST NOT be written automatically, and MUST NOT populate `AllowanceInputs.api`. The reason is evidential, not theoretical: on the maintainer's own Free account the billing page shows 10 GB included Git LFS bandwidth and 10 GB storage, which does not match the commonly-published free-tier figure, and the extension has no way to detect that disagreement. This is the data contract's line 75 - static plan tables are guidance, not a verified account denominator - observed in the wild. Quote that line in a header comment so a future contributor does not promote the hint to a source.
>
> If the table is shipped, source it from GitHub's "Product usage included with each plan" documentation with the URL and a verification date in the header, resolve the account plan from the authenticated `GET /user` response's `plan.name`, and return an explicit unknown for any unrecognized plan. Never fall back to the Free tier.

#### 2.3 - Reconstruct the drawdown numerator, and gate percentages on it reconciling

**Objective**: Establish whether the quantity GitHub counts against an allowance can be rebuilt from documented API data, and refuse to show a percentage if it cannot.

**Prompt**:
> This is the sub-task that decides whether percentages ship at all. On the maintainer's account the extension reports 1,003 Actions minutes for the same month GitHub's Included-usage panel reports 119.7 min used against 2,000 included. Dividing the extension's number by the allowance yields 50% where the truth is 6%. Adding a denominator without resolving this ships that error.
>
> Attempt reconstruction using only documented data. The plain `/settings/billing/usage` endpoint carries `repositoryName` on each line item, and repository visibility is available from `GET /repos/{owner}/{repo}`. Filter Actions line items to private repositories, apply any runner-OS multiplier established in 2.1, and sum. State the cost honestly in the implementation notes: this adds one repository lookup per distinct repository in the usage window, which must be cached, batched where possible, and bounded so a user with many repositories does not trigger a rate-limit storm. If the cost is unacceptable, say so and take the cut line rather than shipping an unbounded fan-out.
>
> Then reconcile. Compare the reconstructed figure against the value GitHub displays on the billing page for the same account and period. Record the comparison in the probe document with both numbers. Define the tolerance before running the comparison, not after, and justify it.
>
> The gate is binary and must be enforced in code, not just in judgment. Percentages render for a metric ONLY when reconstruction reconciles for that metric. If Actions minutes reconciles and storage does not, Actions minutes gets a bar and storage does not. If nothing reconciles, no metric gets a bar in this release and the phase still succeeds - the cut line above covers this explicitly.
>
> Do not tune the reconstruction until it matches. If the first attempt is off, diagnose why and record the finding; a formula reverse-fitted to one account's numbers will silently break on the next account, and this plan has already corrected one confident wrong number.

#### 2.4 - Storage unit reconciliation

**Objective**: Stop the silent refusal when a user enters a storage allowance in the unit GitHub's own billing page shows.

**Prompt**:
> The billing page reports storage entitlement in GB while the usage API reports consumption in GigabyteHours - confirmed on the maintainer's account, which shows "0 GB used / 0.5 GB included" for Actions storage against the API's 63.92 GigabyteHours. `validMatchingAllowance()` at `src/providers/allowances.ts:42` compares units case-insensitively and returns null on mismatch, so a user entering `0.5` from the billing page currently gets no bar and no explanation.
>
> Determine from GitHub's documentation whether a defined conversion exists between the entitlement unit and the reported consumption unit for a billing period. If a documented conversion exists, implement it explicitly with the source cited inline and the derivation visible in the UI. If none exists - the likely outcome, since a GB ceiling and a GigabyteHours integral measure different quantities - do NOT invent one.
>
> In the no-conversion case, give storage an explicit unsupported-denominator state: keep the bordered absolute treatment and add one sentence explaining that GitHub reports storage consumption in GigabyteHours while the entitlement is expressed in GB, so a percentage cannot be derived. An explained absence is a good UI; an unexplained blank is the bug being fixed.
>
> Keep the unit-matching guard intact. It is doing exactly its job; the defect is the missing explanation, not the check.

#### 2.5 - Three allowance states, each rendered distinctly

**Objective**: Stop collapsing "no allowance exists" into "allowance unknown", and explain both.

**Prompt**:
> The data model currently has two allowance states, present and null, and the UI renders null as an unexplained absolute box. The billing page shows there are three states: GitHub displays an Included-usage panel for Actions, Git LFS, and Packages, and none at all for Copilot and Codespaces.
>
> Add a third state to the metric type distinguishing **verified** (a denominator exists and a percentage is derivable), **none** (this product has no included allowance for this account - Copilot Free carries no AI-credit entitlement, so there is nothing to draw a bar against), and **unknown** (an allowance may exist but is not established).
>
> Render each distinctly. Verified gets the teal bar. None gets the absolute treatment plus a short line stating that the plan includes no allowance for this product, so the figure is absolute consumption - accurate, and it closes the maintainer's original question about Copilot showing 0 with no context. Unknown gets the absolute treatment plus a line explaining what would make a percentage available, linking to the allowance field from 2.2.
>
> None of the three may render `0%` or `100%` for a null allowance. That is the data contract's line 71 and the visual contract's line 39, and it is the specific rule that rejected the original zero-allowance proposal.

#### 2.6 - Tests

**Prompt**:
> Cover: `allowanceSource` is never `"api"` on any path unless 2.1 found an API entitlement; a verified metric renders a bar and a correct percentage; a `none` metric renders the no-allowance explanation and no bar; an `unknown` metric renders the unknown explanation and no bar; no state renders `0%` or `100%` for a null allowance (assert against rendered HTML, since this is a contract rule); the storage unsupported state renders its explanation; a mismatched unit still fails the guard; a plan-table hint never writes a value automatically.
>
> Add a reconciliation regression test using the maintainer's observed figures as a fixture: gross 1,003 minutes, allowance-drawdown 119.7, allowance 2,000. Assert that the rendered percentage is the drawdown-based figure and NOT the gross-based 50%. This fixture is the guard against the exact defect this phase exists to fix, and it must fail loudly if a future change reverts to dividing gross by allowance.
>
> Add fixtures for an account whose plan is unresolvable, and for a metric with no included allowance.

## Phase 3: First-run connection

**Goal**: A freshly installed extension connects itself, and a user who declines is left in a clear state and never asked again.

**Prerequisites**: Phase 1 (renamed command ids).

**Stability Gate**: A first activation with an existing VS Code GitHub session connects silently with no prompt; a first activation with no session opens the sign-in flow exactly once; dismissing it records a durable decline and produces no modal on any later activation; the declined state is visible in both the status bar and the panel with a working Connect affordance; a connected user never sees the flow; `npm test` passes.

**Recommended model tier**: Strong. **Recommended effort**: Medium.
**Rationale**: The logic is small but the failure mode is a modal dialog on every VS Code start, which is the most user-hostile bug this extension could ship.

### Sub-tasks

#### 3.1 - First-run flow

**Prompt**:
> Add a first-run connection sequence to `activate()`, running after migration and before the first fetch.
>
> Step one, silent: call the existing `getSession` wrapper with `{ createIfNone: false, silent: true }`. If a session exists, bind it and proceed with no user-visible interaction. Many users will already be signed in to GitHub in VS Code and must never be prompted.
>
> Step two, one modal: if no session exists AND no stored token exists AND no prior decline is recorded, call `getSession` with `createIfNone: true` to open the real VS Code sign-in flow. Do this exactly once.
>
> Step three, durable decline: if the user dismisses or the flow fails, write a `globalState` decline flag and never open the flow again automatically. Explicit user action - the panel's Connect control or the command palette - must still work and must clear the flag on success.
>
> Reuse the existing `logInToMonitor` path rather than duplicating it, so scope escalation and owner resolution behave identically whether the flow was automatic or user-initiated. Guard the whole sequence behind the same `autoFetch` respect the rest of the extension honors, and never block activation on it - the sequence is asynchronous and a slow or hung auth call must not delay VS Code startup.

#### 3.2 - Unconnected presentation

**Prompt**:
> Give the extension an honest unconnected state. ## Phase 7: Copilot AI-credit allowance for organization billing

**Goal**: An organization owner whose Copilot seats are billed through a Business or Enterprise subscription sees a real AI-credit denominator and percentage, derived from GitHub's own published per-seat figure and the organization's assigned seat count, with provenance shown and an override available.

**Prerequisites**: Phase 2 (allowance states, provenance, manual override) and the owner-plan lookup shipped 2026-08-11 (`fetchOwnerPlanName`).

**Stability Gate**: An organization on Copilot Business renders an AI-credit meter whose denominator equals assigned seats multiplied by the published per-seat figure for the current date; the value carries `plan-table` provenance and never `api`; a date after the promotional window uses the standard figure without a code change; an organization whose seat count or plan type cannot be read renders `unknown` rather than a guess; a personal Free account still renders `none`; `npm test` passes.

**Recommended model tier**: Frontier. **Recommended effort**: Max.
**Rationale**: This ships a denominator, which is the single class of value this extension has already been wrong about once. The figure is time-boxed and expires three weeks after this plan was written, so a naive implementation is guaranteed to become wrong rather than merely risk it.

**Status, 2026-08-11**: sub-tasks 7.1, 7.2, and the wiring half of 7.3 were implemented ahead of this plan, at the maintainer's request, after the figures below were verified. Still OUTSTANDING: the provenance DISPLAY in 7.3 (`describeAllowanceProvenance` exists but is rendered nowhere in the panel, for Actions as well as Copilot - a pre-existing gap, so a composed denominator currently shows without its working), and all of 7.4.

### Findings that motivate this phase

Verified 2026-08-11 against GitHub's own documentation, and cross-checked against a live organization (SupiraMedical: 7 billable licenses, 21,000 included credits shown on its AI usage page).

- Included AI credits are **pooled at the billing entity**, computed as assigned licenses multiplied by a per-user figure. GitHub's own worked example: 100 Copilot Business users share a pool of 190,000 credits.
- Published per-user figures: Copilot Business **1,900**, Copilot Enterprise **3,900**.
- **Existing customers receive a promotional figure through 2026-09-01**: Business **3,000**, Enterprise **7,000**. 7 x 3,000 = 21,000, which is exactly what the live organization shows, so the derivation is confirmed rather than inferred.
- This does NOT contradict `docs/v3/v3.16/development/github-entitlement-probe.md`. That probe's finding stands: no endpoint serves an entitlement. What changed is that a published per-seat figure plus a readable seat count now compose into one, which makes this a `plan-table` value with all the caveats that label already carries.

### Sub-tasks

#### 7.1 - Seat and plan-type lookup

**Prompt**:
> Read the organization's Copilot subscription from `GET /orgs/{org}/copilot/billing`, taking the plan type (`business` or `enterprise`) and the assigned seat count from `seat_breakdown`. Return null for every failure - a 404 for an organization with no Copilot subscription, a 403 for a caller who is not an owner, an unrecognized plan type, or a seat count that is absent or not a positive integer.
>
> Match the seat figure to what GitHub bills against. The live organization showed 7 billable Copilot licenses inside a 9-license Team subscription, and 7 is the multiplier that reproduces its 21,000 - so the Team seat count is the wrong number and must not be substituted when the Copilot figure is unavailable.

#### 7.2 - Date-aware per-seat table

**Prompt**:
> Add a per-seat AI-credit table to `planEntitlements.ts` keyed by Copilot plan type, carrying BOTH the standard figure and the promotional figure with its end date, sourced and dated in a comment exactly as `PLAN_ENTITLEMENTS` is.
>
> The promotional window ends 2026-09-01. Resolve the figure against the snapshot's billing period rather than against `Date.now()`, so a historical period keeps rendering the figure that applied to it and the transition needs no code change. Do not encode a single number: an implementation that hardcodes 3,000 becomes wrong on 2026-09-01, and one that hardcodes 1,900 is wrong on the day it ships.
>
> Return null for an unrecognized plan type. Never fall back to the Business figure, for the same reason `resolvePlan` never falls back to Free.

#### 7.3 - Wiring and provenance

**Prompt**:
> Feed the derived allowance into the existing `planTable` input in `enrich.ts` under `copilot-ai-credits`, so it flows through `applyMetricAllowance` and inherits manual-override precedence unchanged. Remove `copilot-ai-credits` from `PRODUCTS_WITHOUT_ALLOWANCE` only where a derivation succeeded - a Copilot Free personal account must still report `none`, and an organization whose figures could not be read must still report `unknown`.
>
> State the derivation in the provenance line, including the seat count and per-seat figure used, so a user seeing 21,000 can check it against their own billing page. A composed number needs MORE provenance than a looked-up one, not less.

#### 7.4 - Personal account billed elsewhere

**Prompt**:
> When the owner is a user, the account belongs to at least one organization, and no personal AI-credit allowance is established, state that a Copilot seat provided by an organization is billed to that organization and offer to switch the billing owner. Phrase it conditionally - the extension cannot read which organization provides a seat - and never present it as a failure. This closes the confusion reported 2026-08-11, where a personal billing page showed no AI credits tab at all while the seat was actively drawing credits.

#### 7.5 - Tests

**Prompt**:
> Cover: 7 seats on Business inside the promotional window yields exactly 21,000; the same input after 2026-09-01 yields 13,300; Enterprise yields 7,000 and 3,900 per seat on the same two dates; an unreadable seat count yields `unknown` and no percentage; an unrecognized plan type yields null rather than the Business figure; a manual allowance still overrides the derived one; a Copilot Free personal account still reports `none`. Pin the boundary date in both directions - the day before and the day of - because a promotional expiry that silently keeps the old figure is the exact failure this phase exists to prevent.
