# Plan - Platform Defaults Config

**Project**: Nexus-Hub
**Version**: v3.16.0
**Slug**: platform-defaults-config
**Plan Type**: Feature (enhancement)
**Created**: 2026-07-28
**Goal**: Establish `configs/platform-defaults.json` as the single place a maintainer edits a per-platform install default, so one edit propagates to every derived artifact on the next install, with a guard that fails the build when any artifact drifts from the declared source, and with every non-Claude lever seeded only after it is verified against that platform's official documentation.

## Overview

Nexus-Hub ships install-time behavioural defaults, but only for one platform, and it declares them in two places. `catalog/hooks/settings.json` carries Claude's `effortLevel`, `model`, and `env.CLAUDE_CODE_EFFORT_LEVEL`, and `scripts/lib/integrations/claude.py` hardcodes the same three values again for the `nexus-hub init` project stub. The v3.15.5 effort-level change had to edit four declarations across those two files and correct four documentation surfaces that restated the value as prose. Every other registered integration declares nothing: the integration `config` dicts hold paths and capabilities (`global_dir`, `skills_subdir`, `hooks_supported`) and no runtime behaviour. So the maintainer's actual complaint is precise: there is no defaults layer, and the one platform that has defaults keeps them in the artifact that ships rather than in a source that generates it.

This release adds that layer. `configs/platform-defaults.json` becomes the authoritative declaration, keyed by the same platform ids the integration registry uses, and every consuming artifact is derived from it rather than maintained beside it. A repo-internal script generates the core keys of `catalog/hooks/settings.json` surgically (preserving the large `hooks` block it also carries) and offers a `--check` mode that fails when an artifact disagrees with the source; the `nexus-hub init` stub reads the defaults directly at runtime, which is free in Python and needs no `jq`. The installers are deliberately NOT touched: they keep reading `catalog/hooks/settings.json` exactly as they do today, so this release introduces no new `jq` dependency and stays independent of the `jq` removal already scoped by the v3.17.0 agent-autonomy-toggle plan.

The riskiest part is breadth, not mechanism. The maintainer chose to research every platform's lever rather than ship a Claude-shaped hole, which means web-verifying a documented default-setting surface for each of the sixteen registered integrations (Aider, Antigravity 1.0, Antigravity 2.0, Claude, Codex, Copilot, Cursor, Gemini, Gemini CLI, Hermes, Kimi, Nexus-AI, OpenClaw, OpenCode, Qwen, Windsurf). The failure mode is inventing a setting a platform does not support, which Nexus-Hub has done before: the `.kimi/agent.yaml` companion was fabricated and had to be dropped in v3.15.0. So verification is a hard gate rather than a best effort. A lever is seeded only when a specific official document names it, with the URL and verification date recorded; everything else is classified UNVERIFIED and explicitly left out of the defaults file. Success is that changing one value in one file, running one command, and reinstalling changes that default everywhere it legitimately applies, and that no default exists for a platform that cannot honour it.

## Phase 1: Defaults contract, generator, and guard

**Goal**: Make `configs/platform-defaults.json` the single place Claude's install defaults are declared, with every derived artifact generated or read from it and a guard that fails the build on drift.
**Prerequisites**: None (foundation phase).
**Stability Gate**: Editing `effortLevel` in `configs/platform-defaults.json` and running the sync script updates `catalog/hooks/settings.json`'s core keys while leaving its `hooks` block byte-identical; the `nexus-hub init` stub produces the same value with no hardcoded literal; `--check` exits non-zero when any artifact is edited away from the source; the check runs in `make validate` and CI; `make validate` and `make test` pass.
**Recommended model**: Strong reasoning tier, high effort. Rationale: this is the contract and the surgical generator every later phase builds on, and the generator writes a file that also carries the hook registrations, so a naive full rewrite would silently destroy them.

### Sub-tasks

#### 1.1 - Define the schema and seed Claude's real values

**Objective**: Fix the shape of the defaults file and seed it from what ships today.

**Prompt**:
> Create `configs/platform-defaults.json` as the authoritative declaration of per-platform install-time behavioural defaults. Key the top-level `platforms` object by the SAME platform ids the integration registry uses (`scripts/lib/integrations/__init__.py::_register_builtins`), so a reader can map an entry to its integration without a translation table. Per platform, carry the settings that platform actually honours plus provenance: the official-doc `source_url` that documents the lever and a `verified` date. Include a `schema_version` and a `meta` block. Seed ONLY `claude`, with the values that ship today (`effortLevel: medium`, `model: opus`, and `env.CLAUDE_CODE_EFFORT_LEVEL: medium`), taken from `catalog/hooks/settings.json` rather than retyped, and record the Claude settings-file documentation URL as its source. Do NOT add any other platform in this phase; Phase 2 verifies the rest. Document the schema in `configs/README.md` (create it if absent), including the rule that a platform appears in this file ONLY when an official document names the lever, and the reminder that `env` values may outrank their scalar counterpart on some platforms so both must be declared together. Acceptance: the file parses, carries exactly one platform, documents the schema, and its Claude values match the shipped template exactly.

---

#### 1.2 - Surgical generator plus a drift check

**Objective**: Derive the shipped artifacts from the source, without destroying what else lives in them.

**Prompt**:
> Add `scripts/sync_platform_defaults.py` (stdlib only, no outbound call) with two modes. `--check` compares every derived artifact against `configs/platform-defaults.json` and exits non-zero on any disagreement, naming the artifact, the key, the declared value, and the found value. `--apply` rewrites the derived artifacts from the source. **The critical constraint: `catalog/hooks/settings.json` also carries the entire `hooks` registration block (SessionStart / PreToolUse / PostToolUse / Stop chains), so the generator MUST update only the declared core keys in place and leave every other key byte-identical.** Do not serialize a fresh object over the file. Load it, set only the declared keys (including nested `env` keys), and write it back preserving key order and the existing 2-space indentation; verify round-trip stability by asserting that an `--apply` run with no source change produces a byte-identical file. Print a clear summary of what changed. Acceptance: `--apply` is idempotent and preserves the hooks block byte-for-byte; `--check` is green on a synced tree and red after any single derived key is edited away from the source.

---

#### 1.3 - Make the project stub read the source directly

**Objective**: Remove the second hardcoded declaration entirely.

**Prompt**:
> Change `scripts/lib/integrations/claude.py` so `_PROJECT_SETTINGS_STUB`'s `effortLevel`, `model`, and `env.CLAUDE_CODE_EFFORT_LEVEL` are read from `configs/platform-defaults.json` at runtime instead of being hardcoded literals. This is Python, so reading JSON is free and introduces no `jq` dependency. Degrade safely: if the defaults file is missing or unreadable (an installed tree may not carry `configs/`), fall back to the values currently hardcoded and log a one-line note rather than raising, so `nexus-hub init` never fails because a source file is absent. Keep the stub's explanatory `_comment` accurate: it should now say the values come from the defaults file and point at it. Update `tests/installer/test_init_subcommand.py` so it asserts the stub matches the DECLARED default rather than a hardcoded string, which makes it a real consistency test instead of a second place to update. Acceptance: changing the declared effort in `configs/platform-defaults.json` changes what `nexus-hub init` writes, with no edit to `claude.py`; the fallback path is tested with the defaults file absent.

---

#### 1.4 - Wire the check into validation and CI

**Objective**: Make drift a build failure.

**Prompt**:
> Wire `python scripts/sync_platform_defaults.py --check` into the `make validate` target and into the CI `validate` job, placed near the other repo-internal structural guards. Add `sync_platform_defaults.py` to the `DEV_ONLY_SCRIPTS` allowlist in `catalog/hooks/tests/test_installer_smoke.py` with a one-line justification, following the three existing precedents (`check_base_template_parity.py`, `verify_platform_contracts.py`, `check_platform_contract_freshness.py`): it is a repo-internal guard with no meaning on an end-user install, so it needs NO installer copy step and both installers stay untouched. Confirm that reading is correct before finalizing, since installer changes are ask-first and this is the decision that avoids them. Acceptance: `make validate` and CI run the check; `test_installers_copy_every_scripts_dir_py_file` passes without either installer being edited.

#### 1.5 - Testing and Stabilization

**Objective**: Prove one-edit propagation and the guard. Iterate until stable before Phase 2.

**Prompt**:

## Phase 2: Per-platform lever research and verification

**Goal**: Establish, for each of the sixteen registered integrations, whether an official document names a settable install-time default lever, and record the answer with evidence.
**Prerequisites**: Phase 1 (the schema defines what a recorded lever looks like).
**Stability Gate**: Every one of the sixteen integrations has a classification (VERIFIED with a specific official-doc URL, a quoted or paraphrased statement of the lever, and a verification date; or UNVERIFIED with the reason) recorded in a policy doc; no lever is recorded on inference, a community post, or an analogy to another platform; a test asserts every VERIFIED entry carries a URL and a date.
**Recommended model**: Strong reasoning tier, high effort. Rationale: the entire phase is a judgement about source authority, and the failure mode (recording a plausible-sounding lever that a platform does not support) ships a broken default to every user of that platform. This is the `.kimi/agent.yaml` mistake's exact shape.

**Prompt**:

## Phase 3: Wire the verified levers into the defaults and their consumers

**Goal**: Declare every VERIFIED lever in the defaults file and make its platform's real write surface consume it, skipping every UNVERIFIED platform with a recorded note.
**Prerequisites**: Phase 1 (the mechanism) and Phase 2 (the verified list).
**Stability Gate**: Every VERIFIED lever is declared in `configs/platform-defaults.json` and reaches its platform's config on install; every UNVERIFIED platform is absent from the defaults file and its absence is explained; the `--check` guard covers the widened set; no platform receives a setting it cannot honour; `make validate` and `make test` pass.
**Recommended model**: Strong reasoning tier, high effort. Rationale: this phase writes install-time defaults across platforms, so the blast radius is every user's install, and each platform's write surface has its own format (JSON, TOML, YAML, instruction-file text) with its own escaping and merge semantics.

### Sub-tasks

#### 3.1 - Declare the verified levers

**Objective**: Widen the defaults file to the verified set only.

**Prompt**:
> Extend `configs/platform-defaults.json` with one entry per VERIFIED platform from the Phase 2 contract, carrying the documented lever keys, the values Nexus-Hub should ship as defaults, and the `source_url` plus `verified` date copied from the contract. #### 3.2 - Consume the levers per platform

**Objective**: Make each declared default actually reach the platform.

**Prompt**:

Acceptance: each VERIFIED platform's default reaches its config in a throwaway-HOME install, or is explicitly recorded as declared-but-not-writable with a reason.

## Notes

- **Sequencing against the jq problem**: this plan deliberately does NOT have the installers read the new file, so it adds no `jq` dependency and is independent of the `jq` removal scoped by the v3.17.0 agent-autonomy-toggle plan. The two can land in either order. If v3.17.0 lands first and removes `jq`, a later cycle may simplify Phase 1's generator into a direct installer read, but that is an optimization and not a prerequisite.
- **Why generation rather than a runtime read**: `catalog/hooks/settings.json` is simultaneously a declared default and the artifact copied to a user's `~/.claude/settings.json`, which is exactly why the value got duplicated into `claude.py`. Generating the template from a separate source resolves the dual role without changing what the installers consume.
- **The hooks block is the hazard in Phase 1**: `catalog/hooks/settings.json` carries the full hook registration chains. The generator must update declared keys in place and is required to prove byte-identical preservation of everything else.
- **Scope boundary against the read-contract**: `docs/policy/platform-read-contracts.md` owns file-discovery paths and capabilities. This plan's lever contract owns behavioural defaults only. Neither should grow into the other.
- **Provisional decisions to confirm at implementation time**: the exact filename `configs/platform-defaults.json`, the script name `scripts/sync_platform_defaults.py`, and the target version `v3.16.0`. The slot was RE-SLOTTED during the v3.15.5 release: this plan was first drafted as `v3.15.7`, but a parallel session had already claimed that slot with `v3.15.7-adoption-raptor-loop-hunt.md`, so the two briefly coexisted in git before this plan moved to `v3.16.0`, the next free slot (`v3.17.0` through `v3.18.0` are taken by the autonomy-toggle, rtk-and-meterless, optmem, and jcodemunch plans). A `v3.18.1` double claim between the interface-craft-skills and optmem plans was resolved on 2026-07-28 by moving interface-craft-skills, plan and comparison together, to `v3.19.1`, so every v3.16 stamp is now unique and this plan's `v3.16.0` is unaffected.
