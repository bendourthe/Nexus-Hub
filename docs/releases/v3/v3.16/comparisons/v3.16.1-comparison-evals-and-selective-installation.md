## Step 1.5: Source Security Scan (Pre-Ingest)

### hamelsmu/evals-skills

**Verdict: CLEAR.**

The default-branch archive contained 14 text files and seven skill directories. It contained no executable scripts, binary files, package manifests, tests, CI workflows, or install hooks. Pattern scans found no prompt-injection payload, hidden Unicode control characters, obfuscated content, destructive command, credential capture, or outbound execution path.

The repository is documentation-only methodology. Its examples discuss evaluation systems and optional observability integrations, but the repository itself does not execute those integrations.

### fcakyon/claude-codex-settings

**Verdict: PROCEED-WITH-CAUTION.**

The default-branch archive contained 1,205 files: 1,203 text files and two WebP images. It includes executable shell, Python, and JavaScript tooling; an Astro site; plugin manifests; hook implementations; workflow files; vendor integrations; and MCP configuration examples. No package-lifecycle install hook or malicious prompt override was found.

The material caution is executable bootstrap guidance in [the LiveKit skill](https://github.com/fcakyon/claude-codex-settings/blob/main/plugins/livekit-skills/skills/livekit-skills/SKILL.md), which recommends piping a downloaded script directly to a shell. Nexus-Hub must not reproduce that pattern. Other high-signal scanner matches were defensive deny rules or fenced documentation examples rather than active malicious behavior.

Ingestion proceeded with all source instructions treated as untrusted data. No source script was executed.

## Executive Summary

Nexus-Hub is the stronger production harness. It has broader platform support, substantially more skills and agents, stronger governance, deeper testing, a local-first security policy, generated catalog metadata, and documented cross-platform installation contracts. Neither source should replace its architecture.

The sources lead in two narrow areas. [evals-skills](https://github.com/hamelsmu/evals-skills) packages evaluation work as a coherent lifecycle: audit an evaluation pipeline, inspect traces, classify errors, validate an evaluator against labeled data, measure retrieval separately from generation, generate controlled synthetic cases, and build a human review interface. Nexus-Hub has the right foundations in [ai-output-evaluation](../../../../../catalog/skills/developer-experience/ai-output-evaluation/SKILL.md), [rag-implementation](../../../../../catalog/skills/ai-development/rag-implementation/SKILL.md), and [skill-eval-loop](../../../../../catalog/skills/workflow/skill-eval-loop/SKILL.md), but it does not yet connect those foundations into an equally concrete evaluation workflow.

[claude-codex-settings](https://github.com/fcakyon/claude-codex-settings) leads in selective installation experience. Its plugin-per-capability layout lets users install a focused subset instead of an entire catalog. Nexus-Hub already models this idea more systematically through profiles, modules, and role bundles in [bundles.json](../../../../../data/bundles.json), but the universal installers do not expose that model as a general user choice. The metadata exists; the cross-platform installation contract is the missing layer.

The recommended v3.16.1 scope therefore has two tracks:

1. Add evaluation-depth content using Nexus-Hub's three-tier skill model. Create one thin `eval-pipeline-audit` entry point, add concrete RAG retrieval metrics, and place detailed error-analysis, evaluator-validation, synthetic-data, and review-interface guidance in Tier-3 references.
2. Operationalize the existing profile and bundle metadata in both universal installers and the integration runner, preserving `full` as the compatibility default.

This yields local, platform-agnostic capability without importing either repository's branding, structure, vendor dependencies, or executable bootstrap practices.

## Step 7: Risks and Conflicts

### C1: Evaluation-Skill Overlap

Creating seven imported skills would fragment Nexus-Hub's existing evaluation surface and produce ambiguous routing between `ai-output-evaluation`, `skill-eval-loop`, `prompt-engineering`, and `rag-implementation`.

**Resolution**: create only the missing `eval-pipeline-audit` entry point. Add the other methods as linked Tier-3 references owned by the existing skills.

### C2: Sensitive Evaluation Artifacts

Traces, prompts, human labels, and failure examples may contain personal data, source code, secrets, or customer content even when the workflow itself is local.

**Resolution**: make local-file operation the default, require data minimization, cross-link `egress-redaction`, and mark external observability as an explicit user-authorized boundary rather than a default integration.

### C3: Installer Compatibility

Changing installer defaults would surprise current users and could produce partial installations that silently omit prerequisites.

**Resolution**: keep `full` as the default, make selection explicit, compute dependency closure before copying, show a deterministic dry-run manifest, and fail closed on unknown or inconsistent selectors.

### C4: Cross-Platform Drift

A selector implemented first in one installer can create different catalogs on Windows and POSIX systems.

**Resolution**: define one behavior contract and fixture set, implement both siblings in the same phase, and gate the work on Bash/PowerShell result parity plus platform integration tests.

### C5: Catalog and Bundle Drift

A new skill can be registered in the catalog but omitted from the relevant module or role bundle, causing selective installs to exclude it.

**Resolution**: add `eval-pipeline-audit` to the appropriate AI-engineering group, regenerate catalog data, validate bundle references, and include selection coverage in the new parity fixtures.

### C6: Attribution and Product Identity

Both sources use permissive licenses, but Nexus-Hub's Reverse-Engineering Attribution Rule forbids source branding in distributed artifacts.

**Resolution**: re-author every adopted method in Nexus-Hub's terminology. Keep source provenance in this comparison and any policy matrix record, not in installed skills, commands, scripts, or user-facing selector names.

### C7: Parallel Version Work

The current branch tracks v3.15.7 implementation and v3.19.0 is already planned. Starting v3.16.1 implementation in the same worktree would mix version scopes.

**Resolution**: complete the comparison now, but create and implement the v3.16.1 plan on its own branch or isolated worktree following the repository's declared branching strategy.
