## Section 1: Executive Summary

LoopX is a **local-first control plane for long-running AI agent work**: a durable state kernel that holds objective, gates, todos, scope, evidence, and quota across turns while Codex, Claude Code, Cursor, or a custom runtime executes bounded slices. It explicitly does not replace the agent runtime. Nexus-Hub is a **multi-platform catalog** of skills, commands, hooks, agents, and rules distributed by an installer. The two are complementary rather than competing: LoopX governs a running loop's state, Nexus-Hub supplies the procedures a loop invokes.

That complementarity is also the central constraint on this comparison. Nexus-Hub made a deliberate, documented decision that the loop **driver** is a host-platform command to reference, never a catalog artifact to ship (CHANGELOG v3.1.0 "Changed"; `agent-orchestration-primitives` Step 8; restated in `loop-engineering/SKILL.md` line 55). Most of LoopX's mass (the state kernel, quota engine, scheduler, `loopx` CLI daemon, benchmark adapters) is exactly the runtime layer Nexus-Hub chose not to own. Recommending it wholesale would reverse a standing architecture decision and import a very large maintenance surface, so it is declined in Section 7.

Nexus-Hub's loop coverage is also further along than a first pass suggests. Four loop-adjacent comparisons already shipped (v3.2.0 loop-engineering, v3.5.0 loopmaxxing, v3.9.0 looper, v3.15.7 raptor-loop-hunt), and the resulting `loop-engineering` skill already carries `iteration_cap`, `check_command`, a dual-condition `exit_condition`, `driver`, `maturity`, `per_iteration_budget`, `trace_log`, `progress_check` (stall and repeated-error detection), and `handoff`. The naive gaps are therefore already closed.

The genuine delta is what a **static loop definition cannot express**, plus a set of process disciplines LoopX has hardened through real operational failure:

1. **Typed human-judgment gates.** LoopX's core control flow asks "human judgment needed? yes, then ask a concrete question and wait" before it asks whether a safe fallback exists. Nexus-Hub's `handoff` is a post-cap destination, not a mid-loop blocking gate that pauses, asks one concrete question, and resumes.
2. **Durable, resumable loop-instance state.** Nexus-Hub loop definitions are static YAML templates. There is no record of a *running* loop whose objective, evidence, and open gates survive a cold start and can be handed to another agent or another tool.
3. **Release capability usage gate.** LoopX requires that any release introducing an opt-in capability teach activation, a minimum validation command, disable/rollback, the authority the activation does *not* grant, and a canonical doc link, machine-checked by a validator. Nexus-Hub ships an unusually high density of opt-in capabilities (`NEXUS_HUB_COPILOT_SKILLS`, `--enterprise`, `NEXUS_DISABLED_HOOKS`, `NEXUS_HOOK_PROFILE`) and `catalog/commands/update.md` has no such gate.
4. **A populated incident archive.** LoopX keeps nine dated, audience-labeled, public-safe incident notes describing agent-behavior failures, each abstracted into a reusable shape and fed back into the owning skill. Nexus-Hub owns the `incident-postmortem`, `known-gaps-tracker`, and `solution-knowledge-base` skills but has **zero** incident artifacts and no `docs/solutions/` directory. The skills exist; the practice does not.
5. **A `doctor` preflight.** `loopx doctor` is the first post-install step in every LoopX quickstart. Nexus-Hub's CLI exposes `init`, `install`, `status`, `upgrade`, and `uninstall` but no `doctor`, despite a documented history of installer and platform-contract drift (the v3.14.1 installer hotfix; the `check_platform_contract_freshness.py` gate).

Every recommended item below is local, service-free, and adds no dependency, credential, or outbound call, so the whole plan clears the MCP Registry Policy as `skill-native` or `re-full`. One check worth recording: LoopX's CI hardening (path-filtered triggers, concurrency groups, `timeout-minutes`, least-privilege `permissions`) looked like a gap and is **not** one. All nine Nexus-Hub workflows already carry it.

## Section 7: Risks, Conflicts, and Items NOT Recommended

### Conflicts with existing Nexus-Hub conventions

- **L1, L5, L6 modify a shipped skill's reference file.** `loop-schema.md` states that its first nine fields are required and any "Optional"-prefixed field is additive, so existing loop definitions stay valid. New fields must be introduced as optional to preserve that contract.
- **L3 touches both installers.** Per the installer-parity rule in `AGENTS.md`, a `doctor` subcommand must land in `scripts/installer.sh` **and** `scripts/installer.ps1` in lockstep, and the PowerShell side must use native equivalents (`ConvertFrom-Json`, `[System.IO.File]::WriteAllText` with a BOM-less encoder) rather than emulating shell mechanics. The v3.11.0 dead-`.ps1` incident is precisely the failure mode here.
- **L4 carries a private-context leak risk.** Incident notes are the single most likely place for internal paths, raw logs, and local state to reach a public repo. The "Public-Safe Shape" section is not decoration; adopt it as a hard requirement alongside the directory, and route the artifacts through the existing `secret-scan` hook.
- **L2 must not become release ceremony.** `/update release` is already a long flow. Scope the gate to capabilities that are genuinely opt-in, and make the no-change path a single explicit declaration rather than a checklist.

| ID | Item | Policy grounds |

Also a very large ongoing maintenance surface for a catalog project. Classified `drop-outright`. The *pattern* survives as L5. |
| N2 | Benchmark adapters (SkillsBench, Terminal-Bench, Docker runtimes) | Out of scope for a distribution catalog and would introduce a heavy Docker dependency. Nexus-Hub's evaluation need is already served by `run_trigger_evals.py` and the v3.16.9 evals plan. Classified `drop-outright`. |
| N3 | The React/Vite frontstage dashboard SPA | Duplicates the v3.16.7 interactive-guide track and adds a Node build chain to a repo whose tooling is Python, Bash, and PowerShell. Classified `drop-outright`. |

### Residual risk

The largest residual risk in this plan is L4 becoming a dumping ground: an incident directory that accumulates notes nobody reads, which is worse than no directory because it implies a practice that does not exist. Mitigate by requiring every incident note to name the durable fix it produced (a skill edit, a test, a gate) and to link it. LoopX's own discipline is the model: an incident is not closed by an explanation, only by a change that makes the lesson durable.
