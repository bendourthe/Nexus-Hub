## Licensing constraint (gates every adoption item)

The source ships a **"Dual-Use License" version 1.1**, classified by GitHub as `NOASSERTION` and by its own `pyproject.toml` as `License :: Other/Proprietary License`. Three clauses are decisive.

1. **Clause 3, non-commercial only.** "The software may not be used, directly or indirectly, in any product, service, or workflow that generates revenue, is offered commercially, or is used within a for-profit organization to support revenue-generating activities." Nexus-Hub is developed inside a for-profit organization, so *any* internal use, including as developer tooling, requires a paid commercial license (Builder $79 single-developer, Studio $349 up to five, Platform $1,999 org-wide).

2. **Clause (c), no registry redistribution.** "You do NOT publish or upload the software or any derivative or portion of it, modified or unmodified, to any public package registry, index, marketplace, or app store." Nexus-Hub *is* a distribution catalog with a `data/marketplace.json`. Vendoring any portion into the catalog would breach this directly.

3. **No use of name or marks**, and derivatives may not be renamed or rebranded.

Consequences, per the user decision recorded on 2026-07-28:

- **No code, no vendoring, no adaptation of source text.** Not a preference, a hard block.
- **No dependency, no registry entry, no bundled install.** Adding it to `catalog/mcp-configs/mcp-servers.json` would ship a commercial-license obligation to every Nexus-Hub user.
- **Architectural ideas remain adoptable.** Every item below is specified clean-room from behavior described in this report.
- **Shipped artifacts must not name the source**, per the Reverse-Engineering Attribution Rule in `AGENTS.md`.

One narrow nuance worth recording: `SPEC_MUNCH.md` publishes the wire format explicitly "so third-party clients and alternate MCP servers can decode MUNCH payloads without depending on the Python reference decoder", which is an open invitation to interoperate. Even so, the recommendation below is to design an independent encoding rather than implement that named format, because adopting the format by name would drag in the marks restriction and couple Nexus-Hub to a proprietary spec it does not control.

### Dimension 5 detail: what Nexus-Hub already has

`extensions/nexus-code-search` is not a stub. It is 18,159 LOC exposing 18 MCP tools with a tree-sitter AST graph across 12 languages (Python, TypeScript, Go, Rust, Java, C#, Ruby, PHP, C, C++, Swift, Kotlin), SQLite plus FTS5 storage, a NodeKind / EdgeKind taxonomy, call-graph traversal covering callers, callees, impact radius, and path finding, content-hash incremental indexing, a debounced filesystem watcher, and per-language eval fixtures under `src/nexus_code_search/eval/fixtures/`. Its README records the policy posture explicitly: zero outbound calls, zero API keys, zero model downloads, classified `already-local` in the RE matrix.

The overlap is therefore substantial. `code_search`, `code_callers`, `code_callees`, `code_impact`, `code_context`, `index_graph`, and `watch_for_changes` already cover the core retrieval and graph surface. **Most of the external tool count is not a gap.** The genuine gaps are four specific capabilities, listed next.

### The five techniques worth taking

1. **Schema-aware compact encoding at the producer.** A line-oriented wire format for MCP tool responses, replacing verbose JSON with a header line plus a legend and column-oriented table sections. Reported savings on real payloads are 39.4% to 55.4%, median 45.5%. Four properties make it safe rather than clever: deterministic (same dict, same bytes), round-trippable (structure, column order, and per-column types reconstruct), fail-open (a client that cannot decode requests JSON instead), and **size-justified** (encoding only fires when it saves at least 15%, so small payloads stay JSON).

    This does **not** duplicate `extensions/nexus-context-compressor`. That package compresses generically at the consumer side through a PreToolUse hook and a `context_compress` MCP tool, with a stronger property (every drop is reversible via a content-hashed CCR store and a `<<ccr:HASH N_rows>>` marker). Producer-side schema-aware encoding and consumer-side reversible compression **compose**: a generic router cannot reach 45% on a structured result table because it does not know the schema, and a schema encoder cannot help with unstructured prose. Both wins are available at once.

2. **Tool-profile gating by model tier.** The tool surface is filtered into `core` (16 tools), `standard` (51), and `full` (62), with the documented cost being roughly 5 to 6k tokens of tool definitions for `core` alone, and explicit per-tier recommendations (small models take `core`, frontier models take `full`). This attacks a cost axis Nexus-Hub currently ignores: **tool definitions are paid on every single request**, before any work happens. `nexus-code-search` exposes all 18 tools unconditionally, and a user running several internal MCP servers pays for all of them every turn.

3. **Edit-safety preflight verdicts.** Rather than exposing raw graph queries and leaving interpretation to the agent, a small family of tools fuses signals into a single verdict plus one recommended action. `check_edit_safe` combines signature impact (external and cross-repo callers depending on the current contract), cyclomatic complexity, test-coverage presence, and runtime traffic into ranked verdict tiers such as `runtime_critical` and `signature_impact`. Siblings cover delete and rename. All are read-only. Nexus-Hub has the raw ingredient (`code_impact`) but not the fused, decision-shaped output.

4. **A PreToolUse guard that routes native search to the index.** A hook intercepts `Grep`, `Glob`, and `Bash` invocations matching `grep` / `find` / `cat` patterns and redirects them to the indexed tools. Two design choices are the valuable part: `Read` is deliberately **not** intercepted, because `Edit` and `Write` require a prior `Read` in session state, and the edit-time guard is a **soft gate** printing to stderr while always exiting 0, with hard-block available behind an environment variable. Without such a guard, an indexed search server is optional and the agent routinely ignores it.

5. **Dependency ceilings justified by behavior, not by version drift.** The `tree-sitter-language-pack>=0.7.0,<1.0.0` pin carries a 14-line comment recording exactly why 1.x is refused: it stopped bundling grammars and now downloads them into a user-level cache on first use, which the comment calls "undisclosed runtime network + executable-write behavior in a read-only local tool" that "breaks airgapped/offline installs". It records the verification date, the issue number, the observed evidence (67 shared libraries written from an empty cache), the exact test-suite result on the newer version, and the conditions under which the ceiling would be revisited. This is a documentation practice that maps directly onto Nexus-Hub's zero-outbound policy, which currently has no comparable convention for recording *why* a ceiling exists.

## Step 7: Risks, conflicts, and items not recommended

### Conflicts with existing Nexus-Hub conventions

| ID | Conflict | Resolution |
|---|---|---|
| B4 | **Apparent overlap with `nexus-context-compressor`.** A reviewer will reasonably ask why Nexus-Hub needs two compression paths | Document the split explicitly in both READMEs: producer-side schema-aware encoding for structured MCP responses, consumer-side reversible CCR compression for everything else. Verify empirically that they compose rather than double-compress, and ensure the encoder runs before the hook sees the payload |
| B2 | **Hook aggressiveness versus the advisory-hook norm.** Nexus-Hub's `workflow-phase-notice` precedent is advisory-only, exit 0, and disableable via `NEXUS_DISABLED_HOOKS` and `NEXUS_HOOK_PROFILE=minimal` | Match that precedent exactly: soft gate by default, exit 0, honor both existing disable mechanisms, and make hard-block strictly opt-in |
| B8 | **Directly contradicts a published guarantee.** `extensions/nexus-code-search/README.md` states "zero outbound calls, zero API keys, zero model downloads" | Do not proceed silently. Either keep dense retrieval out, or ship it as a clearly-labelled opt-in extra with the README claim rewritten and the RE-matrix row amended. Quietly breaking a stated guarantee is worse than not shipping the feature |
| B1 | Tool profiles need a tier signal, and inventing a second model-tier taxonomy would fragment the concept | Reuse the existing `model-routing` skill's tier vocabulary rather than defining new tier names |
| B5 | Risks scope creep toward rebuilding all 62 external tools | Cap at the three safety verdicts plus blast radius. The value is the fused verdict, not tool count. Record the cap in the plan |

### Standing risks

- **R1, scale mismatch.** The source is ~201k LOC with 4,073 tests. `nexus-code-search` is 18k LOC. Any framing of this as "catch up to the external project" is a scope trap. The recommended set is five ideas, not a feature-parity program, and the value/effort scoring above deliberately reflects that.
- **R2, encoding correctness.** A compact encoding that loses a field or reorders a column silently corrupts what the agent reads, and the failure is hard to notice. Round-trip property tests are mandatory before B4 ships, and the fail-open fallback must be exercised in tests rather than assumed.
- **R3, the model-download policy question.** B8 is the only item that would change Nexus-Hub's outbound posture. It is a maintainer decision, not an implementation choice, and it should be resolved before the plan is generated rather than discovered mid-phase.
- **R4, benchmark cost.** B6 calls real models. Keep it developer-only, never installed to user machines, never in default CI, and pair it with `[[ai-billing-safeguards]]` for hard caps.
- **R5, upstream velocity.** The source is at version 1.108.198 with an 11,151-line changelog, so it moves fast. Its current design is a snapshot. Since the adoption is idea-level and clean-room, this is a low concern, but do not re-sync against it later.
- **R6, license posture is dated.** The license is "Version 1.1, effective 2026-06-30". Terms could change. Since no dependency is being taken, this only matters if a future maintainer reconsiders integration, at which point the license must be re-read rather than assumed from this report.

### NOT recommended for adoption

| Item | Grounds |
|---|---|
| **Adopting the MCP server itself, as a dependency, a registry entry, or a bundled install** | Three independent blocks. License clause 3 bars for-profit use without a paid license; clause (c) bars redistribution of any portion to a marketplace, and Nexus-Hub ships `data/marketplace.json`; and a registry entry would push a commercial-license obligation onto every downstream user. Also fails the MCP Registry Policy decision tree, which resolves at tier 3 (reverse-engineer into a local internal MCP) because `nexus-code-search` already exists |
| **Vendoring or adapting any source file** | Proprietary license. Clean-room reimplementation from this report is the only permitted path |
| **License-validation phone-home** | Nexus-Hub has no license to validate, and an internal extension that calls out at startup would breach the zero-outbound guarantee for no user benefit |
| **Token-savings telemetry to a vendor endpoint** | Categorically out. Even aggregate counters to a third-party host violate the zero-outbound posture. If savings measurement is wanted, B6 produces it locally |
| **Cloud LLM summarizer integrations (OpenAI, Groq, OpenRouter, z.ai, MiniMax)** | **Generation-as-service**, named explicitly on the MCP Registry Policy hard-no list. Summarization the agent can perform itself is the policy's tier-2 resolution, and the companion v3.18.1 comparison documents exactly that pattern |
| **Remote starter-pack fetching** | Downloading configuration from a vendor endpoint at install time is scraping-adjacent and unauditable. Nexus-Hub ships its catalog in-repo, which is strictly better |
| **Groq voice and vision extras** | Outbound generation-as-service plus `sounddevice`, `numpy`, and `Pillow` dependencies, for capability unrelated to a code-search index |
| **B9, repository-health CI action** | `drop-outright`. Low value for a catalog repository and it needs PR-write permissions. Nexus-Hub's existing `make validate` / `lint` / `test` gates already cover catalog integrity |
| **The named MUNCH format specifically** | Even though the spec invites third-party decoders, adopting the format by name pulls in the marks restriction and couples Nexus-Hub to a proprietary spec it does not control. Take the four safety properties, design an independent encoding |
