**Goal**: `nexus-code-search` costs less per request and gets used more reliably, through model-tier tool-profile gating, a PreToolUse guard that routes native search to the index, schema-aware response encoding, and fused edit-safety verdicts, all measured by a deterministic local harness.

## Overview

`extensions/nexus-code-search` is already substantial: 18,159 LOC, 17 MCP tools, a tree-sitter AST graph across 12 languages, SQLite plus FTS5, call-graph traversal, content-hash incremental indexing, a filesystem watcher, and the compiled context-map added in v3.15.1. The seeding comparison found that most of the external project's 62-tool surface is therefore **not** a gap. Four specific capabilities are, and this plan builds those four plus two lower-priority extensions.

The two P0 items attack costs that are paid on every single request. Tool definitions are billed before any work happens, and `nexus-code-search` currently exposes all 18 tools unconditionally to every model, so a user running several internal MCP servers pays the full definition cost every turn; phase 1 filters that surface into profiles keyed to model tier. Separately, an indexed search server that the agent forgets to use is dead weight, so phase 2 adds a PreToolUse guard that redirects native `Grep`, `Glob`, and `Bash` search patterns to the index. Both are low-effort and independently shippable.

Phases 3 and 4 add capability. Schema-aware encoding at the producer packs structured tool responses into a compact line-oriented form; it does **not** duplicate `nexus-context-compressor`, which compresses generically at the consumer with reversible CCR markers, because a generic router cannot exploit a schema it does not know and a schema encoder cannot help with unstructured prose. The two compose. Phase 4 then adds fused edit-safety verdicts, where the novelty is the decision-shaped output rather than the underlying data, which `code_impact` already computes.

**Every item in this plan holds the zero outbound calls, zero API keys, zero model downloads guarantee absolutely, with no gated exception.** Two candidates from the seeding comparison were reshaped to meet it rather than being allowed to negotiate with it. The measurement harness (phase 5) is deterministic and credential-free: retrieval quality is scored against a goldset with known-correct answers, which needs no model in the loop, and the live-model A/B from the comparison is dropped outright. Dense retrieval (phase 6) follows the pattern the repository already established in `nexus-context-compressor`'s ML token dropper: it loads pre-placed local weights and never downloads them, degrading to keyword-only search with a precise install hint when weights are absent. Nothing in this plan copies upstream source either; the source project is proprietary and non-commercial-only, so every item is specified clean-room and no shipped artifact names it.

## Phase 2: Search-routing guard

**Goal**: Stop the indexed search surface from being bypassed, by intercepting native search tool calls and redirecting them to the index, advisory by default.
**Prerequisites**: Phase 1.
**Stability Gate**: The hook redirects matching `Grep`, `Glob`, and `Bash` search invocations with a helpful message, never intercepts `Read`, always exits 0 in default mode, honors both existing disable mechanisms, and has a passing pytest suite in `catalog/hooks/tests/`.
**Recommended model**: Strong reasoning tier, medium effort (`claude-opus-5`, medium). A wrong matcher blocks legitimate work across every session, so matcher precision and fail-open behavior carry real risk.

### Sub-tasks

#### 2.1 - Implement the routing guard hook

**Objective**: Add a PreToolUse hook that nudges search traffic toward the index.

**Prompt**:
> Create `catalog/hooks/code-search-routing.sh` plus a `.ps1` sibling, following the authoring rules in `AGENTS.md` and modeling the structure on `catalog/hooks/workflow-phase-notice.sh`. Behavior: on `PreToolUse`, inspect the tool call from stdin JSON; when the tool is `Grep` or `Glob`, or is `Bash` with a command matching a code-search pattern (`grep`, `find`, `cat` used for searching), print a message to stderr naming the equivalent indexed tool and how to call it. Four hard requirements: (a) **never intercept `Read`**, because `Edit` and `Write` require a prior `Read` in session state and blocking it breaks the edit path; (b) default to a SOFT gate that always exits 0 so work proceeds, with hard-block available only behind an explicit environment variable; (c) omit `set -e` in the shell version so a helper failure can never abort before the message prints; (d) the hook is pure local string inspection and must open no network connection and read no credential. Honor `NEXUS_DISABLED_HOOKS=code-search-routing` and `NEXUS_HOOK_PROFILE=minimal`. Add a debug environment variable for logging. Keep the matcher conservative: a false positive that nags on every unrelated `find` is worse than missing some search calls.

## Phase 3: Compact response encoding

**Goal**: Cut the token cost of structured `nexus-code-search` responses with a schema-aware, deterministic, round-trippable, fail-open encoding that only engages when it actually saves.
**Prerequisites**: Phase 1.
**Stability Gate**: A documented Nexus-Hub wire format exists; encode-then-decode reproduces the original structure for every covered tool; encoding engages only above a configurable savings threshold and otherwise emits JSON; a decode failure falls back to JSON rather than erroring; and measured savings are recorded per tool.
**Recommended model**: Strong reasoning tier, high effort (`claude-opus-5`, high). A dropped field or reordered column silently corrupts what the agent reads, which is the hardest class of bug to notice.

### Sub-tasks

#### 3.1 - Design an independent wire format

**Objective**: Specify a Nexus-Hub-owned compact format, taking the safety properties rather than any external format.

**Prompt**:
> Design and document a compact wire format for `nexus-code-search` MCP tool responses at `extensions/nexus-code-search/docs/wire-format.md`. Do NOT implement any externally-named format; design an independent one owned by Nexus-Hub, so the project controls the spec and takes on no third-party naming or licensing entanglement. The format must satisfy four properties, each stated as a testable requirement: **deterministic** (the same response structure encodes to identical bytes every time), **round-trippable** (a decoder reconstructs top-level keys, column order, and per-column types), **fail-open** (a client that cannot decode requests JSON and gets it, and any encoder error falls back to JSON rather than propagating), and **size-justified** (encoding engages only when it saves at least a configurable percentage of bytes, defaulting to 15%, so small payloads stay JSON). Favor a line-oriented layout so a decoder can tokenize by splitting lines. Specify the version marker, the envelope, how tabular results are represented column-wise, and how a decoder distinguishes a compact payload from JSON. The codec must be pure standard library with no new runtime dependency.

---

#### 3.2 - Implement encoder and decoder

**Objective**: Build the codec and wire it into the response path.

**Prompt**:
> Implement the encoder and decoder for the format specified in 3.1 inside `extensions/nexus-code-search/`. Add a per-call format parameter with three values: JSON always, compact always, and automatic (encode only when the savings threshold is met). Default to the behavior that preserves today's output so this cannot regress an existing consumer. Wire it into the tool-response path so every tool benefits without per-tool code. Provide a reference decoder as a small importable module and note in the format doc that a consumer may implement its own from the spec. The threshold must be configurable. Critically: any exception inside the encoder must be caught and must result in valid JSON being returned, never a failed tool call. Standard library only, no network access, no credential.

---

#### 3.3 - Reconcile with the existing compression engine

**Objective**: Prevent the reasonable reviewer objection that Nexus-Hub now has two overlapping compression paths.

**Prompt**:
> Document and verify how the new producer-side encoding relates to `extensions/nexus-context-compressor`. Write the split explicitly in BOTH READMEs: the new codec is producer-side and schema-aware, applying to structured MCP responses from this server; `nexus-context-compressor` is consumer-side and content-routed, applying to arbitrary tool output with reversible CCR markers. Then verify empirically that they compose rather than conflict: run a compact-encoded payload through `compress_output(text)` and confirm the result is not double-compressed into something unreadable, that CCR markers are not corrupted by the encoding, and that ordering (encode at the producer, then compress at the hook) behaves sanely. If they interact badly, document the interaction and add a guard so the compressor leaves compact payloads alone.

---

#### 3.4 - Testing and Stabilization

**Objective**: Generate and run all tests for this phase. Iterate until the phase is stable before advancing to Phase 4.

**Prompt**:
> Generate comprehensive tests for Phase 3, with round-trip correctness as the priority. Use property-based tests where possible: for arbitrary response structures matching the covered schemas, encode-then-decode must reproduce top-level keys, column order, and per-column types exactly. Add explicit cases for an empty result set, a single row, a payload containing the format's own delimiter characters, non-ASCII content, nested structures, and null or missing fields. Assert determinism by encoding the same structure repeatedly and comparing bytes. Assert the savings threshold: a payload below it emits JSON, one above it emits compact. Assert fail-open by injecting an encoder exception and confirming valid JSON is still returned. Assert the composition behavior from 3.3. Record measured savings per tool in the README as real numbers from the test run, not estimates. Run, fix, iterate until green. Then update CI/CD for this phase and optimize it (path filters, concurrency cancel-in-progress, caching, expensive jobs gated to merges) while keeping coverage comprehensive; platform-agnostic with GitHub Actions as the primary example. Do not proceed to Phase 4 until fully tested. After all tests pass, run `/generate-session-history` to document Phase 3.

## Phase 4: Edit-safety verdicts

**Goal**: Give the agent a decision plus one recommended action before it mutates a symbol, instead of raw graph output it has to interpret.
**Prerequisites**: Phase 3.
**Stability Gate**: Three read-only preflight tools exist (edit, delete, rename), each returning a ranked verdict tier plus a one-line recommended action; each is proven read-only by test; and the scope cap is honored with no additional analysis tools added.
**Recommended model**: Strong reasoning tier, high effort (`claude-opus-5`, high). A verdict that under-reports risk actively misleads the agent into an unsafe edit, which is worse than returning nothing.

### Sub-tasks

#### 4.1 - Define the verdict taxonomy

**Objective**: Fix the vocabulary and ranking before any tool emits one.

**Prompt**:
> Define the edit-safety verdict taxonomy for `nexus-code-search` and document it. Verdict tiers must be ordered most-constraining first, and each must state what it means and what the agent should do. At minimum cover: the symbol is exercised at runtime or in production paths (highest stakes), external or cross-repo callers depend on its current signature (body edits acceptable, contract must be preserved), internal callers only, no known callers (a possible dead-code signal), and insufficient index data to judge (must be distinguishable from "safe", never collapsed into it). Specify the inputs each verdict is derived from, drawing only on signals `nexus-code-search` already computes locally: caller and importer edges, cross-file and cross-repo reach, test-coverage presence, and complexity. No verdict may depend on a remote service. State the honesty rule explicitly: when the index lacks the data to judge, the tool must say so rather than returning a reassuring verdict.

---

#### 4.2 - Implement the three preflight tools

**Objective**: Ship edit, delete, and rename safety checks over existing index data.

**Prompt**:
> Implement three read-only MCP tools in `extensions/nexus-code-search/`: an edit-safety check answering "what is my regression risk if I modify this, and what must I preserve"; a delete-safety check answering "who breaks if this disappears"; and a rename-safety check answering "what references must move together". Each returns a single verdict from the 4.1 taxonomy, a one-line recommended action, and the supporting evidence (the specific callers, importers, or coverage facts behind the verdict). All three must be strictly read-only and must never mutate the codebase or the index, and all three compute entirely from the local index with no network access. Compose them from existing graph queries rather than adding new analysis machinery. Assign all three to the standard tool profile from Phase 1, not to core. **Scope cap, recorded deliberately**: stop at these three plus the existing impact query. Do not expand toward a broader analytics surface; the value is the fused verdict, not tool count.

## Phase 5: Deterministic measurement harness

**Goal**: Measure the gains from phases 1 to 4 with a fully offline, credential-free harness, so the improvements are numbers rather than claims.
**Prerequisites**: Phase 4.
**Stability Gate**: The harness runs a fixed task set against an indexed corpus and reports token, byte, latency, and retrieval-quality deltas with the network blocked and no credential present; and no harness artifact is copied to user machines by either installer.
**Recommended model**: Strong reasoning tier, medium effort (`claude-opus-5`, medium). Straightforward to build, but the metric definitions must be sound or the numbers mislead.

**Policy note**: the live-model A/B path described in the seeding comparison is **dropped, not deferred**. It required a provider credential and outbound calls, and no code under `extensions/` takes an API key today. Everything below is deterministic: retrieval quality is scored against known-correct answers, which needs no model in the loop.

### Sub-tasks

#### 5.1 - Build the goldset and task set

**Objective**: Create a stable measurement target with known-correct answers.

**Prompt**:
> Build a measurement corpus and task set under `extensions/nexus-code-search/benchmarks/`. Extend the existing per-language eval fixtures into a goldset where every task records the known-correct answer: the specific symbol, file, or edge set a correct run must return. Include a spread of task shapes: locate a specific function, find all callers of a symbol, identify unused or unimported files, and trace an impact radius. Because the answers are recorded, correctness is checkable by comparison rather than by asking a model to judge, which is what keeps this harness credential-free. Record the methodology in a `METHODOLOGY.md` covering what is measured, what is held constant, what the known confounds are, and an explicit statement that the harness makes no network call and requires no API key. This sub-task builds fixtures and expected answers only.

---

#### 5.2 - Implement the cost measurement path

**Objective**: Measure every token, byte, and latency delta from phases 1 to 4.

**Prompt**:
> Implement the cost half of the harness: for each task in the goldset, execute the tool calls a correct run would make and record response byte size, encoded byte size, token count, tool-definition token cost for the active profile, and wall-clock latency. Use the token estimator already used by `nexus-context-compressor`, which degrades to a deterministic stdlib estimate when `tiktoken` is absent, so this path never *requires* a network call. Report a before/after table across the phase 1 to 4 capabilities: all-tools versus profiled, JSON versus compact encoding. Emit results as both a human-readable table and a machine-readable JSON file. Hard requirement: the entire path must run with the network blocked and with no credential in the environment, and a test must prove it.

---

#### 5.3 - Implement deterministic retrieval-quality scoring

**Objective**: Measure whether the tools return the *right* answers, not just cheaper ones, without a model in the loop.

**Prompt**:
> Implement the quality half of the harness. For each goldset task, run the relevant tool and compare the returned results against the recorded correct answer, computing precision, recall, and the rank position of the first correct result (reciprocal rank), then aggregate across the task set. This replaces the live-model A/B from the seeding comparison and is strictly better for this repository's purposes: it is reproducible run to run, costs nothing, needs no credential, opens no connection, and isolates the retrieval layer from model variance rather than confounding the two.
