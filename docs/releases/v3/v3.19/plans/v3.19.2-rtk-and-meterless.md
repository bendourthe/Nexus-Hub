## Overview

This plan operationalizes the v3.18.2 adoption report comparing Nexus-Hub against RTK (`rtk-ai/rtk`, a Rust command-output compressor plus multi-platform rewrite hooks) and Meterless (`Meterless/Meterless`, a local-first agentic context stack of engine specs). It is sequenced reverse-engineer-first per the report's Step 5.4 ordering: skill-native wins first, then local reverse-engineered builds, with the two supply-chain quick wins pulled to the front because they are high-value, low-effort, and unblock a "verified-install, provably zero-outbound" posture the rest of the work leans on.

Delivery is entirely inside the existing catalog and extensions: no new distribution channel, no binary release, no vendor integration. Phase 1 hardens the bootstrap installers and adds a build-breaking network-call guard over `extensions/nexus-context-compressor`. Phase 2 folds RTK/Meterless triggering-confidence and eval discipline into the `skill-description-authoring` and `skill-eval-loop` skills and adds a link-integrity and convention CI checker. Phase 3 hardens the memory system with provenance-as-invariant and a tiered lifecycle. Phase 4 deepens the compressor with semantic reformatters and introduces a single-source-of-truth command-rewrite protocol with host-permission gating across the existing per-platform hooks. Phase 5 adds bring-your-own-filter extensibility with a content-trust gate, non-destructive truncation, and session-log mining, and files the deferred signed-execution-contract concept as a design study. Phase 6 is the mandatory architecture-refactor, known-gaps, and CI/CD close-out.

Success looks like: a fresh install that verifies what it downloaded and refuses tampered archives; a CI run that fails if the compressor gains a network call; a skill-triggering and eval discipline that catches under/over-triggering and per-slice regressions; memory files that record where every fact came from; and a compressor that reformats (not just strips) the highest-frequency command output, all shipped to every platform the installer already reaches, with `make validate`, `make lint`, and `make test` green.

## Phase 1: Supply-chain hardening

**Goal**: Make the install verify what it downloaded and refuse tampered archives, and make the compressor's zero-outbound guarantee machine-enforced.
**Prerequisites**: None.
**Stability Gate**: A fresh install into a throwaway dir verifies the tarball SHA-256 and rejects an archive containing an absolute or `..` path; the new network-call guard fails the build when a network primitive is injected into the compressor and passes on the clean tree; `make validate` and `make lint` green.
**Recommended model**: Strong reasoning tier, high effort (Claude Opus class, e.g. claude-opus-4-8). Rationale: installer edits are flagged "Ask first" in AGENTS.md and are cross-platform supply-chain code where a mistake breaks every install.

### Sub-tasks

#### 1.1 - Installer integrity verification (A1)

**Objective**: Add SHA-256 verification and a tarball path-traversal guard to the bootstrap download path, modeled on RTK's `install.sh`.

**Prompt**:
> Harden the Nexus-Hub bootstrap download against tampering. This edits installer scripts, which AGENTS.md flags as "Ask first" - confirm the approach before writing, and edit `install.sh` and `install.ps1` (repo root) in lockstep so both platforms behave identically. Today the root `install.sh` `download()` helper fetches the catalog tarball from GitHub with no integrity check (verified: no `sha256`/`checksum`/`tar -tzf` logic present). Model the fix on RTK's `install.sh` (studied in the comparison): (1) before extraction, list the archive (`tar -tzf` on POSIX; the PowerShell equivalent) and refuse to extract if any entry has an absolute path or a `..` component (CWE-22); (2) verify the downloaded tarball's SHA-256 against an expected value - support pinning via `NEXUS_HUB_REF`/a published `checksums.txt` for tagged releases, and when installing from `main` (no published checksum) print an explicit "unverified `main` tarball" warning and allow an opt-out env (mirroring RTK's `RTK_SKIP_CHECKSUM`) rather than silently trusting. Keep the existing curl/wget fallback in `download()`. Do NOT add a new binary release channel (see the comparison's NOT-recommended list). Acceptance: a crafted archive with a `../evil` entry is refused; a checksum mismatch aborts with a clear message; `make lint` (ShellCheck) passes on `install.sh`.

---

#### 1.2 - Zero-outbound CI guard for the compressor (A2)

**Objective**: Add a repo-internal check that fails the build if compressor/engine code makes a network call, mirroring RTK's `.semgrep.yml` confinement of network code to one module.

**Prompt**:
> Add a build-breaking guard that enforces the zero-outbound policy over `extensions/nexus-context-compressor/`. Write `scripts/check_no_outbound.py` (a repo-internal guard, like `check_version_sync.py` and `check_base_template_parity.py` - it does NOT ship to users, so it needs NO installer copy step and NO `.ps1` sibling). It must scan the compressor package (including `test_mcp_server.py`'s server module) for network primitives (`import requests`, `httpx`, `urllib.request`, `socket`, `aiohttp`, `http.client`, subprocess calls to curl/wget) and fail with a non-zero exit and a precise file:line report if any appear outside an explicitly-allowlisted, opt-in module (there should be none today). Wire it into `make validate` and the CI workflow. Add a pytest fixture that injects a network import into a temp copy and asserts the guard flags it, plus an assertion that the real tree passes. Acceptance: `make validate` runs the guard; injecting `import requests` into a compressor module makes CI red; the clean tree is green.

---

#### 1.3 - Testing and Stabilization

**Objective**: Prove both hardening changes work and are covered by CI.

**Prompt**:
> Generate comprehensive tests for Phase 1. For 1.1: a shell/pytest harness that runs the bootstrap into a throwaway dir with (a) a good tarball+checksum, (b) a checksum mismatch, (c) an archive with a `..` entry, asserting install / abort / refuse respectively; validate the PowerShell path on the same three cases. For 1.2: the injection fixture from 1.2 plus a clean-tree pass. Run everything, fix failures, iterate until stable. Then create or update the CI/CD pipeline to cover these changes and optimize it to reduce action minutes (path filters so installer tests run only when `install.*`/`scripts/` change, concurrency cancel-in-progress, dependency caching, gating the Windows-runner installer test to merges/schedule) while keeping coverage comprehensive; keep it platform-agnostic with GitHub Actions as the primary example. Do not proceed to Phase 2 until green. After all tests pass, run `/generate-session-history` to document Phase 1.

## Phase 3: Memory hardening

**Goal**: Make every memory record carry its provenance and be mutated only through an auditable, tiered lifecycle.
**Prerequisites**: None (independent of Phases 1-2).
**Stability Gate**: The `memory` skill and the `catalog/memory` template require a source/origin on every record and define an append-only change log; a tiered promotion/archival lifecycle with preview-first maintenance is documented; a migration path for existing flat memory files exists; `make validate` green.
**Recommended model**: Strong reasoning tier, high effort (Claude Opus class). Rationale: this changes the memory write path and format and needs a safe migration of existing files.

### Sub-tasks

#### 3.1 - Provenance-as-invariant and change log (B1)

**Objective**: Adopt H-MEM's "no record without a source" invariant and append-only ledger for Nexus-Hub memory.

**Prompt**:
> Harden Nexus-Hub's memory system with H-MEM's provenance discipline (comparison Track B, B1). Update the `memory` skill and the `catalog/memory` template so that: (1) every memory record's frontmatter requires a `source`/origin field (what conversation, file, or decision it came from) - a record with no source is treated as invalid; (2) memory mutations are recorded in an append-only change log convention (added/updated/superseded, with a timestamp and reason), so the agent can answer "why did I recall X?"; (3) superseded facts are marked, not deleted (a `supersededBy` analog). Keep this convention-level and agent-native (Markdown + frontmatter), not a runtime store - Nexus-Hub memory is LLM-read files, not a database. Provide a migration note for existing memory files (backfill `source: legacy-import` where unknown). Acceptance: the memory template and skill document the source invariant and the change-log convention with an example record; existing memory files have a documented backfill path.

#### 3.2 - Tiered memory metabolism (B5)

**Objective**: Add a promotion/archival lifecycle with preview-first maintenance and backup/restore.

**Prompt**:

## Phase 4: Compressor and hook depth

**Goal**: Give the compressor semantic reformatting (not just line-stripping) and a single-source-of-truth command-rewrite protocol with host-permission gating across the existing per-platform hooks.
**Prerequisites**: Phase 1 (the zero-outbound guard should cover the new modules).
**Stability Gate**: A single rewrite decision function emits the 0/1/2/3 (allow/passthrough/deny/ask) contract, with thin per-platform hook delegates registered in `catalog/hooks/settings.json`; the rewrite hook reads the host's own permission settings with Deny>Ask>Allow precedence and per-segment allow enforcement; the compressor gains semantic reformatters for a named short list of high-frequency commands (extending the existing modules) with a logged coverage gap; base-template parity guard and platform-contract-verification pass; `make validate`/`make test` green.
**Recommended model**: Strong reasoning tier, high effort (Claude Opus class). Rationale: security-sensitive, cross-platform hook and permission logic plus compressor internals.

### Sub-tasks

#### 4.1 - Single-source-of-truth rewrite protocol (A3)

**Objective**: Implement RTK's shared exit-code rewrite contract once, with thin per-platform delegates.

**Prompt**:
> Adopt RTK's command-rewrite protocol (comparison Track A, A3). Implement the rewrite decision ONCE (a `rewrite` entry point in `extensions/nexus-context-compressor/`, or a dedicated module) that, given a command string, returns one of the RTK exit-code semantics: 0 = allow (rewritten command on stdout, auto-apply), 1 = passthrough (no equivalent), 2 = deny, 3 = ask (rewritten but requires approval). Pin the security-critical default to 3 (ask), never 0 (auto-allow) - copy RTK's test that enforces this. Then make the per-platform hooks in `catalog/hooks/` thin delegates that shell out to this single source of truth and format the platform-specific response. Register any new hook in `catalog/hooks/settings.json` and write a pytest per the existing hook test pattern (`catalog/hooks/tests/`). This touches installer distribution and instruction-adjacent surfaces: run `make validate` (which runs the base-template parity guard) and route through platform-contract-verification; edit installer copy steps only if a new distributed script is added, in `.sh` + `.ps1` lockstep. Acceptance: the rewrite function returns correct exit codes for allow/passthrough/deny/ask; the default is 3; the new hook is registered and tested; `make test` passes.

---

#### 4.2 - Host-permission gating (A4)

**Objective**: Make the rewrite hook read the host agent's own permission rules and never become more permissive.

**Prompt**:
> Add RTK-style host-permission gating (comparison Track A, A4) to the rewrite decision from 4.1. Read the host agent's own permission configuration (Claude `.claude/settings.json` `permissions.{deny,ask,allow}`; and the analogous surfaces for the other platforms the installer targets) and apply Deny > Ask > Allow > Default(ask) precedence. Enforce per-segment allow for compound commands (`&&`/`||`/`;`/pipe): every segment must independently match allow or the whole command drops to ask - copy RTK's per-segment fix. Nexus-Hub's rewrite must never be more permissive than the host. No data leaves the machine (this reads local settings only). Acceptance: a compound command with one non-allowed segment resolves to ask, not allow; a host deny rule wins over an RTK allow; unit tests cover the precedence table.

---

#### 4.3 - Semantic reformatters (A5)

**Objective**: Extend the existing compressor modules with the highest-frequency semantic reformatters, capped and coverage-logged.

**Prompt**:
> Extend the existing compressor modules (`content_router`, `code_compressor`, `smart_crusher`, `ml_token_dropper` under `extensions/nexus-context-compressor/`) with RTK Tier-A semantic reformatting (comparison Track A, A5) for a NAMED SHORT LIST of the highest-frequency commands only: git status (structured), test-runner output (failures-only for pytest/vitest/jest), and linter output grouped by file (ruff/eslint/tsc). This is parse-and-restructure, not line-stripping. Per the comparison's Step 7 risk note, do NOT attempt parity with RTK's ~60 handlers: cap the scope to this list and log the coverage gap explicitly in the compressor README and the v3.18 known-gaps file. Add inline tests asserting >=60% token reduction on realistic fixtures (RTK's bar). Acceptance: each of the three reformatters passes its fixture test with the savings bar; the coverage gap is documented; the zero-outbound guard (1.2) still passes over the new code.

---

#### 4.4 - Testing and Stabilization

**Objective**: Cover the rewrite protocol, permission gating, and reformatters.

**Prompt**:
> Generate tests for Phase 4: the exit-code contract (all four verdicts + default-is-3), the permission precedence table and per-segment enforcement, and each semantic reformatter's savings + faithfulness (output still looks like real command output). Run the hook test suite (`make test`) and the compressor tests. Fix, iterate until stable. Create or update CI to run hook tests and compressor tests with path filters (`catalog/hooks/**`, `extensions/nexus-context-compressor/**`), concurrency cancel-in-progress, and caching; gate any matrix/OS-heavy job to merges. Keep it platform-agnostic. Do not proceed to Phase 5 until green. After all tests pass, run `/generate-session-history` to document Phase 4.

## Phase 5: Compressor polish and session mining

**Goal**: Add user-extensible filters with a content-trust gate, non-destructive truncation, and session-log mining, and file the deferred signed-contract concept as a design study.
**Prerequisites**: Phase 4 (extends the compressor and rewrite surface).
**Stability Gate**: Users can drop a project/global filter file that is applied only after a SHA-256 content-trust gate, with inline filter tests runnable via a verify command; truncated output is recoverable via a tee-to-file mechanism; `session-query`/`continuous-learning` surface unrealized compression savings and repeated CLI mistakes; a signed-execution-contract design study exists under `docs/v3/v3.18/design/`; `make validate`/`make test` green.
**Recommended model**: Strong reasoning tier, medium-high effort (Claude Opus class). Rationale: trust-gate and truncation-recovery correctness; the mining piece is skill-native.

### Sub-tasks

#### 5.1 - BYO-filter extensibility with content-trust gate (A6)

**Objective**: Let users add filters, applied only after a SHA-256 content-trust gate, with inline tests.

**Prompt**:
> Add RTK's bring-your-own-filter model (comparison Track A, A6) to the compressor. Support a project-local and a user-global filter file (a TOML or JSON DSL: a match pattern + line/section actions) with first-match-wins lookup priority (project, then global, then built-in, then passthrough). Gate on-disk filter files behind a SHA-256 content-trust store: an untrusted or edited file is silently skipped until trusted (editing re-invalidates the hash), with `trust`/`untrust` operations. Support inline filter tests (`name`/`input`/`expected`) runnable via a `verify` command that runs them. Be candid in the docs that this is consent + tamper-evidence, not a sandbox (RTK's own framing). Acceptance: an untrusted filter is not applied; trusting then applies it; editing it re-invalidates; `verify` runs the inline tests and reports pass/fail.

---

#### 5.2 - Non-destructive truncation (A7)

**Objective**: Make truncation recoverable via tee-to-file, mirroring RTK's Lossiness model.

**Prompt**:
> Add RTK's non-destructive truncation (comparison Track A, A7) to the compressor. When output is truncated (head/max-lines), tee the full output to a temp file and track whether the loss is recoverable (a Lossiness analog: recoverable tail vs whole loss), so the dropped tail can be recovered on demand (e.g. an offset the user can `tail -n +offset` or a documented recovery command). Acceptance: a truncated result records a recovery pointer; the recovery path reproduces the dropped tail; nothing is silently unrecoverable.

---

#### 5.3 - Session-log mining (A8)

**Objective**: Surface unrealized compression savings and repeated CLI mistakes, extending existing skills (not a new binary).

**Prompt**:
> Extend the `session-query` and `continuous-learning` skills (comparison Track A, A8, classified skill-native) to mine the agent's own past session logs for (1) commands that ran without compression and the savings that were left on the table, and (2) repeated CLI mistakes worth turning into a rule or filter. This is instruction-level guidance plus, if useful, a small local read-only query helper - no new binary subsystem, no outbound call. Cross-reference the compressor's passthrough tracking as the data source. Acceptance: the skills document how to run the mining and what to do with the output (propose a new filter, add a rule); any helper is local and read-only.

---

#### 5.4 - Signed-execution-contract design study (B6, deferred)

**Objective**: File the deferred capability-contract concept as a design note, no runtime.

**Prompt**:
> Write a design study at `docs/v3/v3.18/design/signed-execution-contract-study.md` examining Meterless Scout Intent's signed-execution-contract model (comparison Track B, B6, deferred/concept) as a possible future framing for Nexus-Hub's hook/permission system: a capability-scoped, TTL-bounded, immutable authorization object that executors accept, with out-of-scope calls refused and logged. Assess fit against Nexus-Hub's local-agent reality (no signing infrastructure needed for a single local agent; the value is the discipline, not the crypto). Conclude with a recommendation (adopt-as-convention / defer / drop) for a future version. This is a study only - no code. Acceptance: the study exists, cites the comparison, and ends with an explicit recommendation.

---

#### 5.5 - Testing and Stabilization

**Objective**: Cover the trust gate, truncation recovery, and mining helpers.

**Prompt**:
> Generate tests for Phase 5: content-trust gate (untrusted skipped, trusted applied, edited re-invalidated), inline-filter `verify`, truncation recovery (recovered tail equals the dropped tail), and any session-mining helper (local, read-only). Run, fix, iterate until stable. Update CI with path filters over the compressor package, concurrency cancellation, and caching. Keep it platform-agnostic. Do not proceed to Phase 6 until green.
