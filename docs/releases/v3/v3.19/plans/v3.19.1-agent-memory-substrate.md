**Goal**: Nexus-Hub ships a cross-platform persistent agent-memory substrate that an agent writes to continuously and reads in full at session start within a fixed token budget, plus a repo-wide output-safety contract that keeps agent-consumed output from being silently truncated by any target CLI.

## Overview

Nexus-Hub has four memory-adjacent skills (`session-query`, `context-pack-builder`, `continuous-learning`, `solution-knowledge-base`) and a static ADR template, but every one of them is on-demand and topic-scoped. None is an always-on chronological store that accumulates without prompting and is read in full at the start of every session. This plan closes that gap by adding a new `extensions/nexus-memory/` package: an append-only log of short entries, tiled for reading by an age-decaying summarization tree, where recent entries stay verbatim and older ones collapse into progressively coarser one-line summaries chosen to fit a caller-supplied budget.

The defining constraint is that **the store never calls a model**. When a merge comes due, the tool emits a compression request and the exact command to return the result with; the calling agent performs the summarization and hands it back. That keeps the package at zero outbound calls, zero API keys, and zero new runtime dependencies, which is the posture every internal Nexus-Hub extension holds, and it is tier 2 of the MCP Registry Policy decision tree applied to a storage engine rather than to a service wrapper.

Two decisions from the seeding comparison shape the sequencing. First, the harness-aware output-paging contract (phase 1) lands before any memory code, because a memory read that the harness silently truncates is worse than no memory at all, and the contract is independently valuable to every Nexus-Hub script that prints agent-consumed output. Second, per the design decision recorded on 2026-07-28, the new store is the **durable cross-platform substrate** and Claude Code's native per-project memory directory remains a Claude-specific index that points into it, rather than a competing store. That relationship is written down as a contract in phase 2, before a single byte of storage code exists.

Nothing in this plan copies upstream source. The seeding comparison records that the reference project ships no license file, so all rights are reserved; every item here is specified clean-room from behavioral description, and no shipped artifact names the upstream project, per the Reverse-Engineering Attribution Rule in `AGENTS.md`.

## Phase 1: Output-safety foundation

**Goal**: Establish a repo-wide contract so that any Nexus-Hub script printing agent-consumed output is chunked to survive every target CLI's truncation behavior, and so printed commands are runnable regardless of `PATH`.
**Prerequisites**: None.
**Stability Gate**: A shared paging helper exists with both a byte cap and a line cap, its limits are backed by dated re-verification evidence, at least one existing script consumes it, and tests prove a payload larger than the cap is emitted as multiple parts each under both caps.
**Recommended model**: Strong reasoning tier, medium effort (`claude-opus-5`, medium). The implementation is small, but the per-CLI limits require live re-verification and a wrong constant silently truncates agent input.

### Sub-tasks

#### 1.1 - Re-verify per-CLI output truncation limits

**Objective**: Produce dated, sourced evidence for how much output each supported CLI surface accepts from a single tool call before truncating, and where it truncates.

**Prompt**:
> Determine, for each AI CLI surface Nexus-Hub installs to, how much output a single tool call may print before the harness truncates it, and which part is dropped (head, middle, or tail). Cover at minimum Claude Code, Codex, Gemini / Antigravity, Cursor, and OpenCode. Prefer direct empirical measurement where a surface is available locally; otherwise cite official documentation with a URL and an access date. Do NOT copy figures from any third-party project's source comments, which are undated and unverifiable. Write the findings to `docs/policy/output-truncation-limits.md` as a table with columns: surface, byte limit, token limit, line limit, truncation position, evidence (URL or measurement method), verified date, and a MATCH / DRIFT / UNVERIFIED classification per the convention already used in `docs/policy/platform-read-contracts.md`. Mark any surface you cannot verify as UNVERIFIED rather than guessing, and state in the file that the safe default is the minimum across all verified surfaces.

---

#### 1.2 - Implement the shared output-paging helper

**Objective**: Add one reusable helper that splits agent-consumed output into parts bounded by both a byte cap and a line cap.

**Prompt**:
> Create a shared output-paging helper for Nexus-Hub scripts. Requirements: (a) it accepts text plus an optional part index and returns one part at a time, bounded by BOTH a maximum byte count and a maximum line count, defaulting to the minimum verified across surfaces from `docs/policy/output-truncation-limits.md`; (b) it never splits mid-line; (c) when more parts remain it appends a single trailing line telling the caller the exact command to fetch the next part; (d) when the whole payload fits in one part it adds no framing at all; (e) both limits are overridable by the caller. Place the Python implementation where it is reachable by both repo-level `scripts/` and the extensions, and add a PowerShell sibling if any `.sh` consumer needs it. Treat these as transport limits, explicitly separate from any domain size limit. Include a module docstring stating that these are transport limits, not content limits, and cross-reference the policy file.

---

#### 1.3 - Adopt self-naming command output

**Objective**: Ensure every command string a Nexus-Hub script prints for the agent to run is executable even when the script is not on `PATH`.

**Prompt**:
> Audit Nexus-Hub scripts that print a command for the agent or user to run next. Where a script prints a bare invocation of itself (for example `nexus-memory wake`), change it to print a resolved, runnable path derived from the script's own location at runtime, folded to a `~`-relative form for readability when it sits under the user's home directory. Apply this only to scripts that actually print self-referential commands; do not sweep unrelated output. Add a test asserting that the printed command string resolves to an existing executable file. Scope note: every changed line must trace to this sub-task; do not clean up adjacent code.

#### 1.4 - Testing and Stabilization

**Objective**: Generate and run all tests for this phase. Iterate until the phase is stable before advancing to Phase 2.

**Prompt**:
> Generate comprehensive tests for everything built in Phase 1: unit tests for the paging helper covering a payload under both caps (single part, no framing), a payload over the byte cap only, over the line cap only, over both, a payload with a single line longer than the byte cap (must not split mid-line and must be reported rather than silently corrupted), and correct next-part command emission; plus the self-naming resolution test from 1.3. **Recommended model**: Mid reasoning tier, medium effort (`claude-sonnet-5`, medium). Prose and a small CI assertion, with the design decision already settled by the user.

### Sub-tasks

#### 2.1 - Author the memory substrate contract

**Objective**: Record the authoritative relationship between the new store and harness-native memory so phase 3 implements against a settled design.

**Prompt**:
> Write `docs/policy/memory-substrate-contract.md` recording the following decision, made on 2026-07-28: the new `nexus-memory` store is the durable, cross-platform source of truth for persistent agent memory; a harness's own native memory surface (for example Claude Code's per-project memory directory and its `MEMORY.md` index) remains a platform-specific INDEX that points into the substrate, never a competing store. #### 2.2 - Specify the agent-performed compression protocol

**Objective**: Define the request and response shape for a merge, fixing the zero-LLM-call constraint as a written contract rather than an implementation accident.

**Prompt**:

## Phase 3: Storage engine

**Goal**: Build the append-only, crash-safe, concurrently-writable store with constant-time record access, with no compression logic yet.
**Prerequisites**: Phase 2.
**Stability Gate**: Entries can be appended and read back by index on Windows and POSIX; concurrent writers do not interleave or lose entries; a truncated or partially-written record is detected and recovered without data loss to prior entries; and the store root is relocatable.
**Recommended model**: Strong reasoning tier, high effort (`claude-opus-5`, high). Cross-platform file locking, crash recovery, and concurrency are the highest-risk work in this plan.

### Sub-tasks

#### 3.1 - Scaffold the extension package

**Objective**: Create `extensions/nexus-memory/` following the conventions of its sibling extensions.

**Prompt**:
> Create `extensions/nexus-memory/` modeled structurally on `extensions/nexus-code-search/` and `extensions/nexus-context-compressor/`: a `pyproject.toml` with a `[dev]` extra, `src/nexus_memory/`, a `README.md`, and a test directory. Hard constraints, stated explicitly in the README: Python standard library only for the runtime package (no third-party runtime dependency), zero outbound calls, zero API keys, zero model downloads. The README must carry the same policy-compliance paragraph style as `nexus-code-search`'s, and must state that compression is performed by the calling agent, never by this package. Do not implement storage logic in this sub-task; scaffold only, with the module skeleton and the README claims in place.

---

#### 3.2 - Implement the fixed-width append-only log

**Objective**: Persist entries such that record N is reachable by a single seek with no index file.

**Prompt**:
> Implement the append-only entry log in `src/nexus_memory/`. Every record is padded to a constant byte width so record N lives at offset N times the width, making every lookup one seek and removing any need for a separate index. Requirements: (a) the record width and the maximum entry length are module constants, both overridable through a per-store config file; (b) entries are UTF-8 and the reader and writer both force UTF-8 regardless of system locale, so a non-ASCII character cannot crash a read on a machine with a legacy locale; (c) an entry longer than the maximum is rejected with a clear error, never silently truncated; (d) the file is append-only and existing records are never rewritten; (e) record count derives from file length divided by record width, with a non-integral length treated as a corrupt tail. Provide `append`, `get(index)`, `slice(lo, hi)`, and `count` operations. Document the roughly 2x on-disk cost of padding and why constant-time access is worth it.

---

#### 3.3 - Cross-platform locking and corruption recovery

**Objective**: Make concurrent writes safe on both POSIX and Windows, and make a partial write recoverable.

**Prompt**:
> Add write locking and corruption recovery to the store. Locking must work on POSIX (`fcntl`) and on Windows (`msvcrt`), selected at import time with a graceful fallback, since Nexus-Hub's primary development platform is Windows and the installer targets all three OSes. Requirements: (a) two concurrent appends must both succeed and must not interleave within a record; (b) a process killed mid-append must leave the log recoverable, with a repair operation that detects a non-integral tail and truncates only the incomplete trailing record; (c) repair must never touch a complete prior record; (d) a blank or partially-written record encountered on read must raise a clear, actionable error naming the exact recovery command rather than returning empty content. Write the tests alongside: spawn multiple real processes appending simultaneously and assert every entry is present exactly once and no record is malformed.

---

#### 3.4 - Relocatable store root and configuration

**Objective**: Let the store live outside its default location, with the confidentiality tradeoff documented.

**Prompt**:
> Add a relocatable store root: an environment variable overrides the default user-scoped path, so the store can sit in a synced folder or a git repository. Also add the per-store config file that overrides the tunable sizes (read budget, maximum entry length, and the two transport paging limits from Phase 1), with a subcommand to show and set them. Requirements: (a) the default must remain a local, user-scoped path, never a project directory; (b) the read budget must be changeable in either direction at any time with nothing recomputed, because it is a reading budget and not a storage budget; (c) the README must state plainly that relocating the root inherits that destination's exposure and that a store placed inside a repository can be committed; (d) ship a recommended ignore pattern for that case. Cross-reference `[[egress-redaction]]` for the rule that memory content must be redacted before inclusion in any shared artifact.

---

**Objective**: Generate and run all tests for this phase. Iterate until the phase is stable before advancing to Phase 4.

**Prompt**:
> Generate comprehensive tests for Phase 3: round-trip append and read-by-index; padding correctness at exact, under, and over the record width; UTF-8 content read back correctly under a forced non-UTF-8 locale; over-length entry rejected with a clear error; multi-process concurrent append with no loss and no interleaving; kill-mid-append followed by repair, asserting only the incomplete tail is removed; blank-record read raising the actionable error; relocated root honored; config round-trip. ## Phase 4: Compression tree

**Goal**: Add the age-decaying summarization tree and the agent-driven merge loop, so a store larger than the read budget still reads in full within that budget.
**Prerequisites**: Phase 3.
**Stability Gate**: A read of a store far larger than the budget returns at most the budgeted number of lines, with recent entries verbatim and older ones summarized; pending merges are reported in deterministic order; a completed merge is persisted and reflected in the next read; and deleting the entire tree loses no information because the next merges rebuild it from the log.
**Recommended model**: Strong reasoning tier, high effort (`claude-opus-5`, high). The tiling search and the pending-merge accounting are the algorithmic core, and an off-by-one here silently degrades every read.

### Sub-tasks

#### 4.1 - Implement the age-decaying tiling function

**Objective**: Choose, for a store of N entries and a budget of B lines, which ranges to render verbatim and which to render as summaries.

**Prompt**:
> Implement the read-tiling function. Given a total entry count and a line budget, it returns an ordered list of aligned power-of-two ranges covering the whole store, at most budget-many, with the finest granularity nearest the newest entries. Behavior: (a) when the store fits within the budget, return one range per entry and compress nothing; (b) otherwise find the coarsest tiling that fits by binary searching a single decay parameter that keeps a range whole when its size is at most that parameter times its age; (c) because range sizes move in powers of two, the search can undershoot, so spend any remaining budget by repeatedly splitting the newest non-singleton range, since detail is worth most at the present. This must be a pure function over integers with no I/O, so it is exhaustively testable. Document the intent in the docstring: detail decays with age, recent entries stay verbatim, ancient ones collapse.

---

#### 4.2 - Implement the summary tree store

**Objective**: Persist one file per tree level, so pending work is derivable from file lengths alone.

**Prompt**:
> Implement persistence for range summaries. One file per level (ranges of size 2, 4, 8, and so on), each holding a dense prefix of fixed-width summary records, so a level's length tells you exactly how far compression has progressed at that level. Provide: `put(lo, hi, text)`, `get(lo, hi)`, `drop(lo, hi)` for discarding a bad summary so it can be rebuilt, and a pending-work enumeration that lists buildable-but-unbuilt ranges smallest-first using one length check per level and never a scan. Provide a pending count that computes the same total without materializing the list, clamping each level at zero because entries keep arriving while an agent reads. Preserve the phase-2 invariant: this whole structure is a cache, and deleting it must lose nothing.

---

#### 4.3 - Wire the read command and the merge loop

**Objective**: Expose the user-facing operations that make the store usable by an agent.

**Prompt**:
> Implement the command surface over the engine: read the memory (tile per 4.1, render each range as either its verbatim entries or its summary, page the result through the Phase 1 helper); record one entry; answer a due merge by supplying a summary for a named range; search all entries by regular expression; open a summarized range into its two halves; and discard a bad summary so the next merge rebuilds it. Merge requests surface one at a time in the output of the record operation, formatted per the Phase 2 protocol, and every printed command must use the resolved self-naming path from sub-task 1.3. Nothing may run in a background process. Add the always-loaded integration prose the substrate contract calls for, and verify it against the Phase 2.4 token budget.

---

#### 4.4 - Testing and Stabilization

**Objective**: Generate and run all tests for this phase. Iterate until the phase is stable before advancing to Phase 5.

**Prompt**:
> Generate comprehensive tests for Phase 4. For the tiling function use property-based tests: for any entry count and any budget, the returned ranges tile the store exactly with no gap and no overlap, the count never exceeds the budget, ranges are aligned powers of two, and granularity is monotonically finer toward the newest entry; plus explicit cases for a store under budget (no compression at all), exactly at budget, and far over. For the tree store: pending enumeration is deterministic and smallest-first, pending count matches the enumerated length, a level holding more ranges than the current total clamps to zero rather than going negative, drop-then-rebuild reproduces a summary, and deleting every level file loses no entry. For the command surface: a read of a large store stays within budget, a merge request names a real pending range, and answering it changes the next read. Add an end-to-end test that fills a store well past the budget, answers every merge, and asserts the read is bounded and ordered. Run, fix, iterate until green. Then update CI/CD for this phase and optimize it (path filters, concurrency cancel-in-progress, caching, expensive matrix gated to merges) while keeping coverage comprehensive; platform-agnostic, GitHub Actions as the primary example. Do not proceed to Phase 5 until fully tested. After all tests pass, run `/generate-session-history` to document Phase 4.

## Phase 5: Skill, distribution, and registration

**Goal**: Make the capability reachable from every supported platform through the normal installer path, with skill routing that does not collide with the four existing memory-adjacent skills.
**Prerequisites**: Phase 4.
**Stability Gate**: A clean install places the skill and the extension at the expected per-platform paths; `make validate` passes including the trigger-and-routing gate; and the routing evals prove the new skill wins its own prompts and loses the near-miss prompts belonging to the four existing skills.
**Recommended model**: Strong reasoning tier, medium effort (`claude-opus-5`, medium). Mechanically wide across 14+ platform surfaces and three hand-edited registry files, where a missed registration silently ships a broken catalog.

### Sub-tasks

#### 5.1 - Author the agent-memory skill

**Objective**: Give the agent a SKILL.md that teaches when and how to use the substrate, without colliding with existing skills.
