## Executive Summary

`jakubkrehel/skills` is a narrow, deep, documentation-only collection: seven skills covering interface craft (accessibility, layout, typography, color, UI polish, UX writing) plus one coordinator. It has no build, no tests, no CI, and no governance tooling. Measured as a *project*, Nexus-Hub dominates every infrastructure dimension. Measured as *domain coverage in one specific area*, the comparison inverts sharply.

Nexus-Hub carries 269 skills and three UI-adjacent ones: [frontend-ui-engineering](../../../../../catalog/skills/developer-experience/frontend-ui-engineering/SKILL.md) (132 lines), [hallmark-design](../../../../../catalog/skills/developer-experience/hallmark-design/SKILL.md) (117 lines), and [ui-component-generation](../../../../../catalog/skills/developer-experience/ui-component-generation/SKILL.md) (81 lines). All three are flat single files with zero bundled `references/`. There is no dedicated accessibility skill, no typography skill, no color skill, and no interface-copy skill anywhere in the catalog. The source spends 192 KB on exactly that territory, with prescriptive, value-level guidance (`line-height 1.5 to 1.6 for body copy`, `weights under 300 are display-only at 28px+`, `scale 0.25 -> 1, blur 4px -> 0px`) rather than the principle-level advice Nexus-Hub's UI skills currently give.

Two structural patterns in the source generalize well beyond UI and are the highest-leverage items in this report. The first is an explicit **rule-ownership matrix** (`CLAUDE.md:21-37`) that assigns every overlapping concern to exactly one owning skill and reduces the others to a named handoff. The second is a **coordinator skill** (`better-interface`) that loads the domain skills, deliberately suppresses their standalone output formats, and consolidates into one ranked verdict with a mode-based finding cap and a mandatory "Considered but Rejected" table. Nexus-Hub has cross-links between skills but no ownership arbitration and no consolidating reviewer of this shape.

Eleven adoption candidates result. Every one is pure Markdown skill content: zero new outbound calls, zero new API keys, zero new dependencies, zero new third-party data processors. All classify `skill-native` under the MCP Registry Policy. The single NOT-recommended item is the source's `npx skills add` / skills.sh distribution channel, which would introduce a third-party registry dependency alongside Nexus-Hub's own installer.

The comparison also surfaced a pre-existing defect in Nexus-Hub itself (see Step 3.3): 126 of 139 `agents/openai.yaml` sidecars are machine-truncated mid-word.

## Step 7: Risks and Conflicts

### C1: MIT attribution versus the Reverse-Engineering Attribution Rule (HIGHEST RISK)

The source is MIT-licensed, which requires the copyright notice to accompany substantial portions of the material. Nexus-Hub's own Reverse-Engineering Attribution Rule (`AGENTS.md`) forbids naming the external repo, product, or metric in the distributed artifact, placing attribution in the reverse-engineering matrix row instead.

These two obligations collide ONLY if content is copied verbatim or near-verbatim. The resolution is the policy default: write original guidance informed by the domain rather than transcribing the source. Domain facts are not copyrightable (`.woff2` is the web font format; body line-height of 1.5 to 1.6 is a typographic convention; WCAG contrast thresholds are a published standard), but the source's specific prose, table structures, and worked examples are.

**Mandatory constraints for Group 3**: no verbatim paragraphs, no copied tables, no reused code-example pairs, no reused skill names (`better-*`). Use the descriptive names in Step 6. Record the provenance in `docs/policy/mcp-reverse-engineering-matrix.md`, not in the SKILL.md files. If any file ends up carrying substantial verbatim text, the MIT notice must ship with it, and that outcome should be treated as a signal the item was copied rather than reverse-engineered.

### C2: Skill-count inflation and overlap with `hallmark-design`

Importing all seven skills verbatim would add 7 skills and a second, competing UI doctrine. `hallmark-design` already owns "does this look AI-generated" judgment and `frontend-ui-engineering` already owns component architecture and responsive implementation. Two conflicts follow:

- `better-ui` overlaps `hallmark-design` substantially. Recommendation: merge its recipe-level content into `hallmark-design` (A6) rather than shipping a parallel skill.
- The new cluster must not restate `frontend-ui-engineering`. Apply A7's ownership matrix at authoring time: `frontend-ui-engineering` keeps component architecture, state, and responsive implementation; the new skills own their named domains.

Net catalog change if the recommendation is followed: +5 skills (269 to 274), not +7.

### C3: Registry synchronization burden

Each new skill requires hand-editing three `data/` files (`SKILL_INDEX.md`, `skills.json`, `marketplace.json`). Per the established convention, do NOT run `build_skills_catalog.py`, which rewrites the whole tree and produces an unreviewable diff. Five skills means five hand-synced entries plus two `total_skills` / `skill_count` updates.

### C4: Bundled-reference orphan audit

The source's reference files are flat siblings of `SKILL.md`. Nexus-Hub requires them under `references/` AND requires every bundled file to be referenced from the parent `SKILL.md`, enforced by `validate_skills.py`. Each imported skill must carry a Quick Reference table that links every reference file, or `make validate` emits orphan warnings.

### C5: Source has no verification discipline to inherit

The source ships no Verification checklists and no Common Rationalizations tables. Both are mandatory in Nexus-Hub. This content must be authored fresh for all five new skills; it cannot be adapted from the source because it does not exist there. Budget for it explicitly rather than discovering it at validation time.

Adopting a third-party registry would duplicate that channel while adding an external dependency and an `npx`-executed remote fetch to the install path.
