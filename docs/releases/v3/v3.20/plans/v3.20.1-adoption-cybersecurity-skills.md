## Overview

This plan operationalizes the adoption plan from the cybersecurity skills library comparison. The source is an 817-skill catalog on the same `SKILL.md` open standard, using framework-mapping frontmatter keys byte-identical to the ones Nexus-Hub already declares.

Two constraints from the comparison shape every phase, and they point the same way.

The source is **Apache-2.0** and Nexus-Hub is **MIT**, so no prose, script, or reference file may be copied. Every skill in Phase 4 is authored independently from primary framework sources. This is a legal constraint, not a stylistic preference, and it is the single highest-severity risk in the plan.

Bulk adoption is also **architecturally foreclosed**. Nexus-Hub loads `name` plus `description` plus `summary_l0` plus `overview_l1` for every catalog skill in every session, already ~104k tokens across 273 skills. Importing all 817 would project to ~416k tokens permanently resident. Phase 4 therefore consolidates roughly 173 of their granular, frequently vendor-specific skills into 40 vendor-neutral capability skills, a 4.3:1 ratio that holds Tier-1 growth to ~15k tokens (+14%). That ratio is load-bearing: a 1:1 import of the same material would add ~66k.

Phases 1 through 3 are the higher-leverage half despite being much smaller. Phase 1 ships the framework and conformance tooling. Phase 2 makes coverage visible. Phase 3 is the one item that originates from measuring Nexus-Hub against the source rather than from the source's content: 47 of our skills exceed the 800-line hard cap that `AGENTS.md` sets, against 2 of their 817.

Success looks like this. A skill can declare `mitre_f3` and have it validated and rendered. `make validate` fails when a SKILL.md would break the agentskills.io contract. A committed coverage map shows which ATT&CK techniques the catalog teaches. No skill exceeds 800 lines. A user asking "how do I detect Modbus command injection" or "triage this IOC" routes to a Nexus-Hub skill that did not exist before, and the catalog registers 313 skills consistently across the three registry files.

Grounding note: no `docs/solutions/` store, no `STRATEGY.md`, and no constitution file exist in this repo. Grounding is best-effort and none of these blocked planning.

## Phase 1 - Framework and conformance tooling

**Status**: complete
**Recommended model tier**: strong
**Recommended effort level**: high

**Rationale**: Small, precise, load-bearing edits across five files with an existing contract to honor (the optional-field pattern). Low ambiguity, high cost of a subtle mistake.

#### 1.1 - The `mitre_f3` optional framework field

**Objective**: Add MITRE F3 as a sixth optional framework-mapping field, following the existing optional-field contract exactly.

**Failure modes**: Making the field required, or erroring on its absence, would break all 273 existing skills. Adding it to `FRAMEWORKS` in the generator without adding validation leaves an unvalidated key that accepts a scalar where a list is required. Documenting it in `AGENTS.md` without wiring the generator produces a field that validates but never renders, the silent-no-op class.

**Build class**: load-bearing.

**Prompt**:
> In the Nexus-Hub repo, add `mitre_f3` as a sixth optional framework-mapping frontmatter field. Four edits, all of which must land together. (1) In `AGENTS.md`, add a row to the optional-fields table in "Optional Security and Compliance Framework Mapping": field `mitre_f3`, framework "MITRE Fight Fraud Framework (F3)", example `[F1005.006, F1010]`. Keep the existing sentence that absence is never an error and costs no Tier-1 tokens. (2) In `scripts/validate_skills.py`, add `mitre_f3` to the optional framework fields checked for list shape, matching how `mitre_attack` and `d3fend_techniques` are handled. A scalar value where a list is expected is an error naming the skill and the field; absence is never an error. Confirm the check runs in the `--bundles-only` mode that `make validate` and CI invoke. (3) In `scripts/build_framework_coverage.py`, add `("mitre_f3", "MITRE F3")` to the `FRAMEWORKS` list so it is picked up by `FRAMEWORK_FIELDS` and rendered in the coverage output with the other five. (4) In `catalog/skills/security/security-framework-mapping/SKILL.md`, document the new field and when a skill should declare it: cyber-enabled financial fraud TTPs, the ground ATT&CK leaves after initial compromise. Note in that skill that F3 v1.1 was released 2026-04-09 by MITRE's Center for Threat-Informed Defense. Acceptance: `make validate` passes unchanged on the current catalog (no skill declares the field yet), and adding `mitre_f3: [F1005.006]` to one skill renders it in `build_framework_coverage.py` output while `mitre_f3: F1005.006` fails validation with a message naming the skill and field.

#### 1.2 - ATT&CK Navigator layer export

**Objective**: Add a `--navigator-layer` output to `build_framework_coverage.py` emitting a MITRE ATT&CK Navigator layer JSON from `mitre_attack` values already on disk.

**Failure modes**: Emitting a layer that Navigator refuses to load is worse than emitting nothing, because the failure surfaces only in a browser. The layer schema requires specific `versions` and `domain` keys. Hardcoding a technique list rather than deriving it from SKILL.md files would create a second source of truth that silently rots.

**Build class**: load-bearing.

**Prompt**:
> Add a `--navigator-layer <path>` option to `scripts/build_framework_coverage.py`. When passed, it writes a MITRE ATT&CK Navigator layer JSON derived solely from the `mitre_attack` values already parsed from SKILL.md files, alongside (not instead of) the existing Markdown output. Conform to the Navigator layer format: a top-level object carrying `name`, `versions` (with `layer`, `navigator`, and `attack` sub-keys), `domain` set to `enterprise-attack`, `description`, and a `techniques` array whose entries carry `techniqueID`, `score`, and a `comment` listing the Nexus-Hub skills that teach that technique. Score each technique by the number of skills covering it. Derive nothing from a hardcoded list. Write deterministic output with sorted keys so the file diffs cleanly. Add the option to the module docstring usage block. Acceptance: running with `--navigator-layer docs/attack-navigator-layer.json` produces a file whose `techniques` array length equals the count of distinct `mitre_attack` values across the catalog, and re-running produces a byte-identical file.

#### 1.3 - agentskills.io conformance guard

**Objective**: Create `scripts/check_agentskills_conformance.py`, a read-only stdlib guard asserting every SKILL.md satisfies the agentskills.io open standard.

**Failure modes**: Copying the source's blanket ban on `<` and `>` in frontmatter would regress Nexus-Hub's strictly better semantic placeholder lint and would reject legitimate CLI notation such as `<path>`. Duplicating the name-equals-directory check that `validate_skills.py:360` already enforces creates two places to fix one rule. Registering the script for installer distribution would be wrong: it is a repo-internal guard.

**Build class**: load-bearing.

**Prompt**:
> Create `scripts/check_agentskills_conformance.py` (Python 3, module docstring, type annotations, stdlib only, READ-ONLY, never edits files). It walks every `catalog/skills/*/*/SKILL.md` and asserts the agentskills.io open-standard contract: `name` and `description` are both present and non-empty; `name` is 1 to 64 characters matching `^[a-z0-9]+(-[a-z0-9]+)*$`; `description` is 1 to 1024 characters. Report, as INFORMATION and not failures, the top-level keys Nexus-Hub adds beyond the standard's recognized set (`name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`), because the standard permits additional top-level keys. Do NOT re-implement the name-equals-directory rule, which `scripts/validate_skills.py` already enforces as a hard rule; reference that in the docstring instead. Do NOT add any angle-bracket check: Nexus-Hub's existing v3.15.2 placeholder lint is semantic and strictly more precise than a blanket ban, and duplicating it would regress precision. Collect all failures before a single exit 1. Support `--json` for machine-readable output. Wire into `make validate`. Add the script to `DEV_ONLY_SCRIPTS` in `catalog/hooks/tests/test_installer_smoke.py`, since it is a repo-internal guard needing no installer copy step. Also add a short subsection to `AGENTS.md` recording that Nexus-Hub targets the agentskills.io standard and that this guard proves it, replacing an untested claim with a checked one. Acceptance: exits 0 on the current catalog; truncating a `description` to empty in one skill makes it exit 1 naming that skill.

#### 1.4 - Testing and Stabilization

**Objective**: Prove Phase 1 with tests, and update CI for the phase's changes.

**Prompt**:
> Add `tests/validators/test_agentskills_conformance.py` and extend the existing framework-field tests. Cover: `mitre_f3` absent is valid; `mitre_f3` as a list is valid; `mitre_f3` as a scalar is an error naming skill and field; the Navigator layer output is valid JSON with the required `versions`/`domain` keys and is byte-identical across two runs; conformance passes on the real catalog and fails on a fixture with an empty description. Follow the existing pytest patterns in `tests/validators/`. Confirm `make validate` and `make test` are green and that CI's existing `validate` job picks up both new checks without needing a new job, which would require its own required-check context (the v3.17.6 lesson).

## Phase 3 - Size-norm remediation

**Status**: complete
**Recommended model tier**: strong
**Recommended effort level**: high

**Rationale**: 47 files of judgment-heavy editing where the failure mode is silent information loss. Mechanical splitting would destroy the skills.

#### 3.1 - Relocate over-cap body content into `references/`

**Objective**: Bring all 47 skills over the 800-line hard cap into compliance without losing guidance.

**Failure modes**: Deleting content to hit a line count is the worst outcome and must not happen; this is a relocation, not a cut. Moving the Verification or Common Rationalizations sections out of the body would break the required-section contract in `AGENTS.md`. Creating a `references/` file that SKILL.md never links to trips the orphan-bundle audit. Truncating mid-table or mid-fence corrupts rendering.

**Build class**: load-bearing.

**Prompt**:
> Identify every SKILL.md under `catalog/skills/` whose body exceeds 800 lines (47 at time of writing, max 2,544) and bring each under the cap, targeting 500 where achievable. Method, per skill: keep the required sections in the body (title, When to Use This Skill, Instructions, Common Rationalizations, Verification, Related Skills), and relocate the long-tail material (extended examples, per-language or per-platform variants, deep reference tables, runbooks) into `references/<topic>.md` files, linked from the body the way an external doc would be linked, so the agent pays for them only on demand. Relocate; never delete. Preserve every code fence and table intact. Every new reference file must be linked from its SKILL.md so the orphan-bundle audit passes. Do NOT touch skills already under the cap; this is not a catalog-wide rewrite. Work in batches of roughly 8 skills, running `make validate` after each batch, so a mistake is localized. Acceptance: zero skills over 800 lines; `make validate` green with no new orphan warnings; the Tier-1 fields of every touched skill are byte-identical before and after, since only body content moves.

#### 3.2 - Enforce the cap going forward

**Objective**: Make the norm machine-checked so it cannot regress.

**Failure modes**: A hard error on the 500-line target would fail the catalog immediately, since 107 skills exceed it and `AGENTS.md` grandfathers them. The 800 cap is the hard line; 500 is a warning.

**Build class**: load-bearing.

**Prompt**:
> Add a body-size check to `scripts/validate_skills.py`: a SKILL.md body over 800 lines is a HARD ERROR naming the skill and its line count; over 500 lines is a WARNING. Count body lines only, excluding frontmatter. Run it in `--bundles-only` mode so `make validate` and CI enforce it. Update the "SKILL.md size norm" paragraph in `AGENTS.md` to record that the cap is now machine-enforced rather than advisory, and that the grandfathering clause now applies only to the 500-line warning tier. Acceptance: exits 0 after 3.1; artificially padding one skill past 800 lines makes it exit 1.

#### 3.3 - Testing and Stabilization

**Prompt**:
> Add tests for the body-size check covering both tiers and the frontmatter-exclusion boundary. Confirm `make validate`, `make test`, and the trigger evals are green, and that no skill's `summary_l0` or `overview_l1` changed during 3.1 (a diff over Tier-1 fields should be empty).
