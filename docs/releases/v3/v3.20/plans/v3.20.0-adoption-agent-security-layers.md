## Overview

This plan operationalizes the adoption plan from the agent-security-layers comparison. The comparison found that Nexus-Hub's behavioral security skills (prompt-injection-defense, egress-redaction, agentic-endpoint-hardening) have no infrastructure-level counterpart: nothing in the catalog teaches kernel-level agent confinement (Landlock, seccomp, network namespaces, per-session ephemeral containers), the credential-brokering pattern (placeholder keys inside the agent environment, a broker injecting real keys at the boundary), or the out-of-process egress-boundary architecture (static rules plus LLM judge plus human-in-the-loop escalation).

All four adoption items are skill-native (MCP Registry Policy bucket 2): pure Markdown guidance with zero new dependencies, outbound calls, or credentials. Phase 1 ships the new `agent-execution-isolation` skill with its `/review security` hook (following the `advanced-attack-patterns` precedent). Phase 2 folds the credential-brokering, egress-boundary, and threat-model-triage content into the three existing skills as sections and cross-links. Phase 3 is the mandatory closing refactor/known-gaps/CI phase.

Success looks like: a user reviewing an agent-running project with `/review security` gets the three-question triage engaged automatically; a user asking "how do I sandbox my agent" or "keep API keys out of the agent container" routes to the new skill first in the trigger evals; the catalog registers 275 skills consistently across the three registry files (the plan's original 271 -> 272 census was stale against the live tree).

Grounding note: no `docs/solutions/` store, no `STRATEGY.md`, and no constitution file exist in this repo; grounding is best-effort and none of these blocked planning.

## Phase 1: New skill: agent-execution-isolation

**Goal**: Ship the `agent-execution-isolation` skill under `catalog/skills/security-operations/` covering the three-layer execution-isolation model, registered in all three data registries, gated by trigger evals, and conditionally engaged from `/review security`.
**Prerequisites**: None.
**Stability Gate**: `make validate` passes (bundle audit, placeholder lint, registry integrity); `python scripts/run_trigger_evals.py` passes with the new skill's positives routing first and its near-miss negatives routing away; the `/review` command file carries exactly one new conditional sentence.
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: Authoring a security skill with a hard routing-eval gate against two adjacent skills (agentic-endpoint-hardening, egress-redaction) is the highest-collision-risk content work in this plan.

### Sub-tasks

#### 1.1 - Author SKILL.md and references

**Objective**: Create `catalog/skills/security-operations/agent-execution-isolation/SKILL.md` teaching the three-layer model, plus reference files for the heavy runbook content.

**Build class**: load-bearing.

**Prompt**:
> In the Nexus-Hub repo, create `catalog/skills/security-operations/agent-execution-isolation/SKILL.md`. It teaches running AI agents inside OS-level execution isolation, structured as three layers: (1) infrastructure - Docker-driven sandbox hardened with Landlock filesystem confinement, seccomp syscall filtering, and network namespaces for egress control, plus per-session ephemeral containers with only explicitly mounted directories; (2) runtime - minimal auditable software inside the loop, removing excess components and unpatched parsers; (3) network - assume the container is compromised and place an out-of-process egress boundary (self-hosted HTTP/HTTPS proxy with static URL rules for low-risk traffic, an LLM judge for unmatched high-risk requests, SSRF/RFC-1918 blocking, audit logging, and human-in-the-loop escalation where an approval can update policy). Include the three-question threat-model triage as a first-class checklist: where does execution happen, what software runs inside the loop, what leaves the boundary. State explicitly that the skill EXTENDS `/review security` when the reviewed project runs or embeds AI agents, gated on an applicability check (does the repo spawn agents, hold agent credentials, or make agent-driven egress calls?), following the `advanced-attack-patterns` framing. Constraints: apply the reverse-engineering attribution rule (generic pattern names only - do NOT name NemoClaw, NanoClaw, CrabTrap, or the source article in the skill body); required frontmatter `name`, pushy `description` with verbatim trigger phrases ("sandbox my agent", "Landlock", "seccomp", "egress proxy for agents", "isolate the agent container", "agent credential isolation") AND a SKIP clause fencing off `agentic-endpoint-hardening` (host config-write trust seam) and `egress-redaction` (agent-applied content policy); quoted `summary_l0` (<=15 words) and `overview_l1` (<=150 words); optional framework fields `mitre_attack`, `d3fend_techniques`, `nist_csf` with a `references/standards.md` documenting the mapping. Body <=500 lines; push the Landlock/seccomp/netns and egress-proxy runbook detail into `references/os-sandboxing.md` and `references/egress-boundary.md`, each referenced from SKILL.md (orphan-bundle audit enforces this). Include When to Use / Instructions / Common Rationalizations (concrete failure modes) / Verification (binary, observable) / Related Skills sections; cross-link [[agentic-endpoint-hardening]], [[egress-redaction]], [[prompt-injection-defense]], [[containerization]], [[ai-agent-governance]]. Do not reproduce the source article's incident anecdotes as fact. No unfilled multi-word angle-bracket placeholders (hard validation error).

### Sub-tasks

#### 2.1 - Credential brokering into agentic-endpoint-hardening (item B, P0)

**Objective**: Document the credential-brokering pattern where the agent environment holds only placeholder credentials and a boundary broker injects real keys into approved egress traffic.

**Build class**: load-bearing.

**Prompt**:
> In `catalog/skills/security-operations/agentic-endpoint-hardening/`, add the credential-brokering pattern: the agent process (assumed compromisable) holds placeholder credentials only; a broker outside the trust seam (gateway proxy or host-side injector) substitutes real API keys solely into egress requests that pass policy, so a hijacked agent cannot exfiltrate keys it never held. Place it as a `references/credential-brokering.md` referenced from SKILL.md if the section exceeds ~40 lines, otherwise as a body section. Cover: placeholder-key wiring, broker placement options (L7 proxy, host wrapper), approval flow for new endpoints, and what this does NOT protect against (the broker itself, approved-destination misuse). Cross-link [[agent-execution-isolation]] for the surrounding sandbox and [[authentication-patterns]]. Also add a one-line cross-reference in `catalog/skills/security/authentication-patterns/SKILL.md`'s Related Skills pointing to agentic-endpoint-hardening for agent-credential isolation. Generic pattern names only; keep both SKILL.md bodies within the size norm; run `make validate`.

---

#### 2.2 - Egress boundary section in egress-redaction (item D, P1)

**Objective**: Add the "content policy vs. network boundary" distinction so agent-applied redaction is never mistaken for a perimeter.

**Build class**: load-bearing.

**Prompt**:
> In `catalog/skills/security/egress-redaction/SKILL.md`, add a section distinguishing the skill's agent-applied typed block/redact/hash/pass policy (a content-level control executed by the agent itself) from an out-of-process network boundary the agent cannot bypass. State the failure mode plainly: an agent-applied policy is a semantic guardrail, and a compromised or injected agent can skip it, so high-stakes deployments need an independent egress control (static rules for low-risk traffic, LLM-judge evaluation for high-risk requests, human-in-the-loop escalation). Point to [[agent-execution-isolation]] (its `references/egress-boundary.md`) for the architecture instead of duplicating it. Keep the addition under ~30 lines; verify the skill's existing trigger evals still pass (`python scripts/run_trigger_evals.py`); run `make validate`.
