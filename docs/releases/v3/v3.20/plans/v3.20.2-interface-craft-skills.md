**Goal**: Close Nexus-Hub's interface-craft gap by shipping five new design skills written originally (not copied), merging recipe-level UI polish into `hallmark-design`, adding a coordinating `interface-review` skill, and promoting two generalizable authoring patterns (rule ownership and honest degradation) into the catalog-wide standard.

## Overview

This plan operationalizes the interface-craft comparison. Nexus-Hub carries 269 skills yet has no dedicated accessibility, typography, color, or interface-copy skill anywhere in the catalog; its three UI-adjacent skills (`frontend-ui-engineering` 132 lines, `hallmark-design` 117, `ui-component-generation` 81) are flat single files with zero bundled references. The comparison source spends 192 KB on exactly that territory at a level of prescription Nexus-Hub does not currently reach (exact CSS values, WCAG thresholds, OKLCH gamut handling) rather than the principle-level advice the existing skills give.

Two of the eleven adoption candidates are structural rather than design-specific and carry the highest leverage in the plan. A **rule-ownership matrix** assigns every overlapping concern to exactly one owning skill and reduces the others to a named handoff, which is what keeps a five-skill cluster from contradicting itself and from restating `frontend-ui-engineering`. A **missing-delegate honesty rule** requires a skill whose delegate is unavailable to say so by name rather than reconstruct the missing rules from memory. Both generalize to every future multi-skill cluster, so they land in Phase 1 before any skill is written.

Every candidate is `skill-native` under the MCP Registry Policy: pure Markdown, zero new outbound calls, zero API keys, zero dependencies, zero third-party data processors. The one dropped item is the source's `npx skills add` distribution channel, rejected under decision-tree tier 5 because Nexus-Hub already owns a superior cross-platform installer. The highest project risk is not technical but legal-adjacent: the source is MIT-licensed, so its attribution requirement collides with Nexus-Hub's Reverse-Engineering Attribution Rule if and only if content is copied. Every authoring sub-task below therefore mandates original writing and forbids reusing the source's prose, tables, examples, and `better-*` skill names. Net catalog change is +6 skills (five domain skills plus the coordinator), not +7, because recipe-level UI polish merges into `hallmark-design` instead of shipping a competing skill.

Grounding note: no `docs/solutions/` store and no `STRATEGY.md` anchor exist, so Phase B.5 grounding was best-effort and non-blocking. Two open constraints from the v3.15 known-gaps file are folded into the authoring sub-tasks: skill `description` fields have a **250-character ceiling** (v3.15.3 NI-1), and `validate_skills.py` strict mode still fails on pre-existing over-long descriptions, so CI runs `--bundles-only` (v3.14.2 WN-1). New skills must fit the ceiling rather than extend the allowlist.

## Phase 1: Authoring-standard foundation

**Goal**: Land the two generalizable authoring patterns and the two review-output conventions before any cluster skill is written, so the cluster arrives conformant rather than retrofitted.

**Prerequisites**: None.

**Stability Gate**: `AGENTS.md` carries a rule-ownership section and a missing-delegate honesty rule; the review-output contract carries the rejected-candidates requirement and the mode-based finding cap; `make validate` passes; no skill file was changed in this phase except where the review contract is authored.

**Recommended model**: Strong reasoning tier, medium effort (Opus class, medium). Rationale: the edit is small in line count but every future skill inherits it, so precision of wording matters more than volume. Re-confirmed by `/implement` against the then-current model set.

### Sub-tasks

#### 1.1 - Add the rule-ownership convention to AGENTS.md (A7)

**Objective**: Give multi-skill clusters a required arbitration mechanism so overlapping skills cannot duplicate or contradict each other.

**Prompt**:
> Add a new authoring rule to `AGENTS.md` in the skill-authoring section (near the existing "Description style: combat undertriggering" and size-norm rules). Requirements:
>
> - State the rule: when two or more skills cover adjacent or overlapping territory, the cluster MUST declare a rule-ownership table naming exactly one owning skill per concern. Non-owning skills reference the owner by skill name and describe only the handoff or the secondary effect; they never restate the owned rule.
> - Require the table to live in the cluster's coordinating skill when one exists, or in `AGENTS.md` itself when the cluster has no coordinator.
> - Give a concrete tie-break example so the rule is actionable rather than abstract: one skill decides WHEN a constraint applies and how severe a violation is, while a second owns MEASURING the constraint and remediating it. Two skills touching one concern is fine; two skills both stating the rule is not.
> - Explain the failure this prevents: without ownership arbitration, a reviewer that loads several overlapping skills reports the same root cause two or three times and the user cannot tell whether that means two problems or one.
> - Keep it platform-agnostic and under roughly 25 lines. Do NOT name any external repository, product, or author (Reverse-Engineering Attribution Rule).
> - Do not modify any `templates/ai-instructions/base-*.md` file. This is an `AGENTS.md` authoring rule, not always-loaded instruction text, so the five-template lockstep does not apply.

---

#### 1.2 - Add the missing-delegate honesty rule (A10)

**Objective**: Prevent a skill whose delegate is unavailable from silently reconstructing the missing rules from memory.

**Prompt**:
> Add a second authoring rule to `AGENTS.md`, immediately after the rule-ownership rule from 1.1. Requirements:
>
> - State the rule: when a skill delegates part of its work to another skill and that delegate is unavailable, the skill MUST mark that portion explicitly as not covered, name the unavailable skill, and continue with the remainder. It MUST NOT reconstruct the delegate's rules from memory, substitute a neighbouring skill, or report coverage it did not achieve.
> - Require the honest-degradation path to be visible in the skill's output, not just in its instructions, so a reader can see which portions were actually covered.
> - Explain the failure this prevents: an agent asked to do a holistic review with one delegate missing will improvise plausible-sounding rules for the gap, and the resulting report reads as complete while the improvised section is unreviewed and possibly wrong.
> - Cross-reference `[[verification-before-completion]]`, which owns the general "do not claim completion without evidence" discipline; this rule is its delegation-specific case.
> - Keep it under roughly 20 lines and platform-agnostic.

---

#### 1.3 - Add the rejected-candidates and finding-cap conventions to the review-output contract (A9, A11)

**Objective**: Make review restraint visible and bound review output volume so a short report is distinguishable from a shallow one.

**Prompt**:
> Add two conventions to Nexus-Hub's review-output guidance. Put them where review skills already look: extend `catalog/skills/code-review/multi-agent-code-review/SKILL.md`'s output contract, and add a short cross-referencing note to `AGENTS.md` so future review skills inherit them.
>
> - **Considered but Rejected (A9)**: a review's output MUST include a table of candidates that were inspected and deliberately not reported, each with the reason (the owning rule permits the current implementation, evidence was insufficient, the project convention is intentional, or the change would add complexity without user benefit). State explicitly that these must be real candidates encountered during the review, never invented filler, and that a genuinely thin scope should report the few that exist and say so.
> - **Mode-based finding cap (A11)**: a review that supports depth modes MUST bind each mode to both a coverage scope AND an output cap: a quick mode reports only the higher severities up to a small cap, a full mode covers the whole requested scope up to a larger cap. Add the explicit anti-padding rule: never pad to reach the cap; a short review or a clean result is a valid outcome.
> - Explain the failure each prevents: without a rejected-candidates table, restraint is invisible and a thorough review that found little is indistinguishable from a shallow one; without a cap, a low-signal review pads itself with cosmetic findings and buries the finding that mattered.
> - Do not change `multi-agent-code-review`'s existing confidence-gating behavior. These conventions are additive.

### Sub-tasks

#### 2.1 - Author the accessibility-engineering skill body

**Objective**: Write the skill originally, at value-level prescription, without reusing source text.

**Prompt**:
> Create `catalog/skills/developer-experience/accessibility-engineering/SKILL.md`. Requirements:
>
> - YAML frontmatter: `name: accessibility-engineering`; a pushy `description` **at or under 250 characters** (v3.15.3 NI-1 ceiling) leading with the action, then trigger phrases ("accessibility", "a11y", "keyboard navigation", "screen reader", "ARIA", "focus state", "WCAG"), then a SKIP clause fencing off general frontend implementation (which belongs to `frontend-ui-engineering`) and visual polish (`hallmark-design`); quoted `summary_l0` (<=15 words) and quoted `overview_l1` (<=150 words).
> - Required body sections in order: title and intro; "When to Use This Skill" with an explicit "When NOT to use"; a Quick Reference table linking every reference file; "Instructions"; "Common Rationalizations"; "Verification"; "Related Skills".
> - Cover, at value-level prescription rather than principle-level advice: semantic structure and accessible names; keyboard operability and visible focus; focus order and focus trapping in overlays; form labelling and error association; assistive-technology behavior; minimum hit-area sizing; and reduced-motion and zoom/reflow requirements.
> - "Common Rationalizations" must cite concrete failure modes, not generic principles. For example: "an icon-only control is obvious from its shape" fails because a screen reader announces nothing without an accessible name.
> - "Verification" must be binary and observable (a named check, an inspectable state, a specific attribute present), never "the UI looks accessible".
> - Ownership boundary per Phase 1: this skill DECIDES when contrast is required and how severe a failure is; `color-systems` (Phase 4) owns measuring the rendered pair and remediating it. This skill owns semantic heading structure; `web-typography` (Phase 4) owns how heading levels render visually. State these handoffs by skill name.

> - Optionally declare `nist_csf` or other framework-mapping frontmatter ONLY if a genuine mapping exists and is documented in a `references/standards.md`; otherwise omit the fields entirely.
> - Keep the body at or under the 500-line size norm; push depth into `references/`.
> - **Attribution constraint (mandatory)**: write every sentence originally. Do NOT copy prose, table structures, worked examples, or code-comment pairs from any external source, and do NOT use `better-*` naming. Domain facts (WCAG thresholds, ARIA semantics) are not copyrightable; specific phrasing and example pairs are.
