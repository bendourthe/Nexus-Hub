## 1. Executive Summary

This is a **re-comparison**. Nexus-Hub first compared itself against Spec Kit at v2.0.0 and surfaced 12 adoption candidates (G1-G12). Between then and now, **all 12 candidates were adopted**, and every P3 backlog item from that report (methodology essay, devcontainer, installer path-traversal test) also landed. The v2.0.0 Spec Kit adoption is therefore **100% complete** (the evidence ledger is Section 2). For several of those candidates Nexus-Hub now exceeds the source: its installer manifest tracks SHA-256 + mtime + a full `FileAction` history with `doctor` / `repair` drift detection, where Spec Kit's manifest tracks hashes only for safe uninstall.

Because the v2.0.0 surface is closed, this report covers the **delta**: what Spec Kit became after v2.0.0. Spec Kit evolved from a tight 9-command SDD workflow into an **extensibility ecosystem**. The new surface area is six systems: a third-party **extension system** (RFC-defined, unsandboxed plugin code, dual curated/community catalogs), a declarative **workflow engine** (10 step types, expression language, persisted resumable state), a **presets** layer (stackable template/command overrides with composition strategies and governance presets), a **self-upgrade** mechanism (`specify self upgrade`), an **authentication framework** (GitHub / Azure DevOps PATs for private remote catalogs), and the shared **catalog-stack + manifest** infrastructure those three catalog systems sit on.

The character of this comparison is the inverse of v2.0.0. Where v2.0.0 surfaced 12 clean, zero-risk, skill-native convention adoptions, the v3.5.0 delta is **dominated by runtime extensibility that moves third-party code and credentials across a trust boundary** -- exactly the surface Nexus-Hub's MCP Registry Policy exists to govern. So the mandatory Security and Reverse-Engineering assessment (Section 6) is the decisive part of this report, not an afterthought. The headline outcome: **2 clean skill-native adoptions, 3 partial / re-engineerable adoptions, and 3 deliberate declines** (one of them a hard policy collision). None of the recommended items introduces a new outbound call, credential, or third-party data processor; the declined items do, and that is precisely why they are declined.

**Overall recommendation: adopt selectively and decline deliberately.** The valuable, policy-clean gaps are *conventions and disciplines* abstracted out of Spec Kit's new machinery -- finer-grained lifecycle hooks on Nexus-Hub's own hook surface, a parity-governance check for the `base-*.md` lock-step constraint, template composition-strategy vocabulary, and catalog-import hygiene. The new *machinery itself* (third-party-code install from a community catalog, the credentialed remote-catalog auth framework) is either reverse-engineered into Nexus-Hub's existing local-first equivalents or dropped under the policy.

## 3. Spec Kit's Post-v2.0.0 Evolution (the new surface)

At v2.0.0, Spec Kit was 9 commands + templates + a 30-agent integration registry. It is now a versioned (`0.10.x`) extensibility platform. Six systems are new or substantially evolved.

| # | System | What it is | Key files (in spec-kit) | Trust-boundary character |
|---|---|---|---|---|
| 1 | **Extension system** | Third-party plugins that add commands, hooks, and templates via an `extension.yml` manifest; installed into `.specify/extensions/`, layered at runtime, discovered through dual catalogs | `extensions/RFC-EXTENSION-SYSTEM.md`, `extensions/EXTENSION-API-REFERENCE.md`, `src/specify_cli/extensions.py` | **High** -- runs third-party code with agent privileges, no sandbox; reads env vars / config |
| 2 | **Workflow engine** | Declarative YAML workflows: 10 step types (command / prompt / shell / gate / if / switch / while / do-while / fan-out / fan-in), Jinja2-like expression language, state persisted to `.specify/workflows/runs/` for resume | `workflows/ARCHITECTURE.md`, `src/specify_cli/workflows/{engine,expressions,catalog,base}.py` | **Medium** -- `shell` and `command` steps invoke arbitrary local processes; inputs/outputs visible downstream |
| 3 | **Presets** | Stackable template + command overrides with composition strategies (`replace` / `prepend` / `append` / `wrap` via `{CORE_TEMPLATE}`), priority ordering; governance presets enforce cross-agent / cross-platform consistency | `presets/ARCHITECTURE.md`, `src/specify_cli/presets.py`, `presets/{lean,scaffold,self-test}/` | **Low** -- static template/command content; embedded scripts inherit caller context |
| 4 | **Self-upgrade** | `specify self upgrade` detects install method (uv-tool / pip / editable), compares versions, reinstalls in place via `uv tool install --force`, verifies | `tests/test_self_upgrade_*.py`, `src/specify_cli/_version.py` | **Low-Medium** -- fetches release metadata from GitHub/PyPI; `GH_TOKEN` only if private |
| 5 | **Authentication framework** | Pluggable provider registry (GitHub Bearer, Azure DevOps Basic-PAT) injecting auth headers for private template / extension / workflow catalog fetches; opt-in via `~/.specify/auth.json` | `src/specify_cli/authentication/{base,github,azure_devops,http,config}.py` | **High** -- plaintext PAT storage; credentials reachable by any extension/script reading env |
| 6 | **Catalog-stack + manifest infra** | Shared base for extension/preset/workflow/integration catalogs: ordered resolution (env -> project -> user -> built-in), HTTPS-only validation, `install_allowed` discovery-only flag, dual curated/community catalogs, SHA-256 manifest for safe uninstall, path-traversal validation | `src/specify_cli/catalogs.py`, `integrations/{catalog,manifest}.py` | **High** -- fetches from remote URLs (with auth headers from system 5) |

Notable signal: Spec Kit's **community catalog now lists a "Loop Engineering extension"** (CHANGELOG `0.10.4`, PR #3002), alongside "Spec Kit TLDR", "MemoryLint", and "Data Model Diagram". Nexus-Hub already ships `loop-engineering` as a native skill. The two projects are converging on the same methodology space from opposite directions: Spec Kit is absorbing loopmaxxing concepts as third-party extensions, while Nexus-Hub encodes them natively as catalog skills.

## 6. Security and Reverse-Engineering Assessment (MANDATORY)

This section is mandatory under the Nexus-Hub adoption discipline and is the decisive part of this comparison. Unlike v2.0.0 (where all 12 candidates were trivially clean), the v3.5.0 delta includes candidates that **cross a trust boundary**: they move third-party code or credentials between the local machine and remote catalogs. Each candidate is run through the MCP Registry Policy decision tree in [AGENTS.md](../../../../../AGENTS.md).

### 6.1 Threat model comparison

| Dimension | Nexus-Hub (current) | Spec Kit's new systems | Adoption delta |
|---|---|---|---|
| New runtime dependencies | Python, Bash, PowerShell, pytest; 6 internal MCP servers (all local) | `uv`/`pipx` CLI, Jinja2-like expression evaluator, remote catalog fetch (`httpx`-style client) | **No new deps** for the recommended convention adoptions (N1a, N2a, N3a, N3b, N6). The extension/workflow/auth *runtimes* would add deps -- and those are the declined items. |
| Outbound calls at runtime | Internal MCPs are local; `nexus-web-fetch` is user-initiated only; installer touches GitHub API for plugin install | Extension/preset/workflow **catalog fetches** to remote URLs; self-upgrade to GitHub/PyPI; auth-framework requests to GitHub / Azure DevOps | **New outbound calls** introduced *only* by N1b, N4, N5, N6-as-remote-fetch. The recommended slices (N1a/N2a/N3a/N3b, and N6 as *local import hygiene*) add none. |
| Credentials / API keys | None for the catalog; `tasks-to-issues` reuses the user's existing `gh auth` | `~/.specify/auth.json` stores GitHub / Azure DevOps PATs in **plaintext**; reachable by any extension or shell step | **New credential surface** introduced by N5 only. No recommended item touches it. |
| Source code / prompts leaving the machine | None except the user's own AI-assistant traffic | Extension code runs with agent privileges and can exfiltrate; workflow `shell` steps run arbitrary commands; catalog fetch leaks private URLs | The third-party-code path (N1b) is an **exfiltration surface**. This is the core reason it is gated/declined. |
| New commercial relationship | None | None intrinsically (GitHub is pre-existing); Azure DevOps would be new for some users | None for recommended items. |

**Conclusion:** every *recommended* item (N1a, N2a, N3a, N3b, N6-as-local-hygiene) sits entirely inside Nexus-Hub's existing local-first posture -- zero new outbound calls, credentials, or processors. Every item that would breach that posture (N1b, N4, N5) is gated or declined below. The split is clean and deliberate.

The capability is already met by Nexus-Hub's skill catalog *with* a pre-install scanner (`skill-security-scan` + `nexus-skill-scanner`) that Spec Kit lacks -- adopting Spec Kit's model would be a trust regression, not a gain. |

## 8. Strengths to Preserve (where Nexus-Hub leads)

- **Pre-install skill-security scanning** (`skill-security-scan` skill + `nexus-skill-scanner` MCP). Spec Kit's extension trust model is catalog curation + an `install_allowed` flag with no scanner. This is a structural advantage and the reason N1b is a decline rather than an adoption.
- **MCP Registry Policy + reverse-engineering matrix.** Spec Kit has no governance over third-party data flow; its new auth framework stores PATs in plaintext. Nexus-Hub's policy is exactly what turns this comparison's risky candidates into clean declines.
- **Installer manifest drift detection** (`doctor` / `repair` / `FileAction` history). Exceeds Spec Kit's hash-only uninstall manifest.
- **Breadth.** 256 skills across 21 categories vs. Spec Kit's single SDD vertical. The two remain complementary, not competing.
- **Three-tier loading model + per-skill bundled resources** with orphan-bundle detection in `make validate`. Spec Kit's commands are flat Markdown.

## 9. Risks and Conflicts

- **No naming collisions.** All recommended items are additive prose/skill/script updates or new local validators; none rename or remove existing commands or skills.
- **Parity-check coupling (N3a).** A `base-*.md` parity validator must tolerate the *intentional* per-platform differences the templates already carry (the lockstep rule is "platform-agnostic changes in lockstep", not "byte-identical files"). The check must compare *structure/section presence*, not raw bytes -- otherwise it produces false positives on every legitimate platform-specific line.
- **Lifecycle-hook scope creep (N1a).** Keep new hook events inside the existing Claude-style model (`SessionStart`/`PreToolUse`/`PostToolUse`/`Stop` semantics). Do **not** import Spec Kit's `.specify/extensions.yml`-style per-command hook registry, which presupposes the declined extension runtime.
- **Decline durability.** N1b and N5 should be recorded in the reverse-engineering matrix (`docs/policy/mcp-reverse-engineering-matrix.md`) with their drop rationale, so a future comparison does not re-surface them as fresh candidates. This is the same discipline that closed G1-G12 cleanly.
- **Breaking changes:** none. The recommended bucket is a backward-compatible **MINOR** bump.
