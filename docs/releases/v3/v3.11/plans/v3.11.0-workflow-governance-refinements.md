# Plan - Workflow-Governance Refinements

**Project**: Nexus-Hub
**Version**: v3.11.0
**Slug**: workflow-governance-refinements
**Filename**: v3.11.0-workflow-governance-refinements.md (release-prefixed per the v3.11.0 naming convention introduced in Phase 1)
**Plan Type**: Feature / Enhancement (with a terminal self-refactor phase)
**Created**: 2026-07-06
**Goal**: Every Nexus-Hub command enforces a well-organized development workflow by default - projects get git + version + branch-model + per-version docs detection and bootstrap; every plan ends with a mandatory architecture-refactor + known-gaps + CI/CD-optimize phase that `/implement` and `/update release` execute; `/compare` security-scans sources before ingest and files reports under `comparisons/`; `/presentify` visually verifies its own output; every install is verified to actually surface the catalog's commands, skills, hooks, and rules on every supported platform (Codex, Antigravity, Cursor, Gemini, Copilot, OpenCode, Claude, ...) across Windows, macOS, and Linux; and the Nexus-Hub repo is migrated to follow all these rules with CI green.

## Overview

This release turns a set of implicit "good practices" into command-enforced defaults across the Nexus-Hub catalog. It touches the whole project lifecycle: bootstrap (`/setup`, `/describe`, `/review`), planning (`/plan`), execution (`/implement`, `/update`), external intake (`/compare`), and artifact publishing (`/presentify`). The unifying idea is that an agent following Nexus-Hub commands should end up with a version-controlled, versioned, branch-disciplined, well-documented, well-organized project without the user having to remember any of it.

Discovery uncovered three structural facts that shape the work. First, three of the "retained skills" the commands delegate to - `setup-project`, `analyze-codebase`, and `implement-phase` - do not exist as files; the v3.2.0 consolidation left their bodies only in git history (`ad8409b~1`). Adding durable, editable behavior to those commands therefore requires reconstituting the delegate skills first. Second, the per-version docs layout is inconsistent even within the repo (`docs/archive/` is grouped by major, active docs are flat), and the layout scheme documented in the skills (`docs/versions/v<MAJOR>/v<SEMVER>/`) matches neither. This release standardizes on `docs/v<MAJOR>/v<MAJOR>.<MINOR>/` (active) and `docs/archive/v<MAJOR>/v<MAJOR>.<MINOR>/` (archive), each with `plans/` and `comparisons/` subdirectories, with patch releases sharing their minor directory. Third, several requested behaviors are genuinely net-new (source-security scanning in `/compare`, a mandatory final refactor phase in every plan, empty-dir / duplicate / orphan / structure-complexity detection in `project-refactor`, and a visual-QA loop in `/presentify`), while a few partially exist and only need promotion from optional to mandatory (the per-phase CI/CD check in `implement-phase`). Discovery also confirmed a fourth, independent structural fact that motivates a dedicated distribution phase: the installer copies the catalog to hardcoded per-platform paths and declares success on a successful copy, never verifying that each platform can actually read the artifacts at its real discovery path - so a global-only install leaves project-only-surface platforms (Antigravity 2.0, which reads slash commands/skills only from an open project's `.agents/`) and format-drifted platforms (Codex, whose custom-prompt contract the installer never re-verifies) silently empty, identically across Windows, macOS, and Linux.

Success is demonstrated end-to-end by running the new behaviors against a scratch project and against Nexus-Hub itself: `/setup` on a bare directory initializes git, sets `v0.1.0`, and creates a `develop` branch plus the per-version docs tree; `/describe` and `/review` report a "Project health" block and offer a `/setup` handoff; a freshly generated plan's last phase is the architecture-refactor + known-gaps + CI/CD phase; `/compare` emits a source-security verdict before ingesting a repo and writes its report to `comparisons/`; `/presentify` renders and screenshots its output and iterates on graphic defects; a fresh global install followed by opening an un-seeded project surfaces Nexus-Hub commands in Codex and Antigravity, `nexus-hub doctor` reports PASS per detected platform against its real read-path, and a cross-platform CI install-smoke asserts every platform's read-path is populated on Windows, macOS, and Linux; and the Nexus-Hub repo is migrated to the new docs scheme with `make validate`, `make lint`, and `make test` green and CI action-minutes measurably reduced.

## Phase 1: Canonical docs-layout scheme

**Goal**: Standardize the per-version docs layout on `docs/v<MAJOR>/v<MAJOR>.<MINOR>/` (active) and `docs/archive/v<MAJOR>/v<MAJOR>.<MINOR>/` (archive), each with `plans/` and `comparisons/` subdirectories and patch releases sharing their minor directory, and make every skill/script/reference that encodes a docs path speak this scheme.
**Prerequisites**: None. This is the shared contract every later phase writes against, so it is first.
**Stability Gate**: `scripts/audit-docs.py` correctly identifies version and topic under two-level nesting (e.g. `docs/v3/v3.10/plans/foo.md` -> version `v3.10`, topic `plans`); no skill, command, style-guide, or reference still states the old `docs/versions/...` or flat `docs/<vSEMVER>/` scheme as canonical; `make validate` passes.
**Recommended model**: Strong reasoning tier (Opus-class), high effort - a path scheme change is a cross-cutting contract; getting it wrong cascades into every later phase and into the Phase 8 migration.

## Phase 3: Mandatory final refactor + known-gaps + CI/CD phase in planning

**Goal**: Every plan `/plan` generates ends with a mandatory final phase - an architecture-refactor review (deprecated/obsolete files, empty dirs, redundant files/dirs, overcomplicated structure -> refactor toward a well-organized, intuitive layout) plus a known-gaps review plus a CI/CD create-or-update-and-optimize step - and every phase's testing sub-task includes creating/updating and optimizing the CI/CD pipeline.
**Prerequisites**: Phase 1 (path scheme, since the plan template references docs paths).
**Stability Gate**: A newly generated plan's final `## Phase N` is the architecture-refactor + known-gaps + CI/CD-optimize phase; each phase's testing sub-task references CI/CD create/update/optimize; the plan template validates.
**Recommended model**: Strong reasoning tier (Opus-class), high effort - this modifies the plan contract that all downstream `/implement` runs consume.
