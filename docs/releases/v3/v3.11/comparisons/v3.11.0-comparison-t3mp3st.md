# Comparison: Nexus-Hub vs elder-plinius/T3MP3ST

**Source**: [`elder-plinius/T3MP3ST`](https://github.com/elder-plinius/T3MP3ST) ("A multi-agent offensive-security framework, built to turn the AI coding agent you already run into a zero-day hunter")
**Source type**: Git repository (full TypeScript/JavaScript application, so the 11-dimension comparison applies, but the meaningful analysis concentrates in the Security-Posture and AI-Configuration dimensions)
**Comparison date**: 2026-07-07
**Nexus-Hub baseline**: v3.11.0 in progress (260 skills, 16 commands, 25 hooks, 23 agents)
**Analysis target**: v3.11.0 adoption cycle
**License**: AGPL-3.0. Primary languages TypeScript (58.9%) and JavaScript (37.3%), with small Python, Shell, C, and Dockerfile shares.

---

## Framing and safety note

This is a **defensive** comparison of an **offensive** tool. T3MP3ST is an autonomous exploitation meta-harness: it orchestrates a swarm of attacker agents through a full cyber kill chain (recon, weaponize, deliver, exploit, install, C2, actions-on-objectives), ships an arsenal of offensive tooling (Sqlmap, Metasploit, Hydra, Nuclei, password spray, hash cracking), and includes a dedicated detection-evasion engine (payload obfuscation, sandbox detection, polymorphic generation, WAF bypass, traffic blending, log sanitization).

Nexus-Hub is the polar opposite: a governed, local-first, zero-outbound-by-default catalog whose security content is entirely **defensive** (the `security` and `security-operations` families cover detection engineering, DFIR, threat hunting, incident response, and AppSec review). The purpose of this comparison is therefore NOT to import offensive capability. It is to (1) categorically decline the offensive runtime on both policy and safety grounds, and (2) harvest the small, defensively-relevant, skill-native methodology that hardens Nexus-Hub against exactly the class of threat T3MP3ST represents.

Every self-reported benchmark number below (for example "90.1% pass@1 on XBEN") is reproduced as the source's own claim, not as an endorsed measurement. The value to Nexus-Hub is in the reporting *discipline*, not the score.

## Executive Summary

The two projects sit on opposite sides of the attacker/defender line, and that polarity governs every conclusion.

- **T3MP3ST is an offensive runtime.** A `TempestCommand` orchestrator runs a tick-based, event-emitting loop that drives eight attacker archetypes (RECON, SCANNER, EXPLOITER, INFILTRATOR, EXFILTRATOR, GHOST, COORDINATOR, ANALYST) through Mission Control, backed by a 35-to-83-tool arsenal, an evasion engine, OPSEC detection-limit controls, a multi-provider LLM router, an Express API on port 3333, a "War Room" web dashboard, and an MCP server exposing a `security_recon` tool. Its headline credential feature is a **keyless mode**: rather than requiring an API key, it connects to a locally-installed Claude Code, Codex, or Hermes agent already running on the operator's machine and uses it as the exploitation brain.
- **Nexus-Hub is a governed defensive catalog.** It distributes 260 skills plus commands, hooks, agents, and rules through an installer into 14+ AI assistants under a deliberate reverse-engineer-first, zero-outbound MCP Registry Policy (`AGENTS.md`), and its security posture is defense-only.

Because of that mismatch, the overwhelming majority of T3MP3ST is **not adoptable, by design**. The autonomous exploitation loop, the attacker swarm, the offensive arsenal, the evasion engine, the OPSEC evasion controls, the C2 phase, and the keyless local-agent-hijack credential model are all declined on two independent grounds: the MCP Registry Policy's prohibition on runtime meta-harnesses / daemons / hosted UIs / outbound service wrappers (the v3.10.0 ruflo precedent, `docs/v3/v3.10/comparisons/v3.10.0-comparison-ruflo.md`), and this environment's explicit refusal of detection-evasion tooling and unauthorized C2 frameworks in a broadly-distributed catalog with no per-use authorization context.

What **is** adoptable is short, defensive, and skill-native:

1. **The "local coding-agent hijack" threat pattern (the flagship, and it is pure defense).** T3MP3ST's keyless mode is a concrete, in-the-wild example of a confused-deputy attack: an external meta-harness commandeers a user's already-running Claude Code / Codex / Hermes agent and drives it to perform offensive work, with no API key and using the user's own model quota and machine trust. A catalog-wide search confirmed this exact vector is **not modeled** in the defensive security skills (the only hijack-adjacent match, `catalog/skills/security/skill-security-scan/references/detection-classes.md`, is about scanning skill *files* for malice, a different threat). Recognizing and hardening against "your local agent as someone else's exploitation brain" is the single highest-value, zero-code import.
2. **The reproducible-benchmark-receipt discipline.** T3MP3ST's stated rule is "no number ships without a reproducible receipt": every headline recomputes from committed JSON artifacts via `npm run verify-claims`, with Wilson-95 confidence intervals. A search of the eval skills returned zero matches for that discipline (`verify-claims`, Wilson intervals, committed-artifact receipts). Folding the receipt-and-interval rule into `skill-eval-loop` and `ai-output-evaluation` is a clean methodological win.
3. **The dangerous-action approval-gate and default-deny-egress framing.** T3MP3ST gates its most dangerous drivers (Metasploit, Hydra) behind explicit human approval and enables egress-scope containment by default (networked tools refuse off-scope public hosts, permitting only in-scope target and private/loopback addresses). Both are defensive control patterns that reinforce and could enrich `agent-access-policy`, `egress-redaction`, and `ai-billing-safeguards`.

A non-adoption meta-finding worth recording: T3MP3ST is, in effect, the **threat actor that Nexus-Hub's defensive skills exist to counter**, and several of its own choices independently validate Nexus-Hub doctrine. Its retirement of the nine "Pliny Special" payload catalogs because they showed "no measured uplift to the benchmark" validates the "curate ruthlessly" plus eval-driven rule this very skill enforces; its honest "unbenchmarked and unproven -- 0 executed exploits in full-chain runs" labeling validates the no-silent-caps honesty rule; and its authorization discipline ("point it only at systems you own or have explicit, written permission to test") is the same posture Nexus-Hub's `pentest-reporting` and `ai-attack-patterns` already carry.

## Step 5: Security and Reverse-Engineering Assessment (MANDATORY)

### 5.1 Threat model comparison

| Factor | elder-plinius/T3MP3ST | Nexus-Hub |
|--------|-----------------------|-----------|
| New runtime dependencies | Node runtime, Express, 48 opt-in offensive CLI adapters (Nmap, Sqlmap, Metasploit, Hydra, etc.), a web dashboard, an MCP server | None required by the catalog itself |
| Outbound-call destinations | OpenRouter / Venice / Anthropic / OpenAI APIs; attacker traffic to target hosts; MCP `security_recon` reconnaissance | None by default (reverse-engineer-first policy) |
| Credentials / API keys | Provider API keys via env vars, OR the keyless mode that borrows a local coding agent's authenticated session with no key at all | None |
| Does source / prompt / query text leave the machine | Yes (model prompts to providers; recon/exploit traffic to targets) | No |
| New commercial relationship required | Optional (keyed providers) or none (keyless local-agent hijack, or fully-offline Ollama) | No |
| Guardrail posture | Offensive by design, with RoE, egress-scope containment, and human approval gates as brakes; ships a dedicated detection-evasion engine | Defensive by design; no offensive or evasion content anywhere in the catalog |

The keyless mode deserves its own line: it is the cleanest real-world instance of the confused-deputy problem for AI coding agents. An external process uses the user's already-authenticated, already-trusted local agent as an execution proxy, inheriting its model access, its filesystem reach, and its network position, with no key and no separate audit trail. That is precisely the trust boundary `prompt-injection-defense` and `agent-access-policy` exist to defend, which is why the defensive recognition of this pattern (C1) is the flagship import while the mechanism itself is a hard decline.

## Steps 6 and 7: Sequencing, Conflicts, and NOT-Recommended Items

### Suggested sequence

The plan is small and entirely defensive by design.

1. **C1 local-agent-hijack recognition**: the one clear defensive gap and the flagship. Add a "your local agent as someone else's proxy" threat pattern to `prompt-injection-defense` (recognition + safe-response), reinforced from `agent-access-policy` (least-privilege containment as the mitigation) and referenced from `ai-attack-patterns` as the offensive counterpart it defends against. Independent of the others.
2. **C2 benchmark-receipt discipline**: fold the "no headline number without a committed, recomputable receipt and a confidence interval" rule into `skill-eval-loop` and `ai-output-evaluation`. Independent.
3. **C3 approval-gate pattern**: add an "irreversible or dangerous local action requires an explicit human approval gate" pattern to `agent-access-policy`, cross-linking `ai-billing-safeguards`. Independent.
4. **C4-C5**: optional, low value, adopt only on explicit maintainer request.

### Conflicts and risks

- **No offensive drift (all Declined items).** The dominant risk in this comparison is scope creep from an offensive source. The mitigation is structural: every offensive component is on the NOT-recommended list with explicit grounds, and the surviving candidates add zero offensive capability. Any future PR that cites this report must not smuggle in exploit, evasion, C2, or the keyless-hijack mechanism under cover of the defensive items.
- **C1 framing.** The hijack pattern must be written as recognition-and-posture (how to notice and refuse being driven as a proxy, plus least-privilege containment), NOT as a description of how to build the hijack. It leans on defense-in-depth (`agent-access-policy` sandboxing, `egress-redaction`), consistent with how `prompt-injection-defense` is already framed.
- **C2 honesty rule.** The receipt discipline should preserve the source's honest-labeling posture ("unbenchmarked and unproven" where true). That reinforces, rather than conflicts with, Nexus-Hub's no-silent-caps rule.
- **No new runtime dependency.** None of C1-C5 introduces a dependency, an outbound call, or a credential. The `verify-claims`-style recompute discipline (C2) is a documented practice, not a shipped harness with vendor coupling.
