# Plan -- Plan/Implement Lifecycle Hardening and Living Docs Architecture

**Project**: Nexus-Hub
**Target version**: v3.21.0
**Slug**: plan-implement-lifecycle-and-docs-architecture
**Rank**: 12 of 17 in [`docs/roadmap-prioritization.md`](../../../../roadmap-prioritization.md)
**Plan Type**: Feature
**Created**: 2026-08-24
**Goal**: `/plan` and `/implement` (plus `/setup`, `/update docs`, `/update refactor`, and `/update release`) produce and enforce a fail-closed last phase, a multi-phase implement driver, and the rd-data-dev living-docs architecture so a completed plan means the original goal landed, not only that every phase checkbox was ticked.

## Overview

The last-phase heading already exists. Execution does not match it. `implementation-plan` licenses a "light, near-no-op pass". The implement runbook accepts `skip <X>` on Phase 9. Recent last phases in this repo recorded no layout moves, no workflow edit, and a handoff to `/update release` without an independent check that the plan's Goal is present in the codebase. Refactoring is proposed and skipped. Human testers are asked to exercise incomplete features after Phase 1. `/implement` still runs one phase per invocation, so the maintainer retypes commit-between-phases then release every time.

This plan hardens the existing commands rather than adding a parallel workflow. Last-phase duties become non-skippable except by recording an explicit known-gap with a reason. Each duty leaves a named evidence artifact; "nothing to change" requires quoted scan output. The last phase reviews the codebase against the plan Goal, reconciles known gaps from this plan and from other still-open known-gaps files, actually runs architecture and docs refactor, checks git-tree hygiene, and only then allows `/update release`. `/implement <plan> in-full` and `/implement <plan> phase-by-phase` encode the long prompt as command arguments. Living `docs/handbooks/` (markdown source of truth, generated HTML, one atlas walkthrough, technical companions for key components), `docs/decisions/`, and the current versioned tree become the required consumer standard, with `testing/` and `validation/` self-gated.

Versioned artifacts stay under `docs/v<MAJOR>/v<MAJOR>.<MINOR>/` in this release. The breaking rename to `docs/releases/` + `docs/archives/` remains owned by [`docs/releases/v4/v4.0/plans/v4.0.0-docs-lifespan-tree-and-enforcement.md`](../../../v4/v4.0/plans/v4.0.0-docs-lifespan-tree-and-enforcement.md). That plan is amended in the same authoring session so it consumes handbooks instead of declining them. Nexus-Hub's own ~700-file container move is not done here.

## Goals First

**Target problem**: Multi-phase work still requires a long hand-written prompt, last-phase duties are skippable in practice, and a plan can be "implemented" while the original goal is missing from the codebase and the docs tree does not match the living-handbook architecture consuming projects should have.

**Primary persona**: A Nexus-Hub maintainer or consuming-project user who drives `/plan` then `/implement` across many phases in one working session.

**Secondary persona**: An agent on a consuming project that only has the installed catalog.

**Observable definition of done**:

- New plans never ask a human to manually exercise an incomplete feature while later phases remain. Automated per-phase tests still run.
- The last phase cannot complete, and `in-full` cannot start `/update release`, without a last-phase evidence file covering refactor, known-gaps (this plan and other open files), docs/handbook architecture, git-tree hygiene, CI/CD, and an independent Goal-vs-codebase review.
- `/implement <plan> in-full` implements every incomplete phase in order, commits at each boundary (commit-only on non-final phases), runs the fail-closed last phase, then hands off to `/update release` behind that command's gates.
- `/implement <plan> phase-by-phase` is the same loop with an explicit continue/pause/push menu after each phase.
- Bare `/implement` stays one-phase. New modes are opt-in.
- `/setup project`, `/plan`, `/implement` last phase, `/update docs`, `/update refactor`, and `/update release` all check and repair the required docs architecture.

## Scope

### In scope

- Fail-closed last-phase contract in `implementation-plan`, `implement-phase` (SKILL + runbook), `/plan`, and `/update release` handoff.
- Independent Goal-vs-codebase review as a last-phase duty.
- Known-gaps reconciliation across the current plan and other still-open `known-gaps.md` files.
- Defer human/manual testing prompts to the last phase only; keep automated per-phase tests.
- `/implement` driver modes `in-full` and `phase-by-phase`.
- Required living docs: `docs/handbooks/` (markdown, generated `html/`, one atlas HTML, technical companion HTML for key components), `docs/decisions/`, living top-level `docs/README.md` / `DEVLOG.md` / `todos.md`.
- Wiring `/setup`, `/plan`, `/implement`, `/update docs`, `/update refactor`, `/update release` to create, refresh, snapshot, and fail-closed-check that architecture.
- HTML walkthroughs via existing `/presentify` (`document-to-interactive-html`). Markdown remains authoritative.
- Amendment of the v4.0.0 docs-lifespan plan so it no longer declines a `handbooks/` equivalent.
- Contract tests, CHANGELOG, roadmap rank, and CI coverage for the new gates.

### Out of scope

- Migrating Nexus-Hub's own `docs/v*` tree to `docs/releases/` + `docs/archives/` (v4.0.0-docs-lifespan).
- Replacing GitHub Actions, adding outbound services, or new credentials.
- Requiring `docs/validation/` (GxP signed protocols) or inventing `docs/testing/` trackers on greenfield libraries.
- Auto-deleting git branches. Hygiene is report-only via `scripts/check_release_preconditions.py --branches --repo-settings`.
- Auto-tagging or auto-pushing a release. `/update release` keeps its confirmation gates.
- Changing v4.0.0-cost-effective-ci-cd's eventual no-push-until-final contract beyond aligning `in-full` non-final commits to commit-only now.

## Phase 1: Fail-Closed Last Phase and Deferred Human Testing

**Goal**: Written last-phase work is done work, measured by evidence, including an independent check that the plan Goal landed.
**Prerequisites**: None.
**Stability Gate**: Generated plans omit "near-no-op" and mid-plan human-test prompts; the implement runbook has no casual `skip <X>` on Phase 9; a last-phase evidence file is required before `/update release`.
**Recommended model tier**: frontier
**Recommended effort level**: max
**Rationale**: Distributed command behavior, high context, and the failure mode is a false "done".

### Sub-tasks

#### 1.1 -- Rewrite the planner last-phase template

**Objective**: `implementation-plan` generates a last phase that cannot be satisfied by existing.

**Failure modes**: malformed plan Goal (review must fail closed and name the missing Goal); unreachable known-gaps files (record the glob result and continue with what was found); conflict between "phase complete" and "Goal missing" (Goal review wins; open a known-gap or block release).

**Build class**: load-bearing.

**Prompt**:
> Update `catalog/skills/workflow/implementation-plan/SKILL.md`. Delete every "light, near-no-op pass" license. Change the Testing continuous guideline so automated tests still end every phase, while human/manual testing suggestions are forbidden until the last phase. Expand the mandatory final phase with these non-skippable sub-tasks, each requiring a named artifact in `<version_dir>/development/last-phase-evidence.md`: (1) architecture refactor via `[[project-refactor]]` and `[[docs-layout-refactor]]` -- run the detectors; an empty finding is allowed only when the scan output is quoted; (2) known-gaps reconciliation for this version AND every other `docs/**/known-gaps.md` whose Status is in-progress or whose Open Items remain -- glob both canonical and legacy layouts; (3) living docs architecture check (handbooks, decisions, generated HTML freshness) as specified in Phase 3 of this plan; (4) git-tree hygiene via `python scripts/check_release_preconditions.py --branches --repo-settings` -- report only, never delete; (5) CI/CD coverage of this plan's files; (6) independent Goal-vs-codebase review -- re-read the plan header Goal and Goals First / DoD, then inspect the codebase as if the phases had not been implemented by this agent; a miss is a blocking finding or a new known-gap, not a pass because phase checkboxes are ticked; (7) human/manual testing suggestions, last phase only; (8) full-suite testing and stabilization. ## Phase 2: Implement Driver Modes

**Goal**: `in-full` and `phase-by-phase` replace the long multi-command prompt.
**Prerequisites**: Phase 1 (last-phase gates exist for the driver to stop on).
**Stability Gate**: Argument resolution documents both modes; non-final `in-full` commits are commit-only; last phase still requires the evidence file before `/update release`.
**Recommended model tier**: frontier
**Recommended effort level**: max
**Rationale**: Auto-commit loops and release handoff have high blast radius.

### Sub-tasks

#### 2.1 -- Dispatcher arguments

**Objective**: `/implement` recognizes driver modes without becoming a fat command.

**Failure modes**: unknown second token (show usage, do not start a phase); plan slug that contains "full" as a substring (match whole tokens `in-full`, `full`, `phase-by-phase` only); missing plan (same discovery as today).

**Build class**: load-bearing.

**Prompt**:
> Update `catalog/commands/implement.md` argument resolution. Keep current one-phase behavior for bare `/implement`, `/implement <slug>`, `/implement <path>`, `/implement <slug> phase-N`, and `/implement <slug> next`. Add driver modes as a later positional token, not as the first argument: `/implement <slug-or-path> in-full` (alias `full`) and `/implement <slug-or-path> phase-by-phase`. Document that `in-full` implements every incomplete phase in order, commits at each successful boundary (commit-only on non-final phases; no push), runs the fail-closed last phase, then hands off to `/update release` with its confirmation gates. Document that `phase-by-phase` is the same loop but stops after each phase with: (1) commit and continue; (2) commit, push, and continue; (3) commit and pause; (4) commit, push, and pause; (5) other. Keep the dispatcher thin; the loop lives in `implement-phase`. Preserve model-routing pre-flight per phase. Note Cursor/OpenCode/Copilot have no scriptable model switch. Acceptance: the command file lists the tokens and aliases; it does not inline the nine-stage runbook.
