**Goal**: Give Nexus-Hub a deterministic, model-free, CI-safe skill trigger-and-routing quality gate (catalog-wide description near-collision detection plus per-skill routing assertions), close two smaller validator gaps (unfilled-placeholder lint, behavioral-eval schema interop), and extend the platform roster (Hermes plus a shared `.agents/skills/` path), so the 267-skill catalog is defended against the under/over-triggering failure mode that no current check catches.

## Overview

This plan operationalizes the awesome-llm-apps comparison. That comparison found that Nexus-Hub is at or ahead of parity with the source on almost every dimension, with exactly one genuine, uncaught gap: there is no automated test anywhere in the catalog that detects when two skill descriptions near-collide or that verifies a prompt routes to the intended skill. At 267 skills across 21 categories, description collision is a live routing-safety risk, and the current defenses (the `skill-description-authoring` skill, `optimize_skill_description.py`, and the AGENTS.md "pushy descriptions" guidance) are all authoring-time advice, not a deterministic gate.

The plan is sequenced reverse-engineer-first, exactly as the comparison's Step 5.4 ordering requires. Phase 1 builds the highest-value, lowest-risk item (A1, the catalog-wide description-collision detector) as a new stdlib-only script, shipped warning-only first so its findings can be triaged before it becomes a hard gate. Phase 2 folds the cheap unfilled-placeholder lint (A3) into the existing `validate_skills.py`. Phase 3 extends the Phase 1 runner with optional per-skill `trigger-cases.json` routing assertions (A2), CI-warning on skills that lack cases so the catalog never blocks on incomplete coverage. Phase 4 aligns `skill-eval-loop`'s behavioral `evals.json` to the skill-creator schema for external-tool interop (A4). Phase 5 adds the Hermes integration and a shared-project `.agents/skills/` write path (A5). Phase 6 is the mandatory terminal refactor, known-gaps reconciliation, and CI/CD pass.

Every adoption item is `re-full` per the comparison's reverse-engineering assessment: pure local Python stdlib, zero outbound calls, zero new dependencies, zero new credentials. Success looks like a green `make validate` where the trigger-and-routing gate runs across all 267 skills with a tuned allowlist of intentional near-neighbors, a placeholder lint that catches scaffolded-but-unfinished skills, a documented per-skill trigger-cases convention with a first tranche authored, an interoperable behavioral-eval schema, and Hermes in the platform roster. The distributed artifacts must use generic descriptive names and must not reference the source repository or the upstream patterns it credits, per Nexus-Hub's reverse-engineering attribution rule; attribution stays in the comparison report and the reverse-engineering matrix.

## Phase 1: Catalog-wide trigger-and-routing eval (A1)

**Goal**: Ship a deterministic, model-free, stdlib-only detector that flags any two skill descriptions sharing too much trigger vocabulary across the whole 267-skill catalog, warning-first and then promoted to a tuned CI gate.
**Prerequisites**: None.
**Stability Gate**: The detector runs over all 267 skills via `make validate`; its first-run findings are triaged into real collisions (fixed) versus intentional near-neighbors (allowlisted); the gate is green with the allowlist in place and is registered in both installers, the Makefile, and CI.
**Recommended model**: Strong reasoning tier, high effort (Opus 4.8). Rationale: a new catalog-wide capability whose threshold and stopword tuning is judgment-heavy and whose output becomes a merge gate; default to the strong tier per the no-degradation guarantee. Re-confirmed by /implement against the then-current model set.

### Sub-tasks

#### 1.1 - Build the collision-detection script

**Objective**: Create a new stdlib-only script that tokenizes every skill's `description` frontmatter and flags near-collisions.

**Prompt**:
> Create `scripts/run_trigger_evals.py` (Python 3 stdlib only - `json`, `math`, `os`, `re`, `sys`, `argparse`; no third-party imports). It must:
> 1. Walk `catalog/skills/<category>/<name>/SKILL.md`, parse the YAML frontmatter (reuse the frontmatter parser already in `scripts/validate_skills.py` - import it or mirror its approach; do NOT add pyyaml), and extract each skill's `description` field.
> 2. Tokenize each description: lowercase, split on non-alphanumerics, drop a stopword set and tokens shorter than 3 chars, apply a light suffix stemmer (ing/ed/es/s) so "projects"/"project" and "finished"/"finish" match.
> 3. For every pair of skills, compute vocabulary overlap as `|A intersect B| / min(|A|, |B|)` and report any pair above a configurable threshold (default 0.5) as a near-collision, printed as `FAIL descriptions near-collide: <a> vs <b> (<pct>% shared vocabulary)`.
> 4. Support `--threshold`, `--json`, and an allowlist file path (default `scripts/run_trigger_evals.allowlist.json`) whose entries are intentional near-neighbor pairs that are downgraded from FAIL to an informational line.
> 5. Exit 0 when clean (or warning-only mode), non-zero when un-allowlisted collisions exist in gate mode (`--strict` or a `--gate` flag; default is warning-only).
> Naming and attribution constraint (MANDATORY per AGENTS.md reverse-engineering attribution rule): use generic descriptive names throughout ("trigger and routing eval", "description near-collision"). Do NOT name any external repository, product, author, or upstream metric anywhere in the script, its docstring, or its comments. This is a reverse-engineered local artifact; the source attribution lives only in the comparison report and the reverse-engineering matrix.
> Acceptance: `python scripts/run_trigger_evals.py --json` runs over all 267 skills and emits a structured report of collision pairs with percentages.

Record every (b) as a triaged pair for the allowlist in 1.3. Summarize counts of each class.

## Phase 2: Unfilled-placeholder lint (A3)

**Goal**: Extend `validate_skills.py` to catch unfilled angle-bracket template placeholders in a skill's description and body, so scaffolded-but-unfinished skills cannot pass validation silently.
**Prerequisites**: None (independent of Phase 1, sequenced after it per RE-first ordering and because both touch skill frontmatter).
**Stability Gate**: The lint runs as part of `make validate`, flags a fixture skill with an unfilled `<placeholder>` in both description and body, and produces zero false positives on the real 267-skill catalog (single-word CLI notation like `<path>` and HTML tags are correctly excluded).
**Recommended model**: Mid tier, medium effort (Sonnet 5). Rationale: a bounded regex addition to an existing, well-understood validator; low risk, no new architecture. Re-confirmed by /implement.

### Sub-tasks

#### 2.1 - Add placeholder detection to the validator

**Objective**: Detect multi-word angle-bracket placeholders in description and body while excluding legitimate CLI notation and HTML.

**Prompt**:
> Extend `scripts/validate_skills.py` to detect unfilled template placeholders. A placeholder is a multi-word lowercase angle-bracket span in prose (for example `<what this skill does>`); single-word forms like `<path>` are legitimate CLI-usage notation and must NOT be flagged, and HTML tags never contain multi-word lowercase prose. Apply the check to both the `description` frontmatter field (as an error, since a scaffolded description must never ship) and the SKILL.md body prose (excluding fenced code blocks and inline-code spans, which legitimately contain example placeholders). Return the finding through the existing error/warning channels: description placeholders as errors, body placeholders as errors, consistent with the validator's current severity model and the allowlist/grandfathering behavior already present. Keep the regex tight to avoid false positives on the real catalog.

---

#### 2.2 - Run over the catalog and triage

**Objective**: Confirm zero false positives on the real catalog and fix any genuine unfilled placeholders it finds.

**Prompt**:
> Run the extended `validate_skills.py` over all 267 skills. For every placeholder it flags, confirm it is a genuine unfilled scaffold (fix the SKILL.md in place) versus a false positive (tighten the regex until the false positive is gone without losing true detections). The end state is zero placeholder findings on the real catalog and a fixture skill (added in 2.3) that the lint correctly catches.

#### 2.3 - Testing and Stabilization

**Objective**: Generate and run all tests for this phase. Iterate until the phase is stable before advancing to Phase 3.

**Prompt**:

Run the full validator test suite, fix failures, iterate until green. ## Phase 3: Per-skill trigger-cases and routing assertions (A2)

**Goal**: Define a per-skill `trigger-cases.json` convention and extend the Phase 1 runner to verify, for each skill that has cases, that positive prompts out-rank near-miss negatives and route to the intended skill first; CI warns (never fails) on skills lacking cases.
**Prerequisites**: Phase 1 (shares the `run_trigger_evals.py` runner and its tokenizer/scorer).
**Stability Gate**: The runner consumes optional `catalog/skills/<cat>/<name>/evals/trigger-cases.json`; a first tranche of cases is authored for the highest-traffic and most-collision-prone skills surfaced in Phase 1; the runner passes those, warns on skills without cases, and the convention is documented in AGENTS.md.
**Recommended model**: Strong reasoning tier, high effort (Opus 4.8). Rationale: designing the case schema and the lexical routing assertion is judgment-heavy, and authoring good positive/near-miss cases requires catalog understanding; default strong. Re-confirmed by /implement.

### Sub-tasks

#### 3.1 - Define the trigger-cases schema and convention

**Objective**: Establish the file format and location for per-skill trigger cases and document it.

**Prompt**:
> Define a `trigger-cases.json` schema and location convention: `catalog/skills/<category>/<name>/evals/trigger-cases.json`. The schema is a JSON object with a `skill` field, a `purpose` field, and a `cases` array; each case has `id`, `prompt`, `should_trigger` (boolean), an `assert` string describing the expected routing behavior, and an optional `lexical` boolean (default true; `lexical: false` cases trigger via reasoning, not description vocabulary, and are skipped by the deterministic runner and left for behavioral evals). Document the convention in AGENTS.md under the skill-authoring section (the "Adding a New Skill" area and/or the per-skill bundled-resources subsection), noting that cases are optional, live under the skill's `evals/` subdir, and are consumed by `run_trigger_evals.py`. Confirm this bundled `evals/` subdir does not conflict with the existing orphan-bundle audit (evals/ files are referenced by the runner, not by SKILL.md; adjust the audit's exemptions if needed so `evals/` is not flagged as an orphan).

---

#### 3.2 - Extend the runner to consume cases and assert routing

**Objective**: Add positive/negative routing verification to the Phase 1 runner.

**Prompt**:
> Extend `scripts/run_trigger_evals.py` to, for each skill with a `trigger-cases.json`, score each case's prompt against every skill's description tokens (reusing the Phase 1 tokenizer and scorer) and assert: (a) with 2+ skills, a `should_trigger: true` case must rank its own skill first (else FAIL, printing which skill it mis-routed to); (b) the weakest positive must clear the strongest near-miss negative by a configurable margin (default 1.15x). Skip `lexical: false` cases. Skills without a `trigger-cases.json` emit a WARN (never a FAIL) so the catalog never blocks on incomplete coverage. Keep the same warning-only vs gate posture as Phase 1.

---

#### 3.3 - Author the first tranche of cases

**Objective**: Write trigger-cases for the highest-value skills first.

**Prompt**:
> Author `trigger-cases.json` for a first tranche of skills, prioritized by (1) the skills involved in the near-collision pairs surfaced in Phase 1 and (2) the highest-traffic commands/skills (the dispatchers behind `/plan`, `/implement`, `/review`, `/compare`, `/update`, and the most-invoked ai-development and workflow skills). Each file needs at least three positive cases (real phrasings a user would type) and three near-miss negatives (look-alike requests that must NOT trigger, drawn from the skill's own SKIP clause). Run the runner and confirm the tranche passes; leave the rest of the catalog on the WARN path for incremental authoring in later releases. Log explicitly how many skills have cases versus how many are still on the WARN path, so the coverage gap is visible and not silently understated.

---

#### 3.4 - Testing and Stabilization

**Objective**: Generate and run all tests for this phase. Iterate until the phase is stable before advancing to Phase 4.

**Prompt**:
> Add pytest cases for the routing assertions: fixtures with a positive that correctly ranks its own skill first (pass), a positive that mis-routes (fail), a positive that fails the near-miss margin (fail), a `lexical: false` case (skipped), and a skill with no cases (WARN, exit still 0 in warning mode). Run the suite, fix failures, iterate until green. Update CI/CD to run the extended eval, keeping the Phase 1 path filters and caching; confirm the WARN-on-missing path does not fail CI. Do not proceed to Phase 4 until this phase is fully tested and verified. After all tests pass, run `/generate-session-history` to document Phase 3.
