# Plan - Platform Feature Parity (All Addressable Gaps)

**Project**: Nexus-Hub
**Version**: v3.15.0
**Slug**: platform-parity-all-gaps
**Plan Type**: Feature
**Created**: 2026-07-19
**Goal**: Every supported platform receives all Nexus-Hub surfaces it is actually capable of consuming (skills, commands, agents, rules, hooks), not just an instruction file - so Cursor, OpenCode, Qwen, Kimi, and Copilot reach Claude-level coverage where their read-contracts allow, verified against each platform's current docs.

## Overview

Today only Claude receives the full set of Nexus-Hub surfaces; every other platform is a thin `runner.py` call whose breadth is decided by a small `config` dict in its `scripts/lib/integrations/<name>.py` subclass. The platforms have since converged on shared discovery paths (`~/.agents/skills`, `.agents/skills`, `~/.claude/skills`) and several now natively support far more than Nexus-Hub delivers: Cursor supports skills-as-files, `hooks.json`, agents, and project commands; OpenCode supports an agents folder and `plugins/` (hooks); Qwen and Kimi are Gemini-CLI-class forks that plausibly support TOML commands and a skills folder; Copilot supports a broader project skills surface than the current `core-developer`-only opt-in. This release closes all addressable gaps.

Because the base class tree already supports every surface via config keys (`skills_subdir`, `commands_subdir`, `agents_subdir`, `rules_subdir`, `hooks_subdir`), `wire_project_surfaces()`, the `_catalog_adapters` flatten/command-skill machinery, and the `antigravity2` `hooks.json` precedent, this is overwhelmingly per-subclass configuration plus a few small custom writers - no base-class rewrite. Two config keys (`hooks_supported`, `permissions_file`) are declared on every subclass but never read; this release either wires them up (gate hook installation on `hooks_supported`) or removes them, ending the dead-metadata ambiguity. The riskiest reclassification (Qwen/Kimi) is gated behind a mandatory read-contract web re-verification so we never ship a path a platform changed.

This plan depends on v3.14.5's foundations: the DRY `platform-read-contracts.json` (this release adds the newly-parity surfaces to it) and the runner structured-summary channel (so the new surfaces show correctly in the per-platform checklist). Success looks like: a side-by-side install where Cursor/OpenCode/Qwen/Kimi/Copilot each show a fuller checklist matching their verified read-contract, the runtime `[verify]` pass covers the newly-parity platforms, and the contract doc + JSON reflect the confirmed 2026 formats. No skills are added (so `data/` registry files are untouched), and no `base-*.md` template changes (so `check_base_template_parity.py` stays green).

## Phase 1: Capability model and read-contract web re-verification

**Goal**: Give the integration layer a real capability signal (consume or remove `hooks_supported`/`permissions_file`) and web-verify each target platform's current discovery format, writing the confirmed paths into `platform-read-contracts.json` so the later phases build on verified facts, not assumptions.
**Prerequisites**: v3.14.5 shipped (provides `platform-read-contracts.json` and the runner summary channel).
**Stability Gate**: `hooks_supported` (and `permissions_file`) are either read by base machinery (hook installation gated on the flag) or removed with the callers updated; a documented web re-verification of Cursor, OpenCode, Qwen, Kimi, and Copilot has updated `platform-read-contracts.json` with confirmed paths/formats and a fresh verification marker; the Qwen/Kimi "is it Gemini-CLI-class?" decision is recorded (drives Phase 4); `verify_platform_contracts.py` and `make validate` pass.
**Recommended model**: Strong reasoning tier (Opus-class), high effort. Rationale: changing base capability semantics affects every subclass, and the web-verification outcome gates a downstream reclassification, so a wrong call here propagates.

### Sub-tasks

#### 1.1 - Resolve the dead capability keys

**Objective**: End the `hooks_supported` / `permissions_file` dead-metadata ambiguity.

**Prompt**:
> In `scripts/lib/integrations/`, decide and implement the fate of the `hooks_supported` and `permissions_file` config keys, which every subclass declares but `base.py`/`runner.py`/`lifecycle.py` never read. Preferred: make `hooks_supported` load-bearing - base hook installation (a `hooks_subdir` copy or a custom `hooks.json` writer) only runs when `hooks_supported` is true, so a platform's capability is declared in one place. If a key has no future use, remove it from every subclass config and note it. Do NOT change what any platform currently writes (Claude's hooks path is unaffected). Add a test asserting a subclass with `hooks_supported:false` writes no hook surface and one with true does. Acceptance: the capability keys are either consumed with a test or removed cleanly; existing behavior is byte-identical.

#### 1.2 - Web-verify each target platform's current format

**Objective**: Confirm the 2026 discovery paths/formats for Cursor, OpenCode, Qwen, Kimi, and Copilot before writing their surfaces.

**Prompt**:
> Run the `[[platform-contract-verification]]` procedure (Step 2 web re-verification) for Cursor, OpenCode, Qwen, Kimi, and Copilot. For each, confirm from official docs: skills path + layout (flattened vs nested; does it read `~/.agents/skills` / `.agents/skills` / `~/.claude/skills`?), commands path + format (md / toml / prompt / slash), agents path, rules path, and hooks path + schema. Specifically resolve: does Cursor read a skills folder and a `hooks.json`, and where; does OpenCode read `agents/` and `plugins/`; are Qwen Code and Kimi Code CLI Gemini-CLI-class (TOML commands in `~/.<tool>/commands/`, a skills folder) or genuinely instruction-file-only; and Copilot's project skills path (`.github/skills` vs `.agents/skills`). Record every finding with its source URL in `docs/policy/platform-read-contracts.md` and update `platform-read-contracts.json` accordingly, classifying each as MATCH / DRIFT / UNVERIFIED. Acceptance: the JSON + doc carry verified paths for all five platforms with source URLs, a fresh verification marker, and an explicit Gemini-CLI-class verdict for Qwen and Kimi.

#### 1.3 - Record the reclassification decision

**Prompt**:

This is the gate Phase 4 reads. Acceptance: an unambiguous go/no-go recorded for each of Qwen and Kimi, with the deciding evidence cited.

## Phase 2: Cursor parity

#### 2.2 - Add a Cursor hooks.json writer
