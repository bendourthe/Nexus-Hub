# Plan - agentic-endpoint hardening (sandbox-escapes adoption)

**Project**: Nexus-Hub
**Version**: v3.15.6
**Slug**: adoption-sandbox-escapes
**Plan Type**: Feature (security hardening)
**Created**: 2026-07-23
**Seeded from**: docs/v3/v3.15/comparisons/v3.15.6-comparison-sandbox-escapes.md
**Goal**: Close the config-write-then-executed trust-seam gap that Nexus-Hub's own distributed artifacts (.claude hook configs, git hooks, .cursor/.vscode surfaces) expose, by shipping a threat-model skill, advisory hook enforcement, and opt-in hard enforcement plus best-effort seam monitoring.

## Overview

This plan operationalizes the "Week of Sandbox Escapes" comparison. The unifying finding is that the agent rarely breaks a sandbox directly; it writes a file (a `.claude` hook config, a VSCode task, a virtualenv interpreter, a git fsmonitor hook, a "safe" command hiding dangerous args) that a trusted component outside the sandbox later runs. One of the seven CVEs (CVE-2026-48124) names Nexus-Hub's own distribution channel - workspace-controlled `.claude` hook configs - as the attack surface. Nexus-Hub's deny-by-default doctrine largely exists in `agent-access-policy`, but enforcement and monitoring of the specific config-write-then-executed seam are absent, and the distributed default permission stub is allow-only.

The adoption is entirely local: no candidate introduces a new outbound call, API key, third-party data processor, or runtime dependency. The single item that would (the vendor's commercial endpoint product) is dropped under the MCP Registry Policy hard-no list, and its valuable concept (provenance plus seam monitoring) is reverse-engineered locally as a best-effort ledger with an honest boundary. Candidates order by reverse-engineering bucket: skill-native foundation first (AC1, AC7, AC6 guidance), then local hook and installer builds (AC2, AC4, AC6 deny globs, AC5, AC3).

Note on co-location: this plan's adoption target is v3.15.6, matching its comparison (re-slotted from v3.17.0 into the v3.15.x line by user decision). It shares the v3.15 minor tree with the other v3.15 files (no-ai-slop v3.15.3, presentify v3.15.4, model-prompting-research v3.15.5), each as a separate plan file. Success looks like: a new agentic-endpoint-hardening skill, execution-trigger config paths covered by the advisory hook (with cross-platform `.ps1` parity and tests), a hardened git-guardrails denylist, an opt-in deny-by-default permission stub behind an installer flag, and a best-effort file-provenance ledger - none of which sends anything off the machine.

**Goal**: Establish the canonical execution-trigger-path list, the escape taxonomy, the layered control model, and the vendor-question checklist as a new skill that every enforcement item references.

## Phase 2: Advisory enforcement

**Goal**: Cover the escape config paths in the advisory hook and harden the git denylist for the git-metadata-indirection escape, with cross-platform parity and tests.
**Prerequisites**: Phase 1 (reuses the canonical path list).
**Stability Gate**: `escalation-trigger.sh` warns on every path in the canonical list; `git-guardrails.sh` flags `git -c core.hooksPath=` and `git -c core.fsmonitor=`; both hooks have a `.ps1` sibling with matching behavior and passing pytest coverage; `make lint` and `make test` pass; the hooks do not self-block Nexus-Hub's own `nexus-hub init` writes.
**Recommended model**: Strong reasoning tier, high effort (Opus 4.8, high). Rationale: security hook logic with a real false-positive cost, plus creating cross-platform `.ps1` siblings that must match the bash behavior exactly.

### Sub-tasks

#### 2.1 - Extend escalation-trigger to cover execution-trigger config paths (AC2)

**Objective**: Add the canonical escape config paths to the sensitive-path advisory hook, on both platforms, with tests.

**Prompt**:
> Extend `catalog/hooks/escalation-trigger.sh` so its sensitive-path list also covers the canonical execution-trigger config paths from the Phase 1 skill: `.claude/settings*.json`, `.claude/hooks/*`, `.vscode/tasks.json`, `.vscode/launch.json`, `.git/hooks/*`, `core.hooksPath`, `core.fsmonitor`, `.cursor/*`, and virtualenv interpreter paths. Keep the default action `warn` (advisory), NOT `block`, so the catalog's own wiring is not self-blocked, and add logic (or a documented default-warn carve-out) so Nexus-Hub's own `nexus-hub init` writes to `.claude/settings.json` do not trip a spurious warning. Create the PowerShell sibling `catalog/hooks/escalation-trigger.ps1` with matching behavior (no `.ps1` exists yet, so this is net-new parity, following the four-hook diff-review precedent). Add pytest coverage under `catalog/hooks/tests/` asserting each new path triggers the advisory and that an init-owned write does not. Follow the bash safety rules (`set -euo pipefail`, errors to stderr).

**Objective**: Add the git-metadata-indirection patterns and document the denylist limitation.

**Prompt**:

## Phase 3: Hard enforcement and monitoring

**Goal**: Ship an opt-in deny-by-default permission stub behind an installer flag, and a best-effort file-provenance / trust-seam ledger, without regressing the no-prompt install UX.
**Prerequisites**: Phase 2 (AC5 reuses AC2's canonical path list).
**Stability Gate**: An opt-in `--strict-permissions` / `-StrictPermissions` flag exists in BOTH `scripts/installer.sh` and `scripts/installer.ps1` and installs a deny-by-default permission stub reusing the canonical path list; the default install remains allow-only and no-prompt; a PostToolUse provenance-ledger hook is registered in `catalog/hooks/settings.json` with a `.ps1` sibling and pytest coverage, logs only paths and content hashes (never secrets or file bodies), and is scoped to the current session; `make validate`, `make lint`, `make test` pass.
**Recommended model**: Strong reasoning tier, high effort (Opus 4.8, high). Rationale: installer edits on both platforms (ask-first surface, authorized by the comparison's Full scope), a new PostToolUse hook, and egress-redaction discipline make this the heaviest and riskiest phase.

### Sub-tasks

#### 3.1 - Opt-in deny-by-default permission stub behind an installer flag (AC5)

**Objective**: Offer a hardened permission posture without changing the convenience default.

**Prompt**:
> Add an opt-in deny-by-default permission stub. Create the stub config (a sibling to `configs/permissions/claude-permissions.json`) whose deny/ask entries reuse the canonical execution-trigger path list from Phase 1, with `defaultMode` set to ask/deny rather than auto-approve. Add a `--strict-permissions` flag to `scripts/installer.sh` AND a `-StrictPermissions` flag to `scripts/installer.ps1` (both installers must gain the flag in lockstep, per the installer-aware rule) that installs the strict stub instead of the default allow-only stub. Preserve the existing no-prompt, install-all default: without the flag, behavior is unchanged. Document the deliberate posture split (convenience default, security-hardened opt-in) in the Phase 1 skill and the CHANGELOG. This edits the installers (an ask-first surface); it is pre-authorized by the comparison's Full scope, but confirm the exact flag names and stub contents before writing.

---

#### 3.2 - Best-effort file-provenance / trust-seam ledger hook (AC3)

**Objective**: Correlate agent file writes with later execution, locally and within redaction discipline.

**Prompt**:
> Create a new PostToolUse hook (bash + `.ps1` sibling) under `catalog/hooks/` that maintains a best-effort file-provenance / trust-seam ledger: on a Write/Edit it records the path and a content hash (NEVER the file body or any secret, per `egress-redaction` discipline); on a later Bash command it flags when the command executes a path that was recently agent-written. Register the hook in `catalog/hooks/settings.json` under the appropriate PostToolUse matcher. Bound it: log paths and hashes only, cap correlation to the current session, and keep per-write overhead small. Document the honest boundary in the Phase 1 skill: a local hook cannot instrument every trusted external executor the way a dedicated endpoint agent can; this is the reverse-engineered `re-partial` capability, and the un-achievable cross-executor instrumentation is explicitly out of scope. Add pytest coverage. Follow the bash safety rules and the hook conventions (errors to stderr, exit-0 advisory unless configured otherwise).

---

#### 3.3 - Testing and Stabilization

**Objective**: Prove hard enforcement and monitoring work and CI covers them.

**Prompt**:
> Run `make validate`, `make lint`, and `make test`. Do a throwaway-directory dry-run install BOTH ways: default (confirm allow-only, no-prompt, unchanged) and with `--strict-permissions` / `-StrictPermissions` (confirm the strict stub lands at the expected path). Confirm the provenance-ledger hook registers, logs only paths and hashes, flags an execute-recently-written-path scenario, and never records secrets or file bodies. Update CI/CD to cover the new hook and the installer flag (path-filtered to `catalog/hooks/**`, `configs/**`, `scripts/installer.*`), optimized. Iterate until clean. After all checks pass, run `/generate-session-history` to document Phase 3.
