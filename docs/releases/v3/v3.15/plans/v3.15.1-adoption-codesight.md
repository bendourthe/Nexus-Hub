**Goal**: Extend the existing local-only `nexus-code-search` extension with framework-aware structured extraction (routes, schema, env, middleware, events, components) and a deterministic, committed context-map generator that seeds an AI session cheaply, so Nexus-Hub owns the "compile the codebase into an AI-context map" capability end to end. Definition of done combines a measured token-reduction ratio validated by a deterministic benchmark on real repos AND verified extractor accuracy (recall on fixtures, zero false positives).

## Overview

Nexus-Hub already owns the hard substrate of a deterministic code-context engine. `nexus-code-search` v2.0 ships a tree-sitter AST graph across twelve languages, symbol-level impact radius (`code_impact`), a filesystem watcher (`watch_for_changes`), reverse-import affected-tests (`code_affected_tests`), and content-hash incremental indexing. What it lacks, and what the CodeSight comparison surfaced, is two things: framework-aware structured extraction (HTTP routes across many frameworks, ORM schema with relations, env-var audit, middleware, events, components) and a compiled, committed context-map artifact that an AI reads once at session start instead of re-exploring files every session. Nexus-Hub's current equivalent (`/describe`, `analyze-codebase`) is LLM-native and pays that exploration cost on every session.

This plan builds both, entirely inside `extensions/nexus-code-search`, so it adds no new outbound call, no new dependency beyond what the extension already carries, and no credential. Every capability is reverse-engineered into the local extension per the MCP Registry Policy (tier 3, `re-full`): the external tool is MIT and fully local, so a direct dependency on it is rejected in favor of an owned reimplementation. Shipped artifacts use generic descriptive names and carry no external-source attribution, per the Reverse-Engineering Attribution Rule; provenance is recorded in the reverse-engineering matrix row.

Success is observable on two axes. First, a deterministic benchmark reports a token-reduction ratio (the compiled map versus simulated manual exploration) measured on at least three real repositories, including Nexus-Hub itself. Second, the extractors are validated against per-language fixtures with a recall figure per section (routes, schema, env) and a hard zero-false-positive gate, mirroring the accuracy-harness discipline the comparison observed in the source. The compiled map is emitted to a neutral path (`.nexus/CONTEXT-MAP.md` and a `.nexus/context/` article set), never to `CLAUDE.md` or `AGENTS.md`, which Nexus-Hub already owns as pushed installer templates.

## Phase 1: Compiled context-map generator + one-shot CLI (A, H-cli)

**Goal**: Compile the data `nexus-code-search` already has (symbols, modules, import edges) into a deterministic, committed `.nexus/CONTEXT-MAP.md` plus a `.nexus/context/` article set, exposed as an MCP tool and a `nexus-hub map` one-shot, emitted to a neutral path that never touches CLAUDE.md or AGENTS.md.
**Prerequisites**: None (builds on the existing v2.0 graph).
**Stability Gate**: Running the generator on Nexus-Hub itself produces a valid, style-guide-compliant `.nexus/CONTEXT-MAP.md` with a token-count header; the MCP tool and `nexus-hub map` verb both produce identical output; regenerating on an unchanged tree is a content-hash no-op; existing `nexus-code-search` tests still pass.
**Recommended model**: Strong reasoning tier (Opus-class), medium-high effort. New generator plus a CLI seam integrated with an existing extension under a backward-compatibility constraint. Rationale: touches the extension's public surface. `/implement` re-confirms against the live model set.

### Sub-tasks

#### 1.1 - Context-map data model and generator core

**Objective**: Define the compiled-map content model and the generator that produces it from the existing graph.

**Prompt**:
> In `extensions/nexus-code-search`, add a context-map generator module. Define a content model for a compiled codebase map with sections: overview (language, frameworks best-effort, file/symbol counts), module structure (top-level directories and their symbol counts), most-imported files (placeholder in this phase, filled in Phase 4), and a per-domain article index. Implement a generator that reads the existing tree-sitter graph (nodes, edges, files from `codegraph.db`) and emits (a) a single `.nexus/CONTEXT-MAP.md` and (b) a `.nexus/context/` article set (an `index.md` plus one article per top-level module). Each output file carries a header with an accurate token count (reuse the extension's existing token accounting; `tiktoken` with the stdlib fallback). Emit ONLY to `.nexus/`; never write to `CLAUDE.md`, `AGENTS.md`, `.cursorrules`, or any AI-config file (those are owned by the Nexus-Hub installer). Make regeneration content-hash incremental (skip when inputs are unchanged), mirroring the existing `index_graph` behavior. All generated Markdown must follow `catalog/style-guides/markdown.md` (blank lines around lists/tables/headings, ASCII-only). Do not name any external source in the code or docstrings; use generic descriptive names.

#### 1.2 - MCP tool + `nexus-hub map` one-shot CLI

**Objective**: Expose the generator through the extension's MCP server and as a one-command CLI.

**Prompt**:
> Add an MCP tool (for example `generate_context_map(root, force=False)`) to `nexus-code-search`'s MCP server that runs the Phase 1.1 generator and returns the output paths plus the token-count summary. Add a `nexus-hub map [root]` one-shot CLI verb that does the same from the terminal (zero-config: default to the current directory, respect `.gitignore` and `.nexusignore` like the existing indexer). First verify how the existing `nexus-hub` CLI dispatcher is wired and whether surfacing a new verb requires an installer edit; if it does, STOP and confirm the installer change with the user before making it (ask-first gate). Keep the tool and CLI producing byte-identical output for the same input.

#### 1.3 - Testing and Stabilization

**Objective**: Prove the generator, MCP tool, and CLI are correct and stable; establish CI for the extension.

**Prompt**:
> Write pytest tests for the Phase 1 generator: a fixture repo with a known symbol/module shape asserts the compiled map's sections, the token-count header accuracy (within tolerance), the neutral-path guarantee (no write outside `.nexus/`), and content-hash no-op on regeneration. Assert the MCP tool and `nexus-hub map` produce identical output. Run the full `nexus-code-search` suite to confirm no regression. Then create or update the CI/CD pipeline to run the extension's pytest suite (path-filtered to `extensions/nexus-code-search/**`, with dependency caching and concurrency cancel-in-progress), keeping coverage comprehensive while minimizing action minutes. Keep the language platform-agnostic; GitHub Actions is the primary example. Do not proceed to Phase 2 until all tests pass. After all tests pass, run `/generate-session-history` to document Phase 1.

## Phase 2: Framework extraction I - routes + env + middleware (B part 1)

**Goal**: Add framework-aware route detection, an env-var audit, and middleware detection over the tree-sitter graph, each feeding a section of the compiled map, each fixture-gated for recall and zero false positives.
**Prerequisites**: Phase 1.
**Stability Gate**: On per-language fixtures, route/env/middleware sections meet a stated recall figure with zero false positives; the compiled map gains populated Routes, Environment, and Middleware sections; extraction degrades cleanly (a framework with no detector adds nothing rather than emitting noise).
**Recommended model**: Strong reasoning tier (Opus-class), high effort. Many frameworks, correctness-sensitive, fixture-gated. Rationale: extraction accuracy is the DoD; breadth is large. `/implement` re-confirms against the live model set.

### Sub-tasks

#### 2.1 - Framework-aware route extraction

**Objective**: Detect HTTP routes (method, path, params, behavior tags) across a prioritized framework set, over the graph.

**Prompt**:
> In `extensions/nexus-code-search`, add a route-extraction module that reverse-engineers the detection approach (do not copy source; reimplement in Python over the existing tree-sitter nodes/edges). Scope to the languages already in the graph and START with the frameworks Nexus-Hub's own users actually run, verifying each with a fixture before adding the next: prioritize the common web frameworks per language (for example Express/Hono/Fastify/Next/NestJS for TypeScript, FastAPI/Flask/Django for Python, Gin for Go, Rails for Ruby, Spring Boot for Java, Laravel for PHP). For each route, capture method, path, URL params, and behavior tags (auth, db, cache, payment, ai, queue, email) inferred from the handler. Feed a Routes section into the compiled map and a per-domain article where warranted. Use generic names; do not attribute or name any external source. Do NOT attempt every framework at once: each framework detector lands only with its fixture and a passing recall + zero-false-positive check.

#### 2.2 - Env-var audit and middleware detection

**Objective**: Detect environment variables (required vs has-default, with source file) and middleware (auth, rate-limit, CORS, validation, logging, error handlers).

**Prompt**:
> Add an env-var audit that finds environment-variable references across the scanned languages, classifies each as required or has-default, and records the exact source file (reading `.env.example`-style files by variable NAME only; never read or emit secret values). Add a middleware detector for the common categories (auth, rate limiting, CORS, validation, logging, error handling), tied to routes where the framework expresses middleware in the route chain. Feed Environment and Middleware sections into the compiled map. Both must be fixture-gated with zero false positives.

#### 2.3 - Testing and Stabilization

**Objective**: Establish the accuracy harness for extraction and lock in recall + zero-FP gates.

**Prompt**:
> Build a per-language fixture set (small representative apps per prioritized framework) and an accuracy harness that reports, per section (routes, env, middleware), a recall figure against hand-counted ground truth and a hard zero-false-positive gate (mirroring the accuracy discipline observed in the comparison source). Wire this harness into the extension's pytest suite and into CI (path-filtered, cached). The zero-false-positive gate is a hard CI failure; recall below the stated per-section threshold is a soft warning that must be triaged. Run the full suite; iterate until green. Update CI to cover the new fixtures while keeping action minutes low. Do not proceed to Phase 3 until all tests pass. After all tests pass, run `/generate-session-history` to document Phase 2.

## Phase 5: Measurement + health - token benchmark + map lint (D, E)

**Goal**: Add a deterministic token-savings benchmark (compiled map vs simulated manual exploration) run on at least three real repos including Nexus-Hub, and a map-health lint (orphan articles, missing backlinks, staleness). The benchmark validates half the definition of done.
**Prerequisites**: Phases 1-4 (a rich map to measure and lint).
**Stability Gate**: The benchmark reports a reproducible token-reduction ratio on 3+ repos with a documented methodology; the lint flags injected orphan/backlink/staleness defects in a fixture and passes a healthy map; both run in CI.
**Recommended model**: Strong reasoning tier (Opus-class), medium effort. Rationale: methodology correctness matters and the benchmark gates the DoD; reuses the compressor eval pattern. `/implement` re-confirms against the live model set.

### Sub-tasks

#### 5.1 - Deterministic token-savings benchmark

**Objective**: Measure the compiled map's token cost against simulated manual exploration.

**Prompt**:
> Add a deterministic token-savings benchmark, patterned on `extensions/nexus-context-compressor/evals` (a `runner.py` plus a committed `baseline.json`). For a target repo, measure (a) the compiled map's token count and (b) a simulated manual-exploration cost derived from what was extracted (per-route, per-model, per-component, per-env-var, per-file discovery costs, with a documented revisit multiplier). Report the reduction ratio. Run it on at least three real repositories including Nexus-Hub itself, and commit the baseline so regressions are caught. Document the methodology in the extension README (generic names; the estimation constants are the tool's own, not attributed to any external source). This benchmark is the measured half of the plan's definition of done.

#### 5.2 - Map-health lint

**Objective**: Add a deterministic checker for orphan articles, missing backlinks, and staleness.

**Prompt**:
> Add a map-health lint that checks the `.nexus/context/` article set for orphan articles (not linked from the index), missing backlinks (domain articles not linking to the overview), and staleness (an article whose source files changed since the map was generated). Expose it as an MCP tool and a CLI subcommand. Decide at implementation time whether the richer semantic checks belong in the existing `documentation-consistency` skill (extend it, no registry change) versus this deterministic checker; if any NEW catalog skill is created, register it in `data/SKILL_INDEX.md`, `data/skills.json`, and `data/marketplace.json` in this same sub-task and run `make validate`.

#### 5.3 - Testing and Stabilization

**Objective**: Test the benchmark and lint; confirm the measured DoD axis.
