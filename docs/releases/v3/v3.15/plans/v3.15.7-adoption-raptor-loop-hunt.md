**Goal**: Give Nexus-Hub's security skills the enforcement layer they lack, by adding a two-axis severity model with a needs-live-validation disposition, a refutation-validity taxonomy, a rejection proof burden, a coverage denominator, a fraud-class table, a typed capability-grant execution broker, and a deterministic closure gate.

## Overview

This plan operationalizes the raptor-loop-hunt comparison. Nexus-Hub already has broad security coverage (15 skills under `security/`, 15 under `security-operations/`, plus `adversarial-verifier`, `multi-agent-code-review`, and `loop-engineering`), and the comparison deliberately classified six of the source's headline ideas as ALREADY COVERED rather than as gaps. Loop-until-dry is already in `competitive-generation` as a K-consecutive-rounds no-progress stop with the same K=2 default; generate-then-refute is already `adversarial-verifier`; untrusted-target-text is already `prompt-injection-defense`. None of those is re-adopted here.

What is genuinely absent is the enforcement layer. Nexus-Hub's security skills describe good practice; they do not make specific failures mechanically impossible. Three mechanisms have no equivalent anywhere in the catalog. First, a **coverage denominator**: enumerate the target's components before the hunt, treat that list as the denominator, and record anything unassigned as UNCOVERED rather than letting it be absent, so a partial audit cannot read as complete. Second, **typed dispositions with evidence receipts**, whose standout is `needs-live-validation` for a finding whose only remaining barrier is a layer the reviewer cannot observe. Third, a **rejection proof burden**, on the grounds that a false rejection silently erases a real bug while a false confirmation stays visible and retestable.

Eleven candidates result: nine are `skill-native` doctrine folded into existing skills, and two are local builds (a pure-stdlib capability-grant broker and a deterministic closure-gate diff). Nothing introduces a dependency, credential, or outbound call. Two items that WOULD have introduced egress are explicitly declined under the MCP Registry Policy's reverse-engineer-first rule: prior-art recon against OSV / NVD / GitHub (Nexus-Hub already owns `dependency-security-audit` and `cve-reachability-analyzer`) and a cross-vendor judge gated on provider API keys (the source itself documents the local fallback, and `cross-model-orchestrator` already exists). The source's own hard dependency on an external toolchain is dropped outright; the methodology is fully separable from it.

Two structural constraints shape the plan. The source is a single 1043-line SKILL.md, well past Nexus-Hub's 800-line hard cap, so **no equivalent skill is created**: the doctrine is distributed into the skills that already own each concern, and any receiving skill pushed past the 500-line target moves depth into `references/`. And Phase 5's broker is adjacent to the v3.15.6 sandbox-escapes work (whose central finding is that agents escape by writing config a trusted component later executes), so it is sequenced to compose with that permission stub rather than compete with it.

Grounding note: no `docs/solutions/` store and no `STRATEGY.md` anchor exist, so Phase B.5 grounding was best-effort and non-blocking. Two open constraints from the v3.15 known-gaps are folded in: skill `description` fields have a 250-character ceiling (v3.15.3 NI-1), and CI runs `validate_skills.py --bundles-only` rather than strict mode (v3.14.2 WN-1). Most work here edits skill BODIES, which requires no `data/skills.json` sync; only a frontmatter change does.

## Phase 1: Finding-disposition doctrine

**Goal**: Give a finding whose confirming layer is out of view a first-class place to sit, so it stops being collapsed into an understated severity band.

**Prerequisites**: None.

**Stability Gate**: `pentest-reporting` and `exploitability-analyzer` both document two-axis severity and the four-disposition model; the `needs-live-validation` disposition specifies its required fields; the existing CVSS discipline is preserved rather than replaced; `make validate` passes.

**Recommended model**: Strong reasoning tier, high effort (Opus class, high). Rationale: this changes which findings get escalated, and a sloppy formulation either inflates every uncertain finding or preserves the collapse it is meant to fix. Re-confirmed by `/implement` against the then-current model set.

### Sub-tasks

#### 1.1 - Add two-axis severity and the disposition model to pentest-reporting

**Objective**: Let a report carry what is proven and what is at stake separately, without weakening CVSS reproducibility.

**Prompt**:
> Extend `catalog/skills/security/pentest-reporting/SKILL.md` with a two-axis severity model and a four-value disposition, added alongside (never replacing) the existing CVSS scoring discipline.
>
> - **Two-axis severity**: when only part of the system is observable (client code without the server, one service of several, no running instance), rate TWO numbers rather than one collapsed number: a *confirmed severity* provable from the artifacts in hand, and a *potential severity* representing the worst case if the unobserved assumption turns out insecure. Carry the higher one into triage. State the hard rule: never collapse potential severity to Low merely because the confirming layer is out of view.
> - **Disposition (exactly one per surviving finding)**: `confirmed` (proven from artifacts or a run), `needs-live-validation` (the defect pattern is real and reachable in what you can see, but final proof depends on an unobserved layer), `corrected` (real but mis-scoped or mis-rated, with the accurate version given, used to fix OBSERVED errors and never to downgrade for unseen mitigations), and `rejected` (an OBSERVED reason it is not a bug).
> - Specify `needs-live-validation`'s required fields so it cannot become a soft reject: the exact minimal SAFE validation step (the request, command, or test), the expected vulnerable-versus-safe response, and the potential severity. State plainly that it is a first-class outcome, not a soft rejection.
> - Explain the failure this prevents with a concrete shape rather than an abstraction: an unauthenticated password-reset path with a client-controlled target id and a client-controlled skip-verification flag is a potential-critical the moment the path is real, even when the server is out of scope. Downgrading it to "low, server-dependent" is the documented failure mode.
> - Preserve the existing requirement that every finding carries a full CVSS vector string; the two axes refine how the band is chosen, they do not remove the vector.
> - Keep the body at or under the 500-line size norm; if it grows past, move the disposition detail into `references/` and link it. Body-only edits need no `data/skills.json` sync; if the frontmatter changes, keep the description at or under 250 characters and hand-sync the registry entry.
> - Do NOT name the external source repository, its author, or its `F-NN` finding identifiers anywhere in the skill (Reverse-Engineering Attribution Rule). Write the doctrine in Nexus-Hub's own voice.

## Phase 2: Refutation discipline

**Goal**: Constrain what may kill a finding, so an unconstrained skeptic stops dismissing real findings on plausible assumptions.

**Prerequisites**: Phase 1 (a constrained rejection needs somewhere to fall back to, which is the `needs-live-validation` disposition).

**Stability Gate**: `adversarial-verifier` documents the valid/invalid refutation taxonomy and the rejection proof burden; `security-review` references both; the fallback to `needs-live-validation` is explicit; `make validate` passes.

**Recommended model**: Strong reasoning tier, high effort (Opus class, high). Rationale: these are subtle reasoning rules where an imprecise wording silently reintroduces exactly the false negative being removed. Re-confirmed by `/implement`.

### Sub-tasks

#### 2.1 - Add the refutation-validity taxonomy to adversarial-verifier

**Objective**: Say explicitly what counts as a refutation and what does not.

**Prompt**:
> Extend `catalog/skills/orchestration/adversarial-verifier/SKILL.md` with an explicit refutation-validity taxonomy. The skill currently instructs the agent to try to break an implementation but never constrains what counts as a successful break, which lets a skeptic dismiss real findings on plausible-sounding assumptions.
>
> - **VALID refutations** (the verifier can SEE the reason in the artifacts): the cited code does not do what the claim says; the entry point is not attacker-reachable; a mitigating check is present in code you can actually read; the behavior is designed under the established trust model.
> - **INVALID refutations** (assuming an unobserved layer is secure): "the framework probably handles it", "presumably there is authorization upstream", "a real server would validate this". Name this as the single most common false negative in adversarial review, and give the reason it is invalid: the whole point of the test is that the unseen layer might be broken.
> - **INVALID reachability and gating claims**: "that component is not loaded", "it needs a non-default configuration", "it is behind a flag", asserted without checking. State the principle plainly: a reachability claim KILLS a finding, so it carries the finding's own proof burden and must be verified against the observable build and default configuration before it counts. A capability that ships enabled by default is in scope even when packaged as an optional-looking module.
> - **The fallback**: when the only barrier between a finding and exploitation is a layer that cannot be observed, the correct verdict is `needs-live-validation` (Phase 1), never rejected or Low. Cross-link `pentest-reporting`.
> - Add the symmetry note so the skill does not overcorrect: this discipline is tuned against false positives, and a false negative (dismissing a real high-impact finding as theoretical) is just as much a failure and is the EASIER mistake once in refute mode. Hold both error types in view.
> - Where a panel of verifiers is used, require a majority pointing at an OBSERVED reason before a finding is rejected; a panel may move a finding to `needs-live-validation` on less.
> - Same attribution constraint as Phase 1: no external repo, author, or finding identifiers. Keep within the size norm, pushing depth to `references/` if needed.

---

#### 2.2 - Add the rejection proof burden to adversarial-verifier and security-review

**Objective**: Make a negative finding carry evidence, since a false rejection is the costlier error.

**Prompt**:
> Add the rejection proof burden to `catalog/skills/orchestration/adversarial-verifier/SKILL.md` (as the operational counterpart to 2.1) and reference it from `catalog/skills/code-review/security-review/SKILL.md`.
>
> - State the rule: killing a candidate requires enumerating the sink's ACTUAL input sources and showing the barrier holds on all of them. A value can arrive by URL path, query string, request body, cookie, header, or a decoded blob, and a mitigation blocking one delivery route frequently fails to block the others. A single-route non-reproduction is not a refutation.
> - Require a rejection to record a reason-specific counter-hypothesis (the concrete proposition that kills the finding) rather than a bare verdict, plus a per-route result where each route is either an executed check or an explicitly reasoned not-applicable. State why a bare LIST of routes is insufficient: it proves no check ran.
> - Where a kill rests on a reachability or gating claim, require the build and configuration evidence that establishes it, per 2.1.
> - Give the rationale explicitly so the rule is not read as bureaucracy: false rejections are the costliest error in security review because they silently erase real bugs, while a false confirmation stays visible and gets retested.
> - In `security-review`, keep this to a short referencing section pointing at `adversarial-verifier` as the owner. Do not restate the taxonomy in both skills; one rule, one owner (this is the rule-ownership discipline).
> - Same attribution and size constraints.

## Phase 3: Hunt coverage accounting

**Goal**: Give a security review a denominator, so a partial audit can no longer read as a complete one.

**Prerequisites**: Phases 1 and 2 (a component left uncovered must be recordable, and a swept sink must have somewhere to put an unresolved path).

**Stability Gate**: `security-review` documents the component inventory, the coverage denominator, the UNCOVERED record, multi-altitude traversal, and the proven-dirty sweep rule; the `/review security` command surfaces the coverage statement; `make validate` passes.

**Recommended model**: Strong reasoning tier, medium effort (Opus class, medium). Rationale: additive procedure with a clear shape and lower subtlety than Phases 1 and 2, but it defines the artifact Phase 6's closure gate diffs against. Re-confirmed by `/implement`.

### Sub-tasks

#### 3.1 - Add the completeness gate and coverage denominator to security-review

**Objective**: Make silent omission structurally impossible.

**Prompt**:
> Extend `catalog/skills/code-review/security-review/SKILL.md` with a completeness gate. The skill currently enumerates domains to check but never binds those to the TARGET's own component list, so "I audited the interesting parts" passes silently.
>
> - Require enumerating the entire target as a flat component list BEFORE the review begins: every top-level module, package, service, transport, and deployable unit, not just the subsystems that look interesting. This list is the coverage DENOMINATOR.
> - Require a coverage record in which every component is either covered, or explicitly listed as omitted with a reason (out of scope, build-time-only tooling, generated code, vendored third-party copy). A component not yet assigned is recorded as UNCOVERED and is never simply absent from the record.
> - Require the report to state coverage explicitly ("N of M components covered; the following K omitted because ...") and to never imply the assessment is complete while components sit unexamined. If time or budget does not allow full coverage, say so and list precisely what remains, by component.
> - Add the scaling rule: when the target is large, scale the number of review passes to cover it rather than narrowing the inventory to what is convenient.
> - Require re-enumeration when the target changes (new clone, new release), since a stale inventory silently drops newly added modules.
> - Cross-reference the in-repo precedent by name so the pattern is recognizable: `[[model-prompting-research]]` already applies the same discipline in a different domain, reporting an unresearched model as UNVERIFIED rather than omitting it silently. Cite it as the established Nexus-Hub pattern rather than presenting this as novel.
> - Explain the failure prevented: slicing by hot spots and quietly skipping whole modules is how a shallow audit masquerades as a complete one, and on a mature codebase the unexamined module is often exactly where the next bug lives.
> - Same attribution constraint. If the body passes the 500-line norm, move the procedure detail into `references/` and link it from a Quick Reference table so the orphan-bundle audit passes.

#### 3.2 - Add multi-altitude traversal and the proven-dirty sweep rule

**Objective**: Add a second coverage axis and stop one tested entry point from clearing a whole sink.

**Prompt**:
> Extend `catalog/skills/code-review/security-review/SKILL.md` with two further coverage rules.
>
> - **Multi-altitude traversal (B8)**: different defect classes live at different zoom levels, and a single-pass review implicitly picks one altitude and is structurally blind to the others. Define four altitudes and what each surfaces: whole project (architecture, trust boundaries, authorization model, cross-module data flow), file by file (each file's responsibilities and exported surface), functionality by functionality (each feature traced end to end, source to sink, for EVERY defect class rather than only the headline one), and function by function (parsing, memory, encoding, length arithmetic, comparison logic). State that altitude coverage is ORTHOGONAL to the existing domain coverage: a domain-complete review can still be altitude-blind, so both axes must be tracked.
> - **Proven-dirty sweep (B9)**: once attacker-influenced data or control reaches a security-sensitive operation, sweep that operation's OTHER trigger paths before rating, downgrading, or closing it. Enumerate the sink's own dispatch (every route, command, action, internal caller, and the subsystem's own deserialization or import path) as the candidate trigger surface. State the scoping rule for negative evidence: a check passing on one entry point is evidence for THAT path only, and a path that cannot be resolved is unknown rather than unaffected. One tested entry point is not a cleared sink.
> - Keep both rules referenced from, not duplicated in, `advanced-attack-patterns` and `business-logic-abuse` if those skills touch the same ground. One rule, one owner.
> - Same attribution and size constraints.

## Phase 4: Anti-costume-rigor

**Goal**: Detect a report that CLAIMS work the evidence does not support, using mechanical tells rather than judgment.

**Prerequisites**: Phases 1 through 3 (the tells reference dispositions, rejections, and coverage records defined earlier).

**Stability Gate**: `verification-before-completion` carries the fraud-class table with a checkable tell per row; `pentest-reporting` references it for report claims; every row's tell names a specific artifact mismatch rather than a subjective impression; `make validate` passes.

**Recommended model**: Strong reasoning tier, medium effort (Opus class, medium). Rationale: the difficulty is not volume but ensuring each row's tell is genuinely mechanical; a row whose tell is "the claim seems weak" is worse than no row. Re-confirmed by `/implement`.

### Sub-tasks

#### 4.1 - Author the fraud-class table in verification-before-completion

**Objective**: Enumerate the ways a report can fake having done the work, each with a checkable tell.

**Prompt**:
> Extend `catalog/skills/workflow/verification-before-completion/SKILL.md` with a fraud-class table. The skill already requires fresh evidence before a completion claim, but it does not enumerate the specific ways a report can appear rigorous while the underlying work did not happen. These are dishonesty and costume-rigor signals, distinct from the reasoning errors covered in Phase 2.
>
> Author roughly eight to twelve rows. Each row states the fraud class and the MECHANICAL tell that detects it: what an auditor re-derives to catch it. Cover at least:
>
> - Fabricated evidence: a claimed observation with no matching artifact or logged run behind it.
> - Stale evidence: the evidence was produced against a different build or commit than the one the report targets.
> - Overstated outcome: a weaker observed result presented as a stronger class of finding (a crash reported as proven exploitability with no supporting evidence class).
> - Untested item listed as tested: an entry in a tested-routes list with no execution record behind it.
> - Rationale-free not-applicable: an item marked N/A with no reason given for why it cannot apply.
> - Read-derived coverage: a component marked covered from file reads alone with no logged review action against it.
> - Wrong-instrument sweep: an enumeration performed with a text search where the claim requires a semantic or call-graph enumeration.
> - Capped or completeness-unknown enumeration sold as complete: a truncated result set used as a denominator without positively establishing completeness. Add the fail-closed rule: absence of a truncation flag proves nothing.
> - Dropped pending work: the report omits items still open or awaiting validation, so it reads as done while work is outstanding.
> - Escalation-avoidance: a finding whose deciding layer was out of view marked rejected or Low instead of `needs-live-validation` (the Phase 1 disposition).
>
> Give the framing rule: these are searched for actively, not checked as formatting. Every row must be objectively detectable (a diff, a missing artifact, an exit code, a receipt that does or does not exist). Drop any row whose tell reduces to a subjective judgment.
>
> Same attribution constraint; write the taxonomy in Nexus-Hub's own vocabulary and do not carry over external finding identifiers. If the body passes the size norm, move the table into `references/` and link it.

## Phase 5: Execution-authorization broker

**Goal**: Ship a deny-by-default typed capability-grant broker, so an acting step runs only under an explicit grant rather than because a reasoner asked.

**Prerequisites**: Phases 1 through 4. **Also read `docs/v3/v3.15/plans/v3.15.6-adoption-sandbox-escapes.md` before starting** (comparison conflict C4): that plan ships a deny-by-default permission stub and a trust-seam hook, and this broker must compose with it as the capability-grant layer above it, not duplicate it. If v3.15.6 has not landed, either sequence this phase after it or explicitly document the integration seam.

**Stability Gate**: The broker exists as pure-stdlib Python with no third-party imports; authorization is side-effect-free and independently testable; it denies an ungranted capability, a grant with no authorization source, and an out-of-scope write; it refuses to execute when no sandbox is available; its tests pass; it is bundled under an owning skill and referenced from that skill's SKILL.md.

**Recommended model**: Strong reasoning tier, high effort (Opus class, high). Rationale: security-critical code whose failure mode is silent over-permission, which no test catches unless the test was written for it. Re-confirmed by `/implement`.

### Sub-tasks

#### 5.1 - Build the capability-grant broker

**Objective**: Implement typed authorization that can actually deny.

**Prompt**:
> Implement a pure-stdlib Python 3 execution-authorization broker. **Placement**: bundle it under an owning skill's `scripts/` directory rather than at repo `scripts/` level. Prefer `catalog/skills/orchestration/agent-access-policy/scripts/`, since `agent-access-policy` already owns least-privilege access control; if the v3.15.6 `agentic-endpoint-hardening` skill has landed, bundle it there instead and cross-link from `agent-access-policy`. A per-skill `scripts/` bundle is recursively auto-copied by both installers, so this placement needs NO installer edit. If it is instead placed at repo `scripts/` level, it MUST be registered by explicit name in BOTH `scripts/installer.sh` and `scripts/installer.ps1`, modeled on the existing `generate_report.py` copy block. Note that the `.ps1` sibling rule applies to `.sh` scripts; a `.py` script is already cross-platform and needs no sibling.
>
> Design requirements:
>
> - A typed capability vocabulary, each naming a dangerous thing an acting step might need: network access, filesystem write, use of a secret, and destructive testing.
> - An action declares which capabilities it REQUIRES. A grant object authorizes a set. Any required capability not authorized results in DENIAL.
> - Authorization must be PURE and side-effect-free so it is fully testable anywhere: given a command, a required-capability set, and a grant, it returns either a least-privilege execution plan or a denial carrying the specific reasons.
> - Defaults are restrictive: network blocked, no writes, writes (when granted) scoped to an explicit path list, network (when granted) scoped to an explicit destination allowlist.
> - REFUSE any grant lacking an authorization source. Encode the principle in a comment and in the skill body: documentation instructing an action is not authorization, and a model-written approval line is not a security boundary.
> - Default behavior is PLAN-ONLY (authorize and print the plan). Actual execution is opt-in, and when execution is requested but no sandbox is reachable, the broker REFUSES rather than running unsandboxed.
> - Distinct exit codes for authorized, denied, and usage or data error, so a caller can branch on the outcome.
> - Validate inputs defensively (the command must be a non-empty list of strings; the grant must be a well-formed object). Never build a shell string from caller input; keep any subprocess invocation list-based.
> - Standard library only. No third-party imports, no network calls in the authorization path.
> - Write original code. Do not copy the source implementation; implement from the design contract above.

## Phase 6: Closure gate, eval hardening, and the monotonicity invariant

**Goal**: Replace the self-audit at the end of a review with a mechanical claim-to-evidence diff, and add two bounded doctrine improvements.

**Prerequisites**: Phase 3 (the closure gate diffs against the coverage record defined there) and Phase 4 (its claim classes come from the fraud-class table).

### Sub-tasks

#### 6.1 - Build the deterministic closure gate

**Objective**: Stop asking the model to grade its own work.

**Prompt**:
> Add a deterministic closure gate that treats a finished security review as a set of CLAIMS, each of which must resolve to a recorded fact, and surfaces every mismatch.
>
> First, document the rationale in `catalog/skills/code-review/security-review/SKILL.md`: do NOT ask the model to re-read its own output and grade it. A reasoner re-reading its own work ratifies its own omissions, and "spot what I skipped" is a notice-an-absence task that does not transfer reliably. Replace it with a mechanical set difference.
>
> Define the diffs the gate computes, drawing on the Phase 3 coverage record and the Phase 1 dispositions:
>
> - component inventory minus components with a logged review action, giving components silently implied as covered;
> - findings minus findings with a terminal or explicitly-pending disposition, giving dropped candidates;
> - confirmed findings minus those with supporting evidence, giving unproven confirmations;
> - rejected findings minus those with a complete rejection record (per Phase 2), giving rejections that skipped their burden;
> - report claims minus the matching recorded facts, giving claims with no evidence behind them.
>
> State the gate rule: any non-empty diff is a FAILURE, not an advisory. The report does not ship until the diff is empty or the residue is stated as an explicit caveat. Emphasize verifying coverage and rejection claims, not only confirmations, because those are the claims that SUPPRESS further work.
>
> Implement it as a pure-stdlib Python script bundled under `catalog/skills/code-review/security-review/scripts/`, operating on a simple local review-record file whose shape you define and document in a `references/` file. Build the diff against a Nexus-Hub-native artifact shape (comparison classification `re-partial`); do not attempt to reproduce the external source's run-directory layout. Exit non-zero on a non-empty diff. Write tests asserting the gate FAILS on each seeded mismatch class and passes on a clean record.

#### 6.2 - Harden skill-eval-loop with the adversarial eval patterns

**Objective**: Add trap-based evaluation to an existing eval skill.

**Prompt**:
> Extend `catalog/skills/workflow/skill-eval-loop/SKILL.md` with the adversarial evaluation patterns. Nexus-Hub's existing evaluation surfaces (`skill-eval-loop` paired runs and `scripts/run_trigger_evals.py` routing assertions) are real but not adversarial: neither plants a tempting shortcut nor withholds ground truth.
>
> Add these design rules:
>
> - **Score axes separately, and do not score "find exactly the planted item".** A real target carries incidental valid findings, so penalizing extra valid results trains under-reporting.
> - **Each axis gets a trap**: the tempting shortcut is the failure, the discipline is the pass, and the violation must be objectively detectable.
> - **Two tiers**: deterministic axes that run with no model (true regression tests, run on every change) and live-model axes that need an executor on a seeded fixture. Say plainly that one seed is a smoke test, not a benchmark; multiply seeds and report how many ran.
> - **Ground truth is never shown to the executor.** The fixture's expected-results file is judge-only.
> - **Randomize fixture variants** (names, layout, and the path to the planted item) per seed, so a model cannot memorize the corpus. A fixed corpus measures recall of the corpus, not of the method.
> - **Judge by artifacts, not by the report**: the verdict comes from what the run produced and a diff of the working tree, never from the executor's own prose claim about what it did.
>
> Do not attempt to port the external source's own test suite; it tests that project's scripts against its own schema and is not portable. Only the design transfers. Same attribution constraint.

#### 6.3 - Add the monotonicity invariant to known-gaps-tracker

**Objective**: Adopt the safety property without building the durable store.

**Prompt**:
> Add a short section to `catalog/skills/workflow/known-gaps-tracker/SKILL.md` documenting a monotonic-scrutiny invariant for any cross-run memory the project keeps.
>
> State the invariant: a durable record carried across cycles may only ever RAISE attention. It stores no "this was checked and is fine" signal, never deprioritizes an item out of scope, and never excludes something from re-examination. Prior work becomes a PRIORITY and RECHECK signal, never a coverage claim.
>
> Give the safety argument, which is the reason to adopt it: because every signal can only add effort, even a stale or wrong record can only waste budget re-examining something, never cause a skip. Contrast it with the alternative, where a stale "already handled" entry silently reduces attention and the miss is invisible.
>
> Scope this to doctrine only. Do NOT build a durable cross-run store in this plan (comparison classification: `re-full` but deferred on effort). Note the deferral explicitly so a future cycle can pick it up.
