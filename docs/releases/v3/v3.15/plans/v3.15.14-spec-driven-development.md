# Plan - spec artifact reconciliation and proportional spec depth

**Project**: Nexus-Hub
**Version**: v3.15.14
**Slug**: adoption-spec-driven-development
**Plan Type**: Feature (defect fix plus additive convention)
**Created**: 2026-07-29
**Seeded from**: docs/v3/v3.15/comparisons/v3.15.14-comparison-spec-driven-development.md
**Goal**: Make the spec artifact express the scope boundary that three Nexus-Hub surfaces already audit it for, repoint the `spec-driven-development` completion gate at the canonical template it currently ignores, and make spec depth proportional to blast radius without weakening the hard approval gate.

## Goals and Definition of Done

**Target problem**: The canonical spec template cannot express a scope boundary, so every reviewer run on a template-conformant spec raises a finding the template itself caused. Separately, the skill's Verification checklist validates a rival inline template rather than the canonical one, so "spec complete" is checked against the wrong artifact.

**Persona**: The agent authoring a spec via `/spec` or the `spec-driven-development` skill, and the human reviewing that spec through `spec-quality-checklist.md`, the `scope-guardian-reviewer` agent, or `/plan-review`.

**Definition of Done** (observable):

1. A spec produced from `catalog/templates/spec-template.md` has a section in which to declare non-goals, and `spec-quality-checklist.md`'s existing "Scope is clearly bounded" item (line 22) can be ticked from the template alone.
2. `scope-guardian-reviewer`'s "no 'explicitly out of scope' section" finding (line 14) can no longer fire on a template-conformant spec.
3. `spec-driven-development` SKILL.md names exactly one canonical template, and its Verification checklist lists that template's sections.
4. The skill states a spec-depth rule keyed on blast radius, while the hard gate's "applies regardless of how simple the change looks" and "silence is not approval" clauses survive verbatim.
5. `make validate`, `make lint`, and `make test` pass; the FR-### / SC-### ID contract that `cross-artifact-analyzer` consumes is unchanged.

## Overview

This plan operationalizes the `spec-driven-development` article comparison. Of the article's six spec parts, two were already implemented more strongly than the article describes (assumptions, test plan), one is deliberately divergent and declined (architecture in the spec), and the remainder produced seven candidates (D1 through D7). All ten `speckit.*` commands the article recommends already have first-party equivalents, so the Spec Kit half of the source produced zero candidates.

Every candidate is prose: a Markdown edit to a template, a checklist, or a skill body. Zero new code, outbound calls, dependencies, credentials, or skills. Because no new skill is created, AGENTS.md rule 2 (the three `data/` registry files) does not apply and the catalog count stays at 269. Because `catalog/templates/` already installs to `~/.nexus-hub/templates/` and every target is an existing file, no installer copy step is needed in either `scripts/installer.sh` or `scripts/installer.ps1`.

**Deliberate deviation from strict reverse-engineering bucket order.** The comparison's Section 6.4 orders `skill-native` work before `re-full` work, which would put D6/D4/D3/D5 first. This plan front-loads the `re-full` trio (D1, D2, D7) instead, for the dependency reason recorded in that same section: D2 and D7 add sections to `spec-template.md` while D1 decides which template is canonical, so adding sections before resolving authority means adding them to a contested artifact. D1, D2, and D7 therefore land as one atomic Phase 1. This is the highest-value work in the report despite sitting in the second bucket.

The two highest-risk items are not the largest. Phase 1 changes a completion gate, so it must be atomic or the skill briefly validates sections no template produces. Phase 2 writes a proportionality rule adjacent to a deliberate hard gate, where a loose phrasing ("small changes may skip the spec") would reintroduce exactly the guess-compounding failure the source article opens with.

### Sub-tasks

#### 2.1 - Add the spec-depth tier rule

**Objective**: Make the artifact proportional to blast radius while the approval gate stays unconditional.

**Prompt**:
> Edit `catalog/skills/developer-experience/spec-driven-development/SKILL.md` to add a spec-depth rule. The maintainer decision on 2026-07-29 was explicit: adopt proportionality for spec DEPTH, keep the approval GATE absolute. Full proportionality (allowing the spec step to be skipped below a size threshold) was considered and declined.
>
> - Place the rule immediately after the hard-gate block so a reader meets the gate before the tiering, never the reverse.
> - Open the rule by restating the invariant in one sentence: the gate governs whether you and the user agree on what to build, the depth governs how much document that agreement needs. These are independent.
> - Express depth as a small tier table keyed on blast radius, not on effort or line count. A reasonable shape: a single-file internal change with no observable surface needs a Problem Statement, acceptance criteria, and Non-Goals (a spec that fits in a short message); a multi-file or multi-module change adds User Scenarios with an Independent Test, FR-### items, and Assumptions; a change to behavior, a public API, a data schema, or a CLI surface requires the full canonical template including Invariants. Key the top tier on the same four surfaces the existing "Spec as a Merge Gate" section (lines 263-274) already names, so the two rules agree.
> - Promote the existing rationalization row "Simple tasks don't need long specs, but they still need acceptance criteria. A two-line spec is fine." (line 280) into the stated rule, and leave the rationalization row in place as the rebuttal it already is.
> - Extend "When NOT to use" (line 40) so it distinguishes the two axes explicitly: a single-line fix or typo needs no spec at all, whereas a small-but-real change needs a SHALLOW spec rather than no spec. Today that section is keyed only on change size, which is what left the proportionality question unanswered.
> - Add a Common Rationalizations row rebutting the misreading this rule invites, phrased close to: "The depth rule says small changes get a short spec, so I can skip the approval step." Reality: the depth rule scales the document, never the agreement. A one-line spec still requires an explicit go-ahead before code.
> - Do NOT weaken, soften, hedge, or reword the hard gate (lines 12-23). The clauses "The gate applies regardless of how simple the change looks" and "Silence is not approval" must survive verbatim. Do not add any escape hatch keyed on urgency, triviality, or user impatience.
> - ASCII punctuation only. No em-dashes and no clause-joining spaced hyphens; use commas, parentheses, colons, or separate sentences.
