## Executive Summary

Pillar's series documents seven sandbox-escape findings across Cursor, Codex, Gemini CLI, and Antigravity (2025-2026). The unifying finding is a single pattern: the agent almost never breaks the sandbox directly. Instead it writes a file (a `.claude` hook config, a VSCode task, a virtualenv interpreter, a git fsmonitor hook, a "safe" command that hides dangerous arguments) that a trusted component OUTSIDE the sandbox later runs, loads, scans, or treats as safe. The blast radius is not the agent process; it is everything the agent can write that the host later trusts.

This is directly material to Nexus-Hub because Nexus-Hub distributes exactly these artifacts (`.claude/settings.json` hook configs, a `catalog/hooks/` tree, git hooks, `.cursor/*` surfaces) to exactly these platforms. One of the seven CVEs (CVE-2026-48124: "workspace-controlled `.claude` hook config triggered unsandboxed command execution") describes Nexus-Hub's own distribution channel as an attack surface.

Assessment of Nexus-Hub's current posture: the DOCTRINE largely exists (deny-by-default host execution, containment, approval gates, egress trust-boundary policy, injection recognition), but the ENFORCEMENT and MONITORING of the specific config-write-then-executed seam is absent. The installer ships an allow-only auto-approve permission stub (the opposite of deny-by-default), the sensitive-path advisory hook omits every execution-trigger config path in the escape pattern, and nothing tracks file-creation provenance or the trust handoff.

Seven adoption candidates result. All are local (zero new outbound calls, zero new API keys, zero new third-party data processors). The article's vendor product (Pillar Platform) is the only NOT-recommended item; its capability is reverse-engineered locally as a best-effort provenance ledger instead.

| I3 | Partial | `agent-access-policy` has a "Dangerous-Action Approval Gates" section keyed on effect (side effects, non-undoable actions), default-deny on uncertainty. It is not keyed to writing a config file that a trusted executor later runs. No approval gate fires on a config write today. |
| I4 | Not-applicable (guidance only) | Nexus-Hub is a catalog; it does not control whether a host's Python extension or git fsmonitor runs sandboxed. Actionable only as threat-model guidance in a skill, not as an enforced control. |

## Step 7: Risks, Conflicts, and NOT-Recommended

Conflicts and integration risks:

- AC5 vs existing UX: Nexus-Hub's install philosophy (v3.7.0) is no-prompt, install-all. A default deny stub would contradict that, which is why AC5 is opt-in and the default allow-only stub is preserved. This is a deliberate posture split (convenience default, security-hardened opt-in), not a regression.
- AC2 false positives: legitimate agent edits to `.claude/settings.json` (Nexus-Hub itself writes this during `nexus-hub init`) would trip the advisory. The hook must distinguish the installer's own writes, or default to `warn` (not `block`) for these paths, so the catalog's own wiring is not self-blocked.
- AC4 is a denylist, which is inherently incomplete. The honest deliverable is the specific known-bad patterns plus a documented limitation, not a claim of completeness. The article's own thesis (denylists cannot keep pace) applies to this hook; the skill (AC1) must state that the guardrail is defense-in-depth, not a boundary.
- AC3 performance and privacy: a per-write ledger adds overhead and must never persist secrets or file bodies. Bound it to paths plus content hashes, apply `egress-redaction` discipline, and cap correlation to the current session.

NOT recommended for adoption:

- Pillar Platform (AI Discovery and Posture, Red Teaming and Attack Surface Exposure, Runtime Guardrails, Governance and Compliance): a commercial four-component product that instruments the developer endpoint and receives trust-handoff telemetry. Under the MCP Registry Policy this is a third-party data processor watching the endpoint and falls on the hard-no list (posture / scanning / runtime-guardrail-as-service). It is not vendor-intrinsic to Nexus-Hub (Nexus-Hub is not a Pillar customer, and the capability is reverse-engineerable in concept). Rejected outright. The valuable concept (provenance plus seam monitoring) is reverse-engineered locally as AC3, with the honest boundary that a local hook cannot instrument every trusted external executor the way a dedicated endpoint agent can.
- SAIL 2.0 Framework adopted verbatim as catalog content: it is Pillar's intellectual property. Per the reverse-engineering attribution rule, reference it as an external source in AC7 without reproducing it and without naming the vendor in the distributed skill body. Attribution stays in the references file, not in the shipped skill prose.
