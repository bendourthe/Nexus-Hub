## Executive Summary

CodeSight and Nexus-Hub occupy adjacent problem spaces and target the same six AI assistants (Claude Code, Cursor, Copilot, Codex, Windsurf, Cline). The relationship is complementary, not competitive:

- **Nexus-Hub** is a curated catalog (265 skills, 16 commands, 25 hooks, 23 agents) distributed TO many AI platforms via an installer. Its codebase-understanding capabilities are either LLM-native skills (`/describe`, `analyze-codebase`) that re-read files every session, or a pull/query MCP (`nexus-code-search`) the agent calls on demand.
- **CodeSight** is a deterministic extraction engine that pre-compiles a committed context map (routes, schema, env vars, middleware, dependency graph, hot files) into a single file the AI reads at session start, at roughly 200ms and zero LLM cost, claiming 7x-12x token reduction on a base scan.

The single most important finding: Nexus-Hub already owns the hard part of CodeSight's substrate. `nexus-code-search` v2.0 ships a tree-sitter AST graph across 12 languages, symbol-level impact radius (`code_impact`, the equivalent of blast radius), a filesystem watcher (`watch_for_changes`), and reverse-import affected-tests (`code_affected_tests`). What Nexus-Hub lacks is (1) framework-aware structured extraction (routes across 30+ frameworks, schema across 14 ORMs, env-var audit, middleware, events, components) and (2) a compiled, committed context-map artifact that seeds a session cheaply. Both are textbook reverse-engineering candidates under the MCP Registry Policy (`re-full`: MIT source, fully local, zero-outbound), and both extend an existing extension rather than adding a dependency.

## What CodeSight Is

A zero-dependency (borrows the TypeScript compiler from the scanned project) Node CLI, invoked as `npx codesight`, that runs eight parallel detectors and writes structured markdown.

Core capabilities:

- **Framework-aware route extraction** across 30+ frameworks (Hono, Express, Fastify, Next.js, NestJS, tRPC, FastAPI, Flask, Django, Gin, Rails, Phoenix, Spring Boot, Laravel, ASP.NET, Actix, Axum, Vapor, Roku SceneGraph, and more), with method, path, params, and behavior tags (auth, db, cache, payment, ai, queue).
- **ORM schema extraction** across 14 ORMs (Drizzle, Prisma, TypeORM, Mongoose, Sequelize, SQLAlchemy, Django ORM, ActiveRecord, Ecto, Eloquent, Entity Framework, and others): fields, types, primary/foreign keys, unique constraints, relations.
- **Env-var audit** (required vs has-default, with the exact source file), **middleware detection** (auth, rate-limit, CORS, validation, logging), **events** (BullMQ, Celery, Kafka, Redis pub/sub, Socket.io, EventEmitter), **component/props extraction** (React, Vue, Svelte, SwiftUI, Flutter).
- **Dependency graph + hot files** (most-imported files = highest blast radius), **blast radius** (BFS through the import graph for a changed file), and **coverage map** (which routes and models have test files).
- **Compiled context map**: `.codesight/CODESIGHT.md` plus per-domain files (`routes.md`, `schema.md`, etc.), each with a token-savings header.
- **Wiki knowledge base** (`.codesight/wiki/`): targeted per-domain articles (`auth.md`, `payments.md`) plus an index read at session start, with a health lint (orphan articles, missing backlinks, staleness).
- **Knowledge mode**: extracts decisions, open questions, meeting notes, ADRs, and retros from a folder of `.md` files (Obsidian, Notion, ADR tooling) into a `KNOWLEDGE.md` primer.
- **AI-config generation** (`--init`): writes CLAUDE.md, .cursorrules, copilot-instructions.md, codex.md, AGENTS.md, filling each with the detected stack (writes only if absent; appends a section otherwise).
- **AI tool profiles** (`--profile claude-code|cursor|codex|copilot|windsurf`), an **MCP server** (14 on-demand tools with session caching), a **visual HTML report**, **watch mode**, a **git pre-commit hook**, a **GitHub Action** recipe, `--since HEAD~N` git scoping, `--max-tokens` budget trimming, and a **deterministic token-savings benchmark**.
- **Native-AST WASM plugins** (opt-in): language-driven dispatch via a self-describing `describe()` export, so any language can be plugged in against a published contract.

## Gap Analysis

### External-only (`+`): adoption candidates

Each of these is a CodeSight capability with no deterministic equivalent in Nexus-Hub. Evidence cites CodeSight files.

1. **Framework-aware route extraction** (`src/detectors/routes.ts`, 1969 lines): 30+ frameworks, method + path + params + behavior tags. Nexus-Hub's `nexus-code-search` finds symbols/functions, never HTTP routes. Confirmed: no route detector exists in `scripts/` or `extensions/`.
2. **ORM schema extraction** (`src/detectors/schema.ts`, 1127 lines): 14 ORMs with field types, keys, relations. No Nexus-Hub equivalent.
3. **Env-var audit** (`src/detectors/config.ts`): required vs default, with source file. No equivalent.
4. **Middleware + events detection** (`src/detectors/middleware.ts`, `src/detectors/graphql.ts`): auth/CORS/rate-limit, BullMQ/Celery/Kafka. No equivalent.
5. **Compiled, committed context map** (`src/formatter.ts`, `src/generators/ai-config.ts`): a single `.codesight/CODESIGHT.md` read at session start. Nexus-Hub's `nexus-code-search` is a pull/query surface (the agent calls tools); it produces no committed compiled artifact. This is the largest conceptual gap.
6. **Hot-file ranking** (`src/detectors/graph.ts`): most-imported files, file-level. Nexus-Hub has symbol-level impact but no file-level hot-file rollup.
7. **Deterministic token-savings benchmark** (`src/telemetry.ts`): simulates with/without-map token cost. Nexus-Hub has a compressor eval harness but no map-vs-manual-exploration measurement, so its own token-savings claims are currently unquantified.
8. **Context-map health lint** (`src/generators/wiki.ts`, `lintWiki`): orphan articles, missing backlinks, staleness. Nexus-Hub has an LLM-native `documentation-consistency` skill and a manual dangling-wikilink sweep, but no deterministic checker.
9. **Knowledge-map extractor** (`src/detectors/knowledge.ts`, 508 lines): ADRs/decisions/retros/meeting-notes to `KNOWLEDGE.md`. Nexus-Hub's `solution-knowledge-base` / `devlog-generation` / `session-history` are all LLM-native.
10. **Git-scoped change map** (`--since HEAD~N`): routes/symbols touched in the last N commits. Nexus-Hub has `code_affected_tests` (reverse-import BFS) but not a change-scoped route/symbol map.

### Current-only (`=`): strengths to preserve

- The entire curated catalog: 265 skills, commands, hooks, agents, and the 3-tier loading model. CodeSight has none of this.
- Multi-platform installer distribution across 17+ assistants with per-platform read-contracts.
- The governance layer: MCP Registry Policy, project constitution, phased plans, review pipelines, release automation, `nexus-skill-scanner`.
- `nexus-context-compressor`'s reversible compression (CCR) and `nexus-code-search`'s symbol-level AST graph across 12 languages via tree-sitter (broader true-AST coverage than CodeSight, which is TS-only AST with regex fallback elsewhere).

### Both, different approach (`~`)

- **Codebase understanding.** CodeSight: deterministic compiled map, zero-LLM, committed to git, read once. Nexus-Hub: `/describe` + `analyze-codebase` are LLM-native (re-read each session), and `nexus-code-search` is on-demand query. CodeSight's model is strictly cheaper on cold start; Nexus-Hub's is fresher and more precise per query.
- **Impact analysis.** CodeSight: file-level import-graph BFS plus route/model rollup. Nexus-Hub `code_impact`: symbol-level call-graph BFS. Nexus-Hub's is more precise; CodeSight's is more product-facing (a changed file maps to affected routes and models).
- **AI-config file writing.** CodeSight EXTRACTS facts and injects them (append-if-exists). Nexus-Hub PUSHES curated instruction templates. These can coexist in the same file.

### Both, equivalent (`.`)

- Filesystem watcher: CodeSight `--watch` vs Nexus-Hub `watch_for_changes`.
- Incremental re-indexing: both use content-hash change detection.
- Multi-language monorepo/workspace awareness: both handle pnpm/npm/yarn workspaces.

## Step 5: Security and Reverse-Engineering Assessment

### 5.1 Threat model comparison

| Attribute | CodeSight | Nexus-Hub (today) | After RE adoption |
|---|---|---|---|
| Runtime deps | Zero (borrows project TS); spawns local `python3` for Python AST | Python stdlib + `tiktoken` + tree-sitter wheels; zero outbound | Unchanged (extractors run on the existing tree-sitter graph) |
| Outbound calls | None (WASM plugins download checksummed assets, opt-in only) | None (`already-local` classification) | None |
| API keys / credentials | None | None | None |
| Source/prompt/query leaving the machine | No | No | No |
| New commercial relationship | No | No | No |

### 5.2 Per-item risk scorecard

| Candidate | Risk tier | Note |
|---|---|---|
| A, B, C, D, E, F, G, H | None / Low | Pure local extraction over the existing graph; no new outbound call, key, or dependency. |
| Direct dependency on `codesight --mcp` | Medium | Would add an external npx-spawned process. Rejected in favor of RE (see NOT-recommended). |
| Adopting the WASM plugin distribution model | Medium | Downloads checksummed binaries from GitHub releases (a supply-chain surface). Not needed: tree-sitter already covers Nexus-Hub's languages. Rejected. |

### 5.3 Reverse-engineering viability

| Candidate | Classification | Rationale |
|---|---|---|
| A (context-map generator) | `re-full` | Pure formatting of already-extracted data into a committed markdown artifact. |
| B (framework extractors) | `re-full` | CodeSight is MIT and fully local; the detection logic is regex + AST queries that run against Nexus-Hub's existing tree-sitter nodes. |
| C (hot files) | `re-full` | A sort over the import edges `nexus-code-search` already stores. |
| D (token benchmark) | `re-full` | Deterministic local simulation; reuse the `nexus-context-compressor/evals` runner pattern. |
| E (map lint) | `skill-native` + `re-partial` | The health rules (orphan/backlink/stale) are instructable (extend `documentation-consistency`); a deterministic checker is a small local script. |
| F (knowledge extractor) | `re-full` / `skill-native` | Filename + heading heuristics; achievable as a local extractor or by instructing the agent. |
| G (git-scoped map) | `re-full` | Extends the existing reverse-import BFS with a `git diff` file set. |
| H (one-shot UX + CI) | `re-full` | A CLI subcommand plus a documented workflow; Nexus-Hub already owns the installer and CI patterns. |

Per the MCP Registry Policy, every candidate is either `skill-native` or reverse-engineered into the existing local-only `nexus-code-search` extension. No candidate requires a trusted-vendor wrapper. No candidate is `vendor-intrinsic`.

### 5.4 Recommendation ordering (this IS the adoption plan)

1. **skill-native first:** E (map-health lint rules folded into `documentation-consistency`), the instructable half of F (knowledge extraction as skill guidance).
2. **re-full / re-partial (build internal equivalents), dependency-ordered:**
   - B (extractors) is the substrate. It must land before A can compile a rich map, but A can ship first in a thin form over existing graph data (hot files + symbols) and grow as B lands.
   - Recommended sequence: **A (thin map over existing graph) -> B (framework extractors) -> C (hot files, folds into A) -> G (git-scoped map) -> D (token benchmark, measures A) -> E (lint checks A) -> the deterministic half of F -> H (one-shot UX + CI).**
3. **vendor-intrinsic:** none.
4. **drop-outright:** direct `codesight --mcp` dependency; the WASM plugin distribution model (see NOT-recommended).

## Step 6-7: Sequenced Plan, Risks, and Conflicts

### Suggested phasing (adoption target v3.15.1; this report is co-located with its v3.15.1 adoption plan under docs/v3/v3.15/)

- **Phase 1 (P0):** Candidate A, thin. A `nexus-hub map` command / `nexus-code-search` generator that compiles the existing graph (symbols, hot files, module structure) into a committed `.nexus/CONTEXT-MAP.md` read at session start. Ships value immediately with no new extraction.
- **Phase 2 (P1):** Candidate B. Framework-aware route/schema/env/middleware extractors over the tree-sitter nodes, feeding richer sections into the Phase 1 map. Sequence by language, starting with the languages already in the graph.
- **Phase 3 (P1/P2):** Candidates C, G. Hot-file ranking (folds into the map) and git-scoped change map (extends `code_affected_tests`).
- **Phase 4 (P2):** Candidates D, E, H. Token-savings benchmark (substantiates Nexus-Hub's compression claims), deterministic map-health lint, and the one-shot UX plus a CI recipe.
- **Phase 5 (P3):** Candidate F. Knowledge-map extractor, if demand warrants.

### Risks and conflicts

- **Conflict, AI-config file ownership.** CodeSight's `--init` writes/append CLAUDE.md and AGENTS.md; Nexus-Hub already manages those as pushed templates via the installer and `nexus-hub init`. Do NOT replicate CodeSight's file-writing into those files. Instead, emit the compiled map to a neutral path (`.nexus/CONTEXT-MAP.md`) and, at most, add a single pointer line. This keeps the two systems layered rather than fighting over the same file.
- **Scope risk.** Candidate B is genuinely High-effort (CodeSight spends ~3000 lines on routes + schema alone). Do not attempt all 30+ frameworks at once. Scope to the languages already in the tree-sitter graph and the frameworks Nexus-Hub's own users actually run.
- **Duplication risk.** Nexus-Hub's `code_impact` (symbol-level) and a new file-level hot-file rollup must be presented as distinct, labeled views, not two competing "impact" numbers.
- **Maintenance cost.** Framework detectors rot as frameworks evolve. Adopt only detectors with a test fixture, mirroring CodeSight's `eval/` accuracy harness (route recall, schema recall, zero false positives).

### NOT recommended (with policy grounds)

- **Direct dependency on `codesight` (npm) or `codesight --mcp`.** Rejected under the MCP Registry Policy: an external wrapper is not permitted when the logic is reverse-engineerable locally (tier 3 beats tier 4), and CodeSight is MIT and fully local. Reverse-engineer into `nexus-code-search` instead.
- **The WASM plugin distribution model** (self-describing plugins shipped as checksummed GitHub release assets). Rejected: it adds a binary-download supply-chain surface that Nexus-Hub does not need, because tree-sitter grammars already give `nexus-code-search` true-AST coverage across its languages. The *self-describing extractor interface* idea may be reused internally, but not the download-and-run distribution.
- **Copying CodeSight's `skills` plugin verbatim.** It reads only flat `.claude/skills/*.md` and would miss Nexus-Hub's nested `<name>/SKILL.md` layout. Not an adoption; noted as a compatibility lesson for any future skills-detection work.
