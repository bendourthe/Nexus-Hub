# Platform Capability Ownership Contract

**Version:** v3.15.8
**Plan:** [v3.15.8 Platform Capability Parity and GitHub Usage Monitor](../plans/v3.15.8-platform-parity-and-github-usage-monitor.md)
**Source finding:** [DF-9](../known-gaps.md#df-9---additive-platform-capability-drift-is-deferred-to-v3158)
**Verified:** 2026-08-02

## Decision

This matrix converts the v3.15.7 additive-drift audit into explicit delivery and lifecycle contracts. Phase 1 does not activate any new agent or hook path. A row becomes enforceable only after the named implementation phase supplies its writer, collision behavior, manifest record, repair path, teardown path, and cross-shell tests. Existing skills, commands, instructions, and deny controls remain unchanged.

**Phase 8 update (2026-08-03):** every remaining row is now enforceable, and the headline finding is that most of the Copilot surface was already delivered. Re-verification established that Copilot reads Claude-format customization files by default: its `chat.hookFilesLocations` default includes `~/.claude/settings.json` and `.claude/settings.json`, and its default workspace agent locations include `.claude/agents` -- all paths Nexus-Hub already writes. Those three rows are therefore marked enforceable as **inherited with no owned write**, because adding parallel `.github/hooks` and `.github/agents` copies would put redundant commit-visible duplicates in the user's repository (the same policy concern that keeps `.github/skills` opt-in) for surfaces Copilot already loads, and agent files dedup across levels anyway. The single genuine gap was global agents: `~/.copilot/agents` is Copilot's documented user-profile agent path while `~/.claude/agents` is not, so catalog agents are now written there verbatim. Hermes resolved the opposite way from the v3.15.2 expectation -- the quoted upstream rule is that discovery probes each direct subdirectory of the tap path, so the flattened layout is required and a category-nested migration would have broken it. Full detail: the "Copilot agents and hooks" and "Hermes" sections of [platform-read-contracts.md](../../../../policy/platform-read-contracts.md).

**Phase 7 update (2026-08-02):** three of the four Kimi rows are now enforceable, and the fourth is corrected rather than delivered. Re-verification against the official [agents](https://www.kimi.com/code/docs/en/kimi-code-cli/customization/agents.html), [hooks](https://www.kimi.com/code/docs/en/kimi-code-cli/customization/hooks.html), [tools](https://www.kimi.com/code/docs/en/kimi-code-cli/reference/tools.html), and [configuration](https://www.kimi.com/code/docs/en/kimi-code-cli/configuration/config-files) references established that Kimi loads the catalog's Claude-Code-style agent Markdown natively, so agents need no transform at all and ship as a validated verbatim copy at both scopes. Hooks are a four-field-only `[[hooks]]` array where any extra field makes the config fail to load, so the handler-`name` ownership used for Gemini CLI and Qwen is impossible; ownership is a marker-delimited managed block instead, which also preserves the user's comments and tables byte-for-byte without a non-stdlib TOML round-tripper. The workspace hook row is **not** delivered: Kimi's project config is `.kimi-code/local.toml` and documents only a `[workspace]` table, so the matrix's assumed `.kimi-code/config.toml` path does not exist and that row stays finding-only with its reason recorded. Full detail: the "Kimi custom agents and TOML hooks" section of [platform-read-contracts.md](../../../../policy/platform-read-contracts.md).

**Phase 6 update (2026-08-02):** the four Gemini CLI and Qwen hook rows are now enforceable. Re-verification against the upstream [Gemini CLI hooks reference](https://github.com/google-gemini/gemini-cli/blob/main/docs/hooks/index.md) and the [Qwen Code hooks documentation](https://qwenlm.github.io/qwen-code-docs/en/users/features/hooks/) proved both schemas: hooks live under a `hooks` key in each platform's own `settings.json`, matchers are regular expressions over that platform's tool ids, and Gemini CLI renamed every lifecycle event while Qwen kept the Claude-style names. Neither platform has Codex's `commandWindows` override, and both collapse `Bash` and `PowerShell` onto a single `run_shell_command` tool, so the installing host selects which sibling and which shell-flavored guardrails get registered. Because these hooks live inside the file that also holds the user's model, theme, and MCP configuration, the merge preserves every unrelated key and never rewrites a malformed file. Full detail: the "Gemini CLI and Qwen native hooks" section of [platform-read-contracts.md](../../../../policy/platform-read-contracts.md).

**Phase 5 update (2026-08-02):** the four Codex rows are now enforceable. Re-verification against the official [subagents](https://developers.openai.com/codex/subagents) and [hooks](https://developers.openai.com/codex/hooks) references proved both the paths and the schemas, so neither surface needed an inferred adapter. Two upstream constraints are recorded in the rows rather than papered over: Codex ships its hook engine disabled behind `[features] hooks`, and every non-managed hook stays inert until the user trusts it via `/hooks`. The install summary reports both instead of claiming an active guardrail. Full detail: the "Codex native agents and hooks" section of [platform-read-contracts.md](../../../../policy/platform-read-contracts.md).

## Ownership Rules

- Folder-per-file surfaces use manifest ownership. Nexus-Hub creates only absent destinations, records each owned path, repairs missing or drifted owned files, and removes only manifest-owned files.
- Shared JSON or TOML files require structured merge. Nexus-Hub entries need stable identities, backups before mutation, idempotent upgrade, rollback on parse or write failure, and teardown that removes only owned entries.
- User-owned collisions are preserved. An existing destination with no matching Nexus-Hub ownership record is never overwritten or deleted.
- Finding-only rows are documentation, not runtime promises. They must stay out of `contract_checks`, install summaries, and positive verification claims until their implementation and lifecycle tests land.
- Shared aliases keep one writer. Hermes reads `.agents/skills`, but Codex owns the global alias and Antigravity owns the project alias.

## Enforcement Gate

A later phase may change a row from finding-only to enforceable only when all of these statements are true:

- The official path and schema have been re-verified for the current platform version.
- Bash and PowerShell installers invoke the same registry behavior.
- Install, upgrade, repair, verify, doctor, and teardown behavior is covered.
- Shared configuration preserves unrelated user data and rolls back after a failed merge.
- The install summary reports the surface only when the platform was detected and the write succeeded.
- `docs/policy/platform-read-contracts.json` and its Markdown mirror are updated together.
