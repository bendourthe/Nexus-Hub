## 1. Executive Summary

Looper is a Claude Code skill that coaches the *design* of an agent loop before any iteration runs. It does not execute a loop on invocation. It interviews the user across seven stages (goal, verification, host model, council, gates and control, confirm, emit), critiques each answer against a stage-specific rubric loaded on demand, renders the loop as an ASCII flowchart for confirmation, and only then emits a portable spec (`loop.yaml`), a compiled `loop.resolved.json`, an in-session handoff (`RUN_IN_SESSION.md`), and a thin user-owned runner (`run-loop.py`). Its tagline is "Goal, Plan, Review, Deliver, Judge, Stop clean", and it positions itself as the design layer that sits before Claude Code's execution-layer `/goal` (in-session) and `/loop` (scheduling).

This is the fifth time Nexus-Hub has compared itself in the loop domain, and the prior four comparisons matter here because they already absorbed most of what a loop tool can teach. The v3.8.0 ralph comparison, in particular, was a real executable loop runtime, and it drove the enrichment that gave `loop-engineering` its exit-signal protocol, three-class stall and fault detection, untrusted-task-source fence, task-readiness gate, and per-iteration recovery points, on top of the loop schema (`iteration_cap`, `exit_condition`, `progress_check`, `trace_log`, `per_iteration_budget`, `handoff`) adopted across v3.3.0, v3.5.0, and v3.6.0. So a large fraction of Looper's substance is already owned. Looper's termination guards, its no-progress signature detection, its cross-model review seat, and its iteration and revision caps all map onto skills Nexus-Hub already ships.

What makes Looper worth analyzing is that ralph was a runtime and Looper is a design coach, so Looper surfaces a different slice of loop doctrine: the part that happens *before the first iteration*, and the part that governs *what leaves the machine* when a second model reviews the work. Those are the genuine gaps. The headline outcome is **5 skill-native adoptions** (one of them high-value and security-relevant), and **3 deliberate declines** (two pre-adjudicated by the v3.8.0 standalone-loop-runtime decision, one a cautionary anti-pattern). The high-value gap is **egress redaction plus first-send consent before a cross-model handoff**, a discipline `cross-model-orchestrator` currently lacks entirely even though it inherently sends work to a second model. The next two are the **design-first rubric interview** that refuses to ship a loop with no termination guard or no measurable goal, and the **reviewer-versus-judge verdict-honesty rule** that forbids a notes-only reviewer from claiming a gate is "clean". The declines are Looper's `run-loop.py` thin runner and its `loop.resolved.json` compile step, both of which fall squarely under the v3.8.0 `drop-outright` decision that a loop runtime belongs to the host, not the catalog; and Looper's USD/token budget caps, which it documents as **advisory only**, a posture strictly weaker than the hard caps `ai-billing-safeguards` already provides.

**Overall recommendation: adopt the design-time and cross-model-egress doctrine; decline the runner and the advisory cost cap.** Every recommended item is local Markdown enrichment of `loop-engineering` and `cross-model-orchestrator` (with one optional reference file). No new outbound call, dependency, or credential enters the catalog. Looper is itself a policy-clean, local-first skill (zero outbound at install or interview; PyYAML only for the design-time compiler; it never handles API keys), and its egress discipline is precisely what we should reverse-engineer into our own cross-model doctrine.

## 3. Positioning: Design Layer vs. Execution Layer

Looper's own framing is useful and accurate, and it is worth recording because it sharpens where Nexus-Hub's loop doctrine has been thin. Looper distinguishes three layers:

- **`/goal`** is the in-session execution layer: a persistent objective the same model self-checks. Looper's critique is that this is self-evaluation by the same model (a blind spot), with no portable artifact and no typed verification.
- **`/loop`** is the scheduling execution layer: it fires on a cron or interval but does no goal coaching, no reviewer gates, and no verification structure.
- **Looper** is the design layer (pre-flight): it tightens the goal, defines typed verification, brings in a different model as reviewer or judge, and renders explicit review gates, before anything runs.

Nexus-Hub's `loop-engineering` already covers the bounding and mapping of a loop (the schema, the exit discipline, the host-driver delegation), and its task-readiness gate already routes an underspecified goal to `/plan` or `/idea-refine`. What it does not yet have is an explicit, staged design-time coaching pass with per-stage rubrics that the agent walks before the first iteration. That is the conceptual gap Looper fills, and it composes cleanly with the skills Nexus-Hub already references (`ambiguity-detector`, `requirement-enhancer`) rather than duplicating them.

### 4b. Genuine candidates

These five mechanisms are not yet in the catalog, or are only partially present, and are skill-native.

**L1. Egress redaction plus first-send consent before a cross-model handoff (high value, security-relevant).** Looper's runner applies `privacy.egress[]` rules before any council member is invoked: `redact_prompt_for_member()` substitutes file contents matching `redact` globs with a `[redacted:{path}]` marker (default globs `.env`, `.env.*`, `secrets/**`, `**/*.key`), and `ensure_consent()` blocks the first cross-vendor send, prints the destination, the `sends` list, and the redaction globs, and requires the user to type `yes`; refusal aborts with `consent_refused:{member}`, approval is recorded in `state.json`. Nexus-Hub's `cross-model-orchestrator` sends `PLAN.md`, `REVIEW.md`, and `PROGRESS.md` to a second model and has **no redaction step and no consent step** at all. This is a direct, policy-aligned gap: the MCP Registry Policy exists to govern egress, and a skill that routes project artifacts to an external model CLI is an egress path that currently carries no redaction or consent discipline. Target: enrich `cross-model-orchestrator` with a "Before You Hand Off to Another Model" section (redaction-glob defaults, a first-send consent gate, a record of what was sent), and cross-link it from `loop-engineering` (council seats) and the MCP Registry Policy. Classification: **Missing.**

**L2. Design-first rubric interview (high value).** Looper walks seven stages and loads a stage-specific rubric only when entering that stage (goal-rubric, verification-rubric, council-rubric, control-rubric, model-detection), with a goal rubric that turns "make it good" into a concrete outcome, a definition-of-done artifact, explicit scope boundaries, named context sources, and a named consumer, plus critique prompts ("What would count as done if two competent agents disagreed?") and an anti-pattern list ("improve the project without a target artifact", "goals that require endless polishing with no stop condition"). Nexus-Hub's `loop-engineering` Step 4 is a flat assembly checklist, not a staged coaching pass that refuses to proceed until the goal and verification are well-formed. Target: add a "Design the Loop Before You Run It" section to `loop-engineering`, optionally backed by a `references/loop-design-rubric.md` (goal shape, verification typing, council selection, control guards), composing the existing task-readiness gate (`ambiguity-detector`, `requirement-enhancer`) rather than duplicating it. Classification: **Partially implemented (the bounding exists; the staged design rubric does not).**

**L3. Reviewer-versus-judge verdict-honesty rule (medium value).** Looper splits council roles: a reviewer writes non-binding notes, a judge returns a structured verdict (`{verdict: revise|pass, blocking_issues, confidence, notes}`). Its honesty rule is sharp: only a judge or a human may be the `verdict_source` for a `revise_until_clean` gate, and "a reviewer-only gate can use fixed_passes, but it cannot honestly claim clean". Nexus-Hub's `cross-model-orchestrator` has reviewer and verifier roles and GO/NO-GO gates, but does not state this anti-self-deception rule. It complements the existing maker-is-not-checker rule by also forbidding a notes-only reviewer from being treated as a blocking judge. Target: add the reviewer-versus-judge distinction and the verdict-honesty rule to `cross-model-orchestrator` (or `quality-gate-definitions`). Classification: **Partially implemented (roles exist; the honesty rule does not).**

**L4. Typed-verification ordering plus a design-render confirm gate (medium-to-low value).** Looper types every check as `programmatic` / `judge` / `human` and instructs "programmatic checks first, then judge rubrics, then human signoff", and at stage six it renders the loop as an ASCII flowchart (goal and context, draft plan, plan gate, delivery, delivery gate, final output, with the watched caps in a footer) for the user to confirm before any file is written. Nexus-Hub's `loop-engineering` has `check_command` (programmatic) and an independent checker (judge) and a human gate, but does not rank the three verification types, and has no "render the loop design for human confirmation before the first run" step. Target: add the verification-type ordering and a pre-run design-render-and-confirm note to `loop-engineering`. Classification: **Partially implemented.**

**L5. Argv-array (never shell-string) invocation discipline (low-to-medium value, security hygiene).** Looper expresses every model and check invocation as an argv array ("never shell strings") with a per-call timeout, which is injection-resistant by construction. This matches the global Bash security rule already in force ("use arrays, never interpolate user input into a command string"), but neither `cross-model-orchestrator` nor `loop-engineering` states it for model/check invocations. Target: a one-line discipline note in `cross-model-orchestrator` (and the `loop-engineering` check_command guidance) to express invocations as argv arrays with explicit timeouts. Classification: **Partially implemented (covered by global rules; not stated in the loop / cross-model skills).**

## 10. Recommendation Summary

Looper is the design-time complement to the v3.8.0 ralph comparison. Where ralph (a runtime) taught Nexus-Hub the runtime loop disciplines now in `loop-engineering` (exit-signal protocol, stall and fault detection, untrusted-source fence), Looper (a design coach) teaches the disciplines that happen before the first iteration and at the cross-model boundary. Adopt five skill-native items, in this order: the cross-model egress redaction plus first-send consent (L1, the high-value, security-relevant headline), the design-first rubric interview (L2), the reviewer-versus-judge verdict-honesty rule (L3), the typed-verification ordering plus design-render confirm gate (L4), and the argv-array invocation discipline (L5). Decline Looper's `run-loop.py` runner and `loop.resolved.json` compile step (pre-adjudicated `drop-outright` under the standalone-loop-runtime decision) and its advisory cost caps (weaker than our hard caps). Every adoption is local Markdown; nothing new is installed, called, or credentialed.

If chaining into `/plan from-comparison`, pass `reverse-engineer-first=true`. The generated plan should sequence L1 and L2 first (both P1), then L3 and L4, then L5, and should record the two runtime declines as already-adjudicated rather than as fresh phases.
