## 1. Executive Summary

`no-mistakes` is a compiled Go control plane for AI coding work. It places a local bare git repository (the "gate") between your working repo and your real remote. You `git push no-mistakes <branch>` instead of `git push origin`, a `post-receive` hook notifies a background daemon, the daemon spins up a disposable worktree, and a fixed, opinionated pipeline runs there (`intent -> rebase -> review -> test -> document -> lint -> push -> pr -> ci`). Mechanical findings are auto-fixed by the agent in a bounded loop; anything that touches the user's deliberate intent is escalated for a human decision; nothing reaches the real remote until every check is green, at which point the tool opens a clean PR. It ships a single user-invocable `/no-mistakes` skill that drives the same flow headlessly through a machine-readable `axi` (TOON) interface, plus a TUI for interactive use.

This is a fundamentally different *kind* of artifact than the five loop tools and the orchestration projects Nexus-Hub has compared before. Looper and ralph were small, mostly-Python or shell tools whose substance was loop *doctrine* that mapped onto Nexus-Hub skills. `no-mistakes` is a real runtime: a daemon, a git-plumbing proxy, an IPC layer, a SQLite state machine, a Bubbletea TUI, and a cross-platform service installer. The single most important analytical move in this report is therefore to **separate the runtime from the doctrine**. The runtime (roughly 490 of the 496 files) is a host-side control plane, and Nexus-Hub has a standing, repeatedly-applied decision that host-side runtimes are referenced but never reimplemented in the catalog (the `/loop` decision in v3.1.0, the standalone-loop-runtime `drop-outright` in v3.8.0). The adoptable doctrine lives almost entirely in one file: the `SKILL.md` the tool installs for agents.

That `SKILL.md` is where the genuinely novel material is, and it is good. The headline gap is a **three-way finding-action taxonomy** (`auto-fix` / `ask-user` / `no-op`) paired with a crisp **escalation rule**: a finding that challenges the user's deliberate intent or changes product behavior is a decision only the user can make, so the agent must relay it verbatim and never approve, fix, or skip it on its own. Nexus-Hub's review and verification skills have the pieces (acceptance-criteria review, human gates, adversarial verification) but not this sharp taxonomy or the verbatim-escalation discipline. The next gaps are the **canonical pre-merge verification gate** (a fixed sequence whose order is justified, so that "passed the gate" has a stable meaning across repos), **intent passed verbatim as the review oracle** (enriched with the decisions and tradeoffs a reviewer reading only the diff would not know), and **round-history hygiene** (do not re-report a finding the user already chose to ignore unless the code now presents a materially different issue).

The report also surfaces one clear **security cautionary signal**: `no-mistakes` ships **default-on telemetry** that POSTs usage events to `https://a.kunchenguid.com` (the author's Umami analytics instance), opt-out only via `NO_MISTAKES_TELEMETRY=0`. That is precisely the egress-by-default posture Nexus-Hub's MCP Registry Policy exists to prevent, and it is the principal reason this report stops short of recommending the tool itself, even though a Nexus-Hub user could in principle run `no-mistakes` as a host-side gate while Nexus-Hub supplies the doctrine the agent follows inside it.

**Overall recommendation: adopt the agent-facing doctrine from the `/no-mistakes` skill as local Markdown enrichment of existing skills; decline the Go runtime (host-side, pre-adjudicated) and treat the default-on telemetry as a cautionary anti-pattern, not an adoption.** The headline outcome is **6 skill-native adoptions** (two high value), **1 optional reverse-engineerable enrichment**, and **2 declines** (one runtime, one telemetry). No new outbound call, dependency, or credential enters the catalog.

The relationship is **complementary at the layer boundary and competitive nowhere**. `no-mistakes` is a host-side gate that *runs* a verification pipeline; Nexus-Hub is the *doctrine* an agent follows when it does review, verification, committing, and shipping. In principle the two compose: a developer could push through `no-mistakes` while their agent follows Nexus-Hub skills. The adoption question is not "should the catalog become a runtime" (it should not, and has decided so repeatedly) but "what doctrine in the tool's agent-facing skill is sharper than ours, and can be imported as Markdown".

## 3. Positioning: Control Plane vs. Content

The cleanest way to see what is and is not adoptable is to name the two layers explicitly.

- **`no-mistakes` is a control plane.** It owns execution: it intercepts the push, creates the worktree, runs the steps, applies fixes, watches CI, and forwards to the remote. Its value is that it *enforces* a verification sequence the developer cannot accidentally skip, because the gate sits in the git push path. This enforcement is exactly what a Markdown catalog cannot provide, and exactly what a host runtime can.
- **Nexus-Hub is content.** It owns doctrine: what good review looks like, when to escalate to a human, how to bound a fix loop, how to write a PR body, what verification evidence to require before claiming completion. Its value is that this doctrine reaches every agent on every platform without a runtime, and it is portable across hosts.

The two layers are not in competition; they are stacked. The error to avoid is concluding "no-mistakes does verification better, so the catalog should build a gate". The catalog's whole premise is that it ships no runtime. What the catalog *can* do is absorb the doctrine `no-mistakes` encodes in its agent skill so that a Nexus-Hub-equipped agent behaves the way the `no-mistakes` pipeline expects, whether or not the user runs the gate. That is the adoption thesis for the rest of this report.

### 4b. Genuine candidates

These mechanisms are not in the catalog, or are only partially present, and are adoptable as local Markdown.

**N1. The auto-fix / ask-user / no-op finding-action taxonomy plus the verbatim-escalation rule (high value).** `no-mistakes` classifies every review/test/lint finding by an `action` field, not just a severity. `auto-fix` means objective, mechanical, low-risk (the agent may fix it on its own judgment); `ask-user` means the finding "challenges the user's deliberate intent or touches product behavior" (a call only the user can make); `no-op` is informational. The skill's escalation rule is precise and worth importing nearly verbatim: for an `ask-user` finding the agent must "not approve, fix, or skip it on your own", must relay it "as the pipeline wrote it: its `id`, `file`, and full `description` verbatim", must not "paraphrase, summarize away the detail, or pre-judge the answer", and only then translate the user's decision into a response. It also draws a sharp line on what stays `auto-fix`: "Routine correctness, reliability, or security fixes still stay `auto-fix` even if the smallest fix reintroduces a small amount of previously deleted logic." Nexus-Hub's review skills rate severity and offer human gates, but none of them encodes this action taxonomy or the verbatim-escalation discipline. Target: enrich `intent-based-review` and `receiving-code-review` (and cross-link `verification-before-completion`) with the three-way action taxonomy and the "escalate intent-touching findings verbatim, never resolve them yourself" rule. Classification: **Missing.**

**N2. The canonical pre-merge verification gate, with a justified fixed order (high value).** `no-mistakes` makes its pipeline order non-configurable on purpose, so that "passed the gate" has a stable meaning across repos, and the docs justify each ordering choice (review before test "so the agent reads fresh code"; document after test "so docs are updated against code that's known to work"; lint last among local checks "so it doesn't churn over code that may still change"; push/PR/CI only after local checks pass). Nexus-Hub ships every one of these checks as a separate skill, but has no single doctrine that states the canonical pre-merge sequence and the reason for the order. The result is that an agent assembling its own pre-merge flow has to rediscover the ordering each time. Target: add a "Canonical Pre-Merge Gate" section to `shipping-and-launch` (or `verification-before-completion`) that names the sequence (review -> test -> document -> lint -> commit/push -> PR -> CI), gives the one-line rationale for each ordering decision, and cross-links the per-step skills. Classification: **Partially implemented (every step exists as a skill; the canonical ordered gate doctrine does not).**

**N3. Intent passed verbatim as the review oracle, enriched with decisions and tradeoffs (medium value).** The `no-mistakes` skill is emphatic that `--intent` is "what the user set out to accomplish ... not a description of the diff", that the agent should "err on the side of completeness, not brevity", and that it should "capture the nuance: the user's goal, the specific decisions and tradeoffs they made along the way, any constraints or approaches they ruled in or out", because "the review step uses `--intent` to tell a deliberate decision apart from a mistake, so a thin one-line summary makes it flag things the user already chose". Critically, the tool prefers intent passed verbatim from the live conversation over inferring it from transcripts, which it calls "slower and flakier". Nexus-Hub's `intent-based-review` verifies acceptance criteria but does not stress capturing the ruled-in/ruled-out tradeoffs, nor the failure mode (a thin intent makes review flag deliberate choices as mistakes). Target: sharpen `intent-based-review` with the "capture decisions and tradeoffs, not a diff summary" guidance and the explicit failure mode. Classification: **Partially implemented.**

**N4. Round-history hygiene: do not re-report a finding the user already ignored (medium value).** In its iterative review/fix loop, `no-mistakes` carries a sanitized history of which findings the user previously left unselected, and "on follow-up review passes, that history tells the agent not to re-report user-ignored findings unless the code now presents a materially different issue". This is a sharp, specific discipline for any multi-round agent review, and it directly attacks the common loop failure where the agent re-surfaces the same rejected finding every round. Nexus-Hub's `loop-engineering`, `multi-agent-code-review`, and `receiving-code-review` do not state it. Target: add the round-history "do not re-raise ignored findings unless materially changed" rule to `multi-agent-code-review` (or `loop-engineering`). Classification: **Missing.**

**N5. Deterministic PR body built from a recorded review/fix audit trail (medium-to-low value).** `no-mistakes` builds the PR body's risk, testing, and pipeline sections deterministically from recorded step rounds, rendering auto-fix rounds "as an issue -> fix -> verification narrative instead of a round-numbered log: each fix summary is followed by either a successful re-check or the findings still open after that fix". Nexus-Hub's `pr-description-writer` produces summary / how-to-test / risk / reviewer-notes sections, but as authored prose, not as a narrative derived from a recorded audit trail of what was found and fixed. Target: add to `pr-description-writer` an optional "build the risk/testing sections from the review-and-fix audit trail as an issue -> fix -> verification narrative" pattern. Classification: **Partially implemented.**

**N6. Stop driving at the human-decision boundary; never busy-poll for a human action (low-to-medium value).** `no-mistakes` distinguishes `checks-passed` (validated, CI green, PR open, but not merged) from `passed` (merged), and instructs the agent to stop at `checks-passed`: "Do not wait for the merge ... Never poll or re-run waiting for the merge yourself." This is good general agent doctrine (return control to the human at a human-owned decision point rather than blocking or polling) that generalizes well beyond merges. Target: add the "stop at the human-decision boundary, do not busy-poll for a human action" note to `loop-engineering` (it complements the exit-signal protocol) and/or `shipping-and-launch`. Classification: **Missing (as stated doctrine).**

### 4c. Reverse-engineerable enrichment (optional)

**N7. Diff-to-session matching to recover intent from local agent transcripts (low-to-medium value, optional).** When `--intent` is not supplied, `no-mistakes` recovers it: its `internal/intent` package discovers candidate local agent sessions (Claude Code, Codex, OpenCode, Rovo Dev) within the commit time window, scores each by file-overlap against the diff, drops tool calls, summarizes the remaining user/assistant text, and caches the result. Nexus-Hub's `session-query` already reads local session logs script-first and zero-outbound, but it does not match a *diff* to the session that produced it via file-overlap scoring. This is the one genuinely reverse-engineerable algorithm in the project (a deterministic heuristic, not a runtime). It is marked optional because `no-mistakes` itself deprioritizes it, preferring verbatim intent from the live conversation (the lesson behind N3). Target: optionally enrich `session-query` with a diff-overlap-plus-time-window matching heuristic, expressed as guidance or a thin script. Classification: **Partially implemented (`session-query` reads sessions; diff-to-session matching is absent).** RE classification: `re-partial`.

## 6. Step 5: Security and Reverse-Engineering Assessment (mandatory)

### 6.1 Threat-model comparison

| Dimension | Nexus-Hub (catalog) | no-mistakes |
|---|---|---|
| New runtime dependencies | None added by this comparison | A compiled Go binary plus a long-running daemon installed as a managed OS service |
| Outbound-call destinations | Internal MCPs local; web fetch user-initiated; installer reaches only the project's own GitHub | The configured git remote and PR/CI host (GitHub/GitLab/Bitbucket) that the user already uses; the underlying agent CLI; **plus default-on telemetry to `https://a.kunchenguid.com`** |
| Credentials / API keys | None in the catalog | None stored by the gate itself; the wrapped agent CLI and `gh`/git carry their own auth |
| Source code / prompts / query text leave the machine? | No (web fetch is user-initiated and content-scoped) | Diff and PR content go to the user's own remote/CI (expected); **anonymous usage events (event names, OS/arch, version) go to the author's analytics server by default** |
| New commercial relationship required? | No | No (the remote/CI and the agent CLI are the user's existing relationships); the telemetry endpoint is the author's, not a vendor the user chose |

The decisive finding is the telemetry. `internal/telemetry/telemetry.go` constructs an Umami client with `defaultHost = "https://a.kunchenguid.com"` and fires `Track`/`Pageview` events unless `NO_MISTAKES_TELEMETRY` is set to `0`/`false`/`off`. The payload observed in code is usage-shaped (event name, OS/arch, build version, timestamp), not source code, and sends are best-effort with a one-second timeout. It is still egress-by-default to a third-party-owned endpoint, which is the exact posture Nexus-Hub's policy is written to prevent. This is why the report recommends importing the doctrine but not the tool, and records the telemetry as a cautionary anti-pattern.

## 7. Sequenced Adoption Plan

All recommended items except N7 are local Markdown enrichment. Sequence by value and dependency:

1. **N1 (P0): finding-action taxonomy plus verbatim-escalation rule.** Add to `intent-based-review` and `receiving-code-review` the three-way action taxonomy (`auto-fix` = objective/mechanical, agent may resolve; `ask-user` = challenges deliberate intent or product behavior, escalate; `no-op` = informational) and the escalation discipline (relay an intent-touching finding verbatim with its id/file/full description, never paraphrase or pre-judge, never resolve it yourself). Cross-link `verification-before-completion`. Record the boundary rule that routine correctness/reliability/security fixes stay `auto-fix`.
2. **N2 (P1): canonical pre-merge verification gate.** Add a "Canonical Pre-Merge Gate" section to `shipping-and-launch` naming the ordered sequence (review -> test -> document -> lint -> commit/push -> PR -> CI), with the one-line rationale for each ordering decision, cross-linking the per-step skills. State the payoff: a fixed order makes "passed the gate" mean the same thing every time.
3. **N3 (P2): intent verbatim as the review oracle.** Sharpen `intent-based-review`: capture the user's goal plus the decisions, tradeoffs, and ruled-in/ruled-out constraints (not a diff summary), and state the failure mode (a thin intent makes review flag deliberate choices as mistakes). Note that verbatim live intent beats transcript inference.
4. **N4 (P2): round-history hygiene.** Add to `multi-agent-code-review` (or `loop-engineering`) the rule that an iterative review loop must not re-report a finding the user previously left unaddressed unless the code now presents a materially different issue.
5. **N5 (P3): deterministic PR body from the review/fix audit trail.** Add to `pr-description-writer` an optional pattern that builds the risk and testing sections from the recorded review-and-fix trail as an issue -> fix -> verification narrative.
6. **N6 (P3): stop at the human-decision boundary.** Add to `loop-engineering` and `shipping-and-launch` the note to return control at a human-owned decision point (for example a PR ready to merge) rather than blocking or busy-polling for the human action.
7. **N7 (optional, P3): diff-to-session intent matching.** Only if there is appetite, enrich `session-query` with a diff-overlap-plus-time-window heuristic to recover intent from local transcripts. A reverse-engineering matrix row is required for N7 (it touches transcript content); confirm the redaction posture already in `session-query` covers it.

When implementing, pass `reverse-engineer-first=true` into `/plan from-comparison`. N1 through N6 add no outbound surface and need no matrix row; N7 needs one; the two declines should be recorded as already-adjudicated (runtime) and policy-rejected (telemetry) rather than as fresh phases.

## 8. Risks, Conflicts, and Not-Recommended Items

**Conflicts with existing conventions.** None among N1 through N7. They enrich existing skills without changing their structure. N1 strengthens, rather than contradicts, Nexus-Hub's human-in-the-loop posture; N2 composes the per-step skills rather than replacing them.

**Cautionary signal (security, not an adoption).** `no-mistakes` enables usage telemetry by default and POSTs to the author's Umami endpoint unless the user opts out with `NO_MISTAKES_TELEMETRY=0`. This is a teaching moment in the opposite direction: it is the egress-by-default analytics pattern the MCP Registry Policy classifies as a hard-no. Nexus-Hub should keep its zero-telemetry posture and, if anything, cite this as a concrete example in the policy's rationale. Do not import any telemetry, and do not recommend running `no-mistakes` itself without first documenting the opt-out.

**Not recommended (drop-outright), with grounds:**

| Item | Grounds |
|---|---|
| The Go gate runtime (bare-repo git proxy, post-receive hook, daemon, IPC, SQLite, TUI, AXI/TOON, managed-service installer) | A host-side control plane. Reimplementing it reverses the standing decision (v3.1.0 `/loop`, v3.8.0 standalone-runtime `drop-outright`) that the catalog references runtimes but never ships them. The doctrine this runtime encodes is captured in N1 through N6; the enforcement it provides is the host's job, not the catalog's. |
| Default-on telemetry to `https://a.kunchenguid.com` | Egress-by-default to a third-party-owned analytics endpoint; MCP Registry Policy hard-no. Cautionary example, never an adoption. |
