**Project**: Nexus-Hub

**Plan Type**: Refactor
**Created**: 2026-08-18
**Goal**: Every documentation surface the harness maintains is bounded and consumable by an agent: DEVLOG becomes a thin per-release index with its 208k-word body archived, AGENTS.md drops below its MT-1 pressure point by relocating per-topic sections, and per-version history files gain a retention rule so `docs/` stops growing without limit.

## Overview

Nexus-Hub's documentation strategy is built on progressive disclosure: small always-loaded surfaces, detail on demand. Three surfaces have escaped that discipline. `docs/DEVLOG.md` is an unbounded append-only log now at 3,149 lines / ~208,000 words - too large for any agent to load, and fully duplicated by the per-version `plans/`, `development/history/`, `known-gaps.md`, `docs/decisions/`, and `docs/solutions/` trees that did not exist when DEVLOG was invented. `AGENTS.md` is 9,138 words, 74% of the entire always-loaded doc budget (tracked as open gap MT-1). And `docs/v3/` holds 440 markdown files with no retention or consolidation rule for session histories and development notes, so the historical record grows forever with no consolidate/archive step.

This plan converts DEVLOG from a log into an index (one line per release, linking to that release's plan, history dir, and known-gaps; the current body archived verbatim under `docs/archive/`), rewrites the tooling that writes it (`devlog-generation` skill, `/update release`, `/update docs`, `setup-project` templates) so the index format is self-sustaining, executes the MT-1 ratchet-down on AGENTS.md, and establishes a written retention policy for per-version history files with a light validator warning so drift is visible. Each change carries a decision record where it changes policy.

Success looks like: `docs/DEVLOG.md` under 150 lines and staying there mechanically; `AGENTS.md` meaningfully below its current ceiling with the ceiling ratcheted down; a documented, linked retention policy that `/update release` applies; and no historical content lost - everything archived, nothing deleted.

## Phase 1: DEVLOG conversion and archive

**Goal**: DEVLOG becomes a bounded per-release index; nothing historical is lost.
**Prerequisites**: v3.17.5 released and merged to develop (so the archived body is complete through the last released version).
**Stability Gate**: `docs/archive/DEVLOG-v0-v3.17.md` holds the prior body verbatim; `docs/DEVLOG.md` is <=150 lines in the index format; a decision record exists; all repo references to DEVLOG still resolve.
**Recommended model tier**: strong
**Recommended effort level**: medium
**Rationale**: Mechanical archive-and-rewrite with a clear format contract; the risk is reference breakage, which grep bounds.

### Sub-tasks

#### 1.1 - Decision record

**Objective**: Record the deprecate-as-log / keep-as-index decision.

**Prompt**:
> Create `docs/decisions/accepted/policy/2026-08-18-devlog-index-conversion.md` per `docs/decisions/README.md`. Decision: `docs/DEVLOG.md` stops being an append-only narrative log and becomes a thin per-release index (one line per release: date, version, one-sentence summary, links to that release's plan file, `development/history/` dir, and known-gaps file); the historical body is archived verbatim. Required `## Alternatives considered`: keep as-is (rejected: 3,149 lines / ~208k words, unloadable by any agent, duplicates the per-version tree); delete outright (rejected: loses the only single-glance whole-project chronology); split into per-version DEVLOGs (rejected: duplicates `development/history/` which already exists per version). State explicitly what the index does NOT grant: it is a navigation surface, not a change record - CHANGELOG.md remains the authoritative change record.

#### 1.2 - Archive and rewrite

**Objective**: Move the body, write the index.

**Failure modes**: If a release entry in the old body cannot be mapped to a version dir (early releases predate the canonical layout), the index line links only what exists and marks the rest "pre-canonical layout, see archive"; if `docs/archive/` does not exist it is created; the archive copy is byte-identical (verify by hash) so no content-conflict is possible.

**Build class**: load-bearing.

**Prompt**:
> Move the full current body of `docs/DEVLOG.md` to `docs/archive/DEVLOG-v0-v3.17.md` unchanged except a 3-line header noting the archive date and the decision record. Verify the moved body is byte-identical to the original content (hash both). Rewrite `docs/DEVLOG.md` as: a 5-line header explaining the index format and linking the archive + decision record, then one table or list line per release (newest first): date, version, one-sentence summary, repo-relative links to the release's plan file(s), `development/history/` dir, and known-gaps file where they exist; for pre-canonical releases link the archive. Derive the per-release lines from the archived body's entry headers and git tags; target <=150 lines total. Follow `catalog/style-guides/markdown.md`. Then grep the whole repo for `DEVLOG` and fix every reference that describes it as a narrative log (README, guides, templates, skills, commands) to describe the index; do not change `devlog-generation` internals yet (Phase 2 owns that).

#### 1.3 - Testing and Stabilization

**Objective**: Prove nothing broke and nothing was lost.

**Prompt**:
> Run `make validate`, `make lint`, `make test`. Verify the archive hash check passed, `docs/DEVLOG.md` is <=150 lines, and a repo-wide link check over the new index resolves every link (use the documentation-consistency approach). Run `python scripts/validate_unicode_safety.py --strict --fix --root . --path docs/DEVLOG.md`. Update CI only if a new check was added; otherwise record a no-op. After all tests pass, run `/generate-session-history` to document Phase 1.

## Phase 2: Tooling rewrite for the index format

**Goal**: Every writer of DEVLOG produces the index format, so the file can never regrow into a log.
**Prerequisites**: Phase 1.
**Stability Gate**: `devlog-generation`, `/update release`, `/update docs`, and `setup-project` all specify the index format; a seeded dry-run produces a single well-formed index line; `make validate` and `make test` pass.
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: Touches the release flow itself; a regression here corrupts every future release's docs step.

### Sub-tasks

#### 2.1 - Rewrite the devlog-generation skill

**Objective**: The skill generates index lines, not narrative entries.

**Failure modes**: When the target release has no plan file or history dir yet, the skill emits the line with the missing links omitted and a note, never a broken link; when DEVLOG.md is absent (a consuming project that never had one), the skill creates the index-format file from the header template; when the same version line already exists, the skill updates it in place rather than appending a duplicate.

**Build class**: load-bearing.

**Prompt**:
> Rewrite `catalog/skills/workflow/devlog-generation/SKILL.md` (and any bundled references) so its output contract is the DEVLOG index format from the Phase 1 decision record: one line per release with date, version, one-sentence summary, and links to plan / history / known-gaps. Preserve the skill's discovery logic (git history, docs artifacts) but redirect the rich narrative it used to write into the per-version `development/history/` file instead, cross-linking `[[session-history]]`. Update the frontmatter description (pushy, with SKIP clause: full session narratives - use session-history; change records - CHANGELOG). Keep `summary_l0` / `overview_l1` accurate. Update the skill's entries in `data/skills.json` and `data/SKILL_INDEX.md` if the description changed (hand-edit only those; never run build_skills_catalog.py).

#### 2.2 - Update the update/setup flows

**Objective**: `/update` and `setup-project` write and scaffold the index format.

**Prompt**:
> In `catalog/commands/update.md`, change every step that appends to or syncs DEVLOG (release scope and docs scope) to: generate or refresh the single index line for the current version via `[[devlog-generation]]`, and route narrative content to the per-version history file. In the `setup-project` skill (and any template it scaffolds DEVLOG from), scaffold new projects with the index-format DEVLOG header instead of the narrative template. Grep `templates/` and `catalog/` for any remaining instruction that tells an agent to "append an entry to DEVLOG" and align it. Keep each edit minimal; the format contract lives in the decision record and the devlog-generation skill.

#### 2.3 - Testing and Stabilization

**Objective**: Prove the flow is self-sustaining.

**Prompt**:
> Add or extend a pytest that feeds a fixture repo (or a seeded temp copy) through the devlog index-line generation and asserts: well-formed line, in-place update on re-run (no duplicates), graceful handling of a missing plan/history dir. Run `make validate`, `make lint`, `make test`. Do a manual dry-run of the `/update docs` DEVLOG step against this repo and confirm it edits only the current version's line. Update CI if the new test needs wiring (suite is auto-discovered; confirm). After all tests pass, run `/generate-session-history` to document Phase 2.

## Phase 3: AGENTS.md MT-1 ratchet-down

**Goal**: AGENTS.md returns to being an entry-point document; per-topic depth moves to on-demand files; the budget ceiling ratchets down to lock the gain.
**Prerequisites**: None (independent of Phases 1-2; sequenced here to avoid concurrent edits to shared docs).
**Stability Gate**: AGENTS.md word count reduced by a meaningful margin (target: at least 2,000 words relocated), every relocated section replaced by a 2-4 line summary + repo-relative link, `docs/policy/doc-budgets.json` ceiling lowered to the new count plus small headroom, and `make validate` (including the budget gate and base-template parity) passes.
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: AGENTS.md is inlined into CLAUDE.md context for every session; a botched relocation silently removes guidance agents rely on, and the parity/budget gates interlock.

### Sub-tasks

#### 3.1 - Relocation pass

**Objective**: Move per-topic depth out; keep the map.

**Failure modes**: If a section is referenced by tests (grep `tests/` and `catalog/hooks/tests/` for asserted headings or phrases before moving anything), the reference is updated in the same commit or the section stays; if a relocated file would duplicate an existing policy doc, merge into the existing doc instead of creating a sibling; internal anchors that other docs link to get a stub heading + link left behind.

**Build class**: load-bearing.

**Prompt**:
> Execute the MT-1 disposition on `AGENTS.md`: identify the largest per-topic sections that are reference material rather than always-needed rules (candidates: the full MCP decision tree detail, the per-platform coverage caveats and dated verification notes, the workflow-phase automation recipe pointer material, the model-routing plan/implement detail, the per-skill bundled-resources deep detail) and relocate each to the most fitting existing home under `docs/policy/` or `guides/reference/` (create a new file only when no fit exists). Replace each with a 2-4 line summary plus a repo-relative link. Before moving anything, grep `tests/`, `catalog/hooks/tests/`, and `scripts/` for assertions on AGENTS.md content and update them in lockstep. Do NOT relocate: the golden installer rule, the skill-registration steps, the Critical Conventions, or the Boundaries section - those are the always-needed core. Target at least 2,000 words relocated. Then lower the `AGENTS.md` ceiling in `docs/policy/doc-budgets.json` to the new word count plus ~200 headroom (ratchet down only). Update the MT-1 entry in `docs/v3/v3.17/known-gaps.md` to RESOLVED with the delta.

#### 3.2 - Testing and Stabilization

**Objective**: Prove no guidance was lost and every gate passes.

**Prompt**:
> Run `python scripts/validate_doc_budgets.py --list` (AGENTS.md under its new ceiling), `python scripts/check_base_template_parity.py`, `make validate`, `make lint`, `make test`. Run a link check over AGENTS.md and every file it now links to. Diff-review: for each relocated section, confirm the destination file contains the full original content (nothing summarized away at the destination). Run the unicode sanitize pass on every edited file. After all tests pass, run `/generate-session-history` to document Phase 3.

## Phase 4: History retention policy

**Goal**: Per-version history files get a written lifecycle so `docs/` growth is bounded and old detail is archived, not deleted.
**Prerequisites**: Phase 1 (the policy references the DEVLOG index as the navigation surface).
**Stability Gate**: `docs/policy/docs-retention.md` exists and is linked from AGENTS.md (2-3 lines) and the known-gaps/session-history skills; an advisory validator reports retention-rule violations without failing CI; `make validate` and `make test` pass.
**Recommended model tier**: strong
**Recommended effort level**: medium
**Rationale**: New policy authoring plus one small advisory script; bounded blast radius by design (warn, never block).

### Sub-tasks

#### 4.1 - Author the retention policy

**Objective**: One page that says what lives, what consolidates, what archives, and when.

**Build class**: load-bearing.

**Prompt**:
> Create `docs/policy/docs-retention.md` defining the lifecycle for per-version documentation: (1) ACTIVE - the current minor version's dirs are unrestricted; (2) CONSOLIDATE at release - when a version is released, its `development/history/` files stay as-is but the release's DEVLOG index line becomes the single entry point; (3) ARCHIVE at major+2 minors - when a minor version falls two or more minors behind the current one, its `development/` subtree moves to `docs/archive/versions/v<MAJOR>/` per the existing docs-layout-refactor archive convention (files move, links repaired, nothing deleted); (4) `docs/solutions/` and `docs/decisions/` are exempt (they have their own lifecycles via solution-refresh and the decision-record lifecycle). State the rationale in one paragraph: 440 files under `docs/v3/` and growing, with agents needing recent history hot and old history findable. Add a decision record `docs/decisions/accepted/policy/2026-08-18-docs-retention-policy.md` with `## Alternatives considered` (no rule - rejected, unbounded growth; delete old history - rejected, loses troubleshooting record; per-file TTL - rejected, arbitrary). Add a 2-3 line pointer to the policy in AGENTS.md (within the Phase 3 budget) and cross-link it from the `known-gaps-tracker`, `session-history`, and `docs-layout-refactor` skills' Related Skills sections.

#### 4.2 - Advisory retention check

**Objective**: Drift is visible without blocking anyone.

**Failure modes**: On a repo with no `docs/v*` tree the script exits 0 silently (not an error); on an unreadable directory it warns and continues; it never moves or deletes files itself (report-only), so no conflicting-operation surface exists.

**Build class**: load-bearing.

**Prompt**:
> Add `scripts/check_docs_retention.py`: walk `docs/v*/v*/development/`, compare each minor version against the current version (from the version source `check_version_sync.py` uses), and print a WARN line per version dir that is two or more minors old and not yet archived, with the exact `docs/archive/versions/` destination. Exit 0 always (advisory). Wire it into `make validate` output as informational. This is a repo-internal guard: no `.ps1` sibling, no installer copy step; add it to `DEV_ONLY_SCRIPTS` in `catalog/hooks/tests/test_installer_smoke.py`. Add a pytest with a fixture tree asserting: old-version WARN emitted, current-version silence, exit code 0 in both cases.

#### 4.3 - Testing and Stabilization

**Objective**: Policy linked, checker green, suite green.

**Prompt**:
> Run `make validate`, `make lint`, `make test`. Confirm the new pytest passes, the advisory check runs inside `make validate` without failing it, and every cross-link resolves. Run the unicode sanitize pass on the new policy and decision record. Update CI if needed; otherwise record a no-op. After all tests pass, run `/generate-session-history` to document Phase 4.

## Phase 5: Architecture Refactor, Known-Gaps Reconciliation, and CI/CD

**Goal**: Leave the project well-organized, its known gaps reconciled, and its CI/CD complete and optimized.
**Prerequisites**: All prior phases.
**Stability Gate**: The layout is clean (no deprecated/obsolete files, empty dirs, redundant files/dirs, or overcomplicated structure left un-triaged); the version's known gaps are reconciled; CI/CD covers every change and is optimized; project validation/tests pass.
**Recommended model tier**: frontier
**Recommended effort level**: max
**Rationale**: Repo-wide refactor, reference repair, known-gap reconciliation, and release gating carry high context volume and blast radius.

### Sub-tasks

#### 5.1 - Architecture refactor

**Objective**: Refactor toward a well-organized, intuitive layout.

**Prompt**:
> Identify deprecated/obsolete files, empty directories, redundant files/dirs, and overcomplicated structure, then refactor toward a clean, intuitive layout via [[project-refactor]] and [[docs-layout-refactor]] (propose-then-apply, with confirmation; repair every reference for anything that moves). This version's natural candidate: apply the new retention policy's first archive pass to the oldest v3 minors flagged by `scripts/check_docs_retention.py` (propose-then-apply; nothing deleted).

#### 5.2 - Known-gaps reconciliation

**Objective**: Reconcile the version's open gaps.

**Prompt**:
> Reconcile this version's known gaps via [[known-gaps-tracker]]: resolve, defer, or transfer each open item, and finalize the per-minor known-gaps file for the version. Confirm MT-1 is marked RESOLVED with the Phase 3 delta recorded.

#### 5.3 - CI/CD create/update/optimize

**Objective**: CI/CD covers all changes and is optimized.

**Prompt**:
> Create or update the CI/CD pipeline so it covers every change in this plan, then optimize it to reduce action minutes (path filters, concurrency cancel-in-progress, dependency caching, gating expensive-OS or matrix jobs to merges/schedule) while keeping comprehensive testing. Keep it platform-agnostic; GitHub Actions is the primary example.

#### 5.4 - Cross-installer parity

**Objective**: Prevent operating-system installer drift when the repository ships multiple installers.

**Prompt**:
> If this repository ships more than one installer, run or add a declarative cross-installer parity gate covering distributed artifacts, supported platforms, named capability counterparts, and external-tool fallbacks, then execute the real installers on their target operating systems with identical postconditions. Cross-link [[platform-contract-verification]] so discovery and delivery are checked in the same pass. If the repository ships zero or one installer, record a silent no-op and continue. (This plan adds one repo-internal script under DEV_ONLY_SCRIPTS and no distributed artifacts; the gate should confirm exactly that.)

#### 5.5 - Testing and Stabilization

**Objective**: Prove the refactor preserved behavior and CI/CD is green.

**Prompt**:
> Run the full validation/test suite, confirm the refactor changed no behavior, confirm CI/CD passes and the action-minute reduction is real, and iterate until clean. Generate a session-history entry for this phase.
