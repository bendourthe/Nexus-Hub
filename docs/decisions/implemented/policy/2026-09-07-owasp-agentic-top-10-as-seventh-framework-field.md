# Decision: The OWASP Top 10 for Agentic Applications becomes the seventh mapped framework, as its own frontmatter field and its own coverage column

Status: implemented - skills declare an optional `owasp_agentic` list of `ASI01` to `ASI10`, validated for shape and membership by `scripts/validate_skills.py` and rendered as a column of `docs/framework-coverage.md`, with the ATT&CK Navigator layer deliberately untouched

## Problem

Nexus-Hub maps its security skills to six frameworks (`mitre_attack`, `atlas_techniques`, `d3fend_techniques`, `nist_csf`, `nist_ai_rmf`, `mitre_f3`) and generates a coverage matrix from those fields. Roughly fifteen skills in the catalog teach agent-runtime controls: prompt-injection resistance, tool and permission scoping, memory provenance, execution isolation, inter-agent trust, cascading-failure containment, human-gate design. None of them mapped to the one framework written specifically about agentic systems, so a compliance reader auditing this catalog against agentic risk had no column to read, and the catalog's own coverage matrix could not show whether an agentic risk was addressed at all.

The gap is not cosmetic. The six existing frameworks were written for classical systems, adversarial ML, defensive countermeasures, general cyber risk, AI risk management, and fraud. An agent goal hijack, a rogue agent, or a cascading failure across an agent pipeline has no natural home in any of them.

## Decision

- **Add an optional `owasp_agentic` frontmatter field** taking a list of identifiers `ASI01` through `ASI10`. It follows the same optional-field contract as the six existing framework fields: absence is never an error, it costs no Tier-1 tokens beyond the characters used, and `scripts/validate_skills.py` checks it only when present.
- **Validate shape AND membership.** Each value must match `^ASI(0[1-9]|10)$`, the field must be a list (a bare string is an error), and duplicates within one list are an error. The error names the skill file and the field, matching the existing framework-field error format. Membership validation is the point: a shape-only check would accept `ASI99`, and a fabricated identifier in a compliance-facing matrix is worse than an absent one because it reads as verified coverage.
- **Render it as one column of `docs/framework-coverage.md`**, generated by `scripts/build_framework_coverage.py`, whose `--check` mode fails `make validate` when the committed matrix is stale relative to the frontmatter. Regeneration is the only fix, exactly as for the other six.
- **Do not write OWASP identifiers into `docs/attack-navigator-layer.json`.** That layer is consumed by the ATT&CK Navigator, which resolves technique identifiers against the ATT&CK catalog; an `ASI` identifier is not an ATT&CK technique and would either be dropped silently or render as an unresolvable entry. The Navigator layer stays ATT&CK-only, and a test asserts no `ASI` identifier appears in it.
- **Tag a skill only where its body already teaches the control.** A tag whose control the body does not teach is a mistranscription presented as coverage. Every tagged skill documents each of its identifiers in `references/standards.md` with what the identifier means, why it applies to that skill, and the source URL.

The ten identifiers and their official titles, verified on **2026-09-07** by fetching the OWASP source (the framework document is dated 2025-12-09):

| ID | Official title |
|---|---|
| ASI01 | Agent Goal Hijack |
| ASI02 | Tool Misuse |
| ASI03 | Identity & Privilege Abuse |
| ASI04 | Agentic Supply Chain Vulnerabilities |
| ASI05 | Unexpected Code Execution |
| ASI06 | Memory & Context Poisoning |
| ASI07 | Insecure Inter-Agent Communication |
| ASI08 | Cascading Failures |
| ASI09 | Human-Agent Trust Exploitation |
| ASI10 | Rogue Agents |

Sources fetched, both recorded because the first does not itself enumerate the list:

- <https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/> (the resource page; describes the framework, links the downloadable document, does not list the ten entries inline)
- <https://genai.owasp.org/2025/12/09/owasp-top-10-for-agentic-applications-the-benchmark-for-agentic-security-in-the-age-of-autonomous-ai/> (the announcement, which enumerates all ten with titles)

Two titles were corrected against the fetched source during implementation: ASI03 and ASI06 use an ampersand ("Identity & Privilege Abuse", "Memory & Context Poisoning"), not the word "and" as the adoption plan transcribed them. This is the do-not-invent rule working as intended, and it is why the plan required a re-fetch rather than a transcription from the plan's own text.

## Alternatives considered

- **Fold the OWASP identifiers into the existing `nist_ai_rmf` field.** Rejected: they are a different framework with a different identifier namespace and a different scope, and the coverage matrix's contract is one column per framework. Merging them would make the matrix unable to answer "is this risk covered by OWASP" separately from "is it covered by NIST", which is the question a reader with an OWASP obligation is actually asking.
- **Document the mapping only in `references/standards.md`, with no frontmatter field.** Rejected: prose is not machine-readable, so the mapping would be invisible to `build_framework_coverage.py` and absent from the matrix. The catalog would then claim agentic coverage in fifteen scattered files with no way to audit it in one place, which is the situation the coverage matrix exists to end.
- **Wait for the OWASP Agent Control Standard before mapping anything.** Rejected as a blocker, retained as a watch item. It was announced 2026-09-01 with no published identifiers, so there is nothing to map to yet; blocking a mapping to a published framework on an unpublished one would leave the gap open indefinitely. Revisit when identifiers are published, and treat that as a possible eighth field rather than a replacement for this one.
- **Validate shape but not membership** (accept any `ASI` followed by digits). Rejected: it accepts `ASI99` and `ASI00`, and the failure mode is a plausible-looking identifier in a compliance-facing document. Membership is a closed set of ten, so checking it costs one regex.
- **Write the OWASP identifiers into the Navigator layer alongside ATT&CK techniques**, so one artifact carries everything. Rejected: the Navigator resolves identifiers against the ATT&CK catalog, so an `ASI` entry is at best inert and at worst renders as a broken technique. One artifact per consumer contract is the cheaper invariant.

## Consequences

- **A new optional field is a new thing to get wrong.** The mitigation is that it fails closed at `make validate` time rather than at read time, with the file and field named. The cost is one more validator branch and one more column in a generated document.
- **The coverage matrix must be regenerated whenever a tag changes**, or `--check` fails the local gate and CI. This is the same discipline the six existing frameworks already impose, so it adds no new habit.
- **Tags are judgments and will need revisiting.** A skill tagged `ASI02` today because its body teaches tool scoping may drift as the body is edited. Nothing detects a tag whose supporting sentence was later deleted; the test suite asserts that every identifier is explained in `references/standards.md`, which is a weaker guarantee than asserting the body still teaches the control. That residual gap is recorded rather than papered over.
- **The framework itself will version.** The identifiers adopted here are the 2026 set. A future OWASP revision that renumbers or retitles an entry makes every tag in the catalog stale at once, and the only detection is a human re-fetch. `[[platform-contract-verification]]` already owns periodic re-verification of external contracts and is the natural place for that check to live.
- **This does not make Nexus-Hub OWASP-compliant, and the matrix must not be read that way.** A tag says a skill teaches a control relevant to a risk; it does not say the risk is mitigated in any deployment.
