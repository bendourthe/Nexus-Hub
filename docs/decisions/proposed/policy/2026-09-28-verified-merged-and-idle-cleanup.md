# Decision: Remove a branch or worktree only when seven checks pass at the moment of removal

Status: proposed - `cleanup_merged.py --apply` removes any item that is merged and idle as far as this machine and GitHub can show, re-read before each removal; everything else is reported and kept

## Problem

A full `/implement` run, and a minor run above all, ends with branches and worktrees that nobody needs: merged plan branches, their remote copies, and worktrees whose work is on `develop`. Until now the release flow and the last-phase duties said "Report only; never delete branches", and each run removed only the items its own record listed. So stale refs and checkouts piled up across releases, each pinning objects and each hard to tell apart from live work at a glance.

Removing them is the one step in the run that can destroy someone else's work if it is wrong: another session's worktree, a commit pushed after the merge, an unpushed local commit, or a gitignored `.env` that `git worktree remove` deletes along with the tree. The approval the user gives at the start of the run cannot name these items, because which ones qualify is only known when cleanup runs.

## Proposal

`scripts/cleanup_merged.py` is the only code that removes a branch or worktree it did not create. It is dry-run by default. An item is removed only when every check below passes. The checks are evaluated per item, and on `--apply` they are evaluated again from a fresh read of git and GitHub immediately before that item is removed:

1. **Merged at this exact tip, into the integration branch.** A MERGED pull request from this repository has the branch as its head and the integration branch or the repository's default branch as its base (a merge into any other base is `KEEP merged-elsewhere`), and its `headRefOid` equals the current remote tip and the current local tip (for a worktree, also its `HEAD`). A local tip that descends from the merged head is `KEEP local-ahead`; any other difference is `KEEP head-mismatch`. A branch with no merged pull request (never opened, closed unmerged, merged from a fork, or merged without a pull request at all) is never removed: `KEEP no-merged-pr`. When the remote branch is already gone, the local tip alone must equal the merged head.
2. **No open pull request** uses the branch as head: `KEEP open-pr`.
3. **Not protected.** Not `main`, `master`, `develop`, the integration branch, the repository's default branch, or any branch GitHub reports as protected: `KEEP protected`.
4. **Clean worktree.** `git status --porcelain` is empty (`KEEP dirty`); `git ls-files -v` shows no entry other than an ordinary `H` (assume-unchanged, skip-worktree, and unmerged entries hide edits from `git status`: `KEEP hidden-changes`); there are no untracked files (`KEEP untracked`); and every ignored entry `git status --porcelain --ignored=matching` lists is itself a directory whose own name is in the allowlist `node_modules/`, `__pycache__/`, `.venv/`, `.pytest_cache/`, `dist/`, `build/` (a path that merely passes through such a name, like `src/build/.env`, is `KEEP ignored-not-allowlisted`). The whole tree is then walked, allowlisted directories included, without following any link: a symlink, junction, or other reparse point anywhere is `KEEP link-present`, because `git worktree remove` follows junctions and would delete what they point to; another listed worktree, a nested `.git`, or a submodule checkout inside it is `KEEP contains-worktree`; and a secret-like file name inside an allowlisted directory (`.env`, `.env.*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `id_rsa*`, `id_ed25519*`, `*.kdbx`, `credentials*`, `secrets*`, case-insensitive) is `KEEP sensitive-ignored`. This check exists because `git worktree remove` deletes ignored files with the tree. Every other ignored file inside an allowlisted build or dependency directory is deleted with the worktree by design (accepted trade-off: these directories are regenerable), and the sensitive-name scan is a safety net, not a guarantee.
5. **Not locked**: `KEEP locked`.
6. **Not owned by a run.** No live run record or live runner lock under `~/.nexus-hub/runs/` for this repository names the branch or worktree (`KEEP owned-by-run`). The calling run's own record is not "another run".
7. **Idle.** No reflog entry for the local ref, no entry in the worktree's `HEAD` reflog, and no file change in the worktree in the last 24 hours, and the branch's newest repository-activity event on GitHub (`GET /repos/{owner}/{repo}/activity` with `ref=refs/heads/<branch>`: pushes, force pushes, creation, deletion) is older than 24 hours (`KEEP recently-active`). A time that cannot be read, including an empty activity list, is `KEEP idle-unknown`, never idle.

Around those seven, the executor keeps any item it cannot judge: `unsafe-name` (a ref name holding one of `& | < > ^ % ! " ` ;` is never passed to any tool), `records-unreadable` (any run record that cannot be read makes ownership unknown for every item, and `--apply` then exits 3), `gh-unavailable` (gh missing, unauthenticated, offline, or an answer that reached the 1000-entry `PR_LIMIT` and may be truncated), `remote-unreadable`, `remote-mismatch` (a remote other than the verified `origin`, or a push route `repo_host.verify_push_route` does not report `met`), `checked-out` (the branch is checked out in a worktree that stays, which keeps its remote copy too), `current-worktree` (the worktree `--repo` names or the one holding the process's working directory), `detached`, `missing`, and `status-unreadable`. On Windows, a worktree is renamed to a sibling name and back just before removal; if that fails, an open handle holds it and it is `KEEP in-use`, so a removal never stops halfway. POSIX removes a directory with open files, so the probe does not run there.

`git` and `gh` must resolve to real executables: the shared resolver (`repo_host.absolute_tool`) skips a Windows `.cmd` or `.bat`, because cmd.exe re-parses every argument and a branch name such as `feat/x&mkdir,pwned` would run a second command.

The idle window is at least 24 hours: `--idle-hours` below 24, or not a finite number, is a usage error. The final-pass receipt binds the idle window and the integration branch, `cleanup.merged` accepts it only with at least 24 hours and the record's own target branch, and no receipt is written when any item was kept for a reason that says the pass could not see (`gh-unavailable`, `remote-unreadable`, `records-unreadable`): the pass then exits 3 with `BLOCKED: cannot-verify`.

Removal never forces. A worktree goes through `git worktree remove` without `--force`, then `git worktree prune`. A local branch goes through `git update-ref -d refs/heads/<b> <headRefOid>`, which succeeds only while the ref still equals the merged head, so a squash-merged branch that `git branch -d` refuses is handled without `-D`. A remote branch goes through `git push --force-with-lease=refs/heads/<b>:<headRefOid> origin --delete refs/heads/<b>`: the server deletes only an unchanged tip, which closes the window between the re-read and the push. This is the one lease form allowed; `-D`, a bare `--force`, and `worktree remove --force` stay banned. A removal that fails becomes `KEEP <item> removal-failed <reason>` with any partial state listed, and the pass continues. An exclusive lock beside the run records makes a second concurrent `--apply` exit 3.

The honest property is **merged, and idle as far as this machine and GitHub can show**. A second machine's unpushed worktree, or a local commit on another machine that was never pushed, is invisible to both and is not protected by any of these checks.

This supersedes the "Report only; never delete branches" duty only for items that pass every check, and only through `cleanup_merged.py --apply`. Branch-hygiene reporting (`check_release_preconditions.py --branches`, which now prints the executor's dry run, and the closed-unmerged report) stays in place. A run records that the final pass happened through a sealed receipt that the completion contract's `cleanup.merged` predicate reads.

## Alternatives considered

- **Run-owned only (the previous rule).** Remove only the branches and worktrees the run's own record lists. Safe, but it never cleans anything a run did not create, so the accumulation this record exists to stop continues. Rejected by the user on 2026-09-28.
- **Merged-only.** Remove anything whose pull request merged. Rejected: a merge says nothing about a commit pushed after it, an unpushed local commit, a second session still working in the worktree, or an ignored `.env`. Each is a real way to lose work.
- **A frozen list on the approval page.** The approval names every item, and cleanup removes exactly that list. Rejected by the user in favor of the next option, over the design and security lenses' recommendation: the list is stale by the time a multi-plan run reaches cleanup (the run's own branches only merge later), so it would either miss the items the run produced or need a second approval at the end.
- **Anything that qualifies when the final pass runs, with per-item checks (chosen, 2026-09-28).** The approval covers the rule, not the items; the page shows today's estimate from a dry run.

**Accepted trade-off.** Because the approval does not name items, the seven checks and the re-read before each removal carry all of the safety. Mitigations: the server-side lease on remote deletion, protection of ignored files outside the allowlist, a single final pass after the last merge, and a report of every kept item with the first check it failed.

## Acceptance criteria

- In a fixture with nine items (a merged idle branch whose pull request head equals the tip; a branch whose remote tip moved after the merge; a squash-merged branch; a local branch ahead of its merged head; a branch from develop with no commits and no pull request; merged worktrees with an untracked file, a gitignored `.env`, and a live run record; a branch pushed one hour ago), `--apply` removes exactly the first and third, lists the other seven with their failing check, and leaves the `.env` file intact.
- `python scripts/cleanup_merged.py --dry-run` in this repository lists every candidate with its verdict and removes nothing.
- No git command the executor issues contains `-D`, a bare `--force`, or `worktree remove --force` (asserted over every recorded argv in `tests/validators/test_cleanup_merged.py`).

## Risks

- **Invisible work on another machine.** Stated above as the limit of the property; the idle window and the push-time check reduce but do not remove it.
- **Activity history limits.** GitHub's activity endpoint keeps a limited history; a branch older than its oldest event returns no activity and is kept as `idle-unknown`, which is safe but leaves some genuinely stale branches in place.
- **Pull request list limit.** Open and merged pull requests are read in one call each, capped at 1000 (`PR_LIMIT`). An answer that reaches the cap may be truncated, so every item is then `gh-unavailable` rather than judged from a partial list; a repository with more than 1000 merged pull requests cleans nothing until the query is paginated.
- **Deleted by design.** Ordinary ignored files inside an allowlisted build or dependency directory go with the worktree. The sensitive-name scan catches the common secret file names only.
- **A caller that runs `--apply` without an approval.** The executor itself checks the approval only for `--receipt`. `/update release` and the run use it under the recorded `cleanup-merged` approval or an explicit confirmation; the checks, not the caller, are what make a removal safe.
