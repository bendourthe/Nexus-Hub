# Decision: Conditional Full-Decline Closeout

Status: proposed - qualify a frozen no-release outcome through the existing native captured-answer flow.

## Problem

Nexus-AI v2.16.0 explicitly forbids a release when its model trial fully declines. The trial stopped at an environment gate, and admission-only catalog/default edits correctly did not run. Unconditional release-tag and changed-path requirements prevent native closeout from representing that approved outcome. Falsifying admission edits or publishing a prohibited release would violate the plan.

## Proposal

Use the existing blocker, render, consume and signed-writer flow to capture one bounded conditional-outcome disposition. Revalidate the exact frozen conditions, named checked tasks, protected input files, immutable committed evidence, approved PR head/merge and green integration at render, answer and evaluation. An existing classless platform blocker can be qualified with an explicit proposal file through the same genuine capture flow. An authenticated decline uses its verified integration merge as its completion anchor. Protected inputs remain unchanged at its original head and merge; current expectations may advance only through later approved members with verified green merges and ancestry. Existing non-release, gap, archive and cleanup gates remain required. The native archive preserves immutable origin bindings while rebinding only its deterministic plan and task-path repairs.

## Alternatives considered

- Publish a release or change a catalog merely to satisfy the checker: rejected because it contradicts the frozen decline outcome.
- Accept any checkbox, free-form skip note or unsigned blocker answer: rejected because it would authorize omissions without a bounded captured decision.
- Globally redefine a declined plan as shipped: rejected because it would excuse unapproved late members and weaken release ordering.
- Add a second signer or a replacement checker: rejected because the existing native capture and transaction paths already own authority.
- Leave the consumer blocked indefinitely: preserves the rules but cannot complete a valid approved no-release outcome.

## Acceptance criteria

Prove a genuine native captured answer produces a signed bounded disposition; altered evidence, protected files, task conditions, head/merge, frozen identity and replayed answers fail. Ordinary releases retain their existing requirements. Exercise native archive and subsequent verification with preserved origin and current binding. Treat the installed consumer run as incomplete until its own native completion verdict proves the full closeout.

## Risks

Archive rebinding, exact branch/commit identity, absence checks and signed-versus-unsigned state are trust boundaries. A new gap still needs its separate migration authority. Existing installed-tool failures are recorded separately and are not silently repaired by this change.
