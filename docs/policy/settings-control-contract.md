# Settings Control Contract (living)

**Covers**: the vendor-sourced facts behind the Nexus-Hub Settings catalog (`scripts/lib/settings_control/catalog.json`): which user-level key each tool documents for effort, model, approval posture, and commit attribution, which layers can override it, and what no setting can remove. **Read by**: maintainers adding a control, anyone reviewing a catalog entry, and the `nexus-hub settings explain` text. **Key topics**: admission rule, how `nexus-hub settings show` resolves a state, per-vendor dated sections for Claude Code, Codex, GitHub Copilot (VS Code Copilot Chat and Copilot CLI), findings that changed the plan, the write rules, the VS Code panel contract (launch, order of a change, confirmation, webview), and what stays Not-Settable. It extends `docs/policy/platform-defaults-levers.md`, which owns the install-time seeding levers; this file never restates a shared key and links that file instead.

**Decision record**: [`2026-10-15-settings-control-admission.md`](../decisions/implemented/tooling/2026-10-15-settings-control-admission.md). **Operating guide**: [`guides/NEXUS_HUB_SETTINGS.md`](../../guides/NEXUS_HUB_SETTINGS.md) (what each control means per tool, override fixes, `remove-override`, reset, uninstall).

**Last verified**: 2026-10-30 for v4.14.6 Phase 1; observations added 2026-10-31 (see Probe follow-up); Claude attribution demoted to Not-Settable on 2026-10-31 (see the Attribution bullet there). Quotes are the text returned by the documentation fetch on that date and may abridge the page; a catalog entry cites the URL and the date, never a blog, forum, or issue.

## Admission rule

A write becomes a control only with a fetched primary vendor source and a Proof Record, a `proven` row in `docs/releases/v4/v4.14/development/v4.14.6-proof-matrix.md` produced by `scripts/dev/settings_proof_spike.py` against a fresh session of the real tool. A cell with no Proof Record is cataloged Not-Settable with its reason. The decision is recorded in `docs/decisions/implemented/tooling/2026-10-15-settings-control-admission.md`.

Shared keys (the ones `configs/platform-defaults.json` also seeds) are listed in `docs/policy/platform-defaults-levers.md`. The catalog points to that entry, and `tests/validators/test_settings_control_catalog.py` fails when the key or its value set disagrees.

## Resolution rules

`nexus-hub settings show` reports one record per control, tool, and surface (`cli` rows read files, `vscode-host` rows are read by the panel). Each record has exactly one state. Anything the resolver cannot verify goes in a separate `caveats` list, never in a second state. The rules live in `scripts/lib/settings_control/resolve.py` and read only the catalog, so a change of admission changes a row with no code change.

States are decided in this order for a cell:

1. `not-settable`: no write in the cell is admitted. The catalog reason is shown, and any override layer currently present is listed in `caveats` so a known harm (for example a legacy `env.CLAUDE_CODE_EFFORT_LEVEL`) stays visible.
2. `tool-not-installed`: neither the tool's command is on `PATH` nor its configuration directory exists.
3. `cannot-detect`: the user file or a file a layer could live in is not valid JSON or TOML (the line is named), the tool's `--version` call failed or took over 5 seconds for a version-ranged write, or the row belongs to VS Code, which the CLI never parses.
4. `unverified-for-version`: the installed version is older than the write's proven minimum. Layers found are still listed in `caveats`. A version newer than the proven maximum keeps its normal state and gains one `caveats` note naming the last version checked, because vendors ship weekly and keep documented setting keys.
5. `overridden-by`: a higher layer sets the key. The layer and its catalog fix line are shown, and further layers are listed as `Also set`.
6. `not-covered`: Claude effort only, when a current model id has no `modelSettings` entry while some effort value is set.
7. `in-effect` when the user's file sets the key, otherwise `tool-default`.

Layers are ranked managed file, then environment (the shell, then a settings `env` block), then project file, then user file. An environment layer always overrides, because the vendor says it outranks `/effort` and every saved value. A file layer that holds the same value as the user's own key overrides nothing. Two catalog `detect` gates mirror vendor text: `ignored_values` (the vendor ignores `bypassPermissions` and `auto` from project files) and `when_value_in` (`permissions.disableBypassPermissionsMode` only matters when the user's default is `bypassPermissions`).

Layers no file or API exposes (MDM, server-managed settings, `requirements.toml`, organization policy, the VS Code mode indicator) are `caveats`. Project files are display data only: a file over 1 MB is not read, a symlink leading outside the project is not followed, a Codex project file is read only when `projects."<path>".trust_level` trusts the project or an ancestor, fix lines come from catalog text, and echoed values are cut to 80 characters. Each file is read once into an immutable snapshot.

## Claude Code (fetched 2026-10-30)

Sources: https://code.claude.com/docs/en/settings, https://code.claude.com/docs/en/settings-reference, https://code.claude.com/docs/en/model-config, https://code.claude.com/docs/en/env-vars, https://code.claude.com/docs/en/permission-modes, https://code.claude.com/docs/en/vs-code, https://code.claude.com/docs/en/managed-settings, https://code.claude.com/docs/en/authentication.

- **Precedence and reload.** "Settings precedence, highest first: managed settings, command line, project local, shared project, user." Environment variables "aren't a level in this stack": "`ANTHROPIC_MODEL` exported in your shell applies over the `model` key from any file". Claude Code "watches your settings files and reloads them when they change" and applies most edits to the running session, but "reads some keys only once, at session start"; `model`, `effortLevel`, and `modelSettings` change mid-session with `/model` and `/effort`.
- **Effort.** `effortLevel` accepts `"low"`, `"medium"`, `"high"`, `"xhigh"` and `"max"` "isn't accepted as a level in either key". `modelSettings` maps "a model name to an object" with `effortLevel`; "Claude Code writes each entry under the model's canonical name, such as `claude-opus-5-5`, and matches that model's alias, date-suffixed, `[1m]`, and recognized provider-specific IDs to the same entry." Whether a hand-written alias key is accepted: not found. Order: "1. The `CLAUDE_CODE_EFFORT_LEVEL` environment variable 2. A level you pick in the session ... 3. Launching with `--effort` 4. Your settings". A top-level `effortLevel` "in your user settings file doesn't count for Opus 5.5", which "starts at `medium`"; in project, local, or managed settings it "applies to every model". The environment variable row: "Takes precedence over `--effort`, `/effort`, and the `modelSettings` and `effortLevel` settings."
- **Model.** `model` is "a model alias or full model ID", scope "Any file". Priority: "1. During session ... 2. At startup: `claude --model` 3. Environment variable: `ANTHROPIC_MODEL` 4. Settings 5. `ANTHROPIC_DEFAULT_MODEL`".
- **Posture.** `permissions.defaultMode` values: `default` (alias `manual`), `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions`. "`auto` and `bypassPermissions` don't take effect from project or local settings, so set them in `~/.claude/settings.json`." "For conversations the VS Code extension starts, Claude Code reads only user, managed, and `--settings` values." `skipDangerousModePermissionPrompt` has scope "User, local, or managed". `permissions.disableBypassPermissionsMode` is "the string `"disable"`", scope "Any file", and "takes precedence over `--dangerously-skip-permissions`".
- **Cannot remove under bypassPermissions.** "Deny rules block in every mode, including `bypassPermissions`", plus "Tools matched by an explicit ask rule", the "built-in `AskUserQuestion` tool and MCP tools marked `requiresUserInteraction`", "Recognized `rm` and `rmdir` critical-path removals", connector tools set to `ask`, and "The cross-session messaging safeguards". The page says protected paths such as `.git` and `.claude` are "Allowed" in this mode, so they are not on the Cannot remove list.
- **VS Code extension.** `initialPermissionMode`: "`default`, `plan`, `acceptEdits`, or `bypassPermissions`"; "VS Code reads `initialPermissionMode` from your user settings and ignores workspace values." The mode "you last picked from the mode indicator, if it was Manual, Edit automatically, or Auto" carries over; "Picking Plan or Bypass permissions applies to that conversation only." `allowDangerouslySkipPermissions`: "Adds Bypass permissions to the mode selector." The page does not say that `initialPermissionMode: bypassPermissions` requires it. "Claude Code settings in `~/.claude/settings.json`: shared between the extension and CLI."
- **Attribution.** `attribution.commit` and `attribution.pr` are strings; "Set it to an empty string to hide commit attribution" and the same for pull requests.
- **Environment and paths.** `CLAUDE_CONFIG_DIR` overrides the configuration directory (default `~/.claude`). On Windows credentials are in `%USERPROFILE%\.claude\.credentials.json`, and with `CLAUDE_CONFIG_DIR` set "Claude Code keeps the `.credentials.json` file under that directory instead". Managed settings: `C:\Program Files\ClaudeCode\managed-settings.json` on Windows, `/Library/Application Support/ClaudeCode/` on macOS, `/etc/claude-code/` on Linux and WSL. Agent-session markers: `CLAUDECODE` is "Set to `1` in subprocesses Claude Code spawns", and `CLAUDE_CODE_CHILD_SESSION` is the stricter marker that IDE extensions do not set.

## Findings that change the plan

1. **Copilot CLI documents a posture key.** `defaultPermissionMode` (`manual`, `assisted`, `allow-all`) sets the mode "for new interactive sessions", is ignored in non-interactive runs, and a managed `permissions.defaultMode` overrides it. The plan assumed allow-all was a launch flag only. The key is cataloged Not-Settable until it can be observed.
2. **VS Code has a second posture key.** `chat.permissions.default` carries `autoApprove`. Cataloged as a candidate beside `chat.tools.global.autoApprove`.
3. **Copilot CLI is not installed on the proof machine.** Every Copilot CLI cell has no Proof Record (unchanged by the 2026-10-31 follow-up, which covered Claude Code and Codex only).
4. **The bypass block type.** The vendor type of `permissions.disableBypassPermissionsMode` is the string `"disable"`. The maintainer's `~/.copilot/settings.json` holds the boolean `true`, which is not the documented type, so whether it blocks anything is unproven.
5. **Claude protected paths.** The plan listed `.git` and `.claude` under Cannot remove. The vendor page says bypass mode writes to them without a prompt, so they are not listed.
6. **Codex agent marker.** No Codex, Copilot CLI, or VS Code agent-session marker variable is documented, so the human-presence guard rests on the TTY test for those tools.

## Probe follow-up (2026-10-31)

Observed in a scratch home against Claude Code 2.1.283 and Codex 0.136.0, recorded in the proof matrix (rows W06, W07, W08, W12, O02). Where an observation differs from the vendor text, both are kept.

- **Readouts.** Claude Code answers `/effort status` and `/model` locally in print mode: "Current effort level: low (...)" and "Current model: `claude-haiku-5-5` (effort: low)". `codex exec` prints `reasoning effort: low` in its header before it contacts the API.
- **Effort layers.** `modelSettings.<id>.effortLevel` read back for each of the four current ids. A top-level `effortLevel` in the user file moved `claude-opus-5` and did not move `claude-opus-5-5`, matching the vendor statement that it does not count for Opus 5.5. `CLAUDE_CODE_EFFORT_LEVEL` beat user `modelSettings` whether exported in the shell or set in a settings `env` block, and a project `effortLevel` of `xhigh` beat user `modelSettings`, matching "applies to every model". Without any setting Haiku read `auto (currently high)` where the vendor page says Haiku 5.5 defaults to `medium`.
- **Attribution.** With the default, the session was told to append a `Co-Authored-By` trailer and a `Generated with` line; with `attribution = {commit: "", pr: ""}` it reported none. The lines arrive in a system-reminder for a session in a git repository, so only a model request shows them.
- **Attribution, final result.** The recitation observation above was replaced by a stronger one on 2026-10-31: Haiku asked to commit a staged file in an isolated scratch git repository (global git config, system config, hooks, and templates cut off so the maintainer's attribution hooks cannot strip the line). With the default, `git log` showed `Co-Authored-By: Claude Code <noreply@anthropic.com>` at the end of the commit message and no `Generated with` footer. The empty-strings case was not run, because that one request cost USD 0.7662 against a USD 0.50 cap. The vendor key is documented and half observed, so `claude.attribution` is Not-Settable until the empty-strings commit is observed; the `pr` text has vendor documentation only.
- **A real file is read.** With `CLAUDE_CONFIG_DIR`, `HOME`, and `USERPROFILE` all in a scratch home, Claude Code still loaded the user's `~/.claude/CLAUDE.md` as memory; `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1` stopped it. A probe that needs the model to answer from its own instructions must set that variable.
- **Budget flag.** `--max-budget-usd 0.10` stopped a request only after it cost USD 0.1245, so a budget flag is not a per-request ceiling; the harness keeps its own running tally.

## Not-Settable cells

Each reason lives in the catalog and shows in `nexus-hub settings explain`. A cell moves to a control only after a Proof Record is added and the validator passes.

## Write rules

Added in v4.14.6 Phase 3. These rules are enforced by `scripts/lib/settings_control/apply.py` and `writers.py`, and every write is planned from catalog rows, so a catalog edit changes behavior with no code change.

1. **What is written.** `nexus-hub settings set <control> <value>` writes each admitted row for the requested tool, or every tool. A Not-Settable row, a tool that is not installed, a control value with no faithful mapping, and a Codex file that uses `default_permissions` (posture only) are reported as skipped with the catalog's reason, never written. Editor (`vscode-host`) rows are returned for the panel to write through the VS Code configuration API. A dict value (such as `attribution`) is written leaf by leaf, so unrelated sub-keys survive.
2. **Files.** Writes are atomic, follow symlinks to the real file, keep mode bits (and the DACL on Windows), preserve comments and unrelated bytes, address keys as segment arrays, and are refused when the file does not parse or changes between read and write. The one remaining race is the few microseconds between the final hash comparison and the rename.
3. **Ownership record.** `~/.nexus-hub/settings-control.json` (owner-only) holds, per tool, file, and key path, the first previous value and the value written. `reset` restores a key only while it still equals what was written; otherwise it refuses, names both values, and drops the entry. A removal also stores the exact removed text so `reset` puts the key back in its original place. An entry matches only an admitted catalog write on exactly its tool, file, and key path (a Not-Settable row and an omitted key never match), so a forged or stale entry is ignored and reported, and no file path is read from the record. Every read-modify-write of the record, together with the read and write of the tool file it describes, runs under one exclusive lock file (`settings-control.lock`, an `fcntl` or `msvcrt` advisory lock that the operating system releases when a process dies, the same pattern the installer uses). A command that cannot get the lock in 30 seconds stops with a message and has written nothing. Added in fix cycle 1: before it, a refused write saved a stale snapshot over the record and concurrent commands lost entries.
4. **Installer agreement.** Both installers and the platform-defaults seeder skip every key path in the record. An unreadable record stops seeding for the files it could affect.
5. **Human presence.** Three kinds of change need a person: a write that lowers a safety barrier (`weakens_safety`), every `remove-override` (whether or not the key it removes guards safety), and a `reset` that would put back a weaker value than the one Nexus-Hub wrote (the restored value is checked with the same catalog rule as a `set`, so `bypassPermissions`, `allow-all`, auto-approve, and `block_git_bypass_flags` false all count). A person means an interactive terminal (stdin and stdout are terminals and the person types `yes`, after a printout of the keys) or a one-time panel confirmation (below). All are refused when any agent-session marker named in the catalog is set, whichever tool it belongs to, even with a terminal and even with a valid confirmation. There is no bypass flag. A `reset` that restores a safe value, or removes a key Nexus-Hub added, stays open to an agent: it only undoes a choice toward more safety, and an agent that could not do it would leave a person's own earlier default unreachable. A dry run needs nobody and reports `confirmation.required`. The reason `reset` is gated at all: the plan's rule is "any write with `weakens_safety`", a reset is a write, and without the gate an agent could restore `bypassPermissions` a person had replaced with Ask (finding AF-2 of the Phase 6 deep pass).
6. **Panel confirmation.** The panel writes `~/.nexus-hub/settings-panel-token.json` (created exclusively with mode 0600, which on Windows leaves the user profile's access list in force; deleted by the panel after the call and by the engine on first read) holding only `token_sha256`, `issued_at`, and the exact `action` (`set`, `reset`, or `remove-override`), `control`, `value`, and `tool`, valid 30 seconds. The nonce whose SHA-256 the file holds is generated fresh for each call and handed to the one command the panel starts through that command's environment (`NEXUS_SETTINGS_PANEL_NONCE`); it is never written to disk and the panel removes any inherited value from the child's environment. The engine honors the file only when the nonce in its own environment hashes to the digest, so a process that merely plants or reads the file cannot use it. On POSIX the engine also requires that the file is owned by the user and not readable by others. Added in fix cycle 1: before it the file carried a plain `token` string that nothing verified, so planting any such file was enough.
7. **Residual.** A process running as the same user can do everything the panel does: write the file, put the nonce in a child's environment, and unset the agent marker. The nonce stops a planted or merely read file and the replay of a consumed one; it cannot stop a deliberate forgery by a same-user process, and no design that keeps the panel and the command line as separate programs can, because anything the panel holds, a same-user process can also obtain. The barriers that remain are the agent-marker refusal (which a process can defeat only by deliberately unsetting the variable in a child it starts) and the terminal test. This was reproduced after the fix (`AF-3d` in the Phase 6 evidence) and is recorded, not closed. The planned second layer is the agent-call hook rule (DF-25). Codex, Copilot CLI, and VS Code document no agent-session marker (see finding 6), so for those tools only the terminal test applies.
8. **Removable overrides.** `remove-override` deletes only the keys in the catalog's `removable_overrides` (Claude `env.CLAUDE_CODE_EFFORT_LEVEL` and `permissions.disableBypassPermissionsMode`, Copilot CLI `permissions.disableBypassPermissionsMode`), and only while the owning control has an admitted write on that tool.

## Panel contract

Added in v4.14.6 Phase 4. The VS Code panel (`extensions/nexus-hub-settings/`) is a thin client of the command line. It holds no catalog of its own: every control, value, tool, key, source, and Cannot remove item it shows comes from `nexus-hub settings show --json` and `nexus-hub settings explain <control> --json`.

1. **JSON additions.** `show --json` records carry `removable_override` (`null`, or `{id, weakens_safety, reason}`), set only when a catalog `removable_overrides` key is present in the user's file and `remove-override` would be accepted for that cell. The panel offers "Remove this override" from this field and never infers it from the layer text. `explain --json` carries `control.per_tool`, `control.never_written`, and a top-level `claude_model_ids` list (the bundled ids, used as model suggestions). Both are additive: `schema_version` stays 1.
2. **Launch.** The panel runs `execFile` with `shell: false`, an absolute interpreter, the absolute `~/.nexus-hub/scripts/nexus_hub_cli.py` (or `NEXUS_HUB_HOME` when it is an absolute path), the install root as working directory, `windowsHide: true`, and a 15-second timeout. The interpreter is the user-scope `nexusHubSettings.pythonPath` value (machine scope, so a workspace can never choose it), else the first existing file in a fixed list of standard install locations (Windows per-user, machine, and Microsoft Store installs, then the `py.exe` launcher; `/usr/bin/python3` and similar elsewhere). PATH, the working directory, and the workspace are never searched, so a `nexus-hub.cmd`, `nexus-hub.exe`, or `python.exe` planted in a repository is never run. The workspace folder reaches the command only as `--project=<folder>`, which the engine reads as data.
3. **Order of a change.** The panel plans with `--dry-run`, checks every planned VS Code key with `inspect()` (a workspace or folder value aborts the whole change and is reported as `overridden-by workspace setting`; a key no installed extension contributes is skipped), asks a person to confirm when `confirmation.required` is true, writes the one-time confirmation just before the real call (and hands the nonce to that one command), then applies the VS Code keys at the user (Global) layer and reports each previous value through `record-editor-write`, recording the active profile name. A failed editor write calls `reset` for that control, with its own confirmation because it undoes a change the person approved a moment earlier, and applies the restores it returns. Operations are serialized, and the panel re-reads after every write and after any change to a tool configuration file.
4. **Reset.** The panel plans a reset with `--dry-run` first. When the engine reports that it would put back a weaker value (`confirmation.required`), the panel opens a modal that lists each key and the value it returns to, and sends the real reset with a confirmation only after the person agrees. The engine returns `editor_restores`; the panel restores a VS Code key only while it still holds what Nexus-Hub wrote and only in the profile that wrote it, and otherwise leaves the key and says why.
5. **Rows the engine cannot read.** For an installed row with an admitted `vscode-host` write the engine reports `cannot-detect`, and the panel replaces it with exactly one state read from the key's layers: `overridden-by` (workspace or folder value), `in-effect`, or `tool-default`. VS Code does not expose organization policy to extensions, so the panel adds a note (not a second state) telling the user to look for the lock icon in the Settings editor. A key that is not registered shows `tool-not-installed`.
6. **Confirmation text.** A safety-weakening change opens a modal that lists every key to be written, the Cannot remove items of each tool involved, and, for the posture control, the vendor's own wording for the auto-approve switch ("Automatically approve all tools - this setting disables critical security protections", from the 2026-10-30 settings reference). VS Code's own dialog text was not captured because that row is still a manual observation (proof matrix W23); replace the constant in `viewModel.ts` once it is.
7. **Webview.** The content security policy is `default-src 'none'` with `script-src 'nonce-<per load>'`, `style-src` and `img-src` limited to the extension's own resources, and no network. `localResourceRoots` is the extension's `media` folder. The page script builds the DOM with `textContent` only. Every message from the page is validated against the catalog allowlist (control, value, tool, source write id) before it becomes arguments or an action, and a page never supplies a URL: "Open source" opens only an `https` URL on a vendor documentation host, taken from the engine's own `explain` output.
8. **Untrusted workspaces.** `capabilities.untrustedWorkspaces` is `limited`: the panel shows state and refuses every write while the workspace is untrusted.

9. **Keyboard focus, busy state, and announcements.** While the host works, a control is `aria-disabled="true"` and ignores clicks but stays focusable; only a read-only (untrusted) panel really disables a control, because a disabled control cannot hold focus and the next render would leave focus on the page body. Each render puts focus back on the same control (and the caret in a text field), else on the heading of its card, else on Refresh. Refresh is never really disabled. Sources the person opened stay open. A choice with no current value starts at "Choose a value" and its button waits for a choice, instead of preselecting the first value. A notice is spoken once through two live regions (`role="status"` and `role="alert"`) that exist in the page shell before any text is put in them; the visible notice carries no live role, so nothing is announced twice.
10. **Contrast and layout.** A badge's text is in the foreground color; its tone colors only the outline and the icon, which repeat what the words say. Field edges are the foreground color at 60 percent. `extensions/nexus-hub-settings/test/contrast.test.ts` resolves `media/panel.css` against four sets of `--vscode-*` values (Dark Modern and Light Modern as shipped, and the two high-contrast themes as modeled from VS Code's documented values) and requires 4.5:1 for text and 3:1 for a field's edge and the focus ring. It proves the stylesheet as written, in those four sets; it does not read a running VS Code, and another theme can define any color. The Not settable reasons are written once under the top table rather than in every cell.

## Distribution

Added in v4.14.6 Phase 5. Both installers build and install `extensions/nexus-hub-settings` through the shared extension function, with the VS Code command line only (never Cursor or Antigravity, maintainer decision Q1: the panel writes VS Code user settings, so installing it into another editor would change that editor's settings, not VS Code's). It installs under its own `NEXUS-HUB` header after the last vendor header, with an empty status hint, because the panel has no status-bar item; the installer points the user at the activity-bar view instead. `catalog/hooks/tests/test_installer_smoke.py` asserts the routing in both shells, and `configs/installer-parity.json` carries the declaration. The command line the panel launches reaches users through the installers' whole-tree copy of `scripts/lib` and the `nexus-hub` launcher, so no new copy step exists. The `nexus-hub-settings` group in `scripts/ci/profiles.py` (`--only nexus-hub-settings`) compiles, tests with coverage, packages, and verifies the packaged contents; its agreement test needs Python 3.11 or newer with `tomlkit`.
