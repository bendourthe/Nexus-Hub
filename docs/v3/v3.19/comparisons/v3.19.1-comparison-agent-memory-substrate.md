### Dimension 5 detail: the memory gap

Nexus-Hub has four memory-adjacent surfaces. None of them is what OptMem is, and the distinction is the whole finding.

| Nexus-Hub surface | What it does | Why it is not a persistent memory |
|---|---|---|
| `catalog/skills/workflow/session-query/SKILL.md` | Searches local Claude / Codex / Cursor session logs, Obsidian notes, and exported chat history | Retrospective and query-driven. Requires the user to ask. Returns a digest, not a maintained state |
| `catalog/skills/workflow/context-pack-builder/SKILL.md` | Distills prior digests into `docs/context/<topic>.md` | Manual, on-demand, topic-organized. Explicitly a DISTILL step downstream of `session-query` |
| `catalog/skills/workflow/continuous-learning/SKILL.md` | Mints confidence-scored `.nexus/instincts/<slug>.yaml` behavioral rules | Stores *how to behave*, not *what happened*. Clustering is on-demand, not continuous |
| `catalog/memory/decisions.md` | A 68-line static ADR template | A blank template shipped to users. Holds no state and has no write path |

The unmet capability, stated precisely: **an always-on, append-only, chronological store that the agent writes to continuously during work, reads in full at every session start under a fixed token budget, and compresses automatically as it grows, with no user prompting at any step.** `extensions/` contains no memory package (`nexus-code-search`, `nexus-context-compressor`, `nexus-skill-scanner`, `nexus-skill-server`, `nexus-web-fetch`, plus two usage monitors).

### The four techniques worth taking

1. **Age-decaying summarization tree over an append-only log.** Memories append to a flat log and never mutate. Aligned power-of-two ranges of memories are compressed into single-line summaries forming a binary tree. A read tiles the log with blocks chosen so that recent entries stay verbatim while older ones collapse into progressively coarser summaries. The tiling parameter is found by binary search so the output lands within a caller-supplied line budget. The tree is a pure cache: deleting it loses nothing, because it is rebuildable from the log alone.

2. **The compressing model is the calling agent, not the tool.** When a merge comes due, the tool prints a compression request plus the exact command to run with the result. The agent produces the summary and hands it back. The tool therefore makes zero LLM calls, needs zero API keys, and adds zero outbound traffic, while still getting model-quality summarization. This is precisely tier 2 of the Nexus-Hub MCP Registry Policy decision tree (LLM-native, achievable by instructing the agent's own model) applied to a storage engine.

3. **Fixed-width records make position identity.** Every log line and every tree line is padded to a constant byte width, so record *N* lives at offset *N* times the width. Every lookup is one seek, there is no index file to keep in sync, and a level file's byte length alone reveals exactly how far compression has progressed at that level. The cost is roughly 2x on disk.

4. **Output paging sized to the consuming harness.** Output is split into parts bounded by both a byte cap and a line cap, chosen so a single part survives the truncation behavior of every target CLI. The upstream source records three concrete limits it targets: one harness truncates the middle at 30,000 characters, another truncates the head at 50 KB, and a third budgets 10,000 tokens. These are transport limits, deliberately separated from the memory's own size limits.

### Installer and registry obligations

A new `extensions/nexus-memory/` package inherits the standard obligations recorded in `AGENTS.md`:

- A new skill under `catalog/skills/<category>/` requires updating `data/SKILL_INDEX.md`, `data/skills.json`, and `data/marketplace.json` by hand. Do **not** run `build_skills_catalog.py`, which rewrites the entire tree.
- Any new file under `scripts/<name>.py` must be registered by explicit name in **both** `scripts/installer.sh` and `scripts/installer.ps1`. Files inside `extensions/` and inside a skill's own `scripts/` subdirectory are copied recursively and need no installer edit.
- Every `.sh` shipped in a skill bundle needs a `.ps1` sibling.
- A new internal MCP requires a row in `docs/policy/mcp-reverse-engineering-matrix.md`, classified `already-local`.

## Step 7: Risks, conflicts, and items not recommended

### Conflicts with existing Nexus-Hub conventions

| ID | Conflict | Resolution |
|---|---|---|
| A4 | **Overlaps four existing skills.** `session-query`, `context-pack-builder`, `continuous-learning`, and `solution-knowledge-base` all touch prior context. A fifth surface without clear boundaries would make skill routing ambiguous and would trip the trigger-eval gate | Write the new skill's `description` with an explicit `SKIP` clause fencing off all four. Ship `evals/trigger-cases.json` with at least three positives and three near-miss negatives drawn from those four skills. This is mandatory: the routing eval is a hard gate as of v3.15.2 |
| A4 | **Competes with the harness-native memory directory.** Claude Code already provides a per-project file-based memory with a `MEMORY.md` index. A second parallel store risks split-brain, where facts land in one and are read from the other | Decide the relationship explicitly during planning. Recommended: the new store is the durable cross-platform substrate, and the harness-native directory stays the Claude-specific index. Do not silently duplicate |
| A1 | Existing scripts already print freely with no truncation contract | Introduce the contract as a shared helper plus a documented convention. Retrofit opportunistically rather than in one sweep, to respect the scope rule that every changed line traces to the request |
| A4 | Automatic writes conflict with the repo's "ask first" posture on new categories and installer changes | Memory writes are the agent's own working state, not repo mutations. Keep the store outside the repo by default |

### Standing risks

- **R1, maintenance surface.** A storage engine with a compression tree, a locking strategy, and corruption recovery is a genuine ongoing cost. The upstream source needed 611 lines of tests for 859 lines of implementation, and that ratio is a fair estimate of the real cost. Budget test effort accordingly rather than treating this as a small feature.
- **R2, confidentiality at rest.** A memory store accumulates plaintext facts about the user, their projects, and possibly their clients. Default the store to a local user-scoped path, document that a relocated root inherits that destination's exposure, and apply `[[egress-redaction]]` discipline before any memory content is included in a shared artifact.
- **R3, accidental commit.** A store relocated into a project directory can be committed. Ship an ignore-pattern recommendation and consider a guard in the secret-scan hook path.
- **R4, unverified transport limits.** The three per-CLI truncation figures cited above come from the source's own comments and are undated. Re-verify each against current CLI behavior before hard-coding. Treating a stale figure as fact is exactly the drift the `platform-contract-verification` skill exists to catch.
- **R5, source volatility.** The source repository is three days old at the time of this report. Its design may change substantially. This is not a blocker, because the adoption is clean-room and idea-level, but do not treat any specific constant as settled.

### NOT recommended for adoption

| Item | Grounds |
|---|---|
| **Vendoring or copying any upstream source file** | No license file exists, so all rights are reserved. This is a hard legal block, not a preference. Clean-room reimplementation from the behavioral descriptions in this report is the only permitted path |
| **Naming the upstream project in any shipped artifact** | Reverse-Engineering Attribution Rule in `AGENTS.md`. Attribution stays in this report and the RE matrix row |
| **The `curl \| sh` single-file distribution model for the memory tool** | Nexus-Hub already solved this in v3.7.0 with the dual-mode `install.sh` / `install.ps1` bootstrap plus `nexus-hub upgrade`. Adopting a second, parallel install path would fragment the install story for no gain. Classified `.` (both, equivalent) |
| **The `anim/` demo-render pipeline (Node plus ffmpeg)** | Adds a Node toolchain dependency to produce a marketing GIF. Nexus-Hub already has the `demo-capture` skill for local PR evidence. Classified `~`, and the existing approach is better fitted |
| **A background or daemonized compression process** | Not present upstream either, and correctly so. Nexus-Hub's zero-background-process posture is a strength to preserve. Compression must stay synchronous and agent-driven |
| **Copying the specific per-CLI truncation constants as authoritative** | Undated third-party figures about systems that change. Re-derive them. See R4 |
