## Executive Summary

The two sources sit on opposite sides of Nexus-Hub. RTK is a Rust CLI that compresses noisy command output (git, cargo, npm, docker, kubectl, pytest, aws, terraform, and 60-plus more) into token-efficient text for AI coding agents, plus a family of command-rewrite hooks for eleven-plus platforms. Nexus-Hub already reverse-engineered RTK's declarative filter layer into the internal `nexus-context-compressor` engine, so the RTK comparison answers a narrow, high-value question: what did the real RTK build that a from-scratch filter engine plus multi-platform hook distribution is most likely missing. Meterless is the opposite kind of project: a repository of AGENTS.md-driven engine specifications (H-MEM hierarchical memory, Markovian reasoning-compression, Scout Intent signed-execution-contracts, World Model) with almost no runtime code. Its value to Nexus-Hub is in packaging conventions, memory architecture, and eval discipline, and it is overwhelmingly skill-native (patterns and conventions to adopt) rather than code to copy.

The genuine adoption value is concentrated and clean. Every candidate below is local-only, skill-native, or reverse-engineerable. Not one introduces an outbound call, an API key, a new third-party data processor, or a new runtime dependency, so the MCP Registry Policy gate mostly confirms ordering rather than dropping anything for data-flow risk. Two supply-chain items stand out as high-value and low-effort: adding SHA-256 integrity verification to the Nexus-Hub bootstrap download (RTK refuses to install a binary whose checksum is not in a signed `checksums.txt` and rejects path-traversal entries before extraction), and a CI lint guard that fails the build if the compressor engine makes any network call (RTK enforces this via `.semgrep.yml` confining all network code to one opt-in telemetry module). The deeper tracks are RTK's semantic reformatters and its single-source-of-truth command-rewrite protocol on the RTK side, and memory provenance-as-invariant plus per-slice eval floors on the Meterless side.

Everything RTK does for outbound telemetry, release-binary distribution, and multi-language READMEs is either against Nexus-Hub policy or not applicable to a config-tree catalog, and is moved to the NOT-recommended list.

## Inventory (dimensional findings)

### RTK

- Identity and docs (`Cargo.toml`, `CHANGELOG.md`): version 0.42.4, Apache-2.0, "Rust Token Killer". README is high quality with a token-savings table; seven-language READMEs; a full docs site under `docs/guide`, `docs/usage`, `docs/contributing`, `docs/maintainers`.
- Compression engine (two tiers plus a router). Tier A: ~60 Rust-native command handlers under `src/cmds/` that parse and restructure output (group clippy/tsc/eslint diagnostics by file, show only test failures, structured `git status`/`aws`/`docker`) across 11 ecosystem groups. Tier B: 63 declarative TOML filters under `src/filters/*.toml` (documented count asserted by test at `src/core/toml_filter.rs`), an 8-stage line-processing pipeline with inline `[[tests]]`, concatenated at compile time by `build.rs`. Router: `rtk rewrite` (`src/discover/registry.rs`, `src/discover/rules.rs` with ~75 rewrite rules, `src/hooks/rewrite_cmd.rs`) is lexer-aware (`src/discover/lexer.rs`) and splits compound commands, rewrites only the left of a pipe, strips env prefixes, and refuses unattestable constructs.
- Filter lookup priority and trust (`src/core/toml_filter.rs`, `src/hooks/trust.rs`): project-local `.rtk/filters.toml`, then user-global, then built-in, then passthrough. User-supplied filter files are not applied until trusted via a SHA-256 content hash; editing a trusted file re-invalidates it.
- Multi-platform hooks (`hooks/README.md` and 11 platform dirs plus `openclaw/`): a shared exit-code protocol (0 allow, 1 passthrough, 2 deny, 3 ask) with all hook artifacts as thin delegates to `rtk rewrite`. A security test pins that the default maps to exit 3 (ask), never 0 (auto-allow). Host-permission integration (`src/hooks/permissions.rs`) reads Claude/Cursor/Gemini/Droid native settings with Deny > Ask > Allow > Default precedence and per-segment allow enforcement for compound commands. `rtk init` (`src/hooks/init.rs`) wires the hooks and integrity-stamps them.
- Installer and distribution: `install.sh` (checksum plus path-traversal guard), `Formula/rtk.rb` (Homebrew), cargo/crates, `.deb`/`.rpm` metadata, `release-please` automation, and a 5-target release build matrix that injects the telemetry env vars only for official builds.
- CI/CD, security, testing: `.semgrep.yml` (7 error rules confining network calls and forbidding dynamic exec and raw sockets), `dependabot.yml`, `SECURITY.md`, ~2,450 inline `#[cfg(test)]` tests, build-time filter validation, and a VM benchmark harness (`scripts/benchmark/`).
- Notable patterns: a typed `config.toml` with tunable `[hooks]`/`[limits]`; non-destructive truncation via a `Lossiness` enum plus tee-to-file recovery (`src/core/tee.rs`); meta commands `rtk gain` (savings dashboard from a local SQLite tracking DB), `rtk discover` (mine past session logs for unrealized savings), `rtk learn` (detect repeated CLI mistakes and emit a rules file), and `rtk verify` (run filter inline tests); passthrough/gap tracking as a roadmap signal.

### Meterless

- Identity and structure: Apache-2.0, per-engine versioning (`<engine>-v<semver>`), no single repo version. Root `AGENTS.md` is a pure sub-100-line router (machine-capped by `scripts/check-conventions.mjs`) with a hard folder-isolation rule; `llms.txt` mirrors the map for non-coding agents; each engine ships a 2-line `CLAUDE.md` shim that re-points to its `AGENTS.md` so Claude Code auto-loads the contract.
- Engine spec bundle (`engines/hmem/`): a self-contained unit with `AGENTS.md` (the implementation contract), `docs/` deep-dives with a reader-path index, numbered `examples/` (each a teaching folder), `workshops/`, `demos/`, `conformance/` (a `runner.ts` plus `vectors/vectors.json`), `evals/`, and a runnable `reference/`. Distributed as a single unit via `npx degit`.
- H-MEM (`engines/hmem/AGENTS.md`): memory as a provenance-carrying knowledge graph. Every record requires a `source` (a record with no source is rejected by construction), carries a `confidence`, and is mutated only through an append-only trust ledger of 17 action types with feedback deltas (`helpful +0.05`, `wrong -0.20`) that feed back into ranking. Three tiers with a forgetting curve; an 8-signal hybrid retrieval formula; human-approved "dreaming" synthesis producing `derivedFrom` records; preview-first "sleep" maintenance with backup/restore; conflict resolution that marks losers `supersededBy` but never deletes.
- Markovian (`engines/markovian/AGENTS.md`, `docs/efficiency-model.md`): chunked reasoning for O(1) per-step context via a marker protocol and a structured carryover shape produced by a 4-level compression cascade. Efficiency figures are explicitly labeled as modeled, not measured.
- Scout Intent (`engines/scout-intent/AGENTS.md`): a Sense/Interpret/Guard/Route/Recommend pipeline. An intent registry is the entire surface area ("if an intent is not in the registry, it cannot be acted on"), with two-stage scoring, confidence bands (High/Medium/Low/Reject), explicit clarification triggers and a clarification-rate ceiling, a five-layer risk-guard stack, and signed, TTL-expiring, immutable execution contracts that are the only artifact executors accept.
- Evals: the Scout Intent harness (`engines/scout-intent/evals/`) uses a locked, versioned regression set and a runner that computes metrics with per-slice hard floors, so a release that holds aggregate accuracy but drops a single slice below threshold fails the gate; lowering a threshold requires its own PR. The other three engines ship env-injected conformance runners that assert exact-tier behavior (`HMEM_IMPL=...`).
- Governance discipline: three zero-dependency `.mjs` CI checkers enforce case-sensitive link integrity, kebab-case and no-empty-folders and a line budget, and smoke-run every example. Pervasive intellectual-honesty labeling (modeled vs measured, targets vs results).

## Step 3: Classification of differences

- External-only, adoption candidates (RTK): semantic reformatters (Tier A), the command-rewrite exit-code protocol, host-permission gating, BYO-filter with content-trust and inline tests, non-destructive truncation, installer integrity verification, the zero-outbound lint guard.
- External-only, adoption candidates (Meterless): memory provenance-as-invariant plus ledger, triggering confidence bands plus clarification ceiling, per-slice eval floors and no-lowering-thresholds discipline, case-sensitive link-integrity and convention CI checkers, tiered memory metabolism, the signed-execution-contract capability model.
- Both, different approach: RTK's `discover`/`learn` session-log mining (Nexus-Hub has `session-query` and `continuous-learning`); the CLAUDE.md-to-AGENTS.md auto-load shim (Nexus-Hub already imports `@AGENTS.md`); RTK's local savings dashboard (Nexus-Hub has `product-pulse`).
- Both, equivalent: Apache-2.0 licensing, a substantial docs tree, dependabot/security policy presence.
- Current-only strengths to preserve: the 267-skill catalog and 3-tier SKILL.md progressive disclosure, the 13-plus-platform installer breadth, the zero-outbound MCP Registry Policy (RTK ships opt-in telemetry; Nexus-Hub deliberately ships none), and the reverse-engineer-first governance.

## Step 6: Sequenced adoption plan (RE-first, dependency-aware)

Pass `reverse-engineer-first=true` when chaining into `/plan from-comparison`.

- Phase 1 - supply-chain quick wins (re-full, P0). A1 installer SHA-256 verification and tarball path-traversal guard on the bootstrap download; A2 a CI lint guard that fails the build if `nexus-context-compressor` engine code makes a network call. Both are self-contained and unblock a "zero-outbound, verified-install" posture.
- Phase 2 - authoring and eval discipline (skill-native, P1). B2 triggering confidence bands plus a clarification-rate ceiling folded into `skill-description-authoring`; B3 per-slice hard floors and a no-lowering-thresholds rule folded into `skill-eval-loop`; B4 a case-sensitive link-integrity checker and convention checks added to `make validate`.
- Phase 3 - memory hardening (skill-native, P1 then P2). B1 provenance-as-invariant (require a `source`/origin field, add an append-only change log) in the `memory` skill and MEMORY.md conventions; then B5 a tiered promotion/archival lifecycle with a preview-first maintenance pass.
- Phase 4 - compressor and hook depth (re-full then re-partial, P1). A3 a shared command-rewrite exit-code protocol as a single source of truth with thin per-platform delegates; A4 host-permission gating reading each host's own settings; then A5 the highest-frequency semantic reformatters.
- Phase 5 - compressor polish (re-full, P2). A6 BYO-filter extensibility with a content-trust gate and inline tests; A7 non-destructive truncation with tee-to-file recovery; A8 extend session-log mining in `session-query`/`continuous-learning` to surface unrealized savings.
- Deferred - B6 the signed-execution-contract capability model as a design study for the hook/permission system (concept, P3).

## Step 7: Risks, conflicts, and NOT-recommended items

- Conflicts with existing conventions: A1 assumes a verifiable artifact; Nexus-Hub installs from a `main` git tarball rather than versioned release binaries, so the honest implementation is to pin to a release tag and verify the commit SHA (or publish a per-release checksum), not to invent a binary release channel. A5 semantic reformatters risk scope creep across dozens of tools; cap Phase 4 at a named short list and log the coverage gap rather than promising parity with RTK's ~60 handlers.
- New maintenance burden: A3/A4/A5 add per-platform and per-tool surface area that must track upstream host changes; this is the same drift risk the existing platform-contract-verification step manages, so route these through it. A6 executing user filter files is only acceptable with the content-trust gate shipped in the same change.
- Higher-risk (edits to existing files) vs lower-risk (new files): Phase 1 and Phase 2 are mostly additive (new CI checks, authoring rules). Phase 3 edits the memory write path and MEMORY.md format (migration needed for existing memory files). Phase 4 edits installed hook artifacts across platforms.
- NOT recommended for adoption:
  - RTK outbound telemetry (`docs/TELEMETRY.md`, `src/core/telemetry.rs`): violates the zero-outbound MCP Registry Policy. The only defensible slice is local usage analytics, which `product-pulse` already covers. Policy grounds: Hard-No list (no analytics-as-service) and the zero-outbound default.
  - Homebrew formula and release-binary distribution (`Formula/rtk.rb`, `.github/workflows/release.yml`): not applicable. Nexus-Hub is a config-tree catalog installed into per-platform locations, not a single binary. Adopting a binary channel would duplicate the installer without reducing surface.
  - Seven-language READMEs: low value for the current audience; revisit only if internationalization becomes a goal.
