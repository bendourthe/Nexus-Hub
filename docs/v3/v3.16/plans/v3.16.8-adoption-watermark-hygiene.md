# Plan - Watermark Hygiene: Unicode Fix Mode + /plan and /update Wiring

**Project**: Nexus-Hub
**Version**: v3.16.8
**Slug**: adoption-watermark-hygiene
**Plan Type**: Feature (adoption, seeded from comparison)
**Created**: 2026-08-13
**Seeded from**: docs/v3/v3.16/comparisons/v3.16.8-comparison-watermark-hygiene-and-harness-engineering.md
**Goal**: Every plan file `/plan` writes and every release `/update release` ships is automatically free of invisible Unicode watermark characters and non-ASCII punctuation, enforced by the existing local validator extended with a fix mode, with zero new dependencies.

## Overview

This plan operationalizes the four P0 adoption items from the watermark-hygiene comparison (A2, A1, A3, A4, in RE-first order). Nexus-Hub already detects the core invisible-character set (zero-width characters, Trojan-Source bidi controls) and non-ASCII punctuation via `scripts/validate_unicode_safety.py`, wired into `make validate` and CI. What is missing is an auto-clean capability, a few character classes used for hidden-text smuggling, and the workflow wiring: `/plan` writes plan files without sanitizing them, and `/update release` has no explicit pre-commit hygiene gate.

Phase 1 extends the validator in place: new character coverage (exotic space homoglyphs, Unicode tag characters, soft hyphen, VS16) and an opt-in `--fix` mode with atomic writes, preserving the detect-only default, the 0/1/2 exit-code contract, the `.ps1` BOM exemption, and the non-English-content exemption. Phase 2 wires the workflow surfaces: the plan-writing step gains a mandatory closing sanitize pass (`--strict --fix` on the just-written file), and `/update` gains scope-appropriate gates (detect on docs/changelog scopes, fix-and-block on release artifacts in the release scope). Phase 3 is the mandatory refactor / known-gaps / CI/CD closing phase.

**Ingested post-release defect (added 2026-08-14).** Two sub-tasks in this plan (1.3 and 2.3) do NOT come from the watermark-hygiene comparison. They are the two halves of `BG-2`, a v3.16.7 post-release defect recorded in `docs/v3/v3.16/known-gaps.md`: the manifest generator's blob hashing does not account for a `.gitattributes` `eol=crlf` file, so `nexus-hub verify` returns FAIL on a clean install from the published tarball. The code half joins Phase 1 (extend one `scripts/` file, preserve its contract, test it) and the process half joins Phase 2 (a missing `/update release` gate). They share this release's theme of bytes being exactly what they claim to be, but they are tracked as INGESTED rather than as adoption items so the comparison's scope stays legible.

Success looks like: a plan file generated with a deliberately injected zero-width space comes out clean without manual intervention, `/update release` refuses to commit release artifacts carrying invisible characters, `make validate` and CI behavior are byte-for-byte unchanged for existing callers, and no new dependency, outbound call, or credential is introduced. The two upstream sources' other capabilities (statistical watermark defeat, C2PA/EXIF stripping) are explicitly NOT adopted, per the comparison's NOT-recommended list.

## Phase 1: Validator Coverage and Fix Mode

**Goal**: Extend `scripts/validate_unicode_safety.py` with the missing character classes and an opt-in `--fix` mode, without changing behavior for any existing caller.
**Prerequisites**: None.
**Stability Gate**: `pytest tests/validators/test_validate_unicode_safety.py` passes with new cases for every added character class and for fix-mode round-trips; `make validate` output on the current tree is unchanged versus the pre-change baseline (same findings, same exit code).
**Recommended model tier**: strong
**Recommended effort level**: high
**Rationale**: Small surface but contract-sensitive: the exit-code protocol, the `.ps1` BOM exemption, and the non-English exemption are load-bearing for `make validate`, CI, and both installers, and fix mode writes files.

### Sub-tasks

#### 1.1 - Extend the detection character set (adoption item A2)

**Objective**: Detect exotic space homoglyphs, Unicode tag characters, soft hyphen, and VS16 in English Markdown, closing the gap versus the upstream deterministic layer.

**Failure modes**: An undecodable (non-UTF-8) file is reported as an IO finding with exit 2, never a crash; an unreadable file (permissions) is likewise reported, not skipped silently; two concurrent validator runs are read-only in detect mode and cannot conflict.

**Prompt**:
> In `scripts/validate_unicode_safety.py`, extend detection coverage. Add to the hard-error set (`_UNSAFE_CODEPOINTS`): Unicode tag characters U+E0001 and U+E0020 through U+E007F (hidden-text smuggling channel). Add to the strict-mode punctuation/space set (`_NON_ASCII_PUNCT_CODEPOINTS`, replacement in parentheses): U+2000 through U+200A (space), U+1680 (space), U+202F narrow no-break space (space), U+205F (space), U+3000 ideographic space (space), U+00AD soft hyphen (delete or `-` per context: delete), and U+FE0F variation selector-16 (delete). Rationale for the split: tag characters are never legitimate in this repo's content, so they are errors like zero-width chars; space homoglyphs, soft hyphen, and VS16 can appear in legitimate non-English text, so they follow the existing warn-by-default / `--strict` promotion path and the existing natural-language exemption. Construct all new entries from codepoint integers like the existing sets, so the validator source stays self-detection-free. Do not change the `.ps1` BOM exemption, the exit-code contract (0 no errors / 1 errors / 2 usage-IO), the CLI surface, or the default targets. Update the module docstring's character inventory. Add pytest cases in `tests/validators/test_validate_unicode_safety.py` covering at least one character from each new class, both the error path and the strict-warning path, plus a case proving a `.ps1` leading BOM is still exempt. Acceptance: new tests pass; the full existing test file passes unchanged; `python scripts/validate_unicode_safety.py` on the current repo exits with the same code and finding count as before the change.

---

#### 1.2 - Add the opt-in fix mode (adoption item A1)

**Objective**: Give the validator a `--fix` flag that removes hard-error characters and applies the prescribed ASCII replacements for strict findings, then re-validates, so callers can clean files deterministically instead of looping on manual edits.

**Failure modes**: Malformed or undecodable input is never written back (fix skips the file, reports it, exits 2); a write failure mid-fix cannot corrupt the original because writes go to a temp file in the same directory followed by an atomic rename; two concurrent `--fix` runs on the same file each perform a whole-file atomic replace, so the result is one run's complete output, never an interleaved file.

**Build class**: load-bearing.

**Prompt**:
> In `scripts/validate_unicode_safety.py`, add an opt-in `--fix` flag. Behavior: for each file with findings, remove every hard-error character (zero-width set, bidi controls, tag characters) and, when `--strict` is also passed, apply the ASCII replacement already prescribed in the punctuation map (em dash to `--`, curly quotes to straight, ellipsis to `...`, NBSP and space homoglyphs to a regular space, soft hyphen and VS16 deleted). Without `--strict`, `--fix` repairs only hard errors. Hard constraints: (1) detect-only remains the default; no caller that omits `--fix` sees any behavior change; (2) the exit-code contract is unchanged, and after a fix pass the exit code reflects the POST-fix state (a fully repaired tree exits 0) while the report lists what was changed per file; (3) never touch files matching the existing exemptions: the leading BOM in `.ps1` files stays, and non-English natural-language content (the existing exemption path) is never rewritten; (4) write via temp-file-plus-atomic-rename in the same directory, preserving the file's original newline style (do not normalize LF/CRLF) and writing UTF-8 without adding a BOM; (5) after writing, re-scan the file and fail loudly (exit 1) if findings remain. Add pytest cases: fix removes an injected ZWSP and a bidi override; strict fix replaces an em dash and curly quotes; a `.ps1` BOM survives fix; CRLF files keep CRLF; a file with no findings is not rewritten (mtime unchanged); post-fix re-validation passes. Acceptance: all new and existing validator tests pass; `python -m py_compile scripts/validate_unicode_safety.py` is clean.

#### 1.3 - Fix the `eol=crlf` residual in manifest hashing (INGESTED: v3.16.7 `BG-2`) - **COMPLETE**

**Objective**: `nexus-hub verify` returns PASS on a clean install from the published tarball.

**Status: DONE 2026-08-14.** `_git_eol_attrs()` + `_apply_eol()` in `scripts/generate_manifest.py`; an archive of the index verifies `OK 1231 file(s) match`, `verify: PASS`, up from `1230 OK / 1 MODIFIED / FAIL`. Four regression tests added. Note the proof subtlety recorded in `BG-2`: a local archive must pin `-c core.autocrlf=false -c core.eol=lf` or a Windows host reports ~1180 false mismatches.

**Provenance**: not from the watermark-hygiene comparison. This is a post-release defect ingested from `docs/v3/v3.16/known-gaps.md` (`BG-2`, v3.16.7), found by downloading the published `Nexus-Hub-3.16.7.tar.gz` and verifying it. It lands in this phase because it is the same shape as the rest of Phase 1: extend one existing `scripts/` file, preserve its contract, and test it. It shares this release's hygiene theme (bytes being exactly what they claim to be) but is tracked as an ingested item, not as an adoption item.

**Prompt**:
> v3.16.7 fixed `scripts/generate_manifest.py` to hash a tracked file's GIT BLOB bytes rather than its working-tree bytes, which corrected roughly 678 spurious mismatches caused by `core.autocrlf` on Windows. One residual remains, and it is a clean edge case rather than a flaw in that reasoning: `git archive` (and therefore the GitHub release tarball) APPLIES `.gitattributes` eol conversion, so for a file declared `text eol=crlf` the distributed bytes are CRLF while the blob is LF. `.gitattributes` declares `scripts/nexus-hub.cmd text eol=crlf` deliberately, so the Windows launcher ships with CRLF, and it is the ONLY such file in the covered roots (`git ls-files -- catalog templates scripts data | git check-attr --stdin eol` returns exactly one `eol: crlf`).
>
> Measured impact on the published v3.16.7 artifact: `verify_install.py` reports `OK 1230 file(s) match`, `MODIFIED scripts/nexus-hub.cmd`, verdict `FAIL (1 modified, 0 missing, 0 extra)`. Confirmed by hash: the blob has 0 CRLF and hashes `ae471239...`; the tarball copy hashes `e314f2c6...`. This is user-facing rather than cosmetic, because `verify` returns FAIL on ANY modification, so a user verifying a clean install sees FAIL and the guarantee the command exists to provide is undermined.
>
> Fix: in `_git_blob_sha256`, batch `git check-attr --stdin eol` over the SAME path list already produced by the `git ls-files -s -z` pass (one extra subprocess for the whole set, not one per file), and for any path resolving to `eol: crlf`, convert LF to CRLF before hashing. A path resolving to `eol: lf` or `unspecified` needs no conversion, because the blob is already LF and `git archive` leaves it alone. Do NOT reach for the more thorough alternative (hashing `git archive` output directly) unless a second attribute class appears: it is materially more machinery for one file today, and the `AGENTS.md` scope-fit gate declines it.
>
> Tests, extending `tests/validators/test_verify_install.py` beside the four v3.16.7 WN-1 regression tests: build a real git repo, commit a file under a `.gitattributes` rule declaring `eol=crlf`, and assert the manifest entry equals `sha256(LF-content with CRLF applied)` and NOT `sha256(blob)`. Add the mirror case asserting an `eol=lf` file is unaffected, so the fix cannot regress into converting everything. Keep the existing four tests passing unchanged.
>
> Acceptance criteria: `python -m pytest tests/validators/test_verify_install.py -q` green with the new cases; regenerating `MANIFEST.sha256` and verifying an extracted `git archive HEAD` tarball reports PASS with 0 modified; the untracked-file and non-git-tree fallbacks still behave as before.

#### 2.3 - Add the tarball round-trip as the release flow's FINAL gate (INGESTED: v3.16.7 `BG-2`, process half) - **COMPLETE**

**Objective**: A manifest defect is caught by the release, not by a user.

**Status: DONE 2026-08-14.** `catalog/commands/update.md` gained a `release scope: artifact round-trip (the FINAL gate, after publish)` section: download the published archive, extract, `verify_install.py`, expect PASS; degrades rather than failing since the tag is already pushed; states that a post-publish FAIL is a gap plus a patch and never a history rewrite; and carries both the line-ending pinning requirement for a pre-release local check and the `gh` native-Windows-path trap.

**Provenance**: the process half of the ingested `BG-2` item (see sub-task 1.3). It belongs in this phase because Phase 2 already owns `/update release` gate wiring, and the lesson is precisely a missing gate.

**Prompt**:
> The v3.16.7 release ran every local check green (version sync, contract freshness, bundle audit, unicode safety, 3383 tests) and STILL shipped a manifest that made `nexus-hub verify` report FAIL. The reason is instructive and worth encoding rather than just fixing: every check ran against a LOCAL reconstruction of the artifact (the index, the working tree), and each of those shares its assumptions with the generator it was checking. The defect was only visible against the artifact a user actually downloads.
>
> Add a final gate to the `release` scope in `catalog/commands/update.md`, positioned AFTER the tag-and-push step and before or beside the GitHub Release publish (it needs the tag on the remote to exist): download the published archive for the tag being cut, extract it, run `python scripts/verify_install.py --root <extracted>`, and require `PASS` with 0 modified, 0 missing, 0 extra. Use `gh release download <tag> --archive=tar.gz` when `gh` is available.
>
> Two properties this gate must have, both learned the hard way this cycle. (1) It must DEGRADE, never fail the release: at this point the tag and push have already succeeded, so an unavailable `gh` or no network means printing the exact commands for the user to run later, exactly as the GitHub Release publish step already degrades. (2) It must be honest about what a FAIL means at that point: the release is already public, so the outcome is a known-gaps entry plus a follow-up patch, not a rollback. Say so in the command text so the next agent does not attempt to rewrite published history.
>
> Note the path trap encountered this cycle, because it will recur: `gh` is a Windows binary and cannot read a Git-Bash `/tmp/...` path, so `--notes-file` and `--dir` need a native Windows path when the release is driven from a Bash-style shell.
>
> Acceptance criteria: `make validate` passes; the release-flow section reads as a numbered gate consistent with the existing governance steps, names the exact commands, states the degradation path, and states that a post-publish FAIL routes to a known-gaps entry plus a patch rather than a history rewrite.
