**Goal**: Give Nexus-Hub the long-horizon loop concepts a static definition cannot express (typed human-judgment gates, evidence freshness, resumable instance state), close the release-capability documentation gap, start the incident-archive practice its skills already assume, and add a `doctor` preflight that verifies what the installer actually landed.

## Overview

This plan operationalizes the LoopX comparison. LoopX is a local-first control plane for long-running agent work: a durable state kernel holding objective, gates, todos, evidence, and quota while an external agent runtime executes bounded turns. It is layered with Nexus-Hub rather than competing, which is what makes the adoption boundary sharp. Nexus-Hub decided, and has restated three times, that the loop **driver** is a host command to reference and never a catalog artifact to ship (CHANGELOG v3.1.0; `agent-orchestration-primitives` Step 8; `loop-engineering/SKILL.md` line 55). The comparison therefore declines the entire control-plane runtime, the benchmark adapters, the dashboard SPA, and the Lark extension. What is adopted is the doctrine those systems encode, expressed as local Markdown and two stdlib-only scripts.

Nexus-Hub's loop coverage was already further along than a first pass suggested. Four loop-adjacent comparisons have shipped (v3.2.0, v3.5.0, v3.9.0, v3.15.7), and `loop-schema.md` already carries `iteration_cap`, `check_command`, a dual-condition `exit_condition`, `driver`, `maturity`, `per_iteration_budget`, `trace_log`, `progress_check`, and `handoff`. The naive gaps are closed, so none of them is re-adopted here. Three concepts survive because a static definition structurally cannot express them: a **typed human-judgment gate** that pauses a loop mid-flight and asks one concrete question (distinct from `handoff`, which is only a post-cap destination), **evidence freshness** over a horizon long enough for evidence to go stale, and a **resumable instance record** so a cold start continues rather than re-derives. Two process gaps sit outside the loop entirely: `/update release` has no capability usage gate despite Nexus-Hub shipping an unusually high density of opt-in surfaces, and the `incident-postmortem`, `known-gaps-tracker`, and `solution-knowledge-base` skills all exist while `docs/incidents/` and `docs/solutions/` hold nothing at all. The capability is present; only the practice is missing.

Eleven candidates result: eight are `skill-native` doctrine folded into existing files, two are local builds (a `doctor` preflight and a release-capability documentation validator), and one is a `re-partial` documentation pattern. Nothing introduces a dependency, credential, or outbound call, so the whole plan clears the MCP Registry Policy without a vendor-intrinsic justification anywhere. One candidate that looked like a clear gap was verified and dropped: LoopX's CI hardening (path filters, concurrency groups, `timeout-minutes`, least-privilege `permissions`) is already complete across all nine Nexus-Hub workflows.

Ordering note: the comparison's Step 5.4 places L5 (instance-state pattern) in the reverse-engineering bucket, after the skill-native items. It is grouped into Phase 1 here because all three Phase 1 items edit the same file and because L1's gates need somewhere to persist across a cold start, which is exactly what L5 provides. No vendor-intrinsic or high-risk item is advanced by this grouping, so the intent behind Step 5.4 (cheap local wins before risky external work) is preserved.

Grounding note: no `docs/solutions/` store, no `STRATEGY.md` anchor, and no constitution file exist, so Phase B.5 grounding was best-effort and non-blocking. Three open constraints from the v3.15 known-gaps are folded in: skill `description` fields have a 250-character ceiling (v3.15.3 NI-1), CI runs `validate_skills.py --bundles-only` rather than strict mode (v3.14.2 WN-1), and a new test directory stays invisible to CI until it is named explicitly in `ci.yml` (v3.15.8 QG-2). Most work here edits skill and reference BODIES, which requires no `data/skills.json` sync; only a frontmatter change would.

## Phase 1: Loop schema: gates, evidence freshness, instance state

**Goal**: Give the loop schema the three long-horizon concepts a static definition cannot express, so a loop can pause for human judgment, distrust stale evidence, and resume after a cold start.

**Prerequisites**: None.

**Stability Gate**: `loop-schema.md` documents `gates`, `evidence_freshness`, and an instance-state section; all three are introduced as optional so every existing loop definition stays valid; `loop-engineering/SKILL.md` Step 4 references them; the worked example demonstrates at least one gate; `make validate` passes.

**Recommended model**: Strong reasoning tier, high effort (Opus class, high). These fields change when a loop terminates and who it escalates to, so a loose wording reintroduces exactly the unattended-spend failure the schema exists to prevent.

### Sub-tasks

#### 1.1 - Typed human-judgment gates (L1)

**Objective**: Add a `gates` field that pauses a loop mid-flight, asks one concrete question, and resumes on answer.

**Prompt**:
> Add an optional `gates` field to the Fields table in `catalog/skills/workflow/loop-engineering/references/loop-schema.md`. A gate is a typed, blocking, mid-loop pause, and it must be clearly distinguished from the existing `handoff` field, which is only a post-cap destination for work the loop could not finish.
>
> Specify four gate types drawn from the source's control flow: `owner` (a decision only the work's owner can make), `safety` (an action whose blast radius exceeds the loop's authority), `publication` (anything that becomes externally visible), and `private-data` (a step that would read or emit private context). Each gate declares the concrete question to ask, what unblocks it, and what the loop does while waiting.
>
> Two rules matter and must be stated explicitly. First, the gate asks ONE concrete answerable question, never "how should I proceed"; a vague gate is the same failure as a vibe-based `exit_condition` that the Anti-Patterns section already rejects. Second, a gate pause is not a loop failure and must not consume `iteration_cap`, otherwise a well-behaved loop that correctly asks for judgment is penalized against one that plows ahead.
>
> Add a matching Anti-Pattern entry for a loop that proceeds on a safety, publication, or private-data decision it lacks authority for. Introduce the field as optional so existing definitions stay valid, per the additive contract stated at line 23 of that file. Update the worked example to carry one gate.

---

#### 1.2 - Evidence freshness (L6)

**Objective**: Make evidence staleness expressible for loops that run long enough for evidence to decay.

**Prompt**:
> Add an optional `evidence_freshness` field to the Fields table in `catalog/skills/workflow/loop-engineering/references/loop-schema.md`. It declares how long a piece of evidence stays authoritative and what re-validates it once it expires.
>
> Be precise about why this is not already covered: `trace_log` is append-only per-iteration telemetry, and `progress_check` detects a stalled metric. Neither expresses that a check which passed twenty iterations ago may no longer be true. This matters only for long-horizon loops, so state that plainly rather than implying every loop needs it.
>
> Extend the Evaluation Rule section so a checker evaluating `exit_condition` must confirm the corroborating evidence is still within its freshness window, and cross-link `[[verification-before-completion]]`, whose fresh-evidence requirement this directly extends. Keep the field optional.

---

#### 1.3 - Resumable loop-instance state (L5)

**Objective**: Document the pattern for a running loop's durable state, distinct from its definition.

**Prompt**:
> Add an "Instance state" section to `catalog/skills/workflow/loop-engineering/references/loop-schema.md` documenting the separation between a loop DEFINITION (the reusable template that the Fields table describes) and a loop INSTANCE (one running execution of it).
>
> Specify a local, gitignored, single-file-per-instance record carrying: the resolved objective, open gates and their questions, evidence pointers with their freshness stamps, the iteration counter, and the next continuation step. The purpose is that a cold start resumes rather than re-derives, and that an instance can be handed to a different agent or a different tool.
>
> Three constraints are mandatory. Nexus-Hub ships NO runtime that maintains this file, so document it as a pattern an operator or host driver implements, and say so explicitly to preserve the standing decision that the loop driver is a host command. The file is gitignored by default and carries the `[[egress-redaction]]` discipline, because an instance record accumulates exactly the working context most likely to contain something private. And it composes with rather than replaces `[[filesystem-context-patterns]]` and `[[dev-progress-tracker]]`, so cross-link both and state which owns what.
>
> Note in the section that this is the local pattern reverse-engineered from an external control plane's state kernel, per the MCP Registry Policy's reverse-engineer-first rule; the runtime itself is explicitly out of scope.

Confirm the three new fields and the new section are all optional or additive, so every existing loop definition in `references/loop-library.md` remains valid without edits; if any library loop would now be better with a gate, add it as a demonstration rather than a requirement.

## Phase 2: Release capability usage gate

**Goal**: Make it impossible to ship an opt-in capability that the release notes do not teach the user how to operate, validate, and turn off.

**Prerequisites**: None.

**Stability Gate**: `catalog/commands/update.md` requires the five-element capability block for every new or materially changed opt-in surface; an explicit no-change declaration exists for releases with none; `AGENTS.md` cross-references the gate; `make validate` passes.

**Recommended model**: Strong reasoning tier, medium effort (Opus class, medium). Additive release-step doctrine with a clear shape, but it must be scoped tightly enough not to turn an already-long release flow into ceremony.

### Sub-tasks

#### 2.1 - Add the capability usage gate to /update release

**Objective**: Require the five-element block per opt-in capability at release time.

**Prompt**:
> Add a release capability usage gate to the release section of `catalog/commands/update.md`. When a release introduces or materially changes an OPT-IN capability, workflow, managed skill, or host surface, the release notes must carry, for each affected surface: the exact activation or opt-in mechanism, a minimum runnable validation or readback command, the exact disable / uninstall / rollback path, the authority or privacy boundary that activation does NOT grant, and a canonical versioned documentation link.
>
> Ground the gate in Nexus-Hub's real surface density rather than stating it abstractly. Cite the existing opt-in capabilities as the worked examples: `NEXUS_HUB_COPILOT_SKILLS` (off by default, writes commit-visible `.github/skills/`), the `--enterprise` / `-Enterprise` installer flag for the Gemini CLI integration, `NEXUS_DISABLED_HOOKS`, and `NEXUS_HOOK_PROFILE=minimal`.
>
> Scope it deliberately: the gate applies ONLY to opt-in surfaces, not to every changed line, and a release with no applicable surface change satisfies it with a single explicit no-change declaration rather than a checklist. State that the fourth element (the authority activation does not grant) is the one most often skipped and the one that most often causes a user to over-trust a new surface.
>
> Add a short cross-reference in `AGENTS.md` near the branching and release workflow section so the gate is discoverable from the canonical agent guidance, not only from the command file.

## Phase 3: Incident archive practice and backfill

**Goal**: Turn three skills that already exist into a practice that produces artifacts, without letting the archive become a directory of notes nobody reads.

**Prerequisites**: None.

**Stability Gate**: `docs/incidents/` exists with a documented naming convention and a template carrying a mandatory Public-Safe Shape section; two real incidents are backfilled; every incident names and links the durable fix it produced; `incident-postmortem` references the directory; the `secret-scan` hook covers the path.

**Recommended model**: Strong reasoning tier, medium effort (Opus class, medium). The mechanics are simple, but incident notes are the single most likely place for internal paths, raw logs, and local state to reach a public repo, so the redaction discipline needs deliberate care.

### Sub-tasks

#### 3.1 - Establish the incident artifact type

**Objective**: Create the directory, naming convention, and template.

**Prompt**:
> Create `docs/incidents/` with a `README.md` documenting the artifact type and a template file. The naming convention is `<slug>-YYYYMMDD.md`.
>
> The template must carry, in order: a title, a date, an explicit Audience line naming which maintainers and which owning skill the note is for, a Summary, a mandatory **Public-Safe Shape** section that abstracts the reusable pattern with no local paths, raw logs, private links, or credentials, and a **Durable fix** section that names AND links the concrete change the incident produced (a skill edit, a test, a gate, a hook).
>
> The Durable fix section is the load-bearing one. State plainly in the README that an incident is not closed by an explanation, only by a change that makes the lesson durable, and that an incident note with no linked fix is an open item rather than an archive entry. This is the single control that stops the directory from becoming a graveyard.
>
> Confirm the `secret-scan` hook's Write/Edit coverage applies to this path, and add `docs/incidents/` to any pre-stage private-context scanning guidance so the redaction requirement is enforced rather than merely requested.

#### 3.2 - Backfill two real incidents

**Objective**: Prove the format on genuine failures already narrated in the repo.

**Prompt**:
> Backfill two incident notes from failures already documented in `AGENTS.md`, using only what the repo already records. Do not invent detail.
>
> The first is the v3.11.0 `session-summary.ps1` parse error: a PowerShell sibling shipped broken and stayed dead on Windows for four minor versions because nothing parsed catalog `.ps1` files. Its durable fix is exit-code parity testing plus the Windows PowerShell 5.1 CI leg.
>
> Both share one reusable Public-Safe Shape worth naming explicitly: a cross-platform sibling can be silently non-functional when the test suite only exercises one platform, so parity must be asserted mechanically rather than assumed from the file's existence. Write that shape once and reference it from both notes.

## Phase 4: Engineering discipline transfers

**Goal**: Fold four bounded doctrine items into the files that already own their concerns, without creating a new skill.

**Prerequisites**: None.

**Stability Gate**: `AGENTS.md` carries the smoke-retention policy and the scope-fit pre-add gate; `multi-agent-coordinator` documents claim/lease arbitration; `observability-setup` documents the projection-sink rule; no new skill is created; `make validate` passes.

**Recommended model**: Strong reasoning tier, medium effort (Opus class, medium). Four independent, bounded additions across three files, each with a clear shape and no cross-dependency.

### Sub-tasks

#### 4.1 - Smoke and test retention policy (L7)

**Objective**: Give the growing test suite an explicit keep/delete rule.

**Prompt**:
> Add a test-retention policy to the hook-testing section of `AGENTS.md`. Keep a test only when it validates a durable behavior: shipped CLI or runtime behavior, a reusable contract, a boundary enforcement, a regression that previously broke something real, or a representative fixture likely to catch future bugs.
>
> Add the corresponding delete rule, which is the half that is usually missing: do not keep a test whose main purpose is asserting the exact text of a dated note, a transitional decision, or a temporary artifact. Preserve that information in the document itself and cover shared invariants with one data-driven aggregate test.
>
> Add the size trigger: when a test file grows past roughly 500 lines, re-check whether it is really one test, and prefer moving reusable logic into product modules so the test stays a thin behavior check. Frame all of this against Nexus-Hub's actual suite (`catalog/hooks/tests/`), and be careful not to contradict the existing rule that every behavioral assertion should double as a `.sh`/`.ps1` parity assertion.

---

#### 4.2 - Scope-fit pre-add gate (L8)

**Objective**: Add a gate before new abstractions, not only cleanup after them.

**Prompt**:
> Add a scope-fit review to the Boundaries section of `AGENTS.md`. Before adding a new module, builder, protocol field, CLI option, fixture, or abstraction, name the shipped behavior, active call site, or explicit compatibility contract that requires it. If the only justification is an uncommitted future runner, a design note, or a hypothetical extension with no validation contract, keep the design in docs or todo state until the real call site appears.
>
> Lead with the framing that makes the rule stick: treat code volume as a cost, especially during refactors. A good change makes the next change easier to localize, test, and revert; it should not turn a design possibility into unused production structure.
>
> Position this as the complement to `[[code-simplification]]`, which removes complexity after the fact, and cross-link it. Keep the entry compact; `AGENTS.md` is already long and this is a gate, not an essay.

---

#### 4.3 - Peer claim and lease arbitration (L9)

**Objective**: Let concurrent agents pick work without a designated leader.

**Prompt**:
> Add peer claim/lease guidance to `catalog/skills/orchestration/multi-agent-coordinator/SKILL.md`. The model is that registered agents are peers, and that claims, leases, task boundaries, and capabilities decide who acts next, so no durable leader identity is required.
>
> Specify the minimum a claim carries (the claiming agent's id, the claimed work item, an expiry) and what happens when a lease expires without completion, since an expired lease that nobody reclaims is the actual failure mode. Distinguish this clearly from the skill's existing role-assignment guidance: roles say what an agent does, claims say which agent does this specific item right now.
>
> Note when this is warranted, which is narrower than it sounds: only when multiple agents genuinely contend for one shared work queue. A fan-out with disjoint write scopes does not need leases, and saying so prevents the guidance from being over-applied. Respect the 250-character `description` ceiling if frontmatter changes, and sync `data/skills.json` only if it does.

---

#### 4.4 - Projection sink design rule (L10)

**Objective**: Keep operator displays reading from public-safe projections rather than private source files.

**Prompt**:
> Add a projection-sink design rule to `catalog/skills/infrastructure/observability-setup/SKILL.md`. When building an operator-facing display (a dashboard, status surface, chat summary, or report), render it from bounded, public-safe projections with stable ids, not by parsing a project-specific private document, raw transcript, or local path.
>
> Add the lineage requirement, which is the non-obvious part: when a displayed row supersedes, migrates, or retires an earlier row, represent that as data through lifecycle fields (`row_lifecycle`, `supersedes`, `superseded_by`, `source_id`) rather than as ad hoc prose, so a reader never has to open a private source document to understand why a row changed.
>
> Ground it in Nexus-Hub's four existing usage-monitor extensions (Claude, Codex, Cursor, GitHub), which are exactly this artifact class, and cross-link `[[egress-redaction]]` for anything a multi-user or public sink would render.

## Phase 5: Local verification tooling

**Goal**: Add the preflight Nexus-Hub has never had, so a user can find out that an install did not land where the contract promised before they discover it as silent non-coverage.

**Prerequisites**: Phase 2 (the validator in 5.3 checks the gate that Phase 2 defines).

**Stability Gate**: `nexus-hub doctor` exists in BOTH installers with matching behavior and exit codes; it verifies each detected platform's surfaces against `docs/policy/platform-read-contracts.json`; it is read-only by default; the release-capability validator runs against a release-notes file; both have tests collected by CI.

**Recommended model**: Strong reasoning tier, high effort (Opus class, high). Dual-installer code with PowerShell 5.1 parity is precisely the change class that shipped dead for four minor versions in v3.11.0, and a doctor that reports a false CLEAR is worse than no doctor.

### Sub-tasks

#### 5.1 - Build `nexus-hub doctor` (bash)

**Objective**: Verify installed surfaces against the read-contract and report drift.

**Prompt**:
> Add a `doctor` subcommand to `scripts/installer.sh`, alongside the existing `init`, `install`, and `status` subcommands. It reads `docs/policy/platform-read-contracts.json` (or its installed copy), detects which platforms are present on the machine, and verifies that each surface the contract promises actually exists at the contract path: skills, commands, agents, rules, hooks, and the instruction file, per platform.
>
> Report per platform and per surface with a clear status, summarize drift at the end, and exit non-zero when any detected platform is missing a surface the contract promises. Distinguish three states carefully, because collapsing them is what makes a doctor untrustworthy: a platform that is absent (skip with a note, not a failure), a platform present with all surfaces (pass), and a platform present with a missing or empty surface (fail).
>
> Two hard constraints. It is READ-ONLY by default; any repair is behind an explicit flag and must state what it will change before doing it. And it makes no network call of any kind, which keeps it `re-full` under the MCP Registry Policy and must be stated in a comment so a later change does not quietly add one.
>
> Follow the bash rules in `catalog/rules/bash/`: `#!/usr/bin/env bash`, `set -euo pipefail`, quoted expansions, errors to stderr.

---

#### 5.2 - Build the PowerShell sibling

**Objective**: Give Windows users the same preflight, with matching exit codes.

**Prompt**:
> Add the matching `doctor` subcommand to `scripts/installer.ps1` per the installer parity rule in `AGENTS.md`. Behavior and exit codes must match the bash version for the same machine state.
>
> Use native equivalents rather than emulating shell mechanics, following the guidance that the hook-sibling work established: `ConvertFrom-Json` instead of a `jq` dependency, `[System.IO.File]::WriteAllText` with `UTF8Encoding($false)` instead of `Set-Content -Encoding utf8` if anything is written at all (which for a read-only doctor should be nothing), and `[Console]::IsInputRedirected` where the bash version tests `[ ! -t 0 ]`.
>
> This is the exact change class behind both backfilled incidents in Phase 3, so treat their durable fixes as requirements here: the file must parse under Windows PowerShell 5.1, and exit-code parity must be asserted by a test rather than assumed. Read those two incident notes before writing this sub-task's code.

---

#### 5.3 - Release-capability documentation validator (L2v)

**Objective**: Make the Phase 2 gate mechanically checkable.

**Prompt**:
> Add `scripts/check_release_capability_docs.py`, a repo-internal guard modeled on `check_version_sync.py`. Given a release-notes file and one `--surface <name>` argument per changed opt-in capability, it asserts that each named surface has all five required elements present: activation, validation command, disable/rollback, authority boundary, and a documentation link. Support `--expect-no-optional-capability-changes` for a release with none, which must still produce an explicit declaration rather than passing silently.
>
