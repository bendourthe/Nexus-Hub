# Plan -- /presentify universal ingestion (any file type + whole repos), image prominence, spacing, and output-aspect control

**Project**: Nexus-Hub
**Version**: v3.13.0
**Slug**: presentify-universal-ingestion
**Plan Type**: Feature / Enhancement (existing skill + command; no new skill)
**Created**: 2026-07-13
**Goal**: Extend `/presentify` + `document-to-interactive-html` so that (1) it ingests any mix of file types (adding source code and config, Markdown and plain text, CSV / TSV, and standalone image files) and can take a whole directory or repository as input, building a logically-structured interactive site from it; (2) it preserves and enhances each source visual's PROMINENCE, so a visual that dominates its source stays a hero at native resolution and is never flattened into a uniform thumbnail grid; (3) it lays out with deliberate spacing that eliminates dead vertical space; and (4) it lets the user choose the output aspect (full-width for a 16:9 screen, standard webpage width, portrait, or a custom description) via a menu asked exactly like the style menu, backed by a `--layout` flag. All of this preserves the local-only, zero-external-request, single-file guarantees and builds ON TOP OF the v3.12.0 fidelity / reconstruction / design-variety work rather than duplicating it.

## Overview

The v3.12.0 `presentify-fidelity-and-variety` overhaul already solved the visual-fidelity problems: PDF embedded-raster and vector-figure extraction, native PPTX/DOCX chart extraction, scanned-page OCR with an agent-vision fallback, a figure-reconstruction protocol that preserves printed data labels and reconstructs maps (never dropping them), a site-wide interaction budget, and a seeded design-entropy engine for run-to-run variety. This plan does NOT revisit any of that. Instead it closes the gaps that overhaul did not touch, all surfaced by real-world use.

Three of the gaps are genuinely unaddressed in the current bundle. First, ingestion is still limited to four document formats (`pptx`, `docx`, `xlsx`, `pdf`) and a single, NON-recursive folder expansion (`_expand_inputs` walks one directory level and keeps only those four extensions), so a user who points `/presentify` at a mixed folder or a code repository gets almost nothing. Second, the content model carries no signal of how DOMINANT an image is in its source (`image` blocks have `caption`, `page`, `origin`, `classification`, but no dimensions or page-coverage), and no authoring rule instructs the agent to preserve source visual hierarchy, so a slide dominated by four large photos can be flattened into a uniform thumbnail grid. Third, there is no vertical-density discipline (only a horizontal "use the viewport width on purpose" rule) and no output-aspect control at all (no full-width / standard / portrait choice, no `--layout` flag).

This plan fixes all three in the existing `catalog/skills/specialized-domains/document-to-interactive-html/` bundle and `catalog/commands/presentify.md`. The target persona broadens from "someone converting a deck or report" to "someone pointing `/presentify` at any file, any folder, or a whole repository and getting one coherent, navigable, interactive site." Delivery is: an extractor upgrade (new per-format parsers for code / config, Markdown / text, CSV / TSV, and standalone images; a recursive directory / repository walk with ignore rules, caps, and a coverage note; and a synthesized repository overview + file tree), objective image-prominence signals in the content model plus a prominence-preservation authoring rule, a spacing / density discipline, an output-aspect menu + `--layout` flag wired through the command and skill, a worked example over a mixed repository, and the usual registration / documentation / validation sync. Everything stays local-only: new parsing uses the standard library plus already-present or lazy-imported permissively-licensed libraries with `pip install` hints, generation stays LLM-native, and the output keeps zero external requests.

Success looks like: `/presentify ./some-repo` produces one self-contained interactive site with a synthesized overview and file tree, README and docs first, source code presented as offline-highlighted `code` sections grouped by top-level directory, CSV data as interactive charts or sortable tables, and standalone images placed with the same fidelity discipline as document visuals; a deck-PDF's dominant photos render as prominent heroes rather than a thumbnail grid; the output has no dead half-empty screens; the user is offered a full-width / standard / portrait / other aspect choice (or `--layout` binds it), and the site is built to that aspect; and `make validate`, `make lint`, and `make test` are green.

## Phase 1: Universal ingestion (new formats + recursive repo walk)

**Goal**: `/presentify` accepts any mix of file types and whole directories or repositories. Source code and config, Markdown and plain text, CSV / TSV, and standalone image files each map into the content model; a directory input is walked recursively with sane ignore rules, size / count caps, and a coverage note; and a repository produces a synthesized overview plus a file tree so the output reads as a coherent tour of the project, not a flat dump.
**Prerequisites**: None.
**Stability Gate**: On a mixed fixture folder (a README, a couple of source files in two languages, a `.csv`, a `.png`, and a `.pdf`), `extract_content.py` emits a valid content model containing a code block per source file (language set from extension), a chart or table block for the CSV, an image block for the PNG (with `origin: "inline-image"`), and the existing document sections for the PDF; a directory input is walked recursively; ignored paths (`.git`, `node_modules`, virtualenvs, build output, lockfiles, binaries, over-cap files) are excluded and counted in the coverage manifest with reasons; ordering is deterministic; a repository input yields a synthesized overview section and a file-tree representation; a missing optional library degrades to a documented warning plus `pip install` hint, never a crash; validators green.
**Recommended model**: Strong reasoning tier, high effort. Concrete (Claude Code): Opus 4.8, high effort. Rationale: broad heterogeneous ingestion with many real-world edge cases (encoding detection, binary sniffing, huge files, deep trees, `.gitignore` semantics) where silent loss or a pathological walk are the failure modes. `/implement` re-confirms against the then-current models.

### Sub-tasks

#### 1.1 -- Extend the content model for code, text, tabular, and repository inputs

**Objective**: Give the model the shapes universal ingestion needs, additively (schema_version stays 2; v1 / v2 consumers keep working; unknown fields ignored).

**Prompt**:
> Update `catalog/skills/specialized-domains/document-to-interactive-html/references/content-model.md` with ADDITIVE fields only. (1) Document that the existing `code` block (`{ "type": "code", "text": string, "language": string }`) is now produced by the source-code / config extractor, with `language` inferred from the file extension, and gains an optional `path` (repository-relative source path) and optional `truncated` (boolean; true when a large file was cut, with the body ending in a clear truncation marker). (2) Document that `image` blocks are now also produced from standalone image files with `origin: "inline-image"`. (3) Add a source-format vocabulary note: the `sources[].format` field may now also be `code`, `markdown`, `text`, or `csv` in addition to the four document formats. (4) Add an optional top-level `tree` object (a nested `{ name, kind: "dir"|"file", children? }` structure) capturing the ingested directory / repository layout, used by the authoring stage to render a file-tree overview; it is present only for directory / repository inputs. (5) Document a new section `kind: "overview"` (a synthesized landing section for a repository, additive to the existing `kind` set; unknown kinds already fall back to `content` in the builder). (6) Extend the per-format mapping section with subsections for code / config, Markdown / text, CSV / TSV, and standalone images, and a "directory / repository" subsection describing recursive expansion and the coverage note. Constraints: ASCII-only; follow `catalog/style-guides/markdown.md`; keep the "model is the only contract" framing; state the v1 / v2 compatibility rule holds (all new fields optional). Acceptance: every new field and the new `kind` / `format` values are documented as optional with allowed values, and the per-format mapping covers all four new input classes plus the directory / repository walk.

#### 1.2 -- Recursive directory / repository walk with ignore rules and caps

**Objective**: Turn `_expand_inputs` from a one-level, four-extension folder lister into a robust recursive walker safe on real repositories.

**Prompt**:
> Rewrite `_expand_inputs` (and add helpers) in `catalog/skills/specialized-domains/document-to-interactive-html/scripts/extract_content.py`. A directory argument is walked RECURSIVELY. Exclude, by default: version-control and tooling dirs (`.git`, `.hg`, `.svn`, `.idea`, `.vscode`), dependency / build output (`node_modules`, `.venv`, `venv`, `__pycache__`, `dist`, `build`, `.next`, `target`, `.pytest_cache`, `.mypy_cache`), lockfiles (`package-lock.json`, `poetry.lock`, `Cargo.lock`, `yarn.lock`, `pnpm-lock.yaml`), and any file whose bytes sniff as binary (a NUL-byte / non-text heuristic) unless it is a supported document or image format. Respect a `.gitignore` at the walk root on a best-effort basis (a simple glob matcher is acceptable; document its limits in the runbook). Enforce caps: a per-file size cap (default a few hundred KB for text / code, tunable with a new `--max-text-bytes` flag; over-cap text files are TRUNCATED with a marker, not skipped) and a total-file-count cap (a new `--max-files` flag, default generous, e.g. 400) beyond which further files are skipped; every exclusion / truncation / cap is counted in the coverage manifest with a reason (`ignored-dir`, `gitignored`, `binary`, `over-cap`, `file-count-cap`). Never silently drop content: a capped walk prints one stderr summary of what was skipped and why. Ordering is deterministic (sorted, directories before files or a documented stable order). Constraints: `catalog/rules/python/` (type hints, ruff-clean, no bare except); standard-library-only for the walk / ignore / sniff logic; ASCII-only source; no network calls. Acceptance: on a fixture repository, the walk returns supported files recursively, excludes every default-ignored path and honors a `.gitignore` entry, truncates an over-cap text file with a marker, respects `--max-files`, and the coverage manifest reasons reconcile with what was excluded.

#### 1.3 -- Source-code / config and Markdown / text extractors

**Objective**: Map code, config, Markdown, and plain-text files into the content model.

**Prompt**:
> Add extractors to `scripts/extract_content.py` and register their extensions in `EXTENSION_FORMATS` and the `_extract_one` dispatch. (1) Source code / config: a broad extension-to-language map (at minimum `.py`, `.js`, `.jsx`, `.ts`, `.tsx`, `.go`, `.rs`, `.java`, `.c`, `.h`, `.cpp`, `.cs`, `.rb`, `.php`, `.swift`, `.kt`, `.scala`, `.sh`, `.ps1`, `.sql`, `.r`, `.m`, and config formats `.json`, `.yaml`, `.yml`, `.toml`, `.ini`, `.cfg`, `.env.example`, `.dockerfile` / `Dockerfile`, `.mk` / `Makefile`) maps each file to a single section (heading = repository-relative path) whose one block is a `code` block with `language` from the map and `path` set; honor the 1.2 truncation for over-cap files. (2) Markdown: parse `.md` / `.markdown` into sections by ATX / setext headings (heading text becomes the section heading), body paragraphs into `paragraph` blocks, lists into `bullets` (with `depth` from indent / marker level), fenced code into `code` blocks (language from the fence info string), tables into `table` blocks, and image references to LOCAL files into `image` blocks (resolved relative to the markdown file, through the existing `_encode_image` budget path; remote image URLs are recorded as a caption note, never fetched). (3) Plain text (`.txt`, `.rst`, `.log`): one section, blank-line-separated `paragraph` blocks; `.rst` uses a light heading heuristic (underlined titles) but is not a full parser. (4) Read files as UTF-8 with a tolerant fallback (latin-1 / errors="replace") and record a coverage note when a decode fallback was used. Constraints: standard-library-only (no Markdown library dependency; a compact in-house heading / list / fence parser is fine and must be documented as intentionally minimal in the runbook); Python rules; deterministic ordering; ASCII-only source. Acceptance: a Python file yields a `code` section with `language: "python"` and its path; a README.md yields heading-delimited sections with paragraphs, bullets, fenced code, and a local image resolved to base64; a `.txt` yields paragraph blocks; an over-cap file is truncated with a visible marker.

#### 1.4 -- CSV / TSV and standalone-image extractors

**Objective**: Map tabular data files and standalone images into the model, reusing existing machinery.

**Prompt**:
> Add extractors to `scripts/extract_content.py`. (1) CSV / TSV (`.csv`, `.tsv`): parse with the standard-library `csv` module (sniff the delimiter; TSV forces tab), then reuse the existing grid-to-block logic (`_grid_to_block` / `_table_from_grid`) so a header row plus a numeric body becomes a `chart` block (with an inferred `chart_type_hint`) and a non-numeric grid becomes a `table` block, exactly as the Excel path does; the section heading is the file stem (or repository-relative path). Guard against pathological files with a row / column cap consistent with the 1.2 caps, counted in coverage. (2) Standalone images (`.png`, `.jpg`, `.jpeg`, `.gif`, `.webp`, `.svg`): map each to a one-section `image` block via `_encode_image` (`origin: "inline-image"`, `page` null); `.svg` is embedded as text-based markup where safe (documented) or rasterized through the existing `pypdfium2` / Pillow path if that is simpler and already available; over-budget rasters go through the existing downscale / skip path. Register all new extensions in `EXTENSION_FORMATS` and `_extract_one`. Constraints: standard-library `csv`; reuse existing helpers rather than duplicating grid logic; Python rules; ASCII-only source; deterministic ordering. Acceptance: a numeric CSV becomes a `chart` block whose series match the file; a text CSV becomes a `table` block; a PNG becomes an `inline-image` image block within budget; the delimiter sniff distinguishes CSV from TSV.

#### 1.5 -- Repository overview, file tree, and multi-source assembly

**Objective**: Assemble a walked repository into a coherent presentation shape, not a flat file dump.

**Prompt**:
> Extend the merge / assembly logic in `scripts/extract_content.py` (the `build_model` path) for directory / repository inputs. (1) Emit the top-level `tree` object (from 1.1) capturing the ingested layout. (2) Prepend a synthesized `kind: "overview"` section: the repository / folder name as title, a short synthesized description drawn from the README's first paragraph when present, and a `bullets` summary of top-level areas (directories and notable files); its `source_index` is 0. (3) Order the body deterministically and legibly: README / top-level docs first, then remaining Markdown / docs, then source code grouped by top-level directory (a `section-break` per top-level directory carrying its name), then data files (CSV) and standalone images, then everything else. (4) Keep per-source attribution: each ingested file remains its own source entry with `format` set to its class, so the existing multi-file attribution and the coverage manifest continue to work. (5) Set `title` to the repository / folder name (overridable by `--title`). Constraints: reuse the existing `sources` manifest and coverage machinery; deterministic; Python rules; ASCII-only. Acceptance: a fixture repository yields an overview section, a `tree`, README-first ordering, code grouped under per-directory section-breaks, and a coverage manifest that reconciles with the walk.

## Phase 2: Image prominence preservation

**Goal**: The output respects the source's visual hierarchy. A visual that dominates its source (a large photo occupying most of a slide, the single figure on a page) is rendered as a prominent hero at native resolution; genuinely secondary visuals may be grouped, but heroes are never flattened into a uniform thumbnail grid, and a zoom never shows an upscaled thumbnail.
**Prerequisites**: Phase 1 (the extractor changes land in the same file; sequencing avoids churn).
**Stability Gate**: `image` blocks carry objective prominence signals (`width`, `height` in native pixels when decodable; `page_fraction` when source geometry is available); the content model documents them as optional additive fields; a prominence-preservation authoring rule exists in the reference and is enforced in SKILL.md; on the deck-PDF fixture, the dominant photos carry a high `page_fraction` and the rule instructs hero treatment; validators green.
**Recommended model**: Strong reasoning tier, high effort. Concrete (Claude Code): Opus 4.8, high effort. Rationale: the extractor geometry math (EMU / point / pixel conversions across PDF, PPTX, DOCX) is fiddly and easy to get subtly wrong, and the authoring rule must be phrased so an agent cannot rationalize flattening. `/implement` re-confirms against the then-current models.

### Sub-tasks

#### 2.1 -- Emit objective prominence signals from the extractor

**Objective**: Give the authoring stage the measurements it needs to preserve dominance, computed objectively (the agent does semantics; the extractor does geometry).

**Prompt**:
> Add prominence signals to every `image` block the extractor emits, in `scripts/extract_content.py` (threaded through `_encode_image` or set by each caller). (1) `width` / `height`: the native pixel dimensions of the decoded image (via Pillow when available; null when Pillow is absent or the bytes will not decode). (2) `page_fraction`: the fraction (0..1, rounded to 3 decimals) of the source page / slide AREA the image occupies, computed where source geometry is available: for PDF, the `pdfplumber` image bbox area over the page area; for PPTX, the picture shape width * height (EMU) over the slide width * height; for DOCX inline images and standalone image files, leave `page_fraction` null (no reliable page geometry) and rely on `width` / `height`. (3) Ensure `origin` is already set (it is) so the authoring rule can combine origin + `page_fraction` + count. Update `references/content-model.md` to document `width`, `height`, and `page_fraction` as optional additive fields on `image` blocks (allowed ranges, when null). Constraints: reuse the existing Pillow lazy-import; never fail when geometry is unavailable (emit null); Python rules; deterministic (stable rounding); ASCII-only. Acceptance: on the deck-PDF fixture, a full-slide photo has `page_fraction` near its true coverage and populated `width` / `height`; a small logo has a low `page_fraction`; a standalone image file has null `page_fraction` and populated dimensions.

#### 2.2 -- Author the prominence-preservation rule and enforce it

**Objective**: Turn the signals into a binding authoring rule that preserves source dominance.

**Prompt**:
> Add a "Prominence preservation" subsection to `catalog/skills/specialized-domains/document-to-interactive-html/references/interactive-features.md` (primary-path half) and wire it into SKILL.md. The rule: (1) Respect the source's visual hierarchy. Rank each section's visuals by `page_fraction` (falling back to relative `width` * `height`, then to being the sole / primary visual of a section). A visual that dominates its source (roughly `page_fraction >= 0.5`, or the single primary visual of a section) is rendered as a HERO: large, given its own band or a wide column, not shrunk into a row of equal thumbnails. (2) Only genuinely secondary visuals (several small images of comparable, low `page_fraction`) may be grouped into a gallery / grid, and even then the grid is sized so each image is legible, not a postage stamp. (3) Never flatten a hero: a single dominant image must not be demoted to thumbnail size beside unrelated cards. (4) Native resolution end to end: render from the native-resolution asset and, in the lightbox / zoom, show that same full-resolution `data_uri`, never an upscaled thumbnail (reinforce, do not duplicate, the figure-reconstruction lightbox rule). (5) When `page_fraction` is null (standalone images, DOCX), fall back to `width` / `height` and section role. Then update SKILL.md: add the rule to the authoring Instructions step; add a Common Rationalizations row ("a tidy uniform thumbnail grid looks cleaner" -> a uniform grid erases the source's emphasis; a visual the author made dominant must stay dominant, and flattening it into equal thumbnails is exactly the fidelity loss this rule prevents); add binary Verification items (dominant-source visuals render as heroes; no hero is reduced to a grid thumbnail; the lightbox shows the native-resolution asset). Constraints: SKILL.md body stays within the size norm (point to the reference); ASCII-only; the reference must stay linked from SKILL.md (orphan-bundle audit). Acceptance: the rule is stated with the observable `page_fraction` / dimension thresholds, and the Instructions + Rationalizations + Verification carry it.

#### 2.3 -- Phase 2 stabilization

**Objective**: Prove the signals and the rule on fixtures.

**Prompt**:
> Validate Phase 2. On the deck-PDF and mixed-repository fixtures: confirm (1) `image` blocks carry `width` / `height` and, where geometry exists, a plausible `page_fraction`; (2) a hand-authored sample section built from a high-`page_fraction` image renders it as a hero (wide / own-band) and a group of low-`page_fraction` images renders as a legible gallery, per the new rule; (3) the lightbox shows the native-resolution `data_uri` (compare byte length to the block's, not a downscaled copy); (4) determinism holds (rounding stable). Run `make validate` (orphan-bundle audit sees the reference link) and `ruff check`. Fix and iterate. Then run `/session history` to document Phase 2.

## Phase 3: Spacing / density discipline + output-aspect control

**Goal**: The output has no dead half-empty screens, and the user controls the overall canvas aspect: full-width for a 16:9 screen, standard webpage width, portrait, or a custom description, chosen through a menu asked exactly like the style menu and bindable up front with a `--layout` flag.
**Prerequisites**: None (parallel-safe with Phase 2), lands before Phase 4's worked example.
**Stability Gate**: `references/interactive-features.md` documents a vertical-density rule and the aspect system; the command and skill offer the aspect menu (full-width / standard / portrait / other) with a `--layout` flag that binds and skips the menu, and a documented content-aware non-interactive fallback; SKILL.md Verification enforces both; validators green.
**Recommended model**: Strong reasoning tier, medium effort. Concrete (Claude Code): Opus 4.8, medium effort. Rationale: authoring-rule + command-option design against clear constraints; the risk is an under-specified aspect system or a fallback that blocks a non-interactive run. `/implement` re-confirms against the then-current models.

### Sub-tasks

#### 3.1 -- Vertical-density rule

**Objective**: Give the agent an explicit rule against dead vertical space, complementing the existing horizontal width rule.

**Prompt**:
> Add a "Spacing and density" subsection to `references/interactive-features.md` (primary-path half, near the width-discipline text). The rule: size every section to its content (no fixed one-screen-per-section stretching that leaves half a viewport empty); use a consistent vertical rhythm from the spacing scale rather than large unmotivated gaps; when a section is sparse (a single chart, a short list), either give it a deliberately compact band or pair it with an adjacent related element (a caption, a stat, the source figure) rather than floating it in a sea of whitespace; reserve generous whitespace for intentional emphasis, not as a default that produces dead screens. Cross-reference the existing "use the viewport width on purpose" rule so horizontal and vertical discipline are stated together. Update SKILL.md: add the rule to the authoring Instructions step and a binary Verification item ("no section is left half-empty; sparse sections are compacted or paired, not floated"); fold a "dead vertical space" check into the Step 7 visual-QA screenshot review. Constraints: SKILL.md within the size norm; ASCII-only. Acceptance: the density rule is stated with observable criteria and carried into Instructions + Verification + visual-QA.

#### 3.2 -- Output-aspect menu and `--layout` flag

**Objective**: Let the user pick the canvas aspect, exactly as they pick the style.

**Prompt**:
> Add output-aspect control to `catalog/commands/presentify.md` and the skill.
