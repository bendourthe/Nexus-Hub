# Plan - Agent Autonomy Toggle

**Project**: Nexus-Hub
**Version**: v3.17.0
**Slug**: agent-autonomy-toggle
**Plan Type**: Feature (enhancement)
**Created**: 2026-07-27
**Goal**: Ship a per-workspace, two-tier, hard-gated autonomy toggle that removes approval prompts on every platform with a verified lever while keeping the hook deny layer armed, and harden the existing read-only permission baseline that autonomy amplifies.

> **Retired in v3.17.2.** This file is retained as the historical implementation record. The autonomy controller could not satisfy its provider-independent approval-bypass goal through supported VS Code extension APIs, so its engine, CLI, descriptors, monitor controls, hooks, tests, and feature-specific CI were removed. Phase 1 permission-baseline hardening and generic installer-parity work remain supported.

## Overview

Nexus-Hub today installs a read-only auto-approve baseline to exactly four platforms (Claude Code, Codex, Gemini/Antigravity 1.0, Copilot), and only Claude Code and Gemini receive a genuine per-command allowlist. Claude Code's covers both shells it exposes as tools (a `Bash(...)` block and a `PowerShell(...)` block); Gemini's is POSIX-shaped and covers neither PowerShell nor `cmd.exe` beyond a bare `run_shell_command(dir)`. Codex receives read-scope plus a network allowlist while keeping `approval_policy = "on-request"`, and Copilot receives one instruction-file key and no auto-approve at all. Eleven or twelve of the roughly fifteen registered integrations receive no permission posture whatsoever. The baseline is also global-scope-only: `install_permissions` accepts a scope parameter but every call site in both installers passes `"Global"`, so a `--workspace` install receives nothing. This release closes that coverage gap in the direction users actually ask for: an explicit, consent-gated way to raise a single workspace to unattended operation, delivered uniformly across every platform whose autonomy lever can be verified against official documentation. Be precise about what that does and does not include, because the two coverage questions are separate: Phase 2 extends autonomy descriptors across the roster, NOT the read-only allowlist, so the read-only baseline remains a four-platform artifact when this release ships. Phase 6.2 records that remaining baseline-coverage gap explicitly rather than letting the autonomy rollout imply it was closed.

The feature is deliberately not a "disable all safety" switch. It ships two tiers. The default tier auto-accepts file edits while still prompting on shell commands (Claude Code's `acceptEdits` and its per-platform equivalents). The second tier removes prompts entirely and is reachable only behind a harder gate: typed confirmation, a clean git working tree, a non-protected branch, a mandatory TTL, a timestamped config backup, and an append-only audit log. Autonomy is always written to the project-scoped config and never to the global config, so an agent is never unprompted in `~/` or in an unrelated repository. Critically, the `PreToolUse` hook chain stays armed in both tiers, which makes this posture strictly safer than the `--dangerously-skip-permissions` flag users reach for today: prompts are removed, guardrails are not.

Success is observable in three ways. First, the shipped read-only baseline contains no mutation-capable entry in either its Bash or its PowerShell block, and it installs identically on Windows, macOS, and Linux and at both install scopes (removing the current `jq` hard dependency that silently skips permission installation on a stock Mac). Second, `nexus-hub autonomy` enables, reports, expires, and reverts a workspace's autonomy state on every platform carrying a verified descriptor, and skips-with-note on every platform that does not. Third, an autonomy-active session provably cannot write the execution-trigger config paths that the v3.15.6 escape taxonomy identifies, verified by test rather than asserted.

## Phase 1: Permission-baseline hardening and cross-platform merge parity

**Goal**: Remove every mutation-capable entry from the shipped read-only allowlists in both the Bash and the PowerShell block, eliminate the `jq` hard dependency that silently skips permission installation, close the workspace-scope coverage hole, and add a validator that prevents the class of entry from returning.
**Prerequisites**: None.
**Stability Gate**: The new baseline validator passes on the shipped configs and fails on an injected mutation-capable fixture entry for BOTH a `Bash(...)` and a `PowerShell(...)` shape; a permission install completes on a host with no `jq` present, on a Git-Bash invocation, and at workspace scope; the redirection and `;`-chain matcher findings are recorded in the repository; `make validate` and the validator test suite are green.
**Recommended model**: Strong reasoning tier (Opus class), high effort. Rationale: the work is security-sensitive pattern reasoning about shell side effects, plus dual-implementation installer edits where a subtle asymmetry between the bash and PowerShell paths is exactly the defect being fixed.

### Sub-tasks

#### 1.1 - Harden the read-only allowlists to side-effect level

**Objective**: Rescope every allowlist entry that permits mutation despite being classified read-only.

**Prompt**:
> In the Nexus-Hub repository, harden `configs/permissions/claude-permissions.json` and `configs/permissions/gemini-permissions.json` so that no entry in the read-only auto-approve baseline can cause a write, a deletion, or a remote mutation. Work at the invocation and side-effect level, not the command-name level (this is the `I6` invariant from `docs/v3/v3.15/comparisons/v3.15.6-comparison-sandbox-escapes.md`, derived from the Codex GitPwned allowlist bypass).
>
> Note before you start that two independent auto-approve paths consume these files, and only one of them carries Nexus-Hub's extra syntax guards. Path one is the platform's own native matcher reading the merged `settings.json`, which applies no Nexus-Hub logic at all. Path two is Nexus-Hub's `PreToolUse` hooks (`catalog/hooks/format-bash-description.py` and `catalog/hooks/format-powershell-description.py`), which return `permissionDecision: "allow"` only after applying guards the native matcher does not have: the Bash hook always blocks output redirects (`_has_output_redirect`), and the PowerShell hook rejects any command containing `;`, `{`, `}`, `>`, `<`, a backtick, `$(`, `@(`, `@{`, or `&`, and never auto-approves a multi-line script. Harden these files for path one, which is unguarded, and do not treat a path-two guard as a reason to retain a mutation-capable pattern. Phase 4.1's hook-survival verification is what path two ultimately rests on, so a pattern defended only by a hook is defended only as strongly as that verification comes out.
>
> Audit at minimum these known-suspect `Bash(...)` entries and rescope or remove each one:
>
> - `Bash(gh api *)`: permits `--method POST|PATCH|PUT|DELETE`, so it can delete a repository or close pull requests. Replace with narrowly-scoped read forms, or drop it.
> - `Bash(find)` and `Bash(find *)`: permit `-delete`, `-exec rm {}`, and `-execdir`. Rescope or drop.
> - `Bash(echo *)` and `Bash(printf *)`: shell redirection (`> file`, `>> file`) turns these into arbitrary writes. Determine empirically whether Claude Code's matcher treats a redirected command as matching the bare pattern, then rescope accordingly, and record the empirical finding as a comment in the JSON `_description` or an adjacent note.
> - `Bash(awk *)`: `awk 'BEGIN{print > "/path"}'` writes files. Rescope or drop.
> - `Bash(ip *)` and `Bash(sysctl *)`: `ip link set` and `sysctl -w` mutate system state. Rescope to read-only subcommands.
>
> Then audit the `PowerShell(...)` block of `claude-permissions.json` (currently lines 278 to 455, shipped in v1.1.0 and extended since). Claude Code exposes PowerShell as a separate tool from Bash on Windows, so these are live permission rules, not decoration. Treat the block as unreviewed for path one rather than as verified: the v1.1.0 changelog documents the hook-side syntax guards for it in detail but records no side-effect audit of the patterns themselves, and `docs/permissions-research.md` contains no PowerShell content at all. Audit at minimum:
>
> - `PowerShell(Write-Output *)`, `PowerShell(Write-Host *)`, and `PowerShell(echo *)`: the exact redirection analogue of `Bash(echo *)` above, since `>` and `>>` turn each into an arbitrary write. Resolve them with the same empirical finding.
> - `PowerShell(Get-CimInstance *)` and `PowerShell(Get-WmiObject *)`: both return objects whose methods mutate (the `Win32_Process` `Create` method being the canonical example), which is the same dual-mode `I6` class as `gh api --method DELETE` and not a read-only getter.
> - `PowerShell(Test-Connection *)`, `PowerShell(Test-NetConnection *)`, and `PowerShell(Resolve-DnsName *)`: outbound network reach from an auto-approved pattern. Decide explicitly whether that belongs in a read-only baseline, and record the decision either way.
> - Any entry whose trailing wildcard admits `-CimSession` or another remote-target parameter, which converts a local read into a remote one.
>
> Also determine empirically whether Claude Code's native PowerShell matcher splits a `;` chain the way its Bash matcher splits `&&` and `|` chains. The `format-powershell-description.py` hook already rejects `;`, so this question is only about the unguarded native path, and its answer decides whether a bare `PowerShell(Get-ChildItem *)` pattern can be reached by `Get-ChildItem; Remove-Item x`. Record the finding alongside the redirection finding.
>
> Then sweep the remaining entries in both files for the same class of problem and fix any others you find. Use `Bash(sed -n *)` as the reference for correct scoping in the Bash block (it deliberately admits `sed -n` while excluding `sed -i`), and establish an equivalent reference pattern in the PowerShell block so that sweep has a standard to measure against rather than only an instruction. Preserve every genuinely read-only entry; do not reduce useful coverage. Do not touch `configs/permissions/codex-permissions.toml` (it uses filesystem and network scoping, not command patterns) or `configs/permissions/copilot-permissions.json` (a single instruction-file key).
>
> One coverage observation belongs to Phase 5.3 rather than here: `gemini-permissions.json` carries no PowerShell or `cmd.exe` read-only set at all, so a Windows Gemini user receives a POSIX-shaped allowlist. Do NOT add one in this sub-task, which rescopes existing entries and deliberately does not expand coverage. Record it as an observation and hand it to 5.3.
>
> Acceptance criteria: every retained entry in both the Bash and the PowerShell block is read-only at the side-effect level; the redirection finding and the `;`-chain finding are both recorded in the repository rather than only in the session; each removal or rescope is justified in a one-line comment or in the commit body; no unrelated entry is reworded or reordered.

#### 1.2 - Cross-platform and cross-scope install parity

**Objective**: Make permission installation succeed on every supported host and at every install scope, including a stock macOS with no `jq`, a Windows Git-Bash invocation, and a `--workspace` install.

**Prompt**:
> In `scripts/installer.sh`, the `install_permissions` function merges Claude and Gemini permission templates using `jq`. When `jq` is absent it prints a warning and installs nothing (see the warning around line 753). macOS does not ship `jq`, so a stock Mac silently receives no auto-approve baseline, while `scripts/installer.ps1` uses native JSON handling and has no such dependency. This is a real cross-platform asymmetry.
>
> Fix it by adding a fallback merge path that does not require `jq`. Prefer a small Python helper invoked by the bash installer (Python is already a documented dependency of this repository and both installers already check for it), keeping `jq` as the fast path when present so existing behavior is unchanged on hosts that have it. If you add a new `scripts/<name>.py` helper, you MUST register it by explicit name in BOTH `scripts/installer.sh` and `scripts/installer.ps1`, modeled on the existing `generate_report.py` copy block (see the "Installer-Aware Changes" section of `AGENTS.md`).
>
> Second, fix the Copilot branch's OS detection in the same function: the `case "$(uname -s)"` block handles `Darwin*` and `Linux*` and falls through to a skip for everything else, so a Windows Git-Bash invocation (`MINGW64_NT*`, `MSYS_NT*`, `CYGWIN*`) skips Copilot configuration entirely. Either map those to the `%APPDATA%\Code\User\settings.json` path that `installer.ps1` uses, or emit an explicit note directing the user to the PowerShell installer. Do not guess the path; mirror exactly what `installer.ps1` line 1288 uses.
>
> Third, close the workspace-scope hole. `install_permissions` takes a `scope` parameter documented as `"Global"` or `"Workspace"`, but every call site passes `"Global"`: the four calls in bash sit inside `install_global` (around lines 1197 to 1213) and the four in PowerShell inside its counterpart (around lines 1502 to 1514), while `install_workspace` (bash, around lines 1430 to 1586) never calls the function at all. A `--workspace` install therefore receives no permission baseline on any operating system, and the scope parameter is decorative. Wire the workspace path so the parameter becomes load-bearing.
>
> One design decision gates that wiring and needs a maintainer answer before you write it: at workspace scope the Claude target should be the project's `.claude/settings.local.json`, NOT `.claude/settings.json`, because the latter is commit-visible and would push a permission grant into the user's repository history. This is the same commit-visibility reasoning that made the v3.11.0 Copilot `.github/skills/` surface opt-in. Confirm the per-platform workspace target path for each of the four platforms before writing any of them, and skip-with-note rather than guessing for any platform whose project-scoped permission path is not documented.
>
> Fourth, resolve the standalone-helper asymmetry. `scripts/Install-Nexus-Hub-Permissions.ps1` provides install, uninstall, and backup-repair paths for all four platforms and has no bash sibling, so POSIX users have no equivalent repair route. Do NOT port it to bash. Expose the same install, uninstall, and repair capability through the cross-platform `nexus-hub` CLI instead: Phase 5 is already adding a subcommand to `scripts/nexus_hub_cli.py`, which runs identically on all three operating systems, so a second shell script would create the very dual-implementation drift this phase exists to remove. If that CLI work does not land in this release, record it in Phase 6.2 as a deferred item naming the CLI as the intended home rather than leaving the gap silent.
>
> Modifying the installer scripts is an "ask first" action per `AGENTS.md`. Present the intended diff for both installers and wait for confirmation before applying.
>
> Acceptance criteria: a permission install completes and merges entries on a host with `jq` removed from `PATH`; the bash and PowerShell paths produce an identical merged result for the same input; the Copilot branch no longer silently skips on Git-Bash; a `--workspace` install writes a confirmed project-scoped path for every platform with a documented one and skips-with-note for the rest; no workspace-scope write lands in a commit-visible file without an explicit maintainer decision; the standalone-helper decision is recorded either as shipped CLI capability or as a Phase 6.2 deferral.

**AMENDMENT A3 (2026-08-13)**: two pre-existing bugs surfaced during this sub-task and are pulled into it by maintainer directive rather than deferred to Phase 6.2. Both defeat the Phase 1.1 hardening for existing users, which is the population the hardening exists to protect.

> **Bug 1 - stale Gemini sentinel.** The `GEMINI` branch of `install_permissions` still gates on `grep -q 'run_shell_command(docker ps)'` to decide whether permissions are already configured. This is the identical stale-marker defect the `CLAUDE` branch was fixed for, and its in-code comment already explains why the pattern is wrong ("a single fixed marker made the installer think permissions were already installed and skip merging new entries shipped in later versions"). Because the sentinel entry is still present in every existing user's `settings.json`, those users would never receive the hardened allowlist. Apply in both installers.
>
> Additional acceptance criteria for A3: a Gemini config containing the old sentinel still receives newly-shipped entries; an existing config containing a since-removed entry (for example `Bash(gh api *)`) has it removed on upgrade; a user-added entry that Nexus-Hub never shipped survives the upgrade untouched; a backup exists before any removal; and the bash and PowerShell paths agree on all four behaviors.

#### 1.3 - Add a permission-baseline validator

**Objective**: Prevent mutation-capable entries from re-entering the read-only baseline.

**Prompt**:
> Create `scripts/validate_permission_baseline.py`, a Python-standard-library-only validator that reads `configs/permissions/claude-permissions.json` and `configs/permissions/gemini-permissions.json` and fails with a non-zero exit code when any entry in the read-only baseline is mutation-capable.
>
> Implement the check as a denylist of side-effect-bearing invocation shapes rather than a command-name allowlist, so it catches the `I6` failure class. At minimum detect: a subcommand or flag known to mutate (`--method` with a non-GET verb, `-delete`, `-exec`, `-i` in place-edit position, `-w` for `sysctl`, `link set` for `ip`); a shell redirection operator inside a pattern; and any pattern whose trailing wildcard would admit a mutating flag for a command on a curated list of dual-mode tools (`gh`, `find`, `awk`, `ip`, `sysctl`, `sed`, `tar`, `docker`). Encode the curated list as data at the top of the module with a comment explaining the criterion, so adding a tool is a one-line change.
>
> The validator MUST parse the `PowerShell(...)` prefix as well as `Bash(...)`, with its own cmdlet-shaped rules, because a bash-only denylist would silently pass every future PowerShell regression and the PowerShell block is currently the larger unaudited surface. Encode two more data lists next to the first, with the same one-line-to-extend property. The first is outright-mutating cmdlets and their standard aliases, which must never appear in the baseline at all: `Set-Content`, `Add-Content`, `Out-File`, `New-Item`, `Remove-Item`, `Copy-Item`, `Move-Item`, `Rename-Item`, `Clear-Content`, `Set-ItemProperty`, `New-ItemProperty`, `Remove-ItemProperty`, `Start-Process`, `Stop-Process`, `Invoke-Expression`, `Invoke-Command`, `Invoke-WebRequest`, `Invoke-RestMethod`, `Invoke-CimMethod`, `Set-ExecutionPolicy`, `Register-ScheduledTask`, plus `sc`, `si`, `ni`, `ri`, `cpi`, `mi`, `rni`, `iex`, `icm`, `iwr`, `irm`, `sp`, `saps`, `spps`. The second is dual-mode cmdlets, allowed only when scoped rather than wildcarded: `Get-CimInstance` and `Get-WmiObject` (object methods mutate), and anything a trailing wildcard would let reach a `-CimSession` or other remote-target parameter. Also flag a PowerShell pattern containing `;`, `&`, a backtick, `$(`, or a redirection operator, matching the syntax classes `format-powershell-description.py` already rejects on the hook path so the two layers cannot disagree about what counts as read-only.
>
> Register the validator by explicit name in BOTH `scripts/installer.sh` and `scripts/installer.ps1` (per the `AGENTS.md` installer rule), add a `make validate` step for it in the `Makefile`, and add it to the `validate` job in `.github/workflows/ci.yml`. Follow the registration pattern that `scripts/verify_model_prompting_profiles.py` and `scripts/run_trigger_evals.py` already use.
>
> Acceptance criteria: the validator exits zero against the hardened configs from sub-task 1.1; it exits non-zero and names the offending entry when a fixture config containing `Bash(gh api *)` is passed; it exits non-zero and names the offending entry for each of a `PowerShell(Set-Content *)` fixture, a `PowerShell(Invoke-Expression *)` fixture, and a wildcarded `PowerShell(Get-WmiObject *)` fixture; it parses both prefixes from the same file without either shadowing the other; it is reachable from `make validate` and from CI.

#### 1.4 - Testing and Stabilization

**Objective**: Generate and run all tests for this phase. Iterate until the phase is stable before advancing to Phase 2.

**Prompt**:
> Generate comprehensive tests for everything built in Phase 1. ## Phase 3: Autonomy core engine, consent gate, TTL, and audit

**Recommended model**: Strong reasoning tier (Opus class), maximum effort. Rationale: this is the highest-risk code in the plan.
