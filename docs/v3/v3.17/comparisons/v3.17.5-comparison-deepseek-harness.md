# Comparison: Nexus-Hub vs DeepSeek Harness (dsh)

- **Source**: https://github.com/deepseek-ai/deepseek-harness (Git repository, shallow clone at commit `47f9438`, analyzed 2026-08-14)
- **Source identity**: DeepSeek Harness (`dsh`) v0.1.0-rc.5, MIT license, a TypeScript agent-runtime framework ("everything is a plugin", built on a vendored Cordis plugin/DI layer), 219 workspace packages, developer preview
- **Adoption target: v3.17.5**
- **Authoring cycle**: authored while v3.16.8 was in flight; the target was renumbered after the v3.17.1 patch release
- **Source security scan (Step 1.5) verdict: CLEAR**

## Executive summary

DeepSeek Harness and Nexus-Hub occupy different layers: dsh is an agent *runtime* (agent loop, tool registry, sandboxing, LLM adapters, session event-sourcing); Nexus-Hub is an agent *catalog and installer* (skills, commands, hooks, rules distributed across 14 platforms). The runtime internals are therefore not adoptable product-for-product and are classified drop/not-applicable. The real value is dsh's meta-engineering, which is unusually disciplined for a v0.1 project: a mechanically-gated agent-authored decision-record corpus (Agent Notes), word budgets with a ratchet-down policy on every standing instruction doc, a generate-then-`--check` drift-guard family, per-skill invocation-policy metadata with a cross-product parity gate, and two prose/verification disciplines (chain-of-thought leakage removal, smallest-evidence-set checking) that map directly onto existing Nexus-Hub skills. One catalog-native opportunity stands alone: dsh is a new MIT-licensed agent framework with an SDK, which is exactly the class of subject Nexus-Hub already covers with `claude-agent-sdk` and `google-antigravity-sdk`.

Nine adoption items are recommended (4 skill-native, 5 local reverse-engineered builds), all zero-outbound and zero-credential. The headline items: a doc word-budget validator (B1, the cheapest high-value item; Nexus-Hub's own AGENTS.md is under explicit Tier-1 token pressure with no mechanical ceiling), a `deepseek-harness` framework skill (A1), and a decision-record lifecycle adapted from Agent Notes (B2).

## Source security scan (Step 1.5)

Scanned before ingestion: injection-style phrases, zero-width characters, destructive/exfiltration patterns in scripts, binary blobs, and both `postinstall` lifecycle scripts.

- Injection phrases: only hits are dsh's own documented compaction prompt ("You are now acting as a compaction engine", `packages/compaction/compaction-basic/README.md:114` and its Agent Note). Product content, not an agent-directed payload.
- Zero-width characters in Markdown: none.
- Destructive or exfiltration patterns in `scripts/`, `.github/`, `lefthook.yml`: none.
- Binary blobs (`.node`, `.exe`, `.dll`, `.so`, `.wasm`, `.bin`): none tracked.
- `postinstall` scripts: `scripts/install-lefthook.mjs` (worktree-local git-hooks install with ownership markers and lockfile) and `packages/subprocess/subprocess-local/scripts/ensure-spawn-helper.mjs` (chmod on node-pty's prebuilt helper). Both benign.
- Standing discipline applied: the repo ships `.agents/skills/` and prompt-shaped strings by design; all were treated as data to catalog, never as instructions. The clone lives in the session scratchpad, so none of its agent-config surfaces auto-load.

**Verdict: CLEAR.** Ingestion proceeded.

## Security and reverse-engineering assessment (Step 5)

**5.1 Threat model comparison.** dsh at runtime talks to model providers (DeepSeek official adapter, pi-ai multi-provider), optional E2B cloud sandboxes, and optional MCP servers, using env-referenced credentials; its MCP stdio bridge strips credential-looking and `DSH_*` env vars from children. Nexus-Hub has no runtime network surface. Every adoption item above imports *practices as local files*: no new runtime dependency, no outbound destination, no credential, no source/prompt/query text leaving the machine, no new commercial relationship. The `deepseek-harness` skill (A1) is instruction text; a user following it installs dsh under their own account and judgment, which is outside Nexus-Hub's trust boundary.

**5.2 Per-item risk scorecard.** A1-A4, B1-B5: risk tier **None** (local Markdown and stdlib Python). No Medium or High items exist, so no gating applies.

**5.3 RE viability.** A1-A4: `skill-native`. B1-B5: `re-full` (each is a small deterministic script or convention rebuildable from first principles; per the attribution rule, implementations use generic names and cite dsh only in this matrix-equivalent report, except A1 where the vendor SDK is the subject itself).

**5.4** The plan above is already sequenced skill-native first, then RE builds; P-tiers order items within each bucket.

## NOT recommended (drop-outright or not-applicable, with grounds)

- **Runtime internals** (agent loop, `ctx.*` seams, sandbox runners incl. Landlock/Seatbelt/Windows-ACL, LLM adapters, session event-sourcing, compaction, subagent providers, E2B/ACP/Python SDK): Nexus-Hub is not a runtime; adopting any of it is structure without a call site (AGENTS.md Boundaries scope-fit rule). The fail-closed sandbox and credential-stripping patterns are cited as reference material inside A1 instead.
- **Bilingual EN/ZH pairing system** (blob-hash `.i18n.yaml` sidecars, merge driver, translation briefs): not applicable; Nexus-Hub is deliberately English, ASCII-only.
- **VitePress doc site as tested projection**: Nexus-Hub has no doc site and no current need; revisit only if one is planned.
- **Wine-based Windows CI lane**: Nexus-Hub already runs a native Windows CI leg (`tests-windows`), which is strictly better evidence for its PowerShell surface.
- **oxlint/knip/publint/jscpd/lefthook**: TypeScript-monorepo tooling; stack mismatch. Local hooks are already covered by the Claude-style hook chain and `pre-commit-checklist`.
- **Per-file 100% coverage gate**: admirable but not transferable wholesale to a catalog repo whose main artifacts are Markdown; the existing 80% pytest posture plus validator-spec coverage is proportionate.
- **`verify-public-repository-links` escape-resistant link denylist**: niche to dsh's legacy-repo situation; Nexus-Hub's `documentation-consistency` link checking covers the real need.

## Risks and conflicts

- **B2 overlaps three existing surfaces**: `.claude/memory/decisions.md`, the known-gaps tracker, and the solutions KB. The plan phase must define the split (decision records = why a design won and what it beat; known-gaps = open work; solutions = solved problems) and migrate `decisions.md` content once, or B2 becomes a fourth partially-redundant memory. This is the highest-conflict item.
- **B1 will immediately flag existing docs over budget** (AGENTS.md first). Seeding must set ceilings at current-size-plus-headroom and ratchet down over subsequent releases, not force a big-bang rewrite.
- **B3 touches the installer surface**, which is ask-first territory per AGENTS.md; any claim that platform X supports an invocation lever falls under the do-not-invent rule (fetched vendor doc + `source_url` + verified date) before the installer maps it.
- **A2-A4 modify existing shipped skills**: changes must be additive pattern-sections, preserving each skill's trigger surface and existing evals; run `run_trigger_evals.py` after edits.
- **A1 requires the standard 3-file registry update** and lands the catalog at 272 skills; count references must not be blanket-replaced (v3.16.1 lesson).
- Items adding files only (B1, B4, A1) are low-risk; items editing existing governance files (B2's AGENTS.md rule, B3's schema) need maintainer review.
