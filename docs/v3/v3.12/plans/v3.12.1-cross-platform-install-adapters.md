# Plan - Cross-Platform Install Adapters + Per-Release Format Verification

**Project**: Nexus-Hub
**Version**: v3.12.1
**Slug**: cross-platform-install-adapters
**Filename**: v3.12.1-cross-platform-install-adapters.md (release-prefixed per the v3.11.0 naming convention)
**Plan Type**: Feature / Enhancement (with a terminal refactor + release-readiness phase)
**Created**: 2026-07-13
**Goal**: After the standard one-line install (`irm .../install.ps1 | iex` on Windows, `curl -fsSL .../install.sh | bash` on macOS/Linux), every Nexus-Hub command, skill, rule, and hook is actually discoverable in the new ChatGPT desktop app (Chat + Work + Codex) and the Antigravity IDE, exactly as it already is in Claude Code and Cursor. Every command surfaces BOTH as a slash command AND as a reusable skill (`$name`), so users of either interaction model find it. The canonical Nexus-Hub catalog is unchanged; each platform integration becomes an adapter that translates the catalog into that platform's native format and read-location. Finally, `/update release` gains a Nexus-Hub-specific step that re-verifies each supported platform's current discovery format via targeted web searches before every release, so the install can never again silently drift from what the apps actually read.

## Overview

This release fixes a class of bug that v3.11.0 Phase 7 set up the machinery for but did not resolve: the installer writes the catalog to per-platform paths that the target apps do not actually read, and it declares success on a successful copy. The v3.11.0 audit (`docs/v3/v3.11/platform-read-contracts.md`) even lists the exact suspect contracts as "residual live-verification gaps" (its gaps #1-#7), flagging Codex skill discovery and the Antigravity 2.0 global subpath as unconfirmed. Those gaps are now resolved against the platforms' current (2026) official documentation, and this release applies the confirmed contracts.

Two root causes drive the user-visible failure. First, both Codex and Antigravity require a one-level-deep skill layout (`skills/<name>/SKILL.md`), but Nexus-Hub's catalog is two levels (`catalog/skills/<category>/<name>/`), and the installer copies it verbatim, so every skill folder is buried one level too deep and nothing registers. Second, the install targets the wrong directories: Antigravity's real global read-paths are under `~/.gemini/config/` (`skills/`, `global_workflows/`) and `~/.gemini/GEMINI.md`, not `~/.gemini/antigravity/`; and Nexus-Hub commands reach Codex only through the now-deprecated custom-prompts surface (`/prompts:name`), while the new desktop app steers reusable actions to skills (`$name`), so a command like `presentify` is invisible there.

The verified contracts. Codex / new ChatGPT desktop app: skills are discovered one level deep at `~/.codex/skills/<name>/` and `~/.agents/skills/<name>/` (both documented user locations; project scope `.codex/skills/` and `.agents/skills/`), invoked as `$name`; custom prompts are deprecated but still read from `~/.codex/prompts/*.md` (top-level only) as `/prompts:name`; the instruction file is `~/.codex/AGENTS.md` plus the repo-root `AGENTS.md`. Antigravity 2.0 IDE: global skills at `~/.gemini/config/skills/<name>/`, global slash commands at `~/.gemini/config/global_workflows/<name>.md`, global rules/instructions at `~/.gemini/GEMINI.md`; the `agy` CLI reads skills from `~/.gemini/antigravity-cli/skills/<name>/`; project scope is `.agents/{skills,workflows,rules,hooks}`. Sources: [Codex Build skills](https://learn.chatgpt.com/docs/build-skills), [Codex Custom prompts (deprecated)](https://learn.chatgpt.com/docs/custom-prompts), [Codex AGENTS.md](https://developers.openai.com/codex/guides/agents-md), [Introducing the Codex app](https://openai.com/index/introducing-the-codex-app/), [Antigravity skills codelab](https://codelabs.developers.google.com/getting-started-with-antigravity-skills), [Antigravity IDE codelab](https://codelabs.developers.google.com/getting-started-agy-ide).

The design principle is an adapter pattern: the canonical catalog stays exactly as-is, and each platform integration materializes it into that platform's native shape and location. Every command is emitted twice where the platform supports both surfaces: as a slash command (verbatim `.md` for Claude/Antigravity workflows/Cursor; top-level `.md` for the legacy Codex prompts) and as a reusable skill (`skills/<command>/SKILL.md` synthesized from the command's frontmatter `description` plus its body, so `$presentify`, `$implement`, and every other command work). One honest platform limit is documented: a bare `/presentify` is achievable in Claude, Cursor, and Antigravity, but Codex has no custom bare-slash surface, so there it is `$presentify` (skill) plus `/prompts:presentify` (legacy). Both interaction models are covered on every platform that supports them.

The verification story has three layers. Layer 1 (the missing layer, and the user's explicit process request): does the contract still match each platform's CURRENT official documentation? This is a new Nexus-Hub-specific step in `/update release` that runs targeted web searches per platform and updates the contract doc, adapters, and installers on drift. Layer 2: does the install actually populate the read-paths? This is the existing `runner.py verify` subcommand (v3.11 Phase 7.4), whose expected-path table this release corrects. Layer 3: does the code match the contract doc? This is a new deterministic, offline `scripts/verify_platform_contracts.py` wired into `make validate`. The living contract is promoted from the version-scoped `docs/v3/v3.11/platform-read-contracts.md` snapshot to a durable `docs/policy/platform-read-contracts.md`, maintained the same way as the MCP registry matrix.

Success is demonstrated end-to-end: a dry-run global install produces, for Codex, `~/.codex/skills/presentify/SKILL.md`, `~/.agents/skills/presentify/SKILL.md`, and `~/.codex/prompts/presentify.md`, and every other command as both a skill and a prompt; for Antigravity, `~/.gemini/config/skills/<name>/SKILL.md`, `~/.gemini/config/global_workflows/<name>.md`, and `~/.gemini/GEMINI.md`; `verify_platform_contracts.py` reports zero code-vs-contract divergences; `runner.py verify` reports PASS for Codex and Antigravity against the corrected paths; `/update release` documents and runs the per-platform web-search re-verification before the version bump; and `make validate`, `make lint`, and `make test` are green.

#### 1.2 - Create the shared catalog-to-platform adapter helpers

**Objective**: Factor the catalog-materialization logic into one reusable, tested module so every platform integration produces the correct on-disk shape from one implementation.

**Prompt**:
> Create a shared adapter module for catalog-to-platform materialization (place it as `scripts/lib/integrations/_catalog_adapters.py`, mirroring the existing private-helper naming like `_command_surface.py`; import stdlib + the existing `FileAction`/`InstallContext`/`WriteResult` types only, no outbound calls). Implement three pure helpers, each returning `list[FileAction]` and honoring `ctx.dry_run` / `ctx.overwrite` exactly like the `base.py` copy helpers: (1) `flatten_skills(src_skills_dir, dst_skills_dir, ctx, key)` - copy `catalog/skills/<category>/<name>/` to `<dst>/<name>/` (drop the category level; skill folder names are globally unique, verified, so no collision); this is a generalization of the existing `Antigravity20Integration._mirror_flattened_skills` (antigravity.py:224-246), so extract that logic here and have antigravity call the shared helper in Phase 3. (2) `commands_to_skills(src_commands_dir, dst_skills_dir, ctx, key)` - for each `catalog/commands/<name>.md`, synthesize `<dst>/<name>/SKILL.md`: parse the command file's YAML frontmatter `description`, emit frontmatter `name: <name>` and `description: <lifted description>` (prefix with a short "Run the /<name> command." lead-in so the skill router understands it maps to a slash command), then the command body (everything after the frontmatter) as the skill body; skip a command only if a real catalog skill already owns that folder name (none do today, but guard for it and log a skip). (3) `commands_to_slash(src_commands_dir, dst_dir, ctx, key, style)` - emit slash-command files; `style="verbatim"` copies `<name>.md` unchanged (Claude/Antigravity workflows), `style="codex_prompts"` copies each `<name>.md` top-level (no subdirs) into the prompts dir. Add a module docstring explaining the adapter pattern and cross-referencing `docs/policy/platform-read-contracts.md`. Do NOT wire these into any integration yet - Phases 2-4 do that.

## Complexity Tracking

- **Two-installer lockstep (bash + PowerShell)**: every installer-touching change (Phases 2, 3, 5) must land in both `installer.sh` and `installer.ps1` with byte-equivalent behavior. Mitigation: route delivery through the Python registry integration (single source), so the installers only call `invoke_registry_platform`; `check_base_template_parity.py` and manual dry-run on both shells guard the rest.
- **External-doc dependency**: the corrected contracts depend on 2026 platform docs that can change again. Mitigation: that is precisely what Phase 5.3 institutionalizes; the living contract doc carries source URLs and a last-verified date, and `/update release` re-checks them every release.
- **`~/.agents/skills` is a shared cross-tool location**: both Codex and Antigravity-adjacent tooling reference `~/.agents/`. Writing there is additive and one-level, so it cannot collide with a platform's own skills, but the manifest must track it for clean teardown. Mitigation: use the standard `_copy_tree`/manifest tracking so `teardown` removes exactly what was written.
- **Residual live-verification gaps**: a few paths (the `agy` CLI global workflow dir, Antigravity global hooks, desktop-app skill-dir preference) cannot be confirmed without a live VM. Mitigation: write to all documented candidates (best-effort, additive), record each as a known gap, and let the Phase 5.3 release step confirm them over time.
