# Plan -- /presentify fidelity, interactivity, and design-variety overhaul

**Project**: Nexus-Hub
**Version**: v3.12.0
**Slug**: presentify-fidelity-and-variety
**Plan Type**: Feature / Enhancement (existing skill + command; no new skill)
**Created**: 2026-07-11
**Goal**: Upgrade `/presentify` + `document-to-interactive-html` so that (1) every piece of content in every supported source -- text, data, photos, maps, and figure graphics, including scanned / image-only PDF pages read through a local OCR tier with an agent-vision fallback -- reaches the output, (2) figures whose underlying data is unavailable are analyzed in detail and faithfully reconstructed as interactive charts (or presented as enhanced originals when confidence is low, never fabricated), (3) the output carries site-wide dynamism (scroll, hover, counters, lightboxes) rather than chart-only interactivity, and (4) two runs on the same source with the same style preset still differ meaningfully in palette, feel, and layout via a mechanical design-entropy stage -- all while preserving the local-only / zero-external-request / single-file guarantees.

## Overview

The v3.9.0 `presentify-interactive-html` plan shipped a compositional pipeline (local extractor -> normalized content model -> LLM-authored self-contained site) that works well for text, tables, and spreadsheet data, but a real-world run on a PDF saved from PowerPoint exposed four systematic weaknesses, each traced to a design decision rather than a bug. First, PDF visual extraction was explicitly deferred (DF-v39-presentify-2): `_extract_pdf` reads text and tables only, so photos, maps, and figure graphics in the dominant real-world input format never reach the authoring stage, and a scanned or image-only PDF yields almost nothing at all because OCR was likewise deferred (DF-v39-presentify-1). Second, there is no figure-reconstruction path: `chart` blocks are only produced from `.xlsx` numeric ranges (native PPTX/DOCX chart objects were deferred as DF-v39-presentify-3), so a plot that exists as a static image is never analyzed and rebuilt as a faithful interactive chart. Third, the interactivity contract is chart-centric -- navigation plus zoom/pan/toggle charts -- so a source that yields no `chart` blocks produces a static-feeling page with no scroll, hover, or motion affordances. Fourth, design variety is aspirational rather than mechanical: the attractor blocklist and "differ from the previous run" guidance have no entropy source and no run history, so repeated runs with the same preset converge to similar palettes and layouts.

This plan fixes all four at the root -- and additionally closes the scanned / image-only PDF gap (DF-v39-presentify-1), an explicit scope requirement -- in the existing `catalog/skills/specialized-domains/document-to-interactive-html/` bundle and `catalog/commands/presentify.md`. The target persona is the Nexus-Hub user converting real business, clinical, or board documents -- most often PDF exports of decks -- into interactive sites they can actually share. Delivery is: an extractor upgrade (PDF raster-image extraction, vector-figure region capture via optional local rasterization, scanned-page detection with a local OCR tier plus a zero-dependency agent-vision reading fallback, PPTX group-shape recursion, native PPTX/DOCX chart-part extraction, and an extraction coverage manifest), a content-model v2 (additive, backward-compatible fields for figure provenance, captions, and reconstruction confidence), a new LLM-native figure-reconstruction protocol reference with hard fidelity gates, a site-wide interaction layer with a minimum interaction budget wired into the skill's verification, a seeded design-entropy script plus a persisted run history that makes same-preset variety mechanical, and an end-to-end worked example that replays the failing case (a PDF exported from PowerPoint) plus a two-run same-preset divergence proof. Everything stays local-only: new parsing capability uses lazy-imported permissively-licensed local libraries with `pip install` hints, generation stays LLM-native, and the output keeps zero external requests.

Success looks like: on a PDF-from-PowerPoint fixture, the extraction coverage manifest accounts for every source visual and the output renders each one (as an interactive reconstruction, an embedded original, or an explicitly-skipped item with a reason); on a scanned-PDF fixture, the full text, tables, and figures are recovered accurately through the OCR tier or the agent-vision fallback; every reconstructed chart's numbers trace to a documented read-the-figure worksheet with cross-checks and a view-original toggle; the page passes a site-wide interaction budget (not just chart interactivity); two consecutive same-preset runs produce measurably different palettes, type voices, and layout signatures; DF-v39-presentify-1, DF-v39-presentify-2, and DF-v39-presentify-3 are resolved in the known-gaps ledger; and `make validate`, `make lint`, and `make test` are green.

## Phase 1: Extraction fidelity (extractor + content model v2)

**Goal**: No source content is silently dropped: PDF embedded raster images, PDF vector-figure regions, scanned / image-only pages (via a local OCR tier with an agent-vision fallback), PPTX grouped-shape content, and native PPTX/DOCX chart data all reach the content model, and the extractor emits a coverage manifest the authoring stage must reconcile against.
**Prerequisites**: None.
**Stability Gate**: On a PDF-from-PowerPoint fixture, `extract_content.py` emits image blocks for embedded raster images and rasterized vector-figure regions (or a per-page skip warning when the optional renderer is absent); on a PPTX fixture with grouped shapes and a native chart, grouped text is extracted and the chart becomes a `chart` block with real series values; on a scanned-PDF fixture, low-text pages are detected, their text and tables are recovered through the OCR tier when a local engine is available, and full-page image blocks (origin `scanned-page`) are emitted for agent-vision reading either way; the model output validates against the updated `references/content-model.md` (schema_version 2, additive fields only); the coverage manifest counts match the fixture's actual visuals; a missing optional library degrades to a documented warning plus `pip install` hint, never a crash; validators green.
**Recommended model**: Strong reasoning tier, high effort. Concrete (Claude Code): Fable 5, high effort. Rationale: heterogeneous binary-format spelunking (PDF object streams, OOXML chart parts, shape-tree recursion) where silent data loss is the exact failure mode this plan exists to eliminate; every heuristic (figure-region detection, caption pairing) has messy real-world counterexamples. `/implement` re-confirms against the then-current models.

### Sub-tasks

#### 1.1 -- Extend the content model to v2 (additive, backward-compatible)

**Objective**: Give the model the fields that figure fidelity and reconstruction provenance require, without breaking the v1 contract or the deterministic builder.

**Prompt**:
> Update `catalog/skills/specialized-domains/document-to-interactive-html/references/content-model.md` to schema_version 2 with ADDITIVE fields only (v1 consumers keep working; unknown fields are ignored, exactly like unknown block types). (1) `image` blocks gain optional `caption` (string; nearby caption text when detected), `page` (integer; source page/slide number), `origin` (one of `embedded-raster`, `rasterized-region`, `shape-picture`, `inline-image`, `scanned-page`), and `classification` (string, default empty; filled by the Phase 2 protocol -- e.g. `chart`, `map`, `diagram`, `photo`, `decorative`). (2) `chart` blocks gain optional `provenance` (one of `source-data` for xlsx ranges, `native-chart` for extracted PPTX/DOCX chart parts, `reconstructed-from-image` for Phase 2 reconstructions), `confidence` (one of `high`, `medium`, `low`; required when provenance is `reconstructed-from-image`), `source_image` (a base64 data URI of the original figure, for the view-original toggle), and `axis` (an object with optional `x_label`, `y_label`, `y_min`, `y_max`, `unit` so reconstructions preserve scales). (3) `paragraph` and `table` blocks gain optional `provenance` (one of `text-layer` (the default when absent), `ocr`, `agent-read`) and `ocr_confidence` (number 0-1, present when provenance is `ocr`) so fidelity checks know which text must be verified against the page image. (4) Add a top-level optional `coverage` object: per-source counts of `{images_found, images_kept, images_skipped, skip_reasons: [string], native_charts, tables, vector_regions_rasterized, vector_regions_skipped, scanned_pages_detected, ocr_pages, ocr_low_confidence, agent_read_pages}` -- the extraction coverage manifest the authoring stage reconciles against in Phase 5. (5) Document that `schema_version` becomes 2 and state the compatibility rule explicitly. Constraints: ASCII-only; follow `catalog/style-guides/markdown.md`; keep the "model is the only contract" framing. Acceptance: the schema documents every new field with its allowed values, marks all of them optional, states the v1-compatibility rule, and the per-format mapping sections mention where each new field comes from.

#### 1.2 -- PDF raster-image and vector-figure extraction

**Objective**: Make PDF inputs contribute their photos, maps, and figure graphics -- the root cause of the reported content loss (resolves DF-v39-presentify-2).

**Prompt**:
> Extend `_extract_pdf` in `catalog/skills/specialized-domains/document-to-interactive-html/scripts/extract_content.py`. (1) Embedded raster images: extract each page's embedded images with bytes and position -- use `pypdf`'s `page.images` for bytes (lazy-imported; it is already the text fallback library) and `pdfplumber`'s `page.images` metadata for bboxes and reading-order placement; emit `image` blocks (origin `embedded-raster`, `page` set) through the existing `_encode_image` budget/downscale path, placed at their in-page position relative to the text blocks. Deduplicate repeated per-page assets (logos, footers) by content hash: an identical image appearing on 3+ pages is kept once and skipped elsewhere, counted in the coverage manifest with reason `repeated-asset`. (2) Vector-figure regions: many PDF figures (plots exported from PowerPoint, maps, diagrams) are vector drawings with no embedded raster. Detect figure regions per page by clustering `pdfplumber` non-text objects (curves, rects, lines) into bounding boxes with low text density and above a minimum area, then rasterize each detected region: lazy-import `pypdfium2` (permissive license; `pip install pypdfium2`) to render the page at ~2x scale, crop the region bbox with `Pillow`, and emit an `image` block (origin `rasterized-region`, `page` set). When `pypdfium2` or `Pillow` is absent, print ONE warning listing the affected pages plus the `pip install` hint and continue without failing -- the standing lazy-import discipline. (3) Caption pairing: when a short text line starting with a figure cue (e.g. `Figure`, `Fig.`, `Exhibit`, `Table`) or an isolated short line sits directly below a detected image/region, attach it as the block's `caption`. (4) Fill the `coverage` manifest counts for everything found, kept, and skipped (with reasons). Constraints: follow `catalog/rules/python/` (type hints, ruff-clean, no bare except); every new third-party import stays lazy inside the function that needs it; deterministic ordering; no network calls; ASCII-only source. Acceptance: on a fixture PDF exported from PowerPoint containing at least one photo, one vector chart, and one map, the model contains image blocks for each (raster ones as `embedded-raster`, vector ones as `rasterized-region`), captions are attached where present, repeated logos are deduplicated with a coverage entry, and removing `pypdfium2` from the environment yields the documented warning and a model that still contains the text, tables, and raster images.

#### 1.3 -- PPTX grouped shapes and native PPTX/DOCX chart extraction

**Objective**: Stop losing deck content hidden in groups and native chart objects (resolves DF-v39-presentify-3).

**Prompt**:
> Extend the PPTX and DOCX extractors in `scripts/extract_content.py`. (1) Group recursion: in `_extract_pptx`, recurse into `GROUP` shapes (a group's `.shapes` is iterable like a slide's) so text frames, tables, and pictures inside groups are extracted in z-order; guard against pathological nesting with a sane depth cap. Update the runbook gotcha accordingly. (2) Native PPTX charts: for shapes with `has_chart`, read `shape.chart` (python-pptx exposes `plots[].categories` and `series[].values`) and emit a `chart` block with `provenance: "native-chart"`, the chart's own type mapped into `chart_type_hint` (bar/line/pie families; anything unmappable falls back to `bar` for numeric series), the chart title as a nearby heading or caption when present, and real numbers -- never placeholders. A chart whose data cannot be read (corrupt part, unsupported type) falls back to an `image` block when a picture fill is available, else a coverage `skip_reasons` entry -- never silent loss. (3) Native DOCX charts: `python-docx` does not expose chart parts, so read them from the OOXML package directly -- walk the document part's relationships for `chart` parts and parse `word/charts/chart*.xml` with stdlib `xml.etree` (namespaces `c:` drawingml chart), extracting `c:cat` string/number caches and each `c:ser`'s `c:val` number cache into a `chart` block with `provenance: "native-chart"`. Best-effort: a malformed chart part degrades to a coverage skip entry with reason. (4) Count native charts in the `coverage` manifest. Constraints: same Python rules and lazy-import discipline; stdlib-only for the OOXML XML parsing; ASCII-only; deterministic ordering. Acceptance: a fixture PPTX with a grouped text box and a native bar chart yields the grouped text and a `chart` block whose values match the source data exactly; a fixture DOCX with an embedded chart yields the same; unmappable charts appear in the coverage manifest, not as silent drops.

#### 1.4 -- Deck-PDF sectioning and heading heuristic upgrade

**Objective**: Make a PDF-exported deck read as a deck (one slide per section with real titles), not as "Page N" text soup.

**Prompt**:
> Improve `_extract_pdf` sectioning in `scripts/extract_content.py`. (1) Heading detection by typography: with `pdfplumber`, promote a page's heading from its character-level font sizes (the page's largest-font short line near the top) instead of only the first-short-line heuristic; keep the current heuristic as the fallback when font metadata is unavailable (pypdf path). (2) Deck-PDF detection: when a PDF's pages are landscape-oriented with low text density and consistent layout (a PDF exported from slides), tag the extraction so the mode auto-detect in the command/skill treats it as deck-like (preserve page order as slide flow; one page = one section is already the behavior -- the improvement is the heading quality and a `deck_like: true` hint on the model's source entry, an additive v2 field to document in `references/content-model.md`). (3) Update `references/extraction-runbook.md`'s PDF section: replace the "PDF contributes text and tables only" / "image extraction out of scope" statements with the new coverage (raster images, rasterized vector regions, captions, dedup, the optional `pypdfium2` dependency and its graceful degradation) and the deck-PDF behavior. Constraints: Python rules; ASCII-only; Markdown style guide. Acceptance: the PDF-from-PowerPoint fixture yields real slide titles as section headings (not `Page N`) and a `deck_like` hint; the runbook accurately describes the new PDF coverage and no longer claims images are out of scope.

#### 1.5 -- Scanned-page detection and the two-tier OCR path

**Objective**: Make scanned / image-only PDFs (and scanned pages inside mixed PDFs) contribute their full text, tables, and figures instead of yielding nothing (resolves DF-v39-presentify-1).

**Prompt**:
> Extend `_extract_pdf` in `catalog/skills/specialized-domains/document-to-interactive-html/scripts/extract_content.py` with scanned-page handling. (1) **Detection**: classify a page as scanned when its text layer is empty or near-empty (below a small character threshold) while the page area is dominated by one or more large images, or when its only text is watermark/header boilerplate on an otherwise image-covered page; count `scanned_pages_detected` in the coverage manifest. (2) **Tier A -- local OCR (optional, preferred for bulk text)**: lazy-import a pip-only, permissively-licensed OCR engine -- default `rapidocr-onnxruntime` (`pip install rapidocr-onnxruntime`; bundled detection + recognition on ONNX runtime, no system binary), accepting `pytesseract` as an alternative when the Tesseract binary is already installed -- rasterize the page via the 1.2 `pypdfium2` path at OCR-friendly resolution, run OCR, and emit `paragraph` / `table` blocks with `provenance: "ocr"` and per-block `ocr_confidence`, preserving reading order from the OCR geometry (stable position sort). (3) **Tier B -- agent-vision fallback (always available)**: whether or not OCR ran, emit a full-page `image` block (origin `scanned-page`, `page` set) for every scanned page within the image budget, so the authoring agent can read the page directly per the Phase 2 protocol; when no OCR engine is installed, print ONE warning naming the scanned pages plus both `pip install` hints and continue -- the page images guarantee no content is lost. (4) **Accuracy discipline**: OCR text is never trusted blind -- blocks below a documented confidence threshold are counted in `ocr_low_confidence` so the Phase 2 protocol verifies them against the page image, and numbers in OCR'd tables are ALWAYS verified during authoring regardless of confidence. (5) Update `references/extraction-runbook.md`'s PDF section and out-of-scope list accordingly (scanned-PDF OCR moves from out-of-scope to the two-tier path; document engine choices, rasterization resolution, and the graceful degradation). Constraints: `catalog/rules/python/`; lazy imports only; deterministic block ordering; no network calls; ASCII-only source. Acceptance: a scanned-PDF fixture with known text, a table, and a figure yields (a) with the OCR engine installed: paragraph/table blocks with `provenance: "ocr"`, confidence values, and correct reading order, plus the full-page image blocks; (b) without it: the documented warning and the full-page image blocks only; (c) in both cases the figure region also surfaces per the 1.2 pipeline and the coverage manifest counts reconcile.

## Phase 2: Faithful figure reconstruction protocol (LLM-native)

**Goal**: Every extracted figure image is classified and -- when it depicts data -- analyzed in detail and reconstructed as an interactive chart whose numbers, scales, and units are traceable and truthful, with the original always one toggle away; low-confidence reads are presented as enhanced originals, never fabricated charts. Scanned pages are transcribed and their OCR text verified under the same truthfulness discipline.
**Prerequisites**: Phase 1 (figure images, scanned-page blocks, and provenance fields exist in the model).
**Stability Gate**: `references/figure-reconstruction.md` exists and defines the classification taxonomy, the read-the-figure worksheet, the fidelity cross-checks, the confidence gate, the output patterns (reconstruction + view-original toggle; enhanced-original fallback), and the scanned-page transcription/verification pass; SKILL.md's Instructions include the protocol as a mandatory step whenever image blocks exist, with new rationalization rows and verification items; the orphan-bundle audit sees the new reference; validators green.
**Recommended model**: Strong reasoning tier, high effort. Concrete (Claude Code): Fable 5, high effort. Rationale: this is the truthfulness core -- the protocol must make fabricated data structurally impossible while still extracting maximum value from static figures; writing gates that an agent cannot rationalize around is the hard part. `/implement` re-confirms against the then-current models.

### Sub-tasks

#### 2.1 -- Author the figure-reconstruction protocol reference

**Objective**: Define the complete LLM-native method for turning a static figure image into a faithful interactive reconstruction (or an honest fallback).

**Prompt**:
> Create `catalog/skills/specialized-domains/document-to-interactive-html/references/figure-reconstruction.md`. Structure: (1) **Classification pass** -- the agent reads every `image` block (rendering them from their data URIs) and assigns `classification`: `chart` (data-bearing plot), `map`, `diagram`/`flow`, `table-image`, `photo`, `screenshot`, `decorative`; record the classification back into the model JSON (the v2 field). (2) **Read-the-figure worksheet (charts and table-images)** -- a structured extraction the agent MUST fill before building anything: chart family; title; axis labels and units; tick values and scale type (linear/log); legend entries; per-series point estimates read against gridlines (with an explicit estimated-precision statement, e.g. "read to the nearest 5"); source footnotes. The worksheet is written into the run as an HTML comment adjacent to the reconstructed chart so every number is auditable. (3) **Fidelity cross-checks** -- before accepting a worksheet: endpoints and extrema match the image; category counts match; percentage series that should sum to ~100 do; axis ranges contain all read values; units carried into the `axis` object. Any failed check forces a re-read or a confidence downgrade. (4) **Confidence gate** -- `high` (crisp figure, all ticks legible, cross-checks pass): build the interactive reconstruction (`chart` block, provenance `reconstructed-from-image`, `source_image` set) with a small provenance badge ("reconstructed from source figure") and a view-original toggle that swaps in the embedded original image; `medium` (values partly interpolated): same, plus a visible caption noting values are read from the figure to stated precision, and the original shown by default alongside; `low` (illegible, dense, or ambiguous): NO reconstruction -- present the original image in an enhanced viewer (pan/zoom lightbox, caption, high-resolution re-render when the source was a rasterized region) and say why. Fabricating or smoothing data to make a chart buildable is prohibited in all tiers. (5) **Maps and diagrams** -- rebuild simple structures as interactive inline SVG (hover highlights, labeled regions, pan/zoom) only when every label and relationship in the original is preserved; otherwise use the enhanced-original viewer. Photos and screenshots always render as originals (lightbox-enabled); `decorative` images may be dropped ONLY with a coverage skip entry. (6) **Model round-trip** -- the protocol updates the model JSON (classifications, new reconstructed `chart` blocks referencing their `source_image`) so Phase 5's coverage reconciliation can audit it. (7) **Scanned-page transcription and OCR verification** -- for `image` blocks with origin `scanned-page`, the agent reads the page image and reconciles it with any co-located `provenance: "ocr"` blocks: verify every low-confidence block, verify ALL numeric content (tables, figure values, captions) against the image regardless of confidence, transcribe content OCR missed as new blocks with `provenance: "agent-read"`, and route the page's figure regions into the classification pass above. Transcription follows the worksheet's truthfulness rules: unreadable content is marked unreadable, never guessed. Constraints: ASCII-only; Markdown style guide; generic naming (Attribution Rule); this file MUST be referenced from SKILL.md. Acceptance: the reference defines all seven parts with the worksheet as a copyable template, the confidence gate is binary and observable, and the prohibition on invented data is stated in every tier.

#### 2.2 -- Wire the protocol into SKILL.md and the command

**Objective**: Make figure reconstruction a mandatory pipeline step, not an optional nicety.

**Prompt**:
> Update `catalog/skills/specialized-domains/document-to-interactive-html/SKILL.md` and `catalog/commands/presentify.md`. In SKILL.md: (1) add a numbered Instructions step between extraction and design ("Classify and reconstruct figures") that invokes `references/figure-reconstruction.md` whenever the model contains image blocks, and update the pipeline diagram to show it; (2) add Common Rationalizations rows -- at minimum: "the figure is just a picture, I'll embed it as-is" (a data-bearing figure embedded as a static image throws away the skill's core promise; classify first), "I can eyeball the bar heights, close enough" (unaudited numbers are fabrication; fill the worksheet and cross-check or downgrade confidence), "the chart is blurry so I'll approximate a nicer version" (low confidence means enhanced original, never invented data); (3) add Verification items: every image block carries a classification; every reconstructed chart has a worksheet comment, provenance, confidence, and a working view-original toggle; no reconstructed chart exists whose numbers lack a worksheet. ## Phase 4: Design-entropy engine and run history

**Goal**: Same-preset reruns differ mechanically, not aspirationally: a seeded sampler rolls concrete design tokens from curated axis pools (constrained per preset), a persisted run history forces distance from recent runs, and the brainstorm becomes roll-then-adapt.
**Prerequisites**: None (parallel-safe), but lands before Phase 5's divergence proof.
**Stability Gate**: `scripts/design_seed.py` emits a complete design brief (JSON) sampled from per-preset pools, is deterministic under `--seed` and random otherwise, reads/writes the run history, and rejects candidates too close to recent runs; the brainstorm docs instruct roll-then-adapt; two same-preset invocations produce briefs differing in at least hue family, and at least one of layout signature / type pairing; validators green.
**Recommended model**: Strong reasoning tier, high effort. Concrete (Claude Code): Fable 5, high effort. Rationale: designing axis pools that are simultaneously varied, tasteful, preset-faithful, and hallmark-design-compliant is judgment-heavy; a bad pool bakes in new sameness or ugliness at scale. `/implement` re-confirms against the then-current models.

### Sub-tasks

#### 4.1 -- Build the design-entropy sampler script

**Objective**: A local, dependency-free script that turns "be different this time" into a mechanical roll.

**Prompt**:
> Create `catalog/skills/specialized-domains/document-to-interactive-html/scripts/design_seed.py` (single cross-platform `.py`, stdlib only -- `random`, `json`, `argparse`, `hashlib`, `pathlib`). CLI: `python design_seed.py [--preset corporate|creative|technical|surprise] [--seed N] [--history PATH] [--candidates N] -o brief.json`. Behavior: (1) **Axis pools**: curate in-script pools -- hue-anchor families (at least 12 distinct families spanning the wheel, each with a light AND dark base variant), palette moods (warm-paper, cool-clinical, high-contrast-editorial, muted-earthy, saturated-playful, duotone, ...), neutral temperatures, type voices (serif-display editorial, geometric-sans, humanist-warm, mono-technical, slab-confident, mixed-contrast pairings -- system stacks only), layout signatures (asymmetric split, editorial grid with pull elements, full-bleed banded, sidebar-anchored, magazine spread, offset column rhythm, diagonal/stagger), motion personalities (crisp, weighty, springy, minimal), and signature-move options (one distinctive interactive/layout move per run). (2) **Preset constraints**: each preset maps to a SUBSET of each pool (e.g. `technical` excludes saturated-playful moods but spans all hue families and both light/dark bases; `corporate` constrains mood, not hue), so preset intent holds while palette and feel still vary; `surprise` uses full pools. (3) **Entropy**: default seed from `os.urandom`; `--seed` makes the roll reproducible. (4) **History distance**: read the history file (default `~/.nexus-hub/state/presentify-design-history.json`, created on first write; `--history` overrides), holding the last N committed briefs (source-content hash, preset, chosen axis values, timestamp). Roll `--candidates` (default 3) briefs and emit the one maximizing distance from the last 3 history entries, where a candidate is REJECTED outright if it shares 2 or more of {hue family, layout signature, type pairing} with any of them; if all candidates are rejected, re-roll once with widened pools before accepting the least-similar. (5) **Output**: a JSON brief -- preset, seed, hue family + concrete hex palette suggestion (base/surface/ink/one-or-two accents), mood, type pairing (concrete CSS stacks), spacing rhythm, layout signature, motion personality, signature move, and a one-line human-readable summary -- plus a `--commit` flag that appends the brief to history (called after the run actually uses it). The brief is a STARTING POINT the agent adapts to the content; the script never writes HTML. Constraints: `catalog/rules/python/`; ASCII-only; no third-party imports; deterministic under `--seed`; the attractor look (near-black + amber + mono eyebrows + card grid) must not be reachable as a rolled combination except under `surprise` with explicit low probability. Acceptance: two invocations without `--seed` and with the same preset yield briefs differing per the stability gate; `--seed 42` twice yields identical briefs; the rejection rule demonstrably fires against a seeded history; the history file round-trips and caps its length.

#### 4.2 -- Rewrite the brainstorm as roll-then-adapt and wire the pipeline

**Objective**: Make the entropy stage the skill's default design path so variety survives agent drift.

**Prompt**:
> Update the design-direction content in `catalog/skills/specialized-domains/document-to-interactive-html/references/interactive-features.md` and the corresponding SKILL.md step. New order: (1) a named `--style`/`--theme` still binds (unchanged); (2) otherwise the five-option menu resolves the PRESET; (3) then the agent RUNS `python scripts/design_seed.py --preset <choice> -o brief.json`, treats the rolled brief as the committed starting tokens, adapts hex values and pairings to the content's character (the brief picks the register; the agent tunes within it -- it must NOT re-roll until it likes the answer or silently swap axes back toward the attractor), records the final tokens plus the seed and brief summary in the output's HTML design-record comment, and calls `--commit` so the history advances; (4) the divergence-from-attractor and differ-from-previous-run rules remain as backstops. Document the failure mode this fixes ("same preset, same look every run") and state that skipping the roll is only permitted when the script cannot execute (no Python), in which case the agent must manually vary hue family + layout signature away from the last recorded run and say so. Update SKILL.md: the Instructions step, a Common Rationalizations row ("I have good taste, I don't need the roll" -- taste converges; the roll exists because unseeded choices repeat; adapt the roll, don't override it), and Verification items (the design record includes the seed + brief summary; the history file gained an entry; the tokens match the brief's axes). Update `catalog/commands/presentify.md`'s design-selection section to mention the roll in one sentence. Constraints: SKILL.md <= 500 lines; ASCII-only; the new script MUST be referenced from SKILL.md (orphan-bundle audit). Acceptance: the roll is the default path in both files, the no-silent-re-roll rule is explicit, and verification covers seed, history, and token-brief consistency.
