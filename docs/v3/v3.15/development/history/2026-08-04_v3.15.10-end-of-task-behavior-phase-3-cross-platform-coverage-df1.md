## 2. Chronological Steps

### 2.1 T020 - Event-vocabulary verification

The phase's rule was that a trigger ships only when its event name is verified first-party, because an unverified name produces a hook that is registered, executable, and permanently inert. `escalation-trigger.sh` was exactly that for four minor versions, so this is a demonstrated failure mode rather than a hypothetical one.

| Platform | Trigger A (blocked on human) | Trigger B (finished) | Basis |
|---|---|---|---|
| Claude Code | `Notification` | `Stop` | Phase 1, already shipped |
| Cursor | **none exists** | `stop` | first-party, fetched today |
| Qwen | **none exists** | `Stop` | v3.15.8 first-party, explicit closed list |
| Gemini CLI | none documented | **`AfterAgent`** (renamed) | v3.15.8 first-party |
| Codex | unverified | likely `Stop` | first-party confirms hooks exist but never enumerates events |
| Kimi Code CLI | unverified | unverified | v3.15.8 verified the schema, not the event set |
| Copilot | **impossible** | **impossible** | no hook surface |
| OpenCode | **impossible** | **impossible** | JS/TS Bun plugin runtime (DF-4) |

Three findings changed decisions:

**Trigger A is nearly unique to Claude Code.** Cursor's first-party docs list 21 events across agent, Tab, and app-lifecycle groups. None means "waiting on the human". The closest candidate, `beforeShellExecution`, can return an `ask` permission status, but it fires before *every* shell command rather than only when input is genuinely required, so notifying there would recreate the exact per-turn storm this release removes. Trigger A was therefore omitted for Cursor rather than approximated. Approximating a trigger is worse than omitting one, because the user cannot tell the difference from the notification itself.

**Gemini CLI renamed every event.** `Stop` does not exist there; the completion event is `AfterAgent` (and `PreToolUse` is `BeforeTool`, `PreCompact` is `PreCompress`). Writing `Stop` would have shipped a silently dead hook. This is the single most valuable thing the verification step bought.

**Codex's `PermissionRequest` is secondary-source only.** Several community guides and a docs mirror describe a `PermissionRequest` event that would make Codex the second platform able to express trigger A. It could not be confirmed: `openai/codex` has no `docs/hooks.md`, and the reachable first-party `docs/config.md` carries only a short "Lifecycle hooks" section about `allow_managed_hooks_only`. Nothing was delivered on that evidence. It is recorded as worth settling precisely because the payoff would be real.

Cursor also has a `subagentStop` event, which the contract forbids wiring. That is now asserted by test rather than trusted.

### 2.2 T021 - Delivery to Cursor

Extended `scripts/lib/integrations/cursor.py`: added a `stop` entry to `_hook_registration` and put `notify-on-complete.sh` plus `_notify_common.sh` in `_CURATED_HOOK_SCRIPTS`.

The helper is the part worth calling out. `notify-on-complete.sh` sources `_notify_common.sh` from its own directory, so shipping the hook without the module would have produced a hook that is registered, executable, and silently no-ops on every run: the worst failure mode available, and the same shape as the inert-hook defect this phase exists to prevent. That is now its own test.

Four platforms were NOT given trigger B despite it being expressible, and the reasons are recorded rather than left implicit: Qwen and Gemini CLI merge hooks into their own `settings.json` layouts and each needs its own writer plus test surface (Gemini CLI additionally being enterprise-only opt-in post-2026-06-18, making it the lowest-value target); Codex and Kimi have unverified event sets. Deferring is the honest outcome of a verification-gated phase, not an omission.

### 2.3 T022 - Permanent non-coverage

Copilot and OpenCode are recorded as permanent non-coverage for notifications, with reasons, so a later release does not re-open the question. Both **are** fully covered by Phase 2's end-of-task summary rule, which needs only an instruction surface. That asymmetry is the reason this release has two deliverables instead of one: deliverable 1 is bounded by hook support, deliverable 2 only by having an instruction file.

### 2.4 T023 - DF-1 settled, and a v3.15.9 finding overturned

This is the phase's most consequential result, and it corrects my own work.

During the v3.15.9 release I recorded that "multiple current sources state Cursor exposes no personal/global skills directory" and extended DF-1 to cover the global `~/.cursor/skills/` write on that basis. **First-party documentation disproves it.** `cursor.com/docs/skills` documents four skills read-paths, two of them user-level: `.agents/skills/`, `.cursor/skills/`, `~/.agents/skills/` (global), and `~/.cursor/skills/` (global), plus backward-compatible `.claude/skills/` and `.codex/skills/`. Discovery walks the root recursively.

So the global skills write is correct and load-bearing, and the DF-1 extension is withdrawn. The v3.15.9 text is left in place with a superseded notice rather than rewritten, because a verification log's job is to record what was believed when. The transferable lesson is one the repo already encodes elsewhere: a secondary source is a reason to go read the first-party page, not a finding. I shipped that extension into a release note on secondary evidence, and it was wrong within a day.

The **commands** half resolves differently and independently. Cursor's docs no longer document a commands directory at all; Cursor 2.4 ships a `/migrate-to-skills` skill that converts both user-level and workspace-level commands into skills with `disable-model-invocation: true`; and a community bug report titled "Commands are not detected in the global cursor directory" reports the global path does not work. Because Nexus-Hub already delivers every command as a command-skill through the now-verified skills path, the global `~/.cursor/commands` write is **redundant rather than load-bearing**.

Decision, recorded deliberately as the plan required: **retain the write unchanged.** Writing a directory Cursor ignores is harmless, while removing one it does read would silently drop coverage, and the risk is asymmetric. Flagged for deliberate removal in a later release once someone wants the smaller install surface.

## 5. Deviations

The plan's T021 said to extend "each capable integration". Only Cursor was extended. That is a deliberate narrowing, not a shortfall: the phase's own gating rule is that a trigger ships only on first-party-verified evidence, and applying that rule honestly disqualified Codex and Kimi outright while Qwen and Gemini CLI each need a schema-specific writer that would have outgrown this phase. The alternative, shipping on secondary evidence to hit a task-list line, is the failure this phase was designed to prevent.
