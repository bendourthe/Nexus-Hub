# v3.15.13 - Cursor Live Usage and Monitor Parity

**Project**: Nexus-Hub
**Plan type**: Feature / enhancement, unplanned
**Created**: 2026-08-07
**Base**: the v3.15.12 branch, continued rather than re-cut
**Origin**: phases 6 to 9 of `v3.15.12-cursor-live-transport-and-github-billing-monitor.md`, split out at release time

---

## Why this exists

v3.15.12 concluded that Cursor exposes no personal usage API and rewrote its Definition of Done around that. A maintainer then asked the obvious question - "if we can read the numbers from the usage page, why can't the extension read them the way the Claude and Codex monitors do?" - and the conclusion did not survive it.

The error was inferring the absence of a surface from its absence in the public documentation. That is the same mistake the same version had already corrected once, for GitHub billing authorization (HO-6). Cursor's own client reads personal usage through a unary Connect RPC; the public docs simply do not cover it.

Everything below followed from correcting that: a working transport, then three rounds of making the Cursor monitor look and behave like its siblings, each round driven by a maintainer comparing them side by side.

## Definition of Done (observable)

- The Cursor monitor reports **real** included-usage percentages, billing-cycle bounds, and shared-pool spend, with no manual entry and no credential to manage.
- Its hover, dashboard, inline settings, and warning panel match the Claude and Codex monitors component for component.
- The nonce Content-Security-Policy is intact; matching the siblings introduced no inline handler and no inline style.
- No section claims data the provider does not report.
- The extension installs to Cursor only, never to VS Code.

## Non-goals

- Reading browser cookies, `Login Data`, OS keychains, process memory, or shell history; searching the filesystem for credentials; scraping any HTML billing page. Unchanged, and the README's claim stays literally true.
- Widening the allowlist beyond `cursorAuth/accessToken`. This is what removed the Current Model section rather than implementing it.
- Presenting the undocumented route as a documented API. It is labelled `credential-api` throughout.

## Phase 6: The Real Cursor Usage Route (added mid-version)

**Why this phase exists.** Phases 1-5 shipped, and the monitor still did not work. A maintainer report ("the Cursor Usage monitor is not working at all; 'enter usage manually' makes no sense") produced two findings that this phase acts on.

The first is a correction. Phase 1 concluded that no personal usage surface exists, reasoning from `cursor.com/docs/api` documenting only Enterprise-admin APIs. That inferred absence of a surface from absence in the docs, which is the same absence-of-evidence error this version already corrected once in the GitHub billing auth work (HO-6). Cursor's own client reads personal usage through a unary Connect RPC. The public docs are accurate; they simply do not cover it.

The second is a design objection, and it was right: a manually entered figure is frozen at the moment it is entered, so it goes stale silently and reports a stale number as current. That is the exact failure mode the rest of the extension is built to prevent, so shipping it as the primary path contradicted the product.

**Recommended model tier**: frontier. **Recommended effort level**: max. **Rationale**: a credential-bearing call to an undocumented endpoint, plus a retraction of a published claim. Getting it wrong either breaks a shipped privacy promise or ships a monitor that reports wrong numbers as live.

### What the probe changed about the design

Three payload properties are each a trap, and each is now pinned by a test:

1. **Field names are camelCase**, not the descriptor's snake_case, because Connect applies the proto3 JSON mapping. Building from the descriptor alone reads `undefined` for every field, and the contract guard would have rejected the payload - correct behavior masking an avoidable defect.
2. **Percentages are used exactly as delivered.** On the probed account `(totalSpend / limit) * 100` was 1078.70 against a reported 23.97, because the reported figure uses a base the payload does not expose. Deriving it would render a healthy pool as 1079% and pin every threshold alert on.
3. **Money is minor units; cycle bounds are epoch-millisecond strings.** Spend divides by 100, and a cycle read as seconds dates to 1970.

### Two defects caught inside the phase

- **The production fetch client hardcoded `GET`** while every test passed against a stub that recorded intent. A POST-only Connect endpoint answers a GET with 405, so the suite was green and production would have been broken. Two tests now drive the real client through `global.fetch`.
- **The panel's command guard rejected the new command**, which would have made the primary button silently inert - worse than an absent button, because it looks like the feature is broken. The guard is now exported and asserted against every rendered button.

## Phase 7: Visual Parity With the Sibling Monitors (added mid-version)

### Sub-tasks

- [x] T043 Rebuild the dashboard as a narrow centered column with uppercase section labels
- [x] T044 Replace the warning panel's bare number with a clamped usage ring and center its content
- [x] T045 Add `cursorUsage.showStatusBarLabel`
- [x] T046 Add a visual-parity test file asserting shape rather than copy
- [x] T047 Confirm the extension installs to Cursor only, never to VS Code

### The correctness question inside a presentation phase

The on-demand bar previously measured PERSONAL spend against the SHARED limit. On a live account that rendered $157.32 of $200.00 as a 79% bar, implying a fifth of the budget remained. The pool was in fact fully drawn, with `pooledRemaining` at zero. The bar now tracks the pool, and personal spend is stated beside it, because the pool is what determines whether the next request is billable.

Every Phase 2 rule survives this change and is still asserted: never present the shared pool as a personal cap, never divide it into a per-member figure, drop the bar rather than approximate when a fraction would be meaningless (absent limit, non-positive limit, or a limit in a different currency than the spend), take the reset date from the payload, and clamp an over-limit bar while saying so. The currency-mismatch guard was briefly lost in the rewrite and restored before merge.

### Two defects caught inside the phase

- **Additive fields broke the existing cache.** `parseNullableMoney` accepted `null` but not `undefined`, so a snapshot written by the previous build - which has no such key - failed validation. Every current user's panel would have blanked on upgrade until the next successful fetch. "Absent" and "null" now both mean "not reported". The renderer takes the same care, because a declared `Money | null` type says nothing about data that was persisted before the field existed.
- **An unguarded `activeColorTheme.kind`** threw from inside the tooltip builder on hosts that do not populate it, which presents as a status bar that silently stops updating. The read is now guarded, and the test stub gained the surface so the guard is not the only path exercised.

## Phase 8: Component-Level Parity With the Sibling Monitors (added mid-version)

**Why this phase exists.** Phase 7 matched the visual grammar (pill bars, column, ring) but a maintainer review comparing the three monitors side by side found the components themselves still differed: button styling, a separate settings panel instead of an inline one, different vocabulary for the same concept, and three dashboard sections missing entirely.

**Recommended model tier**: strong. **Recommended effort level**: high. **Rationale**: mostly presentation, with one security-relevant decision (the CSP) and one honesty decision (what "Current Model" can truthfully say for a provider that does not report it).

### Sub-tasks

- [x] T050 Add `getRecommendation` to the Cursor monitor for the Recommendation and Tips sections
- [x] T051 Port the settings form from the Claude monitor as an embeddable module
- [x] T052 Convert the ported inline handlers to delegated listeners for CSP safety
- [x] T053 Rewrite the dashboard to the sibling structure, with the gear toggling the inline form
- [x] T054 Rename to Extra Credits and adopt the two-line organization/personal format
- [x] T055 Restructure the warning panel: centred brand block, advice list, reset box, source footer
- [x] T056 Extend the visual-parity tests to the new components

### Copied, not reimplemented

The settings CSS, `levelSection`, the section markup, and the client script are byte-for-byte copies of the Claude monitor's. This was deliberate: a parallel implementation of "the same form" diverges on the first tweak to either side, and the whole point of the phase is that the two look identical. Only three things were rewritten, because they cannot be shared: the configuration namespace, the metric options (Cursor has two included pools, not a session and a week), and the label text.

### The one place parity was deliberately NOT followed

The sibling dashboards use inline `onclick=` handlers and inline `style="width:..."`. Both require a webview without a strict Content-Security-Policy. This webview runs under a nonce CSP that forbids inline handlers and inline styles, so the verbatim copy would have produced a settings form that rendered perfectly and did nothing at all - every control dead, with no error visible to the user. The handlers are bound by data attribute instead and the bar widths come from generated classes. The visuals are identical; the security posture is not weakened to match.

A pre-existing test (`uses nonce-only local CSP and event listeners`) caught this immediately, which is the argument for keeping such a test even when it looks like a formality.

### What "Current Model" can honestly say

The sibling monitors name the model in use. Cursor's usage API reports per-pool figures and does not expose the editor's selected model, so naming one would be an invention. The section states which pool is under most pressure and says plainly in its subtitle that Cursor's API reports pools rather than the active model. Wiring the real model would require reading it from somewhere outside the allowlisted key, which the authentication boundary excludes.

## Phase 9: Interaction Fixes From Maintainer Review (added mid-version)

**Why this phase exists.** A maintainer used the three monitors side by side and reported five concrete defects. Four were presentation; one was a bug report whose stated symptom pointed at the wrong layer.

### Sub-tasks

- [x] T060 Give only the primary action a filled background; drop Update Figures and Clear Data from the dashboard
- [x] T061 Return the side bar to the Explorer when the warning is dismissed
- [x] T062 Widen the hover bars to span the tooltip
- [x] T063 Remove the Current Model section rather than invent a value

- [x] T065 Correct the README release summary, which still stated a retracted claim

### The bug that was not where it looked

The report was that the Compact status bar toggle "went back to untoggled on its own" after saving. That symptom has two possible causes with opposite fixes: the value never persisted, or it persisted and the UI discarded the displayed state.

A round-trip test written **before** touching the save path settled it: persistence was correct in every case. Had the persistence layer been "fixed" on the strength of the symptom, working code would have changed and both real defects would have survived.

Those defects were:

1. **The form collapsed on every re-render.** Any configuration change rebuilds the entire webview, and the settings section's `hidden` default reasserted itself - so saving made the panel being edited disappear. It now restores its open state through the webview's own state.
2. **Eight writes per save.** `saveSettings` wrote all eight keys unconditionally. Each write fires `onDidChangeConfiguration`, and the dashboard rebuilds on that event, so a single toggle produced eight writes and eight rebuilds. That is the "unresponsive for a few seconds" half of the report. Only changed keys are written now.

### Why Current Model was removed rather than implemented

Cursor's usage API reports per-pool figures and never exposes the editor's selected model. The state database holds `cursor/initialModelState`, not the current one. Surfacing the real model would require widening the allowlist beyond `cursorAuth/accessToken` and changing `CONSENT_SCOPE`, which invalidates every existing grant by design. Reading further into a credential store to populate a cosmetic section is precisely the trade the authentication boundary exists to prevent, so the section is gone. Restoring it is a scope decision, not a UI tweak.

### The README correction

The release summary still read "The headline Cursor goal was withdrawn, with evidence... That is not achievable". Phase 6 falsified that and shipped the feature. The most user-visible document in the repository was therefore telling users the opposite of what the release does, and it is rewritten with the retraction stated rather than quietly edited away.
