**Goal**: Adopt the full set of candidates the codex-lb comparison surfaced, in reverse-engineer-first order, with the directly-requested Codex Usage Monitor as the first concrete build. Every catalog-content item is `skill-native` by default (the agent's own model does any LLM work) with no new outbound call, dependency, or credential; the one product build (the usage monitor) makes a single authenticated call to the user's OWN ChatGPT account endpoint and reuses the existing extension entirely. Everything passes `make validate` / `make lint` / `make test`, is recorded in the CHANGELOG, and reaches every supported platform through the installer where it is catalog content. The persona is downstream Nexus-Hub users on the ChatGPT Codex app plus AI coding agents consuming the catalog.

## Overview

The v3.13.0 comparison of Nexus-Hub against codex-lb (`https://github.com/Soju06/codex-lb`) found the two projects are different product categories (a ChatGPT-account load balancer / proxy vs a skill catalog), so the value concentrated in how codex-lb is built with agents and in one directly-requested product extraction. This release adopts all seven selected candidates: the Codex Usage Monitor (U1), a declarative skill-activation ruleset with a guard (C1), a review-trapdoors convention (C4), a merge-gate contract convention (C6), a spec/context split with a spec-as-merge-gate rule (C5), a concretized cross-model review recipe (C2), and a PR/CI evidence-discipline example (C3).

The flagship, front-loaded build is U1. codex-lb revealed that account-level Codex usage and quota come from an authenticated upstream endpoint (`{base}/backend-api/wham/usage`, evidenced in `app/core/clients/usage.py`), not from proxy interception, so a Codex Usage Monitor needs none of codex-lb's proxy, database, or dashboard. Per the user decision, it ships as a unified multi-provider evolution of the existing `extensions/claude-usage-monitor`: the data layer is generalized behind a provider interface, Codex is added as a second provider (a local credential read plus a single `wham/usage` fetch), and the entire status-bar / SVG-tooltip / dashboard / threshold-warning UI is reused unchanged. This is tier-3 reverse-engineering per the MCP Registry Policy: the endpoint knowledge and payload semantics are extracted into a local fetcher with generic naming and no external-source attribution, and the one outbound call goes only to the user's own OpenAI account.

The remaining six are agentic-development disciplines. Three are skill-native review/verification refinements that compose (C4 a curated recurring-blocker doc convention, C3 a PR/CI-state evidence example folded into `verification-before-completion`, C6 a bound merge-readiness contract that reuses C3's discipline). One is a spec-driven convention (C5: normative `spec.md` vs free-form `context.md`, plus a spec-as-merge-gate rule) adopted as a convention only, never the external `openspec` CLI. One is the standout agentic build (C1: a `skill-rules.json`-style declarative activation ruleset plus opt-in activation and guard hooks that add a deterministic backstop to Nexus-Hub's model-judgment triggering, inverted from codex-lb's fail-closed posture to fail-open / suggest-by-default). The last concretizes Nexus-Hub's already-strong cross-model story into a runnable, model-agnostic loop-until-clean recipe with safety limits (C2).

The design principle is minimum-new-surface and no-new-vendor: U1 reuses the existing extension rather than forking; C3 and C5 and C2 extend existing skills rather than minting new ones; C4 and C6 prefer a convention doc plus a light skill or an extension of `quality-gate-definitions`; C1's LLM-adjacent behavior stays on the session's own model. Two source patterns are deliberately reframed and not adopted as written: the external `openspec` CLI (C5 adopts the convention, not the tool) and the Codex-CLI-locked review loop (C2 stays model-agnostic). One product candidate (P1, codex-lb's provider failover/settlement invariants as reference content for `multi-provider-ai`) is out of the selected scope and deferred to the v3.14 known-gaps ledger as an optional follow-up.

Success is demonstrated end-to-end: the usage monitor builds, reads a Codex token, fetches and renders live Codex usage in the same format as the Claude monitor (with a fail-soft path when the undocumented endpoint is unavailable), and its provider tests pass; the new and edited catalog skills are registered in all three metadata files and pass `make validate`; the C1 hooks are fail-open, opt-in, cross-platform-parity-clean, and pytest-covered; and `make validate`, `make lint`, and `make test` are green with a throwaway dry-run install confirming every catalog artifact lands at its platform target.

## Phase 4: Declarative skill-activation ruleset + guard/tracker hooks (C1)

**Goal**: Adopt the flagship agentic capability: a declarative, file-path- and prompt-keyword-triggered skill-activation ruleset plus hooks that add a DETERMINISTIC backstop to Nexus-Hub's model-judgment triggering, inverted from codex-lb's fail-closed blocking posture to fail-open / suggest-by-default, opt-in per Nexus-Hub's hook philosophy.
**Prerequisites**: None, but sequenced after the skill-native phases per the reverse-engineer-first ordering (it is a `re-full` local-artifact build).
**Stability Gate**: a `skill-rules.json` schema/template exists and is documented; `catalog/hooks/skill-activation-suggest.py` (UserPromptSubmit; suggests the highest-relevance catalog skill from prompt keywords / intent patterns) and `catalog/hooks/skill-guard.py` (PreToolUse Edit/Write; suggests by default and blocks ONLY when an explicit env flag opts into blocking) exist, are fail-open (exit 0 on any internal error), and honor `NEXUS_DISABLED_HOOKS` / `NEXUS_HOOK_PROFILE=minimal`; an optional usage tracker records which skills ran so activation does not re-nag; a pytest suite passes under `make test`; the hooks are registered in `catalog/hooks/settings.json` behind opt-in (ask-first edit); cross-platform parity is satisfied (`.ps1` siblings or a documented cross-platform interpreter strategy); `make lint` (ShellCheck where applicable) is green.
**Recommended model**: Strong tier (Opus-class), high effort - a guard that can gate edits has a larger blast radius than advisory hooks; the fail-open inversion, the ask-first `settings.json` edit, and cross-platform parity all must be right.

### Sub-tasks

#### 4.1 - Design the skill-rules schema and template
