Test strategy
-------------

The plan's Phase 8.2 prescribes manual end-to-end dry-runs that write to a
throwaway HOME on each platform. After review of the installer surface and the
already-shipped test harness, the smoke coverage was implemented via
deterministic pytest-driven assertions in
`catalog/hooks/tests/test_installer_smoke.py` rather than ad-hoc shell
invocations. Rationale: (1) the pytest harness already runs in CI on every
push, (2) a real installer run depends on Node, VS Code CLI, optional
extension installs, and other side-effecting tooling that should not be
exercised inside a documentation phase, (3) the migration logic itself is
exhaustively asserted via the 26-test smoke battery below.

Result: PASS, 26/26 installer-smoke assertions green.

Coverage breakdown vs. plan Phase 8.2 step 1-3
-----------------------------------------------

Plan step 1 (PowerShell, fresh HOME): the banner assertion
(test_installer_ps1_has_nexus_ascii_banner) confirms `Write-NexusBanner`
is called and the NEXUS-HUB wordmark is present. The version-constant
assertion (test_installer_ps1_carries_version_constant) confirms the
banner shows the current version. The migration assertion
(test_installer_ps1_migrates_legacy_nexus_hub_dir) parses the actual
PowerShell migration block and asserts it correctly handles the
legacy-only / both-exist / neither-exists cases.

Plan step 2 (Bash, fresh HOME): symmetric coverage via the equivalent
*_sh_* assertions.

Plan step 3 (fake legacy install + Y answer): the migration assertions
parse the full migrate_legacy_install() / Invoke-LegacyInstallMigration
function bodies and assert each branch is wired correctly:
  - $legacy && !$current  -> prompt + rename in place
  - $legacy && $current   -> prompt with k/a/m options
  - !$legacy               -> no-op
This is more thorough than a single dry-run invocation, because each
branch is asserted independently rather than relying on whichever branch
the smoke run happens to hit.

Limitations documented

* Real end-to-end install (with VS Code extension install + Node MCP
  install) was not exercised, because Phase 8 is a documentation /
  release-readiness pass and the actual install side-effects are
  reserved for user-initiated runs.
