# DevAI-Hub — Design Document

This document explains the architectural decisions behind DevAI-Hub: what was chosen, what was rejected, and why. It is written for contributors who want to understand the project deeply before proposing changes.

---

## What is DevAI-Hub?

DevAI-Hub is a modular behavioral library for AI coding assistants. It gives AI tools (Claude Code, Gemini, GitHub Copilot, Codex) structured skills, workflows, and behavioral rules that make them act more like experienced engineers on a specific project.

It is **not** an API documentation registry, a fine-tuning dataset, or a prompt marketplace. The core value proposition is behavioral: teaching an AI *how to approach* a class of tasks, not just *what APIs to call*.

---

## Architecture Overview

```
DevAI-Hub (this repo)
├── catalog/          ← source of truth for all content
│   ├── skills/       ← 134 skill directories (SKILL.md + agents/)
│   ├── commands/     ← 21 slash command definitions
│   └── hooks/        ← 10 runtime shell scripts
├── templates/        ← AI instruction templates (base + language-specific)
├── scripts/          ← Cross-platform installers + report generator
├── extensions/       ← VS Code extension (Claude Usage Monitor)
└── *.json            ← Pre-built catalogs (skills.json, workflows.json, bundles.json)

                      Installer
                    ↙           ↘
  ~/.claude/              <project>/
  ├── skills/             ├── .claude/skills/
  ├── commands/           ├── CLAUDE.md
  └── hooks/              ├── AGENTS.md
                          ├── .github/copilot-instructions.md
                          └── .gemini/GEMINI.md
```

The installer is a one-time setup step. After installation, all content lives on the user's local filesystem and is loaded by the AI tool's native skill discovery mechanism. There is no runtime service, no network dependency, and no daemon.

## Key Design Decisions

### Why skills are Markdown files, not a database or API

Skills are plain Markdown with YAML frontmatter. This was a deliberate choice over structured JSON schemas, DSLs, or a centralized API.

**Reasoning:**
- AI tools natively read Markdown. Skills are injected directly into the context window; a JSON schema would require a rendering step.
- Markdown is human-readable and editable without tooling. Contributors can write and test a skill in a text editor.
- Version control diffs are meaningful. A changed skill shows exactly what the AI is now being told to do differently.
- Skills need to express narrative reasoning, not just structured data. Markdown supports this; JSON does not.

**What was rejected:** A JSON schema for skills (like an OpenAPI spec for behavior). Rejected because it would constrain expressive power and add a compilation step without clear benefit.

### Why YAML frontmatter for skill metadata

Skill metadata (name, description, agents) uses YAML frontmatter rather than a separate sidecar file or inline comments.

**Reasoning:**
- YAML frontmatter is the standard for static site generators, documentation tools, and the Agent Skills specification. Contributors already know it.
- It keeps metadata co-located with content. A renamed skill does not require updating a separate registry file.
- The `build_skills_catalog.py` script parses frontmatter to generate `skills.json` automatically on commit.

### Why a pre-built skills.json catalog

`skills.json` (177KB) is generated by a pre-commit hook and committed to the repository, rather than generated at install time or served from a remote endpoint.

**Reasoning:**
- Installers do not need Python or any runtime to read the catalog. The PS1 and Bash installers parse `skills.json` for bundle selection without a separate build step.
- Offline and air-gapped environments work without modification.
- The catalog is always consistent with the committed skill content — the pre-commit hook ensures they stay in sync.

**What was rejected:** Generating `skills.json` during installation. Rejected because it requires Python to be available on the installer's machine (not guaranteed on all Windows environments).

### Why local-first distribution (PS1/Bash installers, not npm/pip)

DevAI-Hub is distributed as PowerShell and Bash scripts rather than an npm package or pip package.

**Reasoning:**
- The primary installation target is developer machines, many in enterprise environments with restricted software installation policies. A zero-runtime-dependency installer (PS1/Bash) has the broadest compatibility.
- Skills are Markdown files. There is no compilation, transpilation, or module resolution — no need for a package manager.
- The installer's main job is file copy + path configuration, which shell scripts handle natively.
- npm and pip would require Node.js or Python to be installed, creating a dependency chain that does not exist for the majority of the installed content.

**What was rejected:** npm package distribution. Rejected because it would require Node.js 18+ on every target machine, while many enterprise developers only have Python (or neither). A pip distribution was considered for the report generator only (appropriate, since that component *does* require Python).

### Why separate base templates for each AI platform

DevAI-Hub ships three base instruction templates: `base-claude.md`, `base-gemini.md`, and `base-codex.md`. These are not copies of each other — they are written for each platform's distinct instruction model.

**Reasoning:**
- Claude Code's CLAUDE.md is read by Claude at session start and supports rich context (skills, memory, hooks).
- Gemini's GEMINI.md is read by Gemini CLI, which has different conventions for tool use and memory.
- Codex/AGENTS.md is the open standard for Jules, Cursor, Aider, and other agent platforms — it is intentionally minimal and tool-agnostic.
- GitHub Copilot's `copilot-instructions.md` is a natural-language instruction file with no support for skills or hooks; it requires language-specific snippets rather than universal rules.

A single template for all platforms would either be too generic to be useful on any platform, or too platform-specific to install on others.

### Why {{PLACEHOLDER}} template rendering instead of a full template engine

The installer renders `base-claude.md` by replacing `{{PLACEHOLDER}}` tokens (e.g., `{{PROJECT_NAME}}`, `{{LANGUAGE}}`) with values it detects from the target project.

**Reasoning:**
- Jinja2, Mustache, and similar engines require a Python/Node runtime and introduce additional dependencies.
- The template variables are simple scalar substitutions — there is no conditional logic, loops, or inheritance in the templates.
- `{{PLACEHOLDER}}` syntax is readable as-is in an unrendered template, unlike `{% if ... %}` blocks.
- The installer already has string replacement capabilities in PowerShell (`-replace`) and Bash (`sed`).

### Why the hook architecture uses PreToolUse / PostToolUse / Stop

Claude Code's hook system allows shell scripts to run before and after tool calls, and when a session ends. DevAI-Hub's 10 hooks are organized around these three event types.

**Reasoning for PreToolUse hooks:**
- `secret-scan.sh` and `large-file-guard.sh` run before Write/Edit because they are gatekeepers — they need to prevent bad writes, not clean them up afterward.
- `git-guardrails.sh` runs before Bash because it needs to intercept destructive git commands before they execute.

**Reasoning for PostToolUse hooks:**
- `auto-format-on-write.sh` and `lint-on-write.sh` run after Write/Edit because formatting and linting are transformations on completed writes, not preconditions.

**Reasoning for Stop hooks:**
- `usage-display.sh` shows usage limits at session end, where it provides useful planning information without interrupting the work session.
- `session-summary.sh` and `notify-on-complete.sh` are summary/notification actions that only make sense after all work is done.

### Why bundles and workflows are separate from skills.json

`bundles.json` and `workflows.json` are separate files from `skills.json` rather than embedded sections.

**Reasoning:**
- Skills, bundles, and workflows have different schemas and different consumers. `skills.json` is consumed by the installer and the search command; `workflows.json` is consumed by the workflow orchestrator skill and human readers; `bundles.json` is consumed by the installer's bundle selection UI.
- Keeping them separate allows each file to be validated and updated independently.
- The installer can parse only the file it needs without loading the full 177KB `skills.json`.

### Why 17 skill categories

The 17 categories were derived empirically from the skill content, not designed top-down. The governing principle is: a category should correspond to a developer role or a coherent phase of the software development lifecycle.

Categories were split when a single category grew beyond ~15 skills (e.g., "Developer Experience" was carved out of a general "Development" category). They were merged when two categories had fewer than 3 skills each.

**Notable decisions:**
- "Framework Specialists" and "Language Specialists" are separate from "Developer Experience" because specialist skills have different trigger patterns — they activate when a specific technology is in context, not a general development task.
- "Orchestration" is a standalone category for multi-agent and context management skills, which have no natural home in any development phase category.
- "Compliance" is standalone (not part of "Security") because compliance skills (SOC2, GDPR, ISO) are audit-oriented and address a different audience than code security skills.

### Why the VS Code extension is separate from the hooks

Usage monitoring is provided in three ways: a Stop hook (`usage-display.sh`), a VS Code extension, and a slash command (`/check-usage`). The extension is separate from the hook rather than replacing it.

**Reasoning:**
- The Stop hook works in any terminal environment where Claude Code runs, regardless of whether VS Code is open.
- The extension provides persistent, ambient monitoring in the VS Code status bar — visible between sessions.
- The slash command provides on-demand detail with model-switching recommendations, invocable during a session.

These three mechanisms complement each other rather than overlapping. A user who always works in VS Code benefits most from the extension; a user who works in a terminal benefits most from the hook.

### Why the report generator uses Python + python-docx

`scripts/generate_report.py` generates Word (.docx) and PowerPoint (.pptx) documents from Markdown. It uses Python with the `python-docx` and `python-pptx` libraries.

**Reasoning:**
- The `.docx` and `.pptx` formats are standard in enterprise environments where stakeholder-facing reports must integrate with existing document workflows.
- `python-docx` and `python-pptx` are well-maintained libraries with strong support for the OOXML format.
- Python is already a dependency for the pre-commit hooks (`tools/build_skills_catalog.py`), so introducing it for the report generator does not add a new dependency tier.
- The report generator is entirely optional — users who do not generate reports never need to install it.

**What was rejected:** Pandoc. Rejected because Pandoc's .docx output ignores custom styles and templates, making it difficult to match organization branding. The Python approach supports full template application (logo, fonts, heading styles) from a `.docx` template file.

## Content Model

### Skill lifecycle

```
Author writes SKILL.md
  → pre-commit: build_skills_catalog.py updates skills.json
  → Installer reads skills.json for bundle selection
  → Installer copies SKILL.md to ~/.claude/skills/<category>/<skill>/
  → Claude Code auto-discovers skill at session start
  → Skill description appears in Claude's context
  → Skill triggers when description matches user request
```

### Command lifecycle

```
Author writes catalog/commands/<name>.md
  → Installer copies to ~/.claude/commands/<name>.md (global)
  →                   .claude/commands/<name>.md (project)
  → Claude Code discovers command as /name
  → User invokes /name
  → Claude executes the command prompt
```

### Hook lifecycle

```
Author writes catalog/hooks/<hook>.sh
  → Installer copies to ~/.claude/hooks/<hook>.sh
  → Installer writes hooks/settings.json referencing the hook
  → Claude Code reads settings.json and registers the hook
  → Hook fires on matching tool call event
```

## What This Project Is Not

**Not a prompt injection vector.** Skills and hooks run with the user's explicit consent — the installer requires interactive confirmation, and hooks are only active in Claude Code sessions the user starts.

**Not a training data set.** Skills are behavioral instructions for inference-time use, not examples for fine-tuning.

**Not an API documentation registry.** For versioned API docs (Stripe, OpenAI, etc.), see [Context Hub](https://github.com/andrewyng/context-hub), which is architecturally complementary to DevAI-Hub.

**Not a replacement for project-specific CLAUDE.md.** The installer generates a project-level CLAUDE.md that the developer customizes. DevAI-Hub provides the skills and templates; the developer provides the project context.

## Future Directions

The following capabilities are under consideration but not yet designed or committed:

- **MCP server** — Expose the skills catalog via the Model Context Protocol, enabling IDE-level skill search and on-demand fetch without reinstallation.
- **Feedback/annotations** — Allow agents to rate skill quality and attach persistent notes (local, per-machine) that surface on next invocation.
- **Community skill contributions** — A namespace scheme (`author/skill-name`) and validation pipeline for third-party skills contributed outside the core catalog.

These are tracked in the adoption backlog from the [context-hub comparison](comparison-context-hub.md).
