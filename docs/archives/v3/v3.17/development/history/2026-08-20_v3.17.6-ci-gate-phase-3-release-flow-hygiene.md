## Goal

`/update release` catches the operational failures the v3.17.5 release hit by hand.

## A Design Question The Plan Left Open

Sub-task 3.1 says to extend `catalog/commands/update.md`, which is prose. Sub-task 3.3 says to write tests for the pre-tag assertion. Prose is not testable, and the repository's own test-retention policy in `AGENTS.md` explicitly rejects tests whose purpose is asserting document text.

`update.md` already delegates to nine scripts, so the established pattern resolved it: command prose plus a script that carries the logic. `scripts/check_release_preconditions.py` is that script.

It is **distributed** (copied by both installers) rather than repo-internal, which required an installer edit and therefore explicit approval, since `AGENTS.md` lists installer modification under "Ask first". The reasoning: `/update release` ships to users, so a command describing a safety check absent from their install is prose promising something that is not there. `check_version_sync.py` and `generate_release_changelog.py` set the precedent.

## What Shipped

Three checks, each answering a specific failure.

**`--pre-tag`** (blocking, exit 1). Asserts HEAD is on the expected release branch AND equal to `origin/<release-branch>`. Its placement is the entire point: in the v3.17.5 release a `git checkout main` failed on a OneDrive-locked directory, HEAD stayed elsewhere, and the tag was created there and published, shipping an unreleased plan file in the tarball. A check anywhere earlier cannot catch that, because a checkout that failed silently is exactly the state being guarded, so the assertion reads live git state at the last possible moment and caches nothing. The expected branch is configurable, because a gate that blocks a legitimate release from a differently-named branch is a gate people learn to bypass, which is how this whole version's defect class began.

**`--branches`** (advisory). Reports cleanup candidates and deletes nothing.

**`--repo-settings`** (advisory). Reports `delete_branch_on_merge` with the exact `gh` command to enable it, and reports repository-description drift.

Also added to `update.md`: the post-release back-merge step, because a PR-based release leaves a merge commit on `main` that `develop` lacks, and under `strict` protection that blocks the NEXT release PR.

## Two Places The Plan Was Wrong, Found By Running It

**The branch-hygiene mechanism detects nothing here.** Sub-task 3.2 specifies `git branch -r --merged`. Implemented exactly as written it reported zero candidates while ten stale branches sat on the remote. The reason is that `delete_branch_on_merge` is already enabled, so GitHub auto-deletes a branch the moment its PR merges, making "merged but undeleted" structurally almost always empty. The plan's premise ("39 branches had accumulated") came from the v3.17.5 session, when the setting was OFF; enabling it during that session invalidated the mechanism the plan then specified.

What actually accumulates is branches whose PR was **closed unmerged**. GitHub does nothing for those, and `--merged` cannot see them because they are by definition not merged. On this repository that is the four `test/ci-proof-*` refs Phase 2 created, three abandoned feature branches, and three dependabot refs. The reporter now covers both categories: the merged list is kept, because it is still correct and still the right check for a repository without the setting, and a second closed-unmerged category was added. This exceeds the sub-task's wording and serves its stated objective, which the specified mechanism did not.

**A file glob is the wrong source for catalog counts.** The description-drift check first derived counts by globbing `catalog/commands/*.md` and `catalog/hooks/*.{sh,py}`, giving 21 commands and 34 hooks against a declared 18 and 31: the glob counts permanent aliases as commands and helpers as hooks. That is not an off-by-three, it is a category error, because a drift report exists to tell someone what to write and a confidently wrong number is the number they paste.

Only the skills count has a machine-readable source (`data/skills.json`, one entry per skill). Commands and hooks now come from the figures `README.md` declares, so the comparison is between two hand-maintained surfaces, which is the real drift class. A separate check catches the declaration itself going stale, with a test asserting it holds on the live repository.

With that corrected, the check reports exactly what the plan predicted: the description reads "256 curated skills, 15 commands, 22 hooks" against a declared 273 / 18 / 31.

## Test Results

27 tests in `tests/validators/test_check_release_preconditions.py`, built on real git repositories with a real bare-repo remote, because the failure mode is a git state rather than a function argument. Faking `origin/<branch>` would have tested the mock.

Both directions are asserted throughout. The pre-tag cases cover HEAD on the release branch and synced (pass), HEAD on another branch (abort), detached HEAD (abort), HEAD ahead of origin (abort), HEAD behind origin (abort), a non-default release branch (pass, and the default correctly rejected in that configuration), a missing remote ref (abort), CLI exit codes, and a non-git directory (exit 2, distinct from a failed precondition).

The branch reporter is asserted never to propose a protected branch or one with an open PR, and to leave the branch set byte-identical after running.

Verification of the installer change: `check_installer_parity.py` passes; `test_installer_smoke.py` passes 33 tests including the assertion that every non-`DEV_ONLY_SCRIPTS` script appears in BOTH installers; `installer.ps1` AST-parses; line endings confirmed unchanged (`installer.sh` all LF, `installer.ps1` all CRLF, 13 lines added and none removed in each).

## Deviations

- Implemented as a script plus prose rather than prose alone, to satisfy 3.3.
- The branch reporter covers a second category the plan did not specify, because the specified one is empty here.
- Catalog counts come from the README declaration rather than a file count.
- The repository description was NOT edited. The check reports the drift; changing project metadata is an outward-facing act that belongs to the operator (`NI-2`).
