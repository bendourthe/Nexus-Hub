## Goal

A guard that fails when a required status check is produced only by a conditionally-triggered workflow, so the defect behind seven administrator bypasses in one release day cannot silently return.

## The Mechanism Being Guarded

GitHub treats a missing check and a skipped check as opposites, which is the whole reason the defect is invisible:

- An **untriggered workflow** reports nothing, and "nothing" reads as **Pending** forever. A PR requiring that context can never merge.
- A **skipped job** reports **Success**.

So workflow-level `paths:` and a job-level `if:` look like the same Actions-minute optimization and behave in opposite ways. Source: [GitHub Docs, Troubleshooting required status checks](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/defining-the-mergeability-of-pull-requests/troubleshooting-required-status-checks), fetched 2026-08-19.

## What Was Built

| Artifact | Role |
|---|---|
| `scripts/check_required_check_coverage.py` | The guard. Parses `.github/workflows/*.yml`, resolves each declared context to its job, and fails when that job's workflow is path- or branch-filtered for the protected branch. |
| `docs/policy/required-checks.json` | The declared manifest, seeded from live protection on `main` and `develop`. Local-first: no outbound call at validate time. |
| `tests/validators/test_check_required_check_coverage.py` | 30 tests, both directions. |
| `Makefile`, `.github/workflows/ci.yml` | Wired into `make validate` and into CI's **existing** `validate` job. |
| `catalog/hooks/tests/test_installer_smoke.py`, `AGENTS.md` | Registered as a repo-only guard needing no installer copy step. |

Three failure classes are reported separately because the remedies differ: `UNPRODUCED` (no workflow defines the job, so a rename silently dropped a gate), `CONDITIONAL` (produced, but by a filtered workflow), and `BAD` (unparseable workflow or malformed manifest). All failures are collected before one exit.

A job-level `if:` is never inspected, deliberately. Flagging it would push authors back toward the workflow-level filter that causes the defect, so a false positive there would be worse than a missed warning. That case has its own test.

## Measured Result On This Tree

The guard exits 1, reporting **18 `CONDITIONAL` contexts** (9 per protected branch) across **7 distinct jobs**: `validate`, `shellcheck`, `bootstrap`, `tests`, `install-smoke`, `installer-smoke` (all `ci.yml`), and `colocation` (`doc-colocation.yml`). Zero `UNPRODUCED`, zero `BAD`.

Two things worth noting about that number:

- It reconciles the plan's "seven offending checks" with the API's ten contexts. `installer-smoke` contributes three matrix legs from one job definition, so nine flagged contexts collapse to six `ci.yml` jobs plus `colocation`.
- `verify` (from `presentify-extractor.yml`) is **absent** from the failures. The guard was written from GitHub's documentation, not from that file, and it independently singled out the same workflow the plan identified as already correct. That is the migration target for Phase 2.

## Decisions Taken

**Branch isolation over literal compliance.** Sub-task 1.1 says to wire the guard into `make validate`, and also that it must exit 1 today. Together those turn the required `validate` context red. Landing Phase 1 alone on `develop` would therefore require an administrator bypass for every unrelated merge until Phase 2 lands, which is the exact habit this plan exists to end. The work sits on a feature branch so Phase 1 and Phase 2 reach `develop` together. The alternative of shipping the guard advisory-only (exit 0 with a warning) was rejected: sub-task 1.1 names fail-open behavior as the failure mode to avoid, and v3.17.5 shipped a fail-open validator and patched it the same day.

**Guard in the existing `validate` job, not a new job.** A new job would need its own required context, which is self-referential given what is being fixed. The guard is a sub-second YAML parse with no new dependency.

**Branch filtering is judged per protected branch, not flagged outright.** `branches: [main, develop]` on a `pull_request` trigger is idiomatic and correct, so the guard fails a branch filter only when it excludes the branch being checked. Wildcard and `!`-negated patterns are honoured, each with a test.

## Two Fail-Open Traps Found And Closed

**PyYAML resolves the key `on:` to boolean `True`.** YAML 1.1 treats `on` / `off` / `yes` / `no` as booleans, and GitHub's schema uses one of those words for its most important key. A guard looking up only `cfg["on"]` finds no triggers in *every* workflow, concludes nothing is filtered, and passes cheerfully. `ON_KEYS` accepts both spellings, with a comment explaining why the boolean is there.

**A missing PyYAML must abort, not pass.** `require_yaml()` raises with a `pip install` hint. The test blocks the import via a `sitecustomize` meta-path hook on an isolated `PYTHONPATH`, and a negative control confirmed the same stripped invocation exits 0 when the blocker is absent, so the test fails for the right reason.

## Work Beyond The Prompt

Two things were fixed rather than logged, because both were small and in-scope:

- **`--sync` covered only `main` and `develop`** while the manifest is generic over branches, so a repository with a differently-named protected branch got silence. It now derives the branch list from the manifest and falls back to the default pair when the manifest is unreadable.
- **`--sync` had no test at all**, leaving the plan's "print, never write" requirement unasserted. Three tests now cover it, including one that asserts only `gh api` is ever invoked and never a protection write.
