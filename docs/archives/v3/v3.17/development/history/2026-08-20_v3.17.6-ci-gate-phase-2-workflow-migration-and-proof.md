**Date**: 2026-08-20
**Plan**: [docs/releases/v3/v3.17/plans/v3.17.6-ci-gate-and-branch-hygiene.md](../../plans/v3.17.6-ci-gate-and-branch-hygiene.md)

**Status**: Complete. The plan's Definition of Done item 2 is satisfied by measurement: a docs-only PR and a code-only PR each reached `CLEAN` with zero administrator bypass.

## Goal

Every required status check produced by an unconditionally-triggered workflow, proven by two real PRs merging with no bypass rather than by a green validator.

## What Shipped

`ci.yml` lost its trigger-level `paths:` filters. A cheap `changes` job now classifies the diff into one boolean and gates `bootstrap`, `tests`, `install-smoke`, and `installer-smoke`; the relevance term is ANDed into the existing non-PR gate on `bootstrap-windows` and `tests-windows`. Every re-inclusion justification from the old filter is preserved verbatim, because those paths (`docs/policy`, `docs/*/*/development/*.md`, `docs/incidents`, `docs/decisions`) are validator input, not prose.

`validate` and `shellcheck` stay ungated. Both are cheap, and `validate` runs the guards that read those docs paths, so running it always is simpler to reason about and strictly more signal than the old filter gave.

`doc-colocation.yml` lost its filters with no detector job at all. The check measures 0.1 billed min and a detector costs 0.2, so gating it would have spent minutes to save none. A deliberate deviation from the plan's changes-job prescription, which was written for `ci.yml`.

Then sub-task 2.2 found that none of this was sufficient, and a second PR replaced nine per-job required contexts with one `ci-required` aggregate.

## The Defect Sub-task 2.2 Existed To Find

The plan insisted the proof PRs were "the acceptance test; nothing else settles it," and it was right.

The first docs-only proof PR (#57) reached **BLOCKED**, not CLEAN. **GitHub evaluates a job-level `if:` before matrix expansion**, so a skipped matrix job publishes exactly one check run named after the bare job. The raw check-run API listed `installer-smoke` and never `installer-smoke (ubuntu-latest)` or its two siblings. Five of the ten required contexts never came into existence and sat Pending forever.

`tests` skipped cleanly because it has no matrix: its check name IS its required context. That contrast between `tests` (satisfied) and `installer-smoke` (never reported) isolates matrix expansion as the mechanism, with no guesswork.

Phase 1's guard could not have caught this. It resolves a `job (leg)` context to its bare job id and asks whether that job's workflow is filtered, which it answered correctly. Nobody was asking whether the context NAME survives a skip. That is precisely the limitation Phase 1 recorded as `MT-1` and dismissed as narrow.

**Fix**: one `ci-required` job, `if: always()`, depending on all nine other jobs. Required set collapsed from ten contexts to five: `validate`, `shellcheck`, `ci-required`, `colocation`, `verify`. Matrix jobs may now skip freely and per-leg names stop being load-bearing, which also retires the fragility the plan's Phase 5 consequences list flagged as the price of the migration.

The rejected alternative was un-gating the three matrix jobs so they always publish their leg names. Correct, but roughly 6.3 billed min on every docs-only PR (the 10x macOS leg dominates) against 1.38 measured for the aggregate.

## Fail-Closed, In Two Places

Moving path logic off the trigger inverted the consequence of a mistake. Under a trigger filter, a misclassification left the check Pending: loud, unmergeable. Now it skips a job, and a skipped job reports Success: silent.

The `changes` classifier defaults to `relevant=true`, is only ever narrowed by a complete successful classification, and cannot exit non-zero. Every gate is `!cancelled() && needs.changes.outputs.relevant != 'false'`, and both halves are load-bearing: GitHub skips a job whose dependency failed, so `needs:` alone would have created a NEW silent hole.

`ci-required` uses an ALLOWLIST verdict (`success` or `skipped` pass, everything else fails) rather than a denylist on `failure`/`cancelled`, so a GitHub result value that does not exist yet fails closed. An empty result set fails rather than passing vacuously. The logic is pure bash over per-job env vars, with no `jq` or `python3`, specifically so it stays testable off-CI; the canonical `contains(needs.*.result, 'failure')` one-liner was rejected because it can only express a denylist.

## What The Rehearsal Found

Two dispatched runs on the branch, before anything touched `develop`, surfaced two defects local testing had missed.

`tests/workflows/test_workflow_policy_repo_wide.py` asserted the antipattern as policy: every workflow except `ci.yml` must declare a `paths:` filter. A cost rule had grown into a correctness prohibition. The file already carried the right concept in `IN_WORKFLOW_PATH_FILTER_EXCEPTIONS`, hardcoded to one workflow; the set is now DERIVED from `docs/policy/required-checks.json`, so declaring a new required check automatically forbids a filter on its producing workflow.

`tests-windows` installed only `pytest` while running `tests/validators`, so a PyYAML-importing test broke collection and stopped every other validator test on Windows. That error had also been masking the fact that neither new suite had ever executed on Windows.

Both were only reachable in CI: the local run had covered `tests/validators` and `catalog/hooks/tests`, while CI's `tests` job runs eight separate trees and `tests/workflows` was not among the two.

## Branch Protection

`main` and `develop` now require five contexts instead of ten, changed via `PATCH .../protection/required_status_checks` so nothing else was touched. Snapshots taken before and after confirm every other protection setting is byte-identical. Ordering mattered: `ci-required` had to exist on `develop` before it could be required, or every PR would have blocked on a context that never reports.

A mid-course correction: the option presented named five contexts, and the first implementation declared three. Five is the better answer and was restored. `ci-required` is now a single point of failure, and `validate`/`shellcheck` always run and can never be skipped, so keeping them separately required is free defence in depth against a bug in the aggregate itself.
