## The Count Was Wrong

The plan, this version's session notes, and the project memory all state **seven** administrator bypasses during the v3.17.5 release. Writing the record required naming them, so they were reconstructed rather than restated.

Every pull request merged into a protected branch on 2026-08-19 was checked against the ten contexts required at the time, using the check-runs API on each head commit. **Six** had at least one required context that never came into existence:

| PR | Shape | Files | Required contexts never reported |
|---|---|---|---|
| #50 | zero-file back-merge | 0 | 9 |
| #51 | docs-only | 1 | 8 |
| #52 | code-only | 2 | 1 (`colocation`) |
| #53 | docs-only | 1 | 8 |
| #54 | docs-only | 8 | 8 |
| #55 | zero-file back-merge | 0 | 9 |

`#47`, `#48`, and `#49` reported all ten. Widening the window to `#44`-`#56` added nothing. The seventh is not reconstructible: most likely a second bypass action on one of these six (a re-run after a push), or a miscount in the moment.

The record states six with the per-PR evidence and explains the discrepancy. Padding it to seven would have put one unverifiable number beside six verifiable ones and devalued all of them. This is a knowing deviation from the phase's stability gate ("the record names the seven instances"), recorded as `QG-4`.

## Two Things The Data Showed That Nobody Had Noticed

**`#52` is the code-only direction.** A two-file code change missing only `colocation`. Until this table existed, the problem was described as "docs-only PRs cannot merge". It was symmetrical: the two workflows' filters pointed in opposite directions, so each PR shape failed a different half of the required set.

**`#50` and `#55` are zero-file back-merges**, where a path-filtered required check is unsatisfiable by construction: no changed files means no path can match, inverse filters included. That case needs an administrator merge legitimately and no filter tuning fixes it. Conflating it with the other four is part of why the original problem looked larger and vaguer than it was, and the record separates them explicitly so a future reader does not try to "fix" it.

## The Rejected Record Is The Higher-Value One

The README calls `rejected/` the highest-value folder and the one most likely to be skipped, and the inverse-path no-op design earns its place because **it appears to cost nothing**. Keep every filter, add a companion workflow triggered on the inverse paths declaring the same job names as no-ops. Exactly one of each pair fires, so every required context always reports. No filter changes, no rename, no protection edit.

Its flaw is one step further on: the gate then reports green **without inspecting anything**. And the pull requests most likely to land on the no-op are precisely the ones carrying `docs/policy/**`, `docs/incidents/**`, and `docs/decisions/**`, which are validator INPUT that several guards read. It converts "unmergeable" into "merged unchecked", which is worse because it is silent.

The secondary flaw is durability: two filter sets must stay exact complements forever, and `ci.yml` had already accumulated four re-inclusions across four separate versions, each added because some guard read that path. Any drift yields an invisible gap.

Per the `rejected` lifecycle contract the body is written as the proposal was actually considered, with the verdict on the `Status:` line, so a future proposer sees the design rather than a summary of why it lost.
