## Goal

Skills can declare `user-invocable` / `disable-model-invocation`, validated locally, and mapped at install time only where a platform documents an equivalent lever.

## The Rule That Governed This Phase

The plan rated this `frontier` because it touches the installer and is governed by the do-not-invent rule, with the fabricated `.kimi/agent.yaml` lever as the named precedent. That record was seeded into `docs/decisions/rejected/policy/` in Phase 4 and read before starting.

**The rule earned its keep twice, live, in this phase.** Both times a web-search summary confidently asserted a field the vendor's own page does not document:

| Claimed by a search summary | What the vendor page actually documents |
|---|---|
| Cursor supports `user-invocable` | `name`, `description`, `paths`, `disable-model-invocation`, `metadata`. No `user-invocable`. The claim traced to a community forum thread |
| Antigravity supports `disable-slash-command` | `name` and `description` only, plus "the agent decides based on context" with no per-skill override |

Had either been taken at face value, this phase would have shipped a mapping for a field that does not exist, which is the exact shape of the incident the rule exists to prevent. Both are recorded in the survey document as what the vendor documents, with the discrepancy called out.

## What Was Built

### 6.1 Schema and validator

Two optional strict booleans, `disable-model-invocation` (default `false`) and `user-invocable` (default `true`), validated in `validate_skills.py`'s `--bundles-only` mode, which is what `make validate` and CI run so the check cannot be skipped.

Two rules: a non-boolean value is an error naming skill and field, and the combination `disable-model-invocation: true` + `user-invocable: false` is an error because it leaves a skill nobody can invoke. The second is explicitly a **Nexus-Hub rule, not a vendor rule**; Claude documents each field independently and nothing upstream forbids setting both.

The validator reads the raw frontmatter block through the strict YAML parser rather than the tolerant line-split dict, because that dict stringifies values and would let `user-invocable: "true"` pass as the boolean it is not.

All 273 existing skills declare neither field and pass untouched, which is the property that makes an optional field genuinely optional.

### 6.2 Survey and the Codex mapping

Five platforms surveyed against fetched vendor documentation, recorded in a new `docs/policy/skill-invocation-policy-levers.md`.

| Platform | Verdict |
|---|---|
| `claude` | VERIFIED, both fields, same names and defaults |
| `copilot` | VERIFIED, both fields, same names and defaults |
| `cursor` | VERIFIED, `disable-model-invocation` only |
| `codex` | VERIFIED, different file, different key, **inverted polarity** |
| `antigravity2` | UNVERIFIED, none documented |
| `opencode`, `qwen`, `kimi`, `hermes`, `nexus-ai` | NOT SURVEYED |

"NOT SURVEYED" is kept deliberately distinct from "none documented". The first means nobody looked; the second means someone read the page. Collapsing them is how an unchecked assumption becomes a recorded fact.

**The survey produced a pleasant result**: because Nexus-Hub copies `SKILL.md` verbatim, `claude`, `copilot`, and `cursor` need **no installer change at all**. The fields ride inside the file the installer already copies, and a platform ignores frontmatter keys it does not recognise.

Only `codex` needed real work, since its lever is `policy.allow_implicit_invocation` in an `agents/openai.yaml` sidecar. The maintainer was asked, per the `AGENTS.md` ask-first boundary, and approved building it now.

`codex_invocation_policy` in `_catalog_adapters.py`, invoked from `CodexIntegration._mirror_codex` for both skill roots, has three load-bearing properties, each tested:

1. **The value is inverted, never copied.** `disable-model-invocation: true` emits `allow_implicit_invocation: false`. A mapping that copied the value would produce the precise opposite of the author's intent while looking correct in review, so the generated file carries a comment saying so.
2. **Nothing is emitted unless a skill declares the field**, since Codex's default already matches ours.
3. **An authored sidecar is never overwritten.** OpenAI's `agents/openai.yaml` also carries `interface` and `dependencies` metadata this mapping cannot reconstruct, so a skill shipping its own keeps it and the skip is logged.

The sidecar path (`<skill>/agents/openai.yaml`) was confirmed against OpenAI's documented directory layout rather than assumed, since guessing it would have repeated the very mistake this phase is about.

### Scope decision: a third policy document

The plan said to record verdicts in `platform-defaults-levers.md`'s pattern. That document opens with an explicit scope boundary ("behavioral defaults only") and a warning that it and `platform-read-contracts.md` should not grow into each other.

A per-skill invocation field is neither a per-platform behavioral default nor a discovery path, so it went into a **sibling document following the same pattern** rather than being forced into either. Recorded as a decision record.
