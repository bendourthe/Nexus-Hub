## A2: Chain-of-Thought Leakage

Added as its own H2 family rather than as more `###` entries in the Named-Pattern Catalog, because the catalog operates at sentence level and this family operates at the level of *vantage*: well-formed sentences that silently assume the reader watched the document get written.

Four named patterns, each with a smell line and a before/after in the catalog's existing format: dead decision citations, temporal vantage, stack vantage, and justification residue. The family test is quoted as the plan specified: "could a reader at HEAD, with no transcript, resolve every reference?"

Extended examples went to `references/cot-leakage.md` and are linked from the body, per the skill's existing use of `references/` and the Tier-3 loading convention. The reference file carries what the body should not: the ambiguous cases and, more importantly, the **protected cases**. Temporal language is correct in changelogs, migration guides, deprecation notices, and incident timelines, whose reader is precisely someone comparing two states; a "Common Rationalizations" table or FAQ is not justification residue, because addressing objections is its declared job. A pattern family with no false-positive guidance would train over-application, which for this family means stripping legitimate change-describing prose.

One rationalization row and one verification item were added.

## A3: Smallest Sufficient Evidence Set

The plan's framing ("never default to the full suite locally") needed one adjustment to be safe, and this session supplied the counter-example. Phase 2's real bug (a skill unreachable from every capability module) was caught **only** by a 30-minute suite that no fast loop would have selected.

So the rule is written as **narrowest that COVERS, not narrowest available**, with an explicit clause: when the only check covering the change is slow, the slow check is the narrowest sufficient set and you run it. That preserves the plan's intent (stop reflexively running everything) without licensing the failure that intent could cause.

The section names both failure modes as opposites: under-covering (green output from a suite that does not touch the diff, which is costume rigor with a passing exit code) and over-covering (which trains skipping verification when time is short, and hides which gate owns a regression).

The change-surface table includes a row the plan did not ask for: **new file in a registered tree** to "whatever test asserts registration completeness for that tree", annotated as the most-missed surface because the file works fine and only its discoverability breaks. That row is Phase 2's bug generalized.

Also added: a "report only what ran" rule, including that a check producing no summary line (truncated output, killed process, timeout) produced no evidence and must be re-run. Cross-linked `[[pre-commit-checklist]]` in the body and Related Skills.

## A4: Postmortem Admission Criteria

Two of the three requested elements were straightforward. The third needed adaptation, recorded below and in known-gaps as `MT-3`.

**Admission criteria** were genuinely absent and went in as a new subsection after "When NOT to use this skill", which previously carried only a size threshold. All three tests must pass: subtle (not obvious from the diff), systemic (the process let it through, not just one person), and costly to rediscover. The rationale is stated as a cost, not a virtue: an archive nobody reads is worse than no archive, so admitting a marginal incident taxes every future reader.

**Guardrail linking** became Step 8c, naming three guardrail classes (tests, validator or gate rules, instruction rules) with the requirement to name AND link each, or to state explicitly that none were added and why. It is written to extend rather than replace the existing v3.16.2 Durable fix requirement: Durable fix answers "what closed this incident", Step 8c answers "what makes it unable to recur".

**The executive-summary block was adapted.** The plan asked for a new mandatory 30-second Executive Summary block at the top of the template. The skill already requires a `Summary` section as required-section 1, positioned above the timeline. Adding a second summary beside it would have produced two competing top-of-document summaries, which is a documentation smell and would have made the template worse. Instead the existing `Summary` spec was rewritten to *be* the 30-second executive summary, and to require all four elements the plan named, including the two that were missing: **why the process let it escape** and **the durable lesson**. The intent is fully delivered; the structure is not duplicated.

All three additions have binary verification items.
