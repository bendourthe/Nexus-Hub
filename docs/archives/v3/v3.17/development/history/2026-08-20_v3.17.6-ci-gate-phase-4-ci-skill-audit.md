## Audit Result, Stated For Each Skill

The plan required reporting each finding EXPLICITLY, including where the answer is "nothing found", because a silent audit cannot be distinguished from an audit never run.

| Skill | Recommends workflow-level `paths:`? | Discusses required status checks? | Both together? |
|---|---|---|---|
| `cicd-architect` | **Yes** -- "Pattern 2: Path-Based Triggers" teaches `paths:` + `paths-ignore:` on a `push` trigger | **Yes** -- Verification requires "direct push to main is blocked and at least one status check is required", plus a Common Rationalizations row on branch protection | **YES, antipattern present** |
| `cd-pipeline-generator` | No -- its `on:` block uses `branches:` and `workflow_dispatch` only, with no path filter anywhere | No | **No antipattern found** |
| `cicd-integration` | No -- its only `paths:` is a GitLab `cache:` key, not a trigger filter | Yes, and CORRECTLY: "the pipeline triggers on both `push` and `pull_request` events for the protected branches" | **No antipattern found** |

Two precision notes, because a careless grep would have produced a different answer:

- `cicd-architect` matches `paths:` five times, but three are GitLab `cache:` and `artifacts:` keys. Only the two inside Pattern 2 are trigger filters.
- `cicd-integration`'s single `paths:` hit is likewise a GitLab `cache:` key. Counting it would have produced a false positive and an edit to a skill that needed none.

`cicd-architect` is therefore the only skill that teaches both halves of the trap, and it never connects them: a reader follows Pattern 2 to add a path filter, then follows Verification to require a status check, and has built an unmergeable branch without either instruction being wrong on its own.

## What Was Added, And Where

Only to `cicd-architect`. Adding the rule to the two clean skills was considered and declined: `AGENTS.md`'s scope-fit rule asks what shipped behavior requires an addition, and neither skill teaches the pattern the rule corrects. Putting it there would inflate Tier 2 for both with no defect to fix.

The skill was 769 lines against `AGENTS.md`'s 800-line soft cap, which shaped the split:

- **Inline in `SKILL.md` (+22 lines, now 791)**: Pattern 2 is relabelled "Only safe when the workflow produces NO required status check", states the Pending-versus-Success asymmetry with the vendor citation, and shows the job-level `if:` form including both fail-closed halves. It flags the matrix trap in one sentence and links the reference. One Common Rationalizations row and one Verification item were added.
- **`references/required-status-checks.md` (97 lines)**: the full rationale, the vendor quotation, the fail-closed detector, the three traps, the aggregate-job pattern, and how to verify by opening a real pull request rather than reviewing configuration.

The split follows `AGENTS.md` directly ("Beyond 500 lines, add a `references/` subdirectory ... rather than expanding the body") while keeping the load-bearing rule itself in Tier 2, where a reader hitting Pattern 2 cannot miss it. A correctness rule pushed entirely into a reference file is a rule the agent may never read.

## The Verification Item Is The Interesting Edit

The skill already required "at least one status check is required". That is half the trap: it is exactly the instruction that turns Pattern 2 from a cost optimization into an unmergeable branch. The added item supplies the other half and is observable rather than aspirational:

> Every required status check is produced by a job whose workflow triggers unconditionally: open a pull request touching only paths the filters exclude and confirm each required context reports (a matrix job must be required by its aggregate context, never per-leg).

That is the check this version's own Phase 2 had to perform on itself. A green configuration review passed; the docs-only pull request is what found the matrix defect.

## Gates

- Frontmatter **unchanged** in all three skills, confirmed by diffing for any `name` / `description` / `summary_l0` / `overview_l1` line. No trigger surface moved.
- `validate_skills.py --bundles-only`: PASS, 0 errors, 0 warnings across 273 skills. The new reference file is linked from `SKILL.md`, so the orphan-bundle audit is clean.
- `run_trigger_evals.py --gate`: PASS, 0 un-allowlisted collisions, 0 routing failures. The gate scores skill DESCRIPTIONS, and those are byte-identical, so no neighbouring skill's score can have moved; this is a structural guarantee rather than an observation.
- Markdown style self-check: 0 problems in both files under a fence-aware check (a naive one produced false positives on `# ====` banner comments inside YAML fences). One U+2026 ellipsis slipped into the reference file and was replaced with ASCII `...`. A first pass through this session claimed the validator does not catch that character. It does, as a WARNING, promoted to an error only under `--strict`. The claim was wrong because the validator had been run with its output redirected and only its exit code read. The real finding is worse than a missing rule: `validate_unicode_safety.py` currently emits **1042 warnings** across the repository, so a newly introduced one is invisible in the noise. An exit code of 0 says nothing about whether this phase added a violation.

## Deviations

- Content was split between the body and a new `references/` file to respect the 800-line soft cap. The plan said "a named additive section"; this is that section plus its long form.
- A Verification item was added, which the plan did not request. The skill's existing Verification line is one half of the trap, so leaving it alone would have left the audit incomplete.
