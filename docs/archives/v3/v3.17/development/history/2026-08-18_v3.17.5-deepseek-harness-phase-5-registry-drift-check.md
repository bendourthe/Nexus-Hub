## Goal

A per-skill drift-check proving the hand-edited `data/` registries stay consistent with the catalog, with single-skill diffs.

## What The Check Adds

`tests/validators/test_registry_consistency.py` already covers membership (both directions) and aggregate counts. What nothing covered is **per-skill field agreement**: whether a row that exists and is counted still *says the right thing*. That is the drift this phase targets, and it is quiet by construction, because a stale entry passes every presence and count check while the catalog misdescribes itself.

Scope was widened beyond the plan's three files to include `data/bundles.json` capability-module reachability. That is the `QG-1` blind spot from Phase 2: a skill in no module installs fine and is simply unreachable to any focused install, and it was previously provable only by a ~30-minute integration suite. Moving it into a per-skill validator makes the same signal available in under a second, which is the whole point of a fast gate.

## What It Found

Three real defects, in rising order of severity.

**1. A schema violation I introduced in Phase 2.** `skills.json` `size` is a dict (`{lines, characters, tokens_estimate}`) for all 272 pre-existing entries. The `deepseek-harness` entry set it to an integer, because the plan's prompt said "size" and I wrote `stat().st_size`. Nothing caught it: no test asserts that field's shape. The check found it on first run, and it is fixed with a regression test.

**2. Pre-existing category drift in the index.** `loop-engineering`'s `SKILL_INDEX.md` row read `Workflow` while its directory and `skills.json` entry both read `workflow`. This inflated the index to 22 distinct categories against the catalog's 21. Fixed, with a test asserting the exact defect.

**3. A 171-field text-drift backlog.** This is the significant find.

| Field | Drifted |
|---|---:|
| `skills.json` `description` | 74 |
| `skills.json` `overview_l1` | 51 |
| `skills.json` `summary_l0` | 16 |
| `SKILL_INDEX.md` `summary_l0` | 15 |
| **Total** | **171 fields across 107 of 273 skills** |

The causes are mixed. Some are genuine staleness, where a SKILL.md was edited and its registry entry was not (`google-antigravity-sdk`'s `summary_l0` says "with the Google Antigravity SDK -- async agent loop" in `skills.json` against "on the Google Antigravity SDK: async loop" in SKILL.md). At least six are **encoding corruption**: `skills.json` holds `U+00E2 U+20AC U+201D`, which is the cp1252 rendering of the UTF-8 bytes for an em-dash, where SKILL.md holds a clean `U+2014`. That is exactly the Windows encoding corruption the project's ASCII-only rules exist to prevent, sitting in a file that ships to users and feeds the MCP search server.

## Why The Text Drift Is Not Fixed In This Phase

Repairing 171 fields would mean rewriting `description` values for 74 skills. Descriptions are the **routing surface**: `run_trigger_evals.py` scores them, and Phase 2 demonstrated concretely how a description edit moves scores for neighbouring skills. A 74-description rewrite bundled into a phase about building a checker would be a large, routing-affecting change to a distributed registry, landing in a commit whose stated subject is something else.

So the check ships with two channels:

- **Structural** (name, category, path, editorial field types, membership, orphans, marketplace census, module reachability) is a **hard failure**. This is clean today and gated in `make validate` and CI from now on.
- **Text** (description, summary_l0, overview_l1) is **reported on every run** and fatal only under `--strict`.

The backlog is recorded as `MT-5` with the repair scoped as its own change. A test asserts the drift keeps being reported, so it cannot quietly become invisible; if the repair lands and the count reaches zero, that test is the thing that says so.

This is a deliberate trade-off, and the alternative was worse in both directions: gating hard today would have blocked `make validate` on 171 pre-existing failures, and dropping the text check entirely would have discarded the finding.

## `--emit`, Not `--fix`

Per the plan and the standing hand-edit convention, the tool never writes. `--emit <skill>` prints a paste-ready index row and JSON entry, plus a reminder of the surfaces `--emit` cannot render (statistics, marketplace count, module membership). The full catalog builder remains forbidden because it rewrites the whole tree and turns a one-skill change into an unreviewable diff. This makes the hand edit *checkable and assisted*, which was the design intent.
