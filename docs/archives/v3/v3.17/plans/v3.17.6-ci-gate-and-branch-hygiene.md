# Plan - CI Gate Hygiene and Branch Hygiene

**Project**: Nexus-Hub
**Version**: v3.17.6
**Slug**: ci-gate-and-branch-hygiene
**Plan Type**: Feature (guard + convention + skill audit)
**Created**: 2026-08-19
**Seeded from**: the v3.17.5 release session, which produced seven live instances of the same defect
**Goal**: No PR in a Nexus-Hub-governed repo is ever blocked by a required status check its workflow cannot produce, and the harness teaches and enforces that rule for every project it touches.

## Overview

Shipping v3.17.5 took seven administrator bypasses in one day. Every one traced to a single mechanism, confirmed against GitHub's own troubleshooting documentation:

> "If a workflow is skipped due to path filtering, branch filtering or a commit message, then checks associated with that workflow will remain in a **Pending** state." A PR requiring them is blocked. "If a **job** within a workflow is skipped due to a conditional, it will report its status as **Success**."
>
> -- [GitHub Docs: Troubleshooting required status checks](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/defining-the-mergeability-of-pull-requests/troubleshooting-required-status-checks), fetched 2026-08-19

An untriggered workflow blocks forever. A skipped job passes. Nexus-Hub's required-check set is therefore **structurally unsatisfiable**: a prototype audit run during planning found **7 of 10 required checks come from path-filtered workflows**, and the filters point in opposite directions, so no PR shape can satisfy all ten.

| PR touches | Blocked by |
|---|---|
| Only `docs/**` | `validate`, `shellcheck`, `tests`, `bootstrap`, `install-smoke`, `installer-smoke` (`ci.yml` excludes `docs/**`) |
| Only `scripts/**` | `colocation` (`doc-colocation.yml` includes ONLY `docs/**` and `catalog/skills/**`) |

The fix is not invention. `presentify-extractor.yml` **already uses the correct pattern** in this repo: no workflow-level `paths:`, filtering via job-level `if:`. Its `verify` check is the only required check the audit found structurally sound. This plan makes `ci.yml` and `doc-colocation.yml` match a workflow that already works, adds a validator so the rule cannot silently regress, extends the release flow with the branch-hygiene checks this session showed were missing, and audits the three CI skills that could be teaching the antipattern to every project using the harness.

Every item is local-first: no outbound call at validate time, no credential, no dependency beyond the Python standard library plus the PyYAML the catalog tooling already uses. Where a check needs GitHub state (the required-check list, `delete_branch_on_merge`), it reads a declared manifest by default and offers an opt-in `gh` sync the user initiates.

## Phase 1: Required-Check Coverage Validator

**Goal**: A guard fails when any required status check is produced only by a conditionally-triggered workflow.
**Prerequisites**: None.
**Stability Gate**: The validator exits 0 on the migrated tree and exits 1 on a fixture with a path-filtered required check; pytest suite green; wired into `make validate` and CI.
**Recommended model tier**: strong
**Recommended effort level**: high
**Rationale**: A deterministic YAML-parsing guard with a clear contract, but the correctness argument (which trigger shapes are conditional) needs care, and a wrong answer here silently re-permits the defect.

### Sub-tasks

#### 1.1 - The validator and its manifest

**Objective**: Create `scripts/check_required_check_coverage.py` and `docs/policy/required-checks.json`.

**Failure modes**: A workflow whose `on:` cannot be parsed is a hard error naming the file, never a silent skip (the exact fail-open class v3.17.5 shipped and had to patch). A required check naming a job that exists in NO workflow is a distinct failure from one naming a path-filtered job, because the remedies differ. A manifest listing a check no workflow produces fails rather than passing vacuously. PyYAML is a hard dependency here and its absence is an explicit error, never an empty pass.

**Build class**: load-bearing.

**Prompt**:
> In the Nexus-Hub repo, create `scripts/check_required_check_coverage.py` (Python 3, module docstring, type annotations). It reads `docs/policy/required-checks.json`, a declared list of required status-check contexts per protected branch, and parses every `.github/workflows/*.yml`. For each required context it resolves the producing job (matching a bare job id and a matrix-expanded `job (matrix-value)` form), then fails when that job's WORKFLOW carries `paths:` or `paths-ignore:` on any trigger, because GitHub leaves such a check Pending forever when the workflow does not trigger. Distinguish three failure classes with distinct messages: `UNPRODUCED` (no workflow defines the job), `CONDITIONAL` (produced by a path/branch-filtered workflow), and `BAD` (unparseable workflow or malformed manifest). Collect all failures before a single exit 1. Note in the docstring that a job-level `if:` is CORRECT and must NOT be flagged, citing GitHub's troubleshooting doc: a skipped job reports Success, an untriggered workflow reports nothing. PyYAML is required; its absence is an explicit error with a `pip install PyYAML` hint, never a silent pass. Support `--sync` to print (never write) the current required contexts fetched via `gh api`, so the manifest can be refreshed by hand. Wire the check into `make validate` and add it to `DEV_ONLY_SCRIPTS` in `catalog/hooks/tests/test_installer_smoke.py`. Seed the manifest from this repo's current `main` and `develop` protection. Acceptance: exits 1 today (pre-migration) naming the seven offending checks, which is the evidence Phase 2 then clears.

---

#### 1.2 - Testing and Stabilization

**Objective**: Generate and run all tests for this phase.

**Prompt**:
> Write `tests/validators/test_check_required_check_coverage.py` with tmpdir fixtures covering: a clean tree (unfiltered workflow producing every required check) passing; a path-filtered workflow producing a required check failing as `CONDITIONAL`; a `paths-ignore` variant failing identically; a required check no workflow produces failing as `UNPRODUCED`; a job-level `if:` NOT being flagged (the correctness case that distinguishes this guard from a naive one); matrix-expanded context names resolving to their job; an unparseable workflow failing as `BAD` rather than being skipped; a malformed manifest failing; and all failures collected before one exit. Add a test asserting the guard fails when PyYAML is unavailable rather than passing vacuously, mirroring the v3.17.5 fail-open regression. Run pytest and `make validate`; iterate until green. Extend the CI validate step. After all tests pass, run `/generate-session-history`.

## Phase 2: Workflow Migration and Proof

**Goal**: Every required check comes from an unconditionally-triggered workflow, proven by two real PRs merging with no bypass.
**Prerequisites**: Phase 1 (the validator is the regression guard for this migration).
**Stability Gate**: Phase 1's validator exits 0; a docs-only PR and a code-only PR each satisfy all required checks with zero administrator bypass; Actions-minute cost measured and reported.
**Recommended model tier**: frontier
**Recommended effort level**: max
**Rationale**: This edits the file gating every release. A mistake either blocks all merges or, far worse, silently stops running a check while still reporting green. The blast radius is the whole repository's quality gate.

### Sub-tasks

#### 2.1 - Migrate the two workflows

**Objective**: Move filtering from workflow triggers to job conditions in `ci.yml` and `doc-colocation.yml`.

**Failure modes**: A job that loses its filter entirely (running expensive matrices on every docs typo) is a cost regression, not just a style issue. A job whose `if:` is wrong in the permissive direction runs always (wasteful but safe); wrong in the restrictive direction it skips when it should run and reports Success, which is a SILENT hole in the gate and the outcome to fear. The `changes` job must fail closed: if path detection errors, downstream jobs must run rather than skip.

**Build class**: load-bearing.

**Prompt**:
> Migrate `.github/workflows/ci.yml` and `.github/workflows/doc-colocation.yml` from workflow-level `paths:` filtering to job-level `if:` conditions, following the pattern `presentify-extractor.yml` ALREADY uses in this repo (unfiltered `on:`, job-level `if:`) rather than inventing a new shape. Remove `paths:` from both workflows' `push` and `pull_request` triggers. Add a cheap `changes` job that computes path-category outputs, and gate the expensive jobs on it with `if:`. Preserve every existing justification comment about WHY each path mattered, rewritten to describe the job condition instead of the trigger filter, so the reasoning that produced `docs/policy/**`, `docs/incidents/**`, and `docs/decisions/**` re-inclusion is not lost. The `changes` job MUST fail closed: on any detection error, downstream jobs run. Keep `bootstrap-windows` and `tests-windows` gated to non-`pull_request` as they are today. Do NOT change which jobs exist or their names, since those names are the required-check contexts. Acceptance: Phase 1's validator exits 0, and `python -c "import yaml; yaml.safe_load(open('.github/workflows/ci.yml'))"` parses.

---

#### 2.2 - Prove it with a PR pair

**Objective**: Demonstrate, not assert, that both PR shapes now merge cleanly.

**Prompt**:
> Open two throwaway PRs into `develop`: one touching ONLY a docs file, one touching ONLY a `scripts/` file (a comment edit is sufficient). For each, record which checks reported, which were skipped-as-Success, and confirm `gh pr view --json mergeStateStatus` reaches CLEAN with NO administrator bypass and NO protection toggling. This is the acceptance test for the whole plan; a green validator alone does not prove the platform behaves as documented. Record the Actions-minute delta against the pre-migration baseline (the `changes` job plus any newly-always-running cheap job), and state it plainly even if it increased. Close both PRs without merging. If either fails to reach CLEAN, STOP and diagnose before proceeding; do not bypass to make the phase pass.

---

#### 2.3 - Testing and Stabilization

**Prompt**:
> Run `make validate`, `make test`, and `make lint`. Confirm the two proof PRs from 2.2 behaved as required and that no required-check NAME changed (a renamed job silently drops its required check, re-creating the original defect in a new form; cross-check the job names against `docs/policy/required-checks.json`). After all tests pass, run `/generate-session-history`.

## Phase 3: Release-Flow Hygiene

**Goal**: `/update release` catches the operational failures this session hit by hand.
**Prerequisites**: None (independent of Phases 1-2).
**Stability Gate**: The release flow reports merged-but-undeleted branches and the `delete_branch_on_merge` setting, refuses to tag off the release branch, and includes a post-release back-merge step; the repo-description drift is caught by the docs reconciliation.
**Recommended model tier**: strong
**Recommended effort level**: high
**Rationale**: Each item is small, but they touch the release path, and a wrong pre-tag assertion could block a legitimate release.

### Sub-tasks

#### 3.1 - Pre-tag branch assertion and post-release back-merge

**Objective**: Make two release-flow failures impossible rather than merely documented.

**Failure modes**: An assertion that reads the branch AFTER a failed checkout is worthless, since that is exactly the state it must catch; it must read HEAD immediately before tagging. An over-strict assertion blocks a legitimate release from a differently-named release branch, so the expected branch must be configurable rather than hardcoded to `main`.

**Build class**: load-bearing.

**Prompt**:
> Extend the `/update release` flow in `catalog/commands/update.md` with two steps. First, a pre-tag assertion: immediately before `git tag`, verify `git rev-parse --abbrev-ref HEAD` equals the expected release branch and `git rev-parse HEAD` equals `origin/<release-branch>`, and ABORT with a clear message otherwise. Cite the concrete incident: in the v3.17.5 release a `git checkout main` failed on a locked directory, left HEAD on an unrelated branch, and the tag was created there and published, shipping an unreleased plan file in the release tarball. Make the expected branch name configurable rather than hardcoding `main`. Second, a post-release back-merge step: after the release merges to `main`, merge `main` back into `develop`, because a PR-based release leaves a merge commit on `main` that `develop` lacks, and with `strict` protection that blocks the NEXT release PR. Both steps keep the existing confirmation gates.

---

#### 3.2 - Branch hygiene and repo-metadata drift

**Objective**: Report stale branches and the settings that cause them.

**Prompt**:
> Add a branch-hygiene step to `/update release`: list remote branches already merged into the integration branch using local `git` only (`git branch -r --merged`), excluding the protected branches and any branch with an open PR, and report them as cleanup candidates WITHOUT deleting anything. Separately, when `gh` is available and authenticated, report whether `delete_branch_on_merge` is enabled and offer to enable it with explicit consent; this is user-initiated and uses the user's own CLI, so it introduces no credential and no outbound call from the catalog itself. Note in the command file that Nexus-Hub CANNOT set this on a user's repo at install time, since the installer has no credentials and that would breach the zero-outbound policy. Finally, extend the release docs-reconciliation step to check the GitHub repository DESCRIPTION against the catalog counts: this repo's description read "256 curated skills, 15 commands, 22 hooks" against an actual 273/18/31, having drifted for many releases because no version-carrying surface covers it.

---

#### 3.3 - Testing and Stabilization

**Prompt**:
> Write tests for the pre-tag assertion covering: HEAD on the expected branch and synced (pass), HEAD on another branch (abort), HEAD on the right branch but behind origin (abort), and a configured non-default release branch (pass). Test the branch-hygiene reporter against a fixture repo with merged, unmerged, and open-PR branches, asserting it never proposes deleting a protected branch or one with an open PR. Run `make validate` and `make test`; iterate until green. After all tests pass, run `/generate-session-history`.
