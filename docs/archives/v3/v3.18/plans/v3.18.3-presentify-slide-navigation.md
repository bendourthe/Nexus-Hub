## Overview

Presentify (the `/presentify` command delegating to the `document-to-interactive-html` skill) currently produces a scrolling website: navigation is scroll plus anchor links, and the balanced / rich / cinematic interactivity levels are built on scroll-triggered and scroll-scrubbed animation. Users have requested a PowerPoint-comparable experience: viewport-height slides that fit a typical presentation screen, advanced with keyboard arrows rather than scrolling.

This plan adds a **navigation mode** axis - `scroll` (current behavior, the default and the non-interactive fallback) or `slides` - resolved in the existing Round 1 intake by extending the output-aspect question into a combined "canvas & navigation" question (the interactive question surface caps at four questions per round, so the mode rides the aspect question rather than adding a fifth). A `--nav <scroll|slides>` flag binds the choice and skips it, mirroring every existing flag convention (no-memory rule, design-record provenance, headless fallback).

The load-bearing design problem is animation: slide mode has no scroll, so every scroll-keyed pattern must be re-expressed. The plan defines a three-way slide-native animation grammar - (a) **entry-triggered** effects that run once when a slide activates, (b) **fragment-stepped** effects advanced by arrow keys within a slide (PowerPoint-like builds; the chosen stepping model), and (c) **permanent ambient loops** for atmosphere-class animation (a moving background illustration becomes a smooth repeating animation) - with the discipline that data-bearing animation is never looped (a repeating chart build misreads as new information). Cinematic scroll-scrub maps its camera keyframes onto fragments, with ambient drift while a keyframe holds. The generated file is authored for exactly one mode (no runtime toggle), and the visual-QA loop plus the structural scorer gain slide-mode criteria (per-slide fit, fragment-state capture, no scroll-keyed listeners in slide mode). Success looks like: a `/presentify --nav slides --interactivity cinematic` run produces one offline HTML file whose slides fit a 16:9 screen, advance by arrow key through staged fragments, and carry looping ambient motion where a scroll animation used to be - passing the QA loop's new slide-fit checks.

**Goal**: A complete, binary-checkable authoring contract for slide mode exists as `references/slide-navigation.md`, and Step 6 authors to it.
**Prerequisites**: Phase 1.
**Stability Gate**: The reference file exists, is referenced from SKILL.md (orphan-bundle audit passes), and a hand-authored sample page following it navigates correctly by keyboard in a local browser.
**Recommended model tier**: frontier
**Recommended effort level**: high

### Sub-tasks

#### 2.1 - Author `references/slide-navigation.md`

**Objective**: The slide-mode contract - stage, runtime, keyboard map, fragments, overflow, deep links, accessibility - specified to the same binary standard as the skill's other references.

**Failure modes**: Content taller than a slide: the contract's overflow rule REQUIRES splitting into continuation slides (never an inner scrollbar, except an explicitly-declared scrollable region such as a long table, which must carry a visible affordance); an author who cannot split records the exception in the design record. JS disabled or a parsing error in the inlined runtime: the document must remain readable top-to-bottom in source order (slides degrade to stacked sections), so a broken runtime never produces a blank page. Conflicting inputs (a keyboard step arriving while a fragment transition is mid-flight): the runtime queues or fast-forwards to the step's end state - it never drops the input or double-advances.

**Build class**: load-bearing.

**Prompt**:
> Create `catalog/skills/specialized-domains/document-to-interactive-html/references/slide-navigation.md`, the authoring contract for `nav=slides`. It must specify, each as a binary-checkable rule:
>
> 1. **Stage and sizing**: `<body data-nav="slides">`; each slide is a `100svw x 100svh` (small-viewport units) stage section with a component-prefixed class (`.slide-stage`, `.slide-inner` - never bare `.slide` contents leaking generic class names, per the skill's CSS-namespacing rule); page scrolling is disabled (`overflow: hidden` on the scroll container) and slides transition by transform or opacity, reduced-motion-guarded. The resolved aspect from Round 1 shapes the stage's safe-area (a 16:9 content box centered on non-16:9 screens for the deck option); content scales with the existing root `clamp()` typography contract - the readability floors (16px body / 13px secondary / 12px interactive) apply INSIDE slides at all four QA viewports.
> 2. **Overflow rule (binary)**: a slide's content must FIT its stage at the 1366x768 viewport with the root clamp at minimum; content that cannot fit splits into continuation slides ("Topic (1/2)", "Topic (2/2)") during authoring - an inner scrollbar is forbidden except for an explicitly-declared scrollable region (long table, code block) carrying a visible scroll affordance and a design-record note. This is the slide-mode analogue of the vertical-density rule.
> 3. **Keyboard map and inputs**: ArrowRight/ArrowDown/PageDown/Space = next step; ArrowLeft/ArrowUp/PageUp = previous step; Home/End = first/last slide; touch swipe left/right; on-screen previous/next hit zones and a slide counter ("7 / 24") with a clickable progress rail. "Step" means fragment-then-slide per rule 4. Keys must not fight native behavior inside interactive charts or scrollable regions (when focus is inside one, Escape returns focus to the deck before deck keys re-engage).
> 4. **Fragment stepping (the chosen model)**: elements marked `data-fragment="<n>"` reveal in order within a slide before the deck advances; a chart build, a sequential reveal, or a cinematic camera keyframe is one fragment each; going BACK re-hides the last fragment. A slide with no fragments advances immediately. All fragment state is idempotent (arriving at slide N via Home/End or a deep link shows the correct fully-revealed/fully-hidden state, not a half-build).
> 5. **Deep links and state**: each slide carries a stable id; the URL hash tracks `#slide-<n>`; loading with a hash opens that slide with prior slides' fragments resolved. Browser back/forward move through slide history.
> 6. **Accessibility**: off-screen slides are `inert` and `aria-hidden`; slide changes announce via an `aria-live=polite` region (slide title + position); focus moves to the active slide's heading; all controls are keyboard-focusable; `prefers-reduced-motion: reduce` replaces transitions with instant cuts and (per Phase 3) disables ambient loops.
> 7. **No-JS / print fallback**: without JS, slides render as normal stacked sections in source order; a `@media print` rule prints one slide per page.
> 8. **Interaction budget mapping**: state how the five-point minimum budget is satisfied in slide mode - (1) the progress rail + counter is the section navigation with active state, (2) slide-entry reveals replace scroll reveals (Phase 3 defines the grammar), (3) hover/focus affordances unchanged, (4) lightbox unchanged, (5) the signature interaction unchanged or fragment-stepped.
>
> Reference the file from SKILL.md Step 6 (add the pointer deferred from sub-task 1.2 if not yet shipped). Keep the reference self-contained (readable cold), <=500 lines, ASCII-only. Acceptance: `make validate` passes (orphan-bundle audit sees the reference), and a minimal hand-authored sample page following rules 1-5 navigates correctly by keyboard in a local browser.

## Phase 3: Animation Adaptation Grammar

**Goal**: Every scroll-keyed animation pattern in the balanced / rich / cinematic levels has a defined slide-native equivalent, including the requested ambient-loop conversion for atmosphere-class animation.
**Prerequisites**: Phase 2.
**Stability Gate**: The adaptation table exists and is exhaustive over the scrollytelling pattern catalog; `references/scroll-scrub.md` carries a slide-mode section; no pattern in the catalog lacks a slide-mode row.
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: This is the design core of the feature (the user's explicit requirement): judgment calls about which animations loop, which step, and which run once are semantic decisions with quality blast radius across every future cinematic slide deck.

### Sub-tasks

#### 3.1 - The three-way adaptation grammar in `interactive-features.md`

**Objective**: A normative mapping from every scroll-keyed pattern to its slide-mode expression.

**Failure modes**: A pattern with no table row: the fallback rule is entry-triggered-once (the safest expression), recorded in the design record - the author never invents a fourth grammar. Reduced motion: ambient loops are DISABLED entirely (not slowed) and fragment transitions become instant cuts; entry reveals become visible-immediately. Conflicting triggers (a slide re-entered repeatedly): entry-triggered effects re-run only if idempotent and non-data-bearing (a fade may re-run; a counter re-runs from its final value only if the re-run cannot misread as new data - otherwise it runs once per session).

**Build class**: load-bearing.

**Prompt**:
> In `catalog/skills/specialized-domains/document-to-interactive-html/references/interactive-features.md`, extend the "Interactivity spectrum" and "Scrollytelling pattern catalog" sections with a "Slide-mode animation grammar" subsection. Define the three slide-native trigger classes and the normative mapping table:
>
> 1. **Entry-triggered (once per activation)**: replaces scroll-triggered reveals and animated counters - the effect runs when its slide becomes active. Counters count up on first activation; re-activation shows final values (a re-run must never misread as new data).
> 2. **Fragment-stepped**: replaces progress-driven patterns (progress timeline, before/after scrub, chart build-ups, pinned-graphic step sequences, cinematic camera keyframes) - each discrete state becomes a `data-fragment` step advanced by arrow keys, per the Phase 2 fragment contract. The scrollytelling STATE TABLE requirement carries over unchanged: each step still declares prose claim / visual change / takeaway.
> 3. **Ambient loop (permanent)**: replaces atmosphere-class scroll animation ONLY - moving background illustrations, parallax texture layers, gradient drift, particle fields, slow procedural motion. These become smooth, seamless, infinitely-repeating CSS/JS animations running while the slide is active (paused when inactive, disabled under reduced motion). State the appropriateness rule as binary: ambient conversion applies ONLY to non-data-bearing, non-narrative animation; a chart build, a numeric transition, or any effect whose motion carries MEANING must be class 1 or 2, never a loop - looping data motion fabricates the impression of live data. Amplitude discipline: ambient loops are subtle (background-layer opacity/position drift), never foreground distraction; at most one ambient system per slide.
>
> Then add the mapping table with one row per catalog pattern (scroll reveal -> entry; counter -> entry; parallax layers -> ambient; sticky/pinned graphic sequence -> fragment-stepped; full-bleed image-to-text transition -> fragment or entry; progress timeline -> fragment-stepped; before/after slider -> stays user-initiated (unchanged - user-initiated patterns need no adaptation); marquee/atmospheric texture -> ambient). Close with the fallback rule: an unmapped pattern defaults to entry-triggered-once with a design-record note. State that restrained level in slide mode needs no adaptation (it never had scroll-triggered motion), and balanced/rich/cinematic use this grammar. Acceptance: every pattern named in the scrollytelling catalog has a row; the three classes and the data-bearing prohibition are stated as binary rules.
