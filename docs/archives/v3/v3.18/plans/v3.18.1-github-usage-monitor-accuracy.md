# Plan - GitHub Usage Monitor Accuracy and Warning Parity

**Project**: Nexus-Hub
**Target version**: v3.18.1
**Slug**: github-usage-monitor-accuracy
**Rank**: 3 of 17 in [`docs/roadmap-prioritization.md`](../../../../roadmap-prioritization.md)
**Retargeted**: 2026-08-21, was v3.17.11. Body text below may still cite v3.17.11 (known-gaps section names, self-referencing plan paths, release-step version numbers); the Target version above governs. Reconcile those citations when implementing.
**Plan Type**: Bug-fix campaign
**Created**: 2026-08-19
**Goal**: The GitHub Usage Monitor reports a drawdown that tracks GitHub's own included-usage meter without a hardcoded multiplier table, warns through the same styled webview surface as the Claude, Codex, and Cursor monitors, and explains in writing when Actions minutes are actually consumed.

## Overview

Three defects were reported on 2026-08-19 against extension 0.3.3, all reproduced and root-caused before this plan was written.

**Defect one: the warning arrives as a native toast instead of the styled panel.** The extension fires both surfaces. `maybeShowAlert` reveals the webview AND calls `showWarningMessage`, then auto-dismisses the webview after `notificationTimeoutSeconds` (default 12). Worse, `WarningViewProvider.show()` never calls `this.view.show(true)` when the view already exists, and the view is registered with `retainContextWhenHidden: true`, so it survives dismissal. Every alert after the first in a session therefore rewrites the HTML of an invisible panel while the toast is the only thing the user sees. The Claude monitor does call `view.show(true)` and fires no toast from its alert path.

**Defect two: the meter read 58% while GitHub showed 2,000 of 2,000 minutes consumed.** Refresh is working; the model behind the number is wrong. The extension reconstructs the drawdown as private-repository, GitHub-hosted, standard-runner minutes counted at `OS_DRAWDOWN_WEIGHTS`, which v3.16.4 reverted to `{linux: 1, windows: 1, macos: 1}`. Measured against the account on 2026-08-19 through the Actions jobs API, August private-repository usage on `Nexus-AI` was 1,457 Linux + 187 Windows + 80 macOS minutes across 73 runs and 527 jobs. Unweighted that is 1,724 minutes, which cannot produce a saturated 2,000-minute meter. The unweighted model is falsified.

The reverted weights were not wrong about weighting existing; they were wrong about where the numbers come from. GitHub's historical published multipliers (Linux 1x, Windows 2x, macOS 10x) are exactly the pre-2026 per-minute price ratios: $0.008, $0.016, $0.080. On 2026-01-01 GitHub cut runner prices to $0.006, $0.010, $0.062, so the same mechanism now yields 1x, 1.67x, and 10.33x. Any hardcoded table is therefore a snapshot of a price list that has already moved once and will move again, which is precisely why this number has swung three times.

The fix is to stop hardcoding it. `pricePerUnit` is returned on every `/settings/billing/usage` line item, is documented in the repo's own data contract, and is currently discarded: the normalizer never parses it and `lineItemsOf` hardcodes `pricePerUnit: null`. Deriving each item's weight as its own `pricePerUnit` divided by the Linux rate observed in the same payload produces a self-calibrating drawdown that tracks price changes, new runner types, and ARM variants with no table to maintain. Applied to the measured August data it yields 2,595 weighted minutes, consistent with saturation; the unweighted 1,724 is not.

**Defect three: there is no written account of when Actions minutes are consumed.** Public-repository runs on `Nexus-Hub` (366 in August) appear as metered line items that are then fully discounted, which reads as consumption but never draws down the allowance. Private-repository runs do draw down, price-weighted. Self-hosted and larger runners never draw down. Nothing in the repo states this, so the same question is re-derived each time it comes up.

Success looks like: a drawdown computed from data GitHub returns rather than from a constant; a meter that renders exhaustion honestly instead of stalling below 100%; one warning surface shared by all four monitors, guarded by a parity test; and a policy document plus decision record that make the next challenge argue with evidence.

## Scope boundary

**In scope**: the `github-usage-monitor` extension, one policy document, one decision record, and the known-gaps and CHANGELOG entries.

**Out of scope, deliberately**: scraping `github.com/settings/billing`. The extension authenticates with an OAuth Bearer token; the billing HTML requires a browser session cookie, so the page is not reachable with the credential the extension holds. It is also an undocumented surface with no stability contract. The included allowance itself (2,000 minutes, 0.5 GB) is the one figure no billing endpoint returns, and it continues to come from the plan table with the existing manual override as the correction path.

## Phase 1: Warning-surface parity

**Goal**: The threshold warning appears as the styled webview, every time, and no native toast competes with it.
**Prerequisites**: None.
**Stability Gate**: A second threshold crossing in one session reveals the panel; no `showWarningMessage` remains on the alert path; a parity test asserts all four monitors' alert paths agree; `npm test` passes.
**Recommended model tier**: strong
**Recommended effort level**: medium
**Rationale**: Small, well-bounded diff against a known-good reference implementation; the risk is cross-extension drift, which a test bounds.

### Sub-tasks

#### 1.1 - Fix the reveal

**Objective**: A warning for an already-resolved view becomes visible rather than silently re-rendering.

**Failure modes**: If `view.show()` is unavailable on the host's API surface (older VS Code), fall back to the existing `${WARNING_VIEW_ID}.focus` command rather than throwing; if the view was disposed, `this.view` must be cleared so the focus branch is taken.

**Build class**: load-bearing.

**Prompt**:
> In `extensions/github-usage-monitor/src/warningView.ts`, change `WarningViewProvider.show()` so the view-exists branch calls `this.view.show(true)` after assigning the HTML, matching `extensions/claude-usage-monitor/src/warningView.ts:86-91`. Guard the call so a host without `WebviewView.show` falls back to `executeCommand(`${WARNING_VIEW_ID}.focus`)` instead of raising. In `dismiss()`, clear `this.view` the way the Claude monitor's `hide()` does, so a disposed view cannot leave the provider holding a dead reference. Do not change the rendering function or the CSS.

#### 1.2 - Remove the competing toast

**Objective**: One surface, matching the other three monitors.

**Failure modes**: The auto-dismiss timer and the toast's `.then` handler are coupled - the handler clears the timer. Removing the toast without removing the timer would leave the panel auto-hiding after 12 seconds with nothing to cancel it. Remove both together, and treat the `notificationTimeoutSeconds` setting as retained-but-unused only if something else reads it; otherwise deprecate it in `package.json` with a description noting it no longer applies, rather than deleting a key users may have set.

**Build class**: load-bearing.

**Prompt**:
> In `extensions/github-usage-monitor/src/extension.ts`, rewrite `maybeShowAlert` so it reveals the warning webview only: drop the `vscode.window.showWarningMessage(suggestion.message, ...)` call, the `scheduleWarningDismissal` timeout, and the `dismissed` flag plumbing that exists solely to coordinate them. Keep the threshold-crossing dedupe (`crossedUnnotifiedThreshold`, `markThresholdNotified`) exactly as is. Keep `onOpenDashboard` wired to `showDashboard`. Check every other reader of `notificationTimeoutSeconds` and of the exported `scheduleWarningDismissal`; if nothing else uses them, mark the setting deprecated in `package.json` (description only, key retained) and remove the now-dead export along with its test. Do NOT touch the `showWarningMessage` calls outside the alert path - the reconnect offer, the reconciliation breaker notice, and the partial-logout notice are separate surfaces and stay.

#### 1.3 - Cross-extension parity test

**Objective**: The four monitors cannot silently diverge on warning behavior again.

**Failure modes**: The four extensions have different module layouts and different symbol names, so an import-based test would couple them. Assert on source text with narrowly-scoped patterns instead, and make the test name the offending extension in its failure message so a future break is self-diagnosing.

**Build class**: load-bearing.

**Prompt**:
> Add `extensions/github-usage-monitor/test/warning-parity.test.ts` asserting, for each of `claude-usage-monitor`, `codex-usage-monitor`, `cursor-usage-monitor`, and `github-usage-monitor`: (a) the alert path that calls the warning view's `show(...)` does not also call `showWarningMessage` in the same function body, and (b) the warning view provider's show method calls `view.show(` in its view-exists branch. Read the sibling sources by relative path and skip with an explicit message if a sibling is absent, so the suite still runs in a partial checkout. Failure messages must name the extension and the file. Where the four genuinely differ for a documented reason, encode the exemption as a named constant with a comment rather than loosening the pattern.

#### 1.4 - Testing and Stabilization

**Objective**: Prove the reveal works on a repeat crossing, which is the reported symptom.

**Prompt**:
> Add or extend a test in `extensions/github-usage-monitor/test/ui.test.ts` (or a new `warning-reveal.test.ts`) that drives two successive threshold crossings against a fake `WebviewView` and asserts `show` was called on the second crossing, not only the first - the exact defect. Add a test that no toast is raised from the alert path. Run `npm run compile`, `npm test`, and `npm run test:coverage` in `extensions/github-usage-monitor`. Update `.github/workflows/github-usage-monitor.yml` only if a new command is needed; otherwise record a no-op. After all tests pass, run `/generate-session-history` to document Phase 1.

## Phase 2: Price-derived drawdown

**Goal**: The drawdown weight for every line item comes from that item's own `pricePerUnit`, so no multiplier table exists to go stale.
**Prerequisites**: Phase 1 (independent, but sequenced so a failed drawdown change cannot be confused with a warning-surface change).
**Stability Gate**: `pricePerUnit` flows from the API response to `computeDrawdownMinutes`; `OS_DRAWDOWN_WEIGHTS` is gone as a behavioral input; the measured August fixture yields ~2,595 and renders as exhausted; a period with no Linux item still produces a defensible result or an honest unknown; `npm test` passes.
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: This is the correctness core of the release and the third revision of this number. It changes a user-facing figure, touches the type surface, and has a failure mode (silently wrong percentage) that looks like success.

### Sub-tasks

#### 2.1 - Thread `pricePerUnit` through the pipeline

**Objective**: The field GitHub already returns reaches the code that needs it.

**Failure modes**: `/usage/summary` and `/usage` differ in field set; a snapshot persisted by 0.3.x has no `pricePerUnit` on its breakdowns, so a cached snapshot must deserialize with the field absent and be treated as unknown rather than as zero. Zero is the dangerous value here: it would make an item's derived weight zero and silently drop it from the drawdown.

**Build class**: load-bearing.

**Prompt**:
> Add `pricePerUnit: number | null` to `SkuUsageBreakdown` in `extensions/github-usage-monitor/src/types.ts`, documenting that it is present only on the plain `/settings/billing/usage` endpoint and that `null` means unknown, never zero. Parse it in `parseItems` in `src/providers/normalizer.ts` using the existing `optionalNumber` helper. In `src/providers/enrich.ts`, change `lineItemsOf` to pass `row.pricePerUnit ?? null` instead of the hardcoded `null`. Add a normalizer test asserting the field round-trips, and one asserting an item lacking the field parses to `null` rather than `0`. Confirm `usageStore` deserialization of a 0.3.x-era cached snapshot yields `null` for the new field and add a regression test for that migration case.

#### 2.2 - Derive the weight from price

**Objective**: Replace the constant table with a ratio computed from the same payload.

**Failure modes**: Enumerate and handle each explicitly. No Linux item in the period (an all-Windows month) leaves no denominator - fall back to the plan-table Linux rate rather than to 1.0, and record which was used. Several distinct Linux rates in one period (1-core $0.002 alongside 2-core $0.006) means the standard 2-core rate must be selected deliberately, not by `min`. A `pricePerUnit` of `null` or `0` on an otherwise qualifying item must mark the reconstruction incomplete, exactly as an unresolved repository already does, not contribute zero. Larger and self-hosted runners stay excluded by `classifySku` and are never weighted - price-weighting a larger runner would be a category error, since included minutes cannot be spent on one at all.

**Build class**: load-bearing.

**Prompt**:
> In `extensions/github-usage-monitor/src/providers/drawdown.ts`, replace the `OS_DRAWDOWN_WEIGHTS` lookup inside `computeDrawdownMinutes` with a derived weight: `weight(item) = item.pricePerUnit / linuxReferenceRate`, where `linuxReferenceRate` is resolved once per period by a new exported pure function `resolveLinuxReferenceRate(items)`. That function selects the rate of the standard Linux runner observed in the period, falls back to a documented published constant when no Linux item is present, and returns which source it used so the caller can label provenance. Keep the existing private / GitHub-hosted / standard-runner exclusions unchanged and applied BEFORE weighting. An item that qualifies but carries a `null` or non-positive `pricePerUnit` is added to the unresolved set rather than contributing, so a partial reconstruction stays honest. Extend `DrawdownResult` with the reference rate and its source. Delete `OS_DRAWDOWN_WEIGHTS` as a behavioral input; if it is retained at all, retain it only as a documented historical note stating that 2x / 10x were the pre-2026 price ratios ($0.008 / $0.016 / $0.080) and that the mechanism, not the constants, is what the code now implements. Replace the `usedWeighting` boolean with something that survives this change (for example the distinct weights actually applied), updating every caller including `enrich.ts`.

#### 2.3 - Render exhaustion honestly

**Objective**: A drawdown above the allowance reads as exhausted rather than stalling or overflowing.

**Failure modes**: A percentage over 100 must not break the meter geometry, and must not be clamped so hard that the real figure is hidden. The reported symptom was a meter stuck below 100 while GitHub showed saturation; a fix that clamps silently reproduces the same lie in the other direction. On a Free account with no payment method, exhaustion means further private-repository runs are blocked, which is the actionable fact and belongs in the recommendation text.

**Build class**: load-bearing.

**Prompt**:
> In `src/providers/allowances.ts` and the panel and status-bar renderers, handle the drawdown-exceeds-allowance case explicitly: the bar renders full and in the critical style, the numeric percentage shows the true value (for example 130%), and the state is labelled exhausted rather than silently clamped to 100. Add an `exhausted` allowance state or an equivalent flag if the existing state union cannot express it, and thread it through `recommendations.ts` so the suggestion text for an exhausted Actions allowance states that further private-repository Actions runs will be blocked until the reset date when no payment method or budget is set, while public-repository runs continue to be free. Verify the status bar's compact rendering does not overflow at three digits.

#### 2.4 - Testing and Stabilization

**Objective**: Pin the model against the measured account, including the case that falsified its predecessor.

**Prompt**:
> Rewrite `extensions/github-usage-monitor/test/enrich.test.ts`'s "drawdown weighting" block. Delete the assertion pinning `OS_DRAWDOWN_WEIGHTS` to all-1 and replace its comment with the falsification: measured 2026-08-19 against `Nexus-AI` August via the Actions jobs API, private usage was 1,457 Linux + 187 Windows + 80 macOS across 73 runs / 527 jobs; unweighted 1,724 cannot produce the saturated 2,000-minute meter GitHub displayed, and price-weighted 2,595 can. State explicitly that the retained 2026-08-09 and 2026-08-10 observations do NOT discriminate between the models because that period was 97% Linux, so they must not be cited as support for either. Add fixtures with realistic `pricePerUnit` values ($0.006 / $0.010 / $0.062) covering: the measured August month; a month with no Linux item (fallback rate path); an item with `null` pricePerUnit (unresolved, not zero); a larger-runner item (excluded, never weighted); a self-hosted item (excluded); and a public-repository item (excluded). Assert the exhausted state renders at >100%. Run `npm run compile`, `npm test`, `npm run test:coverage`. Update CI only if a new command is needed. After all tests pass, run `/generate-session-history` to document Phase 2.

## Phase 3: Self-validating reconciliation ledger

**Goal**: The model is judged by accumulated per-month evidence, so a fourth revision has to argue with data rather than with the previous author.
**Prerequisites**: Phase 2.
**Stability Gate**: A committed ledger records one verdict per observed month with its saturation status; the runner refuses to treat a saturated month as a point observation; the two existing August observations are recorded as non-discriminating; `npm test` passes.
**Recommended model tier**: frontier
**Recommended effort level**: high
**Rationale**: This is the anti-swing mechanism and the phase most likely to be reasoned about incorrectly, because the trap it exists to prevent (treating a saturated meter as a measurement) is exactly the trap the previous two revisions fell into.

### Sub-tasks

#### 3.1 - Saturation-aware verdict logic

**Objective**: Encode the difference between a measurement and a lower bound.

**Failure modes**: A saturated meter reports only "at least the allowance" and can never confirm a model, only refute one that predicts below the cap. A month dominated by Linux cannot discriminate between candidate weightings regardless of saturation. Both must be classified as such rather than counted as agreement - counting them as agreement is how the all-1 table was justified.

**Build class**: load-bearing.

**Prompt**:
> Add `extensions/github-usage-monitor/src/providers/reconciliation.ts` with pure functions over an observation `{ month, displayedValue, displayedIsSaturated, allowance, predicted, mixByOs }`. Classify each observation as `refutes` (saturated and predicted below the cap, or unsaturated and outside tolerance), `supports` (unsaturated and within tolerance), or `non-discriminating` (the non-Linux share of predicted drawdown is below a declared threshold, so any candidate weighting yields the same answer within tolerance). Declare the tolerance and the discriminating-power threshold as named exported constants with their justification in a comment, BEFORE any comparison is written, following the precedent of `RECONCILIATION_TOLERANCE` in `drawdown.ts`. No network, no `vscode`, no configuration in this module.

#### 3.2 - Ledger and probe wiring

**Objective**: Verdicts accumulate in a reviewable file instead of in commit messages.

**Failure modes**: The ledger must never contain a credential, and repository names may be sensitive - reuse the hashing convention `scripts/reconcile-drawdown.js` already established and its `--reveal-repos` opt-in.

**Build class**: supporting.

**Prompt**:
> Create `docs/v3/v3.17/development/github-drawdown-ledger.md` with one row per observed month: month, predicted drawdown, displayed value, saturated yes/no, OS mix, verdict, and the date and method of observation. Seed it with the three months this plan can evidence: July 2026 and August 2026 (both saturated, both refuting the unweighted model), and the Aug 1-10 window (non-discriminating, 97% Linux). Extend `extensions/github-usage-monitor/scripts/reconcile-drawdown.js` to emit a row in exactly this format using the Phase 3.1 classifier, and to print the derived Linux reference rate and per-item weights so the mechanism is inspectable. Keep repository-name hashing on by default. Document in the ledger header what would falsify the current model: an unsaturated month with a non-Linux share above the discriminating threshold whose displayed value matches unweighted minutes.

#### 3.3 - Testing and Stabilization

**Objective**: Prove the classifier refuses the specific mistake that caused two prior revisions.

**Prompt**:
> Add `extensions/github-usage-monitor/test/reconciliation.test.ts` asserting: a saturated month whose prediction exceeds the cap classifies as consistent-but-not-confirming, never `supports`; a saturated month whose prediction falls below the cap classifies as `refutes`; a 97%-Linux month classifies as `non-discriminating` even when the numbers match exactly; and an unsaturated mixed-OS month within tolerance classifies as `supports`. Include the real July and August figures as fixtures. Run `npm run compile`, `npm test`. After all tests pass, run `/generate-session-history` to document Phase 3.

## Phase 5: Policy document and decision record

**Goal**: When Actions minutes are consumed is written down once, and the weight change carries its own falsifier.
**Prerequisites**: Phase 2 (so the document describes shipped behavior, not intended behavior).
**Stability Gate**: Both documents exist, are linked from the extension README, pass the markdown style guide and the doc-budget gate, and every external claim carries a source URL and a verified date.
**Recommended model tier**: strong
**Recommended effort level**: medium
**Rationale**: Writing against verified facts; the risk is asserting an undocumented GitHub behavior as documented, which the do-not-invent rule bounds.

### Sub-tasks

#### 5.1 - Actions-minutes policy document

**Objective**: One reference that answers the question without re-deriving it.

**Failure modes**: The single largest hazard is stating the multiplier as GitHub-documented. It is not: GitHub's current pages state per-minute prices and that Windows and macOS cost more, but publish no multiplier for included-minute consumption. Every claim must be marked as either documented-with-source or inferred-with-evidence, and prices change (they changed on 2026-01-01), so every rate needs a verified date.

**Build class**: supporting.

**Prompt**:
