# Plan - Model-Prompting Research and Auto-Tuning

**Project**: Nexus-Hub
**Version**: v3.15.5
**Slug**: model-prompting-research
**Plan Type**: Feature
**Created**: 2026-07-21
**Goal**: Nexus-Hub keeps pace with new model releases automatically: a standalone command runs a web-research swarm that, per live-enumerated model, learns the current best prompting techniques, verifies each finding against a primary source, records model-specific guidance in a distributed per-model profile layer, and auto-applies model-agnostic authoring improvements to the shared catalog (SKILL.md, commands, base-*.md) behind the repo's own automated guards and branch isolation, with a best-effort staleness check wired into /update release.

## Overview

Every new model release (GPT-5.5 to GPT-5.6 Sol, Opus 4.8 to Fable 5, and so on) shifts what "good prompting" means, and Nexus-Hub's skills and commands are authored to a fixed set of prompting conventions that slowly drift out of date. Today there is no mechanism to detect that drift or to refresh the catalog against it. This release adds one: a research-and-tune capability that treats "how to prompt each current model" as a living, web-verified contract, and turns confirmed findings into catalog improvements.

The capability has two write targets with two different autonomy levels, and the separation is a hard rail enforced by the repo's own tooling. Model-specific guidance ("model X prefers terse system prompts, model Y wants explicit step numbering") is fully autonomous but is confined to a per-model profile layer bundled inside the new skill (`references/models/<model>.md` plus a machine index), so it is distributed to every platform as Tier-3 on-demand reference and never touches a shared body. Model-agnostic authoring improvements ("this trigger phrase is clearer", "this rationalization row cites a stronger failure mode") are auto-applied to shared catalog bodies (SKILL.md, commands, base-*.md) but only behind the full guard suite (`make validate`, `check_base_template_parity.py`, `check_version_sync.py`, the freshness/schema validators, `make test`, ShellCheck) and only on an isolated feature branch that stops for human merge. Any edit that fails a guard is auto-reverted or quarantined, never shipped. `check_base_template_parity.py` is what makes the hard rail real: a model-named line in a shared `base-*.md` fails the build, so model-specific content physically cannot land in a shared body.

The research half reuses what already exists: `model-routing` enumerates the live model roster per platform (no hardcoded list), `adversarial-verifier` is the verify stage that refutes a finding before it earns a write, and `ai-billing-safeguards` supplies the hard token-budget cap and kill switch a web-research swarm needs. The fan-out itself is a Dynamic-Workflows template that degrades gracefully to isolated subagents, then to a single sequential agent, and is a silent no-op offline. Web access is the agent's own `WebSearch`/`WebFetch` tool, so nothing here is an external MCP server and the MCP Registry Policy is not engaged.

The primary trigger is the standalone `/tune-prompting` command, run on demand the day a new model ships. `/update release` gains a best-effort governance step (a staleness check) that compares the profile layer's recorded roster against the live roster and flags (and offers to run) a refresh when they diverge, patterned on `platform-contract-verification` but advisory: it never blocks a release and degrades to a logged no-op offline.

Success looks like: running `/tune-prompting` after a new model release produces verified per-model profiles with cited sources, a gap report of proposed model-agnostic authoring changes, and a feature branch carrying only guard-passing edits ready for review; `/update release` surfaces a one-line staleness note when the roster has moved; and the whole feature adds no outbound dependency or credential beyond the agent's own web tool.

## Definition of Done

- `/tune-prompting` runs end to end on demand: enumerate roster, fan out research, adversarially verify, write profiles, propose and guard-gate model-agnostic edits, land on a branch, emit the gap report.
- The per-model profile layer exists in the skill bundle, is schema-valid (hard-gated in `make validate`), auto-distributes via the installer, and carries a freshness marker.
- The model-specific vs model-agnostic classifier is tested, and a model-specific finding provably cannot reach a shared body (parity guard proves it).
- The auto-apply loop is branch-isolated, guard-gated, and auto-reverts a guard-failing edit; it never commits to `develop` or `main`.
- `/update release` carries an advisory, self-gating, offline-degrading staleness step; it never blocks a release.
- `make validate`, `make test`, and ShellCheck are green; both installers register the new repo-level scripts; the skill is registered in the three `data/` registry files.

## Phase 1: Profile-layer contract and validators

**Goal**: Establish the per-model profile layer as a schema-validated, freshness-stamped, auto-distributed contract inside the new skill's bundle, plus the two repo-level scripts that validate and check it, so every later phase reads and writes a real data spine rather than an ad-hoc format.
**Prerequisites**: None (foundation phase).
**Stability Gate**: The profile schema, a machine index with a freshness marker, and at least one seed profile for a current model exist under the skill bundle; `verify_model_prompting_profiles.py` validates the schema and is wired into `make validate` (hard gate, structural); `check_model_prompting_freshness.py` exists and reports roster drift (advisory, non-blocking); both scripts are registered in BOTH installers; `make validate` and `make test` pass.
**Recommended model**: Strong reasoning tier (Opus-class), high effort. Rationale: this is the contract every other phase depends on; a wrong schema or a mis-scoped gate propagates to all later work.

### Sub-tasks

#### 1.1 - Define the profile schema and machine index

**Objective**: Fix the shape of a per-model prompting profile and its index.

**Prompt**:
> Create the profile layer inside the new skill's bundle at `catalog/skills/ai-development/model-prompting-research/`. Define a per-model human-readable profile format `references/models/<model-id>.md` (sections: model id + platform, verified prompting guidance as discrete claims, each claim's primary-source URL and a confidence tag, a "does not apply to shared bodies" reminder, and a `last_verified` date) and a machine-readable index `assets/profiles-index.json` (authoritative: the model roster this layer was last verified against as a sorted list plus a roster hash, `meta.last_verified`, and per-model an array of claim objects `{claim, source_url, confidence, scope: "model-specific" | "model-agnostic-candidate"}`). #### 1.2 - Schema validator (hard gate)

**Objective**: Make structural validity of the profile layer a build gate.

**Prompt**:

---

#### 1.3 - Staleness checker (advisory)

**Objective**: Detect roster drift without blocking anything.

**Prompt**:
> Add `scripts/check_model_prompting_freshness.py` (stdlib only): it reads the index's recorded roster + hash and compares against a roster passed on argv (the caller enumerates the live roster via `model-routing`; the script itself makes no network call). It prints a human-readable verdict - IN SYNC, or DRIFTED with the added/removed/changed model ids - and exits 0 always when `--advisory` is passed (the default for the release step) or non-zero only under an explicit `--strict` flag for local use. It MUST NOT be added to `make validate` or CI as a blocking gate (freshness is decoupled from the release clock by design). Add a pytest covering in-sync, added-model, and removed-model cases. Acceptance: the checker reports drift correctly and never blocks a release in advisory mode.

## Phase 3: Edit-routing classifier and guard-gated auto-apply

**Goal**: Turn verified findings into catalog improvements: classify each finding, confine model-specific guidance to the profile layer (hard rail), and auto-apply only model-agnostic authoring improvements to shared bodies behind the full guard suite, branch-isolated, with auto-revert.
**Prerequisites**: Phase 2 (verified findings + profiles exist).
**Stability Gate**: A classifier labels each finding model-specific or model-agnostic; model-specific findings can only write to the profile layer (a test proves a model-named edit to a shared `base-*.md` is rejected by `check_base_template_parity.py`); model-agnostic edits are applied on a dedicated feature branch (never `develop`/`main`), each followed by the full guard suite, and any guard failure auto-reverts or quarantines that single edit without aborting the run; a gap report + diff summary + `known-gaps` entries are emitted every run; `make validate` and `make test` pass on the seed dataset.
**Recommended model**: Strong reasoning tier (Opus-class), max effort. Rationale: this phase writes to the shipping catalog consumed by every platform; the correctness of the hard rail, the per-edit guard loop, and the auto-revert is the whole safety story.

### Sub-tasks

#### 3.1 - Finding classifier (the hard rail)

**Objective**: Route each finding to the correct write target.

**Prompt**:
> Implement the classifier that reads the `scope` tag on each verified claim and enforces the hard rail: `model-specific` -> profile layer ONLY; `model-agnostic-candidate` -> eligible for a shared-body edit proposal. When scope is ambiguous, default to `model-specific` (the safe default that keeps it out of shared bodies). Model-agnostic candidates target only: a SKILL.md `description`/trigger-phrase/rationalization/verification improvement, a command body clarification, or a genuinely platform-agnostic `base-*.md` line. Document the routing rules in `references/edit-routing.md`. Acceptance: a test corpus of mixed findings routes correctly, and every ambiguous case lands in the profile layer, not a shared body.

---

#### 3.2 - Guard-gated auto-apply loop

**Objective**: Apply model-agnostic edits safely and unattended.

**Prompt**:
> Implement the auto-apply loop: (a) create/checkout a dedicated feature branch `feat/tune-prompting-<stamp>` off the integration branch (stamp passed in by the command, never `Date.now()` inside a workflow) - NEVER commit to `develop` or `main`; (b) for each model-agnostic edit, apply it, then run the full guard suite - `make validate` (includes both parity `check_base_template_parity.py` and the Phase 1 schema validator), `check_version_sync.py`, `make test`, and ShellCheck on any shell edits; (c) if ALL guards pass, keep the edit; if ANY guard fails, `git checkout --` that single file (auto-revert) and record the edit in a quarantine list with the failing guard - do NOT abort the whole run; (d) after the loop, leave the branch with only guard-passing edits committed and STOP for human merge (open a PR body via the `pr-description-writer` shape if `gh` is available; otherwise print the branch + PR instructions). Confirm before the first commit (destructive-git / ask-first posture). Acceptance: on a seed dataset, a guard-passing edit is committed and a deliberately guard-failing edit is auto-reverted and quarantined, with the branch never touching `develop`/`main`.

---

#### 3.3 - Gap report and known-gaps emission

**Objective**: Make every run reviewable regardless of what auto-applied.

**Prompt**:
> Emit, every run: a gap report (Markdown, following the `catalog/style-guides/markdown.md` rules) listing per model the verified findings, what was written to the profile layer, what model-agnostic edits were applied vs quarantined (with the failing guard), and cited sources; a diff summary of the branch; and `known-gaps-tracker` entries for every quarantined edit and every UNVERIFIED model. Acceptance: the report is generated deterministically from the run's results and the quarantine/unverified items appear as known gaps.

**Prompt**:
