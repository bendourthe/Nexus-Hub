## Goal

Make both usage monitors work the way the maintainer expects on first use, without inventing capability that the platforms do not actually expose.

1. **Cursor shows live numbers with no API-key setup.** Install, click one consent prompt, see Cursor Models, Other Models, and on-demand spend. Today the panel reads "No usage data available" because HO-5 keeps live transport disabled entirely.
2. **The GitHub monitor stops being mistaken for a Copilot monitor**, and connects to the GitHub account the user actually wants for billing, without disturbing Copilot's corporate sign-in.

**Persona**: the maintainer running Cursor on a Team plan and VS Code with Copilot on a corporate account, who wants both meters accurate on install and does not want to manage tokens to get them.

## Definition of Done (observable)

- ~~A fresh Cursor install shows real included-usage numbers after exactly **one** consent click and no other setup.~~ **REWRITTEN 2026-08-06 after the T022/HO-5 probe. The original is unachievable, and not because of an implementation shortfall**: Cursor documents no personal-usage API, its SDK explicitly does not auto-discover local credentials, and of 116 bundled extensions in Cursor 3.14.27 **none** declares a Cursor authentication provider and **none** contributes a usage or billing command. - When the undocumented endpoint fails or changes, the panel degrades to cache or manual entry with an explicit staleness label and never shows a wrong number as if it were live.
- No browser cookie store, `Login Data` file, OS keychain, or process memory is read, and no billing page is HTML-scraped. The README's no-cookie / no-scrape claim remains literally true.
- The GitHub extension presents as **GitHub Billing Usage** and its copy states it covers Actions minutes and storage **and** Copilot billing for one owner.
- ~~The GitHub monitor authenticates by default against the VS Code GitHub session **only if** that session is proven acceptable to the billing endpoints; otherwise the PAT remains the default and the session path ships opt-in.~~ **Revised 2026-08-06 (see the T022 pre-work finding):** the GitHub monitor resolves auth **per billing target**, not by one global default. Credentials are never silently broadened or silently swapped. One user can legitimately end up on a session for their personal account and org A, and on a classic PAT for org B (OAuth apps restricted) and an enterprise.

## Non-goals

- Reading browser cookies, `Login Data`, keychains, or process memory. Explicitly out of bounds per the auth probe, and out of bounds here.
- HTML-scraping `cursor.com/dashboard`. The pages are dynamically rendered and their DOM is not a contract.
- Presenting any undocumented route as a documented Cursor API. Such a source is labelled `credential-api`, never `public-api`.
- Changing which GitHub account Copilot uses. The monitor is already independent of it; that stays true.
- Personal-usage data via the Cursor Admin API. It is admin-only, team-scoped, and currently omits the included-usage pool metrics.

## Phase 4: GitHub Auth via the VS Code Session

**Goal**: Let the monitor use the GitHub account VS Code is already signed into wherever that actually works, with a working log out / log in pair, without touching Copilot's session.
**Prerequisites**: Phase 3 (renamed surfaces). **T022's empirical half is maintainer-gated** - see below.
**Stability Gate**: Auth resolves per billing target and each `supported` verdict is backed by a real `200` for that target and endpoint; a negative OAuth verdict is backed by a classic-PAT control succeeding on the same target; log out then log in reaches GitHub's account picker and rebinds the monitor only; Copilot's sign-in is unaffected.
**Recommended model tier**: frontier
**Recommended effort level**: max
**Rationale**: This phase's premise is explicitly unproven in the codebase. `providers/auth.ts:99` records "Phase 1 did not prove that VS Code GitHub sessions are accepted by the billing endpoints; use SecretStorage." Shipping the session path as the default without settling that would replace a working auth model with a broken one.

> **T022 pre-work finding (2026-08-06), which reshapes this phase.** The documentary half of T022 is done and recorded in `development/github-billing-auth-probe.md`. It does **not** settle the question, and three assumptions this plan inherited are wrong:
>
> 1. **The endpoint reference cannot settle OAuth support.** Its token section is titled "Fine-grained access tokens for...", so it enumerates fine-grained support only. OAuth's absence from that list is not a rejection. Any rule of the form "session is unsupported because the doc does not list OAuth" rejects OAuth on absence of evidence and must not be used.
> 2. **GitHub's own docs conflict** for user and organization billing usage: the endpoint reference says fine-grained PATs work, while the "Automating usage reporting" tutorial says billing usage endpoints do not support fine-grained PATs and directs users to a classic PAT. Enterprise is the one documentary negative: its reference explicitly rejects fine-grained PATs and GitHub App tokens.
> 3. **A billing OAuth scope does exist** (`manage_billing:enterprise`, subsumed by `admin:enterprise`), and VS Code's built-in provider forwards caller-supplied scopes rather than filtering them against a fixed allowlist. So the session path cannot be dismissed a priori.
>
> Consequences for implementation: the discovery mechanism is the `X-Accepted-OAuth-Scopes` and `X-Accepted-GitHub-Permissions` response headers, not the prose. `AuthenticationSession.scopes` reports what was **requested**, not granted, so granted scopes must be read from `X-OAuth-Scopes`. **Classic PAT is a first-class credential class** this plan previously never mentioned, and it is the control that makes any negative result interpretable. A bare `403` or `404` proves nothing on its own, because insufficient role, organization OAuth-app restrictions, and SSO authorization all produce the same shapes.

### Sub-tasks

#### 4.1 - Settle the premise before building on it

- [x] T022a Documentary compatibility matrix, recorded doc conflict, and the corrected decision rule docs/v3/v3.15/development/github-billing-auth-probe.md
- [x] T022b Sanitized probe harness with an asserted no-leak serialization contract extensions/github-usage-monitor/src/providers/authProbe.ts
- [~] T022c **PARTIALLY RUN 2026-08-06**: the gating question is answered; the matrix is not complete docs/v3/v3.15/development/github-billing-auth-probe.md

This settles the blocking premise **in the affirmative** - OAuth-app tokens are accepted, and GitHub named the scopes (`user`; `admin:org` or `repo`, with `repo` alone sufficient) - which is what unblocked T023.
    - **Not run**: the `vscode-oauth` legs (a session needs the editor, so this wants the in-editor diagnostic) and the classic-PAT control legs. The control was **not required** for these rows: the decision rule demands a control only for a *negative* verdict, and every row here is a positive or a header-diagnosed scope gap.
    - **Still open**: whether `GitHub for VS Code`'s own OAuth app can obtain `repo` / `user` and is authorized for a given organization. Per-app authorization and SSO mean the `gh` result does not transfer. Enterprise scope is unprobed.

**Prompt**:
> This gates the whole phase, and its empirical half cannot be completed by an agent. **T022a is done**: the documentary matrix is recorded, the conflict between GitHub's endpoint reference and its usage-reporting tutorial is recorded as a conflict rather than resolved in either direction, and the corrected decision rule is written down before any evidence is read. **T022b is done**: the probe is a committed, tested module whose sanitized record cannot carry a token, an `Authorization` header, or a success body, asserted by test rather than promised by comment.
>
> **T022c is the maintainer's step.** For each billing level they have access to, run one `/settings/billing/usage` read per credential class against an account that genuinely holds the required role and has enhanced billing enabled, and record only the sanitized fields the probe emits. The classic PAT is the control: without a `200` from it on the same target, a failing OAuth result is uninterpretable.
>
> Decision rule, fixed in advance. A session is `supported` for a target only on a real `200` for that target and endpoint. A session is `blocked` only when a classic-PAT control succeeds on the same target, the OAuth call fails, and the headers or error identify a scope, OAuth-app-authorization, or token-class cause. Where the docs conflict and a live call returns `200`, record it as "empirically supported as of `<date>`; GitHub documentation is inconsistent" and keep the fallback, because that is weaker than a consistent documented contract. Enterprise fine-grained PATs are rejected documentarily and are never offered or probed.
>
> Do not proceed to 4.2 until T022c is answered for at least the levels the maintainer uses; building the default on an unverified premise is the exact failure this repository keeps re-learning.

#### 4.2 - Implement the resolved auth model

- [x] T023 Implement per-target capability resolution, not a global auth default extensions/github-usage-monitor/src/providers/auth.ts
- [x] T024 Add account identity and per-target capability display extensions/github-usage-monitor/src/settingsPanel.ts

**Prompt**:
> Do **not** encode this as `const DEFAULT_AUTH = "pat"`. >

>
> The settings panel must always show WHICH GitHub account the monitor is bound to for the configured target, because the entire point is that it may differ from the Copilot account, and it must show the capability verdict and its reason so a blocked target explains itself rather than looking broken.

## Notes for Implementers

- **The consent prompt is the whole justification for Phase 1.** The auth probe permits reading Cursor's own state database "only after explicit user authorization". Remove or weaken the prompt and the phase is no longer inside the boundary the probe authorizes.
- **Do not let Phase 4 build on an assumption.** T022 exists because `auth.ts:99` already records that VS Code GitHub sessions were never proven against the billing endpoints. Shipping the session path as default without settling it would trade a working auth model for a broken one.
- **The GitHub extension reports Copilot too.** Any copy or naming that implies Actions-only is wrong.
- **A shared pool is not a personal cap.** The Teams spend rule in the data contract applies to the new on-demand bar.
- **`ci.yml` lists test directories explicitly.** A new directory is invisible to CI until named there.
- **Environment**: `make`, `pytest`, and `ruff` are not on PATH; use `python -m`. The 2-minute tool timeout means long suites need a detached process. The repository is on OneDrive, so filesystem-heavy tests are I/O-bound and do not speed up on more cores unless fanned out across processes.
- **Precedent to honor**: v3.15.11 shipped without a plan (PR-1). This plan exists before its implementation for that reason. A release authorization covers releasing planned work; it does not authorize planning-by-omission.
