## What unblocked this

HO-6 resolved in the affirmative. The probe returned three organization `200`s with a GitHub CLI OAuth token, and GitHub's own `X-Accepted-OAuth-Scopes` named the scopes: `user` for user scope, `admin:org` or `repo` for organizations, with **`repo` alone sufficient**. That killed the "billing usage is fine-grained-PAT-only" reading and made the session path viable rather than speculative.

It did not make it *global*, which is the shape of this phase. OAuth-app authorization and SSO enforcement are per-organization settings, so one user can legitimately end up on a session for their personal account and organization A, and on a pasted PAT for organization B and an enterprise. A single default cannot express that.

## The decision that shaped the phase

**Log-out isolation is structural, not documentary.**

The requirement is that logging out of the monitor must never sign the user out of VS Code's GitHub session, because Copilot and every other extension share it. The obvious implementation is a comment saying so. That does not survive a refactor.

Instead `logOutOfMonitor` is injected a `MonitorOwnedState` with exactly three members - `clearToken`, `clearCapabilities`, `clearSessionPreference` - and **no** sign-out, revoke, or `removeSession` member. It is given no session provider at all. There is therefore no reachable path from log-out to the shared session, and no edit to the function body can create one without changing its signature. Tests assert the injected surface stays that narrow and that the function's arity is 1.

The same reasoning drove the other two guarantees: `clearSessionPreference: true` on log in is what makes GitHub show the account **picker** rather than silently reusing the last account, and `createIfNone: false` on the activation peek is what keeps activation from raising an auth dialog for a user who only opened an editor.

## Troubleshooting trail

1. **BG-13: scope escalation would have requested breadth it did not need.** `nextScopeEscalation` first escalated whenever an accepted scope was ungranted. But a credential already holding `repo` - which GitHub lists as accepted - that *still* failed is not facing a scope problem; it is facing role, SSO, or app approval, none of which a broader scope fixes. Requesting `admin:org` there is precisely the silent broadening the plan forbids. Now returns null in that state, consistent with `diagnoseBlockedReason`, which only reports `insufficient-scope` when no accepted scope is granted. Caught by the test written alongside the function.
2. **BG-14: the new commands would have shipped unexercised.** `logIn` / `logOut` were registered with no test driving them, and the vscode stub had no `authentication` surface, so a test that tried would have failed on a missing API rather than on behavior. That is the same defect class as v3.15.11's BG-9/BG-10, where a hook shipped registered and permanently inert. The stub gained `authentication.getSession` with a scripted session queue and a request log; three tests now drive the real handlers through `activate()`, one of which asserts log out never calls `getSession` with `createIfNone` or `clearSessionPreference`.
3. **A Phase 3 test caught the Phase 4 change.** `test_github_billing_rename.py` pinned the manifest command count at 9, and two new commands make 11. Updated deliberately with a note rather than relaxed to a range: the exact count is what would catch a dropped command.

## What was not achieved, and why

**The `vscode-oauth` leg of T022c is unrun.** A session can only be obtained inside the editor, so per-app authorization and SSO for `GitHub for VS Code` specifically remain unverified. The `gh` result does not transfer, because both are per-app.

This is handled rather than hidden: an unprobed target reports `unknown`, and `unknown` is never treated as `supported`. The code assumes neither answer. Closing it needs an in-editor diagnostic, which doubles as a permanently useful command rather than throwaway probe code.

**Enterprise scope is unprobed** - no enterprise slug on the reference account.

**MT-5 now also covers the new panel copy.** None of the Authorization section has been seen rendered in a real VS Code window.
