## 2. Chronological Steps

### 2.1 Verified the Google include assumption before relying on it

The plan flagged this as an assumption to confirm rather than trust, and confirming it changed the task list. Result:

So one edit to `base-google-shared.md` covers four Google surfaces, and the four include-only shims must NOT carry their own copy or the rule would load twice for one platform. That became an explicit test.

### 2.2 T011 - Authored the rule

`docs/v3/v3.15/development/end-of-task-summary-rule.md` records the verbatim body and the reasoning. Six bullets: summarize even small changes, what changed in one or two lines, the concrete next step or an explicit "nothing outstanding", state blocked or skipped work rather than omitting it, stay scannable, and the carve-out.

Two decisions worth keeping:

**Why instruction text at all.** A hook cannot do this: by the time `Stop` fires the agent has finished generating, so a hook can only print its own text. A skill would under-trigger against an "always" requirement, which is the exact failure mode AGENTS.md's pushy-description rule exists to counter. Always-loaded text is the only mechanism that satisfies "every completed task", which is also why it is budgeted to six bullets.

**Why the carve-out names the rule class, not the section.** Eleven templates carry `## Output Minimization`, telling the agent to suppress verbose output. A bare "always summarize" rule can be resolved against that in either direction. The final bullet therefore reads "Output-minimization rules never apply to this summary" rather than naming the heading, because `generic-instructions.md` has no such section and naming it would leave a dangling reference in one of the twelve. Naming the class also keeps the body byte-identical everywhere, which `INVARIANT_SECTIONS` requires.

### 2.3 T012-T015 - Applied to all 12 substantive templates

Inserted the identical body immediately after `## Output Minimization` in the eleven files that have it, so the carve-out sits adjacent to the rule it qualifies, and after `## Global Style & Communication Preferences` in `generic-instructions.md`, which has a different structure. Applied by script rather than by hand so all twelve bodies are byte-identical by construction.

The section matches the templates' local compact style (no blank line between heading and first bullet) rather than the generated-Markdown style guide, because consistency inside the file is what a reader of that file sees.

### 2.5 T017 - Corrected AGENTS.md

### 2.6 T018 - Test for the coverage the guard cannot see

`tests/validators/test_end_of_task_rule.py`, 20 cases. The parity guard covers the lockstep five and looks at nothing else, so the seven unguarded substantive templates were the real gap. The tests assert: every substantive template carries the section; the body is identical across all twelve (not just the guarded five); the four include-only shims do NOT carry a local copy; the section stays within a line budget because it is always-loaded; the carve-out is present and phrased as an absolute; and the heading is in both guard lists.

One test was wrong on the first run and worth recording. It searched the guard's **source text** for the heading, which matched the module docstring (it mentions both list names) and would have passed even with the heading absent from either list. Rewritten to import the module and assert against the real `REQUIRED_HEADINGS` and `INVARIANT_SECTIONS` values. A test that greps source for a constant name is testing the documentation, not the behavior.

## 4. Known Issues Carried Forward

- **The seven unguarded templates stay unguarded by the parity script.** `check_base_template_parity.py` is scoped to the lockstep five by design, and widening it was out of scope here. The new test covers the gap for this rule specifically, but a future shared section added to all twelve would need its own coverage or would drift silently. A general "all substantive templates agree" guard is a candidate for a later release.
- **Copilot and OpenCode receive this rule but cannot receive Phase 1's notification hooks** (no hook surface, and a JS/TS Bun plugin runtime respectively). That asymmetry is why the release has two deliverables rather than one.
- **Phase 3 still owes the first-party event-vocabulary verification** before any notification hook ships to another platform, plus the DF-1 settlement.
