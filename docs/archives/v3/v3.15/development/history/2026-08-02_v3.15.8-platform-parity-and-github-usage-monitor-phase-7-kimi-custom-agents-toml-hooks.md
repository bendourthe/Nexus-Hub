## 2. Chronological Steps

### 2.1 Re-verify the Kimi contract, which changed the phase

**Branch**: `feat/v3.15.8-platform-parity` | **PR**: N/A | **Merged to**: not merged

**Plan specification**: The phase prerequisite is a completed Kimi scope and schema re-verification. Sub-task 7.1 says to add agents "only if the official schema supports user-authored agents"; 7.2 says to "reject unsupported TOML or undocumented paths".

**What happened**: Read the official agents, hooks, built-in tools, and configuration references. Four findings reshaped the work.

**Agents need no transform.** Kimi discovers Markdown files with YAML frontmatter and explicitly documents the Claude Code shape as loadable: `description` is the only required field, `name` falls back to the filename, the comma-separated `tools` form exists specifically "to keep Claude Code-style agent files loadable", and unknown fields are ignored so foreign fields do not break loading. The catalog already ships exactly that shape, so this is a copy, not a transform -- the opposite of Codex, which needed Markdown-to-TOML.

**Hooks cannot carry an ownership field.** `[[hooks]]` permits only `event`, `matcher`, `command`, and `timeout`, and the docs state that "extra fields will cause the config file to fail to load". So the handler-`name` ownership Phase 6 used is not merely unavailable -- emitting it would break the user's whole configuration. `timeout` is also in seconds here (1-600), not the milliseconds the Gemini-CLI-class platforms use, and each entry holds exactly one command where the catalog groups several.

**Tool names are Claude's.** The built-in tools reference confirms `Read`, `Write`, `Edit`, `Grep`, `Glob`, and `Bash`, with `Skill` documented elsewhere as a tool. So the matcher mapping is near-identity, unlike the Gemini-CLI-class rename to `run_shell_command` / `write_file` / `replace`.

**There is no project hook path.** Kimi's project-local config is `.kimi-code/local.toml`, documented as holding only a `[workspace]` table with `additional_dir`; `[[hooks]]` appears exclusively in the user-level `~/.kimi-code/config.toml`. The matrix's assumed `.kimi-code/config.toml` does not exist.

**Key files changed**: none - verification step

**Troubleshooting**: The configuration page 404s at the `.html` URL used elsewhere in the docs; the extensionless path serves it. Two decisions were put to the maintainer rather than assumed: whether to copy agents verbatim or augment them with the handoff framing Kimi recommends for delegated sub-agents, and whether to claim the shared `~/.agents/agents/` path. Both came back conservative -- verbatim, native-only.

### 2.3 Merge TOML hooks through a marker-delimited managed block

**Branch**: `feat/v3.15.8-platform-parity` | **PR**: N/A | **Merged to**: not merged

**Plan specification**: Merge the verified `config.toml` hook entries using a TOML-aware parser or a narrowly proven structured strategy, give every hook a stable identity, preserve comments and unrelated user entries where the parser permits, back up before mutation, and remove only owned entries on teardown.

**What happened**: Comment preservation and a four-field-only schema together rule out both obvious approaches. `tomllib` is read-only, so a parse-and-re-emit round trip would need a non-stdlib dependency and would still reformat the user's file; and there is no field available to carry a per-entry identity.

The strategy is a marker-delimited managed block (`# >>> NEXUS_HUB_HOOKS_START >>>` to `# <<< NEXUS_HUB_HOOKS_END <<<`) appended to `config.toml`, reusing the marker-merge convention Nexus-Hub already applies to instruction files. The user's TOML is never parsed and re-emitted -- only that region is spliced -- so comments, table order, and whitespace outside the block survive by construction. `[[hooks]]` is an absolute array-of-tables header, so appending at end of file is valid regardless of what precedes it. The block is the identity, which solves ownership without a field.

Safety is layered. A file that is *already* invalid is left untouched and logged, because it is the user's to fix and splicing into it would make our block look like the cause. The merged result is parsed with `tomllib` before it is committed, and a parse failure writes nothing. The previous content is backed up beside the file and the write goes through a temp file replaced atomically.

`build_kimi_hooks` expands each catalog group into one entry per command, suppresses duplicate event-matcher-command triples, drops `PowerShell` (Kimi routes every shell call through `Bash` on all platforms), and folds `MultiEdit` into `Edit`. Commands are host-selected via the Phase 6 `script_for_host` / `command_for` helpers rather than reimplemented.

**Key files changed**: `scripts/lib/integrations/_kimi_native.py`, `scripts/lib/integrations/kimi.py`

**Troubleshooting**: None in the merge itself; the layered validation was designed in rather than debugged in.

Finally `test_uninstall_reverses_install[kimi]` raised `PermissionError` from `rmdir` on a directory that `iterdir()` reported as empty. That is the Windows delete-pending state: a file whose handle another process still holds disappears from the listing but keeps blocking removal. The same code shipped in Codex in Phase 5 and in the Phase 6 mixin, so this was a latent crash in three places -- and crashing partway through teardown is much worse than the cosmetic problem it was trying to solve, because it abandons the rest of the uninstall. Directory removal is now the shared `remove_dir_if_empty`, which logs and reports `kept` instead of raising, and all three integrations call it.

## 5. Plan Discrepancies

- 7.1 allows agents "only if the official schema supports user-authored agents". It does, and more permissively than expected -- no transform is needed at all, so the sub-task shipped as a copy rather than the generated conversion the matrix anticipated.
- 7.2 asks for "a TOML-aware parser or a narrowly proven structured strategy" and "stable IDs". A parser round trip would need a non-stdlib dependency and would reformat the user's file, and the schema has no field for an ID, so the marker block is the narrowly-proven strategy and the block itself is the identity.
- 7.2's workspace half is not delivered. The matrix named `.kimi-code/config.toml`; that file does not exist, so the row is corrected and DF-13 records the reason. This is 7.2's own instruction to reject undocumented paths, applied.
- The plan did not anticipate fixing base-class or installer defects here. Two were found by this phase's tests and fixed because both fell inside its stated scope: manifest-driven repair (a matrix requirement) and the absence of deprecated Kimi paths (an exit-checklist item).
- No implementation sub-task was skipped. 7.3 is closed by this local commit.

## 6. Assumptions Made

- **Kimi's tool names are stable enough to match on**: `Read`, `Write`, `Edit`, `Grep`, `Glob`, and `Bash` are documented in the built-in tools reference, and `Skill` appears as a tool in the agent and prompt-variable docs. A future rename would surface as a matcher that never fires, not as a wrong action.
- **`Edit` covers `MultiEdit`**: Kimi's `Edit` handles repeated replacement through `replace_all` rather than exposing a second tool, so folding is a superset match that can over-trigger a guardrail, never under-trigger it.
- **Appending the block at end of file is always valid TOML**: `[[hooks]]` is an absolute array-of-tables header, so it cannot be captured by a preceding table's scope. The `tomllib` validation before commit is what makes this a checked assumption rather than a bet.
- **A marker comment is stable across Kimi versions**: TOML comments are `#`-prefixed and ignored by any parser, so the markers cannot become semantically meaningful. The risk is a user deleting them by hand, which degrades to a duplicate block on the next install rather than a broken config.
