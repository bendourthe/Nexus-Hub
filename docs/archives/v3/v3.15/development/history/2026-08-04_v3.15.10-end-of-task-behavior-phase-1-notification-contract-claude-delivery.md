## 2. Chronological Steps

### 2.1 T001 - Lock the trigger contract

Authored `docs/v3/v3.15/development/end-of-task-notification-contract.md`. Two triggers: `Notification` for attention-required (permission request or idle-waiting-for-input) and `Stop` for task-complete. `SubagentStop`, `PostToolUse`, and the other per-turn events are explicitly forbidden with the reason recorded. Label format is `<repo> (<branch>)` with a four-step resolution order. The kill switch is defined as a file the hook stats on every invocation, and the measured reason an environment variable is insufficient is recorded in the doc itself so it cannot be lost.

The contract is also honest about what trigger B cannot know: there is no separate "the whole task is done" event, because from the harness's perspective a turn ending IS the agent handing control back. Trigger B fires on that and says so, rather than pretending to infer completion. Guessing between "finished" and "stopped to ask" would be wrong in both directions, and trigger A covers the asking case through a genuinely different event.

### 2.2 T002-T003 - Shared helper

Added `catalog/hooks/_notify_common.{sh,ps1}` with three helpers: `nexus_notify_label` / `Get-NexusNotifyLabel`, `nexus_notify_suppressed` / `Test-NexusNotifySuppressed`, and `nexus_notify_send` / `Send-NexusNotification`. The leading underscore marks it a module rather than a registerable hook, matching the `_skill_rules.py` precedent.

Putting the label resolution in one place is the point: two hooks with two shells is four copies of the same fallback chain, and the `work` defect came from exactly that kind of duplicated detail drifting.

### 2.3 T004-T007 - The two hooks

Rewrote `notify-on-complete.{sh,ps1}` over the helper and added `notify-attention-required.{sh,ps1}`. Both drain stdin so the harness never blocks on an unread pipe, and both exit 0 unconditionally.

Deliberate decision: neither hook uses the payload for its message body. The old completion hook read `session_duration` to decorate the text; the new one ignores it, because a duration is not a reason to notify or to stay silent, and the label answers the question that actually matters (which workspace). The attention hook likewise discards the harness's own `message` field, since its wording varies by trigger while the hook's job is to say WHICH workspace wants attention.

### 2.4 Dry-run mode (added mid-phase, not in the plan)

Writing the tests surfaced a gap the plan had not anticipated: with no dry-run path, a test either pops real desktop toasts onto the developer's screen or cannot assert the label at all. Added `NEXUS_NOTIFY_DRY_RUN`, which prints `<title>\t<message>` to stdout instead of notifying. It makes the label an assertable observable, gives both shell implementations the identical observable so one assertion doubles as the parity check, and is useful by hand for confirming label resolution. Documented in the contract.

### 2.5 T008 - Registration

Added a `Notification` chain to `catalog/hooks/settings.json` running `notify-attention-required.sh`, and confirmed `Stop` still runs `notify-on-complete.sh` only. `SubagentStop` is absent. Per the existing convention only the bash invocation is registered; `.ps1` siblings are not separately registered.

### 2.6 T009 - Tests

Added `catalog/hooks/tests/test_notify_triggers.py`, 55 cases via a `run` fixture parametrized over both implementations, so every behavioral assertion doubles as a parity assertion. The load-bearing ones pin the three field defects: the label names the repository when the hook runs from a subdirectory (the `work` regression), the switch file silences the hook with `NEXUS_DISABLED_HOOKS` and `NEXUS_HOOK_PROFILE` deliberately absent from the environment, and `SubagentStop` is asserted absent from `settings.json`. Also covered: the `CLAUDE_PROJECT_DIR` fallback outside a git tree, backward compatibility of both legacy env controls, a near-miss hook name that must NOT suppress, the two triggers saying different things, exit 0 across five payload shapes including malformed JSON, and the shared helper never being registered as a hook.

### 2.7 Installer-awareness check

Verified rather than assumed, because the golden rule makes this a per-change obligation. Both installers copy several hooks by EXPLICIT NAME (`git-guardrails.sh`, `compress-output.sh`, `usage-display.sh`) and neither contains a folder-level copy of `catalog/hooks`, which initially looked like the new files would not ship. They do: the registry-based `claude` integration declares `hooks_subdir: "hooks"` with `hooks_supported: True`, and `base.py` performs a verbatim tree copy of `catalog/hooks`. Confirmed against reality on this host: all 35 files in `~/.claude/hooks/` are present and nothing registered in `settings.json` is missing from disk. The legacy named copies are a redundant subset serving the guardrails path. **No installer edit is required, and none should be added.**

### 2.8 Shared-fixture fix found by running the suite

The first full parity run passed (262 tests, 318s) but did two things it should not: it raised real desktop toasts, and it spent 5.5 seconds per notification invocation keeping the tray icon alive. `isolated_env` in `test_hook_sibling_parity.py` exists precisely so tests "must not touch the developer's real environment", and a desktop toast is touching it. Added `NEXUS_NOTIFY_DRY_RUN=1` to that fixture and added `NEXUS_NOTIFY_DISABLED_FILE` to its ambient-pop list so a developer's real switch file cannot leak into a parity expectation. This is in the spirit of the fixture rather than a special case for these hooks.

### 2.9 Two production bugs the full-suite run exposed

Running the new test file alone passed 55/55. Running the whole `catalog/hooks/tests` tree failed 4 of 984, all of them the `ps1` variants of the two label tests. Both causes were real defects in the shipped helper, not test artifacts, and neither was reachable by running the new file in isolation.

**Bug 1: an intermittent `$LASTEXITCODE` race that silently degraded the label.**

The failure signatures differed, which is what identified it:

- `test_label_names_repo_when_run_from_a_subdirectory[ps1]` produced `Task complete - hooks`, meaning `git rev-parse --show-toplevel` failed and resolution fell all the way through to the current directory's leaf.
- `test_label_includes_the_branch[ps1]` produced `Task complete - Nexus-Hub` with no branch, meaning the root lookup also failed (falling back to `Get-Location`, which happened to be the repo root) and the branch lookup failed too.

The cause was `& git ... | Select-Object -First 1`. Piping a native command **directly** into `Select-Object -First 1` stops the upstream pipeline early (`StopUpstreamCommandsException`, PowerShell 3+), which can terminate git before `$LASTEXITCODE` is assigned. The guard `if ($LASTEXITCODE -eq 0 ...)` then read an unset or stale value and discarded a perfectly good result. It is a race, so it passed in isolation and lost under load.

This would have shipped a user-visible defect: under load a real notification would have read `hooks` instead of `Nexus-Hub`, which is the exact class of mislabeling this release exists to fix. Fixed by capturing the native command's output fully, then indexing it (`$out = & git ...` then `@($out)[0]`).

**Bug 2: assignment to `$home`, a readonly automatic variable.**

Caught by the editor's PSScriptAnalyzer diagnostic (`PSAvoidAssignmentToAutomaticVariable`) rather than by a test, because no test reached the line. `Test-NexusNotifySuppressed` resolved the default switch path with `$home = $env:HOME`, and `$home` is built into PowerShell and readonly. Renamed to `$userHome`.

The test gap mattered more than the bug: every suppression test set `NEXUS_NOTIFY_DISABLED_FILE` explicitly, so the default-path branch had **zero** coverage, which is why an outright error in it went unnoticed. Added two tests that redirect `HOME` / `USERPROFILE` and exercise the default `~/.nexus-hub/notifications-disabled` path, one asserting suppression with the file present and one asserting the hook still notifies with it absent, so the pair cannot pass by silencing everything. Suite went from 55 to 63.

**Lesson for later phases**: run the whole tree, not just the new file. Both defects were invisible to the file in isolation, and one of them was a race that only a loaded run surfaces.

## 4. Known Issues Carried Forward

- **Windows linger not shortened.** The plan proposed reducing the 5.5-second post-`ShowBalloonTip` sleep. It was not reduced: disposing a `NotifyIcon` too early can cancel a queued toast on Windows 10 and 11, and finding the shortest safe value requires observing a rendered toast on a live desktop, which no test here can do. Exposed as `NEXUS_NOTIFY_LINGER_MS` so it can be measured and tuned deliberately. Open.
- **Trigger A portability is unknown outside Claude Code.** Whether any other platform exposes an event meaning "waiting on the human" is a Phase 3 question and must be verified against first-party docs before a hook ships. An unverified event name produces a hook that silently never fires, which `escalation-trigger.sh` already demonstrated once.
- **AGENTS.md's hook-event list is stale** and now further out of date: it names four events while `settings.json` registers eight (`SessionStart`, `SessionEnd`, `PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `PreCompact`, `Stop`, and now `Notification`). Correcting it is Phase 2 T017; this phase widened the gap rather than closing it.
- **The maintainer's local override is still in place.** `~/.claude/hooks/notify-on-complete.sh` carries a dated `exit 0` guard added on 2026-08-04 to stop the per-turn storm. It is a machine-local file, not the repo. It must be removed (or the installer re-run) for the new behavior to take effect on this machine.

## 5. Deviations

Two additions the plan did not list, both discovered by doing the work:

1. **`NEXUS_NOTIFY_DRY_RUN`** was not in the plan. Without it the phase's own acceptance criterion (an assertable label) is untestable without side effects on the developer's desktop.
2. **The `isolated_env` fixture edit** touches a shared test file rather than only this phase's new code. Justified because the fixture's documented contract was already being violated the moment a notification hook entered the suite.

The plan's suggestion to shorten the Windows linger was consciously NOT followed, with the reasoning recorded above rather than silently skipped.
