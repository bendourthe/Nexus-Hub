## Sub-tasks completed

### 1.1 - Profile schema and machine index

- Created `catalog/skills/ai-development/model-prompting-research/` with three files: `assets/profiles-index.json` (authoritative), `references/schema.md` (the contract doc), and `references/models/claude-opus-5.md` (the seed mirror).
- Index schema 1.0.0 fixes exactly three top-level keys (`schema_version`, `meta`, `models`). `meta` carries `last_verified` (`YYYY-MM-DD`), `platform`, `roster_source` (one of `api` / `picker` / `config` / `manual`), a sorted unique `roster`, and a `roster_hash` defined as `sha256` of the sorted roster joined by single newlines, UTF-8 encoded. Each model entry carries `platform`, `last_verified`, and a non-empty `claims` array of `{claim, source_url, confidence, scope}` objects with an optional `note`.
- `scope` is the hard rail documented in `references/schema.md`: `model-specific` routes to this layer and nowhere else; `model-agnostic-candidate` becomes eligible for a proposed shared-body edit. An ambiguous claim must be `model-specific`, because defaulting that way is merely unhelpful whereas the reverse ships a model-specific line to every platform.
- Seeded `claude-opus-5` from the roster read off the Claude Code model picker (four ids), provenance-tagged `roster_source: picker`. The single claim is tagged `confidence: unverified` and `scope: model-specific` with a TODO note. This is deliberate: no adversarial-verify pass has run, so writing a claim marked verified (with an invented citation to match) would be fabrication, and it would undermine the exact mechanism the release is being built to provide. The seed doubles as a demonstration of the ambiguous-defaults-to-model-specific rule.

### 1.2 - Schema validator (hard gate)

- Added `scripts/verify_model_prompting_profiles.py`: stdlib-only, offline, exit 0 valid / 1 invalid.
- Validates the top-level key set, the full `meta` block, roster sortedness / uniqueness / non-emptiness, `roster_hash` self-consistency (recomputed from `meta.roster` in the same file, which catches a hand-edited roster whose hash was not re-stamped), every claim's shape with allowed `confidence` and `scope` values, and a BOTH-directions match between `models` keys and `references/models/*.md` stems.
- Rejects unknown keys at the top level, in `meta`, in a model entry, and in a claim, so a `sources_url` typo fails loudly instead of being silently ignored.
- Two deliberate non-checks, both documented in the module docstring and covered by dedicated tests: it never judges freshness (no clock read), and it never requires roster coverage (a rostered but unprofiled model is an UNVERIFIED known-gaps item, reported as a note, not a failure).
- Discovers the bundle at the in-repo catalog path and at the FLATTENED `skills/<name>/` layout the installer writes to platform targets, plus an explicit `--bundle` override, so the installed copy under `~/.nexus-hub/scripts/` is usable against an installed tree.
- Wired into the `Makefile` `validate` target and the CI `validate` job, positioned immediately before the platform read-contract checks so the structural-versus-freshness contrast is visible to a future editor.

### 1.3 - Staleness checker (advisory)

- Added `scripts/check_model_prompting_freshness.py`: stdlib-only, and it makes no network call. The caller enumerates the live roster (via `model-routing`) and passes the ids on argv, which keeps the outbound dependency in the agent's own web/API surface rather than in a repo script.
- Verdicts: IN SYNC; DRIFTED with `added` / `removed` lists, plus a distinct "roster ids match but the hash was not re-stamped" case; and UNKNOWN when no live roster is supplied, no bundle is found, or the index is unreadable.
- Exits 0 on every path in the default advisory mode (`--advisory` is accepted explicitly and is a no-op affirmation). Only `--strict` propagates a non-zero exit, and the two flags are mutually exclusive at the argparse level.
- Deliberately NOT added to `make validate` or CI. The module docstring states the reason and contrasts it with `check_platform_contract_freshness.py`, which DOES hard-gate: the platform read-contract must be re-verified for the release being cut, whereas gating profile freshness would let a vendor shipping a model on a Tuesday wedge every release.
- Imports `find_bundle`, `roster_hash`, `INDEX_REL`, and `SKILL_NAME` from the validator rather than redefining them, so the two scripts can never disagree about where the layer lives or how a roster hashes.

### 1.4 - Installer registration (both installers)

- Added a paired copy block to `scripts/installer.sh` (`safe_copy`, in `install_templates`) and `scripts/installer.ps1` (`Safe-Copy`, in `Install-Templates`), both targeting `~/.nexus-hub/scripts/`, placed next to the existing trigger-eval block and modeled on the `generate_report.py` precedent. Each comment notes that the two scripts must land together (the freshness checker imports from the validator) and that the skill bundle itself needs no installer entry, because the recursive skill-folder copy handles it.
- **Verified for real, not just statically.** A full headless installer run exceeded the host time budget (the documented WN-v36-1 Windows constraint), so instead the ACTUAL function bodies were extracted from each installer (`install_templates` plus `safe_copy` / `safe_folder_copy`; `Install-Templates` plus `Safe-Copy` / `Safe-Folder-Copy` via the PowerShell AST) and executed against throwaway HOME directories. Result on both hosts: both scripts land, are byte-identical to source, and the installed validator runs standalone against the repo bundle (exit 0).
- The repo's generalized guard `test_installers_copy_every_scripts_dir_py_file` passes. A name-level diff of the two copy blocks shows 28 shared `.py` scripts in bash and 29 entries in PowerShell, the only delta being `generate_release_changelog.ps1`, a legitimately PowerShell-only sibling, so shared-script parity holds.

### 1.5 - Testing, stabilization, and CI

- 62 new tests in `tests/validators/test_verify_model_prompting_profiles.py` (37) and `tests/validators/test_check_model_prompting_freshness.py` (25), subprocess-invoked through the shared `runner` fixture to match the established validator-test convention (local `REPO_ROOT`, no conftest import).
- Validator coverage: the shipped seed as the must-pass baseline; bundle discovery including the flattened installed layout, a missing bundle, a missing index, and unparseable JSON; 24 parametrized mutations, one per documented structural rule; six wrong-JSON-shape guards (a non-object top level, `meta` as a string, `models` as a list, a model entry as a string, `claims` as a string, a claim as a string); both mirror-mismatch directions; and the two deliberate non-checks.
- Freshness coverage: all three drift verdicts plus combined added-and-removed and the stale-hash case; argv normalization (order and duplicates do not matter); and the non-blocking contract itself, asserting that drift, an absent roster, a missing bundle, a corrupt index, and a malformed roster ALL exit 0 in advisory mode while `--strict` returns 1.
- **Coverage measurement needed explicit plumbing.** Because the tests spawn subprocesses, a plain `pytest --cov` collects nothing ("Module ... was never imported"). Re-measured with `COVERAGE_PROCESS_START` pointing at a BOM-free config plus `coverage combine`, branch coverage on: validator 94%, freshness checker 97%, combined 97%, against the 80% gate. Recorded as MT-2, because CI does not run coverage for this tree at all.
- CI: added the validator as a step in the existing `validate` job. See the deviation note below for why no separately path-filtered job was created. The new pytests need no CI edit; they ride the existing `pytest tests/validators -v` step.

## Deviations from the plan

- **1.5 CI path filter** (recorded as known-gap DF-1). The plan asks for "a path filter scoped to the skill bundle + the two scripts". Implemented instead as a step inside the existing `validate` job, in service of the plan's own CI-optimization goal: that job already triggers on any non-docs change (the workflow-level `paths-ignore: docs/**` covers `catalog/**` and `scripts/**`) and already carries concurrency cancel-in-progress and pip caching, so a dedicated path-filtered job for two fast stdlib scripts would add a cold runner (checkout plus setup-python) rather than save action minutes. The same call was made and recorded at v3.15.1 QG-1, v3.15.2 DF-1, and v3.15.4 Phase 6.3.
- **1.4 dry-run install method**. The plan's acceptance names "a throwaway-HOME dry-run install". A full installer run timed out on this Windows host (WN-v36-1), so the real `install_templates` / `Install-Templates` function bodies were extracted and run against throwaway HOMEs instead. This exercises the actual installer code for the block under test rather than a reimplementation, and the end-to-end full install is covered by CI's `bootstrap` and `bootstrap-windows` jobs.
- **No docs-cleanup-report file** (step 8.5). The audit was clean, and no v3.15 phase has produced such a file (only v3.1, v3.12, and the archived v2.3 have one), so the result is recorded inline here and in the devlog rather than adding an artifact the tree does not otherwise carry.
