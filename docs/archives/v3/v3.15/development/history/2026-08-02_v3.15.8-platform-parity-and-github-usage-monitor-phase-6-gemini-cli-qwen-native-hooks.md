## 2. Chronological Steps

### 2.1 Re-verify both schemas before writing anything

**Branch**: `feat/v3.15.8-platform-parity` | **PR**: N/A | **Merged to**: not merged

**Plan specification**: The phase prerequisite is that Phase 1's hook-event mapping is approved, and 6.1 requires translating "only the verified Gemini CLI hook events" while 6.2 requires rejecting "unsupported TOML or undocumented paths".

**What happened**: Read the upstream Gemini CLI hooks reference and the Qwen Code hooks documentation. Four findings changed the design from what the matrix had assumed.

First, Gemini CLI **renamed every lifecycle event** relative to the Claude-style names the catalog uses: `PreToolUse` is `BeforeTool`, `PostToolUse` is `AfterTool`, `UserPromptSubmit` is `BeforeAgent`, `Stop` is `AfterAgent`, and `PreCompact` is `PreCompress`. Qwen kept the original names, so its map is identity for every event the catalog registers. Second, **matchers are regular expressions over each platform's own tool ids**, not literals over Claude's tool names, so `Bash` has to become `^(run_shell_command)$`. Third, **neither platform has a `commandWindows` slot**, and both route every shell call through a single `run_shell_command` tool, which collapses the catalog's separate `Bash` and `PowerShell` matchers onto one id. Fourth, hooks are **enabled by default** on both, so unlike Codex there is no feature switch to set -- only a user-set kill switch (`disableAllHooks`) to respect.

The reading also surfaced a genuine alternative: Gemini CLI extensions are a fourth hook-precedence layer, reading `~/.gemini/extensions/<name>/hooks/hooks.json` with `${extensionPath}` and `${/}` substitution that would solve the absolute-path and separator problems outright.

**Key files changed**: none - verification step

**Troubleshooting**: None. The extension finding was put to the maintainer rather than decided unilaterally, along with the Windows-dispatch question and whether the existing enterprise and detection gates should change.

### 2.2 Build the shared translation module

**Branch**: `feat/v3.15.8-platform-parity` | **PR**: N/A | **Merged to**: not merged

**Plan specification**: Translate only verified events into the local hook model, use structured merge where the platform owns a shared config, isolate Nexus-Hub entries with stable identity, and support repair and teardown without removing user hooks.

**What happened**: Added `scripts/lib/integrations/_settings_hooks.py` with a frozen `SettingsHookSpec` capturing exactly what differs between the two platforms -- the event map, which events take a tool matcher, the project-directory variable, and whether `shell` and `statusMessage` are documented. `GEMINI_CLI_SPEC` and `QWEN_SPEC` are both written out longhand rather than derived, including Qwen's identity mapping, so an upstream rename shows up as a diff here instead of passing through silently.

`build_settings_hooks` walks the catalog settings, drops any event with no counterpart, translates each matcher into an anchored regex over platform tool ids, and drops `Skill` outright because neither CLI surfaces skill invocation as a tool call. Matchers are emitted only for tool events; the lifecycle events match on a session source or a compact trigger, so a tool matcher there would produce a registration that can never fire.

Added `_settings_hooks_mixin.py` for the install and teardown choreography both platforms share -- copy the host's scripts, merge, warn on the kill switch, prune on teardown. Putting it in one place is deliberate: two hand-written copies is precisely how the two platforms would drift apart in ownership behavior, which is the class of defect the v3.15.6 hook-sibling parity work exists to prevent.

**Key files changed**: `scripts/lib/integrations/_settings_hooks.py`, `scripts/lib/integrations/_settings_hooks_mixin.py`

**Troubleshooting**: None in the translation itself.

### 2.3 Resolve the missing `commandWindows` with host-aware selection

**Branch**: `feat/v3.15.8-platform-parity` | **PR**: N/A | **Merged to**: not merged

**Plan specification**: Keep `.sh` and `.ps1` behavior equivalent (6.1 / 6.2 both require cross-shell parity).

**What happened**: With one command slot per handler and no Windows override, the choice is made at install time from the host. A Windows install registers the `.ps1` sibling and the PowerShell-flavored guardrails (`format-powershell-description`, `require-powershell-description`); a POSIX install registers the `.sh` and the Bash-flavored ones. Registering both would fire the Bash and PowerShell variants of the same guardrail on a single `run_shell_command` call, which is worse than picking one. Both siblings are copied either way, so re-running the installer on the other OS only re-points the registration.

Workspace-scope commands resolve through the platform's own `$GEMINI_PROJECT_DIR` / `$QWEN_PROJECT_DIR` variable rather than an absolute path, so a committed project `settings.json` does not carry one developer's home directory. On Windows the variable is written in PowerShell's `$env:` form to match the PowerShell command. Qwen additionally gets its documented `shell` field set to the host shell, alongside -- not instead of -- the fully-explicit interpreter command, so the registration still runs correctly if the field is ignored or defaulted.

**Key files changed**: `scripts/lib/integrations/_settings_hooks.py`

**Troubleshooting**: The Windows command quotes its path, because a hooks directory under a user profile routinely contains a space. That is asserted by a dedicated test rather than left to inspection.

### 2.4 Wire both integrations and flip the contract rows

**Branch**: `feat/v3.15.8-platform-parity` | **PR**: N/A | **Merged to**: not merged

**Plan specification**: Match Bash, PowerShell, registry, verify, repair, and teardown semantics; retain existing surfaces; update both contract files together.

**What happened**: `GeminiCliIntegration` and `QwenIntegration` each mix in `SettingsHooksMixin`, declare their spec, set `hooks_supported = True`, install hooks at both scopes behind the existing `instruction_only` guard, and override `teardown` to prune before the manifest sweep. Neither sets `hooks_subdir` on the base class, because hooks here are a merge rather than a tree copy.

Ownership is the `nexus-hub:` handler `name`. Both schemas carry `name` for logging, and Gemini CLI fingerprints project hooks on name plus command, so a stable name additionally stops the untrusted-hook warning from re-firing on every install. The installed hooks directory is checked as a second signal, so a handler a user renamed by hand is recognized as ours rather than duplicated.

The merge is deliberately stricter than Codex's: `settings.json` holds the user's model, theme, and MCP configuration, so every unrelated key is preserved, the previous content is backed up beside the file, the write goes through a temp file, and a malformed file is left exactly as found. Teardown untracks the file before the manifest sweep so the user's configuration is never deleted.

Flipped all four matrix rows to enforceable with a Phase 6 decision note, added `hooks_supported` and settings-file `doc_mentions` to both `contract_checks` blocks, added Qwen `install_verify` surfaces for `~/.qwen/settings.json` and `~/.qwen/hooks`, closed both `resolved_in` fields on the drift audit, rewrote the Markdown surface-table rows (adding the previously-absent Gemini CLI workspace row), and added a prose section covering the renames, the regex matchers, the host selection, and the ownership model. Both installers route these platforms through the Python registry already, so only their comments changed.

**Key files changed**: `scripts/lib/integrations/gemini_cli.py`, `scripts/lib/integrations/qwen.py`, `docs/policy/platform-read-contracts.json`, `docs/policy/platform-read-contracts.md`, `docs/v3/v3.15/development/platform-capability-ownership.md`, `scripts/installer.sh`, `scripts/installer.ps1`

## 6. Assumptions Made

- **Both platforms share Gemini CLI's tool vocabulary**: Qwen Code is a documented fork and its own examples use `run_shell_command` and `write_file`, so `_TOOL_IDS` is shared. A future Qwen rename would surface as a matcher that never fires, not as a wrong action.
- **`replace` covers both `Edit` and `MultiEdit`**: neither platform distinguishes single from multi-edit, so both catalog matchers map to the one tool. This can over-trigger a guardrail relative to Claude, never under-trigger it.
- **The `name` field is a safe ownership key**: it is documented as "a friendly name for identifying the hook in logs and CLI commands" on both platforms, so writing a namespaced value into it is within its purpose rather than a repurposing.
- **Setting Qwen's `shell` alongside an explicit interpreter command is harmless**: if Qwen wraps the command in the named shell, the result is one extra process; if it ignores the field, the explicit command still runs. Either way the guardrail executes.
- **A committed project `settings.json` is a real scenario**: this is why workspace scope uses the project-directory variable rather than an absolute path, matching the commit-visibility caution already applied to Copilot's `.github/skills`.

## 9. Summary and Next Steps

Gemini CLI and Qwen Code now carry Nexus-Hub's guardrails natively, from one shared translation module with the genuine per-platform differences isolated in a spec object rather than duplicated across two implementations. The two hard problems were that Gemini CLI renamed every event the catalog uses, and that neither platform has the Windows override slot Codex provided -- solved by an explicit translation map and by choosing the command from the installing host. The two things the documentation does not support are recorded rather than inferred: the extension-packaged hook path (DF-12) and which shell each CLI actually dispatches through on Windows (MT-7).
