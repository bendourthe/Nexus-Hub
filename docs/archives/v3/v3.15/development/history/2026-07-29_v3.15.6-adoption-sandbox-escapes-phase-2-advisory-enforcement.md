## HO-1 resolved at the pre-flight (and a project belief corrected)

Phase 1 handed over HO-1: the hook test suite could not run on this host, and Phase 2's stability gate requires it to pass. Resolving it first turned out to matter beyond this phase.

The suite never needed a POSIX host. On Windows, `C:\Windows\System32\bash.exe` (the WSL launcher stub) **shadows Git Bash on PATH**. It receives a Windows-style script path, cannot resolve it, and exits 127 before executing a line, so every bash-invoking test fails for a reason that looks like a real failure. Measured on the same machine, with no other change:

| PATH | `catalog/hooks/tests` |
|---|---|
| WSL stub first (default) | 99 failed / 361 passed / 36 skipped |
| Git Bash first | 0 failed / 460 passed / 36 skipped |

The two other failing files (`tests/validators/test_session_query_extract.py`, `tests/installer/test_branch_flag.py`) also pass under Git Bash, closing all 103 failures that several releases carried as unavoidable.

**Correction worth recording**: the WN-v36-1 framing ("bash cannot be fully exercised on the Windows dev host", covered on Linux in CI only) is inaccurate. It is PATH shadowing, not host incapability, and it was diagnosable at any time by asking WHICH bash answered rather than whether bash worked.

Phase 2 also made this structural for the files it owns (see 2.1 below), so those tests are correct on any host without PATH ceremony.

## Sub-tasks completed

### 2.1 - escalation-trigger: input-contract fix, groups A and C, init carve-out, PowerShell sibling (AC2)

**The bug found first.** Before adding any path, a check of the input contract showed `escalation-trigger.sh` resolved its target path solely from `$CLAUDE_FILE_PATH`, an environment variable Claude Code does not set. All nine sibling Write/Edit hooks read `.tool_input.file_path` from the stdin JSON payload; this was the only hook in the catalog on the env-var contract. Proven rather than inferred:

- stdin JSON payload `{"tool_input":{"file_path":"src/auth/login.py"}}` produced **no output**.
- `CLAUDE_FILE_PATH=src/auth/login.py` produced the expected warning.

So the hook had never fired in normal operation. Adding AC2's escape surfaces to it would have shipped a longer list in a hook that cannot warn, which is exactly the "reports coverage it does not have" failure the Phase 1 skill names, and it would have passed any test that only asserted the pattern list's contents. Phase 1's own Verification item ("the signal was seen firing, not assumed") is unsatisfiable while the hook cannot read its input, so fixing the contract was necessary to deliver the sub-task's stated intent.

**Changes.**

- Input contract: read the stdin payload first (`jq` when present, a `grep`/`sed` fallback otherwise, matching the sibling convention), accept `.tool_input.path` as the documented alias, treat a JSON `null` as absent, and fall back to `$CLAUDE_FILE_PATH` so any setup exporting it keeps working.
- Added groups A and C of the canonical surface list: `.claude/settings*.json`, `.claude/hooks/*`, `.vscode/tasks.json`, `.vscode/launch.json`, `.git/hooks/*`, `.git/config`, `.cursor/*`, the virtualenv `bin` / `Scripts` paths, and `pyvenv.cfg`. Each pattern is present in both a bare and a `*/`-prefixed form, because a bash `case` glob of `*/.claude/...` does not match a repo-relative `.claude/...`.
- Group B is deliberately ABSENT, and a test pins that, so a future edit cannot add command patterns to a path matcher where they could never fire.
- Init carve-out: `NEXUS_HUB_INIT=1` suppresses the advisory for the five surfaces `nexus-hub init` actually owns (`.claude/settings*.json`, `.claude/hooks/*`, `.cursor/*`, `.agents/*`, `.github/skills/*`), confirmed against the `wire_project_surfaces` implementations. This is a writer-identity control, which is the only discriminator available, because a legitimate installer write and a hostile one produce an identical file. A test asserts it does NOT over-suppress `.git/hooks/*`.
- Default action stays `warn` (tested), with `block` opt-in via `ESCALATION_MODE`.
- Created `catalog/hooks/escalation-trigger.ps1` (net-new parity), using `[Console]::IsInputRedirected` as the equivalent of the bash `[ ! -t 0 ]` guard so it never blocks on an interactive console.

**A parity defect the tests caught.** The first full run failed exactly one case: a Windows backslash path warned under PowerShell but not under bash. Diagnosed through Python (the shell tool's own escaping layer had made an earlier hand-check unreliable, which is itself worth remembering): the `grep`/`sed` fallback reads the RAW JSON string and so does not decode escapes, so `C:\\repo\\.git\\hooks\\x` reached the normalization step, which rewrote each `\\` to `//` and produced `C://repo//.git//hooks//x`, matching no glob. `ConvertFrom-Json` decodes properly, which is why the sibling was already correct. Fixed by decoding the backslash escape in the fallback branch only; the `jq` branch needs no such step.

### 2.2 - git-guardrails: group B patterns, false-positive guards, PowerShell sibling (AC4)

- Added the two inline patterns, written as `git\s+(-c\s+\S+\s+)*-c\s*core\.hooksPath\s*=` (and the `fsmonitor` equivalent) so interleaving another `-c` option is not an evasion. A naive `git\s+-c\s+core\.hooksPath=` would have missed `git -c protocol.version=2 -c core.hooksPath=x`, which is tested.
- Added a separate check for the PERSISTENT form, because `git config core.hooksPath <value>` writes into `.git/config` and applies to every later operation. It needs its own logic rather than another regex, because the same key can be READ harmlessly: the check requires a `git ... config` invocation and a `core.(hooksPath|fsmonitor)` mention and the ABSENCE of `--get` / `--get-all` / `--get-regexp` / `--get-urlmatch` / `--list` / `--unset` / `--unset-all`, so a diagnostic command is not blocked.
- Documented the argv-decomposition limitation in the hook header, not only in the skill: these are fixed regexes over the raw command string, so quoting, spacing, environment indirection, and unlisted flags can evade them.
- Created `catalog/hooks/git-guardrails.ps1` (net-new parity), using `-cmatch` so .NET regex is case-sensitive like `grep -E`.

### 2.3 - Testing and stabilization

- Added `catalog/hooks/tests/conftest.py` with `bash_bin` and `powershell_bin` session fixtures. They PROBE each candidate interpreter by running a hook with empty stdin (every hook exits 0 on empty input, which makes a perfect probe) instead of trusting `shutil.which`, and skip cleanly when nothing usable exists. This is the durable form of the HO-1 fix for the files that use it.
- New `test_escalation_trigger.py` (92 tests) and extended `test_git_guardrails.py` (8 to 70 tests). **Every behavioural assertion runs against BOTH implementations** through a parametrized `run` fixture, which upgrades the plan's "manually confirm parity" instruction in 2.3 into an automated check that cannot be skipped or forgotten.

## Deviations

- **D5 (necessary to deliver the stated intent).** Fixing `escalation-trigger.sh`'s input contract goes beyond sub-task 2.1's literal text, which asks only to extend the path list. It is not optional: the objective is that writes to the escape surfaces trigger the advisory, which is impossible while the hook cannot read its input. Backward compatible via the retained env-var fallback.
- **D6 (test-infrastructure addition).** Added a `conftest.py` and converted `test_git_guardrails.py` to its fixtures. This is why Phase 2's tests pass on this host with no PATH ceremony. The fixtures only define behaviour (no pytest hooks, no collection changes), so they are inert for tests that do not request them.
- **D7 (stronger than asked).** Sub-task 2.3 says to "manually confirm behavior parity" between each `.sh` and its `.ps1`. Implemented as a parametrized fixture so parity is asserted automatically on every run instead of depending on a human remembering to check.
- **D8 (deliberate, documented).** The PowerShell siblings match case-insensitively (`-like`) while bash `case` globs are case-sensitive. Kept on purpose: Windows filesystems are case-insensitive, so `.Claude/settings.json` is the same file as `.claude/settings.json` and the bash matcher would miss a case variant the OS still resolves. The PowerShell behaviour is a strict superset, so it can only warn more, never less.

## Notable findings

- **Two of the three defects were invisible to the plan's own acceptance criteria.** A test suite that asserted "the pattern list contains `.claude/settings*.json`" would have passed on an inert hook. Only checking the input contract, and only running both implementations against the same inputs, surfaced them.
- **The parity test paid for itself immediately.** It found the JSON-escape defect on its first full run. A manual spot-check of a few lowercase POSIX paths would have missed it entirely.
- **The shell tool's escaping layer is not a reliable place to test backslash behaviour.** An early hand-check appeared to show the pre-existing normalization expression was broken; running the same logic from a real script file via Python showed it was correct and that my test harness had been mangled. Ground truth needed a path with no shell-escaping layer.
- **A parallel session switched this shared working tree onto `develop` mid-phase.** Phase 1's commit was never at risk (it lives on the feature branch) and the in-progress files carried across cleanly, but branch state was re-verified before committing. Worth knowing that this working tree is shared.
