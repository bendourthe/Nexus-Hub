## 2. Chronological Steps

### 2.1 Re-verify all three contracts, which reframed the phase

**Branch**: `feat/v3.15.8-platform-parity` | **PR**: N/A | **Merged to**: not merged

**Plan specification**: The prerequisite is that the Copilot and Hermes contracts are re-verified. 8.1 says to add delivery "only where the current contract proves it"; 8.2 says to add hooks "only for verified events and schemas"; 8.3 says to prove the flattened layout remains discoverable and explicitly not to migrate output solely to mirror an example.

**What happened**: Read the GitHub custom-agents reference, the VS Code custom-agents doc, the VS Code hooks doc, and the Hermes skills doc. Three findings changed what the phase needed to build.

**Copilot reads Claude-format files by default.** The documented default for `chat.hookFilesLocations` is `{".github/hooks": true, ".claude/settings.local.json": true, ".claude/settings.json": true, "~/.claude/settings.json": true}`, and the doc states that "VS Code uses the same hook format as Claude Code and Copilot CLI for compatibility". The installer already merges `catalog/hooks/settings.json` into `~/.claude/settings.json` and `.claude/settings.json`, so Copilot was already running those guardrails at both scopes. Separately, the default workspace agent locations are `.github/agents` **and** `.claude/agents`, and the `claude` integration already populates the latter. Six of the eight VS Code hook events are ones the catalog registers.

**One real Copilot gap exists.** The user-profile agent location is `~/.copilot/agents`; `~/.claude/agents` is *not* a Copilot agent path. So outside a repository, Copilot saw no catalog agents at all. Copilot's frontmatter requirements are also permissive enough for a verbatim copy -- `description` is the only required field, `name` is an optional display name, unrecognized fields are ignored, and Claude's tool names (`Read`, `Edit`, `MultiEdit`, `Write`, `Grep`, `Glob`, `Bash`, `Task`, `WebFetch`, `TodoWrite`) are documented aliases mapped to VS Code tools. The one hard limit is a 30,000-character prompt cap.

**Hermes resolves the opposite way from the v3.15.2 expectation.** The docs state it plainly: "Hermes discovers skills by listing every subdirectory of the tap path and probing each for `SKILL.md`". Discovery is one level, not recursive, so the flattened layout is *required* and a category-nested migration would have hidden every skill at depth 2. The "recursive discovery" premise recorded in the drift audit is wrong.

**Key files changed**: none - verification step

**Troubleshooting**: The GitHub custom-agents reference documents frontmatter but not file locations, so the paths came from the VS Code docs it points to. The three genuine forks -- whether to write parallel `.github/` copies, whether to deliver global agents, and how to close Hermes -- were put to the maintainer rather than assumed.

### 2.2 Deliver Copilot global agents

**Branch**: `feat/v3.15.8-platform-parity` | **PR**: N/A | **Merged to**: not merged

**Plan specification**: Add global and project delivery only where the current contract proves it, preserve `NEXUS_HUB_COPILOT_SKILLS` behavior, make ownership explicit, avoid overwriting `.github/agents` files, and keep the implementation safe when Copilot is absent.

**What happened**: Added `_install_global_agents` and `agent_skip_reason` to `CopilotIntegration`. Catalog agents are copied verbatim to `~/.copilot/agents/<name>.agent.md` -- `.agent.md` is the documented extension and the cross-level dedup key, so a project `.claude/agents/planner.md` still overrides the global copy, which is the correct precedence. Validation covers exactly what Copilot documents as fatal: a missing `description`, an empty body, or a prompt over the 30,000-character cap. Writes go through the shared `write_owned_file`, so a user-authored agent at the same path survives and a drifted owned one is repaired.

Detection was widened rather than reused as-is. The existing `install_global` returned early when no VS Code user-data directory was found, which is the right gate for prompt files but wrong for `~/.copilot/agents` -- a Copilot CLI user with no VS Code install would get nothing. It now proceeds when *either* signal is present and skips only when neither is, so each surface is written where its own precondition holds. `teardown` drops the agents directory when the manifest sweep empties it, using the shared `remove_dir_if_empty` from Phase 7.

**Key files changed**: `scripts/lib/integrations/copilot.py`

**Troubleshooting**: None.

### 2.3 Record Copilot hooks and project agents as inherited

**Branch**: `feat/v3.15.8-platform-parity` | **PR**: N/A | **Merged to**: not merged

**Plan specification**: Add hooks only for verified events and schemas, use marker-owned or structured merge behavior, preserve user and organization policy, and add tests proving the installer never claims a hook was installed when Copilot is undetected.

**What happened**: No hook write was added, because the verified schema and locations show the work is already done. Writing `.github/hooks/*.json` would put a redundant, commit-visible duplicate in the user's repository -- the same policy concern that keeps `.github/skills/` opt-in -- for hooks Copilot already loads from the Claude path. The same reasoning applies to `.github/agents`, with the extra point that agent files dedup across levels by filename, so the copy would not even change what Copilot loads.

`hooks_supported` stays `false` and no summary claims a Copilot-owned hook surface, which is the accurate statement: Nexus-Hub owns no such surface, and the Claude one carries the guardrails. The three affected matrix rows are marked **Enforceable -- inherited, no owned write**, with the source column naming the inherited path.

Because the dependency now runs Copilot-on-Claude, it is asserted rather than assumed. A test checks that the `claude` integration still targets `.claude` / `~/.claude` and that the shared hook template still registers events Copilot supports, so a future change there fails loudly instead of silently removing Copilot's hook coverage. A second test asserts no `.github/hooks` or `.github/agents` is ever written, and three more pin the skills selector's off-by-default, bundle-or-`all`, never-overwrite behavior against regression.

**Key files changed**: `docs/v3/v3.15/development/platform-capability-ownership.md`, `docs/policy/platform-read-contracts.json`, `docs/policy/platform-read-contracts.md`, `tests/plans/test_v3_15_8_contracts.py`

**Troubleshooting**: Marking a row "enforceable" when nothing is written is only honest if the row says why, so a new plan-contract test requires every inherited row to name its inherited source, declare `No write` as its write mode, and carry "inherited" in its status. That keeps a future phase from quietly adding a duplicate writer without updating the list.

### 2.4 Verify Hermes layout compatibility

**Branch**: `feat/v3.15.8-platform-parity` | **PR**: N/A | **Merged to**: not merged

**Plan specification**: Prove the existing flattened `SKILL.md` child layout remains discoverable when category-nested examples are documented upstream. Update the contract and known-gaps evidence only if the finding changes behavior; do not migrate output solely to mirror an example layout.

**What happened**: The quoted discovery rule settles it in the stronger direction: not only is no migration warranted, a migration would have broken discovery. Added two regression tests -- every direct child of the delivered skills root has a `SKILL.md`, and no `SKILL.md` exists below depth 1 -- plus checks that command-skills appear, that no ignored `.`/`_` prefix is produced, that the shared `.agents/skills` alias is not written, and that global scope stays detection-gated. Corrected the drift-audit note, which had recorded "recursive discovery" as the reason the flattened layout was acceptable.

**Key files changed**: `tests/integrations/test_copilot_hermes_native.py`, `docs/policy/platform-read-contracts.json`, `docs/policy/platform-read-contracts.md`

**Troubleshooting**: The depth-1 test failed on its first run, and the cause was a pre-existing catalog defect with nothing to do with Hermes. `catalog/skills/code-review/references/` held four checklists at the *category* level rather than inside a skill, so `flatten_skills` -- which treats every direct child of a category as a skill -- shipped a `references` directory with no `SKILL.md` to all nine flattened platforms. The same misplacement meant `code-quality`, `security-review`, and `performance-review` each cited `references/<file>.md` as a path relative to themselves that actually resolved to a sibling directory. On the maintainer's decision to fix rather than defer, each checklist was copied into the citing skill's own `references/` directory per the per-skill bundling convention and the category-level directory removed; the bundle audit stays at 0 errors with no new orphan.

## 6. Assumptions Made

- **`~/.copilot/agents` is served as documented**: it is listed as the user-profile agent location in the VS Code custom-agents doc. Unverified against a live install, which is why the observation sits with MT-6 / MT-7 / MT-8 rather than being claimed here.
- **Copilot's Claude-format defaults remain defaults**: the inheritance holds only while `chat.hookFilesLocations` and the agent-location defaults include the `.claude` entries. A user can disable them per the documented setting, and an upstream change would remove the coverage. The contract records the dependency explicitly so it is auditable at the next verification pass.
- **Claude's tool-name aliases cover what the catalog agents declare**: the alias table maps `Read`, `Edit`, `MultiEdit`, `Write`, `Grep`, `Glob`, `Bash`, `Task`, `WebFetch`, and `TodoWrite`, and unrecognized names are documented as ignored, so a miss degrades to a broader tool set rather than a load failure.
- **Relocating the checklists is behavior-preserving for the three skills**: each now resolves the exact relative path its `SKILL.md` already cited, which it previously could not. Duplicating `code-quality-checklist.md` into two skills is the intended shape of the per-skill bundling convention, not accidental redundancy.
