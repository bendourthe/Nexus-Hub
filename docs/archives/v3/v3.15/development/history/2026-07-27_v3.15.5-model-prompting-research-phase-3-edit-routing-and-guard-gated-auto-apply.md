## The headline outcome: the plan's central safety claim is false

Before writing any Phase 3 code, I tested the premise the whole phase rests on. The plan states, in both its Overview and its Definition of Done, that `check_base_template_parity.py` is what makes the hard rail real: "a model-named line in a shared `base-*.md` fails the build, so model-specific content physically cannot land in a shared body."

Three fixture cases, run against the real guard:

| Case | Setup | Guard result |
|---|---|---|
| A | The same model-named line added to ALL FIVE `base-*.md` inside an invariant section (`Branching`) | **PASSES** (rc=0) |
| B | A model-named line added to ONE file, in a non-invariant section (`Output Minimization`) | **PASSES** (rc=0) |
| C | Control: a genuinely divergent invariant section in one file | Correctly FAILS (rc=1) |

The guard compares the five templates **to each other**. Lockstep is exactly what it verifies, so it prevents drift between the templates and says nothing about whether their shared content is model-specific. Case A is not a corner case: applying the same line to all five is precisely what a well-behaved engine respecting the AGENTS.md lockstep rule would do, so the "safe" behavior is the one that defeats the claimed protection.

The Definition-of-Done item "a model-specific finding provably cannot reach a shared body (parity guard proves it)" therefore cannot be satisfied by the mechanism it names. Rather than write a test asserting something untrue, I implemented the rail where it can actually bind and recorded the correction.

## Sub-tasks completed

### 3.1 - Finding classifier (the hard rail)

- Built `scripts/apply_prompting_edits.py` in the skill bundle, with four routes: `eligible`, `profile-only`, `rejected`.
- **Rule 1, ambiguity resolves to model-specific**: scope must be EXACTLY `model-agnostic-candidate`. Missing, empty, unrecognized, and even differently-cased values all route to `profile-only`. The asymmetry is deliberate and documented: a model-specific claim parked in the profile layer is merely unhelpful, whereas one written into a shared body is distributed verbatim to every platform.
- **Rule 2, six targetable surfaces only**: skill description, trigger phrase, rationalization, verification, command body, and base-template line. Anything else is rejected, so the feature cannot touch installers, hooks, `data/`, READMEs, or CI.
- **Rule 3, the engine rail**: an edit may not INTRODUCE a model identifier into a shared body, whatever its declared scope. Detection compares identifiers in the edit's `new` text against those already in `old`, so rewording a line that already names a model, or removing the name, both stay allowed; adding a new one is blocked. A blocked edit routes to `profile-only` rather than `rejected`, because the guidance is usually fine and only the destination was wrong.
- **Rule 4, structural completeness**: no target, no anchor, or a no-op edit is rejected. A missing or ambiguous anchor surfaces at apply time as a quarantine, because it depends on the file's current contents.
- Documented in `references/edit-routing.md`, including the three-case evidence table and the residual.

### 3.2 - Guard-gated auto-apply loop

- Creates or checks out `feat/tune-prompting-<stamp>` from the integration branch, then asserts HEAD is that branch and is not `main` / `master` / `develop` BEFORE any file is touched. The stamp is caller-supplied and never generated internally, because a workflow runtime has no clock.
- Per eligible edit: snapshot the target's contents, apply the single-anchor replacement, run the full guard suite (skill-bundle audit, base-template parity, profile schema, version sync, trigger-and-routing gate, plus ShellCheck when the edited file is a shell script), then keep on all-pass or restore the snapshot and quarantine on any failure. A quarantine records the failing guard's name and output excerpt. The run continues to the next proposal.
- Edits stay uncommitted unless `--commit` is passed. Every run ends by printing that the branch is for human merge; nothing merges, tags, or pushes.
- **Second plan correction**: the plan specified `git checkout -- <file>` for the revert. That is wrong when two eligible edits target the same file, because it reverts to HEAD and would silently discard an earlier SURVIVING edit along with the failing one. An in-memory snapshot restores exactly the failed edit. Guarded by `test_a_failing_second_edit_does_not_destroy_a_surviving_first_edit`.

### 3.3 - Gap report and known-gaps emission

- Rendered deterministically from one run's results: applied, quarantined (with failing guard and detail), routed-to-profile-layer (with the reason, including hard-rail blocks), rejected, a branch diff summary, and a known-gaps section.
- Known-gaps entries are emitted per quarantined edit (`QG-<id>`) and per unverified model (`NI-<model>`), in the file's established entry shape so they can be pasted straight into the tracker. When there is nothing to record the section says so explicitly rather than being empty.
- Table cells escape pipes and newlines so a claim containing `|` cannot break the Markdown table.

## Defects found and fixed during stabilization

Three initial failures, two of which were the tests catching real bugs:

1. **The `base-*.md` glob over-matched.** `templates/ai-instructions/` holds non-lockstep files (for example `base-google-shared.md`), so the fixture tried to patch a file with no `Branching` heading. Fixed by importing the guard's own `LOCKSTEP_FILES` rather than globbing, so the test follows the guard if the set ever changes.
2. **A model-identifier regex missed the letter-then-digit shape.** `deepseek-v3` did not match, because the pattern required a digit immediately after the separator. Fixed with an optional `v`, which also covers `llama-v2`.
3. **A fixture lacked a genuinely repeated anchor**, so the ambiguous-anchor case actually applied cleanly. Fixed by adding a duplicated line to the seed file while keeping the other anchors unique.

## A gap closed rather than deferred

MT-4 initially recorded that `DEFAULT_GUARDS` is never executed, since the tests inject fast fake guards. Its realistic half is now closed in-phase: `test_every_default_guard_points_at_a_script_that_exists` asserts each default guard names a `.py` script that is present, and `test_the_default_suite_covers_the_gates_the_plan_requires` pins the three gates the plan names. A renamed or moved gate now fails at test time rather than silently quarantining every edit on a live run. What remains deferred is a genuine end-to-end run of the real suite.
