## Goal

Establish the canonical execution-trigger surface list, the escape taxonomy, the layered control model, and the platform audit checklist as a new skill that every later enforcement item references. Pure `skill-native` work (MCP Registry Policy tier 2): no code, no outbound call, no dependency, no credential, and no hook or installer edit.

Why this cycle matters more than a typical adoption: one of the source advisories (CVE-2026-48124) describes a workspace-controlled agent-harness hook configuration triggering unsandboxed execution. That is precisely the artifact class Nexus-Hub's installer distributes, so the comparison names the project's own distribution channel as the attack surface.

### 1.1 - SKILL.md (AC1, plus the AC6 guidance portion)

- `catalog/skills/security-operations/agentic-endpoint-hardening/SKILL.md`, 244 lines and 29790 characters, comfortably under the 500-line size norm. `security-operations` is the correct category (a defensive operational skill, not an AppSec-review one).
- Pushy single-line `description` leading with the action, then the trigger phrases verbatim ("agent sandbox escape", "config-write-then-executed", "trust seam", "harden the coding agent endpoint", "which files the agent writes get trusted", plus hooksPath / fsmonitor abuse, a reachable privileged daemon socket, and a safe-command allowlist bypass), then a four-way SKIP clause fencing off `ai-agent-governance`, `agent-access-policy`, `prompt-injection-defense`, and `skill-security-scan`. `summary_l0` at 12 words, `overview_l1` at 146 words, both inside their norms and both quoted.
- Body sections in the required order: title and intro; When to Use This Skill with an explicit When NOT to use; the pattern model; the taxonomy; the normative surface list; Instructions; the control layers; privileged daemons; the audit checklist; Limits and Honest Boundaries; Common Rationalizations; Verification; Related Skills.
- The pattern is stated as three steps (Write, Trust, Execute) with the structural reason it evades review made explicit: the write is inside the policy boundary and the execution is outside it, so neither side observes a violation and nobody instruments the handoff. Two consequences are stated for stakeholders: the blast radius is the union of everything writable and every privilege held by later readers, and time-of-write is decoupled from time-of-execution, so write-time approval is not execution approval.
- Six-form escape taxonomy (harness hook configuration, editor task or launch configuration, interpreter or shim substitution, version-control metadata indirection, safe-name argument smuggling, privileged local daemon), whose final column is deliberately "why it slips through" rather than a severity rating. A closing note observes that the last two forms are not file writes at all, so a control set covering only writes leaves both open.
- Nine control layers, each marked enforced, advisory, or guidance-only. Layers 4 and 5 are marked **guidance-only on purpose**: whether a vendor's language extension or version-control integration runs sandboxed is that vendor's architecture, and no hook or permission file can change it, so the honest action is to put them to the vendor as questions and record the answer as accepted risk rather than claim a control that does not exist.
- Privileged-local-daemon guidance folded in (the AC6 guidance portion) as an enumeration checklist plus three ordered controls, with the deny globs and least-privilege scoping cross-linked to `agent-access-policy` rather than duplicated there.
- Seven-question platform audit checklist, each question mapped to a layer, with "we do not know" called out as a finding.
- The denylist limitation is stated plainly in the Limits section: a fixed pattern list catches only the strings someone already thought of, every disclosed escape used one nobody had listed, so it is defense-in-depth and not a boundary. Also states that raw-command-string matching is not argument parsing, that local provenance is partial, that seam monitoring cannot cover every executor, that an advisory control prevents nothing, and that the strongest answer to an unclosable seam is an isolated tier rather than another pattern.
- No external vendor, framework, or product is named anywhere in the body; it describes component classes rather than product versions, so it stays accurate as vendors patch.

Each group is a three-column table naming the path or pattern, its executor, and its trigger. A separate "project extension candidates" subsection lists `.vscode/settings.json`, `.devcontainer/*`, `.idea/*`, convention-resolved script directories, and package-manifest lifecycle script fields as commonly-present but deliberately NON-normative, so promoting one is a conscious decision rather than silent scope drift.

## Deviations

- **D1 (corrects a plan defect; materially improves Phase 2's implementability).** The plan lists the canonical paths as one flat set including `core.hooksPath` and `core.fsmonitor`, and sub-task 2.1 asks `escalation-trigger.sh` to cover them. That hook only ever receives a file path (`CLAUDE_FILE_PATH`) and can never match a git config key, so the flat form makes 2.1 unimplementable as literally written. The list is therefore defined in three groups keyed by matching input, and `.git/config` was added to group A as the mechanical consequence of `core.hooksPath` being agent-writable. Phase 2 should route group A and C to `escalation-trigger` and group B to `git-guardrails`.
- **D2.** The instruction to state that "Phases 2 and 3 reuse this exact list" was implemented by naming the concrete consumers instead, since a distributed skill has no "Phase 2" for its reader. The intent (declare the list authoritative, name its consumers, warn about drift) is fully implemented and is more useful to both the end user and the Phase 2 implementer.
- **D3 (departure from precedent, deliberate).** The five prose skill-count surfaces were corrected 269 to 270 in this phase, whereas v3.15.3 deferred count reconciliation to `/update release` and v3.15.5 fixed it in its final phase as NI-4. This phase created the drift, the fix is five single-token edits, and leaving the repo advertising 269 while shipping 270 across three further phases is the worse state. `/update release` re-verifying is idempotent. The hook count (28) was deliberately left alone for Phase 3 to own when it adds the provenance-ledger hook. The README "What's New in v3.15.5" release-notes line was correctly left untouched.
- **D4 (allowlist rather than fix-in-place).** The `ai-agent-governance` near-collision was allowlisted rather than resolved by adding a reciprocal SKIP clause to that skill, because its missing clause is a pre-existing description-quality gap this phase did not create and editing it would also require syncing its `data/skills.json` mirror. Tracked as DF-1. Routing is proven correct in both directions, which is what justifies the allowlist over a description change.

No `# DEVIATION:` markers were left in any shipped file; all four deviations are documented here and in the known-gaps section.

## Notable findings

- **The collision was caused by following the authoring guidance correctly.** AGENTS.md requires a SKIP clause naming look-alike skills to prevent over-triggering; doing so imports their vocabulary into the token set that the pairwise near-collision detector then flags. The detector cannot distinguish "mentioned in order to exclude" from "genuinely overlaps". The allowlist exists for exactly this, and the routing result (all six positives beating every competitor, the governance negative routing away) is the evidence that settles which mechanism applies.
- **A downstream plan already depends on this phase's output.** `docs/v3/v3.16/plans/v3.16.0-agent-autonomy-toggle.md` cites "the v3.15.6 escape taxonomy" and its execution-trigger config paths as a Phase 4 dependency, confirming the normative list is the right deliverable to have shipped first.
- **The hook-test environment constraint is escalated, not just noted.** It was proven pre-existing with a clean-`develop` worktree, but Phase 2 ADDS hook tests and its stability gate requires them to pass, so it is recorded as HO-1 with three concrete verification routes rather than filed as a passive advisory.
