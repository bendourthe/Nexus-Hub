### 2.1 Wire both installers and their parity tests

**Branch**: `feat/v3.15.8-platform-parity` | **PR**: N/A | **Merged to**: not merged

**Plan specification**: Install the GitHub monitor beside Claude and Codex from both shells using the existing utility block, preserve detection and cleanup behavior, keep messages and ordering equivalent, avoid authenticating during install, and add tests that fail if either shell omits or reorders the extension.

**What happened**: Added a `GITHUB` vendor header and a `build_and_install_one_extension` / `Build-And-Install-One-Extension` dispatch to `scripts/installer.sh` and `scripts/installer.ps1`, placed after Anthropic and OpenAI so the installed status items keep the Claude 105, Codex 103, GitHub 101 priority order. The status hint is `GitHub Usage: --` rather than a percentage, because a freshly installed monitor has no credential and therefore no honest denominator. The introductory copy now names all three vendors. Installation builds and installs only; it never contacts GitHub.

**Key files changed**: `scripts/installer.sh`, `scripts/installer.ps1`, `catalog/hooks/tests/test_installer_smoke.py`

**Troubleshooting**: The pre-existing smoke test asserted the two monitors by name in prose, which would have passed while silently ignoring a third. The test is now parameterized over a `USAGE_MONITORS` tuple of directory, extension id, and display name, so adding a fourth monitor without wiring both shells fails immediately. A separate test extracts each shell's monitor order and asserts the two lists are equal, which is the assertion that actually catches drift between shells rather than absence from one.

**Verification**: `test_installer_smoke.py` passes, including the new order and status-hint tests. `shellcheck -S warning scripts/installer.sh` exits 0 and `[Parser]::ParseFile` on `scripts/installer.ps1` reports no errors across 15,269 tokens.

### 2.2 Add the focused workflow, packaging gate, and workflow policy tests

**Branch**: `feat/v3.15.8-platform-parity` | **PR**: N/A | **Merged to**: not merged

**Plan specification**: Trigger only for the GitHub extension and its workflow, use least privilege, immutable action SHAs, Node 22, an exact lockfile cache, PR concurrency cancellation, `npm ci`, compile, coverage, and VSIX packaging, with semantic tests rejecting floating actions, wrong cache paths, ordinary feature-push expansion, or missing gates.

**What happened**: Added `.github/workflows/github-usage-monitor.yml` mirroring the repaired Claude and Codex monitor workflows: `contents: read` only, SHA-pinned `actions/checkout` and `actions/setup-node` with version comments, Node 22 with npm cache keyed on the extension's `package-lock.json`, concurrency cancellation, and a `npm ci` to compile to coverage to package to `verify:package` step order. Added a `verify:package` gate (`scripts/verify-package-contents.js`) that runs `vsce ls` and asserts every runtime asset is present and no coverage report, source tree, test tree, script, source map, nested VSIX, or credential-shaped file ships. Added `.github/dependabot.yml` coverage for the new package. Added `tests/workflows/test_github_usage_monitor_workflow.py` with fourteen semantic assertions, several parameterized across all three monitor workflows so the pins and concurrency settings cannot drift apart.

**Key files changed**: `.github/workflows/github-usage-monitor.yml`, `.github/dependabot.yml`, `.github/workflows/ci.yml`, `extensions/github-usage-monitor/scripts/verify-package-contents.js`, `extensions/github-usage-monitor/test/package-contents.test.ts`, `extensions/github-usage-monitor/.vscodeignore`, `extensions/github-usage-monitor/package.json`, `tests/workflows/test_github_usage_monitor_workflow.py`

**Troubleshooting**: Two problems surfaced here. First, `verify-package-contents.js` failed with `EINVAL` when spawning `npx.cmd`: current Node refuses to execute a `.cmd` shim without a shell, and routing through a shell would make the gate depend on host quoting rules. The script now invokes vsce's JavaScript entry point directly with `process.execPath`, which is both portable and shell-free. Second, and more consequential, writing the workflow tests exposed that `ci.yml`'s `tests` job enumerates test directories by name rather than running `pytest tests`. `tests/workflows` would have been dead on arrival, and `tests/plans` had already been dead since Phase 1 - which is exactly what QG-2 recorded. One added step now collects both, with a comment stating why a new directory is invisible until listed.

**Verification**: 14 workflow-policy tests and 72 combined plan, workflow, and installer tests pass. `python scripts/validate_workflow_security.py` exits 0 with the new workflow present. `npm run verify:package` reports 37 packaged files with no violation.

## 6. Assumptions Made

- **Vendor order encodes status-bar order**: the installer builds monitors in Anthropic, OpenAI, GitHub order and the extensions carry priorities 105, 103, and 101. The order test asserts the installer sequence, which is the part a future edit can silently break.
- **`vsce ls` is a faithful proxy for VSIX contents**: it applies `.vscodeignore` the same way `vsce package` does, so listing is a valid gate and avoids unzipping an archive in CI.
- **A read-only workflow token is sufficient**: the job builds and tests only. It publishes nothing and uploads no artifact, so `contents: read` is the complete requirement.
- **Teal contrast is adequate by calculation**: `#008080` computes to roughly 4.8:1 against white and 4.4:1 against black, clearing the 3:1 non-text floor on both. This is arithmetic, not an observed render; QG-4 still owns the visual confirmation.
