## What this phase had to protect

The comparison declined the source's recommendation to put architecture (data model, module boundaries, interfaces, error handling) into the spec. The grounds were specific: it conflicts with the normative-spec-versus-context split, and it would fail `spec-quality-checklist.md`'s implementation-detail checks at lines 9, 19, and 30. That decline is the boundary this phase had to hold while closing the one narrow slice of the recommendation that is a real gap.

The gap: error handling has no mandatory home in either artifact. It appears only as optional `### Edge Cases` prompts at `spec-template.md` lines 68 to 72, and those prompts name the user-visible edge case by design, not the handling. So "what does this component do when its dependency is unreachable?" was a question no artifact was required to answer.

The risk was that closing it would pull architecture back into the spec, which is exactly the merge that was declined. The whole phase is therefore an exercise in putting something in the right layer rather than the nearest one.

## The skill choice (DC-1)

Sub-task 3.1 delegated the decision: *"Edit `catalog/skills/workflow/implementation-plan/SKILL.md` (or `catalog/skills/workflow/plan-before-code/SKILL.md` if that is the better fit for per-component design detail; pick ONE and state the choice)."*

Both were read before choosing. `implementation-plan` is 445 lines and emits a plan document with a `## Phase N` / `### Sub-tasks` / `#### N.1` structure. `plan-before-code` is 353 lines and runs a conversational explore-plan-execute loop whose plan template is Approach / Implementation Steps / Testing Strategy / Potential Challenges / Estimated Complexity.

**Chosen: `implementation-plan`**, confirmed with the maintainer before any edit. Four grounds:

1. **It produces a durable artifact.** It writes `docs/**/plans/*.md`, so a convention added there lands in a document a reviewer reads later, and in this repository's case is the document `/implement` executes against. `plan-before-code`'s plan lives in the conversation turn.
2. **It already has the attachment point D3 needs.** The per-sub-task template (`#### N.1` with `**Objective**` and `**Prompt**`) is where "a one-line label per sub-task" fits natively. `plan-before-code`'s plan template has no per-sub-task slot, so the same convention would have needed a new structure invented for it.
3. **It is the spec's downstream consumer.** D4 requires keying failure modes off the spec's `### Edge Cases` prompts so the two artifacts compose. That story only works on the skill that runs after `/spec`.
4. **The skills' own cross-link settles the layering.** `implementation-plan`'s Related Skills describes `plan-before-code` as "lightweight planning for individual features within a phase". Per-component design detail spanning a plan belongs to the outer skill.

**Cost accepted and managed.** `implementation-plan` sat at 445 of the 500-line body target against `plan-before-code`'s 353, so the size norm was the one real argument for the other choice. The extraction question was decided rather than dodged: both conventions are authoring-time rules that shape every sub-task an author writes, which is Tier 2 material, whereas a worked catalogue of failure-mode examples would be Tier 3. Edits were budgeted to ~35 lines and landed at 24, finishing at 469 lines, 31 under target.

## 3.1 - Failure modes get a mandatory home at the plan layer

**Template field.** The emitted `#### N.1` sub-task block gained:

> **Failure modes** *(required when this sub-task introduces or changes a component)*: [What the component does when its inputs are malformed or absent, when a dependency it calls is unreachable or slow, and when two of its operations conflict.]

**Authoring rule.** A new `### Step 3.6: Name Each Sub-task's Failure Modes and Build Class` sits between Step 3.5 (phase scoring and model map) and Step 4 (Write the Plan), which is the point in authoring order where the phases are fixed but nothing has been written yet.

Three design points in that rule are worth stating.

**Three named situations, not a general instruction.** "Handle errors well" is satisfiable by any behavior including a silent swallow, so it is a sentiment rather than a requirement. Naming malformed or absent input, an unreachable or slow dependency, and conflicting operations makes the field checkable by a reviewer who did not write it.

**The compose story is stated explicitly.** The spec's `### Edge Cases` names the user-visible edge case ("what happens when an upstream dependency is unreachable?"); the plan's field names the handling ("retry twice with backoff, then serve cache with a staleness banner"). The rule says why the spec deliberately holds only the first: a spec that pinned retry policy would fail the quality checklist's implementation-detail checks.

**The boundary is written as an instruction to future authors, not merely observed.** Step 3.6 ends that paragraph with: do NOT close this gap by pushing error handling, data models, interfaces, or schemas back into the spec template. A boundary that is only honored decays at the next author who notices the same gap and reaches for the nearest artifact; one that is written down survives them.

**Scope limit.** A sub-task that only edits prose, moves a file, or runs a tool introduces no component and carries no failure-mode line. Without that carve-out the field becomes noise on the majority of sub-tasks and gets filled in reflexively, which is worse than absent.

## 3.2 - The scaffolding-versus-proof labeling convention

**Template field.**

> **Build class** *(state only where a reader could not otherwise tell)*: [load-bearing, or scaffolding naming what replaces it and when.]

**The problem it solves**, stated in Step 3.6: a reviewer should never have to guess whether a hardcoded value is a shortcut awaiting replacement or the intended implementation, and that distinction is usually unrecoverable from the diff alone. Where a sub-task deliberately produces something provisional (a stub, a hardcoded fixture, a shortcut taken to reach a checkpoint), it is labelled `scaffolding` and says what replaces it and when. Where it produces the part that actually demonstrates the approach works, it is `load-bearing`.

**Kept deliberately lightweight.** One line, stated only where a reader could not otherwise tell, skipped where the answer is obvious. The plan asked for a label rather than a document section, and the failure mode for a convention like this is growing into a template block that everyone fills in reflexively and nobody reads.

**The provenance note, recorded honestly.** The plan required stating in the skill's own prose that this convention is adopted on its merits, because the example specification cited as demonstrating it contains no code blocks and no such labeling, so the cited evidence does not support the claim. The skill says exactly that, and closes with why the idea survives its evidence failing: the review problem it names is real and observable. No external article, author, newsletter, or repository is named anywhere in the body, per the AGENTS.md reverse-engineering attribution rule. Full provenance goes in the Phase 4.2 matrix row.

## Enforcement added alongside

**Two Verification items:**

- Every sub-task that introduces or changes a component states its failure modes across all three situations, and no error-handling, data-model, interface, or schema detail was pushed back into the spec to achieve it.
- Sub-tasks producing provisional work carry a one-line `scaffolding` build class naming what replaces it and when; `load-bearing` is stated wherever a reader could not otherwise tell.

The first deliberately carries the boundary into the checklist, so an author who closes the gap the wrong way fails their own verification rather than discovering it at review.

**Two rationalization rows**, both aimed at the specific excuse each convention invites. "Error handling is an implementation detail, I will let the implementer decide" is rebutted with the observation that the choice then gets made mid-implementation by whoever hits it first, under time pressure, without review. "The stub is obviously temporary, labelling it is busywork" is rebutted with the asymmetry that matters: it is obvious today and invisible in the diff tomorrow, and the guess that ships is the one treating scaffolding as finished.
