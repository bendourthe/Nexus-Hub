### 2.2 Refactor the duplication the platform phases accumulated

**Branch**: `feat/v3.15.8-platform-parity` | **PR**: N/A | **Merged to**: not merged

**Plan specification**: Identify deprecated or obsolete files, empty directories, redundant monitor abstractions, duplicated installer dispatch, and overcomplicated platform ownership introduced by v3.15.8. Apply only approved, in-scope refactors with reference repair, preserving the independent monitor boundaries and the release worktree discipline.

**What happened**: Surveyed the five modules the platform phases added and found three genuinely duplicated operations: the script-basename split (`_split_command` in Codex, `_split_command` in settings-hooks, `_script_name` in Kimi -- three copies), the ownership predicate plus its group filter (`_handler_is_owned` / `_strip_owned` in Codex and settings-hooks -- two copies, differing only in that the settings-hooks version also checked the `nexus-hub:` name prefix), and the host-command builders (`is_windows_host`, `host_shell`, `script_for_host`, `command_for`, which Kimi imported from `_settings_hooks`).

Added `_hooks_common.py` as the single home for those, with the unified ownership predicate accepting either signal -- a `nexus-hub:` name where the schema has that field, or a command pointing into the installed hooks directory where it does not. That is a safe superset for both callers: Codex handlers carry no `name`, so the name check is a no-op and it falls through to the command fields exactly as before.

Deliberately did **not** unify what differs. Event maps, matcher vocabularies, file formats, and merge strategies stay per-platform, because those divergences are the substance of what the read contract documents and merging them would hide schema differences rather than remove duplication. Removed one trivial wrapper (`SettingsHooksMixin._remove_dir_if_empty`, a one-line delegate to the shared helper) and updated both callers.

Audited the other targets the sub-task names and found nothing to do: no deprecated or obsolete files (the adapters are at most four phases old), no empty directories, no shared monitor abstraction (each extension keeps its own package, tests, and workflow, which was preserved on purpose), and no removable installer dispatch duplication -- both installers already delegate every v3.15.8 platform through the Python registry, so the remaining per-platform shell blocks are provider headers and detection notes, not duplication.

**Key files changed**: `scripts/lib/integrations/_hooks_common.py` (new, 126 lines), `_settings_hooks.py`, `_settings_hooks_mixin.py`, `_codex_native.py`, `_kimi_native.py`, `kimi.py`, `gemini_cli.py`, `qwen.py`

**Troubleshooting**: One reference repair was the point rather than a side effect: `kimi.py` and `_kimi_native.py` imported host helpers from `_settings_hooks`, a module named after a different platform's config file, which read as a deliberate Kimi-on-Gemini-CLI dependency and was not. Those now resolve to `_hooks_common`. Net effect across the eight files is 55 insertions against 152 deletions.

### 2.4 Compare every workflow field-by-field

**Branch**: `feat/v3.15.8-platform-parity` | **PR**: N/A | **Merged to**: not merged

**Plan specification**: Compare every Claude, Codex, and GitHub monitor workflow plus repository CI against the approved lifecycle -- PR validation, protected post-merge smoke, release-only publication, immutable action pins, least-privilege permissions, lockfile caches, concurrency cancellation, stable required aggregates, and no ordinary feature-branch push expansion. Apply only approved corrections and record retained differences. Ensure focused monitor paths do not strand required checks.

**What happened**: Audited all eight workflows on every field. Most of the format was already met: **22 of 22 action refs are pinned to full 40-character SHAs**, all eight declare a concurrency group with `cancel-in-progress: true`, all eight scope pushes to `main` and `develop` with no feature-branch expansion, and 7 of 8 carry a `paths:` filter with `ci.yml` correctly using `paths-ignore: docs/**` as the catch-all.

Two gaps were uniform rather than per-workflow, which is why only a cross-file comparison surfaced them. **Only `github-usage-monitor.yml` declared `permissions:`** -- the six others (`ci.yml`, both older monitors, `code-search`, `doc-colocation`, `presentify-extractor`) declared nothing and ran on whatever the repository default grants. All six are build/test-only, verified by scanning for artifact uploads, `gh` CLI use, comment actions, and pushes, so `contents: read` is their complete requirement and adding it is strictly a tightening. **No workflow declared `timeout-minutes`**, leaving a hung job free to burn the 6-hour default.

Applied both on maintainer approval, then locked them in with `tests/workflows/test_workflow_policy_repo_wide.py`: 70 assertions over the whole directory covering permissions, timeouts, SHA pinning, concurrency cancellation, push scoping, and path filtering. Two exceptions are encoded with their reasons rather than skipped -- `codeql.yml` keeps its job-level `security-events: write` untouched (it needs it to upload results, and a job-level block replaces the default outright), and `ci.yml` satisfies the path requirement through `paths-ignore` because inverting it would defeat its purpose as the catch-all gate. That second assertion is also DF-11's compensating control: `ci.yml` cannot quietly acquire a `paths` filter that would strand installer changes.

**Key files changed**: all eight `.github/workflows/*.yml`, `tests/workflows/test_workflow_policy_repo_wide.py` (new)

**Troubleshooting**: The first audit pass reported no path filters anywhere and permissions on two files. Both readings were wrong: `re.search` with a `^`-anchored pattern and no `re.M` matches only the start of the whole file, so `paths:` and indented `permissions:` were invisible. That would have led to adding path filters that already existed while missing the actual permissions gap -- worth recording because the corrected run inverted the conclusion.

## 6. Assumptions Made

- **`contents: read` is sufficient for the six workflows it was added to**: each was scanned for artifact uploads, `gh` CLI invocations, comment actions, and pushes, and none performs any. A missed requirement would surface as a permission error on the first run rather than as silent damage.
- **30 and 60 minute timeouts are generous enough**: the repository suites run 17-28 minutes on this Windows host and CI's ubuntu runners are faster, so 60 for the two long jobs leaves real headroom. No CI duration baseline exists in this branch to size from, which is why the values are deliberately loose.
- **The unified ownership predicate cannot produce a false positive on Codex**: Codex handlers carry `statusMessage`, not `name`, so the name-prefix branch is inert there and behavior is unchanged. A user who deliberately named their own handler `nexus-hub:*` would be claimed, which is the same assumption Phase 6 already made for Gemini CLI and Qwen.
- **`main`'s 24 extra commits are content-free release merges**: confirmed by inspecting every one and by the 15,370-versus-97 diff shape. If any carried unique content, merging this branch forward would regress it.
