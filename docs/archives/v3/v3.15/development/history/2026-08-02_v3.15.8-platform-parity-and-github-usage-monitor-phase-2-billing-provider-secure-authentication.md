### 2.2 Implement secure authentication and explicit billing scope

**Branch**: `feat/v3.15.8-platform-parity` | **PR**: N/A | **Merged to**: not merged

**Plan specification**: Probe VS Code GitHub authentication only if Phase 1 proved billing acceptance; otherwise validate and store a fine-grained token in `ExtensionContext.secrets`, expose set/validate/rotate/clear commands, and support exactly one user, organization, or enterprise owner with actionable permissions.

**What happened**: Implemented SecretStorage-backed token operations, opaque token syntax validation, validate-before-store and validate-before-rotate guarantees, four extension commands with password-style prompts, explicit disabling of VS Code GitHub session reuse, owner and slug validation, URL encoding, scope-specific endpoints, documented permission diagnostics, and managed-Copilot personal-scope rejection.

**Key files changed**: `extensions/github-usage-monitor/src/extension.ts`, `extensions/github-usage-monitor/src/providers/auth.ts`, `extensions/github-usage-monitor/src/providers/scope.ts`

**Troubleshooting**:

- **Problem**: The first authentication test found that a token ending in a newline was accepted after trimming.
- **Attempted**: Compared the syntax-validation order with the SecretStorage normalization path.
- **Root cause**: Control-character detection ran against the trimmed value instead of the original input.
- **Resolution**: Reject control characters in the original token first, then trim and reject any remaining whitespace.

**Verification**: Authentication, scope, and extension-command tests cover successful storage, validation, rotation failure preservation, clear, cancellation, missing credentials, unsupported session reuse, all three scopes, endpoint encoding, and typed errors without live credentials.

### 2.3 Implement the versioned GitHub billing client and normalizer

**Branch**: `feat/v3.15.8-platform-parity` | **PR**: N/A | **Merged to**: not merged

**Plan specification**: Build current-month requests with the approved API version, bounded timeout, cancellation, rate metadata, typed failures, defensive schema parsing, distinct Copilot units, compatible Actions aggregation, storage-unit protection, separate gross/discount/net amounts, and no false zero.

**What happened**: Added a fetch-injected GitHub client with fixed headers, timeout and caller cancellation, safe JSON parsing, rate-limit metadata, owner-specific endpoints, and typed 401, 403, 404, 429, server, network, cancellation, timeout, and schema errors. Added runtime validation that ignores additive fields, rejects malformed required fields, preserves numeric zero, distinguishes AI credits from premium requests, normalizes managed Copilot organization data, aggregates Actions minutes with raw SKU records, and only combines compatible storage units.

**Key files changed**: `extensions/github-usage-monitor/src/providers/github.ts`, `extensions/github-usage-monitor/src/providers/normalizer.ts`, `extensions/github-usage-monitor/src/providers/index.ts`

**Troubleshooting**:

- **Problem**: The first client test classified a 404 from the AI-credit endpoint as detailed billing usage unavailability.
- **Attempted**: Inspected the endpoint classifier against the Phase 1 fixture routes.
- **Root cause**: A broad `endsWith("/usage")` condition also matched `/settings/billing/premium_request/usage` and `/settings/billing/ai_credit/usage`.
- **Resolution**: Match the exact `/settings/billing/usage` path before assigning the enhanced-billing error.

**Verification**: Fixture-driven tests cover URL and header construction, both Copilot schemas, managed Copilot, Actions usage, additive and malformed payloads, non-JSON success, timeout, cancellation, network errors, 401, 403, 404, 429, and server failures.

## 6. Assumptions Made

- **Node 22 is the package runtime floor**: This matches the plan and the repaired Claude and Codex monitor workflows; Phase 4 must preserve it in CI.
- **The Phase 1 API version remains authoritative**: Requests pin `2026-03-10`; future schema changes must be handled additively and validated before changing the contract.
- **Opaque token formats may evolve**: Validation rejects unsafe whitespace and control characters without hard-coding a provider prefix, while remote validation establishes authorization before storage.
- **No live billing credential is authorized in this session**: All provider behavior is fixture-driven, and no token, username, organization, enterprise, email, or private response enters tests or docs.
- **A denominator is valid only with an exact metric unit**: API and manual allowances never cross AI-credit, premium-request, minute, or storage-unit boundaries.
