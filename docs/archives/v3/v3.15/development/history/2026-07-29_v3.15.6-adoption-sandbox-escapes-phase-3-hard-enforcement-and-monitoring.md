## Sub-tasks completed

### 3.1 - Opt-in deny-by-default permission overlay behind an installer flag (AC5)

**The plan's schema instruction is wrong, and that was established before writing.** Sub-task 3.1 says to set `defaultMode` to "ask/deny". That key takes permission MODES (`default`, `acceptEdits`, `plan`, `bypassPermissions`); `ask` and `deny` are sibling ARRAY keys. Beyond the confusion, `defaultMode` appears nowhere in `guides/reference/CLAUDE_CODE_SETTINGS_REFERENCE.md`, while `allow` / `ask` / `deny` all appear there with worked examples, and `docs/v3/v3.16/plans/v3.16.0-agent-autonomy-toggle.md` Phase 2 schedules confirming the `defaultMode` enum against official docs as unstarted work. Writing an unverified enum into a user's `settings.json` is a schema bet with no upside, because the safest documented value (`default`) is already Claude Code's behaviour. The overlay ships the verified keys only, a test pins the omission, and DF-3 carries the question forward.

**Implemented as an overlay, not a replacement file.** The plan says the flag installs the strict stub "instead of" the default, which read literally means a second file carrying its own copy of the 15KB read-only allow list. `configs/permissions/claude-permissions-strict.json` instead carries ONLY `deny` and `ask` and is merged on top of the base template, so the allow list has one source of truth and cannot drift between two files. The resulting posture is identical; a test asserts the overlay carries no `allow` key.

**The deny-versus-ask split, and why it is a decision.**

- **deny** (22 entries): version-control hooks and config (`.git/hooks/**`, `.git/config`), interpreter and virtual-environment paths (`.venv/**`, `venv/**`, `pyvenv.cfg`), and the group B git execution-indirection commands. An agent write here is essentially never legitimate and the blast radius is a trusted executor running code at host privilege.
- **ask** (12 entries): harness settings and hooks (`.claude/settings*.json`, `.claude/hooks/**`), editor task and launch config (`.vscode/tasks.json`, `.vscode/launch.json`), and editor rules (`.cursor/**`). These have real agent workflows, so a hard deny would break legitimate work while silent approval is the exact escape being defended against. This is control layer 3 of the skill: approval, not prohibition.
- A test asserts the two lists do not overlap, because an entry in both is ambiguous.

**A finding that made the split cleaner**: the permission config governs the AGENT's tool calls, not the installer's own file I/O. So denying `.claude/settings.json` does NOT break `nexus-hub init`, and the tier could be chosen on merit rather than on fear of self-blocking.

**Installer changes, in lockstep.** `--strict-permissions` in `installer.sh` (flag default 0, arg parsing, passthrough, `--help` text, `merge_strict_permissions()`), `-StrictPermissions` in `installer.ps1` (switch param, `-Help` text, `Merge-StrictPermissions`). Three deliberate properties of both helpers: additive (never removes a user's existing entries), no `defaultMode`, and **invoked from the call site** rather than from inside `install_permissions` / `Install-Permissions`, because those functions return early in their allow-merge path (jq missing, nothing new to add, merge failed) and would have silently skipped the overlay in the single most common case, an allow list already up to date.

### 3.2 - Best-effort file-provenance / trust-seam ledger hook (AC3)

New `catalog/hooks/provenance-ledger.{sh,ps1}`, a PostToolUse hook on `Write|Edit|Bash`, registered in `catalog/hooks/settings.json`. Hook count moves to 29.

- **On a write**: appends one tab-separated line, `<epoch>\t<sha256>\t<path>`. Never contents, diffs, environment values, or secret material.
- **On a command**: flags a later same-session command referencing one of those paths, reporting the path, how long ago it was written, and a short hash prefix.
- **Bounded**: per-session ledger file, line cap (`NEXUS_PROVENANCE_MAX`, default 500), hash size cap (`NEXUS_PROVENANCE_HASH_MAX_BYTES`, default 10MB) so per-write overhead stays small.
- **Advisory**: exits 0 on every path, honors `NEXUS_DISABLED_HOOKS` and `NEXUS_HOOK_PROFILE=minimal`.
- **Branch discriminator**: keys on `tool_name` with a field-presence fallback, so a payload carrying both a path and a command is not ambiguous.

**The honest boundary, in the hook and the skill.** A hook observes the tool calls of the harness it is installed in. It cannot instrument an editor extension, a language server, or a version-control integration in another process, so it cannot see the execution half of most real escapes. Same-session correlation ships; cross-executor instrumentation is not locally achievable and is the explicitly dropped part of the `re-partial` classification. The correlation heuristic is also stated plainly: it matches a path or basename anywhere in the command string, so it over-reports and under-reports, and is a tripwire rather than a determination.

## Two defects the parity tests caught

Both are invisible to a POSIX-only test, and both were found by running the same assertions against both implementations.

| Defect | Cause | Fix |
|---|---|---|
| BG-3: ledger unparseable, formats diverged | `Add-Content -Encoding utf8` writes a UTF-8 BOM on Windows PowerShell 5.1, so the first field parsed as a BOM followed by the epoch rather than a bare integer. Parity matters because both implementations can append to the SAME ledger file. | BOM-less `UTF8Encoding($false)` writes, matching the installer's own `Write-JsonFile` |
| BG-4: 65-character hash with a leading backslash | GNU coreutils `sha256sum` escapes a filename containing a backslash and prefixes the output line with `\`, which a Windows path always triggers. | Hash via stdin, removing the filename from the output entirely |

## Deviations

- **D9 (plan schema error; not implemented as written).** `defaultMode` omitted. See 3.1 and DF-3.
- **D10 (better than as written).** The strict stub is a deny/ask overlay merged on top of the base allow list, not a full replacement file, so the allow list keeps one source of truth.
- **D11 (call-site placement).** The strict merge is invoked from the call site because the existing permission functions return early in their allow-merge path.
- **D12 (HO-2 scoped honestly).** `NEXUS_HUB_INIT=1` is exported from `init` in both installers as asked, but the comments state what it does not achieve: the installer's writes never traverse Claude Code's Write/Edit hooks, and the marker is self-asserted, so it must not be promoted to a boundary.

## Notable findings

- **The plan's most dangerous line was a schema, not a design.** "Set `defaultMode` to ask/deny" would have written an unverified enum into every strict user's `settings.json`. Checking the in-repo reference before writing, rather than trusting the plan, is what caught it.
- **Two lint findings were opportunities.** Using the ledger's timestamp instead of silencing the unused-variable warning produced a better advisory ("written 2s ago" reads very differently from "written 40 minutes ago"). Using `tool_name` as the branch discriminator instead of deleting the unused variable removed a real ambiguity.
- **The redaction test is the reason this hook is shippable.** A provenance ledger that could leak a secret would be a net negative; asserting that a planted secret never reaches the ledger or the hook's output is what makes the capability defensible.
