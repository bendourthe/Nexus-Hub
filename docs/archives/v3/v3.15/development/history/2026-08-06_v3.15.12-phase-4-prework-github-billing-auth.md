## Why this is a pre-work session rather than Phase 4

T022 gates Phase 4. The plan expected first-party documentation to answer it. It does not, and finding that out changed the shape of the phase rather than just its answer. No implementation (T023 onward) was written, deliberately: `providers/auth.ts:99` exists precisely because someone previously built on this premise without settling it.

---

## Three premises that were wrong

An external review corrected the approach before any code was written. All three corrections are recorded in `development/github-billing-auth-probe.md`, because each would have produced a wrong implementation.

### 1. The endpoint reference cannot settle OAuth support (a wrong RULE, not just a wrong fact)

The proposed decision rule was: *session becomes default only if the endpoint doc lists a token type VS Code can mint*. The REST reference's token section is titled **"Fine-grained access tokens for..."**, so it enumerates fine-grained support only and is not an exhaustive list of accepted authentication classes. That rule therefore rejects OAuth on **absence of evidence**, and would have permanently foreclosed a viable auth path.

Replaced with: a positive requires a real `200` for that target and endpoint; a negative requires a classic-PAT control succeeding on the same target **plus** headers or an error identifying a scope, app-authorization, or token-class cause.

### 2. A billing OAuth scope does exist

`manage_billing:enterprise` (subsumed by `admin:enterprise`). The earlier claim that GitHub has no billing-specific OAuth scope was wrong for Enterprise Cloud.

### 3. VS Code's provider has no fixed scope allowlist

The current built-in provider accepts caller-supplied scopes, sorts and joins them, and forwards the string into the login flow. No allowlist filters it. It still cannot mint a fine-grained PAT or GitHub App token through `getSession()`.

### Plus one trap

`AuthenticationSession.scopes` reports the scopes the extension **requested**, not what GitHub granted. Trusting it would let a narrowed consent read as a full grant, which would have silently broken the plan's own "never fall back silently" requirement. Granted scopes come from `X-OAuth-Scopes`.

## What the documentary half established (T022a)

| Level | Endpoint reference | Documentary verdict |
|---|---|---|
| User | GitHub App user tokens + fine-grained PATs work, user `Plan: read` | **Conflicted** - the usage-reporting tutorial says billing usage does not support fine-grained PATs, use a classic PAT |
| Organization | + installation tokens, organization `Administration: read` + admin role | **Conflicted**, same contradiction |
| Enterprise | Explicitly rejects GitHub App user tokens, installation tokens, and fine-grained PATs | **Documentary negative** for those classes. Classic PAT is the baseline. OAuth still unprobed |

**The documentary half does not settle T022 for user or organization scope.** GitHub's own docs conflict, so a live probe with a control is the only resolution. That is the substantive finding.

## What was built (T022b)

`src/providers/authProbe.ts`, a bounded one-read probe:

- **Never imports `vscode`.** `probeWithToken` takes a token and a fetch; `probeVsCodeSession` takes an injected session provider. Unit-testable without the editor stub, and credential acquisition stays at the call site.
- **`isProbeAllowed` refuses enterprise + fine-grained** before issuing a request, so a documentary known-negative cannot spend a call or be recorded as ambiguous evidence.
- **A success body is never read.** `readSafeError` returns early on `response.ok` without touching `json()`, asserted with a spy.
- **Only `message` and `documentation_url` survive a failure body.** Everything else GitHub returns is dropped at parse time rather than filtered later.
- **`toSanitizedRecord` is the only supported serialization**, rebuilt field by field rather than spread, so a field added to `ProbeRecord` cannot reach a report until it is added here deliberately.
- **`toMarkdownRow`** emits a paste-ready results row for the probe doc.

The point of `test/auth-probe.test.ts` is that the "never record" list in the probe doc is **machine-enforced**: the serialized form cannot contain the token, `ghp_`, `authorization`, `bearer`, or any success-body field, and the emitted key set must equal the approved set exactly.

## Shipped improvement that fell out regardless of T022c

`withAuthorizationDiagnosis` in `src/providers/github.ts` attaches `X-Accepted-OAuth-Scopes`, `X-OAuth-Scopes`, `X-Accepted-GitHub-Permissions`, and `X-GitHub-Request-Id` to any failed billing response, and appends GitHub's own answer to the message. A `403` now reads "GitHub reports this operation accepts OAuth scopes: admin:org; the credential presented repo, read:user" rather than only the extension's guess from the configured scope. It adds nothing when GitHub reports nothing, so it never invents advice.

## Troubleshooting trail

1. **A false pass in my own verification.** The ASCII check on the new docs used `[System.IO.File]::ReadAllText` with relative paths. .NET resolves those against its own current directory, not PowerShell's `Set-Location`, so every read threw a `DirectoryNotFoundException` and the loop then printed `non-ASCII=0` from a stale variable. It read exactly like a clean pass. Re-run with `Resolve-Path`: the files are genuinely ASCII-clean, but the first result was measuring nothing. Recorded because a verification step that cannot fail is worse than no verification step.
2. **Separating requested from granted scopes** was a direct consequence of the `AuthenticationSession.scopes` trap. `ProbeRecord` keeps both fields and a test asserts they can disagree, so the distinction cannot be collapsed later by someone tidying the type.

## What was not achieved, and why

**T022c is not run, and cannot be run by an agent.** It needs live calls with a classic-PAT control against accounts that genuinely hold the required role and have enhanced billing enabled. Without the control a `403` or `404` is uninterpretable, because insufficient role, organization OAuth-app restrictions, and SSO authorization all produce those shapes. Recorded as **HO-6**, the second maintainer gate in v3.15.12 alongside HO-5.

**No Phase 4 implementation was written.** T023 onward depends on which credential class works per level, and that is what T022c determines.
