## Sub-tasks completed

### 4.1 - The `/tune-prompting` command

- Added `catalog/commands/tune-prompting.md` as a thin dispatcher, following the `route.md` shape (frontmatter `description` only, no other frontmatter needed for commands).
- The description is pushy and carries a SKIP clause fencing off the three realistic mis-routes: `/route` (choosing which model to run), `prompt-engineering` (tuning one prompt for an application), and `/usage` (consumption against limits). Command descriptions are not scanned by the trigger-collision gate (it walks `catalog/skills` only), so this is authored discipline rather than a gated property.
- Arguments: bare for the full flow, a single model id for the scope-first calibration run, `--dry-run`, and `--profiles-only`. The file states explicitly how the last two differ, because the distinction is easy to blur: `--dry-run` still reports what it WOULD change in a shared body, while `--profiles-only` never considers a shared-body edit at all.
- Documents the three load-bearing safety properties inline (the hard rail, branch isolation with human merge, and the budget plus degradation ladder), including the corrected note that `check_base_template_parity.py` does NOT enforce the rail, so a future reader of the command does not inherit the plan's false premise.
- Records the per-platform slash surfaces the new command reaches, per the AGENTS.md requirement to call these out for a new command.

### 4.3 - Register the skill

Hand-edited the three registry files per AGENTS.md rule 2, and deliberately did NOT run the catalog rebuild, which rewrites the whole tree. Tier-1 values (`description`, `summary_l0`, `overview_l1`) were read out of SKILL.md programmatically rather than retyped, so the registry cannot drift from the skill.

Both JSON files were verified to round-trip cleanly at indent 2 before editing, so a load-modify-dump keeps the diff to the additions only. Final diff: 3 lines in `SKILL_INDEX.md`, 4 in `marketplace.json`, 60 in `skills.json`.

**Registering the skill surfaced pre-existing registry drift that no gate was checking.** A four-way comparison isolated exactly what was wrong:

| Source | Before | Correct |
|---|---|---|
| `SKILL.md` files on disk | 268 | (the reference) |
| `skills.json` entry count | 268 | consistent |
| `skills.json` `statistics.total_skills` | **260** | 268 |
| `skills.json` `statistics.categories` sum | **261** | 268 |
| `marketplace.json` category sum | 268 | consistent |
| `SKILL_INDEX.md` total line | **267** | 268 |

The entry list and `marketplace.json` were already correct and per-category consistent. Only the `statistics` block (stale in five categories: code-review 13, developer-experience 30, orchestration 15, project-setup 4, workflow 41) and the index total were stale, both generated 2026-03-26 and never regenerated because the rebuild script is deliberately not run.

All were set to true values. After registration every surface reads a consistent **269** with matching per-category counts, and `marketplace.json`'s `plugin.description` moved to 269 skills and 17 commands.

**Scope note**: correcting `statistics.categories` was completing my own edit rather than adjacent cleanup. Phase 4 necessarily edits that same `statistics` block (to increment `ai-development`), and leaving `total_skills: 269` beside a breakdown summing to 261 would have been self-inconsistent.

### Root cause closed rather than logged

Added `tests/validators/test_registry_consistency.py` (9 tests). It asserts:

- every on-disk skill appears in `data/skills.json`, and no entry lacks a `SKILL.md` on disk;
- `statistics.total_skills` equals the entry count, and `statistics.categories` matches the per-category entry counts exactly;
- `marketplace.json` category counts sum to the catalog size and agree per-category with `skills.json`;
- `SKILL_INDEX.md`'s total line matches the catalog and carries a row per on-disk skill;
- every index summary is quoted, because the MCP server parses those.

Both drifts would have been caught by it, and it found the five-category `statistics` drift the moment it was written (the totals-level tests passed after my first pass; the per-category tests are what exposed the rest). It deliberately covers the machine-readable files only: prose counts in AGENTS.md and README vary in phrasing too much to assert safely, so those stay Phase 6.1's job (NI-4).
