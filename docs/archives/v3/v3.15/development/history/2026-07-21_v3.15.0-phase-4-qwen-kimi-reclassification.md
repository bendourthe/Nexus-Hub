## Overview

Phase 4 is the plan's highest-risk phase: it changes two integrations' base types from instruction-file-only (`MarkdownIntegration`) to full skills mirrors (`+ SkillsIntegration`). Both were GO per Phase 1, and each reclassification was preceded by a direct doc re-read that resolved a Phase-1 known-gap (DF-2 for Qwen, DF-3 for Kimi). Two decisions were taken up front via a batched pre-flight question: Kimi migrates FULLY to the current product (vs keeping `~/.kimi/` back-compat), and Qwen commands are Markdown (vs the plan's TOML wording).

Delivers flattened skills + agents + Markdown commands at `~/.qwen/{skills,agents,commands}` (global, detection-gated on `~/.qwen`) and `.qwen/{skills,agents,commands}` (project), preserving the `QWEN.md` write. Workspace uses the base `super()` chain (QWEN.md at root via `instruction_workspace_dir=""`, skills/agents under `.qwen/` via `workspace_dir`) plus a Markdown command mirror; global is bespoke (detection gate).

## Decisions

- **Qwen commands = Markdown (deviation from the plan's TOML wording)**: Qwen's docs make Markdown the primary format and TOML deprecated (with an in-product migration prompt), so shipping TOML would degrade UX. Markdown is delivered via `mirror_command_surface` (like Cursor). Documented as a deviation.
- **Kimi = FULL migration to `~/.kimi-code/` (maintainer choice)**: over keeping `~/.kimi/` back-compat or a no-go. Trade-off: a user still on the old "Kimi CLI" (`~/.kimi/`) no longer receives a surface; accepted.
- **DF-2 mitigation**: no live Qwen build available, so skills ship to both scopes (global is the reliable path), per the gap's own suggested mitigation.
- **Native skills path only** for both (Qwen `~/.qwen/skills`, Kimi `~/.kimi-code/skills`), not the shared `~/.agents/skills`, to avoid an uninstall teardown conflict with the codex integration.
