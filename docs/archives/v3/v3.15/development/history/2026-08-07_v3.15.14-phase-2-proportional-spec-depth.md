## 2.1 - The depth-tier rule

**Placement.** The plan said "immediately after the hard-gate block so a reader meets the gate before the tiering, never the reverse." A sibling `##` section placed after the gate satisfies the letter of that. The rule went in one level stronger, as `### Spec depth is proportional; the gate is not`, a subsection under the Hard Gate's own heading, before "One Question at a Time". Nested there, the tiering cannot be encountered detached from the constraint it refines, and a reader skimming headings sees it as part of the gate rather than as a neighbour of it. In a governance rule, document order is load-bearing.

**The invariant is restated first, before any tier appears.** "The gate governs whether you and the user agree on what to build. The depth governs how much document that agreement needs. These are independent axes, and this rule moves only the second one."

**Depth is keyed on blast radius, with what blast radius is NOT stated inline.** Effort, line count, and elapsed time are named and excluded, followed by the counterexample: a three-line change to a public API has a larger blast radius than a three-hundred-line change to a private helper. Without that counterexample "blast radius" degrades into a synonym for "size", which is exactly the framing the rule replaces.

**The tier table:**

| Blast radius | Required spec depth |
|---|---|
| One file, internal, with no surface a consumer can observe | Problem Statement, acceptance criteria, and Non-Goals. Short enough to fit in a chat message; it does not need its own file. |
| Multiple files or multiple modules, still internal | The above, plus User Scenarios with an Independent Test, FR-### items, and Assumptions. |
| A change to behavior, a public API, a data schema, or a CLI surface | The full canonical template written to `spec.md`, including Invariants. |

The bottom tier is the promotion the plan asked for: the existing rationalization row "Simple tasks don't need long specs, but they still need acceptance criteria. A two-line spec is fine" is now a stated rule, and the row stays in place as the rebuttal it already was.

**The top tier reuses the merge gate's four surfaces verbatim.** Behavior, public API, data schema, CLI surface, byte-identical between the tier table (line 37) and "The Spec as a Merge Gate" (line 271). This was verified with a single grep matching both. Because they are the same string, the entry rule and the merge rule cannot drift into contradiction, and the skill can state plainly that they are one rule seen from each end: a change that must update its spec before it can merge is a change that needed the full spec before it started.

**Three defenses against the misreading.** First, the guard clause uses three verbs where one would do: "Shrinking the artifact does not shrink the gate, shorten it, or make silence count." Each closes a separate paraphrase route, and the third is aimed at the gate's own "Silence is not approval", the clause a reader in a hurry is most likely to reinterpret. Second, the bottom tier explicitly hands the no-spec question off to "When NOT to use" rather than answering it, so the tier table never becomes the authority on whether a spec exists at all. Third, the closing line resolves ambiguity upward: "When two tiers both look defensible, take the higher one. Over-specifying costs a paragraph; under-specifying costs the rebuild."

**"When NOT to use" now separates the two axes.** It previously read as one sentence keyed only on change size, which is what left proportionality unanswered. It now states that it answers only whether a spec is needed, that how much spec is the depth rule's question, and why keeping them apart matters: "the change is small" is an answer to the second question that reads like an answer to the first, so a change that is small but real gets a SHALLOW spec, not no spec. The closing instruction is to reach for "no spec" only when there is genuinely nothing to agree on, not when there is little to agree on.

**Two rationalization rows, where the plan asked for one.** Row 4 is the one the plan named, rebutting "the depth rule says small changes get a short spec, so I can skip the approval step". Row 5 covers a misreading the plan did not name and that is arguably likelier in practice: "the change is small, so it falls under 'When NOT to use'". These are different errors. The first treats a short spec as licence to skip approval; the second collapses a shallow spec into no spec at all. One row could not rebut both without blurring, so a second was added. Recorded as EN-1, an enhancement rather than a deviation, because it adds material without departing from anything the plan specified.

## 2.2 - The scaling argument

One paragraph added to the opening motivation, immediately after the "Code without a spec is guessing" line so it lands as an explanation of that sentence rather than as a separate claim.

The argument: an agent that reaches an unstated requirement does not stop and ask; it fills the gap with the most plausible interpretation and keeps building on it. In a small codebase those guesses stay visible because there is not much code for them to hide in. In a large one they land in details nobody inspects, so the consequence surfaces later, somewhere else, in code the author never touched, where it reads as an unrelated bug rather than as a decision that was never made. Guess cost therefore scales with the size of the system, not with the size of the change, which is why a small change to a large codebase deserves more written agreement than its diff suggests.

The paragraph closes by tying the argument to the mechanisms the skill already ships, as the plan required: the `[NEEDS CLARIFICATION]` marker and the mandatory `## Assumptions` section both convert a silent guess into a recorded decision the reviewer can overturn with one line.

No external article, author, newsletter, or repository is named anywhere in the file, per the AGENTS.md reverse-engineering attribution rule. Provenance goes in the Phase 4 matrix row.
