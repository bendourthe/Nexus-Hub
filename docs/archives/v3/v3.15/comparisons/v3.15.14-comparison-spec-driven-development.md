## 1. Executive Summary

The article's substance is a six-part spec structure plus one meta-claim about when specs are worth writing. Measured against Nexus-Hub's existing `spec-driven-development` skill, `spec-template.md`, and `spec-quality-checklist.md`, **two of the six parts are already implemented more strongly than the article describes, two are partially implemented, one is deliberately divergent, and one is genuinely missing**. The Spec Kit half of the source is fully closed: all ten `speckit.*` commands map one-to-one onto shipped Nexus-Hub surfaces, so the article's "send them Spec Kit" recommendation produces zero new candidates.

The highest-value finding is not a gap against the article at all. It is an **internal inconsistency the article's checklist exposed**: three Nexus-Hub surfaces audit a spec for scope bounding while the canonical template provides no section to write it in.

- [`catalog/templates/spec-quality-checklist.md`](../../../../../catalog/templates/spec-quality-checklist.md):22 requires "Scope is clearly bounded".
- [`catalog/agents/scope-guardian-reviewer.md`](../../../../../catalog/agents/scope-guardian-reviewer.md):14 reports a finding when there is "no 'explicitly out of scope' section".
- [`catalog/skills/developer-experience/idea-refine/SKILL.md`](../../../../../catalog/skills/developer-experience/idea-refine/SKILL.md):152 gates on "Scope is explicitly bounded: at least one thing is declared out of scope", and produces an `**Out of Scope**` block at line 108.

Meanwhile [`catalog/templates/spec-template.md`](../../../../../catalog/templates/spec-template.md) has exactly four sections (User Scenarios & Testing, Requirements, Success Criteria, Assumptions) and mentions "out of scope" only inside an *example assumption* at line 125. The upstream `idea-refine` stage produces the scope boundary and the downstream reviewers demand it, but the spec artifact in between drops it. Every reviewer run on a template-conformant spec is therefore guaranteed to raise a finding the template caused.

A second defect surfaced by the same read: the skill instructs the author to "use `catalog/templates/spec-template.md` as the starting skeleton for every feature spec" (line 72), then presents a **different** inline template at lines 176-207 (Objective / Tech Stack / Commands / Project Structure / Code Style / Testing Strategy / Boundaries / Success Criteria / Open Questions), and its Verification checklist at line 295 validates "all six core areas (Objective, Commands, Structure, Style, Testing, Boundaries)", which are the **inline** template's areas and not the canonical template's. The skill's own completion gate checks the wrong artifact.

**Overall recommendation: adopt the two structural slots the article names correctly (non-goals and a problem statement), fix the template drift the reading exposed, tier spec depth without touching the hard gate, and decline the article's architecture-in-the-spec merge.** Seven candidates (D1 through D7), zero new outbound calls, zero credentials, zero dependencies, zero new skills, and therefore no `data/` registry or installer edits.

## 8. Risks and Conflicts

- **D6 is the one item that can do harm if written loosely.** The purpose is to make the *artifact* proportional, never the *approval*. A depth rule phrased as "small changes may skip the spec" reintroduces exactly the guess-compounding failure the article opens with, and contradicts SKILL.md:21-23. Phrase it as a tier table keyed on blast radius (a one-file internal change gets acceptance criteria plus non-goals; a multi-module or public-surface change gets the full template), and keep the "silence is not approval" clause untouched. The existing rationalization rows at SKILL.md:281-282 already defend the gate against "this is too simple" and "the user said just build it"; D6 must not weaken either.
- **D1 changes a completion gate and must be atomic.** Repointing Verification at the canonical sections changes what the skill accepts as a finished spec. Split across commits, the skill would briefly validate sections that no template produces. Land D1, D2, and D7 together.
- **D2 must not duplicate the Assumptions section.** `A1`'s example already reads "JWT is out of scope for this feature" (spec-template.md:125). The boundary: Assumptions record a *decision the reviewer can override with one line*; Non-Goals record *scope the reviewer is being asked to confirm is excluded*. State the distinction inline or the two sections will collect the same entries.
- **D7 must not duplicate D2.** Non-Goals declare what will not be built; Invariants declare what existing behavior must not break. Both belong in the template only if the distinction is stated at the point of use.
- **D3 and D4 must stay at the plan layer.** Both describe implementation strategy. Putting either in the normative spec would recreate the I5 conflict this report declines, and would trip the checklist's implementation-detail checks.
- **No new skill, so no registry or installer work.** Every target is an existing file (`catalog/templates/*.md`, `catalog/skills/developer-experience/spec-driven-development/SKILL.md`, and one plan-layer skill). AGENTS.md rule 2 (three `data/` registry files) does not apply, and no installer copy step is needed because `catalog/templates/` already installs to `~/.nexus-hub/templates/`. If implementation adds a *new* template file rather than editing existing ones, re-check the installer path before merge.
- **Breaking changes**: none. Additive sections plus a defect fix, so a backward-compatible **PATCH** or **MINOR** bump is appropriate for v3.15.14.

## 9. Strengths to Preserve (where Nexus-Hub leads)

- **The clarification-marker economy.** The 3-marker hard cap, the `scope > security/privacy > UX > technical` priority order, and the mandatory demotion-to-assumption path (SKILL.md:44-68) are a genuine advance over both the article and Spec Kit, which prompt for assumptions without bounding them. A spec carrying twelve open questions signals scope confusion, and the cap is what surfaces that.
