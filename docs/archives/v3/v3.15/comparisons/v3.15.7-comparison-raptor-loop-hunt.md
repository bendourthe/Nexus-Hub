## Executive Summary

`raptor-loop-hunt` is a single, very deep Claude Code skill: 1043 lines of methodology, three reference schemas, five pure-stdlib Python scripts, and an 11-axis evaluation battery. Its thesis is stated at `SKILL.md:27`: "The prompt is the program." It replaces a model's default single-pass audit behavior with an explicit search procedure, and it backs that procedure with mechanical enforcement rather than prose exhortation.

Nexus-Hub already has substantial security coverage: 15 skills under `security/` and 15 under `security-operations/`, plus [adversarial-verifier](../../../../../catalog/skills/orchestration/adversarial-verifier/SKILL.md), [multi-agent-code-review](../../../../../catalog/skills/code-review/multi-agent-code-review/SKILL.md), and [loop-engineering](../../../../../catalog/skills/workflow/loop-engineering/SKILL.md). Several of the source's headline ideas are therefore already present. Generate-then-refute exists in `adversarial-verifier`. Loop-until-dry exists in [competitive-generation](../../../../../catalog/skills/orchestration/competitive-generation/SKILL.md) as a K-consecutive-rounds no-progress stop with K=2 default, the same rule and the same default the source uses. Iteration caps and observable exit conditions are mandatory fields in `loop-engineering`. Treating a scanned target's text as untrusted data is owned by [prompt-injection-defense](../../../../../catalog/skills/security/prompt-injection-defense/SKILL.md).

What is genuinely absent is the **enforcement layer**, and that is where the value sits. Nexus-Hub's security skills tell the agent what good practice looks like; the source makes specific failures mechanically impossible. Three mechanisms have no Nexus-Hub equivalent at all:

1. **A completeness gate with an explicit denominator.** Enumerate every component before round 1, treat that list as the coverage denominator, and record any component not yet assigned to a cell as `UNCOVERED` rather than letting it be absent from the ledger (`SKILL.md:78-102`). The failure it prevents is a shallow audit reading as a complete one. The nearest in-repo precedent is not in a security skill at all: the in-flight `model-prompting-research` skill requires reporting an unresearched model as UNVERIFIED "rather than omitting it silently" (`SKILL.md:61`). The pattern is proven in the repo; it has simply never been applied to security review.
2. **Typed dispositions with evidence receipts, enforced at transition time.** Every finding lands in exactly one of `confirmed` / `needs-live-validation` / `corrected` / `rejected`, and each terminal transition is refused unless a typed receipt exists (`SKILL.md:443-509`). The standout is `needs-live-validation`: a first-class outcome for a finding whose only remaining barrier is a layer the reviewer cannot observe. The source documents a real case where a judge collapsed such a finding to "low/server-dependent" and it was later confirmed as unauthenticated mass account takeover (`SKILL.md:418-424`).
3. **A rejection proof burden.** Killing a finding carries the finding's own evidentiary burden, because a false rejection silently erases a real bug while a false confirmation stays visible and retestable (`SKILL.md:584-602`).

Eleven adoption candidates result. Nine are `skill-native` doctrine that improves existing skills. Two are `re-full` / `re-partial` local builds: an execution-authorization broker and a deterministic closure-gate script. Nothing requires a new dependency, credential, or outbound call. The source's own hard dependency on the external RAPTOR toolchain is the primary NOT-recommended item, and the methodology is fully adoptable without it.

Candidate B6 (the execution-authorization broker) is worth flagging for sequencing: it is the natural enforcement companion to the v3.15.6 sandbox-escapes adoption, whose central finding is that agents escape by writing config a trusted component later executes. A typed capability grant is exactly the gate that pattern needs.

### 3.1 Adoption candidates

| ID | Bucket | Item | Evidence and gap |
|----|--------|------|------------------|
| B1 | `+` | **Completeness gate with an explicit denominator.** Enumerate every component before round 1; that list is the coverage denominator. Every component is either covered or explicitly listed as omitted with a reason; a component not yet assigned is recorded `UNCOVERED`, never absent (`SKILL.md:78-102`). Reporting must state "N of M components covered" and must never imply completeness while modules sit unexamined (`SKILL.md:703-714`). | No Nexus-Hub security skill defines a coverage denominator. `security-review` enumerates 10 domains to check but has no mechanism binding those to the target's actual component list, so "I audited the interesting parts" passes silently. | B2 | `+` | **Two-axis severity plus the `needs-live-validation` disposition.** When only part of the system is observable, rate confirmed severity AND potential severity separately, carry the higher into triage, and never collapse potential to Low because the confirming layer is out of view (`SKILL.md:411-424`, `SKILL.md:443-454`). | `pentest-reporting` uses a single CVSS-derived band with a context override (`SKILL.md:67-72`). There is no two-axis rating and no disposition for "real and reachable, final proof depends on an unobservable layer". Today such a finding has nowhere to sit except an understated band. |
| B3 | `+` | **Refutation-validity taxonomy.** An explicit list of what may and may not kill a finding. VALID: the cited code does not do what the claim says, the entry is not attacker-reachable, a mitigating check is present in code you can read. Assuming an unseen layer is secure is named as the single most common false negative. | `adversarial-verifier` instructs the agent to try to break an implementation but never constrains what counts as a valid refutation. An unconstrained skeptic dismisses real findings on plausible-sounding assumptions, which is the exact failure this taxonomy blocks. |
| B4 | `+` | **Fraud-class table with mechanical tells.** Sixteen named dishonesty patterns, each with the specific artifact mismatch that detects it: fabricated PoC output (claimed observation with no matching artifact hash), crash inflated to RCE (bare-crash oracle behind a memory-corruption exploitability claim), read-derived coverage (component marked covered from file reads with no logged hunt action), unexecuted vector listed as tested (`SKILL.md:546-569`). | Nexus-Hub has no costume-rigor detection anywhere. `verification-before-completion` requires fresh evidence before a completion claim but does not enumerate the ways a report can fake having done the work. |
| B5 | `+` | **Rejection carries the finding's proof burden.** A kill requires enumerating the sink's actual input sources and proving the barrier holds on ALL of them, because a mitigation blocking one delivery vector rarely blocks the rest. Rationale: false rejections are the costliest error because they silently erase real bugs while false confirmations stay visible and retestable (`SKILL.md:584-602`). | No Nexus-Hub skill places an evidentiary burden on a negative finding. Rejections are currently free, which is where the blind spot lives. |
| B6 | `+` | **Execution-authorization broker (typed capability grant).** A live action declares which of `network` / `write` / `use_secret` / `destructive_test` it requires and runs only under a grant authorizing them, else it is denied. Authorization is pure-stdlib and side-effect-free, the default plan blocks network and writes, a grant with no `authorization_source` is refused, and `--exec` refuses when no sandbox is reachable (`raptor-loop-exec:1-60`, `SKILL.md:911-923`). | B7 | `+` | **Closure gate as a deterministic set diff, not a model self-audit.** Explicitly refuses to ask the model to re-read its own work and grade it, on the stated grounds that a reasoner re-reading its own output ratifies its own omissions and that "spot what I skipped" is a notice-an-absence pass that does not transfer. Replaced by seven mechanical set differences over the ledger; any non-empty diff is a gate failure (`SKILL.md:722-750`). | Nexus-Hub's review skills end with self-assessed Verification checklists, which is precisely the self-audit shape the source rejects. `cross-artifact-analyzer` computes a coverage matrix by ID matching, which is the closest mechanical analogue, but it is scoped to spec-to-task coverage rather than review-claim-to-evidence. |
| B8 | `+` | **Multi-altitude traversal.** Four zoom levels (whole project, file by file, functionality by functionality, function by function), with the observation that a single-pass scan implicitly picks one altitude and is structurally blind to the others (`SKILL.md:52-77`). | `security-review` organizes by vulnerability domain, not by altitude. Domain coverage and altitude coverage are orthogonal, so a domain-complete review can still be altitude-blind. |
| B9 | `+` | **Proven-dirty sweep rule.** Once attacker-influenced data reaches a security-sensitive sink, sweep that sink's other trigger paths before rating, downgrading, or closing. Negative evidence is scoped to the path actually tested; a gate holding on one ingress does not clear the sink (`SKILL.md:621-645`). | No equivalent. Nexus-Hub's security skills treat findings as independent, so one tested-and-gated ingress currently reads as a cleared sink. |
| B10 | `~` | **Trap-based eval battery.** Eleven axes, each with a named tempting shortcut as the failure. Deterministic axes run with no model in milliseconds; live axes use seeded fixtures whose ground truth is never shown to the executor, with randomized symbol names and file layouts so a model cannot memorize the corpus. Verdicts come from produced artifacts, never the executor's prose (`eval/README.md`). | Nexus-Hub has `skill-eval-loop` (paired with-skill / baseline, assertion-graded) and `run_trigger_evals.py` (routing assertions). | B11 | `+` | **Monotonic-scrutiny cross-run knowledge base.** A durable store that can only ever RAISE scrutiny: it stores no coverage and no "safe" signal, never deprioritizes, and never excludes a candidate, so even a fully poisoned store can only waste budget, never cause a skip (`SKILL.md:346-366`). | `known-gaps-tracker` persists unfinished work across versions but carries no monotonicity invariant, so a stale entry can in principle reduce attention. ## Step 7: Risks and Conflicts

### C1: Skill-size norm (hard conflict)

The source is a 1043-line monolith, well past Nexus-Hub's 800-line hard cap and its 500-line target. Adopting it as a single skill would violate the norm on arrival and would be rejected by the size rule in `AGENTS.md`.

### C2: Offensive-content framing

The source is an offensive methodology with a real track record against production software. Nexus-Hub's offensive skills each carry an explicit authorization-and-scope requirement, which the source states once (`README.md:139`) and does not repeat in the skill body.

**Resolution**: every adopted section inherits the receiving skill's existing authorization framing. ### C3: An advisory broker is worse than no broker

B6's value depends entirely on being enforcing. A capability broker adopted as advisory (printing a plan the agent may ignore) creates a false sense of control while changing nothing, which is strictly worse than the current state because it invites relaxed vigilance elsewhere.

**Resolution**: B6 ships as a deny-by-default gate returning a non-zero exit on denial, matching the source's exit-3 contract, or it does not ship. The source's own framing is the test to apply: "A prose AUTH: line a model writes is not a security boundary."

### C4: Overlap with the v3.15.6 sandbox-escapes adoption

v3.15.6 already plans a deny-by-default permission stub and a file-provenance trust-seam hook. B6 is adjacent and could duplicate it.

**Resolution**: treat this as a sequencing dependency, not a conflict. Read the v3.15.6 plan before implementing B6 and position the broker as the capability-grant layer above the permission stub, not a competing mechanism. If v3.15.6 slips, B6 should follow it rather than land first.

### C5: Doctrine density and agent attention

The source's power comes from density, but Nexus-Hub's security skills are already substantial. Adding seven doctrine sections across four skills risks pushing them past the 500-line target and diluting the instructions that matter most.

**Resolution**: measure each receiving skill's line count before and after. Where an addition pushes a skill past 500 lines, move the detail into `references/` and leave a linked summary in the body, per the three-tier model. Note the orphan-bundle audit requires every new reference file to be linked from its parent `SKILL.md`.

### C6: Attribution

MIT-licensed, same constraint as any adopted source. The Reverse-Engineering Attribution Rule forbids naming the external repo in the distributed artifact.

**Resolution**: write the doctrine in Nexus-Hub's own voice, do not reuse the source's prose, tables, or its `F-NN` finding identifiers (which reference the author's private engagement history and are meaningless here). Record provenance in `docs/policy/mcp-reverse-engineering-matrix.md`. Do not carry over the track-record or CVE tables; they are the author's provenance, not adoptable content.
