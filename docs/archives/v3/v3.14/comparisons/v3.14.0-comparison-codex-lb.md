## Step 1.5: Source Security Scan (verdict: CLEAR)

The cloned repository was scanned as potentially adversarial BEFORE any content was ingested for comparison. The scan covered agent-directed instruction files first (highest indirect-prompt-injection risk), then executable agent-side code, build/CI, and manifests.

- **Prompt injection / embedded agent-directed instructions**: none. The repository contains legitimately instruction-like files (`AGENTS.md`, `CLAUDE.md` pointing to `AGENTS.md`, and a full `.agents/skills/**/SKILL.md` tree), but every one is codex-lb's own contributor-facing configuration describing *that* project's workflow. None attempts to override an external agent's instructions, and there are no "ignore previous instructions" payloads. All instruction-like text is treated strictly as data for this comparison.
- **Hidden / obfuscated content**: none. A danger-pattern grep (`curl|wget` piped to a shell, `rm -rf` on `$`/`~`/`/`, `base64 -d`, `eval(`, `nc -e`, `/dev/tcp/`) across `*.sh`, `*.yml`, `*.py`, `*.js`, `*.ts`, `*.toml`, `Makefile`, and `Dockerfile*` returned only legitimate Docker image-slimming lines (`rm -rf /var/lib/apt/lists/*` and pip-cache cleanup). No zero-width characters or base64 instruction blobs.
- **Malicious or destructive code**: none. The executable agent-side code (`.agents/hooks/*.py` and `.agents/skills/codex-review-loop/scripts/codex-subagent.sh`) was read directly. The subagent script is a careful `set -euo pipefail` wrapper around the `codex exec review` CLI with no network calls of its own and no destructive operations. A targeted grep of the hooks for outbound / exec / secret surface (`requests`, `urllib`, `socket`, `subprocess`, `os.system`, `Popen`, `exec(`, `eval(`, `token`, `secret`, `api_key`) matched nothing: the hooks are pure local file-tracking and skill-activation logic.
- **Supply-chain risk**: none. `.env.example` holds placeholder configuration only (SQLite path, upstream base URL, timeouts), no real secrets. `AGENTS.md` references `GITHUB_TOKEN` for CI automation with an explicit "Do not hardcode or commit tokens" instruction, which is standard practice, not harvesting. `.pre-commit-config.yaml` pins conventional tooling (ruff, a `ty` type check, frontend lint/typecheck/test).

Verdict: **CLEAR**. Proceeding to ingestion. The checkout of one deeply-nested `openspec/changes/archive/...` path failed on Windows path-length limits; this affected an archived spec folder only and did not impact any file cited below.

## Executive Summary

codex-lb and Nexus-Hub are **different product categories**, so a literal feature-for-feature comparison is mostly not-applicable. codex-lb is a runtime-infrastructure product: a load balancer and proxy for ChatGPT (Codex) accounts, with account pooling, per-account usage tracking, per-key rate limits, failover / retry, a dashboard, and OpenCode-compatible endpoints (Python 3.13, uv, FastAPI, SQLAlchemy + Alembic, Pillow, plus a TypeScript frontend). Nexus-Hub is a static catalog distributed by an installer to AI coding assistants. Nexus-Hub will not become a proxy, so almost none of codex-lb's product surface is an adoption target.

The comparison's value is concentrated one level up, in **how codex-lb is built with agents**. codex-lb has independently engineered a mature agentic-development harness under `.agents/`, and that harness is precisely Nexus-Hub's product domain. Evaluated against Nexus-Hub, most of codex-lb's disciplines are already present in Nexus-Hub in a more general or more portable form. A small set are genuine sharpening opportunities.

The distinctive net-new opportunities, in priority order:

1. A **declarative skill-activation ruleset plus a PreToolUse guard and usage tracker** (codex-lb's `skill-rules.json` + `skill_activation.py` / `skill_guard.py` / `skill_tracker.py`). This is the flagship finding: a deterministic, file-path-triggered and prompt-keyword-triggered layer that force-suggests (and can hard-block) a skill, directly attacking the skill under-triggering problem that Nexus-Hub's own `AGENTS.md` flags as measurable. Nexus-Hub triggers skills purely by model judgment over a pushy description, with no deterministic backstop.
2. A **review-trapdoors / recurring-blockers doc convention** (codex-lb's "PR Readiness / Review Trapdoors" section): a curated, project-specific list of failure modes agents pre-empt before review.
3. A **machine-checkable merge-gate contract** convention (codex-lb's `CONTRIBUTING.md` merge gates binding CI + cross-model review + PR hygiene into one verifiable gate).
4. A **normative-spec vs free-form-context split with spec-as-a-merge-gate** convention (codex-lb's OpenSpec model), adopted as a convention only, never the external `openspec` CLI.
5. Concretizing Nexus-Hub's **cross-model review** story into a runnable, model-agnostic recipe with the safety limits codex-lb's `codex-review-loop` demonstrates (max iterations, recurrence to `wont_fix`, atomic fix-verify-commit).

One codex-lb pattern (a mid-task **handover worksheet** under `.agents/handover/`) is a convergent independent confirmation of a gap Nexus-Hub already identified in the v3.12.1 comparison (Point 7) and is already being built in the v3.13.0 plan, so it is noted as validation rather than re-added as a candidate.

Separately, a product-surface extraction rises to the top of the priority list because it is directly requested: a **Codex Usage Monitor** VS Code extension that mirrors the existing Claude Usage Monitor (`extensions/claude-usage-monitor`) for the ChatGPT Codex app. codex-lb reveals that account-level Codex usage and quota come from an authenticated upstream endpoint (`{base}/backend-api/wham/usage`, `app/core/clients/usage.py`), not from proxy interception, so the same status-bar / tooltip / dashboard / threshold-warning UI can be reused verbatim while only the credential reader and the fetcher change. This is candidate U1 below and is the recommended first build.

## Detailed Analysis of the Adoptable Set

### C1: Declarative skill-activation ruleset plus guard (flagship)

This is the standout. Nexus-Hub's entire triggering model is model judgment: the agent reads a deliberately pushy `description` and decides whether a skill applies. `AGENTS.md` openly documents that this under-triggers ("Claude has a measurable tendency to under-trigger when the description is narrow"). codex-lb solves the same problem **deterministically**. `skill-rules.json` declares, per skill, `promptTriggers` (keyword and regex `intentPatterns`, including non-English keywords) and `fileTriggers` (`pathPatterns`, `pathExclusions`, `contentPatterns`). A `UserPromptSubmit` hook (`skill_activation.py`) suggests skills from the prompt; a `PreToolUse` Edit/Write hook (`skill_guard.py`) can hard-block an edit with a `blockMessage` ("BLOCKED: Run /project-conventions first") until the required skill has run; a `PostToolUse` Skill hook (`skill_tracker.py`) records which skills were used so `skipConditions.sessionSkillUsed` stops re-prompting; an env override (`SKIP_CONVENTION_GUARD`) provides an escape hatch.

For Nexus-Hub the adoptable capability is a **deterministic activation backstop**: an opt-in rules file plus an activation hook that *suggests* the highest-relevance catalog skill when a prompt or an edited file path matches, closing the under-triggering gap the model-judgment path leaves open. The one hard conflict is posture: codex-lb's guard is fail-closed and blocking, whereas Nexus-Hub's hooks are advisory and fail-open by design. The mechanism must be inverted to opt-in and suggest-only by default (a blocking mode gated behind an explicit env flag, mirroring the `NEXUS_HUB_COPILOT_SKILLS` opt-in precedent).

### C4: Review-trapdoors doc convention

codex-lb's `AGENTS.md` carries a curated "PR Readiness / Review Trapdoors" section: concrete, project-specific failure modes distilled from real review history, kept in-context so agents pre-empt them. Nexus-Hub's `continuous-learning` produces local YAML instincts and `solution-knowledge-base` documents solved problems, but neither is a curated, always-loaded, review-keyed blocker list. The adoptable piece is a lightweight convention (a `review-trapdoors.md` project artifact, referenced from `AGENTS.md`) plus a thin skill that maintains it from recurring review findings. It composes naturally with `continuous-learning` (instincts feed the curated list) and `project-constitution`.

### C6: Merge-gate contract convention

codex-lb binds CI, cross-model review, `mergeable` state, spec presence, and issue linkage into one contributor-and-agent-facing merge contract, with an assistant instruction to verify each gate against live GitHub state. Nexus-Hub has the constituent pieces (`quality-gate-definitions`, `shipping-and-launch`, `git-branching-workflow`) but not a single bound contract. Adopting this means a convention doc plus a checklist skill that composes the existing gates and cites C3's evidence discipline.

### C5: Spec / context split with spec-as-merge-gate

codex-lb keeps `spec.md` strictly normative (MUST/SHALL requirements only) and pushes rationale, examples, and ops notes into `context.md`, with change folders archived by date and a hard rule that behavior / API / schema changes require a spec before code. Nexus-Hub's `spec-driven-development` and phased `/plan` cover the intent but not the normative/context separation or the spec-as-merge-gate rule. The adoptable material is the convention; the external `openspec` CLI is explicitly out of bounds under the reverse-engineer-first policy.

### C2: Concretize cross-model review

Nexus-Hub's cross-model story is broader and vendor-neutral, which is the right posture. The gap codex-lb exposes is concreteness: a single runnable recipe that drives a second model as a background review subagent, parses output into a findings schema, and loops until clean with explicit safety limits (max 3 iterations, recurrence to `wont_fix`, atomic per-finding fix-verify-commit). This is a refinement of `cross-model-orchestrator`, not a new skill, and it must stay model-agnostic (no hardcoded vendor CLI).

### U1: Codex Usage Monitor (reverse-engineered wham/usage fetcher, reused UI)

This is the directly-requested build and the recommended first phase. The existing `extensions/claude-usage-monitor` already provides the entire presentation and alerting layer: a color-coded status-bar item, an SVG hover tooltip with per-metric progress and reset timers, a dashboard webview, configurable thresholds (moderate / high / critical) with notifications, and an auto-refresh loop. Its pipeline is `read local credential -> authenticated usage fetch -> normalized usage model -> render`. A Codex Usage Monitor reuses that pipeline and the whole UI unchanged, swapping only two seams.

- **Credential seam**: the Claude monitor reads the OAuth token from `~/.claude/.credentials.json` (or the macOS Keychain). The Codex variant reads the ChatGPT / Codex OAuth token from the Codex CLI's local credential store (expected `~/.codex/auth.json`, honoring `CODEX_HOME`; the exact path and field names must be confirmed at implementation time because codex-lb performs its own OAuth-to-database login and therefore does not demonstrate the CLI's on-disk layout).
- **Fetcher seam**: the Claude monitor calls the Anthropic usage API. The Codex variant calls `https://chatgpt.com/backend-api/wham/usage` with `build_chatgpt_auth_headers` (a bearer token plus a `chatgpt-account-id` header) and parses the `UsagePayload` shape. That payload maps cleanly onto the monitor's existing model: `UsageWindow.used_percent` becomes the status-bar percentage, `reset_at` / `reset_after_seconds` drive the reset timers, the primary / secondary windows map to the session / weekly metrics the monitor already renders, and `plan_type` / credits / `additional_rate_limits` enrich the dashboard.

Two facts make this a legitimate reverse-engineering target rather than a proxy dependency. First, the usage data is a single authenticated pull from the user's own ChatGPT account (the same call the Codex app already makes on the user's behalf), so there is no new third-party data processor, no new outbound destination beyond the user's own OpenAI account, and no need to run codex-lb, its database, or its dashboard. Second, per the MCP Registry Policy tier-3 rule, the endpoint knowledge and payload semantics are extracted into a local fetcher with generic naming and no external-source attribution in the shipped artifact.

Recommended packaging: generalize the Claude monitor's data layer behind a small provider interface (`credentialSource` + `usageFetcher` + a normalized `UsageModel`) and ship Codex as a second provider, so one extension serves both with a provider toggle, rather than forking a second codebase. The model-switch recommendation engine is repurposed for Codex into throttle / wait-for-reset / account-rotation guidance, since Codex does not expose a cheaper model tier the way Claude does.

**Caveat (durability)**: `wham/usage` is an internal, undocumented ChatGPT backend endpoint. OpenAI can change it without notice, which is the same fragility class as the Claude monitor's dependency on the Anthropic usage endpoint, arguably slightly higher because it is reverse-engineered rather than semi-public. The extension must fail soft (show "usage unavailable", keep the manual-entry fallback the Claude monitor already has) rather than error hard.

## Step 5: Security and Reverse-Engineering Assessment (MANDATORY)

### 5.1 Threat model comparison

Every recommended candidate is internal to the catalog. Adopting the recommended set introduces:

- **New runtime dependencies**: none for the agentic-setup set. C1 ships local hook scripts (Python stdlib only, matching codex-lb's own dependency-free hooks) plus a JSON rules schema. C2 uses whatever model / CLI the user already has. The one dependency the source implies (the external `openspec` CLI behind C5) is explicitly dropped in favor of a convention. U1 reuses the existing VS Code extension toolchain (`extensions/claude-usage-monitor`); no new runtime dependency beyond what that extension already carries.
- **Outbound-call destinations**: none for C1-C6. Activation hooks read local prompt text and file paths; the review recipe drives tools already in the user's environment; conventions and docs make no calls. U1 makes exactly one authenticated call, to `chatgpt.com/backend-api/wham/usage`, which is the user's OWN ChatGPT account endpoint (the identical call the Codex app already makes on the user's behalf). No third-party intermediary, and it mirrors the existing Claude monitor's single call to the Anthropic usage endpoint.
- **Credentials / API keys required**: none newly introduced for C1-C6. U1 reads the user's existing Codex CLI OAuth token from local disk (never transmitted anywhere except back to the user's own OpenAI account) exactly as the Claude monitor reads `~/.claude/.credentials.json`. No new credential is created.
- **Source code / prompts / query text leaving the machine**: none. U1 sends only the auth token to the user's own account endpoint and receives usage figures back; no code, prompt, or query text is transmitted.
- **New commercial relationship with a third party**: none. U1 uses the user's pre-existing ChatGPT / OpenAI relationship.

The two places the source proposes an outbound or vendor-locked dependency are (a) the external `openspec` CLI and (b) the Codex-CLI hardcoding inside `codex-review-loop`. Both are handled below: C5 adopts the convention not the CLI, and C2 is generalized to any model. U1's single outbound call is to the user's own account endpoint and is therefore policy-compliant tier-3 reverse-engineering, not a new third-party data processor.

### 5.3 Reverse-engineering viability

- `skill-native` (agent's own model or a convention, no new artifact beyond docs/skills): C4, C6, C5 (convention layer), C3, P1.
- `re-full` (ship local deterministic artifacts, no outbound): C1 (activation + guard + tracker hooks and the rules schema).
- `re-partial` (ship a local recipe and optional script; model-agnostic, gap documented): C2 (background-review recipe plus an optional wrapper script that calls whatever review CLI the user has); U1 (reverse-engineer the `wham/usage` fetcher and the Codex credential read into a local extension provider; the UI is fully local and reused; the residual gap is the undocumented endpoint's durability, documented as a fail-soft caveat).
- `vendor-intrinsic`: none.
- `drop-outright`: the external `openspec` CLI dependency; the Codex-CLI hardcoding in the review loop; vendor-doc bundling (C8 `openai-docs`); the proxy / load-balancer product itself.

### 5.4 Recommendation ordering

This ordering IS the adoption plan. P-tier from Step 4 operates within each bucket, not across.

1. **skill-native first**: C4, C6, C5 (convention), C3, P1.
2. **re-full / re-partial builds next**: U1 (Codex Usage Monitor; P0, sequenced first among builds because it is directly requested and self-contained), C1 (hooks + rules schema), C2 (model-agnostic recipe).
3. **vendor-intrinsic**: none.
4. **drop-outright** (moved to NOT-recommended): the external `openspec` CLI, the Codex-locked review loop, vendor-doc bundling, and codex-lb's proxy / database / dashboard (U1 extracts only the `wham/usage` endpoint knowledge, none of the proxy machinery).

Note on P0 vs the RE ordering: U1 is P0 (highest value, directly requested) but is a `re-partial` build, so it does not precede the zero-code skill-native wins in pure methodology terms. Because it is self-contained and the top user priority, the sequenced plan below front-loads it as the first concrete build while the skill-native conventions proceed in parallel.

## Step 7: Risks, Conflicts, and NOT-Recommended

### Conflicts to manage

- **C1 guard posture** conflicts with Nexus-Hub's fail-open, advisory hook philosophy. The guard must default to suggest-only, must never block by default, must offer an env-var escape hatch, and must be disabled by `NEXUS_HOOK_PROFILE=minimal`. Model the opt-in on the `NEXUS_HUB_COPILOT_SKILLS` precedent.
- **C1 installer surface** touches both installers and `settings.json`. New scripts under `scripts/` need an explicit copy step in `installer.sh` and `installer.ps1`, and each `.sh` hook needs a `.ps1` sibling for Windows parity.
- **C5 spec convention** must not fork the existing per-version `docs/` plan/spec model. It layers the normative/context split and the merge-gate rule onto `spec-driven-development` rather than introducing a parallel `openspec/`-style tree.
- **C2** must stay vendor-neutral. Hardcoding any single review CLI would violate the reverse-engineer-first posture and the MCP Registry Policy hard-no on generation-as-service.

### NOT recommended for adoption

- **The external `openspec` CLI as a dependency** (C5 as literally built): rejected on reverse-engineer-first grounds. Adopt the convention (normative spec vs context, spec-as-merge-gate), not the tool. Cited policy: `AGENTS.md` MCP Registry Policy decision tree, tier 3 (reverse-engineer into a local equivalent) and the preference for skill-native conventions.
- **The Codex-CLI-locked review loop** (C2 as literally built): rejected as vendor lock-in. The capability is adopted, but model-agnostic on tools the user already has.
- **Vendor-doc bundling** (C8 `openai-docs`) and **per-rule granular skill files** (C8 Vercel bundles): not adopted. Nexus-Hub is vendor-neutral and consolidates knowledge into `catalog/rules/` plus focused skills; `local-docs-lookup` already provides the mechanism without shipping a specific vendor's documentation.
- **The proxy / load-balancer product** (account pooling, dashboard, usage tracking, OpenCode endpoints): not applicable. Different product category. codex-lb's routing invariants survive only as optional reference content for `multi-provider-ai` (candidate P1), never as a product to build.
- **C1's fail-closed blocking default**: the mechanism is adopted; the blocking-by-default behavior is not.
