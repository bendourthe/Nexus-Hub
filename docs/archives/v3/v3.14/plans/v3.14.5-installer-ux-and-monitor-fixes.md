# Plan - Installer UX Modernization, Codex Monitor Fixes, and Mandatory Contract Verification

**Project**: Nexus-Hub
**Version**: v3.14.5
**Slug**: installer-ux-and-monitor-fixes
**Plan Type**: Feature / Bug-fix campaign
**Created**: 2026-07-19
**Goal**: The installer prints a clean, per-platform checklist that reflects what actually installed; the Codex Usage Monitor shows usage (or an honest, actionable fallback) with correct status-bar ordering, a compact-mode toggle, and a theme-adaptive dashboard icon; and every release mechanically re-verifies each platform's read-contract before it can ship.

## Overview

This release modernizes the Nexus-Hub installer's user-facing output and fixes the Codex Usage Monitor, without touching platform feature-parity (that is the sibling v3.15.0 plan). Three workstreams land here. First, the installer console log is rebuilt to the mockup's per-platform checklist (a consistent surface order - Core Files, Skills, Commands, Agents, Rules, Hooks, Core Settings - each row checked against what actually installed), which requires teaching `runner.py` to surface structured per-surface results even under `--quiet` (it currently suppresses them). That same refactor fixes a real defect: undetected platforms (Kimi/Qwen/OpenClaw) currently print "Installed (global scope)" even when the subclass silently skipped them. Undetected platforms are then grouped under one section, the three uncolored vendors get colors, the stacked end-of-run blank lines are collapsed, and the single "Usage Monitors" block is split into vendor-grouped Anthropic and OpenAI utility sections.

Second, all four Codex Usage Monitor bugs are fixed in `extensions/codex-usage-monitor/` (and, for the cross-extension status-bar and compact-mode changes, in `extensions/claude-usage-monitor/`): the `wham/usage` auto-fetch response mapping is reverse-engineered against the real endpoint the official Codex CLI polls, backed by a guaranteed-working manual-entry fallback and an honest, actionable empty state; the status-bar items are re-prioritized so the order is Claude usage, Claude gear, Codex usage, Codex gear; both extensions gain a `compactStatusBar` toggle; and the Codex dashboard tab icon is made theme-adaptive with a light/dark SVG pair, matching the Claude extension.

Third, the mandatory per-release platform-contract verification the user asked for is made real: the four hand-maintained copies of "expected paths per platform" are consolidated into one machine-readable `platform-read-contracts.json`, and a new `check_platform_contract_freshness.py` guard fails `make validate` and CI unless the contract doc was re-verified for the release being cut. Success looks like: a clean side-by-side installer run whose checklist matches reality, a working (or honestly-degraded) Codex monitor demoed live in VS Code, and a release that cannot be tagged with a stale platform contract. Version surfaces bumped at `/update release` (`.claude-plugin/plugin.json` canonical, `data/marketplace.json`, both installers, `CHANGELOG.md`); the two extension `package.json` versions bump in-phase.

## Phase 1: Runner structured per-surface results

**Goal**: `runner.py` returns and can emit a structured, per-platform, per-surface result (which surfaces installed, their absolute paths, and whether the platform was detected or skipped) even when invoked with `--quiet`, so the installer can render an accurate checklist instead of an unconditional success line.
**Prerequisites**: None.
**Stability Gate**: A `runner.py install --quiet --json-summary` (or equivalent structured channel) returns, for each platform, a per-surface action list and a detected/skipped flag; existing human-readable output is unchanged when the new channel is not requested; `tests/integrations/` covers the new summary for a detected and an undetected platform; full pytest suite green.
**Recommended model**: Strong reasoning tier (Opus-class), high effort. Rationale: `runner.py` is the single code path every non-Claude platform installs through; a subtle change to `WriteResult` handling or the `--quiet` early-return can silently break all 13 registry platforms, so this foundational phase carries the release's highest blast radius.

### Sub-tasks

#### 1.1 - Design the structured summary contract

**Objective**: Define the machine-readable shape the installer will consume, reusing the existing `WriteResult` / `FileAction` model rather than inventing a parallel one.

**Prompt**:
> In the Nexus-Hub repo, design a structured per-platform install summary emitted by `scripts/lib/integrations/runner.py`. Read `scripts/lib/integrations/result.py` (`FileAction`, `WriteResult`, the six-value `VALID_ACTIONS`), `runner.py` `cmd_install` / `_render_write_result` (note it early-returns under `--quiet`), and `base.py` `install_global`/`install_workspace`. Define a summary object keyed by platform that records, per canonical surface (instruction-file, skills, commands, agents, rules, hooks, settings), the resolved target path and a status derived from the surface's `FileAction`s: `installed` (any created/updated/unchanged), `skipped-not-detected` (the subclass logged a detection skip note), `not-supported` (the platform declares no such surface), or `absent`. Do NOT change what gets written to disk - only what is reported. Produce a short design note in the working context (surface enum, status enum, how detection-skip is inferred from `WriteResult.notes` / the manifest log) and confirm it covers detected, undetected (Kimi/Qwen/OpenClaw), and not-supported cases. Acceptance: the design maps cleanly onto the existing `WriteResult` without a parallel data model, and identifies exactly which `runner.py` functions change.

## Phase 6: Mandatory platform-contract verification gate

**Goal**: Consolidate the four duplicated "expected paths per platform" sources into one machine-readable `platform-read-contracts.json`, and add a freshness guard that fails `make validate` and CI unless the contract doc was re-verified for the release being cut.
**Prerequisites**: None strictly, but best sequenced after Phase 1 (the runtime `[verify]` checks and the summary both benefit from a shared path table).
**Stability Gate**: A single `platform-read-contracts.json` is the source consumed by the contract doc, `verify_platform_contracts.py` `EXPECTATIONS`, and the runtime `_verify_checks` (no remaining hand-maintained duplicate); `scripts/check_platform_contract_freshness.py` exists, is wired into `make validate` and CI, and FAILS when the contract's verification marker is older than the release being cut; `make validate` is green with a fresh marker and red with a stale one (proven by a fixture); the `platform-contract-verification` skill stamps the marker.
**Recommended model**: Strong reasoning tier (Opus-class), high effort. Rationale: this consolidates four independently-maintained copies into one without changing behavior, and adds release-gating logic whose failure mode (blocking every release, or silently never blocking) is high-consequence, so it needs careful design and adversarial testing.
