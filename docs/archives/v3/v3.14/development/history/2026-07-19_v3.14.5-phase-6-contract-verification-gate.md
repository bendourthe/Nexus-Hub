## Overview

Phase 6 makes per-release platform-contract re-verification a hard gate. Two problems were solved together. First, the "expected read-paths per platform per surface" data was duplicated in three places (`verify_platform_contracts.py`'s `EXPECTATIONS`, the runner's `_verify_checks`, and the prose contract doc), so they could drift apart silently. Second, nothing forced the contract to be re-verified before a release, so a stale contract could ship (the exact failure mode that silently emptied Codex and Antigravity installs in prior versions). The fix is one machine-readable source plus a freshness guard that fails the build when the contract was not re-verified for the version being cut.

## Sub-tasks completed

- **6.1 Single-source JSON.** Authored `docs/policy/platform-read-contracts.json` as the machine-readable source of truth, derived from the prose table. Three sections: `contract_checks` (per-platform config + `doc_mentions` the code-vs-contract checker asserts), `install_verify` (per-platform post-install surface paths the runtime verify pass asserts, with `~/` = home and `{project}/` = target root path tokens), and `meta` (`last_verified` + `verified_for_version`). The prose `.md` stays the human-readable companion and now names the JSON as authoritative.
- **6.2 Both checkers consume the JSON (DRY, behavior-preserving).** `verify_platform_contracts.py`'s `EXPECTATIONS` now loads from `contract_checks` via `_load_expectations()` (with a `main()` guard that fails if the JSON is missing/empty rather than passing vacuously). The runner's `_verify_checks` now builds its per-platform read-path assertions from `install_verify` via `_resolve_contract_path` / `_evaluate_surface`, instead of literal `Path` expressions. No behavior change: same platforms, same PASS/NEEDS-ACTION semantics - verified by re-running the existing verify tests and by confirming `verify_platform_contracts.py` still reports the same 7 platforms OK.
- **6.3 Freshness guard + wiring.** Created `scripts/check_platform_contract_freshness.py`: compares `meta.verified_for_version` to the canonical project version (`.claude-plugin/plugin.json`, or a `--version` override) and exits 1 with an actionable remediation message when they differ. Version-match (not a date window) so the gate is GREEN during development (both are the last-released version) and only RED once `/update release` bumps the version - so a release cannot pass validation on a stale contract. Wired into the `Makefile` `validate` target (after `verify_platform_contracts.py`) and the CI `validate` job (after the base-parity guard). Registered in `test_installer_smoke.py`'s `DEV_ONLY_SCRIPTS` since it is a repo-internal guard like `check_version_sync.py` / `verify_platform_contracts.py`, not installer-copied.
- **6.4 Close the loop in the skill + release command.** Updated `platform-contract-verification/SKILL.md` to treat the JSON as authoritative (Step 1 reads it; Step 4 edits the JSON row first then mirrors the `.md`), added Step 6 "Re-stamp the freshness marker" (set `last_verified` to today and `verified_for_version` to the release version, then run the freshness guard), and added the marker + guard bullets to Verification. Updated the Common Rationalizations "I'll skip it this release" row to point at the now-hard gate. Updated `/update release` governance step 4 (`catalog/commands/update.md`) to state the re-stamp is mandatory and the guard hard-blocks a stale release. Updated the prose doc's maintenance section to describe the JSON as the source and the freshness guard as the third automated guard.
- **6.5 Tests.** Added `tests/validators/test_check_platform_contract_freshness.py` (passes when the stamp matches the release; passes on the real repo by default since plugin version == stamp; fails with the STALE + "governance step 4" message when the release version advances; fails closed on an unresolvable version). Added a DRY-single-source assertion to `tests/validators/test_verify_platform_contracts.py` (EXPECTATIONS keys == `contract_checks` keys, each entry carries the required fields).

## Design decision: honest `last_verified`

The `meta.last_verified` was set to 2026-07-13, not today. Phase 6 builds the freshness *infrastructure*; it does not re-run the platform web-search verification (that is `/update release` governance step 4's job). `last_verified` records when the platform formats were last verified against reality (2026-07-13, per the prose doc), not when the JSON file was authored. Stamping today's date would have the marker falsely assert a verification that did not happen - defeating the very gate being built. `verified_for_version` stays 3.14.4 (the released version), which keeps the guard green during v3.14.5 development and correctly turns it red the moment `/update release` bumps the version.

## Known gaps

- The staleness signal is version-match only, not a date window - deliberate (see the guard's module docstring). A date window would fire during quiet development periods with no release in flight, creating friction with no safety benefit; the version bump is the precise moment re-verification must have happened.
