## Overview

`/presentify` had reached a state where the iterative visual-QA loop reliably repaired a page, but the FIRST rendered page still shipped a recurring family of defects that the loop then had to find. That distinction matters because each repair iteration costs a full render pass and because a defect that survives to delivery is one the reader sees. A real session produced five such defects, each invisible to the checks already in place: a CSS class collision that blanked the hero with zero console errors, a chart series flat-clamped at the axis maximum (fabricated data that looks like a value), a scrub ramp that loaded content dimmed before the reader had scrolled, a change-local re-render that verified the edited section while another section was silently broken, and a source placeholder (`xx subjects`) that an agent would rather estimate than surface.

The common shape is that all five pass every static check. The scorer reads bytes and structure, the console-error listener sees no errors, and the edited section renders clean. So the response is not another static rule: it is a set of BINARY authoring rules where a judgment call was previously implied, plus two new render-time probes that make the invisible classes deterministically visible.

This release is also where authoring stops fighting the scorer. `scripts/visual_qa_score.py` reads specific markup contracts, and a first authoring pass that does not know them earns a repair iteration for reasons unrelated to how the page looks. Phase 1 documents those contracts where the author reads them.

### Intake protocol

Each incoming lesson becomes a numbered sub-task below and follows the same shape Phase 1 used, because that shape is what made Phase 1's guards enforceable rather than advisory:

1. **Name the defect as observed** - what the page did, in one sentence, from the real session.
2. **Name why the existing checks missed it** - static scorer, console errors, change-local render, or agent judgment. A lesson whose defect the existing checks WOULD have caught is a bug report, not a new guard.
3. **Choose the guard's kind**: a BINARY authoring rule in `SKILL.md` (when the correct behavior admits no judgment), a render-time probe plus a rubric criterion (when it is only visible in pixels), an extraction change (when the source content is at fault), or a reference-file pattern (when it is a technique, not a rule).
4. **Add the paired Common Rationalizations row** - the excuse an agent would use to skip it, with the concrete failure it caused. Every Phase 1 guard has one; a guard without one is a suggestion.
5. **Add the prose/behavior test** in `tests/skills/test_presentify_first_shot_hardening.py`, and advance the criteria-count contract tests if a rubric criterion was added.

#### 3.1 - The content-intent brief and Gate A

**Objective**: Record what the artifact must accomplish BEFORE authoring, so an audience mismatch is caught at outline time rather than after delivery. Covers `PRES-01` through `PRES-04`, `PRES-06`, and the `PRES-14` Gate A half.

**Prompt**:
> **Defect as observed**: the first page carried a section titled "What the original got right and wrong", addressed to readers who had never seen the original. It also estimated a reusable multi-product platform when the request was a bounded agent-led pilot, and it opened the regulatory section by arguing that uploading documents is insufficient, rebutting a position the user had never taken (their premise already included agent-led extraction and verification).
>
> **Why the existing checks missed it**: every existing gate runs AFTER authoring and grades the page as built. Nothing in the pipeline records what the page is FOR, so there is no artifact against which "this section addresses the wrong audience" is a detectable contradiction. The four Round 1 choices and the two Round 2 choices are all about FORM (style, aspect, interactivity, imagery, palette, depth); not one is about PURPOSE.
>
> **Guard kind**: a new intake stage plus a new Tier-3 reference. Create `references/content-intent.md` holding the full doctrine, and add a THIRD intake round to `SKILL.md` Step 5 (batched with Round 2, not a separate prompt round, since both run after extraction and the source document's own recommendation is one batched clarification, not several).
>
> Four fields, each INFERRED from the request and source first and asked only when inference is unsafe:
>
> 1. **`source_relationship`** (BINARY, default `standalone`): one of `standalone` (the source informs the output and is never mentioned), `revision-aware` (the output may explain changes from a known prior version), `comparative` (the output intentionally compares sources or versions), or `faithful-adaptation` (the output preserves the source's order and framing). Default to `standalone` unless the user explicitly asked for critique, redlining, version comparison, or change commentary. Under `standalone` the visible output must not contain "the original", "the prior draft", "what was right", "what was wrong", or "original preserved" unless the SUBJECT MATTER independently requires the words.
> 2. **`decision_to_enable`**: the one choice the reader must be able to make after reading. When the request names options to choose among, decision coverage normally spans: what the subject does, the problem it solves, feasibility of the alternative, effort under named assumptions, alternatives, comparative cost, regulatory or operational constraints, a conditional recommendation, and a low-risk proof step.
> 3. **`assumptions`** (the assumption ledger): each stated user assumption classified `accepted` / `needs-verification` / `bounded` / `material-risk`. An `accepted` premise is part of the task contract: no section heading or lead sentence may negate one. Challenging an assumption is permitted only with stated evidence and an explanation of why it changes the decision.
> 4. **`scope_class`** (BINARY where an estimate is produced): one of `working-demonstration`, `decision-grade-pilot`, `controlled-rollout`, or `reusable-platform`. Every visible timeline names its scope class and shows at least three planning assumptions. A bounded pilot must never inherit a reusable-platform estimate.
>
> Record all four (plus `exclusions`) in the design-record HTML comment as a `content_intent` block, using the YAML-ish shape the source document proposes so the record is inspectable and machine-checkable later. Then add **Gate A** to the rubric's gate set: run before visual authoring, checking that the relationship is explicit, the audience and decision are named, assumptions are recorded and preserved, the scope class matches the estimates, required coverage is complete, and no excluded framing appears in the outline. Failure behavior is to revise the OUTLINE, not the HTML.
>
> Add the paired rationalization rows, one per field: "the source is a draft, so I should say what it got wrong" / "the audience never saw the draft; a standalone brief that critiques an invisible document reads as talking to someone else"; "agents make this fast, so the timeline is short regardless of scope" / "agent speed changes execution rate, not the target boundary; a pilot estimate and a platform estimate differ by an order of magnitude and the reader is choosing between them"; and "the user's premise is a bit optimistic, I should flag it" / "an accepted premise is part of the contract; open by building on it, and challenge it only with evidence plus the decision consequence".
>
> Acceptance criteria: `references/content-intent.md` exists and is referenced from `SKILL.md`; Step 5 resolves and records the four fields; the design record carries a `content_intent` block; Gate A is defined in `references/visual-qa-rubric.md`; three rationalization rows added; prose tests assert each field name, the `standalone` default, and the banned-phrase list.

#### 3.2 - Decision-brief authoring rules

**Objective**: Make the page's own structure serve the recorded decision. Covers `PRES-05`, `PRES-09`, `PRES-10`, `PRES-11`, `PRES-12`, and `PRES-13`.

**Prompt**:
> **Defect as observed**, five in one family. The page compared VectorCAST to alternatives without first explaining what VectorCAST does, so a non-technical reader could not evaluate a replacement for something they could not describe. The cost visual was an iceberg, a visible-versus-hidden metaphor, when the actual decision required comparing three options across repeated criteria. The hybrid recommendation said "use a hybrid" without showing which work belongs to agents, which to deterministic tools, and which to human approval. The hero carried production metadata ("Primary-source review", "Original preserved") that is process bookkeeping rather than audience value. The stock-image credit box sat permanently visible, competing with the title. And the competitor table led with engineering features and certification terminology rather than what each option provides and when it fits.
>
> **Why the existing checks missed it**: all six are content-composition judgments. The rubric grades whether a visual is well-formed, sized, relevant, and contrast-safe. It has no criterion for whether the RIGHT visual form was chosen, whether a comparison is preceded by an explanation, or whether an element earns its place in the hero.
>
> **Guard kind**: authoring rules in `references/content-intent.md`, with BINARY one-liners in `SKILL.md` Step 6 where the rule admits no judgment.
>
> 1. **Subject-capability summary before comparison** (BINARY): when the output compares a named product or approach with an alternative, a brief `subject_capability_summary` precedes the comparison, answering what work it performs, what evidence it produces, why its audience values it, and which parts are deterministic tools versus workflow or documentation support. Test: a first-time reader can summarize the subject's role after one section, without the competitor table or the sources appendix.
> 2. **Highlights answer, they do not preview** (in `decision_brief` mode): the first content segment gives conclusions in question-and-answer form, not a table of contents. Each Highlight maps to a later supporting section, and each later section either supports a Highlight or supplies necessary decision context.
> 3. **Cost and comparison visual selection**: choose by the decision, not by familiarity. A MATRIX for several options across repeated criteria; a STACKED BAR only with defensible quantities; a FLOW when costs arise across lifecycle stages; an ICEBERG only when visible-versus-hidden is itself the decision and the hidden categories can be organized. Without exact pricing, label the comparison qualitative and avoid pseudo-precision. This composes with the existing data-fidelity rule: an invented magnitude in a cost chart is the same class of fabrication as a flat-clamped bar.
> 4. **Responsibility lanes for a hybrid recommendation** (BINARY): when a recommendation combines systems or teams, ship a lane visual naming work performed by agents, measurements produced by deterministic tools, decisions retained by qualified people, artifacts passed between lanes, and the conditions that trigger a purchase. Every activity has ONE primary owner, and every system-generated conclusion with regulatory significance shows its review point.
> 5. **Hero-content budget** (BINARY): at most one context label, one title, one framing question or subtitle, and one concise answer where appropriate. No production notes, preservation labels, internal QA labels, or workflow history. Every hero element answers one of: What is this? Why should I care? What is the main conclusion? Provenance belongs in the method, the sources appendix, or the design record.
> 6. **Credits are unobtrusive AND accessible** (BINARY, extends the existing credits rule rather than replacing it): the visual credit is hidden until hover or keyboard focus on large screens, exposed through a FOCUSABLE control, reachable by a touch route, and repeated in full in the sources or credits section. Hover is never the only route. This is the one item here with an accessibility floor rather than a taste judgment, so it is binary in both directions: unobtrusive is not permission to make attribution unreachable.
> 7. **Competitor criteria are reader-centered**: default to what it provides, best fit, relative cost or pricing model, internal work required, regulatory or qualification support, and the important limitation. Engineering feature detail moves to an expandable note or the appendix unless it changes the recommendation.
>
> Acceptance criteria: all seven documented in `references/content-intent.md`; the four BINARY ones stated in `SKILL.md` Step 6; rationalization rows added for the iceberg reach ("everyone understands an iceberg"), the hero metadata ("showing our method builds trust"), and the permanent credit ("attribution has to be visible to count"); prose tests assert the visual-selection rule set, the hero budget list, and the credit disclosure triple (hover, focus, touch).

#### 3.3 - Visual contracts and the semantic-visual gate (Gate B)

**Objective**: Require every major visual to have a stated explanatory job before it is implemented. Covers `PRES-07`, `PRES-08`, and the `PRES-14` Gate B half.

**Prompt**:
> **Defect as observed**: the first VectorCAST visual was an orbit diagram that was present, animated, and attractive, and explained nothing about how the tool turns code into review-ready evidence. Its scroll behavior did not progress with the narrative. The replacement was a five-stage pipeline (prepare, execute, measure, connect, package) where each prose stage activated its matching visual state, and it worked because the visual TRANSITION matched the semantic transition in the text.
>
> **Why the existing checks missed it**: criteria 1 through 11 grade a visual's execution. A decorative visual that renders correctly, sizes correctly, contrasts correctly, and paints correctly passes all of them. There is no criterion for "does this visual make a relationship easier to understand than prose alone", and the scroll-scrub protocol governs asset cost and accessibility rather than semantic synchronization.
>
> **Guard kind**: a pre-implementation contract plus a new rubric gate.
>
> Require a `visual_contract` for every MAJOR visual before implementation, recorded in the design record: **Question** (what reader question does it answer), **Message** (the single conclusion to retain), **Encoding** (what position, color, size, sequence, and connection mean), **States** (what changes during interaction), **Trigger** (what user action causes each state), **Fallback** (what a static or reduced-motion reader sees), and **Evidence** (which claims or data support it). The decisive test is subtractive and belongs in the skill as written: if removing the visual costs the section no explanatory value, redesign it or omit it. Omission must be an explicitly permitted outcome, since a concise table often beats an elaborate interactive graphic, and a gate that can only demand MORE visual work is a cost generator.
>
> For each scrollytelling section additionally require a STATE TABLE (step, prose claim, visual change, reader takeaway), and extend Step 9's capture set so browser QA scrolls to every declared step and verifies the expected state is active, under reduced motion and keyboard navigation too. This composes directly with criterion 11's painted-surface probe: 11 asks whether the surface painted, the state table asks whether it painted the RIGHT state.
>
> Add **Gate B** to the rubric: run after the visual plan and before detailed styling, checking that every major visual has a question and one takeaway, every encoding has a meaning, every interactive state maps to a prose state, qualitative visuals imply no unsupported precision, the static fallback retains the explanation, and the visual is materially better than concise prose or a simple table. Failure behavior is redesign or removal, at plan time, before styling cost is sunk.
>
> Acceptance criteria: the `visual_contract` field set and the state-table format are in `references/content-intent.md` (cross-linked from `references/scroll-scrub.md` and `references/interactive-features.md`); Gate B is in `references/visual-qa-rubric.md`; Step 9 verifies declared scrollytelling states; a rationalization row is added for "the visual looks impressive, that is its job"; prose tests assert the seven contract fields, the subtractive test, and the omission-permitted clause.

#### 3.4 - Typography and density as one system

**Objective**: Fix the composition defects that produced dead space, and fix them together rather than one variable at a time. Covers `PRES-19`, `PRES-20`, `PRES-21`, and `PRES-26`.

**Prompt**:
> **Defect as observed**, measured rather than eyeballed. A hero title used 58% to 70% of its desktop column because a `10.5ch` maximum forced three lines. Highlights answers used about 54% to 60% of their column because a `32ch` cap intended for reading length was applied to DISPLAY text. Several desktop headings took three lines beside an unused track. Every standard section carried `min-height: 82svh`, so short sections kept slide-like empty space below their content. Scrollytelling steps used `58svh` each for simple state changes. And after a deliberate two-line desktop title was introduced, the mobile layout stranded "vs" on its own line until mobile wrapping was defined separately. The coordinated correction cut the 12-section body by 22.6% at 1920x1080 (18,015px to 13,936px), 25.3% at 2560x1300, 21.8% at 1366x768, and 7.6% at 390x844, with no content removed.
>
> **Why the existing checks missed it**: `responsive-typography.md` rule 2 catches prose STRANDED beside dead space, which is the inverse defect. Here the text was not stranded, it was ARTIFICIALLY NARROW inside its own track, and the page was not too dense but too sparse. The font floors are minimums, so nothing in the contract objects to text that is large, correctly measured, and using half its column. Rule 1's fluid-spacing check reads declarations, and `min-height: 82svh` is a viewport-relative value, so it passes as fluid while being exactly the wrong rule.
>
> **Guard kind**: three new rules in `references/responsive-typography.md` (extending it to rules 8, 9, and 10), with the BINARY halves surfaced in `SKILL.md` Step 6.
>
> 1. **Wrap plans for display text** (`PRES-19`): every hero title and major section heading records a wrap plan (target line count at large desktop, standard desktop, and laptop; mobile fallback; phrases that must not become isolated lines). `text-wrap: balance` is a progressive enhancement, NOT the plan, since it cannot express intentional phrasing. Observable criterion: no display heading has an avoidable one-word orphan; a desktop hero normally uses one or two lines; the mobile form is reviewed rather than inferred from the desktop markup.
> 2. **Measure is per text ROLE** (`PRES-20`, sharpening rule 2 rather than duplicating it): classify before assigning width. Long-form single-column prose keeps the 45 to 85 character cap. Display answers and callouts use the available track and control readability through size and hierarchy. Headings optimize phrase grouping and line count. Multi-column text uses fractional tracks with no inner `ch` cap (already rule 2, restated as a role). Table and diagram labels size to the component. Observable criterion: on wide screens a display-text block uses at least 70% of its available track unless the remaining area has a stated visual purpose. Long-form prose is the ONLY default recipient of the character measure.
> 3. **Section height is earned** (`PRES-21`, BINARY): classify each section as `content-height` (the default), `viewport-stage` (a deliberate opening or transition), `scrollytelling-track` (height calculated from the number of meaningful states), or `pinned-comparison` (enough height to complete the state sequence and no more). A standard section carries NO viewport-height minimum. A tall section must name the interaction or content volume requiring the height, and removing its height rule should demonstrably break the intended experience.
> 4. **The coordinated density pass** (`PRES-26`): when density is wrong, revise root type scale, display scale and target line count, text-role measure, grid-track proportions, section and component gaps, line height, explicit or minimum heights, and the relationship to adjacent graphics TOGETHER, reporting which variables changed. Local fixes move empty space rather than removing it. The pass must never resolve density by shrinking body text below its floor, so it composes with rule 4 rather than competing with it: report that body prose stays at or above 16px, secondary at or above 13px, and interactive at or above 12px, at both the clamp floor and 1920px.
>
> Acceptance criteria: rules 8, 9, and 10 exist in `references/responsive-typography.md` with the observable criteria above; the two BINARY rules (section height, per-role measure) are stated in `SKILL.md` Step 6; rationalization rows added for "a narrower measure is always more readable" and "a full-viewport section looks intentional"; prose tests assert the four section classes, the 70% utilization criterion, and the density-pass variable list.

#### 3.5 - Layout QA probes and per-section evidence

**Objective**: Make the 3.4 defects measurable, and make compaction provably safe. Covers `PRES-22`, `PRES-23`, `PRES-24`, `PRES-25`, and the remainder of `PRES-16`.

**Prompt**:
> **Defect as observed**: screenshots showed that the layout felt wrong; only the computed metrics explained why (58% hero utilization, 54% on Highlights answers, three-line headings). A full-page image rendered the VectorCAST section too small to judge, while per-section captures made the wrapping, heading balance, table density, and sticky spacing legible. And widening text while reducing gaps created a NEW risk the old probes could not see, namely copy overlapping an adjacent photo or sticky diagram.
>
> **Why the existing checks missed it**: Step 9's probe set is real but measures different quantities. It records the smallest rendered size per role, the widest band fraction, `scrollWidth`, and key bounding boxes. It computes no line counts, no width utilization, no orphan detection, and no rectangle INTERSECTION, and it never compares a section's height across iterations. Bounding boxes are recorded and then not tested against each other.
>
> **Guard kind**: extensions to the Step 9 probe set and the evidence trail, all inside the existing `page.evaluate()` per capture, so the cost stays one evaluate call rather than a new pass.
>
> 1. **Line-count and width-utilization probes** (`PRES-22`), at every required viewport: rendered line count for hero titles, section headings, display answers, and ledes; element width divided by available parent-track width; one-word final-line detection for display headings; computed font size and line height. The QA report lists every desktop display heading above two lines, every heading or display answer under 70% of an otherwise empty track, and every avoidable one-word orphan.
> 2. **Per-section density deltas** (`PRES-23`): record total rendered height, content bounding-box height, non-content fraction, change from the prior iteration, and a content count or checksum confirming nothing was lost. State the trap explicitly in the reference, because it is the one an optimizing agent will fall into: a smaller section is NOT automatically better, and a large reduction is checked for crowding, clipping, and collision before it is accepted.
> 3. **Text-graphic collision probes** (`PRES-24`): for every mixed-media or multi-column section, record the text-region and graphic-region rectangles at all required viewports and assert intersection is FALSE for regions that must stay separate. An intentional overlay is exempt from this and instead passes the existing scrim, contrast, and safe-area rules. This is the safety interlock on 3.4: widening text is only safe when the graphic boundary is measured in the same pass.
> 4. **Per-section screenshots** (`PRES-25`): capture each top-level section at desktop and mobile plus the meaningful interaction states; assemble contact sheets for whole-document review while keeping the native captures for detail. Every section appears in the evidence set, and each scrollytelling section carries at least one MID-state capture rather than only its initial state. This extends the smoke-set rather than replacing it: the smoke-set is the fixed three-shot regression guard on every iteration, the per-section set is the refinement evidence.
> 5. **Sticky-layer inventory** (`PRES-16` remainder): record the sticky layers per scroll context in the design record, and capture a mid-scroll screenshot for every scroll context containing sticky content. Observable criterion: no content is obscured by another sticky layer at the top, middle, or bottom of its scroll range.
>
> Acceptance criteria: the five probe classes are in `SKILL.md` Step 9's probe bullet and in `references/visual-qa-rubric.md`; the evidence trail records per-section deltas and the content checksum; a rationalization row is added for "the screenshots look fine, I do not need the numbers"; prose tests assert each probe class by name.

#### 3.6 - QA layering, decision readiness, and helper discovery

**Objective**: Name the four QA layers explicitly, add the final reader-level gate, and stop QA helpers from being found by guessing. Covers `PRES-14`, `PRES-17`, `PRES-18`, and records the drops.

**Prompt**:
> **Defect as observed**, two of them. The first artifact passed structural and behavioral QA while carrying an audience mismatch, an oversized estimate, a redundant argument, and weak explanatory visuals, so a full technical pass certified an artifact that did not serve its reader. Separately, the visual-QA script was expected inside the `presentify` package and actually lives under the delegated `document-to-interactive-html` skill, so a clean session had to guess a filesystem path to run a required helper.
>
> **Why the existing checks missed it**: the loop has no vocabulary for its own layers, so "QA passed" means whichever layers happened to run. And `catalog/commands/presentify.md` documents delegation in prose without publishing where the delegate's runtime helpers are, which is a discoverability gap in the command, not a defect in the skill.
>
> **Guard kind**: a rubric restructure, one new gate, and a command-side manifest.
>
> 1. **Name the four layers** (`PRES-14`): Content QA (audience, purpose, assumptions, completeness, readability, claim support), Semantic-visual QA (message, encoding, state changes, fit with the prose), Structural QA (valid HTML, floors, contrast, image sizing, offline integrity, responsive layout), and Behavioral QA (navigation, scroll states, hover, focus, reduced motion, lightboxes, console errors, runtime requests). Layers 3 and 4 exist today and are simply LABELLED, not rebuilt; layers 1 and 2 are Gates A and B from 3.1 and 3.3. BINARY: a document cannot receive a final pass when only the structural and behavioral layers have run.
> 2. **Gate E, decision readiness** (`PRES-18`): run last, using only the visible artifact. A reader can explain what the subject does, identify the viable options, understand the estimate and its assumptions, explain the recommendation and when it would change, and identify the proof step, without undefined technical terms blocking comprehension. Failure behavior is to revise CONTENT even when all technical QA passed. Keep it OPTIONAL and reader-level as the source document proposes; it is the human confidence check, and making it blocking would put a subjective judgment on the release path.
> 3. **Helper manifest** (`PRES-17`): publish the delegated runtime-helper paths in `catalog/commands/presentify.md` so a clean session locates and runs every required QA helper without guessing. Prefer the manifest over wrapper scripts: a wrapper is a second artifact to keep in sync, and the `AGENTS.md` scope-fit gate declines added structure when a documented path solves the problem.
>
> **Recorded drops, with reasons.** The source document's `PRES-08` state-table proposal is built in 3.3, but its metrics section (first-review acceptance rate, intent defect rate, visual replacement rate, estimate correction rate) is DROPPED: those need a measurement pipeline across many sessions that this repository does not have, and shipping the definitions without the pipeline is documentation of an intention. The ten open questions in the source are answered implicitly by the choices above (standalone as the global default, content-intent fields as inferred internal metadata rather than CLI options, `decision_brief` mode triggered by comparison or recommendation language) and are not carried as separate work.
>
> Acceptance criteria: the four layers are named in `references/visual-qa-rubric.md` with the binary final-pass rule; Gate E is defined as optional and reader-level; `catalog/commands/presentify.md` lists the delegated helper paths; the drops are recorded in the v3.16.7 known-gaps section rather than only in this plan; prose tests assert the four layer names and the binary final-pass rule.
