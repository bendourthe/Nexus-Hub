## Implementation

`review-trapdoors/SKILL.md` Step 5 no longer promotes by list size. The "past about 15 entries, promote the lowest-frequency ones" bullet is replaced by a detectability rule: promote a trapdoor to an automated check when its condition can be decided from the diff, the tree, or a command's output. The check lives in the project's existing linter, test suite, or hook, and its failure message names the fix. The check must fail on a seeded reproduction of the original blocker and pass once it is fixed, and only then does the line move to a "promoted" list that names the check's path. List growth remains only as a prompt to look for detectable entries. Running and repairing the check is handed to `[[lint-repair-loop]]`, and scripting it to `[[helper-script-authoring]]`, one sentence each. A Common Rationalizations row ("The trapdoor line is enough.") and a Verification item (every promoted entry records its red and green runs) were added, along with two Related Skills lines. The body is 96 lines, under the 150-line target.

`tests/skills/test_rule_ownership.py` gained the `detectable-trapdoor-promotion` row (owner `review-trapdoors`, non-owner `lint-repair-loop`). `lint-repair-loop/SKILL.md` is outside this member's write claims and does not name `[[review-trapdoors]]`, so the row would have failed the existing "non-owner must name the owner" assertion. The schema gained an optional `names_owner` field (default `True`, so every existing row behaves as before); this row sets it `False`, which keeps the plan's requirement that the non-owner must not restate the anchor clause.

### Verification Expectation (scratch trapdoor, from the skill text only)

Applying Step 5 to "SQL changes must prove parameterized queries" in a scratch project:

1. Detectable: the condition (string-built SQL in a diff) can be decided from the diff, so it earns promotion regardless of list size.
2. Check: a lint rule or test in the project's existing linter or suite, with a failure message such as "build the query with bound parameters instead of string formatting".
3. Seeded failing reproduction: a fixture reproducing the original blocker (an f-string SQL statement) must make the check fail.
4. Passing run: the same fixture rewritten with bound parameters must pass.
5. Promoted-list entry: the line moves to the "promoted" list, naming the check's path.
