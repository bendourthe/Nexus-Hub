## Verification

The commands and results are in the admission record (T036). Highlights:

- The real Windows installer ran twice into a scratch home (`HOME`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, and `NEXUS_HUB_HOME` all scratch, a shim `code.cmd` pointing the editor at a scratch extensions folder and user-data folder, no Cursor or Antigravity launcher reachable). `code --list-extensions` then listed `nexus-hub.nexus-hub-settings@0.1.0`, the installed extension activated in an isolated extension host and opened its view, and the panel agreed with `show --json` on 18 of 18 rows.
- After five `set` calls through the installed CLI, the second installer run left `show --json` identical, record for record, and the Codex file and the ownership record byte-identical. The Claude `settings.json` was rewritten byte-wise by the existing core-settings step with no changed value.
- Nine real locations (VS Code `settings.json`, `~/.claude/settings.json`, `~/.codex/config.toml`, `~/.copilot/settings.json`, the three editors' extension folders, `~/.nexus-hub`, `~/.gemini`) hashed identically before and after the repeated pass. An earlier unfiltered pass showed `~/.nexus-hub` changing in three folders owned by the live session's own hooks, never in anything an installer writes.
- The extension profile group passes through `run.py` (191 tests, 99.04 percent statement and 92.39 percent branch coverage, package, packaged-contents check). `tests/installer`, the smoke tests, `tests/ci`, the settings engine and catalog tests, parity, the handbook check, and the guide citation tests are green; counts are in the admission record.

## CI impact

The `nexus-hub-settings` profile group is explicit-only, so a normal `--profile full` run is unchanged. One new smoke test rides the existing `validate` collection. The workflow file is not on this branch. Its draft was validated in a scratch copy of the staged tree with the extension folder removed (the state of `develop`): 352 passed and 21 skipped across the workflow, contract, and reconciliation tests, and `check_required_check_coverage.py` reported every required context produced unconditionally. The workflow is not a required check. The maintenance pull request must also carry the profile group hunk, because `test_every_only_group_named_by_a_workflow_exists` fails on `develop` once a workflow names a group that is missing there. No remote CI ran.

## Plan delta

- **Status hint.** The plan said to add the extension to the existing build and install path. The path printed "Look for '<hint>' in the status bar", which is wrong for a panel with no status-bar item, so the shared function prints an activation line chosen by whether a hint was passed.
- **Header.** The panel is Nexus-Hub's own, so it installs under its own `NEXUS-HUB` header rather than a vendor header.
- **Workflow ownership.** T033 and T035 are split by file ownership, as described above.
- **Interpreter handoff.** The profile group sets `NEXUS_HUB_TEST_PYTHON` to the run's interpreter so the agreement test never picks a system Python without `tomlkit`.
