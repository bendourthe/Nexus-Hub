## Decision 5.1 (T029)

Command: **`nexus-hub prune-undetected`** (runner subcommand `prune-undetected`), not `teardown --undetected` and not `repair --prune-undetected`.

- `cmd_teardown` hard-codes workspace scope and `IntegrationBase.teardown` unlinks tracked files and `rmtree`s tracked directories with no content check, so reusing it would break decision D3; extending it would change what plain teardown does.
- `doctor` is read-only by contract and `repair` restores files, so neither should delete.
- A dedicated subcommand defaults to a preview, makes `--yes` the only path to deletion, and carries `--unforce`, which Phase 4 needed as the user-facing rollback for forcing.

Engine: `scripts/lib/integrations/_stale.py`, per entry kind as documented in `docs/policy/platform-detection.md` ("Stale Surfaces and Removal").

## Plan Delta

**Disposition: Wrong (blocking, resolved in this phase).**

Evidence: sub-task 5.1 planned to verify files under a tracked directory by comparing them with the bundled catalog source (`_tree_matches`). `_copy_tree` records only the destination directory, not its source, and a catalog comparison fails for any install older than the current catalog, which is exactly the stale case. The rule is instead: a file inside a tracked folder is removed only when it was not modified after the folder was recorded (two-second slack), and files changed or added later are kept. This is conservative (keeps on doubt) but is a timestamp rule, not a content proof; the policy page states it as such. The engine also lives in a new `_stale.py` rather than `base.py`, so plain teardown is unchanged.

Consequence for remaining phases: Phase 6's legacy cleanup reuses this command's `--yes` path and its keep-on-doubt posture; its fingerprint match remains a content proof.
