## Runtime Diagnosis

The active tree contains 820 tracked files; 26 additional paths outside that tree need reference repairs. Because the archive destination already exists, `move_prefixes` invokes one Git process per file. `undo_moves` also invokes one Git process per file, under its separate 120-second rollback budget.

Git index-write measurements showed little benefit from either split index or bypassing the Windows Git launcher. Three full-index writes took 1.090 seconds and three split-index writes 1.003 seconds; the staged tree identifier remained identical and the worktree stayed clean. Split index was then disabled again. Under Python subprocess calls matching the helper's launch method, three writes took 0.891 seconds through `cmd/git.exe` and 0.875 seconds through `mingw64/bin/git.exe`.

A private local clone with the same 9,180 index entries measured 20 actual individual `git mv` operations in 7.703 seconds, or 0.385 seconds per move. Extrapolating that measured sample to 820 moves gives 315.823 seconds for moves alone, excluding archive checks, link baselines, reference repairs, and commit work. This is an extrapolation, not a completed 820-file timing run. It demonstrates why the current per-file process strategy is incompatible with the 180-second work budget on this host, and why a 120-second rollback can leave partial moves. The repository and installed helper have the same code when line-ending differences are ignored.
