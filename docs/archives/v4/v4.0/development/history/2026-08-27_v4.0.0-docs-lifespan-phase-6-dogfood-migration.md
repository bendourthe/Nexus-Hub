## Two defects the dogfood run exposed in shipped tooling

Neither was visible from fixtures. Both are the reason this phase exists.

### Defect 1 - the command never migrated the archive container it documented (FIXED)

`docs-layout-refactor/SKILL.md` step 5 states that `--canonicalize-layout` migrates legacy singular `docs/archive/` to `docs/archives/`, and plan step 6.2 depends on it. `cmd_canonicalize_layout` only enumerated active version directories. The path *parser* already understood both containers, which is exactly why no existing test caught the drift - the code that reads the layout was correct and the code that moves it was not.

Fixed by `_legacy_archive_container`, which contributes the rename to the same migration list so it inherits the existing collision refusal. Three tests cover the migration, the collision refusal, and idempotency on an already-canonical tree.

### Defect 2 - the link gate cannot report zero on the operation it was built for (RECORDED as BG-3)

`link-baseline diff` is a set difference over `(source, link, resolved_target)` tuples. A file that moves changes its `source` key, so every pre-existing broken link inside it counts as `newly_broken` and its old tuple counts as `fixed`. The raw diff read **873 newly_broken / 638 fixed** when the true number of links broken by the move was 444.

The property was proven instead by normalizing the pre-move baseline into post-move coordinates through the rename map and comparing on `(source, resolved_target)` pairs. Recorded as BG-3 with a concrete fix (an optional `--rename-map` on `diff`) rather than left as folklore.

## What was done

1. **Baseline (6.1)**: 871 unresolved links and 763 tracked files recorded before anything moved. The `.gitignore` pre-flight ran over every destination first and reported **0 ignored paths** - this is the trap that fired three times in one release in the source repo.
2. **Migrate (6.2)**: `canonicalize-layout` performed 26 moves (25 v-bucket minors plus the archive container). `docs/v3/` and `docs/v4/` were pruned once empty.
3. **Repair**: two passes. Pass 1 resolved each stale link against its referring file's **pre-move** location, mapped it through the rename map, and re-expressed it from the post-move location - 444 rewrites. Pass 2 handled 62 move-aware residuals (depth shifts that pushed out-of-tree targets under `releases/`, and stale container names) - 72 rewrites. Every rewrite was required to land on a path that exists; nothing was written on a guess.
4. **Consumer repair**: the migration broke consumers, not documents. Old paths were hardcoded three different ways, each needing its own detection: string literals, segment-wise `Path(...) / "docs" / "v3"` construction, and regex with escaped dots inside a CI path filter.

## Guard proven live, and what that revealed

The Phase 4 `old-version-docs-guard` was exercised against the real migrated tree rather than fixtures, which surfaced two further findings:

- The bash sibling **silently no-ops on this workstation** because `jq` is absent - it exits 0 with no output for every payload, including ones it must warn on (BG-5). The guard could only be exercised through its `.ps1` sibling.
- The `.ps1` sibling fires correctly on `docs/releases/v3/v3.1/` and `docs/archives/v2/v2.1/`, but **also warns on `docs/releases/v4/v4.0/`, the version actually being built**, because active-version detection takes the highest version directory on disk and this repository keeps roadmapped `v4.1` and `v4.2` directories (BG-4). Confirmed pre-existing: both directories are in the pre-move inventory.
