### 2.3 CI/CD create, update, and optimize

**Plan specification**: Sub-task 5.3. Cover every change in the plan, then optimize for action minutes while keeping comprehensive testing.

**Coverage, verified**: `ci.yml` triggers unconditionally and classifies paths inside the workflow with a fail-closed detector job. Every path this plan touched is non-docs, so every job runs. The parity-gate extension runs inside the `validate` job's chain; both new test files run in the `tests` job.

**A real gap was found while verifying that.** The `tests` job enumerated test directories by name across four steps (`tests/integrations tests/installer`, `tests/validators`, `tests/skills`, `tests/plans tests/workflows`). Anything outside those names existed, passed locally, and guarded nothing in CI. `tests/test_removed_autonomy_surface.py` sits at the root of `tests/` and matched no step at all. This was not a surprise waiting to be discovered: the workflow's own comment recorded that `tests/plans/` had shipped in precisely this state in v3.15.8. The shape had been noticed once and left in place.

Replaced the four steps with one `python -m pytest tests -v`, which also aligns CI with what `make test` runs locally, so a green local run and a green CI run now mean the same thing.

Added `tests/workflows/test_ci_runs_every_repo_test.py` (4 tests) asserting the property rather than the wording: every test file and every test directory under `tests/` must be reachable from some pytest target in `ci.yml`, and the `catalog/hooks/tests/` suite must still be run. CI can be reorganized freely; it cannot silently drop coverage again. This is the same treatment the repository already gives the required-check antipattern, and for the same reason: a fail-open gate looks exactly like a passing one.

**Optimization, honestly**: neutral. Four pytest process starts collapse into one, saving a few seconds of interpreter and collection startup, while the newly-covered root-level test adds its own runtime. No job was added and no matrix widened. The existing optimizations (concurrency `cancel-in-progress`, pip caching keyed on manifests, the changes-detector gating, Windows and macOS legs restricted to non-PR events) were examined and left alone because they are already correct. Claiming an action-minute reduction here would be inventing one, so the evidence file says so plainly.

**Required-check integrity**: no required status check was added, renamed, or removed, so `docs/policy/required-checks.json` needed no edit. `check_required_check_coverage.py` reports 10 declared contexts across 2 branches, every one produced unconditionally. The v3.17.6 rule is unaffected, because this change edits a step inside an already-unconditional job.

## 3. Troubleshooting

**`make` is not installed on this host.** Every Makefile target was run by extracting its recipe lines into a shell script and running that through Git Bash. Each line runs in its own subshell, because the recipe relies on `make`'s per-line shell isolation; a first attempt without subshells let a `cd` leak forward and silently ran one suite twice while skipping the repo-level tree. Local tooling only; nothing was committed for it.

**A `git add -A` mixed two phases into one commit.** Phase 3's template work was swept into the Phase 2 commit. Caught by reading the commit's file list, then split with a soft reset and a selective re-stage before either commit was pushed.

**Duplicate background test runs.** Two full suites were started concurrently on a host where the repo-level suite takes about seven minutes, so they competed for the same machine. Stopped both and re-ran once.
