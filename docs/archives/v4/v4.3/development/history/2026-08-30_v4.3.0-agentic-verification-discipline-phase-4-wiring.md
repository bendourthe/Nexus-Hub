### 2.4 Prove installer distribution and repair upgrades

**Plan specification**: Prove the new skill resources, HTML rule, paired hook, and settings registration reach real user destinations through both installers.

**What happened**: Recursive catalog copying already carries the skill, its `scripts/` and `references/`, and the HTML rule. Hook scripts still use explicit installer handling. The existing settings merge, however, only handled selected hooks and returned early for existing settings, so copying the new hook files did not prove that an upgraded user would register them.

**Installer correction**: Added generic managed-hook reconciliation to both installers. Identity is event plus exact matcher plus hook type plus final script stem. The stem deliberately ignores `.sh` versus `.ps1` and uses the last script token because Windows commands run through `cursor-hook-compat.py`; this lets a cross-host upgrade replace the managed counterpart without duplicating it. User-owned settings are preserved, removed template hooks are not pruned, and repeated installs are idempotent.

**Input hardening**: PowerShell normalizes missing, null, or non-object `hooks` values before merging. The smoke checker reports a structured failure instead of crashing on a non-object hook container. The counterpart helpers are registered in `configs/installer-parity.json` so future one-sided drift fails validation.

**Real install evidence**: Fresh Windows and WSL POSIX scratch installs materialized every template identity. A second install produced the same parsed JSON. A third pass repaired an intentionally wrong-host suffix without creating duplicates. Destination files and settings registrations were opened and checked after installation.

## 5. Plan Discrepancies

The plan expected recursive copying to carry most artifacts and allowed installer edits only when an explicit copy step was needed. Files did arrive recursively, but existing-user settings still required generic managed-hook reconciliation or the new hook could be present on disk without being registered. Adding the reconciliation to both installers, the parity manifest, smoke checker, and regressions was necessary to meet the stated distribution objective.

The installer contract also required host-neutral managed identity because the same logical hook has `.sh` and `.ps1` registrations and Windows wraps the script through a compatibility adapter. This identity rule was not explicit in the plan but is required for idempotent cross-host upgrades.

The HTML cross-link task exposed an ambiguity between text-flow restrictions and legitimate media bounds. The adopted language preserves responsive text while allowing independent media dimensions.

The plan named `make validate`, `make lint`, and `make test`, but GNU Make is unavailable on this Windows host. The target bodies and repository test suites were executed directly and passed.

## Plan delta

**No blocking delta**: implementation confirmed the planned five-part gate, always-recorded phase delta, fail-closed final deep pass, generated verification expectations, owner-safe cross-links, and real distribution proof. Durable additions are generic managed-hook reconciliation for existing settings, host-neutral hook identity, malformed-hook-container normalization, explicit smoke retry semantics, corrected Tier 1 lifecycle text, terminal deep-pass ordering, and text-specific responsive-width language.

## 6. Assumptions Made

- **Managed ownership**: Matching a template hook by event, exact matcher, type, and final script stem is sufficient to replace Nexus-Hub's managed counterpart while preserving user hooks.
- **Additive upgrades**: The installer owns additions and corrections for current template hooks but does not delete registrations removed from future templates without an explicit deletion policy.
- **Functional smoke scope**: Phase 4 proves distribution and wiring. Whole-release exercise, adversarial evaluation, and human usability remain explicit Phase 5 duties.
- **Transient org result**: Repeated focused, ordered, and full-suite green evidence outweighs one clone failure whose stderr was not captured; no product change is justified without reproduction.
