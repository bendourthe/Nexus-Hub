## 2. Chronological Steps

### 2.1 Red tests and wide-world model

Three initial browser assertions failed on the portrait world and 1x canvas. The world changed from 360x480 to 640x400 logical units. The ship starts at (320, 340), horizontal speed is 260 logical units per second, and its optional vertical band is 300..380. Seeded enemy, shot and asteroid positions moved into the shorter arena, with the spawn exclusion band centered at x=320. The scene source and inline JSON were updated together, including the movement example and its tests; parsed source and inline data remain equal.

### 2.2 Resolution and resize

`sizeCanvas` now sets the backing store to the rounded logical world times the browser's DPR and reapplies `setTransform(dpr, 0, 0, dpr, 0, 0)`. Paint no longer resizes the canvas each frame, which formerly cleared its transform. Browser checks passed at DPR 2 before and after steps and resize. A separate DPR 0.8 probe observed a 512x320 backing store and matching 0.8 transform. The normal stage uses a fluid 8:5 aspect ratio at 1440, 700 and 420 CSS pixels.

The seeded buggy hit, fixed three-hit path and fatal asteroid contact were replayed at DPR 2 before and after a 1440-to-420 resize. Their respective terminal states were identical: buggy `destroyed` at three lives on tick 63, fixed `destroyed` at zero lives on tick 361, and asteroid `destroyed` at three lives on tick 111.

### 2.3 Presentation clipping found by visual inspection

Initial desktop and narrow [normal-stage captures](../training-rebuild/phase4-arena-1440-2x.png) and [narrow capture](../training-rebuild/phase4-arena-420-2x.png) showed the wide stage itself. An initial presentation crop exposed terminal text inside the stage's rectangle. The stage was 759 CSS pixels wide inside a 469-pixel game panel at 1440x900, so the game panel clipped its right side. Existing region-intersection tests only measured the containing panels and missed this child overflow. A new containment assertion reproduced the failure, then the presentation stage was constrained to its column width without abandoning 8:5 geometry. Corrected [desktop stage](../training-rebuild/phase4-present-arena-1440-2x.png), [narrow stage](../training-rebuild/phase4-present-arena-420-2x.png) and [full desktop page](../training-rebuild/phase4-present-page-1440.png) captures were inspected; the canvas and adjacent terminal are distinct, and no page errors occurred.

The inherited v4.4 presentation test required a portrait-or-square stage and a 45% viewport-height floor. Both are incompatible with a contained 8:5 stage in the current three-column deck: at 1440x900, the 469-pixel game column can hold a stage only about 293 pixels high, or 33% of the viewport. The Phase 4 interim contract therefore checks 8:5 geometry, child containment and a 30% floor; Phase 6 replaces the deck. The historical v4.4 presentation evidence was not rewritten.

The living website README now distinguishes that historical portrait result from the current wide-stage test and links to the preserved v4.4 geometry record. Its focused README test passed.
