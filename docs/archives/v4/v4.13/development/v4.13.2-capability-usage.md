# Capability usage -- v4.13.2 (for the release notes)

**Covers**: the five-part Capability usage gate entries for the surfaces v4.13.2 introduces or changes. **Read by**: whoever runs `/update release` for v4.13.2 and copies these into the release notes. **Key topics**: full-by-default `/implement`, completion gate and approval capture, completion plugins, `nexus-hub run-plan`, Codex permissions profile.

## Full-by-default `/implement`

- **Activation**: the default. `/implement <plan>` (or bare `/implement`) asks every approval the run needs once, up front, then runs every phase through release and cleanup.
- **Validation**: after the upfront round, `python ~/.nexus-hub/scripts/check_plan_completion.py record path <plan>` exits 0 and prints the run record; `python ~/.nexus-hub/scripts/check_plan_completion.py check <plan>` prints the current verdict.
- **Disable / rollback**: `/implement <plan> phase <N>` runs exactly one phase, `/implement <plan> next` runs the next one, and `/implement <plan> phase-by-phase` restores the confirm-after-each-phase loop. `/implement pause` stops a full run at the next safe point.
- **Boundary**: approvals cover only the exact values listed in the upfront round; CI workflow, permission, and secret changes are never pre-approvable and always stop the run. Approval capture checks that the text came from a prompt the user typed, not which class it approves (known gap WN-9). On OpenCode a headless run cannot record approvals (WN-4).
- **Documentation**: [`implement-phase/references/completion-contract.md`](https://github.com/bendourthe/Nexus-Hub/blob/v4.13.2/catalog/skills/workflow/implement-phase/references/completion-contract.md).

## Completion gate and approval capture hooks

- **Activation**: registered by default on the platforms whose turn-end and prompt-submit events are documented (`docs/policy/completion-levers.json`). A session with no run record is never affected.
- **Validation**: `grep -c -E "completion-gate|approval-capture" ~/.claude/settings.json` prints at least `2`. On Codex, trust the hooks once with `/hooks`; untrusted hooks are skipped.
- **Disable / rollback**: `export NEXUS_DISABLED_HOOKS=completion-gate,approval-capture`, or `NEXUS_HOOK_PROFILE=minimal`.
- **Boundary**: the gate only asks the checker for a verdict and cannot approve, push, or release anything; it releases the session after three refusals or whenever the checker cannot evaluate. Capture stores digests of prompt lines in `~/.nexus-hub/runs/prompts/`, never the text.
- **Documentation**: the completion contract above.

## Completion plugins (OpenCode, OpenClaw, Pi, Hermes)

- **Activation**: installed by default when the platform's config root already exists. OpenClaw and Hermes also need `openclaw plugins enable nexus-completion-gate` or `hermes plugins enable nexus-completion-gate` (DF-4).
- **Validation**: the plugin file exists, for example `~/.config/opencode/plugins/nexus-completion-gate.ts`, and `opencode debug config` loads without error.
- **Disable / rollback**: set `NEXUS_HUB_COMPLETION_PLUGINS=0` before installing, or delete the plugin file; the Nexus-Hub uninstaller removes it.
- **Boundary**: a plugin only starts another turn with the checker's reason; it grants no tool permission. The plugins start Python by bare name, so on Windows a `python.exe` planted in the working directory could run (WN-10).
- **Documentation**: [`docs/policy/completion-levers.json`](https://github.com/bendourthe/Nexus-Hub/blob/v4.13.2/docs/policy/completion-levers.json).

## `nexus-hub run-plan`

- **Activation**: an explicit command: `nexus-hub run-plan <plan> --platform <row>` (for example `claude`, `codex`, `opencode`), after `/implement <plan>` has recorded the approvals.
- **Validation**: `nexus-hub run-plan --help` lists the platform rows; a run prints `cycle N: ...` per cycle and ends with the checker's terminal verdict.
- **Disable / rollback**: do not run it; it installs nothing and holds only a lock file beside the run record while it runs.
- **Boundary**: it passes no bypass flag and refuses a platform whose global config bypasses approvals, so an unattended run edits and runs commands only where the platform's own permissions allow it (project-level settings are not yet checked, WN-11). It does not cap spend; `--max-cycles` bounds the cycles.
- **Documentation**: the completion contract above.

## Codex permissions profile

- **Activation**: merged into `~/.codex/config.toml` by the installer; re-run the installer to update an existing file.
- **Validation**: `grep -n -E ":minimal|:workspace_roots" ~/.codex/config.toml` shows both `"read"` entries; `codex sandbox -- sh -c 'echo ok'` prints `ok` on Linux.
- **Disable / rollback**: edit or remove the `[permissions.default.filesystem]` entries; they are ordinary Codex settings.
- **Boundary**: both entries are read-only; writes stay gated. An unattended Codex run still needs the user to trust the hooks with `/hooks` and to grant write entries for the project and its `.git` (WN-5).
- **Documentation**: [Codex configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference).
