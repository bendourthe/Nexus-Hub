# Comparison: AI-native developer mistakes and harness token efficiency

Gap analysis of Nexus-Hub against two pasted article sources: a senior engineer's "8 mistakes" talk outline (chapter titles only) and a Cursor engineer's harness token-efficiency prompt. Covers the pre-ingest security verdict, per-insight classification with file evidence, the reverse-engineering assessment, a prioritized adoption plan, queued-plan overlap, and gaps. Read it before planning v4.13.3 or before the v4.16.0 instruction-necessity review.

- Authored: 2026-09-24 (in-flight release: v4.13.0, tagged)
- Adoption target: v4.13.3 (unconfirmed; see "Adoption target" below)
- Source type: web article x2, pasted inline (no URLs)
- Source security verdict: PROCEED-WITH-CAUTION

## Source security scan (Step 1.5)

Verdict: **PROCEED-WITH-CAUTION**.

- No malicious code, destructive commands, obfuscated payloads, zero-width characters, or exfiltration patterns in either source.
- Source B is written as a set of instructions to an agent ("Change directly, each in its own revertible commit", "Report back with"). It was read strictly as data. None of its directives were executed; this report proposes, it does not change the harness.
- Source A consists only of eight chapter titles with timestamps. Every Source A interpretation below is inferred from a heading and is marked as such. The underlying video transcript was not available (no URL supplied).

## Headline findings

1. **The rendered context contradicts the templates.** Read as a model receives it, the installed `~/.claude/CLAUDE.md` is 872 lines and about 13.8k words. Lines 1-331 are an unmarked pre-v2 Nexus-Hub install (a 206-skill index and an older `# Global` section) outside the `<!-- NEXUS_HUB_START -->` block. So every session loads two full skill indexes and two conflicting copies of the global rules. The installer's marker merge (`scripts/lib/installer/instruction_merge.py:37`) only replaces the marked block, and `scripts/lib/integrations/legacy.py` has no rule that recognizes an unmarked legacy block. Source B's instruction "read the rendered requests, not just the templates" would have caught this, and no validator can, because every template is correct.
2. **The session-start hook injects stale facts into every session.** `catalog/hooks/session-start.sh:20-24` hardcodes `SKILL_COUNT=184`, `COMMAND_COUNT=33`, and `v1.1.5`, and points at `/search-skills` and `/commands-cheatsheet`, both removed in v3.2.0. The catalog is at 337 skills, 19 commands, v4.13.0. This is the "confusing or contradictory information" that Source B principle 3 warns static context produces. No queued plan covers it (keyword sweep of v4.13 to v4.17 plans: zero hits outside an unrelated push-size-guard mention).
3. **The full skill index is embedded in 13 instruction templates.** `{{SKILL_INDEX}}` expands to `data/SKILL_INDEX.md` (345 lines, about 6.5k words) in every template except the Antigravity/Gemini CLI stubs. That includes platforms that already list skills natively from their `skills/` folder (Claude Code, Codex, Cursor, Gemini, OpenCode), and it sits beside an on-demand `search_skills` MCP tool. This is the largest static-context source Nexus-Hub controls. Source B section 3 says it should be discoverable on demand rather than resent every turn.
4. **Most of Source B's model-fit and economics advice is already queued.** `v4.16.0-instruction-necessity-review`, `v4.16.1-adoption-model-adaptive-harness`, `v4.16.2-adoption-agent-tooling-and-subagent-cost`, and `v4.17.3-adoption-harness-economics-and-portable-engineering-system` together cover the emphasis audit, per-model tuning, subagent model mix, and local per-task cost measurement. This comparison feeds those plans rather than duplicating them.

## Prioritized adoption plan (Steps 5.4 and 6)

Ordering follows the RE buckets first (skill-native, then re-full), with the P-tier applied inside each bucket. Dependencies: C3 should land before C4 so the index change is measured rather than asserted.

**Bucket 1: skill-native**

1. C6: add the authoring rules to `catalog/skills/ai-development/prompt-engineering/SKILL.md`. Validate with the registry checker and `make validate`.
2. C7: add a rule-ownership table to the coordinating context skill (proposed: `context-engineering`, which shapes what is present; `prompt-token-optimization` owns cost measurement), and replace restated rules in the other five with handoffs.
3. C9: file a decision record proposing on-demand `docs/todos.md` reads. The user decides; no template change until approved.

**Bucket 2: re-full**

4. C1: fix `catalog/hooks/session-start.sh` and `.ps1` together; extend the existing parity test so counts are asserted against `data/skills.json`, never a literal.
5. C5: change the digest writer (`session-summary.sh` / `.ps1`) to carry plan state; keep the 8000-character cap.
6. C3: add the measurement script as a `DEV_ONLY_SCRIPTS` entry (repo-internal, no installer copy). Record the baseline for the five lockstep platforms in the release evidence.
7. C2: add a legacy-block rule to `scripts/lib/integrations/legacy.py` that recognizes the pre-marker signature (`# Nexus-Hub Skill Index` plus a `**Total:` line outside the markers). It reports and backs up the block and removes it only on confirmation or a flag. It must go through the v4.13.1 user-edit-preservation path.
8. C4: gate the index pointer behind a flag, run the skill routing evals before and after, and ship only if trigger accuracy does not drop. The five lockstep templates change together; `check_base_template_parity.py` must stay green.
9. C8: optional tail mode in the compressor CLI.

## Not recommended

| Item | Reason |
|---|---|
| A8: drop branches and worktrees | The `develop` + `main` model protects installer users from half-applied phases. `main` is a release artifact. |
| A5 as a hard removal of todo tracking | The rule is in the user's own global instructions. It is only proposed (C9), never removed unilaterally. |
| B5, B6, B15 harness request-assembly changes | Nexus-Hub does not own request assembly, caching, or reasoning items. The host platforms do. |
| Removing the skill index everywhere | Copilot and the guardrails-only platforms have no native skill enumeration. There the index is the only discovery path, and removing it would be the Source B trap "offloading a tool the model needs on the first turn". |

## Adoption target

Default resolved target: **v4.13.3**. v4.13.0 is released, v4.13.1 and v4.13.2 hold queued plans, and v4.13.3 is the first free patch slot. The P0/P1 items (C1, C2, C5) are defect fixes that affect every installed session today, so ranking them behind the v4.14 to v4.17 queue would leave the stale banner and the duplicate index in place for eleven more releases. The larger items (C3, C4) could instead move to a slot after v4.16.0 so they land with the necessity review. **This target needs the user's confirmation before a plan is generated.**

## Risks and conflicts (Step 7)

- C2 touches content in the user's own instruction file. It must never delete silently; back up the block, show a diff, and require confirmation (see the preserve-user-edits discipline).
- C4 risks skill under-triggering on platforms whose native skill listing shows descriptions less prominently than the embedded table. It is gated on routing evals.
- C1 and C5 edit hooks, which AGENTS.md "Ask first" lists as needing approval. Both need `.sh` and `.ps1` parity and `make test`.
- C4 edits the five lockstep templates plus the eight non-guarded substantive templates.

## Gaps

- Source A's arguments are unknown beyond its chapter titles. Supplying the video URL would allow a transcript via the `youtube-transcript` skill and could change A2, A3, A5, and A7.
- No per-session token measurement was taken. The word counts above (13.8k words rendered, 6.5k-word index) are static-size proxies, not billed tokens, and cache hit behavior was not observed.
- The installed-state findings (Finding 1) come from one machine. Whether other users carry the same legacy block depends on their install history.
