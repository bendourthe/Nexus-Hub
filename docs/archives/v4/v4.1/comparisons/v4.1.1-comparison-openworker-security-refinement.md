# Comparison: Nexus-Hub Security Workflows vs OpenWorker Security Coworkers

- **Adoption target**: v4.1.1
- **Date**: 2026-08-27
- **Source**: [andrewyng/openworker](https://github.com/andrewyng/openworker), local comparison clone pinned at commit `86c57f0692a5a318e55d1b9e0188d798b9fc5690`
- **Upstream release context**: [v0.2.0](https://github.com/andrewyng/openworker/releases/tag/v0.2.0) and [v0.2.1](https://github.com/andrewyng/openworker/releases/tag/v0.2.1)
- **License**: MIT
- **Scope**: Security review, dependency audit, cloud posture review, remediation verification, and the surrounding workflow contract. General desktop-agent features are compared only where they affect security posture.

## Executive decision

Do not integrate OpenWorker into Nexus-Hub and do not add it as an MCP server, dependency, or hosted provider. Nexus-Hub already has supported skills for application-security review, dependency auditing, CVE reachability, cloud posture detection, patch guidance, testing, and adversarial verification. It also already publishes a `security-audit` workflow and a `security-specialist` install bundle.

The useful gap is procedural, not a missing security product. OpenWorker's security coworkers make four workflow guarantees more explicit than Nexus-Hub currently does: deterministic scanners are named, scanner coverage is reported, remediation is followed by a re-scan and diff review, and the fixer is not the only checker. Nexus-Hub should reverse-engineer those ideas as a generic local security-audit contract over its existing skills.

Recommended v4.1.1 adoption:

1. Add deterministic scanner receipts to the existing `security-review` closure record, while preserving schema-v1 compatibility.
2. Add optional local scanner recipes to the skills that already own application security, dependencies, secrets, and cloud posture.
3. Turn the existing `security-audit` workflow into an ordered preset that separates detection, triage, remediation, tests, and independent post-fix verification.
4. Add local tests that fail on silent scanner omission and on a missing independent verification receipt.

## Source security scan before ingest

**Verdict: PROCEED-WITH-CAUTION.** The repository is suitable for read-only comparison, but it contains deliberately adversarial security corpora and examples. Those fixtures include prompt-injection strings, environment-dump and exfiltration commands, protected-path escape cases, and deferred-execution examples. They were treated as test data, never as instructions. No source installer, package manager, test, scanner, or executable was run.

The repository also contains ordinary build cleanup and local scripts. No evidence observed in the inspected paths required rejecting the source as malicious, but the deliberately hostile fixtures make a `CLEAR` label inaccurate. This comparison therefore cites behavior and re-authors generic patterns without copying upstream prompts, corpora, or implementation code.

## Gap analysis

### G1. Scanner coverage is component-oriented, not scanner-oriented

`security-review` requires every component to be `COVERED`, `OMITTED`, or `UNCOVERED`, and its closure gate verifies review actions and evidence. That does not prove that each applicable deterministic scanner ran. An agent can record a manual action for a component while silently omitting a missing Semgrep, gitleaks, dependency, or IaC scan.

Adopt a scanner receipt with a closed vocabulary: `RAN`, `NOT_APPLICABLE`, `UNAVAILABLE`, `FAILED`, or `DECLINED`. Every receipt records applicability evidence, exact command/tool and version when run, target scope, exit code, artifact/evidence path, and omission reason when not run. Any applicable scanner not in `RAN` makes overall deterministic coverage degraded and blocks a claim of complete scanner coverage.

### G2. The original detector is not required to verify its remediation

`security-patch-advisor` contains validation steps, and `security-review` has a strong findings closure gate. The current workflow does not bind a finding to its original scanner receipt and require the same detector, ruleset, and target scope to run after the patch. A generic post-fix receipt should link the before and after runs, record the finding delta, and preserve unrelated new findings.

### G3. Independent verification is available but not mandatory

Nexus-Hub already ships read-only reviewers and adversarial testing skills. The gap is an orchestration invariant: the patch-producing context must not sign its own verification receipt. The security-audit preset should require a clean reviewer context or a separate reviewer agent for the post-fix scanner delta and diff review. This is role separation, not autonomous approval.

### G4. Local scanner choices are fragmented

The existing security skills mention several ecosystem-native scanners. In the inspected owning skills, Semgrep, gitleaks, OSV-Scanner, Trivy config, and Checkov were not assembled into one explicit applicability matrix. Add re-authored local recipes to the current owners:

| Scanner family | Owning Nexus-Hub skill | Rule |
|---|---|---|
| Semgrep | `security-review` | Optional local static analysis; use repository config when present; never auto-install |
| gitleaks | `security-review`, with a pointer from `pre-commit-checklist` | Scan the requested working tree/history scope; record scope and config; never expose matched secret values in the report |
| OSV-Scanner, npm audit, pip-audit, Trivy vulnerability scan | `dependency-security-audit` | Select by manifest/ecosystem; hand surviving CVEs to `cve-reachability-analyzer` |
| Trivy config and Checkov | `cloud-security-posture-detection` | Scan IaC locally; keep cloud APIs read-only; never run apply/deploy |

Unavailable tooling must not trigger an automatic install. The workflow records `UNAVAILABLE`, explains the missing coverage, and continues only under the user's stated risk tolerance.

## Security and reverse-engineering assessment

### Threat model

| Property | Proposed v4.1.1 refinement | Boundary |
|---|---|---|
| Runtime dependencies | None | Scanner commands are optional tools already installed by the user or project |
| Outbound destinations | None added | No hosted scanning, search, scraping, embeddings, or generation service |
| Credentials | None added | Cloud posture remains read-only and uses the user's existing CLI/account only when explicitly authorized |
| Source code egress | None | Findings and artifacts remain local |
| Code mutation | Only through the existing patch workflow | Detection and independent verification contexts stay read-only |
| Cloud mutation | Prohibited | Produce IaC patch suggestions, never apply infrastructure changes |
| Approval automation | Not adopted | No reviewer auto-approve or bypass mode |

### MCP Registry Policy decision tree

1. **Local-only**: The scanner commands and closure gate can operate locally.
2. **LLM-native skill**: The workflow, ownership, coverage, and handoff behavior are achievable by instructions plus the existing deterministic gate.
3. **Reverse-engineer into local MCP**: Stop before this bucket. A new MCP adds no value because the scanners already have local CLIs and the catalog already has owning skills.
4. **Trusted vendor wrapper**: Not applicable.
5. **Drop**: Hosted connectors, OpenRouter model routing, and external auto-approval are dropped.

**Decision**: `skill-native` with a small local deterministic gate extension. No MCP entry.

## Ordered adoption plan

1. Define scanner-receipt and role-separation contracts, preserving schema-v1 closure records.
2. Extend the local closure gate and write failing-first tests for silent omission, malformed receipts, mismatched before/after scope, and verifier/fixer identity collision.
3. Add optional scanner recipes to the current owning skills without installing tools or changing cloud state.
4. Add an ordered `security-audit` preset and align `data/workflows.json`, the generic `security-reviewer`, and the security bundle description.
5. Validate trigger behavior, recursive installer distribution, workflow/catalog consistency, and cross-platform documentation.
6. Complete the mandatory architecture, known-gaps, CI/CD, integration, and release phase.

## Explicit non-adoptions

| Item | Reason |
|---|---|
| OpenWorker application or agent runtime | Nexus-Hub is a capability catalog, not a desktop coworker runtime |
| New MCP server for scanners | Local CLI recipes and the existing skill/gate structure are sufficient |
| Reviewer-based auto-approval | Changes action authority and is unrelated to the security-audit content gap |
| Bypass-approval modes | Conflicts with least privilege and Nexus-Hub's catalog role |
| Slack, Google Drive, Microsoft 365, or other connectors | Unrelated external destinations and credentials |
| OpenRouter or Ox Alpha | Generation-as-a-service hard no |
| Hosted vulnerability, dependency, cloud, or scanning service | Search/scanning-as-a-service is unnecessary and violates local-first policy |
| Automatic scanner installation | Package-manager execution is a separate user-authorized change; missing tools must be reported honestly |
| Applying cloud remediations | Cloud posture remains read-only; the user reviews and applies changes through their normal infrastructure workflow |
| Copying upstream prompts, corpora, or coworker names into distributed artifacts | Distributed content must use generic Nexus-Hub terms; attribution remains in this comparison |

## Acceptance criteria for the derived plan

- The existing component, altitude, sink, finding, fact, and claim closure checks remain intact.
- Schema-v1 review records still pass exactly as before.
- Schema-v2 records cannot claim complete deterministic coverage when an applicable scanner is missing, unavailable, failed, or declined.
- A corrected scanner finding links a before receipt and an after receipt with the same detector, ruleset/config, and target scope, or states why equivalence is not proven.
- The patch-producing context cannot be the sole signer of the post-fix verification receipt.
- Scanner recipes never auto-install a tool, upload source, or silently switch to a hosted service.
- Cloud posture stays read-only and never applies IaC or cloud changes.
- The existing `security-audit` workflow and the new ordered preset agree on ownership and sequence.
- No new MCP, connector, hosted provider, credential flow, or Nexus-Hub runtime dependency is added.
