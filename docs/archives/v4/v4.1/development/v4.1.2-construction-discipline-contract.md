# v4.1.2 Construction-Discipline Contract

This document is the wording source for the always-on `## Construction Discipline` section. Copy the invariant body below into the twelve substantive instruction templates. Do not copy this document's ownership table, non-goals, or budget note into those templates.

The section is always-loaded. Target at most six loaded body lines. Hard cap: eight non-empty body lines. Detail belongs in `minimal-construction` and `over-engineering-review`.

Distributed copy uses generic names only. Do not name an external product in any text that is copied into templates.

## Always-on invariant body

Copy this block verbatim, including the heading. Do not restate security-review, accessibility, or verification procedures here.

```markdown
## Construction Discipline
- After reading the real flow, stop at the first sufficient rung: skip, reuse this codebase, stdlib, native feature, installed dependency, one line, then minimum.
- Governs what you build, not how you talk. Do not drop trust-boundary, data-loss, security, accessibility, or a proving command owned by `verification-before-completion`.
- End-of-Task Summary and user-requested explanation are not debt. `minimal-construction` and `over-engineering-review` own intensity and delete-lists. Mark a cut ceiling with `construction-debt:`.
```

## Loaded facts (do not expand the template to restate them)

1. Seven-rung pre-write ladder, after reading the real flow: skip unneeded work, reuse this codebase, stdlib, native platform feature, already-installed dependency, one line, then minimum new code.
2. The rule governs what you build, not how you talk.
3. Do not drop trust-boundary validation, data-loss handling, security, accessibility, or a proving command owned by `verification-before-completion`.
4. End-of-Task Summary and a user-requested explanation are not construction debt.
5. Intensity levels and delete-list review live in named skills. Do not invent an env var or config file for them.
6. A deliberate corner that cuts a real ceiling uses a `construction-debt:` comment naming the limit and the revisit trigger.

## Placement

Insert the heading immediately after `## End-of-Task Summary` and before the next heading (`## MCP Registry Policy` on most templates; `## Context References` on `base-claude.md`; `## Domain Instructions` on `generic-instructions.md`).

Do not put the rule inside `## Output Minimization`. Do not add the heading to include-only shims: `base-antigravity-10.md`, `base-antigravity-20.md`, `base-antigravity-cli.md`, `base-gemini-cli.md`.

Lockstep parity: add `Construction Discipline` to both `REQUIRED_HEADINGS` and `INVARIANT_SECTIONS` in `scripts/check_base_template_parity.py`.

## Cluster ownership

Non-owners reference the owner. They do not restate the owned rule.

| Concern | Owner | Non-owners do |
|---|---|---|
| How small a new solution is (reuse, stdlib, native, installed dep, one line, minimum) | `minimal-construction` | Point at it |
| YAGNI for extra machinery inside a requested feature | `minimal-construction` | Do not decline the user's requested feature silently; `Consequential Decisions` still governs scope expansion |
| Collapse of existing over-abstraction without behavior change | `code-simplification` | `minimal-construction` does not become a refactor skill |
| Dead / unreachable code at scale | `dead-code-eliminator` | Point at it |
| Diff- or repo-scoped over-engineering delete-list | `over-engineering-review` | `code-quality` keeps SOLID/maintainability; `code-smell-detector` keeps Fowler smells |
| Unrequested code versus a plan | `implementation-convergence` | Construction ladder does not invent plan gaps |
| Plan scope / cut-lines | `plan-review` (scope-guardian lens) | Point at it |
| Repo-internal do not add unused structure to Nexus-Hub | AGENTS.md Boundaries | Not distributed as a user coding rule |
| Trust-boundary validation, security, accessibility | `security-review` and the owning security/a11y skills | `minimal-construction` names the handoff; it does not restate those rules |
| Completion claims and proving commands | `verification-before-completion` | Do not adopt a one-assert floor or YAGNI-on-tests |
| How the agent talks | `agent-communication` plus End-of-Task Summary | Do not adopt code-first, three-lines, or delete-the-explanation |
| Version-level deferrals | `known-gaps-tracker` | Point at it |
| SQALE / interest quantification | `technical-debt-analyzer` | Point at it |
| In-code named ceilings with an upgrade trigger | `construction-debt:` harvest in `minimal-construction` | Generic marker; never an external product name |

## Template non-goals

- Do not restate security-review, accessibility, or verification procedures in the template body.
- Do not add an env var, flag file, or config key for intensity. Intensity is a skill argument. The compact template is always on.
- Do not add an MCP, hook, statusline, or host `settings.json` mutation for this rule.
