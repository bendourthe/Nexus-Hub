# v4.1.1 Local Security-Audit Contract

This document is the normative contract for Nexus-Hub schema-v2 security-audit closure records. It extends the existing schema-v1 review record; it does not replace component coverage, altitude passes, sink sweeps, finding dispositions, facts, or report claims.

Distributed artifacts use generic Nexus-Hub terms only: scanner receipt, remediation handoff, independent verifier, and deterministic coverage. This contract does not add a scanner product, an MCP server, a hosted scanning service, or automatic tool installation.

## Compatibility

Schema v1 remains valid. A record with `schema_version` equal to `1` is evaluated only on the original five claim-to-evidence diffs. Extra schema-v2 keys on a v1 record are ignored.

Schema v2 is opt-in. A full security-audit workflow must emit schema v2. A focused or manual review may keep schema v1 when it includes an explicit scoped-coverage statement that deterministic scanner completeness is not claimed.

Unknown `schema_version` values are usage errors. The gate does not guess a schema.

## Scanner inventory

A schema-v2 record must include `scanner_inventory`, the complete set of deterministic scanners considered for this run. Each entry has a unique `id`, a boolean `applicable`, and non-empty `evidence` for that applicability decision.

The inventory is the scanner denominator. A scanner that was considered cannot disappear. Every inventory `id` must have at least one matching `scanner_receipts` entry whose `scanner_id` equals that `id`.

Suggested inventory identities for a full audit, used only when the target makes them applicable:

- `semgrep` for local application static analysis
- `gitleaks` for secrets scanning
- `osv-scanner`, `npm-audit`, `pip-audit`, and `trivy-vuln` for dependency scanning as selected by manifests
- `trivy-config` and `checkov` for local IaC configuration

The gate does not hard-code that list. It evaluates the inventory the record declared.

## Receipt states

Every scanner receipt uses exactly one of these states:

| State | Meaning |
|---|---|
| `RAN` | The scanner executed against the recorded target |
| `NOT_APPLICABLE` | Applicability evidence shows this scanner does not apply |
| `UNAVAILABLE` | The scanner applies, but the tool is not present locally |
| `FAILED` | The scanner was invoked and did not complete successfully |
| `DECLINED` | The scanner applies, but the user declined to run it |

Any other state is unsupported.

## Receipt fields

Each `scanner_receipts` object has a unique `id` and a `scanner_id` that matches the inventory.

A `RAN` receipt must include all of the following non-empty fields, plus an integer `exit_code` that is not a boolean:

- `scanner_version`
- `applicability_evidence`
- `target_scope`
- `config_fingerprint`
- `command`
- `started_at`
- `finished_at`
- `artifact_path`

`target_scope` is an object. It must include a non-empty `fingerprint` and may include `paths`. The fingerprint is the exact target identity used for before/after comparison.

`config_fingerprint` is the ruleset or configuration identity actually used. A repository config that would fetch rules over the network is not implied by this field; authorization for outbound fetching is a skill-level rule, not a gate input.

A `NOT_APPLICABLE` receipt must include `applicability_evidence` and `omission_reason`. Missing evidence is treated as a forged non-applicability claim.

`UNAVAILABLE` and `DECLINED` receipts must include `applicability_evidence` and `omission_reason`.

A `FAILED` receipt must include `applicability_evidence`, `command`, integer `exit_code`, and `omission_reason`.

Optional `observed_finding_ids` on a `RAN` receipt names finding IDs observed in that scan artifact. The gate never executes a scanner; those IDs are inert recorded data.

## Deterministic coverage

A schema-v2 record must include `deterministic_coverage` with `status` equal to `complete` or `degraded`.

Coverage is complete only when every applicable inventory scanner has a successful `RAN` receipt. Any applicable scanner that is `UNAVAILABLE`, `FAILED`, or `DECLINED` makes coverage degraded.

A `complete` claim is a failure when any applicable scanner did not `RAN`. A missing receipt for an inventory scanner is a silent omission and is always a failure, including when coverage is already marked `degraded`.

`NOT_APPLICABLE` with evidence does not degrade coverage. `NOT_APPLICABLE` without evidence is malformed.

The report may not claim complete scanner coverage while status is `degraded`.

## Remediation receipts

A schema-v2 record must include `remediation_receipts`. The list may be empty when the audit produces no patch.

Each remediation receipt has:

- unique `id`
- `finding_ids` naming the corrected findings
- `fixer_identity`
- `before_receipt_id`
- `after_receipt_id`
- `finding_delta` with `resolved_finding_ids`, `unresolved_finding_ids`, and `new_finding_ids`

A finding with disposition `corrected` and a non-empty `source_scanner_id` is a scanner-sourced correction. It must link equivalent before and after receipts for that detector. Equivalence means the same `scanner_id`, the same `config_fingerprint`, and the same `target_scope` fingerprint.

Unrelated new findings from the after scan must remain visible. An after-scan finding ID that is not present in the findings collection with a terminal or explicitly pending disposition is unresolved.

A no-fix audit omits scanner-sourced corrections and keeps `remediation_receipts` empty.

## Verifier identity

A schema-v2 record must include `verifiers`. Each verifier has `identity` and boolean `read_only`.

When `remediation_receipts` is non-empty, at least one verifier must be independent of every `fixer_identity` and must have `read_only` equal to true. The patch-producing context may appear as an additional verifier, but it cannot be the only verifier.

The independent verifier reviews the patch diff and the before/after scanner delta. It does not apply patches, mutate infrastructure, or auto-approve actions.

A detection-only audit with empty remediations does not require an independent post-fix verifier.

## Closure diffs

Schema v1 keeps these diffs:

- `components_without_review_action_or_caveat`
- `findings_without_terminal_or_pending_disposition`
- `confirmed_findings_without_supporting_evidence`
- `rejected_findings_without_complete_rejection_record`
- `report_claims_without_matching_facts`

Schema v2 adds:

| Diff | IDs recorded | Failure meaning |
|---|---|---|
| `applicable_scanners_without_successful_run` | scanner inventory ids | Silent omission, or a complete-coverage claim while an applicable scanner did not `RAN` |
| `malformed_or_unsupported_receipt_states` | receipt ids, or scanner ids for inventory shape errors | Unsupported state or missing required receipt fields, including `NOT_APPLICABLE` without evidence and `RAN` without `scanner_version` |
| `corrected_scanner_findings_without_equivalent_rescan` | finding ids | A scanner-sourced correction without linked before and after receipts |
| `mismatched_detector_config_or_scope` | finding ids | Before and after receipts disagree on detector, config fingerprint, or target scope |
| `unresolved_new_after_scan_findings` | finding ids | The after scan introduced a finding that has no terminal or explicitly pending disposition |
| `fixer_is_sole_verifier` | `verifiers` | Missing independent read-only verifier, or the fixer is the only verifier |

Any non-empty diff is a closure failure (exit `1`). Malformed JSON, missing required collections, duplicate IDs, and unknown schema versions remain usage errors (exit `2`). Exit `0` is clean.

## Read-only and local-only constraints

This contract does not authorize:

- automatic scanner installation or package-manager mutation
- hosted scanning, search, embeddings, or generation services
- applying IaC or cloud remediations
- an independent verifier that writes patches or approves its own prior fixes

Missing tools stay visible as `UNAVAILABLE`. Cloud posture review, when in scope, remains read-only.
