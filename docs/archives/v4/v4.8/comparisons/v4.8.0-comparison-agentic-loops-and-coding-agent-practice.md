## Why these sources matter to this project

Both documents describe the discipline Nexus-Hub exists to distribute: how to run coding and knowledge-work agents so that autonomy is bounded, verified, and recoverable. The PDF is a skills map for the human operator (directing the workflow, enabling autonomy, reviewing, customizing the harness, foundations). The DOCX is a control-stack model for the system (prompt, context, harness, loop, graph) with a run-contract schema, a verifier taxonomy, ten loop failure modes, a graph-readiness discipline, and a security and governance layer anchored on the OWASP Top 10 for Agentic Applications and NIST AI RMF.

Nexus-Hub already adopted the core of this material in three earlier cycles: `docs/releases/v3/v3.2/comparisons/v3.2.0-comparison-loop-engineering.md`, `docs/releases/v3/v3.5/comparisons/v3.5.0-comparison-loopmaxxing-and-autoresearch.md`, and the v4.3.0 agentic-verification-discipline plan. The `loop-engineering` skill carries an exit-signal protocol, idempotent completion gates, reward-hacking doctrine, three-class stall detection, typed human gates, evidence freshness, bounded fan-out, and unattended-loop sandboxing. So this comparison is not a discovery of loop engineering. It is a gap audit against two documents that have consolidated the field since, and the gaps it finds are precise: an intake scorecard the loop skill lacks, a graph-readiness gate the orchestration skill lacks, a knowledge-work verifier taxonomy the research surface lacks, an OWASP agentic mapping the security cluster lacks, and two Foundations layers the public guide stops short of.

## Step 7 -- Risks, conflicts, and items not recommended

### Conflicts with existing Nexus-Hub conventions

- **A5 vs the retired v3.17.0 autonomy toggle.** That plan tried to remove approval prompts through platform levers and was retired because no supported API existed. A5 is doctrine about which autonomy level to choose, not a lever that changes one. State this in the skill so a reader does not expect a runtime.
- **A2 vs schema stability.** The loop schema declares its first nine fields required and every optional field additive. A2 must add optional fields only; promoting any of them to required would invalidate the six library loops.
- **A6 vs research ergonomics.** A fail-closed completion block on `/research` would reject every run that cites a paywalled source. Ship it advisory in v4.8.0; a threshold becomes blocking only after a measured baseline exists, which is the DOCX's own Stage 0 advice.
- **A9 vs the guide's design rules.** The README records that a mockup is a source of teaching, not markup to paste, and that a rename is not finished until every sentence about the old name has been read. Two new scenes touch the "That is the whole mental model" closer, which currently asserts the spine ends at Harnesses.
- **B1 vs framework-field parity.** `validate_skills.py` checks list shape only; the coverage builder must handle a framework whose IDs are `ASI01` to `ASI10` rather than dotted technique codes. Confirm the ID format from the fetched document before writing the regex.

### Change-risk notes

- Reference-file additions (A1, A3, A4, A6 taxonomy, A7) carry no installer risk: skill trees are copied recursively and the orphan audit is the only gate.
- Body edits to `loop-engineering` and `agent-orchestration-primitives` are the highest-traffic skills in the orchestration cluster; both are near their 500-line targets, so new content goes to `references/` and the body gets one linking sentence each.
- B1 needs a decision record under `docs/decisions/` because it adds a validator field, per `AGENTS.md` "Decision Records".
