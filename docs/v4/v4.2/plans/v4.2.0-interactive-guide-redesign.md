**Goal**: Redesign the Nexus-Hub interactive guide into a concise, distinctive, portfolio-aligned learning experience that lets software engineers understand the model-versus-harness distinction, install Nexus-Hub immediately, and follow a realistic command-to-result workflow inside an interactive IDE simulation.
**Primary source**: `guides/website/nexus-hub-guide.html`

## Overview

The current guide is comprehensive but too dense for first contact. Home spans roughly 275 source lines and repeats its message through stats, four-card grids, long comparisons, migration tables, workflow diagrams, and navigation cards. Foundations spans roughly 448 lines and teaches six concepts across two ladders before reaching the distinction the workshop audience needs most. Training contains 31 slides, frequently separating a command from its result, which makes the workflow feel like a sequence of static examples instead of visible work happening inside a project.

This enhancement will preserve the guide's self-contained, offline, single-file contract while changing its teaching model. Home becomes a short orientation and installation surface. Foundations leads with the user's preferred analogy: the model is the brain with knowledge and reasoning; the harness is the accumulated skills, experience, workflow, and guardrails that make the brain useful on real projects. Training becomes an interactive software-engineering workbench with a repository tree, editor or diff surface, assistant conversation, terminal or test output, command timeline, and human decision gates that animate together for each Nexus-Hub workflow step.

The redesign will inherit the portfolio's actual visual primitives rather than approximating them: its light/dark token logic, `portfolio-theme` preference key, deep-teal navigation, cyan/teal accents, and constellation canvas behavior. It will deliberately clear the `hallmark-design` anti-slop gates by replacing the centered gradient hero, pill-stat row, repeated equal cards, gradient text, and uniform section rhythm with an editorial technical layout, asymmetric hierarchy, solid role-based actions, varied content bands, and restrained motion. Nexus-Hub remains the canonical source; the portfolio receives a verified published copy without manual content drift.

## Goals First

**Target problem**: Software engineers seeing Nexus-Hub for the first time cannot quickly explain what it adds to an AI coding assistant or visualize how its commands change a real project's files, artifacts, tests, and decisions.

**Primary persona**: A software engineer or engineering team attending a live workshop and evaluating whether Nexus-Hub belongs in their daily coding workflow.

**Secondary persona**: A self-guided portfolio visitor who needs a credible overview, installation command, and concrete demonstration without facilitator narration.

**Observable definition of done**:

- A first-time visitor can state in one sentence that the model supplies knowledge and reasoning while Nexus-Hub supplies reusable experience, workflows, and enforced guardrails.
- The visitor can install Nexus-Hub from Home using one macOS/Linux or Windows command without opening a separate Installation page.
- The visitor can run or step through a realistic IDE simulation and see, for every command, the input, tool activity, durable artifact or code change, quality gate, and next human decision.
- The guide supports light and dark modes, persists the same preference key as the portfolio, uses the constellation background consistently, and remains usable with reduced motion.
- The canonical Nexus-Hub guide and the portfolio-published copy have a deterministic, documented synchronization path and no stale counts or version strings.

**Success measures**:

- Comprehension: at least 4 of 5 workshop participants can correctly explain "model versus harness" after Foundations without facilitator correction.
- Workflow recall: at least 4 of 5 participants can identify the next command and its expected artifact after completing the guided workbench.
- Navigation: Home, Foundations, Training, Workflows, and Reference are reachable by keyboard and their state is reflected in the URL.
- Accessibility: Lighthouse Accessibility is at least 90 in both themes, with no high-severity keyboard, contrast, heading, or reduced-motion defect.
- Fidelity: desktop, tablet, phone, projector, light-mode, and dark-mode visual QA records no open high-severity issue.

## Scope

### In scope

- Simplify Home and absorb the two one-command installation paths.
- Remove Installation from primary navigation and retain advanced install detail only where it remains useful.
- Rewrite Foundations around the model-as-brain and harness-as-experience distinction, with agent/tools and prompt/context as supporting concepts rather than parallel top-level lessons.
- Replace the 31-slide training deck with a smaller, dynamic, interactive IDE workbench.
- Reuse real command/output fixtures from the Trivia Quiz example while improving how changes and artifacts are visualized.
- Add a portfolio-aligned light/dark theme, shared preference behavior, and constellation background treatment.
- Apply the hallmark anti-slop design gates and responsive/accessibility requirements.
- Establish deterministic Nexus-Hub-to-portfolio publication and drift verification.
- Update guide maintainer documentation, tests, and CI coverage.

### Out of scope

- Changing Nexus-Hub command semantics, installer behavior, catalog contents, or supported-platform behavior.
- Replacing the Trivia Quiz example application unless a minimal fixture change is required to demonstrate an existing workflow accurately.
- Adding telemetry, hosted analytics, a server, a framework, a CDN, remote fonts, or runtime network dependencies.
- Rebuilding the rest of the online portfolio.
- Generating AI imagery or importing a theme catalog.

## Phase 4: Model-versus-Harness Foundations

**Goal**: Teach one memorable distinction first, then reveal supporting concepts only when useful.
**Prerequisites**: Phase 3.

#### 4.1 - Reframe Foundations around brain and experience

**Objective**: Replace the two long ladders with a direct conceptual model.

**Prompt**:
> Rewrite `#page-foundations` in `guides/website/nexus-hub-guide.html` around three concise roles: Model = the brain (trained knowledge and reasoning); Agent/platform = the hands and workspace (tools that can read, edit, run, and observe); Harness = experience and operating discipline (skills, commands, context-selection procedures, rules, hooks, gates, and durable workflow). Make Model versus Harness the visual and narrative focus, using the user's language "brain with knowledge" and "skills and experience" while keeping technical accuracy. Explain that Nexus-Hub does not replace or retrain the model; it installs reusable experience and guardrails around the assistant. Move prompt engineering, context engineering, detailed reasoning history, and the six-term recap into a compact "Go deeper" glossary or disclosure. Acceptance: the primary section can be read in under three minutes; each role has one sentence, one concrete software example, and one limitation; no claim says the model is a literal database or human brain.

#### 4.2 - Build one interactive raw-versus-harness demonstration

**Objective**: Let the reader see the difference instead of reading multiple tables.

Acceptance: the demonstration makes causal attribution clear; no side is a straw man; keyboard and screen-reader users can access both states and their differences.
