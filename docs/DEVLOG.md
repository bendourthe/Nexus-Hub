# Development Log

## [2026-05-06] - Release 1.1.2: Opt-In Git Pre-Commit Claude Review Hook

*   **Goal**: Close a gap that the existing agent-level `secret-scan.sh` Claude Code hook cannot close on its own. `secret-scan.sh` is a `PreToolUse:Write/Edit` hook, so it only fires when Claude Code itself proposes a write. Code edited from Cursor, Copilot, Codex, Gemini, a terminal editor, or a teammate's machine never passes through that gate. A patch release adds an **opt-in** git pre-commit hook that pipes `git diff --cached` through `claude -p` for an LLM review. Because the trigger surface is `git commit`, the new hook fires on every commit regardless of which agent (or human) authored the change. The two hooks are complementary, not redundant: regex at write-time (deterministic, zero token cost, Claude Code only) plus LLM at commit-time (judgment-driven, catches debug artifacts and TODOs that regex never could, all editor paths). Patch release rather than minor bump because the change is strictly additive and gated behind explicit per-repo opt-in - no existing repository's behavior changes until the user runs the new slash command.

*   **What Changed**:
    *   **`catalog/hooks/claude-diff-review.sh`** - the hook itself, ~120 lines of bash. Reads `git diff --cached`, caps the diff at 50 KB by default (configurable via `DEVAI_DIFF_REVIEW_MAX_BYTES`), pipes it through `claude -p` with a strict review prompt covering hardcoded credentials, debug artifacts, unfinished TODOs, and large commented-out code blocks. Parses Claude's response on the first line (`VERDICT: PASS|WARN|BLOCK`) and exits accordingly: `PASS` silent allow, `WARN` prints findings to stderr but allows the commit, `BLOCK` refuses the commit with exit 1. Fail-open on every error path - missing CLI, empty response, unparseable verdict, oversized diff, merge / cherry-pick / rebase in progress, env-var bypass set. Three explicit bypass paths: `DEVAI_DIFF_REVIEW_DISABLE=1 git commit ...` per-commit override, git's standard `--no-verify` flag, and the configurable size cap.
    *   **`catalog/commands/install-claude-pre-commit-hook.md`** - new slash command. When invoked from inside a target repo, copies `~/.devai-hub/hooks/claude-diff-review.sh` to that repo's `.git/hooks/pre-commit`. Detects pre-existing hooks: if the file already contains the DevAI-Hub marker (`# claude-diff-review.sh`), reports already-installed and exits cleanly; otherwise shows the existing hook to the user and offers replace / abort / chain-manually paths, with a `.git/hooks/pre-commit.devai-backup-<timestamp>` backup written before any overwrite. Cross-platform: works on Linux, macOS, and Windows (Git for Windows runs hooks via its bundled bash, so the bash source runs natively).
    *   **Installer wiring** in both `scripts/installer.sh` (line 1424) and `scripts/installer.ps1` (line 1733), inside the existing `install_templates` function next to the style-guides copy. Distributes the hook source to `~/.devai-hub/hooks/claude-diff-review.sh` on POSIX or `%USERPROFILE%\.devai-hub\hooks\claude-diff-review.sh` on Windows, with `chmod +x` on POSIX. The hook is intentionally **not** added to `catalog/hooks/settings.json`, because settings.json wires Claude Code PreToolUse hooks; this is a git hook with a different trigger surface and a different lifecycle. The shared `~/.devai-hub/` location (not per-platform under `~/.claude/hooks/`) reflects that the hook is platform-agnostic on the trigger axis.
    *   **`catalog/hooks/tests/test_claude_diff_review.py`** - 11 new pytest tests covering bash syntax (`bash -n`), env-var bypass short-circuit, empty-diff exit, missing-CLI fail-open with warning to stderr, merge-state skip, rebase-state skip, diff-size-cap warning, and PASS / WARN / BLOCK / unparseable verdict parsing. The stub `claude` CLI is a fake bash binary placed on PATH that emits a fixed response; the temp git repo fixture creates a fresh repo with one staged change so the hook has a real diff to inspect. Combined hook test suite: 273 tests passing (262 prior + 11 new).
    *   **Canonical version bump 1.1.1 -> 1.1.2** across the same 13 files as v1.1.1: `.claude-plugin/{plugin,marketplace}.json`, `data/{bundles,marketplace,templates,workflows}.json`, `catalog/hooks/session-start.sh`, `scripts/installer.sh`, `scripts/installer.ps1`, `catalog/skills/README.md`, `guides/SUBAGENTS_GUIDE.md`, `infrastructure/{hooks,tools}/README.md`. Plus `session-start.sh` `COMMAND_COUNT` 32 -> 33 (one new slash command). CHANGELOG migrated from `[Unreleased]` to `[1.1.2] - 2026-05-06`; CHANGELOG footer Unreleased link bumped to `v1.1.2...HEAD`, and a new `[1.1.2]: v1.1.1...v1.1.2` comparison link added.

*   **Design Rationale**: The most important judgment call was **opt-in vs. opt-out**. An opt-out design (auto-install the hook on every DevAI-Hub install) was rejected for three reasons. First, every commit becomes a `claude -p` call (~3-8k input + ~200 output tokens, ~2-10s latency); silently imposing that on every user every commit is too aggressive. Second, the hook may produce false positives on legitimate `# TODO(jane):` markers, dummy test data, and config templates with placeholder values; a user surprised by their first BLOCK on a routine commit will reach for `git commit -n` and lose trust in the safety guarantee permanently. Third, a Claude-CLI-not-installed warning printed on every commit by default is noise. The opt-in design (run `/install-claude-pre-commit-hook` once per repo) makes activation an explicit consent gesture and gives the user one clear place to look ('which repos have this enabled?') rather than a per-machine policy that's hard to audit. The second key call was placing the hook source under `~/.devai-hub/hooks/` rather than `~/.claude/hooks/` (where existing PreToolUse hooks live). The hook is not a Claude Code hook - it's a git hook that happens to call the Claude CLI - and putting it under `~/.claude/` would mislead users into thinking it's wired through the Claude Code hook system. The third call was the verdict format: a strict first-line `VERDICT: PASS|WARN|BLOCK` that the bash hook can grep and `case` on, rather than free-form prose the hook would have to parse. The cost is one extra prompt-engineering instruction; the benefit is a deterministic mapping from LLM output to exit code, with a fail-open default for any unparseable response.

*   **Migration Impact**: NONE for any existing repository. The hook ships to `~/.devai-hub/hooks/` but is never auto-wired into any `.git/hooks/pre-commit` - users opt in per-repo by running the slash command. Existing v1.1.1 installations re-run the installer and pick up one new file (`~/.devai-hub/hooks/claude-diff-review.sh`); no existing files are overwritten, no settings.json schema changes, no permission entries added.

*   **Known Issues / Follow-ups**: The hook depends on Claude Code CLI being on PATH; users on Cursor / Copilot / Codex / Gemini who haven't separately installed Claude Code will get a non-fatal warning on every commit until they install it or set `DEVAI_DIFF_REVIEW_DISABLE=1`. A future minor bump could ship parallel reviewers for other CLIs (e.g. `gh copilot suggest`, `gemini -p`) and select based on which is on PATH. The 50 KB diff cap means very large commits skip review entirely; teams that want full coverage on big commits should either raise the cap (`DEVAI_DIFF_REVIEW_MAX_BYTES=204800`) or move the review to CI rather than pre-commit. The verdict prompt instructs Claude to default-PASS on documentation, lockfiles, and obvious test fixtures, but the LLM's judgment on what counts as "obvious" will produce some false positives until the prompt is tuned against real-world commit data; the WARN verdict (allow with warning) is the intentional escape valve for this. The carryover follow-ups from v1.1.1 (Gemini / Codex / Copilot stale-sentinel bug class in the permission installers; `[System.Environment]::*` family unmatched by `fnmatch`) remain open for a v1.2.0 candidate slate.

*   **Test Posture**: All four quality gates clean. `make validate` (JSON integrity across `data/*.json`) passes. `bash -n` on `claude-diff-review.sh` and `installer.sh` clean. The new test file (`test_claude_diff_review.py`) is 11/11 green; full hook test suite is 273/273 against v1.1.2. The installer-smoke test from v1.1.1 (which now reads the canonical version from `.claude-plugin/plugin.json` at runtime) passes against `1.1.2` without a code change - the resilience fix from the prior release is working as designed. No new tests were authored for the slash command itself because the command body is interpreted by Claude at invocation time and is not under unit test (the same pattern as every other slash command in `catalog/commands/`).

*   **Current Status**: All v1.1.2 surfaces shipped. The annotated `v1.1.2` tag is created locally with the release commit; push to origin happens at user direction.

## [2026-05-06] - Release 1.1.1: Commit-Message No-Hard-Wrap Rule + Smoke-Test Robustness

*   **Goal**: Close two small but recurring papercuts shipped to users in v1.1.0. First, `/generate-commit-message` and the `code-commit-workflow` skill enforced a no-hard-wrap rule on bullet points but said nothing about body paragraphs, so the agent kept producing commit messages with paragraph bodies wrapped at ~72 columns - the user had to correct this manually after every commit. Second, the installer-smoke test hard-coded the canonical version string, so every version bump caused the smoke test to fail until a follow-up commit patched the literal. Patch release; no behavioral or schema changes; no installer-rerun side effects.
*   **What Changed**:
    *   **No-hard-wrap rule extended from bullets to all body content** in `catalog/commands/generate-commit-message.md` and `catalog/skills/workflow/code-commit-workflow/SKILL.md`. Both files now require every paragraph and every bullet point in the commit body and footer to be a single continuous source line, regardless of length. The common wrap columns (50, 72, 80, 100) are called out explicitly so the agent cannot rationalize one of them as "the convention." The subject-line 50-character cap remains the only exception (a hard limit, not a wrap).
    *   **Examples reworked** in `code-commit-workflow/SKILL.md` to match the rule. Three "Good Examples" that previously demonstrated wrapped paragraph bodies were unwrapped; a hard-wrapped "Bad Example" was added so the failure mode appears side-by-side with a Good Example. Two new entries in the Common Rationalizations table rebut the "72-column convention" excuse (modern Git tooling, GitHub, GitLab, IDE diff views, and `git log` all soft-wrap on display; hard-wrapped source breaks copy-paste round-trips into changelogs and review comments) and the "split for readability" excuse (visual readability is the renderer's job; if a bullet is genuinely too long, split it into two distinct bullets, not into a continuation line that breaks the bullet's identity in Markdown and Git UIs). Quality Checklist and Verification gain a no-wrap item with a `git show --no-patch HEAD` spot-check.
    *   **Cross-platform reach without an installer edit**: `catalog/commands/generate-commit-message.md` reaches Claude Code (`commands/`), Gemini / Antigravity (`workflows/`), and Codex (`prompts/`) via the installer's recursive copy of `catalog/commands/`. `catalog/skills/workflow/code-commit-workflow/SKILL.md` reaches all five platforms via the skill index in their respective `base-*.md` instruction files. Cursor / OpenCode / Copilot, which do not get a per-command file copy, still inherit the rule because their `base-*.md` instruction templates already carry the global "Never hard-wrap paragraph text" rule and now point at a skill body whose examples and rebuttals are aligned with that rule.
    *   **Installer-smoke test no longer hard-codes the canonical version string** (`catalog/hooks/tests/test_installer_smoke.py`, committed as `3e80f88` between v1.1.0 and v1.1.1). The test now reads the version from `.claude-plugin/plugin.json` at test time. Future PATCH / MINOR / MAJOR bumps will not require a follow-up commit to keep the smoke test green - the v1.1.1 bump itself is the first to benefit.
    *   **Canonical 14-file version bump** plus the two installer scripts: `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`, `data/bundles.json`, `data/marketplace.json`, `data/templates.json`, `data/workflows.json`, `catalog/hooks/session-start.sh`, `scripts/installer.sh`, `scripts/installer.ps1`, `catalog/skills/README.md`, `guides/SUBAGENTS_GUIDE.md`, `infrastructure/hooks/README.md`, `infrastructure/tools/README.md`, `README.md`, `CHANGELOG.md`, plus this DEVLOG entry. CHANGELOG migrated from `[Unreleased]` to `[1.1.1] - 2026-05-06`; CHANGELOG footer Unreleased link bumped to compare from `v1.1.1...HEAD`, and a new `[1.1.1]: v1.1.0...v1.1.1` comparison link added.
*   **Design Rationale**: The bullet-only scope of the original rule was an oversight, not a deliberate scoping decision. The user's `CLAUDE.md` global already carried "Never hard-wrap paragraph text at a fixed column width" as a communication-style rule, but the more specific commit-message guidance in the command and skill files only mentioned bullets - and agents follow the more specific local rule, so the global was effectively shadowed in commit-message generation. Users who installed v1.1.0 will see the new commit-message behavior the next time they invoke `/generate-commit-message` (the command body is re-read on every invocation). The installer can be re-run if desired but is not required for this release - the v1.1.0 install copy of `~/.devai-hub/skills/code-commit-workflow/SKILL.md` is the only file users would refresh, and only because its body content changed.

## [2026-05-05] - Release 1.1.0: PowerShell Tool Parity + Known-Gaps Tracker

*   **Goal**: Close the description-and-auto-approve UX gap for Claude Code's PowerShell tool, which until this release got no description treatment at all - approval dialogs only showed the truncated start of the script body, leaving the user to click "Details" before they could understand what the agent was about to run. The Bash tool has had this treatment since v0.9.x via `format-bash-description.py` + `require-description.sh`. v1.1.0 ships the PowerShell parallel and bundles in the per-version known-gaps tracker authored earlier in the cycle. Minor bump: changes are additive; existing Bash-only configurations are unaffected.
*   **What Changed**:
    *   **PowerShell description hook pair**: `catalog/hooks/require-powershell-description.sh` (direct port of the Bash twin - blocks calls with no `description` field) and `catalog/hooks/format-powershell-description.py` (~270 lines, slimmer than the Bash twin: no shell-construct/env-var/prefix-cmd unwrapping, conservative single-line allow-list). The format hook prepends a `# ===== Description ===== #` comment block to the script body so the description stays visible in the truncated approval-dialog preview, since Claude Code does not surface the `description` field in the PowerShell approval header today (unlike Bash). Both register under `"matcher": "PowerShell"` in `catalog/hooks/settings.json`.
    *   **PowerShell auto-approve allow-list** (~100 patterns) added to `configs/permissions/claude-permissions.json`: read-only `Get-*`, `Test-*`, `Resolve-*`, `Format-*`, `Select-*`, `Sort-*`, `Group-*`, `Measure-*`, `ConvertFrom-*` / `ConvertTo-*`, `Where-Object` (comparison-statement form only), CIM/WMI getters, network info getters, hashing, and the common aliases (`ls`, `dir`, `cat`, `pwd`, `gci`, `gc`, `gm`, `sls`, ...).
    *   **Conservative-by-default safety model**. A PowerShell command auto-approves only when ALL of these hold: single line (no `\n`), no script-block characters (`{` `}`), no statement separator (`;`), no I/O redirection (`>` `<`), no subexpression (`$(`, `@(`, `@{`), no call operator (`&`), no backtick (`` ` ``) outside single-quoted strings - and `$(` and backticks are also rejected inside double-quoted strings because PowerShell interpolates and escapes there. Multi-line scripts never auto-approve. `ForEach-Object` is intentionally excluded because `ForEach-Object Name` (property access, safe) and `ForEach-Object Delete` (method invocation, destructive) are syntactically indistinguishable.
    *   **Installer wiring**: both `scripts/installer.sh` and `scripts/installer.ps1` extended to copy the two new hook files by explicit name (per the project's "installer copies scripts by explicit name, never by folder" rule) and to merge two new PowerShell PreToolUse entries into existing settings.json. The merge logic checks `require-powershell-description` separately from `require-description` so an upgrade path that already has the Bash hook still picks up the PowerShell pair without skipping. The fresh-install path inherits the new entries automatically from the updated `catalog/hooks/settings.json` template.
    *   **MANDATORY rule extension** in `templates/ai-instructions/base-claude.md`. Codex / Gemini / Cursor / OpenCode templates are unchanged because none of those agents expose a PowerShell-specific tool - the cross-platform consistency rule applies to platform-agnostic behavior, not platform-specific features.
    *   **Test coverage**: new `catalog/hooks/tests/test_format_powershell_description.py` with 80 tests covering the pipeline splitter, quote-aware syntax scanner, allow-list matcher, real-config integration (parametrized over safe and unsafe command samples), description-box rendering, and end-to-end subprocess flow. Combined hook test suite: 261 tests passing.
    *   **Known-gaps tracker** (shipped earlier in the cycle as a separate commit, bundled into v1.1.0): `catalog/skills/workflow/known-gaps-tracker/SKILL.md` plus integrations across `/implement-phase` (Phase 8 step 2), `/wrap-up-session` (Phase 4 Step 4b sweep + Phase 6 Step 6b finalize), and `/generate-plan` (Step 0.6 prior-version known-gaps ingest). Per-version, append-only log at `docs/<version>/known-gaps.md` recording NI / DF / BG / WN / MT / QG items. Files flip from `in-progress` to `finalized` on version bump. The next `/generate-plan` ingests open items and seeds them into the discovery interview.
    *   **Stale-sentinel bug in Claude permission installer (caught during v1.1.0 verification)**: real-session test against the v1.1.0 install showed that the user's `~/.claude/settings.json` had received the new PreToolUse hook entries but had ZERO new `PowerShell(...)` allow patterns despite the catalog template carrying ~100 of them. Root cause: the Claude branch of all three permission installers (`scripts/installer.sh` line 433, `scripts/installer.ps1` line 724, `scripts/Install-DevAI-Permissions.ps1` line 120) used a single hard-coded sentinel string (`Bash(gh pr list)` / `WebFetch(domain:api.github.com)` / `WebFetch(domain:github.com)`) to detect "permissions already installed" and skip the entire merge. Any user who installed v0.9.5+ would have one of these sentinels and would never receive any allow-list entry shipped in later versions. Fix: replaced the binary sentinel with a count-based delta - the installer computes how many of the template entries are not already present, skips the file write entirely when the delta is zero, and writes (with a backup) plus reports `(N new entries)` when the delta is positive. The Gemini / Codex / Copilot branches in the same files have the same bug pattern but do not ship new entries in v1.1.0; tracked as a follow-up rather than fixed in this release.
    *   **PowerShell dialog UI doesn't render `updatedInput.command` like Bash does (caught during v1.1.0 verification)**: third real-session test exposed yet another Bash-vs-PowerShell asymmetry. For Bash, the format hook's `updatedInput.command` (with the `# ===== Description ===== #` comment block prepended) renders directly under the dialog header so the user sees what the command does without expanding any panel. For PowerShell, the same `updatedInput.command` is hidden inside a collapsed "Details" panel - the dialog body shows only the generic "Do you want to proceed with PowerShell?" header. Fix: the hook now also writes the model-supplied description into `permissionDecisionReason`, which Claude Code renders in the dialog body for both tools. Auto-approved commands keep the existing reason text ("All pipeline segments match configured allow patterns") so the audit trail still distinguishes them; non-allow-listed commands carry the description verbatim. Two updated regression tests in `test_format_powershell_description.py` assert this. Full hook test suite is still 262 tests passing.
    *   **Extra read-only automatic-variable patterns added to allow-list (caught during v1.1.0 verification)**: same real-session test showed the model reaching for `$PWD.Path` when asked for a read-only command. The cmdlet equivalent `Get-Location` was in the allow-list and auto-approved; the property-access form `$PWD.Path` was not, so the user got an extra approval dialog they did not expect. Added `$PWD`, `$PWD.Path`, `$PWD.ProviderPath`, `$HOME`, `$PROFILE`, `$PID`, `$Host.Version`, `$Host.Name`, `$Host.UI.RawUI.WindowSize`, `$ExecutionContext.SessionState.Path.CurrentLocation` and the verbose forms of `$PSVersionTable` to `configs/permissions/claude-permissions.json`. Skipped `[System.Environment]::*` family because Python's `fnmatch` treats `[...]` as a character class - the literal `[` in a pattern is interpreted as the start of a set match, so a static pattern can never match these expressions. If we ever need to allow them, we would need to either escape the brackets via fnmatch's `[[]` syntax or move the matcher off `fnmatch`. Tracked as a follow-up.
    *   **PowerShell hook now returns `permissionDecision: "ask"` for non-allow-listed commands (caught during v1.1.0 verification)**: same real-session test exposed a more dangerous bug - even after manually verifying the hook ran (transcript showed `PreToolUse:PowerShell hook_success` events with our exact comment-block JSON), Claude Code was executing destructive commands like `Set-Content -Path "hello.txt" -Value "hello world"` without ever showing the approval dialog. Diagnosis by transcript-replay: when a `PreToolUse:PowerShell` hook returns `updatedInput` without an explicit `permissionDecision`, Claude Code's PowerShell tool treats the absence of a decision as approval and runs the command silently. The Bash tool falls through to a default-ask path in the same scenario; the PowerShell tool does not. Fix: when our hook decides NOT to auto-approve, it now explicitly emits `{"permissionDecision": "ask", "permissionDecisionReason": "PowerShell command not in auto-approve allow-list", "updatedInput": {...}}`. The comment-block envelope is still rendered into the script body so the description stays visible in the truncated approval-dialog preview, but the `"ask"` decision forces Claude Code to gate execution on user approval. New regression test in `test_format_powershell_description.py` asserts the `ask` decision is set for any non-allow-listed command; another test asserts the same when the description is already pre-formatted. Full hook test suite is now 262 tests passing.
    *   **Post-install restart reminder** in both `scripts/installer.sh` and `scripts/installer.ps1`. Surfaced after a real test caught the trap: the developer ran the installer, saw the "Installation Complete" banner, but the new PowerShell hook still didn't fire in their already-running Claude Code session. Diagnosis: hook files were copied byte-identical, settings.json was correctly merged with the new PowerShell PreToolUse entries, but Claude Code reads settings.json at session start and does not hot-reload it (upstream blocker tracked at `anthropics/claude-code#17127`). Fix is documentation-only on the catalog side - the installer's "Installation Complete" path now prints a yellow notice telling the user to restart any running Claude Code / Cursor / Gemini / Codex / Copilot sessions. Same notice mirrored in the v1.1.0 CHANGELOG and README "What's New" upgrade-note callout. This same blocker was previously hit during v0.9.7 Phase 5 (effort-level hot-reload) and remained in memory; v1.1.0 makes the limitation visible at install time so future users do not lose 10 minutes diagnosing what looks like a hook bug but is actually a session-cache issue.
*   **Design Rationale**: The single most important judgment call in this release was the conservative-by-default allow-list scope. PowerShell's universal script-block syntax (`{ ... }`) means `Where-Object {$_.Foo -eq 'x'}` (filter, safe) and `ForEach-Object { Remove-Item $_ }` (destructive) look syntactically identical at the regex level. Rather than write a full PowerShell parser into the format hook, the rule blocks ANY `{` outside single-quoted strings and accepts that `Where-Object` and friends only work in their modern comparison-statement form (`Where-Object Name -eq foo`). Same for `ForEach-Object`: rather than try to distinguish property access from method invocation, the cmdlet is excluded from the allow-list entirely. The cost is that some legitimate read-only patterns require manual approval; the benefit is that the safety model is provably correct without parsing PowerShell. The Bash twin's complexity (~860 lines handling shell constructs, env-var prefixes, command unwrapping, output-redirect detection, `bash -c` extraction) was deliberately not ported - the PowerShell hook is one-third the length and a fraction of the surface area for bugs. The 14-file canonical version-bump surface from v0.9.7 / v1.0.0 is reused; no new bump targets needed.
*   **Migration Impact**: NONE for users who only use the Bash tool - the PowerShell hooks are gated by the `"matcher": "PowerShell"` in settings.json. Users who already have the Bash description hooks installed will pick up the PowerShell pair on the next installer run. Users who don't run the installer keep the v1.0.0 behavior (PowerShell calls land in approval dialogs without a description) until they install. No breaking changes; no API changes; no destructive operations.
*   **Known Issues / Follow-ups**: The format hook only auto-approves single-line PowerShell commands. Multi-line scripts always require manual approval, even when every line is read-only. This is a deliberate scope choice for v1.1.0; a more sophisticated multi-line analyzer (or a "trusted multi-line script template" allow-list) could land in a future release if usage telemetry shows it would meaningfully reduce friction. `ForEach-Object` is also outside the allow-list pending a clean way to distinguish its property-access form from its method-invocation form without parsing PowerShell. The Gemini / Codex / Copilot branches of the permission installers (`scripts/installer.sh`, `scripts/installer.ps1`, `scripts/Install-DevAI-Permissions.ps1`) carry the same stale-sentinel bug class as the Claude branch fixed in v1.1.0; not fixed in this release because those branches do not ship new entries in v1.1.0, but tracked as a follow-up. The `[System.Environment]::*` family of read-only patterns can never be added via `fnmatch` because Python interprets `[...]` as a character class - if those patterns ever become important, the matcher would need either fnmatch's `[[]` literal-bracket escape or a different matching engine.

    **Claude Code upstream rendering inconsistency (acknowledged limitation):** the PowerShell approval dialog renders an empty body when a `PreToolUse` hook returns `permissionDecision: "ask"`, while the Bash dialog renders the hook-prepended comment block under the header. Three output surfaces tested (`updatedInput.command`, `updatedInput.description`, `permissionDecisionReason`) - none reach the PowerShell dialog body.
