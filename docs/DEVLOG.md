## [2026-05-06] - Release 1.1.5: Sectioned-Bullet Structure for Commit Messages

*   **Goal**: Close the structural gap that v1.1.1 / v1.1.4 didn't address. v1.1.1 forbade hard-wrapping inside paragraphs and bullets; v1.1.4 propagated that rule into the downstream commands that actually generate commit messages (`/implement-phase`, `/wrap-up-session`, `/update-version`). But neither release said anything about *body structure* - the agent could still produce a body of 5-6 long flowing paragraphs separated by blank lines, which forces reviewers to read every paragraph linearly to find the change for a specific component. Reported live: a v1.1.4-generated commit (the next `/implement-phase` run after the v1.1.4 install) came out exactly that shape - properly unwrapped paragraphs but six of them in a row, no labeled sections, no scannable anchors. Patch release because the change is content-only across five command and skill files (no schema, no installer, no test changes).

*   **What Changed**:
    *   **`catalog/commands/generate-commit-message.md` body rules + example replaced.** Adds a "Body structure (CRITICAL for non-trivial commits)" rule requiring labeled sections with bullets (headers ending in a colon, grouped by component / module / theme). The 1-2 sentence intro paragraph + sectioned-bullet body shape replaces the prior "paragraphs and/or bullet points" guidance. Always treats **Tests** and **Known gaps** / **Deviations** as dedicated final sections. Whitespace constraint added: exactly one blank line between sections; bullets contiguous within a section. The example block was rewritten to demonstrate the sectioned style on a realistic multi-component commit (Reporting package / Packaging and paths / Desktop UI / Tests / Known gaps - patterned after the user-supplied "after" example). A counter-example block was added showing the multi-paragraph flowing-prose body shape that the agent must NOT produce, even with the no-hard-wrap rule honored.
    *   **`catalog/skills/workflow/code-commit-workflow/SKILL.md` Body subsection + Examples + Rationalizations + Checklist all extended.** New rule paragraph in the Body subsection mirrors the canonical command. New Good Example added at the end of the Good Examples section showing the sectioned style on the same Phase 6 docxtpl scenario (paralleling the user-supplied "after" example). New Bad Example showing the multi-paragraph flowing-prose body shape. New Common Rationalizations row rebutting "flowing paragraphs read better than bulleted lists for prose-heavy commits" - the agent's likely failure mode given its training on academic prose conventions. Quality Checklist gains a sectioned-structure item explicitly naming the Tests and Known gaps / Deviations sections.
    *   **`catalog/commands/implement-phase.md` post-phase sub-step 6 inline rule expanded.** Adds the sectioned-bullet rule with implementation-specific suggested headers. *   **Design Rationale**: Most important call was **how strictly to enforce the sectioned style**. Three options: (1) require sectioned-bullet structure for *every* commit body, including trivial 1-2 file commits where it's overkill; (2) require it only for "non-trivial" commits with no clear definition; (3) define the threshold explicitly as "any commit touching multiple components." Option 3 - the choice this release makes - has a clear rule the agent can apply (count the distinct components in the diff; if > 1, use sectioned style). The same rule now appears in all five files with identical wording, so a future regression in any one is detectable by diffing against the others. The second key call was **what counts as a section header**. The user's example used `Reporting package (`src/reporting/`):` style (component path in backticks, then a colon) which works well for code-component commits. For wrap-up commits, headers are activity-typed (`DEVLOG:`, `Documentation:`); for release commits, they map directly to CHANGELOG section names (`Added:`, `Changed:`, `Fixed:`). The release deliberately gives different suggested header palettes per command so the agent has a context-appropriate starting point rather than a generic "use sections" instruction it has to invent headers for. The third call was **rejecting an enforcement test** - a static check that scans command bodies for "generate" + "commit message" without a sectioned-style rule could prevent regressions but adds maintenance burden and false positives. Tracked as a v1.2.0+ candidate; for now, the cross-file consistency of the rule wording IS the regression signal.
